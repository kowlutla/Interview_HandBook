Chapter 59 · Module 9 · Data structures for ranking and collaboration

Sorted Sets, Top-K, CRDTs and OT

This chapter covers two families of ideas that appear again and again in system design interviews. The first is keeping data in sorted order and answering "who are the top K?" cheaply, from skip lists and heaps to leaderboards and streaming heavy hitters. The second is letting many people edit the same data at once without a central lock, using operational transformation (OT) and conflict-free replicated data types (CRDTs).

1. Why these structures matter

Many product features boil down to one of two questions. The first: "show me the best N things right now." This is a game leaderboard, a "trending hashtags" list, the "top 10 most viewed videos this hour", a list of the heaviest-traffic IP addresses during an attack. The second: "two people changed the same thing at the same time; what should the result be?" This is a shared document, a shared shopping cart, a counter that is incremented in two data centers at once, a note that was edited on a phone while offline.

These look unrelated, but both are about maintaining a useful summary of a changing collection without scanning all of it, and without a single point that every update must pass through. For ranking, the trick is an ordered structure so that insertion, deletion and "give me the top K" are all fast. For collaboration, the trick is giving operations or data a mathematical shape (commutative, associative, idempotent) so that replicas converge regardless of the order in which updates arrive.

The chapter is organized in two halves. Sections 2 to 9 are about ordered data and top-K. Sections 10 to 18 are about collaborative editing and conflict-free data. The case study Design a Collaborative Editor applies the second half end to end; this chapter provides the machinery.

2. Ordered structures: balanced trees recap

A sorted set is a collection of unique members, each with a numeric score, that can be read back in score order. The operations we want are: add or update a member's score, remove a member, find a member's score, get the rank of a member (its position in sorted order), and read a range by rank or by score. A plain array kept sorted gives fast reads but O(n) inserts, because everything after the insertion point must shift. A hash map gives O(1) lookup by member but no order. We need both at once.

2.1 Binary search trees and why balance matters

A binary search tree (BST) stores one key per node, with every key in the left subtree smaller than the node and every key in the right subtree larger. Searching walks from the root, going left or right at each node, so the cost is the height of the tree. If keys arrive in random order, the height is about log2 n and everything is O(log n). But if keys arrive already sorted (1, 2, 3, 4, ...), a naive BST degenerates into a linked list of height n, and every operation becomes O(n).

Self-balancing trees prevent this by rearranging nodes (rotations) after inserts and deletes so the height stays O(log n) in the worst case. Common variants:

  • AVL tree: keeps the heights of two child subtrees within 1 of each other. Strictly balanced, so lookups are slightly faster, but inserts need more rotations.
  • Red-black tree: colors nodes red or black with rules that keep the longest path at most twice the shortest. Looser balance, fewer rotations on writes. This is what many standard libraries use for ordered maps (for example Java's TreeMap and C++ std::map are typically red-black trees).
  • B-tree and B+ tree: each node holds many keys (a whole disk page), giving a very wide, very shallow tree. This is what database indexes use (see Chapter 18 and Chapter 19), because on disk the cost that matters is the number of pages read, not comparisons.

To support rank queries ("what is the position of this member?") a balanced tree can be augmented: each node also stores the size of its subtree. Rank is then computed on the way down by summing the sizes of the left subtrees you skip. This gives O(log n) rank and O(log n) "find the k-th element". Augmentation is the same idea Redis uses with skip lists, as we will see next.

2.2 The weakness of balanced trees

Balanced trees are correct and fast, but they are awkward in two ways. First, rebalancing is intricate code: rotations change several pointers at once, and getting a delete wrong in a red-black tree is a classic source of bugs. Second, rebalancing touches nodes near the root, which makes concurrent updates hard: a rotation near the root conflicts with nearly every other operation, so a concurrent tree typically needs coarse locking. These two weaknesses are the main reasons for the structure in the next section.

3. The skip list

A skip list, invented by William Pugh in 1990, gets the same expected O(log n) behavior as a balanced tree using only linked lists and a coin flip. The idea starts from a sorted linked list. Searching a sorted linked list is O(n) because you must walk one node at a time. What if some nodes had "express lanes" that skip ahead?

3.1 Levels and random promotion

Imagine a bottom-level (level 0) linked list that contains every element in sorted order. Build a second list above it containing roughly half of the elements, a third list containing roughly a quarter, and so on. Each element that appears in a higher list is linked to its own copy below. A search starts at the top-left, moves right along the sparse top list as long as the next key is not past the target, then drops down a level and repeats. The upper levels let you skip large stretches; the lower levels give precision.

How do we decide which elements appear in higher levels? Randomly. When inserting a new element, flip a coin repeatedly: the element is always in level 0; with probability p (commonly 1/2, and Redis uses 1/4) it is also promoted to level 1; with probability p again from level 1 to level 2, and so on, up to a maximum level cap (Redis uses 32). The number of levels an element occupies is its height. The expected number of elements at level i is n times pi, which is exactly the halving pattern we wanted, with no rebalancing code at all.

3.2 Search, insert and delete walkthrough

Search for key 70. Start at the head node on the highest level. Look at the next node on this level. If its key is less than or equal to 70, move to it; otherwise drop down one level while staying on the current node. In the figure, the head on level 3 points to 30, and 30 is below 70, so we move there. The next node on level 3 does not exist (or is beyond 70), so we drop to level 2 at node 30, move right to 40, then see that the next level-2 node is 90, which overshoots, so we drop to level 1. On level 1 we move from 40 through 60 to 70. We are at 70 and can stop (or drop to level 0 to read the node's data). The total work is the number of right moves plus the number of drops.

Insert key 55. First run a search for 55, but remember, on every level, the last node visited before dropping. These are the predecessors of the new node at each level. Then flip coins to choose the new node's height, say 2 (levels 0 and 1). Splice the new node into level 0 and level 1 by pointing the predecessors' next pointers at it and its own next pointers at what used to follow them. Nothing else in the structure moves. There are no rotations and no global rebalancing.

Delete key 40. Search for it, again recording predecessors on each level, then unlink the node from every level it appears in. Again only local pointers change.

3.3 Why it is O(log n) on average

The analysis is easiest to see backwards. Trace the search path in reverse, from the found node up to the head. At each step you either went "up" (the node you are on is also present at a higher level, which happens with probability p) or "left" (it is not). So the reversed path is a sequence of coin flips; you climb a level on each success. To climb all the way to the top level (about log1/p n levels) you expect about (log1/p n) / p steps in total. That is O(log n) expected, with a small constant. The worst case is O(n), but it requires an astronomically unlikely sequence of coin flips; with n of a million, the probability of significantly exceeding the expected time is negligible. This is a probabilistic guarantee, not a deterministic one, which is the one trade you make in exchange for simplicity.

The expected space is n / (1 - p) pointers, so about 2n with p = 1/2 and about 1.33n with p = 1/4. A lower p means fewer pointers and slightly more steps per search; this is why Redis chose 1/4.

3.4 Rank queries in a skip list

To support rank, each forward pointer stores a span: the number of level-0 nodes it skips. While searching, add up the spans of every pointer you follow; the sum on arrival is the node's rank. To fetch the element at rank r, walk the same way but move right whenever accumulated span plus the next span does not exceed r. This gives O(log n) rank and O(log n) range-by-rank, exactly the same as an augmented balanced tree.

3.5 Why Redis uses a skip list for sorted sets

Redis sorted sets (ZSETs, see Chapter 15) pair a skip list with a hash table. The hash table maps member to score, giving O(1) ZSCORE. The skip list orders the (score, member) pairs, giving O(log n) ZADD, ZREM, ZRANK and range reads. Small ZSETs use a compact listpack encoding (a contiguous array) instead, switching to skip list plus hash when they grow. Redis's own author gave these reasons for choosing a skip list over a balanced tree:

  • Simplicity. A skip list is easy to write, debug and modify; adding spans for rank took little code.
  • Range operations are natural. Once the first element of a range is found, the rest is a plain walk along the level-0 list. Redis's level-0 list is also doubly linked, so ZREVRANGE walks backwards just as cheaply.
  • Memory flexibility. The promotion probability is a tunable knob that trades memory for speed.
  • Performance comparable to balanced trees. In practice, similar speed with less implementation risk.

Redis is single-threaded for command execution, so concurrency is not the reason there. It matters for other systems, as described next.

3.6 Skip lists versus balanced trees for concurrency

The biggest practical advantage of skip lists in multi-threaded programs is that updates are local. Inserting or deleting touches only the few predecessor nodes at the levels where the element lives. There is no rotation near the root that invalidates other threads' work. This makes lock-free or fine-grained-locking implementations feasible. Java's ConcurrentSkipListMap is the well-known example; LevelDB and RocksDB use a skip list for their in-memory write buffer (the memtable), where many readers run alongside a writer. Concurrent balanced trees exist but are far harder to implement correctly.

4. Heaps and priority queues

A priority queue is an abstract data type: you can insert an item with a priority, and you can always extract the item with the highest (or lowest) priority. A binary heap is the standard implementation. It is a complete binary tree, stored compactly in an array, with the heap property: in a min-heap, every parent is smaller than or equal to its children, so the smallest element is always at the root.

Array layout: for the node at index i (starting at 0), its children are at 2i+1 and 2i+2 and its parent is at (i-1)/2 rounded down. To insert, append the element at the end and sift up, swapping with its parent while it is smaller than the parent. To extract the minimum, take the root, move the last element to the root, and sift down, swapping with the smaller child until the property holds. Both operations cost O(log n); peeking at the minimum costs O(1); building a heap from n items in one pass (heapify) costs O(n).

The heap is the right tool when you only ever need the extreme element: schedulers picking the next job by deadline, Dijkstra's shortest path, merging K sorted lists, and the top-K algorithm in the next section. It is the wrong tool when you need rank, arbitrary range scans, or fast lookup by key, where the sorted set above wins. Heaps are also memory-compact and cache-friendly because they are plain arrays, which is why a heap of 1,000 items inside a streaming operator is cheap.

The heap is also what powers timers and delay queues: a min-heap keyed on fire time lets a scheduler sleep until the earliest deadline. See Chapter 38 for scheduling designs that build on this.

5. Leaderboards

A leaderboard ranks players (or users, products, posts) by a score and answers queries such as "who are the top 100?", "what is my rank?", "who is just above and below me?". It is the textbook use of a sorted set.

5.1 Redis ZSET operations

A single Redis sorted set key (for example lb:global) holds member to score. The operations that matter:

Ties need a rule. Redis orders equal scores lexicographically by member name. If you want "earlier achiever ranks higher", encode the tie-breaker into the score, for example score * 2k plus an inverted timestamp, as long as the result stays within the 53 bits of integer precision of a double.

For a single board of 10 million players, one Redis node holds the structure in a few hundred megabytes (tens of bytes per member plus pointers), handles tens of thousands of updates per second, and answers any rank query in microseconds. That is why most leaderboard designs start, and often end, with one sorted set plus a replica for reads and persistence for durability (see Chapter 15).

5.2 Sharded leaderboards and merging

When one node is not enough, either because of write rate, memory or because the board is naturally partitioned, you shard. There are two ways, and they have very different consequences.

Shard by player (hash of player id decides the shard). Writes spread evenly. But the top 100 now lives in pieces across every shard, and a global rank requires knowing how many players on every shard have a higher score. The top-K query becomes scatter-gather: ask each shard for its own top 100, then merge the S sorted lists, taking the largest 100 overall (a K-way merge with a heap, O(S * K log S)). This is exact, because the global top 100 must be contained in the union of per-shard top 100s. Global rank of a player is computed as the sum over shards of the count of members with a higher score (ZCOUNT shard (score +inf), which is S parallel O(log n) calls.

Shard by score range (shard 1 holds scores 0-999, shard 2 holds 1000-1999, ...). The top K comes from the one or two highest shards, and a rank is "all players in higher shards plus rank within my shard", where the higher-shard counts are cheap cached numbers. But score distributions are skewed and shift over time, so ranges need rebalancing, and a hot score range (everyone clustered around the average) overloads one node. Moving a player when their score crosses a boundary is a cross-shard transaction. Range sharding suits scores that change slowly and distribution that is known; hash sharding is the safe default.

5.3 Approximate rank for huge boards

Consider a game with 500 million players. Showing the exact top 100 is easy. Showing every player their exact rank ("you are number 183,442,901") is expensive, and few players care about the exact digits. Options:

  • Score histogram. Maintain bucket counts per score range (for example 10,000 buckets). A player's approximate rank is the sum of the counts of all higher buckets plus a fraction of their own bucket by linear interpolation. Updates are two counter changes (decrement old bucket, increment new). Error is bounded by one bucket's population. This gives "top 3%" style answers cheaply, and the histogram is tiny and trivially mergeable across shards by adding counts.
  • Sampling. Keep a random sample (say 1 in 1,000 players) in the sorted set; rank is the sample rank times 1,000. Cheap and unbiased with a quantifiable error.
  • Quantile sketches such as t-digest or the GK algorithm give a percentile of a score with a bounded error from very small memory and merge across shards. See Chapter 57 for the family of probabilistic structures.
  • Exact for the top, approximate for the rest. Keep an exact sorted set for the top 10,000 (where players look at the exact position) and show percentile bands below that. This matches how people actually use leaderboards.

5.4 Time-windowed boards

"Daily", "weekly" and "all-time" leaderboards are common. The simplest approach is one sorted set per window, with the window in the key (lb:2026-11-17, lb:2026-W47). Every score event does a ZINCRBY on each active window key. Old keys are deleted with EXPIRE after the window ends (plus a grace period for display). To produce "last 7 days" from daily boards, use ZUNIONSTORE with sum aggregation across seven daily keys into a temporary key, cached for a minute. This is O(total members) so do it on a schedule, not per request. For a true rolling window with exact expiry, you would need to subtract old events; most products accept bucketed windows (hourly or daily buckets) because the cost and complexity are far lower.

Watch out A leaderboard read must not become a hot key. If millions of clients refresh "top 100" every second, cache the result in application memory or a CDN for one to five seconds (Chapter 13). Only each player's own rank query needs to be fresh, and even that can lag a few seconds.

6. Top-K

The top-K problem is: from a collection of items (or a stream of events) find the K items with the largest value, where the value is either given (scores) or is the frequency of occurrence (most-viewed, most-searched). Frequency-based top-K is the harder and more commonly asked variant.

6.1 Exact top-K with a heap

For a fixed collection of n scored items, keep a min-heap of size K. For each item: if the heap has fewer than K items, push it. Otherwise compare it to the heap's minimum (the root); if the new item is larger, pop the root and push the new one; if not, discard it. After one pass the heap holds exactly the K largest items. The cost is O(n log K) time and O(K) memory, much better than sorting everything (O(n log n)) when K is small. Using a min-heap for the largest items is the non-obvious part: the root is the weakest of the current winners, which is exactly the one a challenger must beat.

An alternative is quickselect (partition-based selection), O(n) average, but it needs all the data in memory and is not streaming.

For frequency top-K the situation is harder: you need a count per distinct item, via a hash map from item to count. With 100 million distinct search queries, the hash map itself is the memory problem. Keeping exact counts for an unbounded stream means O(distinct items) memory, which is why streaming approximations exist.

6.2 Streaming top-K and heavy hitters

A heavy hitter is an item whose frequency exceeds a threshold, such as more than 1% of all events. Finding the top K most frequent items in a stream, using memory far smaller than the number of distinct items and a single pass, is the heavy-hitters problem. Three classic approaches:

Count-Min Sketch plus a heap

A Count-Min Sketch (CMS, see Chapter 57) is a table of d rows and w columns of counters with d independent hash functions. To count an event, hash the item with each of the d functions and increment one counter in each row. To estimate an item's count, take the minimum of its d counters. Collisions only ever inflate counters, so the estimate is never below the true count, and with width w about e/ε and depth d about ln(1/δ), the overestimate is at most ε times the total number of events with probability at least 1 - δ. The sketch uses fixed memory (for example 2,000 by 5 counters, about 40 KB) no matter how many distinct items appear.

But the sketch alone cannot list the top items, because it does not store the items themselves. The standard pattern pairs it with a small min-heap of size K (plus a set of members). For each arriving event: update the sketch, get the new estimated count, and if the item is in the heap, update its entry; otherwise if the estimate exceeds the heap's smallest estimate, replace that entry. At any time the heap holds the current candidate top K with approximate counts. Memory is the sketch plus K entries.

Misra-Gries and Space-Saving (counter-based)

Misra-Gries keeps at most k-1 counters. When an item arrives: if it already has a counter, increment it; else if there is a free counter, start it at 1; else decrement all counters by 1 (removing any that reach zero) and drop the new item. Every item whose true frequency exceeds n/k is guaranteed to still have a counter at the end, and each counter underestimates the truth by at most n/k. Intuitively, a decrement step cancels k distinct items at once, so an item that is truly frequent cannot be fully cancelled out.

Space-Saving (Metwally et al.) also keeps k counters but handles overflow differently: when a new item arrives and all counters are in use, it replaces the item with the smallest count, giving the newcomer that smallest count plus one (and remembering the old count as the possible error). Estimates are therefore overestimates, with a known error bound per item, and the algorithm is usually the best in practice for top-K because the counters always concentrate on the genuinely frequent items. Implementations store counters in a structure that finds the minimum in O(1), commonly a "stream-summary" linked list of count buckets.

6.3 Distributed top-K: per-shard top-K then merge

When the stream is too large for one machine, partition it and compute locally, then combine. The approach depends on how the data is partitioned, and this is where correctness limits appear.

  • Partitioned by item (key). All events for the same item go to the same shard (for example hash of the item). Every shard's counts are therefore complete for its items. Each shard computes its exact or sketch-based top K, and the merger takes the K largest from the union. This is exactly correct (up to sketch error), because the global top K must be in some shard's local top K.
  • Partitioned arbitrarily (round robin, by user). Events for the same item are scattered, so the item's count is split across shards. Now a globally popular item might be only fifth on each shard and miss every shard's local top K. Merging local top-Ks then gives wrong results. An item with 1,000 events split 250/250/250/250 can lose to items with 300 events concentrated in one shard.

Fixes for the arbitrary-partition case: (a) re-partition by item first (a shuffle, the standard first step in a MapReduce or Flink job, see Chapter 37), then compute top-K per partition; (b) have each shard report more than K (top K times a safety factor), then fetch the missing counts for the candidates from all shards in a second round (the classic TPUT-style algorithm); (c) use mergeable summaries (Count-Min Sketches add cell by cell, Space-Saving and Misra-Gries summaries have defined merge procedures), so each shard sends a small summary and a coordinator merges them with a bounded error.

A two-level aggregation also helps with hot keys (one item so popular that its shard is overloaded): pre-aggregate counts locally in a short window (for example one second) before sending to the item's owner, reducing messages by orders of magnitude.

6.4 Time windows

Most real top-K questions are windowed: "top 10 searches in the last hour". The stream-processing vocabulary (Chapter 37) applies directly:

  • Tumbling window: fixed, non-overlapping slots (every hour on the hour). Compute top-K per slot; emit when the slot closes, using a watermark to decide when late events no longer arrive.
  • Sliding (hopping) window: a window of length L that advances by a smaller step s (the last hour, updated every minute). Implement it by keeping per-step partial summaries (one sketch per minute) and combining the last L/s of them. Because sketches add, combining 60 one-minute sketches gives the hourly sketch; expiry is dropping the oldest minute. This beats re-reading the raw events.
  • Decay: instead of a hard window, multiply old counts by a decay factor (for example half-life of an hour) so recent events weigh more. This needs only one set of counters and gives a smooth "recent popularity".

7. Trending detection and sliding-window counters

"Most popular" and "trending" are different. A word like "the" or a permanently popular hashtag is always top-K by raw count, but it is not trending. Trending means unusual growth compared with the item's own normal level. Practical approaches:

  • Ratio of recent to baseline. Compute the count in the current window (last 10 minutes) divided by the average count in the same slot over previous days or weeks. A topic with usual count 50 now at 500 scores 10; a permanently huge topic going from 1,000,000 to 1,100,000 scores 1.1. Add a minimum absolute count and smoothing (for example add a constant to both numerator and denominator) so tiny items with 1 event versus 0 do not produce infinite ratios.
  • Z-score or burst detection. Compare the current count to the mean and standard deviation of history; flag items several deviations above.
  • Velocity and acceleration. Compare consecutive windows: items whose rate of change is high are trending.
  • Diversity filter. Require that the burst is spread over many distinct users, not one account posting a topic a million times, to resist spam and bots (a HyperLogLog distinct-user count per topic works well, see Chapter 57).

8. Merkle tree recap

A Merkle tree is a hash tree: every leaf is the hash of a block of data, and every internal node is the hash of its children's hashes, so the root hash summarizes the whole data set. Two replicas holding the same data have the same root. If the roots differ, compare the children: descend only into subtrees whose hashes differ. After O(log n) comparisons you find exactly which blocks are different and transfer only those. This is why they appear in anti-entropy repair in Dynamo-style stores such as Cassandra and Riak (see Chapter 33 for the full treatment), in Git and blockchains (content integrity), and in file-sync tools.

It belongs in this chapter for one reason: it is the cheap way to prove two replicas converged. CRDTs and OT promise that replicas end up in the same state; comparing a few root hashes is how a system verifies the promise cheaply instead of comparing whole documents, and how it finds a replica that has diverged because of a bug or lost update. Merkle trees do not resolve conflicts, only detect them; they pair naturally with the merge rules we cover next.

9. Why concurrent edits conflict

Switch topic to collaboration. Suppose a shared document contains the text CAT. Alice and Bob both have this version open. At the same moment, Alice inserts "H" at position 1 (making CHAT) and Bob deletes the character at position 2 (the "T", making CA). Each applies their own change instantly (collaborative tools must feel instant, so we cannot wait for a server round trip before showing the keystroke). Then each sends their change to the other.

If Bob's replica naively applies "insert H at 1" to CA, it gets CHA, which is right. But if Alice's replica applies "delete at 2" to CHAT, it deletes the "A" (now at index 2) and ends with CHT. The replicas now disagree (CHA versus CHT) and neither is what Bob intended. The problem is that positions are relative to a document version, and when concurrent operations arrive, the version they were created against is no longer the current version.

Approaches to avoid this:

  • Locking (only one editor at a time, or per-paragraph locks). Simple but destroys the real-time experience and fails offline.
  • Last-writer-wins on the whole document. One person's work is silently lost. Unacceptable for text.
  • Operational transformation (OT): keep position-based operations, but rewrite an incoming operation to account for the concurrent operations already applied. Section 10.
  • CRDTs: change the data model so that operations do not depend on positions at all: every character has a unique, stable identity, and operations refer to identities. Concurrent operations then commute by construction. Sections 11 to 14.

The goal in all cases is a property usually called convergence (every replica ends up in the same state once it has seen the same set of operations), plus intention preservation (the result matches what each user meant, for example Bob's delete still deletes the "T" he saw, not whatever now sits at index 2).

10. Operational transformation (OT)

OT is the technique behind Google Docs (and its ancestors Jupiter, Google Wave and EtherPad-style editors). Every edit is expressed as an operation, for example insert(pos, char) or delete(pos). When two operations were generated concurrently against the same document state, one of them must be transformed against the other before being applied, so that its position is adjusted for the effect of the other.

10.1 The transform function

Define transform(a, b) as: given two operations a and b that were both created against the same document state, return a' which is a rewritten to apply after b has been applied, preserving a's intention. The desired property for convergence (called TP1) is:

apply(apply(S, a), transform(b, a))  ==  apply(apply(S, b), transform(a, b))

In words: applying a then the transformed b, ends in the same state as applying b then the transformed a. Think of a diamond: both paths from the starting state S reach the same final state.

For the two text operations, the rules for transforming an insert (position p1, char c) against another insert (position p2) are:

  • If p1 < p2, the other insert is to the right of mine and does not affect me: keep p1.
  • If p1 > p2, the other insert shifted my target right by one: use p1 + 1.
  • If p1 == p2, both want the same slot. We need a deterministic tiebreak (for example by client or site id, lower id goes first) so both sites choose the same order, otherwise they diverge.

Against a delete at position d: if p1 <= d keep p1 (inserting before the deleted char is unaffected), else use p1 - 1. Transforming a delete against an insert or another delete follows the mirror-image logic, with the extra case that two concurrent deletes of the same character must collapse so that the second becomes a no-op (otherwise a neighboring character gets deleted by mistake).

10.2 Server-ordered OT (the practical design)

General peer-to-peer OT, where any client can talk to any other, requires transform functions satisfying a second property (TP2) about three-way concurrency, and TP2 is notoriously hard to get right; many published algorithms were later found to have counterexamples. The approach used in practice (Jupiter, Google Wave, Google Docs, ShareDB) avoids it by putting a central server in the loop that imposes a single total order on operations.

Each client tracks the server revision number it is based on. The protocol:

  1. The client applies its own edit locally at once and sends (op, baseRevision) to the server. It may have only one operation in flight at a time; further local edits are composed into a buffer and sent after the acknowledgment.
  2. The server receives the op. If its baseRevision is older than the server's current revision, it transforms the incoming op against every operation the server has applied since that revision (in order), then applies it, appends it to the history and increments the revision.
  3. The server broadcasts the (transformed) op to all other clients and acknowledges the sender.
  4. Each client, on receiving a remote op, transforms it against its own pending (in-flight and buffered) operations before applying it to the local document, and transforms its pending operations against it as well.

Because the server defines a single order and each client has just one linear history to reconcile with, only the two-party property TP1 is needed, which is far easier to guarantee. The cost is a central component: the server is a serialization point per document (one document lives on one server shard, which is fine, as documents are independent) and it needs a durable operation log.

10.3 Worked example: two concurrent inserts

The document is ac at server revision 5. Alice wants to insert "b" at index 1 (giving abc); Bob wants to insert "d" at index 2 (giving acd). Both ops are based on revision 5 and both are sent simultaneously.

StepEventServer doc and revisionAlice's docBob's doc

Had the two inserts targeted exactly the same index, the tiebreak (for example the server's arrival order, or client id) would decide, but all participants would apply the same decision.

10.4 Inclusion transformation and exclusion transformation

In the OT literature, inclusion transformation (IT) is the forward transform used above: rewrite operation a so that it includes the effect of b, allowing it to apply after b. Exclusion transformation (ET) is the opposite: rewrite a so that it excludes b's effect, as if b had not happened. ET is needed in peer-to-peer designs (for example the GOT/GOTO family) to undo the effect of operations in the history before re-including them in the correct order; it is also what makes undo/redo in a collaborative editor work, since to undo your own operation you must transform its inverse over everything others have done since. Server-ordered designs rarely need ET for ordinary sync, but need an equivalent for undo.

10.5 Google Docs style, complexity and pitfalls

A Google Docs-style system carries richer operations than insert and delete: retain (skip N characters), insert string, delete N characters, and attribute changes (bold, link) over ranges, usually bundled as a list "retain 5, insert 'abc', retain 3, delete 2" covering the entire document length (the representation used in ShareDB's rich-text type and the Quill Delta format). Operations in this form can be composed (merge two sequential ops into one) and transformed against another list in a single linear walk, so transform cost is O(length of ops) rather than the document size. Structured content (tables, lists, comments) uses tree-shaped OT, which is substantially harder.

Complexity. The server transforms each incoming op against up to d concurrent ops (those committed since the client's base revision), so cost per op is O(d) transform calls, each linear in op length. With high latency or many editors, d grows. The number of distinct transform-function pairs grows as the square of operation types (every type must be transformed against every other), so adding an operation type is expensive in testing effort.

Correctness pitfalls:

  • Failing TP1 or TP2 in rare operation combinations produces silent divergence; such bugs are found only through randomized testing and fuzzing (the standard defense is a fuzzer that runs thousands of random concurrent operation sequences and asserts all replicas converge).
  • Tiebreaking must be deterministic and symmetrical on all sites.
  • Concurrent delete of the same range needs the collapse rule; delete versus insert inside the deleted range needs a defined outcome (usually the insert survives, placed at the deletion point).
  • Client buffering bugs (more than one op in flight, or transforming against the wrong pending list) break the server's assumption about the base revision.
  • The server's operation history must be kept long enough that slow or offline clients can still be transformed against it; long offline sessions become expensive, which is one reason OT handles offline editing poorly.
  • Undo semantics: "undo my last change" must not undo someone else's text, which requires the transform of an inverse operation as noted above.

11. CRDTs: the idea

A Conflict-free Replicated Data Type (CRDT) is a data structure designed so that replicas can be updated independently and concurrently, without coordination, and are guaranteed to converge once they have exchanged their updates, whatever the order of delivery. There is no central transformer or server needed for correctness. Each replica applies its own updates locally and immediately (so reads and writes are always available, even offline) and merges what it receives from others.

11.1 State-based versus operation-based

AspectState-based (CvRDT, convergent)Operation-based (CmRDT, commutative)

Typical fitReplicated key-value stores with anti-entropy (Riak, Redis Enterprise)Editors with a reliable log/transport (Yjs and Automerge send operations or updates)

Convergence conditions. A state-based CRDT converges if its states form a join-semilattice (a set with a partial order in which any two elements have a least upper bound), updates only move a state upward in that order (monotonic), and merge computes the least upper bound. Merge is then automatically commutative (order of arrival does not matter), associative (grouping does not matter) and idempotent (receiving the same state twice does not matter): the three properties that let you survive reordering, batching and duplication. An operation-based CRDT converges if concurrent operations commute and the delivery layer provides causal, exactly-once delivery. Delta-state CRDTs are a hybrid: they ship only the part of the state that changed (the delta), which is itself a valid state and merged the same way, giving small messages with weak delivery requirements.

11.2 Counters: G-Counter and PN-Counter

A plain integer with "+1" cannot just be merged with max or sum: if two replicas both start at 5 and each add 1 independently, the answer should be 7, but max gives 6 and "sum the replicas' values" gives 12. The fix is to track contributions per replica.

A G-Counter (grow-only counter) is a vector with one non-negative integer slot per replica. Replica i only ever increments slot i. The value is the sum of all slots. Merge takes the element-wise maximum. Because each slot is only changed by its owner and only grows, the max of two versions of a slot is always the newer one; merge is commutative, associative and idempotent. Example with replicas A, B, C: A holds [3,0,0], B holds [0,2,0]. After merge both hold [3,2,0] with value 5; a duplicate merge changes nothing.

A PN-Counter (positive-negative counter) supports decrements by pairing two G-Counters: P for increments and N for decrements. Value = sum(P) - sum(N); merge merges each separately. It cannot enforce a lower bound (like "stock never below zero") without coordination, since two replicas can each decrement the last unit concurrently. That is a general limit of coordination-free designs, discussed under CALM below.

11.3 Sets: G-Set, 2P-Set and OR-Set

  • G-Set (grow-only set). Only additions are possible. Merge is set union. Simple and correct, but you cannot remove anything.
  • 2P-Set (two-phase set). Keep an add set A and a remove set R (a "tombstone set"), both grow-only. An element is present if it is in A and not in R. Merge is union of each. The flaw: once removed, an element can never be re-added, because it stays in R forever. This is an acceptable limit for some data (a unique id used once) but not for a shopping cart.
  • OR-Set (observed-remove set). Each add attaches a unique tag (for example replica id plus counter) to the element. A remove deletes only the tags that the remover has observed for that element. Concurrent add and remove of the same element: the remove did not see the new add's tag, so the add survives ("add wins"). Re-adding after removal creates a fresh tag, so it works. State is a set of (element, tag) pairs; in the state-based form, removed tags are recorded (or tracked via causal context, as in the optimized OR-Set) so that merge does not resurrect them.

11.4 Registers: LWW and multi-value

A register holds a single value that can be overwritten. Two concurrent writes need a resolution rule.

  • LWW-Register (last-writer-wins). Each write carries a timestamp (and replica id as a tiebreak). Merge keeps the value with the larger timestamp. It is trivially convergent and cheap, but it silently discards one of the concurrent writes, and with physical clocks that drift (see Chapter 27) the "last" write may not be the one the user made last. Hybrid logical clocks reduce, but do not eliminate, the data-loss nature of LWW. It is acceptable for data where the latest value truly wins (a user's profile picture, a "last seen" time) and dangerous otherwise.
  • Multi-value register (MV-Register). Writes carry a version vector. If one write causally follows another, it overwrites. If two writes are concurrent, both are kept as siblings, and a read returns all of them so the application (or user) resolves the conflict, which a later write then supersedes. This is the Dynamo and Riak "siblings" behavior. No information is lost, at the price of pushing the merge decision to the reader.

The version vectors used here, and the happens-before reasoning behind "causally follows" versus "concurrent", are those of Chapter 27. Replication context is in Chapter 24 (leaderless replication, where this conflict handling originates).

13. Sequence CRDTs for text

A counter or set is easy; ordered text is the hard case. The core move is the one mentioned earlier: give every character a unique identity that never changes, and define operations in terms of identities instead of indexes. "Insert H after the character whose id is (alice, 7)" means the same thing regardless of what else has happened to the document. Different sequence CRDTs differ in how they generate ids and how they order concurrent inserts at the same spot.

13.1 RGA (Replicated Growable Array)

RGA stores the document as a linked list of elements; each element has a unique id, typically a pair (logical timestamp, replica id) built from a Lamport clock (see Chapter 27), so ids are totally ordered and respect causality. To insert, a replica creates a new element with a fresh id and names its predecessor (the element it goes right after). On receiving this remote insert, a replica finds the predecessor and places the new element after it. If other elements were already inserted after that same predecessor (a concurrent insert at the same location), the new element skips over any siblings with a larger id and goes in front of those with a smaller one, which gives every replica the same deterministic order (the newer insert ends up nearer to the predecessor). Delete does not remove the element; it marks it as a tombstone (hidden but still present), because other replicas may still have concurrent operations naming it as a predecessor.

13.2 Logoot and LSEQ (dense identifiers)

Logoot takes a different route and avoids a linked structure. Each element gets a position identifier drawn from a dense, totally ordered space, such as a list of integers compared lexicographically (with a site id and counter to make them unique). To insert between elements with positions [3] and [4], generate a position between them, for example [3, 7]. Order is determined purely by comparing identifiers, so no predecessor pointers or tombstones are needed: delete really removes the element. The cost is that identifiers can grow long, for instance when many users keep inserting at the same spot (typing at the end of a document creates ever-deeper identifiers if the allocation strategy is naive). LSEQ improves this by choosing identifier allocation strategies adaptively (alternating whether new identifiers cluster near the left or right boundary at each depth) so that growth is sub-linear for common editing patterns, such as typing forward or typing backward.

13.3 Yjs and Automerge

The two most widely used libraries.

  • Yjs implements a sequence CRDT variant (the YATA algorithm) in which each inserted item records its left and right origin neighbours at insertion time and a client id; these resolve the order of concurrent inserts. Its most important engineering trick is that runs of consecutive characters typed by the same client are stored as a single block with one id and a length, instead of one object per character, which cuts memory and encoding size dramatically. It supports shared text, arrays, maps and XML, exposes a compact binary update format, has pluggable network providers (WebSocket, WebRTC) and persistence, and is popular in editor integrations (ProseMirror, Quill, CodeMirror, Monaco).
  • Automerge models a whole JSON-like document (maps, lists, text, counters) as a CRDT with a full operation history, giving the "git-like" capabilities of branching, merging and time travel. Its modern implementation is a Rust core with bindings for several languages, and a compact columnar binary format.

Both give offline-first editing: a client edits with no network, accumulates updates, and merges on reconnect without a server needing to transform anything. A server is still useful, but only as a relay and persistence layer, not as an arbiter.

13.4 Tombstones, garbage collection and metadata growth

The price of CRDT convergence is metadata. A document of 100,000 visible characters may carry ids for all of them, plus tombstones for every character ever deleted. Without cleanup, a heavily edited document grows without bound: a document edited for years is far larger than the text it shows. Mitigations:

  • Run-length blocks (Yjs): one block per contiguous run of characters, so overhead is per run, not per character. Typical documents stay within a small multiple of the text size.
  • Tombstone garbage collection. A tombstone can be physically removed once every replica has observed the delete, since then no future operation can reference it as a predecessor. Knowing that requires tracking what each replica has seen (version vectors, see Chapter 27), which is hard when replicas can be offline indefinitely. Common compromises: Yjs drops the content of deleted items (keeping a tiny placeholder that preserves ordering information), which already removes most of the weight; systems with a known set of participants collect once all have acknowledged; others periodically re-base (snapshot the document into a fresh state and require clients to resync), accepting that very old offline copies cannot merge.
  • Compaction of history. Automerge-style documents can be saved as a compressed snapshot plus recent changes; full history can be discarded if time travel is not needed.
  • Identifier length (Logoot family): bounded by allocation strategy (LSEQ) and occasional renumbering coordinated across replicas.
Watch out "CRDTs need no coordination" is true for convergence, but not for cleanup. Garbage collection, schema migration of the document model, and permission changes ("revoke Bob's edit access") do need agreement between replicas or a trusted server. Design the control plane separately from the data plane.

This shows a useful principle: choose the weakest merge rule that preserves user intent; per-property LWW is enough for shapes, while text needs a sequence CRDT or OT.

15. Where these are used

  • Riak offers CRDT data types (counters, sets, maps, registers, flags) on top of its Dynamo-style leaderless replication, where concurrent writes during partitions are the norm (Chapter 24).
  • Redis Enterprise Active-Active (CRDB) replicates Redis data across geographically separate clusters using CRDT semantics for strings (with LWW), counters, sets, hashes and more, so each region can accept writes locally with low latency and merge asynchronously (Chapter 15).
  • Figma for multiplayer design documents, with a server that orders updates and per-property conflict rules.
  • Collaborative notes and code editors built on Yjs or Automerge, including local-first apps that work fully offline and sync later.
  • Offline-capable mobile apps that queue edits and merge on reconnect (Chapter 56 covers the client side: local storage, sync queues, push).
  • Distributed counters for likes, views and inventory approximations across data centers (G-Counter and PN-Counter style).
  • Collaborative editing at large by Google Docs, Etherpad and similar, with OT.

15.1 The CALM theorem

The CALM theorem (Consistency As Logical Monotonicity) states that a program has a coordination-free, consistent distributed implementation if and only if it is monotonic: its output only grows as more input arrives and never needs to retract something previously concluded. Set union, counting up, and "have we seen X" are monotonic. "Is the count exactly zero?", "is the set empty?" and "stock never negative" are non-monotonic: a later input can invalidate an earlier answer, so they need coordination (a quorum, a lock or consensus). CRDTs are the data-structure embodiment of monotonic computation, which explains both why they need no coordination and why they cannot enforce global invariants such as uniqueness or non-negative balances. For the larger picture of what you give up or keep under partitions, see Chapter 28.

15.2 Version vectors and causality, recap

A version vector (see Chapter 27) has one counter per replica. Comparing two vectors tells you whether one version happened before the other (all entries less than or equal, at least one strictly less), or whether they are concurrent (each has an entry the other lacks). Concurrency is exactly the situation that needs a conflict rule. Version vectors are used by multi-value registers to decide whether to overwrite or keep siblings, by CRDT delivery layers to enforce causal order ("I have not yet seen the operation this one depends on, so buffer it"), and by garbage collection to determine what every replica has observed. G-Counters are in effect version vectors whose entries are the value.

16. Presence and cursors

Collaborative tools also show who is here and where their cursor and selection are. This is ephemeral state: it is only meaningful while the user is connected, it changes very frequently (every mouse move or keystroke), and losing an update does not matter because the next one replaces it. That makes it a poor fit for the durable operation log and a good fit for a separate, lightweight channel.

  • Separate channel. Presence travels over the same WebSocket (Chapter 6) but as a different message type, never stored in document history. In Yjs this is the "awareness" protocol.
  • Last value wins, with a time to live. Each client broadcasts its state (name, color, cursor position, selection); recipients keep the latest per client and drop clients that have not sent a heartbeat for some seconds (for example every 5 s, expire after 15 to 30 s). Because it is LWW per client and each client is the only writer of its own record, there are no conflicts.
  • Cursor positions must be transformed too. If Alice's cursor is at index 10 and Bob inserts 3 characters before it, her cursor should move to 13. In OT, cursor positions are transformed by the same functions as operations. In CRDTs, store a cursor as a relative position, an anchor to a character id (plus a side), which stays correct as the document changes and resolves back to an index on render.
  • Throttle and coalesce. Send cursor updates at most every 50 to 100 ms and drop intermediate ones. With N users in a room, every update fans out to N-1 others, so total traffic grows as the square of users; large rooms show only nearby or most-recent participants, or reduce cursor update rates.

17. Worked example: a shared document with three clients

Design a note editor where three users (Ana, Ben, Cho) edit one document, one of them (Cho) on a phone that is briefly offline. We compare how the server-ordered OT design and the CRDT design behave, using the same scenario. The document starts as Hi (server revision 10).

Events: Ana types " all" at the end, Ben concurrently inserts "!" at the end, and Cho, offline, inserts "Oh, " at the start. All three edits happen before any sync.

17.1 Server-ordered OT

StepWhat happensResult
1Ana's op ins(2, " all")@r10 reaches the server first.Applied. Doc Hi all, r11. Broadcast to Ben (Cho is offline).
2Ben's op ins(2, "!")@r10 arrives, server is at r11. Transform against Ana's insert: same position 2, tie-break by arrival order (server's earlier op goes first), so Ben's index shifts to 6.Applied as ins(6, "!"). Doc Hi all!, r12.
3Ben's client receives Ana's op, transforms it against its pending op, applies it, and gets the ack.Ben shows Hi all!.

The server did the heavy lifting: it transformed Cho's op against the two missed revisions. If Cho had been offline for an hour with 5,000 ops by others, the server and the client would both have to transform long histories, which is why OT is poor for long offline sessions.

17.2 CRDT (RGA or YATA-style)

  • Each character already has an id. "H" and "i" are (1,s) and (2,s). Ana's " all" is created as ids (3,ana) to (6,ana) after element (2,s). Ben's "!" is (3,ben) after (2,s) too. Cho's "Oh, " is created before "H" (anchored at the document start) with ids (1,cho) to (4,cho).
  • When updates merge in any order, Ana's and Ben's inserts both follow "i". The order between them is decided by ids: with the rule "larger id first", (3,ben) beats (3,ana), so Ben's "!" is placed directly after "i" and Ana's run follows it, giving Hi! all. Ana's run is a sequence whose characters stay attached to their left neighbours, so Ben's "!" lands before or after the whole run, never in the middle. With the opposite id rule the result would be Hi all!; either way every replica agrees. (This differs from the OT result above only because the tie-break rule differs.) (The interleaving of concurrent runs in the middle is the known anomaly that careful algorithms such as YATA and RGA avoid for contiguous runs.)
  • Cho's offline edits are sent as a batch of updates when she reconnects. No transforms occur; each replica just integrates the updates by id, and the server merely relays them. Cho's phone had applied her insert at once, and later receives Ana's and Ben's updates by the same mechanism.
  • Presence: each client has an awareness record (name, color, cursor as a relative position). When Cho reconnects, her cursor anchor (a character id) is still valid even though the text moved.

Observe the difference in the failure case: if the server crashes in the OT design, the in-flight ops and revision numbers need the durable log to recover; in the CRDT design, any client holding the full state can reseed the server, since the state itself is the source of truth.

17.3 Sizing

Take a note with 20,000 characters and 30,000 total edits over its life. A CRDT with per-character ids and no run-length encoding might need about 16 to 32 bytes of metadata per element, so 50,000 elements (live plus tombstones) is roughly 0.8 to 1.6 MB; with run-length blocks (Yjs-style) it is typically tens to a couple hundred KB. The OT approach stores 20 KB of text plus an operation log of 30,000 ops at, say, 20 to 40 bytes each, about 600 KB to 1.2 MB, which can be compacted into periodic snapshots (for example every 100 revisions) and old ops discarded after all clients have moved past them. Both are modest for text; the difference matters more for very large, long-lived documents, and in that case you plan for GC or snapshot compaction up front. Network cost is small either way: a keystroke is tens of bytes. For the case study end to end (sharding documents, storage, fan-out) see Design a Collaborative Editor.

18. Interview Q&A

Why does Redis use a skip list for sorted sets rather than a balanced tree?

A skip list gives the same expected O(log n) insert, delete, search and rank (using spans on each pointer) as a balanced tree, but with far simpler code: there are no rotations, and insertion only splices a few local pointers. Range queries are natural: find the start in O(log n) and then walk the bottom-level list, which is doubly linked in Redis for reverse ranges. The promotion probability is a tunable memory versus speed knob, and Redis uses 1/4 to save pointers. It is paired with a hash table so that score lookup by member is O(1). Redis does not need the concurrency advantages of skip lists because command execution is single-threaded, so the main reasons are simplicity and comparable performance.

How would you design a global leaderboard for 100 million players with real-time rank?

Start with the fact that one Redis sorted set can hold tens of millions of members and handles add, increment and rank in O(log n), so a single shard (with replicas for reads) may suffice for the top of the board. Beyond that, shard by player id hash, send each score update to its shard, and serve the global top K through scatter-gather: each shard returns its local top K and the service merges them, which is exact because the global top K is contained in the union. For "what is my rank", an exact answer costs S parallel ZCOUNT calls, which is acceptable for a player's own view; for huge boards use score histograms or quantile sketches and show percentile bands below the top few thousand. Cache the top 100 for a few seconds so refresh storms do not hammer Redis, and keep daily and weekly boards as separate keys with TTLs.

Explain how you find the top K most frequent items in a stream that does not fit in memory.

If the number of distinct items is small enough, a hash map of counts plus a min-heap of size K gives exact results in O(n log K). When distinct items are too many, use an approximate heavy-hitter structure. A Count-Min Sketch holds counters in fixed memory and overestimates counts by a bounded amount; pair it with a min-heap of K candidates, updating the heap each time an item's estimate is raised above the heap's minimum. Alternatively Space-Saving keeps K counters and replaces the smallest counter when a new item arrives, which tends to be the most accurate in practice. Both are mergeable, so you can run them per shard and combine summaries. State the guarantee: items above a frequency threshold are found, and the counts carry a small, known error.

Why can per-shard top-K then merge produce wrong answers, and how do you fix it?

It is exact only if each item's events all land on one shard (partition by item). If events for one item are spread across shards, an item that is globally the third most frequent could rank sixth on every shard and be absent from every local top K, so the merge misses it. Fixes include re-partitioning by item with a shuffle before counting, asking each shard for more than K and then querying exact counts for the candidate set in a second round, or using mergeable summaries such as Count-Min Sketches that add cell by cell. In stream engines, pre-aggregate locally in short windows to reduce shuffle volume and to defuse hot keys.

How is trending different from most popular, and how would you detect it?

Most popular is raw volume, which is dominated by permanently popular topics. Trending is unusual growth relative to a topic's own baseline. Compute the recent window's count (for example last ten minutes) and divide by a smoothed historical average for the same time of day, or compute a z-score against history, and require a minimum absolute volume so tiny topics do not spike on one event. Add a distinct-user check, using HyperLogLog, so one account or botnet cannot create a trend. Run this on tumbling or sliding windows in a stream processor and keep the highest scores in a small heap.

Walk through how operational transformation resolves two concurrent inserts.

Both clients start from revision r, apply their insert locally, and send the operation with the base revision to the server. The server applies the first arrival unchanged. For the second, it sees the base revision is behind, so it transforms the operation against every operation committed since: if the earlier insert was at an index less than or equal to this one, this one's index shifts right by the length inserted; for the same index a deterministic tie-break, such as arrival order, applies. The transformed operation is applied and broadcast. Each client, when it receives a remote operation, transforms it against its own unacknowledged operations before applying, and the transform diamond (TP1) guarantees that both orders reach the same text. The server's total order is what avoids the harder TP2 requirement.

What is the difference between state-based and operation-based CRDTs, and what makes merge safe?

A state-based CRDT ships its state (or deltas) and merges with a function that is commutative, associative and idempotent, so it tolerates lost, duplicated and reordered messages; this is the property you want for gossip and anti-entropy. An operation-based CRDT ships individual operations, which are small, but requires the delivery layer to give exactly-once and causal-order delivery, and the operations must commute when concurrent. The mathematical basis is a join-semilattice where updates only move state upward and merge is the least upper bound, which guarantees every replica that has seen the same updates holds the same state. Delta-state CRDTs combine the small messages of the operation-based approach with the weak delivery needs of the state-based one.

Describe how an OR-Set handles a concurrent add and remove of the same element.

Every add gives the element a fresh unique tag. A remove deletes only the tags that the removing replica had observed. If another replica concurrently adds the same element, that add has a new tag the remover never saw, so after merging, the new tag survives and the element is present: add wins over a concurrent remove. A later re-add after a remove also creates a new tag, so unlike a 2P-Set, elements can come back. The cost is metadata: tags and the record of removed tags accumulate and must be compacted using causal context once all replicas have observed them.

When would you choose OT, when CRDTs, and what are the main drawbacks of each?

Choose server-ordered OT for an always-online, server-centric product where a central server must enforce permissions and validation and where documents are mostly text with a few operation types; its drawbacks are the correctness difficulty of transform functions, the server as a serialization point, and poor behavior with long offline sessions. Choose CRDTs when you need offline-first behavior, peer-to-peer or multi-region active-active replication, or rich nested data, since merging is automatic and local; the drawbacks are metadata growth from ids and tombstones, the need for garbage collection with agreement between replicas, harder access control with untrusted peers, and some anomalies in intention preservation. A common modern hybrid is a server that relays CRDT updates, validates permissions and stores snapshots.

Why can't a CRDT enforce "inventory never goes below zero"? What do you do instead?

That invariant is non-monotonic: whether a decrement is allowed depends on the global total, and two replicas can each see one remaining unit and each decrement it, producing minus one after merge. The CALM theorem says such conditions need coordination. Practical options are to split the stock into per-replica allowances (escrow or reservation, in which each replica may sell only its own share and transfers shares with coordination), to route the scarce-resource decisions through a single leader or consensus group, or to accept overselling and compensate afterwards, as many retailers do. CRDTs remain useful for the parts that are monotonic, such as counting views or recording events.

How do you handle presence and cursors in a collaborative editor?

Treat them as ephemeral, per-client state on a separate lightweight channel, not as part of the durable document history. Each client broadcasts its own record (user, color, cursor and selection) at a throttled rate and others keep the latest record per client, expiring clients that miss heartbeats after some seconds. Cursor positions must follow document changes, so in OT they are transformed like operations and in CRDTs they are stored as relative positions anchored to a character id. Because fan-out grows with the square of participants in a room, large rooms limit update frequency or show only nearby participants.

19. Recap

  • A sorted set needs fast insert, delete, score lookup, rank and range. A hash map plus an ordered structure gives it. Balanced trees do this deterministically but are hard to implement and to make concurrent; skip lists do it with random promotion, local pointer splices and O(log n) expected time, and are what Redis uses (with spans for rank).
  • Heaps give O(1) peek and O(log n) insert and extract of the extreme element in a compact array. They are the right tool for schedulers and for exact top-K using a min-heap of size K (O(n log K)).
  • Leaderboards use ZADD, ZINCRBY, ZREVRANGE and ZREVRANK. Shard by player and merge per-shard top K for exactness; use histograms or quantile sketches for approximate rank on enormous boards; use one key per time window with TTL.
  • Streaming top-K uses Count-Min Sketch plus a heap, or Misra-Gries and Space-Saving counters. Distributed top-K is exact only when each item is owned by one shard; otherwise re-partition, over-fetch, or merge mergeable summaries. Windows use buckets, sliding combos of sketches, or decay.
  • Trending is growth relative to baseline, filtered by minimum volume and distinct users. Sliding-window counters trade exactness for constant memory with bucket rings.
  • Merkle trees detect divergence between replicas cheaply by comparing hashes top-down.
  • Concurrent edits conflict because positions are relative to a version. OT rewrites operations (transform, TP1, server ordering to avoid TP2); CRDTs give elements permanent identities so operations commute.
  • CRDT building blocks: G-Counter, PN-Counter, G-Set, 2P-Set, OR-Set, LWW and multi-value registers, then sequence CRDTs (RGA, Logoot/LSEQ, Yjs, Automerge). State-based CRDTs need an idempotent, commutative, associative merge; operation-based ones need causal exactly-once delivery.
  • CRDT costs are metadata and tombstones, mitigated by run-length blocks, GC when all replicas have seen a delete, and snapshots. CALM explains why they cannot enforce non-monotonic invariants.
  • Presence and cursors are ephemeral LWW state on a separate channel, with relative cursor anchors.
