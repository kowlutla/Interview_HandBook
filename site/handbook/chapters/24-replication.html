Chapter 24 · Module 3 · The Data Layer

Replication

Replication means keeping copies of the same data on several machines. This chapter explains why you do it, the three families of replication (single-leader, multi-leader, leaderless), what goes wrong when copies disagree or lag behind, how failover works and where it hurts, and how to size and monitor a replicated system.

1. Why replicate at all

A replica is a copy of a dataset held on a different machine. Replication is the ongoing process of keeping those copies in step with each other as the data changes. If data never changed, replication would be trivial: copy the files once and be done. The whole difficulty of this chapter comes from one fact: data changes while copies are being made, and machines and networks fail at awkward moments.

There are four distinct reasons to keep copies, and a good candidate names which one is driving the design, because each pushes toward different choices.

  • Availability. A single database server will eventually crash, be rebooted for patching, or lose its disk. If a second machine already holds an up-to-date copy, the service can carry on after a short switch-over instead of being down until someone restores a backup. Replication turns a machine failure from an outage into a blip.
  • Latency (geographic proximity). As the CDN chapter showed (Chapter 12), light is slow over long distances. A user in Singapore reading from a database in Virginia pays 150-250 ms per round trip. A replica in Singapore answers reads in a few milliseconds. This is the reason for placing copies in several regions.
  • Read scaling. Most applications read far more than they write, often 10 to 1 or 100 to 1. One machine can only serve so many queries per second. If you spread reads over five replicas, read capacity grows roughly fivefold, while the single write path remains the same. This is the cheapest scaling step before you need sharding (Chapter 25).
  • Durability. A disk can fail and take the only copy of the data with it. Keeping the same bytes on a second machine, ideally in a different rack, zone, or region, means a single hardware loss cannot destroy data. Note that replication is not a backup: a bad DELETE or a corrupting bug is faithfully replicated to every copy within moments. You still need point-in-time backups (Chapter 21 covers where they live).
Key idea Replication is a trade: you buy availability, read capacity, latency, and durability, and you pay with consistency complexity. As soon as there are two copies, a reader can see a stale one, two writers can disagree, and a failed machine may have held a write that nobody else saw. Everything else in this chapter is about managing those three problems.

Replication differs from sharding (also called partitioning). Sharding splits the dataset so each machine holds a different piece; it scales writes and total storage. Replication keeps the same piece on several machines; it scales reads and survives failures. Real systems use both: the data is split into shards and every shard is replicated. When people say "a three-node cluster", always ask whether the three nodes hold the same data (replication) or different data (sharding), or a mix.

The three families of replication differ in who is allowed to accept writes, and that single choice shapes everything else.

2. Single-leader replication

The most common design, by a wide margin, is single-leader replication, also called leader-follower, primary-replica, or (older terminology) master-slave. One node is designated the leader. All writes must go to it. The other nodes are followers (also called replicas or secondaries). The leader applies each write to its own storage and also records it in a replication log, an ordered stream of changes. Each follower reads that stream and applies the changes in the same order. Reads may be served by the leader or by any follower.

2.1 The write path, step by step

  1. The client sends a write (for example UPDATE accounts SET balance = 90 WHERE id = 7) to the leader.
  2. The leader checks constraints, takes locks, and applies the change to its data files. For durability it first appends the change to its own local write-ahead log (WAL) and flushes it to disk.
  3. The change is placed in the replication stream. The leader sends it to each follower, or each follower pulls it, depending on the product.
  4. Each follower appends the change to its own log and applies it to its own data. It then tells the leader how far it has got.
  5. Depending on the synchronization mode (section 4), the leader acknowledges the commit to the client after step 2, after the first follower confirms, or after all followers confirm.

2.2 Why one leader is attractive

Because a single node decides the order of all writes, there is a single, well-defined history. Two clients cannot write conflicting versions of the same row on different machines; the leader serializes them. That removes an entire class of problems (write conflicts) and keeps the mental model simple: followers are just lagging, read-only mirrors of the leader. The costs are that the leader's capacity limits write throughput, and that the leader is a single point of failure that you must be able to replace (section 6).

3. What exactly travels in the replication log

"Send the changes to the follower" hides a real design choice: what is a change? There are four common answers, each with different trade-offs.

3.1 Statement-based replication

The leader logs every write statement (the SQL text) and each follower re-executes it. It is compact and human-readable, but it breaks whenever a statement is not deterministic. NOW() or RAND() yield different values on each machine. A statement using an auto-increment column depends on the exact order of other statements. A statement with a side effect (triggers, stored procedures, user-defined functions) may behave differently. Statements that depend on existing data, such as UPDATE ... WHERE with no ORDER BY, can touch rows in a different order. Early MySQL used this mode; MySQL now defaults to row-based or a mixed mode that switches to row-based when a statement is unsafe.

3.2 Write-ahead log (WAL) shipping

Most storage engines already write every change to an append-only write-ahead log before touching the data pages, so that they can recover after a crash. The leader can simply ship these same log bytes to followers, who replay them. PostgreSQL's streaming replication works this way. The advantage is that it is exact: the follower's data pages end up byte-for-byte equivalent, and there is no non-determinism. The disadvantage is that the WAL describes changes at the level of disk blocks and storage-engine internals, so leader and follower must run the same storage format and usually the same major version. That makes zero-downtime major upgrades hard, because you cannot simply have a new-version follower replay an old-version leader's log.

3.3 Logical (row-based) log replication

A logical log describes changes at the level of rows: "row with primary key 7 in table accounts changed from balance 100 to balance 90", "row 8 inserted with these column values", "row 9 deleted". It is decoupled from storage internals, so followers may run a different version or even a different engine, and external systems can consume the stream. MySQL's row-based binary log and PostgreSQL's logical decoding are examples. This is also the basis of change data capture (CDC), where tools such as Debezium read the log and publish row changes to Kafka (Chapter 34), to feed search indexes (Chapter 22), caches, and data warehouses.

3.4 Trigger-based replication

Database triggers or application code record changes into a side table, and an external process ships them. This is flexible (you can replicate a subset, transform data, or replicate between different products) but has higher overhead and more bugs than built-in replication. Use it only when built-in replication cannot do the job.

4. Synchronous, asynchronous, and semi-synchronous

The leader has to decide when to tell the client that a write succeeded. This is the most important knob in single-leader replication, because it sets the trade-off between durability and latency.

4.1 Asynchronous replication

The leader writes locally, immediately acknowledges the client, and ships the change to followers in the background. Writes are fast (no waiting for the network) and the leader keeps working even if every follower is down. The danger: if the leader crashes after acknowledging but before a follower received the change, that write exists only on the dead leader's disk. If you promote a follower, the acknowledged write is lost. If the old leader later comes back, it holds writes the cluster has moved past. This is the default in most databases because the latency and availability behaviour is so much better.

4.2 Synchronous replication

The leader waits until the follower has confirmed it received (and possibly flushed or applied) the change before acknowledging the client. If the leader dies, at least one other machine holds every acknowledged write, so nothing acknowledged is lost. The costs: every write pays at least one network round trip to the follower, and if the synchronous follower becomes slow or unreachable, writes stall. With a single synchronous follower, a hiccup on that follower halts the leader. Fully synchronous to all followers is therefore almost never used: with ten followers, any one failure blocks writes.

4.3 Semi-synchronous

The practical compromise: designate one (or a small number of) follower as synchronous and keep the rest asynchronous. If the synchronous follower fails or lags too much, the system promotes an asynchronous one to take over the synchronous role (or temporarily degrades to async). This guarantees that at any moment at least two nodes hold each acknowledged write, so a single failure never loses data, while a slow follower in a far region cannot block everything. MySQL calls its version "semi-sync" (the leader waits for an acknowledgement that the change reached at least one replica's relay log). PostgreSQL offers synchronous_commit levels and synchronous_standby_names with quorum syntax such as "any 1 of (a, b, c)". Cloud databases such as Amazon Aurora go further by writing to a quorum of storage nodes across zones before acknowledging.

5. Replication lag and its anomalies

With asynchronous followers, a follower is always slightly behind. The delay between a write on the leader and its visibility on a follower is replication lag. Under normal load it is milliseconds. During a write burst, a long-running transaction, a network problem, or a slow disk on the follower, it can grow to seconds, minutes, or hours. A system with this property offers eventual consistency on followers: if writes stop, all followers will eventually show the same data, but at any moment a reader may see an older state.

This is fine for some reads (a "views" counter) and unacceptable for others (your own profile after you saved it). Three anomalies come up repeatedly and each has a name, a clear scenario, and well-known fixes.

5.1 Reading your own writes

A user posts a comment. The write goes to the leader. The page reloads and the read goes to a follower that has not yet received the comment. The user sees their comment missing and assumes it was lost, then posts it again. The guarantee that fixes this is read-your-writes consistency (also read-after-write): a user always sees the effects of their own earlier writes, though other users' writes may still be delayed.

Fixes.

  • Read from the leader for data the user may have modified. For example, always read the user's own profile from the leader, other people's profiles from followers. This requires knowing what a user could have modified, which is easy for "my profile" and hard in general.
  • Time-based stickiness. For one minute after a user writes anything, send all their reads to the leader (or to followers whose lag is known to be below that window). Simple, and often good enough.
  • Track a position token. When the leader acknowledges a write, return its log position (the LSN, or a logical timestamp) to the client. On the next read, the client sends the token and the router only uses a follower that has applied at least that position, or waits briefly until one has. MongoDB's causal consistency sessions and "afterClusterTime", and PostgreSQL techniques that compare pg_last_wal_replay_lsn() to a saved LSN, work this way.
  • Cross-device complications. If the same user writes on a phone and reads on a laptop, per-device stickiness fails. The position token must be stored server-side per user rather than in one device's memory, and if replicas span regions, the user's requests may need to be routed to the same region.

5.2 Monotonic reads

A user refreshes a page twice. The first read is served by an up-to-date follower and shows a comment. The second read is served by a more lagging follower and the comment disappears, as though time went backwards. Monotonic reads guarantees that successive reads by one user never move backward in time: once you have seen a newer state, you will not later see an older one. It is weaker than strong consistency (you may still see old data) but forbids this confusing regression.

Fixes. The simplest is to route each user to the same replica for a session, choosing it by hashing the user id rather than at random. The drawback is that if that replica fails, the user moves to another that may be further behind, so you also keep a high-water-mark token (the highest log position the user has seen) and refuse to serve from a replica that is behind it.

5.3 Consistent prefix reads

Imagine a conversation: Alice asks "How far into the future can you see, Mrs. Cake?" and Mrs. Cake answers "About ten seconds usually." The two writes have a causal order (the answer depends on the question), but if they land on different shards that replicate at different speeds, an observer might see the answer before the question. Consistent prefix reads guarantee that if a sequence of writes happened in a certain order, anyone reading them sees them in that order: you may see a prefix of the history, but never a history with holes or reordering.

Fixes. Write causally related data to the same partition (all messages of one conversation share a partition key), or use a database that tracks causal dependencies explicitly (version vectors, hybrid logical clocks; see Chapter 27). Single-partition systems get this property automatically because the replication log has one order.

Watch out These guarantees are cheap to give inside one datastore and hard to give across several. If your service reads user data from a cache, a search index, and a replica, each has its own lag, and the combination can violate all three guarantees at once. State which consistency level each read path needs (Chapter 28) instead of assuming "the database is consistent".

6. Failover: replacing a dead leader

Followers can fail and be replaced easily: restart them, and they catch up from the log. A leader failure is harder, because one node is special. Failover is the process of promoting a follower to be the new leader, reconfiguring clients and other followers to use it, and making sure the old leader cannot cause harm. It can be manual (an operator runs a command) or automatic.

6.1 The steps of automatic failover

  1. Detect. There is no perfect way to know a node is dead; you only know it has stopped responding. Nodes exchange heartbeats, and if several are missed over a timeout (often 5-30 seconds), the leader is declared failed. A short timeout detects real failures quickly but causes false positives during a load spike, a garbage-collection pause, or a network blip, triggering needless failovers that themselves cause disruption. A long timeout means a longer outage after a real crash.
  2. Choose a new leader. Usually the follower with the most up-to-date log (the highest applied position) is best, because it loses the least data. Nodes may vote, or a controller may decide. This is a consensus problem: all nodes must agree on a single new leader. See Chapter 29 for Raft and leases.
  3. Reconfigure. Clients (or a proxy or virtual IP or DNS record) must send writes to the new leader, and the remaining followers must start replicating from it.
  4. Handle the old leader. If it returns, it must learn that it is no longer leader and become a follower, discarding or reconciling any writes the new leader never saw.

6.2 What can go wrong

  • Lost writes. With asynchronous replication, the new leader may be missing the last few writes that the old leader acknowledged. When the old leader rejoins, those writes conflict with what the new leader has accepted since. The usual (and painful) outcome is that the old leader's unreplicated writes are discarded. This is dangerous when other systems already saw them. A famous case: a stale follower promoted to leader reused auto-increment primary keys that had already been handed out and cached in Redis, so some users saw other users' private data. Always consider what outside systems observed.
  • Split-brain. Two nodes both believe they are the leader and both accept writes. This can happen if the old leader was only partitioned from the others (not dead) or paused (a long garbage-collection or VM pause) and wakes up unaware that it was replaced. Both leaders accept writes, the histories diverge, and merging them may be impossible without data loss. Some systems have a safety mechanism that shuts down one leader if two are detected, but a badly designed one can shut down both.
  • Wrong timeout. Too aggressive and a temporary overload triggers failover, which adds more load (new leader, catch-up, cache warmup), potentially causing a failover storm.
  • Replication lag blind spots. The most caught-up follower is still only as good as its position. If you promote a follower that is minutes behind, you lose minutes of data.
  • Client confusion. Clients with cached connections or DNS entries keep sending writes to the dead or demoted leader until they refresh.

6.3 Fencing: making the old leader harmless

The robust defense against split-brain is fencing, which means forcibly preventing the old leader from doing damage even if it does not know it was deposed. There are two broad forms.

  • STONITH ("shoot the other node in the head"): before or while promoting a new leader, the controller cuts power to the old node through a power-management interface or cloud API, or detaches its storage. After that, the old node cannot write. This is blunt but reliable, and used in classic high-availability clusters.
  • Fencing tokens (epochs, terms, generations). Every leadership change increments a number. Each write carries the leader's number, and storage or followers reject writes with a lower number than the highest they have seen. A paused old leader wakes up, sends a write with epoch 7, and is refused because the cluster is at epoch 8. Raft's term and Kafka's leader epoch are this idea, and Chapter 30 explains fencing tokens with distributed locks.

6.4 Tools: Patroni, Orchestrator, and managed services

Few teams script failover from scratch. Patroni manages PostgreSQL clusters: each node runs a Patroni agent that holds a leader key with a time-limited lease in a distributed store (etcd, Consul, or ZooKeeper). Only the holder of the lease may run as primary; if it cannot renew the lease, it demotes itself. When the lease expires, the remaining agents compete for the key, and the best-positioned replica wins and is promoted. A proxy such as HAProxy or PgBouncer, or a virtual IP, routes clients to whoever holds the key. Orchestrator (originally from GitHub) discovers MySQL replication topologies, detects failures from several vantage points (it requires the leader and its replicas to agree before acting, which reduces false positives), and promotes a replica, repointing the others. Managed services (Amazon RDS Multi-AZ, Aurora, Cloud SQL, Azure) hide this behind a DNS endpoint and typically complete failover in 30 to 120 seconds, or faster for Aurora. MongoDB replica sets and Redis Sentinel build election into the product.

6.5 A failover runbook

If asked how you would operate this, give an ordered checklist, because the order prevents harm.

  1. Confirm the leader is really unavailable from more than one vantage point (not just one monitor with a bad network path).
  2. Fence the old leader (stop the service, cut network, detach storage) before promoting anyone. Promoting first and fencing second is how split-brain happens.
  3. Pick the most advanced replica by comparing applied log positions; record how many writes might be missing.
  4. Promote it and verify it accepts writes (a test write and a read back).
  5. Repoint the remaining followers and clients (proxy, DNS with a low TTL, or service discovery). Restart or drain connections that still point to the old leader.
  6. Rebuild or rejoin the old leader as a follower. If it holds writes the new leader lacks, save them somewhere for analysis before overwriting; then re-initialize it from a fresh snapshot (section 7).
  7. Reconcile data that other systems saw (caches, search indexes, message queues, downstream consumers) and write the incident review including how much data, if any, was lost.

7. Adding a follower: snapshot plus catch-up

You need new followers when capacity grows, when a follower dies permanently, or when the old leader rejoins after failover. The difficulty: the leader keeps accepting writes while you copy, so a plain file copy gives an inconsistent mix of old and new states, and locking the leader for the duration of the copy would mean downtime. The standard procedure avoids both.

  1. Take a consistent snapshot of the leader at a known point in the replication log, without locking the database. Most engines offer this (PostgreSQL pg_basebackup, MySQL with Percona XtraBackup, MongoDB initial sync, or a storage-level snapshot such as an EBS snapshot). The snapshot is associated with an exact log position (a PostgreSQL LSN, a MySQL binlog coordinate or GTID).
  2. Copy the snapshot to the new node and restore it.
  3. Connect to the leader and request all changes since the snapshot position. The follower is now catching up: it applies the backlog of changes made during the copy.
  4. When the backlog is drained, the follower is caught up and keeps applying changes as they happen. It can now serve reads and be a candidate for promotion.
Watch out A follower can also fall so far behind that it needs a re-sync. PostgreSQL replication slots keep WAL for a lagging replica, which protects it but can fill the leader's disk if the replica is dead and nobody notices. This is a classic production incident. Alert on slot retention size, and set a maximum such as max_slot_wal_keep_size.

8. Multi-leader replication

In multi-leader (also multi-master or active-active) replication, several nodes accept writes, and each forwards its writes to the others. Each leader is simultaneously a follower of every other leader. Why accept the added complexity? Three situations justify it.

8.1 Multi-datacenter operation

With one leader in one region, every write from another continent crosses the ocean, adding 100-200 ms, and if the leader's datacenter is lost all writes stop until a cross-region failover. With a leader in every datacenter, each region's users write locally, and each datacenter keeps working if the link to another fails. Replication between datacenters is asynchronous, so the slow link does not slow user writes. The cost is that two users in different datacenters can change the same record at the same time, creating write conflicts (section 9). Multi-leader setups also have subtle interactions with auto-incrementing keys, triggers, and integrity constraints, which is why many teams treat them as a last resort.

8.2 Clients with offline operation

A calendar or notes app on your phone must work with no connectivity. The phone keeps a local database and accepts writes, and syncs later. Each device is in effect a leader with a very unreliable network link: the replication delay can be hours or days. CouchDB/PouchDB are designed for this model, and it explains why mobile sync is full of conflict-handling code.

8.3 Collaborative editing

Real-time editors (Google Docs, Figma, Notion) let many people edit the same document. Each user's edits apply locally at once and are propagated to others, so each client acts like a leader. The conflict-resolution machinery is either operational transformation (OT), where a server transforms concurrent operations so they commute, or CRDTs (section 9.4). Locking the document avoids conflicts but kills the experience, which is why this application naturally falls into multi-leader territory.

8.4 Topologies

A replication topology says which leader sends writes to which. With two leaders it is trivial. With more, the shapes are:

  • All-to-all (mesh): every leader sends to every other. Most fault-tolerant (no single link matters), but messages can arrive in different orders at different nodes, so an update can overtake the insert it depends on, and you need version vectors or causality tracking to order them.
  • Circular (ring): each node forwards to the next. Fewer connections, but one broken node or link interrupts the chain. Writes carry the ids of the nodes they passed through to prevent infinite loops.
  • Star (tree): one root node forwards between others. Simple, but the root is a bottleneck and a single point of failure.

9. Conflicts: detecting and resolving them

A write conflict occurs when two writes to the same data are concurrent, meaning neither writer had seen the other's write when it made its own. (Note that "concurrent" does not mean "at the same instant"; it means "neither causally depends on the other". Two edits made an hour apart by users who were both offline are concurrent.) In single-leader systems the leader orders writes, so concurrent writes are simply serialized: the later one wins or one is blocked. In multi-leader and leaderless systems conflicts are real and must be dealt with.

9.1 Avoid the conflict

The best strategy is to design conflicts away. If all writes for a given record are routed to the same leader (for example each user has a "home region" and all their writes go there), then from that record's perspective the system is single-leader and cannot conflict. Failover to another region changes the home but only rarely. This does not remove all conflicts but removes most, and many production multi-region systems rely on it.

9.2 Last write wins (LWW)

Attach a timestamp to every write and keep the one with the highest timestamp; discard the others. It is simple, converges everywhere, and requires no application logic. It is also lossy: concurrent writes are silently dropped even though each was acknowledged to its client as successful. Worse, it relies on clocks, which are not synchronized perfectly (Chapter 27). If one server's clock runs 200 ms fast, its writes beat later writes from other servers. LWW is acceptable for data where losing an update does not matter (a cache entry, a last-seen timestamp). In Cassandra, which resolves conflicts this way, the safe practice is to treat each write as an immutable value, for example by giving each write a unique key instead of updating one in place.

9.3 Merge and application-level resolution

  • Keep siblings. Store all concurrent versions and return them all to the application at read time, which merges them (Riak calls these siblings; Dynamo's shopping cart merged by union). This preserves data but pushes complexity into app code. A classic bug: a shopping cart that merges by union resurrects items the user deleted, because a deletion is the absence of data. The fix is to record deletions as tombstones.
  • Custom conflict handlers. The database calls your code on write (when it detects the conflict while replicating) or on read. Bucardo, CouchDB's deterministic winner plus conflict list, and MySQL tooling follow this pattern.
  • Merge by value. For some types, an automatic merge is correct: a counter's concurrent increments add up, a set's concurrent adds union.

9.4 CRDTs: a preview

A conflict-free replicated data type (CRDT) is a data structure whose operations are designed so that replicas can apply them in any order, any number of times, and still converge to the same state. Examples: a G-counter (each replica keeps its own count, the total is the sum, merging takes the maximum per replica); an OR-set (adds carry unique tags, removes remove specific tags, so a concurrent re-add survives); sequence CRDTs for text. Redis Enterprise active-active, Riak data types, and some collaborative editors use them. The price is metadata growth and limited expressiveness (you cannot express "balance must stay non-negative" with a plain CRDT). The deeper treatment belongs with consistency models (Chapter 28).

9.5 Detecting concurrency with version vectors

To decide whether two versions conflict or one simply supersedes the other, systems keep a version vector (generalization of a vector clock): per replica, a counter of how many writes from that replica are reflected in this version. Compare two vectors: if every counter in A is at least that in B, then A includes B and replaces it; if neither dominates, they are concurrent and conflict.

10. Leaderless (Dynamo-style) replication

Amazon's 2007 Dynamo paper popularized a design with no leader at all. Any replica accepts writes. A client (or a coordinator node acting for it) sends each write to several replicas in parallel, and each read to several replicas, and combines the answers. Cassandra, Riak, ScyllaDB, and Voldemort follow this model. There is nothing to fail over: if a replica is down, requests go to the others, so one dead node causes no visible disruption.

10.1 Quorums: n, w, r

Each key is stored on n replicas (commonly 3, chosen by consistent hashing; see Chapter 25). A write is declared successful once w replicas acknowledge it. A read queries r replicas and returns the freshest value among the responses. The key rule:

Quorum condition: w + r > n If the number of replicas written (w) plus the number read (r) exceeds n, then any read set and any write set must overlap in at least one replica, so a read always contacts at least one replica that has the latest acknowledged write. With n = 3, w = 2, r = 2: 2 + 2 = 4 > 3, and the overlap is at least 1. The system tolerates n - w failed replicas for writes and n - r for reads (here, one of each).

Why the overlap guarantees freshness: the write went to some w replicas. A read picks some r replicas. If w + r > n, the two groups cannot be disjoint (there are only n machines in total), so at least one replica in the read group holds the new value. The reader picks the value with the highest version or timestamp, so it sees the latest write.

10.2 Tunable consistency

You can choose w and r per request, which is called tunable consistency. With n = 3:

10.4 Sloppy quorums and hinted handoff

A strict quorum requires w of the designated n replicas for the key. If a network problem cuts a client off from most of those n nodes, writes fail even though other healthy nodes exist. A sloppy quorum accepts writes on any w reachable nodes, even ones outside the key's designated set. When the designated replicas come back, the stand-in node forwards the data to them: this is hinted handoff. It greatly improves write availability, but it weakens the guarantee: the w nodes written might not overlap the r nodes read, so w + r > n no longer guarantees reading the latest value until the hints are delivered. Dynamo and Riak enable it by default; Cassandra offers hinted handoff but keeps its quorum strict by default.

10.5 Keeping replicas in sync: read repair and anti-entropy

A replica that was down misses writes. Two mechanisms heal this.

  • Read repair. When a read contacts several replicas and sees different versions, the coordinator returns the newest to the client and writes it back to the stale replicas. It repairs data that is read, so frequently read keys are fixed fast, but rarely read keys stay stale for a long time.
  • Anti-entropy. A background process compares replicas and copies missing data. To avoid comparing every row, replicas build Merkle trees (hash trees) over key ranges and exchange them: matching hashes mean identical ranges, mismatching hashes narrow down to the exact differing keys (Chapter 33). Cassandra's nodetool repair does this and must run regularly, within the tombstone retention window (gc_grace_seconds, default ten days), or deleted data can come back to life.

10.6 What quorums do not guarantee

It is tempting to say w + r > n gives strong consistency. It does not, for several reasons. With sloppy quorums, the sets may not overlap. If two writes are concurrent, the winning value may be chosen by LWW and a write lost. If a write succeeds on fewer than w replicas, it is reported as failed but is not rolled back on the replicas that accepted it, so later reads may return the value of a "failed" write. A node that recovered from a stale replica can reduce the number of replicas holding the new value below w. Timing edge cases (a read concurrent with a write) can return either old or new value, and two readers might see them in opposite order. Quorums give probabilistic freshness, not linearizability (Chapter 28); strict guarantees need consensus (Chapter 29) or Cassandra's lightweight transactions (Paxos-based compare-and-set).

11. Replication in real systems

11.1 PostgreSQL

Physical streaming replication ships WAL records to standbys, which replay them (hot standbys serve read-only queries). Modes range from asynchronous (default) to synchronous with synchronous_commit = remote_write, on, or remote_apply, which controls whether the standby must have received, flushed, or applied the record before commit returns. Logical replication uses publications and subscriptions at the table level, allowing version upgrades and selective replication. Failover is not built in: use Patroni, repmgr, or a managed service. A subtle point is query conflicts on hot standbys: a long query on a standby can conflict with WAL replay that vacuums rows it still needs, and the standby either delays replay (increasing lag) or cancels the query (hot_standby_feedback and max_standby_streaming_delay choose which).

11.2 MySQL

MySQL replicates its binary log, in statement, row, or mixed format. A replica has an I/O thread that fetches binlog events into a relay log and an SQL thread (or several parallel workers) that applies them. Historically the single apply thread was a lag source, and multi-threaded replication fixed much of that. GTIDs (global transaction identifiers) label each transaction so that a replica can switch leaders without hand-computing file and offset. Semi-sync plugins give the compromise of section 4. Group Replication and InnoDB Cluster add consensus-based membership and automatic failover. Orchestrator is the usual external tool.

11.3 MongoDB replica sets

A replica set is typically three members: one primary and two secondaries, replicating via the oplog (a capped collection of logical operations). If the primary is unreachable for the election timeout (default 10 seconds), the members hold a Raft-style election and the candidate with the most recent oplog and a majority of votes wins; this uses a term number to fence stale primaries. Writes with write concern w: "majority" are acknowledged only after a majority replicated them and survive failover; w: 1 may roll back. Read concern and read preference (primary, secondary, nearest) choose staleness. Rolled back writes are saved to files for manual review. An arbiter (a voting member without data) can break ties but weakens durability, so a third data-bearing member is preferable.

11.4 Cassandra

Leaderless, with n called the replication factor (usually 3) per keyspace, and per-query consistency levels (ONE, QUORUM, LOCAL_QUORUM, ALL). Writes first go to a commit log and an in-memory memtable on each replica, so each write is fast. Hinted handoff, read repair, and scheduled anti-entropy repair keep replicas converging. Conflicts resolve by last-write-wins at the column level using timestamps, so clocks must be reasonably synchronized (NTP) and you should avoid updating the same cell from many clients. The multi-datacenter setup uses NetworkTopologyStrategy with replicas per datacenter.

11.5 Kafka

Each topic partition has a leader and followers, and the in-sync replica set (ISR) is the leader plus followers that are fully caught up within replica.lag.time.max.ms. A producer using acks=all gets an acknowledgement only after every ISR member has the record, and min.insync.replicas sets the minimum ISR size for a write to be accepted (typical production setting: replication factor 3, min.insync.replicas 2). If the ISR shrinks below the minimum, writes are rejected instead of risking loss. When the leader fails, the controller elects a new one from the ISR, so no acknowledged write is lost. Allowing an out-of-sync replica to lead (unclean leader election) trades durability for availability and is off by default. Kafka's newer KRaft mode uses Raft for cluster metadata. See Chapter 34.

11.6 Raft-based systems

etcd, Consul, CockroachDB, TiKV, and YugabyteDB replicate each range or group through a Raft log. A leader appends an entry and considers it committed once a majority of replicas have stored it. That is replication with a quorum rule built in: with 3 replicas, 2 must ack; with 5, 3; and any new leader must have all committed entries, so no acknowledged write is lost and split-brain is impossible, because a leader needs a majority of votes and old terms are rejected. The price is that every write waits for a majority round trip, and a cluster that loses its majority becomes unavailable for writes (consistency over availability). Chapter 29 (Consensus and Leader Election) shows the mechanics. A typical modern distributed SQL database shards data into ranges and runs a separate Raft group per range.

12. Chain replication (overview)

Chain replication arranges the replicas in a line: head, middle nodes, tail. Writes enter at the head and are forwarded node by node to the tail; the write is acknowledged only when the tail has it. Reads go to the tail, which holds only fully replicated data, so reads are strongly consistent without voting. It is a form of synchronous replication where the work is pipelined and the load of sending to many followers is spread across the chain rather than concentrated on the leader. Failure handling relies on a separate configuration service that removes a failed node and relinks neighbours. The weaknesses are write latency that grows with chain length (every hop is sequential) and that one slow node slows the whole chain. Variants (CRAQ) let any node serve reads of clean data. It appears in storage systems such as Azure Storage and in research and cloud blob stores; remember it as "sync replication in a pipeline, reads from the tail".

13. Geo-replication preview

Placing replicas in other regions serves two goals: nearby reads for users, and survival of a regional disaster. The physics matters: a cross-region round trip is typically 60-150 ms (US east to west about 60-70 ms, US to Europe about 80-100 ms, US to Asia 150-250 ms). That makes synchronous cross-region replication expensive for every write, so most systems replicate asynchronously across regions and synchronously (or by quorum) between zones within a region, where round trips are about 1-2 ms. The common patterns are: active-passive (one primary region, a standby elsewhere; simple, with an RPO of seconds), read-local, write-primary (followers in every region, writes forwarded to the primary), and active-active (multi-leader or leaderless with conflict resolution, or home-region routing). Choosing among them, failing a whole region over, and migrating data without downtime are covered in Chapter 26.

14. Monitoring replication

You cannot manage what you do not measure. Key signals:

  • Replication lag in bytes and in seconds. Bytes (leader position minus replica applied position) shows backlog; seconds shows user-visible staleness. In PostgreSQL compare pg_current_wal_lsn() with each standby's replay_lsn in pg_stat_replication; MySQL shows Seconds_Behind_Source, which can be misleading (it reads zero when the I/O thread is stalled), so prefer a heartbeat table: a row the leader updates every second with the current time, which each replica compares to its own clock. MongoDB shows lag in rs.printSecondaryReplicationInfo().
  • Replica state: whether each follower is connected, streaming, or stuck in catch-up or initial sync.
  • Retained log size: replication slots, binlog disk use, and oplog window (in hours: the time span the oplog covers; if a secondary is down longer than this, it needs a full resync).
  • Leader changes: frequent elections indicate flapping due to a bad timeout, network, or overload.
  • ISR size (Kafka), hint backlog and repair status (Cassandra), pending compactions.
  • Replica-served consistency: the rate of reads that required fallback to the leader.

Alert on the percentile of lag against a defined budget (for example "p99 lag above 5 s for 5 minutes"), and also on lag growth, since a slowly growing lag means the replica will never catch up. Exercise failover regularly (game days), because an untested failover path is usually broken.

16. Worked example: sizing replicas and a lag budget

Scenario. A social app has 20 million daily active users on a PostgreSQL primary. Peak read traffic is 30,000 queries per second (QPS), peak write traffic is 1,500 QPS, and the average write generates about 2 KB of WAL. The SLO is 99.95% availability with a worst-case loss of no acknowledged writes on a single machine failure, and the product requirement is that a user sees their own posts immediately and other people's posts within 5 seconds.

16.1 Number of read replicas

One database node of this class comfortably serves about 8,000 read QPS at the target latency while also handling the 1,500 writes (the writes consume part of its capacity). Keep 40% headroom so that a failure does not saturate the survivors, which means planning each node at about 5,000 read QPS in normal operation.

  • Reads to serve from replicas: 30,000 QPS (the primary serves only reads for read-your-writes).
  • Replicas needed in normal operation: 30,000 ÷ 5,000 = 6.
  • If one replica fails, 5 remain and each takes 6,000 QPS, within the 8,000 limit. But we also want to survive losing a whole zone. With 6 replicas over 3 zones, a zone loss leaves 4, each at 7,500 QPS, which is barely under the limit. Adding a seventh (spread 3-2-2) leaves at least 4 after the worst zone loss, so a seventh does not help the worst case by itself; use 8 replicas (3-3-2), leaving 5 after a zone loss at 6,000 QPS each. Final plan: 8 read replicas plus the primary and a synchronous standby.

16.2 Replication bandwidth

  • WAL generated at peak: 1,500 writes/s × 2 KB = 3 MB/s, or 24 Mbit/s per replica stream.
  • With 9 standbys (8 replicas plus the synchronous standby) the primary sends 9 × 3 MB/s = 27 MB/s, about 216 Mbit/s. This fits on a 10 Gbit/s link with ease, but note the primary does the fan-out; with 30 replicas you would use cascading replication (replicas that feed other replicas) to spread the load.
  • Cross-region standby: 24 Mbit/s of sustained WAL traffic is easy over a WAN link, but the RTT (about 80 ms) governs the minimum lag, not the bandwidth.

16.3 Lag budget

The 5-second staleness target for other people's posts is the total budget. Decompose it:

ComponentTypicalBudget
Commit on primary and WAL send~5 ms50 ms
Network to replica (same region)~1 ms50 ms
Replay on replica (apply)~10 ms500 ms under bursts
Cross-region standby~80 ms1 s
Safety margin for bursts and vacuum/replay conflicts3 s

Steady state lag is well under 100 ms, so the 5 s budget is for spikes. The alert fires when p99 lag exceeds 3 s for 2 minutes (a warning) and 5 s for 5 minutes (a page); the router removes any replica above 5 s from the read pool automatically.

16.4 Durability and failover

  • Semi-sync: the synchronous standby is in a second zone, 1-2 ms away. A commit costs about 2 ms extra, so a 5 ms write becomes about 7 ms. No acknowledged write is lost if the primary dies, since the standby has it.
  • Failover time with Patroni: lease TTL of 30 s, loop wait 10 s, so detection takes up to 30 s, election and promotion 5-10 s, proxy repoint 2-5 s, for a total of roughly 40-45 s of write unavailability.
  • Availability check: 99.95% allows 0.05% × 30 days × 24 h × 60 min ≈ 21.6 minutes of downtime per month. At 45 s per failover, you can afford about 28 failovers a month, so even a few unplanned events fit comfortably. Lowering the lease TTL to 15 s would halve detection time but would raise false failovers, so keep 30 s.
  • Read-your-writes: after a write, the user's reads go to the primary for 10 seconds (the session token carries the write LSN), which adds only a small fraction of traffic (users who just wrote are under 5% of reads, or about 1,500 QPS to the primary). That fits the primary's capacity.
Result 1 primary, 1 synchronous standby in another zone, 8 read replicas across 3 zones, one delayed replica (1 hour behind) as protection against bad deploys, a p99 lag alert at 5 s, and session tokens for read-your-writes. Total replication egress from the primary is about 27 MB/s.

17. Interview Q&A

What is the difference between synchronous and asynchronous replication, and which would you pick?

With asynchronous replication the leader acknowledges a write once it is on its own disk and ships it to followers afterwards, so writes are fast and followers cannot block the leader, but a leader crash can lose the most recent acknowledged writes. With synchronous replication the leader waits for a follower to confirm, so no acknowledged write is lost on a single failure, but each write pays a round trip and a stuck follower can stall writes. In practice I pick semi-synchronous: one nearby synchronous follower for durability, the rest asynchronous for reads and cross-region copies. For truly lossy-tolerant data such as analytics events, plain async is fine.

A user saves their profile and then sees the old version after the page reloads. What happened and how do you fix it?

This is a read-your-writes violation: the write went to the leader but the read was served by a follower that had not yet applied it, which is replication lag. I would fix it by routing the user's reads to the leader for a short window after they write, or by returning the write's log position to the client and only reading from replicas that have reached that position. For cross-device cases the position should be stored server-side by user. The solution costs a little extra leader load, and users who just wrote are a small share of reads.

How does automatic failover work, and what can go wrong?

Nodes monitor the leader with heartbeats and declare it dead after a timeout. The cluster then chooses the most up-to-date follower, promotes it, repoints clients and other followers, and demotes the old leader if it comes back. Risks include losing unreplicated writes when replication is asynchronous, split-brain if the old leader was merely paused and keeps accepting writes, false failovers from too short a timeout, and downstream systems that saw writes which the new leader never had. I mitigate with semi-sync replication, leases in a consensus store, fencing tokens or STONITH, conservative timeouts, and a rehearsed runbook.

What is split-brain and how do you prevent it?

Split-brain is two nodes both believing they are the leader and both accepting writes, producing diverging histories that are difficult or impossible to merge. It is usually caused by a network partition or a long pause on the old leader. Prevention has two parts: elect leaders only with a majority vote or a lease so that at most one leader can exist per term, and fence the old leader so that its writes are refused, using an incrementing epoch checked by storage or followers or by forcibly shutting the node off. A lease-based leader must also step down when it cannot renew the lease.

Explain quorum reads and writes with n=5. Which w and r would you choose?

With five replicas, a write acknowledged by w nodes and a read from r nodes always overlap if w + r is greater than 5, so a read sees at least one copy of the latest acknowledged write. The common choice is w=3 and r=3, which tolerates two failed nodes for both reads and writes and balances cost. If reads dominate and must be fast, w=5 and r=1 makes reads cheap but a single failure blocks writes; if writes dominate, w=1 and r=5 does the reverse. Note that this holds only for strict quorums without concurrent writes or sloppy quorum behaviour; it does not by itself give linearizability.

How do you handle write conflicts in a multi-leader system?

First I try to avoid them by routing all writes for a given record to one home leader, which makes that record effectively single-leader. When conflicts still occur, the options are last-write-wins, which is simple but silently loses updates and depends on clocks; keeping siblings and merging in the application; using CRDTs, which merge automatically for counters, sets, and text; or running custom resolution code based on business rules. I detect concurrency with version vectors rather than timestamps, because they distinguish one write superseding another from two truly concurrent writes. The choice depends on whether losing an update is acceptable for that data.

What are hinted handoff and read repair, and why do you need anti-entropy as well?

Hinted handoff lets another node temporarily accept a write destined for a down replica and hand it over when the replica returns, which keeps writes available. Read repair fixes stale replicas when a read notices they returned an older version, by writing the newest value back. Both are opportunistic: hints can expire or be lost and read repair only touches keys that get read. Anti-entropy is the systematic background comparison, usually through Merkle trees, that finds and copies any remaining differences, and it must run regularly (for example within Cassandra's tombstone grace period) so deleted data does not resurrect.

Why do Kafka and Raft-based systems lose no acknowledged writes on leader failure, when async MySQL can?

They only acknowledge after a defined set of replicas has the data: Kafka with acks=all waits for every member of the in-sync replica set (and requires the set to be at least min.insync.replicas in size), and Raft waits for a majority. When the leader dies, the new leader is chosen only from nodes that have all acknowledged data (the ISR, or a majority-elected candidate with the most complete log), so nothing acknowledged is lost. Async MySQL acknowledges before any replica has the data, so a promoted replica may lack acknowledged writes. The price is added write latency and unavailability when too few replicas remain.

How do you add a new replica to a busy database without downtime?

I take a consistent snapshot of the leader along with its log position, without locking writes, restore it on the new node, and then have the node stream and apply all log entries since the snapshot position until it is caught up. Only then does it join the read pool or become eligible for promotion. The leader must retain its log long enough for the new node to catch up, so I watch log retention and replication slots and cap them to avoid filling the leader's disk. For very large datasets I use storage snapshots or incremental backups to shorten the copy.

How would you monitor replication health and what would you alert on?

I measure lag in both bytes and seconds per replica, preferably with a heartbeat row that the leader updates and replicas compare to their clock, since built-in seconds-behind metrics can be misleading. I alert on p99 lag crossing the staleness budget, on lag that keeps growing, on replicas that are disconnected or in resync, on log or slot retention nearing disk limits, on frequent leader elections, and on shrinking ISR or unreachable quorum. I also run periodic failover drills and verify backups, because replication alone does not protect against logical corruption.

18. Recap

  • Replication keeps copies for availability, lower latency, read scaling, and durability; it is not a backup and it costs consistency complexity.
  • Single-leader is the default: one writer, an ordered log (statement, WAL, or logical rows), followers apply in order.
  • Sync, async, and semi-sync set the trade between write latency and data loss; semi-sync with one nearby synchronous follower is the usual compromise.
  • Lag produces named anomalies: read-your-writes, monotonic reads, consistent prefix; each has a cheap fix (leader reads, sticky replicas, position tokens, same-partition writes).
  • Failover involves detection, election, promotion, and reconfiguration; guard against lost writes and split-brain with leases, fencing epochs, and a runbook that fences before promoting.
  • New followers start from a snapshot tied to a log position and catch up from the log.
  • Multi-leader serves multi-datacenter, offline, and collaborative uses but creates conflicts, resolved by avoidance, LWW, siblings and merge, CRDTs, or custom code, detected via version vectors.
  • Leaderless systems use n, w, r with w + r > n for overlap, plus sloppy quorums, hinted handoff, read repair, and anti-entropy; they give tunable, not strict, consistency.
  • Know the specifics: Postgres WAL streaming, MySQL binlog and GTIDs, MongoDB oplog and write concern, Cassandra consistency levels, Kafka ISR, Raft majority commit.
  • Monitor lag in bytes and seconds, retained log, elections, and ISR; size replicas for failure headroom and set a lag budget.
