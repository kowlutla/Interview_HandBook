CAP, PACELC and Consistency Models

Once data lives on more than one machine, every read raises a question: which value am I allowed to see? This chapter states the CAP theorem precisely, extends it with PACELC, lays out the consistency models as a ladder from linearizable to eventual, and teaches you to pick the right rung for each feature in an interview.

1. Why consistency is a design decision

On a single machine with a single copy of the data, the question "what does a read return?" has an obvious answer: the latest write. The moment you keep the data in more than one place, which you do for fault tolerance, for read throughput, and for low latency near users (see Chapter 24 on replication), the copies can disagree for a while. A write lands on one replica and takes time to reach the others. During that window, two readers asking different replicas can get different answers.

A consistency model is a contract between the storage system and the programmer. It says which of those differing answers the system is allowed to hand back. A strong model promises that the system behaves as if there were one copy, which makes application code simple but costs latency and availability. A weak model lets the system answer quickly from whatever copy is nearest, which is fast and resilient but pushes the work of coping with stale or reordered data onto the application.

The important point for an interview is that this is a tradeoff you choose per feature, not a property you pick once for a product. A bank balance and a "like" counter on the same app deserve very different treatment. Candidates who say "we will use a strongly consistent database" for everything, or "we will use eventual consistency for scale" for everything, both miss the point. Strong answers say which operations need which guarantee, what anomaly the user would see without it, and what it costs to provide.

Key idea Consistency is the price list for coordination. Stronger guarantees require replicas to talk to each other (or to a leader) before answering. That talking costs latency in normal operation and availability during failures. Everything in this chapter is a way of deciding how much of that price a given feature is worth paying.

This chapter builds on two neighbours. Chapter 24 explains how copies are made (leader-follower, multi-leader, leaderless quorums) and where replication lag comes from. Chapter 27 explains why we cannot simply use wall clocks to order events and introduces logical clocks. Here we assume both and focus on what guarantees you can state to users. Chapter 29 then shows the machinery (Raft, Paxos) that implements the strongest guarantees.

2. The CAP theorem, stated precisely

CAP is the most quoted and most misquoted result in distributed systems. The usual slogan is "pick two of consistency, availability and partition tolerance." That slogan is misleading, so let us state each term as the theorem (Gilbert and Lynch's formalization of Eric Brewer's conjecture) actually defines it.

2.1 The three terms

  • Consistency (C) in CAP means linearizability: every read returns the value of the most recent completed write, and all clients see operations in one single real-time order, as if there were exactly one copy of the data. It does not mean the "C" in ACID (which is about application invariants such as foreign keys). It is also stronger than the everyday sense of "eventually the same."
  • Availability (A) in CAP means that every request received by a non-failed node must eventually get a non-error response. Note the strictness: not "most requests," not "the service is mostly up," but every request to every live node, even if that node cannot reach the others. Latency is not bounded by the definition, only that an answer comes.
  • Partition tolerance (P) means the system continues to operate even when the network drops or delays an arbitrary number of messages between nodes, so that the nodes split into groups that cannot talk to each other.

2.2 What the theorem says

Here is the argument in plain language. Suppose a system has two replicas, A and B, holding the same value of x. A network partition cuts the link between them. A client writes x = 2 to replica A. Another client then reads x from replica B.

  • If B answers, it can only return the old value, because it has no way to learn about the write. The system was available but the read is not the most recent write, so it was not consistent.
  • If B refuses to answer (returns an error or waits until the partition heals), the system stays consistent but not available, because a live node failed to respond.

There is no third option. During a partition you must give up either C or A. That is the whole theorem.

2.3 Why it is about partitions, not a free choice of two

The slogan "pick two" suggests you could build a CA system that has consistency and availability and simply does not tolerate partitions. In a distributed system over a real network that is not a meaningful option: networks do drop packets, switches fail, cloud availability zones get cut off, and a long garbage-collection pause or an overloaded node looks exactly like a partition to everyone else (see Chapter 27). You do not get to opt out of P. The honest statement is: when a partition happens, you must choose between C and A. When there is no partition, the theorem says nothing at all, and you can have both. A "CA" system is really a single-node system, or a system that has simply decided partitions will be treated as total failure.

Watch out Do not say "we chose CA." Interviewers hear that as a misunderstanding of CAP. Say instead "this component is CP: during a partition the minority side stops serving writes," or "this one is AP: both sides keep accepting writes and we reconcile later."

3. Common misconceptions, and CP versus AP in practice

3.1 Misconceptions worth correcting out loud

  1. "CAP means a system is permanently CP or AP." No. The choice only bites during a partition, and many systems let you pick per request (Cassandra consistency levels, DynamoDB strong or eventual reads, Cosmos DB's five levels). A system can behave as CP for one operation and AP for another.
  2. "Availability in CAP is the same as uptime or 99.99 percent." No. CAP availability is an all-or-nothing property about every live node answering every request. A CP system with a majority quorum may still have excellent practical uptime: the majority side keeps serving, and only clients stuck on the minority side see errors. That system is "not available" in the CAP sense yet is highly available in the operations sense.
  3. "Consistency in CAP is ACID consistency." No. CAP's C is linearizability, a property of how reads and writes on a single object interleave. ACID's C is about the database keeping application invariants true.
  4. "NoSQL means AP, SQL means CP." No. A single-node relational database is not even in the conversation, a Postgres cluster with synchronous replication leans CP, and a document store such as MongoDB with majority concerns is CP-leaning, while DynamoDB, Cassandra and Riak default to AP-leaning behaviour. The label depends on configuration.
  5. "CAP forces a tradeoff all the time." No. It describes behaviour during partitions only. Most of the time the interesting tradeoff is latency versus consistency, which is what PACELC (next section) captures.
  6. "Partitions are rare, so ignore CAP." Partitions inside one data center are less common than across regions, but they and partition-like events (gray failures, long pauses, overloaded nodes, misconfigured firewalls) happen often enough that you must have decided in advance what the system does.

3.2 What CP and AP systems actually do

A CP system keeps a single agreed history. It typically needs a majority (quorum) of replicas to accept a write or to serve a linearizable read. During a partition, the side with the majority continues; the minority side rejects requests or blocks. Examples: ZooKeeper and etcd (consensus-based coordination stores; see Chapter 29), Google Spanner, HBase, and MongoDB with majority write concern and majority reads from the primary. You choose CP when serving a wrong answer is worse than serving no answer: leader election, distributed locks, configuration, account balances, inventory that must not oversell.

An AP system lets every reachable replica keep accepting reads and writes. During a partition both sides keep going, and when the partition heals the system must reconcile conflicting writes (last-write-wins, vector clocks, application-level merges, or CRDTs, covered in section 14). Examples: Cassandra and Riak with low consistency levels, DynamoDB's original design, and DNS. You choose AP when being down is worse than being temporarily wrong: shopping carts, social feeds, like counts, presence, metrics, telemetry.

4. PACELC: the tradeoff when nothing is broken

CAP only talks about the rare moment of a partition. But the choice between "check with other replicas" and "answer immediately from here" exists on every single request, partition or not. Daniel Abadi pointed this out with PACELC, read as: if there is a Partition, choose between Availability and Consistency; Else (normal operation), choose between Latency and Consistency.

Why does a latency tradeoff exist without failures? Because replicas are physically separate. If a write must be acknowledged by a replica in another region before the client is told "done" (synchronous replication, Chapter 24), the client waits at least one cross-region round trip, which is tens to a couple of hundred milliseconds. If the write is acknowledged after only the local copy is updated (asynchronous replication), it is fast, but a reader elsewhere may see old data until replication catches up. Likewise for reads: a linearizable read must confirm with the leader or a quorum; a local read from the nearest replica is fast but may be behind.

Typical classifications, with the caveat that most of these systems are configurable and the labels describe defaults or common configurations:

ClassMeaningTypical examples
PA/ELAvailable during partitions, low latency otherwiseCassandra and Dynamo-style stores at low consistency levels, Riak
PC/ECConsistent during partitions, consistent (and slower) otherwiseSpanner, HBase, traditional replicated relational databases with synchronous replicas, etcd
PA/ECAvailable in a partition but consistent otherwiseOften cited for MongoDB with its older defaults; shows the model is not always clean
PC/ELConsistent in a partition, fast otherwisePNUTS (Yahoo) is the usual example: timeline-consistent local reads, strong writes via a master
Interview tip PACELC is the better thing to cite for design decisions, because the "Else" case is the one you live in 99.9 percent of the time. Saying "this is latency versus consistency in normal operation, so reads from the nearest replica give us 5 ms but may be up to a second stale" is far more concrete than reciting CAP.

5. The consistency ladder

CAP's C is one specific, very strong model. Between "one copy" and "anything goes" there is a whole spectrum, and naming the right point on it is a mark of a strong candidate. Think of it as a ladder. Each rung up forbids more anomalies (surprising behaviours) and costs more coordination. Each rung down is cheaper and faster but lets the application see stranger things.

The next sections walk the ladder from the top. For each rung we give a plain definition, the anomaly it prevents, and a small example. Throughout, a history means the recorded sequence of operations (writes and reads, with start and end times) seen by clients, and a model is just a rule about which histories are legal.

6. Linearizability (strict consistency in practice)

6.1 The definition

A system is linearizable if every operation appears to take effect at a single instant somewhere between its start (when the client sent it) and its end (when the client got the reply), and all operations can be placed on one timeline consistent with those instants. Two consequences follow. First, once a write finishes, every later read (a read that starts after the write ended) must see it or something newer. Second, once any reader has seen a new value, no later reader may see the old one. This is why linearizability is called a recency guarantee: it ties the order of operations to real, wall-clock time.

"Strict consistency" is the theoretical ideal in which operations take effect instantly at a global time; it cannot be implemented because messages take time to travel, so linearizability is its practical, achievable form and the one people mean in interviews. When we say "strongly consistent" for a single object or key, we almost always mean linearizable.

6.2 Timelines that are and are not linearizable

Operations that overlap in real time are concurrent, and the system may order them either way. Operations that do not overlap must respect real-time order. The diagram uses a register x that starts at 0. Client A writes 1. Clients B and C read.

A second way to see the same rule: once the write has been acknowledged to the writer, a read that begins afterward must not return the old value, no matter which replica serves it. In a leader-follower system with asynchronous followers, reading from a follower can violate this, which is exactly the "read your own write" surprise. Fixing it requires either routing reads to the leader, or having followers confirm they are caught up, which is the cost discussed in section 11.

6.3 What linearizability buys you

  • Uniqueness and constraints. Claiming a username or a seat, "create if not exists," or enforcing "exactly one leader" all require that two concurrent claimants cannot both succeed. That needs a single agreed order.
  • Locks and leader election. A lock service that is not linearizable can hand the same lock to two clients.
  • Cross-channel timing. If Alice finishes uploading a photo and tells Bob over the phone, Bob's request should see it. A recency guarantee covers channels the database cannot observe.

6.4 Scope: single object, not whole transactions

Linearizability is about operations on one object (a register, a key, a row). It says nothing about transactions touching several objects. That distinction matters in section 10.

7. Sequential, causal and PRAM consistency

7.1 Sequential consistency

Sequential consistency says: there exists one global order of all operations that every client agrees on, and each client's own operations appear in that order in the sequence the client issued them. What it drops compared with linearizability is the tie to real time. The agreed order may lag behind the wall clock: a write that finished a second ago may legally be ordered after a read that started later, as long as everybody sees the same order.

The anomaly it still prevents: two readers disagreeing about the order of two writes. If client A writes x = 1 and then client B writes x = 2, no reader may see 2 followed by 1 while another sees 1 followed by 2. The anomaly it permits: a stale read that is "consistent but old." In practice sequential consistency is mostly a theoretical stepping stone; real systems either give you linearizability (with a leader or consensus) or fall to causal and below. Its main value in an interview is to show you know that "everyone agrees on the order" and "the order matches real time" are different promises.

7.2 Causal consistency

Causal consistency guarantees that if one operation could have influenced another, every client sees them in that order. "Could have influenced" is the happens-before relation (Chapter 27): operations by the same client are ordered; a read that returned a value is ordered after the write that produced it; and the relation is transitive. Operations with no such relation are concurrent, and different clients may see them in different orders.

The classic example is a comment thread. Alice posts "Is anyone coming tonight?" Bob replies "Yes, I am." Without causal consistency, a third user on a lagging replica might see Bob's reply first, which is nonsense: the reply appears to answer a question that does not exist yet. With causal consistency the reply is never visible before the question it responds to. Causal consistency is the strongest model that can still be available during a partition (a known result), which makes it very attractive: you give up recency, but never cause-and-effect. It is typically implemented by attaching dependency metadata (vector clocks or version vectors, or hybrid logical clocks) to writes and having a replica delay exposing a write until its dependencies are visible. MongoDB offers causally consistent sessions; research systems such as COPS and Eiger are in this family.

7.3 PRAM (FIFO) consistency

PRAM (pipelined RAM) or FIFO consistency only promises that the writes issued by a single client are seen by everyone in the order that client issued them. Writes from different clients may be seen in different orders by different readers, and it does not track cross-client dependencies. It is weaker than causal (it ignores "I read Bob's write, then wrote mine") and is mostly useful as a conceptual rung: it is cheap, because per-writer sequence numbers suffice. It corresponds to the monotonic writes session guarantee below.

8. Session guarantees

Full causal consistency is heavy. Often what users actually notice are four narrow oddities within their own session. Terry and colleagues defined four session guarantees that are cheap, local, and fix most of the user-visible weirdness of an eventually consistent store. Together the four are equivalent to causal consistency for a single session.

GuaranteePlain-language ruleAnomaly it prevents
Read your writesAfter I write, my own later reads see that write (or newer).I change my display name, refresh, and see the old name.
Monotonic readsOnce I have seen a value, my later reads never return anything older.I see a comment, refresh, it vanishes (my second read hit a lagging replica), refresh again, it is back.
Monotonic writesMy writes are applied in the order I issued them.I save a draft then publish it; the replica applies publish first and the draft overwrites it later.
Writes follow readsA write I make after reading something is ordered after what I read.I read a post and reply; the reply is visible before the post on some replica.

8.1 How they are implemented

The guarantees are provided per client session, using cheap tricks rather than global coordination:

  • Sticky sessions: route a session to one replica so it sees a growing prefix of history. This gives monotonic reads and read-your-writes as long as that replica survives and does not lag behind the writes you made elsewhere. Simple, but fails on replica failover.
  • Session tokens (version vectors or log positions): after a write, the server returns a token such as a log sequence number. The client sends the token with later reads, and any replica must either have caught up to that position or forward the request to one that has (or wait). Cosmos DB's session consistency and MongoDB's causally consistent sessions work this way, as do many read-replica setups using LSNs.
  • Read from leader after write: for a short window after a user writes (say 10 seconds, longer than typical replication lag), send that user's reads for the same data to the leader. Alternatively, route reads of data the user owns (their own profile) to the leader and everything else to followers.
  • Client-side tracking: the client remembers the highest version it has seen and rejects or retries older responses (useful for monotonic reads).
Interview tip When you propose read replicas for scale, volunteer the follow-up yourself: "reads from replicas can lag, so for a user's own freshly written data we route to the leader for a few seconds, or carry an LSN token for read-your-writes." That one sentence shows you understand the whole section.

9. Bounded staleness and eventual consistency

9.1 Bounded staleness

Bounded staleness weakens linearizability by a controlled amount: reads may be behind the latest write, but by no more than K versions or T seconds. It is not a different ordering model so much as a quantified recency guarantee. It is attractive because users and product owners can reason about it ("the dashboard is never more than 5 seconds old"), and because it is cheap to enforce: replicas know their own replication lag and stop serving, or redirect, once they exceed the bound. Azure Cosmos DB exposes it directly with configurable K and T. Many systems implement it informally with "don't read from a replica more than N seconds behind." Combined with a monotonic-read guarantee it gives a sensible user experience for feeds and dashboards.

9.2 Eventual consistency

Eventual consistency promises only that if writes stop, all replicas will eventually converge to the same value. It says nothing about how long that takes, nor what readers see meanwhile: they may see old values, values going backwards, or different values on different replicas. It also needs a conflict resolution rule if two replicas accepted concurrent writes to the same key: last-write-wins by timestamp (simple, but silently loses one write and is vulnerable to clock skew), version vectors with application-level merge (the Dynamo shopping cart returned "siblings" for the app to merge), or CRDTs that merge automatically (section 14).

Mechanisms that make convergence happen: read repair (a read that sees different versions writes the newest back to stale replicas), hinted handoff (a node holds writes for an unreachable peer and delivers them later), and anti-entropy (background comparison of replicas, often with Merkle trees, to find and fix differences). See Chapter 24 for these in the leaderless setting.

"Eventual" is a weak promise on paper but in practice, replication lag inside one region is usually milliseconds. The danger is not that it is slow on average; it is that during a failure or overload the lag can grow to minutes, and your application must not break when that happens.

10. Transaction isolation versus distributed consistency

Two vocabularies get confused constantly, because both talk about "consistency" and "ordering":

  • Isolation levels (from the database world, Chapter 18: read committed, repeatable read, snapshot isolation, serializable) describe how concurrent transactions, each touching possibly many objects, may interleave. Their anomalies are dirty reads, non-repeatable reads, phantoms, lost updates and write skew.
  • Consistency models (from the distributed systems world, this chapter) describe how operations on replicas of one object appear ordered, with anomalies such as stale reads and reordering.

Serializability says that a set of transactions behaves as if executed one at a time in some order. That order does not have to match real time. A serializable database may order a transaction that committed an hour ago after one that committed a second ago, if the result is equivalent. Linearizability says single-object operations respect real-time order, but says nothing about multi-object transactions.

You can have either without the other, and the combination is the strongest:

Not linearizable (no real-time guarantee)Linearizable (real-time order)
Not serializable (weak transaction isolation)Typical eventually consistent store with read committed; many default configurationsA single-key linearizable register or lock service (one key used on its own); no multi-key transactions
SerializableA database that is serializable but allows stale reads from replicas or snapshotsStrict serializability: transactions behave as one at a time in an order that also respects real time. Spanner (external consistency), FoundationDB
Watch out Do not say "we use serializable isolation so reads are always fresh." A serializable transaction running against a lagging read replica or snapshot can legally return stale data. Freshness needs the real-time (linearizable) component, and that is what strict serializability, or reading from the leader, adds. Snapshot isolation, often marketed as "serializable" in some products, still allows write skew.

11. The cost of linearizability

If linearizability gives such clean semantics, why not use it everywhere? Because it has fundamental costs.

11.1 Latency

To guarantee a read returns the latest write, some replica must either know it is the sole authority (a leader whose lease is valid) or must check with a quorum. Either way the request pays a round trip to a distant node. Within one data center that is around 0.5 to 1 ms. Across regions it is the speed of light: US East to Europe is roughly 70 to 90 ms round trip, US to Asia-Pacific 150 to 250 ms. A linearizable write spanning three regions needs a majority (two of three), so it waits for the second-closest region: if the nearest peer is 80 ms away, every write costs at least about 80 ms, no matter how fast the hardware. Attiya and Welch showed that this is not an engineering shortcoming: in any linearizable system, operation latency is bounded below by network delay. You cannot buy your way out with faster machines.

11.2 Availability

As CAP showed, a linearizable system cannot serve both sides of a partition. It also reduces ordinary availability: a leader failure means a pause while a new leader is elected (Chapter 29), typically seconds, during which writes (and linearizable reads) are unavailable. A system with local reads and no leader has no such pause.

11.3 Throughput and operations

A single leader per shard is a throughput ceiling, which is why strongly consistent systems shard (Chapter 25) and keep strong guarantees within a shard while relaxing across shards, or pay for cross-shard coordination with two-phase commit or distributed timestamps. Strong consistency across the whole data set is the most expensive thing you can ask for.

Key idea Do not ask "should this be consistent?" Ask "what is the cost to the user of seeing stale or reordered data here, and is that cost bigger than the latency and downtime we would pay to prevent it?" Money, uniqueness and locks usually say yes. Likes, views and feeds usually say no.

12. How real systems expose consistency levels

Almost no production datastore is a pure point on the ladder. They give you dials. Know the dials of the main ones so that you can name the setting in an interview.

12.1 DynamoDB

Reads are eventually consistent by default and may return data slightly behind. You can request a strongly consistent read per request, which goes to the partition's leader and reflects all acknowledged writes; it costs twice the read capacity of an eventually consistent read, has slightly higher latency, and can fail if the leader is unreachable. Global secondary indexes only support eventual reads. Global tables (multi-region) have traditionally replicated asynchronously with last-writer-wins conflict resolution; check current documentation for newer multi-region options rather than assuming. Transactions (TransactWriteItems) give serializable isolation across items.

12.2 Cassandra

Leaderless with tunable consistency levels per request: ONE, TWO, QUORUM, LOCAL_QUORUM, EACH_QUORUM, ALL, plus ANY for writes. With replication factor N, if you write to W replicas and read from R replicas and R + W > N, the read set overlaps the write set, so a read sees the latest acknowledged write (for example N = 3, QUORUM = 2 for both: 2 + 2 > 3). Be careful: that overlap gives the latest write in normal conditions but does not by itself make the system linearizable (sloppy quorums, concurrent writes and clock-based timestamps can still produce anomalies). Cassandra also offers lightweight transactions (Paxos-based compare-and-set) for the few operations that truly need linearizability, such as uniqueness. LOCAL_QUORUM keeps latency regional by only waiting for replicas in the local data center.

12.3 Spanner

Google Spanner provides external consistency, which is strict serializability, across continents. It uses Paxos-replicated groups plus TrueTime, a clock API that returns a time interval with a known bound on uncertainty (a few milliseconds), derived from GPS and atomic clocks. A transaction picks a commit timestamp and then waits out the uncertainty ("commit wait") so that its timestamp order matches real-time order. Spanner also offers cheaper stale reads at a past timestamp or bounded staleness, served from any replica with no coordination. It is the textbook case of paying latency (commit wait plus cross-region quorum) for the strongest guarantee. See Chapter 27 for why bounded clock error is the key.

12.4 MongoDB

Two dials: write concern (how many replicas must acknowledge: w:1, w:"majority", plus journaling) and read concern (local, available, majority, linearizable, snapshot). Majority writes with majority read concern avoid reading data that could later be rolled back after a failover. linearizable read concern (read from the primary, confirming it is still primary) gives linearizability on a single document at a latency cost. Read preference (primary, secondary, nearest) decides where reads go and interacts with these. Causally consistent sessions provide read-your-writes, monotonic reads and writes, and writes-follow-reads when combined with majority concerns.

12.5 Azure Cosmos DB

Cosmos DB makes the ladder an explicit product setting with five levels: strong (linearizable; restricted with multi-region writes), bounded staleness (reads lag by at most K versions or T time), session (read-your-writes, monotonic reads and writes within a session; the default and most used), consistent prefix (reads never see out-of-order writes: if writes were A then B then C, you may see A, A-B, or A-B-C but never A-C), and eventual. This is a handy summary to quote.

14. CRDTs and coordination-free design (a preview)

If strong consistency costs coordination, an attractive idea is to design operations that do not need coordination to be correct. A CRDT (conflict-free replicated data type) is a data structure whose merge operation is designed so that replicas can accept updates independently and any two replicas that have seen the same set of updates end in the same state, regardless of the order or duplication of messages. This works when the merge function is commutative (order does not matter), associative (grouping does not matter) and idempotent (applying twice is the same as once).

14.1 Examples

  • G-counter (grow-only counter): each replica keeps its own slot in a vector of counts and increments only its own slot. The value is the sum of the slots. Merge takes the element-wise maximum. Two replicas count likes independently, merge later, and the total is right.
  • PN-counter: two G-counters, one for increments, one for decrements; value = positives minus negatives.
  • G-set and OR-set (observed-remove set): a grow-only set merges by union. An OR-set tags each added element uniquely so that a remove only removes the adds it has observed; an add concurrent with a remove survives ("add wins"). This is the shopping-cart behaviour.
  • LWW-register: keeps the value with the latest timestamp. Simple but loses concurrent writes.
  • Sequence CRDTs for collaborative text editing, which give each character a stable position identifier.

14.2 The CALM idea, briefly

The CALM theorem (Consistency As Logical Monotonicity, Hellerstein and Alvaro) gives a principled answer to "which programs can be coordination-free?" Roughly: a program whose output only grows as it receives more input (monotonic logic: adding facts never retracts earlier conclusions) can be made eventually consistent without any coordination and still be correct. Programs that need to retract or reason about "nothing else is coming" (non-monotonic: deleting, counting to a final total, "is this seat still free?") need coordination somewhere. This explains why a grow-only set or a counter is easy while "claim the last seat" is not. It also gives you a design heuristic: restructure the problem to be monotonic where you can (append events instead of overwriting, use tombstones, model "reserved" as a growing set of claims) and put coordination only at the few points that are inherently non-monotonic.

Watch out CRDTs guarantee convergence, not that the converged answer is what the business wants. An OR-set cart that resurrects a removed item because a concurrent add won is convergent but may surprise users. CRDT metadata (tombstones, per-replica slots) also grows and needs garbage collection. Treat CRDTs as a tool for the safe subset of your data.

15. Designing the user experience around eventual consistency

When you choose weaker consistency, the product must handle it gracefully. Many of the best tricks are interface tricks and cost nothing in the datastore.

  • Optimistic UI. After the user clicks like or posts a comment, update their screen immediately from local state while the request is in flight. The user sees their action instantly (read-your-writes by construction), and if the server rejects it, roll back with an error. Make sure a page refresh does not show the old state: keep the pending write locally or use a session token.
  • Show provisional state honestly. "Saving...", "Pending", "Processing payment." Present eventually consistent facts as in progress, not final. A bank shows pending transactions separately from the posted balance.
  • Idempotent operations and request ids. Retries are the normal response to a timeout, and a retry must not apply twice. Attach a client-generated idempotency key to each write.
  • Avoid exact numbers where approximate is fine. "1.2K likes", "about 3 left" or "10+ watching" hide small inconsistencies and invite no complaints.
  • Stable ordering and cursors. Paginate feeds with a cursor (the last seen item id or timestamp), not an offset, so that a replica switch does not repeat or skip items. Use a "new posts available" pill instead of live reshuffling.
  • Read your own writes locally. Keep a short-lived client cache of what the user just wrote and merge it into results from the server.
  • Reconcile and compensate. If an oversell happens (two buyers got the last item because the check was eventual), apologise and refund, which is a business-level fix. Airlines overbook on purpose for this reason.
  • Defer strictness to the commit point. Let people browse a stale catalogue; check the authoritative state only at checkout.

16. Worked examples

16.1 Tuning a quorum for a Cassandra-style store

Suppose a profile store replicates each row on N = 3 nodes in one region. Compare three configurations by their guarantees and cost, assuming a node answers in about 2 ms and a slow outlier takes 20 ms.

16.2 Read replicas and read-your-writes, with numbers

A social app has one primary and four read replicas. Writes: 2,000 per second. Reads: 40,000 per second, 95 percent from replicas. Typical replication lag is 50 ms with occasional spikes to 5 seconds. A user edits their profile photo and the app redirects to their profile page, which reads from a replica. With a 50 ms lag and a redirect taking about 100 ms, most reads see the new photo, but during a spike of up to 5 seconds the user sees the old photo and thinks the save failed. If 0.5 percent of the time is spent in spikes, the affected requests are a tiny share of traffic, but they are exactly the ones that generate support tickets.

Fix: after any write, set a short-lived marker for that user (cookie or server-side flag, for example 10 seconds, comfortably above typical lag). While the marker is present, that user's reads for their own data go to the primary. Cost: the extra primary load equals the reads from recently writing users. If 2 percent of users have written in the last 10 seconds and make 10 percent of reads, that is about 4,000 reads per second moved from replicas to the primary in the worst case, and typically far less because only reads of their own data are redirected, perhaps 80 to 400 per second. That is affordable and removes the confusing anomaly. A more precise version carries the write's log position as a token and lets any replica that has passed it serve the read.

16.3 Seat booking across two regions

A ticketing system has regions US and EU and 50,000 seats for one event. Requirements: never sell a seat twice; seat map browsing must be fast everywhere. Design: each event is owned by one leader region (say US), with a consensus group or synchronous replica providing linearizable writes. Seat map views are served from regional caches refreshed every 2 seconds (bounded staleness of 2 seconds). To buy, the client calls the leader with claim(seat, user, request_id); the leader performs an atomic conditional update "set owner if empty" and returns success or "taken." An EU user pays about 90 ms extra on the claim for the cross-region hop, accepted because it is one action per purchase. Browsing remains local at a few milliseconds. When the cache shows a seat as free but the claim fails, the UI says "just taken, here are similar seats." If the US region is unreachable, EU purchases for US-owned events fail (CP behaviour) rather than risk double sale, while browsing continues.

16.4 A distributed likes counter

A video has 10 million likes and thousands of likes per second at peak. Strong consistency would mean a cross-region write per like. Instead each region keeps a PN-counter (or batches increments in memory and flushes every second as a delta); regions exchange deltas asynchronously. A read returns the sum of known per-region counts, rounded for display ("10.2M"). During a partition each region still counts its own likes; once connectivity returns, the totals converge exactly. The per-user "have I liked this" flag, however, needs a set (an OR-set or a keyed record per user and video) so that unliking works, and uses read-your-writes: the user sees their own like immediately via optimistic UI.

17. Interview Q&A

Explain the CAP theorem. What does each letter mean, and why is "pick two" misleading?

CAP says that in a distributed system, when a network partition occurs, you cannot have both consistency and availability. Consistency here means linearizability: every read sees the most recent completed write, as if there were one copy. Availability means every non-failed node answers every request. Partition tolerance means the system keeps working despite lost messages between nodes. "Pick two" is misleading because partitions are not optional in a real network: you cannot choose to forgo P, so the real choice is C or A only during a partition. When the network is healthy there is no trade at all in CAP terms, though PACELC points out there is still a latency tradeoff. I would describe a component as CP or AP for its behaviour during a partition instead of claiming "CA."

What does PACELC add, and why is it more useful in design discussions?

PACELC extends CAP: if there is a Partition, choose between Availability and Consistency; Else, in normal operation, choose between Latency and Consistency. The second half matters more in practice because partitions are rare while every request pays the latency cost of coordination. A system that waits for a cross-region replica before acknowledging is consistent but slow; one that acknowledges locally is fast but may serve stale reads elsewhere. It lets me classify systems: Cassandra at low consistency levels is PA/EL, Spanner is PC/EC. In a design I use it to justify statements such as "reads go to the nearest replica for latency, accepting up to a second of staleness."

Define linearizability and show an example history that violates it.

Linearizability means every operation appears to take effect atomically at one point between its invocation and its response, and those points form a single order consistent with real time. So once a write completes, all later reads must see it or something newer, and once any client has seen a value, no later client may see an older one. A violating history: a write of x = 1 is in progress. Client B reads 1 and finishes. Then client C starts a read and gets 0. C began after B ended yet saw the older value, so the value went backwards in real time, which no single ordering can explain. This is easy to produce by reading from a lagging follower, and it is allowed under eventual consistency but not under linearizability.

What is the difference between linearizability and serializability?

Serializability is about transactions over possibly many objects: the result must equal some serial execution of those transactions, but that order need not match real time. Linearizability is about single-object operations and requires the order to respect real time, but says nothing about multi-object transactions. They are independent. A system with both is strictly serializable, the strongest practical guarantee, provided by Spanner and FoundationDB. In an interview I link serializability to the isolation chapter (write skew, phantoms) and linearizability to this chapter (recency, locks, uniqueness), and I warn that serializable does not imply fresh reads.

What are the session guarantees and how would you implement read-your-writes with read replicas?

The four are read-your-writes, monotonic reads, monotonic writes and writes-follow-reads; they are per-session promises that remove most user-visible oddities of eventual consistency without global coordination. To implement read-your-writes with replicas, I would have the write return a log position or version token, store it in the session or cookie, and attach it to subsequent reads. A replica serves the read only if it has applied at least that position, otherwise it waits briefly or redirects to the leader. A simpler version routes a user's reads to the leader for a short window after they write, longer than typical replication lag. Sticky routing to one replica helps monotonic reads but breaks on failover, so tokens are more robust.

Why is causal consistency interesting, and what does it cost compared with eventual?

Causal consistency guarantees that effects are never visible before their causes, such as a reply before the original post, while allowing unrelated operations to appear in any order. It is the strongest model that can remain available during a partition, so it gives a meaningful guarantee without sacrificing availability or local reads. The cost over eventual consistency is metadata and delayed visibility: every write carries dependency information such as version vectors or hybrid logical clocks, and a replica must hold back a write until its dependencies have arrived. It does not give recency, so a reader may still see old data. It suits chat and comment systems well.

What does linearizability cost, and why can't faster hardware fix it?

It costs latency and availability. To return the latest value, a read or write must contact the leader or a majority of replicas, which across regions is bounded by the speed of light: tens of milliseconds between continents, with a majority write waiting for the second-nearest replica. That is a lower bound set by network delay, not by hardware. For availability, a node that cannot reach the majority must refuse requests, and a leader failure pauses writes during election. Throughput is also bounded by a single leader per shard. So I use linearizability only where invariants demand it (money, locks, uniqueness) and keep everything else weaker.

How do you pick the consistency level for a likes counter versus an inventory count versus a bank balance?

I start from the harm of a wrong value. For likes, an error of a few is invisible and the volume is huge, so eventual consistency with a CRDT or batched counter is right, and it keeps working during partitions. For inventory, browsing counts can be stale, but the final decrement must be atomic so the last item is not sold twice, so I use a linearizable conditional update on the authoritative store, perhaps with a reservation that expires. For a bank balance, correctness dominates: linearizable per account plus serializable transactions across accounts, accepting extra latency and brief unavailability, and I show pending items as pending. The principle is the weakest model that protects the invariant.

Does a Cassandra QUORUM read plus QUORUM write give linearizability?

Not by itself. With replication factor 3, R = 2 and W = 2 satisfy R + W > N, so the sets overlap and a read sees the latest acknowledged write under normal conditions. But linearizability needs more: a concurrent read and write can still produce a history where a later read goes backwards, because a write may have reached only one replica when it fails, and different readers may see it or not. Last-write-wins timestamps from skewed clocks can also reorder writes. For operations that truly need linearizability, such as claiming a unique name, Cassandra offers lightweight transactions based on Paxos, at a higher latency.

Describe CRDTs and when you would use them.

A CRDT is a replicated data type whose merge operation is commutative, associative and idempotent, so replicas can accept updates independently, exchange state in any order with duplicates, and still converge to the same value. Examples: grow-only counters, PN-counters, observed-remove sets, and sequence types used for collaborative editing. I would use them where concurrent updates are common and a coordination round trip is unacceptable: like counts, presence, shopping carts, collaborative documents, and offline-first apps. I would not use them for invariants that need a global decision such as "only one winner" or "never below zero", which are not monotonic and need coordination, as the CALM principle explains. I also mention metadata growth and the fact that convergence is not the same as business correctness.

How would you explain stale reads to a product manager, and what UX patterns reduce the pain?

I would say: after you change something, other servers learn about it slightly later, usually within milliseconds but occasionally seconds, so someone might briefly see the old value. Then I offer patterns: optimistic UI so the actor sees their own change at once, a pending state for things that are in progress, read-your-writes routing for the user's own data, approximate numbers where exactness adds nothing, cursor-based pagination so lists do not jump, and strict checks only at commit points like checkout. Where wrong outcomes are possible, such as overselling, define a compensation like a refund and apology. This frames weak consistency as a deliberate product choice with a plan, not a bug.

Spanner is globally consistent. Doesn't that break CAP?

No. Spanner is a CP system: during a partition, the replicas that cannot reach a Paxos majority cannot commit writes, so it gives up availability in the CAP sense. It is highly available in practice because it runs many replicas across zones with very reliable private networking, so such partitions are rare, and the majority side continues. What Spanner adds is strict serializability across regions, achieved by TrueTime, a clock API with bounded uncertainty, and commit wait, which delays commits until the timestamp is safely in the past. The price is write latency of a cross-region quorum plus a few milliseconds of wait, which is the PACELC consistency-over-latency side.

18. Pitfalls checklist

  • Claiming "CA" or "we chose two of three": say CP or AP during partitions.
  • Treating "available" as uptime; in CAP it means every live node answers.
  • Confusing ACID's C with CAP's C, or serializable with linearizable.
  • Adding read replicas without addressing read-your-writes and monotonic reads.
  • Using last-write-wins with wall-clock timestamps and not noticing lost writes under clock skew.
  • Building locks or uniqueness checks on an eventually consistent store.
  • Using one consistency level for the entire system instead of per feature.
  • Assuming R + W > N alone gives linearizability.

19. Recap

  • CAP: during a network partition, a system must choose between linearizable consistency and availability; partitions cannot be opted out of, so describe components as CP or AP, never "CA."
  • PACELC adds the everyday tradeoff: without a partition, you still trade latency against consistency, because coordination across replicas costs round trips.
  • The ladder runs from linearizable, through sequential, causal, PRAM and session guarantees, to bounded staleness and eventual. Each rung down removes coordination and exposes more anomalies.
  • Linearizability is a recency guarantee on single objects; serializability is an isolation guarantee on transactions. Both together is strict serializability (Spanner).
  • Session guarantees (read-your-writes, monotonic reads and writes, writes-follow-reads) are cheap fixes for the most visible anomalies and are implemented with tokens or sticky routing.
  • Linearizability costs cross-region latency, availability during partitions and leader failovers, and single-leader throughput limits.
  • Real systems expose dials: DynamoDB strong reads, Cassandra levels with R + W > N, Spanner stale reads, MongoDB read and write concerns, Cosmos DB's five levels.
  • Choose per feature: strong for money, locks, uniqueness and the last-item decision; causal or session for chat and profiles; eventual for counters, feeds and search.
  • CRDTs and monotonic design (CALM) avoid coordination where operations merge safely; UX patterns such as optimistic UI hide the remaining staleness.
