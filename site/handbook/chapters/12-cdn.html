Content Delivery Networks (CDN)

A CDN puts copies of your content on servers all over the world, so users get data from somewhere close instead of from your data center. This chapter covers how a CDN works inside, how requests find it, how to control what it caches, how video is delivered, and what can go wrong.

1. The problem: distance and load

Suppose your servers are in Virginia, USA, and a user opens your website from Singapore. Even if your server is fast, the user's experience is limited by something you cannot optimize with code: the speed of light.

Light in an optical fiber travels at roughly two thirds of its speed in a vacuum, about 200,000 km per second. Virginia to Singapore is about 15,000 km, so one trip takes at least 15,000 ÷ 200,000 = 75 ms, and a round trip (request and reply) at least 150 ms. Real networks are slower than this, because cables do not follow straight lines and every router adds delay, so 200-250 ms is common.

That round trip is paid several times before the first byte of a page arrives:

  1. The TCP handshake needs 1 round trip.
  2. The TLS handshake (TLS 1.3) needs another round trip. (TLS 1.2 needs two.)
  3. The HTTP request and the start of the response need a third.

So the user waits for about 3 × 150 ms = 450 ms or more before anything useful appears, even if your server answers instantly. A page with 50 images multiplies this problem, although browsers reuse connections to reduce it.

There is a second problem: load. If one origin has to serve every image, video, and script to every user in the world, it needs enormous network bandwidth and many servers. The same cat photo might be sent from the origin a million times. That is wasteful and expensive.

Key idea A CDN solves both problems by serving popular content from servers that are geographically close to users. The user gets lower latency, and the origin only has to send each object to the CDN once per edge instead of once per user.

2. What a CDN is, and its parts

A Content Delivery Network is a globally distributed network of cache servers, run by a provider such as Cloudflare, Akamai, Fastly, Amazon CloudFront, or Google Cloud CDN. You point your domain at the CDN, and the CDN sits between your users and your servers.

The terms you need:

  • Origin: your own servers, or storage such as an S3 bucket, where the original content lives. It is the source of truth.
  • Edge server (edge node): a cache server run by the CDN, located close to users.
  • PoP (Point of Presence): a data center or location containing many edge servers. Large CDNs have hundreds of PoPs in many countries. Within a PoP, content is spread over many servers.
  • Routing layer: the mechanism that sends each user to a nearby healthy edge (section 3).
  • Control plane: the management side, where you set caching rules, certificates, and purge content. The edges receive their configuration from it.

A CDN is not only a cache. Modern CDNs also terminate TLS close to users, compress responses, speed up the connection to the origin, absorb attack traffic, and run small programs at the edge (sections 13 and 14). But caching is the core.

3. How a user reaches the nearest edge

Your site is www.example.com. How does a browser in Singapore end up talking to a Singapore edge, while a browser in Frankfurt talks to a Frankfurt edge, with the same name? There are two main techniques, and many CDNs use both.

3.1 DNS-based routing

When you use a CDN, your domain name (often through a CNAME record) points at a name controlled by the CDN. The CDN runs its own smart DNS servers. When a lookup arrives, the CDN's DNS looks at where the query came from and replies with the IP address of a nearby edge that is healthy and not overloaded. A user in Singapore gets one IP, a user in Frankfurt gets another.

The weakness: the CDN's DNS sees the location of the user's DNS resolver, not the user. Usually they are close (an ISP resolver), but if someone uses a public resolver in another country, they may be sent to a poorly placed edge. An extension called EDNS Client Subnet lets the resolver pass part of the user's address along, which fixes this where supported. Also, DNS answers are cached for their TTL, so changes (such as removing a failed edge) take effect slowly. CDNs use short TTLs, often tens of seconds, to reduce this.

3.2 Anycast routing

With anycast, the CDN announces the same IP address from many PoPs at once, using the internet's routing protocol (BGP). Each router on the internet forwards traffic toward the "closest" announcement by network path. So a packet to 203.0.113.10 from Tokyo arrives in the Tokyo PoP, and one from Frankfurt arrives in Frankfurt, with no special DNS logic.

Benefits: failover is quick, because if a PoP stops announcing the address (it fails or is taken down), routing moves traffic to the next-closest one within seconds. It also spreads DDoS attack traffic over many PoPs, because the attackers' packets go to whichever PoP is nearest to each of them. The caveat: "closest" means fewest network hops by routing policy, not always the lowest latency or the shortest distance, and a routing change in the middle of a long TCP connection could, rarely, send later packets to a different PoP. CDNs engineer around this.

Interview tip A clear short answer to "how does the user get to the nearest edge?" is: "The CDN either returns a nearby edge's IP from its DNS based on the resolver's location, or announces one anycast IP from every PoP so the internet routes users to a close one. Many CDNs combine both."

4. The life of a request: hit and miss

Once the user is at an edge server, what happens depends on whether the edge already has the content. The two cases look like this:

4.1 What the edge checks on every request

  1. Is there an entry for this cache key? (Section 8 covers the key.) If not, it is a miss.
  2. Is the entry still fresh? The entry carries a lifetime from the origin's response headers. If the lifetime has not passed, it is a hit.
  3. If it has expired, the edge does not have to download the whole object again. It sends a conditional request to the origin ("send it only if it changed since version X"). If unchanged, the origin answers 304 Not Modified with no body, and the edge refreshes the entry's lifetime cheaply.

4.2 Request collapsing

Imagine a new video thumbnail goes live and 5,000 users request it within one second at the same edge, before it is cached. A naive edge would send 5,000 requests to the origin. A good edge uses request collapsing (also called request coalescing): it sends one request to the origin and holds the other 4,999 until the answer arrives, then answers them all from it. This protects the origin from the stampede problem described in Chapter 14.

4.3 How to tell what happened

CDNs add response headers that help debugging. Age is standard and shows how many seconds the copy has been in cache. Most CDNs also add a vendor-specific header showing hit or miss (for example X-Cache: HIT, or CF-Cache-Status: HIT on Cloudflare). When something is not being cached as expected, these headers are the first thing to check.

5. Pull vs push, and what the origin can be

5.1 Pull CDN (the common model)

The CDN fetches content from your origin on demand, the first time someone asks for it (the miss flow in section 4). You do not upload anything to the CDN. You only configure the origin address and rules. This is simple, and the CDN only holds what users actually request. The cost is that the first request at each edge is slow, and an edge that has evicted or never seen an object must fetch again.

5.2 Push CDN

You upload content to the CDN's storage ahead of time, and the CDN distributes it. Nothing goes to your origin at request time, so there are no cold misses for pushed content. It suits content that changes rarely and is large, such as software releases, game patches, or a scheduled video launch. The cost: you have to manage uploads and removals yourself, and you may pay to store content that nobody requests.

5.3 What the origin can be

  • An application server or load balancer, for dynamic pages and API responses.
  • An object store such as Amazon S3 or Google Cloud Storage, the usual choice for images, video, and downloads. It is cheap, durable, and scales well. Chapter 21 covers object storage.
  • Several origins at once, with rules like "/api/* goes to the app servers, /images/* goes to S3".
Protect the origin from direct access If anyone can request your origin directly, an attacker can bypass the CDN (and its protection) and overload it. Lock the origin so it only accepts traffic from the CDN, by allowing only the CDN's IP ranges, requiring a secret header that the CDN adds, or using the CDN's private connection to the origin.

7. Controlling caching with HTTP headers

Your origin tells the CDN (and browsers) how to cache each response, using HTTP headers. The most important header is Cache-Control. Learn these directives; interviewers often probe them.

s-maxage=NLike max-age, but for shared caches only (CDNs). It overrides max-age for them. This lets you cache long at the CDN and short in browsers.

# A public product page: browsers 1 minute, CDN 5 minutes, serve stale for 30 s while refreshing
Cache-Control: public, max-age=60, s-maxage=300, stale-while-revalidate=30

# A logged-in account page: never share
Cache-Control: private, no-store

7.1 Validation: ETag and Last-Modified

When a cached copy expires, it may still be correct. To avoid re-downloading it, the origin includes a validator: an ETag (an opaque version identifier, often a hash of the content) or a Last-Modified date. When the entry expires, the edge asks "do you still have version "abc123"?" using If-None-Match: "abc123". If yes, the origin replies 304 Not Modified with an empty body. This saves bandwidth, though it still costs a round trip to the origin.

7.2 The Vary header

Sometimes the same URL gives different responses depending on a request header, for example the compression the client accepts (Accept-Encoding: br vs gzip). The origin lists those headers in Vary (for example Vary: Accept-Encoding), and the CDN stores a separate variant for each distinct value. This is correct and useful. But a careless Vary can destroy caching: Vary: Cookie or Vary: User-Agent makes every different cookie or browser string a separate copy, so almost nothing is shared. Section 8 shows this with a simulator.

8. Cache keys: what makes two requests "the same"

The edge decides hit or miss by looking up a cache key built from the request. By default, the key is made from the host and the URL path, often including the query string. Whatever you include in the key splits the cache into more entries. Whatever you leave out merges requests into one entry.

That choice is the most common reason a CDN performs badly:

  • Including too much (every cookie, the whole User-Agent, tracking parameters like ?utm_source=...) means requests that should share a copy each get their own, so hit ratio collapses.
  • Including too little (ignoring a query parameter that actually changes the response, such as ?lang=fr or ?width=300) means users get the wrong content. This is a correctness bug, not just a performance one.

The right approach is to build the key from only what changes the response: ignore tracking parameters, normalize parameter order, strip cookies for static content, and normalize Accept-Encoding into a few values.

Try it: cache-key simulator

Twelve users request the same image, /img/logo.png, but with different tracking parameters, cookies, and browsers. The image itself is identical for everyone. Choose what goes into the cache key and see how many separate copies the CDN must keep.

9. Tiered caching and the origin shield

A large CDN has hundreds of PoPs. If a new object is requested at 200 PoPs for the first time, a simple setup sends 200 separate requests to the origin, one from each PoP. For a heavy video or a purged hot object, that is a heavy load on the origin.

Tiered caching adds layers between the edges and the origin. Edges that miss ask a larger regional cache first, and regional caches that miss ask a single origin shield (a designated PoP close to the origin). Only the shield talks to the origin. The shield also benefits from request collapsing, so even if every edge asks at once, the origin sees one request.

Tiered caching also raises the overall hit ratio, because a less popular object that the small edge cache evicts may still live in the larger regional cache. The tradeoff: a miss at the edge now takes one or two extra internal hops, so it is slightly slower for rarely used content, but the origin is far better protected.

10. Invalidation: changing content that is already cached

Once content is spread over hundreds of PoPs and into browsers, how do you change it? This is the same hard problem as in Chapter 13, with a much bigger blast radius. There are three approaches, and good systems use the first as the default.

10.1 Versioned URLs (the best approach)

Never change what a URL points to. Instead, put a version or content hash in the file name: app.3f9c1a.js, logo-v7.png. When the file changes, the build produces a new name, and the HTML that references it is updated. The old URL stays cached harmlessly until it expires, and the new URL starts fresh at every edge. There is nothing to invalidate. You can cache these files for a year with immutable.

The one thing that must not be long-cached is the entry point that names the versioned files (the HTML page, or a small manifest). Give it a short TTL or revalidation.

10.2 Short TTLs

For content that cannot have versioned names (a news front page, a price list), choose a short TTL (seconds to minutes) and combine it with stale-while-revalidate, so users always get an instant answer and fresh content arrives soon after. Staleness is bounded by the TTL.

10.3 Purge (explicit invalidation)

You can tell the CDN to remove content now, through its API, by exact URL, by prefix (/images/products/*), or by tag. Tag-based purge (called surrogate keys or cache tags) is powerful: the origin labels responses with tags like product-123 and category-shoes, and one purge call for product-123 removes every cached object, page or API response, that mentions that product.

Know the limits of purging:

  • It is not instant everywhere. Propagation to all PoPs takes from about a second to a few minutes depending on the provider. For a short window, some users still see the old version.
  • It can be rate-limited or billed. Some providers charge for purge requests beyond a free quota.
  • Purging does not touch browsers. Copies already in users' browsers remain until their max-age passes. Versioned URLs avoid that problem.
  • A purge-all is dangerous. It empties the cache, and every request becomes a miss at once, which can overload the origin (section 16).
Rule of thumb Use versioned URLs for assets, short TTL with stale-while-revalidate for pages, and tag-based purge for content that must update quickly (such as a corrected price or a takedown). Treat purge as an emergency tool, not the main strategy.

11. Large files and video streaming

Video is the largest share of internet traffic, and CDNs exist largely to carry it. Delivering a two-hour movie as one giant file would be a poor experience: the user must wait for a big download, cannot easily skip ahead, and cannot adapt if their network slows down. Modern streaming solves this with segmented adaptive streaming.

11.1 How adaptive streaming works

  1. Encode several quality levels. The video is processed into several versions, called renditions (for example 1080p at 5 Mbps, 720p at 3 Mbps, 480p at 1.2 Mbps).
  2. Cut each rendition into short segments of a few seconds each (commonly 2 to 10 seconds), stored as ordinary small files.
  3. Publish a manifest. A small text file (a .m3u8 playlist in HLS, an .mpd file in MPEG-DASH) lists the renditions and the URL of every segment.
  4. The player downloads the manifest, then fetches segments one after another. After each segment, it measures how fast the download was and chooses the quality for the next segment. This is adaptive bitrate (ABR).

11.2 Why this fits a CDN so well

  • Each segment is a small, immutable, cacheable file. Millions of viewers watching the same show request the same segments, so the hit ratio is very high.
  • Segments can be cached for a long time (they never change), while the manifest of a live stream is cached for only a second or two, since new segments keep being added.
  • The origin only has to produce each segment once per tier, no matter how many viewers there are.
  • Popular content can be pre-positioned (pushed or pre-warmed) into edges before a big release. Large providers go further and put their own cache appliances inside ISP networks, so traffic never crosses the wider internet. Netflix's Open Connect is the best-known example.

11.3 Other large files

For large downloads such as software installers, the CDN supports byte-range requests (Range: bytes=0-1048575), so a client can resume a download or fetch parts in parallel. Some CDNs cache large objects in fixed-size slices, so a request for one part does not require the whole file to be cached first.

12. Private and protected content

A CDN edge is a public server, so how do you serve content that only certain users may see, such as a paid video or a private photo? You cannot rely on the origin checking each request, because the point of the CDN is that the origin is not contacted. The answer is for the origin to issue a signed URL, and for the edge to verify it.

A signed URL contains an expiry time and a signature, typically an HMAC computed with a secret key shared between your app and the CDN. The edge recomputes the signature, and rejects the request if it does not match or if the time has passed. The expiry limits how long a leaked link works (often minutes to hours). Related tools:

  • Signed cookies: the same idea but for many files, such as all segments of a video, so you do not need to sign every URL.
  • Geo-restriction: the edge blocks or allows requests by country (for licensing rules).
  • Hotlink protection: reject requests whose Referer is another website.
  • Token binding: include the client IP or a session ID in what is signed, so a leaked link is useless elsewhere.

13. Security benefits and risks

13.1 What a CDN adds

  • TLS termination near the user. The slow TLS handshake happens over a short distance, and the edge keeps warm, reusable connections to the origin.
  • DDoS absorption. A CDN's network capacity is far larger than a single site's. Attack traffic is spread across many PoPs and filtered at the edge, so it never reaches the origin. Anycast helps here.
  • Web Application Firewall (WAF) and bot management. The edge can inspect requests and block common attacks, such as SQL injection, and suspicious bots, before they reach your servers.
  • Hiding the origin. Users see the CDN's addresses, not yours, as long as you lock the origin down (section 5).
  • Rate limiting at the edge, which stops abusive clients cheaply.

13.2 Risks to understand

  • Cache poisoning. If the response depends on a request header that is not part of the cache key, an attacker can send a request with a malicious value in that header, cause the origin to produce a harmful response, and have the edge cache it and serve it to everyone. The defense is to make sure every input that changes the response is in the key (or ignored by the origin).
  • Web cache deception. An attacker tricks a user into visiting a URL like /account/settings/fake.css. If the CDN decides what to cache by file extension, it may cache the private page. The defense is to base caching on the origin's Cache-Control headers, not just on the URL.
  • Caching personalized responses by mistake (section 6).
  • A third party in the path. The CDN sees all your traffic (it terminates TLS), so provider security and trust matter.

14. Edge compute and dynamic content

Not all content can be cached, but a CDN can still help with it.

14.1 Dynamic acceleration

For responses that cannot be cached (a personalized API call), the request still goes to the origin, but the CDN makes the trip faster. The user connects to a nearby edge (a short TLS handshake), and the edge forwards the request to the origin over an already-open, optimized connection, sometimes using better routes than the public internet. This can reduce latency noticeably even with a 0% hit ratio.

14.2 Edge compute

Many CDNs let you run small pieces of your own code at the edge: Cloudflare Workers, Lambda@Edge and CloudFront Functions, Fastly Compute. Typical uses:

  • Rewriting URLs and redirects without contacting the origin
  • A/B testing and feature flags, deciding a variant at the edge
  • Authentication checks, such as validating a token before serving cached content
  • Resizing and converting images on demand (for example to WebP or AVIF) and caching each result
  • Assembling pages from cached fragments with a small personalized part
  • Geo-based decisions, such as language or region

The limits: edge code runs under tight time and memory limits, has limited access to databases (which are far away), and is harder to debug. Use it for light logic, not for heavy business processing.

14.3 Other transformations at the edge

Compression (gzip, Brotli), minification, image optimization, and protocol upgrades (serving HTTP/2 or HTTP/3 to browsers even if the origin only speaks HTTP/1.1) are commonly handled by the CDN without any changes to your origin.

17. Choosing a CDN, comparing it to other components, and cost

17.1 How a CDN differs from similar components

ComponentMain jobDifference from a CDN
Reverse proxy / load balancerDistribute traffic to your servers in one data center or regionIt sits near your servers. A CDN sits near your users, in many locations.
Application cache (Redis)Speed up your app's data access inside your data centerIt is used by your servers, not by end users' requests directly.
Browser cacheAvoid repeat downloads on one deviceOne user only. A CDN is shared by all users near an edge.

They work together: browser cache first, then the CDN, then your load balancer and servers, then Redis, then the database.

17.2 Choosing

Compare providers on: PoP coverage where your users are, performance for your content type, features you need (purge speed and tag support, edge compute, WAF, video features), the cost model, support, and operational tools. Large systems sometimes use multiple CDNs to improve reliability and negotiate cost, with a traffic manager that steers users between them, at the price of added complexity: configuration and rules must be duplicated and kept in sync.

17.3 Cost

You usually pay for data transferred out (per GB, with lower rates at higher volume), requests, and extras such as edge compute, purges, and advanced security. CDN transfer is often cheaper per GB than serving the same bytes from your own cloud data center, so a CDN frequently reduces the bill, besides making things faster. A high hit ratio is the biggest cost lever. Origin egress fees, which you would otherwise pay on every byte, drop in proportion.

18. Worked example: a global photo-sharing site

Problem. Design the image delivery for a photo-sharing service with users worldwide. There are 100 million image views per day, the average image is about 200 KB, and some photos are private.

Step 1: Estimate the load

  • Requests: 100,000,000 ÷ 86,400 seconds ≈ 1,160 requests per second on average. Using a 3× peak factor, about 3,500 per second.
  • Data: 100,000,000 × 200 KB = 20 TB per day, which is about 1.85 Gbps on average (20 × 10¹² bytes × 8 ÷ 86,400 s), and around 5.5 Gbps at peak.

Serving this from one region is possible, but every user outside it gets slow images, and the origin bears the full bandwidth. A CDN is clearly the right tool.

Step 2: Choose the architecture

  • Origin: original photos stored in an object store (S3 or similar), which is durable and cheap.
  • CDN: a pull CDN in front of the object store, with the origin locked so only the CDN can read it.
  • Image variants: users on phones need small versions. Generate resized variants (thumbnail, medium, large), either at upload time or on demand at the edge, and name them with the size and a content hash, such as /img/9f3c/medium.webp.
  • Cache headers for public photos: Cache-Control: public, max-age=31536000, immutable, since each URL's content never changes. Editing a photo creates a new hash and URL.
  • Cache key: only path and the size or format parameter. Ignore tracking parameters and cookies. Normalize Accept-Encoding, and choose the image format (WebP or AVIF) by Accept using a small, deliberate Vary.
  • Private photos: the app checks the user's permission and returns a signed URL that expires in, say, 10 minutes. The edge verifies it. For privacy, set the shared-cache lifetime shorter and include the signature in the key, or serve through a separate path.
  • Tiering: enable an origin shield so the many edges do not each fetch from the origin.

Step 3: Check the numbers

Assume a 95% edge hit ratio (reasonable for hot, immutable photos, though the long tail of old photos lowers it). Then the origin sees about 5% of requests and bytes:

  • Origin requests: 3,500 × 0.05 ≈ 175 per second at peak.
  • Origin bandwidth: about 0.09 Gbps on average, about 0.28 Gbps at peak, instead of 5.5 Gbps. With the shield, repeated fetches of the same object from different regions are cut further.

The long tail matters: many old photos are rarely viewed, so they miss at the edge and the regional tier. Their fetch is a normal origin read, and the object store handles that load easily.

Step 4: Failure and operations

  • Origin down: stale-if-error keeps the previous copies serving. Photos are immutable, so stale is the same as fresh.
  • CDN issue: a second CDN with DNS failover for critical traffic, if the business needs it.
  • A takedown (a photo must disappear): use a tag-based purge on the photo's tag, and revoke the signed URL path.
  • Monitoring: hit ratio, byte hit ratio, origin request rate, TTFB from several regions, and error rates.
What the interviewer wants to hear You estimated the load, chose pull plus object-store origin, designed versioned URLs, protected private content with signed URLs, kept the cache key tight, protected the origin with a shield and locked access, and said what you would monitor and how it fails.

19. Common interview questions

What problem does a CDN solve?

It reduces latency by serving content from servers close to the user, which shortens the round trips for connection setup and data. It also offloads the origin, because popular content is sent from the origin to the CDN once and then delivered to many users from the edge. It improves availability and absorbs attack traffic as well.

How does a user get routed to the nearest edge?

Through DNS-based routing, where the CDN's DNS returns the address of a nearby healthy edge based on the resolver's location, or through anycast, where all PoPs announce the same IP and internet routing sends users to a close one. Many CDNs combine them.

Pull vs push CDN: when would you use each?

Pull is the default. The CDN fetches content on the first request, it needs no upload management, and it only stores what users request. Push is for large, predictable, rarely changing content such as software releases or a scheduled video launch, where you want it on the edges before the first request and want no cold misses.

How do you update content that is already cached around the world?

Best is versioned (content-hashed) URLs, so a change is a new URL and nothing needs invalidating. For mutable pages, use short TTLs with stale-while-revalidate. For urgent changes, use a tag-based purge through the CDN's API, remembering that propagation is not instant and that purges do not clear browser caches.

What is the difference between max-age and s-maxage?

max-age applies to every cache, including browsers. s-maxage applies only to shared caches such as CDNs and overrides max-age for them. Together they let you cache for a long time at the CDN, where you can purge, and a short time in browsers, where you cannot.

What is a cache key, and why does it matter?

It is the identifier the edge uses to decide whether two requests are the same. Including too many things (cookies, tracking parameters, raw User-Agent) splits the cache into many entries and destroys the hit ratio. Leaving out something that changes the response serves wrong content. The key should contain exactly what changes the response.

What is an origin shield?

A designated cache tier close to the origin that all other edge and regional caches consult before contacting the origin. It collapses many simultaneous misses from different PoPs into a single origin request, which protects the origin and raises the overall hit ratio.

How does a CDN deliver video?

By adaptive bitrate streaming (HLS or DASH). The video is encoded at several qualities and cut into short segments, a manifest lists them, and the player chooses the quality of each next segment based on measured network speed. Each segment is a small immutable file, so it caches well and viewers of the same content share it.

How do you serve private content through a CDN?

The application authenticates the user and issues a signed URL (or signed cookie) containing an expiry time and a signature. The edge verifies the signature and expiry without contacting the origin. Keep lifetimes short, and keep the origin accessible only from the CDN.

What could go wrong if you put a CDN in front of a dynamic site?

Personalized responses could be cached and shown to other users, a poorly chosen cache key could mix up content, stale data could linger after updates, and a purge-all could cause every request to miss and overload the origin. You prevent these with Cache-Control: private for personalized content, careful keys and Vary, short TTLs, versioned URLs, and an origin shield.

If the CDN has a 95% hit ratio, is the origin safe?

Not necessarily. At 95% the origin still sees 5% of the traffic, and a mass-miss event (purge, deployment, new viral object) can send 100% to it briefly. The origin must be sized for the peak miss rate, protected by a shield and request collapsing, and able to degrade gracefully.

20. Recap

  • Distance causes latency, and connection setup multiplies it. A CDN puts cached copies on edge servers near users, and it also offloads the origin.
  • Users are routed to the nearest edge by DNS-based routing, anycast, or both.
  • A hit is served at the edge. A miss goes to the origin, is stored, and is returned. Request collapsing prevents a stampede of identical misses.
  • Pull is the default. Push is for big, predictable releases. Always lock the origin so it only accepts CDN traffic.
  • Control caching with Cache-Control (max-age, s-maxage, private, no-store, stale-while-revalidate), validators (ETag), and Vary.
  • The cache key must contain exactly what changes the response. Too much kills the hit ratio, too little serves wrong content.
  • Tiered caching and an origin shield protect the origin and raise the hit ratio.
  • Invalidate with versioned URLs first, short TTLs next, and purge only as a targeted tool.
  • Video uses segmented adaptive streaming, so every segment is a cacheable small file.
  • Protect private content with signed URLs, never cache personalized responses as shared, and watch for cache poisoning and a mass-miss overload.
