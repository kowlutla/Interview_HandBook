Forward and Reverse Proxies

A proxy is a server that sits in the middle of a conversation and talks on behalf of one side. This chapter explains the two directions a proxy can face, what a reverse proxy does inside (event loops, connection pools, buffers, timeouts), how headers carry the real client identity, how WebSocket and gRPC pass through, and how proxies fail and how to design for it.

1. What a proxy is and why it exists

The word proxy means "someone who acts on your behalf". In networking, a proxy is a server that receives a request from one party, then makes a request of its own to another party, then passes the answer back. To the party on each side, the proxy is the other end of the conversation. The client believes it is talking to a server. The server believes it is talking to a client. In between, the proxy is free to look at the traffic, change it, remember it, refuse it, or send it somewhere different from where it seemed to be going.

That freedom is the whole point. A plain network cable or a router only moves packets. A proxy understands a protocol (usually HTTP, sometimes raw TCP) well enough to make decisions: "this request is for the images service", "this user has exceeded their quota", "I already have this answer saved", "this response is large, so I will compress it". Putting such a decision point on the path means you can add behavior without touching either the client or the server.

There are two directions a proxy can face, and the difference matters more than anything else in this chapter:

  • A forward proxy acts on behalf of clients. The clients know about it (or the network forces them through it), and the servers on the internet usually do not know the original clients exist. Think of a company network where every employee's browser goes out through one gateway.
  • A reverse proxy acts on behalf of servers. The clients usually do not know it exists. They think they are talking to www.example.com, and behind that name a proxy fans their requests out to many backends. This is the one you will draw in nearly every system design interview.
Key idea A forward proxy hides and controls clients from the servers they visit. A reverse proxy hides and protects servers from the clients that visit them. The software can be identical (Nginx, Envoy and HAProxy can all do both); what differs is whose interests it serves and who configured it.

2. Forward proxies

A forward proxy is configured by or for the client side. An office has a gateway; the browsers are told (through a setting or an automatic configuration file) "send your web requests to proxy.corp.example:3128". The browser then sends the request to the proxy and asks it to fetch the page. The proxy makes the outbound connection to the real website and relays the answer. The website sees the proxy's address, not the employee's laptop.

2.1 What forward proxies are used for

  • Egress control. "Egress" means traffic leaving your network. A company wants to decide which outside sites its machines may reach. If every machine can only get to the internet through the proxy (the firewall drops everything else), the proxy becomes a single place to allow or deny destinations by domain, category, or user. This is also how servers in a locked-down production network are allowed to call, say, only the payment provider's API and an update server, and nothing else. It limits what malware or a compromised service can reach, and stops data leaving to unknown hosts.
  • Anonymity and address hiding. Because the destination sees the proxy's IP address, the real client address is hidden. Privacy services, VPN-like products and scraping fleets use proxies for this. It is not perfect anonymity: the proxy operator can see everything, and the request itself can still carry identifying cookies or headers. An anonymous proxy simply moves trust from the destination to the proxy.
  • Caching. If 500 employees download the same operating system update, a caching forward proxy fetches it once and serves the other 499 from local disk, saving bandwidth and speeding up downloads. Squid is the classic example. Today, with most traffic encrypted, this works well for large public files and package mirrors, and far less for general web browsing.
  • Filtering and inspection. The proxy can block malware sites, scan downloads for viruses, enforce policies such as "no social media at work", and log every access for audit. To inspect encrypted traffic it must perform TLS interception: it terminates the employee's TLS connection using a certificate signed by a company certificate authority that the laptops have been configured to trust, reads the plain traffic, then opens a separate TLS connection to the real site. This works but is invasive, breaks applications that pin certificates, and makes the proxy a very valuable target.
  • Access from restricted networks and rate control. A proxy in a specific country lets a client appear to come from there, and a pool of proxies lets a scraper spread requests across many source addresses (which is the thing sites often try to defend against).
  • Authentication and accounting. The proxy can demand credentials (the Proxy-Authorization header, answered with status 407 when missing) and count usage per user or team.

2.2 How a forward proxy handles HTTP and HTTPS differently

For plain http:// traffic, the client sends the proxy a request whose request line contains the full URL, because the proxy needs to know where to go: GET http://news.example/index.html HTTP/1.1. The proxy can read and cache the whole exchange, because nothing is encrypted.

For https:// traffic the client does not want the proxy to read anything. It uses the HTTP CONNECT method to ask the proxy to set up a raw tunnel. The browser sends CONNECT news.example:443 HTTP/1.1. The proxy opens a TCP connection to that host and port, replies 200 Connection established, and from that moment simply copies bytes in both directions without understanding them. The browser then performs its TLS handshake through the tunnel directly with the destination server. The proxy sees only the destination host name and port (and the amount of data), never the paths, headers or bodies. That is why a forward proxy that is not doing TLS interception can allow or block by domain but cannot filter by URL path or scan content.

2.3 SOCKS versus HTTP proxies

An HTTP proxy understands HTTP. It can read request lines, add headers, cache, and apply rules by URL for plain HTTP, and it uses CONNECT for everything else. SOCKS (version 5 is the one used today) is a lower-level, protocol-agnostic proxy protocol. The client opens a connection to the SOCKS server, negotiates an authentication method, and then says "connect me to this address and port" (the address can be an IP or a domain name). After that the SOCKS server just relays bytes. SOCKS does not know or care whether those bytes are HTTP, SSH, a database protocol or email, and SOCKS5 can also relay UDP datagrams. The cost of that generality is that it cannot cache or inspect HTTP, because it never parses it.

2.4 Explicit versus transparent proxies

An explicit proxy is one the client is configured to use. The client knows, so it addresses the proxy and (for HTTP) puts full URLs on the request line. Environment variables such as HTTPS_PROXY, browser settings or an automatic proxy configuration script do this. Because the client cooperates, explicit proxies can authenticate users and are the cleanest to operate.

A transparent proxy (also called an intercepting proxy) is one the client does not know about. The network, for example a router or firewall, quietly redirects outgoing port 80 or 443 packets to the proxy. The proxy then recovers the intended destination from the original packet's address, or from the HTTP Host header or the TLS SNI (the server name sent at the start of TLS). Transparent mode needs no client configuration, which is attractive for guest Wi-Fi and ISPs. The downsides: it cannot easily authenticate individual users, it complicates HTTPS (interception requires a trusted CA or the proxy can only look at SNI), it can break clients that detect it, and it creates confusing failures because nobody on the client side realizes a proxy is involved.

The same words are used on the reverse side. A reverse proxy is always transparent to clients in the sense that clients just resolve a name and connect. Do not confuse "transparent" in that casual sense with the formal forward-proxy meaning above; the formal term is about whether the client's configuration includes the proxy.

Interview tip In a system design interview, forward proxies come up in two places: controlling outbound calls from a service tier (an "egress proxy" that allows only approved destinations and gives you one place to log and rate-limit calls to third parties), and as the background for explaining what a reverse proxy is not. Spend a sentence on them, then move to the reverse proxy.

3. Reverse proxies

A reverse proxy is the front door of a service. Public DNS for api.example.com points at it. Clients open connections to it and send requests as if it were the real server. The proxy chooses a backend (also called an upstream), forwards the request, gets the response, and returns it. Backends can be on private addresses that are not reachable from the internet at all.

Almost every production web system has one, even if it is called something else (the L7 load balancer, the ingress controller, the edge gateway, the "front proxy"). The reason is that it is the natural place to put work that does not belong in every application server and that is cheaper to do once at the edge. The following list covers what that work is.

3.1 What a reverse proxy does for you

  • TLS termination. The proxy holds the certificate and private key, performs the expensive TLS handshake with the client, and talks plain HTTP (or a fresh internal TLS connection) to the backend. Certificates are managed and rotated in one place instead of on every application server, and the application code never touches cryptography. Chapter 3 covers the handshake. When the internal network is not trusted you re-encrypt to the backend (TLS re-encryption) or use mutual TLS inside a mesh (Chapter 50).
  • Routing. Using the host name, URL path, headers or cookies, the proxy picks which backend pool gets the request: /api/* goes to the API service, /static/* to a storage bucket, admin.example.com to the admin app. This lets one public address front many internal services and lets you move a path from the old system to a new one without any client change, which is exactly what the strangler fig migration needs (Chapter 44).
  • Load balancing across backends. It spreads requests over many identical servers and avoids unhealthy ones. Algorithms and health checks are in Chapter 9; an L7 load balancer is a reverse proxy with a strong balancing feature set.
  • Compression. Text responses (HTML, JSON, JavaScript) compress to a fraction of their size with gzip or Brotli. Doing it in the proxy keeps application servers focused on business logic. Compression costs CPU, so proxies compress only types and sizes where it pays off and skip already compressed content such as JPEG images or video.
  • Caching. The proxy can keep copies of responses and answer repeat requests without bothering the backend. It is a small, close version of what a CDN does (Chapter 12); section 10 covers the rules.
  • Buffering slow clients. A phone on a poor connection takes seconds to upload a request or download a response. Without help, your application thread would sit waiting on that slow socket. The proxy absorbs the slow transfer on its side so the backend can finish in milliseconds. Section 7 explains this, because it is one of the strongest reasons to have a proxy at all.
  • Connection pooling and multiplexing to upstreams. Thousands of clients connect to the proxy, but the proxy talks to each backend over a small set of long-lived, reused connections. This avoids a TCP and TLS handshake per request and keeps backend connection counts small and predictable (section 6).
  • Security shield. Backends sit on private addresses. The proxy can drop malformed requests, enforce size and rate limits, require authentication, hide server version details and internal topology, apply a web application firewall, and absorb floods before they reach the application.
  • Canary and weighted routing. The proxy can send 1% of traffic to a new version, or only requests carrying a particular header or cookie, and watch error rates before widening the rollout (Chapter 43).
  • Protocol translation. It can accept HTTP/2 or HTTP/3 from browsers and speak HTTP/1.1 to old backends, or turn HTTPS into HTTP, or gRPC-Web into gRPC.
  • Observability. Every request passes through it, so it is the cheapest place for access logs, request IDs, latency histograms and error counts, even for backends you cannot modify.

4. Reverse proxy vs load balancer vs API gateway vs CDN

These four terms overlap, and interviewers like to ask how they differ. The honest answer is that they are roles, and one piece of software often plays several. A useful way to separate them is by the extra job each adds on top of the common core of "receive a request, pick a target, forward it".

The overlap is real. A CDN edge node is a reverse proxy with a big cache run by someone else. An API gateway is a reverse proxy with API-management features. An L7 load balancer is a reverse proxy whose headline feature is backend selection. Nginx can be deployed as any of the four on different days. The mental model that keeps you out of trouble:

  • Reverse proxy is the general mechanism: a server that accepts requests on behalf of others.
  • Load balancer emphasizes spreading and resilience across many identical backends.
  • API gateway emphasizes policy about who may call which API and how much, plus composition of backend services into client-friendly APIs.
  • CDN emphasizes geography and caching, and is mostly operated by a vendor.
Watch out Do not draw four separate boxes in an interview unless each earns its place. Say what each one is for. For a small service, "a load balancer doing TLS termination in front of the app servers" is a complete answer. Add a gateway when you need per-client auth and quotas across many services, and a CDN when you have static content or global users.

5. How a reverse proxy works inside

The reverse proxy handles a huge number of simultaneous connections, most of which are idle most of the time: a client opens a connection, sends a request, then waits for a response, or waits for the next click. A design that dedicates one thread to each connection (the classic Apache prefork or thread-per-request model, discussed in Chapter 8) spends memory on thousands of mostly sleeping threads and burns CPU switching among them. Modern proxies instead use an event loop.

5.1 The event loop and worker processes

An event loop is a single thread that asks the operating system "tell me which of my sockets are ready". Linux provides epoll (BSD has kqueue) for this: you register thousands of sockets, and one call returns just the ones that have data to read or room to write. The thread then handles each ready socket briefly, never blocking, and goes back to ask again. Because it never waits on a single slow connection, one thread can juggle tens of thousands of connections. This is why a small Nginx instance can hold 50,000 open connections using only a few hundred megabytes of memory.

One event loop uses one CPU core, so to use all the cores the proxy runs several of them:

  • Nginx has one master process (reads configuration, starts and replaces workers, handles signals) and several worker processes, typically one per CPU core (worker_processes auto;). Each worker runs its own event loop. The kernel spreads new connections across workers, and workers share nothing important, so there is little locking. A reload starts new workers with the new configuration and lets old workers finish their in-flight requests, which gives zero downtime configuration changes.
  • Envoy uses one main thread for control tasks and a set of worker threads, each with its own event loop. A connection is assigned to one worker for its whole life. Because of this, the connection pools to upstreams are per worker, so total upstream connections equal roughly (workers × pool size).
  • HAProxy runs a number of threads (nbthread) in one process, again each running an event loop, with configuration split into frontends (what it listens on) and backends (the server pools it forwards to).

5.2 The life of one request

  1. Accept. A worker accepts the client's TCP connection. If TLS is configured, it does the handshake (cheaper on repeat visits thanks to TLS session resumption).
  2. Read the request. It reads and parses the request line and headers into memory, enforcing size limits and a header read timeout. A request body, if any, is read into a buffer in memory and spilled to a temporary file on disk when it is large (unless streaming is configured).
  3. Match a rule. It matches host, path and headers against routing rules, applies authentication or rate limits, and may answer straight from cache, never involving a backend.
  4. Pick an upstream. A balancing algorithm chooses one backend that the health checks consider alive.
  5. Get a connection. It takes an idle keep-alive connection to that backend from the pool, or opens a new one (a connect timeout applies).
  6. Send and wait. It writes the request, then waits for the response, bounded by a read timeout between bytes or an overall request timeout.
  7. Return the response. It buffers or streams the response to the client, adds or removes headers, perhaps compresses it, writes a log line, and returns the upstream connection to the pool.

5.3 Sample configurations

The three snippets below show the same idea in three products: a public listener, a pool of backends, keep-alive reuse and explicit timeouts. They are trimmed for clarity; real files have more settings. First, Nginx.

worker_processes auto;                 # one worker per CPU core
events { worker_connections 20000; }   # max sockets per worker

http {
  upstream app_pool {
    least_conn;                        # balancing algorithm
    server 10.0.1.11:8080 max_fails=3 fail_timeout=10s;
    server 10.0.1.12:8080 max_fails=3 fail_timeout=10s;
    keepalive 64;                      # idle upstream connections kept per worker
  }

  server {
    listen 443 ssl http2;
    server_name api.example.com;
    ssl_certificate     /etc/ssl/api.crt;
    ssl_certificate_key /etc/ssl/api.key;

    client_header_timeout 10s;         # slowloris defence
    client_body_timeout   15s;
    client_max_body_size  10m;
    send_timeout          30s;

    location /api/ {
      proxy_pass http://app_pool;
      proxy_http_version 1.1;          # needed for upstream keep-alive
      proxy_set_header Connection "";  # do not forward "close"
      proxy_set_header Host $host;
      proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
      proxy_set_header X-Forwarded-Proto $scheme;
      proxy_connect_timeout 2s;
      proxy_read_timeout    30s;
      proxy_next_upstream error timeout http_502 http_503;
      proxy_next_upstream_tries 2;
    }
  }
}

Envoy configures the same idea as listeners (where it accepts), routes (how a request maps to a cluster) and clusters (the upstream pools with health checking, circuit breakers and retries). A fragment of the cluster and route sections:

- name: app_pool
  type: STRICT_DNS
  lb_policy: LEAST_REQUEST
  connect_timeout: 2s

    consecutive_5xx: 5

HAProxy separates frontends from backends and is very explicit about timeouts:

defaults
  mode http
  timeout connect 2s
  timeout client  30s        # idle or slow client
  timeout server  30s        # waiting on the backend
  timeout http-request 10s   # time allowed to send full request headers
  option forwardfor          # add X-Forwarded-For
  option http-server-close

frontend web
  bind :443 ssl crt /etc/ssl/api.pem
  acl is_api path_beg /api/
  use_backend app_pool if is_api

backend app_pool
  balance leastconn
  option httpchk GET /health
  http-check expect status 200
  retry-on conn-failure empty-response
  retries 2
  server app1 10.0.1.11:8080 check maxconn 200
  server app2 10.0.1.12:8080 check maxconn 200
Key idea All three products expose the same four knobs that matter in practice: a balancing algorithm, health checking, timeouts at each stage (connect, read, write, idle), and limits (connections, queue depth, body size). Interviews reward candidates who name the timeouts and caps explicitly rather than saying "just put a proxy in front".

6. Upstream connection pooling and keep-alive

Opening a new TCP connection costs one round trip for the handshake, and an encrypted connection costs one or two more for TLS. Inside a data center a round trip is perhaps 0.5 ms, so a new connection adds a few milliseconds. That sounds small, but at thousands of requests per second the work (CPU for the handshake, kernel state, ephemeral ports) adds up quickly, and short-lived connections leave sockets in the TCP TIME_WAIT state for around a minute, which can exhaust the available local ports. Reusing connections avoids all of that.

Keep-alive means leaving a connection open after a response so the next request can use it. HTTP/1.1 does this by default, but in front of backends it needs the proxy to actively manage a pool: a set of idle connections to each backend that requests borrow and return. The effect is a big asymmetry that makes reverse proxies valuable:

Without a proxyWith a reverse proxy and pooling
50,000 clients each hold a connection to an app server, so each server tracks thousands of sockets and the thread or file-descriptor limit is a bottleneck50,000 clients connect to the proxy; each app server sees perhaps 100-300 long-lived connections from the proxy
Each new client costs a full TCP and TLS handshake at the app serverThe proxy pays the client handshake; handshakes to backends are rare because pooled connections are reused
Slow clients occupy app server capacitySlow clients occupy only proxy memory

Details that cause real bugs:

  • Idle timeout mismatch. If a backend closes idle connections after 5 seconds but the proxy keeps them for 60, the proxy may pick a pooled connection at the exact moment the backend closes it. The request is sent into a dead connection and fails with a reset. The rule: the proxy's idle timeout for upstream connections must be shorter than the backend's. The same rule applies between a cloud load balancer and your server: your server's keep-alive timeout must exceed the load balancer's idle timeout.
  • Pool size. Too small and requests queue waiting for a free connection. Too large and you let the proxy overwhelm a backend. With HTTP/1.1 one connection carries one request at a time, so the connections needed equal the concurrent requests (Little's Law from Chapter 2). HTTP/2 multiplexes many requests on one connection, so a handful of connections can carry many requests.
  • Per-worker pools. In Nginx and Envoy each worker has its own pool, so a configured pool of 64 with 8 workers means up to 512 connections to each backend. Remember to multiply.
  • Hop-by-hop state. The client-side connection and the upstream connection are separate. HTTP/1.1 versus HTTP/2 can differ on each side, and so can TLS settings.

7. Request and response buffering, and slowloris

7.1 Why buffering protects the backend

Imagine a backend with a pool of worker threads, say 200 per server. A request occupies a thread from the moment it starts until the response is fully written. Suppose the actual work takes 40 ms. If a client on a poor mobile connection needs 2 seconds to download a 300 KB response, then without a proxy that thread stays occupied for the whole 2 seconds, mostly doing nothing but waiting for the network to accept bytes. Now 100 such clients arrive and they hold 100 of the 200 threads, while the CPU is almost idle.

With response buffering the backend writes the full response to the proxy at data center speed (a few milliseconds), the proxy stores it in memory or a temporary file, and the backend thread is free immediately. The proxy then feeds the slow client at the client's pace, using only a socket and a buffer, and its event loop does not mind. The same idea applies in the other direction: with request buffering the proxy reads an entire upload from a slow client first, and only then connects to the backend and sends the complete request at full speed. The backend never waits on a slow uploader.

Buffering has costs and exceptions, and you should be able to name them:

  • Memory and disk. The proxy must store buffered data. Nginx keeps response buffers in memory (a configurable number and size) and spills to temporary files for larger responses; large uploads are written to disk. Size and spill limits need to be set sensibly or the proxy will run out of memory or disk under load.
  • Latency. With request buffering the backend does not begin work until the whole upload has arrived. With response buffering the first byte to the client may be delayed until the proxy has received the response (or a buffer's worth of it).
  • Streaming protocols. Server-Sent Events, long-polling streams, large video downloads that should start playing at once, gRPC streaming and WebSockets all need the proxy to pass data along as it arrives. For those routes turn buffering off (in Nginx, proxy_buffering off; or sending X-Accel-Buffering: no from the backend; proxy_request_buffering off; for streaming uploads). Forgetting this is a classic cause of "my live feed arrives in big lumps every 30 seconds".

7.2 Slowloris and slow-body attacks

The idea behind buffering and timeouts also defends against a cheap denial-of-service technique. In a slowloris attack, the attacker opens thousands of connections to your server and sends the HTTP request headers extremely slowly, a single header line every ten seconds, never finishing the request. A server that allocates a thread (or a connection slot) per connection and waits patiently ends up with all its capacity held by clients that are doing almost nothing. The attacker needs very little bandwidth. A related attack, slow POST (also called R.U.D.Y.), sends the headers promptly but trickles the body at a few bytes per second. A slow read attack requests a large response and then reads it one tiny window at a time.

An event-loop reverse proxy is naturally resistant, because an idle connection costs a few kilobytes, not a thread. Even so, it has connection and memory limits, so you add explicit defenses at the proxy:

  • Short header and body timeouts. Require the complete request headers within, say, 10 seconds (client_header_timeout in Nginx, timeout http-request in HAProxy). Require progress on the body (client_body_timeout), measured between reads, not for the whole upload.
  • Minimum data rate. Close connections that fall below a minimum throughput after a grace period (some proxies and cloud services offer this directly).
  • Connection limits per source address (limit_conn in Nginx, stick-table in HAProxy), and a cap on total connections and on the number of header bytes and body bytes.
  • Send timeouts. Drop clients that will not drain a response (send_timeout).
  • Buffer before forwarding. Because the proxy waits for the full request before contacting the backend, a slowloris victim is the proxy's cheap sockets, not your application threads.
  • Do not rely on one layer. A CDN or cloud load balancer in front absorbs large floods and often enforces its own header timeouts (Chapter 55 covers DDoS more broadly).

8. Header handling, real client IP and trust boundaries

Once a proxy is in the middle, the backend's TCP connection comes from the proxy, so the address the backend sees is the proxy's, not the user's. The original information has to travel in HTTP headers. This sounds like a plumbing detail, but it drives rate limiting, geolocation, fraud checks, audit logs, and security. It also has an important trap: headers can be forged.

8.1 The headers that carry the original request

  • X-Forwarded-For (XFF). A de facto standard that holds a comma-separated list of addresses. Each proxy that handles the request appends the address of the peer that connected to it. After two proxies it might read X-Forwarded-For: 198.51.100.7, 10.0.0.5, meaning the first value is the original client (as claimed) and the later ones are intermediaries.
  • X-Forwarded-Proto (http or https) and X-Forwarded-Host / X-Forwarded-Port. After TLS termination the backend sees plain HTTP, so it needs to know the client used HTTPS in order to build correct absolute URLs, set Secure cookies and avoid redirect loops.
  • Forwarded (RFC 7239). The standardized replacement that puts the same information in one structured header: Forwarded: for=198.51.100.7;proto=https;host=api.example.com;by=10.0.0.5. Adoption is partial, so many systems still use the X-Forwarded family and you often meet both.
  • Host. The name the client asked for. Routing by virtual host depends on it. A proxy normally passes the original Host through (proxy_set_header Host $host;). If it instead sets Host to the backend's internal name, the application can generate wrong links and cookies scoped to the wrong domain. Some backends (for example a cloud storage origin) require the Host of their own name; then the original goes in X-Forwarded-Host.
  • Via. Lists the protocol and name of each intermediary, useful for debugging and loop detection.
  • PROXY protocol. A small preamble (originally from HAProxy) that a TCP-level proxy prepends to the connection to carry the original source and destination address, so even a non-HTTP backend or an L4 balancer can pass the client address without HTTP headers. The receiving server must expect it, otherwise the preamble looks like garbage.
  • Request IDs. Proxies often add a unique X-Request-ID (or a W3C traceparent) if the client did not send one, so that logs across services can be joined (Chapter 52).

8.2 Hop-by-hop headers

Most headers describe the whole request and are passed along unchanged. A few describe only one connection and must not be forwarded: Connection, Keep-Alive, Proxy-Authenticate, Proxy-Authorization, TE, Trailer, Transfer-Encoding and Upgrade, plus any header named in the Connection header. A correct proxy strips these and sets its own for the next hop. This is exactly why WebSocket needs special configuration (section 9): Upgrade is hop-by-hop, so the proxy has to deliberately re-create it.

8.3 The trust boundary: who may you believe?

Anyone can send X-Forwarded-For: 1.2.3.4 with their request. Your proxy, if it blindly appends, produces X-Forwarded-For: 1.2.3.4, 198.51.100.7. An application that naively reads the leftmost value as the client IP now believes the attacker is 1.2.3.4. The consequences are concrete: an attacker bypasses an IP-based rate limit by rotating fake values, evades an IP allowlist (X-Forwarded-For: 10.0.0.1 to look internal), poisons audit logs, or frames another address.

The fix is to define a trust boundary. Your own proxies are trusted; anything beyond them is not. The correct algorithm is to read the header from the right: take the address that connected to your outermost trusted proxy as the true peer, then walk left through the list while each address belongs to a trusted proxy (known ranges), and stop at the first one that does not. That address is the client as far as you can verify.

Practical rules that follow from this:

  • At the outermost proxy, the one that faces the internet, either overwrite client-supplied X-Forwarded-For with the real peer address, or append to it but remember that the pre-existing part is untrusted. Many teams choose overwrite because it is simplest to reason about. (In Nginx, proxy_set_header X-Forwarded-For $remote_addr; overwrites, while $proxy_add_x_forwarded_for appends.)
  • Behind a CDN or cloud load balancer, configure the list of trusted proxy ranges and let a module resolve the real client address (Nginx ngx_http_realip_module with set_real_ip_from, real_ip_header and real_ip_recursive on; Envoy xff_num_trusted_hops). Many CDNs also send a dedicated header (a single client IP value) that is more reliable than parsing XFF, but it is only trustworthy if the origin accepts traffic only from the CDN.
  • Make the origin unreachable except through the proxy (security groups, private networking, mutual TLS, or a shared secret header). Otherwise attackers connect directly and spoof every header.
  • Strip internal headers on the way in. If your backends trust headers such as X-User-Id or X-Internal-Auth set by the gateway, the edge must delete any copies sent by clients before adding its own.
  • Normalize and validate: a proxy and a backend that parse the same request differently can be exploited for HTTP request smuggling, where an ambiguous combination of Content-Length and Transfer-Encoding lets an attacker hide a second request inside the first. Defense is to use strict, current proxy versions, reject ambiguous requests, and prefer HTTP/2 or consistent HTTP/1.1 parsing on both hops.

9. WebSocket and gRPC through proxies

9.1 WebSocket

A WebSocket (Chapter 6) begins life as an ordinary HTTP/1.1 request that asks to switch protocols: the client sends Connection: Upgrade and Upgrade: websocket with a key. The server answers 101 Switching Protocols, and from then on the same TCP connection carries framed, two-way messages instead of HTTP. For a proxy this raises three issues.

  1. The upgrade headers are hop-by-hop. A proxy that follows the HTTP rules would strip them. It must be told to pass the upgrade through. In Nginx this takes proxy_http_version 1.1; plus proxy_set_header Upgrade $http_upgrade; and proxy_set_header Connection "upgrade";. Envoy and HAProxy have an explicit upgrade configuration or detect it automatically.
  2. After the upgrade, the proxy is a byte relay. It no longer sees requests and responses, so per-request features (retries, caching, response-code based health, per-request routing) do not apply to messages, and buffering must not hold data back.
  3. Connections are long-lived and idle most of the time. Default read timeouts (Nginx defaults to 60 seconds of silence) will kill a quiet socket, so either raise proxy_read_timeout for the WebSocket location or have the application send periodic ping frames so the connection is never silent. Each socket also costs a file descriptor on the proxy and on the backend, so raise limits, and plan for the thundering herd when a proxy restarts and every client reconnects at once (use jittered client back-off).

9.2 gRPC

gRPC (Chapter 5, Chapter 47) runs on HTTP/2. Two details matter to a proxy. First, gRPC puts its status code (grpc-status) in HTTP trailers, headers sent after the body. A proxy must support HTTP/2 end to end and forward trailers; an HTTP/1.1-only hop breaks it. Nginx has dedicated grpc_pass, Envoy and HAProxy handle it natively. Second, gRPC streaming calls can be open for minutes or hours, so response buffering must be off for them and timeouts must be generous or per-stream.

The deepest gRPC proxy issue is load balancing granularity. HTTP/2 puts many requests on one long-lived connection. A layer-4 balancer picks a backend once per connection, so a client with a single connection sends every call to the same backend, and a newly added backend receives no traffic from existing clients. An L7 proxy that understands HTTP/2 balances per request (per stream) across its upstream connections, which is why gRPC systems use Envoy, a service mesh sidecar or client-side balancing rather than a plain TCP balancer. Another practical wrinkle: browsers cannot speak native gRPC, so a proxy often translates gRPC-Web to gRPC.

10. Caching proxy semantics

A caching proxy (a Varnish or Squid server, an Nginx with proxy_cache, a CDN edge) stores responses and replays them for later identical requests. HTTP defines the rules for doing that safely. These rules are the same ones Chapter 12 relies on and Chapter 13 generalizes, so this section covers just what a proxy must decide.

10.1 Is this response cacheable, and for how long?

  • Cache-Control from the origin is the main instruction. max-age=N says the response is fresh for N seconds. s-maxage sets a lifetime for shared caches (proxies and CDNs) separate from the browser's. public and private say whether shared caches may store it (private means only the user's own browser). no-store forbids storing anywhere. no-cache means "you may store it, but you must revalidate with the origin before reusing it", which is a common misunderstanding.
  • Without explicit lifetimes a cache may estimate freshness from Last-Modified, a practice called heuristic freshness. Without any validators it should not cache.
  • By default only responses to GET (and HEAD) with cacheable status codes (200, 301, 404 and a few others) are stored. A response to a request with an Authorization header is not stored by a shared cache unless the response explicitly allows it. A response carrying Set-Cookie is often not cached by default in proxy configurations, because it is probably personal.

10.2 What counts as "the same request"? The cache key and Vary

The proxy builds a cache key, by default from the method, host and full URL including the query string. Two requests with the same key share one stored response. Some responses differ by request header, for instance gzip versus plain, or language. The origin lists the headers that matter in Vary (for example Vary: Accept-Encoding), and the proxy must store a separate variant per distinct value. Vary: Cookie or Vary: User-Agent fragments the cache into near-useless pieces. A wrongly narrow key is worse: if personalized content is cached under a key that ignores the user, one user's page is served to another, a serious leak. Always design what is part of the key on purpose.

10.3 Freshness, revalidation and staleness

When a stored response expires, the proxy does not have to throw it away. It sends a conditional request to the origin with If-None-Match: "etag" (or If-Modified-Since). If the content has not changed, the origin replies 304 Not Modified with no body, and the proxy refreshes the lifetime of its copy, saving bandwidth. Two extensions are valuable for resilience: stale-while-revalidate lets the proxy serve the stale copy immediately while it refreshes in the background (users never wait), and stale-if-error lets it serve a stale copy when the origin is failing, turning an outage into a degraded but working site. Nginx offers proxy_cache_use_stale and proxy_cache_background_update for the same ideas.

10.4 Stampede protection and invalidation

If a popular entry expires and 5,000 requests arrive in the same second, a naive proxy sends 5,000 identical requests to the origin. Request collapsing (Nginx proxy_cache_lock on;, Varnish request coalescing) lets one request go to the origin while the others wait for its answer. This is the proxy-level version of the cache stampede problem covered in Chapter 14. For removing content before it expires, a proxy typically supports a purge API (by URL or tag), or you change the URL (versioned file names) so old entries are simply never requested again.

Watch out A shared proxy cache and personalized responses are a dangerous combination. If a page that depends on the logged-in user is accidentally served with public, max-age=..., the cache will hand one user's account page to the next visitor. Mark user-specific responses private or no-store, and make the proxy bypass the cache when a session cookie is present unless you have deliberately designed otherwise.

11. Sidecar proxies: a preview

Everything so far puts a proxy at the edge of the system. A growing pattern puts a proxy next to every service instance. In this sidecar model, a small proxy (often Envoy) runs in the same host or Kubernetes pod as the application. The application talks to localhost, and the sidecar handles all traffic in and out of that instance. Because it is a proxy on both sides of every service-to-service call, it can add mutual TLS between services, retries and timeouts with sensible defaults, circuit breaking, load balancing based on live health, request-level metrics and traces, and traffic shifting for canaries, all without any change to application code or language.

This is the data plane of a service mesh. The tradeoffs (extra hop latency, memory per pod, operational complexity, debugging difficulty) and the control plane are the subject of Chapter 50. For now, remember that a sidecar is simply a reverse proxy and a forward proxy combined and placed next to each service: inbound traffic is handled as a reverse proxy would, outbound as a forward proxy would.

12. Failure modes and how to design them

A proxy is on the path of every request, which makes it both a convenient place to add resilience and a dangerous place to make mistakes. First, learn what the proxy's own error responses mean, because they are the vocabulary of incident diagnosis.

Different causes call for different fixes, so make sure your dashboards and alerts separate them and also record which upstream and which phase (connect, send, wait, read) failed. Envoy adds response flags to its logs (for example, one for "no healthy upstream" and one for "upstream connection failure") that make this easy.

12.2 Timeouts: set every one, and make them nest

A proxy has several distinct timers, and defaults are rarely right for your service. The connect timeout (how long to wait for a TCP connection to open) should be short, a second or two, because inside a data center a connection either opens in milliseconds or something is wrong. The read timeout (how long to wait for the response) should be a bit above the slowest legitimate request, based on the 99th or 99.9th percentile latency, not the average. Client-facing timeouts (header, body, send, idle) should be tight enough to defeat slow attacks yet long enough for slow mobile networks.

Timeouts must also nest correctly across hops. If a browser times out at 60 seconds, the load balancer at 45, the proxy at 30, and the backend's own downstream call at 25, then a slow dependency ends in a clean error at 25 seconds. If the inner timeouts are longer than the outer, the outer layer gives up and (often) retries while the inner work is still running, doubling the load on an already slow system. The rule of thumb is that each layer's timeout is slightly shorter than the layer above it, and the deadline is propagated down so work is abandoned when no one is waiting for it (Chapter 40 and Chapter 51).

12.3 Retries and non-idempotent requests

Retrying at the proxy turns many transient failures (a backend that just died, a reset connection) into successes invisible to the client. It is also one of the most dangerous features when used carelessly, for two reasons.

  • Duplicated side effects. If the proxy sends POST /payments to backend A, A processes it and charges the card, but the connection resets before the response arrives, the proxy cannot tell whether the work happened. A retry to backend B may charge the customer twice. Safe-by-default behaviour is to retry automatically only when the proxy knows the request was not processed (the connection could not be established, or the backend refused the stream) or when the method is idempotent (GET, HEAD, PUT, DELETE, OPTIONS by HTTP semantics). Nginx follows this: it does not retry non-idempotent methods (POST, PATCH, LOCK) once the request has been sent, unless you add non_idempotent to proxy_next_upstream. For writes that must be retried, require an idempotency key that the backend deduplicates on (Chapter 32, Chapter 5).
  • Retry storms. When a backend is overloaded and slow, retries add extra load to something already failing, which makes it fail more, which creates more retries. Three retries across three layers is 27 attempts for one user click. Defences: cap retries to one or two, use a retry budget (retries may be at most, say, 10% of normal traffic), add jittered back-off, retry only on failures that are likely transient, and avoid retrying at several layers. Envoy's retry budgets and per-try timeouts make this explicit.

12.4 Connection exhaustion

Several limits can run out, and each fails differently:

  • File descriptors. Every socket is a descriptor. The default per-process limit (often 1,024) is far too low for a proxy that holds tens of thousands of connections; raise ulimit -n and worker_rlimit_nofile. Symptom: "too many open files" errors and refused connections even though CPU is idle.
  • Ephemeral ports. A proxy connecting to one backend IP and port from one source IP can have only about 28,000 to 60,000 concurrent connections to that destination, since the source port is the only varying part of the connection identity. With many short-lived connections, TIME_WAIT sockets pile up. Fixes: keep-alive pooling, more backend IPs or source IPs, and a wider ephemeral port range.
  • Backend connection and thread limits. If the proxy can open more concurrent connections than the backend can handle, the backend falls over. Cap per-backend connections (maxconn in HAProxy, max_connections in Envoy) and queue or shed the excess, preferring a fast 503 over a slow collapse. Backpressure and bounded queues are covered in Chapter 8 and shedding in Chapter 16.
  • Proxy memory. Many slow clients each holding buffers can exhaust memory; bound buffer sizes and connection counts, and use timeouts as above.
  • Head-of-line blocking. With HTTP/1.1 to backends, one slow response blocks its connection. With HTTP/2 to the backend, one connection carries many streams, but a stalled connection stalls all of them, so keep several connections per backend.

12.5 Header spoofing

Covered in section 8.3: forged X-Forwarded-For, forged internal-auth headers, and a Host header that points routing at a different virtual host. To design against it, overwrite or sanitize at the outermost trusted layer, strip internal headers from external requests, validate Host against an allowlist, and ensure the origin accepts traffic only from the proxy.

12.6 The proxy as a single point of failure and a bottleneck

Every request goes through it, so its failure is total. The remedies are the standard ones: run several proxy instances behind a layer-4 balancer, a floating IP or anycast (Chapter 9 explains high availability of the load balancer itself); deploy configuration changes gradually and validate them before applying (a syntax error pushed to all proxies at once is a global outage, so use nginx -t, canary the config to a subset, and keep the last good version for rollback); make reloads graceful; autoscale on connections and CPU; and watch proxy-added latency. A well-tuned proxy adds well under a millisecond per request but a mistuned or overloaded one adds queueing delay that appears as latency on every service behind it.

Design checklist for any proxy tier Run at least two instances across failure domains. Set connect, read, send, header and idle timeouts explicitly and make inner ones shorter than outer ones. Cap connections per backend and queue depth. Retry only idempotent requests or those that never reached the backend, with a budget and jitter. Overwrite client-supplied forwarding headers at the edge. Lock the origin to the proxy. Separate 502, 503 and 504 in metrics. Reload configuration gracefully and roll it out gradually.

14. Worked example: sizing the proxy tier for a shopping site

An e-commerce site receives 8,000 requests per second at peak. The application servers run 40 ms of work per average request and are Java servers with a limit of 200 request threads each. About 10% of users are on slow mobile networks where a typical 300 KB response takes about 2 seconds to download. Total concurrent client connections at peak are about 60,000 because browsers keep connections open between clicks.

14.1 Without a buffering proxy

Mean time a backend thread is occupied per request is 90% of requests at 40 ms plus 10% at 40 ms + 2,000 ms: 0.9 × 0.040 + 0.1 × 2.040 = 0.036 + 0.204 = 0.24 seconds. By Little's Law, the concurrent threads needed are arrival rate times time in system: 8,000 × 0.24 = 1,920 threads. At 200 threads per server that needs 10 servers, and nearly all that capacity is spent waiting on slow sockets. Also, each of these servers would have to hold about 6,000 client connections itself, and perform every TLS handshake.

14.2 With a reverse proxy that buffers

The proxy absorbs the slow transfers. The backend thread is now held for roughly the work time plus a negligible hand-off (say 45 ms): 8,000 × 0.045 = 360 threads, so 2 servers would suffice for thread capacity (we will run more for redundancy and CPU headroom). The slow phones still wait 2 seconds, but only the proxy pays.

14.3 The proxy tier itself

  • Connections. 60,000 client connections divided over 4 proxy instances is 15,000 each. With 4 workers per instance this is around 3,750 sockets per worker, comfortably inside a 20,000 per worker limit. Memory per idle connection is small, typically a few KB to tens of KB with TLS state, so about 15,000 × 50 KB = 750 MB per instance in the worst case. Set descriptors well above 20,000 per process.
  • Upstream pools. Concurrent upstream requests are 360 on average; budget for a 3x burst, about 1,100. Spread over 6 backend servers (extra for redundancy) that is about 180 connections per backend at the burst, below the 200-thread limit. Cap each backend at maxconn 200 so the proxy queues or sheds instead of overloading it. With 4 proxies, each keeps roughly 45 connections per backend at peak, so a keep-alive pool of 64 per worker is more than enough.
  • Handshake savings. If every request opened a fresh upstream connection, 8,000 new TCP connections per second would hit the backends; with pooling it is a small trickle of new connections, mostly after backend restarts.
  • Timeouts. Client header timeout 10 s, client body timeout 15 s, upstream connect 1 s, upstream read 10 s (the slowest legitimate API call is about 3 s at the 99.9th percentile), and retries limited to idempotent GETs, one retry, within a 10% retry budget. A POST to the checkout endpoint is never retried automatically; it carries an idempotency key so a user-initiated retry is safe.
  • Failure of one proxy. With 4 instances at 25% each, losing one raises the others to 33%, still comfortable. Failure of one backend: health checks eject it within a few seconds, retries on connect failure protect most in-flight requests, and the remaining 5 backends absorb the load.

15. Interview questions and answers

What is the difference between a forward proxy and a reverse proxy?

A forward proxy represents clients: it sits on the client side, clients are configured to use it, and the servers on the internet see the proxy's address rather than the client's. It is used for egress control, filtering, caching and anonymity. A reverse proxy represents servers: it sits in front of your backends, clients think it is the real server, and it provides TLS termination, routing, load balancing, caching, compression and protection. The software can be the same; the difference is whose side it is on and who knows about it.

Why put a reverse proxy in front of application servers instead of exposing them directly?

Several reasons that compound. It terminates TLS in one place, so certificates are managed centrally. It buffers slow clients so application threads are not held waiting on slow networks, and pools connections so backends see few, long-lived connections instead of thousands of short ones. It hides the topology and gives one point to enforce limits, authentication and request filtering. It lets you route by path or host, roll out canaries, and swap backends without clients noticing. The price is one more hop, one more component that must be highly available, and one more thing to configure correctly.

How does a reverse proxy like Nginx handle tens of thousands of connections with so few threads?

It uses an event-driven model. Each worker process runs a single loop that asks the operating system (using epoll on Linux) which sockets are ready to read or write, handles those briefly without ever blocking, and then asks again. An idle or slow connection costs only a small buffer and a descriptor, not a thread. To use several cores, the proxy runs one worker per core, each with its own loop and its own upstream connection pool. This is why a proxy can sit in front of thousands of slow clients and still use little memory and CPU, and why heavy blocking work should never be done inside it.

A user's real IP shows up as the proxy's IP in your logs. How do you fix it, and what could go wrong?

The proxy adds the original address to a header such as X-Forwarded-For (or the standard Forwarded header, or uses the PROXY protocol at the TCP level), and the application or a proxy module reads it. The danger is that clients can send that header themselves. If the application takes the leftmost value, an attacker can pretend to be any address and bypass rate limits or allowlists. The fix is to define the trusted proxy ranges, overwrite or sanitize the header at the outermost proxy, read the header from the right skipping trusted hops, and make sure the origin cannot be reached except through those proxies.

What do 502, 503 and 504 mean, and how do you debug each?

502 Bad Gateway means the proxy reached the upstream but got an invalid response or the connection was refused or reset, so look for crashed or restarting backends, port or protocol mismatches, or idle-timeout mismatches on pooled connections. 503 Service Unavailable means the proxy had no healthy upstream or a limit rejected the request, so check health checks, circuit breaker or connection caps, and deployments with zero ready instances. 504 Gateway Timeout means the upstream accepted the request but was too slow, so look at backend latency, thread pool saturation, slow dependencies, and whether the proxy's read timeout is realistic. Good proxy logs record which upstream and which phase failed, which usually narrows it down in minutes.

Is it safe for a proxy to retry failed requests? What are the risks?

It is safe when the request is idempotent or when the proxy knows the backend never processed it, such as a failed connection attempt. For a non-idempotent request like POST /payments, a retry after the request was sent can run the operation twice, because a reset connection does not tell you whether the work was done. Nginx, for instance, refuses to retry such requests by default. The second risk is retry storms: retries add load to a struggling backend and multiply across layers. Use a small retry count, a retry budget, jittered back-off, per-try timeouts, and idempotency keys for writes that must be retryable.

How do WebSockets and gRPC change what you need to configure on a proxy?

For WebSockets the proxy must pass the Upgrade handshake through, because the Upgrade and Connection headers are hop-by-hop and would otherwise be stripped. After the 101 response it only relays frames, so buffering must not hold data back, and the default idle read timeout will disconnect quiet sockets unless you raise it or the app sends pings. For gRPC the proxy must speak HTTP/2 end to end and forward trailers, since the status code lives there. Streaming RPCs need buffering off and generous timeouts, and you need an L7 HTTP/2-aware balancer, since a connection-level balancer would pin all of a client's calls to one backend.

What is slowloris and how does a reverse proxy defend against it?

Slowloris holds many connections open by sending request headers or bodies extremely slowly, so a server that dedicates a thread or slot to each connection runs out of capacity while the attacker uses almost no bandwidth. An event-loop proxy is naturally resilient because idle connections are cheap, and it adds explicit defenses: tight timeouts for receiving headers and for progress on bodies, limits on connections per source address and in total, caps on header and body size, and a send timeout for clients that will not read responses. Because the proxy buffers the whole request before contacting the backend, half-finished requests never reach the application. A CDN or cloud load balancer in front adds another layer.

How is a reverse proxy different from an API gateway and a load balancer? When would you use each?

They are overlapping roles. A reverse proxy is the general mechanism. A load balancer is a reverse proxy (or an L4 forwarder) whose focus is spreading traffic over identical instances with health checks. An API gateway is a reverse proxy plus API-management policy: authentication, API keys, per-client quotas, request transformation and aggregation across services. In a small system one Nginx or a cloud load balancer does all of it. As the number of services and external consumers grows you introduce a gateway for policy, and add a CDN for static content and global reach. In an interview, justify each component by the problem it solves rather than listing them all.

How would you make the proxy tier itself highly available and safe to change?

Run at least two or three instances in different failure domains, in front of a layer-4 balancer, virtual IP or anycast address, so that no single proxy failure is visible. Size so that the loss of one instance leaves headroom. Treat configuration as code: validate syntax before applying, roll it out to a small subset first, keep the previous version for quick rollback, and prefer graceful reloads that let in-flight requests finish. Monitor connections, descriptor usage, 5xx rates by upstream, and proxy-added latency. For the dependency risk, keep the proxy logic thin so a bad rule cannot take down everything, and fall back to stale cache entries when the origin is down.

Explain the difference between the HTTP CONNECT method and SOCKS, and what a forward proxy can see for HTTPS traffic.

With CONNECT, the client asks an HTTP proxy to open a TCP tunnel to a host and port, the proxy answers 200, and then relays bytes blindly while the client performs TLS directly with the destination. The proxy sees only the destination host and port and traffic volume, so it can allow or block by domain but not by path or content unless it does TLS interception with a certificate authority the clients trust. SOCKS5 is a lower-level, protocol-agnostic proxy protocol that tunnels any TCP (and UDP) connection without understanding HTTP at all, so it can carry SSH or database traffic, but cannot cache or inspect web content.

16. Recap

  • A proxy terminates one connection and opens another, which gives it a place to apply policy. A forward proxy serves clients (egress control, filtering, caching, anonymity); a reverse proxy serves servers (TLS termination, routing, balancing, caching, buffering, shielding).
  • HTTPS through a forward proxy uses CONNECT, a blind tunnel; SOCKS is a lower-level, protocol-agnostic alternative. Explicit proxies are configured on the client; transparent ones are forced by the network.
  • Reverse proxy, load balancer, API gateway and CDN are overlapping roles of the same mechanism, differing in emphasis: general fronting, spreading load, API policy, global caching.
  • Inside, proxies use event loops and a few worker processes or threads, pool and reuse upstream connections, and enforce timeouts and limits at every stage. Buffering protects backend threads from slow clients and is the first line of defense against slowloris; turn it off for streaming routes.
  • Original client details travel in X-Forwarded-For / Forwarded and friends. Trust only what your own proxies added, read right to left, overwrite at the edge, and lock the origin to the proxy.
  • WebSocket needs Upgrade passed through and long idle timeouts or pings; gRPC needs HTTP/2 with trailers and per-request L7 balancing.
  • Caching proxies follow Cache-Control, Vary, validators and conditional requests, with collapsing to stop stampedes. Never cache personalized responses publicly.
  • 502 means the upstream broke the exchange, 503 means unavailable or shed, 504 means too slow. Nest timeouts, retry only safe requests with a budget, cap connections, and make the proxy tier redundant and safely deployable.
