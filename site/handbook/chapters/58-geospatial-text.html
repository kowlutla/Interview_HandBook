Geospatial and Text Structures

Two kinds of questions break ordinary database indexes: "what is near this point on the map?" and "what words start with, contain, or resemble this text?". This chapter explains the data structures built for them: geohash, quadtrees, S2 and H3 for space, and tries, inverted indexes, edit-distance structures, Aho-Corasick and ropes for text. It ends with how to choose among them and a worked example with one million moving drivers.

1. The nearby-search problem and why latitude/longitude indexes fail

Imagine a ride-hailing app. A rider opens the app at some latitude and longitude, and the system must find the available drivers within about two kilometres. The naive design is a table drivers(id, lat, lon, status) with a query such as WHERE lat BETWEEN a AND b AND lon BETWEEN c AND d, which asks for every driver inside a small box around the rider. The natural first instinct is to create an index on lat and another on lon. This does not work well, and it is worth understanding exactly why, because every structure in the first half of this chapter exists to fix this one problem.

A B-tree index (see the database indexing chapters) keeps values in one sorted order. It answers "give me everything between value A and value B" very efficiently, because everything in that range sits next to each other in the sorted structure. Latitude alone is one dimension, so a B-tree on latitude can return all drivers in a horizontal band of the world between two latitudes. But that band is the entire width of the planet. A band 4 km tall around a big city contains every driver in every city at that latitude: thousands of drivers in other countries that you will immediately throw away. The same is true for a longitude index, which returns a vertical stripe from the North Pole to the South Pole.

The database could use both indexes, fetch both candidate sets and intersect them. That is better than a full scan, but each of the two sets is still enormous (a whole band and a whole stripe), and only their small intersection is the answer. The cost is proportional to the size of the bands, not the size of the answer. A composite index on (lat, lon) does not rescue us either: the sort order is latitude first, then longitude, so within one exact latitude the longitudes are sorted, but two points 100 metres apart north-south are far apart in the sorted order, separated by every point with a latitude in between.

Key idea Two-dimensional proximity cannot be answered by a one-dimensional sorted index directly. Every geospatial structure does one of two things: it flattens the plane into a one-dimensional key whose locality is mostly preserved (geohash, S2, H3), or it builds a spatial tree that divides the plane hierarchically (quadtree, k-d tree, R-tree).

There are two more facts that shape every design in this chapter. First, the Earth is a sphere (really an oblate spheroid), so distance is not Euclidean. One degree of latitude is always about 111 km, but one degree of longitude is about 111 km at the equator and shrinks to zero at the poles, proportional to the cosine of the latitude. At London (about 51 degrees north) a degree of longitude is about 70 km. A "square" in degrees is therefore not a square on the ground. Second, an index only narrows down candidates. After the index returns, say, 500 drivers from nearby cells, the application still computes the true distance (the haversine formula, or a cheaper flat-earth approximation for short ranges), filters by the exact radius and sorts. A good geo index returns a small superset of the answer; it does not have to return exactly the answer.

The related case study, Design Uber / Nearby Search, puts these pieces into a full system. This chapter is the toolbox.

2. Geohash

Geohash, invented by Gustavo Niemeyer in 2008, is the simplest flattening scheme and the one interviewers expect you to know. It turns a latitude/longitude pair into a short string such as ezs42. The string names a rectangular cell on the map; longer strings name smaller cells inside it. Because it is just a string, you can store it in any database column, index it with an ordinary B-tree, and search it with a prefix match.

2.1 How encoding works: interleaving bits, then base32

The idea is repeated halving, like a binary search on the map. Start with the whole longitude range, -180 to 180. Ask: is the point's longitude in the lower half (-180 to 0) or the upper half (0 to 180)? Write down 0 for lower, 1 for upper, and keep the half that contains the point. Repeat on the surviving half. Each answer is one bit, and after 20 steps the range has shrunk from 360 degrees to about 360 / 2^20 = 0.00034 degrees, around 38 metres. Do exactly the same for latitude, whose range is -90 to 90. You now have a string of longitude bits and a string of latitude bits.

The next step is the heart of the scheme: interleave the two bit strings, taking one longitude bit, then one latitude bit, then the next longitude bit, and so on, starting with longitude. Finally, cut the combined bit string into groups of 5 bits and write each group as one character of a base32 alphabet. Geohash uses the alphabet 0123456789bcdefghjkmnpqrstuvwxyz, which is the digits plus the lowercase letters except a, i, l and o, removed because they are easy to confuse with other characters. Five bits give 32 values, so 5 bits per character matches the 32-letter alphabet exactly.

Here is the classic worked example, the point latitude 42.6, longitude -5.6 (northern Spain):

  • Longitude -5.6 in [-180, 180]: midpoint 0, the point is below it, bit 0. In [-180, 0]: midpoint -90, point is above, bit 1. In [-90, 0]: midpoint -45, above, bit 1. In [-45, 0]: -22.5, above, bit 1. In [-22.5, 0]: -11.25, above, bit 1. The first five longitude bits are 0 1 1 1 1.
  • Latitude 42.6 in [-90, 90]: midpoint 0, above, bit 1. In [0, 90]: 45, below, bit 0. In [0, 45]: 22.5, above, bit 1. In [22.5, 45]: 33.75, above, bit 1. In [33.75, 45]: 39.375, above, bit 1. The first five latitude bits are 1 0 1 1 1.
  • Interleave, longitude first: 0 1 1 0 1 1 1 1 1 1. The first group of five bits is 01101 which is 13, the 14th symbol of the alphabet, e. The second group is 11111 which is 31, the last symbol, z. Continuing the same process gives s, 4 and 2, so the result is ezs42.

Decoding is the reverse: expand each character to 5 bits, de-interleave, and replay the halvings. The result is not a point but a rectangle, and the centre of that rectangle is the usual decoded coordinate. So a geohash always means "somewhere inside this box", never an exact location.

2.3 The prefix property

Because every longer geohash is formed by subdividing the cell of its prefix, all points inside a cell share that cell's geohash as a prefix. The cell ezs4 contains the 32 cells ezs40 through ezs4z, and every point in it has a geohash starting with ezs4. This turns a geographic query into a string prefix query. In SQL it is WHERE geohash LIKE 'ezs4%', which a plain B-tree index serves with one range scan (everything from ezs4 up to just before ezs5). A key-value store can do the same with a sort key and a "begins with" condition. In a hash-sharded store you can also group by prefix. The ordering is also hierarchical, so you can reduce precision simply by truncating the string, which is handy for heat maps and aggregation ("how many rides started in each 5-character cell?").

Watch out The prefix property goes only one way. A shared prefix guarantees two points are close (they are in the same cell). The absence of a shared prefix does not mean two points are far apart. This is the boundary problem, next.

2.4 Neighbours and the boundary problem

Suppose a rider stands exactly on the line between two geohash cells, ezs42 and ezs48. A driver 20 metres away on the other side of the line has a different geohash, even though they are very close. If the system queried only the rider's own cell, it would miss that driver completely. Worse, at some boundaries the two sides share almost no prefix. The prime meridian (longitude 0) and the equator (latitude 0) are the very first halvings, so a point at longitude -0.0001 and a point at longitude +0.0001 differ in the very first bit and therefore in the first character, although they are 22 metres apart. The same happens at every boundary where a high-order bit flips.

The standard fix is to query the cell and its eight neighbours (north, north-east, east, south-east, south, south-west, west, north-west): nine cells in a 3 by 3 block. If the cell size is at least the search radius, any point within the radius of the rider must lie in one of those nine cells, so no true result is missed. You then compute exact distances for the candidates and discard those outside the circle. The neighbour of a geohash can be computed by a small lookup table (the algorithm decodes the cell, steps by one cell width or height, and re-encodes, or uses border/neighbour tables per character), and libraries provide a neighbors() function.

2.5 Edge cases: poles, the antimeridian, and variable cell shape

Longitude wraps around: +180 and -180 are the same meridian (the antimeridian, near the International Date Line). A cell on the eastern edge of the geohash grid has a neighbour on the western edge, and good neighbour code wraps. Latitude does not wrap: there is nothing north of the North Pole, so cells in the top row have no north neighbours, and the query should simply skip them. Near the poles the grid itself becomes strange. All geohash cells at a given length have the same angular size, but a degree of longitude near 85 degrees north is only about 10 km wide instead of 111 km. Cells become tall thin slivers and the "square" approximation breaks, so a ring of neighbours covers a much smaller ground distance east-west than north-south. For consumer apps with users in cities this rarely matters, but you should mention it, and it is one reason Redis GEO restricts latitudes to roughly plus or minus 85.05 degrees.

Cell shape also varies with latitude in the other direction: in Oslo a length-6 cell is physically narrower than the same cell in Singapore. This is called variable cell size. Distances computed from "number of cells" are therefore approximate, which is another reason to always filter with the real distance formula. If you need cells of uniform area (for example to compare supply and demand fairly across regions), geohash is a poor choice and S2 or H3 are better.

2.6 Why geohash is popular anyway

Despite the boundary and distortion issues, geohash is widely used because it is trivial to implement, human readable, works in any store that supports string keys, and needs no special database extension. Its weaknesses are the discontinuity at high-order boundaries, the poor shape at high latitudes, and the fact that a rectangular z-order curve jumps: consecutive cell ids in sort order can be far apart on the map, so a radius query becomes several scattered range scans rather than one contiguous one. Those jumps are what the Hilbert curve in S2 reduces.

3. Quadtrees

A geohash divides the world on a fixed grid, the same whether a cell holds one driver or ten thousand. A quadtree divides the map adaptively: it splits a region into four equal quadrants only when that region contains too many points. Dense areas get small cells, empty areas stay as one large cell.

3.1 Building and inserting

Each tree node covers a rectangle. A leaf node stores a small list of points. The node has a capacity, also called the split threshold, for example 100 points. The procedure is:

  1. Start with a single root leaf that covers the whole map (or the whole service area).
  2. To insert a point, walk from the root down to the leaf whose rectangle contains the point: at each internal node, pick one of the four children (north-west, north-east, south-west, south-east) by comparing the point's coordinates to the node's centre.
  3. Add the point to that leaf's list. If the list now exceeds the capacity, split the leaf: create four child leaves, each covering a quarter of the rectangle, redistribute the points among them, and turn the node into an internal node that stores only child pointers.
  4. If many points are identical or extremely close, splitting repeats and the tree gets very deep. Real implementations set a maximum depth (or minimum cell size) and let the deepest leaves exceed the capacity.

With N points and capacity C, a balanced-ish tree has about log base 4 of (N / C) levels in dense areas. One million points with capacity 100 need about 10,000 leaves, so about 7 levels if the distribution were uniform; clustered data goes deeper in the clusters but is still logarithmic. Insert and point lookup are therefore O(depth), cheap and predictable.

3.2 Range and nearest-neighbour queries

Range query (all points inside a rectangle or circle): start at the root and recurse only into children whose rectangle overlaps the query region. At a leaf, test each stored point. Whole subtrees that do not overlap are skipped, which is the pruning that makes the structure fast. If the query region fully contains a node, every point beneath it qualifies and can be returned without per-point checks.

Nearest-neighbour or k-nearest: a simple method searches a circle of growing radius using range queries. A better method is best-first search: keep a priority queue ordered by the minimum possible distance from the query point to each node's rectangle. Pop the closest node; if it is a leaf, test its points and update the best-k list; if internal, push its children. Stop when the closest remaining node is farther than the k-th best point found. This visits only the few nodes near the query.

3.3 Dynamic versus static, and where quadtrees live

A static quadtree is built once from a fixed set of points (shops, restaurants, ATMs) and rebuilt occasionally, for instance nightly. It can be packed tightly and shipped to servers as a read-only snapshot. A dynamic quadtree supports inserts, deletes and splits while serving traffic. Deleting is the harder half: if sibling leaves become sparse, the tree should merge four children back into one leaf, otherwise it slowly fills with empty nodes. A common rule is to merge when the combined count falls below half the capacity, which prevents a node from flapping between split and merged states when its count hovers around the threshold.

A quadtree is normally an in-memory structure, because it is pointer-based and does not map neatly onto disk pages the way a B-tree does. That is fine for location data: one million points of 16 to 32 bytes plus tree overhead fit in under 100 MB. The typical deployment keeps one quadtree per service-area shard in memory on the "location service" and rebuilds it from a durable store after a restart. Compare this with geohash, which leans on the database; this is the main operational difference between the two.

Moving objects. A driver who moves is a delete followed by an insert. That is wasteful if most moves stay inside the same leaf. Implementations therefore update the stored coordinates in place and only remove and reinsert when the new position falls outside the leaf's rectangle. A second trick is lazy update: tolerate stale positions for a few seconds and batch the structural changes. Even so, a heavily mutated tree with locks can become a bottleneck, which is why systems that track millions of moving objects often prefer a flat grid (a fixed-size version of the same idea) with simple hash-map buckets; see section 9.

4. R-trees and k-d trees, briefly

Two more spatial trees appear often enough to name.

A k-d tree is a binary tree where each level splits the points by the median value of one coordinate, alternating between x (longitude) and y (latitude). A node is a point; its left subtree holds points below the splitting coordinate, its right subtree the points above. Nearest-neighbour search is fast, roughly O(log n), and the structure is compact. Its weakness is updates: inserting and deleting points can unbalance it, and rebalancing is expensive, so it suits static data sets (for example the points of interest in a map tile) and machine-learning nearest-neighbour search more than live fleets.

An R-tree is a balanced tree, similar to a B-tree, where each node stores the minimum bounding rectangle that encloses all its children. Leaves hold the actual objects, which may be points, lines or polygons such as a city boundary or a delivery zone. Sibling rectangles may overlap, and a search must follow every child whose rectangle intersects the query. Because it is balanced and page-oriented, an R-tree works on disk. This is what GIS databases use: the PostGIS GiST index is an R-tree variant (section 8). Variants such as R*-trees reduce overlap through smarter splitting. Choose an R-tree when you store shapes rather than just points, or when the index must live on disk and support concurrent updates.

5. Google S2

S2 is the geometry library developed at Google and used by Google Maps, MongoDB (the 2dsphere index), and many ride-sharing and delivery systems. It addresses the weaknesses of geohash: distortion near the poles and the discontinuous curve. It is useful to know both the idea and the names of its parts.

  • Sphere to cube faces. S2 imagines the Earth enclosed in a cube. Each point on the sphere is projected outward onto one of the cube's six faces. A non-linear adjustment is applied so cells at the corner of a face are not much smaller than cells at the centre; this keeps the area of cells at the same level within a factor of roughly two. Compare that with geohash, whose cells shrink to slivers toward the poles. Because every face is a square, each face is a clean quadtree.
  • Hierarchical levels. Each face is subdivided like a quadtree. Level 0 is the whole face (one sixth of the Earth, roughly 85 million square kilometres). Each level splits every cell into 4, down to level 30, where a cell is about one square centimetre. Level 12 cells are a few square kilometres, level 15 are roughly the size of a city block or two.
  • Hilbert curve ids. Cells are numbered along a Hilbert space-filling curve. Geohash numbers cells along a Z-shaped curve that has long jumps. The Hilbert curve visits the cells of a square in a continuous path, so cells that are close along the curve are almost always close in space and vice versa; far fewer big jumps. A cell is identified by a 64-bit integer: 3 bits for the face, then 2 bits for each level of subdivision, then a trailing 1-bit marker followed by zeros that tells you the level. Because every cell is a contiguous range along the curve, the cell id range of a parent contains the ids of all its descendants. A region of the map therefore turns into a few ranges of integers, and an ordinary sorted index answers range queries.
  • Region covering. To find everything inside a circle, polygon or rectangle, S2's RegionCoverer computes a small set of cells, possibly of mixed levels, that together cover the region. You give it a minimum level, a maximum level and a maximum cell count (for example 8 or 16). Large interior areas use big cells and the ragged edge uses small cells. Each covering cell then becomes one range scan: cell_id BETWEEN cell.range_min AND cell.range_max. Unlike geohash's "always 9 cells", the number and sizes of scans adapt to the query shape, so large radii work without enumerating hundreds of fine cells.
Key idea S2 gives you hierarchical cells (like geohash), near-uniform area on the sphere (unlike geohash), contiguous 64-bit ids (so a B-tree range scan suffices), and a covering algorithm for arbitrary shapes. The price is a library dependency and ids that are not human readable.

6. Uber H3 and why hexagons

H3 is a hierarchical geospatial index open-sourced by Uber in 2018. It divides the globe into hexagonal cells at 16 resolutions (0 to 15). Resolution 0 has 122 base cells; at resolution 9 a cell is about 0.1 square kilometres (edge around 170 m), and at resolution 15 about one square metre. Every cell has a 64-bit index. H3 starts from an icosahedron (a 20-faced solid) laid over the sphere rather than a cube, which spreads distortion more evenly. Twelve of the base cells are pentagons, because a sphere cannot be tiled by hexagons alone, but they are placed over open ocean, away from most cities.

Why hexagons? Consider a square grid. A square has 8 neighbours but two kinds: the four edge neighbours whose centres are one cell width away, and the four diagonal corner neighbours whose centres are about 1.41 times as far. When you ask "all cells within one step of this cell", the distance to the farthest result differs by 41 percent depending on direction. A hexagon has 6 neighbours, all sharing an edge, and the distance between the centre of a cell and the centre of each neighbour is identical. Walking outward k steps (an H3 "k-ring" or grid disk) gives rings that approximate a circle far better than squares do. This matters for things Uber actually does: smoothing surge pricing across adjacent cells, finding "drivers within roughly 2 cells", computing travel-time estimates, and aggregating demand without directional bias. Hexagons also approximate a circle more closely for the same area, so there is less wasted area when covering a radius.

Two caveats are worth stating. H3 cells do not nest exactly: a parent hexagon contains about seven children, but the child hexagons are not perfectly inside the parent (the boundary is approximate), so a "children of" query is not exactly equal to a "within parent" query. Also, pentagon cells have 5 neighbours and need special handling in the library. These are why H3 is excellent for aggregation, analytics and neighbour-based reasoning, while S2 is stronger when you need exact hierarchical containment and polygon coverings.

8. Geospatial indexing in real databases

You rarely implement these structures yourself; you pick a database that has one. Know what each product does under the hood, because that predicts its limits.

  • PostgreSQL with PostGIS. Adds geometry and geography types and functions such as ST_DWithin(point, point, metres) and ST_Distance. A GiST index (Generalized Search Tree) on the column implements an R-tree over bounding boxes. The planner uses it to prune candidates, then the exact function filters. The <-> operator gives index-assisted k-nearest-neighbour ordering. Best choice when you also need polygons, joins, transactions and rich queries, and the data volume fits a relational database. Updates at hundreds of thousands per second are not its sweet spot, since each update writes to a disk-based tree and generates WAL.
  • Elasticsearch / OpenSearch. A field of type geo_point stores latitude/longitude, and the geo_distance, geo_bounding_box and geo_shape queries use it. Internally, Lucene indexes points in a BKD tree (a k-d tree variant organised in blocks), so it is a spatial tree rather than geohash. Geohash and geotile grids appear in aggregations (geohash_grid) for map heat-maps. It combines geo filters with full text and ranking, ideal for "restaurants near me matching 'ramen' sorted by rating". See Chapter 22. Because documents are immutable segments, frequent location updates are expensive.
  • Redis GEO. GEOADD key lon lat member stores each member in a sorted set whose score is a 52-bit geohash integer. GEOSEARCH key FROMLONLAT lon lat BYRADIUS 2 km (older name GEORADIUS) computes the covering cells (the centre cell plus neighbours at a suitable precision), runs range scans on the sorted set, and filters by exact distance. In-memory, very fast, easy to update, perfect for live positions; limits are the memory size of one node, the single-threaded command execution, and latitudes restricted to about plus or minus 85.05 degrees. Scale out by running one key per region or per shard (section 9).
  • MongoDB 2dsphere. Stores GeoJSON points and shapes and indexes them with S2 cells in a B-tree. Operators $near, $geoNear (aggregation) and $geoWithin serve proximity and containment. It covers both points and polygons and can combine with other fields in compound indexes.
  • DynamoDB and other key-value stores. There is no native spatial index, so you use the geohash pattern: store each item with a geohash attribute, use a coarse prefix (say 5 characters) as the partition key, and the full-length geohash as the sort key. A nearby search computes the cell and its 8 neighbours, issues up to 9 queries with begins_with or a sort-key range, and merges and filters the results. Hot cells (a stadium, a city centre) become hot partitions, so pick the precision with that in mind. The same pattern works on Cassandra, HBase or any ordered key-value store.

As a rule of thumb: relational plus shapes, use PostGIS; text plus geo, use Elasticsearch; real-time positions, use Redis or an in-memory grid; global scale with simple points, use a key-value store with geohash or S2 keys.

9. Handling moving objects at scale

A restaurant does not move; a driver moves every few seconds. Static points are a read-heavy problem and ordinary indexes suffice. Moving objects turn it into a write-heavy problem. A disk-based index with a durable write for every update will not survive. The approach is to separate three concerns:

  1. The latest position of every object, kept in memory, updated constantly, tolerant of loss (the next update arrives in seconds).
  2. A grid or tree over those positions that answers "who is near here?" It is derived from the latest positions and changes only when an object crosses a cell boundary.
  3. History, the track of positions, written asynchronously to a log (a message queue and then a data lake), possibly sampled at a lower rate for analytics and disputes.

9.1 The write rate and what reaches the index

The raw rate is simply the number of drivers divided by the update interval: 1 million drivers every 4 seconds is 250,000 updates per second. That is fine for an in-memory store sharded over a few machines, impossible for a single relational primary. Two observations reduce the real work. First, a driver at 10 m/s (36 km/h) travels only 40 m in 4 seconds, so for a cell about a kilometre across only about 3 to 4 percent of updates move a driver into a different cell. Overwriting the stored coordinates is cheap; the grid itself changes on only those boundary crossings. Second, the clients can reduce traffic: send updates only if the driver moved more than some threshold, adapt the interval to speed, and batch several updates per request.

9.2 The in-memory grid

The simplest and most robust structure is a fixed grid: a hash map from cell id (geohash, S2 or H3) to the set of driver ids in that cell, plus a hash map from driver id to its current position and cell. An update looks up the old cell, compares it with the new cell, and moves the id between sets only if it changed. A nearby query computes the cell and neighbour ids, unions the sets, fetches positions and filters by distance. All operations are O(1) per cell and need no tree rebalancing, which is why this beats a dynamic quadtree for high churn. It is effectively a quadtree frozen at one level.

9.3 TTL, liveness and failure

Drivers disappear: the phone loses signal, the app is killed, the battery dies. A stale entry that says "available driver here" leads to failed matches. Each entry carries a last-seen timestamp and a TTL (time to live), typically about 2 to 3 update intervals, so 8 to 15 seconds. Redis can expire a key natively; with a sorted-set GEO structure you instead store a separate heartbeat key or run a periodic sweep that removes members older than the TTL. Reads also filter by timestamp, so a delayed sweep does not return ghosts. When a shard crashes, the grid is rebuilt simply by waiting a few seconds, since every live driver re-reports on its next update; no heavy recovery is needed, which is why durability is not required here.

9.4 Sharding by cell

One machine cannot hold or serve everything forever, so shard the grid (see Chapter 25). The shard key should be a spatial key so that a nearby query touches few shards: choose a coarse cell (for example geohash length 4 or S2 level 8) and map those cells to shards. Hashing the coarse cell id with consistent hashing (see Chapter 57) spreads cells evenly and allows adding shards with little movement. Hashing the driver id instead would spread load perfectly but forces every nearby query to fan out to all shards, which is why spatial sharding is preferred. The issues are hotspots (an airport, a concert, central Manhattan on Friday night) and boundary queries that cross two shards. Mitigate by sharding at a granularity fine enough that a single big city spans many shards, by splitting hot cells further, and by letting the search service query two or three shards in parallel and merge.

10. Dense versus sparse regions and radius expansion

A fixed-precision grid has a built-in mismatch. A cell of 1.2 km by 0.6 km in central Tokyo might hold 400 drivers; the same-sized cell in rural Montana might hold none. Two failure modes follow.

Dense cells. If a cell has thousands of entries, a query that scans the 3 by 3 block returns tens of thousands of candidates and distance checks become costly; the shard that owns it becomes hot. Remedies: use a finer precision in dense areas (a quadtree does this automatically; with a grid you can choose precision per region or split a hot cell into children on demand); cap the number of candidates returned by the index and sort by approximate distance; or give the matching service a bounded top-N rather than the complete list.

Sparse cells and radius expansion. If the 9-cell search returns fewer drivers than needed, widen the search. The standard approach is to step the precision up (shorter geohash, bigger cells) or add rings: first try the 3 by 3 block at length 6, then if fewer than k results, repeat at length 5 (cells about 5 km), then length 4 (about 20 to 40 km), until you have enough candidates or reach a maximum radius. With H3 you grow the k-ring by one step each round. Each round is a bounded number of cell lookups, and because the distance filter is exact, expanding never returns wrong results, only more candidates. Define a stopping rule (maximum radius, maximum rounds, or a time budget) so the sparse case does not scan the planet. A useful hybrid is an adaptive index: a quadtree whose leaves are keyed by cell id, or a grid that records a count per cell so the search can pick the first precision likely to return enough points.

Interview tip When asked "what if there are no drivers nearby?", answer with radius expansion in rounds and a hard cap, and mention that you stop early once you have k good candidates. When asked "what if a stadium empties?", mention hot-cell splitting and per-shard rate limits.

11. From space to text: structures for strings

The second half of this chapter turns from maps to words. Text problems have the same shape as geospatial ones: an ordinary B-tree on a whole string handles "equals" and "starts with" well enough, but cannot do "contains this word", "words that start with these three letters ranked by popularity", "close to this misspelling", or "does any of 10,000 banned phrases occur in this paragraph". Each need has a structure designed for it, and the pattern is again to pre-organise data so the question is answered by walking a small structure rather than scanning everything.

12. Tries

A trie (pronounced "try", from retrieval), also called a prefix tree, stores a set of strings so that strings sharing a prefix share the same path. Each edge represents one character; each node represents the prefix spelled by the path from the root. A node is marked as a terminal if a stored word ends there. The root is the empty prefix.

12.1 Insert, search and prefix queries

Insert a word by walking from the root, following the child for each character and creating it when missing; mark the last node terminal. Search (exact lookup) walks the same path and succeeds if every step exists and the final node is terminal. Prefix query ("is there any word starting with ca?") walks the prefix and succeeds if the path exists; to list all words with that prefix, walk to that node and then traverse its entire subtree. The cost of insert and lookup is O(L), where L is the word's length, independent of how many words are stored. Compare a balanced tree of strings, which needs O(L log n) because each comparison costs up to L.

12.2 Autocomplete: top-K per node

Naive autocomplete walks to the prefix node and traverses its whole subtree, which for the prefix "a" can mean millions of words, then sorts them by popularity. That is far too slow for a request that must answer in tens of milliseconds. The fix is to precompute and store at each node the top K completions (K around 5 to 10) with their scores. A lookup then costs O(prefix length) plus K to return. The cost moves to the write path: when a score changes, the lists of every ancestor node must be updated (up to L nodes), which is why autocomplete systems update scores in batches from aggregated logs rather than on every keystroke. Memory grows by K entries per node, often acceptable if you store ids or pointers to a shared string table rather than copying strings. The full design (data collection, aggregation, trie building, serving and freshness) is in Design Search Autocomplete.

12.3 Memory and compressed (radix) tries

A plain trie is memory hungry. A node with an array of 26 child pointers uses 26 x 8 = 208 bytes even if it has one child; for full Unicode an array is impossible, so nodes use maps, which have their own overhead. A trie of one million English words has several million nodes, most of them in long single-child chains, such as the tail -ization. Two techniques help.

  • Compressed trie or radix tree (Patricia trie). Collapse every chain of single-child nodes into one edge labelled with a string. The words romane, romanus, romulus become a root edge rom with branches an (then e, us) and ulus. The number of nodes is bounded by about twice the number of stored words, instead of the number of characters. Radix trees are used for IP routing tables, in the Linux kernel, and in key-value stores such as Redis streams and ART (adaptive radix tree) indexes.
  • Compact child storage. Use sorted small arrays or bitmaps for sparse nodes and only switch to bigger arrays when a node has many children (the idea behind ART), or store the whole trie as a flat array of bytes (a double-array trie) for a read-only dictionary.

12.4 Ternary search trees and DAWGs

A ternary search tree (TST) gives each node one character and three pointers: less, equal and greater. To search for a word, compare the next letter with the node's character: go left if smaller, right if larger, and go to the middle child (consuming the letter) if equal. It behaves like a binary search tree on characters nested inside a trie. A node needs 3 pointers instead of a 26-slot array, so it uses far less memory, it supports prefix and "near" searches, and it is slightly slower per lookup. It is a good compromise when the alphabet is large or memory is tight.

A DAWG (directed acyclic word graph, also called a minimal acyclic finite-state automaton) goes further: it merges not only common prefixes but also common suffixes. The words walking, talking, working share the ending -ing, which becomes one shared sub-graph. A DAWG of an English dictionary is a fraction of the size of the equivalent trie and is used in word games, spell checkers and, as finite-state transducers (FST), in the term dictionary of Lucene. The cost is that it is built offline and is effectively read-only, and storing per-word data such as popularity needs extra care.

13. Inverted index and posting-list compression (recap)

Where a trie answers prefix questions, the inverted index answers "which documents contain this word?". It maps each term (word) to its posting list, the sorted list of ids of documents containing the term, possibly with positions and frequencies. A multi-word query fetches the lists for each term and intersects them (AND) or merges them (OR), then ranks the results. Elasticsearch, Lucene, Solr and most search engines are built on it; the full treatment, including analyzers, shards and ranking, is in Chapter 22, so only the data-structure points are repeated here.

Why compress posting lists? Common terms have lists with hundreds of millions of ids, and a search engine's speed is largely determined by how fast it can stream these lists through memory. The central trick is delta encoding: since the list is sorted, store the differences between consecutive ids instead of the ids. The list 1000, 1003, 1010, 1012 becomes 1000, 3, 7, 2; the numbers are small, so they fit in few bits. Then compress the small numbers:

  • Variable-byte (varint) encoding: use 7 bits of each byte for data and the top bit to say "more bytes follow". A number below 128 takes one byte.
  • Frame of reference and PForDelta: split the list into blocks of, say, 128 deltas, find the number of bits needed for the largest typical value, and pack them all at that width, storing a few exceptions separately. This is very fast with modern CPU vector instructions and is what Lucene uses.
  • Roaring bitmaps: for dense lists, store a set of ids as a bitmap per chunk of 65,536 ids and switch the chunk representation among array, bitmap and run-length depending on density. Intersection is bitwise AND. Used by Lucene for filters, and widely in analytics systems.
  • Skip pointers: store extra markers every 128 or so entries so an intersection of a short list with a long one can jump forward instead of reading every entry.

Compression is both a space saving (often 4 to 10 times smaller than raw 32-bit ids) and a speed gain, because less memory bandwidth is needed.

14. N-grams, edit distance and fuzzy search

Users misspell. A search for "recieve" should find "receive". To support this, define "close" precisely: the Levenshtein edit distance between two strings is the minimum number of single-character insertions, deletions and substitutions needed to turn one into the other. "kitten" to "sitting" is 3 (substitute k with s, substitute e with i, insert g). The standard dynamic programming algorithm fills a table of size m by n with the cost of converting each prefix of one string into each prefix of the other, in O(mn) time. That is fine for comparing two words, but far too slow to compare a query against a dictionary of millions of words, so we need structures that avoid most comparisons. (A variant, Damerau-Levenshtein, also counts the swap of two adjacent letters as one edit, matching typical typos better.)

14.1 N-grams

An n-gram is a run of n consecutive characters. The 3-grams (trigrams) of "hello", padded with spaces, are " h", " he", "hel", "ell", "llo", "lo ". Index every dictionary word by its n-grams, using an inverted index from n-gram to word. To find candidates for a misspelled query, look up its trigrams and keep the words that share many of them (measured with the Jaccard or Dice overlap); then compute exact edit distance on only that small candidate set. Two strings within edit distance 1 or 2 usually share most of their n-grams, so the filter rarely loses the right answer. N-grams also power "contains" substring search (PostgreSQL pg_trgm) and search-as-you-type with edge n-grams, which index only the prefixes of each word ("h", "he", "hel", "hell", "hello"), turning prefix matching into an exact term lookup in an ordinary inverted index.

14.2 BK-trees

A BK-tree (Burkhard-Keller tree) indexes words in any metric space, including edit distance. Pick any word as the root. To insert a word, compute its distance d to the root; follow (or create) the child edge labelled d, and repeat recursively. To search for all words within distance r of a query q, compute d = distance(q, node). If d is at most r, the node is a match. Then, by the triangle inequality, only children whose edge label lies between d minus r and d plus r can contain matches, so every other branch is pruned. For small r (1 or 2) this typically inspects a small fraction of the dictionary.

Search engines such as Lucene use an even faster approach for fuzzy queries: they build a Levenshtein automaton, a small finite-state machine that accepts exactly the strings within distance k of the query, and intersect it with the FST of the term dictionary, so the traversal visits only plausible terms. In practice, the distance is limited to 1 or 2 because the number of matches grows quickly, and the first letter is often required to match to cut candidates.

15. Suffix arrays and suffix trees

If you must find a pattern anywhere inside one very long string (a genome, a log file, a whole book), a trie of words does not help, because the match can begin at any character. A suffix array sorts all suffixes of the text (the strings starting at every position) and stores the starting positions in sorted order. Any substring is a prefix of some suffix, so a pattern of length m can be found by binary search in O(m log n). A suffix tree is a compressed trie of all suffixes and finds a pattern in O(m), independent of text length, but needs roughly 10 to 20 times the memory of the text, whereas a suffix array takes about 4 to 8 bytes per character. For that reason suffix arrays (and the FM-index derived from them, used in bioinformatics) are more common in practice. In interviews a mention is enough: "for substring search in one big text I would use a suffix array; for many documents I use an inverted index with n-grams".

16. Tokenization basics

Before any text structure can be used, raw text must be split into tokens, and the quality of this step decides search quality. A typical analysis pipeline does the following in order: normalise Unicode and case (so "Cafe" and "cafe" match, and accents optionally fold); split on whitespace and punctuation (with care for tokens like c++, email addresses and URLs); remove very common stop words (the, of) if desired, although modern engines often keep them for phrase queries; apply stemming or lemmatization to reduce "running" and "ran" to a common root; and optionally expand synonyms. The same pipeline must be applied at index time and query time, or the tokens will not match. Languages without spaces, such as Chinese and Japanese, need dictionary-based segmentation or character n-grams. Mixed-language and emoji content are other common sources of mismatches. In an interview, state that the analyzer is part of the index definition and changing it requires a reindex.

17. Aho-Corasick: matching many patterns at once

Suppose you must scan every chat message for any of 50,000 banned words, or scan network packets for thousands of malware signatures. Running one search per pattern costs 50,000 passes over the text. The Aho-Corasick algorithm finds all occurrences of all patterns in a single pass, in time O(length of text + number of matches), independent of the number of patterns.

It has two ingredients. First, build a trie of all the patterns. Second, add failure links: for each node, the failure link points to the longest proper suffix of the node's string that is also a prefix of some pattern (i.e. another node in the trie). These links are computed by a breadth-first traversal of the trie. When scanning text, you keep a current node and consume one character at a time. If the node has a child for the next character, move to it. If not, follow failure links until a node with that child is found (or reach the root). Whenever the current node, or any node reachable along its output links, ends a pattern, report a match. The scanner never moves backwards in the text, which is why it is linear.

Uses include profanity and spam filters, intrusion detection engines (Snort uses it), antivirus signature scanners, fgrep, and entity tagging ("find every product name from this list in the article"). It lives in memory, and for very large pattern sets the state table can be stored as a compact array.

18. Ropes and piece tables for text editors

An editor holds a document and applies inserts and deletes at a cursor. A single contiguous array or string makes every insertion in the middle copy all the text after it, O(n), which is painful for a 50 MB file. Editors therefore use structures that make edits cheap.

  • Gap buffer: an array with an empty "gap" kept at the cursor; typing fills the gap and moving the cursor moves the gap. Simple and fast for local edits (used by Emacs) but moving the cursor far means copying.
  • Rope: a balanced binary tree whose leaves hold short string chunks, and whose internal nodes store the total length of the left subtree. To find character i, walk down comparing i to the stored lengths. Insertion splits a leaf and re-links; delete and concatenation also take O(log n). Ropes make large concatenations and splits cheap and are used where huge text is manipulated (and in some language runtimes).
  • Piece table: keeps two read-only-ish buffers, the original file and an append-only add buffer for everything typed, plus a list of pieces, each saying "take length L from buffer B starting at offset O". The document is the concatenation of the pieces. Inserting text appends it to the add buffer and splits one piece into two with a new piece between them; deleting just trims or removes piece entries; nothing is copied or overwritten. Undo is easy because old text is never destroyed. VS Code stores the pieces in a balanced tree (a "piece tree") to find the piece at a character offset in O(log n).

For collaborative editing the problem changes: several users edit concurrently and the system must merge operations, using operational transformation or CRDTs, usually on top of a rope or piece-table representation per replica. That is covered in Design a Collaborative Editor.

20. Worked example: nearby drivers for 1 million drivers updating every 4 seconds

Requirements. One million online drivers, each reporting position every 4 seconds. Riders request "drivers within 1 km" at a peak of 20,000 requests per second across the world. The answer must come back within 100 ms, and a stale position older than about 12 seconds must not be returned.

20.1 Write load

  • Updates: 1,000,000 / 4 = 250,000 updates per second.
  • Payload per update (driver id 8 B, lat and lon as two 8 B doubles, timestamp 8 B, heading and speed, headers): around 50 to 60 bytes at the application level. 250,000 x 50 B = about 12.5 MB/s, or 100 Mbit/s. Network-wise this is modest; the request count, not the bytes, is the concern. Batching 10 updates per HTTP call at the gateway cuts requests to 25,000 per second.
  • Persisting every point to history: 12.5 MB/s x 86,400 s = about 1.08 TB per day. Sampling history to one point every 20 seconds cuts this to roughly 215 GB per day; this is written to a log stream, not the serving store.

20.2 Memory

For each driver keep id, lat, lon, timestamp, cell id and status: about 48 bytes, rounded to roughly 100 bytes with hash map overhead. 1,000,000 x 100 B = 100 MB. The cell map adds another small amount. Memory is not the bottleneck at all; one machine could hold the data. We shard for write throughput and availability, not capacity.

20.3 Sharding

A single Redis or in-process grid handles on the order of 100,000 simple operations per second, so 250,000 writes per second plus 20,000 queries (each touching 9 cells) needs several nodes. Choose 8 shards by hashing a coarse cell (geohash length 4, cells about 39 km by 20 km) to a shard with consistent hashing. This gives about 31,000 writes per second per shard, leaving headroom, and each shard has replicas for failover. A city is split over many length-4 cells so no shard owns an entire metropolis. A rider query at a boundary may contact two shards; the search service issues those requests in parallel.

20.4 Choosing the cell size and the query cost

The radius is 1 km, so use geohash length 6 (about 1.2 km by 0.6 km). The cell height of 0.6 km is smaller than the radius, so the 3 by 3 block covers only 1.8 km north-south, which is not enough margin on the sides in the worst case; to be safe we have two options: length 5 (4.9 km cells, the 3 by 3 block is safe but large) or length 6 with the 5 by 5 block (25 cells). Compare the candidate counts for both. A dense city has maybe 50,000 online drivers over 600 square kilometres, about 83 per square kilometre. A length-5 cell has 24 square kilometres, so about 2,000 drivers per cell and 18,000 for the 3 by 3 block; filtering 18,000 candidates per query at about 50 ns for a distance computation is 0.9 ms, but at 20,000 queries per second that is 18 seconds of CPU per second, 18 cores. It is feasible yet wasteful. Using length 6 with the 5 by 5 block (25 cells of 0.72 square kilometres = 18 square kilometres) gives about 1,500 candidates and 75 microseconds of distance work per query, 1.5 cores in total. Finer cells win here. In sparse areas, the same query returns few drivers and the radius expansion of section 10 kicks in.

20.5 What actually changes in the index

A driver moves about 40 metres in 4 seconds at 36 km/h. With cells 600 to 1,200 m wide, a crossing happens roughly once every 15 to 30 updates, so only about 3 to 7 percent of updates change cell membership: about 7,500 to 17,500 set mutations per second across all shards, while the other updates only overwrite a position field. TTL is 12 seconds (three missed updates): a driver silent for longer is removed by a sweep and filtered out at read time.

21. Interview Q&A

Why can't I just index latitude and longitude with ordinary B-trees?

A B-tree orders values along one axis, so an index on latitude returns a band that spans the whole world and one on longitude returns a pole-to-pole stripe. The real answer is only the small overlap, but the database must read and intersect both huge sets, so cost scales with the band size, not the answer size. A composite (lat, lon) index also fails because points that are close north-south can be far apart in the sorted order. The fix is either to flatten the two dimensions into one locality-preserving key (geohash, S2, H3) or to use a genuinely spatial tree (quadtree, R-tree, k-d tree).

Explain how a geohash is computed and what its prefix means.

Repeatedly halve the longitude range and the latitude range, writing 0 for the lower half and 1 for the upper half each time. Interleave the two bit sequences starting with longitude and group them in fives, mapping each group to a character of the base32 alphabet. Each extra character subdivides the cell into 32. All points in a cell share its geohash as a prefix, so a geographic area becomes a string prefix, and a B-tree range scan or a "begins with" query finds everything in it.

What is the geohash boundary problem and how do you handle it?

Two points a few metres apart can fall in different cells, and at the top-level boundaries (the equator and prime meridian) they share no prefix at all. Querying only the home cell therefore misses close neighbours. The remedy is to query the home cell plus its eight neighbours, choosing a precision whose cell is at least as large as the search radius, and then filter by exact distance. Wrap longitude at the antimeridian and skip non-existent northern or southern neighbours at the poles.

Geohash versus quadtree: when do you pick each?

Geohash is a fixed-grid key that fits in any database column, shards naturally by prefix and is trivial to implement; its cells do not adapt to density. A quadtree adapts by splitting crowded cells, so a dense city gets fine cells and an ocean gets one big one, which gives good nearest-neighbour performance, but it is an in-memory pointer structure that must be rebuilt after a crash and is awkward to update under heavy churn. I would use geohash or a grid for the persistent, sharded side and possibly a quadtree inside a service for adaptive in-memory search.

Why do S2 and H3 exist if geohash works?

Geohash cells distort with latitude, its Z-order curve jumps so a region becomes scattered ranges, and neighbours are awkward at boundaries. S2 projects the sphere onto cube faces so cells have near-uniform area, orders them with a Hilbert curve so ranges are contiguous, and offers region covering for arbitrary shapes. H3 uses hexagons, whose six neighbours are all the same distance away, which is ideal for smoothing, aggregation and "within k rings" reasoning. They cost a library dependency and unreadable ids, which is why simple systems still use geohash.

How do you handle a million drivers updating location every few seconds?

That is 250,000 writes per second, so I keep only the latest position in memory, in a sharded grid keyed by cell id, rather than writing to a disk index. Updates overwrite the position and change set membership only when a driver crosses a cell, which is a few percent of updates. A TTL of a few update intervals removes drivers who disappear, and history goes to a Kafka-style log asynchronously, sampled. Shards are chosen by coarse cell so that a nearby query touches one or two of them.

How would you shard a location service and what goes wrong?

Shard by a coarse spatial cell, hashed with consistent hashing, so that all drivers in an area live together and a query fans out to few shards. Sharding by driver id gives even load but forces every query to hit all shards. The problems are hotspots such as airports or event venues, which you fix by using finer cells for hot regions or splitting hot cells further, and boundary queries that need two shards, which you handle by querying them in parallel and merging. See the sharding chapter for rebalancing.

What happens when a search area is empty or very dense?

In sparse areas, expand in rounds: re-run the query with a shorter geohash (larger cells) or a bigger ring until you have enough candidates or hit a maximum radius, and stop early once k good results are found. In dense areas, a fixed cell holds too many points, so use finer cells, cap the candidate count, or split the hot cell; a quadtree does this automatically. Since the final step always filters by exact distance, expansion changes only cost, not correctness.

How does a trie support autocomplete efficiently, and what are its costs?

Walking the prefix takes O(length of prefix), but listing and ranking the subtree is expensive for short prefixes. So each node stores its top-K completions with scores, making the lookup read a single node. The cost is memory (K entries per node, mitigated by storing ids) and write amplification, because changing a score means updating up to L ancestors; therefore scores are updated in periodic batches from aggregated query logs, and a radix trie or FST shrinks the structure.

How would you support typo-tolerant search over a large dictionary?

Computing edit distance against every word costs O(mn) per word, so first narrow candidates. Index words by n-grams in an inverted index and keep the words sharing most n-grams with the query, or use a BK-tree where the triangle inequality prunes most branches, or a Levenshtein automaton intersected with the term dictionary as Lucene does. Then compute exact edit distance on the small candidate set, restrict to distance 1 or 2, and rank by popularity and distance.

When would you use Aho-Corasick instead of regular expressions or repeated searches?

When there are many fixed patterns, say thousands of banned phrases or signatures, and the text is a stream. Searching each pattern separately costs patterns times text length, whereas Aho-Corasick builds one trie with failure links and reads the text once, in time linear in the text plus the matches. It does not handle general regex, so for flexible patterns you combine it with a regex confirmation step on the matches.

Why does a text editor not store the document as one big string?

An insertion in the middle of a flat array shifts everything after it, O(n), which is slow for large files and makes undo costly. A rope stores chunks in a balanced tree so edits cost O(log n); a piece table keeps the original file and an append-only buffer and represents the document as a list of slices, so edits modify only the list and undo is trivial. Editors like VS Code use a piece tree for this reason.

22. Recap

  • B-trees on latitude and longitude fail because proximity is two-dimensional; flatten it to a cell id (geohash, S2, H3) or use a spatial tree (quadtree, k-d tree, R-tree).
  • Geohash interleaves longitude and latitude bits and writes them in base32; shared prefix means same cell, but a missing prefix does not mean far, so query the cell plus 8 neighbours and filter by exact distance. Mind poles, the antimeridian and variable cell size.
  • Quadtrees split crowded cells, support range and best-first nearest queries, live in memory, and handle high-churn moving objects less gracefully than a flat grid. R-trees index shapes on disk (PostGIS GiST); k-d trees suit static data.
  • S2 uses cube faces and Hilbert-ordered 64-bit ids with region covering; H3 uses hexagons so all neighbours are equidistant.
  • Databases: PostGIS (R-tree), Elasticsearch (BKD tree), Redis GEO (geohash in a sorted set), MongoDB 2dsphere (S2), DynamoDB (geohash key pattern).
  • Moving objects: keep latest positions in a sharded in-memory grid with TTL, send history to a log, shard by coarse cell, expand the radius in rounds for sparse areas and split cells for dense ones.
  • Text: tries give O(L) prefix lookup, top-K per node gives autocomplete, radix tries, TSTs and DAWGs save memory; inverted indexes with delta-compressed postings power full-text search; n-grams, BK-trees and Levenshtein automata give fuzzy search; suffix arrays find substrings; Aho-Corasick matches many patterns in one pass; ropes and piece tables make editing cheap.
  • With 1 million drivers every 4 seconds: 250,000 writes per second, about 100 MB of state, 8 shards, and only a few percent of updates change cell membership.
