Caching II: Failure Modes and Distributed Caches

A cache makes a system fast on a good day and can make it fall over on a bad one. This chapter explains how caches fail (stampedes, penetration, avalanches, hot keys, stale data, outages), how to defend against each, and how a cache is built as a distributed system of its own.

1. Why caches fail in interesting ways

Chapter 13 covered the happy path: the patterns (cache-aside, read-through, write-through, write-back), eviction, invalidation and sizing. It ended with a warning that a cache changes the failure behaviour of your system. This chapter is about that warning.

The root issue is that a cache with a high hit ratio hides load from the database. Suppose the database can serve 5,000 reads per second and the application receives 100,000 reads per second. With a 97% hit ratio only 3,000 reads per second reach the database, which is fine. But the database is now sized for the cache's success. If the cache is emptied, or a popular entry vanishes at the wrong moment, the database suddenly sees up to 100,000 reads per second, twenty times what it can take. It slows down, requests time out, the application retries, and the retries add more load. The cache did not just stop helping; it left behind a system that cannot survive without it.

Key idea A cache is a load amplifier in reverse: it multiplies the load the database sees by (1 - hit ratio). Every failure mode in this chapter is a way for that reduction to briefly stop working. Defence means either keeping the hit ratio up, or making sure the database is protected when it drops.

2. Cache stampede (thundering herd)

2.1 What happens

A cache stampede (also called a thundering herd or dog-piling) occurs when a popular entry expires or is evicted and many requests arrive for it before anyone has refilled it. With cache-aside, each of those requests sees a miss and independently goes to the database to compute the same value. If the entry is read 2,000 times per second and the query takes 500 ms, then in the half second after expiry about 1,000 requests all run the same expensive query at once. The database slows down, which makes the query take longer, which lets even more requests pile in. The original entry was one row; the damage is a database melt-down.

2.2 Mitigation: request coalescing (single-flight)

The most direct fix: when many requests need the same missing key, let one of them do the work and make the rest wait for its result. Inside a single application process this is called single-flight or request coalescing. The process keeps a map of keys currently being loaded. The first request for a key registers itself and calls the database; later requests for the same key find the entry and simply wait on it, then all receive the same answer. Go's singleflight package and Guava's loading cache both do this. With 50 app servers, you get at most 50 database calls per expiry instead of 1,000, one per server. This is cheap, needs no extra infrastructure, and should be the default.

2.3 Mitigation: a lock with a short TTL

To reduce it to one call across the whole fleet, use a distributed lock in the cache itself. On a miss, a request tries SET lock:hot-key token NX PX 5000 (set only if absent, expire after 5 seconds). The winner queries the database, writes the value, and deletes the lock. Losers either sleep briefly (say 20-50 ms) and re-read the cache, or serve a slightly stale copy if one exists. The lock must have a TTL so that a crash of the winner cannot block the key forever, and the TTL should be longer than the typical load time but short enough to recover quickly. Note this is an efficiency lock, not a correctness lock: if it occasionally lets two loaders through, the only cost is a duplicate query. (Correctness locks are discussed in Chapter 30.)

2.4 Mitigation: probabilistic early expiration

Instead of waiting for expiry, let requests refresh a little early, at random. Store with each value the time it took to compute (delta) and its expiry. On each read, compute a small random chance of treating the value as expired, where the chance rises as expiry approaches and is larger when delta (the cost of recomputing) is larger. The published formula (often called XFetch) is: recompute if now - delta * beta * ln(rand()) >= expiry, with beta around 1. Because ln(rand()) is negative, the left side is pushed forward in time by a random amount. In practice one unlucky request refreshes the value a few seconds before it would have expired, while everyone else still gets hits. No locks, no coordination, and it works naturally with cache-aside.

2.5 Mitigation: stale-while-revalidate and refresh-ahead

Stale-while-revalidate keeps two deadlines per entry: a soft TTL (after which the value is considered old) and a hard TTL (after which it is deleted). If a read finds a value past its soft TTL but before the hard TTL, it returns the old value immediately and triggers one background refresh. Users never wait and the database sees one refresh. This is the same idea as the HTTP stale-while-revalidate directive used by CDNs (Chapter 12). The cost is serving data a bit older than the soft TTL, so it suits data with a staleness budget.

Refresh-ahead (introduced in Chapter 13) goes one step further: a background job periodically reloads known-hot keys before they expire, so the value is never absent. It is excellent for a small, known set (home page, config, top-100 products) and wasteful for a large long tail, because you reload keys nobody reads.

3. Cache penetration: requests for keys that do not exist

A cache only stores what exists. If a request asks for user:99999999 and that user does not exist, the database returns nothing, there is nothing to cache, and the next request for the same key goes to the database again. This is cache penetration: the cache never absorbs the traffic, so every such request passes through. It happens by accident (a buggy client, a deleted product with old links) and on purpose (an attacker enumerating random ids to bypass the cache and hit the database).

3.1 Negative caching

The simplest defence is to cache the absence itself: store a special marker such as NULL under that key with a short TTL (30 to 120 seconds is typical). The next requests get a hit on the marker and return "not found" without touching the database. Keep the TTL short for two reasons: attackers can fill the cache with millions of useless keys, and a legitimately created record should appear soon. If your creation path can write the real value, it overwrites the marker immediately.

3.2 Bloom filter in front

Negative caching does not help when the attacker uses a new random key each time, because every key is a first miss. A Bloom filter is a compact bit-array structure that answers "might this key exist?" with no false negatives and a small, tunable rate of false positives. You load it with every valid key (or id range). On a request, the application checks the filter first: if it says "definitely not present" the request is rejected at once, without cache or database. If it says "maybe", the normal cache-aside path runs. A filter for 100 million ids at a 1% false-positive rate needs about 10 bits per key, roughly 120 MB, which fits in memory. The filter must be updated when records are added (adding is easy; deleting needs a counting variant or periodic rebuild). Redis supports Bloom filters through a module, and you can also keep one in-process.

Also validate input at the edge (id formats, ranges) and apply rate limiting per client (Chapter 16); these stop the crudest attacks before any cache logic runs.

4. Cache avalanche: mass expiry or loss

A cache avalanche is a stampede on a larger scale: a large fraction of the cache becomes unavailable at once, so the database receives a wave of misses for many different keys. Common causes:

  • Synchronised TTLs. A job loads 500,000 keys at 03:00 with a one-hour TTL. At 04:00 they all expire together.
  • Cache restart or flush. A node or the whole cluster restarts with an empty memory, or someone runs a flush command.
  • Deploy side effects. A new release changes the key format (or a cache-key version prefix), so every key misses until refilled.
  • Node failure. One shard of a ten-shard cache dies: 10% of the keys vanish, which for a database sized for 3% misses is already a 3x overload.

4.1 Defences

  • TTL jitter. Add randomness: instead of exactly 3,600 seconds, use 3,600 plus a random 0-600 seconds. Expiries then spread over ten minutes instead of landing at one instant. It is the single cheapest anti-avalanche measure.
  • Warm-up. Before a new or restarted cache takes traffic, preload the hottest keys (from a hot-key list, recent access logs, or a replay of top queries). See cold start in Chapter 13.
  • Staggered deploys and rolling restarts. Restart cache nodes one at a time, and let the cache refill before the next. With key-format changes, use gradual rollout (a percentage of traffic on the new key version) or dual-write old and new keys during migration.
  • Multi-layer caching. A small in-process cache in front of the distributed cache, and a CDN in front of both, mean losing one layer is partly absorbed by the next.
  • Protect the database. Per-query concurrency limits, connection-pool caps, and load shedding (Chapter 16) ensure a miss wave queues or fails fast rather than collapsing the database.
  • Replicas and sharding with smaller blast radius. More, smaller cache nodes (with replicas) mean one failure loses a smaller share of keys.

5. Hot keys and big keys

Even a perfectly working cache can be unbalanced. Distributed caches assign each key to one node, so load on a key lands on one machine. Two shapes of imbalance matter.

5.1 Hot keys

A hot key is a single key receiving a huge share of traffic: the product page during a flash sale, a celebrity's profile, a global config. Adding cache nodes does not help, because the key lives on exactly one of them. That node's CPU or network saturates while the others idle, and its latency spikes for every other key it holds too. Remedies:

  • Local replicas (in-process copy). Each application server keeps the hot key in its own memory for a very short TTL (1-5 seconds). Requests are answered from the process with no network hop, and the distributed cache sees one read per server per few seconds instead of thousands per second.
  • Key splitting with suffixes. Store N copies under keys like product:42#0 to product:42#7. Readers pick a random suffix, so the load spreads over up to 8 nodes. Writers must update or delete all copies, so use this for read-heavy, rarely-changing values.
  • Request-level cache. Within one request, memoise lookups so the same key is not fetched many times (a page that renders a "current user" widget 20 times should fetch it once).
  • Detecting hot keys. You cannot fix what you cannot see. Options: client-side sampling counters that report the top keys, proxy-level statistics, the cache server's own hot-key reporting where available (Redis has a --hotkeys scan mode under certain eviction policies, and monitoring commands that are too expensive to leave on in production), or sampled logs. Many teams run a periodic job that aggregates sampled counters and pushes the top keys into a local-replica list automatically.

5.2 Big keys

A big key is a single value that is very large: a 50 MB serialised list, a hash with ten million fields, a leaderboard stored as one object. Problems: reading it blocks the (often single-threaded) server for milliseconds to seconds, saturates the network link, causes memory fragmentation, and makes deletion or expiry stall the node. Rebalancing and replication of that key are slow. Fixes: split large collections into pages or buckets (feed:user42:page3), store only ids and fetch details separately, compress values, set a size limit in code review, and scan for outliers regularly. In practice, keeping values under a few hundred KB, and collections under tens of thousands of elements, avoids most trouble.

6. Consistency between cache and database

The cache and the database are two separate stores, and no transaction spans both. Any scheme that updates them in sequence can interleave badly with another request. Chapter 13 covered the standard approach (update the database, then delete the cache key) and why it is preferred. Here are the concrete races that remain.

6.1 Race 1: stale fill after delete

Reader R finds a miss and reads the old value from the database. Before R writes it to the cache, writer W updates the database and deletes the cache key. Then R, slow, writes the old value into the cache. The cache now holds stale data until its TTL ends. This needs a read to be slower than a write plus delete, so it is rare but real, especially with read replicas lagging behind the primary.

6.2 Race 2: why update-then-set is worse

If writers set the new value in the cache instead of deleting, two concurrent writers can update the database in order A then B, but write the cache in order B then A. The cache keeps A's value permanently (until TTL) while the database holds B's. Deleting is safer because a deleted key is simply refilled from the truth. Deleting the cache before updating the database is also bad: a reader can refill the old value in between.

6.3 Fixes

  • Short TTL as a backstop. The cheapest safety net: even if a race leaves stale data, it dies within the TTL. Every cached entry should have one.
  • Delayed double delete. Delete the key right after the database write, then delete it again after a delay (for example 500 ms to 1 s, longer than a read-plus-fill plus replication lag). The second delete removes any stale fill from Race 1. It narrows the window rather than closing it, and needs a reliable way to run the delayed task (a queue with delay, not a thread sleep that dies on restart).
  • Versioning. Store a version number (row version, timestamp or log sequence number) with the data. A fill is written only if its version is newer than what the cache holds (a compare-and-set script, or a versioned key such as product:42:v17 where the writer bumps the current-version pointer). The stale reader's write is then rejected or lands under an old key nobody reads.
  • CDC-based invalidation. Instead of the application deleting keys, a change-data-capture pipeline reads the database's commit log (binlog or WAL) and issues the deletes. Because the log is ordered and only contains committed changes, invalidation never misses a write (even from other services or batch jobs), and can be retried until it succeeds. You can also apply the delayed second delete here. The price is extra infrastructure and a small lag (typically tens to hundreds of milliseconds).
  • Leases. The cache hands the missing reader a token; a write or delete invalidates the token, so the late SET is refused. Memcached-style leases (described in the Facebook memcache paper) do this and also reduce stampedes, since only the token holder refills.
  • Accept staleness. Many data types tolerate seconds of staleness (view counts, recommendations, catalog descriptions). Decide the budget per data type explicitly. For data where staleness is unacceptable (account balance, inventory at checkout, permissions revocation) do not read through the cache for the decision, or read the database for the final check.
Watch out Read replicas make the race worse: a reader fills the cache from a replica that lags by a few hundred milliseconds, so the cache can be refilled with a value older than the write just invalidated. Delayed delete should be longer than the replica lag, or fills should read from the primary for recently written keys.

7. The cache as a dependency: degrading gracefully

Teams often call the cache "optional" in design reviews and then discover in an outage that it is load-bearing. Decide in advance what happens when the cache is slow or unreachable.

  • Tight timeouts. A cache lookup should have a timeout of a few milliseconds to tens of milliseconds. A cache that hangs for 2 seconds is worse than a cache miss: threads pile up waiting and the whole service stalls. Treat a timeout as a miss.
  • Circuit breaker. If cache errors exceed a threshold (say 50% over 10 seconds), stop calling the cache for a period and go straight to the next path, then probe occasionally to see if it recovered. This avoids paying the timeout on every request. (Breakers are covered in Chapter 27.)
  • Protect the database. With the cache gone, the database must not receive the full load. Options: serve stale data from a local in-process cache, cap concurrent database queries per instance with a semaphore, shed low-priority traffic, return a degraded response (omit recommendations, show cached-at-CDN page), and keep a coarse rate limiter in front.
  • Avoid cold-start overload on recovery. When the cache comes back empty, the first minutes are an avalanche. Bring traffic back gradually (ramp from 10% to 100%), warm hot keys first, and keep the breaker half-open so only some requests refill at a time. Do not let all instances reconnect and flood the new node simultaneously.
  • Retries with backoff and jitter. A retry storm against a recovering cache or database prolongs the outage.
  • Test it. Run game days that kill the cache in a staging environment or a small slice of production. Capacity tests should be done with the cache disabled, to learn the real limit of the database.

8. Local versus distributed caches, and two-level caches

8.1 The two kinds

A local (in-process) cache lives inside the application's own memory (for example Caffeine in Java, or a simple map with expiry). Access takes microseconds, with no network and no serialisation. Each server has its own copy, so the fleet holds N duplicates, the data is limited by the process heap, and copies can disagree with each other: one server may have the new value while another still has the old one. A distributed cache (Memcached, Redis) is a separate tier of servers shared by all application servers. Access takes a network round trip (typically 0.2 to 1 ms inside a data center), but every server sees the same data, the total capacity scales by adding nodes, and the cache survives application restarts.

8.2 Two-level caches and invalidation broadcast

The two are often combined. L1 is a small in-process cache with a short TTL; L2 is the distributed cache; the database is last. A read checks L1, then L2, then the database, filling each level on the way back. L1 absorbs hot keys and removes network cost; L2 gives a large shared pool. The difficulty is invalidation: when one server changes data and deletes the key in L2, the L1 copies on the other servers still hold the old value. Options:

  • Short L1 TTL only. Simplest. Accept up to a few seconds of staleness. Good enough for most read-heavy data.
  • Invalidation broadcast. When a key changes, publish an event (Redis pub/sub, a message bus, or a CDC stream) that every server subscribes to, and each drops its local copy. This brings staleness down to the message delay, but pub/sub is usually best-effort: a server that is disconnected misses messages, so the short L1 TTL must remain as a backstop.
  • Server-assisted client caching. Some stores can tell clients which keys they cached have changed (Redis client-side caching tracking, covered in Chapter 15).

9. Distributed cache architecture

Once the cache is a fleet of nodes, the first question is: which node holds which key? There are three common answers.

9.1 Client-side sharding with consistent hashing

The client library knows the list of cache nodes and picks one by hashing the key. A naive scheme, node = hash(key) mod N, remaps almost every key when N changes (going from 10 to 11 nodes moves about 10/11 of the keys, an instant near-total miss storm). Consistent hashing places nodes and keys on a ring; a key belongs to the next node clockwise. Adding or removing one node moves only about 1/N of the keys. Virtual nodes (each physical node appears at many ring positions) smooth out the load. The mechanism and its trade-offs are explained in Chapter 25. Memcached client libraries (such as ketama-style hashing) use exactly this. Strength: no extra hop, no extra component. Weakness: every client needs the same node list and algorithm, so a membership change must roll out consistently or clients disagree; and logic is duplicated across languages.

9.2 Proxy-based

Clients talk to a proxy that knows the topology and forwards requests: twemproxy (nutcracker, from Twitter) for Redis and Memcached, and mcrouter (from Facebook) for Memcached. The proxy handles sharding, connection pooling (reducing the number of connections that cache nodes must hold), failover, and in mcrouter's case features such as replicated pools, prefix routing and shadow traffic for warming. Clients stay simple and topology changes happen in one place. The cost is one more network hop (typically sub-millisecond), and the proxy tier itself must be highly available and scaled.

9.3 Server-side cluster

The cache nodes themselves know about each other and the key placement, as with Redis Cluster, which divides the key space into 16,384 hash slots assigned to nodes. A client sends a command to any node; if the slot belongs elsewhere, the node answers with a redirection (MOVED) and smart clients cache the slot map. Nodes detect failures and promote replicas without external coordination. Details are in Chapter 15. This avoids a proxy and gives built-in failover, but clients must be cluster-aware, and multi-key operations are limited to keys in the same slot.

9.4 Adding and removing nodes

With consistent hashing, adding a node takes over about 1/N of the keys from its neighbours. Those keys are absent from the new node, so they miss and are refilled from the database: a controlled mini-avalanche of about 1/N of your traffic. With 10 nodes that is roughly 9% of keys, which at a 97% hit ratio takes misses from 3% to about 11% for a while. Add nodes gradually, ideally in off-peak time, and warm them. Removing or losing a node strands its keys and sends them to neighbours the same way. A subtle problem is stale resurrection: if a node leaves, a key is written elsewhere, and the node later returns still holding an older copy of that key, readers can see old data. Remedies are short TTLs, flushing a node before rejoining, or using a design that treats cache nodes as disposable.

9.5 Replication for cache availability

A plain Memcached cluster has no replication: a lost node is simply lost keys. That is acceptable when the database can absorb the miss wave. When it cannot, replicate. Redis supports primary-replica replication and automatic failover (Sentinel or Cluster), so a replica holds a copy and takes over in seconds. Memcached-based deployments use mcrouter replicated pools: writes go to two or more pools and reads go to one, falling back to another on failure. Another approach is "gutter" nodes (from the Facebook design): a small spare pool that takes over for a failed node's keys with a short TTL, so the failure does not push its entire load to the database. Replication doubles memory cost, and asynchronous replication means a failover can lose the last few writes or serve slightly older data, which is usually fine for a cache.

11. Monitoring a cache

A cache that is not measured degrades silently. Track:

  • Hit ratio (hits divided by hits plus misses), overall and per key prefix or endpoint. A fall from 97% to 94% doubles the database's miss traffic, so alert on changes, not only on a low absolute value.
  • Evictions per second. Steady evictions mean the working set exceeds memory: the cache is too small or values are too big. A sudden jump signals a new large-key pattern or a leak. Compare with expirations: expiry is normal, eviction is pressure.
  • Latency percentiles (p50, p99, p99.9) as seen by clients, not just server-side. Slow commands, big keys, swapping, and network saturation show first in the tail.
  • Memory: used versus configured maximum, and the fragmentation ratio (resident memory divided by memory the store thinks it uses). A ratio well above 1.5 means a lot of memory is wasted by allocator fragmentation (common after many deletes of varied-size values); a ratio below 1 can mean the system is swapping, which is disastrous for latency.
  • Connections, network throughput, CPU per node, and per-node key counts and request rates to spot imbalance and hot keys.
  • Replication lag and failover events where replicas exist.
  • Database load alongside cache metrics. The cache-to-database ratio is the real outcome: queries per second reaching the database should move inversely with hit ratio.

12. Capacity planning with numbers

Suppose a service has 20 million active users, and the cache stores a 2 KB profile object for each, plus 5 KB for 2 million product records.

  1. Raw data: 20,000,000 x 2 KB = 40 GB, plus 2,000,000 x 5 KB = 10 GB, total 50 GB.
  2. Overhead: each entry carries key, metadata and allocator overhead, typically 50 to 100 bytes or more; 22 million entries add roughly 2 GB. Allocator fragmentation and headroom add another 20 to 30%. Plan for about 50 GB x 1.3 + 2 GB, roughly 67 GB.
  3. Do we need it all? Access is skewed (Chapter 13). If the hottest 20% of users produce 80% of reads, caching only those 4 million profiles (8 GB) already gives a hit ratio near 80% for profiles. A full dataset gives about 97% or more with TTL-limited misses. Decide using the database's headroom: if the DB can take 5,000 reads per second and peak is 100,000, you need at least a 95% hit ratio, which pushes toward caching most of the active set.
  4. Node count by memory: with 16 GB usable per node, 67 GB needs 5 nodes. Add replicas (x2, so 10 nodes) and spare capacity so that losing one node still leaves memory to hold the data: 6 primaries plus 6 replicas is a common shape.
  5. Throughput check: 100,000 reads per second at 97% hit ratio is 97,000 cache reads per second across 6 primaries, about 16,000 per second each, well within a single node's capability (tens of thousands to hundreds of thousands of simple operations per second). Bandwidth: 97,000 x 2 KB is about 194 MB/s total, or roughly 32 MB/s per node, comfortable on a 10 Gbit link.
  6. Failure budget: losing one of 6 primaries without replicas loses about 17% of keys. At 100,000 requests per second that adds about 17,000 misses per second to the database, over three times what it can handle (5,000). So either replicate, add more smaller nodes, or have load shedding ready. This single calculation justifies replication for this system.
Interview tip State the failure case in numbers: "if one cache node dies, X% of keys miss, which becomes Y queries per second against a database that can do Z". It shows you size caches for failure, not just for the average day.

13. A worked incident walkthrough

An e-commerce site runs a sale. Product pages are cached for 10 minutes (TTL 600 s). The database (one primary and two replicas) handles about 6,000 reads per second. Normal peak traffic is 120,000 page reads per second at a 98% hit ratio, so the database sees 2,400 per second.

13.1 What happened

The operations team restarted all cache nodes at once for a security patch. With an empty cache, every request missed. 120,000 reads per second hit a database that handles 6,000. Queries queued, response times rose past the application's 2-second timeout, and the application retried each failed read twice, so demand rose to roughly 360,000 attempts per second. Even when a page's value was fetched successfully, it often arrived after the client had given up, so the cache was not refilled quickly. The system stayed down well after the restart had ended, because the arrival rate exceeded capacity continuously: a classic metastable failure, where the overload sustains itself.

13.2 Recovery

  1. Block most traffic at the load balancer, admitting about 5%, so the database sees roughly 6,000 per second.
  2. Disable retries or enable backoff, to stop the amplification.
  3. Run a warm-up job that loads the top 50,000 products from a pre-computed hot-key list.
  4. Raise admitted traffic step by step (5%, 20%, 50%, 100%) as the hit ratio climbs above 90%, and watch DB latency at each step.

13.3 Prevention

  • Rolling restarts, one node at a time, with replicas and a refill pause between nodes.
  • Single-flight and short locks so each product is loaded once, not thousands of times.
  • TTL with jitter, and a stale-while-revalidate window.
  • A circuit breaker plus per-instance database concurrency limit, and retry budgets with exponential backoff.
  • A runbook with the traffic-gating and warm-up steps, rehearsed in a game day, and a standing alert on hit ratio drop.

14. Common interview questions

What is a cache stampede and how do you prevent it?

A stampede happens when a popular key expires or is evicted and many concurrent requests all miss and recompute it against the database at once. I prevent it in layers. Inside each server I use single-flight so concurrent requests for one key share one load. Across servers I add a short-TTL lock so only one refill runs, or I use stale-while-revalidate so readers get the old value while one refresh happens in the background. For known hot keys I use refresh-ahead or probabilistic early expiration, and I add TTL jitter so keys do not expire together.

Distinguish cache penetration, stampede and avalanche.

Stampede is many requests for one key that just disappeared. Avalanche is a large number of different keys becoming unavailable together, such as synchronised expiry or a cache restart. Penetration is requests for keys that do not exist at all, so they can never be cached and always reach the database. The fixes differ: single-flight and locks for stampede, jitter, warm-up and layering for avalanche, and negative caching and Bloom filters for penetration.

How would a Bloom filter protect the database from random-key attacks?

I load the filter with all valid ids, then check it before the cache. If it says the id is definitely absent, I return not found immediately, with no cache or database access. A Bloom filter has no false negatives, so real keys are never rejected, and a small false-positive rate only means a few non-existent keys fall through to normal cache-aside. It uses about ten bits per key at 1% false positives. The weakness is that deletions need a counting filter or rebuild, so I rebuild periodically and also cache NULL results with a short TTL.

How do you handle a hot key?

First I detect it with sampled counters or per-node request metrics, because adding nodes does not help when a key lives on one node. Then I keep a very short-lived copy in each application process, so most reads never reach the network. If it is still too hot, I split the value into several copies under suffixed keys that hash to different nodes and let readers pick randomly, with writers updating all copies. This suits read-heavy data. I would also check that nothing is accidentally making the key hotter, such as repeated lookups in one request.

Explain a race condition between a cache and a database and how to fix it.

A slow reader misses the cache, reads the old value from the database, and before it fills the cache a writer updates the database and deletes the key. The reader then writes the old value into the cache, which stays stale until the TTL. Fixes include a short TTL as a safety net, a delayed second delete after the replica lag, writing with a version so older values are rejected, memcache-style leases, or CDC-based invalidation that deletes keys from the commit log. I choose based on how stale the data is allowed to be.

Why delete the cache entry instead of updating it on write?

If two writers update the database in one order and the cache in the opposite order, the cache keeps the wrong value indefinitely. A delete has no value to get out of order: the next reader refills from the database, the source of truth. Delete also avoids wasting work on keys that will not be read again before they change. The remaining risk is the stale-fill race, which is handled by TTLs, delayed delete or versioning.

What happens if the cache cluster goes down, and how do you design for it?

All reads fall through to the database, so if the database is sized for the cache's hit ratio it can be overloaded and take the whole service down. I design for it with tight cache timeouts treated as misses, a circuit breaker, per-instance concurrency limits on database queries, load shedding of low-priority traffic, a local in-process cache as a fallback, and replicas so a single node failure does not lose its keys. On recovery I ramp traffic gradually and warm hot keys first, to avoid a second wave.

Compare client-side sharding, a proxy, and a server-side cluster for a distributed cache.

Client-side sharding uses a consistent-hash ring in the client library: there are no extra hops, but every client needs the same membership list and library logic. A proxy such as twemproxy or mcrouter keeps clients simple and centralises routing, pooling and failover, at the cost of an extra hop and another tier to operate. A server-side cluster, like Redis Cluster, has nodes own hash slots and redirect clients, giving built-in failover and resharding but requiring cluster-aware clients and restricting multi-key operations. In all three, a hot key still sits on one node.

What happens when you add a node to a cache cluster, and how do you limit the damage?

With consistent hashing, about 1/N of the keys move to the new node, and those keys miss until refilled. With modulo hashing nearly everything moves, which is why modulo is a bad choice. To limit the impact I add one node at a time during low traffic, warm the new node if possible, keep stampede protection on, and ensure the database has headroom for the extra misses. For removals I do the same in reverse, and I make sure a returning node does not serve stale old data.

When would you use a two-level cache, and what is its main problem?

I use an in-process L1 over a distributed L2 when some data is very hot and tolerates brief staleness, because L1 removes network latency and shields L2 from hot keys. The main problem is that L1 copies on different servers can diverge when data changes. I handle it with a short L1 TTL, often a few seconds, plus an invalidation broadcast over pub/sub or CDC so servers drop their local copy quickly. Because broadcasts can be lost, the TTL remains as the backstop.

How do you size a cache and decide how many nodes you need?

I estimate the number of entries times the average size, add per-entry overhead and 20 to 30% headroom for fragmentation, and then consider the access skew to see how much of the data actually must be cached for the target hit ratio. I derive the target hit ratio from the database's capacity: the allowed miss rate is database capacity divided by peak traffic. Then I divide by usable memory per node and add replicas. Finally I test the failure case: losing one node must not push the database past its capacity.

15. Recap

  • A cache hides load from the database. Every failure mode here is a way that protection briefly disappears, so size and protect the database for misses.
  • Stampede: many requests refill one key. Use single-flight, short locks, stale-while-revalidate, probabilistic early expiry, refresh-ahead.
  • Penetration: non-existent keys bypass the cache. Use negative caching with short TTLs, Bloom filters, input validation, and rate limits.
  • Avalanche: many keys vanish together. Use TTL jitter, warm-up, rolling restarts, multi-layer caching, and database protection.
  • Hot and big keys unbalance nodes: use local copies, suffix splitting, request-level caching, detection, and size limits.
  • Consistency: delete after write, always set a TTL, and add delayed double delete, versioning, leases or CDC for stricter needs; accept staleness where the data allows.
  • Dependency: timeouts as misses, circuit breakers, DB concurrency limits, graceful degradation, gradual recovery.
  • Architecture: local caches for speed, distributed for shared capacity, two-level with invalidation broadcast; shard by consistent hashing in the client, a proxy, or a cluster; replicate when failure would overload the database.
  • Operate it: watch hit ratio, evictions, tail latency and fragmentation; plan capacity for the failure case.
