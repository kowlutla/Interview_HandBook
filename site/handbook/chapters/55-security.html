Security for System Design

Every design you draw in an interview will be asked one question at the end: "and how is this secured?" This chapter gives you a structured answer: how to think about threats, how users and services prove who they are, how access is decided, how data is protected in transit and at rest, and how to keep a multi-tenant system safe end to end.

1. Threat modeling: how to think before you pick tools

Security in a system design interview is not a list of products. It is a way of reasoning. The reasoning is called threat modeling, and it answers four plain questions: what are we protecting, who might attack it, how could they get at it, and what do we do about that? If you can walk through those four questions out loud for any design, you will sound like a senior engineer, because you are showing that every control you add exists for a reason.

1.1 Assets, attackers, and trust boundaries

An asset is anything of value that an attacker would want or that you must keep correct: customer data, passwords, payment details, encryption keys, the availability of the service itself, and the integrity of records such as account balances. Ranking assets matters, because you cannot defend everything equally. A public blog post and a stored credit-card token deserve different effort.

An attacker (or "threat actor") is described by capability and motivation, not by name. Typical ones are an anonymous person on the internet, a registered user who tries to read another user's data, a malicious or compromised tenant in a multi-tenant system, a compromised internal service, a malicious insider, and an attacker who has stolen a laptop or a credential. Notice that several of these are already "inside" your network. Modern security assumes the network is not a safe place.

A trust boundary is a line in your architecture where the level of trust changes: from the internet into your edge, from the edge into your private network, from one tenant to another, from your service into a third-party API, from application code into the database. The most important rule of threat modeling is this: data and requests crossing a trust boundary must be authenticated, validated, and often encrypted. Most real breaches are a failure to treat some boundary as a boundary, for example trusting a header that a client could have set, or trusting any caller that happens to be inside the VPC.

Always say what you are not defending against (for example, a nation-state with physical access to your data center) so the interviewer sees that you made a conscious choice.

1.3 Principles that guide every decision

  • Least privilege: every user, service, and key gets only the permissions it needs, for only as long as it needs them. A service that reads one table should not hold credentials that can drop the database.
  • Defense in depth: assume any single control will fail and layer several, so one failure is not a breach. Section 18 draws the layers.
  • Secure by default and fail closed: when something is unknown or an error happens (the authorization service is down), deny rather than allow.
  • Never trust the client: anything from a browser or mobile app can be forged. Re-check permissions and re-validate input on the server.
  • Minimize the attack surface: fewer public endpoints, fewer open ports, fewer dependencies, less data stored. Data you never collected cannot leak. This links to Chapter 56.
  • Use proven building blocks: never invent your own cryptography or your own authentication protocol. Use TLS, OAuth 2.0, OIDC, and well-reviewed libraries.

2. Authentication versus authorization

These two words are confused constantly, and mixing them up in an interview is a red flag. Authentication (authn) answers "who are you?" It verifies an identity, using something you know (password), something you have (phone, hardware key), or something you are (fingerprint). Authorization (authz) answers "what are you allowed to do?" It takes an already-known identity and decides whether it may perform a specific action on a specific resource.

The order is fixed: authenticate first, then authorize. A request that fails authentication gets HTTP 401 Unauthorized (the name is historic; it really means "unauthenticated"). A request from a known user who lacks permission gets 403 Forbidden. A third subtle option is to return 404 Not Found for resources the caller must not even know exist, which avoids leaking existence of other tenants' objects.

A very common bug class, ranked first in the OWASP API list, is broken authorization: the system authenticates the caller correctly but forgets to check that the caller owns the object they asked for. Fetching /orders/1002 while logged in as the owner of order 1001 and getting the data is called an IDOR (insecure direct object reference) or, in API terms, BOLA (broken object level authorization). Section 10 and section 16 return to it.

Interview tip State the split early: "Authentication happens once at the edge and produces a verified identity. Authorization happens on every request, close to the data, using that identity." This single sentence frames most of the rest of your answer.

3. Passwords and credentials

Even with modern options such as passkeys, most systems still store passwords. The rules for doing it correctly are well established, and interviewers love to probe them.

3.1 Never store the password: store a slow, salted hash

If you store passwords in plain text, one database leak exposes every user, and because people reuse passwords, it exposes their accounts elsewhere too. If you encrypt them, then whoever steals the key (often stored nearby) gets them all. The correct approach is a one-way hash: you store a value computed from the password that cannot be reversed. At login you hash the submitted password the same way and compare.

But ordinary hashes such as SHA-256 are designed to be fast, and fast is the enemy here. A modern GPU can try billions of SHA-256 guesses per second, so a leaked table of fast hashes falls to a dictionary attack in hours. Password hashing therefore uses deliberately slow and memory-hungry algorithms with a tunable cost:

  • Argon2id: the current recommendation (winner of the Password Hashing Competition). You tune memory, iterations, and parallelism. Memory hardness makes GPU and custom-hardware attacks expensive.
  • bcrypt: older, widely available, with a cost factor that doubles the work for each increment. It limits input to 72 bytes. Perfectly acceptable if Argon2 is not available.
  • scrypt and PBKDF2: scrypt is memory-hard; PBKDF2 is the one often required by compliance standards, but it is weaker against GPUs because it is not memory-hard.

You tune the cost so that one hash takes roughly 100 to 500 ms on your hardware. That is invisible to a human logging in but cripples an attacker who needs billions of guesses.

3.2 Salt and pepper

A salt is a random value, unique per user, mixed into the hash and stored beside it in plain form. It does two jobs. First, two users with the same password get different hashes, so an attacker cannot see who shares a password. Second, it defeats rainbow tables, precomputed tables of hash-to-password, because the table would need to be rebuilt for every salt. Modern libraries generate and embed the salt in the output string automatically (the stored string contains the algorithm, the cost, the salt, and the hash). A pepper is an additional secret mixed in that is stored outside the database, for example in a KMS or HSM, so a stolen database alone is not enough to crack hashes. It is optional defense in depth.

3.3 Defending the login endpoint

The hash protects data at rest. The login endpoint needs its own defenses against online guessing:

  • Rate limiting and lockout: limit attempts per account and per IP address, with exponential back-off. Locking an account hard after five failures lets an attacker lock out real users (a denial of service), so prefer progressive delays plus CAPTCHA or step-up challenges. Rate limiting mechanics are in Chapter 16.
  • Credential stuffing: attackers take username and password pairs leaked from other sites and try them on yours, at low rate from thousands of IPs, so per-IP limits fail. Defenses: check new passwords against breached-password lists, device and behavior risk scoring, bot management (section 17), and MFA.
  • Uniform responses: return the same message and similar timing for "unknown user" and "wrong password" so attackers cannot enumerate valid accounts.
  • MFA (multi-factor authentication): require a second factor. Strength differs: SMS codes can be hijacked by SIM swapping; TOTP apps (a code derived from a shared secret and the current time) are better; push approvals can be abused by "fatigue" prompts; WebAuthn / passkeys (public-key credentials bound to the site origin) are phishing-resistant because the browser will not sign a challenge for a fake domain.
  • Account recovery is part of the attack surface. Reset tokens must be random, single-use, short-lived, and stored hashed. A weak "forgot password" flow bypasses all your hashing work.
Watch out Slow hashing is also a denial-of-service lever: an attacker can spam your login with requests, each costing 300 ms of CPU. Rate-limit before hashing and consider isolating login work on its own pool of servers.

4. Sessions versus tokens, cookies and CSRF

After a user authenticates, you cannot ask for the password on every request. The server must remember that this client already proved its identity. There are two classic ways.

4.1 Server-side sessions

The server creates a random, unguessable session ID (at least 128 bits from a cryptographic random generator), stores the session data (user ID, roles, expiry) in a store such as Redis (Chapter 15), and gives the ID to the client in a cookie. On every request the server looks the ID up. Benefits: you can revoke instantly (delete the entry), you can change permissions mid-session, and the client holds nothing meaningful. Cost: a lookup per request and a shared session store that must be highly available and scaled, which is why stateless services in horizontally scaled systems often prefer tokens.

4.2 Stateless tokens

The server issues a signed token that contains the identity and claims (section 5). Any server can verify it using only a key, with no lookup. That scales easily and works across services. The price is that revocation is hard (section 5.4).

4.3 Cookies and their security flags

Browsers send cookies automatically with every matching request. The flags you must know:

  • HttpOnly: JavaScript cannot read the cookie, so a cross-site scripting (XSS) bug cannot steal it directly.
  • Secure: sent only over HTTPS.
  • SameSite=Lax | Strict | None: controls whether the cookie is sent on cross-site requests. Strict never sends it cross-site. Lax (the browser default today) sends it on top-level navigations such as clicking a link, but not on cross-site POSTs, images or frames. None requires Secure and allows all cross-site use (needed for some embedded or third-party flows).
  • Domain, Path, and the __Host- name prefix, which pins a cookie to one exact host and prevents sibling subdomains from overwriting it.
  • Max-Age / Expires: bound the lifetime. Also set an idle timeout and an absolute timeout on the server side.

4.4 CSRF and XSS: the two browser attacks

CSRF (cross-site request forgery) abuses the fact that cookies are sent automatically. You are logged in to bank.example. You visit evil.example, which contains a hidden form that posts to bank.example/transfer. Your browser attaches your bank cookie, and the bank thinks you made the request. Defenses: SameSite cookies (the first line today), a per-session anti-CSRF token that must be echoed in a header or form field (an attacker's page cannot read it, because of the same-origin policy), checking the Origin header, and requiring a custom header or JSON content type on state-changing requests. Note that CSRF applies to credentials the browser attaches automatically (cookies, basic auth). A token placed manually in an Authorization header by your own JavaScript is not sent by the attacker's page, so it is immune to CSRF.

XSS (cross-site scripting) means attacker-controlled script runs inside your page. It can do anything the user can do, and if tokens live in localStorage, it can steal them. Defenses: escape output by context (most frameworks do by default), avoid dangerous DOM APIs, sanitize any user HTML, and deploy a strict Content Security Policy that restricts where scripts may load from.

5. JSON Web Tokens in depth

A JWT (JSON Web Token, pronounced "jot") is the most common token format. It is a compact, URL-safe string that carries claims and is protected by a signature, so a receiver can trust the contents without asking anyone.

5.1 Structure

A signed JWT (technically a JWS) has three parts separated by dots, each Base64URL-encoded: header.payload.signature.

  • Header: JSON naming the signing algorithm (alg), the token type, and usually a key identifier (kid) saying which key signed it.
  • Payload (claims): JSON statements about the subject. Registered claims include iss (issuer), sub (subject, the user ID), aud (audience, who the token is for), exp (expiry time), nbf (not before), iat (issued at), and jti (unique token ID). You add custom claims such as roles or tenant ID.
  • Signature: computed over header.payload with a key. Changing any byte invalidates it.
Watch out A signed JWT is encoded, not encrypted. Anyone holding it can Base64-decode and read the claims. Never put secrets or sensitive personal data in the payload. If confidentiality is needed, use an encrypted token (JWE) or an opaque reference token.

5.2 Signing algorithms

  • HS256 (HMAC with a shared secret): one secret both signs and verifies. Simple and fast, but every verifier can also forge tokens, so it only suits one service talking to itself.
  • RS256 / ES256 (asymmetric signatures): the issuer signs with a private key, and everyone verifies with the public key. Verifiers cannot forge tokens. This is the right choice when many services or third parties consume tokens. ES256 and EdDSA give smaller signatures and faster operations than RSA.

5.3 Validation: the checklist, and famous pitfalls

Verifying means more than "the signature is valid". A correct validator checks, in order: the algorithm is on a server-side allow-list; the signature verifies with the key looked up by kid from a trusted source; iss equals the expected issuer; aud includes this service; exp is in the future and nbf in the past (allow small clock skew, such as 60 seconds); and any required claims are present. Known pitfalls:

  • alg: none: the spec once allowed unsigned tokens. Libraries that obeyed the header accepted forged tokens. Never let the token choose the algorithm.
  • Algorithm confusion: an attacker switches an RS256 token to HS256 and signs it using the server's public key as the HMAC secret. If the library uses the same key for both, it validates. Fix: fix the expected algorithm per key.
  • Missing aud check: a token meant for service A is replayed against service B, which trusts the same issuer.
  • Trusting kid or jku URLs from the token to fetch keys from attacker-controlled locations. Only fetch keys from your configured issuer.

5.4 Expiry, refresh tokens, and the revocation problem

Because a self-contained token is valid until exp and no server checks a list, you cannot cancel it. If a token leaks or a user is fired, it works until it expires. This is the revocation problem, and the standard answer has layers:

  1. Short-lived access tokens (5 to 15 minutes). The damage window is small.
  2. Long-lived refresh tokens stored securely (HttpOnly cookie, or secure storage on mobile) and exchanged at the authorization server for new access tokens. Refresh tokens are checked against a database, so they can be revoked. Revoking the refresh token stops renewal, so access ends within one access-token lifetime.
  3. Refresh token rotation: each use returns a new refresh token and invalidates the old one. If an old one is presented again, that signals theft, and the server revokes the whole token family.
  4. Deny lists for emergencies: a small, fast store (cache) of revoked jti values or "tokens issued before time T for user X are invalid", checked by the gateway. This adds back a lookup, but only against a tiny set, and entries expire when the tokens would have.
  5. Opaque tokens with introspection: for high-risk operations, use random reference tokens that the resource server validates by calling the authorization server (RFC 7662 introspection). Fully revocable, at the cost of a call (cacheable for seconds).

Stale claims are the sibling problem: if a user's role changes, the old token still carries the old role until expiry. Short lifetimes plus keeping fine-grained permissions out of the token (look them up at decision time) keeps this manageable.

5.5 JWKS and key rotation

With asymmetric signing, verifiers need the issuer's public keys. The issuer publishes them as a JWKS (JSON Web Key Set), a JSON document at a well-known URL (for example https://auth.example.com/.well-known/jwks.json), with each key labeled by kid. Services fetch it, cache it (respecting cache headers), and refetch when they see an unknown kid. Rotation is then smooth: publish the new public key first, start signing with it, keep the old public key published until all tokens signed with it have expired, then remove it. No service redeploy is needed, which makes JWKS a good example of how config distribution (Chapter 49) supports security.

6. OAuth 2.0: delegated authorization

OAuth 2.0 solves a specific problem: letting an application act on a user's behalf at another service without giving the application the user's password. A photo-printing site wants to read your photos in a cloud drive. Instead of asking for your drive password, it redirects you to the drive's login, you approve a narrow permission, and the printing site receives a limited, revocable access token.

The four roles: the resource owner (the user), the client (the app asking for access), the authorization server (issues tokens after authenticating the user and getting consent), and the resource server (the API that accepts the tokens). Scopes name what access is requested (photos:read). Note that OAuth is about authorization (delegated access), not login. Login on top of OAuth is OIDC (section 7).

6.1 Authorization code flow with PKCE

This is the flow to recommend for almost every interactive app: server-rendered web apps, single-page apps, and mobile apps. It works in two steps so the access token never travels through the browser's address bar. The browser carries only a short-lived, single-use authorization code, which the client then exchanges at the token endpoint over a direct back-channel.

PKCE (Proof Key for Code Exchange, pronounced "pixy") protects public clients, which cannot keep a secret (a mobile app or browser app), from an attacker who intercepts the code. The client invents a random code_verifier, sends only its hash (code_challenge) in the first step, and reveals the verifier in the exchange. The server checks that the hash matches. An attacker who stole the code does not know the verifier, so the code is useless to them. Current guidance recommends PKCE for all clients, even confidential ones.

6.2 Client credentials

No user is involved: a backend service authenticates as itself to get a token for machine-to-machine calls. The client sends its client_id and a secret (or better, a signed client assertion or an mTLS certificate) to the token endpoint and gets back an access token with the scopes it was granted. Use it for server jobs and service integrations. The token represents the application, so it must never be used where a user identity is needed for authorization.

6.3 Device code flow

For devices without a browser or keyboard, such as a smart TV or a CLI. The device requests a device code and a short user code from the authorization server and shows the user a URL and the short code. The user opens the URL on a phone or laptop, signs in, and enters the code. Meanwhile the device polls the token endpoint until the user finishes, then receives its tokens. The user authenticates on a capable device, and the constrained device never handles the password.

6.4 Why implicit flow is deprecated, and other flows to avoid

The implicit flow returned the access token directly in the redirect URL fragment, skipping the code exchange, because old browsers could not make cross-origin calls. That put the token in the browser history, in referrer headers, and in front of any script on the page, with no way to bind it to the client that asked. Now that browsers support CORS and PKCE, the code flow with PKCE replaces it, and OAuth 2.1 removes implicit entirely. The resource owner password credentials flow, where the client collects the user's password and sends it to the authorization server, is also removed, because it teaches users to type passwords into third-party apps and cannot support MFA.

6.5 Token types and handling

Bearer tokens work like cash: whoever holds one can use it. Mitigations: keep lifetimes short, restrict scopes and audience, send only over TLS, and consider sender-constrained tokens (DPoP or mTLS-bound tokens) that are useless without a private key held by the client. Redirect URIs must be matched exactly against a registered list, or an attacker can steer the code to their own site.

7. OpenID Connect, SSO, and SAML

OpenID Connect (OIDC) is a thin identity layer on top of OAuth 2.0. It adds a standard ID token (a JWT) that tells the client who just logged in (sub, iss, aud equal to the client ID, nonce to prevent replay, and auth time), a /userinfo endpoint, standard scopes (openid, profile, email), and discovery at /.well-known/openid-configuration, which points to the JWKS. The rule of thumb: the ID token is for the client (to know the user); the access token is for the API. Do not send an ID token to an API as a credential.

Single sign-on (SSO) means a user authenticates once at an identity provider (IdP) such as Okta, Entra ID, or Google, and then gains access to many applications (service providers) without logging in again. Each application redirects to the IdP, which sees its existing session cookie, and sends the user back with an assertion. Benefits: one place for MFA and policy, one place to disable a leaver (central offboarding), no password per app.

SAML 2.0 is the older, XML-based enterprise standard for the same job. The service provider redirects the browser to the IdP with a SAML request, the user authenticates, and the IdP posts back a digitally signed XML assertion with the user's attributes, which the service provider verifies against the IdP's certificate. It is common in large enterprises and B2B SaaS, so a multi-tenant SaaS usually supports per-tenant SAML or OIDC federation, where each customer connects its own IdP. SAML has had signature-wrapping vulnerabilities, so use a maintained library. Rule of thumb: OIDC for new apps and mobile, SAML for enterprise customers who demand it. Provisioning of users from the IdP is typically handled by SCIM.

8. API keys

An API key is a long random string identifying a calling application or customer, passed in a header. It is not a user login. Keys are popular for developer APIs because they are trivial to use. They are weaker than OAuth because they are long-lived static secrets with no built-in scope, expiry, or proof of possession, and they leak into logs, repos, and screenshots.

Good practice: generate at least 128 bits from a secure random source; show the key once and store only a hash (a fast hash is fine for high-entropy random keys, unlike human passwords); give keys a readable non-secret prefix (sk_live_ab12...) so users and secret scanners can recognize them and the server can find the record by prefix; attach scopes, rate limits, and an owner; support multiple active keys for zero-downtime rotation; support expiry and instant revocation; send only in headers (never in URLs, which get logged); and alert on use from unusual locations. Use API keys to identify and meter clients, but use OAuth tokens when you need user-level authorization.

9. Service-to-service authentication

Inside the system, services call each other thousands of times a second. "It is on the private network" is not authentication. If one service is compromised, an attacker on the same network can call every other service. Service identity must be explicit.

9.1 Mutual TLS (mTLS)

In ordinary TLS only the server proves its identity with a certificate. In mutual TLS the client also presents a certificate, so both ends are authenticated, and the channel is encrypted. Each service gets a short-lived certificate (hours to days) from an internal certificate authority, and the certificate carries the service identity (for example a SPIFFE ID such as spiffe://prod/ns/payments/sa/api). The receiving side can then say: "this call is from the orders service, cryptographically", and authorize accordingly. Operating this by hand is painful (issuing, rotating, reloading certificates), which is why a service mesh sidecar or ambient layer does it transparently. See Chapter 50.

9.2 Workload identity

The question under mTLS is how a workload gets its first credential without a stored secret. Workload identity solves this by having the platform attest who the workload is. A pod proves its identity to the orchestrator (via a projected service-account token or the node's attestation), and an identity system (SPIFFE/SPIRE, or a cloud provider's workload-identity federation) exchanges that for a short-lived certificate or cloud credential. No long-lived password is baked into images or config, and a stolen credential expires quickly. This is the same idea as an instance role in a cloud: the code asks the metadata service for temporary credentials instead of reading an access key from a file.

9.3 Propagating user context: token exchange and signed internal tokens

A request often starts with a user and fans out through several services. If service B simply trusts a user ID header from service A, then any compromised service can claim to be any user (the "confused deputy" problem). Options:

  • Forward the user's token unchanged. Simple, but each downstream service must accept the edge token, and it carries a broad audience.
  • OAuth 2.0 token exchange (RFC 8693): service A presents the user's token to the authorization server and receives a new token for audience B, with narrower scope and possibly an "actor" claim recording that A acts on behalf of the user. B can check both who the user is and which service is calling.
  • Internal signed identity token: the gateway verifies the external token once, then mints a short-lived internal token (signed with an internal key) containing only the verified user, tenant, and scopes. Internal services trust only that, never external ones.

10. Authorization models

Authentication tells you who is calling. Authorization models are the ways to express what that caller may do. Choose the simplest one that fits, and know when it breaks.

10.1 RBAC: role-based access control

Permissions are grouped into roles (admin, editor, viewer), and users are assigned roles. It is simple, easy to audit ("who is an admin?"), and fits most internal tools. It breaks down when you need per-object rules ("editors can edit only their own team's documents") because the number of roles explodes ("role explosion").

10.2 ABAC: attribute-based access control

Decisions use attributes of the subject (department, clearance), the resource (owner, classification, tenant), the action, and the context (time, IP, device posture). A rule might read: allow if user.department == doc.department AND doc.classification <= user.clearance AND request.time within office hours. Very flexible, but rules are harder to reason about and audit, and every attribute must be available at decision time.

10.3 ReBAC and Zanzibar-style systems

Relationship-based access control says access follows from relationships in a graph: "Alice is an editor of folder F; document D is in folder F; editors of a folder are viewers of every document inside it; so Alice can view D." This models sharing, nested groups, and inheritance naturally, which is how Google Drive-style products work. Google's Zanzibar paper describes a global authorization service that stores relation tuples in the form object#relation@user (for example doc:readme#viewer@user:alice, or doc:readme#parent@folder:eng), plus a namespace configuration that defines how relations compose (viewer includes editor, viewer includes the parent's viewers). A check call, "does user U have relation R on object O?", walks the graph. It is designed for very high read volume and low latency, with consistency tokens ("zookies") so a check after a permission change does not use a stale snapshot (the "new enemy" problem: removing someone from a folder and then adding a secret document must not let the removed person see it). Open-source implementations in this style include SpiceDB, OpenFGA, and Ory Keto.

10.4 Policy engines and policy as code

As rules grow, hard-coding if statements across services becomes unmanageable and impossible to audit. A policy engine such as OPA (Open Policy Agent, policies written in Rego), Cedar, or Casbin takes the question "may subject S do action A on resource R in context C?" together with data and returns allow or deny. Policies live in version control, are reviewed and tested like code, and are pushed to a sidecar or library next to each service so decisions take microseconds and do not add a network hop. The pattern is a PDP (policy decision point, the engine) and a PEP (policy enforcement point, the code or proxy that asks and obeys). Keep decisions deterministic and keep failing closed.

10.5 Scopes versus permissions

These are often conflated. A scope is a coarse permission granted to a client by the user at consent time: "this app may read orders". It limits what the token can do. A permission is what the user may do on a particular resource, according to their role or relationships. The effective access is the intersection: the app asked for orders:read and the user is allowed to read order 7 only if both are true. Scopes without object-level checks are the top cause of BOLA bugs: a valid orders:read token is not permission to read every order.

10.6 Multi-tenant authorization

In a multi-tenant SaaS (Chapter 42), the deadliest bug is one tenant seeing another's data. The tenant ID must be a first-class, verified part of every request: it comes from the authenticated token, never from a client-supplied field, and travels in request context to every layer. Enforce it at several levels: every query includes a tenant filter (ideally injected by a data-access layer, not hand-written); the database enforces it too with row-level security policies; caches and queues use tenant-scoped keys; object storage uses per-tenant prefixes with per-tenant policies; and encryption keys can be per tenant. Roles are evaluated within a tenant ("admin of tenant acme" is not admin of tenant globex). Platform staff accessing a tenant should use audited, time-limited "break-glass" access.

11. Where to enforce: gateway versus service

Which component makes the allow or deny decision? The honest answer is "both, for different things". The API gateway is a natural coarse-grained choke point: it terminates TLS, verifies token signatures and expiry, checks audience and scopes, applies rate limits and WAF rules, strips untrusted headers, and rejects obviously unauthenticated traffic before it consumes service capacity. Doing this once, centrally, keeps services simple and gives consistent logging.

But the gateway cannot know whether user 42 owns order 1002. That needs business data, so fine-grained, object-level authorization must happen in the service (or via a call to the policy or relationship service) right where the data is loaded. A system that relies only on the gateway has a "hard shell, soft center": if an attacker reaches a service another way (a compromised pod, a misrouted internal call), nothing stops them. So services must still verify the identity they are handed, ideally by validating a token or mTLS identity themselves rather than trusting plain headers.

12. Encryption in transit

Data crossing any network can be read or altered by someone along the path. TLS (Transport Layer Security) gives three guarantees: confidentiality (eavesdroppers see ciphertext), integrity (tampering is detected), and server authentication (a certificate signed by a trusted authority proves you reached the real domain). The handshake negotiates a version and cipher, authenticates the server, and agrees on session keys using an ephemeral key exchange (ECDHE), which gives forward secrecy: stealing the server's long-term key later does not decrypt recorded traffic. Handshake costs and round trips, TLS 1.3 versus 1.2, and session resumption are covered in Chapter 3; here the system-level choices matter.

  • TLS everywhere, including inside: encrypt browser to edge, edge to services, service to service, and service to database. "Internal traffic is safe" fails the moment an attacker is inside.
  • Minimum TLS 1.2, prefer 1.3; disable old protocol versions and weak ciphers.
  • HSTS (Strict-Transport-Security) tells browsers to use HTTPS only, defeating downgrade attacks.
  • Certificate lifecycle: automate issuance and renewal (ACME / Let's Encrypt or a cloud certificate manager) with short lifetimes, because expired certificates are one of the most common causes of outages. Monitor expiry.
  • Where to terminate: at the CDN, load balancer, or gateway for performance and WAF inspection, then re-encrypt to the origin (do not leave the last hop in plain text). Mobile apps may use certificate pinning for high-risk apps, at the cost of operational pain when certificates rotate.
  • mTLS for service identity (section 9), and VPN or private links for inter-datacenter traffic.

13. Encryption at rest, keys, and KMS

Encryption at rest protects data on disks, snapshots, and backups against stolen media, misplaced backups, and some insider threats. Be precise about what it does and does not do: it does not protect against an attacker who has valid application credentials, because the database transparently decrypts for authorized sessions. Its real value is limiting the blast radius of lost storage and enabling controls over the keys.

13.1 Envelope encryption

Encrypting everything directly with one master key has two problems: the master key would be used constantly (and exposed to many systems), and rotating it would mean re-encrypting all data. Envelope encryption uses two layers. A data encryption key (DEK), generated locally per object, per file, or per tenant, encrypts the data. A key encryption key (KEK) held in a KMS (key management service) encrypts the DEK. You store the wrapped (encrypted) DEK next to the data. To read, you send the wrapped DEK to the KMS, which checks that the caller is permitted, unwraps it, and returns the DEK so you can decrypt locally.

13.2 KMS, HSM, rotation

A KMS is a managed service that stores master keys, performs wrap and unwrap operations, enforces who may use which key, and logs every use. Underneath, keys are protected by an HSM (hardware security module), a tamper-resistant device that performs cryptography without ever exposing the raw key. Cloud KMS products are backed by HSMs; dedicated HSMs or cloud HSM clusters are used when compliance requires single-tenant hardware or customer-controlled key material. Typical rotation practice: rotate KEKs automatically on a schedule (for example yearly), keep old versions for decryption, re-wrap DEKs lazily; rotate DEKs when data is rewritten; and have a documented procedure for emergency rotation after suspected compromise. Cryptographic erasure (deleting a tenant's key to make their data unrecoverable) is a neat way to meet deletion requirements, including in backups (see Chapter 56).

13.3 Client-side encryption and customer-managed keys

With client-side encryption, data is encrypted before it reaches your servers, and the provider never holds the key. It protects against provider compromise and may be a regulatory requirement, but the server can no longer search, index, or deduplicate that data, key loss means permanent data loss, and sharing needs key exchange. End-to-end encrypted messengers do this. A middle path popular with enterprise SaaS is BYOK / customer-managed keys: each tenant's DEKs are wrapped with a KEK in the customer's own KMS account. The customer can revoke access, and your service loses the ability to decrypt, which is a strong selling point but adds a dependency on the customer's key availability on every access (cache unwrapped keys briefly).

14. Secrets management

A secret is any credential: database passwords, API keys, signing keys, certificates. The cardinal rules: never commit secrets to source control, never bake them into images, never print them in logs, and never put them in plain environment variables or config files that are checked in. Instead:

  • Keep them in a dedicated secrets manager (HashiCorp Vault, a cloud secrets manager, or Kubernetes secrets backed by KMS encryption). Access is authenticated with the workload's identity (section 9.2), authorized by policy, and fully audited.
  • Prefer dynamic, short-lived secrets: the manager creates a database user valid for one hour per instance and deletes it afterwards. A leaked credential soon dies, and each instance has an attributable identity.
  • Make rotation routine and automatic. If rotating a secret is scary, it will not happen. Support two valid versions at once during rotation.
  • Scan code, commits, container images, and CI logs for secrets, and block pushes that contain them. Treat any secret that ever touched a repo as compromised and rotate it.
  • Fetch secrets at start-up or on demand and keep them in memory only. Applications should be able to reload them without restart.
  • Limit scope: one secret per service and environment, so a leak in staging cannot touch production.

Config distribution and dynamic reloading, which secrets rely on, are discussed in Chapter 49.

15. Hashing versus encryption versus signing (and MACs)

Interviewers regularly ask you to distinguish these. Keep this table in your head.

PrimitiveReversible?KeysPurposeExamples
HashNo (one way)NoneFingerprint, integrity check, dedup, lookup of random secretsSHA-256, SHA-3, BLAKE3
Password hashNo, deliberately slowSalt (not secret)Store passwordsArgon2id, bcrypt, scrypt
Symmetric encryptionYes, with the keyOne shared secret keyConfidentiality of data at rest or in a sessionAES-256-GCM, ChaCha20-Poly1305
Asymmetric encryption / key exchangeYes, with the private keyPublic + private pairAgree on keys, encrypt small items to a recipientRSA-OAEP, ECDH, X25519
MACNo (it is a tag)Shared secretIntegrity and authenticity between parties who share a keyHMAC-SHA256
Digital signatureNo (it is a tag)Private signs, public verifiesAuthenticity and integrity for anyone with the public key, non-repudiationRSA-PSS, ECDSA, Ed25519

Key points: a hash proves nothing about who created the data, because anyone can compute it; a MAC or signature adds that. Use authenticated encryption (AEAD modes such as GCM) so that data is both secret and tamper-proof, never raw ECB or unauthenticated CBC. A MAC and a signature both ensure integrity and authenticity, but only a signature lets third parties verify without being able to forge, which is why JWTs for many consumers use asymmetric signing. Compare hashes and MACs in constant time to avoid timing leaks. And encoding (Base64, URL encoding) is none of these: it provides no secrecy at all.

16. API security

Most breaches of modern systems happen through the API layer. The OWASP API Security Top 10 is the checklist that interviewers have in mind. The main risks, in plain language:

16.1 The OWASP API risks you should be able to name

  • Broken object level authorization (BOLA): changing an ID in the URL reveals someone else's object. Fix: check ownership or tenancy on every object access; use unguessable IDs as extra defense, never as the only one.
  • Broken authentication: weak tokens, missing expiry, no brute-force protection, credentials in URLs.
  • Broken object property level authorization: returning fields the caller should not see (excessive data exposure) or accepting fields they should not set (mass assignment).
  • Unrestricted resource consumption: no limits on request rate, payload size, page size, or expensive queries.
  • Broken function level authorization: a normal user calls an admin endpoint because only the UI hid it.
  • Unrestricted access to sensitive business flows: automated abuse of legitimate flows, such as buying all tickets or creating thousands of fake accounts.
  • Server-side request forgery (SSRF): see below.
  • Security misconfiguration: verbose errors, permissive CORS, default credentials, unneeded HTTP methods.
  • Improper inventory management: forgotten old API versions and debug endpoints still live.
  • Unsafe consumption of third-party APIs: trusting data from partners without validation.

16.2 Input validation and injection

All input is hostile until proven otherwise. Validate against an allow-list: type, length, range, format, and enumerated values, rejecting anything else, using a schema (JSON Schema, protobuf) at the edge. Validation reduces risk, but it does not replace context-specific handling. SQL injection happens when input is concatenated into a query; the fix is parameterized queries (prepared statements) so data can never become code. The same pattern applies to NoSQL queries, OS commands (avoid shelling out), LDAP, and template engines. Output must be encoded for its context (HTML, JavaScript, URL) to prevent XSS. Deserializing untrusted data into arbitrary objects is a classic path to remote code execution; use plain data formats and strict schemas (Chapter 7).

16.3 SSRF

If your service fetches a URL supplied by a user (webhook, image import, link preview), an attacker can make your server request internal addresses such as the cloud metadata endpoint http://169.254.169.254/, which can return temporary cloud credentials, or internal admin services that trust the internal network. Defenses: allow-list destination hosts where possible; resolve DNS yourself and block private, loopback, and link-local ranges after resolution (and re-check on redirects, to defeat DNS rebinding); disable redirects or re-validate them; run fetchers in an isolated network segment with no access to internal services; require the metadata service v2 session-token mode; and give the workload minimal cloud permissions so a stolen credential is worth little.

16.4 Mass assignment

If you bind the entire JSON body onto a model object, a client can add "role": "admin" or "tenantId": "other" and set fields you never intended. Use explicit request DTOs with only allowed fields, and take server-controlled fields (owner, tenant, role, price) from the authenticated context, never from the body.

16.5 CORS

Browsers enforce the same-origin policy: a page from one origin cannot read responses from another. CORS (cross-origin resource sharing) is a relaxation: your API sends Access-Control-Allow-Origin to say which origins may read its responses. It is a browser protection for your users, not an access control for your API; non-browser clients ignore it. Common mistakes: reflecting any request origin, or combining Allow-Origin: * with credentials (browsers refuse the wildcard with credentials, so people reflect the origin instead, which is dangerous). Use an exact allow-list of origins, and treat preflight (OPTIONS) responses as part of your policy. Related headers worth setting: Content-Security-Policy, X-Content-Type-Options: nosniff, Referrer-Policy, and Cache-Control: no-store on sensitive responses.

16.6 Rate limiting and resource limits as security

Rate limiting (Chapter 16) is not only for fairness; it stops credential stuffing, scraping, enumeration, and cheap denial of service. Layer it: per IP at the edge, per user or API key and per tenant at the gateway, and tight special limits on expensive or sensitive endpoints (login, password reset, OTP verification, search). Also cap request body size, JSON nesting depth, page size, query complexity (especially GraphQL depth and cost), upload size, and timeouts. Return 429 with Retry-After.

17. DDoS, WAF, and bot management

Availability is a security property. Attacks come at several layers, and defenses must match.

LayerAttack exampleDefense
L3/L4 volumetric (network, transport)UDP and SYN floods, reflection and amplification (DNS, NTP), saturating bandwidthAnycast absorption across many PoPs, provider scrubbing centers, SYN cookies, upstream filtering. You cannot out-bandwidth this alone
L7 (application)HTTP floods of expensive requests, slow-read attacks (Slowloris), cache-busting query strings, expensive search or login callsWAF rules, rate limits, caching, challenge pages, request timeouts, autoscaling with caps
Application logic abuseCredential stuffing, scraping, inventory hoarding, fake sign-upsBot management, behavioral analysis, device fingerprints, CAPTCHA, per-account limits

A WAF (web application firewall) inspects HTTP requests against rules that detect SQL injection patterns, XSS payloads, known exploit signatures, and protocol anomalies. It can run in detect-only mode first, to measure false positives before blocking. It is a useful safety net and a way to ship a "virtual patch" while a real fix is built, but it is never a substitute for secure code, since attackers can often craft bypasses. Bot management distinguishes humans, good bots (search crawlers), and bad bots using IP and ASN reputation, TLS and HTTP fingerprints, JavaScript or device challenges, and behavior over time. Key operational points: put the CDN in front (Chapter 12) so most traffic never reaches you; hide origin addresses and accept traffic only from the CDN so attackers cannot bypass it; cache aggressively; degrade gracefully (shed low-priority traffic, serve stale); cap autoscaling to avoid an enormous bill during an attack (a "denial of wallet"); and have a runbook and a provider contact for emergencies.

18. Network security, zero trust, and defense in depth

The classic model was a hard perimeter, a "castle and moat", with a soft interior. Once an attacker was inside, they could roam. Modern designs assume the interior is hostile too.

  • VPC and subnets: a virtual private network in the cloud. Put only load balancers and gateways in public subnets; keep application servers and databases in private subnets with no public IPs, reachable only through defined paths. Outbound internet access goes through a NAT or egress proxy that can be filtered, which also limits data exfiltration and SSRF damage.
  • Security groups and network ACLs: security groups are stateful per-instance firewalls with allow rules ("the database accepts port 5432 only from the app tier's group"). Network ACLs are stateless subnet-level rules, a coarser extra layer. Default to deny and open the minimum.
  • Private endpoints: reach managed services (object storage, databases, KMS) over private addresses inside your network instead of the public internet, and use endpoint policies to restrict which buckets or accounts are reachable.
  • Segmentation: separate environments (prod, staging) and sensitive workloads (payments) into separate accounts or networks, with strict, audited links between them. In Kubernetes, use network policies so pods talk only to allowed peers.
  • Zero trust: "never trust, always verify". Network location grants nothing. Every request is authenticated and authorized with a strong identity (user plus device health, or workload identity), access is least-privilege and context-aware, and everything is logged. In practice: mTLS between services, identity-aware proxies in front of admin tools instead of a flat VPN, and short-lived credentials.
  • Admin access: no direct SSH from the internet; use bastions or session managers with MFA and recorded sessions, just-in-time elevation, and break-glass procedures.

19. Audit logging and tamper evidence

An audit log is a record of security-relevant actions: who did what, to which resource, when, from where, and with what outcome. It answers the "R" in STRIDE (repudiation) and is essential for incident response, forensic work, and compliance (SOC 2, ISO 27001, HIPAA, PCI). It differs from application debug logging: it is structured, complete for defined event types, retained for a long period, and access-controlled.

What to log: authentication events (success, failure, MFA, password reset), authorization denials, privilege and role changes, access to sensitive data (reads included, for high-value records), administrative actions, configuration and key changes, data exports, and cross-tenant or support access. Each event includes a timestamp (synchronized clocks), actor (user, service, and on whose behalf), action, resource, tenant, source IP and device, result, and a request or trace ID to correlate across services. Never log secrets, tokens, full card numbers, or unnecessary personal data; mask or hash them.

Tamper evidence means that if someone alters or deletes entries, you can tell. A determined attacker who gets into a system will try to erase their trail. Approaches: ship logs immediately to a separate, write-only account or system that the application cannot modify; store them in append-only or write-once (WORM, such as object lock) storage; and hash-chain the records, where each entry includes the hash of the previous one, so changing or removing any entry breaks every later hash. Periodically anchor the latest chain hash (sign it with a KMS key or publish it to an independent place), and a Merkle tree variant allows efficient proof that a particular entry exists unchanged (the same structure used in certificate transparency, see Chapter 33). Pair this with alerting on suspicious patterns (impossible travel, mass exports, many denials) so the log is actively watched, not just archived.

20. Secure file upload and download

User-supplied files are a rich attack surface: malware, oversized files, HTML or SVG containing script, path traversal in filenames, and access to other users' files. The scalable and safer pattern is to keep file bytes away from your application servers and use pre-signed URLs with object storage (Chapter 21).

Upload. The client asks your API for permission to upload. Your API authenticates and authorizes the user, picks an object key (server-generated, including the tenant ID and a random ID, never the user's filename), and returns a short-lived pre-signed URL (or a presigned POST policy) that embeds constraints: exact key, content type, maximum size, and expiry of a few minutes. The client uploads directly to storage. A signed URL works because the URL contains a signature computed with the server's storage credentials over the method, path, expiry and conditions, so storage can verify it without calling your API. After upload, an event triggers asynchronous processing: scan for malware, verify the real file type by content (not extension or client-declared MIME type), strip metadata, re-encode images, then move the object from a quarantine bucket to the serving bucket and mark it available. Files remain unusable until scanning passes.

Download. Your API authorizes the user for that specific file, then issues a short-lived signed URL (or a signed CDN cookie or URL for many assets), so the access check happens once and bandwidth flows directly from storage or the CDN. Serve user content from a separate, cookie-less domain so that any script inside an uploaded file cannot read your application's cookies, send Content-Disposition: attachment for untrusted types, and set X-Content-Type-Options: nosniff. Keep the bucket private with block-public-access on; a public bucket is one of the most common data leaks.

Watch out A pre-signed URL is a bearer credential: anyone who gets the link can use it until it expires. Keep expiry short, avoid logging full URLs (the signature is in the query string), bind to a content type and size for uploads, and never sign a URL for a key chosen directly by the client without checking it is within the caller's tenant prefix.

21. Supply chain and dependency security

Modern software is mostly other people's code. A single compromised library, build tool, or container base image can compromise every system using it (the "supply chain" attack). Notable patterns: malicious packages with names close to popular ones (typosquatting), dependency confusion (a public package with the same name as your internal one), a maintainer account takeover, a compromised build or CI pipeline injecting code, and vulnerable transitive dependencies. Controls:

  • Know what you run: generate and store an SBOM (software bill of materials) for each release so you can answer "are we affected?" within minutes when a new vulnerability appears.
  • Scan continuously: software composition analysis for known vulnerabilities in dependencies and images, static analysis (SAST) of your code, and secret scanning. Triage by exploitability and exposure, and set time-to-fix targets.
  • Pin and verify: lock files with exact versions and hashes; use an internal proxy registry with an allow-list; configure scoped registries to defeat dependency confusion; review new dependencies and prefer small, well-maintained ones.
  • Protect the pipeline: CI runners with least privilege, short-lived credentials via workload identity instead of stored secrets, required code review and signed commits, isolated and reproducible builds, and no long-lived deploy keys.
  • Sign and attest: sign artifacts and container images (for example with Sigstore) and have the deployment platform admit only images signed by your pipeline. Frameworks such as SLSA describe levels of build integrity.
  • Minimal images: small base images, non-root users, read-only file systems, dropped capabilities. Less code means fewer vulnerabilities.
  • Patch routinely and quickly for critical items. Operating practices such as this tie into Chapter 53.

22. Data classification and least privilege in practice

Not all data is equal, and protecting everything at maximum level is expensive and slows teams. Data classification sorts data into tiers and attaches rules to each tier. A typical scheme:

TierExamplesTypical rules
PublicMarketing pages, public docsIntegrity controls; no confidentiality needed
InternalInternal wikis, non-sensitive metricsEmployees only, standard encryption
ConfidentialCustomer content, business records, personal dataEncryption at rest and in transit, role-based access, audit logging, retention limits
RestrictedPasswords, payment data, health records, encryption keys, government IDsDedicated segregated stores, per-tenant keys, tokenization, very few people with access, full audit, strict retention, masked in logs and non-production

Practical consequences: tag data at the schema level (a column is marked as personal data) so tooling can find it, mask or tokenize it in logs, analytics and test environments, keep restricted data in separate databases with narrower access, and apply data minimization and retention limits, since the safest data is data you do not hold. Regulatory duties (GDPR deletion and access requests, residency) are covered in Chapter 56.

Least privilege is applied through concrete habits: separate IAM roles per service with only the actions and resources needed (no wildcard resources), separate read and write database users, short-lived credentials, time-bound just-in-time elevation for humans, regular access reviews that remove stale permissions, and automated detection of unused permissions. Also separate duties for dangerous actions: requiring two people (or an approval) to change production keys or delete a tenant.

23. Incident response

You will eventually have an incident. Mature teams plan before it happens. The standard phases:

  1. Prepare: inventory assets, centralize logs, define on-call roles, prepare runbooks, and rehearse with game days. Make sure you can rotate every credential and key quickly and that backups are isolated and tested.
  2. Detect and triage: alerts from logs, anomaly detection, a WAF, user reports, or a vulnerability disclosure program. Decide severity and assemble a response team with a clear incident commander.
  3. Contain: stop the bleeding without destroying evidence: revoke tokens and sessions, rotate exposed keys, isolate affected hosts or accounts from the network, block attacker IPs, disable a vulnerable feature behind a flag.
  4. Eradicate and recover: remove the foothold, patch the root cause, rebuild from known-good images rather than cleaning compromised machines, restore data from clean backups, and monitor closely after returning to service.
  5. Communicate: internal stakeholders, affected customers, and regulators within legal deadlines (for example GDPR requires notifying the authority within 72 hours of becoming aware of a personal-data breach). Be factual and timely.
  6. Learn: a blameless post-incident review, with root cause, timeline, and tracked follow-up actions. Add detection and tests so the same failure cannot recur silently.

Design choices that make response easier: centralized, tamper-evident audit logs; short-lived credentials (so revocation is mostly "wait or rotate one thing"); per-tenant keys (so the blast radius is one tenant); feature flags and kill switches; and immutable infrastructure that can be rebuilt on demand.

24. Worked example: securing a multi-tenant SaaS API end to end

Problem: you run a B2B project-management SaaS. Customers (tenants) have users who read and write projects and tasks through a web app, a mobile app, and a public REST API. Enterprise tenants want SSO with their own IdP. You store attachments. Scale: 5,000 tenants, 2 million users, about 20,000 requests per second at peak. Assets: tenant business data (confidential), credentials (restricted), keys (restricted), availability. Main attackers: anonymous internet users, a malicious user within one tenant trying to read another tenant, credential stuffers, and a compromised internal service.

24.1 Walk-through, in the order a request travels

  1. Edge. DNS points to the CDN. The CDN absorbs volumetric floods and terminates TLS 1.3 with HSTS. A WAF runs managed rules and bot management challenges suspicious clients, especially on /login. The origin accepts connections only from the CDN. Static assets are cached; API responses with private data use Cache-Control: private, no-store.
  2. Authentication. Users log in with passwords (Argon2id, per-user salt, a pepper held in the KMS, breached-password check) plus MFA, passkeys encouraged. Enterprise tenants use SSO: OIDC or SAML to their IdP, with SCIM provisioning so leavers are disabled automatically. The web app uses authorization code with PKCE; the access token is a 10-minute JWT signed with ES256 whose key set is published at JWKS and rotated every 90 days. Refresh tokens rotate on use and live in an HttpOnly, Secure, SameSite=Lax cookie with CSRF protection on the refresh endpoint. Machine integrations use client credentials with scoped, per-tenant clients, and API keys (hashed at rest, prefixed) for simple read-only integrations.
  3. Gateway. It checks signature, algorithm allow-list, iss, aud, exp, and scopes; consults a small deny list for revoked users; applies rate limits at three levels (per IP, per user, per tenant plan, see Chapter 16); strips any client-supplied identity headers; enforces body size and schema validation; and mints a short-lived internal token carrying tenant_id, user_id, and scopes. At 20,000 requests per second, local JWT verification is a few tens of microseconds each and needs no network call, which is why stateless tokens suit this tier.
  4. Service authentication. Services hold short-lived certificates from the workload identity CA; the mesh gives mTLS between all pods, and network policies allow only the necessary paths (Chapter 50). A service accepts calls only from callers whose identity is on its allow-list, and trusts only the internal token for user context.
  5. Authorization in the service. The tenant ID comes from the verified token, never the URL or body. Every query goes through a data-access layer that adds tenant_id = :tenant. For "can this user edit task T?", the service calls the authz service (ReBAC: user is a member of the project, project belongs to the tenant, role grants edit), with decisions cached for a few seconds. Unknown or error results deny. Requests are bound to explicit DTOs, preventing mass assignment of fields such as tenant_id or role.
  6. Data layer. The database sets the tenant in the session and uses row-level security policies as a second wall: even a buggy query missing a tenant filter returns nothing from other tenants. Data is encrypted at rest with envelope encryption: a DEK per tenant, wrapped by a KMS key; large enterprise tenants may bring their own key. Searches and caches use tenant-prefixed keys. Backups are encrypted and stored in a separate account with deletion protection.
  7. Files. Upload and download use pre-signed URLs scoped to tenant/uuid keys, with quarantine scanning, a separate cookie-less domain for serving, and signed CDN URLs for downloads.
  8. Outbound calls. Webhooks and URL imports go through an isolated egress proxy that blocks private and metadata addresses (SSRF), with timeouts and size caps.
  9. Secrets and supply chain. Database credentials are dynamic, one-hour credentials issued by the secrets manager through workload identity. CI builds produce signed images with SBOMs; the cluster admits only signed images; dependency scanning gates merges.
  10. Audit and detection. All security events (logins, role changes, exports, support access, key use, authorization denials) stream with tenant and trace IDs into a hash-chained, write-once store in a separate account, and into a SIEM with alerts for credential-stuffing patterns, impossible travel, mass exports, and spikes in 403s. Tenants can view their own audit trail.
  11. Operations. Support staff access tenant data only through time-limited, approved, fully logged break-glass sessions. Runbooks cover token and key revocation per tenant, and the system can disable a single tenant's access without affecting others, which is the benefit of cell-based isolation (Chapter 42).

25. Interview Q&A

What is the difference between authentication and authorization, and where do you do each in a microservice system?

Authentication establishes who the caller is; authorization decides what that caller may do on a specific resource. In a microservice system I authenticate once at the edge or gateway, verifying a token or session and producing a trusted identity that is passed along as a short-lived internal token. Authorization is enforced at two depths: coarse checks such as scope and audience at the gateway, and fine-grained object-level checks inside the service that owns the data, because only that service knows whether this user may see this record. Failing to do the second is the classic broken object level authorization bug.

How should you store passwords, and why not SHA-256?

Store a salted hash made with a slow, memory-hard password hashing algorithm such as Argon2id (or bcrypt, scrypt) with a cost tuned to roughly a few hundred milliseconds. SHA-256 is designed to be fast, so attackers with GPUs can test billions of guesses per second against a stolen table, while a per-user random salt stops rainbow tables and hides duplicate passwords. I would also add a pepper in a KMS, rate-limit and monitor login, check passwords against breach lists, and require MFA, because the hash only protects the data at rest and not the online guessing path.

JWTs cannot be revoked. How do you deal with that?

A self-contained JWT is valid until it expires, so the main control is to keep access tokens short, such as five to fifteen minutes, and use refresh tokens that are stored server-side and can be revoked, with rotation and reuse detection to catch theft. For urgent cases, such as a fired employee, keep a small deny list of revoked token IDs or a "valid after" timestamp per user, checked at the gateway, whose entries expire when the tokens would. For the most sensitive operations, use opaque tokens with introspection or a fresh authorization check. The tradeoff is always between statelessness and immediacy of revocation.

Walk me through the OAuth 2.0 authorization code flow with PKCE and why it exists.

The client creates a random verifier and sends its hash as a challenge when redirecting the user to the authorization server. The user authenticates and consents, and the server redirects back with a one-time code, which the client exchanges at the token endpoint along with the original verifier; the server checks the hash and returns tokens. The browser only ever carries the code, never the token, and PKCE ensures a stolen code is useless because an attacker lacks the verifier. It replaced the implicit flow, which put tokens in the URL and could not bind them to the requesting client.

What is the difference between OAuth 2.0 and OpenID Connect?

OAuth 2.0 is a framework for delegated authorization: it issues access tokens that let a client call an API on a user's behalf, without telling the client who the user is in any standard way. OpenID Connect adds an authentication layer on top: an ID token (a signed JWT with subject, issuer, audience, and nonce), a userinfo endpoint, standard scopes, and discovery metadata. So you use OIDC to sign users in and OAuth access tokens to call APIs, and you should never use an ID token as an API credential.

How do services authenticate to each other, and how do you carry the end user's identity?

Services use mutual TLS with short-lived certificates issued from a workload identity system, so each side cryptographically knows the other's service identity and no static password exists. A service mesh typically automates it. For user context, I would not trust a plain user ID header; instead the gateway mints a short-lived internal token, or a service performs OAuth token exchange to obtain a token narrowed to the downstream audience, so a compromised service cannot impersonate any user anywhere. Authorization at each service then considers both the calling service and the user.

When would you choose RBAC, ABAC, or a Zanzibar-style ReBAC system?

RBAC fits systems with a small set of stable roles and is the easiest to audit, but it explodes when rules depend on individual objects. ABAC supports rules over attributes and context such as department, classification, or time, at the price of harder reasoning and attribute plumbing. ReBAC is ideal when access flows from sharing and hierarchy, as in documents, folders, teams, and organizations, because permissions are edges in a graph that is checked quickly with consistency tokens. Many real systems use RBAC for administrative roles and ReBAC or a policy engine for per-object decisions.

How do you prevent one tenant from accessing another tenant's data?

I treat the tenant ID as part of the verified identity, taken from the token and never from request parameters, and propagate it in context to every layer. The application adds the tenant filter through a shared data-access layer, the database enforces row-level security as a second barrier, caches, queues, and storage use tenant-scoped keys and prefixes, and encryption keys can be per tenant. I add automated cross-tenant tests, audit logging of access, and break-glass controls for staff, and I use cell-based deployment to limit the blast radius if something still goes wrong.

Explain envelope encryption and why it is used.

Data is encrypted locally with a data encryption key, and that key is itself encrypted ("wrapped") by a key encryption key that never leaves the KMS or HSM. The wrapped key is stored next to the ciphertext, and to decrypt you ask the KMS to unwrap it, which both enforces access policy and creates an audit entry. This avoids sending bulk data to the KMS, limits exposure of the master key, allows per-object or per-tenant keys, and makes rotation cheap because you only re-wrap small keys rather than re-encrypt all the data.

What is SSRF and how would you defend against it?

Server-side request forgery is when an attacker makes your server send requests to a destination of their choice, typically via a feature that fetches user-provided URLs. The danger is reaching internal-only services or the cloud metadata endpoint that returns temporary credentials. Defenses include allow-listing destinations, resolving DNS yourself and blocking private, loopback, and link-local ranges after resolution and on every redirect, running fetchers in an isolated network segment through an egress proxy, using the more protected metadata mode, and giving the workload minimal permissions so a stolen credential has little value.

How do you design secure file uploads for a high-volume service?

Keep file bytes off the application servers: authorize the user, generate a server-controlled object key, and return a short-lived pre-signed URL constrained by size and content type so the client uploads directly to a private quarantine bucket. An event triggers scanning, real type detection, and metadata stripping, and only clean files are moved to the serving location. Downloads are authorized when a signed URL is minted and served from a separate cookie-less domain with a forced attachment disposition and nosniff headers, which prevents uploaded content from running as script in your origin.

How would you protect a public API from DDoS and credential stuffing?

I would layer defenses: a CDN with anycast absorbs volumetric attacks and caches content, with the origin hidden and reachable only from the CDN. A WAF and bot management handle application-layer floods and automated clients, the gateway applies per-IP, per-user, and per-tenant rate limits with tighter limits on login and reset endpoints, and the app uses MFA and breached-password checks to blunt stuffing. I would also cap autoscaling to avoid runaway cost, shed low-priority traffic under load, and keep a runbook and provider escalation path.

26. Recap

  • Threat model first: assets, attackers, trust boundaries, then STRIDE per component. State what you do not defend against.
  • Authenticate once, authorize every time, and enforce object-level checks next to the data. Fail closed.
  • Passwords: Argon2id or bcrypt with per-user salt, rate limiting, breach checks, MFA or passkeys. Sessions in HttpOnly, Secure, SameSite cookies, with CSRF defenses.
  • JWT: signed, not encrypted. Validate algorithm, signature, iss, aud, exp. Use short lifetimes, rotating refresh tokens, a JWKS for key rotation, and a small deny list for emergencies.
  • OAuth: authorization code with PKCE for users, client credentials for machines, device code for limited devices; implicit and password flows are retired. OIDC adds identity; SAML serves enterprises.
  • Between services use mTLS with workload identity, and token exchange or an internal token for user context.
  • Choose RBAC, ABAC, ReBAC, or a policy engine by need. Scopes limit clients, permissions limit users, and both must pass. Tenant ID comes from the token and is enforced at every layer, including the database.
  • TLS everywhere; envelope encryption with a KMS or HSM at rest; automated secret rotation; know hashing versus encryption versus MAC versus signature.
  • API hygiene: validate input, parameterize queries, block SSRF, avoid mass assignment, lock down CORS, and limit every resource.
  • Layer DDoS, WAF, and bot defenses behind a CDN; segment networks, adopt zero trust, keep audit logs tamper-evident, scan uploads, secure the supply chain, classify data, and rehearse incident response.
