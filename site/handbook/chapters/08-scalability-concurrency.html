Scalability and Concurrency

Scaling a service means keeping it fast and correct as the load grows. This chapter explains what to measure, why adding machines does not give perfect speed-up, how to design the application tier so that machines are interchangeable, how threads, event loops and pools really behave under load, and which concurrency bugs appear the moment two requests touch the same data.

1. What scalability actually means

People say "this design does not scale" without saying what they mean. A precise definition makes every later discussion easier. A system is scalable if, when the load grows, you can keep its quality of service (latency and availability) acceptable by adding resources, and the cost of doing so grows in a reasonable way, ideally roughly in proportion to the load. A system that needs ten times the money to handle ten times the load is fine. A system that needs a complete rewrite at twice the load is not.

1.1 Load parameters

Before you can talk about growth you must say what is growing. The numbers that describe load are called load parameters, and they depend on the system. For a web service the main one is requests per second. For a chat system it may be the number of open connections and messages per second. For a database it may be the ratio of reads to writes, or the number of rows. For a social feed it is the number of followers per user, which decides how much work one post creates (this "fan-out" is the textbook example of a load parameter that dominates the design). Picking the wrong parameter leads to sizing the wrong thing. If your real problem is that a few celebrity accounts have millions of followers, adding web servers will not help.

1.2 Throughput and latency

Two measures describe how a service performs under a given load.

  • Throughput is how much work completes per unit of time: requests per second, messages per second, megabytes per second.
  • Latency is how long one piece of work takes from the moment it arrives until the answer is complete. Strictly, response time includes waiting in queues, while service time is only the time spent being processed. Under load the waiting part grows and dominates.

Latency must be described with percentiles, not the average. The p50 (median) says what a typical request sees. The p99 says that one request in a hundred is slower than this value. A user who loads a page that makes 30 backend calls has roughly a 1 in 4 chance of hitting the p99 of at least one of them (more with more calls), so tail latency decides the experience. Chapter 2 covers estimation of the numbers themselves; Chapter 54 covers how targets are written as SLOs.

1.3 The shape of the curve

Throughput and latency are linked, and the link is not linear. At low load each request is served immediately, so latency is flat at the service time. As utilization of the bottleneck resource approaches 100 percent, requests start to arrive while others are still being processed, so they wait in a queue. Queueing theory shows that waiting time grows steeply: for a simple single-server queue the average time in the system is proportional to 1 / (1 - utilization). At 50 percent utilization the factor is 2, at 90 percent it is 10, at 99 percent it is 100. Throughput meanwhile flattens at the maximum the resource can do, and if load keeps rising the system can even get worse (more work in progress, more memory, more context switching), which is called congestion collapse.

Key idea You never run a service at 100 percent of capacity, because the latency cost of the last 20 percent is enormous. "Capacity" in interviews should mean the load at which p99 latency still meets the target, not the load at which the machine melts. This is the origin of headroom (section 14).

1.4 Dimensions of scaling

Load can grow in different ways: more users, more data per user, more requests per user, or heavier requests. Each stresses a different resource. More users mostly stress the app tier and connection counts. More data stresses storage, indexes and memory for caching. Heavier requests stress CPU. When asked "how would you scale this", first ask which of these is growing, because the cure differs.

2. Vertical versus horizontal scaling, and the limits

2.1 Two directions

Vertical scaling (scale up) means moving to a bigger machine: more cores, more memory, faster disks. It is the simplest thing that can possibly work, because the software does not change. There is no distribution, no network between components, no data placement problem, and transactions on one database stay trivially consistent. Its limits are that the biggest machine has a ceiling, price rises faster than capacity near the top of the range, and one machine is one failure domain: if it dies, everything dies, and replacing it usually means downtime.

Horizontal scaling (scale out) means adding more machines and spreading the work over them. In principle the ceiling is much higher, machines are cheap commodity units, and losing one machine loses only a fraction of capacity. The price is complexity: you need a way to split the work (a load balancer, Chapter 9, or partitioning of data, Chapter 25), the machines must be able to cooperate, and every network hop adds latency and a new way to fail.

A sound default in interviews: scale the stateless tiers horizontally, scale the stateful tier vertically as far as is sensible (it is the hard one to distribute), and only then partition the data. Do not jump to sharding when a bigger instance and a read replica would carry you for another two years.

2.2 Why ten machines are not ten times faster: Amdahl's law

Adding machines only speeds up the part of the work that can be done in parallel. If a fraction s of the work is inherently serial (it must happen one after another, for example a single lock, a single leader, a single database writer), then no matter how many machines N you add, the speed-up is limited. Amdahl's law says:

speedup(N) = 1 / ( s + (1 - s) / N )

Take s = 0.05, so 5 percent of the work is serial. With N = 10 the speed-up is 1 / (0.05 + 0.095) = 6.9. With N = 100 it is 1 / (0.05 + 0.0095) = 16.8. With N = infinity it is 1 / 0.05 = 20. A mere 5 percent serial section caps you at 20 times, however many servers you buy. The practical lesson is to find and shrink the serial part (a global lock, a single-row counter, a sequential ID generator, a single-threaded step) rather than to keep adding hardware.

2.3 It gets worse: the Universal Scalability Law

Amdahl is optimistic, because it says adding machines never hurts. Real systems have a second cost: the workers must talk to each other. Neil Gunther's Universal Scalability Law (USL) adds a term for this. The relative capacity with N workers is:

C(N) = N / ( 1 + a (N - 1) + b N (N - 1) )

The two coefficients mean different things:

  • a (contention) is the cost of waiting for a shared resource that only one worker can use at a time: a lock, a queue head, a single database row. This is the same effect as Amdahl's serial fraction. It bends the curve toward a flat ceiling.
  • b (coherency, or crosstalk) is the cost of keeping the workers' views consistent with each other: cache invalidation messages, replication of shared state, distributed locks, all-to-all gossip. Because every worker may have to talk to every other, this cost grows with N squared. It bends the curve downward, so that past some N adding workers makes throughput fall.

Example with a = 0.03 and b = 0.0005. At N = 8 the denominator is 1 + 0.03 × 7 + 0.0005 × 56 = 1.238, so capacity is 8 / 1.238 = 6.5. At N = 32 it is 1 + 0.93 + 0.0005 × 992 = 2.426, giving 13.2. At N = 64 it is 1 + 1.89 + 2.016 = 4.906, giving 13.0. At N = 128 it is 1 + 3.81 + 8.13 = 12.94, giving 9.9. The peak is near N = sqrt((1 - a) / b) = sqrt(1940) which is about 44. More machines past that point make the cluster slower.

Interview tip You do not need to recite formulas, but naming the two enemies earns credit: contention (waiting for something shared) and coherency (keeping copies in agreement). Then say how your design reduces them: partition the shared thing, avoid shared state, or relax consistency.

3. Stateless service design and where state goes

The easiest tier to scale horizontally is one whose servers are interchangeable. A server is stateless when it does not keep anything between requests that the next request would depend on. Any request can then go to any server, so a load balancer can use simple round robin or least-connections, you can add or remove servers at will, and a crashed server loses nothing (the next request just goes elsewhere). Most of horizontal scaling in practice is the work of making the app tier stateless and pushing state to a place that is designed to hold it.

"Stateless" does not mean the system has no state. It means the app servers do not own the only copy. Durable state belongs in databases, object storage, or queues, and short-lived shared state belongs in an in-memory store such as Redis (Chapter 15). Local memory is still fine for things that are rebuildable and safe if different servers disagree briefly, such as a local cache of configuration or a compiled template.

3.1 What counts as hidden state

  • Login sessions kept in server memory, the classic case.
  • Uploaded files written to a local disk, so a later request on another server cannot find them. Use object storage (Chapter 21).
  • In-process caches that hold the only copy of a computed result, or whose staleness causes visible disagreement between servers.
  • Scheduled jobs inside every instance, so that with 10 instances the nightly job runs 10 times. Use a single scheduler or a lock (Chapter 30).
  • WebSocket connections and in-memory subscriptions: connections are inherently attached to one server, so message delivery needs a shared fan-out layer (Chapter 6).
  • Local counters such as a rate limiter that counts per instance and therefore allows N times the intended rate (Chapter 16).

3.2 Sessions: three ways to handle them

A session is the server-side memory that says "this browser is logged in as user 42, with this cart". There are three standard designs.

Sticky sessions (session affinity)

The load balancer remembers which server handled the first request of a user, usually by a cookie or by hashing the client address, and sends all later requests to the same one. The application can keep the session in local memory unchanged. It is the cheapest fix for a legacy application, but it has real costs: when that server dies or is replaced during a deploy, its users lose their sessions and are logged out; load becomes uneven because heavy users stay glued to one server; and autoscaling down is awkward because you must drain servers that still hold live sessions.

Shared session store

The app server keeps only a session ID in a cookie. The data lives in a fast shared store, typically Redis or Memcached, keyed by that ID. Every server can serve every user. Costs: one extra network round trip (usually under a millisecond within a data center), and the store becomes a critical dependency that must be replicated and sized. Benefits: a server crash loses nothing, logout and permission changes take effect at once, and you can inspect or expire sessions centrally.

Signed tokens (for example JWT)

The server puts the identity and a few claims into a token, signs it with a secret or private key, and gives it to the client, which sends it back each time. Any server holding the verification key can validate it without a lookup, so no shared store is needed on the hot path. The trade-offs: a signed token cannot be recalled before it expires unless you add a deny list (which reintroduces a lookup), so keep lifetimes short (minutes) and combine them with a longer-lived refresh credential; the token travels on every request, so keep it small; and it must never hold data the user should not read, because the payload is signed, not encrypted, unless you use an encrypted variant. Authentication details are in Chapter 55.

Watch out Making servers stateless moves the state, it does not delete it. The shared store, the database and the object store are now where scaling pressure lands. Stateless app tiers are easy to scale precisely because you handed the hard problem to systems built for it, so be ready to say how those scale (replication, sharding, cluster mode).

4. Scaling reads versus scaling writes

Most systems read far more than they write (ratios of 10 to 1 up to 1000 to 1 are common), and reads and writes scale by different techniques. Treat them separately.

4.1 Scaling reads

Reads can be copied because they do not change anything. The ladder of techniques, roughly in order of how cheap they are:

  1. Avoid the work: HTTP caching in the browser and a CDN (Chapter 12) so many requests never reach you.
  2. Cache in front of the database with an in-memory cache (Chapter 13, Chapter 15). A cache that serves 95 percent of reads cuts database read load by 20 times.
  3. Read replicas: copies of the database that receive changes from the primary (Chapter 24) and serve reads. They add read capacity linearly but data may be slightly stale (replication lag), so a user who just wrote may not see the write if the next read hits a replica. The usual fix is to read your own writes from the primary for a short time.
  4. Precompute expensive answers (materialized views, denormalized tables, search indexes) so a read is a simple lookup.
  5. Partition the data (Chapter 25) when a single dataset no longer fits one machine's memory or disk.

4.2 Scaling writes

Writes are harder, because every write must reach the authoritative copy and copies cannot simply be multiplied: adding replicas does not add write capacity (each replica must apply every write too). The tools:

  • Make each write cheaper: fewer indexes, narrower rows, batching many small writes into one transaction, using an append-only log structure (Chapter 19).
  • Buffer and smooth with a queue (Chapter 34): accept the request quickly, write it to a durable log, and let workers apply it at a steady rate. This converts spikes into a steady stream, at the price of eventual visibility.
  • Partition by key (sharding) so that different keys are written on different machines. This is the only approach that scales write throughput without limit, and its difficulty is the choice of key, rebalancing, and cross-shard operations.
  • Reduce what must be written: aggregate counters in memory and flush periodically, sample, or drop writes that carry no lasting value.
  • Relax consistency where the business allows, so that writes can be accepted in several places (Chapter 28).
Key idea Reads scale by copying (caches, replicas, CDNs). Writes scale by splitting (sharding) or by smoothing (queues, batching). Ask early what the read to write ratio is, because it tells you which half of this section you need.

5. Bottleneck analysis: a method

The throughput of a pipeline is the throughput of its slowest stage. Improving any other stage changes nothing. So scaling is a loop: find the current bottleneck, relieve it, and measure again, because the bottleneck then moves somewhere else. In an interview you do the same thing on paper.

5.1 The method

  1. Draw the request path: client, edge, load balancer, app server, cache, database, downstream services.
  2. Estimate the load at each stage in the unit that stage cares about: requests per second at the load balancer, concurrent threads at the app server, queries per second and rows touched at the database, bytes per second on the network. Chapter 2 gives the arithmetic.
  3. Compare each against its capacity and compute utilization. The stage with the highest utilization is the candidate bottleneck.
  4. Classify the resource: CPU, memory, disk I/O, network bandwidth, connections, locks, or a downstream dependency. Different resources need different cures.
  5. Relieve it by the cheapest effective means: remove the work (cache), make it cheaper (index, batch), add capacity (replicate, scale out), or split the data.
  6. Repeat until the target load is met with headroom.

5.2 Signals that tell you which resource is saturated

A useful framing is the USE method: for every resource check Utilization (how busy), Saturation (is work queued waiting for it), and Errors. Saturation is the most informative of the three because a resource at 100 percent utilization with no queue is fine, while one at 70 percent with a growing queue is already a problem.

6. Concurrency models of a server

A server must handle many requests at once. How it organizes that decides how many concurrent requests it can hold, how much memory they cost, and what kind of bugs you will meet. There are four main models.

6.1 Thread per request

The server assigns each incoming request to an operating-system thread, which runs the request from start to finish. Code is written in a plain sequential style: call the database, wait for the answer, continue. This is how classic Java servlet containers, Apache prefork and many Python and Ruby servers work. It is easy to write and to debug, and a blocked thread does not stop others. The costs: each thread has its own stack (commonly 512 KB to 1 MB reserved, though only the used part is committed), the kernel must schedule thousands of them and switch between them (a context switch costs microseconds and pollutes CPU caches), and a thread that waits on I/O sits idle yet occupies memory. A few thousand threads per machine is a practical upper range, which caps concurrent requests at roughly that figure.

6.2 Event loop

One thread (or a small number, one per core) runs a loop. It asks the operating system "which of my many connections are ready?", then runs short handlers for the ones that are, and never blocks. When a handler needs to wait, such as for a database reply, it registers a callback and returns to the loop. This is the Node.js model and also how Nginx, Redis and Netty are built. One thread can hold tens of thousands of idle connections, since an idle connection costs only a small data structure instead of a thread. The cost is discipline: any handler that blocks or computes for a long time stalls every other connection on that loop. A 200 ms CPU-heavy JSON transform blocks everyone for 200 ms. CPU-heavy work must be moved to a worker pool.

6.3 Async and reactive styles

An event loop is awkward to write by hand because the logic is split into callbacks. Languages added syntax to restore a readable shape. Promises and async/await (JavaScript, Python asyncio, C#, Rust) let you write sequential-looking code that suspends at each wait and resumes later on the loop. Reactive streams (Reactor, RxJava) model data as streams with operators and add backpressure, a protocol by which a slow consumer tells the producer to slow down (section 10). They run on an event loop too, so the same rule applies: do not block.

6.4 Lightweight threads: coroutines, goroutines, virtual threads, actors

A third route keeps the readable thread-per-request style but makes "threads" cheap. Go's goroutines, Kotlin coroutines and Java's virtual threads are scheduled by the language runtime, not the kernel, start with a few kilobytes of stack, and when one performs blocking I/O the runtime parks it and runs another on the same OS thread. You can have hundreds of thousands of them. You write straight-line code, and the runtime does the multiplexing that the event loop made you do by hand.

The actor model (Erlang/OTP, Akka) is a related idea with a different safety story. Each actor owns its private state and handles one message at a time from its mailbox, and actors communicate only by sending messages. Because only one message touches the state at once, there are no locks inside an actor, and a failure is contained by supervision. This suits many independent stateful entities (one actor per user, device or game room). The cost is that sequences across actors are asynchronous and need explicit design for ordering, timeouts and mailbox growth (an unbounded mailbox is an unbounded queue).

7. Blocking and non-blocking I/O

The concurrency models above differ in how they treat waiting. Most server work is waiting: for the network, the disk, the database. Understanding what the operating system offers explains why event loops exist.

7.1 Blocking I/O

With a blocking call, such as read() on a socket with no data yet, the operating system puts the calling thread to sleep until data arrives. The thread cannot do anything else meanwhile. To serve 10,000 connections this way you need 10,000 threads.

7.2 Non-blocking I/O and readiness notification

With non-blocking mode, read() returns immediately with "nothing available yet" instead of sleeping. A program could poll every socket in a loop, but that wastes CPU. So operating systems provide a way to ask the kernel to watch many sockets at once and report which are ready. The older calls select and poll take the full list every time, so they cost time proportional to the number of watched sockets. On Linux the efficient call is epoll: you register sockets once, and the kernel gives back only the ones that are ready, so the cost scales with the number of active sockets rather than the number watched. BSD and macOS have kqueue, Windows has I/O completion ports, and newer Linux has io_uring, which batches submission and completion of I/O through shared ring buffers and also covers file I/O.

An event loop is exactly this: call epoll, get a list of ready sockets, run a handler for each (each reads or writes what is available without blocking), and go back to epoll. That is how one thread can multiplex thousands of connections, which is known as solving the "C10K problem" (ten thousand concurrent connections), and today's servers target hundreds of thousands or a million connections per machine, limited by memory and file descriptor limits.

7.3 Where non-blocking helps and where it does not

Non-blocking I/O helps when requests spend most of their time waiting: proxies, gateways, chat servers, services that fan out to many other services. It does not help CPU-bound work, which keeps a core busy regardless. It also does not make a slow database fast: if the database takes 200 ms, the request still takes 200 ms, but the app server can hold thousands of such waiting requests cheaply. Be careful with libraries: a blocking JDBC call or a synchronous file read inside an event-loop handler silently turns your scalable server into a one-request-at-a-time server. Check that the whole call chain is non-blocking, or push blocking calls to a separate pool.

Watch out Async does not remove the need for limits. An event-loop server can accept 50,000 requests while only 100 can proceed against a database. The other 49,900 sit in memory as pending work. Without bounds on in-flight work (sections 9 and 10) you replace thread exhaustion with memory exhaustion.

8. CPU-bound versus I/O-bound sizing, thread pools and queues

8.1 Two kinds of work

A task is CPU-bound if it spends nearly all of its time computing (image resizing, encryption, parsing large documents). It is I/O-bound if it spends most of its time waiting for something else (a database, an HTTP call). Real requests are a mixture: for instance 5 ms of CPU and 45 ms of waiting. The mixture determines how many threads (or concurrent tasks) each core can usefully keep busy.

8.2 The sizing rule

For CPU-bound work, more threads than cores only add context switching, so use about one thread per core (cores or cores + 1). For mixed work, a widely used estimate is:

threads per core  ≈  1 + (wait time / compute time)

If a request computes for 5 ms and waits 45 ms, the ratio is 9, so about 10 threads per core keep the core busy: while nine are waiting, one is computing. On an 8-core machine that means about 80 worker threads. If the same request waits 495 ms (500 ms total), you would want about 100 threads per core, which is why thread-per-request servers with slow dependencies run out of threads long before CPU, and why event loops and cheap threads are attractive.

This is a starting point to be confirmed by load testing, because real behaviour depends on garbage collection, lock contention, and the capacity of what the threads are waiting for. More threads help only until the downstream dependency (the database) saturates, at which point extra threads just queue up there.

8.3 Little's Law

The most useful single formula in this chapter, first met in Chapter 2, is Little's Law. For any stable system:

L = λ × W

where L is the average number of items in the system (in progress plus waiting), λ (lambda) is the average arrival rate, and W is the average time each item spends in the system. It holds regardless of distribution or scheduling, which is what makes it so powerful. Uses:

  • Concurrency needed. If a service gets 2,000 requests per second and each takes 50 ms on average (0.05 s), then L = 2,000 × 0.05 = 100 requests are in flight at any moment. You need at least 100 concurrent slots (threads, coroutines) to keep up, plus headroom.
  • Pool size. The same formula sizes a database connection pool (section 9).
  • Throughput ceiling. If you have 200 threads and each request takes 100 ms, the most you can do is λ = L / W = 200 / 0.1 = 2,000 per second. If the downstream slows to 400 ms, the ceiling drops to 500 per second with no change in your code. This is how a slow dependency becomes an outage.
  • Queue length. The number waiting is arrival rate times waiting time, so a queue of 1,000 items at 500 per second means each item waits 2 seconds.

8.4 Separating pools (bulkheads)

Do not run all work in one big pool. Give separate pools to separate dependencies and workloads, so that if one dependency becomes slow, only its pool fills and the rest of the service continues. This is the bulkhead pattern named after the watertight compartments of a ship (see Chapter 40 and Chapter 51). In an event-loop server the equivalent is to keep the loop free and send CPU-heavy or blocking work to dedicated pools.

8.5 Queue sizing in front of a pool

A pool with N workers is normally paired with a queue that holds tasks when all workers are busy. The queue absorbs short bursts, which is its only legitimate job. Think of the queue length in terms of time: a queue of 100 items for a pool that completes 1,000 per second adds at most 100 ms of delay, acceptable. A queue of 100,000 would add 100 seconds of delay, by which time the clients have given up, so the server is now doing work whose results nobody wants. A queue should be sized so that the worst-case wait is within the latency budget, which is Little's Law again: max queue length ≈ throughput × acceptable wait.

9. Connection pools to databases and their math

Opening a database connection is expensive: a TCP handshake, TLS, authentication, and on the database side a process or thread and memory (PostgreSQL uses a process per connection, roughly several megabytes each; MySQL a thread). So applications keep a connection pool: a set of already-open connections that requests borrow and return. A request that needs the database takes a connection from the pool, uses it, and puts it back. If none is free, the request waits (up to a timeout) for one to be returned.

9.1 The math

Apply Little's Law. If each query holds a connection for W seconds on average and queries arrive at λ per second, the number of connections in use is λ × W. With 1,000 queries per second each holding a connection for 5 ms, that is 1,000 × 0.005 = 5 connections busy on average. A pool of 10 to 20 gives comfortable room for variation. People are often surprised that the right pool is so small. A large pool does not make the database faster. A database has limited CPU cores and disk parallelism, and beyond a point more simultaneous queries just contend with each other. A frequently quoted rule of thumb is that a pool of roughly (2 × database cores) + effective disk spindles per database is a sensible starting point, to be tested.

9.2 The multiplication trap

The pool is per application instance, so the total demand on the database is instances × pool size. With 50 instances at 20 connections each, the database sees 1,000 connections, far more than it can use and possibly beyond its configured maximum (a typical default maximum is in the low hundreds). Autoscaling makes it worse: when load rises and the platform adds more instances, the connection count rises exactly when the database is already stressed, which can turn a slowdown into an outage. Defences:

  • Keep per-instance pools small, and compute the total against the database limit before choosing the instance cap.
  • Put a connection pooler or proxy between the apps and the database (PgBouncer, ProxySQL, RDS Proxy). Hundreds of app connections are multiplexed onto a few dozen real ones. In transaction pooling mode a server connection is held only for the duration of a transaction, but features that rely on session state (session variables, some prepared statements, advisory locks) can break.
  • Use read replicas with their own pools so reads do not compete with writes for the same connections.

9.3 Pool configuration that matters

  • Maximum size: the cap discussed above.
  • Acquire timeout: how long a request waits for a free connection before failing. Keep it short (hundreds of milliseconds to a few seconds), so that a saturated pool turns into fast errors and not into a pile of threads hanging.
  • Query and statement timeouts: a query that runs forever holds a connection forever. Set limits in both client and database.
  • Connection lifetime and validation: recycle connections periodically and test them, because firewalls and load balancers silently drop idle connections, which otherwise show up as sudden errors.
  • Leak detection: code that borrows a connection and forgets to return it (for example on an exception path) slowly drains the pool, a classic cause of "the service hangs after a few hours".

The same ideas apply to HTTP client pools toward other services: bound the number of connections and requests per destination, set timeouts, and fail fast.

10. Backpressure, bounded queues and load shedding

When work arrives faster than it can be processed, something has to give. A system with no plan lets the queue grow without bound until memory runs out or latency becomes useless. A system with a plan chooses where to push back.

10.1 Unbounded queues are a trap

An unbounded queue looks harmless because it never rejects work. But if the arrival rate stays above the service rate, the queue grows forever: memory fills, garbage collection thrashes, and the age of the oldest item rises until every response is too late to matter. Because requests at the back wait so long, by the time they are served the client has timed out and retried, so the server does work whose answer is thrown away, and the retries add yet more load. This feedback loop is why overload usually ends in a total outage, not a gentle slowdown.

10.2 Bounded queues and backpressure

The remedy is to bound every queue and decide what happens when it is full. Backpressure means the slowness of a downstream stage is felt by the upstream one, instead of being hidden in a growing buffer. Options when the bound is hit:

  • Block the producer (a bounded blocking queue). This slows the producer to the consumer's speed. It works inside one process and in reactive streams, but over a network, blocking ties up the caller's resources.
  • Reject immediately with an error such as HTTP 503 Service Unavailable or 429 Too Many Requests, optionally with a Retry-After header. The caller learns fast and can back off.
  • Drop the oldest or the lowest-priority item. Dropping the oldest is often right for real-time data (stale data is worthless); dropping newest is right when order and fairness matter.
  • Signal upstream in the protocol: TCP's receive window, HTTP/2 flow control, and reactive streams' "request(n)" all let a consumer say how much it can take.

10.3 Load shedding (preview)

Load shedding is deliberate rejection of some requests to protect the rest. A server estimates its own health (queue depth, in-flight count, CPU, or the age of the oldest queued request) and refuses new work when over a threshold. Smart shedding also prioritizes: keep health checks, logins and payments, and drop prefetches, analytics and background refreshes first. Rate limiting (Chapter 16) is the sibling technique that limits by caller to keep one client from consuming everything; shedding limits by total capacity. Together with timeouts, retry budgets and circuit breakers (Chapter 40) they make up the overload defences of a service.

Interview tip When you add a queue anywhere in a design, say its bound and what happens when it is full. "A bounded queue of 1,000, and beyond that we return 503 and clients retry with jittered backoff" is a short sentence that signals senior thinking.

11. Concurrency problems inside services

Once many requests run at the same time, they will sometimes touch the same data at the same instant. The resulting bugs are the hardest kind: rare, hard to reproduce, and invisible in a single-user test.

11.1 Race conditions and shared state

A race condition is a bug whose outcome depends on the unlucky timing of concurrent operations. The classic form is check-then-act: the code checks a condition and then acts on it, but the condition can change between the two steps. "If the username is free, create it" lets two requests both see it free, and both create it. "If stock is above zero, sell one" oversells the last item.

Inside one process, shared mutable state is the source: a static field, a singleton holding a map, a cached object modified by request threads. Even counter++ is three steps (read, add, write) and two threads can both read 5 and both write 6, losing one increment. The cures are to avoid sharing (make objects immutable, keep state per request), to use atomic operations or concurrent data structures, or to protect the state with a lock. But across several app servers in-process locks are useless, since each server has its own memory. The shared state that matters lives in the database or shared store, and the protection must live there too.

11.2 The lost update

The most common concurrency bug in web services is the lost update. Two requests read the same row, each computes a new value from what it read, and each writes. The second write overwrites the first, silently discarding it.

11.3 The toolbox of cures

  • Make the update atomic in the database. Instead of read-modify-write in the application, send UPDATE accounts SET balance = balance + 50 WHERE id = 7. The database applies it under its own row lock, so concurrent increments serialize correctly. This is the cheapest and best fix whenever the new value can be expressed as an operation on the old one. Conditional forms such as UPDATE stock SET qty = qty - 1 WHERE id = 9 AND qty > 0 also fix check-then-act: the check and the act are one statement.
  • Pessimistic locking. Lock the row before reading it: SELECT ... FOR UPDATE inside a transaction. Others who try to lock the same row wait until you commit. This is correct and simple, but holds locks while your code runs (so keep the transaction short, never call remote services inside it), risks deadlocks if two transactions lock rows in different orders (always lock in a consistent order), and reduces concurrency.
  • Optimistic concurrency control. Assume conflicts are rare. Read the row together with a version number (or timestamp, or a hash of the content), and write with UPDATE ... SET ..., version = version + 1 WHERE id = ? AND version = ?. If zero rows were updated, someone else changed it first, so re-read and retry or report a conflict to the user. No locks are held while the user or the code thinks, which makes it ideal for web forms and for conflict-rare data. Under heavy conflict on the same row, retries pile up and it performs worse than a lock. HTTP exposes the same idea with ETag and If-Match headers, returning 412 Precondition Failed on a mismatch (Chapter 5).
  • Unique constraints and idempotency keys. Let the database enforce "only one" with a unique index and treat a duplicate-key error as the signal that someone else won. The same device protects against retries creating duplicates (Chapter 32).
  • Isolation levels. Database transactions run at an isolation level that decides which anomalies can occur. Read committed (a common default) permits lost updates in read-modify-write code; repeatable read or snapshot isolation detects some of them; serializable prevents them all but may abort transactions that you must retry. See Chapter 18 and Chapter 31 for the details; the point here is not to assume the default protects you.
  • Distributed locks when the resource is not a database row (for example "only one instance runs this report"). They are tricky because of expiry and clock pauses; use fencing tokens (Chapter 30).
  • Serialize by key. Route all operations for one entity to one worker, using a partitioned queue (all events for user 42 go to the same partition) or one actor per entity. There is then no concurrent access to that entity at all.

12. Lock contention and hot rows

Locks protect correctness but they are also the serial section of Amdahl's law. Many requests wanting the same lock form a queue, and the throughput on that item is limited to one holder at a time. If a lock is held for 5 ms, the most one lock can sustain is 1 / 0.005 = 200 operations per second, no matter how many servers you add. This is the (a) term of the USL in practice.

12.1 Hot rows and hot keys

A hot row is a single database row that many transactions want to update: a global counter, the "total sales today" row, the balance of one very active account, the inventory of the one popular product during a flash sale. Each update takes a row lock, so all updates to that row run one after another. Even if each takes one millisecond, the row caps at about 1,000 updates per second, and with lock queues and transaction overhead often far less. Sharding does not help, since the row lives on one shard. The same pattern is a hot key in a cache or partitioned store, where one key receives disproportionate traffic and overloads the single node that owns it.

12.2 Ways to relieve contention

  • Shorten the critical section. Do computation, remote calls and logging outside the lock or transaction. Take locks late and release early.
  • Split the hot counter into N sub-counters ("striping" or "sharded counters"). Each increment picks one at random; a read sums them. With 20 sub-rows, write capacity is about 20 times higher. The price is a more expensive read and an approximate view while updates are in flight.
  • Aggregate in memory and flush in batches. Count in the app or a cache (such as Redis INCR) and write the total to the database every second.
  • Append instead of update. Record each event as a new row in a log table and compute the total by summing (or periodically rolling up). Inserts do not contend on one row.
  • Reserve in chunks. For flash-sale stock, give each app server or shard a block of units to sell locally, rebalancing occasionally, rather than every sale hitting one stock row.
  • Queue and serialize. Funnel updates for the hot entity through a single consumer which applies them in order and batches them. Contention becomes a queue, which is bounded and observable.
  • Replicate hot read keys. For a hot cache key, keep several copies under suffixed names (key#1 to key#8) or add a small local cache in each app server with a short TTL (Chapter 14 covers hot-key and stampede handling).
  • Lock-free structures. Inside a process, use atomic variables and concurrent collections rather than one big mutex, and partition maps by key.
Watch out Retries make contention worse. If a hundred requests fail with a conflict and all retry immediately, they collide again. Use exponential backoff with jitter (random delay) and a bounded number of attempts.

13. Scaling the application tier: a checklist

When the question is "make this service handle ten times the traffic", walk down this list. Each item is a thing a reviewer would look for.

  1. Statelessness. No local sessions, files or in-memory-only data. Sessions in a shared store or signed tokens (section 3).
  2. Load balancing. A load balancer in front with health checks and connection draining (Chapter 9). Prefer least-connections or round robin to sticky routing.
  3. Bounded everything. Bounded thread pools, bounded queues, bounded connection pools, bounded request and payload sizes, explicit timeouts on every outgoing call (section 10).
  4. Right concurrency model for the workload: event loop or cheap threads for I/O-heavy fan-out, more cores for CPU-heavy work, separate pools for blocking calls (sections 6 to 8).
  5. Database protection. Cache hot reads, use replicas, index, batch, pool connections, and add a pooler before adding instances (section 9).
  6. Idempotent, retry-safe operations so that retries and duplicate deliveries are harmless (Chapter 32).
  7. Move slow work off the request path. Emails, thumbnails, reports and webhooks go to a queue and workers (Chapter 34, Chapter 35).
  8. Concurrency-safe writes. Atomic updates, versions, unique constraints; no in-process locks protecting shared data (section 11).
  9. Graceful startup and shutdown. A new instance must warm up (connections, caches) before taking traffic, and on shutdown must finish in-flight requests, which matters for autoscaling and rolling deploys.
  10. Observability. Per-instance metrics for request rate, latency percentiles, error rate, pool and queue depths, saturation (Chapter 54), so that you know which of the above fails first.
  11. Load testing with realistic traffic against a production-like environment to find the real knee of the curve, not the one on the whiteboard.

13.1 Containers, instances and autoscaling (preview)

A stateless service packaged as a container image can be started many times from the same image. An orchestrator such as Kubernetes keeps a desired number of copies running, replaces failed ones and spreads them over machines. Autoscaling adjusts that number automatically from a metric: average CPU, requests per instance, queue depth, or a custom signal. It brings several traps that tie back to this chapter. New instances take time to start and warm up (tens of seconds to minutes), so autoscaling reacts to a spike late; scale-out multiplies database connections (section 9); and CPU is a poor trigger for I/O-bound services, whose CPU stays low while their threads or pools are saturated, so concurrency or queue depth is a better signal. Set a floor (minimum instances) for availability, a ceiling to protect dependencies, and prefer scheduled scaling for predictable peaks. Chapter 43 covers the mechanics.

14. Capacity planning with headroom

Capacity planning is deciding in advance how many resources you need. The steps are: forecast the load (including the peak, not just the average), measure the capacity of one unit (one instance, one database) at the target latency, divide, and add margin.

  1. Peak, not average. Daily traffic is not flat. A peak-to-average ratio of 2 to 5 is common, higher for events, so size for the peak (Chapter 2).
  2. Capacity of one unit at the knee. Load test one instance and find the request rate at which p99 still meets the target, say 400 requests per second. That is its usable capacity, not the rate at which it crashes (say 650).
  3. Divide. Peak load divided by usable capacity gives the instance count.
  4. Add N+1 or N+2 redundancy. Plan so that the service survives losing one instance, or one whole availability zone, at peak. With three zones and a requirement to survive the loss of one, each zone must carry 50 percent of peak, so total capacity must be 150 percent of peak, and each zone runs at 67 percent in normal operation (Chapter 41).
  5. Headroom for growth and surprises. Keep normal peak utilization at 50 to 70 percent so that spikes, deploys, a failed zone and a slow dependency do not push you over the knee. Re-forecast regularly, because provisioning can take weeks for hardware and growth compounds: 10 percent a month is 3.1 times in a year.
Key idea Headroom is not waste. It buys you time to react: autoscaling lag, failures and traffic surprises all consume it. Cost optimization comes from reducing the work per request and from autoscaling down off-peak, not from running hot at the peak.

A concrete story shows how all of this fits together. Start with a small product and double the load again and again, each time doing the cheapest thing that works. In an interview you can narrate this ladder; the skill is knowing when to climb a rung.

16. Worked example with numbers

Problem: an order service must handle a peak of 6,000 requests per second. Each request does 4 ms of CPU work, then makes one database query that takes 10 ms, and one call to a payment-status service that takes 36 ms. The target is p99 under 300 ms. Size the app tier, thread pools, database pool and headroom.

16.1 Per-request time and concurrency

Service time per request is 4 + 10 + 36 = 50 ms, of which 4 ms is CPU and 46 ms is waiting. By Little's Law the number of requests in flight at the peak is L = λ × W = 6,000 × 0.050 = 300 concurrent requests.

16.2 Threads per instance

Take instances with 4 cores. The sizing estimate is 1 + wait/compute = 1 + 46/4 = 12.5 threads per core, or about 50 threads per instance. Each instance can then hold roughly 50 requests in flight. To hold 300 concurrent requests we need 300 / 50 = 6 instances at 100 percent. Now check CPU: at 6,000 requests per second the whole fleet needs 6,000 × 4 ms = 24 CPU-seconds per second, which means 24 cores fully busy, and 6 instances × 4 cores = 24 cores, so they would be at 100 percent CPU. That is on the knee, so we need headroom.

16.3 Headroom and redundancy

Target 60 percent CPU at peak: 24 / 0.6 = 40 cores = 10 instances. Now require that we survive losing one of three zones. Spread across 3 zones, 12 instances (4 per zone) gives 8 remaining after a zone loss: 8 instances × 4 cores = 32 cores, CPU utilization 24 / 32 = 75 percent, still under the knee. Choose 12 instances. Normal utilization is 24 / 48 = 50 percent, comfortable. The thread pool of 50 per instance gives 600 slots against 300 needed at peak, so the pool is also not the limit, even when a zone is lost (8 × 50 = 400 vs 300).

16.4 Database connections

Database work per request is 10 ms held, so connections in use = 6,000 × 0.010 = 60 connections busy on average at the peak. If the pool is per instance with 12 instances, 60 / 12 = 5 busy per instance on average. A per-instance pool of 10 gives room for bursts, for a total of 120 possible connections. Suppose the database has 16 cores: the rule of thumb of about 2 × cores + a few suggests useful concurrency near 35 to 40, so 120 simultaneous connections is more than it can use and, if autoscaling later doubles the fleet, rises to 240. Put a pooler in front limiting real connections to about 40, with app-side acquire timeouts of 200 ms. Queries at 60 busy average on 16 cores means queries will queue at the database: that is a real concern that says the database, not the app tier, is the bottleneck. Remedies by cost: a cache for repeated reads (if 70 percent of queries are cacheable, load drops to about 18 busy connections), a read replica, or a faster query via an index.

16.5 Downstream dependency

The payment-status call takes 36 ms and we make 6,000 per second, so 216 concurrent calls into that service at the peak. If it slows to 360 ms (ten times), in-flight calls become 2,160 and our 600-slot pool fills in seconds. Unless protected, every request thread would hang and our whole service fails. Therefore: a timeout of about 150 ms on that call, a separate bulkhead pool of, say, 300 slots for it, a circuit breaker that opens when most calls fail, and a fallback (return "status pending") so that the order endpoint degrades gracefully. A bounded queue of 200 in front of the pool with a 503 beyond it caps the added delay: 200 / 6,000 = 33 ms.

18. Interview Q&A

What does it mean for a system to be scalable, and how would you measure it?

A system is scalable if I can keep its latency and availability within target as load grows by adding resources, at a cost that grows roughly in proportion. I measure it by picking the load parameter that matters (requests per second, connections, data size), then running load tests at increasing levels while recording throughput and p50 and p99 latency. The result is a curve with a knee, the point where queueing makes latency bend upward. Capacity is the load at the knee, not at failure, and scalability is how well that knee moves right as I add instances. I also check for diminishing returns, since contention and coordination can make the second doubling worth much less than the first.

Why does adding servers not give linear speed-up? What do Amdahl's law and the USL say?

Some work is serial, such as a lock, a single leader or a single database writer. Amdahl's law shows that if a fraction s is serial, the speed-up can never exceed 1/s: with 5 percent serial it is capped at 20 times regardless of servers. The Universal Scalability Law adds coherency cost, the price of keeping workers consistent with each other, which grows with the square of the worker count and eventually makes throughput fall. So the practical work is to find the shared thing, shrink or partition it, and avoid designs where every node must talk to every other node.

How do you make a service stateless, and what do you do about sessions?

I move everything that must survive between requests out of the app process: durable data to the database, files to object storage, shared short-lived data to Redis, scheduled jobs to a single scheduler. For sessions there are three options. Sticky sessions pin a user to a server but lose sessions on failure and unbalance load. A shared store such as Redis keyed by a session ID lets any server serve any user and supports instant revocation at the price of an extra network call and a critical dependency. Signed short-lived tokens carry identity in the client and need no lookup, but cannot be revoked early without a deny list. I usually use signed tokens for identity, plus a shared store for anything revocable.

Explain thread-per-request versus an event loop. When would you choose each?

Thread per request gives each request an OS thread that blocks on I/O, which keeps code simple but costs memory and context switching, so a machine tops out at thousands of concurrent requests. An event loop uses a few threads and the operating system's readiness notification (epoll) to multiplex many connections, so waiting is cheap, but any blocking or CPU-heavy handler stalls everyone on that loop. I choose an event loop or cheap threads (goroutines, virtual threads) for I/O-heavy work with many idle or slow connections, such as gateways and chat. For CPU-heavy work I want parallelism across cores, with a pool sized near the core count, and I keep long computation off event loops.

How do you size a thread pool, and how does Little's Law help?

For CPU-bound tasks I use about one thread per core. For mixed tasks the estimate is threads per core of 1 plus wait time over compute time, so a request that computes 5 ms and waits 45 ms wants about 10 threads per core. Little's Law gives the total concurrency required: in-flight work equals arrival rate times time in the system, so 2,000 requests per second at 50 ms means 100 in flight. It also gives the throughput ceiling of a fixed pool, pool size divided by request time, which shows how a slow dependency cuts capacity without any code change. I confirm the numbers with a load test, since garbage collection and downstream limits shift them.

Why is a database connection pool usually small, and what goes wrong with many instances?

Connections in use equal query rate times the time each holds a connection, so 1,000 queries per second at 5 ms need only about 5 connections. A database has limited cores and disk parallelism, so more concurrent queries beyond a point just contend and slow each other down. The trap is that pools are per instance, so 50 instances with 20 connections each means 1,000 connections, and autoscaling adds more exactly when the database is stressed. I keep pools small, set short acquire and statement timeouts, and put a pooler such as PgBouncer between the app and the database so real connection count is independent of the number of instances.

What is backpressure and why should queues be bounded?

Backpressure means a slow downstream stage makes upstream stages slow down or refuse work, instead of hiding the overload in a growing buffer. An unbounded queue never rejects, so under sustained overload it grows until memory is exhausted, and the oldest items wait so long that clients have already timed out and retried, doubling the load while the server does useless work. A bounded queue gives a clear policy when full: block the producer, reject quickly with 503 or 429, or drop the least valuable item. I size the bound from the latency budget, since the maximum wait is queue length divided by throughput. Fast rejection keeps accepted requests fast and lets clients back off.

Two requests update the same account balance at the same time. How do you prevent a lost update?

The lost update happens when both read the old value, compute, and the second write overwrites the first. If the change can be expressed as an operation on the old value, the best fix is an atomic statement such as UPDATE ... SET balance = balance + 50, so the database serializes it under a row lock. If I must read, think and write, I use either pessimistic locking with SELECT FOR UPDATE inside a short transaction, or optimistic concurrency with a version column and a conditional update that affects zero rows on conflict, after which I re-read and retry with backoff. Optimistic suits rare conflicts and long think times, pessimistic suits frequent conflicts. I would also check the isolation level rather than assume the default prevents this.

What is a hot row and how would you fix it?

A hot row is a single row, such as a global counter or the stock of a flash-sale product, that many transactions update. Row locks serialize them, so throughput on that row is capped at roughly one over the lock hold time, and sharding does not help since the row lives on one shard. Fixes: shorten the transaction, split the counter into many sub-counters and sum on read, accumulate in memory or Redis and flush in batches, append events instead of updating, give each server a block of stock to sell locally, or funnel updates through one consumer through a queue. Which to choose depends on how exact the reads must be. I would also add jittered backoff to retries so conflicts do not synchronize.

How would you scale the app tier for 10 times the traffic, and what would you worry about?

I would confirm statelessness first, then put the instances behind a load balancer with health checks, and compute the instance count from peak load, per-instance capacity at the knee, and zone-failure redundancy, keeping peak utilization around 60 percent. Then I would look at what the extra instances do to dependencies: database connections multiply, so I add a pooler and cache hot reads; downstream services get ten times the calls, so I add timeouts, bulkheads and bounded queues. I move slow work to a queue, make writes idempotent and concurrency-safe, and set autoscaling on a signal that matches the workload, such as concurrency or queue depth for I/O-bound services. Finally I load test to find the real knee, since the bottleneck will have moved.

Autoscaling just added instances but latency got worse. What happened?

Several things can cause this. The new instances may be cold and slow to warm caches and connections, and a load balancer sending them full traffic at once can overload them. The extra instances multiply database connections or downstream calls, so the shared dependency, which was the real bottleneck, saturates further. The trigger metric may be wrong, such as CPU for an I/O-bound service, so scaling happened late or on noise. Finally, the problem may have been contention on a lock or hot row, where more instances only add more waiters, as Amdahl and the USL predict. I would look at saturation signals on the dependencies first, then use slow-start in the load balancer and a better scaling metric.

19. Recap

  • Scalability is keeping latency and availability acceptable as load grows, at proportional cost. Name the load parameter, and measure throughput with percentile latency. Capacity is the knee of the curve, so keep headroom.
  • Scale up first because it is simple, scale out the stateless tiers, and partition data last. Amdahl's serial fraction and the USL's contention and coherency terms explain why more machines give diminishing, and eventually negative, returns.
  • Stateless services are interchangeable. Sessions go to a shared store or signed tokens, files to object storage, jobs to a single scheduler; state is moved, not removed.
  • Reads scale by copying (cache, replicas, CDN); writes scale by splitting (sharding) or smoothing (queues, batching).
  • Find the bottleneck by following the request path and comparing load to capacity per stage, checking utilization and saturation, and repeat as the bottleneck moves.
  • Thread per request is simple but costly; event loops with epoll and lightweight threads make waiting cheap but require non-blocking code. Size by wait-to-compute ratio and verify with Little's Law, L = λ × W.
  • Connection pools should be small and the total is instances times pool size; use a pooler, timeouts and leak detection. Bulkhead dependencies into separate pools.
  • Bound every queue, apply backpressure, shed load fast with 503 or 429, and use jittered backoff on retries.
  • Concurrent requests cause lost updates and check-then-act races. Prefer atomic SQL, then versions (optimistic) or row locks (pessimistic), unique constraints, and serialization by key. In-process locks do not work across servers.
  • Hot rows cap throughput at one over the lock hold time; split, batch, append or queue them.
  • Plan capacity from peak load, usable capacity at the knee, N+1 or zone redundancy and 50 to 70 percent utilization. Climb the scaling ladder only as measurements demand.
