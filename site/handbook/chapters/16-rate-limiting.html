Rate Limiting and Load Shedding

Every system has a finite capacity, and the traffic sent to it is never perfectly polite. This chapter explains how to decide who may use how much (rate limiting), how the classic algorithms work step by step, how to make a limiter work across many servers, and what to do when the system is overloaded anyway (load shedding and admission control).

1. Why limit at all

A server can only do so much work per second. If requests arrive faster than the server can finish them, they queue up, latency rises, memory fills with half-finished work, and eventually the server falls over. Worse, the failure is usually not graceful: a server that is 20% overloaded does not serve 80% of requests well, it often serves almost none of them well, because every request is slow and clients time out and retry, which adds even more load. This spiral is called congestion collapse.

Rate limiting is the practice of deliberately rejecting (or delaying) requests that exceed an agreed allowance, so that the system stays inside the region where it works well. Load shedding is the related practice of dropping some work when the system is already overloaded, regardless of any allowance, so the work that remains can still be done quickly. The first is a policy about who may use how much; the second is a survival reflex about how much total the system can take right now. Both end with some requests receiving a fast "no" instead of everyone receiving a slow, failing "maybe".

There are four main reasons to limit, and a good answer in an interview names them separately because they lead to different designs.

1.1 Abuse and security

Some callers are hostile: a script guessing passwords, a scraper copying your whole catalog, a bot creating fake accounts, or a buggy client in an infinite loop. A limit on login attempts per account (for example 5 per 15 minutes) makes password guessing impractical. A limit on account creation per IP slows spam. These limits are small and strict because legitimate users almost never come close to them.

1.2 Fairness

Capacity is shared. If one customer sends a huge batch job at noon, the interactive users of all other customers should not suffer. A per-customer limit means no single caller can take more than their share, which is the heart of multi-tenant isolation (section 10). Fairness limits are usually set well above normal use but well below total capacity.

1.3 Cost control

Some requests cost real money: an API call that triggers an LLM inference, a paid third-party lookup, an SMS, a large export. Limits cap the bill. They also implement the business model: a free tier gets 60 requests per minute, a paid tier gets 600, and an enterprise contract gets 6,000. Here the limit is a product feature, so it must be predictable and documented.

1.4 Protecting dependencies

Your service may be fast, but the database behind it, a legacy system, or a partner API may be slow and fragile. A limiter in front of that dependency (a per-dependency limit) stops your own traffic from crushing it. This is the bulkhead idea: contain the damage by giving each downstream a bounded amount of your attention.

Key idea Rate limiting is a policy tool: it answers "how much may this caller use?" and is based on identity. Load shedding is a survival tool: it answers "how much can we take right now?" and is based on current health. A robust system has both, because even well-behaved callers, each under their own limit, can add up to more than the system can handle.

2. Where to place limiters

A request travels through several layers on its way to your data, and each layer can enforce a limit. The right answer is usually "more than one layer", because each layer protects against a different thing and each knows different information.

2.1 In the client

A well-behaved client limits itself: it spaces out calls, batches them, and backs off after errors (section 7.3). Client-side limits cannot be trusted for protection, because a hostile or buggy client simply ignores them, but they are valuable because they stop good clients from wasting requests that would be rejected anyway, and they make the whole system calmer. SDKs you publish should include this behaviour.

2.2 At the edge or API gateway

The gateway is the natural home for coarse limits, because every request already passes through it and it already authenticates the caller. See Chapter 11 for the gateway's role in general. Limits here are typically per API key, per user, per IP address, and one global ceiling. The advantage is that rejected requests never reach your services, so a flood costs you almost nothing downstream. The disadvantage is that the gateway does not understand the business cost of each endpoint unless you configure that, so its limits are blunt.

2.3 In the service

The service itself knows which endpoint is expensive, which tenant is calling, and how loaded it is right now. It is the right place for concurrency limits (section 9), per-tenant fairness, and load shedding (section 8). Even when the gateway limits traffic, each service should protect itself, because a bug, a retry storm from another internal service, or a misconfigured gateway can send it more than expected. Internal callers are not automatically polite.

2.4 Per dependency

When service A calls database B or partner API C, a limiter (or a concurrency cap) in A's client code for that dependency bounds how hard A can push it. This also protects A: if C is slow, a cap on in-flight calls to C stops A from filling all its threads waiting on C. Libraries commonly combine this with timeouts and circuit breakers.

Interview tip Say it in layers: "Coarse, cheap limits at the gateway to drop floods early; precise per-tenant and per-endpoint limits in the service; concurrency limits and shedding as the final safety net; and the client cooperates with backoff." That one sentence shows you understand that no single placement is sufficient.

3. What to key on, and tiers

A limiter counts events per something. That "something" is the key. Choosing the key is the most important policy decision, because it decides who is being treated as one caller.

Evaluate the cheapest and most general checks first so that obvious abuse is rejected with the least work, and make sure a rejected request does not consume tokens from the other limits it never reached.

3.1 Tiers and quotas

Two words are often mixed up. A rate limit bounds speed over a short window ("100 requests per second"), protecting capacity. A quota bounds total consumption over a long period ("1 million requests per month", "10 GB per day"), enforcing the contract and the bill. You usually want both: the quota says how much you may use in total; the rate limit says how fast you may use it, so a customer cannot burn a month of quota in a minute and take the service down.

Plans (tiers) map to limits: a free tier with low rates and no burst allowance, a paid tier with higher limits, and an enterprise tier with negotiated, sometimes dedicated, capacity. Store the limits as configuration keyed by plan, loaded into the limiter (or read from a fast cache), so changing a customer's plan takes effect without a deploy. Allow explicit per-customer overrides, because a sales deal or an incident will eventually require one.

Watch out Keying by IP alone is a classic trap. Behind carrier-grade NAT, thousands of legitimate mobile users can share one public address, and a single limit would lock them all out. Conversely, an attacker with a botnet uses a different IP per request and never trips an IP limit. Use IP as one signal among several, not as the only identity.

4. The algorithms, step by step

All limiters answer the same question: "given the history of this key, may this new request proceed?" They differ in how much history they remember (memory cost), how accurately they enforce the limit, and how they treat bursts. We will use one running example: a limit of 100 requests per minute.

4.1 Fixed window counter

Idea. Divide time into fixed windows (for example each calendar minute: 12:00:00 to 12:00:59, then 12:01:00 to 12:01:59). Keep one counter per key per window.

  1. When a request arrives, compute the window it belongs to, for example window = floor(now / 60 s).
  2. Increment the counter stored under the key (user, window).
  3. If the new count is above 100, reject; otherwise allow.
  4. Let the counter expire shortly after the window ends, so memory is reclaimed.

Strength. It is extremely cheap: one integer per key, one increment per request. It is easy to implement in Redis with INCR and EXPIRE, and easy to explain to users ("100 per calendar minute").

Weakness: the boundary burst. The counter resets sharply at the window edge. A client can send 100 requests in the last second of one window and another 100 in the first second of the next. In a two-second span the server has accepted 200 requests, twice the intended rate, even though no window was ever violated.

Whether this matters depends on your purpose. For a billing quota it hardly matters. For protecting a fragile backend, a 2x spike at every boundary can be exactly the load you wanted to avoid.

4.2 Sliding window log

Idea. Remember the exact time of every recent request, and at each new request count how many fall within the last 60 seconds, a window that slides with the clock.

  1. Keep a sorted list of timestamps per key (in Redis, a sorted set with the timestamp as score).
  2. On a new request at time t, delete all entries older than t - 60 s.
  3. Count the entries remaining. If the count is 100 or more, reject.
  4. Otherwise add t to the list and allow.

Strength. It is exact. At any instant, no more than 100 requests exist in any 60-second span, so there is no boundary burst.

Weakness. Memory is proportional to the limit: up to 100 timestamps per key (each perhaps 16 to 40 bytes with structure overhead), so a limit of 10,000 per hour means up to 10,000 entries per key, and millions of keys become expensive. Each request also costs an O(log n) insert plus a range delete. Use it when limits are small and accuracy matters, such as login attempts.

4.3 Sliding window counter (the weighted approximation)

Idea. Keep just two fixed-window counters, the current one and the previous one, and estimate the sliding window by weighting the previous count by how much of it still overlaps the sliding window.

  1. Maintain prev (requests in the previous complete window) and curr (requests so far in the current window).
  2. Let elapsed be the fraction of the current window that has passed (for example 15 s of 60 s is 0.25).
  3. Estimate the number of requests in the last 60 seconds as prev * (1 - elapsed) + curr.
  4. If the estimate plus this request exceeds the limit, reject; otherwise increment curr and allow.

Strength. Two integers per key give an accuracy that is good in practice. Cloudflare has reported that this approximation was within a very small error of the exact answer on real traffic, and it removes the boundary burst almost entirely. Weakness. It assumes requests in the previous window were spread evenly, so if they were all bunched at the end the estimate undercounts slightly; it is an approximation, not a guarantee. For most APIs that is an excellent trade.

4.4 Token bucket

Idea. Picture a bucket that holds tokens. Tokens are added at a steady rate (the refill rate), up to a maximum (the capacity). Each request must take one token to proceed; if the bucket is empty, the request is rejected. The capacity determines how large a burst is allowed, and the refill rate determines the long-run average.

  1. Store two values per key: tokens and last_refill_time.
  2. On a request at time t, compute tokens = min(capacity, tokens + (t - last_refill_time) * refill_rate) and set last_refill_time = t. (Refill lazily, only when a request arrives, so no background timer is needed.)
  3. If tokens >= 1, subtract 1 and allow. Otherwise reject, and the caller can be told to wait (1 - tokens) / refill_rate seconds.

Example: capacity 20, refill 10 per second. A caller that was idle for two seconds has a full bucket of 20 and can send 20 requests at once (a burst), then 10 per second afterwards. Over any long period the average cannot exceed 10 per second, and no burst can exceed 20, so you have two independent knobs: average rate and burst tolerance. This is why token bucket is the most widely used algorithm: it matches how real traffic behaves (bursty but bounded). Amazon API Gateway, Stripe, and many others describe their limits this way. Memory is two numbers per key.

4.5 Leaky bucket

Idea. Picture a bucket with a hole in the bottom. Requests pour in at the top; water leaks out of the hole at a constant rate. If requests arrive faster than the leak, the bucket fills; when it is full, new requests overflow and are dropped. There are two common readings, and it helps to know both.

  • As a queue (traffic shaper). The bucket is a FIFO queue of fixed size. A worker removes one request every fixed interval and forwards it. Bursts are absorbed in the queue and released at a perfectly smooth rate. Requests that arrive when the queue is full are dropped. The output is smooth, which is ideal for protecting a backend that cannot tolerate bursts. The cost is added latency (requests wait in the queue) and the fact that old requests may be served while new ones are dropped.
  • As a meter. A counter represents the water level; each request adds 1, and the level drains at a constant rate. If adding the request would exceed the capacity, reject. This variant does not queue; it is mathematically the mirror image of the token bucket (water level = capacity minus tokens) and allows the same bursts.

4.6 GCRA (Generic Cell Rate Algorithm)

GCRA comes from telephone and ATM networks and is mathematically equivalent to a token bucket, but it stores one number per key instead of two. It is used by several real limiters (for example the Redis-based redis-cell module and some API gateways) because a single value can be updated atomically with simple operations.

The one stored value is the TAT, the theoretical arrival time: the earliest moment at which the next request would be "on schedule". Two constants define the policy: the emission interval T (the time each request "costs", which is 1 / rate) and the burst tolerance tau (how far ahead of schedule a caller may run, equal to (burst - 1) * T).

  1. Read the stored TAT (use the current time if there is none).
  2. If now < TAT - tau, the caller is too far ahead of schedule: reject, and tell them to retry after TAT - tau - now.
  3. Otherwise allow, and set TAT = max(now, TAT) + T.

6. Distributed rate limiting

Everything so far assumed one process holding the counters. Real services run on many instances behind a load balancer, and a user's requests land on different ones. If each instance keeps its own counter with a limit of 100, a user could get 100 per instance, so 4,000 across 40 instances. You need the instances to share state, or to coordinate somehow. There is no free option: every approach trades accuracy, latency, and availability.

6.1 Central store (usually Redis)

The common design keeps all counters in one fast shared store, usually Redis (see Chapter 15). Every instance asks the store before serving. Redis is a good fit: it is in-memory, handles on the order of tens to hundreds of thousands of simple operations per second per node, processes commands one at a time, and supports key expiry.

6.2 Fixed window with INCR and EXPIRE, and its race condition

The simplest Redis limiter for a fixed window is two commands: INCR key (atomically adds 1 and returns the new value) and EXPIRE key 60 (so the key disappears after the window). The first request creates the key, because incrementing a missing key makes it 1.

The trap is doing them as two separate steps from the application. If the instance crashes, or the connection drops, between INCR and EXPIRE, the key lives forever, the counter never resets, and the user is blocked permanently. The fix is to make the pair atomic, either by calling EXPIRE only when INCR returned 1 and accepting a tiny residual risk, or (better) by running both inside one Lua script, which Redis executes without interleaving any other command.

6.3 Why you need atomic scripts for anything else

Token bucket needs "read tokens, compute refill, decide, write back". If you do that as separate GET and SET calls, two instances can interleave:

  1. Instance A reads tokens = 1.
  2. Instance B reads tokens = 1.
  3. A decides "allow" and writes tokens = 0.
  4. B also decides "allow" and writes tokens = 0.

Both requests passed on one token. This is a read-modify-write race, and under heavy concurrency it lets far more through than the limit. Solutions are: a Lua script (Redis runs a whole script as one uninterruptible unit, so the read, compute, and write cannot interleave), or optimistic transactions with WATCH and MULTI (retry on conflict, which performs badly under contention), or a single atomic command such as INCR when the algorithm allows it. Lua is the standard answer. A sketch of a token bucket script:

-- KEYS[1] = bucket key ; ARGV = capacity, refill_per_sec, now_ms, cost
local data = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(data[1]) or tonumber(ARGV[1])
local ts = tonumber(data[2]) or tonumber(ARGV[3])
local elapsed = math.max(0, tonumber(ARGV[3]) - ts) / 1000
tokens = math.min(tonumber(ARGV[1]), tokens + elapsed * tonumber(ARGV[2]))
local allowed = 0
if tokens >= tonumber(ARGV[4]) then tokens = tokens - tonumber(ARGV[4]); allowed = 1 end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', ARGV[3])
redis.call('PEXPIRE', KEYS[1], 120000)  -- expire idle buckets
return allowed

Two details deserve attention. First, the time now_ms should come from one consistent clock (either the Redis server clock or a trusted source), because instance clocks drift and a drifting clock distorts refill. Second, the key must expire (here after two minutes of inactivity) or millions of dead buckets accumulate. In a sharded Redis Cluster, all state for one key must live in one script call, so the key (not several keys) determines the shard.

6.4 Local approximation with periodic sync

One network round trip per request is costly: it adds roughly a millisecond (more across availability zones) and puts every request through Redis. A cheaper design makes most decisions locally and syncs occasionally.

  • Token leasing (batching). Each instance asks Redis for a chunk of tokens (for example 50) and then serves 50 requests from its local pool with no network call, fetching another chunk when it runs low. Redis traffic drops by the chunk size. The accuracy cost: tokens leased to an idle instance are stranded, and a burst may exceed the limit by up to the sum of unspent leases. Choose small chunks for users with low limits, larger chunks for users with high limits.
  • Local counters with periodic sync. Each instance counts locally and, every 100 ms or so, adds its count to the shared total and reads back the global count. Decisions use the last known global total plus the local count. The limit can be overshot by whatever the other instances admitted during one sync interval.
  • Divide the limit. Give each of N instances a limit of L/N. It is simple and needs no coordination, but is wrong when load balancing is uneven or N changes, because a single instance may receive most of a user's traffic and reject early.

6.5 Sticky routing and sharded counters

Sticky routing. If the load balancer sends all requests for one key (user, API key) to the same limiter node, for example by consistent hashing on the key (Chapter 9), that node can keep the counter in local memory and be exact, with no network hop. The costs: load becomes uneven if one key is very hot, and if the node dies its counters are lost (a small, brief over-admission, usually acceptable) and traffic must be re-hashed.

Sharded counters. For one very hot key (a global limit of 50,000 per second, or one huge tenant), a single Redis key becomes a bottleneck, since one key lives on one shard handled by one thread. Split the counter into K sub-counters (key:0 to key:K-1), give each a share of the limit (limit / K), and have each request pick one at random or by instance. This spreads the load over K shards. The price is lower accuracy: one sub-counter can reject while others still have room, so you may reject a little early. Rebalance leftover capacity occasionally if that matters.

6.6 Fail-open versus fail-closed

The limiter is itself a dependency, and it can fail: Redis is down, slow, or partitioned. You must choose in advance what a failed check means.

  • Fail-open: if the limiter cannot decide, allow the request. Availability is preserved, but protection is gone exactly when something is wrong, so a failure of Redis plus a traffic spike can overload the backend. This is the usual choice for general API traffic and fairness limits, because blocking all users because the limiter is down would be an outage caused by a safety feature.
  • Fail-closed: if the limiter cannot decide, reject. This is correct for limits that guard against abuse with real damage, such as login attempts, SMS sending, or paid third-party calls, where letting everything through is worse than a temporary outage of that one feature.
  • Degrade to local: a middle path. On failure, switch to the local limit (L/N per instance) so you still have approximate protection. Pair it with a short timeout (for example 5 to 20 ms) on the Redis call and a circuit breaker so a slow Redis does not make every request slow.
Watch out A limiter that adds a synchronous network call to every request has made itself part of your availability. Set a tight timeout, decide the failure mode per limit (not globally), and test it by actually killing Redis in staging.

7. Response design and client behaviour

7.1 What to return

When a request is rejected for exceeding a limit, return HTTP status 429 Too Many Requests, not 403 (forbidden) or 500 or 503. 429 tells the client precisely that it is its own rate that is the problem and that retrying later may succeed. (HTTP 503 Service Unavailable is the appropriate status when the whole service is shedding load, section 8, since that is not the caller's fault; it too can carry Retry-After.)

Include a Retry-After header saying when to try again, either as a number of seconds or as an HTTP date. Many APIs also send informational headers so clients can pace themselves before they hit the limit. The names are not fully standardised (an IETF draft defines RateLimit-Limit, RateLimit-Remaining, and RateLimit-Reset; the older X-RateLimit-* forms are widespread):

HTTP/1.1 429 Too Many Requests
Retry-After: 12
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1731800460
Content-Type: application/json

{"error":"rate_limited","message":"Limit of 100 requests per minute exceeded","retry_after_seconds":12}

Send the limit headers on successful responses too, so a well-behaved client sees Remaining shrinking and slows down before being rejected. Be careful about what a rejection reveals: it should say which limit was hit, but not leak internal capacity numbers or information about other users.

7.2 Hard limits, soft limits, and throttling

Not every excess request has to be rejected. A hard limit rejects immediately. A soft limit lets the request through but flags it (and perhaps bills for overage). Throttling (also called delaying or shaping) holds the request briefly in a queue and serves it later, which is the leaky bucket behaviour. Delaying is friendlier for background clients, but it holds a connection and a thread, so it is dangerous for large excesses; always bound the delay and the queue.

7.3 Client behaviour: backoff with jitter

What the client does after a rejection decides whether the system recovers. If every rejected client retries immediately, the rejection itself becomes more load, and the pattern repeats. Good clients use exponential backoff: wait a base delay (say 100 ms), then double after each failure (200, 400, 800 ms...) up to a maximum cap and a maximum number of attempts. If the server sent Retry-After, obey it instead of guessing.

Backoff alone is not enough, because clients that failed at the same moment retry at the same moments (all at 100 ms, then all at 200 ms), producing synchronized waves called a thundering herd. The fix is jitter: randomise each wait. A common recipe, "full jitter", picks a random delay between 0 and the current backoff ceiling: sleep = random(0, min(cap, base * 2^attempt)). This spreads the retries smoothly over time. Retries should also be capped by a retry budget (for example, retries may add at most 10% extra load across the client), and only idempotent requests, or requests carrying an idempotency key, should be retried automatically.

Key idea A rate limit is a contract with two halves. The server must say clearly how much, how fast, and when to come back. The client must slow down, wait with jitter, and stop after a budget. A limiter with unsophisticated clients mostly converts overload into a larger volume of rejected retries.

8. Load shedding and admission control

Rate limits are about identity and fixed allowances. But suppose all callers are within their limits and the database is still struggling, a deploy made a code path slower, or half your instances were lost. Total demand now exceeds actual capacity. No per-caller limit can see this. Load shedding reacts to the system's own condition: it deliberately drops some requests so that the rest finish quickly. Admission control is the gate that makes the decision at the door, before the request consumes resources.

8.1 Why dropping some work is better than doing all of it slowly

Suppose a service can finish 1,000 requests per second but receives 1,500. If it accepts all of them, queues grow without bound. Each request waits longer and longer until the client's timeout (say 2 seconds) expires. The server then finishes work for clients that have already given up, which is wasted effort, and meanwhile clients retry, adding more load. The server's goodput (useful completed work) collapses even though it is 100% busy. If instead it admits only 1,000 per second and rejects 500 immediately, those 1,000 complete fast and successfully, and the 500 rejected callers get a fast signal they can act on. Rejecting is cheaper than accepting and failing.

8.2 Priority classes

Not all requests are equally valuable. Classify them and shed the least important first. A typical scheme: critical (login, payment, health checks, anything blocking a user from completing a purchase), normal (standard interactive reads), low (prefetching, analytics, recommendations refresh), and batch (background jobs, exports). As load rises, the system first rejects batch, then low, then normal, and never rejects critical until the end. Priority must come from a trusted source (set by an upstream gateway or an internal header that clients cannot forge), and the mapping must be simple enough that engineers can reason about it.

8.3 Load signals: queue length, queue delay, and CoDel

The gate needs a signal that the system is overloaded. Options, from simplest to best:

  • CPU or memory usage. Easy to read, but a poor and delayed signal: a service waiting on a slow database can be overloaded with low CPU.
  • Queue length. Count the requests waiting for a worker; if it passes a threshold, reject new ones. Simple, but the right threshold depends on how fast requests are served, so it must be retuned whenever performance changes.
  • Queue delay (sojourn time). Measure how long requests actually wait in the queue. This is the idea behind CoDel (Controlled Delay), an algorithm originally from network routers. It says: a queue that is merely full for a moment (a good queue, absorbing a burst) is fine; a queue where the minimum wait stays above a target (for example 5 ms) for a sustained interval (for example 100 ms) is a bad queue that is not draining, so start dropping. Delay is the thing users feel and the thing that tells you the queue is persistent, so it adapts to speed automatically.
  • LIFO instead of FIFO under overload. When overloaded, serve the newest requests first. The oldest requests have probably already timed out on the client side, so serving them is wasted work. Combine with dropping any request whose deadline has already passed.

Also propagate deadlines: a request carries its remaining time budget downward, and every service drops it immediately if the budget is spent, rather than doing work nobody is waiting for.

8.4 Adaptive concurrency limits

Choosing a fixed queue threshold by hand is fragile, because capacity changes with deploys, data growth, and neighbours. Adaptive concurrency limiting finds the right number of in-flight requests automatically, borrowing ideas from TCP congestion control. The service tracks the latency of requests. The principle (as in Netflix's open-source concurrency-limits library, and Envoy's adaptive concurrency filter) is:

  1. Measure the best-case latency when the service is lightly loaded (the "no-queue" latency).
  2. Allow a limit of N requests in flight at once; excess requests are rejected immediately.
  3. If measured latency stays near the no-queue value, there is spare capacity, so increase N slowly (additive increase).
  4. If latency rises well above the baseline (a queue is forming) or requests time out, decrease N sharply (multiplicative decrease, for example by 10% to 50%).

This is the AIMD pattern: increase gently, back off fast. The limit settles near the true capacity of the service and keeps following it as conditions change, with no hand tuning. Little's law gives the intuition: in-flight requests = throughput x latency. If a server handles 1,000 requests per second at 50 ms, about 50 are in flight; if latency doubles because of a slow dependency, the same cap of 50 in flight automatically halves the admitted throughput, shielding the dependency.

8.5 Graceful degradation

Shedding does not have to mean a blank error. Before rejecting, reduce the cost of serving: return a cached or slightly stale answer, skip optional features (recommendations, personalisation, rich previews), return fewer results, lower image quality, or turn off expensive features through a feature flag (the "brownout" approach). The user gets a simpler but working page, and the system recovers capacity. Design the degraded modes in advance and test them; a fallback written during an incident is rarely correct.

8.6 Where shedding must live

Shed as early and as cheaply as possible. Rejecting after parsing the body, authenticating, and opening a database connection means you have already paid most of the cost. Put the gate at the front of the request pipeline, make the decision with a few in-memory reads, and reject with a tiny pre-built response. Health checks must bypass shedding (or have top priority), otherwise the load balancer may mark an overloaded-but-working instance unhealthy and move its load onto the others, spreading the collapse.

9. Concurrency limits versus rate limits

These are different tools and the difference is a common interview probe.

  • A rate limit bounds how many requests start per unit of time: "100 per second". It does not consider how long each takes.
  • A concurrency limit bounds how many requests are in progress at once: "50 at a time". It does not consider how often they start.

Little's law links them: concurrency = arrival rate x average duration. Suppose requests normally take 50 ms and you allow 100 per second; then concurrency is 100 x 0.05 = 5. Now the database slows and requests take 2 seconds. At the same 100 per second, concurrency becomes 200: the service is flooded with in-flight work, threads and memory run out, yet the rate limiter sees nothing wrong because the rate never changed. A concurrency limit of, say, 50 would have kept the service healthy by rejecting the new requests as soon as 50 were in flight.

Use a rate limit to enforce policy (fairness, plans, abuse) and a concurrency limit to protect resources (threads, connections, memory, a downstream database). A per-dependency bulkhead is a concurrency limit: "at most 20 simultaneous calls to the payment provider". The adaptive concurrency limit of section 8.4 is the self-tuning version. Production services usually have both.

10. Multi-tenant systems and noisy neighbours

In a multi-tenant system, many customers (tenants) share the same servers and databases. A noisy neighbour is a tenant whose heavy use degrades the others: a customer starting a bulk import, a runaway integration, or a tenant hit by their own traffic spike. Isolation is covered fully in Chapter 42; rate limiting is its first and cheapest tool.

10.1 Layered fairness

Apply limits at two levels. A tenant limit caps the whole organization (sized by plan). Inside it, a per-user or per-API-key limit prevents one user from using the whole tenant allowance. On top of those, per-endpoint limits for expensive operations, and a global limit as the ceiling. A tenant exceeding their allowance gets 429s while everyone else is unaffected, which is the core promise of isolation.

10.2 Weighted fair sharing and burst borrowing

Fixed per-tenant caps waste capacity: if only three of ten tenants are active, most capacity sits idle. Better designs allow borrowing: each tenant has a guaranteed share (their reserved floor) and may burst above it when there is spare capacity, but must give it back when others need it. Two common mechanisms are weighted fair queuing (each tenant has a queue and a weight, and workers pick from queues in proportion to weights) and hierarchical token buckets (a parent bucket for the pool, child buckets for tenants with guaranteed and ceiling rates). Under light load everyone is served fully; under pressure, shares are respected.

10.3 Per-resource limits for shared backends

Request rate is a crude measure of a tenant's impact because requests differ in cost. A more accurate approach is to charge a request a cost in tokens proportional to the resources it uses (a simple read costs 1, a search costs 5, a report costs 50, or cost measured as database time consumed), so one bucket limits actual load. For shared databases, add per-tenant limits on concurrent queries, rows scanned, or connections, and consider moving the largest tenants onto dedicated capacity or separate cells so their blast radius is contained.

Interview tip When asked about noisy neighbours, escalate in steps: per-tenant rate limit, then cost-weighted limits, then fair queuing with borrowing, then dedicated pools or cells for the biggest tenants. Mentioning that limits alone do not isolate shared resources like a database buffer cache shows depth.

11. Abuse versus DDoS

Rate limiting and DDoS defense overlap but are not the same. Abuse is misuse of the service by identifiable callers: scrapers, credential-stuffing bots, over-eager integrations. It is bounded by identity, so per-key and per-account limits work well. A DDoS (distributed denial of service) attack uses a huge number of sources to overwhelm capacity, either by sheer bandwidth (volumetric attacks that fill your network links), by exhausting connection state (SYN floods), or by sending many legitimate-looking expensive requests (application-layer attacks such as repeated search queries).

Your application-level limiter cannot stop a volumetric attack: by the time packets reach your gateway, the link is already full. That defense belongs in front of you (a CDN and DDoS-protection provider with large anycast capacity, see Chapter 12), with cheap early filtering and shedding as the last layer. Application-layer floods are the overlap: use per-endpoint limits for expensive routes, challenge suspicious clients (proof of work, CAPTCHAs), prefer cached answers, and use shedding with priorities so authenticated paying customers keep working. The full threat model, WAF rules, and bot management are in Chapter 55.

12. Monitoring and tuning

A limiter you cannot observe is a risk: too tight and you block real customers invisibly; too loose and it protects nothing. Track these:

  • Allowed versus rejected counts, per limit rule, per tenant, per endpoint. A sudden rise in rejections for a large customer is either an attack or a bug in their client, and either way someone should know.
  • Rejection ratio overall. In a healthy system it is a fraction of a percent. A sustained high ratio means limits are wrongly sized.
  • Limiter latency (p50, p99) and Redis health: command latency, memory, evictions (an evicted counter silently forgets a user's usage), connection errors.
  • Fail-open events. Count and alert whenever the limiter could not decide. Silent fail-open means you are unprotected without knowing it.
  • Near-limit usage. The distribution of "percent of limit used" per key shows who is about to be limited, which drives outreach, plan upgrades, and sensible limits.
  • Shedding metrics: in-flight count versus the adaptive limit, queue delay, requests shed by priority class, and goodput.

12.1 Tuning

Start from data, not guesses. Measure the real request distribution per key, and set the limit above the 99th percentile of legitimate use so honest customers are almost never blocked, while still far below what the system can bear. Run a new limit in shadow (log-only) mode first: compute the decision, record "would have rejected", but allow the request. Review who would have been affected, adjust, then enforce. Roll limits out gradually, and give a way to override per customer. Review them regularly, because traffic grows and a limit that was generous a year ago may now block normal usage.

Capacity limits should come from load tests: find the throughput where p99 latency starts to climb sharply (the "knee"), and set the global limit and concurrency cap a safe margin below it, for example at 70-80% of the knee, leaving headroom for a lost instance or zone.

14. Worked sizing example

Scenario: a public REST API for a SaaS product. Peak traffic is 20,000 requests per second across 40 gateway instances (500 per instance on average). There are about 5 million active API keys in a day, with three plans: free (60 requests per minute), pro (600 per minute), and enterprise (6,000 per minute). We want per-key token buckets enforced centrally.

14.1 Memory

One token bucket per key is two numbers (tokens, timestamp) in a Redis hash. With key name, hash overhead, and the TTL, a realistic figure is about 150 bytes per key. For 5 million active keys: 5,000,000 x 150 B = 750 MB. Idle keys expire after about two minutes, so the live set is smaller than the daily count. Even doubled for headroom, this fits comfortably in one node's memory (a few GB).

14.2 Throughput

Each request needs one limiter check, so at peak that is 20,000 Lua calls per second. A single Redis primary can typically handle tens of thousands of such small scripts per second, but it is the cheapest component to be conservative with: running at 20,000 on one node leaves little headroom and has no hot-key protection. Plan 3 shards (hash by key) so each peak runs at about 6,700 operations per second, around a third of a conservative 20,000 per second assumed capacity, with a replica per shard for failover. Add the global limit as its own sharded key (for example 8 sub-counters).

14.3 Latency and the benefit of leases

A same-zone Redis call is typically around 0.3 to 1 ms, so the limiter adds about 1 ms to every request, acceptable against a 50 ms typical API latency, with a 10 ms timeout as a hard bound. Now apply token leasing for enterprise keys, which carry heavy traffic: a lease of 100 tokens means one Redis call per 100 requests. If enterprise keys produce 12,000 of the 20,000 requests per second, Redis calls from them fall from 12,000 to 120 per second, reducing total load from 20,000 to about 8,120 per second. The cost is accuracy: with 40 instances each holding up to 100 unspent leased tokens for a key, overshoot can reach up to 4,000 for that key, which is below the key's 6,000-per-minute allowance and quickly corrected, so it is acceptable for enterprise; free keys use lease size 1 (exact) because their limits are small.

Burst capacity is set to about 6 seconds of the sustained rate for paid plans (so a client can send a short burst after being idle) and a smaller burst for free users. A global ceiling of 25,000 per second (about 1.25x observed peak, below the load-tested knee of about 35,000) sits above these, and each gateway instance enforces a concurrency cap of around 800 in-flight requests, tuned from Little's law: 500 requests per second x 0.05 s typical latency = 25 in flight normally, so 800 is a generous guard rather than a normal constraint.

14.5 Failure behaviour

If Redis is unavailable: free and pro traffic fails open to a local limiter at one fortieth of each key's allowance (good enough to blunt abuse), login and SMS endpoints fail closed, and a fail-open counter pages the on-call engineer if it stays non-zero for more than a minute. Monthly quotas are stored durably in the primary database and updated in batches from aggregated counts, so a Redis flush cannot erase billing data.

15. Interview Q&A

Which rate limiting algorithm would you choose for a public API, and why?

I would choose a token bucket as the default. It has two clear parameters, the refill rate for the long-run average and the capacity for the allowed burst, which matches how real clients behave: quiet for a while, then a quick burst of calls. It needs only two numbers of state per key and is easy to make atomic in Redis with a short Lua script. If the product requirement were a strict "no more than N in any rolling minute" with low memory, I would use a sliding window counter instead, and I would reserve the sliding window log for small, strict limits such as login attempts, where exactness is worth the memory.

What is the problem with a fixed window counter and how do you fix it?

The counter resets sharply at window edges, so a client can send the full allowance at the end of one window and the full allowance again at the start of the next, producing up to twice the intended rate within a short span. The fix is a sliding approach. The sliding window log tracks exact timestamps but is memory heavy. The sliding window counter keeps two counters and weights the previous window by its remaining overlap, giving a close approximation in constant memory. A token bucket also avoids the issue because bursts are bounded by capacity regardless of any boundary.

How would you implement a rate limiter shared by many application servers?

I would keep the counters in a central Redis, keyed by identity such as the API key and the rule. The check must be atomic, so the whole read, refill, decide, and write sequence runs in one Lua script, which prevents two servers from both spending the same last token. Keys carry a TTL so idle ones disappear. To reduce latency and Redis load I could let each server lease batches of tokens, accepting small overshoot. I would put a short timeout and circuit breaker on the Redis call and decide per limit whether to fail open or closed if Redis is unavailable.

What is a race condition in a distributed limiter, and how do you avoid it?

A race happens when two servers read the same counter value, each decides to allow, and each writes back, so both requests pass although only one token remained. Under load this lets many more requests through than the limit. It is a classic read-modify-write problem. The solution is to make the operation atomic, either with a single command such as an increment, or by running the logic in a Lua script, which Redis executes without interleaving other commands. An alternative is optimistic transactions with WATCH, but those retry heavily under contention, so Lua is preferred.

Should a rate limiter fail open or fail closed when its store is down?

It depends on what the limit protects, so I decide per limit. For general API fairness limits I fail open, because rejecting all traffic just because the limiter is broken would turn a safety feature into an outage. For limits guarding costly or dangerous actions, such as password attempts, SMS sending, or paid third-party calls, I fail closed, since unlimited use is worse than a short outage of that feature. A good middle path is to fall back to a coarse local limit on each instance so there is still some protection, and to alert loudly whenever the fallback is active.

What is the difference between a rate limit and a concurrency limit, and when does each matter?

A rate limit bounds how many requests start per unit of time; a concurrency limit bounds how many are in flight at once. They are connected by Little's law: concurrency equals arrival rate times duration. If a dependency slows down, the rate stays constant but concurrency climbs, exhausting threads and memory, and only the concurrency limit notices. So I use rate limits for policy, such as fairness, plans, and abuse, and concurrency limits to protect resources and downstream dependencies. Adaptive concurrency limits tune the number automatically from observed latency.

What is load shedding and how is it different from rate limiting?

Rate limiting enforces a per-caller allowance regardless of how the system is doing. Load shedding reacts to the actual health of the system: when demand exceeds current capacity, it rejects some requests so that the rest complete quickly. This avoids the situation where an overloaded server accepts everything, serves nothing within the client timeout, and wastes effort on requests already abandoned. A good shedder classifies requests by priority and drops batch and low-value traffic first, makes the decision at the very front of the pipeline where it is cheap, and returns a fast 503 with Retry-After.

How do adaptive concurrency limits work?

The service measures request latency and treats the lowest recent latency as the no-queue baseline. It allows N requests in flight and rejects beyond that. While latency stays near baseline it increases N slowly, and when latency rises or timeouts occur it cuts N sharply, in the same additive-increase, multiplicative-decrease pattern as TCP congestion control. The limit converges near the real capacity and follows changes caused by deploys, data growth, or a slow dependency without anyone retuning it. Netflix's concurrency-limits library and Envoy's adaptive concurrency filter are real implementations of the idea.

How do you stop one tenant from degrading everyone else in a multi-tenant system?

I start with per-tenant rate limits sized by plan, plus per-user limits inside each tenant so one user cannot consume the tenant's whole allowance. Because requests differ in cost, I then charge expensive operations more tokens or limit concurrent queries per tenant. To avoid wasting idle capacity I allow borrowing above a guaranteed share through weighted fair queuing or hierarchical token buckets. For the largest or riskiest tenants I move them to dedicated pools or cells to contain the blast radius. Limits alone cannot isolate shared resources like caches, which is why cells matter.

What should a rate limited response look like, and how should clients react?

The server returns 429 Too Many Requests with a Retry-After header, plus limit headers such as the limit, remaining count, and reset time, and a clear error body saying which limit was hit. The client should honour Retry-After, and otherwise use exponential backoff with jitter, for example a random delay between zero and a capped, doubling ceiling, so many clients do not retry in synchronized waves. It should cap the number of attempts, keep a retry budget so retries cannot multiply load, and only auto-retry idempotent operations. Without these, a limiter just converts overload into a storm of retries.

Can application-level rate limiting protect you from a DDoS attack?

Only partly. Per-identity limits work against abuse by a small number of callers, but a DDoS uses thousands of sources, each sending little, so per-IP limits are weak, and volumetric attacks fill your network links before packets even reach your application. The primary defense is in front of the application: a CDN or DDoS provider with large anycast capacity that absorbs and scrubs traffic, plus a WAF. Inside, I add per-endpoint limits for expensive routes, challenges for suspicious clients, cached responses, and priority-based load shedding so important authenticated traffic keeps flowing.

16. Recap

  • Limit for four reasons: abuse, fairness, cost, and protecting dependencies. Rate limiting is a policy on identity; load shedding is a survival reflex on current system health.
  • Layer the limiters: client self-throttling, coarse gateway limits (Chapter 11), precise service limits and concurrency caps, and per-dependency bulkheads.
  • Choose keys carefully (user, API key, tenant, endpoint, IP, global), usually combining several; separate short-window rate limits from long-window quotas; map plans to limits in configuration.
  • Algorithms: fixed window is cheap but has boundary bursts; sliding log is exact but memory heavy; sliding window counter approximates well in two counters; token bucket offers explicit rate and burst and is the default; leaky bucket smooths output; GCRA is a one-number token bucket.
  • Distributed limiting uses a central store with atomic Lua scripts to avoid races, TTLs on every key, and an explicit accuracy-versus-latency choice among central, sticky, leased, and local designs; decide fail-open or fail-closed per limit.
  • Reject with 429 and Retry-After; clients must back off exponentially with jitter and keep a retry budget.
  • Shed load early and cheaply, by priority, using queue delay (CoDel-style) or adaptive concurrency limits; degrade gracefully before rejecting; exempt health checks.
  • Concurrency limits protect resources and respond to slowness (Little's law); rate limits express policy. In multi-tenant systems combine tenant limits, cost weighting, borrowing, and cells (Chapter 42).
  • Application limiters do not stop DDoS; that needs edge absorption (Chapter 55). Monitor rejection ratios and fail-open events, and introduce limits in shadow mode first.
