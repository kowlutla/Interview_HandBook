API Design

An API is the contract between your service and everyone who calls it, and it is the hardest part of a system to change once clients depend on it. This chapter teaches how to model resources, pick methods and status codes, make retries safe, paginate, evolve without breaking clients, handle slow operations, choose between REST, gRPC and GraphQL, and present an API clearly in an interview.

1. Why API design matters

An API (application programming interface) is the set of operations one piece of software offers to another, together with the exact shape of the requests and responses. In this chapter we mostly mean a network API: a client (a mobile app, a browser, another service) sends a message over the network, and a server answers.

Why does the design deserve a whole chapter? Because an API is different from internal code in one crucial way: you do not control the callers. If you rename a function inside your own program, the compiler finds every use and you fix them in one commit. If you rename a field in a public response, every mobile app already installed on a user's phone, every partner integration, and every script somebody wrote three years ago breaks, and you cannot force them to update. An API is therefore a long-lived promise. Good API design is mostly about making promises you can keep for years while the system behind them changes completely.

A good API has these properties:

  • Predictable. Once a developer has seen two or three endpoints, they can guess the fourth. Consistent naming, consistent errors, consistent pagination.
  • Hard to misuse. Retrying a request does not double-charge a customer. Required fields are enforced. Dangerous operations are explicit.
  • Evolvable. You can add features without breaking existing clients.
  • Efficient enough. It does not force a client to make thirty round trips to draw one screen, and it does not ship a megabyte when ten kilobytes would do.
  • Observable and protectable. It reports limits, versions, and errors in a form machines can act on.
Key idea Design the API from the caller's point of view first (what are they trying to accomplish, and what will they retry, cache, and paginate?), and only then map it onto your internal tables and services. An API that mirrors your database schema leaks implementation details that you will later be unable to change.

In an interview, the API is usually the first concrete artifact you produce after requirements and estimation (Chapter 1 and Chapter 2). It forces you to state exactly what the system does, and it exposes the read/write ratio and the data model. Section 16 covers how to present it.

2. REST resource modeling and URL design

REST (Representational State Transfer) is an architectural style for APIs built on HTTP. Most people mean something practical by "REST API": you expose resources (nouns) at URLs, and clients act on them with the standard HTTP methods, exchanging representations (usually JSON). A resource is any thing the API talks about that has an identity: a user, an order, a photo, a payment. A representation is the data describing the current state of that resource at that moment.

Two ideas make this style powerful. First, the verbs are standardized (GET, POST, PUT, PATCH, DELETE), so generic infrastructure such as caches, proxies, gateways and browsers already understands what they mean (see Chapter 10 and Chapter 11). Second, requests are stateless: every request carries everything the server needs, so any server in a pool can handle any request, which is exactly what makes horizontal scaling and load balancing easy (Chapter 9).

2.1 Naming resources

Practical rules that interviewers expect you to follow:

  • Use nouns, not verbs, in the path. The HTTP method is the verb. Write POST /orders, not POST /createOrder.
  • Use plural collection names. /orders is the collection, /orders/8841 is one member. Plural everywhere is more consistent than mixing singular and plural.
  • Use lowercase and hyphens for multiword names (/shipping-addresses). Pick one style and never mix.
  • Nest to express ownership, but only one or two levels. /orders/8841/items says items belong to order 8841. Deeper paths like /users/7/orders/8841/items/3/reviews become awkward; once an item has its own globally unique ID, give it a top-level address too, such as /items/3.
  • Use opaque, stable IDs. Do not expose auto-increment integers if guessing the next one is a security or business leak (competitors can count your orders). UUIDs or time-sortable IDs (Chapter 32) are common.
  • Keep the query string for filtering, sorting, pagination and field selection, not for identity: /orders?status=shipped&sort=-created_at.

2.2 Actions that do not fit CRUD

CRUD (create, read, update, delete) covers most things, but some operations are genuine actions: cancel an order, publish a draft, transfer money, reset a password. There are three accepted ways to model them, in rough order of preference:

  1. Model the action's result as a resource. "Transfer money" creates a transfer: POST /transfers with source, destination and amount. You get an ID, a history, a status, and something to retry safely. This is usually the best answer.
  2. Change state through a field. Cancel an order with PATCH /orders/8841 and body {"status":"cancelled"}. Fine when the state machine is simple, but the server must reject illegal transitions.
  3. Use a sub-resource verb as a last resort. POST /orders/8841/cancel is pragmatic and widely used (Stripe and many others do it). Just be consistent, and use POST because the action is not idempotent by default or has side effects.
Interview tip You will not be penalized for POST /orders/{id}/cancel. You will be penalized for GET /deleteOrder?id=5. Say out loud that you chose the action sub-resource because the operation is a state transition with side effects, and mention you would return the updated order.

2.3 What representations look like

A response should describe the resource with stable field names, include its ID and a timestamp or two, and avoid leaking internals. Use ISO 8601 UTC timestamps (2026-11-17T09:30:00Z), represent money as an integer amount of the smallest unit plus a currency code ({"amount":1999,"currency":"USD"}) because floating point cannot represent decimal money exactly, and use strings for large identifiers because JavaScript numbers lose precision above 2^53. Choose one casing convention (snake_case or camelCase) for JSON field names and keep it everywhere.

GET /orders/8841
200 OK
{
  "id": "ord_8841",
  "status": "shipped",
  "total": {"amount": 4599, "currency": "USD"},
  "created_at": "2026-11-17T09:30:00Z",
  "customer": {"id": "usr_17", "href": "/users/usr_17"},
  "items_href": "/orders/ord_8841/items"
}

3. HTTP methods, safety and idempotency

Every HTTP request has a method that says what the client wants. Two properties of methods matter enormously for system design, so define them carefully.

  • A method is safe if it does not change server state in a way the client is responsible for. Reading is safe. Safe methods can be freely prefetched, cached, and retried by crawlers, browsers and proxies.
  • A method is idempotent if making the same request once or many times leaves the server in the same final state. The response may differ (a second DELETE of the same order may return 404 instead of 204), but the effect on the data is the same. Idempotency is what makes retries safe. Networks drop replies, so a client that sent a request and got a timeout does not know whether it was executed; if the method is idempotent it can simply resend.

HEADSame as GET but headers only (check existence, size, ETag)YesYesYes
OPTIONSAsk what is allowed (CORS preflight)YesYesNo
PUTReplace the whole resource at a known URL (or create it there)NoYesNo
DELETERemove the resourceNoYesNo
PATCHPartially modify a resourceNoNot guaranteedNo
POSTCreate a member in a collection, or run an actionNoNoRarely

3.1 The distinctions that cause bugs

PUT versus PATCH. PUT sends the complete new representation; fields you omit are treated as removed or reset. That makes it naturally idempotent: sending the same full document ten times gives the same state. PATCH sends only the changes. A patch such as {"nickname":"Sam"} is idempotent, but a patch described as an operation, such as {"op":"increment","field":"likes"}, is not. Two standard patch formats exist: JSON Merge Patch (send a partial object, null removes a field) and JSON Patch (a list of explicit operations). Merge patch is simpler; JSON Patch is more precise for arrays.

POST versus PUT for creation. If the server chooses the ID, use POST /orders and return 201 Created with a Location: /orders/8841 header. If the client chooses the ID (for example a client-generated UUID), PUT /orders/{client-id} is idempotent create-or-replace, which is a clean way to get retry safety without a separate key.

DELETE idempotency. The first DELETE removes the item and returns 204. The second finds nothing; returning 404 or 204 are both defensible. What matters is the end state: the item is gone. Idempotent describes the state, not the status code.

Watch out Never perform state changes on GET. Link prefetchers, browser extensions and web crawlers follow GET links freely, so a "delete" link that is a GET will eventually be triggered by a robot. Also, GET requests are logged in proxies and browser history, so do not put secrets in the URL query string.

4. Status codes

The status code is a three digit number in the response that tells the client, in a machine readable way, what happened. The first digit gives the class. Using the right code matters because clients, gateways, retry libraries, monitors and browsers all make decisions on it without reading your body: retry a 503 but not a 400, cache a 200 but not a 500, alert on 5xx rates.

The practical rule for retries: 4xx means "your request is wrong, do not just resend it" (with 408, 409 in some cases, and 429 as exceptions that are worth retrying after a delay), while 5xx means "my fault, a retry may work". A client library can apply this rule without knowing anything about your domain, but only if you use the codes honestly. Returning 200 OK with {"error":"not found"} in the body defeats every monitor, cache and retry policy in between, and is a common mistake.

5. Idempotency keys for POST

POST is not idempotent, and POST is exactly the method used for the operations where duplicates hurt most: charge a card, place an order, send an email. Consider this timeline. A mobile app sends POST /payments. The server charges the card and writes the row, but the response is lost because the phone entered a tunnel. The app sees a timeout. It cannot tell whether the charge happened. If it retries blindly the customer may be charged twice; if it does not retry, the customer may have paid for nothing.

The fix is an idempotency key: a unique value the client generates for each logical operation and sends in a header, conventionally Idempotency-Key: 7c9e6679-... (a random UUID). The server records the key together with the result of the first request. If the same key arrives again, the server does not execute the operation again; it returns the stored result. Now the client may retry as many times as it likes, and the effect happens exactly once.

5.1 What the server must get right

  • Atomic claim. Two retries can arrive at the same moment (a client timeout plus an impatient user double-tap). The key must be claimed with a unique constraint or a compare-and-set so only one request proceeds. The loser either waits for the winner or gets 409 Conflict saying "a request with this key is in progress".
  • Store the response, status code and body, not only a "seen" flag, so the retry returns the same answer.
  • Bind the key to the request. Save a hash of the request body. If a key reappears with a different body, that is a client bug; reject it rather than silently replaying an unrelated result.
  • Scope the key to the authenticated customer so one tenant cannot collide with or read another's.
  • Expire keys after a window (commonly 24 hours to a few days), because the table would grow forever. The window must exceed the longest retry horizon of any client.
  • Make the side effect and the key record commit together. If you charge the card and then crash before saving the result under the key, a retry will charge again. Ideally write the business row and the key row in one database transaction, and pass the same key downstream to external providers that support it.

The deeper treatment, including deduplication in message consumers and ID generation, lives in Chapter 32. For the API, the one-line summary is: PUT, DELETE and GET are idempotent by definition, and for POST you add an idempotency key. Clients should generate the key once per logical operation and reuse it on every retry of that operation, and use exponential backoff with jitter between retries.

Good pattern Let the client generate the resource ID (a UUID) and use PUT /payments/{uuid}. The URL itself is the idempotency key, with no extra header and no separate key table.

6.1 Content negotiation

Content negotiation lets one URL serve different representations of the same resource. The client states what it can handle with Accept (for example Accept: application/json, or Accept: application/xml;q=0.5, application/json where q is a preference weight). The server picks the best match, labels it with Content-Type, or answers 406 Not Acceptable when it cannot satisfy the request. The same mechanism handles compression (Accept-Encoding: gzip) and language. If a cache sits in between, the response must carry Vary: Accept (or the relevant header) so the cache stores separate copies per variant; forgetting Vary is a classic source of one user receiving another's format.

Some APIs also use content negotiation for versioning (Accept: application/vnd.example.v2+json); see section 9.

6.2 Conditional requests and ETags

An ETag (entity tag) is an opaque string the server attaches to a representation that changes whenever the content changes, such as a hash of the body or a row version number. It enables two valuable behaviors.

Conditional reads save bandwidth. The client caches a response along with its ETag. Next time it sends GET /orders/8841 with If-None-Match: "v17". If the resource is unchanged the server replies 304 Not Modified with no body; the client reuses its copy. The server still did a lookup, but the payload (often the expensive part on a mobile network) is not sent.

Conditional writes prevent lost updates. Two people open the same document. Alice saves, then Bob saves, silently overwriting Alice's work because Bob started from the old version. With optimistic concurrency, Bob's PUT includes If-Match: "v17". The server compares the current version; if it is now "v18" (Alice's save), it rejects Bob with 412 Precondition Failed, and the client must re-fetch, merge, and retry. This is the HTTP form of the compare-and-set idea used throughout distributed systems (Chapter 31), and it needs no locks held across user think time. Requiring it for risky resources by returning 428 when the header is missing is a good defensive design.

7. Pagination

A collection endpoint such as GET /orders might match ten million rows. Returning them all would exhaust memory, saturate the network and time out. Pagination returns the collection in bounded slices, and the design of the slicing has real consequences for correctness and performance. Always set a default page size and a hard maximum (for example default 20, max 100) so no client can request everything at once.

7.1 Offset pagination

The simplest scheme: GET /orders?offset=40&limit=20 (or page=3&per_page=20, which is the same idea with offset = (page-1) x per_page). In SQL: SELECT ... ORDER BY created_at DESC LIMIT 20 OFFSET 40.

Strengths: trivial to implement, supports jumping to an arbitrary page ("go to page 17"), and easily returns a total count so UIs can draw page numbers.

Weaknesses, and they are serious at scale:

  • Cost grows with the offset. The database cannot jump to row 1,000,000; it must walk past (read and discard) the first million rows before returning your 20. Deep pages become slow, and a crawler walking all pages performs quadratic total work.
  • Unstable under writes. If a new row is inserted at the top while a user reads page 1 and then requests page 2, every row shifts down by one, so the last row of page 1 appears again as the first row of page 2 (a duplicate). If a row is deleted, one row is skipped entirely. For feeds that change constantly this is visible and annoying.
  • Total counts are expensive. COUNT(*) over a large filtered set can be slow; many large APIs omit or approximate it.

7.2 Keyset (seek) pagination

Instead of "skip N rows", keyset pagination says "give me rows that come after the last one I saw". The client sends the sort key of the last item: GET /orders?limit=20&after_created_at=2026-11-17T09:30:00Z&after_id=8841. In SQL: WHERE (created_at, id) < (:ts, :id) ORDER BY created_at DESC, id DESC LIMIT 20. With an index on (created_at, id) the database seeks straight to that position in the B-tree, so page 1 and page 100,000 cost the same (Chapter 18).

Two details are essential. First, the sort key must be unique and totally ordered; sorting by created_at alone fails when two rows share a timestamp, so always append a tiebreaker such as the primary key. Second, because the position is anchored to a value, not a row count, inserts and deletes elsewhere do not cause duplicates or skips. The tradeoff: you cannot jump to "page 17", only go next (and, with a reverse query, previous), and sorting by arbitrary user chosen columns requires an index for each supported sort.

7.3 Cursor pagination

Cursor pagination is keyset pagination with the position hidden inside an opaque token. The response includes "next_cursor": "eyJ0cyI6..." (typically base64 of the last key, sometimes signed or encrypted), and the client simply passes ?cursor=eyJ0cyI6... back. Because the token is opaque, clients cannot depend on its structure, so you can change the underlying implementation later (switch the sort key, add shard information, even move from keyset to a search engine's scroll mechanism) without breaking anyone. The cursor can also embed the filter and sort parameters so a client cannot accidentally change them mid-iteration.

GET /orders?limit=2&status=shipped
200 OK
{
  "data": [ {"id":"ord_9"}, {"id":"ord_8"} ],
  "page": { "next_cursor": "b3JkXzg6MjAyNi0xMS0xNw", "has_more": true }
}
GET /orders?limit=2&status=shipped&cursor=b3JkXzg6MjAyNi0xMS0xNw

Cursors are the default in most large public APIs (Slack, Stripe, GitHub's GraphQL, and others). Page links in a Link header (rel="next") are an HTTP-native way to deliver the same thing.

Interview tip Default to cursor pagination for anything feed-like or unbounded, and say why: stable under inserts and constant cost per page. Mention you would offer offset only on small admin views that truly need page numbers. Also mention the response shape: items, next_cursor, and has_more.

8. Filtering, sorting and field selection

Collections need ways to narrow, order, and trim what is returned. Keep these in the query string and make them predictable.

8.1 Filtering

The simplest style is one parameter per field: GET /orders?status=shipped&customer_id=usr_17. For ranges, use suffixes or bracket operators, such as created_after=2026-11-01 and created_before=2026-11-30, or created_at[gte]=.... Resist inventing a full query language unless you truly need one, because each operator you expose is a promise to keep supporting and to keep indexed. Every filter you allow must be backed by an index, otherwise one client's innocent filter becomes a full table scan that harms everyone. Validate and reject unknown parameters with 400 instead of silently ignoring them, so a typo does not return unfiltered data.

8.2 Sorting

A common convention is sort=created_at ascending and sort=-created_at descending, with commas for multiple keys (sort=-priority,created_at). Only allow sorts that you have indexed, and always add the unique ID as the final tiebreaker so ordering is deterministic and works with cursors (section 7).

8.3 Field selection and expansion

Different clients need different amounts of data. Sparse fieldsets let the client ask for only some fields: GET /users/7?fields=id,name,avatar_url. The opposite need is to avoid extra round trips for related data: expansion (GET /orders/8841?expand=customer,items) embeds the related resources instead of just IDs or links. Both are partial answers to the over-fetching and under-fetching problems that GraphQL (section 14) solves more thoroughly. Cap the expansion depth, otherwise a single request can fan out into an enormous query.

8.4 Search

Free-text search (GET /products?q=red+shoes) is usually backed by a search engine rather than your primary database (Chapter 22); treat it as filtering with relevance sorting, which makes strict cursor semantics harder, so document what guarantees you give.

9. Versioning and backward-compatible evolution

Requirements change, so the API must too. The goal is to change it without breaking existing clients. Think of two kinds of change.

9.1 Compatible (additive) changes

These are safe to make in place, with no new version, provided clients follow the tolerant reader rule (ignore fields they do not recognize):

  • Adding a new optional request field with a sensible default.
  • Adding a new field to a response.
  • Adding a new endpoint or a new optional query parameter.
  • Adding a new value to an enum only if you documented from day one that clients must handle unknown values.

9.2 Breaking changes

These need a new version, or a long deprecation process:

  • Removing or renaming a field, or changing its type or meaning (for example seconds to milliseconds).
  • Making an optional request field required, or tightening validation.
  • Changing the status code or error shape for a case.
  • Changing default behavior, such as default sort order or page size.
  • Changing pagination or authentication schemes.

9.3 Versioning strategies

The pragmatic answer in interviews: major version in the URL path (/v1), reserved for genuine breaking changes, with everything else evolved additively inside a version. Keep the number of live major versions small (one or two) because every version is code you must maintain, test and secure.

9.4 Deprecation process

Retiring a version or field is a communication problem as much as a technical one: announce a date, add a Deprecation and Sunset header to responses (standard headers for this purpose) pointing to migration docs, measure which clients still call the old version by logging a client ID or user agent, contact them directly, run brownouts (brief scheduled failures) to flush out forgotten callers, and only then return 410 Gone. Never remove something that your metrics still show in use by paying customers without a plan.

Watch out Mobile apps are the hardest clients: old versions of an app stay installed for years because users do not update. Plan to support old API versions for as long as the oldest app version you cannot force-upgrade, and build a minimum-version check ("please update") into the app from the first release.

10. Error contract, authentication and rate-limit headers

10.1 A consistent error contract

Errors are part of the API, and callers write code against them. Use the right HTTP status (section 4) and a consistent machine-readable body for every error, from every endpoint. The standard format is Problem Details for HTTP APIs (application/problem+json); the useful shape is as follows.

HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json
{
  "type": "https://api.example.com/errors/validation-failed",
  "title": "Validation failed",
  "status": 422,
  "code": "validation_failed",
  "detail": "2 fields are invalid.",
  "request_id": "req_5f2a9c",
  "errors": [
    {"field": "email", "code": "invalid_format", "message": "Not a valid email address"},
    {"field": "quantity", "code": "out_of_range", "message": "Must be between 1 and 100"}
  ]
}
  • A stable, documented error code that programs switch on. The human message may change or be translated; the code must not.
  • A request ID echoed in the body and a response header, so a customer can quote it to support and you can find the trace.
  • Field-level details for validation, listing all problems at once rather than one per round trip.
  • No internals. Never return stack traces, SQL, host names or library versions. For 5xx, log the details server-side and return a generic message plus the request ID.
  • Say whether it is retryable. The status class tells most of it; some APIs add "retryable": true.
  • Be careful about information leaks. Returning 403 versus 404 for a resource the caller may not see can reveal whether it exists; for sensitive resources return 404 to both.

10.2 Authentication and authorization at a high level

Authentication answers "who are you?" and authorization answers "what are you allowed to do?". At the API level the common mechanisms are:

  • API keys: a long random secret in a header, identifying an application or account. Simple, good for server-to-server calls, but a leaked key works until revoked, and keys carry no user identity or fine scopes unless you add them.
  • Bearer tokens (OAuth 2.0 access tokens) in Authorization: Bearer ...: short-lived tokens issued by an authorization server, carrying a user, a client, and scopes (for example orders:read). They are often JWTs (signed JSON tokens) that a gateway can validate without calling a database. A refresh token obtains new access tokens, and revocation is the hard part of JWTs.
  • Mutual TLS: both sides present certificates; common between internal services and in the service mesh (Chapter 50).
  • Signed requests (HMAC over method, path, body and timestamp): used for webhooks and some cloud APIs, and protects against tampering and replay.

Always use HTTPS, never put credentials in URLs, and perform authorization on the server for every object access, not just at the login step: the classic vulnerability is a user changing /orders/8841 to /orders/8842 and reading someone else's order (broken object level authorization). Typically the gateway authenticates and rejects obviously invalid tokens (Chapter 11), while the service decides whether this principal may touch this specific object. Token formats, OAuth flows, key management and threat modeling are covered in Chapter 55.

10.3 Rate-limit headers

Rate limiting protects the service from overload and abuse and gives each client a fair share (the algorithms, such as token bucket, and where to enforce them are in Chapter 16). The API's job is to communicate the limit so well behaved clients can slow down before they are rejected:

HTTP/1.1 200 OK
RateLimit-Limit: 100
RateLimit-Remaining: 12
RateLimit-Reset: 30

HTTP/1.1 429 Too Many Requests
Retry-After: 30
Content-Type: application/problem+json

Here the limit is 100 requests per window, 12 remain, and the window resets in 30 seconds. (The names have been used with an X- prefix for years, and a standard for unprefixed RateLimit-* fields is being finalized, so say "typically".) When the limit is exceeded, return 429 with Retry-After, and make clients respect it with exponential backoff and jitter so that a thousand throttled clients do not all retry at the same instant. Limits are usually keyed per API key or user, sometimes per endpoint cost, and the response should say which limit was hit.

11. Long-running operations and webhooks

Some operations cannot finish within a normal request timeout (commonly 30 to 60 seconds, and gateways and mobile networks cut connections sooner): generating a large report, transcoding a video, importing a million rows, provisioning a server. Holding the connection open ties up server threads and fails whenever the network blinks. The standard answer is to make the API asynchronous: accept the work, return immediately, and let the client learn the result later.

11.1 The 202 Accepted plus status resource pattern

The client sends POST /reports. The server validates the request, enqueues a job on a queue (Chapter 34), and responds right away with 202 Accepted and a pointer to a status resource: Location: /jobs/job_77. The client then reads GET /jobs/job_77, which returns the state (queued, running, succeeded, failed), a progress number, and, when finished, a link to the result (/reports/rep_12) or an error object. Some APIs answer the finished status with a 303 See Other redirect to the result. A job resource can also support DELETE /jobs/job_77 to cancel. The status resource itself is cheap and cacheable for a short time.

Polling is simple and works through every firewall, but it creates wasted requests and a delay up to the polling interval. Good practice: return Retry-After (or a suggested interval) in the status response and let clients back off. For very long jobs, polling every few seconds across millions of clients is real load, which motivates webhooks.

11.2 Webhooks

A webhook is a reverse API call: instead of the client asking "is it done?", your server sends an HTTP POST to a URL the client registered, carrying an event such as payment.succeeded. Webhooks suit events whose timing the client cannot predict. Delivery is hard to get right, because you are now the client of an unreliable server you do not control. A production design has these parts:

  • Signature. Anyone can POST to the client's public URL, so the receiver must verify the event is really from you. Compute an HMAC (a keyed hash) of the raw body plus a timestamp using a per-endpoint secret, and send it in a header such as Webhook-Signature: t=1731835800,v1=ab12.... The receiver recomputes it, compares in constant time, and rejects timestamps older than a few minutes to block replay of captured requests. Rotating secrets should allow two valid signatures during the overlap.
  • At-least-once delivery with retries. The receiver might be down or slow. Treat any non-2xx response or a timeout (use a short one, perhaps 5 to 10 seconds) as failure and retry with exponential backoff and jitter over hours or days (for example 1 minute, 5 minutes, 30 minutes, 2 hours, and so on). After a final failure, move the event to a dead-letter store, mark the endpoint unhealthy, and notify the owner. Disable endpoints that fail for days.
  • Idempotent consumers. At-least-once means duplicates happen. Every event carries a unique, stable id; the receiver stores processed IDs and skips repeats. Events may also arrive out of order, so include a timestamp or sequence number and design handlers so that later state wins.
  • Respond fast, process later. The receiver should verify, persist the event, return 200 immediately, and handle the work from its own queue, otherwise slow handling triggers needless retries.
  • Thin or fat payloads. A "thin" event contains only the type and resource ID, and the receiver calls the API to fetch the current state (safer, avoids stale data and large payloads). A "fat" event embeds the data (fewer round trips, but can be stale or out of order).
  • Operator tools. A delivery log with replay, a "send test event" button, and a way to list recent failures turn a support nightmare into self service.

Reliable event delivery inside your own system (outbox pattern, brokers, ordering) is covered in Chapter 35 and Chapter 36; a webhook is that same pattern pushed over the public internet. If clients need a live stream rather than discrete events, see Chapter 6.

12. Bulk and batch endpoints

Making one call per item is fine for ten items and terrible for ten thousand: each call pays network latency, authentication, and rate-limit budget. Batch endpoints accept many operations in one request: POST /orders:batchCreate or POST /orders/batch with a list. The key design questions are:

  • Atomic or partial? All-or-nothing is simple to reason about but one bad item fails everything and requires a transaction across items (hard if they span shards). Partial success is more practical for large batches. The response must then report a result per item.
  • Status code with partial failure. Return 200 OK (or 207 Multi-Status) with an array where each element has its own status, ID and error; the top-level status says the batch itself was processed, not that every item succeeded. Preserve request order, or echo a client-supplied reference ID per item so results can be matched.
  • Size limits. Cap items per batch (for example 100 or 1000) and total payload bytes, and document them.
  • Idempotency. One idempotency key for the whole batch, plus per-item client IDs so a retried batch does not create duplicates.
  • Rate limits. Charge the batch by the number of items, otherwise batching becomes a loophole around the limit.
  • Very large bulk loads (millions of rows) should not be a request body at all: return a pre-signed upload URL for object storage (Chapter 21), then start an async import job (section 11) that reads the file and reports progress and a downloadable error report.
POST /orders/batch
{ "items": [ {"ref":"a","sku":"S1","qty":2}, {"ref":"b","sku":"S2","qty":0} ] }

{ "results": [
  {"ref":"a","status":201,"id":"ord_91"},

13. gRPC

gRPC is a remote procedure call framework originally from Google. Instead of resources and verbs, you define services with methods, and the client calls them like local functions: orderService.GetOrder(request). It runs over HTTP/2 and encodes messages with Protocol Buffers (protobuf), a compact binary format (see Chapter 7; HTTP/2 itself is in Chapter 3).

13.1 Protobuf and the contract

You write a .proto file that is the single source of truth: it declares messages (typed structures) and services. Code generators produce client stubs and server skeletons in many languages, so a Go service and a Java service share a type-checked contract with no hand-written parsing.

syntax = "proto3";
service OrderService {
  rpc GetOrder (GetOrderRequest) returns (Order);                    // unary
  rpc ListOrders (ListOrdersRequest) returns (stream Order);         // server streaming
  rpc UploadEvents (stream Event) returns (UploadSummary);           // client streaming
  rpc Chat (stream ChatMsg) returns (stream ChatMsg);                // bidirectional
}
message Order {
  string id = 1;
  int64 total_cents = 2;
  string currency = 3;
  repeated string item_ids = 4;
}

Each field has a number (the tag), and the wire format identifies fields by number, not name. That is what makes protobuf evolvable: you can add new fields with new numbers, and old readers ignore them; old writers simply omit them and readers see defaults. The rules for safe evolution are to never reuse or renumber a field, never change a field's type incompatibly, and mark removed fields as reserved. Messages are typically 3 to 10 times smaller than the equivalent JSON, and parsing is much cheaper, because there are no field name strings and numbers are varint-encoded.

13.2 The four call types

  • Unary: one request, one response. Most calls.
  • Server streaming: the client sends one request and reads a stream: a large result set delivered incrementally, or a feed of updates (stock prices).
  • Client streaming: the client sends a stream and gets one reply: uploading a long series of sensor readings or file chunks, answered with a summary.
  • Bidirectional streaming: both sides send independently over one open call: chat, collaborative editing, a long-lived control channel.

13.3 Deadlines, cancellation and errors

gRPC treats time limits as a first-class part of every call. The client sets a deadline (an absolute point in time by which the answer must arrive), and gRPC propagates the remaining time to the server and onward to every downstream call the server makes. When the deadline passes, the call is cancelled everywhere, so servers stop doing work nobody is waiting for. This is the correct way to prevent a slow dependency from piling up threads (Chapter 40, Chapter 51). Set deadlines on every call; the default in many libraries is "wait forever", which is a bug waiting to happen. gRPC also has its own status codes (OK, INVALID_ARGUMENT, NOT_FOUND, DEADLINE_EXCEEDED, UNAVAILABLE, PERMISSION_DENIED, and so on) which map roughly to HTTP ones, plus trailing metadata for rich error details.

13.4 Operational considerations

  • Load balancing. gRPC multiplexes many calls over one long-lived HTTP/2 connection, so a plain connection-level (layer 4) load balancer sends all of one client's traffic to one backend. You need request-level balancing, either a layer 7 proxy that understands HTTP/2 or client-side balancing with a service mesh (Chapter 9, Chapter 50).
  • Browsers. Browsers cannot use raw gRPC because they do not expose HTTP/2 trailers and framing control. gRPC-Web, usually through a proxy, or a REST/JSON gateway generated from the same proto, bridges this.
  • Debuggability. Binary payloads cannot be read with curl and a text editor; you need tools (grpcurl, reflection) and good logging.
  • Retries. Retry only idempotent methods, and use hedging and retry budgets sparingly. Streaming retries are complicated.

When to choose gRPC: internal service-to-service calls where latency, throughput and a strongly typed contract matter; polyglot microservice fleets; streaming needs; mobile clients that benefit from small payloads (with care). When not to: public APIs for unknown third parties, browser-first products, or when you need HTTP caching and human friendly debugging.

14. GraphQL

GraphQL is a query language and runtime for APIs, created at Facebook. Instead of many endpoints each returning a fixed shape, there is usually one endpoint (POST /graphql) and the client sends a query describing exactly the data it wants, and receives exactly that. It was designed to fix two problems with fixed REST endpoints. Over-fetching: GET /users/7 returns forty fields when a list item needs three. Under-fetching: drawing one screen needs the user, their orders, and each order's items, which takes several round trips (a particular pain on slow mobile networks).

14.1 Schema, queries and resolvers

The schema is a strongly typed description of everything that can be asked: object types, their fields, and the entry points (Query for reads, Mutation for writes, Subscription for streams of events). It is the contract, and tools use it for validation, documentation and code generation.

type User  { id: ID!  name: String!  orders(first: Int): [Order!]! }
type Order { id: ID!  total: Int!  items: [Item!]! }
type Query { user(id: ID!): User }

query {                       # client asks for exactly this shape
  user(id: "7") {
    name
    orders(first: 2) { id total }
  }
}

Each field in the schema is backed by a resolver, a function that knows how to fetch that field's value (from a database, another service, a cache). The server executes the query by walking the tree: it calls the resolver for user, then for each requested sub-field, calling the resolver of orders for that user, and so on. Resolvers are independent, composable, and can each call a different backend, which is why GraphQL is popular as an aggregation layer in front of many services (a "backend for frontend").

14.2 The N+1 problem and DataLoader

Resolver-by-resolver execution has a classic trap. Suppose a query asks for 50 orders and the customer name on each. The orders resolver runs one query returning 50 rows (that is the "1"). Then the customer resolver runs once per order, issuing 50 separate lookups (the "N"). That is 51 database calls where 2 would do, and with nesting it multiplies further.

The standard fix is DataLoader style batching. Each resolver, instead of querying immediately, asks the loader for key customer_id=17. The loader collects every key requested during the same tick of execution, de-duplicates them, and issues one batched query (WHERE id IN (17, 22, 31, ...)), then hands each resolver its own row. It also caches per request so the same customer is fetched once.

14.3 Costs and difficulties

  • Caching is harder. REST gets HTTP caching, CDNs and ETags for free because each URL names a resource and GET is cacheable. GraphQL sends different query bodies to one URL, usually by POST, so URL-based caches do not help. Options: persisted queries (the client sends a short hash of a pre-registered query, which allows GET and CDN caching), client-side normalized caches keyed by type and ID (as in Apollo or Relay), and server-side caching per resolver or per entity.
  • Unbounded queries. A client can ask for deeply nested or enormous results: user { friends { friends { friends { ... } } } }. Defences: a depth limit, query cost analysis (assign each field a cost, multiply by list sizes from first: arguments, reject queries above a budget, and also rate limit by cost rather than request count), required pagination arguments with maximums, a request timeout, and an allow-list of persisted queries for public clients. Disable or restrict schema introspection in production if the schema is sensitive.
  • Errors. GraphQL typically returns HTTP 200 even for errors, with an errors array and possibly partial data. Monitoring by HTTP status no longer works, so you must monitor the error array and per-field metrics.
  • Authorization is per field, in every resolver, which is easy to miss. Centralize it.
  • File upload, and rate limiting need extra thought, and performance debugging is harder because a single endpoint hides which query shapes are slow.
  • Schema evolution is gentler than REST: add fields freely, mark old ones @deprecated, and observe field-level usage before removing. This is why many teams run GraphQL without versions.

15.1 Designing for mobile and low bandwidth

Mobile clients have high latency, variable and expensive bandwidth, limited battery, and connections that drop whenever the user enters an elevator. The API should account for that:

  • Fewer round trips. Each request on cellular may cost 100 to 500 ms. Provide screen-shaped endpoints (a "backend for frontend"), expansion, batch endpoints, or GraphQL so one screen needs one or two calls.
  • Smaller payloads. Enable gzip or Brotli compression, use field selection, return thumbnails with explicit sizes, and consider protobuf or other binary formats. Do not send the entire object when a list row needs three fields.
  • Aggressive, correct caching. Use ETags and 304 so revalidation is nearly free, and Cache-Control for static data. Serve images through a CDN (Chapter 12).
  • Cursor pagination with small pages that match what fits on screen, so infinite scroll loads progressively.
  • Retry safety. Idempotency keys on every mutation, because mobile networks drop responses constantly. The app should queue writes offline and replay them with the same keys.
  • Delta sync. For data that changes slowly, let the client send "give me changes since token T" and receive only the differences, with deletions as tombstones.
  • Push instead of poll. Use push notifications or a held-open connection for updates, because polling drains battery (Chapter 6).
  • Tolerant versioning. Old app versions live for years (section 9.4). Never assume the latest client; send a minimum-supported-version signal.
  • Resumable large transfers. Use range requests or chunked, resumable uploads so a dropped connection does not restart a 200 MB video upload.

Cost, privacy and device considerations that go beyond the wire format are in Chapter 56.

16. Designing APIs in an interview

When an interviewer says "design a ride-sharing app" or "design Twitter", they expect you to define the interface early, but concisely. The aim is to show you understand the core entities and the operations on them, not to write complete OpenAPI documents. A reliable procedure:

  1. Restate the functional requirements as verbs the user performs (post a tweet, follow a user, read the home timeline).
  2. Name the core resources (nouns): users, tweets, follows, timeline.
  3. List one endpoint per requirement with method, path, key parameters and the response shape. A short table or a list is ideal.
  4. Annotate the interesting parts only: which calls are paginated (and how), which need idempotency keys, which are async, which are the hot read path, and which require authentication. This is where your judgment shows.
  5. Choose the protocol with a sentence of justification ("REST for the public API, gRPC between internal services").
  6. Connect it to the rest of the design. The read endpoint determines the caching strategy, the write endpoint determines the queue, the pagination style determines the index.
Interview tip Spend two or three minutes on the API, not ten. Write the endpoints on the board in the form POST /v1/tweets {text} and move on. Say "I will use cursor pagination for the timeline because it is a high-churn feed" in one breath. Do not list every CRUD endpoint for every entity; show the five that drive the design and say the rest are analogous. If the interviewer cares about a detail, they will ask.

Things interviewers listen for: you identify the client identity from the auth token and never take user_id from the request body for authorization; you put idempotency keys on payments and order placement; you mention pagination on every list; you flag async for slow work; you consider rate limits and abuse; and you can explain how the API evolves. Avoid these anti-patterns: verbs in URLs for plain CRUD, 200 OK with an error body, unbounded list responses, exposing database IDs and internal column names, one giant endpoint that does everything, and tight coupling of response shape to table schema.

17. Worked example: the API for a small ticketing service

Let us design the API for TicketHub, a small service where customers browse events, reserve seats, pay, and receive tickets. The numbers are modest: 2 million registered users, about 500 events live at a time, peak of 20,000 requests per second when a popular event goes on sale, of which about 90 percent are reads. Mostly mobile clients, plus a public partner API.

17.1 Resources and requirements

Requirements as verbs: search and view events, view seat availability, hold seats briefly, pay for the hold, view my tickets, cancel an order, and get notified about changes. Resources: events, seats (sub-resource of an event), holds, orders (with payment), tickets, and webhook-endpoints for partners.

17.3 Why each decision

  • Seat availability polling is the hot path. 90 percent of 20,000 requests per second is 18,000 reads per second on seats. A 3 second cache shared at the edge collapses those to a few hundred origin requests per second per event. The price is that a displayed seat may already be taken, which is acceptable because the authoritative check is the hold request, which returns 409 if the seat is gone. The UI handles 409 gracefully.
  • Holds, not locks. A hold is a resource with an expiry, which maps cleanly to REST and avoids long-lived locks. The seat service uses an atomic conditional update, and a background job releases expired holds.
  • Idempotency keys on POST /holds and POST /orders. A user on a train tunnel taps "Pay" twice. The order service claims the key atomically, so one order is created and one charge is issued, and the second tap returns the stored response.
  • 202 for orders. The payment provider may take several seconds, so the API returns 202 and a status URL. The app polls every 2 seconds with Retry-After guidance, and the server also sends push and webhook events so partners need not poll.
  • Cursor pagination for events and tickets, because new events arrive constantly and users scroll on mobile. Page size 20 with a hard maximum of 100.
  • Errors use one problem+json shape with stable codes such as seat_unavailable, hold_expired, payment_declined, plus a request ID.
  • Rate limits per API key and per user: for example 100 requests per minute for ordinary clients, lower for POST /holds to blunt scalper bots, with RateLimit-* headers and 429 plus Retry-After (Chapter 16).
  • Versioning by /v1 path, additive evolution inside it, and Sunset headers when v2 arrives.
  • Protocol choice. REST and JSON for the public and mobile API (cacheable, easy for partners). gRPC internally between the gateway, seat, and order services where latency matters. GraphQL is not needed here; if the mobile team later wants one-call screens, add a BFF.

Sample failure walk-through: the user taps Pay. The app sends POST /v1/orders with key K. The order service inserts K, calls the payment provider (passing K as the provider's own idempotency key), and the provider times out. The service marks the order pending and returns 202. The app polls GET /v1/orders/ord_5 and sees pending. A reconciliation job later asks the provider about K, learns the charge succeeded, sets paid, issues tickets and emits order.paid. The user and the partner are both told, nothing was charged twice, and the user was never left looking at a spinner for a minute.

18. Interview Q&A

What is the difference between PUT and PATCH, and why does it matter for retries?

PUT replaces the entire resource with the representation you send, so sending the same PUT repeatedly always produces the same final state; it is idempotent by definition. PATCH applies a partial change. Whether a PATCH is safe to retry depends on its content: setting a field to a value is idempotent, but an instruction like "increment by one" is not. For retry safety I either prefer PUT with a full document, make patches absolute rather than relative, or attach an idempotency key to non-idempotent patches.

A client times out on a payment POST. How do you make sure retrying does not double-charge?

The client generates a unique idempotency key per logical payment and sends it in a header on the first attempt and every retry. The server atomically claims the key (unique constraint) in the same transaction that records the payment, and stores the response. A retry with the same key and the same body returns the stored response without running the charge again; a concurrent duplicate gets 409 while the first is in progress; a reused key with a different body is rejected. Keys expire after a retention window, and the key is also forwarded to the payment provider so its side is deduplicated too.

Why is offset pagination a problem at scale, and what do you use instead?

Offset makes the database read and discard all skipped rows, so deep pages get slower linearly, and a crawler paging through everything does quadratic work. It is also unstable: an insert or delete between requests shifts the window, so the client sees duplicates or misses items. I use keyset pagination exposed as an opaque cursor: the query is WHERE (sort_key, id) < (:last) against an index, which costs the same for any page and is unaffected by changes before the cursor. The tradeoffs are no random jump to page N and the need for a unique, indexed sort order including a tiebreaker.

How do you version an API without breaking existing clients?

Most evolution should be additive within a version: new optional request fields, new response fields, new endpoints, with clients required to ignore unknown fields. Breaking changes, such as removing or changing the meaning of a field, get a new major version, typically in the URL path (/v2) because it is visible and easy to route and test. I keep at most one or two major versions alive, announce deprecations with Deprecation and Sunset headers, measure who still calls old versions, run brownouts, and only then return 410. For mobile I plan for old app versions to exist for years.

When would you choose gRPC over REST, and when not?

I choose gRPC for internal service-to-service traffic where I want a strict typed contract, compact binary payloads, low latency, HTTP/2 multiplexing, deadline propagation, and native streaming, especially across several languages. I avoid it for public APIs consumed by unknown third parties or browsers, where REST is more accessible, easy to debug with curl, and benefits from HTTP caching and CDNs. Operationally I must remember that gRPC needs request-level load balancing because it keeps long-lived connections, and that every call needs an explicit deadline.

What is the N+1 problem in GraphQL and how do you fix it?

GraphQL runs a resolver per field, so a list of N parents with a nested field makes one query for the list and then N separate queries for the child, which is N+1 database calls. The fix is batching with a DataLoader: resolvers request keys from a loader, which collects all keys asked for in one execution step, deduplicates them, and runs one query with an IN clause, then distributes the results back. It also caches per request. Beyond that, I add query depth and cost limits so a client cannot ask for an enormous graph.

Why is caching harder with GraphQL, and what can you do about it?

REST caches well because each resource has a URL and GET is cacheable, so browsers, proxies and CDNs just work. GraphQL typically sends different query bodies via POST to a single URL, so those layers cannot key on the URL. Mitigations are persisted queries (clients send an ID or hash of a registered query so it can use GET and a CDN), normalized client caches keyed by type and ID, resolver-level and entity-level caching on the server with a loader, and response cache hints for public data. Highly personalized data is rarely CDN cacheable in either style anyway.

How would you design an endpoint for an operation that takes ten minutes?

I would not hold the connection. The POST validates input, creates a job record, enqueues the work, and returns 202 Accepted with a Location header for a status resource, such as /jobs/123. The status resource reports queued, running, succeeded or failed with progress, a Retry-After hint, and a link to the result when done; the job can be cancelled with DELETE. For clients that cannot poll efficiently I add signed webhooks with retries and event IDs for deduplication. The POST also takes an idempotency key so a retry does not start the job twice.

How should a webhook sender make deliveries secure and reliable?

For security, sign every payload with an HMAC using a per-endpoint secret, include a timestamp inside the signed data, and have receivers verify the signature in constant time and reject old timestamps to prevent replay; also require HTTPS and support secret rotation. For reliability, treat anything but a 2xx within a short timeout as a failure and retry with exponential backoff and jitter over hours or days, then dead-letter and disable chronically failing endpoints. Delivery is at least once, so every event has a stable ID and consumers must be idempotent and tolerate out-of-order arrival. A delivery log with replay makes it operable.

What does a good error response look like?

It uses the right HTTP status so clients and infrastructure can react without parsing, and a consistent JSON body, ideally problem+json, on every endpoint. The body has a stable machine-readable code, a human message, a request ID for support and tracing, and a list of field-level problems for validation so all errors are reported at once. It never exposes stack traces or internals, and it distinguishes client errors (4xx, do not blindly retry) from server errors (5xx, retry with backoff). For rate limiting it returns 429 with Retry-After.

How do you present the API in a system design interview without wasting time?

I list the core resources and write one endpoint per functional requirement in a compact form with method, path, and the key fields, then annotate only the interesting aspects: pagination style, idempotency keys on payments or creation, async for slow operations, auth, and which endpoints are hot reads. I state the protocol choice in a sentence and tie the API to the rest of the design, for example how the timeline read drives caching and how the write drives the queue. I keep it to a few minutes and offer to expand any endpoint on request.

19. Recap

  • An API is a long-lived promise to callers you do not control; design from the caller's view and keep implementation details out of it.
  • REST: nouns in plural paths, standard methods, shallow nesting, opaque IDs, filters in the query string. Model actions as resources where possible, else as a sub-resource POST.
  • GET, PUT, DELETE are idempotent; POST is not, so use an idempotency key (atomic claim, stored response, body binding, expiry). Use status codes honestly: 4xx for client faults, 5xx for server faults, 429 with Retry-After for limits.
  • ETags give cheap revalidation (304) and optimistic concurrency (If-Match and 412). Use Vary with content negotiation.
  • Paginate every list with a hard maximum. Prefer cursor (opaque keyset) pagination: constant cost and stable under writes. Offset is only for small, static data. Every filter and sort needs an index and a unique tiebreaker.
  • Evolve additively, version the major number (usually in the path) only for breaking changes, keep few live versions, and deprecate with Sunset headers, metrics and brownouts.
  • One error contract with stable codes and request IDs. Authenticate with tokens over HTTPS, authorize every object, and publish rate-limit headers.
  • Slow work: 202 plus a status resource, polling with Retry-After, or signed webhooks with at-least-once retries and idempotent consumers. Batch endpoints need per-item results and size limits.
  • gRPC: protobuf contracts, four call types, deadlines, great internally, needs L7 balancing. GraphQL: client-shaped queries and a typed schema; beware N+1 (use DataLoader), weak HTTP caching and unbounded queries (use depth and cost limits).
  • Mobile: fewer round trips, small payloads, ETags, idempotent retries, delta sync, and support for old app versions.
  • In interviews, show a few endpoints with the interesting annotations (pagination, idempotency, async, auth), justify the protocol, and tie it to the architecture.
