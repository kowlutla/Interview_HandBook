Chapter 34 · Module 5 · Asynchronous Architecture

Message Queues, Logs and Kafka

A message broker lets one part of a system hand work or facts to another part without waiting for it. This chapter explains why that is useful, how queues, logs and publish/subscribe systems differ, how RabbitMQ and SQS behave, and then takes Apache Kafka apart: partitions, the write path, producers, consumer groups, replication, exactly-once, retention, sizing, failures and operations.

1. Why asynchronous messaging

In a synchronous call, service A sends a request to service B and waits for the answer. A's thread is blocked, A's latency includes B's latency, and if B is down or slow then A is down or slow too. In an asynchronous design, A writes a message to an intermediary called a broker and moves on. B reads the message later, at its own pace. The broker holds the message in between. A is the producer (publisher, sender); B is the consumer (subscriber, receiver).

This one change, putting durable storage between two services, buys five distinct things. An interviewer expects you to name them separately, because each one justifies the extra moving part in a different situation.

  • Decoupling in time. Producer and consumer do not need to be running at the same moment. If the consumer is being deployed or has crashed, messages wait in the broker. The producer is unaffected.
  • Decoupling in knowledge. The producer does not need to know who consumes its messages, how many consumers exist, or what language they are written in. A new consumer can be added later without touching the producer.
  • Buffering and smoothing spikes (load leveling). Traffic is bursty. Suppose a flash sale produces 50,000 orders per second for two minutes, but your fulfilment service can safely do 5,000 per second. Without a buffer you must either overprovision fulfilment tenfold for a two-minute event or drop requests. With a queue, the spike is absorbed into the backlog and drained over the next twenty minutes. You pay for average capacity instead of peak capacity, and the cost is that the work finishes later.
  • Fan-out. One event ("order placed") must reach many independent systems: billing, inventory, email, analytics, fraud detection. The producer publishes once and each subscriber gets its own copy.
  • Reliability and retry. If processing a message fails, the broker can hand it out again. Work is not lost because a worker died halfway. Combined with a dead-letter queue (section 3), failures can be isolated and inspected rather than blocking everything.
Watch out Asynchrony is not free. The caller no longer gets an immediate result, so the user interface must cope with "accepted, will be processed" instead of "done". You also gain duplicate messages, reordering, backlog monitoring and one more critical system. If the caller genuinely needs the answer right now (for example, "is this card valid?"), a synchronous call is the right tool. Section 16 covers when not to use a queue.

2. Three models: queue, log and publish/subscribe

The word "queue" is used loosely, but there are three genuinely different storage and delivery models. Most confusion in interviews comes from mixing them up, so learn the differences precisely.

2.1 The classic queue (competing consumers)

A traditional queue stores messages until a consumer takes one. Each message is delivered to one consumer, and once that consumer acknowledges it, the broker deletes it. If several consumers read from the same queue, they compete for messages: each message goes to exactly one of them, which spreads work across a pool of workers. The queue is a work list. Typical uses are job processing, email sending and image resizing. Ordering is first-in first-out in principle, but with several consumers and retries, the order in which messages are finished is not guaranteed. RabbitMQ and Amazon SQS are queues in this sense.

2.2 The log (retained, replayable)

A log is an append-only sequence of records, each with a sequential position called an offset. Records are not deleted when read. They are removed only by a retention policy (for example, after seven days, or when the log exceeds a size). A consumer keeps its own bookmark: "I have read up to offset 1,204,331." Reading is simply scanning forward from a position, so many independent consumers can read the same data at different speeds, and a consumer can rewind to reprocess history. Kafka, Apache Pulsar and Amazon Kinesis are log-based. The log is the model behind event sourcing and stream processing (Chapter 36, Chapter 37).

2.3 Publish/subscribe (topic fan-out)

In pub/sub, a publisher sends a message to a named topic, and every subscriber of that topic receives a copy. The emphasis is on broadcasting to multiple independent interested parties. Classic pub/sub (for example Amazon SNS, Google Pub/Sub topics with several subscriptions, RabbitMQ fanout exchanges) usually gives each subscriber its own queue, so each subscriber consumes at its own pace. A log gives you pub/sub for free: each consumer group is an independent subscriber with its own offsets. A queue gives you pub/sub only if you create one queue per subscriber and have the broker copy messages into each.

3. Broker-style queues: RabbitMQ, SQS and cloud pub/sub

3.1 RabbitMQ: exchanges, bindings, queues

RabbitMQ implements the AMQP model. A producer never writes straight to a queue. It publishes to an exchange along with a routing key (a string label such as order.created.eu). The exchange applies a rule to decide which queues get a copy. The link between an exchange and a queue is called a binding, and it carries a pattern. Consumers read from queues.

  • Direct exchange: delivers to queues whose binding key exactly equals the routing key. Good for routing a message to one named worker pool.
  • Fanout exchange: ignores the key and copies the message to every bound queue. This is pub/sub broadcast.
  • Topic exchange: binding patterns with wildcards (order.*.eu, order.#), so subscribers can express interest in categories.
  • Headers exchange: routes on message header values instead of the key.

Acknowledgements. When RabbitMQ delivers a message to a consumer, the message is marked "unacked" but stays in the broker. The consumer sends an ack when processing succeeds, and only then is the message deleted. If the consumer's connection drops before the ack, the broker re-queues the message for another consumer. This is at-least-once delivery. A consumer can also send a nack or reject to say "I cannot process this", optionally asking for requeue, or routing it to a dead-letter exchange.

Prefetch (QoS). The broker pushes messages to consumers instead of waiting to be polled. Prefetch count is the maximum number of unacknowledged messages a consumer may hold at once. Setting prefetch to 1 gives fair distribution (a slow worker gets one message at a time and a fast worker gets more) but wastes time on network round trips. Setting it to 1,000 maximizes throughput but one stuck consumer can hold 1,000 messages hostage while others sit idle. Typical values for tasks of uneven length are small (1 to 20); for tiny fast messages, in the hundreds.

Durability. A message survives a broker restart only if the queue is declared durable, the message is marked persistent, and the broker has written it to disk. Publisher confirms tell the producer when the broker has taken responsibility. Classic RabbitMQ queues live on one node; quorum queues replicate with Raft (Chapter 29) across several nodes for availability. RabbitMQ is excellent at flexible routing, priorities, per-message TTL and request/reply, and handles tens of thousands of messages per second per node. It is not designed to retain huge histories or to be replayed.

3.2 Amazon SQS

SQS is a fully managed queue: no servers, effectively unlimited throughput for the standard type, and you pay per request. Its behaviours are worth knowing precisely.

  • Pull model with visibility timeout. Consumers call ReceiveMessage. The message is not deleted; instead it becomes invisible to other consumers for the visibility timeout (default 30 seconds). If the consumer finishes, it calls DeleteMessage. If it crashes or is too slow, the timeout expires, the message becomes visible again and another consumer receives it. This is how SQS implements at-least-once and retry without a connection to track. Set the timeout longer than your worst-case processing time, or extend it while working; otherwise a slow job is processed twice at the same time.
  • Standard versus FIFO. Standard queues offer very high throughput, at-least-once delivery and best-effort ordering, so duplicates and reordering happen. FIFO queues give ordering within a message group ID (messages with the same group ID are delivered in order and one at a time per group) and deduplication over a five-minute window using a deduplication ID. FIFO has lower throughput (hundreds to a few thousand messages per second per queue, higher with batching and high-throughput mode), so you spread load across many group IDs. This is the same idea as Kafka keys and partitions.
  • Long polling. Short polling returns immediately even when empty, burning requests (and money) and sometimes missing messages on a subset of servers. Long polling (WaitTimeSeconds up to 20) holds the request open until a message arrives or time runs out, cutting empty responses and cost.
  • Dead-letter queue (DLQ) and redrive. A queue can have a redrive policy: after a message has been received maxReceiveCount times without deletion, SQS moves it to a separate dead-letter queue. This isolates poison messages (section 13) so they stop being retried forever. Operators inspect the DLQ and can redrive messages back after fixing the bug.
  • Limits. Messages are small (256 KB historically, raised to 1 MiB in 2025); retention is 1 minute to 14 days (default 4 days); delayed delivery up to 15 minutes. There is no replay and no cross-consumer fan-out inside one queue.

3.3 Cloud pub/sub services

SNS (Amazon Simple Notification Service) is a topic: publishers send once and SNS pushes a copy to every subscription (SQS queues, Lambda functions, HTTP endpoints, email). The common AWS pattern is SNS fan-out to SQS: one topic, one SQS queue per consuming service, so each service gets durable buffering and its own DLQ. Google Cloud Pub/Sub has topics and subscriptions; each subscription is effectively an independent queue with acknowledgement deadlines, redelivery, optional ordering keys, dead lettering and, in some modes, seek-based replay of retained messages. Azure Service Bus and Event Hubs fill the same two roles (queue/topic broker, and log-style stream). The principle is the same everywhere: topic for fan-out plus a per-subscriber durable queue for pacing.

4. Kafka architecture overview

Apache Kafka is a distributed, replicated, partitioned commit log. It was created at LinkedIn to move activity events and metrics between systems at very high volume, and is now the default backbone for event streaming. Its central design decision is to do very little per message at the broker: append to the end of a file, and let consumers read by position. This makes it fast, and it explains most of its behaviour.

4.1 The vocabulary

  • Broker: a Kafka server process. A cluster has several brokers (three to hundreds).
  • Topic: a named stream of records, such as orders. A topic is a logical category.
  • Partition: a topic is split into N partitions. Each partition is an independent, ordered, append-only log and is the unit of storage, replication and parallelism. Partitions of one topic are spread over brokers.
  • Record (message): a key (optional), a value (bytes), a timestamp and optional headers. Kafka does not interpret the value; serialization is your choice (Chapter 7), often Avro or Protobuf with a schema registry.
  • Offset: the sequential number of a record within its partition (0, 1, 2, ...). It is unique only within one partition. A position in Kafka is the triple (topic, partition, offset).
  • Replica: a copy of a partition on some broker. One replica is the leader, the others are followers (section 8).
  • Consumer group: a set of consumers that share the work of reading a topic (section 7).

4.2 How a partition is stored on disk

A partition is a directory on a broker's disk. It is not one giant file but a series of segments. Each segment is a trio of files named after the offset of its first record, for example 00000000000012345678.log:

  • The .log file holds the records themselves, appended in order, batch after batch.
  • The .index file is a sparse offset index: it maps a record offset to a byte position in the .log file, but only for some entries (one per few kilobytes of data), not every record. To find offset 12,345,999, Kafka picks the segment by file name (binary search on the base offsets), binary-searches the sparse index for the nearest earlier entry, then scans forward in the log a short way.
  • The .timeindex file maps timestamps to offsets, so "start reading from 09:00 yesterday" works.

Only the newest active segment is written to. When it reaches a size limit (default 1 GB) or age limit, Kafka rolls to a new segment. Old segments are immutable. This matters for retention: deleting old data is just deleting whole files, which is cheap, instead of removing records one by one.

4.3 Why Kafka is fast: sequential I/O, page cache, zero-copy

Kafka reads and writes disks, yet reaches hundreds of megabytes per second per broker. Three design choices explain it.

  1. Sequential I/O. Appending to the end of a file and reading forward is the access pattern that disks (and even SSDs) do best. A spinning disk does sequential transfers at 100-200 MB/s but random access only at about a hundred operations per second. Kafka never updates records in place and never seeks randomly in the normal path.
  2. The operating system page cache. Kafka does not keep its own large in-process cache of messages. It writes through the OS, which holds recently written and read file pages in free RAM (the page cache). A write returns after the data is in the page cache; the OS flushes to disk in the background. Consumers that are keeping up read data that was written seconds ago, which is still in RAM, so they never touch the disk. Because the cache belongs to the OS and not the JVM heap, it survives a broker process restart and creates no garbage collection pressure. This is why Kafka brokers typically run with a modest heap (around 6 GB) and as much free RAM as possible for the page cache. Durability then comes from replication (section 8), not from fsync on every message; Kafka by default lets the OS decide when to flush.
  3. Zero-copy transfer. To serve a consumer, a naive server would read the file into memory, copy into the application, copy into a socket buffer and send. That is four copies and several context switches. Kafka stores records on disk in the same binary format it sends over the network, so the broker can use the sendfile system call to move bytes from the page cache directly to the network card, without passing through the application. This saves CPU and memory bandwidth. (When TLS encryption is enabled, the data must pass through user space for encryption and zero-copy no longer applies, so TLS costs throughput.)

Add batching (producers send groups of records, brokers store and fetch groups, compression applies to a whole batch) and the result is a system where the per-record overhead is tiny.

5. The write path

Follow one record from a producer to durable storage. The steps below assume acks=all (section 6.3), the setting you want when data must not be lost.

  1. The producer application calls send(topic, key, value). The producer library serializes the key and value, asks its partitioner which partition to use, and places the record in an in-memory batch for that partition.
  2. A background sender thread ships a batch when it is full (batch.size) or has waited long enough (linger.ms). The producer knows which broker leads each partition from cluster metadata it has fetched, so it sends the batch directly to the leader broker of that partition.
  3. The leader appends the batch to the active segment of its log (in the page cache) and assigns offsets.
  4. Followers continuously send fetch requests to the leader, the same request type consumers use, and append what they receive to their own logs.
  5. The leader tracks how far each in-sync follower has caught up. When all replicas in the in-sync replica set (ISR) have the batch, the leader advances the high watermark past it. Only records below the high watermark are visible to consumers.
  6. The leader responds to the producer with success and the assigned offset. If the producer does not get a response in time, it retries (which is where idempotence matters, section 6.4).

6. Producers in depth

6.1 Keys and the partitioner

The partitioner decides which partition receives each record. The rules for the default partitioner are: if the record has a key, the partition is a hash of the key (Kafka uses murmur2) modulo the number of partitions, so all records with the same key go to the same partition and therefore stay in order. If the key is absent, modern clients use a sticky strategy: fill a batch for one partition, then move to another, which gives even spread while still producing large batches. You can also supply a custom partitioner or name a partition explicitly.

Choosing the key is a design decision. Use the entity whose events must stay ordered: orderId for order lifecycle events, userId for per-user state, accountId for a ledger. The key must have high cardinality and an even distribution, or you get hot partitions (section 13). Note the hash is taken modulo the partition count, so adding partitions to a topic changes where keys map: a key that lived on partition 4 may move to partition 9 for new records, breaking per-key ordering across the change. Plan partition counts up front.

6.2 Batching, linger and compression

A producer that sent each record in its own network request would be limited by per-request overhead. Instead it accumulates records per partition into batches. Two settings control the trade-off between throughput and latency. batch.size (default 16 KB) is the maximum bytes in a batch; linger.ms is how long the sender waits for more records before sending a not-yet-full batch (default 0 in older clients, meaning send immediately if the sender is free; newer clients default to a small positive value). Raising linger to 5-20 ms with a larger batch size sharply improves throughput and compression ratios at the cost of a few milliseconds of latency. For a latency-critical low-volume topic, keep linger at zero.

Compression is applied per batch by the producer (gzip, snappy, lz4, zstd) and the batch stays compressed on the broker and on the wire until the consumer decompresses it. Larger batches compress better because repeated field names in similar JSON records are found. Typical ratios are 2x to 5x for JSON text. zstd and lz4 give a good balance of ratio and CPU. Since the broker stores and replicates compressed batches without recompressing them (when the topic's compression type is left as "producer"), compression saves network, disk and page cache all at once.

acks=all is only as strong as the ISR. If the ISR shrinks to the leader alone, "all in-sync replicas" means just the leader, which is the same as acks=1. The setting min.insync.replicas (section 8.3) forces the broker to reject writes when the ISR is smaller than the minimum, trading availability for safety. The usual production recipe is replication factor 3, min.insync.replicas=2, acks=all: you survive one broker failure with no loss and no downtime.

6.4 The idempotent producer

Retries create duplicates. Imagine the leader writes a batch and the acknowledgement is lost on the network. The producer times out and resends; the leader appends the same records a second time. Retrying can also reorder: if batch 1 fails and batch 2 succeeds, then batch 1's retry lands after batch 2.

The idempotent producer (enable.idempotence=true, the default in recent clients) fixes this. On start, the producer receives a unique producer ID from the broker. Each record batch to a partition carries a monotonically increasing sequence number. The broker remembers the last sequence numbers per (producer ID, partition) and discards a batch whose sequence it has already seen, and rejects out-of-order ones so the producer retries in order. The result is exactly-once per partition within one producer session: no duplicates and no reordering from retries. It does not protect against the application itself sending the same business event twice, nor does it survive a producer restart (new producer ID); that is what transactions and application-level idempotency keys address (section 9, and Chapter 32).

Interview tip When asked "how do you avoid losing messages in Kafka", give the full chain on the producer side: replication factor 3, min.insync.replicas=2, acks=all, idempotence on, and handle send failures by checking the callback or future. On the consumer side add: commit offsets only after processing. Candidates who mention only "use acks=all" miss half the answer.

7. Consumers, groups, offsets and rebalancing

7.1 Pull model and consumer groups

Kafka consumers pull: they issue fetch requests with a starting offset and receive the next batch of records, optionally waiting up to fetch.max.wait.ms until fetch.min.bytes are available. Pull lets each consumer control its own pace, so a slow consumer does not need back-pressure signalling; it just falls behind.

To scale reading, consumers join a consumer group by sharing a group.id. The topic's partitions are divided among the group's members so that each partition is read by exactly one consumer in the group at a time. With 12 partitions and 4 consumers, each consumer gets 3. With 12 partitions and 12 consumers, one each. With 15 consumers, three are idle. So the partition count is the ceiling on consumer parallelism for a group. Different groups are completely independent, each receiving the full stream, which is how one topic serves billing, search indexing and analytics simultaneously.

7.2 Offsets and commits

The group's progress is stored as one number per partition: the offset of the next record to read. Committing an offset means writing it to a special internal Kafka topic named __consumer_offsets. After a crash or reassignment, the new owner of the partition resumes from the last committed offset. The commit strategy determines the delivery guarantee:

  • Auto commit (enable.auto.commit=true): the client commits periodically in the background (every 5 seconds by default). Convenient, but it can commit offsets of records the application has fetched but not finished processing. A crash then loses those records (at-most-once for that window). Or, after processing but before the next auto-commit, a crash causes reprocessing (duplicates).
  • Manual commit after processing (commitSync / commitAsync): process the batch, then commit. A crash between processing and commit means the batch is processed again: at-least-once. This is the standard safe choice, combined with idempotent processing.
  • Commit before processing: at-most-once; a crash after commit and before finishing loses the record. Occasionally acceptable for metrics.
  • Store offsets with the results in the same database transaction as the side effect, then seek to them on startup. This gives effectively-once for a database sink without Kafka transactions.

The setting auto.offset.reset decides where a group with no committed offset begins: earliest (start of retained data) or latest (only new records). Choosing latest by accident in a new group means silently skipping history; choosing earliest on a huge topic means a long catch-up.

7.3 Rebalancing

Whenever the membership of a group changes (a consumer joins, leaves cleanly, crashes, or stops sending heartbeats) or the topic's partition count changes, partitions must be reassigned. This process is the rebalance. A group coordinator (one of the brokers) tracks membership. Consumers send periodic heartbeats (heartbeat.interval.ms, around 3 s) from a background thread; if the coordinator hears nothing for session.timeout.ms (often 10-45 s), the consumer is declared dead. Separately, if the application does not call poll() within max.poll.interval.ms (default 5 minutes), the consumer is considered stuck and removed. This second timer is the usual cause of surprise rebalances: a batch of slow records exceeds the poll interval.

In the classic eager protocol, a rebalance is a stop-the-world event. Every consumer in the group revokes all its partitions, rejoins the group, a group leader runs the assignor, and everybody receives new assignments. During this window nobody in the group consumes. For a group with hundreds of members and large state, this pause can last tens of seconds or minutes.

Why rebalances hurt. (1) Lost throughput during the pause, and lag accumulates. (2) Consumers that hold in-memory state (aggregations, caches, open DB cursors) must flush or rebuild it, which is costly for stream processors. (3) Records that were processed but not yet committed are processed again by the new owner, producing duplicates. (4) A rebalance storm can start when the pause itself makes other consumers miss their heartbeat or poll deadline, triggering another rebalance, repeatedly (section 13).

Mitigations. Use the cooperative sticky assignor (CooperativeStickyAssignor), which keeps partitions where they are and moves only what is needed, in two incremental steps. Use static membership (group.instance.id plus a longer session timeout) so a pod that restarts within the timeout gets its old partitions back with no rebalance at all. Keep per-poll work short (lower max.poll.records) so you never exceed max.poll.interval.ms. Roll deployments gradually instead of restarting all consumers at once. Newer Kafka versions also offer a server-driven group protocol (KIP-848) that moves assignment logic to the broker and removes the global synchronization barrier.

7.4 Consumer lag

Lag for a partition is the log end offset (the newest record) minus the group's committed offset. It counts how many records the consumers are behind, and, divided by the consumption rate, estimates how long until they catch up. Lag is the health metric of a consumer group. A steady small lag is normal. Lag that grows without bound means consumption is slower than production: scale out consumers (up to the partition count), speed up processing, or fix a stuck consumer. Lag that is high on a single partition points to a hot key or a poison message stuck on that partition. Alert on lag growth over time and on time lag (age of the oldest unprocessed record), not just a fixed count, because 10,000 records of lag is a blip on a 50k/s topic and a disaster on a 10/s topic.

8. Replication, ISR and the controller

Replication in general is covered in Chapter 24; here is how Kafka specialises it. Replication is per partition. Each partition has a replication factor (typically 3): one replica is the leader and handles all reads and writes for that partition by default, and the others are followers that only copy the leader's log by fetching. Because leadership is per partition and partitions are spread out, every broker is a leader for some partitions and a follower for others, so load is balanced.

8.1 In-sync replicas and the high watermark

Waiting for every replica would make a slow or dead follower block all writes. Kafka instead tracks the in-sync replica set (ISR): the leader plus every follower that has fetched up to the leader's log end recently (within replica.lag.time.max.ms, default 30 s in modern versions). A follower that falls behind or stops fetching is removed from the ISR; when it catches up, it rejoins. The ISR is dynamic, and it is recorded in cluster metadata.

The high watermark (HW) is the highest offset that has been replicated to all ISR members. Consumers can read only up to the HW. This guarantees that a consumer never sees a record that could disappear if the leader fails, because any record below the HW exists on every in-sync replica and any of them could become leader. Records between the HW and the leader's log end offset are "uncommitted".

8.2 Leader failure and election

When a leader broker dies, the cluster elects a new leader for each of its partitions from the ISR. Every ISR member has all committed records, so nothing acknowledged under acks=all is lost. Producers and consumers receive a metadata error, refresh metadata, and continue with the new leader, typically within seconds. A rejoining old leader must truncate any uncommitted tail of its log that does not match the new leader's history, then follow it. (Kafka uses a leader epoch, a counter incremented per election, to make truncation precise and to avoid divergent logs.)

8.3 min.insync.replicas and unclean leader election

min.insync.replicas is the minimum ISR size for which a write with acks=all is accepted. With replication factor 3 and min ISR 2, the system tolerates one failure with both durability and availability, but if two brokers are lost the partition becomes read-only for producers (writes fail with NotEnoughReplicas). That is the CAP trade-off made visible: you choose consistency over availability for this partition.

What if all ISR members are down and only an out-of-sync replica is alive? Unclean leader election (unclean.leader.election.enable, default false) decides. If false, the partition stays offline until an ISR member returns: no data loss, but downtime. If true, an out-of-sync replica becomes leader immediately: the partition is available, but it is missing the records the old leader had acknowledged, and those are permanently lost (and offsets may later be reused with different content). Enable it only for data you can regenerate (metrics, logs), never for financial or order events.

8.4 The controller, ZooKeeper and KRaft

One broker acts as the controller. It watches broker liveness, performs leader elections when brokers fail, and records metadata changes (topics, partitions, ISR, configuration). Historically the controller kept this metadata in ZooKeeper (Chapter 30), a separate cluster, and the controller was elected through it. A new controller had to reload all metadata from ZooKeeper, which scaled badly past roughly 100,000 partitions and made failover slow.

KRaft mode (Kafka Raft, the default in current releases and the only option from Kafka 4.0) removes ZooKeeper. A small set of controller nodes (usually three or five) runs the Raft consensus protocol (Chapter 29) over an internal metadata log called __cluster_metadata. One is the active controller (the Raft leader); the others hold a hot copy and can take over quickly. Brokers fetch metadata updates from this log just as followers fetch data. Benefits: one system to operate instead of two, much faster controller failover, and support for far more partitions per cluster. Note that this Raft group is only for metadata; the replication of record data still uses the ISR mechanism described above.

9. Delivery semantics and exactly-once

The general theory of at-most-once, at-least-once and exactly-once delivery is in Chapter 32. Applied to Kafka:

  • At-most-once: producer acks=0 or no retries, and/or the consumer commits before processing. Messages may be lost, never duplicated.
  • At-least-once: producer retries with acks=all, and the consumer commits after processing. Nothing is lost, but duplicates occur after retries or consumer crashes. This is the default realistic choice, paired with idempotent consumers (for example, an upsert keyed on a business ID, or a processed-ID table).
  • Exactly-once: each input record affects the output exactly once, even across failures. Kafka offers this inside the Kafka ecosystem through transactions.

9.1 How Kafka transactions work

The classic exactly-once case is consume, transform, produce: read records from topic A, compute, write results to topic B, and record progress. If the process crashes after writing to B but before committing its offset on A, a restart reprocesses the input and writes duplicates to B. A transaction makes "write outputs" and "commit input offsets" a single atomic unit.

  1. The producer sets a stable transactional.id and calls initTransactions(). A transaction coordinator broker maps this id to a producer ID and an epoch. If an old instance with the same id is still alive (a zombie), the new instance bumps the epoch and the broker fences the old one, rejecting its writes.
  2. The producer calls beginTransaction(), sends records to any number of partitions and topics, and calls sendOffsetsToTransaction() to include the consumed offsets of the input topic as part of the transaction.
  3. The producer calls commitTransaction(). The coordinator writes a commit decision to its transaction log, then writes commit markers into every partition involved. (An abort writes abort markers instead.)
  4. Consumers configured with isolation.level=read_committed read only up to the last stable offset and skip records of aborted transactions. Consumers with the default read_uncommitted see everything, including aborted data.

Kafka Streams enables this with a single setting (processing.guarantee=exactly_once_v2). Costs: extra latency (the commit requires marker writes), slightly lower throughput, and read_committed consumers are held back by any long-open transaction. Limits matter in interviews: exactly-once applies to the Kafka-to-Kafka loop. The moment you call a payment API, send an email or update an external database, that side effect is outside the transaction and you are back to at-least-once, so the side effect itself must be idempotent (idempotency keys, Chapter 32) or you use the outbox pattern (Chapter 31).

Key idea "Exactly-once" is really at-least-once delivery plus deduplication or atomic commit of effects. Kafka gives you that inside its own log (idempotent producer, transactions, fencing). For anything outside Kafka, you provide the idempotency.

10. Retention and log compaction

Since consuming does not delete data, Kafka needs an explicit rule for discarding it. Each topic has a cleanup policy.

10.1 Time and size retention (delete policy)

With cleanup.policy=delete, whole segments are removed once they are older than retention.ms (default 7 days) or when the partition exceeds retention.bytes. Only closed segments are deleted, judged by the newest timestamp in the segment, so actual retention is a little longer than configured. Retention is independent of consumption: a record is deleted on schedule even if no one has read it, so a consumer that is down for longer than retention loses data (it will find its committed offset no longer exists and fall back to auto.offset.reset). Alert on lag measured against retention. Long retention is cheap compared with other systems because storage is sequential files; some deployments retain for months, and tiered storage moves older segments to object storage (Chapter 21) while keeping recent data on local disks.

10.2 Log compaction

With cleanup.policy=compact, Kafka keeps at least the latest record for every key and discards older records with the same key. The topic becomes a changelog of a table: reading it from the start reconstructs the latest state of every entity. A background cleaner thread rewrites older segments, dropping records whose key has a newer value. A record with a key and a null value is a tombstone, meaning "delete this key"; it is retained for delete.retention.ms so that consumers can see the deletion, then removed. The active segment is never compacted, so recent duplicates are visible, and compaction does not change offsets: offsets of surviving records stay the same and simply have gaps.

Compaction powers the internal __consumer_offsets topic, Kafka Streams state-store changelogs, and "table" topics like a user profile feed that new services replay to bootstrap a local cache. It is also how you can honour a deletion request for personal data in a log (write a tombstone for that key). You can combine policies (compact,delete) to compact and also drop data older than a limit.

11. Ordering and choosing the partition count

Kafka guarantees order only within one partition. Records with the same key go to the same partition and therefore are read in the order they were written. Across partitions there is no ordering at all: if events for order 7 are on partition 2 and events for order 8 are on partition 5, a consumer may see 8's events before 7's even though 7 happened first. Global ordering of a topic requires a single partition, which limits throughput to one consumer and is rarely worth it. The design rule: choose a key such that only events that must be ordered relative to each other share a key.

A producer with retries and several in-flight requests can reorder records within a partition unless idempotence is enabled (it preserves order with up to five in-flight requests per connection). Consumers that process records of one partition concurrently with a thread pool destroy order again, so parallelize across partitions or keys, not within one partition's stream.

11.1 How many partitions?

Partitions set the maximum parallelism of consumption and the aggregate write throughput, but each has a cost. Reason from both sides.

  • Lower bound from throughput. Let T be the target throughput, p the throughput one producer can push to a single partition, and c the throughput one consumer can process from one partition. You need at least max(T/p, T/c) partitions. In practice consumer processing speed is the bottleneck.
  • Lower bound from consumer parallelism. If you want to run up to N consumers in a group, you need at least N partitions, and you should plan for future growth.
  • Upper bound costs. Each partition is a set of open files and memory buffers on every replica, adds leader-election and recovery time after a broker failure (more partitions to elect), increases replication work, and enlarges the metadata. Do not create thousands of partitions for a small topic.
  • You can add partitions later, never remove them, and adding changes key-to-partition mapping (section 6.1), breaking per-key ordering for existing keys. So choose a count with headroom from the start (for example 2-3x current need), prefer numbers with many divisors (12, 24, 60) so consumers divide them evenly, and treat a repartition as a migration (create a new topic, dual-write or copy, switch consumers).

12. Worked example: capacity sizing

Scenario: an event pipeline for an e-commerce platform. Average 20,000 events per second, peak 50,000 per second, average record size 1 KB (uncompressed), keyed by orderId. Three independent consumer groups read the topic (fulfilment, search indexing, analytics). Retention 7 days, replication factor 3, compression about 3x for the JSON payloads. Each consumer thread can process about 500 records per second.

12.1 Ingress and egress bandwidth

12.2 Storage

Average ingress is 20,000 x 1 KB = 20 MB/s raw. Per day: 20 MB/s x 86,400 s = 1.73 TB raw. Seven days: 12.1 TB raw. After 3x compression: about 4.0 TB for one copy. With replication factor 3: about 12.1 TB across the cluster. Keep disks under about 60% full, leaving room for segment rolling, rebalancing and growth, so provision 12.1 / 0.6 = about 20 TB of disk. On 6 brokers, that is about 3.4 TB each, so give each broker 4 TB of SSD.

12.3 Partitions

Consumer parallelism is the limit. At peak, 50,000 / 500 = 100 consumer threads are needed to keep up, so at least 100 partitions. Add headroom for growth and for catching up after a backlog (to drain a backlog you need spare capacity above the arrival rate), so choose 120 partitions (divisible by 2, 3, 4, 5, 6, 8, 10, 12, 15, 20, 24, 30, 40, 60). Per-partition write rate at peak is 50 MB/s / 120 = about 0.4 MB/s raw, far below what a partition can take, so partitions are not constrained on the write side. Replicas: 120 x 3 = 360 partition replicas over 6 brokers = 60 per broker, which is comfortable.

12.4 Broker count and the failure check

Throughput alone would need only two or three brokers; 100 MB/s is small for modern hardware. The binding constraints are storage (about 12 TB across brokers at 60% fill) and fault tolerance. Six brokers across three availability zones with rack awareness (broker.rack) place each partition's three replicas in three different zones. If one broker fails, its 60 replicas (about 20 of them leaders) move to the survivors, each absorbing about a fifth more load, and a replacement broker must re-replicate about 2 TB (12.1 TB / 6): at a throttled 100 MB/s that takes roughly 5.5 hours; at 300 MB/s about 2 hours. During that time the ISR for affected partitions is 2 of 3, which still meets min.insync.replicas=2, so writes continue. A second simultaneous failure in another zone would block writes for partitions that lost two replicas, which is why you leave headroom and watch under-replicated partitions.

12.5 Time to drain a backlog

If the fulfilment consumers are down for 30 minutes during an average load, the backlog is 20,000 x 1,800 = 36 million records. With 100 consumers at 500 records per second each (50,000 per second) and new records still arriving at 20,000 per second, the net drain rate is 30,000 per second, so recovery takes 36,000,000 / 30,000 = 1,200 s = 20 minutes. This is the load-leveling effect of section 1 in numbers, and it shows why you leave consumer capacity above the average rate.

14. Operations

14.1 What to monitor

  • Under-replicated partitions: partitions where the ISR is smaller than the replica set. Should be zero in steady state. The single most important broker alert.
  • Offline partitions and active controller count: offline partitions must be zero; exactly one active controller.
  • ISR shrink and expand rate: frequent flapping signals slow disks or network.
  • Consumer lag and time lag per group and partition, plus the group's state (stable, rebalancing).
  • Request latency (produce, fetch) at p99 and the request-queue and network-processor idle ratios, which show broker saturation.
  • Disk usage, disk I/O wait, page cache hit, network throughput per broker, and JVM garbage collection pauses.
  • Skew: bytes in per partition, to catch hot keys.

14.2 Partition reassignment

When you add brokers, Kafka does not automatically move existing partitions to them; new brokers sit empty until you run a partition reassignment (the kafka-reassign-partitions tool, or automation such as Cruise Control). The plan lists, for each partition, the new replica set. The new replicas are added as followers, copy the whole log from the leader, join the ISR, and the old replicas are then removed. Because this copies terabytes, you throttle the replication bandwidth so that production traffic is not starved, run it off-peak, and move in small batches. Reassignment is also how you drain a broker before decommissioning it, fix skew, or change the replication factor. A related operation is preferred leader election: after a failure, leaders concentrate on the survivors; once the original broker recovers, leadership is moved back to the preferred replica (first in the replica list) to restore balance.

14.3 Other operational practices

Use rolling restarts (one broker at a time, waiting until under-replicated partitions return to zero before the next). Set client quotas so one noisy producer or consumer cannot take the cluster's bandwidth. Use a schema registry with compatibility rules so a producer cannot publish a format that breaks consumers. Mirror clusters across regions with MirrorMaker or similar for disaster recovery (Chapter 26); offsets differ between clusters and need translation. Managed offerings (Confluent Cloud, Amazon MSK, Redpanda, Aiven) remove much of this toil at a price.

16. When not to use a queue

  • The caller needs the result now. A user waiting for a search result or a card authorization wants a synchronous answer. Request/reply over a queue adds latency and complexity.
  • Low volume, simple needs. A job table in your existing database, polled with SELECT ... FOR UPDATE SKIP LOCKED, can serve a few hundred jobs per second with no new infrastructure. Do not introduce a Kafka cluster for ten events per minute.
  • Strong cross-entity consistency. If two updates must be atomic and visible together, use a transaction, not two messages with eventual consistency. Where a workflow spans services, see Chapter 31.
  • Hiding an overloaded downstream. A queue turns overload into a growing backlog. Without back-pressure, rate limits or autoscaling, the backlog becomes hours of delay or exhausts retention. A queue is a buffer, not extra capacity.
  • You need strict global ordering and high throughput at the same time; the two conflict.
  • You cannot make consumers idempotent and cannot tolerate duplicates; at-least-once delivery will hurt.

18. Interview Q&A

Why use a message queue instead of calling the other service directly?

A direct call couples the caller to the callee's availability and speed, so a slow or failed callee degrades the caller, and spikes pass straight through. A queue decouples them in time (the consumer can be down), absorbs bursts by buffering so you provision for average load, lets you add consumers without changing the producer, and adds retry for transient failures. The price is eventual processing, duplicate and out-of-order handling, and another critical system to run, so I would use it when the caller does not need the result immediately.

What is the difference between a queue and a log like Kafka?

In a queue, a message is handed to one consumer and deleted after acknowledgement; the broker tracks per-message state and the goal is distributing work. In a log, records stay until retention expires, each consumer group keeps its own offset per partition, and reading is non-destructive, so many groups can read the same data and any group can rewind to replay history. Consequently logs fit event streaming, stream processing and event sourcing, while queues fit job distribution with per-message routing, priorities and TTLs.

How does Kafka achieve such high throughput?

It turns all disk activity into sequential appends and sequential reads, which disks handle at full bandwidth. It leans on the OS page cache, so recently written data is served from memory to consumers that keep up. It stores records in the same format as the wire format and uses sendfile for zero-copy transfer from cache to socket. Producers batch records and compress whole batches, which reduces network, disk and cache use at once. The broker itself does little work per message: no per-message acknowledgement bookkeeping, since consumers track a single offset.

How do you guarantee no message loss in Kafka?

On the producer: replication factor 3, min.insync.replicas=2, acks=all, idempotence enabled, and check callbacks so failures are retried or surfaced. On the broker: disable unclean leader election, and spread replicas across racks. On the consumer: disable auto commit and commit the offset only after the record is processed, accepting at-least-once and making processing idempotent. Also keep retention longer than the worst consumer outage so unread data is not deleted. This gives you durability against a single broker failure; it cannot protect against losing a whole cluster without cross-cluster replication.

Explain consumer groups and what limits parallelism.

A consumer group is a set of consumers sharing a group id. Kafka assigns each partition to exactly one consumer in the group, so the group collectively reads the topic once and each record is handled by one member. The number of partitions is therefore the maximum useful number of consumers: extra consumers sit idle. Separate groups are independent and each read all records, which provides publish/subscribe. To scale beyond the limit you must have more partitions (planned in advance) or make each consumer faster, for instance by handing records to a worker pool keyed so that per-key order is preserved.

What is a rebalance and why is it a problem?

A rebalance redistributes a group's partitions when members join, leave, crash, or the partition count changes. In the eager protocol all consumers give up all partitions and wait for new assignments, so the whole group stops processing, lag builds, in-memory state is lost and uncommitted work is reprocessed. A slow consumer exceeding the poll interval can trigger repeated rebalances, a storm. I would use the cooperative sticky assignor so only moved partitions pause, static membership so quick restarts do not trigger rebalances, smaller poll batches, and staged deployments.

Explain ISR, high watermark and min.insync.replicas.

Each partition has a leader and followers; the ISR is the leader plus followers that are caught up within a time limit. The high watermark is the highest offset replicated to every ISR member, and consumers can only read below it, so they never see data that might vanish on a leader change. With acks=all, a write is acknowledged when all ISR members have it, and min.insync.replicas sets the smallest ISR allowed for such writes to succeed. With RF 3 and min ISR 2 you survive one broker loss with no data loss and no downtime, and if two are lost writes are rejected rather than accepted on a single copy, which chooses consistency over availability.

How does Kafka achieve exactly-once, and what are the limits?

Within Kafka it combines the idempotent producer (producer id plus sequence numbers to dedupe retries), transactions (atomic writes to multiple partitions together with the consumer offsets of the input, coordinated through a transaction coordinator with commit markers), and epoch-based fencing of zombie producers. Consumers using read_committed skip aborted data. The limit is that it covers the read-process-write loop within Kafka. Once a side effect leaves Kafka (a database write, an API call, an email) you are at-least-once again, so that effect must be idempotent or done via an outbox, because no broker can make an external system transactional with itself.

How do you choose the number of partitions and the key?

Estimate required throughput divided by the per-partition producer and consumer throughput, and make sure the count covers the maximum number of consumers you want, then add headroom since you can add partitions later but not remove them, and adding them remaps keys. Avoid overshooting, because each partition costs file handles, replication traffic and failover time. Choose a key that groups only the events needing relative order (like orderId), with many distinct values and even spread, so no single key becomes hot. If one key is genuinely huge, I would salt it or split it, giving up strict order for that entity or ordering within sub-keys.

A consumer is stuck on one partition and lag is growing only there. What do you do?

Single-partition lag points to a poison message or a hot key, not general under-capacity. Look at the consumer logs for repeated exceptions at the same offset, and check whether the committed offset is advancing. If it is a poison record, route it to a dead-letter topic after bounded retries, commit past it, and fix the producer or deserializer; for a hot key, check bytes per partition, then change the key or partitioning. As a short-term step I can reset the group offset past the bad record, accepting that it is skipped, after saving it for later analysis.

Kafka or SQS for a background job system on AWS?

For job distribution to a worker pool, SQS is usually better: fully managed, per-message visibility timeout and retry, built-in DLQ, easy scaling by adding workers, and no partition planning. Kafka fits when I need many independent consumers of the same stream, replay, strict per-key ordering at very high throughput, or stream processing. If events must also feed analytics and search, I might publish to Kafka as the system of record and use SQS for specific task execution, but I would avoid the operational cost of Kafka for a simple job queue.

19. Recap

Recap

  • Asynchronous messaging decouples producers and consumers in time and knowledge, buffers spikes, fans out events and enables retry, at the cost of eventual processing, duplicates and one more system.
  • A queue deletes messages after acknowledgement and distributes work (RabbitMQ, SQS). A log keeps records, lets each reader hold an offset and allows replay (Kafka, Pulsar, Kinesis). Pub/sub broadcasts one message to many subscribers.
  • RabbitMQ routes through exchanges and bindings, with acks and prefetch. SQS uses a visibility timeout, long polling, FIFO groups for ordering and a redrive DLQ.
  • Kafka topics are split into partitions, each a replicated append-only log stored as segments with sparse indexes. Speed comes from sequential I/O, the page cache, batching, compression and zero-copy.
  • Producers choose a partition by key hash; batching and linger trade latency for throughput; acks=all with min.insync.replicas=2 and idempotence prevent loss and duplicates from retries.
  • Consumers in a group each own distinct partitions; partition count caps parallelism. Commit after processing for at-least-once. Rebalances pause consumption; use cooperative assignors and static membership. Watch lag.
  • Replication: leader and followers per partition, ISR, high watermark, leader election from the ISR, unclean election trades data for availability, KRaft replaces ZooKeeper for metadata.
  • Exactly-once inside Kafka uses transactions and fencing; outside Kafka you need idempotent effects.
  • Retention deletes old segments by time or size; compaction keeps the latest value per key. Ordering exists only within a partition; choose keys and partition counts carefully because they are hard to change.
  • Size with throughput, storage with retention and replication, and consumer parallelism; plan failures: broker loss, lag, rebalance storms, hot partitions and poison messages.
