Object Storage (S3-style)

Object storage is the place where the internet keeps its photos, videos, backups, logs, and data lakes: an enormous, cheap, extremely durable bucket of immutable blobs, reached over HTTP. This chapter explains what it offers, how a system like Amazon S3 is built inside (metadata service, storage nodes, erasure coding, repair), what it costs, how to use it well, and how to answer "design your own S3" in an interview.

1. Why object storage exists

Almost every product eventually has to store large amounts of unstructured data: user-uploaded images, video files, PDF invoices, machine learning datasets, database backups, application logs. You could put these in a relational database as BLOB columns, but that is a poor fit. Databases are tuned for small, structured, frequently updated rows with transactions. Large blobs bloat the database, slow down backups and replication, and make every byte expensive because database storage sits on fast, costly disks and is replicated with heavyweight machinery.

You could also use a file server (NFS or a clustered file system), but file systems carry a lot of baggage: a hierarchical directory tree that must stay consistent, file locks, in-place partial writes, and permission models designed for a single organization. Scaling a file system to billions of files and hundreds of petabytes is a hard problem that few organizations solve well.

Object storage takes a deliberately simpler contract. You store a whole blob (an object) under a name (a key) inside a container (a bucket). You can read it back, replace it entirely, or delete it. You cannot edit the middle of it in place, and you cannot take a lock on it. In exchange for giving up those features, the system can scale almost without limit, spread data across data centers, store it cheaply with erasure coding instead of full copies, and promise durability that is far stronger than any single disk or server could offer.

Key idea Object storage trades POSIX file-system features (in-place edits, directories, locks, rename) for scale, durability, and low cost per gigabyte. The contract is: whole objects, written once, read many times, addressed by a key, over HTTP.

In this chapter, "S3-style" means the interface and guarantees popularized by Amazon S3 and copied by Google Cloud Storage, Azure Blob Storage, Cloudflare R2, MinIO, Ceph's RADOS Gateway, and others. We use S3 numbers and vocabulary because they are the best known, but the design ideas are common to all of them.

2. Block vs file vs object storage

Storage comes in three fundamental flavors. Interviewers often ask you to pick one, so understand what each is and when it is right.

2.1 Block storage

Block storage exposes a raw device made of fixed-size blocks (for example 4 KB) addressed by number. A server attaches it like a disk (Amazon EBS, a SAN volume, a local NVMe drive). The operating system puts a file system or a database engine on top. Block storage gives the lowest latency (sub-millisecond to a few milliseconds), supports small random reads and writes in place, and is what databases and virtual machine disks need. It is usually attached to one machine at a time, is limited to terabytes per volume, and costs the most per gigabyte.

2.2 File storage

File storage exposes a shared hierarchical file system over a network protocol such as NFS or SMB (Amazon EFS, a NAS appliance). Many machines can mount the same directory tree, open files, read and write byte ranges in place, and rely on directories, permissions, and sometimes locks. It is the right tool when existing software expects a normal file system and several machines must share it, such as home directories or a content management system. It scales less far than object storage and costs more per gigabyte.

2.3 Object storage

Object storage exposes a flat namespace of immutable objects over HTTP. Each request is independent (no mounted session, no open file handle). Latency is higher (tens of milliseconds to first byte), but throughput is huge when you read many objects or many ranges in parallel, capacity is effectively unbounded, and cost per gigabyte is the lowest of the three.

3. The object model

3.1 Buckets and objects

A bucket is a named top-level container. In S3 bucket names are globally unique across all customers, because the name appears in the URL (my-bucket.s3.amazonaws.com). A bucket carries configuration that applies to everything inside: region, access policy, versioning, encryption default, lifecycle rules, logging, event notifications. An account normally has a limited number of buckets, so buckets are for organizing configuration, not for one-per-user designs. If you have a million users, use one bucket with a key prefix per user.

An object consists of three things: a key (its name inside the bucket, up to about 1 KB of UTF-8), the data (an opaque sequence of bytes, from zero bytes to 5 TB in S3), and metadata. System metadata includes size, last-modified time, ETag, content type, storage class, and encryption details. User metadata is a small set of custom key-value pairs you attach at upload time (for example x-amz-meta-owner: ana). Many systems also support tags, key-value labels that can drive lifecycle and access rules.

3.2 Flat namespace and prefixes

Object storage has no real directories. The key photos/2026/cat.jpg is one single string. The slashes are ordinary characters. Consoles and tools pretend there are folders by letting you list with a prefix (photos/2026/) and a delimiter (/). The LIST call then returns the keys that start with the prefix, and groups keys that share the next delimiter into "common prefixes", which look like subfolders.

This has practical consequences. Renaming a "folder" means copying every object to a new key and deleting the old ones, because there is no directory node to rename. Moving a single object is also copy plus delete. An "empty folder" does not exist unless someone created a zero-byte placeholder object whose key ends with a slash. And listing is a range scan over sorted keys, which is why key design (section 14) matters for performance.

3.3 Immutability and overwrite

Objects are immutable: there is no "append 10 bytes" or "change bytes 100 to 200". A PUT to an existing key replaces the whole object atomically. Readers see either the old object or the new one, never a mixture. That atomic whole-object replacement is a simple and powerful property, and it is what lets the internal design avoid locks and in-place update machinery (section 7).

Some systems offer a narrow exception: Google Cloud Storage can "compose" several objects into one, and Azure supports append blobs. S3 added an append-style feature only in a limited form on a special bucket class. For an interview, treat objects as write-whole, read-whole-or-ranges.

3.4 Versioning

When versioning is enabled on a bucket, a PUT to an existing key does not destroy the old data. Each write creates a new version with a unique version ID, and the key points at the latest. A plain DELETE does not remove anything: it adds a delete marker as the newest version, so ordinary GETs return "not found" while older versions remain recoverable. You can GET, restore, or permanently delete a specific version ID. Versioning protects against accidental overwrites and deletions (and against some ransomware), at the cost of storing every version until a lifecycle rule expires the old ones.

3.5 Immutability policies: object lock

Object Lock (S3), bucket locks and retention policies (GCS), and immutable blob storage (Azure) provide WORM (write once, read many) behavior. You set a retention period or a legal hold on an object version, and for that time nobody, including the account root user in compliance mode, can delete or overwrite it. This is how regulated industries meet record-keeping rules and how backup teams make backups ransomware-proof.

3.6 Names and URLs

A typical object URL looks like https://my-bucket.s3.us-east-1.amazonaws.com/photos/2026/cat.jpg (virtual-hosted style) or https://s3.us-east-1.amazonaws.com/my-bucket/photos/2026/cat.jpg (path style). The bucket and region choose the cluster, and the key is passed to the metadata layer. Choose key names that are stable, URL-safe, and designed for how you will list and partition them.

The S3 REST API is the de facto standard. Learn the core calls and their behavior. Everything is an HTTP request signed with credentials (section 16).

4.1 Range reads

A GET can carry a header such as Range: bytes=0-1048575 to fetch only that slice, returning 206 Partial Content. Ranges let a video player jump to the middle of a file, let a download manager resume, and let analytics engines read only the footer and the needed column chunks of a Parquet file. Because each range is an independent request, a client can fetch many ranges in parallel and reach very high aggregate throughput from a single object. The system does not need to read the whole object to serve a range, because it stores objects as chunks (section 8).

4.2 Conditional requests

Standard HTTP conditionals work on objects. If-None-Match and If-Modified-Since on a GET let a client ask "send it only if it changed", answered with 304 Not Modified and no body, which is how a CDN revalidates cached copies (see Chapter 12). On writes, conditional headers give you a basic concurrency control. Modern S3 supports If-None-Match: * on PUT, meaning "create this key only if it does not already exist" (a compare-and-create), and conditional writes against an ETag for compare-and-swap in newer versions. This makes it possible to build simple leader-election or commit protocols directly on object storage, which table formats for data lakes rely on. Say "supported by major providers in recent years" and avoid claiming exact semantics for each vendor.

4.3 The ETag

The ETag is an identifier of the object's content version. For a simple, unencrypted single-part upload it is the MD5 hash of the bytes. For multipart uploads or some encryption modes it is not a plain MD5; for multipart it is a hash of the part hashes with a dash and part count. Treat the ETag as an opaque version token for equality checks, not as a guaranteed content hash. If you need a verifiable content hash, ask for a checksum (SHA-256 or CRC) which modern S3 supports natively, or store your own hash in metadata.

4.4 Presigned URLs

A presigned URL is a normal object URL with a time limit and a signature baked into the query string. Your backend, which holds credentials, computes the signature for a specific method on a specific key (for example "PUT this key within 15 minutes"). Anyone who has the URL can perform exactly that action until it expires, without having any credentials of their own. This is the standard pattern for letting browsers and mobile apps upload and download directly from the object store, so large files never pass through your application servers (section 16.3).

4.5 Errors and retries

Calls can fail with 503 Slow Down when you exceed a partition's request rate, and with ordinary network errors. The correct client behavior is exponential backoff with jitter. Since PUT replaces the whole object atomically and DELETE is idempotent, retrying is safe. A retried PUT may create a second version if versioning is on, but never a corrupted object.

5. Large uploads: multipart, resumability, and dedup

Uploading a 20 GB video as one HTTP request is fragile: if the connection drops at 19 GB you start over, a single TCP stream is limited in speed, and a server would need to handle an enormous request body. Multipart upload solves this by splitting the file into parts uploaded independently.

5.1 How multipart upload works

  1. Initiate. The client calls "create multipart upload" for the key. The service returns an upload ID.
  2. Upload parts. The client sends each part (S3: 5 MB to 5 GB each, up to 10,000 parts, so up to 5 TB total; the last part can be smaller) with its part number and the upload ID. Parts can be sent in any order and in parallel across several connections. Each upload returns the part's ETag.
  3. Complete. The client sends the list of part numbers and ETags. The service stitches the parts into one object, and only then does the key become visible. Until completion, readers see nothing (or the previous object).
  4. Or abort. The client aborts, and the service discards all uploaded parts.

5.2 Why it is better

  • Parallelism: several connections together saturate a fast link, which one TCP stream often cannot.
  • Resumability: if the connection drops, the client re-sends only the missing parts. It can ask the service to list parts already uploaded under the upload ID, which is how an upload survives an app restart or a laptop going to sleep.
  • Retry cost is small: a failed 64 MB part is retried, not the whole 20 GB.
  • Unknown total size: the client can start uploading parts of a stream (a live recording) before it knows the final size.
  • Atomic visibility: readers never see a half-uploaded object.

5.3 Choosing part size

Larger parts mean fewer requests and less overhead, but a failure wastes more work, and memory use rises with parts in flight. Smaller parts retry cheaply but cost more requests (each request is billed) and hit the 10,000 part limit sooner. A common choice is 8 to 64 MB; for a 20 GB file, 64 MB parts give about 320 parts. A reasonable rule is to use multipart above about 100 MB and choose a part size so the part count stays well below 10,000.

5.4 Resumable uploads in your own product

For consumer apps, the flow is usually: the client asks your API to start an upload. Your API creates the multipart upload (or a resumable session in a provider with a different mechanism, such as GCS resumable uploads or the tus protocol) and returns presigned URLs for each part. The client uploads the parts directly to object storage, in parallel, remembering which parts finished (in local storage). On completion the client calls your API, which calls "complete", records the object in your database, and enqueues processing such as virus scanning or transcoding. Your application servers never touch the bytes.

5.5 Deduplication by hash

If many users upload the same file (a popular video, an identical attachment), storing it once saves money. The idea is content-addressed storage: compute a cryptographic hash (SHA-256) of the data, use the hash as the storage key (or look it up in an index), and store only one copy no matter how many logical files refer to it. At upload time the client can compute the hash first and ask "do you already have this hash?"; if yes the upload is skipped entirely (instant upload). You can dedup whole files, or split files into chunks (fixed size, or content-defined chunking so an insertion does not shift every boundary) and dedup per chunk, which is what backup and file-sync systems do. See the Dropbox-style design in the file-sync case study (Case study: file sync).

Dedup has costs to name: you need an index from hash to location, you need reference counting or garbage collection to know when a chunk is no longer used by any file, a cross-user dedup can leak information ("this file already exists" tells an attacker someone else has it), and encryption with per-user keys defeats dedup unless you use convergent encryption. Object stores themselves normally do not dedup across objects; dedup is a layer you build on top.

6. How an object store is built: the big picture

The central design idea is a hard split between two planes. The data plane stores the bytes. The metadata plane stores the mapping from names to the places where bytes live, plus everything about the object (size, version, ACLs, tags). Separating them lets each be scaled and optimized on its own terms: the data plane is a huge number of cheap disks optimized for throughput and capacity, the metadata plane is a smaller, sharded, low-latency, strongly consistent database.

6.1 The components in detail

  • Front-end (API) tier. A fleet of stateless servers behind a load balancer (Chapter 9). They terminate TLS, authenticate and authorize the request (section 16), enforce rate limits, parse the S3 API, compute or verify checksums, stream bytes to and from storage nodes, and talk to the metadata service. Because they are stateless, you scale them by adding machines.
  • Metadata service. A distributed, sharded, strongly consistent database holding, for every object version, the key, size, checksum, timestamps, user metadata, ACL pointers, and the chunk map (which storage nodes and disks hold which shards). It also supports ordered range scans for LIST. Section 7 covers it.
  • Placement service. Decides which storage nodes get the shards of a new object, subject to failure-domain rules (never put two shards of one object on the same disk, preferably not in the same rack, and for a multi-zone class, spread across zones) and to capacity balance.
  • Storage nodes. Servers each with many disks (for example 30 to 100 large HDDs). A node stores shards as blobs in large append-only files on its local file system or directly on raw disk, keeps a small local index of shard location within those files, and serves reads and writes by shard ID. They are intentionally simple.
  • Background workers. Scrubbing, repair, rebalancing, garbage collection, lifecycle, replication, and notifications (sections 9, 10, 11, 18).

6.2 Why split metadata from data

The two workloads are opposites. Metadata operations are tiny (hundreds of bytes), extremely numerous (billions of objects, many of them small), latency-sensitive, and need strong consistency and ordered scans. Data operations are large, bandwidth-bound, and need only durable, cheap storage. If you combined them, you would force either expensive low-latency storage for all bytes or slow storage for the index. Split, the metadata service can live on SSDs with a consensus protocol (Chapter 29) while the data plane lives on dense HDDs, and each is sized by its own growth curve: metadata grows with the number of objects, data grows with total bytes.

7. The metadata service

7.1 What it stores and why it is hard

Think of it as one gigantic sorted table: (bucket, key, version) -> record. A large region can hold trillions of rows. The record holds the fields above. The table must support: point lookup by key (every GET and HEAD), atomic insert or replace (every PUT), delete, and ordered range scan by prefix (LIST). It also has to be strongly consistent, since users now expect read-after-write (section 12), and highly available and durable, because losing metadata means losing every object even if the bytes are intact.

7.2 Sharding by key range

You cannot put a trillion rows on one machine, so the key space is partitioned into ranges (see Chapter 25). Because LIST must return keys in sorted order, range partitioning on (bucket, key) is natural: each shard owns a contiguous slice of the sorted key space, say all keys from photos/2026/a to photos/2026/m. A LIST with a prefix touches one or a few shards, in order. A hash partition would spread load evenly but would turn a LIST into a scatter-gather across all shards followed by a merge.

Range sharding brings the hot partition problem. If clients write keys with a monotonically increasing prefix such as a timestamp (2026-11-17-12-00-01.log), all new writes land in the last range, which becomes a hot shard. The service reacts by splitting hot ranges automatically and moving the halves to different machines (the same mechanism as in Bigtable-style tablets and HBase regions), but a split takes time, and a sudden spike can hit the limit before splits catch up. That is why S3 documentation talks about request rates "per prefix" and why high-throughput clients randomize or spread prefixes (section 14).

7.3 Atomicity and strong consistency

Every object write is a single-row operation, so it lands on exactly one shard and can be made atomic with that shard's replication protocol (a Paxos or Raft-style group, or a quorum-replicated log). The key invariant for correctness is the commit point: an object becomes visible exactly when its metadata row is committed. Bytes are written to storage nodes first. Only after enough shards are durably stored does the front end commit the metadata row. If the front end crashes before the commit, the shards on storage nodes are orphans: bytes that no key points to. They are harmless (invisible) and are cleaned up later by garbage collection (section 11). If the commit succeeds, the object is visible and the data is already safe. This ordering, data first and metadata commit last, is the single most important idea in the write path.

7.4 Where the metadata itself lives

Metadata shards are stored on SSD-backed nodes and replicated (often 3 or 5 copies) across zones, because they must answer in a few milliseconds. Indexes for hot ranges are cached in memory. The metadata service is the real scaling bottleneck of an object store, which is why "small objects" (section 14.3) are a problem: ten billion 1 KB objects need as much metadata as ten billion 1 GB objects, though they hold a millionth of the bytes.

8. The data plane: write and read paths

8.1 Chunking and shards

A big object is first divided into chunks (or "stripes"), commonly several megabytes each. This lets reads of different ranges be served by different nodes in parallel, and keeps unit sizes manageable. Each chunk is then protected either by replication or by erasure coding (section 9), producing several shards, each stored on a different disk, rack, or zone. Small objects are often packed together into one larger container file on disk so the node does not manage millions of tiny files.

8.2 The write (PUT) path step by step

  1. The client sends PUT /bucket/key. The front end authenticates the caller, checks the bucket policy and quota, and starts streaming the body.
  2. The front end asks the placement service for a set of target nodes for the object's chunks (for 6+3 coding, nine nodes in distinct failure domains).
  3. As bytes arrive, the front end computes a checksum, splits the data into 6 data pieces, computes 3 parity pieces, and writes the 9 shards to the 9 storage nodes in parallel. Each node writes the shard durably to disk (flushing to stable storage) and returns an acknowledgment with its own checksum.
  4. When enough shards are acknowledged (typically all of them, or a write quorum that still leaves the required safety margin), the front end commits the metadata row, atomically replacing the old version of the key.
  5. Only now does the front end return 200 OK with the ETag. From this moment any GET or LIST must see the new object.

8.3 The read (GET) path

  1. The front end authenticates, then looks up (bucket, key) in the metadata service and obtains the latest version's record and chunk map.
  2. For a range request it computes which chunks cover the range.
  3. It requests shards from the storage nodes. With erasure coding, the 6 data shards are enough to reassemble the chunk, so it normally reads those 6 with no decoding work. If one is slow or missing, it reads a parity shard instead and decodes. Many systems issue a few extra reads and use the first 6 that arrive, trimming tail latency (a "hedged" request).
  4. The front end verifies the shard checksums as it streams data back. If a checksum fails, it discards that shard, reconstructs from others, and flags the bad shard for repair.

Reads need no coordination between nodes and no locks, because shards are immutable once written. That is a large part of why object stores scale reads so well.

8.4 Storage node internals

On a storage node, shards are appended to big log-like extent files (for example 1 GB) rather than stored as one file per shard, which avoids file-system overhead and keeps writes sequential, the ideal pattern for hard disks. A small index (often a key-value store such as RocksDB on an SSD) maps shard ID to (extent, offset, length, checksum). Deletion marks space dead; compaction later rewrites extents that are mostly dead, to reclaim space (see log-structured storage in Chapter 19).

9. Durability: replication vs erasure coding

A single disk fails with an annual probability of very roughly 1 to 2 percent. At the scale of an object store with hundreds of thousands of disks, disks fail every day, and entire servers, racks, and occasionally zones fail too. Durability means that despite this, your bytes are not lost. The system achieves it by storing redundancy across independent failure domains (disk, server, rack, zone) and by repairing quickly after each failure.

9.1 Option A: replication

Store N full copies (commonly 3) on different failure domains. Reads can be served by any copy. Writes go to all copies. Recovery from a lost copy is simple: read one surviving copy and write a new one. The downside is cost: 3 copies is a 3x storage overhead (raw bytes stored divided by logical bytes), which is expensive at exabyte scale. Replication is still used for hot, small data, for metadata, and for places where simplicity and read latency matter more than cost.

9.2 Option B: erasure coding

Erasure coding (EC) is the technique behind RAID 5 and 6, generalized. Split a piece of data into k data shards and compute m parity shards using a code such as Reed-Solomon, so you store n = k + m shards in total. The magic property: any k of the n shards are enough to reconstruct the original data. So the system survives the loss of any m shards. Storage overhead is n / k.

Take 6+3: 6 data shards and 3 parity shards, 9 in total. The data survives any 3 simultaneous shard losses, and the overhead is 9 / 6 = 1.5x. Compare with 3-way replication, which survives 2 losses at 3x. So EC 6+3 is both cheaper (1.5x vs 3x) and safer (tolerates 3 failures vs 2). Other common schemes are 8+4 (1.5x, survives 4), 10+4 (1.4x), or very wide codes at 1.2x for cold data.

9.3 How erasure coding works (intuition)

The simplest example is a single parity shard: store data shards D1 and D2 plus P = D1 XOR D2. If D1 is lost, D1 = D2 XOR P. This is k=2, m=1 (RAID 5 style). Reed-Solomon generalizes this using arithmetic over a finite field, so each parity shard is a different linear combination of the data shards. Any k of the n shards give k independent equations, enough to solve for the k unknown data shards. You do not need to know the math in an interview; you need to know "any k of n suffice", the overhead n/k, and that decoding costs CPU and requires reading k shards.

The key tension: wider codes are cheaper in raw storage but costlier to repair. Rebuilding one lost 2 MB shard under 6+3 means reading six 2 MB shards (12 MB) across the network, a 6x amplification. Under 10+4 it is 10x. During a large failure (a rack going down), repair traffic can become a significant load on the network and disks, and a longer repair window means a higher chance of additional failures overlapping. Some systems use locally repairable codes (LRC), which add a few local parity shards so that a single lost shard can be rebuilt from a small group (say 6 neighbors rather than 12), trading slightly higher overhead for much cheaper common-case repair. Azure storage uses an LRC design.

Common practice is a hybrid: small objects and fresh hot data are stored replicated (3 copies), and a background process converts large and older data to erasure-coded form, getting the low overhead where it counts.

9.5 Durability math

Let us estimate the chance of losing an object using plain assumptions (they are optimistic, because failures are not perfectly independent, but they show the shape).

  • Disk annual failure rate (AFR): 2 percent. A disk dies on average once in 50 years.
  • Repair window: after any shard is lost, the system restores it in about 24 hours. During that window the remaining shards must not suffer enough additional failures to exceed tolerance.
  • Probability a given disk fails in one 24-hour window: p = 0.02 / 365, about 5.5 x 10-5.

Three-way replication. Data is lost if all 3 copies are gone in the same window: roughly p3 = 1.7 x 10-13 per window. Over 365 windows, about 6 x 10-11 per year. That is already around 10 nines of annual durability.

Erasure code 6+3 (9 shards). Data is lost if 4 or more of the 9 shards fail in the same window. The number of ways to pick 4 of 9 is 126. So the probability is about 126 x p4 = 126 x (5.5 x 10-5)4 = 126 x 9.2 x 10-18 = 1.2 x 10-15 per window, and about 4 x 10-13 per year. That is about 12 nines, better than 3x replication at half the storage cost.

Real systems get close to or better than these figures by spreading shards across zones, repairing in a few hours instead of a day, scrubbing so latent errors are caught, and designing for correlated failures (a bad firmware batch, a power event). Equally, real failure rates have correlated tails that the independent model ignores, which is why providers invest in diversity (different disk vintages and racks) and why the largest durability risks are often software bugs and human mistakes (an operator deleting the wrong thing), not random disk death.

Watch out Durability math assumes failures are independent and repair finishes within the window. If repair is starved (network saturated, a backlog of failed disks), the effective window grows and the probability of loss grows with the cube or fourth power of it. Repair speed is therefore a first-class durability control, not an afterthought.

9.6 Cross-region replication

Spreading shards across zones protects against a zone outage. It does not protect against a whole-region disaster, a destructive bug, or an account compromise. For that, enable cross-region replication: an asynchronous service copies each new object (and optionally deletes and metadata) to a bucket in another region, usually within seconds to minutes, with an SLA of 15 minutes for most objects on some providers. Replication is asynchronous, so there is a replication lag and the destination is eventually consistent relative to the source. Combine it with versioning and object lock so that a malicious delete is not propagated destructively.

10. Checksums, scrubbing, and background repair

Disks do not only die cleanly. They also suffer silent corruption: a flipped bit, a misdirected write, a bad sector that returns wrong data without an error. If a system trusted what it read, corruption would spread into repairs and replicas, producing bad data with good durability numbers. So integrity checking is built into every layer.

10.1 Checksums everywhere

  • The client can send a checksum (CRC32C, SHA-256) with the upload, and the service verifies that the bytes it received match, so corruption in transit is caught. Modern S3 clients compute these by default.
  • The front end computes a checksum per chunk and stores it in the metadata record.
  • Each shard carries its own checksum, checked by the storage node on every read and by the front end after receiving it.
  • Checksums are re-verified when data moves (repair, rebalancing, replication) so a bad copy never replaces a good one.

10.2 Scrubbing

Cold data may sit for years without being read, so latent corruption could accumulate unnoticed until the day you need it, by which time several shards may be bad. A scrubber is a background process that continuously reads every shard at a low rate (rate-limited so as not to hurt user traffic), recomputes the checksum, and reports mismatches. The goal is to detect corruption within a bounded period, such as every shard verified every few weeks. A bad shard is marked lost and handed to the repair system. Scrubbing is what makes the "repair window" assumption in the durability math true for data nobody reads.

10.3 Repair

The repair system maintains the invariant "every chunk has all n shards healthy". It learns of problems from several sources: the node that holds a shard went down (heartbeat timeout), a disk was ejected, the scrubber found corruption, or a client read hit a bad checksum. For each affected chunk it reads enough surviving shards, rebuilds the missing shards, and writes them to new healthy locations chosen by placement, then updates the chunk map in metadata.

Repair is prioritized by risk: a chunk that has lost 3 of 9 shards (one more loss away from data loss) is repaired before a chunk that lost 1. Repair is also rate-managed: fast enough to keep the window small, but bounded so a mass failure does not starve foreground traffic. Because the lost disk's contents are spread over thousands of other disks (each chunk's shards are placed on different sets), the rebuild work is parallelized across the whole cluster. A failed 20 TB disk is rebuilt not by one disk reading at 100 MB/s (which would take over two days) but by thousands of disks each contributing a little, finishing in hours.

10.4 Handling node failures vs temporary outages

A node that is merely rebooting should not trigger a mass rebuild. Repair systems apply a delay (for example 15 minutes to an hour) before treating a missing node as lost, because reconstructing a node's worth of data when it was only briefly offline wastes network. During the delay, reads of affected chunks work in degraded mode using other shards.

11. Garbage collection and deletes

Deleting an object in an object store is a two-stage affair, because the metadata and the data live in different systems and because multi-step operations can fail midway.

  1. Logical delete. DELETE removes (or version-marks) the metadata row, atomically. From that instant the object is gone to every client.
  2. Physical reclaim. The shards on storage nodes are no longer referenced. A garbage collector finds and frees them, typically after a safety delay.

Two kinds of garbage exist. Deleted data is shards whose metadata was removed. Orphans are shards that were written for a PUT or multipart part whose metadata commit never happened (the front end crashed, the client abandoned the upload). GC finds both by comparing what storage nodes hold against what the metadata service references: shards not referenced by any live metadata row (and older than a grace period) are deleted. The grace period matters, since a shard written a few seconds ago may belong to an in-flight upload whose commit has not yet landed; deleting it would corrupt the new object. Typical designs only collect orphans older than hours or days.

Further sources of garbage: unfinished multipart uploads (use a lifecycle rule "abort incomplete multipart uploads after 7 days"), old noncurrent versions of versioned objects (lifecycle rule "expire noncurrent versions after 30 days"), and delete markers with no remaining versions. On disk, deleted shards leave holes in extent files; compaction rewrites mostly-dead extents to reclaim space.

Interview tip Lead with the invariant: "bytes first, metadata commit last, delete metadata first, bytes last." Under that ordering, a crash anywhere can leave only unreferenced garbage, never a dangling pointer to missing data. Garbage is a cost problem, not a correctness problem, and a periodic sweep fixes it.

12. Durability vs availability, and the consistency model

12.1 What "eleven nines" means

S3 Standard advertises 99.999999999% (eleven nines) durability of objects over a given year. It means the expected annual loss rate is about 10-11 per object: if you store 10 million objects, you can expect to lose one object every 10,000 years on average. It is a statistical design target derived from failure and repair models like the one in section 9.5, not a guarantee about any one object and not a promise you will never lose data to your own mistakes (a deleted object is "durably deleted").

It says nothing about whether you can reach the data right now. That is availability: the fraction of requests that succeed. S3 Standard is designed for around 99.99% availability (about 53 minutes of unavailability per year), and its SLA is lower still. Durability and availability are independent properties: a system can lose no data and still be down for an hour. Cheaper classes (infrequent access, one-zone) keep high durability inside their scope but have lower availability designs, and one-zone classes are explicitly vulnerable to losing the whole zone.

12.2 Consistency model

Historically S3 had a confusing mixed model: read-after-write consistency for new object PUTs but only eventual consistency for overwrite PUTs, DELETEs, and LIST. A client could overwrite an object and then read the old version for a short while, or list a bucket and not see a key it just wrote. This broke many applications, especially big data jobs that wrote files and then listed them to find outputs, and required workarounds (an external consistency layer such as S3Guard).

Since December 2020, S3 provides strong read-after-write consistency for all operations in all regions: after a successful PUT or DELETE, any subsequent GET, HEAD, or LIST reflects it. Google Cloud Storage and Azure Blob Storage offer strong consistency as well. The enabler is the strongly consistent metadata layer from section 7: because every operation goes through the single authoritative shard for the key, which is replicated with a consensus-style protocol, a read after an acknowledged write always sees it, and LIST scans the same ordered, consistent index.

What strong consistency does not give you:

  • No transactions across objects. Writing two keys is two independent operations. Another client can see one without the other. There is no atomic multi-object rename or commit. Systems like Apache Iceberg, Delta Lake, and Hudi build table commits using a single atomic metadata-file swap (a conditional PUT).
  • Concurrent writers to one key: last writer wins, with the order defined by the commit order at the metadata shard. There is no locking; use conditional writes or versioning if you need to detect conflicts.
  • Cross-region replication is asynchronous, so a replica bucket in another region lags the source.
  • Caches in front (a CDN, a browser, a client SDK) can serve stale copies according to their TTLs.

Not every S3-compatible product is strongly consistent for listing, so for portable designs state your assumption explicitly.

12.3 List semantics

LIST returns keys in ascending lexicographic (UTF-8 byte) order, at most 1,000 per call, with a continuation token. Listing a bucket of billions of keys is slow and expensive (each page is a billed request), so never design an application that needs to list the whole bucket on a hot path. Keep your own index of objects in a database, and use LIST for administration and batch jobs, or use the provider's inventory feature, which delivers a daily file listing all objects.

14. Performance: partitions, request rates, small objects, throughput

14.1 Latency and throughput profile

A GET has a first-byte latency of roughly 10 to 100 ms for hot data in the standard class (a metadata lookup plus a disk seek on an HDD fleet), and then streams at the speed of the client connection. A single connection might reach 50 to 100 MB/s. Aggregate throughput is practically limited only by how many parallel requests you issue and by your network interface. Object storage is therefore excellent for bulk throughput and mediocre for chatty small random I/O. If you need single-digit-millisecond access, put a cache (Chapter 13) or a CDN (Chapter 12) in front, or use a premium low-latency class (such as S3 Express One Zone), which keeps data on SSD in one zone.

14.2 Prefix partitioning and request rates

Because the metadata is range-partitioned (section 7.2), request rate scales with the number of partitions your keys occupy. S3 documents that a bucket supports at least 3,500 write requests per second (PUT, COPY, POST, DELETE) and 5,500 read requests per second (GET, HEAD) per prefix, with no limit to the number of prefixes. In practice the service splits partitions as load grows, but a sudden step in load, or concentrating on one narrow range, returns 503 Slow Down until splits catch up.

Guidance for key design:

  • Avoid sequential hot prefixes if you will write at thousands per second. Keys like logs/2026-11-17-12-00-01-123.json concentrate on the tail. Put a short hash or random-looking component early: logs/a3/2026-11-17-... or hash the user ID (users/9f/ana/...) so load spreads over many ranges.
  • But keep listing in mind. Randomized prefixes make "list everything for date X" harder. Many designs use a stable partition prefix (a hash into, say, 256 buckets) plus a date, and run 256 parallel listings.
  • Put the grouping you list by near the front (tenant, then date), and the high-cardinality part later.
  • Avoid reading and writing the same key at huge rates: a single object is served from one place and cannot scale beyond a hot-object limit. Replicate copies under different keys, or front it with a CDN.

14.3 The small objects problem

Object stores are efficient for objects of megabytes and up. They are inefficient for billions of tiny objects (a few KB) for several reasons:

  • Metadata cost per object is roughly constant, so a 2 KB object costs the same index space as a 2 GB one, and may cost more in metadata than in data.
  • Erasure coding a tiny object produces nine tiny shards, wasting overhead on headers and padding; many systems replicate or pack small objects instead.
  • Request charges and latency are per request, so reading a million 1 KB objects costs a million requests, about 1,000 times more per byte than reading one 1 GB object.
  • Minimum billable sizes (for example 128 KB in infrequent-access classes) and minimum storage durations penalize small objects.

The standard fix is batching small items into larger objects: concatenate many records into one file (log batches, Parquet or ORC files in a data lake, tar or zip archives, a custom packfile with an index), and use range reads to fetch one record by offset. You keep a small index (in a database) mapping record ID to (object key, offset, length). This is the technique behind Facebook's Haystack for photos and many log pipelines.

14.4 Tuning throughput

  • Parallelize: use many concurrent connections, and split large GETs into ranged GETs (for example 8 to 16 MB each) run in parallel. Use multipart for uploads.
  • Keep connections warm (HTTP keep-alive, connection pooling) to avoid repeated TLS handshakes (Chapter 3).
  • Co-locate compute and data in the same region (and ideally zone) to cut latency and avoid transfer fees. Use a VPC gateway endpoint so traffic stays on the provider's network.
  • Retry with backoff and jitter, and retry slow requests (a request taking much longer than the median is re-issued) to trim tail latency.
  • Right-size objects to about 64 MB to 1 GB for analytics workloads, so each task does a few large sequential reads instead of many small ones.
  • Use transfer acceleration or a CDN for users far from the bucket's region.

15. Storage classes, lifecycle policies, and the cost model

15.1 Storage classes

Most data is accessed heavily when it is new and rarely afterwards: a photo is viewed constantly for a week, a log file is searched for a day, a backup is read only in a disaster. Object stores exploit this by offering storage classes (tiers) that trade access speed and price. Colder tiers charge much less per gigabyte-month, but charge more per retrieval, impose minimum storage durations, and may add retrieval delay.

How can archive be so cheap? Internally, it often means data on very dense disks or tape libraries, spun down or powered off, with wide erasure codes and batched, scheduled retrieval, so the cost per gigabyte falls sharply while latency rises. "Restore" from archive is an asynchronous job: you request it, wait, and the object becomes readable for a number of days as a temporary copy.

15.2 Lifecycle policies

You rarely move objects between classes by hand. A lifecycle policy is a set of rules on a bucket, matching objects by prefix or tag, that automatically transition objects to colder classes and expire (delete) them as they age. A background lifecycle engine scans the metadata (an efficient range scan) and performs the transitions and deletes.

15.3 The cost model

Object storage bills along three axes. Knowing them is how you decide between designs.

  1. Storage: per gigabyte-month, by class. Roughly 2 cents per GB-month for hot storage at major providers (about $23 per TB-month), a fraction of that for cold. Versioning, noncurrent versions, incomplete multipart parts, and replicas all count.
  2. Requests: per thousand or per million operations. Writes, lists, and copies cost roughly an order of magnitude more than reads (on the order of $0.005 per 1,000 PUTs and $0.0004 per 1,000 GETs for the hot class). Colder tiers charge more per request. Small objects make request cost dominate.
  3. Data transfer (egress): bytes leaving the provider's network to the internet, around 5 to 9 cents per GB at list price, falling with volume. Ingress is free. Transfer within a region is generally free, and cross-region or cross-zone transfer has a smaller fee. Egress is often the largest line item for media-serving workloads, and is the main reason to use a CDN with cheaper transfer, or an egress-free provider such as Cloudflare R2, or to keep compute in the same region as the data.

Numbers drift, so in an interview round them and state they are list-price approximations. Show the structure: "storage is cheap, requests are cheap per call but add up with small objects, egress is the surprise."

16. Access control and encryption

16.1 Who can do what

Every request must be authenticated (who are you) and authorized (are you allowed). S3-style systems layer several mechanisms:

  • Identity-based policies (IAM): attached to users or roles ("this role may GetObject on arn:aws:s3:::my-bucket/reports/*"). This is how your services get access, normally through short-lived role credentials rather than long-lived keys.
  • Resource-based bucket policies: attached to the bucket, JSON documents granting or denying actions to principals, including other accounts, with conditions (source IP range, require TLS, require encryption headers, VPC endpoint, MFA).
  • ACLs: legacy per-object or per-bucket grants. Modern guidance is to disable them and use policies.
  • Block Public Access: an account or bucket level master switch that overrides any policy that would make data public. Leaving this on prevents the most common breach: a misconfigured public bucket.
  • Evaluation rule: an explicit Deny anywhere wins. Otherwise access requires an Allow from identity policy or resource policy (within one account), and for cross-account access both sides must allow.

Requests are authenticated by a signature (AWS Signature Version 4): the client computes an HMAC over the canonical request (method, path, headers, payload hash, timestamp) with a secret key derived from its credentials. The server recomputes it. The secret never travels, replays are limited by the timestamp, and the payload hash makes tampering detectable. This is the same mechanism that presigned URLs use.

16.2 Encryption

In transit: TLS (HTTPS) for every request, enforceable by a bucket policy that denies non-TLS requests.

At rest has several variants. In all of them the object is encrypted with a unique data key, and the data key is itself encrypted ("wrapped") by a master key. This is envelope encryption, and it keeps the master key in a small, well-guarded key management service (KMS) while the bulk data is encrypted at line speed on the storage tier.

ModeWho holds the keyNotes
SSE-S3 (server-side, provider-managed keys)ProviderDefault, free, no setup. Encrypts all new objects by default today.
SSE-KMS (keys in a KMS you control)You control key policy and rotation, provider's KMS does the cryptoAudit trail of every key use, ability to revoke by disabling the key. Adds a KMS call per request (cost and rate limits, mitigated with bucket keys).
SSE-C (customer-provided key per request)You send the key with every requestProvider never stores the key. You must manage and transmit keys safely.

16.3 Presigned URLs and the upload pattern

The most common architecture for user content: the browser or mobile app never receives long-term credentials. It asks your API "I want to upload a profile picture". Your API authenticates the user, picks the object key (never let the client choose it freely, to avoid overwriting others' data or path tricks), optionally constrains content type and maximum size through a presigned POST policy, and returns a short-lived URL. The client uploads straight to object storage. For downloads of private content, your API checks permission and returns a presigned GET URL valid for a few minutes. The user never sees credentials, your servers carry no file bytes, and costs and bandwidth scale on the object store rather than on your fleet. A signed URL is a bearer token, so keep expiries short and avoid logging full URLs.

Watch out Do not trust uploaded files. Treat the bucket as untrusted input: scan for malware, validate content type rather than extension, serve user-uploaded HTML from a separate domain so scripts cannot run on your main origin, and process uploads asynchronously (queue plus worker) triggered by an event notification (section 18).

17. Common uses: CDN origin, data lake, backup target

17.1 Origin for a CDN

Object storage is the most common origin behind a CDN (Chapter 12). The bucket holds images, video segments, downloads, and static websites. The CDN caches objects at the edge so most requests never reach the bucket, which cuts latency and egress cost dramatically (CDN transfer is usually cheaper than direct egress, and the origin-to-CDN transfer is often discounted or free). Details that matter:

  • Lock the bucket to the CDN. Keep the bucket private and let only the CDN's identity read it (origin access control), so users cannot bypass the cache and the bucket cannot be scraped directly.
  • Immutable, versioned keys. Because objects are write-once, name them by content hash (/img/9f3c.../medium.webp) and set Cache-Control: public, max-age=31536000, immutable as object metadata. Updates become new keys, so no purge is needed.
  • Set the right metadata at upload: Content-Type, Cache-Control, Content-Encoding (when pre-compressed), because the origin passes these on.
  • Range requests from video players and download managers pass through the CDN to the object store, which supports them natively.
  • Protect hot-object limits: the CDN's origin shield collapses misses so the bucket sees one request per object per cache lifetime.

17.2 Data lake foundation

Analytics platforms use object storage as a data lake: raw and curated datasets stored as files, typically in a columnar format such as Parquet or ORC, partitioned by key prefix (events/dt=2026-11-17/part-0001.parquet). Compute engines (Spark, Trino, Presto, Athena, Snowflake external tables) are separate from storage, so you scale and pay for each independently and can spin compute up and down. Range reads let an engine fetch just the footer and the column chunks it needs. Large append-friendly files and parallel reads match the object store's strengths.

The gap is database semantics. Plain files on object storage have no transactions, no atomic multi-file commits, no schema evolution, and slow listing. Open table formats (Apache Iceberg, Delta Lake, Apache Hudi) add a layer of metadata files on top: a table snapshot is a manifest of data files, and a commit atomically swaps a pointer to the new manifest (relying on conditional writes or a small catalog). That provides ACID commits, time travel, and efficient planning without listing. See Chapter 37 for batch pipelines.

17.3 Backup and archive target

Object storage is the default destination for database dumps, snapshots, log archives, and compliance records because it is cheap, durable, and offsite. Good practice: enable versioning, write backups with object lock in compliance mode for ransomware resilience, replicate to another region or account, use lifecycle rules to move to archive tiers and expire after the retention period, encrypt with KMS keys, and test restores regularly (a backup you have never restored is a hope, not a backup). Read costs and archive restore delays matter for recovery time objectives, so keep recent backups in a fast tier (see Chapter 41).

17.4 Other uses

Static website hosting, software artifact and container image registries (whose layers are content-addressed blobs), machine learning datasets and model checkpoints, user-generated media, log and metrics archives, and as the large-payload side of the claim-check pattern (put the big payload in a bucket and send only the key through a queue; see Chapter 35).

18. Event notifications

Object stores can emit an event when something happens to an object: created (PUT, POST, copy, multipart complete), removed (delete, delete marker), restored from archive, lifecycle transition or expiration, replication failure, and so on. You configure a bucket to send matching events (filtered by prefix and suffix, such as uploads/ and .jpg) to a destination: a message queue, a pub/sub topic, an event bus, or a serverless function.

Design points to mention: delivery is generally at-least-once, so handlers must be idempotent (Chapter 32), keyed by bucket, key, and version ID; events for the same key can arrive out of order (use the sequencer or version to detect staleness); the notification path is separate from the write path, so there is a small delay and a rare chance of a missed event, so for critical flows pair events with a periodic reconciliation scan (the inventory report). Send events to a queue (Chapter 34) rather than directly to a slow consumer to get buffering and retries. Do not write the output back to the same prefix that triggers the event, or you create an infinite loop.

20. Interview form: "design your own S3"

This question appears as "design a blob store", "design Dropbox storage", or "design S3". A structured way to answer in 40 minutes:

20.1 Requirements and scope (5 minutes)

Functional: create buckets, PUT, GET (including ranges), DELETE, LIST by prefix, multipart upload for large files, versioning, access control. Non-functional: extreme durability (state a target such as eleven nines), high availability (four nines), strong read-after-write consistency, scale to trillions of objects and exabytes, cost-efficient for cold data, objects from bytes to 5 TB. Explicitly out of scope unless asked: in-place edits, POSIX semantics, transactions across objects, low-latency random IO. Do a quick size estimate (section 21 shows one).

20.2 API and data model (3 minutes)

Lay out the REST calls from section 4, the bucket and key model, immutable objects with whole-object atomic replace, versioning. Name the central decision: metadata plane separate from data plane.

20.3 High-level design (10 minutes)

Draw section 6's diagram: load balancer, stateless front ends, metadata service, placement service, storage nodes, background workers. Walk the PUT path and the GET path (section 8). State the commit-point invariant: bytes first, metadata last.

20.4 Deep dives (15 minutes), pick based on interviewer interest

  • Metadata scaling: range partitioning on (bucket, key), splitting hot ranges, replication via consensus per shard, directory service caching the range map, LIST by range scan.
  • Durability: erasure coding 6+3 or 8+4, shards across zones, failure-domain-aware placement, the durability math, scrubbing, prioritized repair, hybrid replicated-then-EC for small and hot data.
  • Large uploads: multipart with parallel parts, resume, atomic complete, abort and lifecycle cleanup.
  • Garbage collection: orphans, deleted data, grace periods, compaction.
  • Consistency: why metadata through a consensus group gives read-after-write and consistent LIST.
  • Hot spots and small objects: prefix design, batching, packing.
  • Tiering and cost: lifecycle engine, moving data to wide EC or archive media.
  • Security: signed requests, IAM and bucket policies, envelope encryption, presigned URLs.

20.5 Wrap up (5 minutes)

Failure scenarios (disk, rack, zone, metadata leader, repair storm), monitoring (durability risk metrics such as the count of chunks with fewer than n healthy shards, repair backlog, scrub coverage, error rates by partition, p99 latency), and what you would build later (cross-region replication, events, inventory, object lock).

Interview tip The strongest answers name the tradeoffs explicitly: "I chose range partitioning for ordered LIST at the price of hot-range risk, which I mitigate with auto-splitting." "I chose 6+3 over 3x replication because it halves storage and tolerates one more failure, at the price of 6x read amplification during repair and poor efficiency for tiny objects, so I replicate objects under 1 MB." Do not just list components.

21. Worked example: sizing a photo and video store

Problem. A social app has 50 million daily active users. Each user uploads on average 0.4 items per day (photos and short videos). Items average 3 MB (a blend: 2 MB photos, 30 MB video clips for a small fraction). Keep each item for at least 5 years. Each item is viewed about 20 times in its first week, almost never after a month. Design the storage tier and cost it roughly.

Step 1: Write and read load

  • Uploads per day: 50,000,000 x 0.4 = 20 million items per day, so about 230 per second on average, and about 700 per second at a 3x peak.
  • Ingest bytes per day: 20,000,000 x 3 MB = 60 TB per day, an average of about 5.6 Gbps (60 x 1012 x 8 / 86,400).
  • Views per day: 20 million x 20 = 400 million GETs per day within a week of upload, about 4,600 per second on average and 14,000 per second at peak. With a 95 percent CDN hit ratio (Chapter 12), the bucket sees about 700 GETs per second at peak.

Step 2: Capacity

  • Logical growth: 60 TB per day x 365 = about 22 PB per year. Over 5 years, about 110 PB logical (ignoring growth and thumbnails).
  • With 6+3 erasure coding (1.5x): 165 PB raw. With 3x replication it would be 330 PB, so EC saves 165 PB of disks.
  • Thumbnails and transcodes add maybe 20 percent, so budget about 200 PB raw. With 20 TB drives at 75 percent target fill (leaving headroom for repair and growth), each drive holds 15 TB usable: 200 PB / 15 TB is about 13,300 drives. At 60 drives per node, that is about 220 storage nodes.
  • Object count: 20 million per day x 365 x 5 = 36.5 billion objects, plus variants (say 4 per upload) so about 150 billion objects. At roughly 300 bytes of metadata per record, that is 45 TB of metadata, times 3 replicas = about 135 TB on SSD across the metadata shards. If each metadata shard holds 500 GB, that is about 90 shards, which is easily sharded and shows metadata is far smaller than data.

Step 3: Durability check (6+3, spread over 3 zones)

From section 9.5, per-chunk annual loss probability is about 4 x 10-13 in the model, or around twelve nines. Across 150 billion objects, the expected loss is 150 x 109 x 4 x 10-13, which is 0.06 objects per year in this simple model. Real durability targets are lower than the ideal model, so the design is consistent with an "eleven nines" claim. A zone outage leaves 6 of 9 shards reachable, so reads continue (degraded, using parity) and nothing is lost.

Step 4: Repair load

Assume a 2 percent annual failure rate across 13,300 drives: about 266 drive failures per year, roughly 0.7 per day. Each failed 20 TB drive (at 75 percent full, 15 TB of data) requires reading 6 x 15 TB = 90 TB to rebuild 15 TB. If 1,000 drives contribute 50 MB/s each for repair (50 GB/s), the rebuild finishes in 90,000 GB / 50 GB/s = 1,800 seconds, about 30 minutes of cluster-wide effort, in practice hours with throttling. Daily repair traffic is about 0.7 x 90 TB = 63 TB, a small fraction of the network, which shows that 6+3 is operationally comfortable. A rack failure (about 40 nodes) is a larger event but the same mechanism works.

Step 5: Cost with tiering

  • Hot data: most views occur in the first week and fall off within a month. Keep the last 30 days in Standard: 60 TB x 30 = 1.8 PB, at about $23 per TB-month is about $41,000 per month.
  • Move older data to Infrequent Access after 30 days and to cold Instant Retrieval after 90: roughly 108 PB x about $4.6 per TB-month (0.2x) is about $500,000 per month at steady state. If everything stayed in Standard, 110 PB x $23 is about $2.5 million per month. Lifecycle tiering cuts the bill by about 5x. (Cloud providers give volume discounts and you might run your own hardware instead, but the proportions are what an interviewer wants to see.)
  • Egress: with a 95 percent CDN hit ratio, the bucket serves origin traffic of only the 5 percent of views that miss: 5 percent of 1.2 PB per day is about 60 TB per day, mostly discounted origin-to-CDN transfer. Direct egress without a CDN would be 1.2 PB per day, around $100,000 per day at $0.09 per GB, a clear reason for the CDN.

Step 6: Upload and processing flow

The app asks the API for an upload. The API authenticates, picks a key such as u/<hash-of-user>/<uuid> (hash first, so writes spread over key ranges), and returns presigned multipart URLs (videos) or a single presigned PUT (photos). The client uploads straight to the bucket. An object-created event goes to a queue, workers scan the file, generate thumbnails and transcodes into v/<hash>/..., and write rows into a database recording the owner, key, and status. Reads go through the CDN with versioned URLs, and private items use short-lived signed URLs. A lifecycle rule cleans abandoned multipart uploads after 3 days.

What the interviewer wants to hear You sized throughput, capacity (with EC overhead), metadata, and repair; you separated hot and cold with lifecycle tiering; you kept bytes off your app servers with presigned URLs; you protected the bucket with a CDN; and you explained how durability holds with a failed disk, rack, or zone.

22. Common interview questions

When would you use object storage instead of a database or a file system?

Use object storage for large, immutable-or-rarely-changed blobs such as images, video, backups, logs, and datasets, especially when the volume is large or growing without a known limit. A database is a poor and expensive place for big blobs, and a file system gets hard to scale and replicate beyond a few hundred terabytes. The tradeoff is that you cannot edit in place and latency is tens of milliseconds, so keep the structured metadata about the blobs (owner, status, permissions) in a database and store only the bytes in the bucket.

Why does an object store separate metadata from data?

The two have opposite shapes: metadata is tiny, numerous, latency-sensitive, and needs strong consistency and ordered range scans, while data is large, throughput-bound, and just needs cheap durable bytes. Separating them lets metadata live in a sharded, consensus-replicated, SSD-backed index and the data on dense, inexpensive disks. Each scales along its own axis: metadata with the object count and data with the byte count. It also makes the commit point crisp: an object exists when its metadata row commits.

Explain erasure coding and why 6+3 can be better than 3x replication.

Erasure coding splits data into k data shards and adds m computed parity shards, so that any k of the n = k+m shards can rebuild the data. With 6+3 you store 9 shards for every 6 shards of data, a 1.5x overhead, and survive the loss of any 3. Three-way replication costs 3x and survives only 2 losses, so EC is half the cost and tolerates more failures. The price is higher repair cost (rebuilding one shard reads six), CPU for encoding and decoding, and inefficiency for tiny objects, which is why small and hot data is often replicated instead.

What does "eleven nines of durability" mean, and is it the same as availability?

Eleven nines means an annual object loss probability of about 10-11, so with ten million objects you expect to lose one every ten thousand years. It is a design target from redundancy and repair models, not a promise about any single object. It is not availability: availability is the fraction of requests that succeed, typically about 99.99 percent for standard classes. A system can be fully durable and still be unreachable for an hour. You raise durability with redundancy, scrubbing, and cross-region copies, and raise availability with stateless front ends, replicated metadata, and retries.

What is the consistency model of S3 today, and how do you get it?

Since 2020 S3 provides strong read-after-write consistency for PUT, DELETE, GET, and LIST, so a successful write is immediately visible to every later read in the same bucket. It works because every operation for a key goes through its authoritative metadata shard, which replicates with a consensus protocol, and the object becomes visible only when the metadata row commits, after the data is safely stored. It does not give multi-object transactions or atomic rename, and cross-region replication stays asynchronous, so those need application-level designs or table formats like Iceberg.

How does multipart upload work, and why use it?

The client initiates an upload and gets an upload ID, then uploads numbered parts (5 MB to 5 GB each in S3) independently, possibly in parallel and in any order, and finally sends a complete request listing the part numbers and their ETags, which stitches them into one object that becomes visible atomically. It gives parallel throughput, cheap retries of a failed part, resumability after a crash, and support for files over the 5 GB single-PUT limit. You should add a lifecycle rule to abort incomplete uploads, since the stored parts are billed until aborted.

How would you deduplicate uploaded files?

Use content addressing: hash the file (or fixed-size or content-defined chunks) with SHA-256, and use the hash as the storage identity, keeping an index from hash to location with a reference count. The client can compute the hash first and ask the server whether it already has it, skipping the upload entirely. You need garbage collection driven by reference counts to delete chunks no file uses. The caveats are the extra index, the cross-user privacy leak of confirming that a file already exists, and the fact that per-user encryption keys defeat dedup unless you use convergent schemes.

What happens if the server crashes in the middle of a PUT?

The write path stores the data shards first and commits the metadata row last, so a crash before the commit leaves only orphan shards that no key refers to. The client never got a success response, so it retries, and the object appears atomically when a retry commits. The orphans are found by garbage collection, which compares what storage nodes hold with what the metadata references, and are deleted after a grace period so that in-flight uploads are not damaged. A crash after the commit is harmless because the data was already durable.

Why can high request rates cause 503 errors, and how do you design keys to avoid it?

The metadata index is range-partitioned by key, so the leading part of a key decides which partition handles it. Sequential prefixes such as timestamps send all new writes to the newest range, which saturates before automatic splitting can spread it. To avoid it, put a hashed or well-distributed component early in the key so load fans out over many partitions, and have clients retry with exponential backoff and jitter. The tradeoff is that listing by time then needs parallel listings across the hash buckets, so keep your own index for lookups.

How do you handle billions of tiny objects?

Avoid storing them as individual objects, because per-object metadata, per-request fees, and erasure-coding overhead make them expensive and slow. Batch many small records into larger files (a few tens to hundreds of megabytes), keep an index in a database mapping each record to its file, offset, and length, and fetch individual records with range reads. This is how photo stores such as Haystack and log pipelines work, and why data lakes use big Parquet files rather than one file per row.

How do you let a mobile app upload a large video securely without passing it through your servers?

The app calls your API, which authenticates the user, chooses the object key, creates a multipart upload, and returns short-lived presigned URLs for each part (or for a single PUT if small). The app uploads parts directly to the bucket in parallel, tracking progress so it can resume, then calls your API to complete, which verifies the object and records it in your database and enqueues processing via an event. Credentials never reach the client, your servers carry no file bytes, and expiry and size constraints on the presigned URL limit abuse.

How would you reduce the cost of a 5 PB bucket where most data is rarely read?

First measure access patterns using storage analytics or inventory. Then apply lifecycle rules to transition aging data to infrequent, cold, and archive classes, or use automatic tiering when access is unpredictable, while accounting for minimum durations, retrieval fees, and per-transition costs. Clean up incomplete multipart uploads and old noncurrent versions, compress and batch small files, and put a CDN in front of popular content to cut egress. Keep compute in the same region as the data to avoid transfer fees.

How do you protect against accidental deletion and ransomware?

Turn on versioning so deletes only add a marker and overwrites keep old versions, add object lock in compliance mode for backup data so that nobody can delete it within the retention period, require MFA for destructive operations, apply least-privilege IAM and separate backup accounts, and replicate to another region or account. Also enable Block Public Access and monitor with access logs and event alerts. Finally, test restores, since protection only counts if recovery works.

23. Recap

  • Object storage stores whole, immutable blobs under flat keys in buckets, accessed over HTTP. Compared with block (in-place, low latency, one host) and file (shared tree), it gives the largest scale and lowest cost per gigabyte.
  • The API is PUT, GET (with ranges and conditionals), HEAD, DELETE, LIST by prefix, and multipart upload for large files. Presigned URLs let clients transfer directly without credentials.
  • The design splits a metadata plane (sharded, consistent, ordered index of keys to chunk locations) from a data plane (storage nodes holding shards). Write bytes first and commit metadata last, so a crash leaves only collectable orphans.
  • Erasure coding (for example 6+3) gives 1.5x overhead and survives three losses, versus 3x for triple replication. The price is repair read amplification, CPU, and poor fit for tiny objects.
  • Checksums, scrubbing, prioritized background repair, and garbage collection keep durability true over time. Durability (eleven nines) and availability (about four nines) are different properties.
  • Strong read-after-write consistency for all operations is standard today, but there are no multi-object transactions.
  • Performance: range-partitioned metadata means spread key prefixes, retry with backoff, parallelize ranges and parts, and batch small objects.
  • Storage classes and lifecycle rules cut cost as data cools. Watch the three cost axes: storage, requests, egress.
  • Secure with IAM, bucket policies, Block Public Access, envelope encryption (SSE-S3, SSE-KMS), and short-lived presigned URLs. Use events plus idempotent consumers for processing.
  • Typical roles: CDN origin, data lake base (with table formats), backup target (versioning plus object lock). Alternatives: HDFS, Ceph, MinIO, Swift.
