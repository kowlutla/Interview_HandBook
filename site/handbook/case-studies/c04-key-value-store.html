Case study 4 · Worked solutions

Design a Key-Value Store

We design a Dynamo-style, always-writable, horizontally scalable key-value store: how keys are spread over machines, how copies are kept, how conflicting writes are detected and merged, how the system heals itself after failures, and how each node stores data on disk. We finish by contrasting it with a strongly consistent store built on Raft.

How to approach this problem (read this first)

"Design a distributed key-value store" is huge, and the common failure is to dump every distributed systems term you know. This section gives a path that builds the design one forced decision at a time.

What the interviewer is really testing

The interface is trivial, so the test is whether you can derive the internals from the requirements. Three hard parts matter. First, placement: how data spreads over many machines and moves little when machines come and go. Second, the consistency and availability trade: what happens on a write when replicas are down or disagree, and how they converge. Third, what each node does with its disk. If you can explain why "always writable" forces conflicts, versions and repair, you have shown the real understanding.

The thinking order, step by step

  1. Ask the questions that choose the trade. Say: "Must writes always succeed, or is it more important that every read is correct?" Also ask value size, read to write ratio and latency target. This comes first because the answer (availability first, eventual consistency) decides the whole design family.
  2. Estimate data and nodes. Say: "10 billion keys at 2.2 KB is 22 TB, times 3 replicas is 66 TB, and with 50 percent disk headroom that is about 40 nodes." Do size before operations per second, because capacity sets the node count and then you can divide traffic by it.
  3. Draft the API with the context object. Say: "get returns the value plus a context; put sends it back, and r and w are per-request." The context is the hint that versions exist.
  4. Show the one-box design and why it fails. Say: "A hash map plus a log works on one machine, but it fails on capacity, throughput and availability, so I need both partitioning and replication." Neither alone is enough.
  5. Solve placement. Say: "Hash modulo node count reshuffles almost everything, so I use a ring with virtual nodes." Then name the preference list of three distinct nodes.
  6. Solve the read and write path with quorums. Say: "N is 3, W and R are 2, so read and write sets overlap, and one dead replica does not block." Then add sloppy quorum and hinted handoff for the availability promise.
  7. Handle disagreement. Say: "Concurrent writes will happen, so each value carries a version vector and conflicts are returned as siblings." Then name the three repair layers: hints, read repair, Merkle anti-entropy.
  8. Go inside a node. Commit log, memtable, SSTables, bloom filters, compaction, tombstones. Keep it short unless asked.
  9. Close with membership, multi-region and contrast. Mention gossip and a failure detector, LOCAL_QUORUM across data centers, and when you would choose a Raft store instead.

The decision points

  • AP or CP? Ask: what does a stale or conflicting read cost? A slightly old cart is cheap, so choose availability. A double-spent balance is not, which would point to consensus.
  • Hash modulo, ring, or fixed slots? Ask: how much data may move when a node joins? Only about 1/N, so a ring with virtual nodes (fixed slots are a valid alternative if you accept a coordinator).
  • Which R and W? Ask: is the workload read-heavy or write-heavy, and can I lose a node? 3, 2, 2 is the default; shift toward one side only with a reason.
  • Last-write-wins or vector clocks? Ask: is silently losing a concurrent update acceptable? For session data yes; for carts, keep siblings and merge.
  • Leaderless or leader-based replication? Ask: do I need ordering or compare-and-set? If not, leaderless gives lower latency and higher write availability.

Common mistakes on this problem

  • Hash modulo node count. Fix: use a ring with virtual nodes so adding a node moves about 1/N of data.
  • Claiming R + W greater than N is strong consistency. Fix: say it guarantees overlap only, not ordering.
  • Sizing 22 TB and forgetting replicas and compaction headroom. Fix: multiply by 3 and plan for about 50 percent fill.
  • Ignoring conflicts. Fix: explain version vectors and who resolves siblings.
  • Dropping tombstones too early. Fix: keep them longer than the repair interval plus allowed downtime.
  • Treating "node down" as "node removed". Fix: separate the two so a flaky network does not trigger data movement.

1. Problem statement and clarifying questions

The prompt is short: "Design a distributed key-value store." A key-value store is the simplest database interface there is. You give it a key (a short identifier such as cart:u8231) and it stores or returns an opaque value (a blob of bytes, typically a few kilobytes). There are no joins, no secondary indexes, no SQL. Because the interface is so small, the interesting part is entirely inside: how to make it hold more data than one machine can, answer in a few milliseconds, and keep working when machines die. Real examples include Amazon's Dynamo (the design this page follows), Apache Cassandra, Riak, and Voldemort. Redis and etcd are also key-value stores but make very different choices, which we compare in section 15.

In an interview the first move is to ask questions that pin down the trade-offs (the framework is in Chapter 1). The table lists the questions and the answers we will assume for the rest of the page.

2. Requirements and scope

2.1 Functional requirements

  • put(key, value, context): store a value under a key. The optional context is version metadata returned by an earlier read; it tells the store which version this write is based on (section 9).
  • get(key): return the value or, if concurrent writes conflicted, all the conflicting values plus a context.
  • delete(key, context): remove a key. Internally this is a write of a special marker called a tombstone (section 11).
  • Tunable consistency per request: the caller chooses how many replicas must answer.
  • Optional time-to-live (TTL) per key, after which the key disappears.

2.2 Non-functional requirements

  • High availability for writes: a write is accepted as long as a configurable minimum number of replicas are reachable, even if some nodes or a whole rack is down. Target 99.99% request availability.
  • Low latency: p99 under 10 ms in-region.
  • Horizontal scalability: add nodes to add capacity, with only a small fraction of data moving.
  • Durability: once a write is acknowledged, it survives the loss of any single node (and with a write quorum of 2 out of 3, any single node simultaneously).
  • Partition tolerance and eventual convergence: after a network partition heals, replicas converge to the same data without operator action.
  • Decentralized: no single master node whose failure stops the cluster. Every node can accept any request.

2.3 Explicitly out of scope

  • Multi-key transactions, secondary indexes, and range queries.
  • Strong (linearizable) consistency. We contrast with it, but our design does not provide it by default.
  • Fine-grained access control and encryption key management beyond a brief mention in section 14.
Key idea The requirements say "always writable" and "eventually consistent". That one decision shapes everything: it forces replicas to accept writes independently, which creates conflicts, which in turn needs versioning, conflict resolution, and background repair. A design that required strong consistency would be built from different parts (section 15).

3. Capacity estimation

Estimation techniques are in Chapter 2. We use round numbers and show every step.

3.1 Traffic

  • Average load: 200,000 operations per second (ops/s).
  • Read:write 4:1, so 160,000 reads/s and 40,000 writes/s on average.
  • Peak is 3 times average: 600,000 ops/s, which is 480,000 reads/s and 120,000 writes/s.

3.2 Data size

  • 10 billion distinct keys. Average key 50 bytes, average value 2 KB, plus about 100 bytes of metadata per record (version vector, timestamp, checksum). Record size is about 2,150 bytes, which we round to 2.2 KB.
  • Logical data: 10 billion × 2.2 KB = 22 TB.
  • Replication factor N = 3: 22 TB × 3 = 66 TB of stored data (before compression; real systems typically see 1.5 to 2 times compression for JSON-like values, which we treat as extra headroom).
  • New data per day: 40,000 writes/s average × 86,400 s = 3.46 billion writes a day. Most are overwrites of existing keys, so net growth is much smaller than 3.46 billion × 2.2 KB = 7.6 TB. Assume 5% of writes are new keys: about 0.38 TB of logical growth per day, 140 TB a year of logical data if sustained. We therefore plan capacity in steps and budget to add nodes continuously.

3.3 Node count

  • Each node has 4 TB of NVMe storage. An LSM store needs free space for compaction (section 11), so we aim for at most 50% fill, around 2 TB of data per node. The 66 TB needs at least 66 / 2 = 33 nodes. We choose 40 nodes (about 1.65 TB each, 41% full).
  • Replica operations at peak. Each write goes to 3 replicas: 120,000 × 3 = 360,000 replica writes/s. Each read with R = 2 contacts 2 replicas (one full read plus one cheaper digest read): 480,000 × 2 = 960,000 replica reads/s. Total 1.32 million replica operations/s.
  • Per node: 1,320,000 / 40 = 33,000 operations/s. A modern NVMe-backed LSM node handles this comfortably (tens of thousands of operations/s, with the memtable and OS page cache absorbing much of the read load).

3.4 Bandwidth and memory

  • Client writes at peak: 120,000 × 2.2 KB = 264 MB/s into the cluster. The coordinator forwards to two further replicas: 528 MB/s of internal traffic.
  • Client reads at peak: 480,000 × 2.2 KB = 1.06 GB/s out to clients. Digest reads add little because they carry only a hash.
  • Spread over 40 nodes this is well under 100 MB/s per node, far below a 10 Gbit/s (about 1.25 GB/s) network card.
  • Bloom filters (section 11): at about 10 bits per key, a node holding 10 billion × 3 / 40 = 750 million replica keys needs 750 million × 10 bits = 7.5 billion bits, about 0.94 GB of memory.
  • Memtable: 256 MB per node before flush. Page cache: whatever remains of, say, 64 GB RAM, which holds the hottest few percent of the 1.65 TB.
  • Tokens: with 256 virtual nodes per machine, the ring has 40 × 256 = 10,240 tokens, a tiny table that every node can hold in memory.
Interview tip State the replication multiplier explicitly. Candidates often size storage for 22 TB and forget that three copies means 66 TB, and that compaction headroom roughly doubles the raw disk you must buy.

4. API design

The client-facing API is small. Design details of APIs in general are in Chapter 5; here the unusual part is the context object that carries version information.

GET  /v1/kv/{key}?r=2
  200 OK
  { "values": [ {"value": "base64...", "ts": 1731800000123} ],
    "context": "opaque-token-encoding-the-version-vector" }
  // If concurrent versions exist, "values" holds several entries (siblings).
  // 404 if the key does not exist (or was deleted and the tombstone is current).

PUT  /v1/kv/{key}?w=2
  { "value": "base64...", "context": "opaque-token-or-empty", "ttl_seconds": 86400 }
  200 OK   { "context": "new-opaque-token" }
  // context from an earlier get tells the store which version(s) this write supersedes.
  // 503 if fewer than w replicas acknowledged in time (the write may still land later).

DELETE /v1/kv/{key}?w=2
  { "context": "opaque-token" }
  204 No Content

Three details deserve attention:

  • Opaque context. The client treats the context as a black box: read it from a get, send it back unchanged on the next put. Inside it is a version vector (section 9). Hiding it lets the server change the representation without breaking clients.
  • Per-request consistency knobs. r and w are the number of replicas that must respond. Defaults are r = 2, w = 2 with N = 3 (section 5.3).
  • Idempotency. A retry of the same put with the same context writes the same version and is safe. The details of idempotent design are in Chapter 32.

5. Data model and storage choice

Each stored record has this logical shape:

key        : bytes (up to 256 B)
value      : bytes (up to 1 MB), or a tombstone marker
version    : version vector, e.g. {nodeA:3, nodeC:1}
timestamp  : wall-clock time at the coordinator (used for last-write-wins and tombstone expiry)
ttl        : optional expiry time

5.1 Why not use an existing database per node?

Each node needs a fast, local, embedded storage engine for its share of the keys. The workload is point reads and writes with heavy write volume, and the data can be many times larger than RAM. A B-tree engine updates pages in place, which causes random writes. A log-structured merge tree (LSM tree) turns every write into a sequential append and organizes data into sorted immutable files, which suits write-heavy workloads and SSDs. Chapter 19 explains both families in depth; we pick an LSM tree and detail it in section 11. Many real Dynamo-style systems (Cassandra, Riak with LevelDB or Bitcask, ScyllaDB) do exactly this.

5.2 The three placement questions

The distributed part answers three questions for every key:

  1. Which nodes own this key? Answered by consistent hashing with virtual nodes (section 7).
  2. How many of them must agree for an operation to succeed? Answered by quorums (section 5.3).
  3. What happens when replicas disagree? Answered by versioning and repair (sections 9 and 10).

5.3 Replication and quorums in one paragraph

Every key is stored on N = 3 nodes, called its replicas (general replication theory is in Chapter 24). A write is sent to all N replicas but reported successful once W of them acknowledge. A read is sent to the replicas and returns once R reply. The rule R + W > N guarantees that every read set overlaps every write set in at least one node, so a read sees the most recent acknowledged write, provided the system is not using sloppy quorum (section 8) and no conflicting concurrent writes exist. With N = 3, W = 2, R = 2 we get 2 + 2 = 4 > 3. This tolerates one replica being down for both reads and writes.

N, R, WBehaviourUse when
3, 2, 2Balanced. R + W = 4 > 3. Survives one node down for reads and writes.Default.
3, 1, 3Fast reads, writes need all replicas. One node down blocks writes.Read-heavy, rare writes.
3, 3, 1Fast, highly available writes; reads need all replicas and may be slow.Write-heavy logging where reads are rare.

6. A first simple design, then the scaled architecture

6.1 Version zero: one box

The simplest key-value store is a hash map in memory with an append-only file for durability. A write appends a line to the log and updates the map; a restart replays the log. This gives microsecond reads, but fails three ways: capacity is limited to one machine's RAM, throughput to one machine's cores, and one failure loses availability. The next step is to copy the box (replication) and then split the data over many boxes (partitioning). Doing only replication does not add capacity; doing only partitioning loses data when a box dies. We need both.

6.2 The scaled architecture

The final design has no master. All 40 nodes run the same software. A client can send a request to any node, which then acts as that request's coordinator: the node that finds the replicas, forwards the work, collects replies, and answers the client. Nodes learn who is alive and who owns which token ranges through gossip (section 10.4). Clients can either send to any node through a load balancer, or use a smart client library that holds the ring map and sends straight to a replica of the key (saving one hop).

7. Deep dive 1: partitioning with consistent hashing and virtual nodes

7.1 Why not hash modulo the node count?

The first idea is node = hash(key) mod 40. It spreads keys evenly, but when you add a 41st node, mod 41 changes the answer for almost every key: roughly 40/41 of all data would have to move. For a 66 TB cluster that is a catastrophe. We need a scheme where adding or removing one node moves only about 1/N of the data. That scheme is consistent hashing, explained fully in Chapter 25 and Chapter 57.

7.2 The ring

Imagine the output space of a hash function (say 128 bits) bent into a circle. Each node is given one or more positions on the circle, called tokens. To find where a key lives, hash the key to get a position, then walk clockwise until you meet a token; that node is the key's primary owner. For replication factor N = 3, the key is also stored on the next two distinct physical nodes clockwise. This list of N nodes is the key's preference list.

7.3 Why virtual nodes

With one token per node, the segments between tokens differ wildly in length, so some nodes get much more data than others. Worse, when a node dies, its entire load falls onto its single clockwise neighbour. Virtual nodes (vnodes) fix both: each physical machine owns many tokens, say 256, scattered at random around the ring. Each node then owns many small ranges, the sum of which is close to 1/40 of the ring (the statistical spread shrinks as the number of tokens grows). When a node leaves, its many small ranges go to many different neighbours, so the load is shared. When a node joins, it takes a few small ranges from many existing nodes, so streaming happens in parallel from many sources and finishes fast. Machines with more disk can simply be given more tokens, which handles heterogeneous hardware.

Walkthrough. The circle is the hash ring, with physical nodes A, B and C each holding two small marks called vnodes (A1, A2, B1 and so on). 1. hash(key) puts the key at one point on the circle. 2. Walk clockwise to the first token, B1, which belongs to node B. That is replica one. 3. Continue to C1, node C, replica two. 4. The next token is A2, node A, replica three. If a token belongs to a node already chosen, skip it so all three replicas are on different machines. The right-hand notes show the benefit: when node D joins, it takes small slices from many nodes, so about 1/(N+1) of data moves, streamed in parallel. This design avoids hash modulo, which would reshuffle nearly every key. On a whiteboard draw the circle, drop the key, and walk clockwise out loud. With one token per node instead, ranges would be uneven and a failure would overload one neighbour.

7.4 How many vnodes?

Too few tokens give imbalance; too many make the ring metadata large, slow repair, and increase the number of range-level sessions (every Merkle comparison is per range). Typical systems used 256 tokens per node historically; newer ones use 16 or fewer with smarter token allocation. For our 40-node cluster, 256 tokens means 10,240 ranges. With 66 TB total data, each range holds about 6.4 GB across replicas (66 TB / 10,240), a convenient unit for streaming and repair.

7.6 Request routing: where does the coordinator run?

There are two designs. In the server-side coordinator design, the client sends to any node (through a load balancer); that node forwards to the true replicas. This keeps clients simple but adds a hop. In the smart client design, the client library downloads the ring map, computes the preference list itself, and talks directly to a replica, which acts as coordinator; this saves one network round trip and shifts load off the balancer. The client refreshes its map periodically and when a node answers "not my range". The Dynamo paper used both: a generic load balancer for simplicity and a partition-aware client for the lowest latency. Our default is the smart client with fall-back to any node, because at 10 ms p99 one hop (about 0.5 ms in a data center) is cheap but not free.

8. Request flows: put and get with quorums

8.1 The write path (put)

  1. The client sends put(key, value, context, w=2) to a coordinator, ideally one of the key's three replicas.
  2. The coordinator hashes the key, consults its ring map, and finds the preference list (nodes B, C, A in the figure).
  3. It builds the new version: it increments its own counter in the version vector from the supplied context (section 9.2) and stamps the record with its wall-clock time.
  4. It writes the record locally (commit log, then memtable) and sends the same record in parallel to the other two replicas.
  5. Each replica appends to its own commit log, updates its memtable, and acknowledges.
  6. As soon as W = 2 acknowledgements (counting the coordinator's own) arrive, the coordinator answers the client "success". The third replica's reply is not waited for; if it is slow or down, the system repairs it later (section 10).
  7. If fewer than W acknowledgements arrive before the timeout (say 50 ms), the coordinator returns an error. The write may still have reached one replica; the client may retry, and repair will reconcile.

8.2 The read path (get)

  1. The client sends get(key, r=2) to a coordinator.
  2. The coordinator asks the closest replica for the full value and the other replicas for a digest (a hash of their stored version), to save bandwidth.
  3. When R = 2 replies are in, it compares them. If the digests match, it returns the value.
  4. If the digests differ, the coordinator fetches full versions from both and compares version vectors: if one dominates the other (it is a strict descendant), the newer wins; if they are concurrent, both are returned as siblings to the client.
  5. The coordinator then issues read repair: it writes the winning version to any replica that returned a stale one, in the background (section 10.2).
Walkthrough. This is a sequence diagram with Client, Coordinator, Replica 2, Replica 3 and a crossed-out Replica 1 that is down. The top part is a put with W equal to 2. 1. The Client sends put with a context. 2. The Coordinator replicates to the replicas. Replica 1 never answers. 3. Replica 2 and Replica 3 each acknowledge. 4. It repairs the stale replica asynchronously, after replying. The point is that a quorum, not every replica, decides the outcome. If you remove read repair, hot keys would stay stale until anti-entropy runs.

8.3 What the quorum rule really promises

If R + W > N and the quorums are strict (always the real preference-list nodes), then a read quorum contains at least one node that saw the latest acknowledged write. The coordinator picks the newest by version. This is "read-your-writes" in the common case, but it is not linearizability: concurrent writes, a write that failed midway but landed on one node, and clock effects can all show surprising results (see Chapter 28). With sloppy quorums (next section) even this overlap guarantee is lost for the period of the failure.

Watch out A common wrong claim is "R + W > N gives strong consistency". It gives overlap, not an ordering guarantee. A write that is acknowledged by only one node and then reported as failed can still be read later; two concurrent writes can both succeed. True linearizability needs a single ordered log per key range, as in Raft (section 15).

8.4 Sloppy quorum and hinted handoff

Suppose replica 1 for a key is down. A strict quorum with W = 2 still succeeds (2 of the 3 respond), but if two replicas are down it fails and the store stops accepting writes for that key, which violates "always writable". A sloppy quorum relaxes this: the write goes to the first N healthy nodes on the ring walking clockwise from the key, even if they are not the key's usual replicas. Say node D, the next node after the three owners, is healthy. The coordinator sends the replica meant for the down node to D along with a hint: a note saying "this record belongs to node A; hand it over when A comes back". D stores the hinted data in a separate local area. When gossip reports that A is alive again, D streams the hinted records to A and then deletes them. This is hinted handoff.

Walkthrough. Replica B, Replica C and Replica A (marked down) are the key's usual owners; Node D is the next healthy node on the ring; the Coordinator sees that A is down. Phase 1, while A is down: 1. The coordinator writes normally to B and C. 2. It sends the copy meant for A to D, labelled with a hint saying the owner is A. 3. D stores it in a separate area. Phase 2, when A recovers: 4. D learns through gossip that A is back. 5. D streams the hinted records to A and then deletes them. The note says hints are kept for a limited time, for example 3 hours, after which anti-entropy must repair A. The drawing shows how the store stays writable when two of three owners are unreachable, instead of failing the write as a strict quorum would. Point at the arrow to D. The cost is that a read from the usual owners may miss the parked data until handoff. If D dies, those hints are lost.

Hinted handoff gives high write availability and speeds up recovery after short outages. It does not replace repair: hints can be lost if D itself dies, are capped by time and size, and do not help a node that was down for days. That is why Merkle-tree anti-entropy exists (section 10.3).

9. Deep dive 2: versioning, vector clocks and conflict resolution

9.1 Why conflicts happen

Because any W of N replicas can accept a write, and sloppy quorums let others accept it too, two clients can update the same key at the same time on different replicas, or one client can update a key while another replica is cut off. After the partition heals the replicas hold different values with no obvious "latest". We need a way to tell "version B came after version A" (so A can be dropped) from "A and B happened independently" (so both must be kept and merged). Background on time and ordering is in Chapter 27.

9.2 Vector clocks

A vector clock (also called a version vector in this context) is a list of (node, counter) pairs attached to each value. When a node coordinates a write, it takes the vector from the context the client supplied, increments its own counter (adding an entry if absent), and stores the result with the new value. Comparison rules:

  • Vector X descends from Y if every counter in Y is less than or equal to the matching counter in X. Then X is a newer version and Y can be discarded.
  • If neither descends from the other, the versions are concurrent (a conflict). Both are kept as siblings and returned to the reader.
Walkthrough. This timeline follows a shopping cart. 1. D1 is [milk] with vector {A:1}. 2. D2 is [milk, eggs] with {A:2}, coordinated by node A. 3. Client 1 and client 2 both read D2 while the replicas are cut off from each other. 4. Client 1 writes through A and creates D3 [milk, eggs, bread] with {A:3}. 5. Client 2 writes through B and creates D4 [milk, eggs, juice] with {A:2, B:1}. 6. The next get returns both D3 and D4 as siblings, because neither vector dominates the other: A is higher in D3 and B is higher in D4. 7. 9.4 Practical issues

  • Vector growth. Every new coordinator adds an entry. Dynamo bounded this by storing a timestamp per entry and truncating the oldest entries once the vector exceeds, say, 10 entries. Truncation can create false conflicts (never lost data, but extra siblings), which is safe. Another approach is to restrict coordinators to the key's top replicas, so only three node ids ever appear.
  • Sibling explosion. A client that repeatedly writes without a context creates a new sibling each time. Mitigate by requiring context on updates and by capping siblings with an alert.
  • Clock dependence. Vector clocks do not use wall clocks to order, which is exactly why they are safe under skew. LWW does, which is its weakness. Even our timestamp for tombstone expiry only needs rough accuracy.
  • Dotted version vectors are a refinement that avoids false siblings when the same client updates through different coordinators; mention it if asked for improvements.

10. Deep dive 3: how replicas heal (read repair, hints, Merkle anti-entropy)

Replicas drift apart for many reasons: a replica was down, a write reached only some replicas, a disk lost data, a hint expired. The system needs layers of healing that work at different speeds. Gossip and Merkle trees are explained in Chapter 33; here is how we use them.

10.1 The three repair layers

LayerTriggerScopeCostCatches

10.2 Read repair

Described in section 8.2, read repair compares the replies of a read and writes the newest version to any replica that was behind. Because it only touches keys that are read, it keeps hot data consistent cheaply but does nothing for data nobody reads. Some systems additionally query all N replicas for a small random percentage of reads (a background read repair chance) so that even lightly read keys get checked.

10.3 Merkle-tree anti-entropy

To compare two replicas of a key range holding millions of keys without sending every key, each replica builds a Merkle tree (hash tree). The leaves are hashes of small groups of keys (or key ranges, a fixed number such as 1,024 buckets per range). Each parent is a hash of its children's hashes, up to a single root hash. Two replicas first exchange root hashes. If equal, the whole range is identical, in one small message. If not, they exchange the child hashes, descend only into the subtrees that differ, and finally exchange the actual keys in the differing leaf buckets. The bandwidth is proportional to the number of differences, not the size of the data.

Walkthrough. Two trees are drawn side by side, one per replica. Each has a root, two middle hashes (h(1,2) and h(3,4)) and four leaves L1 to L4, where each leaf hashes a bucket of keys. 1. The replicas exchange root hashes and find they differ. 2. They compare children. h(1,2) matches on both sides, so the whole left subtree is skipped. 3. h(3,4) differs, so they compare L3 and L4. 4. Only L4 differs, so they exchange the keys in that one bucket and reconcile by version. Red boxes mark the differing path. This shows why anti-entropy is cheap in bandwidth: it costs about the number of tree levels in hash exchanges plus one bucket of keys, not a full copy of the range. The alternative, sending every key and comparing, would cost as much as the data. Draw the matching subtree greyed out. If trees are not built per range, a single mismatch would force a larger comparison.

Trees are built per key range (per vnode range) so that a mismatch limits itself to that range. Building a tree requires scanning the range's data on disk, so repairs are scheduled and throttled; a typical operational rule is to run a full repair on every range more often than the tombstone grace period (section 11) to avoid resurrected deletes. Because the tree is rebuilt as data changes, real systems recompute it at repair time rather than keep it live, trading CPU for simplicity.

10.4 Failure detection and gossip

Every node must know which other nodes are alive and which tokens they own, without a central registry. Nodes use a gossip protocol: once per second each node picks a few random peers and exchanges its view of the cluster, a table of (node, heartbeat counter, state, tokens, version). Heartbeat counters only increase, so a node that sees a newer counter for X knows X was alive recently. Information spreads epidemically in about log(N) rounds (for 40 nodes, a handful of seconds).

Failure detection on top of this uses an accrual failure detector (the Phi accrual detector, used in Cassandra and Akka). Rather than a fixed timeout, it tracks the history of heartbeat arrival intervals and computes a suspicion level phi: the larger phi, the less likely the node is alive. A node is marked down when phi exceeds a threshold (for example 8). This adapts to network jitter: a slow-but-live node on a congested link is not declared dead as readily as with a fixed 1-second timeout. Mark-down is a local opinion: it only controls whether this node tries to talk to the peer and whether it uses hints. It does not remove the peer from the ring; permanent removal is an explicit operator action (section 12). That keeps temporary glitches from triggering mass data movement.

Interview tip Say explicitly that "down" and "removed" are different states. A transient failure triggers hinted handoff; only a human or an automation policy declares a node dead for good and triggers re-replication. This separation prevents a flaky network from causing a rebalancing storm.

11. Deep dive 4: the storage engine on each node (LSM tree) and tombstones

Everything above is about the distributed layer. When a replica receives a write, it must persist it durably and quickly. The design is a log-structured merge tree, covered in Chapter 19. Here we apply it.

11.1 Write path on one node

  1. Commit log (WAL, write-ahead log). The write is first appended to a sequential log file on disk. This is fast (sequential I/O) and gives durability: after a crash the log is replayed. The log is synced either on every write (safest), in groups every few milliseconds (a good compromise, "group commit"), or periodically (fastest, risks losing the last interval's data if the machine crashes, but the other replicas still have it).
  2. Memtable. The record is inserted into an in-memory sorted structure (skip list or red-black tree), keyed by key. Reads check here first.
  3. Flush. When the memtable reaches its size limit (256 MB here), it becomes immutable, a new memtable takes over, and the old one is written out as a sorted file called an SSTable (sorted string table). The commit log segment covering it can then be deleted.
  4. Compaction. Over time many SSTables accumulate. A background process merges several SSTables into fewer, larger ones, keeping only the newest version of each key and dropping expired tombstones and overwritten data.

11.2 Read path on one node

  1. Check the memtable (and any memtable being flushed).
  2. For each SSTable, newest first, ask its bloom filter whether the key might be present. A bloom filter is a compact bit array that answers "definitely not here" or "maybe here". With about 10 bits per key the false-positive rate is about 1% (Chapter 57), so nearly all SSTables that do not contain the key are skipped with no disk read.
  3. For SSTables that pass, use the sparse index (cached in memory) to find the right block, read it (typically 4 to 64 KB), and look for the key.
  4. Merge the results across memtable and SSTables, choosing the newest version per the record's timestamp or version, and return.
Walkthrough. The top half is the write path and the bottom half is the read path on one node. Write path: 1. A put arrives and is appended to the Commit log, a sequential file that gives durability. 2. It is inserted into the Memtable, a sorted structure in RAM. 3. At 256 MB the memtable flushes into an immutable SSTable at the first level. 4. Background compaction merges several SSTables into a larger one, keeping the newest version and dropping old data and expired tombstones. Read path: 5. A get checks the Memtable first. 6. Bloom filters let it skip SSTables that cannot hold the key. 7. For any file that might, the Index finds the block and one disk read returns it. The picture shows why writes are fast (one sequential append plus a RAM insert) and why reads stay acceptable only because of bloom filters and compaction. If you remove the commit log, a crash loses the memtable.

11.4 Deletes and tombstones

SSTables are immutable, so a delete cannot erase data in place. Instead it writes a special record called a tombstone ("this key was deleted at version V"). Reads that find a tombstone as the newest version return "not found". The tombstone must be replicated like any write, and it must live long enough to reach every replica. If a replica was down during the delete and the tombstone were discarded too soon, that replica on return would still hold the old value, and anti-entropy would copy it back to the others: a deleted key resurrects. Hence the rule: keep each tombstone for a grace period (for example 10 days, longer than the maximum time a node may be down or the repair interval) before compaction may drop it. Tombstones have their own costs: a range that was heavily deleted and then read must skip many tombstones, which slows reads; and they consume space until compaction removes them. TTL expiry is implemented the same way, with an expiry marker that turns into a tombstone.

Watch out Do not set the tombstone grace period shorter than your repair cycle. If repairs run every 7 days and tombstones live 3 days, any replica that missed a delete can bring the deleted data back. The invariant is: repair interval plus longest tolerated downtime must be less than the grace period.

12. Membership change and rebalancing

12.1 Adding a node

  1. The operator starts the new node with a list of seed nodes (well-known nodes that new members contact first).
  2. It contacts the seeds, learns the ring through gossip, and picks its tokens (256 random positions, or tokens chosen to even out ranges).
  3. It enters a "joining" state. For every range it will take over, it streams the data from the current replicas. Because each of its 256 small ranges comes from a different neighbour, many nodes stream a little each in parallel, rather than one node bearing all the load. Moving about 1/41 of 66 TB is roughly 1.6 TB; at an aggregate 500 MB/s of throttled streaming that takes about 55 minutes.
  4. While joining, the new node receives new writes for those ranges (so it does not fall behind) but does not serve reads until streaming completes.
  5. Once complete it flips to "normal", gossips the new state, and the old replicas later delete the ranges they no longer own (a cleanup step run after the join finishes, because it competes for I/O).

12.2 Removing a node

A planned decommission streams the node's ranges to the next owners before it leaves, so data is never under-replicated. For a dead node that will not return, the operator runs a remove: the surviving replicas of each range stream data to the new owner to restore N = 3 copies. This is automatic repair of redundancy, and it competes for network and disk, so it is throttled. Replacing a dead node with a new one that inherits the same tokens is cheaper than a remove-and-add, because only the replacement's own ranges move.

12.3 Avoiding conflicting views of the ring

Because membership is gossip-based, two operators might start changes at the same time, or different nodes might briefly disagree about the ring. Dynamo used a ring-change log with versions; Cassandra historically allowed only one bootstrapping node at a time per cluster and later added consistency checks. The safe practice is: serialize topology changes, and make a node refuse to serve ranges it does not believe it owns (clients then re-fetch the ring). Some modern systems store topology in a small strongly consistent service (for example a Raft group, Chapter 29), keeping the data path decentralized while the control plane is linearizable. That is a good point to mention when asked "how do you avoid split-brain in membership?".

13. Scaling, hot keys, caching and multi-data-center

13.1 Hot keys and hot partitions

Hash partitioning spreads keys evenly, but a single extremely popular key (a celebrity profile, a feature flag read by every request) still lands on three nodes, which may be overwhelmed even though the cluster is idle. Remedies, from cheapest:

  • Client-side or edge caching with a short TTL for read-heavy hot keys (Chapter 13). A 1-second TTL cuts reads of a key to at most one per second per cache.
  • Read from more replicas: use R = 1 for that key class, spreading reads over all three replicas.
  • Key splitting: store the hot value under key#0 ... key#k (k copies), reading a random one and writing all. This works for read-heavy hot keys; for hot counters, shard the counter and sum on read.
  • Detect and adapt: nodes sample request counts per key and report outliers so operators or an automatic policy can raise the replication factor for that key.
  • Request coalescing at the coordinator: many concurrent reads for the same key share one replica fetch.

Hot partitions arise too from skewed key design (for example prefixing every key with the date). The fix is key design: put a high-cardinality component first. See Chapter 25 for the general discussion.

13.2 Rack and data center awareness

Plain "next two nodes clockwise" might choose three machines in the same rack, so one top-of-rack switch failure loses all copies. The placement strategy therefore walks the ring but skips nodes in racks already used by this key until it has spread the replicas over distinct racks (or availability zones). Across data centers, it ensures each region holds a defined number of replicas.

13.3 Multi-data-center replication

With three data centers (DC-A, DC-B, DC-C) we keep N = 3 replicas per data center (9 total) or a smaller number such as 3 + 2 + 2 depending on cost. Each data center forms a local ring segment, and the coordinator sends writes to replicas in all data centers but waits for acknowledgements only from a local quorum. Two common levels:

  • LOCAL_QUORUM: wait for 2 of the 3 replicas in the coordinator's data center. Latency stays in single-digit milliseconds; cross-region copies arrive asynchronously (typically within 100 ms to 300 ms depending on distance). A data center failure loses at most the last few hundred milliseconds of writes from the local view, but other data centers carry on.
  • EACH_QUORUM or global quorum: wait for a quorum in every data center. It gives stronger cross-region guarantees but adds a cross-region round trip (70 to 150 ms) to every write and loses availability if one region is unreachable.

Our default is LOCAL_QUORUM reads and writes, which gives read-your-writes within a region and eventual consistency across regions. Conflicts across regions are exactly the concurrent-writes case handled by vector clocks, and cross-region repair runs through the same hinted handoff and Merkle machinery. Region-level patterns (active-active, failover, data residency) are in Chapter 26.

Walkthrough. Three data center regions are drawn, with DC-A as the region where the client lives. 1. The Client talks to a Coordinator in DC-A. 2. The coordinator sends the write to its three local replicas in DC-A and waits for two of them to acknowledge; this is LOCAL_QUORUM and it is the only thing the client waits for. 3. In the background the write is copied to the three replicas in DC-B and the three in DC-C, usually 100 to 300 ms behind. 4. If DC-C is unreachable, hints are stored and replayed later. The drawing shows a design where the write path never pays a cross-region round trip, avoiding the alternative of EACH_QUORUM, which adds 70 to 150 ms and fails if one region is unreachable. Point at the dashed arrows as asynchronous. The cost is eventual consistency between regions, which vector clocks handle as concurrent writes.

13.4 Caching

The store itself is the cache-like tier of many systems, so extra caches mostly exist inside the node: the memtable, the OS page cache, a row or key cache, and the bloom filters and index summaries kept in RAM. Do not add a separate cache in front unless profiling shows hot keys that justify it (section 13.1).

14.2 Consistency and idempotency decisions

  • Default is eventual consistency with N = 3, R = 2, W = 2; the application chooses stronger or weaker per request.
  • Writes are idempotent: replaying the same record with the same vector is a no-op because replicas keep only versions not dominated by others.
  • Reads can return siblings; the client library offers a merge callback so that application developers do not have to hand-write sibling handling each time.
  • For operations needing true compare-and-set (unique usernames, leases), this store is the wrong tool; use a consensus-backed store or a "lightweight transaction" feature built on Paxos per key (section 15).

14.3 Security and abuse

  • Mutual TLS between clients and nodes and between nodes (Chapter 55); authentication of clients with tokens and per-keyspace authorization.
  • Encryption at rest per SSTable or at the volume level; keys held in a key management service.
  • Per-tenant quotas on request rate and stored bytes to stop a noisy tenant from filling disks or starving others (see rate limiting in Chapter 16); a maximum value size (1 MB) to bound memory and network spikes.
  • Gossip and the admin interface live on a private network; a rogue node must not be able to join the ring without credentials.

14.4 Monitoring and SLOs

General approach is in Chapter 54. For this system the signals that matter:

  • SLOs: 99.99% of requests succeed; p99 read and write latency under 10 ms in-region; p99.9 under 50 ms.
  • Per node: pending compactions, SSTable count per read (target under 5 at p99), bloom filter false-positive rate, memtable flush time, commit log sync latency, disk fill percent (alert at 60%), dropped messages.
  • Cluster: gossip state disagreements, hints stored and replay lag, read repair rate (a rising rate means replicas are drifting), time since last successful repair per range, tombstones scanned per read.
  • Client side: sibling count per read, quorum failure rate, speculative retry rate.

14.5 Cost notes

  • Storage dominates: 40 nodes with 4 TB NVMe each hold 66 TB of data in 160 TB raw. Compression (often 1.5 to 2 times) and moving cold data to a cheaper tier shrink it.
  • Replication factor and number of data centers multiply cost directly. Three data centers with three replicas each is 9 copies of every byte; ask whether every key space needs it.
  • Cross-region bandwidth is billed by cloud providers; compress replication traffic and avoid cross-region reads.
  • Repair and compaction consume I/O; sizing nodes for 50% headroom is a cost you pay for stable latency.

15. Contrast: a strongly consistent, Raft-based key-value store

An interviewer will often ask "what if I need linearizable reads and writes?". Stores like etcd, Consul, and the key-value layer of CockroachDB or TiKV take a different path, using consensus (see Chapter 29). The key range is replicated by a Raft group of typically 3 or 5 nodes: one is the elected leader, all writes go through the leader, which appends them to a replicated log and commits an entry once a majority has stored it. Every replica applies the same entries in the same order, so all copies are identical, and reads served by the leader (with a lease or read-index check) see the latest committed write. There are no siblings, no vector clocks, and no read repair, because divergence is prevented rather than repaired.

Key idea The choice follows the cost of a stale or conflicting read. If a stale read costs a slightly outdated cart, choose leaderless and availability. Many real platforms use both: a Raft store for small, critical metadata (such as our ring topology) and a Dynamo-style store for the bulk data.

15.1 Why not just use Raft everywhere?

You can, with multi-Raft (thousands of groups, one per range), as CockroachDB and TiKV do. The cost is that every write needs a majority round trip and a leader; a multi-region deployment pays cross-region latency or sacrifices consistency across regions; and the store is unavailable for writes on the minority side of a partition. For workloads that need 99.99% write availability with single-digit-millisecond latency in each region, leaderless replication with tunable quorums remains the better fit.

16. Evolution, phasing and alternatives not chosen

16.1 What to build first

  1. Phase 1 (MVP): single-node LSM engine with commit log, memtable, SSTables, bloom filters, and a simple get/put/delete API. Prove durability and performance on one box.
  2. Phase 2: consistent hashing with vnodes, static membership, N = 3 replication with quorums, last-write-wins. This is already a usable distributed store.
  3. Phase 3: gossip membership, failure detection, hinted handoff, read repair, node join and decommission with streaming.
  4. Phase 4: Merkle anti-entropy repair, tombstone grace periods, vector clocks with siblings for selected key spaces, rack awareness.
  5. Phase 5: multi-data-center replication, per-tenant quotas, hot-key tooling, backup and point-in-time restore.

16.2 What changes at 10x scale

  • 400 nodes and 220 TB logical (660 TB replicated). Gossip cost grows but remains modest (each node still talks to a few peers per second); the ring map is still small (about 100,000 tokens). Reduce tokens per node (for example 16 to 32 with smart allocation) to keep repair unit counts manageable.
  • Repair becomes the operational bottleneck: a full repair across 660 TB takes days. Adopt incremental repair (only data written since the last repair) and subrange repair, and run it continuously at low priority.
  • Large clusters benefit from cells (Chapter 42): several independent clusters of 40 to 100 nodes, with tenants assigned to cells, so a bad compaction storm or software bug only affects one cell.
  • Tail latency becomes dominant: add speculative retries, replica selection by latency, and admission control.
  • Cold data (large share of 220 TB) moves to a tiered store or is expired with TTLs.

16.3 Alternatives considered and not chosen

  • Master-based sharding (HBase, Bigtable style): a master assigns key ranges to servers, storing data on a distributed file system. Gives strong consistency per row and range scans, but depends on a master and a coordination service, and writes are unavailable during region reassignment.
  • Fixed hash slots with a configuration service (Redis Cluster): simpler movement, but replication is asynchronous with a primary per slot, so acknowledged writes can be lost at failover.
  • Chain replication: strong consistency with high throughput by passing writes down a chain, reads from the tail; needs a reliable failure detector and configuration master.
  • Quorum plus CRDTs everywhere: removes siblings entirely but constrains the data model to mergeable types.

17. Interview questions and strong answers

Why use consistent hashing with virtual nodes instead of hash modulo N?

With modulo, changing N changes the result for nearly every key, so adding one node to a 40-node cluster would move about 97.5% of the data. Consistent hashing places nodes and keys on a ring so that adding a node only takes over the ranges adjacent to its tokens, roughly 1/(N+1) of the data. A single token per node leaves uneven loads and dumps a failed node's entire load on one neighbour, so we give each machine hundreds of vnodes: the load evens out statistically, data is streamed from many peers in parallel when a node joins, and bigger machines can simply get more tokens.

With N = 3, how do you choose R and W, and does R + W > N give strong consistency?

R = 2 and W = 2 is a balanced default: any read set overlaps any write set in at least one replica, and the system tolerates one replica being down for both operations. R = 1, W = 3 favours reads, R = 3, W = 1 favours writes. But R + W > N only guarantees overlap, not linearizability. A write acknowledged by one node and reported failed can still be seen, concurrent writes can both succeed and become siblings, and sloppy quorums break overlap during failures. If you need a total order or compare-and-set, you need consensus rather than quorum overlap.

What is a sloppy quorum and what does it cost?

When some of the key's designated replicas are unreachable, the coordinator writes to the next healthy nodes on the ring instead and tags the data with a hint naming the intended owner. This keeps writes available even if two of three replicas are down. The costs are that a later read quorum drawn from the designated replicas may not include the node holding the hint, so the read can miss the latest write until handoff completes, and that hints can be lost or expire. It trades consistency for availability and must be paired with read repair and anti-entropy.

Explain vector clocks with an example, and when you would rather use last-write-wins.

A vector clock is a set of per-node counters attached to each value; a write increments the coordinating node's counter on top of the version the client read. If one vector dominates another, the dominated version is obsolete; if neither dominates, the writes were concurrent and both are kept as siblings. For example {A:3} and {A:2,B:1} are concurrent because each has a counter the other lacks. The client merges and writes back with a context covering both. Last-write-wins is acceptable when losing a concurrent update is harmless (session heartbeats, last-seen timestamps) and you prefer the simplicity of no siblings, but it depends on synchronized clocks and silently drops one of two concurrent writes.

How do replicas become consistent again after a node was down for two days?

Hinted handoff only covers a short window (hours), so after two days the hints have expired. The node rejoins, replays its own commit log, and then repair takes over: Merkle-tree anti-entropy compares each of its ranges with the other replicas, finds the differing leaf buckets with a few hash exchanges, and streams just those keys. Read repair also fixes keys as clients read them. The crucial operational point is to finish this repair before the tombstone grace period expires, otherwise deleted data can reappear.

Why are tombstones needed, and what is the risk of removing them too early?

In an LSM tree, files are immutable, and in a replicated system a delete must also reach replicas that may be down. A tombstone is a versioned "deleted" record that propagates like any write. If it is dropped before all replicas have it, a replica that missed the delete still holds the old value and later anti-entropy will treat it as the only version and copy it back, resurrecting the key. So tombstones are retained for a grace period longer than repair interval plus the maximum tolerated downtime. The downside is that many tombstones slow reads and use space, so delete-heavy workloads need tuning or a different data model such as time-bucketed tables.

How does the LSM tree on each node get fast writes, and how do you keep reads fast?

A write is an append to the commit log (sequential, so fast and durable) plus an insert into the in-memory memtable; no random disk write happens. Memtables flush to immutable sorted SSTables, and background compaction merges them to bound their number. Reads check the memtable, then use per-SSTable bloom filters to skip files that cannot contain the key, followed by a sparse index and one block read. Leveled compaction limits how many files can contain a key to about one per level, which keeps read latency predictable at the price of more write amplification.

How would you handle a hot key that receives 100,000 reads per second?

The three replicas of that key cannot absorb it while the rest of the cluster idles. First add a short-TTL cache in front (client or edge), since a one-second TTL collapses 100,000 reads to at most one per cache per second. Next let reads use R = 1 across all replicas and coalesce identical in-flight reads at the coordinator. If it is still too hot, split the value into several copies under suffixed keys and read a random one; for hot counters, shard and sum. Finally monitor per-key request rates so you can detect these keys automatically.

How do you add a node without downtime or a rebalancing storm?

The new node joins, learns the ring through gossip, picks its vnode tokens, and streams the data for those ranges from the current owners while receiving new writes for them. It does not serve reads until streaming completes. Because its 256 small ranges come from many different peers, each source sends only a small portion, and the streaming is throttled so foreground latency is protected. Old owners delete the moved ranges only after the join completes. Topology changes are serialized so two concurrent changes cannot give inconsistent ownership.

When would you choose a Raft-based store instead of this design?

When a stale read or a conflict is unacceptable: leader election and locks, configuration, unique-key constraints, financial balances, or metadata such as the cluster ring itself. Raft gives linearizable reads and writes and supports compare-and-set because a single leader orders the log, but writes pause during elections and the minority side of a partition cannot write. The leaderless store stays writable on both sides and has lower latency across regions, at the cost of siblings and eventual consistency. Many production systems combine them, keeping small critical metadata in Raft and bulk data in the leaderless store.

How does the failure detector decide a node is down, and what happens next?

Nodes gossip heartbeat counters. Each node tracks the arrival times of those heartbeats and a phi accrual detector converts the gap since the last one into a suspicion value, compared with a threshold. This adapts to network jitter better than a fixed timeout. Marking a node down is local and reversible: it stops sending requests there and starts storing hints, but data does not move. Only an operator action or a long-outage policy removes the node from the ring and triggers re-replication, which stops flaky networks from causing mass data movement.

18. Recap

  • Requirements shaped the design: always-writable, low latency, horizontally scalable, eventually consistent, so a leaderless, Dynamo-style architecture.
  • Numbers: 200,000 average and 600,000 peak ops/s, 22 TB logical, 66 TB with N = 3, about 40 nodes with 256 vnodes each, about 33,000 replica operations/s per node at peak.
  • Partitioning: consistent hashing with vnodes spreads keys evenly and moves about 1/N of data on membership change. Replicas are the next distinct nodes (and racks) clockwise.
  • Replication: N = 3, tunable R and W (default 2 and 2). R + W > N gives overlap, not linearizability. Sloppy quorum plus hinted handoff keeps writes available.
  • Versioning: vector clocks detect concurrent writes; siblings are returned for client merge, with LWW and CRDTs as alternatives.
  • Healing: hinted handoff for short outages, read repair for hot keys, Merkle anti-entropy for everything else; gossip and a phi accrual detector track membership without a master.
  • Node storage: commit log, memtable, SSTables, bloom filters, leveled compaction; deletes are tombstones kept longer than the repair interval.
  • Operations: hot keys (cache, split, spread reads), rack and data center aware placement, LOCAL_QUORUM across regions, throttled streaming.
  • Contrast: a Raft-based store gives linearizability and compare-and-set but is unavailable on the minority side of a partition; choose by the cost of a stale read.
