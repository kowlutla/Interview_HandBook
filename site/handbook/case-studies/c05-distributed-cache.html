Case study 05 · Worked solutions

Design a Distributed Cache

We design a shared in-memory cache service in the style of Memcached or a Redis cluster: many servers that together hold hundreds of millions of hot objects, so that the databases behind them see only a small fraction of the traffic. The hard parts are not "put and get". They are spreading keys without reshuffling everything, surviving node failures, stopping stampedes and hot keys, and keeping cached data close enough to the truth.

How to approach this problem (read this first)

What the interviewer is really testing. Nobody is checking whether you know what a hash table is. The interviewer wants to see three things. First, can you spread keys over many machines so that adding a machine does not wipe the cache (consistent hashing or slots). Second, can you keep the database alive when the cache misbehaves: a node dies, a key becomes hot, or a popular entry expires and thousands of callers rush to rebuild it. Third, can you be honest about consistency, meaning how the cached copy and the database copy drift apart and how you bound that drift. Everything else is detail around these three.

The thinking order, step by step

  1. Pin down what kind of cache it is. Say: "Is this a cache in front of a database, so losing data is safe, or a store we must not lose?" Ask this first because it decides everything: a cache may drop entries, a database may not. Our answer is a cache, no durability promised.
  2. Ask for the scale, then fix three numbers. Say: "What is peak operations per second, how many keys, and how big is a value?" Estimate memory first (1 billion keys times about 1.1 KB gives about 1.3 TB) because memory, not request rate, decides how many machines you need. Then compute request rate per node and see that it is modest.
  3. Ask about the hit rate target and what sits behind the cache. Say: "If the hit rate is 98%, the database only sees 2% of reads. What happens to it if the hit rate drops?" This creates the idea that the database is sized for misses, which is where the hardest failures come from.
  4. Draft the API. Say: "I will keep it small: get, multi-get, set with a TTL, delete, compare-and-set." Draft it before the design so the interface you promise drives what the servers must do. Mention that get may return a lease, as a hint of where you are going.
  5. Draw the one-box design and break it. Say: "One server with cache-aside works first. It breaks on memory, request rate, single point of failure and restart." Each break becomes one new component: sharding, replicas, a control plane.
  6. Choose the sharding scheme. Say: "Modulo would reshuffle 97% of keys when I add a node, so I will use slots or a hash ring." This comes right after the one-box design because it is the first fix.
  7. Walk the read and write flows. Say: "On a miss the app reads the database and fills the cache. On a write, commit to the database then delete the key." Tracing the flows exposes the races, which you then name.
  8. Deep dive the dangers. Say: "Now the three things that cause outages: stampedes, hot keys, and stale data." Pick the interviewer's interest, but cover leases, near-caches and the stale-fill race.
  9. Close with failure, scale and operations. Say: "If a node dies, 1/32 of keys miss; here is how the database survives that, and how I would resize."

The decision points

  • Cache-aside or write-through? Ask: should the cache know about the database? Here the cache must be safe to wipe at any time, so cache-aside with delete on write wins.
  • Memcached or Redis? Ask: do I need replication, failover and structures built in, or the simplest and most memory-efficient store? At 47,000 ops/s per shard either works, so the choice follows team size and operations.
  • Modulo, ring or slots? Ask: how much moves when I resize? Only a fixed slot table or a ring with virtual nodes keeps that near 1/N.
  • Client-side routing or proxy? Ask: how many languages and tenants? Many tenants and quotas push you to a proxy tier; one latency critical path pushes you to a smart client.
  • Replica or no replica? Ask: what does a cold shard cost the database? About 45,000 extra reads per second, so a replica buys a lot.

Common mistakes on this problem

  • Using hash modulo N. Fix: say out loud that a resize would empty the cache, and switch to slots or a ring.
  • Treating the cache as a database. Fix: state early that losing any entry must be safe, and refuse write-behind.
  • Ignoring the database behind the cache. Fix: always translate a cache failure into extra database reads per second.
  • Forgetting hot keys. Fix: remember that more shards do not help one key; use a near-cache or copies.
  • Updating the cache on write instead of deleting. Fix: commit first, delete after, and mention the stale fill race.
  • Skipping estimation. Fix: compute memory first; it justifies 32 shards instead of a guess.
Interview tip Spend your best minutes on what happens when the cache is wrong or gone: stampede, hot key, stale fill and cold start. Almost any candidate can say "consistent hashing". Few can say what the database sees when a shard dies.

1. Problem statement and clarifying questions

The prompt is "design a distributed cache". That is broad on purpose. A strong candidate does not start drawing boxes; they first narrow it down by asking questions, as laid out in Chapter 1. A cache sits in front of a slower, more durable store (a database, a service) and keeps copies of recently or frequently used data in memory. "Distributed" means one machine is not enough, either because the data does not fit in the memory of one machine, or because one machine cannot serve the request rate.

QuestionAssumed answer
Who are the clients?Internal backend services (a few hundred services, thousands of application instances). Not browsers.
Is it a cache or a database?A cache. Losing any entry must be safe, because the source of truth is a database. We never promise durability.
Which data model?Key to value, with an optional time to live (TTL). Values are opaque bytes up to 1 MB. A few simple server-side structures (counters) are nice to have, not required.
Who populates it?The application (cache-aside, see Chapter 13). The cache itself does not talk to databases, except for an optional invalidation feed.
Scale?About 1.5 million operations per second at peak, one billion live keys, average value around 1 KB.
Latency target?Server-side p99 under 2 ms; client-observed p99 under 5 ms within a data center.
Availability?99.99%. But "available" has a special meaning here: a cache outage must degrade the system, not take it down (section 14).
Consistency?Eventual with a bounded staleness. Reads may be stale by at most a few seconds in the normal case; we avoid stale data being stuck forever.
Multi-tenant?Yes. Many teams share the service, so we need isolation of memory and request rate (section 12).
Multi-region?Each region runs its own independent cluster. Cross-region invalidation is a stretch topic (section 15).

2. Requirements

2.1 Functional

  • get / multi-get: fetch one or many keys. Multi-get matters because a single web request often needs 20 to 100 objects.
  • set / add / delete: store with a TTL, store only if absent (add, useful for locks and leases), remove.
  • compare-and-set: store only if the entry has not changed since I read it (a version token). This is how we avoid some write races.
  • increment/decrement: atomic counters (rate counters, view counts).
  • TTL and eviction: expired entries disappear; when memory is full the least valuable entries are dropped automatically.
  • Namespaces per tenant with quotas.

2.2 Non-functional

  • Low latency: sub-millisecond in the server, one network hop on the read path.
  • High hit rate: 97 to 99% of reads should be answered from memory. The hit rate is the product's real quality metric, because every miss costs a database read.
  • Horizontal scalability: add nodes to add capacity, with only a small fraction of keys moving.
  • Fault tolerance: a node can die without a visible error burst and without crushing the database.
  • Operability: clear metrics, safe resizing, rolling upgrades.

2.3 Out of scope

Durable storage (that is a database, see Chapter 20 and the key-value store in case study 4), strong consistency across cache and database, cross-key transactions, secondary indexes, and query languages. Where a feature would pull us toward being a database, we say no, because a cache that tries to be a database is worse at both jobs.

3. Estimation

We do the arithmetic from Chapter 2 and let it drive decisions. The numbers below are used consistently for the rest of the page.

3.1 Traffic

  • Peak: 1.5 million ops/s. Average over the day is about 40% of peak, so roughly 600,000 ops/s.
  • Read to write ratio of 20:1. Peak reads = 1.5M × 20/21 ≈ 1.43M reads/s. Peak writes (sets and deletes) ≈ 71,000/s.
  • Target hit rate 98%. Misses = 2% × 1.43M ≈ 28,600 reads/s reach the databases, plus each miss triggers one cache fill, so fills ≈ 28,600 sets/s of the 71,000 total writes. The rest (about 42,000/s) are update-driven deletes and sets.
  • If the hit rate fell to 90%, misses would be 143,000/s, five times more. A database sized for 40,000 reads/s would fall over. This is why the hit rate is a first-class SLO and why a cold cluster is dangerous (section 11).

3.2 Memory

  • Average entry: key 50 bytes + value 1,000 bytes + per-item metadata (hash chain pointer, LRU pointers, expiry, flags, CAS id; memcached uses about 48 to 56 bytes) ≈ 1,100 bytes.
  • One billion keys × 1,100 B = 1.1 TB of raw data.
  • Slab allocator internal waste and hash table overhead add about 15% (section 8.1): 1.1 TB × 1.15 ≈ 1.27 TB. Round to 1.3 TB, and plan to run at about 85% full so there is room for growth, giving about 1.5 TB of memory in total.
  • Node choice: 64 GB machines, 52 GB given to the cache (the remainder for OS, network buffers, fork copy-on-write headroom and the process itself). 1.5 TB ÷ 52 GB ≈ 29 primaries. We use 32 shards (a power of two, tidy for operations). Each primary holds about 1.3 TB ÷ 32 ≈ 41 GB of data, which is 79% of its 52 GB: some headroom.
  • Each shard has one replica, so there are 64 nodes. Memory is not the cost driver for the replica question: replicas double the bill but halve the risk (section 9).

3.3 Per-node load and bandwidth

  • 1.5M ops/s ÷ 32 ≈ 47,000 ops/s per primary on average. A single-threaded Redis process handles on the order of 100,000 simple ops/s; a multi-threaded Memcached handles several hundred thousand. So the request rate is comfortable; hot keys, not average load, are the risk (section 7).
  • Bandwidth: 1.5M × 1.1 KB ≈ 1.65 GB/s in total, about 13 Gbit/s across the whole cluster and about 52 MB/s (0.4 Gbit/s) per primary. Fine for 10 Gbit NICs. Multi-gets of big batches can produce bursts, but the average is small.
  • Connections: 4,000 application instances × 32 shards × 4 connections each = 512,000 connections in total, or 16,000 per node. That is manageable for an event-driven server but a good reason for client-side pooling or a proxy tier (section 13).

3.4 What the numbers tell us

  • Capacity is dominated by memory, so the key design question is memory efficiency: the allocator, the eviction policy and the item overhead.
  • Request rate per node is modest, so we can afford an extra hop (proxy) if it buys us operability.
  • The database is sized for the miss traffic, about 29,000 reads/s. Anything that multiplies misses (node loss, resize, cold start, stampede) is the main threat.

4. API design

We offer a small binary or text protocol, in the spirit of the Memcached protocol or the Redis RESP protocol (see Chapter 15). The logical API, which a client library wraps:

get(ns, key)                           -> { value, flags, cas, ttl_remaining } | MISS | LEASE(token) | STALE(value, token)
get_multi(ns, [key...])                -> map key -> same result as get
set(ns, key, value, ttl, flags)        -> STORED
add(ns, key, value, ttl)               -> STORED | EXISTS      (only if absent)
cas(ns, key, value, ttl, cas_token)    -> STORED | EXISTS | NOT_FOUND
lease_set(ns, key, value, ttl, token)  -> STORED | REJECTED   (token must still be valid)
delete(ns, key)                        -> DELETED | NOT_FOUND
touch(ns, key, ttl)                    -> TOUCHED              (extend TTL without moving the value)
incr(ns, key, delta)                   -> new value
stats / admin: slots, migrate, drain, flush(ns)

Notes on the choices. The ns (namespace) is the tenant or keyspace; it is part of the stored key so two tenants can use the same key text. get can return a lease or a stale value; these two outcomes implement stampede protection and are explained in section 7. touch exists because rewriting a 500 KB value just to extend its life wastes bandwidth. Every response includes the remaining TTL so a client can decide whether to refresh early. There is no "list all keys" or "scan by pattern" in the public API: it would hold up a node and encourage using the cache as a database.

5. Data model and storage choice

Each shard is a hash table in memory. A table entry points to an item; an item holds the key, the value bytes, expiry time, flags, a version number (the CAS id) and the pointers the eviction algorithm needs. There is no disk on the hot path. We choose memory because the latency target (sub-millisecond) and the request rate are far beyond what a disk-based store gives at this cost; a cache is explicitly a place where the price per read operation matters more than the price per gigabyte. Options for the server software:

OptionStrengthsWeaknessesUse here?
MemcachedSimple, multi-threaded, very predictable memory (slab allocator), tiny per-item overhead, huge operational recordNo replication or persistence built in, only strings, clustering is entirely client or proxy sideGood fit for pure caching at scale
Redis (cluster mode)Rich structures, built-in replication, failover and slot-based sharding, optional persistenceSingle-threaded command execution per process (I/O threads help), larger per-item overhead, fork-based snapshots need memory headroomGood when you want replication and failover out of the box
Build our ownTailored to the workloadYears of engineering for allocator, networking and bugsNo. In an interview, build on one of the above and explain its internals

We design the service as a cluster of Redis-or-Memcached-like shard processes plus a thin control plane, and where the two products differ we say so. The sharding and routing logic can be written once for both. The data lives only in RAM; the source of truth is always the database, which is why we can tolerate losing a node. Tools for the database side are in Chapter 17 and Chapter 24.

6. A first simple design, then the scaled architecture

6.1 One box

Start with one cache server (say a 64 GB machine running Redis or Memcached). Application servers use cache-aside: read the cache; on a miss read the database and fill the cache. This already gives 100,000 or more ops/s and one hop. What breaks as we grow:

  1. Memory: 1.3 TB does not fit on one machine.
  2. Request rate: 1.5M ops/s exceeds one process, and one NIC.
  3. Single point of failure: if the one box dies, 100% of reads go to the database and it collapses.
  4. Blast radius: a restart empties the cache.

So we shard (spread keys over many nodes), replicate (a second copy for failover), and add a control plane to know who owns what.

6.4 Request flow: write

  1. The application writes the new value to the database first (the database is the source of truth).
  2. After the database commit, the application issues delete(key) to the cache (not "set the new value"; section 10 explains why delete is safer).
  3. Independently, the change feed from the database also emits a delete for the key, which repairs the case where the application crashed between steps 1 and 2 or where another system wrote to the database.
  4. The next reader misses, takes a lease, loads the fresh row and refills the cache.

7. Deep dive: stampedes and hot keys

Two problems turn a healthy cache into an outage. Both are covered in general terms in Chapter 14; here we decide exactly what our service does about them.

7.1 The stampede (thundering herd)

A stampede happens when a popular entry disappears (its TTL expires, it is evicted, or it is deleted by an invalidation) and many clients ask for it in the same instant. Every one of them sees a miss, and every one of them runs the same expensive database query. Suppose one key is read 50,000 times per second and the query takes 40 ms. In the 40 ms before the first refill lands, about 50,000 × 0.04 = 2,000 requests all miss and all hit the database for the same row. If the query is heavy, the database slows down, the refill takes even longer, more requests pile up, and the slowdown feeds itself.

We use four layered defenses.

  1. Leases (server side). On a miss, the shard does not just say "miss". It hands the first caller a lease: a unique token meaning "you are the one allowed to fill this key". It remembers the token. Later callers for the same key within a short window (say 10 seconds) get either a "wait and retry in a few milliseconds" answer or, if we kept one, a stale value. Only the holder may call lease_set with the token. This is the mechanism described in Facebook's Memcache paper, and it also solves a second problem: if a delete arrives while the lease is out, the shard invalidates the token, so a slow filler cannot write an old value after a newer delete (section 10).
  2. Single-flight (client side). Inside one application process, concurrent requests for the same missing key share one in-flight load. The first thread runs the loader; the others wait on its result. This cuts duplicate work by the number of threads per instance, and it does not need any server support.
  3. Stale-while-revalidate. We store each value with a soft expiry earlier than its hard expiry. For example the hard TTL is 10 minutes, the soft TTL is 9 minutes. Between 9 and 10 minutes the shard returns the old value flagged as stale and gives one caller a lease to refresh it in the background. Users see no latency spike, and the database sees one query.
  4. TTL jitter. If a million keys are all loaded at 09:00 with a 1-hour TTL, they all expire at 10:00 together. Adding a random +/-10% to every TTL spreads expiry over six minutes.
Key idea A lease turns "N callers all do the work" into "one caller does the work, N-1 wait a few milliseconds or accept slightly old data". The shard is the right place to decide who is first, because it is the only place that sees every caller.

Sometimes the database is the thing in trouble, so we also add a global cap: each tenant has a ceiling on lease grants per second, and clients apply circuit breaking and load shedding to loaders, so a stampede across many different keys (a "dogpile" rather than a single hot key) is bounded too.

7.2 Hot keys

Consistent hashing spreads keys evenly, not load. A single celebrity profile, a feature flag read on every request, or a viral product can receive 200,000 reads per second. All of them hash to the same shard, and that shard's CPU (or single thread, in Redis) and NIC saturate while 31 other shards are idle. Adding shards does not help, because the key still lives on exactly one of them.

Walkthrough. The figure has three horizontal bands, each a different answer to the same problem. Red means overloaded, amber is a shard, soft green is the near-cache, purple is the caller. 1. Top band: 4,000 app instances all send the hot key to Shard 7, which turns red because its CPU and network card are full and every other key on it suffers. 2. Middle band: each instance first asks its own near-cache with a one second lifetime, and only one read per instance per second continues (dashed arrow) to Shard 7. That gives the 4,000 reads per second in the figure instead of 200,000. 3. Bottom band: the key is stored as key#0 to key#3 on four different shards and the caller picks one at random, so load splits four ways. It is drawn as a comparison because adding shards alone cannot help one key. On a whiteboard, start with the red box and add the cheapest fix first. The cost to mention is staleness for the near-cache and four writes for the copies; remove either fix and the hot shard stays saturated.

Remedies, in the order we would reach for them:

  1. Near-cache (local cache) in the client. Each application instance keeps a small in-process map (a few thousand entries, bounded, with an admission policy such as TinyLFU so one-off keys do not pollute it) with a very short TTL, typically 0.5 to 2 seconds. With 4,000 instances, even a 1-second TTL turns 200,000 reads/s into at most 4,000 reads/s at the shard. The cost is staleness of up to the TTL, which is why we only enable it for keys that tolerate it, and why the near-cache is never used for data that must reflect a write immediately.
  2. Detect, then promote. Shards keep a cheap approximate counter of the top keys (a count-min sketch, see Chapter 57, or sampling one request in a hundred). When a key crosses a threshold such as 20,000 reads/s, the control plane marks it hot and pushes the flag to clients, which switch on near-caching for it automatically. Developers do not need to know in advance.
  3. Replicate the hot key under several names. Store profile:42#0 through #3, each hashing to a different shard; readers pick a random suffix. Reads divide by four. Writes must update or delete all four, so this suits read-mostly keys. Redis replicas serving reads (READONLY) give a similar effect without suffixes, at the price of replication lag.
  4. Split a hot aggregate. A shared counter that is written a lot (a global view count) is best sharded into N sub-counters that are summed on read, or buffered in the client and flushed periodically.
  5. Rate-limit as a last resort. If one key is abusive, the proxy sheds the excess for that key rather than letting it harm its neighbours (see Chapter 16).

8. Deep dive: memory management

8.1 Slab allocator

The obvious way to store variable-size values is to call the system allocator (malloc) for each item and free it on eviction. Over days of operation with items of random sizes coming and going, this leaves memory full of small unusable gaps. That is external fragmentation: the process holds 52 GB but cannot place a new 3 KB item. Memcached avoids it with a slab allocator.

Memory is cut into fixed 1 MB pages. Each page is assigned to one slab class, and a class has a fixed chunk size. Chunk sizes grow geometrically by a growth factor (the memcached default is 1.25): for example 96, 120, 152, 192, 240 ... bytes, up to the page size. A page for the 240-byte class is split into 1 MB ÷ 240 B ≈ 4,369 chunks. An item is stored in the smallest chunk that fits it, so a 200-byte item sits in a 240-byte chunk and wastes 40 bytes. That wasted tail is internal fragmentation; with a factor of 1.25 the average waste is roughly 10 to 12%, which is where our 15% overhead estimate in section 3 comes from (it also covers the hash table).

Walkthrough. Read it top to bottom. The top row shows the whole memory split into 1 MB pages, each page owned by one slab class; three example classes are drawn as amber boxes with their chunk size (152 B, 1,184 B, 12 KB). 1. The lesson is the waste numbers under each item: that internal waste is the price paid for never fragmenting memory. The alternative, calling the general allocator for every item, leaves gaps nobody can use after days of churn. On a whiteboard, draw one page cut into equal squares. Remove the per-class rule and a freed 3 KB hole cannot hold a 5 KB item; keep it but never rebalance pages, and you get slab calcification.

The famous failure of slabs is slab calcification. Pages are assigned to classes as traffic arrives; if the workload's size distribution later shifts (for instance values grow from 200 B to 2 KB), the old class keeps all its pages while the new class has too few, and it starts evicting aggressively although plenty of memory exists in total. Mitigations: an automatic slab rebalancer that reclaims pages from classes with low eviction pressure (built into modern memcached), tuning the growth factor, and separate pools for very different size profiles. Redis, in contrast, relies on jemalloc and can suffer from memory fragmentation instead; it reports a fragmentation ratio (resident memory divided by used memory) and supports active defragmentation. A ratio persistently above about 1.5 is a sign to investigate.

8.2 Eviction: LRU and LFU approximations

When a shard is full and a new item arrives, something must go. A perfect LRU (least recently used) keeps a linked list of all items ordered by last access and evicts from the tail. Every read must move the item to the head, which means taking a lock on shared list pointers on every hit. At 100,000 reads/s per node this lock is the bottleneck, and the two pointers per item cost 16 bytes of the item's overhead. Real caches therefore approximate.

ApproachHow it worksTradeoff
Exact LRU listDoubly linked list, move to head on each hitAccurate, but lock contention and pointer memory
Segmented LRU (memcached)Items live in HOT, WARM and COLD segments per class; a background thread moves items between them; a hit only sets a bit, and the item is moved lazilyHits are almost lock free; scan resistant, because a one-time item never reaches WARM
Sampled LRU (Redis)No list. Each item stores a coarse last-access clock (24 bits). LFU (least frequently used)Store an approximate access count (Redis uses an 8-bit logarithmic counter with decay over time) and evict the lowestProtects stable popular keys from being flushed by a scan; needs decay so old favourites eventually leave

Which one for us? A general-purpose service with mixed tenants should default to an LRU approximation (segmented or sampled), because recency adapts fast to changing workloads. A tenant whose traffic is a stable Zipf distribution (a few very popular keys) with periodic batch scans of the whole data set should choose LFU, because a scan would otherwise evict every popular key. Redis exposes both as policies (allkeys-lru, allkeys-lfu, and volatile-* variants that only evict keys that have a TTL); for a cache we want an allkeys-* policy so that memory pressure never produces "out of memory" write errors. See Chapter 15.

Watch out Do not fill memory to 100%. Eviction, replication buffers, client output buffers and (in Redis) fork copy-on-write during snapshots all need headroom. We run primaries at about 80 to 85% of the configured memory and alert at 90%.

8.3 TTL and expiry

A TTL says when an entry stops being valid. Removing expired entries has two parts. Lazy expiry: when a key is read, the shard checks its expiry time and discards it if it is past. This is free but never reclaims a key nobody reads again. Active expiry: a background task samples keys that have a TTL and deletes the expired ones. Redis samples 20 keys per round, ten times per second, and repeats at once if more than a quarter were expired, so a burst of expiry does not leave memory full of dead data. Memcached uses a crawler thread that walks the LRU. Expired items also take priority as eviction victims because freeing them costs nothing in hit rate.

TTL choice is a business decision, not just a technical one: it bounds staleness (section 10), controls how long cold data occupies memory, and, if every key gets the same TTL, creates synchronized expiry (hence jitter, section 7.1). Typical guidance: short (seconds to minutes) for data that can change without us noticing, longer (hours) for data protected by explicit invalidation, and never "no TTL" for derived data, because a missed invalidation would then be permanent.

9. Replication and failover

Losing a primary loses 1/32 of the cache (about 41 GB). The misses from that loss are 1/32 of 1.43M reads/s ≈ 45,000 reads/s of extra traffic aimed at the database, on top of the normal 28,600 reads/s: a 1.6x increase. A database sized with roughly 2x headroom survives it, but it is an expensive moment, and refilling 41 GB over the database path takes a long time (section 11). A replica avoids this.

9.1 Replication design

  • Asynchronous primary to replica copy. Writes are acknowledged by the primary immediately and streamed to the replica afterwards. We choose async because a cache write should cost sub-millisecond. The consequence: if the primary crashes, the last few milliseconds of writes may be missing on the replica. For a cache that is acceptable: a missing entry is only a miss; a missing delete is the dangerous case, because the replica then keeps a stale value (see section 10, and mitigation by TTL and the change feed).
  • One replica per shard in a different failure domain (another rack, ideally another availability zone). Zone placement is the main thing that makes a replica useful. Memcached has no built-in replication, so the same effect comes from the proxy writing to two pools (mcrouter's replicated pools), at the cost of two writes per set.
  • Replica reads: normally off. Serving reads from replicas adds capacity but exposes replication lag, so we enable it only for hot keys and tolerant tenants.

9.2 Failure detection and promotion

Walkthrough. This is a timeline from left to right; the colour of each dot shows the state: red for broken, amber for suspicion and voting, green for recovered. 1. At t = 0 the primary dies and nobody knows yet. 2. Within a few seconds its peers stop getting heartbeats and mark it as suspect (PFAIL). A single peer's opinion is not enough. 3. When a majority of primaries agree, the node is declared failed and its replica asks for votes. 4. Around 15 seconds in, the replica is promoted and a new slot map with a higher epoch is published. 5. Clients refresh their map and traffic recovers. The red bar underneath is the window in which 1/32 of keys miss or time out, so clients must fail fast and read the database. It is drawn as phases because the point is the tradeoff in the footnote: shorter timeouts recover sooner but trigger false failovers during a slow patch. On a whiteboard, mark the two dots where agreement happens. Without the majority rule, one confused peer could demote a healthy node.

In Redis Cluster the nodes themselves gossip heartbeats (Chapter 33). A node is flagged as suspect by a peer that misses replies for the node timeout, and declared failed when a majority of primaries agree. The replica with the most up-to-date replication offset requests votes, and wins with a majority, incrementing a config epoch that makes the newest map win (the same ideas as in Chapter 29). For a memcached-based deployment, an external controller (health checker plus a small consensus-backed store) plays the same role and the proxy tier swaps the endpoint.

Two hazards deserve explicit mention. Split brain: a partitioned old primary may keep accepting writes. In a cache the damage is bounded because those writes will be dropped when it rejoins as a replica and resyncs, but clients on the minority side can read stale data; the old primary stops serving when it cannot reach a majority of primaries for its node timeout. Flapping: a node that fails and recovers repeatedly causes constant map changes; we add hysteresis (a minimum time before a failed node may rejoin as primary).

10. Deep dive: consistency with the source database

The cache and the database are two copies of the same fact, and no protocol between them is both cheap and perfectly consistent. The patterns are in Chapter 13 and the theory in Chapter 28. This section decides which write policy this service recommends and how it closes the known races.

10.1 The classic races

Walkthrough. Three vertical lifelines: Reader A, the cache shard, and Writer B with the database. Time runs down. Red text is the bug, green text is the fix. 1. Reader A misses and receives lease token L1. 2. A reads the database and gets the old value v1, then stalls (a slow network or a pause). 3. Meanwhile Writer B commits the new value v2 to the database. 4. B deletes the key from the cache, and the shard marks lease L1 as void. 5. A wakes up and tries to store v1. Without leases this plain set succeeds, and the cache holds the old value until the TTL ends. With leases, lease_set carrying L1 is rejected, v1 is thrown away, and the next reader loads v2. The figure is drawn with a long gap between steps 2 and 5 because the race needs a slow reader. The alternative it avoids is hoping the timing never happens, which at 1.4 million reads per second it will. On a whiteboard, mark the two arrows labelled 5 in red and green. Remove the token check and the stale value lives for a full TTL.
  1. Stale fill after delete (figure above). Fixed by leases, or by add plus versions: store a version number from the database row with the value and refuse to overwrite a higher version (a compare-and-set on version).
  2. Delete before commit. If the writer deletes the key and only then commits to the database, a reader can miss in between, read the old row, and refill with the old value. The rule is: always commit first, delete after.
  3. Lost delete. The cache node is unreachable at delete time, or the app crashes after the commit. Mitigations: retry the delete from a durable queue, a change feed that emits deletes from the database log (so even writes by other systems are covered), and a TTL as the final backstop. A short-lived "tombstone" approach (set the key to a delete marker for a few seconds) protects against replication-lag reordering.
  4. Replica lag on reads. If the cache fill reads the database from a read replica that is behind, the cache gets an old value. Fill from the primary database or from a replica known to have caught up past the write (a database version or timestamp comparison; see Chapter 24).

10.2 Invalidation feed

Application-side deletes cover only the writes the application knows about. A change data capture pipeline tails the database's replication log (the binlog or write-ahead log) and publishes row changes to a queue (Chapter 34). A fleet of invalidators consumes it and issues deletes, routing each by key to the right shard. This catches writes from scripts, other services and manual fixes. It is eventually consistent (typically sub-second to a few seconds behind), idempotent (deleting twice is harmless), and it is how large deployments make cached data converge. The invalidator carries the row version so that a delete never races ahead of a fill that is itself newer.

Finally, state the guarantee honestly: after a database write commits, the cache may serve the old value for the time it takes the delete or CDC event to arrive (milliseconds to seconds), and never longer than the TTL. Readers that need read-your-writes (the user who just saved a setting) bypass the cache or use a session-scoped flag to read from the database for a few seconds.

11. Cold start, warm-up and rebalancing

11.1 Why an empty cache is dangerous

A freshly started cluster has a hit rate of zero. All 1.43M reads/s would flow to databases that are sized for 28,600 reads/s, which is 50 times too much. The databases would fail, loaders would time out, nothing would get cached, and the system would not recover on its own: a classic metastable failure in which the cure (a warm cache) can never form because the sickness (database overload) prevents the fills. The same thing happens in miniature when a shard restarts empty.

Defences, from cheapest to most involved:

  1. Never lose the cache by accident. Rolling restarts one shard at a time, replicas promoted before the primary is restarted, and persisted snapshots (Redis RDB or a memcached warm-restart file in shared memory) so that a process restart reloads memory in seconds.
  2. Admission control during warm-up. A new or empty cluster is brought into service by gradually shifting traffic: 1%, then 5%, 25%, 100% of keys (or tenants), with the percentage raised only when the database load and hit rate stay inside limits. A feature flag in the client decides, per key hash, whether to consult the new cluster.
  3. Warm-up by replay. Replay recent reads: a log of the last hour of key accesses, sampled, can be played against the databases at a controlled rate to prefill the hottest keys first (the long tail can fill itself). Or copy from an existing warm cluster (a second region, or the cluster being replaced) at a rate limit.
  4. Priority and shedding. While cold, the loaders favour critical tenants and shed optional work, so the database serves the traffic that matters (Chapter 40).
  5. Lease-limited fills. Leases (section 7) ensure that at most one load per key runs at a time, so the cold database sees the number of distinct hot keys, not the number of requests.

A rough warm-up estimate: if the database can give us 15,000 spare reads/s on top of normal load, loading 41 GB (about 37 million entries at 1.1 KB) for a single shard would take 37M ÷ 15,000 ≈ 2,500 s, about 41 minutes, even with perfect efficiency. This is why we replicate and why we do not casually restart whole shards.

11.2 Scaling out with few extra misses

Suppose traffic grows and we add a 33rd shard. If routing is hash(key) mod N, going from 32 to 33 changes the shard for about 97% of the keys: nearly the whole cache becomes unreachable at once, a catastrophe equal to a cold start. This is the reason for consistent hashing (section 13): when a node is added, only about 1/33, roughly 3%, of the keys move, and all of them move to the new node.

Walkthrough. The left column is the existing amber shards, each owning a block of the 16,384 fixed slots; the soft green box on the right is the new, empty 33rd shard. Green arrows show slots flowing from every old shard into the new one, a small share each (15 or 16 slots), so no single shard is drained. The four numbered lines at the bottom are the per slot protocol. 1. Mark the slot as migrating on the source and importing on the target. 2. Copy its keys in small batches with their remaining TTL. 3. While copying, reads for keys not yet moved are served by the source and reads for moved keys get an ASK redirect to the target. 4. When the slot is empty, publish the new owner with a higher epoch, and clients learn it from a redirect or a map refresh. It is drawn with fixed slots because moving whole named slots is exact, while moving keys by hash range is fuzzy. On a whiteboard, draw one slot travelling. Without step 3, keys in flight would briefly vanish and show up as misses.

Two ways to rebalance. Without data movement: the new shard simply starts empty and takes its slots. The 3% of keys that moved miss once each; reads rise from 2% misses to about 2% + 3% × 98% ≈ 4.9%, so database reads rise from 28,600/s to about 70,000/s (2.45x) and decay as the new shard fills. That is survivable if the database has headroom, but we avoid it by live slot migration as in the figure: copy the slot's keys with their remaining TTL from the old owner to the new one, in small batches and at a limited rate (for example 100 MB/s per shard) so the source stays responsive. Moving 39 GB at an aggregate of about 2 GB/s (32 sources in parallel at roughly 60 MB/s each) takes under a minute of wall-clock bandwidth, though we pace it to be gentle: 20 to 30 minutes is typical in practice. During the move, a request for a slot that is mid-migration may need one extra hop (the ASK redirect), the only added latency. Leaving the old copy in place until the new owner is confirmed also means that if the migration is abandoned, nothing is lost.

The reverse operation (scale in, or replacing a node) is a drain: move slots away first, then remove the node. For memcached with ketama-style consistent hashing (no slots), the proxy can run both the old and new rings for a transition window: read from the new owner, fall back to the old owner on a miss, and populate the new owner. This makes the rebalance invisible at the cost of a second lookup on misses during the window. Capacity planning rule: add nodes before utilisation exceeds 80% of memory, because migration itself needs headroom, and never resize and deploy at the same time.

12. Multi-tenant quotas and isolation

Many teams share the cluster. One careless tenant, with a scan that touches millions of keys, can flush everyone else's working set and double the database's miss traffic. Isolation applies to three resources; the cell and noisy-neighbour ideas are in Chapter 42.

  • Memory. Each tenant receives a byte quota within a shared shard. Items carry a tenant id (the namespace). When the shard must evict, it picks a victim from the tenant that is furthest over its quota, falling back to global LRU among tenants under quota; a tenant under its quota cannot be evicted by a neighbour's growth. Unused quota is borrowed freely (this is what makes sharing cheaper than separate clusters) and reclaimed on demand. Very large or very sensitive tenants get a dedicated pool (own shards), which is the strongest isolation and costs the most.
  • Request rate. A token bucket per tenant at the proxy tier (see Chapter 16), for example 200,000 ops/s with a burst of 400,000. Excess requests get a fast "throttled" reply that the client treats as a miss, so the application degrades instead of queueing at the shard.
  • Connections and value size. Maximum connections per client host, a maximum value size (1 MB) and a maximum key length (250 bytes), so that nobody ties up buffers or blows up the slab classes.

Operationally, each tenant gets a dashboard of its own hit rate, memory use and throttle count, plus a cost showback (bytes held times price). Quotas change through the control plane, not by redeploying clients. Security (section 15) also uses the namespace: a credential grants access to specific namespaces only.

13. Deep dive: sharding, routing and the client library

13.1 Consistent hashing and slots

We need a function from key to shard that (a) spreads keys evenly, (b) is computed by clients without asking anyone, and (c) changes for only a small fraction of keys when shards are added or removed. Plain modulo fails (c) as shown. Consistent hashing (see Chapter 25 and Chapter 57) places both nodes and keys on a circle of hash values; a key belongs to the first node clockwise from its hash. Removing a node hands its range to the next node; adding one takes a slice from its neighbour. Because a physical node placed at a single point would get uneven ranges, each node is placed at many points, called virtual nodes (ketama uses about 100 to 200 per server), which evens the load to within a few percent and spreads a failed node's keys across all survivors rather than dumping them on one neighbour.

Walkthrough. The big circle is the hash space, a loop of numbers. Coloured dots on it are server points: each colour (amber A, blue B, green C) is one physical server that appears twice, as A1 and A2, B1 and B2, C1 and C2. The small green dot is a key, k1, and the red dot is a new server point D1. 1. Hash the key to a position on the circle. 2. Walk clockwise to the first server point; that server owns the key (B1 for k1). 3. If server A dies, its arcs pass to the next points clockwise, which belong to different servers, so the load spreads. 4. Adding D1 only claims the arc between its neighbour and itself. The text on the right gives the numbers: 160 points per server across 32 servers, giving about 8% load spread, and 1/33 of keys moving on an add. Each server appears many times because one point per server gives uneven arcs, and the alternative of modulo moves almost every key. On a whiteboard, draw the circle and walk clockwise out loud. If you remove the repeated points, one neighbour absorbs a whole failed server.

Two refinements matter in practice. Slots instead of a ring: hash the key to one of a fixed number of slots (16,384 in Redis Cluster), then keep an explicit table slot to shard. The table is small, balanced exactly (not statistically), and rebalancing is the movement of named slots. Hash tags: if two keys must live together (for a multi-key operation), the client hashes only a marked part of the key. Use sparingly, because it creates skew. There is also rendezvous (highest-random-weight) hashing, which needs no virtual nodes: score each node against the key and pick the highest. It has the same minimal-movement property and costs O(N) per lookup, fine for 32 nodes.

The proxy tier is stateless and scaled horizontally behind a load balancer or, better, per-host sidecars (see Chapter 10).

13.3 Client library behaviour

A cache is only as good as its worst client. A good library does the following.

  • Short timeouts. A cache call that takes 50 ms is worse than a miss. Typical timeouts are 5 to 20 ms for gets. A timeout is treated as a miss, not an error that fails the user's request.
  • Bounded retries with a budget. At most one retry, and only while retries stay under about 10% of requests, otherwise retries amplify an overload (Chapter 51). Sets and deletes are idempotent, so retrying them is safe.
  • Circuit breaker per shard. After repeated failures to one shard, stop calling it for a few seconds and treat its keys as misses (while the lease and database caps protect the database).
  • Batching and pipelining. Group multi-gets by shard and issue them in parallel, so 100 keys cost about the slowest of 32 parallel calls, not 100 sequential ones. Cap batch sizes so one response does not fill a connection for long.
  • Connection pooling with a small fixed number of connections per shard and keep-alive, avoiding the connect cost and the connection storms after a restart.
  • Topology refresh. Refresh the slot map on a redirect, on connection errors and periodically (every 30 to 60 s), with jitter so thousands of clients do not refresh together.
  • Hedged requests. For tail latency, if a get is not answered within the p95 time (say 3 ms), send the same read to the replica and take the first reply, at a cost of about 5% extra reads.
  • Serialization and compression. A compact, versioned format (see Chapter 7); compress only values above a size threshold (for example 1 KB), because compression trades CPU for memory and bandwidth. Include a schema version in the value so deploys that change the format can read or ignore old entries.
  • Metrics from the client. Hit, miss, timeout, latency per namespace, because the client sees what the server cannot (the full request time).

14. Failure modes and degraded mode

The principle: the cache is an optimization, so its failure must never be a correctness failure, but it often is a capacity failure, because the database was sized assuming a 98% hit rate. We plan for both. Resilience patterns are in Chapter 40 and Chapter 41.

14.1 Degraded mode

If the cache is unavailable or the hit rate collapses, the service enters a defined degraded mode instead of improvising:

  1. Clients stop waiting: calls time out quickly and are treated as misses.
  2. A global concurrency limit on database loaders keeps the database inside its capacity (for example at most 60,000 concurrent-rate reads per second). Excess loads either wait briefly, or return a default or stale value from the near-cache, or an error for non-critical features.
  3. Non-critical tenants are shed first; critical read paths (login, checkout) keep priority.
  4. Where a feature allows it, serve slightly stale data longer ("serve stale on error"): the stale-while-revalidate copy and the near-cache extend lifetime while the backend is struggling.

The gutter pool from Facebook's design is a small separate set of cache servers (on the order of 1% of capacity). When a client cannot reach a primary shard, it asks the gutter pool instead and stores the value there with a short TTL (a few seconds). The gutter absorbs the traffic of the failed shard's hottest keys and caps database load at the cost of brief staleness; no resharding is needed during the failure.

15. Security, monitoring, multi-region and cost

15.1 Security and abuse

  • Network isolation: shards in private subnets, never exposed to the internet (several well-known data breaches came from open Redis ports); only proxies and approved clients can connect.
  • Authentication and TLS: mutual TLS or per-tenant credentials with namespace scoping (see Chapter 55). TLS costs CPU (often 10 to 30% on small-value workloads), which is a reason to terminate it in the proxy tier on a trusted network if policy allows.
  • Sensitive data: cache only what you would accept being exposed to a mis-scoped read; encrypt or avoid personal data, and honour deletion requests (a delete in the database must also reach the cache, within the TTL at worst). See Chapter 56.
  • Abuse: cache penetration (a flood of requests for keys that do not exist, so every call misses) is countered with negative caching (store "not found" for a short TTL such as 30 s) or a Bloom filter of existing ids, per Chapter 14. Key flooding by one tenant is caught by quotas.

15.2 Monitoring and SLOs

The signals, following Chapter 54:

  • Hit rate per tenant and per namespace: hits ÷ (hits + misses). The SLO is a floor, for example 97% over 5 minutes for the production tenants. Watch the miss rate too, because a stable percentage can hide a doubling of absolute database load when traffic doubles.
  • Latency: p50, p99, p99.9 at the shard and at the client; the gap between them is network and queueing.
  • Evictions per second and eviction age (how old the evicted items were): evicting items younger than their TTL means the cache is too small for its workload; this is the most useful capacity signal.
  • Memory: used versus max, fragmentation ratio, per-slab-class pages, per-tenant bytes.
  • Replication lag and failover count, slot-map version skew across clients, connection counts, rejected or throttled requests.
  • Hot key reports: top-N keys per shard from sampling.
  • Backend load: database reads per second caused by misses, correlated with the cache's miss rate. An alert that fires when misses rise beyond what the database can take is the single most protective alert.

SLOs: 99.99% of requests answered (hit, miss or fast timeout) within 5 ms at the client; hit rate at or above 97%; staleness bound: 99.9% of invalidations applied within 5 seconds of the database commit.

15.3 Multi-region

Each region runs its own cluster in front of its local database replicas; cross-region reads for cache misses are slow and fragile. The hard part is invalidation: a write in region A must delete the key in region B. Facebook solved this by having the database's replication stream carry the invalidations, so the delete arrives in order with the data (Chapter 26). A second tool is a short TTL on keys that may be written from other regions. We do not replicate cache contents across regions, because the data is cheap to rebuild and replication traffic would exceed the benefit.

15.4 Cost

The cluster is 64 nodes of 64 GB, memory-heavy instances. At a placeholder price of $0.50 per hour per 64 GB node (check actual provider pricing), that is 64 × 0.50 × 730 ≈ $23,000 per month. The replicas are half of this, which is the price of the failover guarantee. Compare with the value: without the cache, the databases would need to serve 1.43M reads/s instead of 28,600, about 50 times more, which would cost far more than $23,000 per month. Savings levers: compress large values (often 2 to 3x), shorten TTLs on cold data, drop the replica for tenants who can tolerate a cold shard, right-size using the eviction-age signal, and move rarely-read big values to cheaper tiers (SSD-backed cache extensions exist in both products).

16. Evolution and alternatives

16.1 What to build first

  1. Phase 1 (weeks): a replicated Redis or Memcached pair per tenant, cache-aside in a shared client library with timeouts, TTL jitter and single-flight. Dashboards for hit rate.
  2. Phase 2: sharding with a slot map, a proxy tier, leases and stale-while-revalidate, quotas.
  3. Phase 3: CDC-driven invalidation, hot key detection with near-cache promotion, gutter pool, automated resizing and warm-up tooling.
  4. Phase 4: multi-region invalidation, SSD tiers, chargeback.

16.2 At 10x scale

  • 10x traffic (15M ops/s) and 10x data (13 TB): about 320 shards. Memory stays the driver, so SSD-backed tiers (flash for the long tail, RAM for the head) become attractive, as 13 TB of RAM is costly.
  • A single proxy fleet and a single slot map become operational risks. Split the service into cells (Chapter 42): each cell serves a group of tenants with its own proxies, shards and control plane, bounding the blast radius of any bug or overload.
  • With 320 shards, gossip-based failure detection costs grow; hierarchical or externally coordinated membership is preferred.
  • Network becomes a bottleneck for large values (13 times the bandwidth); local near-caches and compression carry more weight.

16.3 Alternatives not chosen

  • A purely local in-process cache: the lowest latency, but each of 4,000 instances caches independently, the combined hit rate is poor for a big key space and invalidation is hard. We use it only as a near-cache for the hottest keys.
  • Write-behind or a durable cache: turns the service into a database with weaker guarantees. Not chosen.
  • CDN or HTTP caching instead: right for public static content (Chapter 12), but it does not serve internal service-to-service object lookups with fine-grained invalidation.
  • Strong consistency between cache and database (distributed transactions): would add latency and fragility to every write. TTL plus invalidation gives bounded staleness at a fraction of the cost.

17. Interview Q&A

Why not just use hash(key) mod N to pick the shard?

Modulo is perfectly even and trivial to compute, but it ties every key's location to N. When you go from 32 to 33 shards, a key stays put only if its hash gives the same remainder under both, which happens for about 1 key in 33; roughly 97% of the cache moves. Because moved keys are simply unreachable (the new owner is empty), the hit rate drops to a few percent and the database suddenly sees nearly the full read load, an outage disguised as a routine resize. Consistent hashing or fixed slots change only the keys that must move, about 1/33 here, and slots let us copy those keys live so even they rarely miss.

Memcached or Redis for this service?

If the workload is plain strings with simple get and set, a very high request rate and huge memory, Memcached gives predictable memory use, multi-threading and low per-item overhead, and gets its replication and failover from a proxy such as mcrouter. If you want built-in replication, automatic failover, slot-based clustering, data structures like counters and sorted sets, and optional persistence for fast restarts, Redis Cluster provides them in one product, at the price of higher per-item memory and a mostly single-threaded engine per shard. At our 47,000 ops/s per shard either works; I would pick Redis Cluster when the team is small and wants fewer moving parts, and Memcached plus a proxy tier when the fleet is huge and uniform.

A key is requested 200,000 times per second. What do you do?

First note that adding shards cannot help, since one key lives on one shard. Put a near-cache of about one second in each client, which reduces the load at the shard to roughly one request per client instance per second, about 4,000 per second here. If the key can tolerate no staleness, store it under several suffixed names that hash to different shards and read a random one, updating all copies on write; or allow reads from the replica. Detect hot keys automatically with sampled counters and promote them without developer action, and protect neighbours with a per-key rate limit at the proxy.

How do you stop a cache stampede?

Layer several defences. The shard issues a lease to the first missing caller and makes the others wait briefly or take a stale value, so only one database query runs per key. Inside each process, single-flight collapses concurrent loads. Stale-while-revalidate with a soft TTL lets users keep getting the old value while one caller refreshes it. TTL jitter prevents mass simultaneous expiry. Finally a global limit on database loaders caps total pressure even when many different keys miss at once.

The database row changes. How do you keep the cache from serving stale data forever?

Commit to the database first, then delete the key (not set it), so a later reader reloads fresh data. The classic race is a slow reader that loaded the old row before the write and fills the cache after the delete; leases close it because the delete invalidates the outstanding lease token, or you can carry a row version and refuse older versions. Back this up with a change data capture feed that emits deletes for any write, including ones the application did not make, and with a TTL as the ultimate bound. The honest guarantee is bounded staleness: typically under a few seconds, never more than the TTL.

What happens when a cache node dies, and how do you avoid overloading the database?

With async replicas, a failure detector flags the node after missing heartbeats, a majority agrees, and the most up-to-date replica is promoted; clients learn the new map from a redirect or refresh. For the several seconds that takes, 1/32 of keys miss, adding about 45,000 reads per second at the database, so clients use short timeouts, a circuit breaker and leases to collapse duplicate work, and the database is provisioned with roughly 2x headroom. A gutter pool can hold the hottest keys of the dead shard for a few seconds. Afterwards, warm the replacement gradually rather than all at once.

How do you add a node without a spike of misses?

Use consistent hashing or slots so only about 3% of the keys change owner when going from 32 to 33 shards. Then migrate those slots live: copy keys in small batches with their remaining TTL from the old owner to the new one, serve reads from the source until a key has moved, redirect afterwards, and publish the new owner when the slot is empty. If you cannot copy, run both rings for a window, read from the new owner and fall back to the old one on a miss. Pace the migration to protect the source, and only resize when memory is below about 80% so the move has headroom.

Explain LRU, and why a real cache does not implement it exactly.

LRU evicts the item whose last access is oldest, based on the idea that recent use predicts future use. Exact LRU keeps all items in a linked list and moves the item to the head on every read, which needs a lock around shared pointers and 16 bytes of extra memory per item, so it becomes a bottleneck at high read rates. Memcached therefore uses segmented LRU with lazy bumping so hits are almost lock free, and Redis stores a coarse timestamp and, to evict, samples a few random keys and removes the oldest, which closely approximates LRU at no per-hit cost. If the workload has scans, an LFU policy protects popular keys better.

How do you share the cache fairly among many teams?

Namespace the keys per tenant and enforce three quotas: memory (evict preferentially from the tenant furthest over its allotment, so a growing neighbour cannot push a tenant under quota out), request rate (a token bucket at the proxy, with excess answered as fast misses), and limits on connections and value size. Unused quota may be borrowed, which is what makes a shared cluster cheaper than separate ones. Tenants with extreme or sensitive needs get dedicated shards. Per-tenant dashboards of hit rate, memory and throttling make quotas something teams can reason about, and credentials are scoped to namespaces.

Why is a cold cache so dangerous, and what do you do about it?

The databases are sized for the miss traffic (about 2% of reads), so a hit rate of zero sends 50 times more load than they were built for. They slow down, requests time out, the loaders never finish filling the cache, and the system stays broken even when the original cause is gone. So we avoid emptiness (rolling restarts, replicas, snapshots), bring new capacity in gradually by shifting a growing percentage of keys, prefill the hottest keys by replaying recent access logs at a controlled rate, and use leases and a global loader cap so the database sees each key's load once. During recovery we shed low-priority traffic.

Should the cache write to the database (write-through or write-behind)?

For a general-purpose shared cache I would not. Write-through needs the cache tier to know each database's schema and failure behaviour, slows every write and still misses writes that bypass it. Write-behind makes the cache the holder of the only copy of recent writes, so a node loss means data loss, which turns a cache into an under-engineered database. Cache-aside with delete on write keeps the cache stateless with respect to correctness: it can be wiped at any time and the system remains right, only slower. The exceptions are specific, tolerant use cases such as counters where losing a few seconds of increments is acceptable.

18. Recap

  • Sizing: 1.5M ops/s, 1 billion keys at about 1.1 KB gives roughly 1.3 TB of data, 32 shards of about 41 GB each on 52 GB of usable RAM, plus a replica for each. Memory is the cost driver, request rate per node is modest, and the database is sized for the 2% of reads that miss.
  • Sharding: consistent hashing with virtual nodes, or 16,384 slots, so a resize moves about 1/N of the keys; route through a proxy tier by default, with a smart-client option.
  • Memory: slab allocation avoids fragmentation at the price of about 10 to 15% internal waste; eviction uses approximate LRU (segmented or sampled) or LFU; TTLs are jittered and expire lazily plus actively.
  • Protection: leases, single-flight, stale-while-revalidate and TTL jitter defend against stampedes; near-cache, key replicas and sampling-based detection defend against hot keys.
  • Consistency: cache-aside, commit then delete, leases or versions against stale fills, a CDC feed for invalidation, and TTL as the backstop. The guarantee is bounded staleness.
  • Availability: asynchronous replicas with majority-agreed promotion; fast client timeouts, circuit breakers, database headroom, a gutter pool and a defined degraded mode, because the cache failing must never be a correctness failure.
  • Operations: slot migration for live scale-out, gradual warm-up, per-tenant quotas, and metrics led by hit rate, eviction age and database load from misses.
