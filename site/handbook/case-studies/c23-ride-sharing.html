Design a Ride-Sharing Service

A ride-sharing service connects a rider who wants to go somewhere with a nearby driver who is willing to take them, in seconds, while both phones move through a city. The hard parts are that the data is a firehose of moving points, that "nearest driver" must be answered thousands of times per second, that a driver must never be promised to two riders, and that price and arrival time must be computed from a live, constantly changing picture of supply and demand. This page designs it for 20 million trips a day and works through location ingestion, geospatial indexing, matching, ETA, surge pricing and failure modes.

How to approach this problem (read this first)

What the interviewer is really testing. There are three hard parts. First, can you see that this is several problems with different shapes: a huge stream of moving locations, a "who is near here" query, and a small transactional core where a driver must never be given two rides. Second, can you pick a geospatial index that suits points that move constantly. Third, can you make assignment correct under races (two riders, one driver) while keeping everything else fast and allowed to be slightly stale.

The thinking order, step by step

  1. Ask scope and scale questions. Say: "Single rider on demand rides only? How many trips a day, and how often does a driver report location?" Ask first because pooling, scheduling and delivery would each change the design, and the 4 second reporting interval is the number that drives everything.
  2. State the consistency stance. Say: "Locations can be stale; the assignment cannot be wrong." This one sentence tells the interviewer you will use two storage worlds. It comes before the estimate so the estimate can be split the same way.
  3. Estimate the location stream first. Say: "1 million online drivers every 4 seconds is 250,000 updates per second, about 300 times the peak trip rate." Do this number first because it dwarfs the trip requests (about 900 per second at peak) and it proves why location cannot go into the trip database.
  4. Draft the APIs: location, estimate, request, accept. Say: "Location is fire and forget with a sequence number; ride creation carries an idempotency key; the price is locked by a signed token." Start with location because it is the highest volume call.
  5. Show the naive design and break it. Say: "One table, a range query on latitude and longitude. It cannot take the writes, it scans a strip of the world, and two requests can pick the same driver." Each broken point leads to a fix: in-memory index, cells, conditional write.
  6. Introduce cells and the geo index. Say: "I divide the map into hexagon or S2 cells; a query reads the pickup cell plus neighbours." This is the first bottleneck solved, so it goes before matching.
  7. Do the matching and assignment path. Say: "Get about 30 candidates from cells, re-rank by road ETA, offer to one driver for 15 seconds, bind with a conditional write." Then show the trip state machine.
  8. Cover ETA and surge briefly. Say: "ETA is a road graph with traffic and an ML correction; surge is a smoothed, capped, rate limited multiplier per cell." Do them after the core works because both are inputs to it.
  9. Close with city partitioning, failures and fallbacks. Say: "The city is the unit of isolation, and every dependency has a fallback." End with what you would build first.

The decision points

  • Is this data durable or disposable? Ask what happens if it is lost for 4 seconds. Locations are disposable, so memory; trips are not, so a durable store.
  • Geohash, quadtree, S2 or H3? Ask whether the points move. They move constantly, so a fixed grid wins over a quadtree that must rebalance.
  • Greedy or batched matching? Ask whether scarcity is high. In dense cities batch for 1 to 3 seconds; elsewhere take the nearest by ETA.
  • Lock or conditional write for assignment? Ask what stays correct if a lease expires at the wrong time. Only the database condition, so correctness lives there.
  • Push or poll for live location? Ask who needs it. Riders on a trip get push; the pre-booking map polls.

Common mistakes on this problem

  • Writing every location to the main database. Fix: in-memory index plus a Kafka log.
  • Using a latitude and longitude range query. Fix: cell ids and ring search.
  • "Pick the first driver and mark busy." It races. Fix: conditional update plus a unique active ride per driver.
  • Ranking by straight line distance only. Fix: re-rank the top candidates by road ETA.
  • Recomputing surge at request time. The price shown changes. Fix: a signed surge token that locks the shown value.
  • Going global too early. Fix: city as the unit of partition and homing.
Interview tip Early on say: "This is four problems: a location firehose, a geospatial query, a small transactional trip core, and a feedback loop for surge and ETA." Then give each its own store and consistency level. That framing earns most of the credit.

1. Problem statement and clarifying questions

The prompt is one line: "Design Uber." A strong candidate does not start drawing cars on a map. Following the interview framework in Chapter 1, we first pin down what is being built. The questions below, with the answers we assume for the rest of the page, set the scope.

2. Requirements and scope

2.1 Functional requirements

  • A driver can go online and offline, and while online continuously publishes location and availability.
  • A rider can see nearby available drivers and get a fare estimate and pickup ETA for a pickup and destination pair.
  • A rider can request a ride. The system finds a suitable driver, offers the trip, and on acceptance binds the two together.
  • Both parties see each other's live location during the pickup and the trip.
  • The trip moves through a defined set of states (requested, offered, accepted, arrived, in progress, completed, cancelled) and every state change is recorded.
  • On completion the fare is computed from the actual route, time and the locked surge multiplier, and payment is triggered.
  • Either party can cancel under defined rules (possibly with a fee).

2.2 Non-functional requirements

  • Low latency matching and real-time updates: seconds, not minutes.
  • High availability for the request path: a rider who cannot request a ride goes to a competitor, so we favour availability for location and discovery data (Chapter 28).
  • Strong consistency for the assignment: exactly one driver per trip and exactly one trip per driver at a time.
  • Write-heavy ingestion: hundreds of thousands of location writes per second that must not delay trip requests.
  • Graceful degradation: if surge, ETA ML or maps are down, fall back to simpler estimates rather than fail the request.
  • Durable money and trip records: a completed trip is never lost.

2.3 Out of scope

Pooling and route-sharing optimisation, scheduled rides, driver onboarding and background checks, the payment processor internals (see Case study 14), turn-by-turn navigation rendering, fraud models beyond the hooks, and the internals of map tile serving.

3. Estimation with real arithmetic

Estimation (Chapter 2) must reveal which part is the expensive one. Here it is the location stream, not the trips. We round aggressively and keep the numbers consistent for the whole page.

3.1 Trips and demand

  • 20 M trips per day = 20,000,000 / 86,400 s = about 230 trip requests per second on average. Demand is spiky (commute hours, Friday night, events): peak is about 3x average, about 700 per second globally. A single city at a stadium exit can see 10x its own average for a few minutes, which is why we reason per city and per cell.
  • Not every request ends in a completed trip. If 80% complete, requests are about 25 M per day, about 290 per second average and about 870 per second at peak. We use about 900 requests per second as the design peak.
  • Average trip duration is 20 minutes. Concurrent trips on average = 20 M x 20 min / 1,440 min per day = about 280,000; peak about 3x = about 830,000 concurrent trips.

3.2 Driver supply and the location firehose

  • 5 M registered drivers; about 1 M are online on average and about 1.5 M at peak. Utilisation is trips-in-progress over online drivers = 280,000 / 1,000,000, about 28% (the rest are waiting or driving to a pickup).
  • Each online driver reports a location every 4 seconds. Average rate = 1,000,000 / 4 = 250,000 updates per second; peak = 1,500,000 / 4 = 375,000 per second. This is 400 times larger than the trip request rate, and it dominates the system's write load.
  • Payload per update: driver id (8 B), latitude and longitude (8 B), heading, speed, accuracy, timestamp, status and app overhead, about 100 bytes encoded compactly (Chapter 7). Peak ingress = 375,000 x 100 B = about 37.5 MB/s, about 300 Mbps. That is small for bandwidth but large in message count.
  • Raw location history if we keep it all: 250,000 x 100 B x 86,400 s = about 2.2 TB per day, about 790 TB per year. We keep full detail for 7 days for disputes and ML (about 15 TB hot) and downsample after that.

3.3 Rider reads

  • Riders open the app and look at the map about 60 M times a day (about 3 per completed trip including window shopping). Each view fetches nearby drivers: about 700 per second average, about 2,100 per second peak.
  • While watching the map or an approaching driver, the app receives pushed updates every 4 seconds. If 1 M riders are watching at peak, that is 1,000,000 / 4 = 250,000 pushes per second, comparable to the inbound location rate. This is the real-time delivery problem in section 8.3.

4. API design

Riders and drivers use REST for commands and a persistent connection (WebSocket or a push channel, Chapter 6) for live updates. User ids always come from the auth token, never from the body (Chapter 5).

POST /v1/drivers/me/status        { "state": "online" | "offline" }
POST /v1/drivers/me/location      (also sent as a stream on the open connection)
  body: { "lat": 37.7749, "lng": -122.4194, "heading": 90, "speed_mps": 8.2,
          "accuracy_m": 6, "ts": 1731859200000, "seq": 48211 }

GET  /v1/rides/{id}               current state, driver, ETA, location

# driver side
POST /v1/offers/{offer_id}/accept     POST /v1/offers/{offer_id}/decline
POST /v1/rides/{id}/arrived           POST /v1/rides/{id}/start    POST /v1/rides/{id}/complete

# push channel (server to client)
{ "type": "driver_location", "ride_id": "...", "lat": ..., "lng": ..., "eta_s": 180 }
{ "type": "ride_state", "ride_id": "...", "state": "ACCEPTED" }
{ "type": "offer", "offer_id": "...", "pickup": {...}, "expires_in_ms": 15000 }

Four details matter. First, client_request_id makes ride creation idempotent, so a rider on a flaky mobile network who taps twice does not order two cars (Chapter 32). Second, the surge_token is a signed, short-lived (a few minutes) opaque value that encodes the multiplier the rider was shown. It lets the server honour the displayed price without trusting a client-supplied number, and it expires so stale surge cannot be replayed. Third, the location endpoint returns 202 with no body: location is high-volume, loss-tolerant, and the next update supersedes the last, so the server does not wait on durability. Fourth, seq is a per-driver monotonically increasing counter so that out-of-order or duplicated updates can be discarded cheaply (Chapter 27).

6. A first simple design, then the scaled architecture

6.1 The simple version

Start with one app server and one database. Drivers post their latitude and longitude into a drivers table every 4 seconds. A ride request runs a query for the nearest available drivers, picks the first, and sets its status to busy.

SELECT driver_id FROM drivers
WHERE status = 'available'
  AND lat BETWEEN :lat - 0.02 AND :lat + 0.02
  AND lng BETWEEN :lng - 0.02 AND :lng + 0.02
ORDER BY (lat - :lat)^2 + (lng - :lng)^2 LIMIT 5;

This is correct and fine for a town. At our scale it fails in three ways. The table takes 375 K updates per second, which no single relational primary handles, and each update rewrites an index. A two-column range scan on latitude and longitude uses one B-tree index poorly: it can narrow on one axis and must filter the other, so it reads a long strip of the world. And "pick the first and mark it busy" has a race: two concurrent requests can both read the same driver as available. So we separate ingestion from the index, use a proper spatial partitioning (section 7.1), and make assignment an atomic conditional write (section 7.2).

Responsibilities. The Gateway authenticates, rate-limits (Chapter 16) and holds the long-lived connections (Chapter 11). The Location service accepts the 375 K updates per second, validates and de-duplicates them, updates the in-memory index, and publishes to Kafka. The Matching service (often called dispatch) owns the "find and offer" logic. The Ride service owns the trip state machine and is the only writer of trip rows. ETA and routing answers "how long from A to B now". Pricing computes fares and applies the surge multiplier from the surge cache. The Push service forwards driver positions to the right riders and state changes to both apps. All of these are stateless except the Location service's index and the Matching service's per-city state, which are partitioned by geography (section 9).

Step by step. (1) The rider app sends the request with its idempotency key. (2) The Ride service writes the ride in state REQUESTED to the durable trip store before doing anything else; this is the point at which the request is safe. It then hands the ride to Matching. (3, 4) Matching asks the geo index for available drivers in the cell containing the pickup and in rings of neighbouring cells until it has enough candidates (a few dozen). (5, 6) Straight-line distance is a poor proxy for pickup time (rivers, one-way streets, highways), so Matching asks the ETA service for road travel times from all candidates to the pickup in one batched call and re-ranks. (7, 8) It sends an offer to the best driver with a 15-second expiry; the driver accepts or declines, or the offer times out. (9) On accept, Matching calls the Ride service, which performs the atomic assignment (section 7.2). (10, 11) Both apps are notified, and the driver's live location starts being relayed to the rider (section 8.3).

6.5 The trip state machine

Walkthrough. Blue boxes are the happy path states, from left to right: REQUESTED, OFFERED, ACCEPTED, ARRIVED, IN_PROGRESS, and COMPLETED in green. The two red boxes below are exits: NO_DRIVERS and CANCELLED. 1. A ride starts in REQUESTED once saved. 2. When Matching sends an offer it becomes OFFERED. If the driver declines or the offer times out, it returns to REQUESTED so the next candidate can be tried (the text above the boxes). 3. An accepted offer moves to ACCEPTED, then the driver arrival moves it to ARRIVED, the start moves it to IN_PROGRESS, and the end to COMPLETED. 4. Dashed red arrows are cancellations, allowed from earlier states, with fee rules depending on how far along the ride is. The line at the top says the key thing: every arrow is a conditional write from an expected state. Draw the arrows one at a time and say "from this state only". Without this rule, a late accept after a cancel would revive a dead ride.

The state machine is the contract between rider, driver and billing. Writing it down makes concurrency tractable: every actor (rider cancel, driver accept, timeout timer, support agent) issues a transition request with the state it expects to see, and the database accepts at most one winner. This is optimistic concurrency, described in Chapter 8.

7. Deep dives

Four parts are where an interviewer will push: how to find nearby drivers fast, how to assign a driver without double-booking, how to compute an ETA, and how surge pricing works. Each is treated with alternatives and a decision.

7.1 Deep dive: the geospatial index

The query is "give me available drivers within about 2 km of this point, sorted roughly by closeness", and it runs both for the rider's map view (about 2,100 per second at peak) and for every match attempt (about 900 per second, plus retries). Meanwhile 375,000 positions per second are changing the data. The index therefore has to be cheap to update and cheap to query by area. The general techniques are explained in Chapter 58 and the dedicated Case study 13; here we apply them to moving objects.

The idea of a cell

Instead of storing a raw latitude and longitude and searching numerically, we divide the world into cells and give each cell an id. A point maps to its cell id with a pure computation, with no lookup. To find drivers near a point we compute the point's cell and its neighbouring cells, and read the set of drivers stored under each cell id. A query becomes "union of a few small sets", which is a handful of hash lookups.

Walkthrough. The grid on the left is a map cut into cells. The dark dot is the rider's pickup point. The amber cell around it is ring 0. The eight green cells around that are ring 1. Green dots are available drivers, and the blue cells are cells we have not read. The text on the right lists the steps. 1. Convert the pickup point to a cell id with arithmetic, no lookup. 2. Read the set of drivers stored under ring 0 and ring 1, which is nine small lookups. 3. If fewer than about 30 candidates come back, add ring 2, which is 16 more cells. 4. Stop at a radius cap. 5. Sort what you found by straight distance, keep the top 30, and hand them to the ETA service. The number to remember is the cell count (9, 25, 49), which stays the same however many drivers are in the city. Remove the neighbour rings and a driver just across a cell edge is missed.

Decision. Use a hierarchical cell grid, S2 or H3, at one fixed resolution for the driver index (cells about 0.5 to 1 km across, so a city has thousands of cells), and the same system at a coarser resolution for the partitioning key and for surge. Hexagons give uniform neighbour distances, which helps both the ring search and surge smoothing, so we pick H3-style hexagons (the diagram draws squares for simplicity); an interviewer who prefers S2 is equally well served, because the structure of the solution is identical. Quadtrees are the right answer for static points of interest (Case study 13) but poor for points that move constantly. A fixed grid never needs rebalancing: a move is "remove driver id from the old cell's set, add to the new one", and most updates do not even cross a cell boundary (at 8 m/s, about 30 m per update, versus cells of hundreds of metres), so most updates only overwrite the driver's record.

How the index is stored and partitioned

Two structures: driver_live: driver_id to record and cell_index: cell_id to set of available driver ids. A driver in an ongoing trip is removed from cell_index (not available) but keeps a live record so the rider can see them. The simplest implementation is Redis: hash plus set commands, or its geospatial commands, per city shard, which works to a few hundred thousand operations per second per cluster. At full scale the index lives inside the Location service as an in-process structure, partitioned by city (or by a coarse cell, for megacities), with each partition owned by exactly one process at a time using consistent hashing (Chapter 25, Chapter 57) and a replica receiving the same Kafka stream as a warm standby. The Redis form is fine to describe first because it is easy to explain; sorted-set ideas appear in Chapter 59.

Watch out Do not put the 375 K per second location writes into your trip database, and do not make them durable synchronously. They are a cache of "where the driver is right now". Also do not forget expiry: a driver whose phone lost signal must disappear from the index. Each record carries its timestamp, and the query ignores anything older than 30 seconds; a background sweeper removes stale entries from cell sets.

Batched matchingCollect requests and idle drivers in a city for a short window (about 2 seconds), build a cost matrix of ETAs, and solve a bipartite assignment (the Hungarian algorithm or a cheaper heuristic) to minimise total pickup time.Better global outcome, especially under scarcity; adds up to the window length in latency; more complex; needs per-city sequencing.

Decision. Start with greedy nearest by road ETA, and add small-window batching in dense cities, where the benefit is real. The window is short (1 to 3 seconds) so the extra latency is hidden inside the 5-second target. Offers go to one driver at a time with a 15-second expiry, and the ranking also considers driver attributes such as car class and rating thresholds. The ranking is a scoring function, not a rule, so it can be tuned and tested through experiments.

Making assignment atomic

When a driver accepts, we must bind ride and driver so that this driver has no other active ride and this ride has no other driver. Two things can go wrong. The same driver can accept two offers from two matching workers (two dispatchers overlapping near a boundary, or a retry), and the same ride can be accepted twice (a timeout fires and offers it to driver B while driver A's accept is in flight).

-- one transaction, executed by the Ride service
UPDATE rides SET state='ACCEPTED', driver_id=:d, version=version+1
  WHERE ride_id=:r AND state IN ('REQUESTED','OFFERED') AND version=:v;     -- ride still open?
INSERT INTO driver_by_ride_active(driver_id, ride_id) VALUES (:d, :r);      -- unique driver_id
-- if either statement affects 0 rows or violates the unique key, roll back: "offer no longer valid"

The conditional update protects the ride; the unique key on driver_id protects the driver. Both fit in one transaction when the two rows are on the same shard. If the ride row and the driver's active record live on different shards, use a two-step approach: first claim the driver with a conditional write on a small per-driver record (compare-and-set from available to reserved, with an expiry), then update the ride, and release the driver claim if the second step fails. That is a tiny saga (Chapter 48, Chapter 31) with a compensation. A single-key lock with a lease (Chapter 30) serves a similar purpose, but a lease can expire at the wrong moment, so the database's conditional write remains the source of truth: the lock only reduces contention, correctness never relies on it alone.

The offer timeline

The offer itself has state too. An offer row records the driver, the ride, an expiry and an outcome. The accept call carries the offer id; if the offer has expired or the ride has moved on, the accept is rejected and the driver app shows "this trip is no longer available". A timer (a delayed message on the queue, Chapter 38) fires at the expiry and moves to the next candidate, and the transition from OFFERED back to REQUESTED is itself conditional so that a timer that fires just after an accept does nothing.

7.3 Deep dive: ETA

An ETA is needed in three places: pickup ETA for ranking and for the rider, trip duration for the fare estimate, and a continuously updated ETA during the ride. Accuracy matters because it shapes the rider's decision to wait, and it feeds pricing.

Layer 1: the road graph and shortest path

Represent the road network as a directed graph. Nodes are intersections, edges are road segments with length, speed limit, turn restrictions and a travel-time function that depends on the time of day. The textbook answer is Dijkstra's algorithm, and its A* variant with a straight-line heuristic. On a metropolitan graph of millions of nodes, plain Dijkstra typically takes tens to hundreds of milliseconds per query, too slow when matching needs 30 ETAs per request at 900 requests per second (27,000 route computations per second). The standard speed-up is preprocessing: contraction hierarchies add shortcut edges so a query visits only a few hundred nodes and answers in about a millisecond; the cost is rebuilding when edge weights change, which is why live traffic is usually applied as a correction rather than by rebuilding every minute. For many-to-one queries (30 drivers to one pickup), run one backward search from the pickup and read all driver ETAs from it, which is much cheaper than 30 separate searches.

Layer 2: traffic and history

Edge speeds come from two sources. Historical profiles: for each edge and each 15-minute bucket of the week, the median speed, computed offline from the breadcrumb archive by a batch job (Chapter 37). Live speeds: a stream job reads the Kafka location log, map-matches each noisy GPS point to the most likely road segment (GPS can be 5 to 20 m off, worse among tall buildings), computes segment speeds over the last few minutes, and publishes deltas that the routing service blends with the historical value, weighting live data more when many drivers contributed recent samples.

Layer 3: learned correction

Even good segment speeds miss effects: traffic-light waiting, parking at the pickup, driver behaviour, rain. A machine-learned model takes the routing ETA as an input feature plus context (time, weather, pickup type, city) and predicts the residual, that is the amount by which the route-based estimate is typically wrong. The graph answers the structural part exactly and the model handles the noisy remainder. If the model is down we serve the uncorrected route ETA, which is still within reasonable error.

The ETA service is stateless apart from its in-memory graph copy, so it scales by adding replicas and is partitioned by region (a city's graph is only a few GB). Results for popular origin and destination cells at a given time bucket are cached for a short TTL (Chapter 13): fare estimates for the same cell pair within the same minute can safely be shared.

7.4 Deep dive: surge pricing

Surge (dynamic pricing) raises the price where demand exceeds supply. It has two jobs: reduce demand from riders who can wait or walk elsewhere, and attract more drivers to the area. The problem is to compute a multiplier per small area, quickly, without oscillation.

Walkthrough. The top row is the pipeline, left to right. 1. Ride requests (demand events) and driver locations (supply events) enter from the left. 2. The Stream job counts both per cell per minute and slides a 5 minute window over them, to ignore noise. 3. The Multiplier calc takes the ratio, smooths it with neighbouring cells, clamps it and limits how fast it can change. 4. The result is written into the Surge cache (amber), which Pricing reads on every estimate. The row of coloured cells at the bottom shows what happens to six neighbouring cells: each shows a raw ratio on top and the final multiplier below. The red cell with ratio 3.2 ends at 2.4x, not 3.2x, because it is averaged with its neighbours and capped. Green cells below ratio 1.2 stay at 1.0x. Point at that red cell when asked about oscillation. Without smoothing and the step limit, price and demand chase each other in a loop.

The computation, step by step. For each cell and each minute, the stream job (Chapter 37) counts demand (ride requests, and optionally app opens with a destination entered in the cell) and supply (available drivers in the cell, from the geo index, plus drivers about to finish nearby). It compares them over a sliding window of about 5 minutes to avoid reacting to noise. The raw imbalance, say demand divided by supply, is smoothed with the neighbouring hexagons so adjacent blocks do not have wildly different prices, which would look arbitrary and encourage riders to walk across a line. The result is mapped to a multiplier through a curve (for example flat at 1.0 until the ratio exceeds about 1.2, then rising), clamped to a maximum (regulators and event rules sometimes impose caps; during emergencies many operators cap or disable surge), and ramped so that it can rise or fall by only a bounded step each interval. The ramp avoids oscillation: if a high price makes demand drop and drivers arrive, the ratio falls, the price drops, demand returns, and the cycle repeats. Slow, smoothed changes damp that loop.

Decision. Ship the reactive ratio with smoothing and caps first; it is explainable to riders, regulators and support. Add a forecast layer later as an input to the same curve, with the reactive value as the fallback.

Pricing consistency. A rider sees a price at estimate time and requests a ride up to a few minutes later. We do not recompute at request time. The estimate response carries a signed surge_token (multiplier, cell, product, expiry of about 2 to 5 minutes). The ride request presents the token, the Ride service verifies the signature and expiry, and stores the multiplier on the ride row. The fare at completion is then computed from the actual distance and time with that locked multiplier. If the token has expired and the multiplier has since gone up, the app must show the new price and ask the rider to confirm again. The surge value itself is eventually consistent across replicas, and that is fine because the token pins the specific value each rider was shown.

8. Scaling, bottlenecks, hot spots and caching

8.1 Scaling the location ingestion

375 K updates per second is an easy number if the work per update is small and the data is partitioned. Partition by city (or by a coarse cell inside a big city): the gateway looks up the driver's current city from the last update and routes to that partition. Each partition receives its slice of the stream, so one city needs at most a few tens of thousands of updates per second, handled by a single process with an in-memory index. We batch writes (apply a hundred updates at a time), compress Kafka batches, and have drivers send updates adaptively: every 4 seconds while moving, every 15 to 30 seconds while stationary, and immediately on a status change. The mobile client also batches and delays sends on weak connections, with the server discarding out-of-order data by seq. Adaptive reporting can easily cut the rate substantially and also helps battery life (Chapter 56).

Walkthrough. From left to right: the drivers (purple), many stateless Gateways, the city partitions, Kafka, and three consumers on the far right (Archive, Speed job, Surge job). 1. Up to 375,000 messages per second arrive from 1.5 million drivers. 2. Any Gateway can take any driver, because the Gateway only looks up which city that driver is in. 3. It forwards the update to the partition that owns that city, each a primary with a replica. A megacity is split by coarse cell into several partitions. 4. Draw the solid hot path from drivers to partitions first, then add Kafka as a branch. This design means each partition sees only its city's slice, not the full 375,000. If Kafka were put in the hot path, a Kafka slowdown would stop matching.

8.2 Hot spots

  • Geographic hot spots. An airport, a stadium or New Year's Eve concentrates both drivers and requests in a few cells. The cell index handles that (each cell lookup is a set read), but the matching worker for a busy cell can become the bottleneck, so matching is sharded by cell prefix inside a city, and batched matching naturally absorbs bursts because it processes a window at a time. Airports often use a separate queue or staging lot: drivers are admitted into a virtual FIFO and matched in order, which also resolves fairness complaints.
  • Hot keys. A single driver record is written every 4 seconds, which is no problem, but a single surge key read on every estimate is hot. Surge values are cached in process in each Pricing instance with a 10 to 30 second TTL.
  • Skew across cities. A few cities carry a large share of trips, so partitions are sized by load rather than count, and megacities have dedicated clusters.

8.3 Delivering live location to riders

During a ride, a rider's app displays the driver's car moving. That needs a push path from the geo index to the right phone about every 4 seconds. At 1 M watching riders that is 250,000 pushes per second (section 3.3). The mechanism: when a ride is accepted, the Push service records a subscription "rider R watches driver D" in the gateway that holds the rider's connection (Chapter 6). The Location service, on each update for D, checks its small in-memory map of "drivers with active subscribers" and forwards the position to the gateway, which writes it down the rider's WebSocket. Only drivers on a trip need this, so the lookup is cheap. The app smooths the 4-second updates with interpolation so the car glides rather than jumps. If the connection drops, the app falls back to polling GET /rides/{id} every few seconds and reconnects. For the "cars nearby" view before booking, we do not subscribe at all: the app polls every 5 seconds, since a slightly stale picture is fine and polling is simple and scalable (the response can even be cached for a second per cell).

8.4 Caching and read paths

  • Nearby-drivers responses: cached per cell for about 1 second inside the Location service; at 2,100 requests per second the saving is modest but removes duplicate scans on busy cells.
  • Fare estimates: cached by (origin cell, destination cell, product, minute) for about a minute, then adjusted for the current surge multiplier.
  • Geocoding and place search (typing an address) use a separate search service and cache heavily; autocomplete itself is Case study 11.
  • Trip reads (GET /rides/{id}): primary key lookups on the trip store with a replica read for non-critical views; the apps also hold the state locally and reconcile on reconnect.

9.2 Consistency and idempotency decisions

  • Strongly consistent: the ride row and the driver-active uniqueness. Every state transition is a conditional write. These are the only places where we pay for consensus or a synchronous replica write (Chapter 28, Chapter 29).
  • Eventually consistent, loss-tolerant: driver locations, nearby-driver lists, surge values, ETA caches.
  • Idempotent commands: create ride (client request id), accept offer (offer id plus conditional update), complete ride (conditional on IN_PROGRESS), charge (payment idempotency key). Every retry is safe, which is what lets us use at-least-once messaging throughout (Chapter 35).
  • Ordering: location updates carry a driver-local seq; trip transitions carry a version. A late message loses by comparison rather than by wall clock time, because phone clocks are unreliable (Chapter 27).
  • Dual views: the rider and the driver may briefly disagree (the rider cancelled but the driver's app has not received it yet). The server's state wins; the driver's later "start trip" fails the state condition and the app corrects itself.

9.3 Multi-region

Cities are nearly independent: a rider in Mumbai never matches a driver in Chicago. We therefore make the city (or a group of nearby cities) the unit of isolation, in the spirit of cells (Chapter 42). Each city is homed in one region that holds its geo index, matching state, trip shard and surge job, so the whole hot path is single-region and low-latency, and an outage affects only the cities in that cell. Cross-region data is limited to the user and driver account directory (replicated, mostly read), the global pricing configuration, and analytics, shipped asynchronously through Kafka mirroring (Chapter 26). A traveller who lands in a new city simply uses that city's region, with their profile fetched from the account service. Trips near a region boundary are rare and handled by assigning border cells to one region. Disaster recovery is by replicating each city's trip data to a second region; on failover, drivers' apps reconnect and the live index rebuilds in a few seconds, and only the in-flight trips need reconciliation from the replicated trip state.

10. Security, abuse, monitoring and cost

10.1 Security and abuse

  • Authentication and authorisation: short-lived tokens; a driver can only read their own offers and the rider's pickup and name for an assigned ride; a rider sees only the assigned driver's position, never other riders. Check authorisation on every push subscription (Chapter 55).
  • Location privacy: positions are personal data. Minimise retention (full detail 7 days, then aggregated), restrict internal access, and coarsen the positions of nearby drivers shown on the pre-booking map (round them, or hide the exact heading) so an observer cannot track an individual driver. Reveal the exact destination to the driver only as late as the product allows (Chapter 56).
  • Fraud: GPS spoofing to fake surge hot spots or fake trips; collusion between rider and driver to collect incentives; stolen payment cards. Controls include velocity checks, device attestation, anomaly detection on trips with no movement, and holds on suspicious payouts.
  • Abuse of the API: rate limits per user, device and IP at the gateway; limits on cancellation frequency (Chapter 16).
  • Safety: trip sharing, an emergency button and audit trails are served from the same trip and location data, so retention and access rules must make room for them.

10.3 Cost notes

  • Compute for the location tier is modest: 375 K small messages per second across a few hundred cores. Most cost is in maps and ML (routing graph replicas per region, model serving) and in storage of the location archive (about 2.2 TB per day raw), so downsampling after 7 days is a major saving: keeping one point per 15 seconds after the first week is roughly a 4x reduction, and older data is dropped at the end of the retention period.
  • Third-party map data and map matching (or the cost of building them) is often a large vendor line item; caching ETAs and geocoding is the lever.
  • Push notifications and SMS for offers and status are billed per message; use persistent sockets first and fall back to push or SMS only if the socket is down.
  • Driver incentives, not infrastructure, are typically the biggest spend; better matching (lower pickup time) can save more money than any cache.

11. Evolution: phasing, 10x scale and alternatives

11.1 What to build first

  1. Phase 1 (one city): a relational database with a spatial extension or a Redis geo index, a single-region deploy, greedy nearest matching with straight-line distance, flat pricing, polling for live location. This validates the product.
  2. Phase 2 (a few cities): separate the Location service and the trip store, add Kafka, move to the cell index, introduce the state machine with conditional writes, add push over WebSockets, and use a map provider's routing API for ETA.
  3. Phase 3 (many cities): own the road graph and the ETA service, reactive surge, per-city partitioning and cells, batched matching in dense cities, an experimentation framework.
  4. Phase 4 (global): ML ETA residuals and demand forecasting, multi-region cells with DR, pooling and scheduled rides, fraud systems.

11.2 At 10x scale

  • 200 M trips per day, 3.75 M location updates per second at peak. The partitioned-by-city architecture scales roughly linearly; what changes is that the largest cities need sub-city partitions with their own matching workers, and Kafka needs more partitions (Chapter 34).
  • Edge aggregation: regional location collectors reduce wide-area traffic by batching and by dropping redundant updates from stationary drivers.
  • Matching moves toward global optimisation per city per second, which increases ETA query volume substantially; precomputed ETA matrices between cells in the same city become attractive.
  • The location archive grows to roughly 8 PB per year raw, so the retention policy and columnar archive formats become a cost priority.

11.3 Alternatives not chosen

  • One global geo index. Simple to reason about but gives up isolation and adds cross-region latency for no benefit, since matches are always local.
  • Writing every location to the primary database. Wastes durability on data that expires in seconds and would require a huge write-optimised cluster.
  • Quadtree index. Adapts to density, but rebalancing under constant movement is costly; a fixed grid with finer cells in dense areas (hierarchical resolution) gives most of the benefit.
  • Broadcasting offers to all nearby drivers. Increases noise for drivers and wasted offers; kept only as a fallback in supply-poor areas.
  • A pure ML dispatcher with no explicit state machine. Models can rank candidates but must never own the correctness of assignment.

12. Interview Q&A

Why do you keep driver locations in memory and not in the main database?

Location data is written 375,000 times per second at peak, and each value is only useful for a few seconds, because the next update replaces it. Making each write durable would need a huge write-optimised cluster to preserve data that has almost no value after 4 seconds. Instead the live position is held in an in-memory index, with a replica fed from the same stream, and the full history is appended to Kafka and archived for ML and disputes. If an index node dies, it refills from the next round of driver updates within seconds. The trip database, by contrast, holds the small amount of data whose loss would matter, such as who was assigned to which ride.

How do you find the closest drivers to a rider efficiently?

I divide the map into hierarchical cells (S2 or H3), keep for each cell the set of available drivers, and compute the rider's cell id by pure arithmetic. A query reads the rider's cell and its neighbours (8 for square S2 cells, 6 for H3 hexagons), widening to the next ring if there are fewer than about 30 candidates. The cost is bounded by the number of cells read, not by the number of drivers in the city. I then rank by straight-line distance, keep the top 30, and re-rank by road ETA from the routing service, because straight lines ignore rivers, one-way streets and highways. A fixed grid is preferable to a quadtree here since drivers move constantly and a grid never needs rebalancing.

Two riders request at the same instant and the same driver is the best match for both. What happens?

Both matching attempts may offer to that driver, but only one accept can win, because assignment is a conditional write. The Ride service updates the ride only if it is still open, and inserts into the active-driver table whose unique key on driver id rejects a second active ride for that driver. The loser gets "offer no longer valid" and the dispatcher moves to the next candidate for that rider. To reduce wasted offers, a driver with an outstanding offer is also marked reserved in the index for the offer duration, and batched matching in dense cities assigns the contested driver to whichever rider gives the lowest total cost. Correctness never depends on that reservation, only the database condition does.

How would you compute the ETA, and why not just use straight-line distance?

Straight-line distance can be badly wrong: a driver across a river is 300 metres away and 20 minutes away. I use a road graph with time-of-day speeds, and a speed-up such as contraction hierarchies so a route query takes around a millisecond and one backward search from the pickup serves all candidate drivers at once. Live speeds, learned from the drivers' own GPS after map matching, are blended with historical profiles. Finally a machine-learned model predicts the residual error of the route estimate, adding effects such as traffic lights and pickup delay. If the model or live feed fails, the system falls back to the plain graph estimate, then to a distance-based guess, so ETAs always exist.

Explain how surge pricing is computed and how you stop it from oscillating.

A stream job counts demand (requests) and supply (available drivers) per hexagonal cell over a sliding window of a few minutes. The ratio is smoothed across neighbouring cells, mapped through a curve to a multiplier, clamped at a maximum, and ramped so it changes by a bounded step per interval. Oscillation occurs because a price rise cuts demand and draws drivers, which pushes the ratio down, which drops the price, which brings demand back. The sliding window, spatial smoothing and bounded step size all slow that feedback loop. The rider is shown a signed token with the multiplier, so the price shown is the price charged even though the underlying value keeps changing.

What happens if a driver accepts a ride just as the rider cancels?

Both events become conditional state transitions on the same ride row. The cancel moves REQUESTED or OFFERED to CANCELLED, the accept moves OFFERED to ACCEPTED, and the database applies whichever arrives first. The other fails its precondition. If the cancel wins, the driver's accept returns "trip no longer available" and the driver app clears the offer. If the accept wins, the rider's cancel is processed as a cancellation of an accepted ride, which may carry a fee under the cancellation rules. Neither actor can push the trip into an invalid state, and because the commands are idempotent, retries are harmless.

How do you deliver the driver's moving position to the rider's phone?

When a ride is accepted, the rider's gateway connection is registered as a subscriber to that driver. Each time the Location service accepts a position update for a driver who has subscribers, it forwards the update to the gateway holding the rider's WebSocket. Only drivers on a trip are tracked, so the extra lookup is small even though the total push rate can reach 250,000 per second at peak. The app interpolates between updates so the car moves smoothly. If the socket drops, the app falls back to polling the ride endpoint and reconnects. Browsing the map before booking uses simple polling every few seconds, because slightly stale data is fine and polling scales trivially.

How would you scale this to multiple regions and what data crosses regions?

I treat the city as the unit of isolation. Each city is homed in one region that has its geo index, matching service, trip shard and surge pipeline, so the latency-critical path never crosses a region boundary. Only slow-moving data crosses regions: the account directory, configuration, and analytics streams. A rider travelling abroad uses the new city's region, with the profile fetched on demand. For disaster recovery, a city's trip data is replicated to a second region, and on failover the location index is rebuilt from fresh driver updates in seconds. This also contains blast radius, since a bad deployment or a failure in one city cell does not affect the others.

How do you handle bad GPS data, such as a driver whose position jumps across the city?

I filter at ingestion and again at consumption. Each update carries an accuracy value, so low-accuracy points are dropped. A speed check against the previous position rejects teleports, for example implied speeds above about 200 km/h. The sequence number discards out-of-order duplicates. For road-speed learning and fares, points are map-matched to the road network with a probabilistic model that considers the sequence of points, which smooths jitter in urban canyons. For fares we use the matched route and fall back to the estimated route if breadcrumbs have gaps. A driver who goes silent for 30 seconds is removed from the available set, so a dead phone cannot be offered rides.

How would you add pooled rides to this design?

Pooling changes matching from a driver-per-rider problem to one where a new request can join a trip in progress. The Matching service would also query active trips whose route passes near the pickup, and evaluate the detour for existing riders using the ETA service, accepting only if every rider's added delay stays under a threshold. The trip entity becomes one vehicle trip with several rider legs, and the "driver has one active ride" constraint becomes a capacity constraint. The state machine gets per-leg states, and pricing splits the fare. The geo index, ETA and push layers do not change, which is a good sign that the original decomposition was right.

Recap

  • The problem splits into four shapes: a location firehose (375 K updates per second), a geospatial query, a small transactional trip core (about 900 requests per second) and an analytic loop for surge and ETA.
  • Live locations live in memory, partitioned by city and indexed by hexagonal or S2 cells; they are loss-tolerant and refilled every 4 seconds. Kafka carries the stream to side consumers.
  • Nearby search is a ring search over cells, bounded by cells read, then re-ranked by road ETA from a contraction-hierarchy router with live speeds and an ML residual.
  • Matching starts greedy and moves to small-window batched assignment in dense cities. Assignment correctness comes from conditional writes: a version check on the ride and a unique active-ride key per driver.
  • The trip is an explicit state machine; every command is idempotent and every transition is a compare-and-set, so late, duplicated or racing messages are harmless.
  • Surge is a smoothed, clamped, rate-limited multiplier per cell; the rider pays the value in the signed token they saw.
  • Cities are the unit of isolation and multi-region homing, which keeps the hot path local and contains failures.
  • Every dependency has a fallback: no surge means base fare, no ML means graph ETA, no Kafka means stale surge but working matching.
