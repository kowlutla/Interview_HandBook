Design a Gaming Leaderboard

We design the ranking service behind a large online game: players finish matches, their scores change, and millions of people ask "what is my rank?", "who is in the top 100?" and "who is near me?" The interesting part is that a leaderboard is a database query (order everything by score) that has to answer in a few milliseconds while the data changes thousands of times per second. We build it on Redis sorted sets, then show what breaks when one sorted set is no longer enough.

How to approach this problem (read this first)

What the interviewer is really testing. A leaderboard sounds like a one-line SQL query, so the test is whether you see why that query is slow for "what is my rank" and what data structure fixes it. After that there are three hard parts. One is making a very hot write path correct when events are retried, so a match is counted exactly once. Another is ties and resets: equal scores need a fair order, and daily, weekly and season boards need clean rollover. The last is what to do when one sorted set no longer fits on one machine, and how you answer rank questions across shards.

The thinking order, step by step

  1. Ask what views the board must serve. Say: "Top K, my exact rank, players around me, a friends board, and which time windows?" Ask this first because each view is a different query, and "my rank" is the one that makes this problem hard.
  2. Ask about exactness and ties. Say: "Does a player ranked 40 millionth need an exact rank? And how do equal scores order?" The answer to the first decides whether sharding is easy. The second changes the score encoding.
  3. Estimate the write rate first. Say: "30 million daily players times 10 matches is 300 million events a day, about 3,500 a second, 14,000 at peak, and 42,000 sorted-set updates at peak with three windows." Writes first, because for a leaderboard the writes, not the reads, are the surprise.
  4. Estimate memory. Say: "About 100 bytes per member, 100 million members, so 10 GB for the season set and about 19 GB for all windows of one mode." This shows a single node can hold it, so you do not shard too early.
  5. Draft the API. Say: "The write carries an event id for idempotency and returns 202. Reads carry a window and say whether the rank is exact." These two details are what interviewers check.
  6. Name the data structure. Say: "A Redis sorted set: a hash table plus a skip list with spans, so rank, range and update are all logarithmic." Say why a database index does not do this as well at this update rate.
  7. Show the simple design and break it. Say: "One service and one Redis works for a million players. It fails on durability, duplicates, bursts and capacity." Then add the log, the dedupe, the queue and the score table.
  8. Walk the write path. Show the order: log, dedupe, durable table, Redis, then commit the offset. Explain why a crash anywhere is safe.
  9. Deep dive windows or sharding. Use the time you have left. Close with failures, rebuild from the log, and the hybrid of an exact top set plus approximate rank for the rest.

The decision points

  • SQL or a sorted set? Ask: how fast must rank queries be while the data changes tens of thousands of times a second? Only an order-statistic structure in memory does that, so Redis.
  • Write synchronously or through a queue? Ask: can the game wait for ranking? It must not, so go through a log with idempotent consumers.
  • Fan out to all windows on write or compute windows on read? Ask: can a union of huge sets run on the hot path? No, it blocks the node, so write to each window.
  • Shard by player hash or by score range? Ask: which queries must be cheap? Hash makes writes easy and ranks expensive; score range makes reads cheap and writes complex. Attention is skewed to the top, which suggests a hybrid.
  • Exact or approximate rank for everyone? Ask: who looks at the number? Exact matters at the top, and an estimate is fine at the bottom.

Common mistakes on this problem

  • Answering with ORDER BY and an index. Fix: explain that rank means counting higher scores and show the logarithmic structure.
  • Sharding on the first diagram. Fix: do the memory arithmetic and show that one node holds a mode.
  • Using an increment without a duplicate guard. Fix: an event id and a dedupe step before the increment.
  • Treating Redis as the only copy. Fix: keep a log and a score table, and rebuild Redis from them.
  • Ignoring ties. Fix: pack the score and inverted time into one number.
  • Computing weekly boards with a union at read time. Fix: write to each window and expire old ones.

1. Problem statement and clarifying questions

The prompt: "Design a leaderboard for an online game." A leaderboard looks trivial. In a relational database it is SELECT player, score FROM scores ORDER BY score DESC LIMIT 100. The trouble starts with the other queries. "What is the rank of player 7,412,090?" means counting how many players have a higher score, which on a table of 100 million rows is a scan or at best an index range count, repeated by millions of players who refresh their rank screen after every match. Before drawing anything, we ask questions that pin down the shape of the problem, and we state the answers we assume.

QuestionAssumed answer
How many players?100 million registered, 30 million daily active (DAU), one global ranking per game mode plus regional rankings.
What is a "score"?A non-negative integer, at most about one billion, computed by the game server after a match. It accumulates over a season (for example ranked points). It is not sent by the client, because clients cannot be trusted.
Which views are needed?Top K (K up to 100, paged up to 1,000), my exact rank and score, an "around me" window (the 5 players above and below me), and a friends leaderboard.
Which time windows?All-time (per season), weekly, and daily. Weekly and daily boards reset on a schedule, and past winners must be retrievable.
How fresh must it be?A player's own rank must reflect the match they just finished within about one second. The public top 100 may lag by a few seconds.
How are ties handled?Players with equal scores are ordered by who reached the score first. Two players never share exactly the same position.
Is exact rank required for everyone?Exact for the top 10,000 and for any query inside one shard. For a player ranked 40 millionth, "top 40 percent" is acceptable (section 11).
Is data loss acceptable?A leaderboard can be rebuilt, but not from nothing. Scores are the product of matches and must not be silently lost, so a durable source of truth is required (section 14).
Interview tip State the central insight in the first minutes: "Ranking is an order-statistic query. A sorted set backed by a skip list answers rank, top K and range in logarithmic time, so the whole design is about keeping that structure in memory, keeping it durable, and splitting it when it outgrows a machine." Then ask whether exact global rank is needed for every player, because that one answer decides whether sharding is easy or hard.

2. Requirements and scope

2.1 Functional requirements

  • Submit a score. The game backend reports a result for a player. The leaderboard updates the player's total (or keeps their best score, depending on the game mode).
  • Top K. Return the first K entries (rank, player, score), with paging.
  • My rank. Return the exact rank and score of one player.
  • Around me. Return the window of players immediately above and below a given player.
  • Friends board. Return the player and their friends ordered by score.
  • Windows. Separate daily, weekly and season boards, with archived results of finished periods.

2.2 Non-functional requirements

  • Latency: read endpoints p99 under 50 ms from the client's region; score update visible in the player's own rank within 1 second.
  • Availability: 99.95 percent for reads. A degraded leaderboard (slightly stale) is far better than an error page, because the game itself must not depend on it.
  • Scale: tens of thousands of writes per second at peak, with read traffic roughly twice the write traffic (section 3).
  • Correctness: every accepted match result is counted exactly once, even when events are retried or delivered twice.
  • Durability: a Redis node crash must not lose confirmed scores.

2.3 Out of scope

Matchmaking, the anti-cheat engine itself (we only note where it plugs in), and the in-game economy. We also exclude monetary prizes, which would demand stronger audit guarantees than a normal leaderboard. Real-time push of rank changes is covered briefly as an extension, not designed in full (the transport is in Chapter 6).

3. Estimation

Technique reminder: start from users, derive average rates, multiply by a peak factor, then size memory and bandwidth (Chapter 2). Let us do it with real arithmetic.

3.1 Write rate

30 million DAU, each finishing about 10 scored matches a day, gives 30M x 10 = 300 million score events per day. A day has 86,400 seconds, so the average is 300,000,000 / 86,400 = about 3,500 events per second. Gaming traffic is peaky (evenings, weekends, a new season launch), so we take a peak factor of 4: about 14,000 events per second. Each event produces one update per window (daily, weekly, season), so the leaderboard stores see 3 x 14,000 = 42,000 sorted set updates per second at peak.

3.2 Read rate

Each active player opens a leaderboard screen about 20 times a day (after matches, from the menu), which is 30M x 20 = 600 million reads a day, or 600,000,000 / 86,400 = about 6,900 per second on average and about 28,000 per second at peak (factor 4). Each screen typically triggers two backend calls: "my rank plus around me" and "top 100". The top 100 call is identical for every user, so it is cacheable (section 9). The personalised call is not.

3.3 Memory

A Redis sorted set stores each member in two structures: a hash table (member to score) and a skip list (ordered by score). With a short member string (an 8 to 16 byte player id), the total is roughly 80 to 120 bytes per member including pointers and allocator overhead. We use 100 bytes. For the season board, 100M members x 100 B = 10 GB. The weekly board holds players active in the week, say 60M x 100 B = 6 GB. The daily board holds 30M x 100 B = 3 GB. Total: about 19 GB for one game mode. That fits on one machine with 32 to 64 GB of RAM for a single mode, but we have many modes and regions, and we must leave headroom for fork-based snapshots (section 14), so we plan on replicas plus sharding.

3.4 Storage and bandwidth

Durable score events: 300M x 100 B = 30 GB per day, about 11 TB per year if kept raw, which is why raw events live in cheap log storage with a retention window (30 days hot, then compressed archive). The current score table is only 100M rows x 50 B = 5 GB. Bandwidth is small: a top 100 response is about 100 x 40 B = 4 KB, so even 28,000 reads per second is about 112 MB/s if every response were uncached, and a cache removes most of it.

QuantityValueConsequence
Score events3,500 / s average, 14,000 / s peakIngest through a queue; smooth bursts
Sorted set updates42,000 / s peak (3 windows)Fits one Redis primary (roughly 100,000 simple ops/s) but with little headroom

Conclusion: this is not a huge system at 100M players. A single well-tuned Redis primary per board really can do the job, and an interview answer that starts with sharding is premature. But the same design at 1 billion players, or with 100 modes and regions, needs the techniques of sections 10 to 12. We design for the first and explain the second.

4. API design

The API is a small REST (or gRPC) surface. The write endpoint is internal (called by trusted game servers), the reads are public through the gateway (see Chapter 5).

POST /internal/v1/scores                      (game server only, mTLS)
  { event_id, player_id, board: "ranked-eu", delta: 25, match_id, ts }
  -> 202 { accepted: true }

GET /v1/boards/{board}/top?window=weekly&offset=0&limit=100
  -> { window_id: "2026-W46", as_of, entries: [ {rank, player_id, name, score}, ... ] }

GET /v1/boards/{board}/me?window=season
  -> { rank: 120345, score: 8421, percentile: 99.88, exact: true }

GET /v1/boards/{board}/around?window=daily&span=5
  -> { me: {rank, score}, above: [ ...5 ], below: [ ...5 ] }

GET /v1/boards/{board}/friends?window=weekly      (friend list from the social service)
  -> { entries: [ {rank_among_friends, player_id, score}, ... ] }

GET /v1/boards/{board}/archive?window=weekly&window_id=2026-W45&limit=100
  -> frozen final standings of a finished period

Design notes. The write carries an event_id, a unique id per match result, which is the idempotency key (Chapter 32): the same event delivered twice must add its points once. We send a delta rather than an absolute score so that two matches finishing close together both count, but a game mode that keeps the best single score would send an absolute score and use "keep max" semantics. The write returns 202 Accepted, because processing is asynchronous through a queue (section 7); the client learns about its new rank through the next read, or a push. Reads carry the window and return a window_id so a client rendering Monday's board knows it is not mixing it with Sunday's. The response states exact: true/false so the UI can show "top 40 percent" when only an estimate is available.

5. Data model and storage choice

We need two kinds of storage with different jobs. The first answers ranking questions fast. The second remembers the truth durably. Mixing the two jobs in one store is the common mistake.

StoreHoldsWhy this store
Redis sorted sets (Chapter 15, Chapter 59)One key per board and window: member = player id, score = encoded scoreRank, range and update are logarithmic and in memory. A relational index can also do it, but not at this update rate and read latency.
Event log (Kafka, Chapter 34)Every score event, partitioned by player idDurable, replayable. It absorbs bursts and lets us rebuild any board.
Wide-column or relational store (Chapter 20)Current score per (board, window, player), player profile (name, avatar), archived final standingsDurable source of truth for "what is this player's score"; cheap point reads; supports bulk rebuild by scanning.

5.1 Key naming

lb:{ranked-eu}:season:2026S4        sorted set, all-time for the season
lb:{ranked-eu}:week:2026-W46        sorted set, expires 8 weeks after the week ends
lb:{ranked-eu}:day:20261117         sorted set, expires 14 days after the day ends
lb:{ranked-eu}:cnt:season:2026S4    small hash of per-shard counts (sharded mode only)
player:{id}:profile                 name, avatar (a separate cache; never in the sorted set)

The sorted set member is only the player id, never a name or a JSON blob. Keeping members short keeps the 100 bytes per member estimate honest, and a rename does not touch the leaderboard. The names for the 100 rows of a page are fetched in a batch from the profile cache after ranking is known. The braces in {ranked-eu} are a Redis Cluster hash tag so that keys of one board land in the same slot when we want them together (for example to run one script over daily and weekly).

6. How a Redis sorted set works, and why it fits

A sorted set (ZSET) holds unique members, each with a floating point score, kept ordered by score. Internally, once a ZSET grows beyond a small size (by default more than 128 entries, or a member longer than 64 bytes, it switches from a compact list to the full form), Redis stores two structures side by side.

  • A hash table from member to score. It answers "what is player X's score?" in constant time, and detects whether a member exists.
  • A skip list ordered by score (ties broken by member bytes). A skip list is a linked list with extra "express lane" pointers at several levels, built randomly so that each node appears at level 1 with probability 1, at level 2 with probability about 1/4, and so on (Redis uses p = 0.25 and a maximum of 32 levels). A search starts at the top lane, moves right while the next node is smaller, then drops down a lane. The expected number of steps is O(log N). Redis augments each forward pointer with a span, the number of bottom-level nodes it skips. Adding spans along the search path gives the rank of a node, which is how ZRANK is logarithmic and not linear.
Walkthrough. Three layers of boxes show a skip list, drawn from the fast lane at the top to the full list at the bottom. Purple boxes are the heads, blue boxes are nodes in the express lanes, and green boxes at level 1 are every player in score order: A 990 down to G 500. Each blue box shows a span, the number of bottom-level nodes the pointer jumps over. 1. To find the rank of F, start at the head of the top lane. 2. Jump to C, which skips 3 nodes. 3. Jump from C to F, which skips 3 more. 4. Add the spans, 3 plus 3, to get 6, so F is the sixth highest. Only two hops were needed. The design is a list with shortcuts and counts, instead of a plain sorted array that needs a scan to count. On a whiteboard, draw the bottom row first, then add lanes and write the spans. Without spans the structure could find a score quickly but could not give a rank.
CommandPurposeCost
ZADD key GT score memberInsert or update; the GT flag only updates when the new score is greater (keep-best semantics)O(log N)

ZCOUNT key min maxHow many members have scores in a range (used by the sharded rank)O(log N)
ZREMRANGEBYRANKTrim the board, for example keep only the top 1,000,000O(log N + M)

Two properties make this the right primitive. First, every ranking question is a logarithmic operation: with N = 100 million, log2 N is about 27, so a rank lookup is a few dozen pointer hops, around 10 to 50 microseconds of CPU plus network. Second, updates and reads touch the same structure atomically. Redis executes commands one at a time on a single thread, so a ZINCRBY followed by a ZREVRANK inside one script cannot interleave with another client's command. The cost is that a single sorted set lives on a single node and is bounded by that node's memory and single-thread throughput, which is the thing we must engineer around at scale. The alternative of a relational table with an index on score is discussed in section 11.

Watch out ZREVRANGE with a large range (say 1 million entries) blocks the single Redis thread for tens of milliseconds and stalls every other command on that node. Always cap limit at the API (we allow 1,000 per page), and never let an admin tool or analytics job run unbounded range reads against the live primary.

7. A first simple design, then the scaled architecture

7.1 First design: one service, one Redis

The simplest working version is a Leaderboard service in front of one Redis instance. The game server calls POST /scores, the service runs ZINCRBY lb:season delta player, and the read endpoints call ZREVRANK, ZREVRANGE and ZSCORE. This is perfectly adequate for a game with a million players, and a candidate who says so earns trust. It breaks in four ways at our scale, each of which drives one part of the final design.

  1. Durability. Redis memory is the only copy. A crash with the default snapshot schedule loses the last minutes of scores, and a total loss loses everything. We add a durable event log and score table (section 14).
  2. Duplicates and retries. If the game server times out and retries POST /scores, ZINCRBY adds the points twice. We add an event id and a deduplicating consumer (section 8).
  3. Bursts. A season launch can multiply the write rate for minutes. Synchronous writes from game servers would push back into gameplay. We put a queue between them (section 8).
  4. Capacity and blast radius. One primary holds everything. When memory or CPU runs out, or the node dies, every board is affected. We add replicas, then sharding (sections 10 to 12).

8. Request flow: submitting a score

  1. A match ends. The authoritative game server computes the result and calls POST /internal/v1/scores with a unique event_id (for example the match id plus player id).
  2. Score ingest validates the schema and the signature, and appends the event to the Kafka topic, keyed by player_id. It replies 202 as soon as Kafka has acknowledged the write to its replicas. The game is never blocked on Redis.
  3. A ranker worker reads the event. It checks the dedupe set (SET dedupe:{event_id} 1 NX EX 172800); if the key already existed, the event is a duplicate and is skipped.
  4. The worker updates the durable score table: score = score + delta (a conditional update that also records the event id, so even a lost dedupe key cannot cause double counting).
  5. The worker updates Redis with one pipelined round trip containing three commands, one per window, on the daily, weekly and season sets. Plain ZINCRBY works when ties are not encoded; with the tie-break of section 9 it sends ZADD with the encoded score computed from the new total.
  6. The worker commits its Kafka offset. If it crashes before committing, the event is processed again, and steps 3 and 4 make that harmless.
Walkthrough. This sequence diagram has six lifelines: game server, ingest, Kafka, ranker, score table and Redis. 1. The game server sends the result with an event id. 2. Ingest appends it to Kafka, Kafka acknowledges, and the dashed green arrows return a 202 to the game server. This is the end of the player's wait. 3. Later, the ranker polls a batch from Kafka. The green box marks the dedupe check, which drops events already seen. 4. The ranker adds the delta in the score table. 5. In one pipelined call it updates the daily, weekly and season sets in Redis. 6. It commits the offset last. The note at the bottom says a crash before the commit replays the event, and the dedupe check and the conditional update make the replay harmless. The design is at-least-once delivery plus idempotent apply. Point at the order: table before Redis, commit last. Swap the order of the table and Redis and Redis may run ahead of the truth.

Why this ordering? The durable score table is written before Redis. If Redis is lost, the table can rebuild it. If the table write succeeds and the Redis write fails, the worker retries (the commit comes last), and Redis catches up. The opposite order (Redis first) could leave Redis ahead of the truth, with no record of why. The at-least-once delivery of a log plus idempotent apply gives the effect of exactly-once processing, the standard pattern from Chapter 32 and Chapter 35.

One subtle point: ZINCRBY itself is not idempotent, so the guard must come before it. Where a mode keeps the best score, ZADD key GT score member is naturally idempotent (applying the same score twice leaves the same state), which is another reason to prefer "best score" semantics when the game design allows.

9. Ties, score encoding and reading flows

9.1 The tie problem

Two players with 8,421 points have no defined order in the score alone. Redis breaks the tie by comparing the member bytes lexicographically, so the tie-break would be by player id: arbitrary, and unfair to a player who reached 8,421 first. Products usually want one of three behaviours.

PolicyMeaningExample ranks for scores 900, 800, 800, 700How to implement
Earliest achiever firstEqual scores ordered by time reached; every player has a distinct rank1, 2, 3, 4Pack time into the low bits of the score (below)
Competition ranking ("1224")Equal scores share a rank; the next rank skips1, 2, 2, 4Rank = 1 + count of strictly higher scores (ZCOUNT on a pure score range)
Dense ranking ("1223")Equal scores share a rank; no gaps1, 2, 2, 3Needs a count of distinct scores above; keep a histogram of score to count

We choose "earliest achiever first" for display (it is what players expect and it gives unique positions), and keep the pure score available for the percentile logic.

9.2 Packing score and time into one double

Redis scores are 64-bit IEEE doubles, which represent integers exactly up to 2^53 (about 9 x 10^15). We have room for two integers if their bit lengths sum to at most 53. Let the real score fit in 30 bits (maximum 2^30 = 1,073,741,824, above our one billion cap) and let the time component use the remaining 23 bits. A season lasts at most about 90 days; 90 x 86,400 = 7,776,000 seconds, which is below 2^23 = 8,388,608, so seconds since season start fit. We want a higher score to rank first and, for equal scores, an earlier time to rank first, so we store the time inverted:

encoded = score * 2^23 + (2^23 - 1 - seconds_since_season_start)

score 8421 at second 100 -> 8421 * 8388608 + (8388607 - 100)
score 8421 at second 900 -> 8421 * 8388608 + (8388607 - 900)    (lower, so ranks after)
Walkthrough. A single 53-bit box is split into two parts. The blue left part is 30 bits for the real score, which dominates the order. The amber right part is 23 bits for inverted time, meaning the largest value minus the seconds since the season started. 1. A bigger score makes a bigger number, so it ranks higher. 2. For two equal scores, the player who got there earlier has a smaller seconds value, so a larger inverted value, so a larger number, so a higher rank. 3. To read the real score back, divide by 2 to the 23rd power and drop the fraction. The green box notes that 53 bits is the largest integer range a double holds exactly, so the encoding loses nothing. The design puts the tie-break in the score itself instead of a second lookup. On a whiteboard, draw the box and label which side wins. Without the inverted time, ties fall back to player id order, which is arbitrary.

Two cautions. With cumulative ZINCRBY you cannot simply add a delta to an encoded value, because the time part would drift; the worker therefore reads the current pure score (from the score table, or ZSCORE then decode), computes the new total, and writes with ZADD, ideally inside a short Lua script so the read-modify-write is atomic. And a score that grows past 2^30 breaks the layout, so the cap is enforced at ingest.

9.3 Reading: top K, my rank, around me

Top K is ZREVRANGE key 0 K-1 WITHSCORES. Because every client sees the same answer, we cache the rendered page. The Read API serves it from a local in-process cache refreshed at most once per second per (board, window); a request that finds the entry expired triggers one refresh while others use the old copy (the single-flight pattern in Chapter 14 that prevents a stampede). With 28,000 reads per second at peak and a 1 second TTL, Redis sees about one top-K call per board per second per API instance, instead of tens of thousands.

My rank is ZREVRANK key player plus 1, together with ZSCORE. This is personalised, so it cannot share a cache entry across players; it goes to a replica. At 28,000 per second spread over replicas, each doing a call that costs roughly 20 microseconds of server time, a single replica could handle it, and we use several for availability.

Around me needs the rank first, then a slice around it. Doing it as two round trips races with updates: the rank may shift between them. We run both in one Lua script so they see the same state:

-- KEYS[1] = board key, ARGV[1] = player, ARGV[2] = span
local r = redis.call('ZREVRANK', KEYS[1], ARGV[1])
if not r then return nil end
local lo = math.max(0, r - tonumber(ARGV[2]))
local hi = r + tonumber(ARGV[2])
return { r, redis.call('ZREVRANGE', KEYS[1], lo, hi, 'WITHSCORES') }

Friends board. The social service returns a friend list (typically up to a few hundred ids). We call ZMSCORE key f1 f2 ... The rank among friends is just the position in the small sorted list.

10. Deep dive: daily, weekly and season windows

A leaderboard with resets is really several leaderboards. Players want "today", "this week" and "this season", each with its own winners and rewards, and finished periods must remain readable. The design question is how to keep them all up to date cheaply and roll them over safely.

10.1 Options compared

OptionHowProsCons
A. Fan out on write (our choice)Every event updates the daily, weekly and season sets (three ZINCRBY in one pipeline)Reads are a single key lookup. Option B is tempting because it looks free, and the trap in it is the blocking cost, which an interviewer will probe.

10.2 Rollover and archival

  1. Pre-create. The window manager decides each window id from a configured calendar in UTC (for example week:2026-W47), and ingestion computes the target key from the event's match end time, not the processing time. A match that ends at 23:59:58 but is processed at 00:00:03 still counts for the old day.
  2. Grace. The previous window remains writable for a short grace period (for example 10 minutes) to take late events from consumer lag, then it is sealed.
  3. Freeze and archive. At seal time, a job reads the final top N (say the top 10,000 plus reward tiers) with a paged ZREVRANGE against a replica, writes it to the archive store, and publishes a window_closed event for the reward system.
  4. Expire. The set gets a TTL (daily: 14 days; weekly: 8 weeks) so memory is reclaimed automatically. The archive store holds the permanent record of the final standings, so a hot key vanishing never loses history.
Walkthrough. A horizontal line is the clock. Green boxes are live windows, the amber box is the grace period, red boxes are sealed or expiring, and the green box on the lower right is the archive. 1. Day 17 is live until 00:00 UTC, and events are routed by match end time. 2. At midnight day 18 starts, as a new key on the lower row. 3. Time zones: boards use one global UTC calendar so a ranking has a single meaning. A "local day" board per region is just another board key with its own boundaries, which the generic window manager already supports. Season reset (a new key, with an optional soft reset of ratings carried over from the last season) is the same mechanism with a longer period, and it is the moment of the biggest spike: 30M players touch the new key within hours. We pre-warm it and stagger client refreshes by a random delay.

11. Deep dive: sharded leaderboards at huge scale

11.1 When one sorted set is not enough

At 100M players a single primary per board suffices, by the estimates of section 3. Scale the product to one billion players and 10x the event rate: the season set is 100 GB, which exceeds a node's practical memory (and a fork for a snapshot would need up to double in the worst case), and 420,000 sorted-set updates per second would saturate one thread. Redis Cluster does not help by itself, because a single key (one sorted set) always maps to a single slot and therefore a single node. We must split one logical leaderboard into several physical sorted sets ourselves. There are two natural ways, and the choice shapes every query. Sharding technique is covered in Chapter 25 and hashing in Chapter 57.

11.2 Option 1: shard by player id (hash)

Choose N shards, say 16. Shard of a player = hash(player_id) mod N. Each shard is its own sorted set holding about 1/N of the players, so the load and memory spread evenly and independent of the score distribution.

  • Update: one shard, one ZADD. Scales linearly with N.
  • Top K: ask every shard for its own top K, then merge the N lists of K and keep the K largest. This is correct, because the global top K must be inside the union of per-shard top K. Cost: N parallel calls, each returning K entries, then an in-memory merge of N x K items (16 x 100 = 1,600 items, trivial).
  • Exact rank of one player: the rank is 1 plus the number of players with a higher score across all shards. The player's own shard answers with ZREVRANK; each other shard answers ZCOUNT key (score +inf (count of strictly higher). Sum the counts. Cost: N parallel calls, each logarithmic.
  • Around me: hard. The neighbours in global order are spread over all shards. Computing the exact window needs a score-range query on every shard (ZREVRANGEBYSCORE around the player's score with a small limit) and a merge. It works, but costs N calls and the merge needs care with ties.
Walkthrough. The Read API on the left sends requests to four of the sixteen amber shards. Each shard holds players whose id hashes to its number. Arrows fan out left to right, and dashed arrows return to the green result boxes. 1. For the top 100, ask every shard for its own top 100. 2. Merge the sixteen lists, 1,600 candidates, and keep the best 100. This is correct because the global top 100 must be inside the union of the local lists. 3. For an exact rank, the player's own shard returns a rank and the other fifteen return a count of strictly higher scores. 4. Add the counts and add one. The design spreads load evenly but each read touches all sixteen shards, so latency is the slowest shard. Mention timeouts and hedged requests. Point at the fan-out arrows and the merge box. Remove the merge step and each shard would show a different top list.

11.3 Option 2: shard by score range

Partition the score axis into contiguous ranges: for example shard A holds scores 0 to 999, shard B 1,000 to 4,999, and so on, with narrow ranges at the top where many queries land. A player lives in exactly the shard that covers their score and moves between shards when their score crosses a boundary.

  • Top K: read from the highest shard only, falling to the next if it holds fewer than K. One or two calls.
  • Exact rank: rank = (number of players in all higher-scored shards) + (rank within own shard). The first term comes from a small table of per-shard counts (lb:...:cnt) updated on every move; the second is a single ZREVRANK. Cost: one or two calls.
  • Around me: almost always inside one shard, one call.
  • Costs: a player changing score across a boundary needs a move: remove from the old set, add to the new one, update both counts. That is two keys, so it is not atomic and needs a careful ordering and a reconcile job. Distribution is skewed: scores cluster (most players have low scores), so low shards are huge and top shards are tiny, and the boundaries must be re-chosen as the distribution drifts. The shard that holds the currently active middle range receives most updates and becomes a hot spot.
Walkthrough. Three amber shards are cut by score, not by player: H holds 9,000 and up, M holds 3,000 to 8,999, L holds 0 to 2,999. The green box on the right is a counts table with the size of each shard. 1. For the rank of the player at 8,421, find the shard by score, which is M. 2. Read the count of all higher shards from the table, 20,000. 3. Ask M for the player's rank inside it, 100,345. 4. Add them: 20,000 plus 100,345 is 120,345. The top 100 comes from H alone, and the around-me window usually from M alone. The lower text warns that the move across a boundary is the hard part and that L is far larger than M, so it needs its own split. The design makes reads cheap by making writes harder. Draw the counts table next to the shards. Without it, a rank would need a count from every higher shard on each read.

Decision. We use a hybrid that matches how people actually use leaderboards. The top end (say the top 100,000 players) is served from one dedicated small sorted set that is fed by a filter: when a score crosses the "top cutoff" it is also written into the top set. This gives exact top K and exact rank for the players who care most, with one call. Everyone else is on hash shards, where we avoid the N-way scatter by accepting an approximate rank: for a player outside the top set, we estimate rank from a score histogram (counts of players per score bucket, refreshed every few seconds from ZCOUNT on the shards, or maintained incrementally on write). Rank is the number of players in higher buckets plus an interpolation inside the bucket. The UI shows "Top 40 percent" for them, or an exact rank only when they open the screen explicitly (which runs the N-way count). Nobody in an interview or a product review needs to know they are exactly 40,118,201st, and nobody notices an error of a few hundred places at that depth. A related probabilistic tool is the t-digest or a count-min style summary (Chapter 57).

Key idea Leaderboard read patterns are extremely skewed: almost all attention goes to the top and to a window around the player. Exact answers matter at the top; approximate answers are fine at the bottom. Designing the precision to follow the attention is what makes the sharded design affordable.

12. Scaling, bottlenecks and hot spots

  • Read replicas. Reads of my rank, top K and around me go to Redis replicas (asynchronous replication, Chapter 24). Replica lag, normally a few milliseconds, means a player who just finished a match might briefly see the old rank. For the "my own rank right after my match" screen, the Read API can send that one call to the primary (a read-your-writes route) or retry once if the returned score is older than the score the client reports having.
  • Hot key. The top-K key is read by all players. The in-process cache with a 1 second TTL, plus a shared cache tier, collapses this to a handful of Redis calls per second. The season key is written by everyone, and this is bounded by one primary's single thread: a Redis primary does roughly 100,000 simple commands per second, we use 42,000 at peak, so we have about 2.4x headroom. If a mode needs more, it moves to hash shards or fewer windows are fanned out on write.
  • Write batching. Ranker workers batch 100 to 500 events, collapse several events of the same player into one ZADD (only the final score matters for a keep-latest board), and send them in one pipeline. This cuts commands per second severalfold during bursts and is the cheapest scale lever.
  • Partitioning workers. Kafka is partitioned by player id, so one player's events are processed in order by one worker, and the number of partitions bounds the parallelism (for example 64 partitions for 64 workers).
  • Network and CPU. A Redis primary also spends CPU on replication to every replica, which scales with replica count. A tree of replicas (replicas of replicas) or limiting to 2 to 3 replicas per shard keeps the primary's load bounded.
  • Regional boards. Regional leaderboards (EU, NA, Asia) are separate boards in separate regional clusters, so most players read and write nearby. The global board is built by merging regional top lists (a periodic job) and is allowed to be a few seconds old. See Chapter 26.
  • Real-time push. If the product wants live rank movement, a notification path publishes "your rank changed by more than X" over a WebSocket or push channel (Chapter 6), rate limited per player so a busy mode does not create 14,000 notifications per second to a single feed.

13. Persistence, rebuild and recovery

Redis is memory first. Persistence has two built-in mechanisms: RDB snapshots (a point-in-time dump written by a forked child process, compact and quick to load but loses everything since the last snapshot) and the append-only file (AOF) (every write logged, with fsync policy always, everysec or no). The usual production choice is AOF with everysec plus periodic RDB, which loses at most about one second of writes on a crash. Replicas add a second copy in another zone, with failover by Sentinel or a cluster manager (Chapter 41). A fork-based snapshot of a 10 GB set uses copy-on-write memory; under heavy writes, many pages are duplicated, so we keep memory headroom (for example allow the dataset to use 50 to 60 percent of RAM).

But even with AOF and replicas, we treat Redis as a derived view, not the source of truth. The durable truth is the Kafka log plus the score table. This yields three recovery tools of increasing cost.

SituationRecoveryTime

Because rebuild is cheap and the bulk-load path is the same code as the live path, we run it regularly: a nightly reconciliation samples random players and compares Redis scores with the score table, alarming on drift. A weekly full rebuild into a shadow key, compared to the live key by checksum, proves that recovery works before we need it. The rule to remember: a backup you have never restored is not a backup.

15. Security, abuse, monitoring and cost

15.1 Cheating and abuse

  • Trust boundary. Only authoritative game servers can write scores, using mutual TLS and signed events. A client app never calls the write endpoint. This removes the largest class of cheating (a modified client posting a score of one billion).
  • Plausibility checks. Ingest rejects deltas outside the range possible for one match, and anomaly jobs flag players whose score velocity is a statistical outlier. Flagged players are shadow-listed: removed from the public sorted sets (ZREM) without notifying them, pending review. A ban removes the player from all windows and from the archive of the current season, which is why the archive is written from the live set only after a delay.
  • Read abuse. Scrapers pull the top 1,000 repeatedly. Per-client rate limits at the gateway (Chapter 16, Case study 3) and the cached top list make this cheap. Paging depth is capped.
  • Privacy. Players can hide from public boards. Hidden players remain in the ranking for their own rank, but are filtered from public pages (display names only for players who opted in). See Chapter 56.

15.2 Monitoring and SLOs

  • SLIs: read latency p50 and p99 per endpoint; consumer lag (seconds between event time and Redis apply); Redis command latency and slow-log counts; memory use and fork duration; replication lag; drift found by reconciliation; cache hit ratio of the top list.
  • SLOs: 99.95 percent of reads succeed over 30 days; p99 read under 50 ms; 99 percent of score events visible in Redis within 2 seconds; zero lost accepted events (checked by comparing log offsets to applied offsets).
  • Alerts: consumer lag above 10 seconds; Redis memory above 70 percent (fork risk); replication lag above 1 second; reconciliation mismatch above 0.01 percent. See Chapter 54.

15.3 Cost notes

Memory dominates the bill. For a mode with 19 GB of sorted sets, we need primary and two replicas, at about 64 GB each: three nodes per shard, and with a 16-shard fleet, about 48 memory-optimized nodes for one very large game. Cost levers: trim the board (ZREMRANGEBYRANK to keep only players with more than zero points or only those active in the last 30 days, with the long tail answered by the approximate percentile from the histogram), expire the daily and weekly sets aggressively, and use a short member id (a numeric id in binary-safe form, not a UUID string, saves roughly 30 bytes per member, a 30 percent reduction). Kafka retention (30 days) and the archive tier cost far less than Redis memory per gigabyte.

16. Evolution, phasing and alternatives not chosen

16.1 What changes at 10x

At 300 million DAU: 140,000 events per second at peak, 420,000 sorted-set updates per second. We move from one primary per board to hash sharding (16 to 64 shards), adopt the hybrid top set plus histogram for approximate rank, scale Kafka to a few hundred partitions, shrink fan-out by writing the daily board only and deriving the weekly total from a counter-per-day table for non-competitive modes, and split boards by region as the default. Reads: the top list cache moves from per-process to a shared tier plus a CDN for public "season hall of fame" pages (Chapter 12).

16.2 What we build first

  1. Phase 1: one Redis primary with a replica, the score table, direct writes from workers fed by Kafka, the four read endpoints, top-K cache, and one window (season).
  2. Phase 2: daily and weekly windows, the window manager with archive, dedupe, reconciliation job, dashboards and alerts.
  3. Phase 3: friends board, tie-break encoding, regional boards, rate limits and anti-cheat integration.
  4. Phase 4: sharding with the top set and histogram approximate rank, only when capacity numbers show it is needed.

16.3 Alternatives not chosen

  • Use the relational database for everything: simplest to operate, but rank queries and write volume do not fit beyond a few million active players.
  • Cassandra or DynamoDB counters with a sort key on score: they scale writes, but rank requires counting, which these stores do not offer natively; useful as the durable score store, not as the ranking engine (Chapter 20).
  • Stream processing (Flink) that continuously maintains the top K: excellent for a global top K computed over a huge unsorted stream (see the heavy-hitters approach of Case study 20), but it does not answer "my rank" for an arbitrary player.
  • Skip the leaderboard and use a social feed ranking: a different problem (Case study 6); ranking there is by a model score, not a monotone number.
  • Exactly-once via distributed transactions across Kafka, table and Redis: heavier than needed; idempotent consumers achieve the same effect.

17. Interview Q&A

Why a Redis sorted set rather than a SQL table with an index on score?

The question a leaderboard asks most is "how many players have a higher score than me?", which is an order-statistic query. A Redis sorted set keeps a skip list whose pointers carry spans, so rank, insert and range are all O(log N) in memory, in tens of microseconds. A B-tree index in a relational database gives fast ordered scans, but a count of rows above a key usually walks the index range, which grows with N, and every update also pays for the write-ahead log and index maintenance. At 100 million players with 14,000 updates per second at peak, the SQL path needs heavy replication and caching to approximate what the sorted set gives natively. I would still keep SQL or a wide-column store as the durable score table, because Redis is memory first.

How do you break ties fairly, and what are the pitfalls?

Redis orders equal scores by member bytes, which would rank by player id, so I pack a time component into the score. Using a 30 bit score and a 23 bit inverted time (seconds since season start) totals 53 bits, the exact integer limit of a double, so a higher score ranks first and, among equal scores, the earlier achiever ranks first. The pitfalls are that you cannot use ZINCRBY with an encoded value because the time part would drift (read the pure score, add, re-encode, write with ZADD in a script), that scores above 2^30 overflow the layout so ingest must cap them, and that product might prefer shared ranks (competition ranking), which comes from counting strictly higher pure scores.

How do you serve the around-me view efficiently and consistently?

Take the player's rank with ZREVRANK, then read the slice from rank minus 5 to rank plus 5 with ZREVRANGE. Both steps run inside one Lua script, so no update can move the player between the two calls and make the window misaligned. The cost is two logarithmic operations plus eleven rows, a few tens of microseconds. Names and avatars are attached afterwards from the profile cache in one batch, which keeps the sorted set free of strings. On a hash-sharded board the neighbours are scattered, so I would use the hybrid design: exact around-me only in the top set, and score-bucket windows (approximate) for deep ranks.

A single leaderboard has outgrown one Redis node. What do you do?

Redis Cluster does not split one sorted set, so I split the leaderboard myself. Hash sharding by player id spreads load evenly and makes updates single-shard, but top K and exact rank need all N shards (merge of per-shard top K lists, sum of ZCOUNT results). Range sharding by score makes reads cheap with a counts table but creates hot shards, skew and multi-key moves across boundaries. I would combine them: a small exact top set for the top 100,000, hash shards for everyone, and an approximate rank from a score histogram for the deep tail. That matches where users actually look and keeps the common queries to one call.

How do you implement daily and weekly boards without tripling the cost?

I accept the amplification. Each score event updates three sorted sets (day, week, season) in one pipelined round trip, so reads are single-key lookups and each window expires independently. Computing the weekly board with ZUNIONSTORE of daily sets looks cheaper but would block a single-threaded Redis for seconds on tens of millions of members, so it is only acceptable for small or off-peak jobs. The real mitigations are batching and collapsing events per player before writing, smaller daily and weekly sets since only active players are present, and TTLs. Windows are chosen by match end time, with a short grace period to absorb late events before archiving.

What if Redis loses data or the whole cluster goes down?

Redis is a derived view of the durable record, which is the Kafka log plus a score table that holds each player's current total. For a node crash, a replica is promoted and workers re-apply any uncommitted events idempotently. For a lost shard, I load the last snapshot and replay Kafka from its offset. For corruption, I rebuild from the score table by scanning it and bulk loading with pipelined ZADD into a new key, then RENAME it into place; at roughly 500,000 adds per second that is a few minutes for 100 million players. I rehearse this rebuild regularly and run a reconciliation job that samples players and alerts on drift, because an untested recovery path is a hope, not a plan.

How do you make score updates exactly-once?

True exactly-once delivery across a network is not available, so I get the same effect with at-least-once delivery and idempotent processing. Each match result carries a unique event id. The worker first claims it with an atomic set-if-absent on a dedupe key with a TTL longer than the retry window, then applies a conditional update to the score table that also records the event id, and only then updates Redis and commits the Kafka offset. A replay after a crash hits the dedupe key or the conditional update and does nothing. Since ZINCRBY is not idempotent by itself, the guard must come first; for best-score modes, ZADD GT is naturally idempotent.

How do you detect and handle cheaters on the leaderboard?

First, remove the trust problem: only authoritative game servers can post scores, over mutual TLS with signed events, so a modified client cannot write. Second, validate plausibility at ingest, rejecting deltas outside what one match can award, and run offline anomaly detection on score velocity. Third, make removal cheap: a flagged player is taken out of the public sorted sets with ZREM (shadow listing) and, if banned, from all windows, and because ranks of everyone below shift automatically, no reordering is needed. I delay final archiving of a window slightly so that bans from the review queue are reflected in the permanent standings and rewards.

How do you show a friends leaderboard?

The social service gives me the friend ids, usually a few hundred. I fetch their scores in one call with ZMSCORE (or a pipeline of ZSCORE), sort the small result in the application and attach names from the profile cache. The rank among friends is simply the position in this list. I avoid ZINTERSTORE with a friends set on the hot path because it writes a temporary key and its cost grows with the larger set sizes. For a player with thousands of friends I cap the list or page it. On a sharded board, the batch is grouped by shard so each shard gets one call.

How would you provide live rank updates to the client?

I would not stream the whole leaderboard. After a player's score is applied, the worker can compute the new rank for that player only (one ZREVRANK), and push it over the existing push or WebSocket channel if it changed by more than a threshold, rate limited per player. For the public top 100, clients poll the cached endpoint every few seconds, or subscribe to a channel that publishes the diff once per second. This keeps the fan-out proportional to meaningful changes, rather than to the 14,000 events per second at peak.

18. Recap

  • A leaderboard is an order-statistic problem. A Redis sorted set (hash table plus skip list with spans) gives rank, top K and range in O(log N), and updates atomically on a single thread.
  • Numbers: 30M DAU, 300M events a day, 3,500 per second average and 14,000 at peak; three windows make 42,000 sorted-set updates per second; about 100 bytes per member gives roughly 19 GB per mode.
  • Write path: game server, ingest, Kafka keyed by player, rank workers with dedupe, durable score table first, then pipelined updates to the day, week and season sets, then the offset commit. At-least-once plus idempotence gives exactly-once effect.
  • Reads: cached top K, ZREVRANK for my rank, a Lua script for around-me, ZMSCORE for friends. Names come from a separate profile cache.
  • Ties: pack inverted time into the low bits of the score (30 + 23 = 53 bits), or compute competition rank from counts of strictly higher scores.
  • Windows: fan out on write, route by match end time, keep the old window open briefly, then seal, archive and expire.
  • Beyond one node: hash shards need scatter-gather for top K and rank; score-range shards make reads cheap but move players across boundaries. The practical answer is an exact top set plus hash shards and an approximate rank for the deep tail.
  • Redis is a derived view. The log and score table are the truth; rebuild is routine and rehearsed.
