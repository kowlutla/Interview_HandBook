Design a Distributed Unique ID Generator

Every row, message, order and event in a large system needs a name that nothing else will ever share, and it must be handed out by hundreds of machines at once without them talking to each other. We walk from random UUIDs and database ticket servers to the Snowflake bit layout, and spend most of our time on the two things that actually break it: clocks that go backwards, and two machines that believe they own the same worker number.

How to approach this problem (read this first)

What the interviewer is really testing. The question sounds small, and a candidate who says "use a UUID" and stops has missed the point. The interviewer wants to see whether you can list the properties an ID needs (unique, compact, roughly time ordered, no per-ID coordination), compare several real approaches against them, and then go deep on what breaks the winner. For a Snowflake-style design the two breakers are clocks that move backwards and two processes that believe they own the same worker number. Both produce silent duplicates, which corrupt data. The depth you show on those two failures decides the interview.

The thinking order, step by step

  1. Ask what the ID is for and how wide it can be. Ask: primary key or public token, 64 or 128 bits, must it sort by time, must it be gap free? Say: "I will assume a 64-bit primary key that is roughly time ordered, gaps allowed." Start here because the answers eliminate half the options.
  2. Name the trade-off triangle. Say: "Uniqueness, compactness and order; the question is how much coordination each costs." This frames the comparison that follows.
  3. Estimate rate and key width. Say: "300,000 IDs per second average is about 25.9 billion a day, so an 8-byte key against a 16-byte key is a difference of about 207 GB a day before indexes." This is why 64 bits matters. Then show the bit budget: 41 plus 10 plus 12.
  4. Draft the API. An embedded library call and a small service for clients that cannot hold a worker number. Mention that IDs go to JavaScript clients as strings.
  5. Walk the options from simplest. Single auto-increment, ticket servers, UUID, then Snowflake. Say what each fails, so the winner looks earned.
  6. Draw the Snowflake layout and the generator loop. Show the example arithmetic. Say: "Coordination moved from once per ID to once per process start."
  7. Deep dive worker-id assignment. Leases, quarantine, self-expiry, and the high-water mark.
  8. Deep dive clock rollback. Tiered policy by size of the offset.
  9. Close with scaling, failures, multi-region and evolution. Mention disjoint worker ranges per region.

The decision points

  • Central counter or local generation? Ask: can any shared counter handle 1,000,000 per second without becoming a single point of failure? No, so generate locally.
  • 64 or 128 bits? Ask: how many times is the key repeated in indexes and foreign keys? Often, so 64 bits unless zero coordination matters more.
  • Random or time ordered? Ask: does the primary key sit in a B-tree? Yes, so time ordering avoids random page writes.
  • Wait, reject or replace on a clock rollback? Ask: how large is the offset? Small waits, medium rejects, large replaces the worker.
  • How are worker numbers assigned? Ask: how often do processes start? Often, so use leases and recycle numbers, not static config.

Common mistakes on this problem

  • Answering "UUID" with no comparison. Fix: compare size, order and index behaviour.
  • Ignoring clock rollback. Fix: show the duplicate it causes and a tiered policy.
  • Assigning worker ids from the IP address. Fix: use leases with quarantine, because 10-bit hashes collide quickly.
  • Claiming strict global ordering. Fix: say k-sortable, correct to within clock skew.
  • Sending 64-bit numbers to JavaScript as numbers. Fix: return strings.
  • Using these IDs as secrets. Fix: use random 128-bit tokens for anything security related.

1. Problem statement and clarifying questions

The prompt is "Design a distributed unique ID generator." On a single database this is trivial: an auto-increment column hands out 1, 2, 3 and the database serializes the callers. The moment data is spread over many shards, many services and many regions, there is no single counter to ask. Yet we still want identifiers that are unique, compact, cheap to produce and, ideally, roughly ordered by creation time. The question is really about choosing which of those properties to keep and how to build them without a central bottleneck.

QuestionAssumed answer
What is an ID used for?Primary key for orders, messages, posts and events across about 200 services. IDs are also exposed in URLs and APIs, so they should not be absurdly long.
How big can it be?64 bits. It fits a database BIGINT and a Java long, and it is half the width of a 128-bit key. Anything wider costs memory in every index and foreign key.
Must IDs be sortable by time?Roughly, yes ("k-sortable": sorted order is correct to within a small window such as a few milliseconds). Strict global order is not required and is not achievable without coordination.
Must IDs be strictly sequential or gap free?No. Gaps are fine. Business-visible numbers such as invoice numbers are a separate problem (section 18).
Scale?Average 300,000 IDs per second, peak 1,000,000 per second, across all services, in 3 regions.

Can IDs be guessed?Internal keys may be guessable. Public capability tokens (password reset links) must not use this generator at all.

Interview tip State the trade-off triangle immediately: uniqueness, compactness and order. Random UUIDs give uniqueness without coordination but are wide and unordered. Database counters give order and compactness but need coordination. Snowflake buys all three by splitting the coordination into a one-time worker-number assignment plus a clock. Then say that the interesting failure is the clock.

2. Requirements and scope

2.1 Functional requirements

  • Unique: no two calls, anywhere, at any time in the next 69 years, return the same value.
  • 64-bit numeric: positive, fits a signed 64-bit integer.
  • Roughly time ordered: an ID generated later is almost always numerically larger, so sorting by ID approximates sorting by creation time.
  • Decodable: the creation time and the generating worker can be extracted from the ID, which helps debugging and time-range queries without a separate timestamp column.
  • Available: generating an ID never blocks on a quorum or a remote database in the normal path.

2.2 Non-functional requirements

  • Throughput: 1,000,000 IDs per second at peak across the fleet; each generator at least 100,000 per second.
  • Latency: under 1 microsecond in-process, under 2 ms p99 as a remote service.
  • Fault tolerance: losing any generator, any zone, or the coordination service must not stop generation on machines already running.
  • Safety under time faults: a backwards clock must never produce a duplicate (section 10).

2.3 Out of scope

Gap-free business sequences (invoice numbers), unguessable security tokens, global strict ordering (that needs a consensus sequencer, Chapter 29), and content-addressed IDs (hashes of the data), which solve a different problem.

3. Estimation

ID generation is cheap in CPU terms, so the arithmetic is about the capacity of the bit layout and the storage cost of the IDs, not about compute. Technique is covered in Chapter 2.

3.1 Rate and volume

Peak 1,000,000 IDs/s; average 300,000 IDs/s. Per day at the average: 300,000 x 86,400 = 25.9 billion IDs/day. Per year: 300,000 x 31,536,000 = about 9.5 trillion IDs/year. Over 69 years that is roughly 650 trillion, about 6.5 x 10^14. A signed 64-bit space holds 2^63 = 9.2 x 10^18, so the raw count is not the constraint. What matters is how we partition the space among time, worker and sequence.

3.2 Storage and index cost of key width

An 8-byte ID for 25.9 billion rows per day is 207 GB/day of key bytes alone, about 76 TB/year. A 16-byte UUID doubles that to 414 GB/day, and every secondary index and foreign key that repeats the ID doubles too. If a table has three indexes and two child tables referencing it, the key is stored about six times, so halving the key saves several hundred GB per day. That is the quantitative argument for 64 bits.

One worker can emit up to 4,096,000 IDs per second. The entire fleet's 1,000,000/s peak could in principle come from one worker, so the number of workers is chosen for availability and locality, not throughput. Spread over 1,024 workers the peak is about 977 IDs/s each, using 0.024 percent of a worker's ceiling. In practice we plan 64 to 128 generator processes per region and keep the rest of the 1,024 as headroom for restarts (section 8).

3.4 Worker-id churn

If 200 services each embed a generator in about 2 processes on average (a steady fleet of about 400), and deploys, crashes and autoscaling restart each process about 20 times a day, we see on the order of 400 x 20 = 8,000 process starts per day. If each start consumed a worker id permanently, 1,024 would be gone in a few hours. Worker ids must therefore be leased and recycled, which is the central operational problem of section 8.

4. API design

We expose two shapes. An embedded library produces the ID in-process with no network hop. A thin service covers clients that cannot hold a worker id (browsers, short-lived functions, scripts). API style is in Chapter 5.

// Embedded library
IdGenerator gen = IdGenerator.create(leaseClient, config);
long id = gen.nextId();                       // thread safe, microseconds
IdParts p = IdGenerator.decode(id);           // { timestampMs, workerId, sequence }

// Service
POST /v1/ids          { "count": 100 }        -> { "ids": ["123...", ...] }
GET  /v1/ids/{id}/decode                      -> { "created_at": "...", "worker": 417, "sequence": 12 }

// Lease protocol (internal, used by the library at startup)
acquire(service, instance_hint)  -> { worker_id, lease_id, ttl_ms, last_ts_ms }
renew(lease_id)                  -> { ttl_ms }
release(lease_id)                -> {}

Notes. IDs are returned to JSON clients as strings: a JavaScript number is an IEEE double with only 53 bits of integer precision, so a 63-bit ID would be silently rounded. The batch form (count) amortizes network cost: one call can return up to 1,000 IDs. The lease returns last_ts_ms, the highest timestamp this worker id ever used, which a new owner must wait out (section 10.4). A failed nextId call is safe to retry because IDs are interchangeable: a retry may waste an ID, never duplicate one.

5. Data model and storage choice

The generator itself holds almost no state: a last timestamp and a sequence counter, in memory, per worker. The only durable state is the lease registry that hands out worker ids, a tiny, strongly consistent store of 1,024 rows.

WorkerLeaseworker_id (key), owner (host, pid, start nonce), lease_deadline, last_ts_ms, generationHeld in a consensus-backed store such as etcd or ZooKeeper (Chapter 30), or in a relational table with a primary key on worker_id (Chapter 18). About 1,024 rows and a few writes per second.

We use a consensus store for leases because the safety property, "no two live processes hold the same worker id", is mutual exclusion, which the coordination chapter treats, including the same caveat about leases and process pauses that we revisit in section 8. We deliberately do not store issued IDs anywhere. Recording every ID would make the generator as heavy as the databases it serves.

6. The candidate approaches, from simplest to real

Before drawing the final design, walk through the options in order of how an interviewer expects the conversation to go. Each one fails a requirement, and the failure motivates the next.

6.1 One database auto-increment

A single table with an auto-increment column is the baseline. IDs are small, perfectly ordered and gap-light. It fails for two reasons. Every ID generation is a write to one primary, so the ceiling is the write throughput of one database (typically a few thousand to tens of thousands of inserts per second), far below 1,000,000/s. And that primary is a single point of failure for every service that creates anything (Chapter 24). Sharding the data (Chapter 25) makes it worse: each shard has its own counter, so shard 1 and shard 2 both hand out 1, 2, 3, and the same primary key now appears in two places.

6.2 Multi-master with step offsets, and ticket servers

The classic fix is to give each of N database servers a different offset and step. With two servers, server A starts at 1 and steps by 2 (1, 3, 5), and server B starts at 2 and steps by 2 (2, 4, 6). The sequences never collide. This is the "ticket server" pattern popularized by Flickr: a dedicated tiny table whose only purpose is to hand out IDs, using REPLACE INTO Tickets64 (stub) VALUES ('a'); SELECT LAST_INSERT_ID(); and two MySQL servers configured with auto_increment_increment = 2 and offsets 1 and 2. Application servers pick one ticket server round robin and fall back to the other if one is down.

Walkthrough. On the left, purple boxes are App servers 1, 2 and N. In the middle, green boxes are Ticket server A and Ticket server B. The red box on the right lists the weaknesses. 1. An app server needs an ID and picks a ticket server in turn, which is the round robin noted below the arrows. 2. Server A, configured with offset 1 and step 2, returns the next odd number. 3. Server B, with offset 2 and step 2, returns the next even number. 4. If one server is down, the app uses the other. Because one hands out only odd and the other only even numbers, they never collide, with no talk between them. That is the clever part. The cost is shown on the right: every ID is a network call, order across the two servers is only approximate, and adding a third server means changing steps on live databases. On a whiteboard, write the two sequences 1, 3, 5 and 2, 4, 6. Remove one server and the other still works, but throughput halves and gaps appear.

Ticket servers are a legitimate answer for modest scale, but they have real costs. Every ID is a network call (a typical 0.5 to 1 ms inside a datacenter), so a service that needs a thousand IDs per request is slow. Ordering is only per server, so IDs from A and B interleave unpredictably. Growing from two servers to three means changing the step on live databases without ever reusing a value, an operation that needs a planned gap in the sequence. A batch variant (a server hands out blocks of, say, 1,000 numbers that the application consumes locally) lifts throughput by 1,000x and is the idea behind many "segment" allocators. It makes IDs coarsely ordered and wastes the unused part of a block when an application restarts, which is acceptable.

6.3 UUIDs

A UUID is a 128-bit value, written as 36 characters with hyphens. Version 4 fills 122 of the bits with random data. Anyone can generate one with no coordination at all. The chance of a collision is governed by the birthday bound: with 122 random bits the probability that any two of n IDs collide is about n^2 / 2^123. For n = 10^12 (a trillion) that is 10^24 / 1.06 x 10^37, about 10^-13, so collisions are practically impossible, as long as the random source is good. Three problems remain. The ID is 128 bits, double our budget (section 3.2). It is random, so as a primary key in a B-tree index each insert lands on a random leaf page, which causes cache misses, page splits and write amplification (section 11). And it carries no time, so you cannot sort by it.

Newer UUID versions fix the ordering. UUIDv7 (standardized in RFC 9562) puts a 48-bit Unix millisecond timestamp in the most significant bits, then version bits, then random or counter bits (about 74 bits remain for randomness and sub-millisecond ordering). It is k-sortable and needs no worker id, which makes it a very good default when 128 bits are acceptable. ULID is similar: 48-bit timestamp plus 80 random bits in a 26-character text encoding. MongoDB's ObjectId is 12 bytes: 4 bytes of seconds, 5 bytes random per process, 3 bytes counter.

6.4 Snowflake: pack time, worker and sequence into 64 bits

Twitter's Snowflake (2010) observed that uniqueness can be built by construction instead of by luck. If every ID contains the millisecond it was made, the worker that made it, and a counter that distinguishes IDs made by that worker within the same millisecond, then no two IDs can be equal unless the same worker produced the same sequence number in the same millisecond, which the worker prevents locally. The only coordination needed is making sure no two live workers share a worker id. That is a tiny, rare operation, done once at process start, instead of one per ID.

Walkthrough. The long bar is the 64 bits of one ID, with bit 63 on the left and bit 0 on the right. Each coloured block is a field. The small green block is the sign bit, always 0. The wide blue block is the 41-bit timestamp in milliseconds since a custom epoch. The amber block is the 10-bit worker id. The green block on the right is the 12-bit sequence. Under the bar, a worked example shows how to build and take apart an ID. 1. Take the time delta, 1,000,000 ms, and shift it left by 22 bits. 2. Add worker 417 shifted left by 12. 3. Add sequence 12. 4. The sum is 4,194,305,708,044. To decode, shift right or mask. The time is in the high bits so numeric order follows creation time. The worker bits stop two machines from making the same ID in the same millisecond, and the sequence stops one machine from repeating itself within one millisecond. On a whiteboard, draw four boxes with widths 1, 41, 10, 12. Remove the worker field and two machines could duplicate each other.

The arithmetic in the example is worth checking in an interview. Shifting left by 22 bits multiplies by 2^22 = 4,194,304, so 1,000,000 becomes 4,194,304,000,000. The worker field is shifted by 12, so 417 x 4,096 = 1,708,032. Adding the sequence 12 gives 4,194,305,708,044. Because fields occupy disjoint bit ranges, the additions never carry between fields, and reading them back is just masks and shifts.

Key idea Snowflake does not remove coordination. It moves it from "once per ID" to "once per process start", and replaces the rest with a local clock. Every hard problem in this design is a place where that replacement can be wrong: the clock lies, or two processes believe they hold the same worker id.

Decision. We choose Snowflake-style IDs as the primary generator because they meet the 64-bit, ordered, coordination-free-per-ID requirements. We keep UUIDv7 as the documented alternative for teams that prefer zero coordination and accept 128 bits (section 18).

7. High-level architecture and request flows

There are three layers. The generator is a small in-process library (or a sidecar) that holds a worker id and produces IDs. The lease registry hands out and recycles worker ids. The ID service is a thin stateless tier, itself composed of generator processes with leased worker ids, for clients that do not embed the library. Clock discipline (NTP or a cloud time service) is an external dependency that we monitor but do not own.

Without the monitor, a rolling clock fault would go unseen.

7.1 Flow A: process startup

  1. The process boots and asks the lease registry for a worker id, passing its host, pid and a random start nonce.
  2. The registry picks a free or expired worker id, writes a lease row with a deadline (for example now + 60 s), and returns worker_id, a generation number and the last_ts_ms that previous owners reached.
  3. The process reads its own clock. If the clock is earlier than last_ts_ms, it waits (or refuses to start) until the clock passes it. This makes reuse of a worker id safe (section 10.4).
  4. The process starts a renewal loop at a third of the TTL, and begins serving nextId.

7.2 Flow B: nextId on the hot path

  1. Read the clock in milliseconds and subtract the custom epoch.
  2. If the time equals the last timestamp, increment the sequence. If the sequence overflows 4,095, spin until the next millisecond.
  3. If the time is greater than the last timestamp, reset the sequence to 0 (or a small random start, section 9.3).
  4. If the time is less than the last timestamp, the clock went backwards: apply the rollback policy of section 10.
  5. Store the new last timestamp, compose the 64 bits, return. No network, no lock beyond a short mutex or atomic.
Walkthrough. Four lifelines from left to right: Generator, Lease registry, Local clock and Caller. Time runs downward. Green arrows are replies, dashed means periodic. 1. The Generator asks the registry to acquire a worker id and sends its host and a random nonce. 2. The registry replies with worker 417, generation 9, and the last timestamp T0 used by earlier owners. 3. The Generator reads the local clock. 4. It sees that now is greater than T0, so it is safe to start, and it begins renewing every third of the TTL. 5. Later a Caller asks for nextId. 6. The Generator reads the clock. 7. The clock returns the millisecond value. 8. The Generator composes the ID from timestamp, worker 417 and sequence and returns it with no network call. The top half happens once per process, the bottom half once per ID. The check at step 4 is the reason a reused worker number is safe. Without it, a host whose clock is behind could reissue old numbers.

7.3 Generator algorithm

synchronized long nextId() {
    long now = currentMillis() - EPOCH;
    if (now < lastTs) {                       // clock went backwards
        return handleRollback(now);           // section 10
    }
    if (now == lastTs) {
        seq = (seq + 1) & 4095;
        if (seq == 0) {                       // 4096 IDs already issued this ms
            now = waitNextMillis(lastTs);     // spin or sleep ~1 ms
        }
    } else {
        seq = 0;
    }
    lastTs = now;
    return (now << 22) | (workerId << 12) | seq;
}

The method is serialized with a lock or implemented with a compare-and-set on one packed 64-bit state word. At 1,000 IDs per second per worker, contention is irrelevant. Even at the 4 million per second ceiling, a single uncontended lock costs tens of nanoseconds per call.

8. Deep dive 1: worker-id assignment

Everything in Snowflake depends on one invariant: at any moment at most one live process emits IDs with a given worker id, and a later owner of that id never emits an ID that an earlier owner already emitted. The second half is the clock part (section 10.4). The first half is a mutual exclusion problem with the usual wrinkle that a "live" process may be paused.

We choose leases from the registry, with static ranges per region as a fallback (section 14). 8.2 Why leases alone are not safe, and how we make them safe

This is the same hazard as any lock with a timeout (a paused holder resumes after expiry and still believes it has the lock). We cannot make the registry perfectly protect the data, because the "resource" here, the ID space, has no server that can check a fencing token. We therefore combine four defenses. Each is cheap.

  1. Self-expiry check on the hot path. The generator remembers the local monotonic-clock time at which its lease will expire, minus a safety margin. Before every ID it checks that the monotonic clock is still before that time. If not, it refuses to issue IDs and re-acquires. A process pause that happens between the check and the use is the remaining gap, but it is only a few instructions wide, and the next defense covers it.
  2. Generous TTL versus renewal. TTL 60 s, renew every 20 s. A process has to miss two renewals before the lease is at risk, and the registry does not hand a worker id to a new owner until a quarantine period (for example 2 x TTL, 120 s) has passed since the last renewal. Garbage collection pauses and brief partitions are far shorter than that.
  3. Wait out the old timestamps. The new owner of a worker id waits until its own clock exceeds the highest timestamp the previous owner could have used (last_ts_ms persisted at each renewal, plus the lease TTL). Then even an old owner that wakes up cannot collide, because the new owner's timestamps are strictly greater than anything the old one issued before its lease was lost, and the old owner (if it wakes) is blocked by defense 1.
  4. Allocate in the least recently used order. The registry hands out the worker id that has been free for the longest. Recently released ids are not reused for as long as possible, so a stale process is much more likely to find its id unclaimed than reassigned.
Watch out A nonce in the ID is not a fix for a worker-id collision, because it would need bits we have spent. The honest statement is: worker-id uniqueness is a probabilistic-free guarantee only to the extent that the lease, quarantine and self-expiry assumptions hold. State that assumption out loud (bounded clock rate drift and pauses shorter than the margin) rather than claiming it is impossible to violate.

8.3 Sizing the worker-id space

From section 3.4, we can see 8,000 process starts per day. With a 120-second quarantine per release, the number of ids tied up in quarantine at any instant is starts per second times quarantine: (8,000 / 86,400) x 120, which is about 11 ids. Add the steady-state fleet of about 400 processes and the registry needs roughly 411 of 1,024 worker ids at the busiest, a comfortable 40 percent utilization. If the fleet grows toward 800, we reallocate bits (section 17) rather than shrinking the quarantine.

8.4 Datacenter and region bits

The 10-bit worker field is often split as 5 bits of datacenter and 5 bits of machine (32 datacenters x 32 machines). Splitting statically wastes capacity when regions are unequal. We instead treat the 10 bits as one opaque number and let each region own a range (for example region 1 owns 0 to 340, region 2 owns 341 to 681, region 3 owns 682 to 1,023), which keeps uniqueness across regions even if a regional registry is isolated (section 14).

9. Deep dive 2: choosing the bit layout and the sequence

9.1 Choosing the custom epoch

The 41-bit timestamp counts milliseconds since a custom epoch, not since 1970. If we used the Unix epoch, 2^41 ms from 1970 expires in about 2039, which is far too soon. Choosing the epoch as the project start date (say 2024-01-01) gives about 69.7 years, until roughly 2093. The epoch is fixed forever and stored in config. If we ever need to extend lifetime, we have to shift bits (section 17), because changing the epoch would reorder old and new IDs.

9.2 Trading bits among the three fields

The 63 usable bits are a budget. Different companies allocate them differently, and the trade-off is itself a good interview discussion.

LayoutTimeWorkerSequenceLifetimePeak per worker

Our workers peak at about 977 IDs/s, but a single process can see a microburst of 4,000 IDs in one millisecond (a batch insert). 12 sequence bits absorb that. If a burst exceeds 4,096 in a millisecond the generator waits for the next millisecond, which delays the caller by under 1 ms. That is a throttle, not a failure.

The more workers you need, the fewer sequence or time bits remain. If the fleet needed 16,384 workers the choices are fewer sequence bits (limiting burst size), a coarser tick (10 ms), or a 128-bit ID. This is why Instagram uses 13 bits for a logical shard: their generation happens inside the database shard, so the worker id is the shard id, which also lets them route a read by looking at the ID's shard bits.

9.3 Sequence reset: zero or random start?

Resetting the sequence to 0 every millisecond is correct but skews distribution. If most workers issue one ID per millisecond, nearly all IDs end in sequence 0, so the low bits are almost constant. That is harmless for uniqueness, but it matters when the ID is used for hash-based sharding (id mod N): with N a power of two, all those IDs land on shard 0 plus a worker-derived offset. Two fixes. Shard on a hash of the ID rather than the raw low bits (Chapter 57), or start each new millisecond with a small random sequence (for example 0 to 9). The second has a cost: a random start reduces the headroom to 4,087 at worst, and it must still never wrap back to equal an already issued number in the same millisecond, which the overflow check handles.

9.4 Monotonic within a worker, k-sortable across workers

Within one worker, IDs are strictly increasing: the timestamp never goes down (section 10) and the sequence rises inside a millisecond. Across workers, two IDs generated in the same millisecond differ in the worker field, so which is larger is arbitrary. If worker clocks disagree by 5 ms, an ID created later by a worker with the slower clock can sort before an ID created earlier by the faster one. That is exactly what k-sortable means: the order is correct to within k, where k is the clock skew plus one millisecond. For sorting a feed, k of a few milliseconds is invisible. For deciding "which write happened first" it is not usable, so never use these IDs as a causal order (Chapter 27).

10. Deep dive 3: clock skew and clock rollback

The generator trusts that the timestamp it reads never decreases. Real clocks violate this. Understanding why, and what to do, is the most heavily probed part of this question.

10.1 How clocks go backwards

  • NTP step corrections. If a clock has drifted by more than the slew threshold (typically 128 ms for the classic ntpd, configurable in chrony), the daemon may step the clock directly to the right time, which can jump backwards by seconds.
  • Leap seconds. A positive leap second repeats the second 23:59:59 (or shows 23:59:60). Naive systems see time go back by one second. Large providers avoid this by "smearing" the leap second across many hours so time is always monotonic but slightly slow.
  • VM migration, pause and restore, host suspend. A virtual machine restored from a snapshot or migrated to a host with a different clock source can see time jump either way.
  • Operator error. Someone sets the date by hand, or a bad time server is configured.

The consequence is not just an out-of-order ID. If the clock goes back by 3 ms, the worker will again reach millisecond values it already used. With the same worker id and the sequence restarting at 0, it emits IDs it emitted before: exact duplicates. That is the data-corrupting outcome we must prevent.

Walkthrough. The top line is the clock reading, as one worker sees it, at six moments. Dots are readings: 1000, 1004, then 1001 (red, the step back), 1002, 1004, and 1005 (green, safe again). The red curved arrow marks the offset, 3 ms, between the highest reading 1004 and the new reading 1001. Reading it: 1. The worker has already issued IDs for millisecond 1004. 2. The clock steps back to 1001. 3. If it carried on, it would produce millisecond 1001 to 1004 again, with the same worker and sequence, so duplicates. 4. Only when the reading passes 1004 is it safe. The three boxes below give the policy by size of offset. Small, up to 5 ms: wait. Medium, up to about a second: reject and drain from the load balancer. Large: refuse, alert, release the lease and restart with a fresh worker id. The number that matters is the offset. Without this check, a rollback silently makes duplicates.

10.2 Prevention: a clock that cannot go back

The first line of defense is not to read a clock that steps. Configure the time daemon to slew only: chrony and ntpd can adjust frequency gradually (up to a small percentage) so time stays monotonic, and refuse to step except at boot. Use smeared leap seconds from the cloud provider's time service. Inside the process, measure elapsed time with the monotonic clock (the language's nanosecond timer, which never goes back) and compute the timestamp as wall_at_start + monotonic_elapsed. This protects against steps while running, at the price of slowly diverging from wall time if the process is very long-lived, so we re-anchor at each lease renewal only if the new wall time is not behind (we never anchor backwards).

10.3 Detection and policy on the hot path

Even with prevention, the generator must check now < lastTs on every call, because the check costs nothing and a duplicate costs a data-corruption incident. We define the offset d = lastTs - now and apply a tiered policy:

Offset dActionWhy
0 < d at most 5 msBlock the caller until the clock passes lastTs (sleep for d, then recheck).Cheap, invisible to callers, and preserves uniqueness and monotonicity.
5 ms < d at most 1 sReject the call with a retryable error and mark the generator unhealthy. The load balancer routes to other workers; embedded callers fall back to a local backup generator or retry.Blocking for hundreds of ms stalls request threads. Healthy peers can serve.
d above 1 sStop issuing, raise an alert, release the lease, and restart the process so it acquires a (possibly different) worker id after waiting out the old timestamps.Something is badly wrong with the host clock; the safest thing is a fresh start on a verified clock.

Another policy, sometimes seen, is the logical clock approach: keep using max(now, lastTs) and just keep incrementing the sequence, borrowing from the future. It never blocks, but it silently lets the embedded timestamp run ahead of real time, and it overflows the sequence quickly if the rollback is long. If the timestamp runs ahead, IDs are still unique, but "created at" decoding is wrong and, if the process restarts, the new instance has no memory of how far ahead it ran. We therefore reserve it for tiny offsets and rely on the tiered policy above.

10.4 Persisting the high-water mark across restarts

A restart loses the in-memory lastTs. If the restarted process reuses its old worker id on a host whose clock is behind the old timestamps, it will reissue numbers. The defense is a persisted high-water mark. At each lease renewal (every 20 s) the generator writes last_ts_ms + TTL to the registry, meaning "I promise never to have used a timestamp above this". A new owner of that worker id then must observe its own clock above that value before issuing, waiting if necessary. Because the mark is written ahead of use (a limit rather than the exact last value), it costs one write per renewal, not per ID.

// on renewal, every TTL/3 (about 20 s)
promised = now_ms + TTL_ms + SAFETY_MS        // upper bound of timestamps used until the next renewal
registry.renew(lease_id, last_ts_ms = promised)

// on startup with an inherited worker id
if (clock.now_ms() <= lease.last_ts_ms) sleep(lease.last_ts_ms - clock.now_ms() + 1)

Typically the wait is zero, because a new process starts at least a quarantine period after the old one died, and the quarantine already exceeds the TTL. The wait only bites when the new host's clock is genuinely behind, which is the situation we want to catch.

10.5 Clock skew across workers

Skew between workers (not rollback within one) never produces a duplicate, because the worker field differs. It only widens the k in "k-sortable". We monitor skew against a reference and alert if it exceeds, for example, 50 ms, because beyond that sorting by ID starts to misorder visibly (a chat message shown above an earlier one). Skew detection compares each worker's clock to the NTP reference reported by the time daemon (offset and estimated error).

11. K-sortable IDs, B-trees and why order matters for databases

Time ordering is not a cosmetic feature. It changes how the database behaves. Most relational and many NoSQL engines store the primary key in a B+tree or an LSM tree (Chapter 19). Consider what happens when a million rows arrive with random keys versus roughly increasing keys.

Walkthrough. The picture compares two B-tree leaf rows side by side. On the left, five green leaf pages under the heading Random UUIDv4 keys. Five red arrows point to different pages, because each new random key lands on a different leaf. On the right, under Snowflake or UUIDv7 keys, four full green pages and one amber hot leaf at the end. Green arrows all point at that last leaf. 1. A random key insert must find its leaf, which may be on disk, so the whole index must stay in memory to be fast. 2. Splits leave pages about half full. 3. A time ordered key always belongs on the rightmost leaf, so the working set is a few pages. 4. Earlier pages fill densely and stay untouched. The note at the bottom gives the caveat: on a very heavy insert load that one hot page can itself become a hotspot, so sharded tables spread it with a hash. To read it, compare the number of pages the arrows touch. If the arrows on the left were drawn as one point, the argument for ordered IDs would disappear.

The practical difference can be large: random UUID keys are widely reported to cause substantially slower inserts and larger indexes than sequential keys once the index exceeds memory, because each insert may need a random disk read and pages end up only partly full after splits. The exact factor depends on the engine, so state it qualitatively in an interview. There is a second benefit: pagination and range queries by time. "Give me the 50 newest orders" becomes ORDER BY id DESC LIMIT 50 using the primary key index, with no separate timestamp index (see Chapter 17). Decoding the ID also gives the creation time for free in logs and debugging.

Two cautions. First, time-ordered IDs leak information: anyone who sees two IDs can compute how many were created between them and when. For order numbers, that reveals business volume, which competitors might want. Second, on a sharded system that distributes by the raw ID, time-ordered keys make all new writes hit the newest range, a classic hotspot (Chapter 25). Hash the ID (or the tenant) for shard placement, and keep the ordered ID as the within-shard primary key.

12. Scaling, bottlenecks and hot spots

This system scales almost embarrassingly. There is no shared mutable state on the hot path, so adding generators adds capacity linearly. The places that can still bite are worth naming.

  • Per-worker ceiling. 4,096 IDs per millisecond, 4.096 million per second, versus our worst-case 977 per second per worker (section 3.3). A worker would need to run at 4,000x its current load to saturate. If a caller needs bulk IDs (a data import of a billion rows), it should use several workers or the batch API, not a single generator.
  • ID service tier. For clients that call the service, each pod is a generator with its own worker id. With 1,000,000 IDs/s peak and batch size 100, that is 10,000 requests per second, easily handled by about 10 pods (a pod can serve far more than 1,000 requests per second of this kind, leaving large headroom). Scale pods with load (Chapter 43); each new pod consumes a worker id for its life.
  • Lease registry. A consensus store is sized for its writes. Our lease writes are renewals: 400 processes renewing every 20 s is 20 writes per second, plus about 0.1 per second of acquire and release. That is trivial for etcd or ZooKeeper, which handle thousands of writes per second. The registry is not on the data path, so even a total outage only blocks new processes from starting.
  • Hot clock calls. Reading the clock on every ID is cheap on modern Linux (about 20 to 50 ns using the vDSO, a mapped kernel fast path). If a virtualization layer forces a real system call for the clock (a rare configuration), the cost is about a microsecond, still fine; we cache the millisecond and refresh it from a background thread only if profiling shows it matters.
  • Skewed use of the time bits. Fleets that all start batch jobs at midnight issue bursts in the same millisecond across many workers. Uniqueness is safe because workers differ. Downstream tables may see a hot key range; handled by sharding on a hash (section 11).
  • Caching: nothing to cache. IDs are produced, not looked up. Decoding is pure arithmetic.

We do not shard anything because there is nothing to shard. The "partitioning" is done by construction: the worker field partitions the ID space so generators never need to agree on which number comes next.

13.1 Consistency and idempotency decisions

The generator is deliberately available over consistent when the registry is partitioned: running generators keep issuing IDs because their uniqueness depends on local state and a lease they already hold, not on a live quorum. That is safe because the quarantine period guarantees nobody else gets their worker id until well after the lease deadline. The registry itself is a CP system (Chapter 28): when it cannot reach a quorum it refuses to hand out worker ids, since a duplicated assignment is far worse than a delayed one. A common idempotency pattern is for the client to generate the ID once (for an order) and send it with the create request, so that a retried create is recognized by its primary key and does not make a second row. This is only correct because the ID is unique and stable across the retry.

14. Multi-region

Each region runs its own lease registry and its own generators, so IDs can be created with no cross-region latency and survive a region isolation. Uniqueness across regions comes from disjoint worker-id ranges (section 8.4): region 1 owns 0 to 340, region 2 owns 341 to 681, region 3 owns 682 to 1,023. A region can never hand out an id from another's range, even while partitioned, so there is nothing to reconcile later. The three ranges are decided statically at launch and recorded in the immutable layout config.

  • Clock sources. Each region has its own time source. Cross-region skew is the sum of both regions' offsets from true time, typically a few milliseconds, which is the k in k-sortable. Do not promise cross-region ordering.
  • Range exhaustion. If one region grows far larger than the others, ranges must be rebalanced. Because ids are leased and quarantined, move a range only while its ids are unallocated, and update the immutable config in a controlled migration (section 17). Having 1,024 ids spread over three regions leaves about 340 per region against a need of about 130 at the busiest, so we have more than 2x headroom.
  • Region failover. When a region's workloads fail over to another, they request worker ids from the surviving region's registry, which draws from its own range. IDs created in the failed region before failover stay valid because they embed the old region's worker ids.
  • Emergency range. Reserve a small slice (for example worker ids 1,000 to 1,023) that only a manual runbook can hand out, for the case where a region's registry is unavailable for hours. Processes started this way are tracked by hand and cannot be auto-recycled.

The general topic of replication and failover across regions is in Chapter 26 and disaster recovery in Chapter 41.

15. Security and abuse

  • Predictability. A Snowflake ID is guessable: given one ID, the neighbors in time and sequence are easy to enumerate. Never use it as a bearer secret (session id, password reset token, signed URL). Use 128 or more random bits from a cryptographic generator for those. If you must expose IDs publicly and want to prevent enumeration (/orders/12345), authorize every access on the server (Chapter 55) rather than relying on obscurity, and optionally encrypt the numeric ID with a format-preserving cipher at the API boundary.
  • Information leak. The timestamp and the worker id reveal creation time, rate and approximate topology. Decide whether that is acceptable for public IDs.
  • Service abuse. The ID service can be asked for huge batches. Cap count (for example 1,000), authenticate callers, and rate limit per client (Chapter 16), since a malicious or buggy loop could burn the ID space of one worker at 4 million per second.
  • Registry access. Only the lease client identity may write lease rows. A compromised or misconfigured client that could write arbitrary worker leases could cause duplicates deliberately.

16.1 Cost

The cost is negligible compared with the systems it serves. The registry is 5 small nodes. The ID service is about 10 small pods plus headroom. The embedded library costs nothing. The dominant cost is indirect: the key width. At 25.9 billion IDs per day, choosing 8-byte over 16-byte keys saves about 207 GB per day of key bytes before indexes and replicas (section 3.2); at a typical block-storage price of a few cents per GB-month and 3x replication, that is the line that matters, not the generator's compute.

17. Evolution, phasing and what changes at 10x

17.1 What to build first

  1. Phase 1. UUIDv7 or a single ticket-server pair if the team is small. It works today, needs almost no infrastructure, and the bit-layout debate can wait.
  2. Phase 2. Embedded Snowflake library with static worker ids from StatefulSet ordinals, slew-only NTP, rollback handling and decode helpers.
  3. Phase 3. Lease registry, quarantine, high-water marks and the canary duplicate detector. This is when autoscaling and multi-region become safe.
  4. Phase 4. ID service for non-embedding clients, batch API, quotas, dashboards.

17.2 At 10x scale

10,000,000 IDs per second at peak is still only 2.4 times one worker's ceiling, so the layout still works. What strains is the worker count (more processes) and the burst per millisecond (10,000 per ms spread across workers is fine). If the fleet outgrows 1,024 workers, the options are: borrow bits from the sequence (10 worker bits become 13, sequence 12 becomes 9, giving 512 IDs per ms per worker, enough for our 977 per second average); move to a 10 ms tick (Sonyflake style) which frees 3 bits; or change the layout version. Because the layout is versioned, a new layout must be distinguishable from the old one. Reserve the sign bit's neighbor, or use disjoint timestamp ranges: all new-layout IDs sort above old ones if the new epoch's start is later and the migration happens at a fixed instant.

17.3 Alternatives not chosen

The main alternatives are summarized in the next section. We did not choose a centralized sequencer (a consensus-backed counter, Chapter 29), because it puts a consensus round or at least a network hop on every ID, which costs milliseconds and makes the sequencer a global dependency. A block-allocation hybrid (the registry hands out blocks of 10,000 numbers) is a viable simpler design if strict k-sortability is not needed.

18. Alternatives and related problems

18.1 When UUIDv7 is the better answer

If 128 bits is acceptable, UUIDv7 removes the whole lease registry and the worker-id problem: its 74 random-ish bits make collision negligible without any assignment. It still depends on a clock for ordering (a rollback only misorders IDs rather than duplicating them, since the random bits differ with overwhelming probability). The price is the doubled key width and a weaker decode story (no worker id). For many companies that is the right call; for ones with billions of rows per day and several indexes, the 64-bit width wins.

18.2 Gap-free business sequences

Invoice numbers, cheque numbers and some tax identifiers must be gapless and in order. This is a different problem: a single serialized allocator in a database transaction (UPDATE counters SET n = n + 1 RETURNING n inside the same transaction that writes the invoice), so a rolled-back transaction does not consume a number. It scales only to the throughput of that row, typically hundreds per second, which is fine for invoices. Keep this separate from the primary-key generator, which may skip values freely.

18.3 Other designs worth naming

  • Hash of content (content-addressed IDs): the ID is a digest of the data, giving deduplication and integrity but no ordering and 256 bits.
  • Database sequences per shard plus a shard prefix (Instagram style): ID = time bits + shard id + per-shard sequence generated inside Postgres with a PL/pgSQL function; no external service, and the shard id is embedded so routing is trivial.
  • Hierarchical ids (parent id plus child counter): useful for orders and order lines; the child number only needs to be unique under its parent.

19. Interview Q&A

Why not just use UUIDs everywhere and skip all this?

UUIDv4 is a perfectly safe default when you do not care about order or size, and for small systems it is the right answer because it needs no infrastructure. At our scale it costs twice the key width, which multiplies through every index and foreign key (hundreds of gigabytes per day here), and its randomness causes scattered B-tree inserts and poor cache behavior. UUIDv7 repairs the ordering but not the size. So the honest answer is: UUIDv7 if 128 bits are fine, Snowflake if you need 64 bits and decodable fields. I would say that trade-off out loud and let the constraints choose.

Two workers get the same worker id. What happens and how do you prevent it?

If both are alive and both issue IDs in the same millisecond with the same sequence, they emit identical IDs, and the database either rejects one with a duplicate key error or, worse, an upsert overwrites a row. Prevention is layered: a lease registry that is the only source of worker ids, a quarantine so a recently released id is not reissued quickly, a self-expiry check on every call so a paused process stops itself, and a high-water mark so a new owner waits out the old timestamps. Detection is a duplicate-key alert and a canary that samples IDs. I would also be clear that the guarantee rests on bounded pause and clock drift assumptions, not on magic.

What do you do when the system clock moves backwards?

First, do not let it happen: slew-only NTP, smeared leap seconds, and a monotonic clock anchored at startup. Second, detect it on every call by comparing now to the last timestamp. For a small offset (a few milliseconds) the generator waits until the clock catches up; for a medium offset it fails health checks and the load balancer drains it; for a large offset it releases its lease and restarts with a fresh worker id after waiting out the stored high-water mark. The invariant is simple: never issue an ID whose timestamp is not greater than or equal to the last one with the same worker id and a larger sequence.

Why is the timestamp in the most significant bits?

Because numeric comparison of integers looks at the high bits first. Putting time first means that IDs created later compare larger, so sorting by ID approximates sorting by time and database indexes see mostly increasing keys. If the worker id were first, IDs from worker 1 would all sort before those of worker 2 regardless of time. The order inside the same millisecond is arbitrary across workers, which is why we call it k-sortable rather than strictly ordered.

How does a new service instance get its worker id, and what if the registry is down?

At startup it acquires a lease on one of 1,024 worker ids from a consensus-backed registry, gets back the last timestamp used by prior owners, waits if its clock is behind, and renews every third of the TTL. If the registry is down at startup, the process cannot get a safe id and should fail to start (fail closed) or, in a documented emergency, take an id from a reserved manual range. Processes already running are unaffected until their lease deadline, which we set to be much longer than typical outages.

How many IDs per second can one worker produce, and how do you scale beyond it?

With 12 sequence bits it can produce 4,096 IDs per millisecond, which is 4,096,000 per second. Beyond that the generator waits for the next millisecond, which is a built-in throttle. To scale, add workers: each has its own worker id, and IDs never collide. With 1,024 workers the theoretical ceiling is about 4.2 billion IDs per second. If more is needed, shorten the tick, take bits from the worker field, or use a wider ID.

Can you use these IDs to determine which event happened first?

Only approximately. Within one worker, yes, as timestamps never go down. Across workers the order is correct only to within the clock skew, typically a few milliseconds, because two IDs in nearby milliseconds from different machines may sort the wrong way. For causality you need logical clocks, version vectors or a consensus sequence (Chapter 27), not wall-clock IDs. I would use the ID for pagination and storage locality, and a separate mechanism for correctness-critical ordering.

Why not use a central ID server or a database sequence for everything?

It would give exact order and no clock risk, but it puts every ID creation behind one network call and one machine or one consensus group. At a million IDs per second a single database cannot sustain the writes, a consensus group adds a round trip of milliseconds per ID, and the service becomes a global point of failure. Batching blocks of numbers reduces the load but gives up fine-grained time order. Snowflake removes the hot-path coordination at the cost of operational care around clocks and worker ids, which is a better trade at this scale.

How would you migrate an existing system from auto-increment IDs to Snowflake IDs?

Widen the column to 64-bit unsigned (or confirm it is a BIGINT) and make clients treat IDs as opaque strings so JavaScript clients do not lose precision. Start generating new rows with Snowflake IDs while old rows keep their small integers; because the timestamp is in the high bits and the old values are tiny, old IDs sort before new ones, which preserves rough order. Dual-read for a while, and move foreign keys step by step. There is no need to rewrite old rows unless you want uniform decoding, and rewriting would require a coordinated migration of every reference (Chapter 26).

Is it a problem that IDs reveal time and worker information?

It can be. Anyone who sees two IDs can estimate how many records were created between them, which can reveal business volume, and the worker bits leak topology. For internal keys this is usually fine. For public identifiers, either accept the leak, encrypt the ID at the API boundary, or expose a separate random public id and keep the Snowflake ID internal. In every case, authorization must be checked on each access, because a guessable ID with no access check is a vulnerability regardless of the generator.

20. Recap

  • The choice is a triangle of uniqueness, compactness and order. UUIDv4 gives uniqueness only. Ticket servers give order but need a network hop per ID. Snowflake gives all three by packing time, worker and sequence into 64 bits.
  • Layout: 1 sign, 41 timestamp (about 69.7 years from a custom epoch), 10 worker (1,024), 12 sequence (4,096 per ms per worker, 4.096 million per second). Capacity is not the constraint; correctness around the clock and the worker id is.
  • Worker ids are leased from a consensus-backed registry with quarantine, self-expiry and a persisted high-water timestamp, so reuse is safe and a paused old owner cannot collide.
  • Clock rollback is the dangerous event: prevent with slew-only NTP and monotonic anchoring, detect on every call, and respond by size (wait, drain, replace).
  • Time-ordered IDs make B-tree inserts append to a hot edge and keep indexes dense; hash the ID for shard placement to avoid a hot shard.
  • IDs are k-sortable, not causally ordered, and are guessable, so never use them as secrets or as proof of order.
  • UUIDv7 is the best alternative when 128 bits are acceptable; gap-free business numbers are a separate transactional allocator.
