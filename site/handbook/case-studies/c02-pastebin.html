Design Pastebin

Pastebin lets anyone store a chunk of text, get a short link, and share it. It looks like a toy, but it hides the classic split between small hot metadata and large cold content, a key-generation problem, expiry at scale, and an abuse problem. This page solves it the way a strong candidate would in a 45-minute interview.

How to approach this problem (read this first)

Pastebin looks like a toy, and that is the trap. If you start drawing boxes immediately you will end up with a generic web app. This section gives you a way to start and a way to keep going.

What the interviewer is really testing

Traffic here is small: about 12 writes and 116 reads per second on average. So the interviewer is not testing raw throughput. They want to see three things. First, that you notice the data is mostly bytes, not requests (10 GB of new text a day), and so you split metadata from content. Second, that you can hand out unique, unguessable keys without a race. Third, that you handle expiry, abuse and privacy, which are the parts real pastebin sites actually struggle with.

The thinking order, step by step

  1. Clarify size, visibility and expiry. Say: "How large can a paste be, who can read it, and does it expire?" These three answers (1 MB cap, public/unlisted/private, user-chosen expiry) shape the storage split, caching rules and cleanup. Ask them first because every later choice depends on them.
  2. Estimate QPS, then bytes. Say: "That is about 12 writes per second, so QPS is easy; the real number is 10 GB per day, about 3.65 TB a year." Do QPS first to prove it is small, then storage, because storage is where the interesting finding is.
  3. Draft the API. Create returns a key and a delete token; read has HTML and raw forms. Say: "Reads can return 410 for expired and 404 for private pastes of others." The status codes already hint at expiry and access control.
  4. Name the two kinds of data. Say: "Metadata is small and queried; the text is large and immutable. I will keep them in different stores." This is the central design decision, so state it as soon as the API is on the board.
  5. Draw the one-database design and break it. Say: "This works, and here are six things that fail as it grows." Each failure becomes one component later.
  6. Scale the read path. Say: "Reads are 10 times writes and content is immutable, so CDN and Redis do most of the work." Then trace the create and read flows in order.
  7. Deep dive on keys. Say: "Random plus retry works at 12 writes per second; I will show a pre-generated key pool as the way to remove the race at scale." Compare options in a table.
  8. Deep dive on expiry. Say: "Correctness comes from checking the time on read; cleanup is only about cost." This split is the cleanest answer you can give.
  9. Finish with abuse and failure. Say what happens if the object store, the key service or the sweeper fails, and mention a separate cookieless domain for raw content.

The decision points

  • Database or object storage for the text? Ask: how big, how mutable, how often queried? 10 KB, immutable, fetched whole, so object storage, with only the hash in the row.
  • Random keys, counter or key pool? Ask: must keys be unguessable? Yes for unlisted pastes, so no plain counter; choose a pool or random-plus-retry and explain the tradeoff.
  • Lazy or eager expiry? Ask: can an expired paste be served for a minute? No, so check on read, and clean up in the background for space.
  • Cache private pastes at the CDN? Ask: could a shared cache answer an authorization question? No, so private responses are never cached at the edge.
  • Deduplicate content or not? Ask: is the saving worth reference counting? Perhaps 10 to 30 percent of bytes; treat it as a later phase.

Common mistakes on this problem

  • Putting 10 KB text blobs in the main database. Fix: store text in object storage and keep a hash in the row.
  • Using sequential IDs for unlisted pastes. Fix: use random keys so the link is a usable secret.
  • Relying on a cleanup job for expiry. Fix: check expiry on every read and cap cache TTLs.
  • Caching private pastes in the CDN. Fix: use private, no-store and bypass the cache for authenticated requests.
  • Ignoring abuse and stored XSS. Fix: serve raw text as text/plain with nosniff from a separate domain.
  • Writing metadata before the blob. Fix: write the blob first so a crash leaves garbage, not a dangling pointer.

1. Problem statement and clarifying questions

The prompt is usually one sentence: "Design Pastebin." A user pastes text (code, a log, a config file), the service stores it, and returns a URL such as https://paste.example/aZ3kP9xQ. Anyone with the URL (or only the owner, for private pastes) can open it later and see the text, usually with syntax highlighting. Pastes can expire after a time the user chooses. The first five minutes of the interview are for questions, following the framework in Chapter 1. Here are the questions worth asking, with the answers I will assume for the rest of the page.

QuestionAssumed answer
How many users and pastes?About 1 million new pastes per day. Reads dominate at 10 reads per write, so 10 million reads per day.
How big is a paste?Average 10 KB. Hard maximum 1 MB per paste (anything bigger is a file-sharing problem, not a paste problem).
Anonymous or logged-in users?Both. Anonymous pastes are allowed (that is the main use), logged-in users get a history list and can delete or edit their pastes.
Visibility?Three levels: public (listed and indexable), unlisted (anyone with the link), private (owner only).
Expiry?The user picks: 10 minutes, 1 hour, 1 day, 1 week, 1 month, or never. Default one month for anonymous users, so storage does not grow forever.
Custom URLs?Optional for logged-in users; the core design uses generated keys.
Syntax highlighting?Yes, for common languages. It must not slow the read path down.
Edits and history?Logged-in owners can create new versions; older versions stay readable at a version-specific URL.
Availability and latency?Reads 99.95 percent available, p99 under 200 ms for a cached read. Writes can be slightly slower (under 500 ms).
Durability?A paste that has not expired must not be lost. This is the one hard promise.
Global?Yes, readers are worldwide, writers mostly the same. One primary region with a CDN in front is enough to start.
Interview tip Say out loud which assumption is the dominant one. Here it is "reads are ten times writes, and most pastes are read only a few times." That one sentence drives caching, CDN use, and the storage split.

2. Requirements and scope

2.1 Functional requirements

  • Create a paste from text with optional title, language, visibility, and expiry, and receive a short key and URL.
  • Read a paste by key, as an HTML page with highlighting and as raw text.
  • Delete a paste (owner only, or anonymous with a secret delete token returned at creation).
  • Expire pastes automatically at their chosen time; after expiry reads return "gone".
  • List a logged-in user's pastes; list recent public pastes.
  • Create new versions of an existing paste, and read old versions.
  • Report abusive pastes; moderators can remove them.

2.2 Non-functional requirements

  • Read-heavy and highly available. A link that was shared in a chat must open quickly, from anywhere.
  • Durable. Non-expired pastes are never lost (object storage with replication gives eleven nines of annual durability, typically).
  • Cheap per paste. Storage is the dominant cost, so size limits, expiry, and deduplication are cost features, not extras.
  • Unguessable for unlisted pastes. The key is the only secret, so keys must not be sequential or predictable.
  • Abuse-resistant. A free anonymous write endpoint is a magnet for spam, malware hosting, and leaked credentials.

2.3 Out of scope

Binary file hosting, collaborative real-time editing (that is a different design, see Chapter 6), full-text search over all pastes, comments, and payments. I will mention search and collaboration only as evolution options.

3. Estimation

Estimation technique is covered in Chapter 2. The goal is not precision but to find out which resource is the bottleneck. Round numbers are fine; show the arithmetic.

3.1 Traffic

These are tiny numbers. One decent database could serve 600 reads per second. That is a useful finding: this system is not hard because of QPS. It is hard because of storage growth, key generation correctness, expiry, and abuse. If an interviewer wants more drama, scale users 100x (100 million pastes per day, 60,000 peak reads per second) and the same architecture still works because every component is horizontally scalable.

3.2 Storage

QuantityArithmeticResult
Content per day1,000,000 x 10 KB10 GB per day
Content per year10 GB x 365about 3.65 TB per year

Content is 20 times bigger than metadata (10 KB versus 500 B). The metadata of five years (about 900 GB) still fits on one large database server, though we will shard or replicate for availability. The content (18 TB, and more with a 100x scale-up) belongs in object storage, which is why the central design decision is the split in section 6.

3.3 Bandwidth and cache memory

  • Read bandwidth: 116 reads per second x 10 KB = about 1.2 MB per second average, which is about 9 megabits per second. Peak is 600 x 10 KB = 6 MB per second, about 50 megabits per second. Trivial for one region, which again shows the CDN is for latency and origin protection, not bandwidth.
  • Write bandwidth: 12 x 10 KB = 120 KB per second average.
  • Hot set: reads follow a skewed distribution; a paste shared in a popular thread gets most of its reads in the first day. Suppose 3 million distinct pastes are read each day and the top 20 percent (600,000) take most traffic. Content 600,000 x 10 KB = 6 GB; with metadata 600,000 x 0.5 KB = 0.3 GB. About 6 to 7 GB of cache holds the working set. One Redis node (see Chapter 15) holds that easily.

3.4 Key space

Keys use the 62 characters 0-9, a-z, A-Z. With 8 characters there are 62^8 = about 2.18 x 10^14 keys. We create 365 million pastes per year (1,000,000 x 365), so ten years use 3.65 billion keys, which is 0.0017 percent of the space. That sparse usage is what makes random keys unguessable: an attacker who tries a random 8-character key hits a live paste with probability about 1 in 60,000 for each guess, and rate limits make scanning impractical. The related short-link design in Case study 1 goes deeper on encodings; here the focus is the pre-generated key service.

3.5 Rough cost

Prices change, so treat these as order of magnitude. Object storage standard tier typically costs about 2 to 3 cents per GB-month. 18 TB is 18,000 GB, so about $400 to $550 per month after five years with no expiry. Requests cost about $0.005 per 1,000 PUTs: 30 million PUTs per month is about $150. GETs cost about $0.0004 per 1,000; with a 90 percent CDN hit ratio only 1 million per day reach the origin, about 30 million per month, around $12. Egress to the internet dominates if you serve from storage directly (about 9 cents per GB at list price), which is another reason to put a CDN in front: serving all 3 TB per month of reads from storage would be about $270, versus a few dollars for the roughly 300 GB that reach the origin behind a CDN, and at 100x scale it matters. The summary: storage and its lifetime are the cost, which expiry and dedup attack directly.

4. API design

A REST API over HTTPS (principles in Chapter 5). Write calls need an API key or session cookie (anonymous calls get strict IP rate limits). Every create call accepts an Idempotency-Key header so client retries do not make duplicate pastes (see Chapter 32).

Design notes. The create call returns 413 Payload Too Large above 1 MB and 429 Too Many Requests when rate limited. Reads return 404 for unknown keys, 410 Gone for expired or deleted pastes (clients and crawlers learn the difference), and 403 only for authenticated users who are not allowed; for private pastes of other users, return 404 to avoid confirming that the key exists. List endpoints use cursor pagination, not offsets, because offsets get slower and unstable as data changes.

5. Data model and storage choice

There are two different kinds of data with opposite properties, so they get different stores.

Size per pasteabout 500 Babout 10 KB (up to 1 MB)

5.1 Metadata in a database

The metadata row is small, queried by key, and queried in other ways (by owner, by expiry). A sharded relational database or a key-value store such as DynamoDB or Cassandra works (compare in Chapter 20 and Chapter 17). I would pick a relational database with a read replica per region at this scale: the data is small, we want secondary indexes and transactions for the version counter, and sharding by key hash is available when needed (Chapter 25).

pastes(
  key            CHAR(8)  PRIMARY KEY,
  owner_id       BIGINT   NULL,            -- NULL for anonymous
  title          VARCHAR(100),
  language       VARCHAR(20),
  visibility     SMALLINT,                 -- 0 public, 1 unlisted, 2 private
  status         SMALLINT,                 -- 0 active, 1 expired, 2 deleted, 3 blocked
  current_version INT,
  created_at     TIMESTAMP,
  expires_at     TIMESTAMP NULL,           -- NULL = never
  delete_token_hash BYTEA NULL,
  size_bytes     INT,
  view_count     BIGINT                    -- approximate, updated asynchronously
)
paste_versions(
  key            CHAR(8),
  version        INT,
  content_hash   CHAR(64),                 -- SHA-256 hex, also the object name
  size_bytes     INT,
  created_at     TIMESTAMP,
  PRIMARY KEY (key, version)
)
blobs(
  content_hash   CHAR(64) PRIMARY KEY,
  object_key     VARCHAR(100),             -- e.g. blobs/ab/cd/abcd...
  ref_count      BIGINT,                   -- number of versions pointing here
  first_seen_at  TIMESTAMP
)
INDEX pastes(owner_id, created_at DESC)
INDEX pastes(expires_at) WHERE status = 0 AND expires_at IS NOT NULL

Notice what is not in the table: the text. The row holds the hash, and the hash is the name of the object in storage.

5.2 Content in object storage

Object stores such as Amazon S3, Google Cloud Storage, or Azure Blob (Chapter 21) are built for exactly this: large numbers of immutable blobs, cheap per GB, replicated across availability zones for durability, and with built-in lifecycle rules and CDN integration. Putting 10 KB blobs in the relational database would work for a year, but then you pay for expensive database storage, the buffer pool fills with cold text, backups and replicas become huge and slow, and every replica copies all of it. Moving the text out keeps the database small, which means it stays in memory and stays fast.

Object key layout matters. Object stores partition by key prefix, so avoid prefixes that all start the same way, and avoid timestamps as the first element. Using the hash gives a uniform spread: blobs/ab/cd/abcdef.... Small pastes are written as a single PUT. For text, store gzip or zstd compressed (text typically compresses 3x to 5x, a direct 70 percent cost cut) and mark Content-Encoding so it can be served as-is.

Key idea Metadata is small, hot, queried, and mutable, so it lives in a database. Content is large, cold, immutable, and fetched as a whole, so it lives in object storage. The row points to the blob by content hash. This split is the answer to "where do you store the paste?"

5.3 Why not store small pastes inline?

A reasonable optimization: pastes under 2 KB (a sizeable share of all pastes) could be stored inline in the metadata row, saving one network hop to object storage on every read. The cost is two code paths and a migration problem when a paste grows via edit. I would not do it first; a Redis cache of the content makes the second hop disappear for hot pastes anyway. Mention it as an optimization, not the baseline.

6. A first simple design

Start with the simplest thing that works, then find where it breaks.

Walkthrough. This is the simplest version, drawn so you can break it. 1. The Browser or client sends a POST to create or a GET to read. 2. The App server validates input and generates a random key. 3. It stores metadata and text together in One database and reads them back the same way. Every arrow goes through the same two boxes, which is the point: there is nothing to replicate, cache or expire. On a whiteboard draw these three boxes in under a minute and then list what fails: the database fills with cold text at 10 GB a day, both boxes are single points of failure, key collision checks race under concurrency, nothing deletes expired data, every read hits the database, and nothing limits abuse. Each of those becomes a box in the next diagram. If you remove the "text in the database" part and move it out, you get the central split of this design.

Where it breaks: (1) the database grows by 10 GB per day, mostly cold text, so backups and replicas become slow and expensive; (2) a single app server and a single database are single points of failure; (3) random key generation in the app needs a collision check against the database on every write, which is a read-before-write race under concurrency; (4) nothing removes expired data; (5) every read hits the database even though most reads are for the same few hot pastes; (6) no abuse controls. Each of these gives one component in the scaled design.

7. Scaled high-level architecture

Walkthrough. Read the picture from the left. Purple Clients first reach the CDN, which answers public reads from the edge. Misses go to the Load balancer with rate limiting, then split into two blue stateless services: Write API and Read API. 1. A create goes to Write API, which takes a key from the Key service, puts the text in Object storage and the row in the Metadata DB. 2. A read goes to Read API, which checks Redis (amber), then the Metadata DB, then Object storage. 3. Cleanup workers and the Abuse pipeline hang off a Queue, outside the request path. Reads and writes are split because reads are 10 times more frequent and must stay up when writes degrade. Point at the Queue as the boundary between user-facing and background work. If the Queue and workers are removed, expired data never leaves and abusive content is never scanned.

Component roles, in the order a request meets them:

  • CDN (Chapter 12): caches raw and HTML responses of public and unlisted pastes at the edge. Never caches private pastes.
  • Load balancer and rate limiter (Chapter 9, Chapter 16): spreads traffic, enforces per-IP and per-account limits, and rejects oversize bodies before they reach the app.
  • Write API and Read API: separated because their scaling, caching, and failure behavior differ. Reads are 10x more frequent and must stay up even if writes are degraded.
  • Key service: hands out unique pre-generated keys (section 9).
  • Metadata database: source of truth for key, owner, visibility, expiry, status.
  • Object storage: source of truth for text.
  • Redis cache (Chapter 13): read-through cache of metadata and small hot content.
  • Queue and workers (Chapter 34): asynchronous work (abuse scanning, view-count aggregation, expiry deletion, blob garbage collection).

8. Request flows

8.1 Create a paste

Walkthrough. A sequence diagram: time flows downward and each column is a participant. 1. The Client posts text and options to the Write API. 2. The Write API validates size and rate, compresses, and computes the content hash. 3. It asks the Key service for a key and gets one such as aZ3kP9xQ, usually from its in-memory batch. 4. It PUTs the blob to the Object store only if the hash is new, and gets an OK. 5. In one transaction it inserts the paste row, the version 1 row and increments the blob reference count in the Meta DB. 6. It replies 201 with the URL and delete token, and queues an asynchronous scan. The key point is the order in steps 4 and 5: blob first, metadata second. If the process dies between them you have an orphan blob that cleanup removes. Swapping the order could leave a row pointing at nothing, which a user would see.
  1. The edge or load balancer rejects bodies over 1 MB and applies rate limits.
  2. The Write API validates fields, normalizes line endings, compresses, and computes the SHA-256 of the content.
  3. It takes the next unused key from its local batch (section 9).
  4. It checks the blobs table for the hash; if absent it PUTs the object (deduplication, section 12). Object PUT is idempotent for the same name and bytes.
  5. In one database transaction it inserts the paste row and the version row and increments the blob's reference count.
  6. It returns the URL, and publishes a "paste created" event to the queue for asynchronous abuse scanning and indexing of public pastes.

8.2 Read a paste

Walkthrough. Another sequence diagram, this time for reads. 1. The Client requests the paste URL. 2a. If the CDN has it, the edge answers and nothing else happens; for a popular public paste this is the usual outcome. 2b. On an edge miss the request is forwarded to the Read API. 3. The Read API asks Redis for metadata and content. 4a. A hit returns at once. 4b. A miss reads the metadata from the Meta DB. 5. The Read API checks status and expiry against the clock, then fetches the blob from the Object store. 6. It fills Redis with a TTL capped by the remaining lifetime. 7. It returns 200 with Cache-Control, and 8. the edge stores the response. Whiteboard tip: draw the short loop 1 to 2a first, then the longer path. The expiry check in step 5 is what makes cleanup a cost feature and not a correctness requirement. Remove it and an expired paste could be served from cache.

At step 5 the Read API must check status and expires_at against the clock before returning anything. That check is the "lazy" half of expiry (section 10). Raw reads return the bytes with Content-Type: text/plain; charset=utf-8, X-Content-Type-Options: nosniff and a Content-Disposition that stops browsers from rendering pasted HTML as a page on our domain (a classic stored-XSS trap; see section 14).

9. Deep dive 1: key generation

Every paste needs a unique, short, unguessable key. The interviewer will probe this because "just generate a random string" hides a race.

9.1 Options

OptionHowProsCons
A. Random 8 chars plus uniqueness checkEach app server picks a random key, tries INSERT, retries on duplicate-key errorNo extra service; stateless; unguessableA collision costs a retry; collision probability rises as the table fills (small here: at 3.65 billion keys the chance per try is 0.0017 percent); hot path depends on the database being the arbiter
B. Hash of content, truncatedMD5 or SHA-256 of text, take first 8 charsFree dedupSame text from two users gets the same key (bad for private and for delete); truncation collisions between different texts; guessable if you know the text
C. Counter plus base62Global increasing id encoded in base62No collisions, shortest keysSequential keys are enumerable, so unlisted pastes are scannable; the counter is a coordination point

Option C with a shuffling function (an id permuted by a keyed block cipher so output looks random) is a neat variant, but it adds cryptographic details. I choose D, because it removes the contention from the write path and the cost of the component is small. Option A is a reasonable fallback and I would say so out loud: at 12 writes per second the simple approach would work, and picking D is about demonstrating how to remove a race at scale. The core idea matches the ID-generation material in Chapter 32.

9.2 How the key service works

Walkthrough. The left side is the offline part and the right side is the serving part. 1. The Generator job creates random 8-character keys and inserts them into unused_keys, where the primary key rejects any duplicate once, offline. 2. The Key allocator, in one atomic step, moves 1,000 rows from unused_keys to allocated_keys and returns them. 3. Write API 1, 2 and 3 each hold a batch in memory and hand out keys without any network call per paste. 4. When a server dies, the keys it still held are simply lost; the note says this wastes at most 1,000 out of 218 trillion. The design avoids the alternative of picking a random key and checking the database on every write, which is a read-before-write race. Point at the atomic move as the only place a double hand-out could happen. If the allocated_keys table is removed, you cannot tell which keys have already been given out.

Details that matter:

  • Uniqueness is guaranteed by the pool. The generator inserts into unused_keys with the key as primary key; duplicates are rejected there, once, offline. After that no two batches ever share a key because rows are moved, not copied.
  • Atomic hand-out. The allocator runs a transaction (delete 1,000 rows from unused_keys returning them, insert into allocated_keys), or uses a primitive such as SELECT ... FOR UPDATE SKIP LOCKED so two allocators never take the same row. This is the one place where a double hand-out could occur, so test it hardest.
  • Server crash. Keys held in memory by a crashed server are simply never used. With 2.18 x 10^14 keys, losing thousands is irrelevant. Do not try to recover them; recovery logic is where double-use bugs are born.
  • Batch size. At 60 writes per second peak across, say, 6 write servers, one server uses about 10 keys per second, so a 1,000-key batch lasts about 100 seconds and the allocator sees under one request per second per server. A server also prefetches the next batch when 20 percent remain, so the allocator being briefly down does not block writes.
  • Sharding the pool. If the allocator becomes a bottleneck at 100x scale, partition the pool by first character and assign each write server a partition; no coordination at all.
  • Last line of defence. The pastes.key primary key still rejects a duplicate. If that ever fires, the server discards the key, takes the next one, and raises an alert, because it means the key service has a bug.
  • Unguessability. Keys must come from a cryptographically secure random source, not a linear generator whose output could be predicted from a few samples.
Watch out The KGS is a single point of failure only if you make it one. Run the allocator as several stateless instances over a replicated database, keep prefetched batches in the writers, and keep a fallback path (option A: random key plus insert-and-retry) so that creation still works if the allocator is down for minutes.

Should keys ever be reused after a paste expires? With 62^8 keys, no. Reuse creates a nasty class of bugs: stale links, search engine caches, and CDN copies suddenly show someone else's text. Never recycling keys also keeps the "410 Gone" answer meaningful.

10. Deep dive 2: expiry and cleanup

Expiry has two jobs: correctness (an expired paste must not be served) and cost (expired data must eventually be deleted, so storage does not grow without bound). Those two jobs are handled by two different mechanisms, which is the standard answer: lazy expiry for correctness, background cleanup for space.

10.1 Lazy expiry (correctness)

Every read checks expires_at (and status) against the current time. If the paste has expired, the API returns 410 Gone and does not touch the object store. This is exact to the second, needs no scanning, and works even if the background job is behind or broken. The check costs a comparison on a row we already loaded.

The cache layers must respect expiry too. When the Read API fills Redis or sends a response to the CDN, it caps the TTL: TTL = min(default_ttl, expires_at - now). A paste that expires in 10 minutes is cached for at most 10 minutes, so no layer keeps serving it afterwards, and no purge call is needed. The HTTP response carries Cache-Control: public, max-age=N and an Expires consistent with that cap (see Chapter 12 on cache headers, and Chapter 14 for what goes wrong when TTLs are wrong). Early deletion (owner deletes, moderator blocks) is different: no TTL covers it, so those events trigger an explicit CDN purge by key plus a Redis delete.

10.2 Background cleanup (space)

Lazy expiry alone never reclaims space, because nobody reads an expired paste again. A background sweeper does the deletion.

Walkthrough. This is a state machine read left to right with time along the way. 1. Active: the paste is served normally. 2. At expires_at the paste becomes Expired: reads return 410 because of the lazy check, but nothing has been deleted yet. 3. The sweeper, within minutes, marks the row as Tombstoned. 4. After a 24 hour grace period the garbage collector deletes the blob. The notes explain the main idea: the gap between "not readable" and "physically gone" is deliberate. Because readers are already blocked at expires_at, the sweeper may be late and it only costs money. Metadata rows can be dropped after a longer window, such as 30 days, to keep 410 answers and evidence. On a whiteboard draw the four boxes and mark which one is correctness and which is cost. If you remove the grace period, a new paste with the same content could race with deletion of the shared blob.

Three ways to implement the sweeper, compared:

ApproachHowTradeoff
Periodic queryEvery minute: select rows where status is active and expires_at < now in batches of 1,000 using the partial index; mark them expired; enqueue blob releaseSimple; the index scan is cheap; but deleting millions of rows individually creates write amplification and table bloat
Time-partitioned tablesPartition metadata by expiry day; when a whole partition is past its retention window, drop it as one cheap operationVery cheap bulk deletion; but the expiry date must be known at creation and "never" pastes need their own partition; changing an expiry moves the row
Store-native TTLDynamoDB TTL on the metadata item; S3 lifecycle rules on an expiry-day tag or prefixAlmost no code; deletion is best effort and can lag by hours or days, which is why lazy checks still matter

I would use the periodic query for metadata at this scale (1,000,000 expiring rows per day is about 12 per second, nothing) with a daily partition scheme as the planned scale-up. For blobs, deletion is gated by a reference count (section 12): the sweeper decrements the count, and a separate garbage collection job deletes blobs whose count has been zero for more than a grace period. The grace period guards against the race where a new paste with the same content arrives just as the old one is released.

Sweeper requirements: it must be idempotent (running a batch twice is harmless, because marking an already expired row expired changes nothing), resumable (it keeps a high-water mark, or simply re-queries), and it must rate limit itself so a backlog does not flood the database or the object store. Schedule and orchestrate it as in Chapter 38; run it as several workers each owning a key-hash range so they do not overlap, or use SKIP LOCKED to claim batches.

Key idea Never make correctness depend on a background job. The read path enforces expiry by comparing timestamps; the sweeper is only a cost optimization. A broken sweeper then produces a bigger bill, not a data leak.

11. Deep dive 3: read-heavy caching and the CDN

Reads are 10 times writes, and pasted content is immutable per version. Immutable content is the best possible thing to cache: there is nothing to invalidate on update, because an update creates a new version. The layers, from the user inward:

  1. Browser cache. Cache-Control: public, max-age=300 for the paste page, longer for versioned raw URLs.
  2. CDN edge. Caches public and unlisted pastes by URL. A viral link is served by the edge with near-zero origin load (this is the "thundering herd" protection; enable request collapsing so that 10,000 simultaneous misses on one new URL produce one origin fetch; see Chapter 14).
  3. Redis. Read-through cache (Chapter 13) keyed by paste key holding metadata and, for content under 64 KB, the text. Larger content is not cached in Redis; it goes to object storage, which is fast enough and expensive to hold in memory. Eviction is LRU.
  4. Database replica and object store. The authoritative layers, only reached on a miss.

11.1 What may the CDN cache?

VisibilityCDNRedisNotes
PublicCache, TTL capped by expiryYesListed and indexable
UnlistedCache, TTL capped by expiry, X-Robots-Tag: noindexYesAnyone with the link; caching does not weaken this because the key is the credential
PrivateNever (Cache-Control: private, no-store)Metadata only, content fetched after the auth checkA shared cache must never answer an authorization question for someone else

The danger is a cache serving a private paste to a stranger. Two defences: the Read API sets private, no-store on every private response, and the CDN configuration also bypasses cache when an auth cookie or Authorization header is present, so a header mistake in one place cannot leak data. For private pastes whose blobs are fetched directly, hand out short-lived signed object-store URLs (valid 60 seconds) after the authorization check; the signature is the proof of authorization, and the bytes flow object store to client without passing through our servers.

11.2 Cost and hit ratios

If the CDN hit ratio for public pastes is 90 percent and Redis catches 90 percent of what is left, then of 10 million daily reads, about 1 million reach Redis and about 100,000 reach the database and object store. That is about 1 read per second at the origin. The database and object store are then sized for writes and durability, not reads. Hit ratios are lower for long-tail pastes (a paste read once is never a hit), which is why Redis uses a short TTL for pastes not yet proven hot, and why we do not pre-warm anything.

11.3 Syntax highlighting

Two options. Server-side highlighting (a library such as Pygments) produces ready HTML: it works without JavaScript and can be cached at the CDN, but costs CPU on the read path or needs a pre-render step. Client-side highlighting (a JavaScript library in the page) moves the work to the user's browser: the server returns raw text, which is cheaper and gives you the raw endpoint for free, though the first paint is plain text and very large pastes can freeze a browser tab.

I choose client-side highlighting by default, with the page and script bundle cached for a long time, and a hard cap (for example no highlighting over 200 KB, the user sees plain text with a "highlight anyway" button). Language is taken from the user's choice or from a cheap detector at write time (file extension in the title, shebang line, or a heuristic), stored in the metadata so reads never detect. If SEO for public pastes matters, pre-render highlighted HTML in a background worker after creation and store it as a second object; then the CDN serves that. This is a good example of moving CPU from the read path to the write path, where traffic is 10x lower.

12. Deep dive 4: dedup, versioning, and size limits

12.1 Deduplication by content hash

Many pastes are identical: the same stack trace pasted by many developers, the same install script, spam sent a million times. Because the blob's name is the SHA-256 of its (compressed or normalized) content, writing the same content twice produces the same object name, so the second write needs no storage at all.

Walkthrough. Three pastes sit on the left: aZ3kP9xQ version 1, Qm81LbT2 version 1 and aZ3kP9xQ version 2. 1. Each paste version computes the SHA-256 hash of its content and points at a row in the blobs table. 2. Two of them have identical text, so both point at the same blob row 9f2c...e1, whose ref_count is 2. 3. The third has different text and points at its own blob row, ref_count 1. 4. Each blob row maps to one Object in storage named by the hash. The figure shows that keys, owners, visibility and expiry stay per paste, and only the bytes are shared. The alternative it avoids is deduplicating at the key level, where one user deleting a paste would affect another. Point at ref_count: it is the number that decides when the blob may be removed. If the counts drift too low, you delete live content, so reconciliation matters.

What the design must get right:

  • Dedup is on content, not on identity. Two users pasting the same text get two keys and two metadata rows. Never dedupe at the key level (option B in section 9) or one user's delete or expiry would affect another's paste.
  • Reference counting. Insert increments the count inside the same transaction as the metadata insert; release (expiry, delete, new version replacing) decrements. A blob is deleted only when the count is zero and has stayed zero for the grace period. A periodic reconciliation job recounts references from paste_versions and fixes drift, because counters in a distributed system eventually drift after crashes.
  • Race on the first write. Two writers upload the same new content simultaneously: both PUT the same name with identical bytes, the second overwrite is harmless, and the blob row insert uses "insert if not exists". Idempotent writes make the race safe.
  • Privacy leak. Dedup can reveal that someone already stored a given file: if the server answers "already exists, skipped upload" to a client that sent only the hash, an attacker confirms a secret document is stored. Because our clients always upload full content and the server answers identically either way, this side channel does not exist. Never expose a "upload by hash" shortcut.
  • Hash collisions. SHA-256 collisions are not a practical concern. A shorter or weak hash (MD5) would be, because attackers can craft colliding inputs. Use SHA-256.
  • Expected savings. Honest estimate: on a general paste site perhaps 10 to 30 percent of bytes are duplicates, dominated by spam and logs. Real, not magical. It also gives a cheap abuse feature: when a blob hash is flagged as malicious, every paste referencing it can be blocked in one update.

12.2 Versioning

An edit never changes a blob. It writes a new blob (or reuses one if the text equals an earlier version), inserts paste_versions(key, n+1, hash), and updates pastes.current_version in one transaction. Optimistic concurrency avoids lost updates: the client sends the version it edited (If-Match: 3), and the update fails with 409 Conflict if the current version has moved on. The same URL /aZ3kP9xQ shows the latest version; /aZ3kP9xQ/v2 shows version 2.

Caching consequences: version-specific URLs are fully immutable, so they carry Cache-Control: public, max-age=31536000, immutable (still capped by the paste's expiry). The unversioned URL changes when a new version is created, so it has a short TTL (60 seconds) and the write path deletes the Redis entry and purges the CDN URL on edit. Storage cost of history is bounded by limiting versions per paste (say 50) and by diffs only if cost demands it; with a 1 MB cap, storing full versions is simpler and the dedup mechanism already removes unchanged repeats. An expired paste expires with all its versions.

12.3 Size limits

Size limits are a safety feature as well as a cost feature. Enforce at every layer, cheapest first:

  • Edge or load balancer: reject requests with Content-Length above 1 MB plus overhead, and stop reading the stream at that limit even if the header lies (chunked uploads).
  • API: validate again after decoding, count characters and bytes, reject invalid UTF-8 or null bytes (a hint of binary uploads).
  • Tiered limits: anonymous 512 KB, logged-in 1 MB, and, as an optional extension beyond the 1 MB base cap, paid or verified 10 MB (stored in multipart form). Limits also apply per day per account in bytes, not only in requests.
  • Reading side: highlighting cap and line length cap so that one pathological paste (a 1 MB single line) cannot hang browsers.

13. Private and public pastes: access control

Access rules are simple but must be enforced in one place, not scattered. A single function canRead(user, paste) is called by every read path (HTML, raw, JSON, versions, signed URL issuance). Its logic:

ConditionResult
status is deleted or blocked410 for everyone except moderators

Visibility public or unlistedAllow
Visibility private and caller is the ownerAllow
Visibility private and anyone else404 (not 403, so existence is not confirmed)

Unlisted pastes are protected by secrecy of the key (a capability URL). That works only if the key is random (section 9), if keys are not shown in public indexes, and if we send noindex and Referrer-Policy: no-referrer so the link is not leaked to third-party sites via the Referer header. Warn users that unlisted is not private: anyone who gets the link can see it, and the link may be forwarded or appear in logs and browser history.

Changing visibility after creation is an access-control event with cache consequences: public to private must purge CDN and Redis entries immediately (a TTL is not enough, because the owner expects the paste to vanish now). Account-level authentication and session handling follow Chapter 55: session cookies with HttpOnly and SameSite, API tokens hashed in the database, CSRF protection for state-changing calls. Anonymous deletion uses the delete_token, stored only as a hash in the row, like a password.

14. Security and abuse

A free, anonymous write endpoint that publishes text on your domain attracts spam, phishing pages, malware command-and-control configs, doxxing, and leaked credentials. Abuse is not a footnote; it decides whether the service survives. Layers of defence:

  • Rate limits (Chapter 16): per IP and per account on creates (for example 20 per hour anonymous, 200 per hour logged-in) and on reads of keys that return 404 (to stop scanning for valid keys). Token bucket in Redis. Add a proof-of-work or CAPTCHA step when an IP crosses a threshold.
  • Content scanning, asynchronously. After a successful create, an event goes to the abuse pipeline: signature and pattern checks (known malware hashes, private keys, credential formats like cloud access keys), URL reputation lookups, spam classifiers. Hits flip status to blocked and purge caches within seconds or minutes. Scanning is asynchronous so a slow scanner never blocks users; for highest-risk accounts (new, anonymous, flagged IP) it may be synchronous.
  • Hash blocklist. Because blobs are content-addressed, a blocklist of bad hashes rejects known-bad content at upload for free and blocks all existing duplicates.
  • Reports and moderation. A report endpoint feeds a review queue; several reports from independent users raise priority. Moderator actions are audited.
  • Stored XSS and content sniffing. A pasted HTML file served as text/html on your domain would run attacker scripts with your cookies. Always serve raw content as text/plain with nosniff, escape text when rendering the page, use a strict Content-Security-Policy, and serve raw content from a separate domain without cookies (for example raw.paste-usercontent.example), the standard defence.
  • Secrets and privacy. Detect and warn on pasted secrets, honor deletion requests and legal takedowns (including from backups and CDN, with a documented retention window), and log access to private pastes only with minimal fields. See Chapter 56.
  • Encryption. TLS in transit, server-side encryption at rest for object storage and database. Optional end-to-end encrypted pastes (the key stays in the URL fragment after # and is never sent to the server) trade away server-side scanning, highlighting and search; offer them as a clearly labelled mode.

15. Scaling, bottlenecks, and hot spots

  • Stateless API tier. Scale out behind the load balancer (Chapter 8, Chapter 9); auto-scale on CPU and request latency (Chapter 43).
  • Metadata DB. One primary plus read replicas serves the first several years (900 GB, 60 writes per second peak, a few hundred reads per second after caches). When it outgrows one machine, shard by hash of the key (Chapter 25); because every hot lookup is by key, the shard is trivially routed, and random keys spread load evenly. The only cross-shard queries are "my pastes" (solved with a secondary table keyed by owner_id, an index maintained asynchronously) and the expiry sweep (each shard sweeps itself).
  • Object storage. Effectively unlimited. The thing to watch is request-rate limits per prefix; hash-prefixed names spread load. Small-object overhead matters at billions of objects (per-request costs, minimum billable object size on some tiers); at extreme scale pack many small pastes into larger log-structured segment files, which is how some stores internally avoid the small-object cost.
  • Hot keys. A paste linked from a front page may take thousands of reads per second. The CDN absorbs it; if the CDN is bypassed, a single Redis key can still serve tens of thousands of reads per second, and an in-process LRU cache in each Read API instance removes even that. Request coalescing on a cache miss prevents a stampede.
  • Hot writes. View counters would turn each read into a database write on the same row. Instead buffer counts in Redis (INCR) and flush to the database every minute, accepting that the number is approximate (or take counts from CDN logs).
  • Recent and public lists. The "recent public pastes" feed is a time-ordered list of the last N public keys, kept in Redis as a capped list or sorted set (see Chapter 59), not computed by scanning the database.

Consistency decisions. Metadata is strongly consistent within the primary; reads from replicas and caches are eventually consistent, and that is acceptable because content is immutable, with two exceptions that get explicit handling: deletion/blocking (explicit purge) and visibility changes (explicit purge). Order of writes is blob, then metadata; order of deletes is metadata state change, then cache purge, then blob release. These orders are chosen so that any crash leaves garbage (cheap) rather than dangling pointers (user visible), and the principles echo Chapter 31: no distributed transaction across the database and the object store, only ordered, idempotent steps plus reconciliation.

Multi-region. Start with one primary region and a CDN. For disaster recovery, replicate the database asynchronously to a second region and enable cross-region replication on the bucket; the recovery point objective is the replication lag (seconds) and the failover is manual or automated per Chapter 41. Active-active writes are not worth it: key allocation, reference counts and expiry all become harder. If writers are global, route writes to the home region and let reads fan out through CDN and regional replicas (Chapter 26).

Combined, a 5-year footprint of 18 TB falls to a few TB and cost to well under a hundred dollars a month for storage. Check the claim with your own sizing rather than quoting it blindly.

18. Evolution and phasing

18.1 What to build first

  1. Phase 1 (week 1): app servers, one relational database, one bucket, random-key-plus-retry, expiry check on read, CDN in front, size limit, IP rate limits.
  2. Phase 2: Redis cache, background sweeper and blob GC, read replicas, delete tokens, user accounts and private pastes, basic abuse scanner and report queue.
  3. Phase 3: key service, dedup with reference counts, versioning, separate raw-content domain, cross-region replication.
  4. Phase 4: sharding, search, pre-rendered highlighting, tiered storage.

18.2 At 10x and 100x

At 10x (10 million pastes per day, 6,000 peak reads per second, 100 GB of new text per day): the CDN absorbs read growth; the database still fits on a big primary, but backups and replica rebuilds get painful, so shard metadata by key hash. Storage is 36 TB a year before compression and expiry; lifecycle tiering becomes important. The key pool needs a bigger refill rate and possibly per-shard pools. At 100x the sweeper must be sharded and partition-drop based, the abuse pipeline needs real machine learning and human moderation staffing, and object-store request costs (not bytes) dominate, which justifies packing small pastes into segment files.

18.3 Alternatives not chosen

  • Everything in one database. Simplest, but bloats the database and mixes hot and cold data. Fine under 100 GB.
  • Everything in a key-value store such as DynamoDB, including text. Works up to the item size limit (400 KB in DynamoDB), forces our 1 MB cap into another design, and costs more per GB than object storage.
  • Counter-based keys. Shorter, but enumerable, so a poor fit for unlisted pastes.
  • Client-side encryption by default. Strong privacy, but breaks scanning, highlighting on the server, and dedup.
  • Global search over pastes. A search engine (Chapter 22) fed from the queue, public pastes only; a feature with real abuse and cost implications, so deliberately later.

19. Interview Q&A

Why not just store the paste text in the database row?

You can, and for a small project you should. At 10 GB of new text per day the database would grow about 3.65 TB per year of cold, immutable bytes. That bloats backups, slows replica rebuilds, fills the buffer pool with data nobody reads, and costs several times more per GB than object storage. Splitting lets the database hold only a small metadata table that stays in memory, while object storage provides cheap, highly durable, effectively unlimited capacity for content. The cost of the split is two systems to keep consistent, which we handle with blob-first write ordering and garbage collection.

How do you guarantee two users never get the same key?

Uniqueness is enforced in two places. The key service guarantees it by moving keys from an unused table to an allocated table atomically, so a key is only ever handed to one writer. Independently, the primary key on the paste table rejects a duplicate insert, and if that ever triggers the writer takes a new key and alerts on the bug. Pure random generation with insert-and-retry also works at this scale, but pre-generation takes collision handling off the hot path and avoids a read-before-write race.

What happens to keys held by a crashed app server?

They are abandoned. Each server holds a batch of about 1,000 keys in memory; if it crashes the keys are never used. Out of 218 trillion possible keys, losing a few thousand per crash costs nothing, while trying to recover them would require tracking exactly which keys were consumed and invite double-allocation bugs. Simplicity wins: leak, never reuse.

How do you make expired pastes disappear and still keep the system correct if cleanup is delayed?

The read path compares expires_at to the current time on every request and returns 410 for anything expired, so correctness never depends on the cleanup job. Cache TTLs are capped at the remaining lifetime, so Redis and the CDN also stop serving the paste on time. A background sweeper then marks rows expired and releases blob references, and a garbage collector deletes unreferenced blobs after a grace period. If the sweeper falls behind, you pay for extra storage, but nobody sees expired data.

How would you stop a private paste from leaking through the CDN?

Private responses carry Cache-Control: private, no-store, and the CDN is configured to bypass cache for any request with an auth cookie or authorization header, so one misconfiguration cannot cause a leak. The authorization check happens on every request at the origin, and for large content the origin issues a short-lived signed URL to the blob only after that check. For not-found cases it returns 404 rather than 403 so existence of private keys is not revealed. When a paste changes from public to private, we explicitly purge the CDN and Redis rather than waiting for a TTL.

Is content deduplication worth it, and what are its pitfalls?

It saves storage on repeated content (spam, common logs, scripts), perhaps 10 to 30 percent on a general site, and gives a nice bonus: blocking one bad hash blocks every paste with that content. Pitfalls are reference counting (counts must be updated transactionally, reconciled periodically, and deletion must use a grace period or you lose data on a race), the privacy side channel if the API ever tells a client "this already exists" without full upload, and the need to keep identity and permissions per paste while only the bytes are shared. I would add it after the basic system works.

How do you handle edits without breaking caches?

Treat each version as an immutable blob and an immutable URL. A version-specific URL can be cached for a year because it never changes. The unversioned URL points to the latest version, so it gets a short TTL, and the edit operation deletes the Redis entry and purges the CDN URL. Concurrent editors are handled with optimistic concurrency: the client says which version it edited, and a mismatch returns 409 so no update is silently lost.

How would you add search over public pastes?

Publish a "paste created" event to a queue and have an indexing consumer write only public, non-blocked pastes into a search engine; deletes, expiry and blocks must emit events too so the index does not serve removed content. Index limited text (the first N KB) to control cost, and re-check status on result display. This is eventually consistent by design, and search is a separate, optional system, so its outage does not affect creating or reading pastes. The abuse risk is larger, since search makes bad content discoverable, so scanning must complete before indexing.

What if the interviewer says traffic is 100 times higher?

Reads are handled by CDN and cache scaling, which are horizontally scalable. The metadata database is sharded by key hash, which is easy because lookups are by key; "my pastes" goes through an owner-keyed secondary table. The key service pool is partitioned by prefix to remove the allocator as a bottleneck. Expiry becomes partition-drop based, and object-store request cost rather than bytes becomes the major bill, which pushes toward batching small pastes into segment files. Abuse handling needs automation and human moderation capacity, which is usually the real scaling limit.

How do you make sure a created paste is never lost?

The blob is written to a replicated object store first, and only after that succeeds is the metadata row committed, so a visible paste always has its content. The store keeps copies across availability zones, and we replicate the bucket and database to a second region for disaster recovery. A scheduled audit reads a sample of non-expired blobs and verifies their hash, and deletions go through a grace period and soft-delete retention to protect against counter bugs. Together these give the durability promise the requirements demand.

20. Connects to and recap

Recap

  • The system is small in QPS (about 12 writes and 116 reads per second average) but large in stored bytes (10 GB per day), so the design is about storage, keys, expiry, and abuse.
  • Split data by nature: metadata (about 500 B, queried, mutable) in a database; text (about 10 KB, immutable) in object storage, named by content hash.
  • Generate keys from a pre-generated pool handed out in batches: unique by construction, no collision handling on the hot path, unguessable, never reused.
  • Expiry is lazy for correctness (check on read, cap cache TTLs) and background for cost (sweeper, reference-counted blob garbage collection with a grace period).
  • Cache in layers: browser, CDN for public and unlisted pastes, Redis for metadata and small text; never cache private responses in shared caches.
  • Dedup by SHA-256 saves bytes and enables hash blocklists, but needs reference counting, reconciliation, and care about privacy side channels.
  • Versions are immutable; edits create new versions with optimistic concurrency; versioned URLs cache for a year.
  • Enforce size limits at every layer; serve raw text from a cookieless domain with nosniff; rate limit, scan asynchronously, and block by hash.
  • Order operations so that crashes leave garbage, not dangling pointers: blob first, then metadata; on delete, metadata state first, then purge, then blob release.
