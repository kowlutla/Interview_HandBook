HLD: Security, Observability and Operations interview questions

The cross-cutting topics of every system design interview: authentication and authorization, tokens, OAuth2/OIDC, encryption, common attacks, privacy and multi-tenancy; logs, metrics, traces, SLOs and incident response; CI/CD, rollouts, migrations, cost, capacity and infrastructure as code.

How to use this page

Interviewers rarely ask these topics on their own. They show up as follow-ups inside a design: "how do users log in?", "how would you know it is broken?", "how do you roll this out safely?". Click a question, answer it aloud first, then open the answer. Questions marked Basic are vocabulary, Intermediate are the usual follow-ups, Senior are trade-off and judgment questions. Scenario questions (orange) are the "your service sees X, what do you do" type. Where an incident is quoted, only the headline is given and details are hedged.

Authentication, sessions and tokens

What is the difference between authentication and authorization? Basic
Say this: "Authentication proves who you are; authorization decides what that identity may do. AuthN happens once at the edge and yields an identity; AuthZ runs on every request, next to the data, and must default to deny."

What each one is. Authentication (AuthN) is the act of verifying a claimed identity: you present a password, a passkey, a one-time code, a client certificate or a token, and the system checks it. The output is an identity, for example "user 42, tenant acme". Authorization (AuthZ) takes that identity plus an action and a resource ("user 42 wants to DELETE order 9001") and answers yes or no.

Why they are separate. Knowing who someone is says nothing about what they may touch. A hotel key card (authentication) opens your door, not every door; the card system then checks which rooms the card is allowed into (authorization). If you merge the two ideas you end up with systems where "logged in" quietly means "allowed to do anything".

AuthNAuthZ

A request walked through.

  1. Browser sends GET /orders/9001 with a token.
  2. The gateway verifies the token signature and expiry (AuthN). Result: user 42.
  3. The orders service loads order 9001 and sees owner_id = 77.
  4. It compares: 42 is not 77 and 42 has no "support" role, so it returns 403 (or 404 to avoid revealing the order exists).
Trap: authenticating at the gateway and then trusting every internal call. A valid login says nothing about whether user A may read user B's order. Always check ownership in the service that owns the data, otherwise you ship the classic IDOR (insecure direct object reference, also called broken object level authorization) bug, which is the number one API vulnerability in most surveys. A common interviewer follow-up: "why 401 for a missing login but 403 for a forbidden action?" Because 401 means "I do not know who you are, try credentials", 403 means "I know who you are and the answer is no".
Server-side sessions versus tokens: how do they differ and when do you pick each? Intermediate
Say this: "A session keeps the state on the server and hands the browser an opaque id; a token keeps the state in a signed document the client carries. Sessions revoke instantly, tokens verify without a lookup. I pick sessions for one web app, tokens for many services or third-party clients, and often combine short-lived tokens with a revocable server-side refresh record."

Why the question exists. HTTP is stateless: after the login request succeeds, the next request arrives with no memory of it. Something must carry "this is user 42" from request to request. There are two places to put that memory: on the server, or in the message.

Session mechanism.

  1. User posts credentials. Server creates a record in a store such as Redis: sess:9f3a... = {user:42, roles:[editor], created:...} with a TTL.
  2. Server replies Set-Cookie: sid=9f3a...; HttpOnly; Secure; SameSite=Lax. The id is random and meaningless on its own (an opaque handle).
  3. Each request carries the cookie; the server does a lookup (about one Redis round trip, often under a millisecond to a few milliseconds) and gets the user.
  4. Logout or "sign out everywhere" simply deletes records.

Token mechanism. The server signs a small document {sub:42, roles:[editor], exp:...}. The client sends it in an Authorization: Bearer header. Any service holding the verification key checks the signature locally. No store is needed on the hot path.

Session idSelf-contained token

Decision rule. One backend, browser clients, you want instant logout and "kill all sessions after a password change": sessions. Many independent services, mobile apps or partners that must verify identity without sharing a database: tokens. Most real systems blend them: a 10-minute access token for APIs plus a refresh token stored server-side that you can revoke.

Pitfalls. Sessions: the session store becomes a critical dependency and must be replicated, or you need sticky sessions. Tokens: teams choose them for "scalability" and then bolt on a denylist, ending up with the worst of both. Be honest about that trade-off in an interview.

What is a JWT and how is it structured? Basic
Say this: "A JWT is three base64url parts, header.payload.signature. The payload carries claims like who, issuer, audience and expiry. It is signed, so it cannot be altered, but it is only encoded, not encrypted, so anyone can read it."

What it is. A JSON Web Token is a compact, URL-safe string that carries claims (statements about a subject) and a signature proving who issued them. It exists so that a service can trust a statement such as "this is user 42, an editor, valid for 10 more minutes" without calling the service that issued it.

The three parts, each base64url-encoded and joined by dots:

  • Header: the signing algorithm and key id, e.g. {"alg":"RS256","kid":"2026-11"}. The kid tells the verifier which public key to use, which makes key rotation possible.
  • Payload (claims): sub (subject, the user), iss (issuer), aud (audience, who the token is meant for), exp (expiry), nbf (not before), iat (issued at), jti (unique id) plus custom claims such as roles or tenant id.
  • Signature: computed over base64(header) + "." + base64(payload). With HS256 it is an HMAC using one shared secret (everyone who can verify can also forge). With RS256 / ES256 it is a private-key signature; verifiers only need the public key, so they cannot mint tokens.

Tiny example. Decoded payload:

{"iss":"https://login.example.com","sub":"u-42","aud":"orders-api",
 "exp":1795000600,"scope":"orders:read","tenant":"acme"}

The API verifies the signature with the issuer's public key, then checks that iss is the expected issuer, aud is itself and exp is in the future.

Common misunderstanding. A standard signed JWT (technically a JWS) is encoded, not encrypted. Paste one into any decoder and you can read it. Never put secrets or sensitive personal data inside; if you truly need confidentiality use an encrypted JWT (JWE), or an opaque token instead. The signature proves integrity and origin, nothing more.

What interviewers probe. Why alg=none and algorithm-confusion attacks (an attacker switches RS256 to HS256 and signs with the public key as if it were a secret) are real: the verifier must pin the allowed algorithms and never trust the header's choice.

What are the pros and cons of JWTs? Intermediate
Say this: "JWTs trade easy revocation for easy verification. They scale because no lookup is needed, but they stay valid until expiry and their claims go stale, so I keep them short-lived and verify them strictly."

Why people use them. In a microservice system, calling a central session store on every request from every service adds latency and a shared failure point. A signed token lets each service verify the caller locally using a public key it fetched once.

ProsCons
Stateless verification: no lookup, scales horizontally, no shared session storeCannot be revoked before expiry without adding state back
Carries claims, so services avoid a call to the user serviceClaims go stale: role removed, but the token still says admin until it expires
Works across domains, services and mobile clientsLarger than a session id, sent on every request (a token with many roles can reach several KB and hit header size limits)
Standard, many libraries; with public-key signing the verifiers hold no secretEasy to misuse: alg=none, algorithm confusion, missing aud/exp checks, storing in localStorage

Worked example of staleness. At 10:00 an admin is demoted to viewer. Their token was issued at 09:55 with a 60-minute life and still says role: admin. Until 10:55 every service that trusts the token lets them act as admin. With a 10-minute life the window is at most 10 minutes. This is the practical reason for short expiry.

When not to use JWTs. A single monolith with a browser UI gains almost nothing over a plain server-side session, and loses easy logout. "JWT everywhere" is a fashion, not a requirement.

Mitigations to name. Short expiry (5 to 15 minutes) plus refresh tokens, strict validation, small claim sets (put an id and fetch details when needed), and a TTL-bounded denylist for emergencies.

How do you revoke or invalidate a JWT? Senior
Say this: "A pure stateless JWT cannot be revoked, so I either shorten its life or add a little state. Default design: short-lived access token, rotating refresh token I can revoke, and a small TTL-bounded denylist for emergencies like a stolen device."

The core problem. Verification is a local signature check. The issuer is not consulted, so it does not learn that you want the token dead. Every revocation scheme therefore either shrinks the time window or reintroduces a lookup somewhere.

  1. Short expiry plus refresh token (the default). Access token lives about 10 minutes. The long-lived refresh token is stored server-side as a database row. Revoke the row and the user is locked out within at most 10 minutes. Cost: nothing extra on the hot path.
  2. Denylist. Keep revoked token ids (jti) in Redis with a TTL equal to each token's remaining life. Because tokens expire anyway, entries vanish and the list stays small. Cost: a lookup per request, which gives up part of the stateless benefit.
  3. "Not valid before" per user. Store user:42:min_iat = T. Reject any token whose iat is before T. One tiny cached read revokes all of a user's tokens ("log out everywhere", password changed).
  4. Token versioning. A ver claim compared with a per-user counter; bump the counter to invalidate. Same idea, different encoding.
  5. Key rotation. Change the signing key so every old token fails. Nuclear option for a signing-key compromise, logs everybody out.
  6. Opaque tokens with introspection (RFC 7662). The token is a random string and each resource server asks the identity provider "is this active?". Full control, one extra hop; cache answers for seconds to bound load.

Choosing. Consumer app: option 1, plus 3 for "sign out everywhere". High-security (banking, admin consoles): opaque tokens or very short JWTs plus introspection on sensitive actions. Fan-out to hundreds of services: keep JWTs and rely on short expiry, since a denylist would need to reach all of them.

Pitfall. Revoking only the access token while leaving the refresh token alive: the attacker simply mints a new one. Always revoke at the refresh/session level first.

Where should a browser app store tokens, and why? Intermediate
Say this: "Not in localStorage. Keep the long-lived credential in an HttpOnly, Secure, SameSite cookie so scripts cannot read it, and keep any access token in memory only. Accept that cookies bring CSRF and defend against it."

The threat model. Two attacks matter in the browser. XSS (attacker script runs in your page) can read anything JavaScript can read. CSRF (a foreign site triggers requests to yours) abuses credentials the browser attaches automatically. Each storage choice favours one defence and exposes you to the other.

StorageXSSCSRF
localStorage / sessionStorageToken readable by any script: one XSS bug leaks it, and the attacker can use it from their own machineNot sent automatically, so immune
In-memory variableHarder to steal (gone on refresh, not at a known key) but a running script can still call your API as the userImmune
HttpOnly + Secure + SameSite cookieScript cannot read it, so it cannot be exfiltrated; the attacker can still make requests from inside the page while it is openExposed; mitigated by SameSite and CSRF tokens

A pattern that works.

  1. Login sets the refresh/session credential as an HttpOnly; Secure; SameSite=Lax cookie scoped to the auth path.
  2. The SPA calls a refresh endpoint at startup and gets a 5-minute access token in the JSON body, held in a JS variable.
  3. API calls use Authorization: Bearer from memory; a page reload simply refreshes again.

Mobile apps are different: use the OS secure store (iOS Keychain, Android Keystore), never plain preferences. Another strong option is the backend-for-frontend pattern, where a thin server holds the tokens and the browser only ever has a session cookie.

Pitfall. Believing HttpOnly "solves XSS". It only protects the cookie value; an XSS bug still lets the attacker act as the user, so you still need output encoding and a strict Content Security Policy.

What is refresh token rotation and why use it? Senior
Say this: "Every refresh returns a new refresh token and kills the old one. If an old one is ever presented again, someone has a copy, so the server revokes the whole family and forces re-login. It turns silent theft of a long-lived credential into a detectable event."

Why it exists. A refresh token lives for days or weeks, so a stolen one is a long-lived key. Without rotation the thief and the real user can both refresh forever and nobody notices. Rotation makes the two collide.

How it works, with a timeline.

  1. Login issues access token A1 and refresh token R1 (family F).
  2. Client later sends R1; server marks R1 as used and returns A2 and R2.
  3. An attacker who had copied R1 sends it. Server sees R1 already used, concludes it leaked, and revokes family F including R2.
  4. Both the attacker and the real user must log in again; the server logs the event and can alert the user.

The order matters: whichever party presents the old token second triggers the alarm. It does not tell you which one was the thief, but it ends the session for both, which is the safe outcome.

Real-world wrinkle: the race. A flaky network can make the genuine client send R1, lose the response, then retry R1 and get flagged as an attacker. Remedies: a short grace window (for example 10 to 30 seconds) in which the previous token is still accepted and returns the same successor, or storing the last successor so an identical retry is idempotent. Multi-tab browsers cause the same race, so coordinate refreshes through one tab or a lock.

Other hardening. Bind tokens to the client (device key, DPoP, mTLS-bound tokens), set an absolute session lifetime plus an idle timeout, and store only a hash of each refresh token server-side so a database leak does not hand out valid ones. OAuth 2.1 and current browser guidance recommend rotation for public clients such as SPAs and mobile apps.

How should passwords be stored? Why not SHA-256 or encryption? Basic
Say this: "Store a slow, salted, adaptive hash: argon2id preferably, or bcrypt or scrypt. Not encryption, because it is reversible, and not plain SHA-256, because it is far too fast to guess against."

The goal. Assume your database will leak one day. The stored value should make it as expensive as possible for the attacker to recover the original passwords, which many users reuse on other sites.

Why not encrypt. Encryption is reversible by design. If the key leaks (and it sits near the app that must use it), every password leaks at once. You never need to read a password back, only to check a guess, and a one-way hash does exactly that.

Why not SHA-256. General-purpose hashes are built to be fast. A single modern GPU can try billions of SHA-256 guesses per second, so most human-chosen passwords fall in minutes. A password hash is designed to be slow and, for argon2 and scrypt, memory-hungry, which blunts GPUs and custom hardware. Each guess costs the attacker tens to hundreds of milliseconds and real RAM.

The ingredients.

  • Salt: a unique random value per user, stored next to the hash. Two users with password "hunter2" get different hashes and precomputed rainbow tables are useless. The salt is not secret.
  • Work factor: a tunable cost (bcrypt cost, argon2 memory/iterations/parallelism). Raise it as hardware improves; store parameters in the hash string so old hashes keep verifying and can be upgraded at next login.
  • Pepper (optional): a secret value kept outside the database (HSM or secrets manager) mixed into the hash so a DB-only leak is not enough.

Example stored value: $argon2id$v=19$m=65536,t=3,p=4$<salt>$<hash> where m is memory in KiB, t iterations, p parallelism.

Operational points. Tune the cost so one verification takes roughly 100 to 500 ms on your real servers. Because hashing is deliberately expensive, login is itself a CPU denial-of-service target, so rate limit it. Also screen new passwords against breached-password lists, offer MFA or passkeys, and compare hashes in constant time. A frequent interview probe: "bcrypt truncates at 72 bytes", so pre-hash or use argon2id for long passphrases.

What is MFA and what are passkeys? Intermediate
Say this: "MFA needs two different kinds of proof: know, have, are. Passkeys go further by replacing the password with a per-site key pair, so there is no shared secret to phish or leak."

Why MFA exists. Passwords get phished, reused and leaked. A second factor means a stolen password alone is not enough. The factors must be of different types: something you know (password, PIN), have (phone, hardware key) or are (fingerprint, face). Two passwords is not MFA.

Strength ladder, weakest to strongest.

FactorWeakness
SMS codeSIM swapping, SS7 interception, easily phished
TOTP app (6 digits changing every 30 s)Phishable by a real-time proxy that relays the code to the real site
Push approval with number matchingPrompt-bombing fatigue; number matching reduces it
FIDO2/WebAuthn hardware key or passkeyPhishing resistant; main residual risk is account recovery

How a passkey works.

  1. Registration: the device creates a key pair for this site. The private key stays in secure hardware (TPM, Secure Enclave) and is unlocked by biometric or PIN; the server stores only the public key.
  2. Login: the server sends a random challenge. The device signs it with the private key, including the site's origin in the signed data.
  3. The server verifies the signature with the stored public key.

Because the origin is part of what is signed, a look-alike phishing domain gets a signature that is useless on the real site. Nothing in your database can be replayed, so a leak exposes no credentials. Synced passkeys (iCloud Keychain, Google Password Manager) add convenience; device-bound keys add assurance.

Pitfalls. The weakest link becomes recovery: if "forgot password" is an email link, an attacker simply uses that path. Design recovery with equal care, offer backup codes, and use step-up authentication (re-prompt MFA) before sensitive actions such as changing email or payout details.

When do you use API keys, and how do you design them safely? Intermediate
Say this: "API keys identify a calling application, not a person. I generate them from a secure random source, show them once, store only a hash plus a prefix, send them in a header, scope and rotate them. For delegated user access I would use OAuth2 instead."

What it is and when it fits. An API key is a long random string that a developer attaches to requests so the platform knows which app or project is calling. It suits server-to-server calls, developer platforms, simple metering and per-key rate limits, where there is no end user to log in.

How to design it, step by step.

  1. Generate at least 128 bits from a cryptographically secure random source, for example sk_live_ab12cd34.... Include a readable prefix that identifies the key type and environment.
  2. Show it once. After creation the user can never see it again, exactly like a password.
  3. Store only a hash. SHA-256 is acceptable here (unlike passwords) because the key is high-entropy random, so brute force is infeasible and the hash can be indexed for fast lookup. Keep the first 6 to 8 characters in clear for support and for finding the record.
  4. Transport in a header (Authorization or X-API-Key), never in a URL: URLs end up in access logs, browser history and referrer headers.
  5. Scope and limit: read-only versus read-write keys, per-resource scopes, per-key rate limits and quotas.
  6. Lifecycle: several keys per account so you can rotate with overlap, optional expiry, instant revoke, last-used timestamp, and secret scanning (publish your key format so GitHub-style scanners can detect and report leaks).

Limits. A key is a bearer secret: anyone holding it is the app. It carries no user identity, no standard expiry and coarse permissions. For acting on behalf of a user with consent and limited scopes, use OAuth2; for strong service identity, use mTLS or workload identity. Never embed a powerful key in a mobile app or a browser bundle, because users can extract it.

What is mTLS and where is it used? Intermediate
Say this: "In mutual TLS both sides present certificates, so each end cryptographically knows who the other is. It is the standard way to give microservices a workload identity, along with encryption, without passing tokens around."

From scratch. In ordinary HTTPS only the server proves itself: your browser checks the site's certificate. The server has no cryptographic idea who the client is and relies on a password or token afterwards. In mutual TLS (mTLS) the server also requests a certificate from the client and verifies it against a trusted certificate authority (CA). The handshake only completes if both certificates are valid.

Why use it. Inside a cluster, "which service is calling me?" has no good answer from an IP address, since IPs are reused and spoofable. A certificate gives each workload an identity (for example the SPIFFE id spiffe://prod/ns/shop/sa/orders) that cannot be forged without the private key.

How it looks in a service mesh.

  1. The mesh control plane (Istio, Linkerd) acts as a CA and issues each pod a short-lived certificate, often valid for hours.
  2. A sidecar proxy handles TLS for the app, so application code is unchanged.
  3. When orders calls payments, the sidecars do the mutual handshake; payments' sidecar knows the caller is "orders".
  4. An authorization policy then says "only orders may call POST /charge".

Other uses: B2B APIs where partners hold client certificates, IoT devices, and database or Kafka connections.

Costs and pitfalls. You must run a CA and automate issuance and rotation, because manual certificates expire and cause outages (expired certificates are among the most common self-inflicted incidents, so monitor expiry). Debugging is harder because traffic is opaque. And mTLS proves which service is calling, not which end user it acts for, nor what it may do: you still need authorization and usually a propagated user token.

OAuth2, OIDC and SSO

What problem does OAuth2 solve, in plain words? Basic
Say this: "OAuth2 lets a user give an app limited, revocable access to their data on another service without giving the app their password. The app gets an access token with specific scopes. It is about delegated authorization, not login."

The problem before OAuth. Imagine a photo-printing app that wants your photos from a cloud drive. In the old days it asked for your drive username and password. That meant the printing app could do anything as you, could keep the password forever, and the only way to stop it was to change your password, breaking every other app.

What OAuth2 does instead.

  1. The printing app sends you to the drive's own login page (it never sees your password).
  2. You log in there and see a consent screen: "Printing app wants to read your photos".
  3. You approve; the drive gives the app an access token limited to the photos.read scope and a short life.
  4. The app calls the drive's API with that token. You can revoke the grant at any time without touching your password.

The four roles.

RoleIn the example
Resource ownerYou
ClientThe printing app
Authorization serverThe drive's login and token service (issues tokens)
Resource serverThe drive's photo API (accepts tokens)

Key vocabulary. A scope is a named permission (photos.read). An access token is the short-lived credential presented to the API. A refresh token is a longer-lived credential used only to get new access tokens.

Trap: OAuth2 by itself is not authentication. An access token says "the bearer may do X", not "this person is user 42". Using it as a login proof leads to account takeover bugs (the token could have been issued to a different app). That gap is what OpenID Connect fills with the ID token.
Walk through the Authorization Code flow with PKCE. Senior
Say this: "The app redirects the user to the authorization server with a hashed secret (the PKCE challenge). After login the browser comes back with a one-time code. The app exchanges the code plus the original secret, over a back channel, for tokens. Intercepting the code is useless without the secret."

Why a code at all? The browser address bar, history and redirects are exposed places. Tokens should not travel through them. So the authorization server first returns a short-lived, one-time authorization code via the browser (front channel), and the client trades it for tokens on a direct server-to-server style request (back channel).

Why PKCE (pronounced "pixy"). A public client (mobile app, SPA) cannot keep a client secret, so a malicious app on the same phone could register the same redirect scheme, steal the code and trade it for tokens. PKCE (Proof Key for Code Exchange) binds the code to the app that started the flow.

  1. Prepare. Client generates a random code_verifier (43 to 128 characters) and computes code_challenge = BASE64URL(SHA256(verifier)). It also creates a random state.
  2. Authorize request. Redirect to /authorize?response_type=code&client_id=...&redirect_uri=...&scope=openid orders&code_challenge=...&code_challenge_method=S256&state=.... The server remembers the challenge.
  3. Login and consent. The user authenticates at the authorization server (MFA, SSO happen here) and approves the scopes.
  4. Redirect back to redirect_uri?code=abc&state=.... The client checks that state matches what it sent.
  5. Token request. Client POSTs code, redirect_uri and the original code_verifier to the token endpoint. The server hashes the verifier and compares it with the stored challenge. Match, and it returns the access token (plus refresh token, plus ID token if OIDC).
  6. Call the API with Authorization: Bearer <access token>.

What each protection stops. state defeats CSRF on the callback (an attacker cannot make your browser finish a login the attacker started). PKCE defeats code interception. Exact redirect_uri matching defeats code redirection to an attacker's site. Codes are single-use and live about a minute.

Current guidance. PKCE is recommended for all clients, including confidential server-side ones, and is mandatory in OAuth 2.1 drafts. Confidential clients additionally authenticate at the token endpoint with a secret or private-key JWT.

Which OAuth2 grant types exist and which would you avoid? Intermediate
Say this: "Authorization Code with PKCE for anything with a user, Client Credentials for service to service, Device Code for input-limited devices. I would avoid Implicit and the Password grant; both are deprecated."

What a "grant" is. A grant is the recipe a client uses to obtain an access token. Different situations need different recipes depending on whether a user is present, whether the client can keep a secret, and whether it has a browser.

GrantUseNote
Authorization Code + PKCEWeb, mobile, SPA with a userThe default; tokens never pass through the browser URL
Client CredentialsService to service, no userClient authenticates with secret, private-key JWT or mTLS; token represents the app itself
Device CodeTVs, CLIs, consoles without a good browserDevice shows a code; user approves on a phone or laptop
Refresh TokenGet new access tokens quietlyRotate and bind to client
ImplicitOld SPAsAvoid: the access token returned in the URL fragment leaks via history and referrers; replaced by Code + PKCE
Password (ROPC)LegacyAvoid: the app handles the user's password, defeating the point of OAuth, and cannot support MFA

Examples. A nightly billing job calling the invoice API uses Client Credentials: it posts its client id and secret and gets a token with scope invoices:write; there is no user. A smart TV app uses Device Code: the TV shows "go to example.com/activate and type K7QW-92XA", you do so on your phone, and the TV polls until approved.

Decision rule. Is a human involved? If yes, Code + PKCE (Device Code if there is no browser). If no, Client Credentials. Pitfall: using Client Credentials tokens for user-specific data loses the end user's identity and permissions; propagate the user via token exchange instead.

What does OpenID Connect add on top of OAuth2? Intermediate
Say this: "OIDC adds authentication to OAuth2. With the openid scope you also get an ID token, a signed JWT that says who logged in, how and when, plus a standard userinfo endpoint and a discovery document. The ID token is for the client; the access token is for the API."

The gap it fills. OAuth2 gives an app permission to call an API but deliberately says nothing about the user's identity. Early "login with X" implementations guessed at identity by calling a profile API with the access token, each provider doing it differently and with security bugs. OIDC standardised it.

What you get.

  • ID token: a JWT with iss (who issued), sub (stable user id at that issuer), aud (your client id), exp, iat, nonce (binds it to your login attempt), often auth_time, amr (how the user authenticated) and, with the profile/email scopes, name and email.
  • UserInfo endpoint: call it with the access token to get more claims.
  • Discovery: /.well-known/openid-configuration lists the authorize, token and JWKS URLs, so clients configure themselves from one issuer URL. The JWKS document publishes the public signing keys.
  • Standard scopes: openid (required), profile, email, offline_access (refresh token).

Client duties on receiving the ID token: verify signature (from JWKS), iss, aud equals your client id, exp, and nonce equals what you sent. Then identify the user by the pair (iss, sub), not by email, because emails can change or be reassigned.

Rule of thumb and trap. The ID token tells the client who the user is. Do not send it to APIs as a credential; its audience is the client, not the API. APIs take the access token, whose audience is the API.

What is SSO and how does it work? Compare SAML and OIDC. Intermediate
Say this: "SSO means log in once at a central identity provider and every connected app trusts its assertion. The IdP keeps its own session, so when a second app redirects the user there, they bounce straight back signed in. SAML is the XML enterprise standard; OIDC is the modern JSON one."

Why it exists. Without SSO, each of 40 company apps stores its own passwords: users reuse passwords, IT cannot enforce MFA uniformly and offboarding means visiting 40 admin consoles. SSO centralises authentication in one identity provider (IdP) such as Okta, Entra ID or Google; apps are service providers / relying parties.

The mechanism, with a timeline.

  1. User opens App A. No local session, so App A redirects to the IdP with an authentication request.
  2. User logs in at the IdP (with MFA). The IdP creates its own session cookie and returns a signed assertion (SAML) or ID token (OIDC) to App A.
  3. App A validates it and creates its own local session.
  4. Later the user opens App B. App B redirects to the IdP; the IdP sees its live session cookie and immediately returns a fresh assertion with no prompt. That invisible bounce is the "single sign-on".

How should an API validate an incoming access token? Intermediate
Say this: "Verify the signature with pinned algorithms and the issuer's cached keys, then check issuer, audience, expiry and scopes, and finally the object-level permission. If the token is opaque, introspect it and cache briefly."

Why every check matters. A signature only proves that some trusted issuer signed something. Without the other checks an attacker can replay a token meant for a different API, an expired one, or one with too few scopes.

  1. Signature. For a JWT, fetch the issuer's JWKS once, cache it, and pick the key by kid. Pin the allowed algorithm (for example RS256 only); reject none and never let the token header pick HS256 against a public key. If the kid is unknown, refresh JWKS once (rate limited) before rejecting, which handles key rotation.
  2. Issuer: iss must equal your trusted issuer URL exactly.
  3. Audience: aud must name this API. This stops a token issued for the reporting API being replayed against the payments API.
  4. Time: exp in the future, nbf not in the future, allowing a small clock skew (30 to 60 seconds).
  5. Scopes or roles: the endpoint needs orders:write; does the token carry it?
  6. Object-level check: does user 42 own order 9001? Tokens cannot answer this.
  7. Opaque token: call the introspection endpoint and cache the answer for a few seconds to bound load on the IdP.

Where it runs. Often at the API gateway for coarse checks (so bad tokens never reach services), with services re-checking fine-grained rules. Pass identity inward as a signed internal header or a down-scoped token, not by forwarding the user's raw token to every hop, because every service then holds a credential that could be abused elsewhere (the confused-deputy risk).

How do microservices authenticate to each other and carry the end user's identity? Senior
Say this: "Two separate questions: which service is calling, answered by mTLS or cloud workload identity, and on whose behalf, answered by a short-lived, narrowly scoped user token or signed assertion. Then each service authorizes both. No shared static API key, no 'inside the network is trusted'."

Why two layers. When the orders service calls payments, payments needs to know (a) it really is orders and not a compromised neighbour, and (b) which customer triggered the call and what that customer may do. Mixing the two into one credential causes either over-trust or lost user context.

  • Workload identity ("who is the service"): mTLS with per-service certificates from a mesh (SPIFFE ids), or cloud IAM roles and Kubernetes service account tokens. Certificates are short-lived and rotated automatically.
  • User context ("on whose behalf"): the edge validates the user's token once, then each hop carries either a signed internal assertion (X-User-Id inside a JWT signed by the gateway) or a token obtained via OAuth token exchange (RFC 8693) with narrower audience and scope and short life. Payments sees "orders, acting for user 42, for scope charge, valid 60 s".
  • Authorization at each service: a policy such as "orders may call payments charge only", enforced by mesh authorization policies, plus the user-permission check in the owning service.

Example flow. Browser to gateway (user token, validated), gateway to orders (mTLS plus internal token for user 42), orders to payments (mTLS as "orders" plus exchanged token, audience payments). If the notification service is compromised, it has no certificate identity allowed to call payments and no token with that audience.

Anti-patterns. A shared static internal key cannot be traced to a caller, scoped or rotated cheaply. Trusting a plain X-User-Id header without signing lets any internal caller impersonate anyone. Forwarding the original user token everywhere gives every service the user's full power.

Authorization models, secrets and zero trust

Compare RBAC and ABAC. When would you choose each? Intermediate
Say this: "RBAC grants permissions through roles: simple and auditable but coarse. ABAC evaluates attributes of user, resource and context: expressive but harder to audit. I start with RBAC, add attribute or relationship checks for object-level rules, and use ReBAC for sharing models."

RBAC (role-based access control). Users are assigned roles (admin, editor, viewer); roles hold permissions (article:publish). To answer "may Priya publish?" you look up her roles and check them. It is easy to explain to auditors: "who can publish? everyone with the editor role".

ABAC (attribute-based access control). A policy is evaluated over attributes: of the subject (department, clearance), resource (owner, classification, hospital), action and environment (time, IP, device). Example: a doctor may read a record if record.hospital == user.hospital and the user is on shift and the device is managed. You could never express that with a handful of roles.

RBACABAC
ExpressivenessCoarse, staticFine-grained, contextual
Failure modeRole explosion (editor-team-A, editor-team-B, ...)Policy sprawl; hard to answer "who can access X?"
PerformanceSimple lookupPolicy engine evaluation (OPA, Cedar), usually microseconds to milliseconds
Best forInternal tools, capability-level accessData-dependent, regulated, multi-tenant rules

ReBAC (relationship-based). Permissions follow a graph: "user is editor of folder; document is in folder; therefore user can edit document". This is the Google Zanzibar model (used by Drive, and by open implementations such as SpiceDB or OpenFGA) and fits sharing and nested-ownership designs where roles per object would be impossible.

Decision rule. Few stable capabilities: RBAC. Rules depend on data or context, or role count is exploding: add ABAC conditions on top. Documents, folders, orgs and teams with inheritance and sharing: ReBAC. In practice: RBAC for coarse capability ("may use the billing module"), attribute or relationship checks for the object ("this invoice belongs to your tenant").

Pitfall. Hard-coding if (role == "admin") across the codebase makes policy impossible to review. Centralise decisions behind one function or policy engine so rules can be changed and audited in one place.

Where should authorization logic live: gateway, each service, or a central service? Senior
Say this: "Layered: the gateway does authentication and coarse scope checks, a shared policy library or sidecar makes decisions with one policy language, and the service owning the data enforces object-level rules. Default deny, fail closed, log decisions."

Why not just one place? Each location sees different information. The gateway sees the route and token but not that order 9001 belongs to tenant B. The service sees the data but, written ad hoc by ten teams, tends to implement checks ten different ways. A central service has consistency but adds latency and a new critical dependency.

LocationGood atWeak at
GatewayToken validity, scopes, rate limits; uniform and cheap; blocks bad traffic earlyCannot know object ownership; can be bypassed if internal calls skip it

How to make central policy safe. Do not make a network call per decision on the hot path. Run the engine as an embedded library or local sidecar, push policy bundles and the relevant data to it, and cache. If the policy store is unreachable, keep serving with the last known policy and fail closed for decisions it cannot compute.

Balanced design.

  1. Gateway: validate token, check scope for the route, rate limit.
  2. Service: call the shared policy library with (subject, action, resource attributes).
  3. Data layer: row-level filters (tenant id, owner) as the final backstop.

Rules to state. Default deny. Enforce on the server, never rely on a hidden button. Decisions must be logged (who, what, result, policy version) to support audits and incident reviews. A pitfall: authorization checked in the UI layer or a list endpoint but forgotten on the "get by id" or export endpoint.

How do you manage secrets (passwords, API keys, certificates)? Intermediate
Say this: "Secrets live in a dedicated manager, never in git, images or logs. Workloads authenticate with platform identity, get only what they need, ideally short-lived dynamic credentials, and everything rotates and is audited. Leaked means rotated, not just deleted."

Why it is hard. A secret is only useful if the running app can read it, yet it must be unreadable to everyone and everything else: developers, CI logs, container layers, backups, crash dumps. Hard-coded or committed secrets are the most common breach cause because git history, Docker image layers and logs are copied widely and kept forever.

  • Store: a secrets manager (HashiCorp Vault, AWS Secrets Manager, GCP Secret Manager, Azure Key Vault), encrypted with KMS. Kubernetes Secrets are only base64-encoded unless you enable encryption at rest and restrict RBAC; many teams sync from an external manager (External Secrets, CSI driver).
  • Access: the workload proves who it is with platform identity (IAM role, Kubernetes service account token) and is granted only its own paths, each read audited.
  • Dynamic credentials: instead of a long-lived database password, the app asks Vault, which creates a database user valid for, say, one hour and deletes it afterwards. A leak then has a tiny useful life, and each instance has a distinct identity for tracing.
  • Rotate: automate it and support two valid versions during the changeover (create new, update consumers, retire old) so there is no downtime.
  • Detect: pre-commit hooks and CI secret scanning; managed scanners on the hosting platform; alerting on unusual secret access.

Example: rotating a DB password without downtime. Create a second DB user, store it as version N+1 in the manager, have the app reload it (watch or restart in a rolling fashion), confirm no traffic uses user N, then drop user N.

Trap: the "secret zero" problem: something must authenticate to the vault first. Answer: do not store a bootstrap password; use platform identity (cloud instance role, Kubernetes service account, workload attestation). Another trap: deleting the commit that contained a key. Treat any exposed secret as compromised and rotate it.
What is zero trust? Intermediate
Say this: "Never trust, always verify. Instead of a hard perimeter with a soft, trusted inside, assume the network is hostile and authorize every request using strong identity of both user and workload, least privilege and context."

The old model and why it failed. The classic design was a castle and moat: a firewall and VPN at the edge, and anything inside the network was trusted. Once an attacker got a foothold (phished laptop, compromised dependency) they could move laterally to databases and internal tools because nothing inside checked anything. Remote work, cloud and SaaS also dissolved the perimeter: where is "inside" now?

Core ideas.

  • Verify explicitly: every request is authenticated and authorized using identity, device health and context (location, risk), not network location.
  • Strong identity everywhere: MFA and device posture for users; mTLS or workload identity for services.
  • Least privilege and short-lived credentials: access is just-in-time and expires.
  • Micro-segmentation: network policies allow only the needed service-to-service paths, so a compromised pod cannot reach the database.
  • Encrypt everything, including internal traffic; log and monitor continuously.
  • Assume breach: design to limit blast radius and detect lateral movement.

Concrete example. Replace the corporate VPN with an identity-aware proxy: an engineer opens the internal wiki; the proxy checks their SSO session, MFA, that their laptop is managed and patched, and that they belong to the right group, then allows that app only. Being "on the network" grants nothing.

Honest framing for interviews. Zero trust is a direction and a set of principles, not a product you buy. It costs effort (certificate automation, policy management, more latency and failure points), so adopt it incrementally starting with the most sensitive systems.

What is least privilege and how do you apply it to a cloud service? Basic
Say this: "Every identity gets only the permissions it needs, for only as long as it needs them. That limits the damage when any one credential or service is compromised."

Why. Breaches are inevitable at some level; what you control is the blast radius. A thumbnail worker that can read every bucket and delete databases turns a small bug into a catastrophe. The same worker with a narrow policy turns it into a minor incident.

How to apply it.

  • Per-workload roles: the thumbnail worker may s3:GetObject on uploads/* and s3:PutObject on thumbnails/*, nothing else. No wildcard actions or resources.
  • Humans: no standing admin. Use time-boxed, approved, audited elevation (break-glass or just-in-time access) and separate accounts for admin work.
  • Databases: separate users for the app (DML only), migrations (DDL), and analytics (read replica, maybe masked columns). The app account cannot drop tables.
  • Separate accounts or projects for production, staging and sandboxes, with explicit cross-account roles.
  • Review and prune: use access analyzers and last-used data to remove permissions unused for 90 days; start narrow and widen on demand rather than start broad.
  • Network: default-deny security groups and network policies.

Pitfall. Teams give *:* "temporarily" to unblock a deploy and never revisit it. Policy-as-code checks in CI that reject wildcard grants catch this early.

Encryption and key management

Explain encryption in transit versus at rest and what each protects against. Basic
Say this: "In transit (TLS) protects data moving across a network from eavesdropping and tampering. At rest protects stored data from stolen disks, backups and snapshots. Neither helps if the running app or its credentials are compromised, so sensitive fields may need application-level encryption."

Two different threats. Data exists in two states with different attackers. While moving between a browser, load balancer, service and database, someone on the path (a compromised router, a shared Wi-Fi, a neighbour in the cloud network) could read or alter it. While sitting on disk, the risk is someone obtaining the storage itself: a lost drive, a leaked snapshot, a misconfigured bucket, or a curious infrastructure operator.

In transitAt rest
HowTLS (HTTPS), mTLS, TLS to the database and message brokerVolume/disk encryption, database TDE, object-store server-side encryption; typically AES-256
Protects againstEavesdropping and tampering on the networkStolen disks and backups, exposed snapshots, an operator reading raw storage
Does not protect againstA compromised endpointA compromised running app (it reads decrypted data), SQL injection, stolen application credentials

Why "at rest" is weaker than it sounds. With transparent disk or database encryption, the database decrypts for any authenticated query. If an attacker steals the app's credentials and runs SELECT, they get plaintext. At rest encryption defends the media, not the application.

Going further.

  • Application-level (field) encryption: encrypt card numbers or national ids in the app before writing, so DBAs, backups and a leaked dump see only ciphertext. Cost: you cannot query or index those fields normally (use deterministic encryption or blind indexes for equality search, with trade-offs).
  • End-to-end encryption: only the users' devices hold keys, so even the provider cannot read content. Cost: no server-side search, spam scanning or easy account recovery.

Decision rule. Always do both transit and rest as the baseline (they are mostly free in cloud). Add field-level encryption for the most sensitive attributes, and E2E when the threat model includes the provider itself.

How does TLS work at a high level, and why asymmetric plus symmetric crypto? Intermediate
Say this: "TLS uses a certificate to authenticate the server, an ephemeral key exchange to agree a fresh shared secret, and then fast symmetric encryption for the data. Asymmetric crypto solves agreeing a key with a stranger but is slow; symmetric is fast but needs a shared key. Ephemeral keys give forward secrecy."

The problem. Two strangers on a public network must agree on a secret key and be sure they are talking to the real site, not an impersonator, with an eavesdropper reading every byte.

The handshake in steps (TLS 1.3 flavour).

  1. ClientHello: supported versions, cipher suites and the client's ephemeral Diffie-Hellman public value.
  2. ServerHello: chosen cipher and its own ephemeral public value. Now both can compute the same shared secret without ever sending it.
  3. Server certificate and signature: the server sends its certificate chain and signs the handshake transcript with its long-term private key. The client checks the chain leads to a trusted CA, the hostname matches, the certificate is unexpired and not revoked, and that the signature verifies. This is the authentication step.
  4. Key derivation and Finished: both derive symmetric session keys from the shared secret and confirm the handshake was not tampered with.
  5. Application data flows with symmetric AEAD encryption (AES-GCM or ChaCha20-Poly1305), which is orders of magnitude faster than RSA or elliptic-curve operations and also authenticates each record.

Why both kinds. Asymmetric crypto (RSA, ECDSA, Diffie-Hellman) lets two parties establish trust or a shared secret with no prior secret, but costs a lot per byte. Symmetric crypto is fast but needs the key already shared. So asymmetric is used briefly at the start, symmetric for the bulk.

Forward secrecy. Because the DH values are ephemeral (thrown away after the session), stealing the server's private key next year cannot decrypt traffic someone recorded today. Without it, a single key leak exposes all history.

Operational notes. TLS 1.3 needs one round trip (TLS 1.2 needs two); session resumption can cut it further (0-RTT data has replay risk, so only use for idempotent requests). Terminating TLS at the load balancer is convenient, but in a zero-trust design re-encrypt to backends. Expired certificates and incomplete chains are the classic outage causes: automate renewal and monitor expiry.

What is envelope encryption and why is it used? Senior
Say this: "A data key encrypts the data locally; a master key in a KMS encrypts that data key, and the wrapped data key is stored next to the ciphertext. The master key never leaves the HSM, only tiny keys cross the network, and rotating the master key means re-wrapping small keys, not re-encrypting terabytes."

The problem it solves. Suppose you want a KMS (cloud key service backed by hardware security modules) to protect a 5 GB file. Sending 5 GB to the KMS to encrypt is slow, expensive and bounded by request size limits (KMS APIs typically accept only a few KB). But encrypting locally with a key you keep in application memory defeats the purpose of having an HSM.

The envelope scheme.

  1. Write: the app asks KMS for a fresh data encryption key (DEK) (or generates one and asks KMS to wrap it). KMS returns the DEK in plaintext plus a copy encrypted under the key encryption key (KEK), which lives only in the KMS/HSM.
  2. The app encrypts the data locally with the plaintext DEK (AES-GCM), then discards the plaintext DEK from memory.
  3. It stores {ciphertext, wrapped DEK, KEK id/version} together.
  4. Read: the app sends the wrapped DEK to KMS; KMS checks permissions, logs the request and returns the plaintext DEK; the app decrypts locally.

Think of a safe-deposit box: the data sits in a strongbox (encrypted with the DEK), the strongbox key is locked inside a bank vault (KEK) that never leaves the bank.

Benefits.

  • Master key never leaves the HSM.
  • Only 32-byte keys travel to KMS, so latency and cost are small; DEKs can be cached briefly.
  • Cheap rotation: new KEK version only requires re-wrapping DEKs.
  • Granularity: a DEK per object, per file or per tenant limits blast radius and allows crypto-shredding (destroy one tenant's key and its data is gone).
  • Every unwrap is an auditable, permission-checked event.

Pitfall. The KMS becomes an availability dependency: if it is down or throttled you cannot decrypt. Cache DEKs for short periods and treat KMS quotas as a capacity limit. Cloud object stores, EBS and databases all use exactly this pattern internally.

How do you manage and rotate encryption keys? Senior
Say this: "Keys live in a KMS or HSM, apps ask it to encrypt, decrypt or unwrap and never hold root keys. Duties are separated, every use is logged, keys are versioned and rotated on schedule or suspicion, and old ciphertext stays readable because it records its key version."

Why key management is the real work. Algorithms like AES are not what gets broken; keys get lost, leaked or left unrotated. Losing a key means losing the data permanently, while leaking it means losing confidentiality. Management is about controlling both risks.

  • Generate and hold in KMS/HSM (cloud KMS, Vault transit, hardware module). The app calls the service; the root key material is never exported.
  • Separate duties: the people or roles that administer keys (create, rotate, delete) differ from those that can use them (encrypt, decrypt). Every use is logged and alertable.
  • Versioning and rotation. Each ciphertext is tagged with the key version. On rotation new writes use version N+1; old data still decrypts with N. Then either re-encrypt lazily on access, or in a batch job when policy demands, and finally disable and schedule deletion of old versions. Rotate on a schedule (commonly yearly for KEKs, much more often for DEKs) and immediately on suspected compromise.
  • Backup and disaster recovery: replicate key material across regions through controlled mechanisms (multi-region keys). A region loss must not destroy the ability to decrypt backups. Deletion should have a mandatory waiting period (7 to 30 days) to survive mistakes.
  • Customer-managed keys (BYOK / HYOK): enterprise customers hold or can revoke the key; revocation makes their data unreadable. Cost: your availability now depends on their key service, and support gets harder.

Crypto-shredding. To "delete" data in backups, replicas and immutable logs, destroy the per-user or per-tenant key. The remaining ciphertext is unreadable. This is how you reconcile GDPR erasure with append-only systems.

Worked rotation example. Day 0 KEK v1 wraps all DEKs. Day 365 enable v2: new DEKs are wrapped with v2; a background job re-wraps old DEKs (cheap, only keys) and finishes in hours. v1 is disabled, observed for errors for 30 days, then deleted.

Hashing, encryption, signing and HMAC: what is the difference? Basic
Say this: "Hash: one-way fingerprint, no key. Encryption: reversible with a key, for confidentiality. HMAC: a hash with a shared secret, proves the message came from a key holder. Digital signature: private key signs, public key verifies, proves origin to anyone."

Start with the question each answers. Confidentiality ("nobody else can read it") uses encryption. Integrity ("it was not changed") uses a hash or MAC. Authenticity ("it really came from X") uses an HMAC or signature.

ToolReversible?Key?Use

Examples. A download page publishes the SHA-256 of a file so you can check integrity (but a hash on the same compromised server proves little; sign it). A payment provider sends a webhook with HMAC-SHA256(secret, timestamp + body); you recompute and compare in constant time: only a holder of the shared secret could produce it. Differences that trip people up. HMAC versus signature: with HMAC both sides share the secret, so either could have produced the message (no non-repudiation); with signatures only the private-key holder can sign. Encryption alone does not guarantee integrity: use authenticated modes (GCM) that do both. And never invent your own: use vetted libraries and modern primitives.

Common attacks and design-level defences

What is injection (SQL and others) and how do you design against it? Basic
Say this: "Injection happens when untrusted input is interpreted as code. The fix is to keep data and code separate with parameterized queries, backed by least-privilege accounts and allowlist validation."

How it works. A program builds a command as a string and mixes user input in. If the input contains syntax the interpreter understands, the attacker rewrites the command.

// vulnerable
query = "SELECT * FROM users WHERE name = '" + input + "'"
// input:  ' OR '1'='1
// becomes: SELECT * FROM users WHERE name = '' OR '1'='1'   -- returns every row

Worse inputs can append statements, read other tables with UNION, or on some engines run OS commands. The same family exists wherever a string is parsed as a language: NoSQL operators in JSON, OS shell commands, LDAP filters, XPath, server-side template engines and log lines (forged entries).

Defences, strongest first.

  • Parameterized queries / prepared statements. The SQL text is sent with placeholders, the values separately: SELECT * FROM users WHERE name = ?. The database parses the structure first, so a value can never become syntax. ORMs do this by default, but raw string building inside an ORM ("... WHERE x = " + id) is still vulnerable, and so are dynamic table or column names, which cannot be parameterized and must be matched against an allowlist.
  • Allowlist validation of type, length and format (an id must be digits) as defence in depth, not as the main defence. Blocklisting quotes does not work.
  • Least privilege: the app's database user has no DROP, no access to other schemas, perhaps read-only for read paths, so a successful injection has limited impact.
  • No shell from user input: call library functions or pass argument arrays, never concatenated command strings.
  • Safe error handling: do not return SQL errors to clients; they teach the attacker the schema.

Probe to expect. "Is escaping enough?" Escaping is fragile and context-dependent; parameterization is structural and is the answer. Also mention WAFs as a mitigation layer, not a fix.

What is XSS, and what are the defences? Intermediate
Say this: "XSS is attacker-controlled script running in a victim's browser as your site. Defend by encoding output for its context, a strict Content Security Policy, HttpOnly cookies, and sanitizing any rich text you must allow."

Why it is serious. Browsers trust scripts from your origin completely. If an attacker gets a script into your page it can read the DOM, call your APIs with the user's session, capture keystrokes, steal tokens kept in localStorage and rewrite the page into a fake login form.

Three types.

TypeWhere the payload comes fromExample
StoredSaved by the server and shown to othersA comment containing a script tag appears on every reader's page
ReflectedSent in the request and echoed in the responseA search page prints ?q= unescaped; the attacker emails a crafted link
DOM-basedClient code writes untrusted data into the pageScript reads location.hash and puts it into the DOM as HTML

Defences.

  • Output encoding in the right context. The same text needs different escaping inside HTML body, an attribute, a JavaScript string or a URL. Modern frameworks (React, Angular, Vue) escape text by default, so the danger lies in their "render raw HTML" escape hatches and in manually built DOM strings.
  • Content Security Policy (CSP): a response header limiting where scripts can load from. A strict policy (nonce-based, no inline script, no unsafe-eval) means even an injected script tag will not run. It is the best safety net.
  • HttpOnly cookies so session cookies are unreadable to scripts, and short-lived tokens.
  • Sanitise rich text (comments, emails) with a vetted allowlist library, not hand-written regexes.
  • Isolate user content: serve uploaded HTML or SVG from a separate cookie-less domain, and set Content-Type and X-Content-Type-Options: nosniff.

Pitfall. Input validation on the way in is not a substitute; the dangerous step is output into a specific context. Store raw, encode on output.

What is CSRF and how do you prevent it? Intermediate
Say this: "CSRF tricks a logged-in user's browser into sending a request, and the browser attaches the cookie automatically. Prevent it with SameSite cookies, anti-CSRF tokens on state-changing requests, and origin checks."

The attack, step by step.

  1. You are logged in to bank.com; your browser holds the session cookie.
  2. You visit evil.example, which contains an auto-submitting form: POST https://bank.com/transfer?to=attacker&amount=1000.
  3. Your browser sends the request to bank.com and, because it is a request to that domain, attaches the cookie.
  4. The bank sees a valid session and performs the transfer. The attacker never saw the cookie; they only borrowed the browser's habit of sending it.

When it applies. It exploits automatic credential sending, so it matters for cookie (and HTTP-auth) sessions. APIs that require an Authorization: Bearer header set by your own JavaScript are not vulnerable in the same way, because a foreign page cannot make the browser add that header.

Defences.

  • SameSite cookies: Lax (default in modern browsers) withholds cookies on cross-site POST and sub-requests; Strict withholds them on all cross-site navigations. Often enough on its own, but defence in depth is wise.
  • Anti-CSRF token: a random per-session or per-request value embedded in the form (or sent as a header by your JS) and checked on every state-changing request; an attacker's page cannot read it. The double-submit-cookie variant compares a cookie and a header.
  • Check Origin / Referer headers; require custom headers on JSON APIs, which triggers a CORS pre-flight a foreign site cannot pass.
  • Never change state on GET. Require re-authentication or a confirmation for sensitive actions.

Contrast to remember. CSRF abuses the site's trust in the browser (it trusts the cookie); XSS abuses the user's trust in the site. An XSS bug defeats CSRF protections because the attacker's script runs inside your origin and can read the token.

What is SSRF and why is it dangerous in cloud systems? Senior
Say this: "SSRF lets an attacker make my server fetch a URL they choose, so they reach internal services and the cloud metadata endpoint with the server's network position. I defend with allowlists, blocking private ranges after resolving DNS, isolated fetchers and hardened metadata (IMDSv2)."

What it is. Many features fetch a user-supplied URL: import from link, image by URL, webhooks, link previews, PDF or screenshot renderers. The fetch originates from your server, which sits inside your network behind the firewall. The attacker supplies http://localhost:8080/admin or http://10.0.3.7/internal-api and your server obediently returns the content.

Why cloud makes it worse. Every cloud VM can query a link-local metadata service at 169.254.169.254. On a misconfigured setup, GET /latest/meta-data/iam/security-credentials/<role> returns temporary credentials of the instance's role. With SSRF the attacker reads them through your app, then uses them from their own machine. The 2019 Capital One breach is widely reported to have involved SSRF against a misconfigured web application firewall to obtain cloud credentials (details per public reporting).

Defences, layered.

  1. Prefer allowlists of destination hosts or domains when the feature allows it.
  2. Otherwise validate after resolving: resolve the hostname yourself, reject private (10/8, 172.16/12, 192.168/16), loopback, link-local and metadata addresses (including IPv6 and decimal or hex encodings), then connect to that resolved IP. Re-resolving later enables DNS rebinding, where the name first points to a public address, then to an internal one.
  3. Handle redirects: do not follow them blindly; re-validate each hop. Allow only http and https; no file: or gopher:.
  4. Isolate: run fetchers in a segregated network segment with egress firewall rules and a role with no useful permissions.
  5. Harden metadata: require IMDSv2 (session token header, a hop limit that stops containers forwarding), or block the metadata IP from application containers; give instances minimal roles.
  6. Limit what is returned: do not echo raw responses back to users; cap size and time.

Interview angle. Mention "blind SSRF" too, where no response is returned but timing or side effects still reveal internal ports and services.

How do you defend a system against DDoS? Senior
Say this: "Absorb volumetric attacks at a large edge such as a CDN or scrubbing network, filter application-layer attacks with WAF, bot detection and rate limits, protect the hard-to-scale backend with caching and load shedding, and cap autoscaling so the attacker cannot bankrupt me."

Why it is a different problem. A distributed denial-of-service attack uses thousands of machines to exhaust a resource: bandwidth, connection tables, CPU or a database. You cannot out-provision a botnet from your own data centre, so defences push the fight to places that have more capacity than the attacker.

Resilience measures.

  • Cache and serve stale at the edge so repeated requests never reach the origin.
  • Load shedding and priorities: drop expensive anonymous work first and keep logged-in or paying traffic alive; degrade (read-only, static pages) rather than die.
  • Protect shared bottlenecks (database connections, auth service) with queues and limits.
  • Preparation: a runbook, contacts at your CDN and ISP, traffic baselines to spot attacks, and rehearsals.

Trap. Autoscaling alone is not a defence: you pay for the attacker's traffic (the "economic denial of service" or denial-of-wallet) and scaling the web tier just forwards the flood to a database that cannot scale. Set maximum capacity and budget alerts, and protect the choke point.

What is a replay attack and how do you defend against it? Intermediate
Say this: "A replay re-sends a genuine captured message, so its signature still checks out. Defend by putting a timestamp and a unique nonce inside the signed data and rejecting old or already-seen messages, and by using idempotency keys on money-moving operations."

The attack. The attacker does not forge anything. They record a legitimate request, say "pay merchant 100 EUR" with a valid signature or token, and send it again later (or many times). Because the bytes are authentic, verification passes. TLS prevents capture on the wire, but replays can still happen from a compromised proxy, a log file, a stolen token or a malicious client.

Defences.

  1. Timestamp inside the signed payload with a short window. The receiver rejects anything older than, say, 5 minutes. This bounds how long a capture is useful. It needs reasonably synchronised clocks.
  2. Nonce or unique message id, remembered for the window. Keep seen ids in a Redis set with a TTL equal to the window; a repeat is rejected. Timestamp plus nonce means the store only needs to hold five minutes of ids.
  3. Idempotency keys for operations with side effects: the client sends Idempotency-Key: 7f3...; the server stores the key with the result and returns the same result on repeats. This protects against attackers and also against honest retries after a timeout.
  4. Short-lived tokens limit how long a stolen credential works; sequence numbers or counters in protocols (TLS records, TOTP counters); OIDC nonce ties an ID token to one login attempt.

Example. Stripe-style webhooks sign timestamp + "." + body with HMAC. The receiver recomputes, compares in constant time, and rejects if the timestamp is more than a few minutes off. Signing the timestamp is essential: if the timestamp were an unsigned header, an attacker could freshen it.

How do rate limiting and abuse prevention work, and what do you key the limit on? Intermediate
Say this: "Rate limiting caps how fast a caller can hit me, to protect capacity, fairness and security. I use a token bucket for burst tolerance, key it per user or API key once authenticated and per IP before that, enforce it in Redis, and return 429 with Retry-After."

Why. Without limits, one buggy client in a retry loop, one scraper or one attacker brute-forcing passwords can consume the shared capacity and hurt every other tenant. Limits also create the pricing and quota tiers of API products.

AlgorithmHow it worksNote
Token bucketA bucket holds up to N tokens, refilled at R per second; each request takes oneAllows bursts up to N while averaging R; the most common choice
Leaky bucketRequests enter a queue drained at a fixed rateSmooths output to a steady rate

Sliding window (log or counter)Counts over the last 60 seconds continuouslyAccurate; log version uses more memory, counter version approximates

What to key on.

  • Per IP: cheap and works before login, but many users share an office NAT (punished unfairly) and attackers rotate IPs.
  • Per user or API key: accurate once authenticated.
  • Per tenant: fair multi-tenancy and the basis for plan quotas.
  • Per endpoint: tight limits on login, password reset, SMS sending and expensive search; loose on cheap reads.

Layer them: coarse IP limits at the edge, finer per-key limits in the service.

Implementation. A Redis counter or token bucket updated atomically with a Lua script, one key per caller, so all instances share state. Local in-process limits synced periodically are faster but approximate. Return 429 Too Many Requests with Retry-After and rate-limit headers so well-behaved clients back off. Decide deliberately what happens if the limiter store is down: fail open for ordinary APIs (availability) but fail closed for login or SMS sending (security and cost).

Beyond limits: CAPTCHA or proof-of-work for suspicious clients, progressive delays, and account lockout used carefully, since an attacker can lock out victims on purpose (a DoS lever); prefer throttling and step-up verification. Anomaly detection and tiered quotas complete the picture.

Scenario: login traffic spikes 50x at 3 a.m. and many accounts report suspicious activity. What do you do? Senior
Say this: "This looks like credential stuffing. I confirm from the traffic pattern, contain with tighter limits and bot challenges, protect affected accounts with forced resets and revoked sessions, then fix the root issue with MFA and breached-password screening."

Distinguishing the attack type. Brute force hammers one account with many passwords. Credential stuffing tries one leaked email and password pair per account across many accounts, from many IPs, so per-account lockouts and per-IP limits barely notice it. The signature: huge number of distinct usernames, one or two attempts each, a failure rate far above normal (say 95% versus the usual 5%), unusual user agents or ASNs, and a few successes, which are the actual victims.

  1. Confirm quickly: dashboards for login attempts by outcome, distinct IPs, distinct usernames per IP, user agents and countries; compare with a normal night.
  2. Contain: tighten per-IP and global limits on /login, enable bot challenges (CAPTCHA or proof-of-work) for suspicious clients, block bad ASNs and known proxies at the WAF, add step-up (email or MFA) for logins from new devices, and keep legitimate users flowing.
  3. Find the victims: list accounts with successful logins that match the attack pattern (new device, same IP as many failures). Revoke their sessions and refresh tokens, force a password reset, check for changed email, payout details or added API keys, and notify users.
  4. Prevent recurrence: screen passwords against breached lists at login and signup, push MFA and passkeys, add risk-based scoring (device fingerprint, impossible travel), return uniform error messages so attackers cannot enumerate accounts, and make sure registration and reset endpoints do not leak whether an email exists.
  5. Review: alert on login failure ratio, capture a post-mortem, and consider regulatory notification if accounts were accessed.

Watch out: an aggressive IP block can lock out a whole corporate NAT; hard-locking accounts hands attackers a way to deny service to real users.

Scenario: an engineer pushed a cloud access key to a public repository an hour ago. What now? Intermediate
Say this: "Treat the key as compromised: revoke it first, then audit what it did, clean up anything the attacker created, then scrub the repo and prevent it happening again. History cleanup comes last, not first."

Why the speed matters. Automated scanners watch public commits and test found keys within minutes, commonly to start crypto-mining instances or exfiltrate data. After an hour you must assume it was already used.

  1. Revoke or deactivate the key immediately and issue a replacement to the legitimate system (via the secrets manager). Do this before touching git, because rewriting history does not undo copies already scraped.
  2. Audit usage with cloud audit logs (CloudTrail, equivalent): every call made with that key since the push. Look for new users, roles or access keys (persistence), launched instances in odd regions, storage listing and downloads, changes to security groups and billing alarms.
  3. Remediate: terminate unknown resources, delete rogue identities, rotate any secrets the key could read (it may have fetched others), and check data stores for exfiltration. If personal data may be accessed, involve security and legal for breach assessment.
  4. Clean the repository: remove the secret and rewrite history (git filter-repo), force push and ask forks and caches to purge. Assume the secret is burned regardless.
  5. Prevent: pre-commit and CI secret scanning, platform push protection, short-lived credentials via roles or OIDC federation so there is no long-lived key to leak, least privilege, budget and anomaly alerts, and a blameless post-mortem about why a long-lived key existed.

Privacy, compliance and multi-tenancy

What is PII and what does GDPR mean for system design? Intermediate
Say this: "PII is any data that identifies a person alone or in combination. GDPR applies to anyone handling EU residents' data and turns into design requirements: know where PII lives, minimise and expire it, support access and erasure requests, secure it, and be able to report a breach within 72 hours."

What counts as PII. Name, email, phone, address, government ids, but also IP address, device id, cookie id, precise location and anything linkable back to a person. GDPR uses the broader term personal data. Special categories (health, biometrics, religion, political opinion, sexual orientation) have stricter rules. GDPR applies by who the data subjects are (people in the EU), not where your servers sit.

Design consequences, each with a reason.

  • Know where PII lives. You cannot protect or delete what you cannot find. Keep a data inventory or catalog, classify fields, and keep PII in a few guarded stores; elsewhere reference people by an internal id (pseudonymization: the link back is kept separately and protected).
  • Data minimisation and retention. Collect only what the purpose needs and give each dataset a retention period with an automated purge. Data you do not have cannot leak.
  • User rights: access and export, rectification, erasure ("right to be forgotten"), restriction, portability and objection. You generally have about one month to respond, so build self-service tools and internal workflows rather than handling them by hand.
  • Lawful basis and consent. Record what each person agreed to, when and in which version of the policy, and honour withdrawal quickly.
  • Security and breach notification. Encryption, access control and audit logs; notify the supervisory authority within 72 hours of becoming aware of a qualifying breach, so detection and incident process matter.
  • Privacy by design and default. The most private setting is the default; keep PII out of logs, URLs, analytics events and test data.
  • Processors and transfers. Third parties (analytics, email, support tools) are processors needing contracts, and moving EU data to some countries needs a legal mechanism.

Pitfall. Anonymised versus pseudonymised: truly anonymous data is out of GDPR scope, but data that can be re-linked (hashed emails, device ids) is still personal data. Fines can reach up to 4% of global annual turnover or 20 million euros, whichever is higher.

How do you implement "delete my data" across a distributed system? Senior
Say this: "Inventory every store holding the user's data, drive deletion as an orchestrated, retryable workflow with an audit trail, use soft delete then hard delete, and handle immutable stores such as logs and backups with crypto-shredding, short retention and re-applying a deletion list on restore."

Why it is hard. In a monolith with one database you delete rows. In a distributed system a person's data is spread across the primary database, caches, search indexes, a data warehouse, Kafka topics, object storage, logs, backups, third-party tools (CRM, email provider, analytics) and derived data such as ML features. Miss one and you have failed the request and kept illegal data.

  1. Map the data. Maintain a catalog of which service owns which personal data, and require each service to implement a delete (or anonymise) handler as part of launch review.
  2. Orchestrate. A request becomes a workflow (event or saga): the identity service emits UserDeletionRequested(userId); each service deletes its data and acknowledges. A coordinator tracks status, retries until all complete, alerts on stuck steps and records an audit entry per store without retaining the PII itself.
  3. Soft delete, then hard delete. First mark the account as deleted and disable it for a grace period (commonly around 30 days) so mistakes and fraud claims are recoverable, then purge for real.
  4. Handle immutable stores. Append-only logs, Kafka topics and backups cannot be edited row by row. Options: keep PII out of them in the first place (events carry ids, not names); crypto-shredding by encrypting each user's data with a per-user key and destroying the key; short retention so data ages out; compacted topics with tombstone records; and for backups, document that they expire within N days and that any restore must re-apply the deletion ledger before the data is used.
  5. Third parties: call their deletion APIs and keep proof; contracts must require it.
  6. Exceptions: legal retention duties (tax invoices, anti-fraud, litigation hold) may override erasure; keep only the minimum required, restrict access, and delete when the obligation ends.

Verify. Periodically test with a canary user: create, delete, then search every store for traces. Also remember derived datasets: model training data and aggregates may need anonymisation or retraining policy decisions.

What is data residency and how does it affect architecture? Senior
Say this: "Data residency means certain data must stay in a given country or region. I design regional cells, pin each tenant to a home region at signup, keep only non-personal routing metadata globally, and watch for hidden copies in logs, backups, analytics and support tools."

Why it exists. Laws (some national regulations, public-sector and health rules) and customer contracts require that data about citizens or tenants stay within a jurisdiction, or restrict transfers abroad. Selling to a German bank or the Indian government often depends on it. Note the distinction: residency is where data is stored, sovereignty is who has legal control over it, and the two can differ.

Architecture consequences.

  • Regional cells/stacks. Each region runs a full, independent copy of the service and its data stores. A tenant is assigned a home region at signup and all its data (database, object storage, search index, queues, caches, backups) stays there.
  • Thin global layer. Only non-personal data is global: the tenant-to-region map, billing aggregates, public content. The edge or global router looks up the tenant and sends the request to its region.
  • Avoid cross-region calls with PII. Service-to-service calls stay inside the region; identity may need a regional directory.
  • Hidden leaks to hunt down: logs and traces shipped to a central region, metrics with user ids, analytics pipelines, support tools and screenshots, CDN caches, error trackers, backups and DR replicas that quietly land in another geography. Do DR within the allowed boundary (a second zone group or second in-country region).

Trade-offs. N deployments mean N times the operations, deployments and cost; global features such as cross-region search, shared analytics and global admin views need aggregated or anonymised data; moving a tenant between regions becomes a planned migration; latency for travelling users. Where residency is not required, prefer a single global design for simplicity.

Rollout idea. Start by making region a first-class attribute in the data model and routing layer even before a second region exists, because retrofitting it later is very hard.

What makes a good audit log, and how does it differ from application logging? Intermediate

Different audiences, different guarantees. Application logs help engineers debug and may be sampled, dropped, rotated within days and changed freely. Audit logs answer questions like "who exported the customer list on 3 March?" for security investigations, regulators and customers, so losing or altering entries defeats their purpose.

How do you isolate tenants in a multi-tenant SaaS system? Senior
Say this: "There is a spectrum from shared tables with a tenant_id column to a dedicated stack per tenant: more isolation costs more. I use a tiered approach with the same code, pooled for small tenants and dedicated for large or regulated ones, and defend the shared model with enforcement in the data layer, not in each query."

The problem. A SaaS product serves many customers (tenants) from one system. The business wants low cost per tenant; each customer demands that no one else ever sees their data, that neighbours cannot slow them down, and sometimes that their data is encrypted with their own key or stays in their region.

ModelIsolationCost / ops

Tiered approach. Small self-service tenants share a pool; enterprise or regulated tenants get dedicated databases or cells; the same code runs everywhere and a tenant router maps tenant to location. Moving a tenant between tiers should be an operation, not a rewrite.

Defence in depth for the shared model.

  1. Tenant id comes from the verified token, never from a request parameter or body that the client controls.
  2. Apply it automatically, not by hand in each query: an ORM filter or base repository, or database row-level security (for example PostgreSQL policies keyed on a session variable such as app.tenant_id), so forgetting a filter fails closed.
  3. Tenant-scoped everything else: cache keys (t:acme:order:9), search index filters or routing, queue topics and object storage prefixes, per-tenant encryption keys.
  4. Automated tests that attempt cross-tenant reads and writes on every endpoint, plus per-tenant audit logs.

Pitfalls. Background jobs and async handlers losing the tenant context; thread-local tenant ids not cleared on reused threads; the connection pool reusing a connection with a stale tenant setting. Isolation of performance (noisy neighbours) is a separate problem from isolation of data, see the next question.

What is the noisy neighbour problem and how do you handle it? Intermediate
Say this: "One tenant's heavy usage consumes shared CPU, connections, cache or queue throughput and slows everyone. I handle it with per-tenant quotas and rate limits, bulkheads, fair scheduling, moving heavy tenants to dedicated capacity and per-tenant observability."

What it looks like. At 9:00 a customer launches a bulk import of 5 million rows. The import saturates the shared database connection pool and the worker queue. Other tenants' ordinary requests wait for connections and time out, even though nothing is wrong with their usage. This is the main operational risk of shared infrastructure.

Controls, from cheap to heavy.

  • Per-tenant limits: API rate limits, concurrent request caps, storage and job-size quotas, so no tenant can take more than its share.
  • Bulkheads: separate thread pools, connection pools and queues per tenant tier or even per tenant (named after ship compartments: a leak floods one section, not the whole ship). Heavy batch work should not share a pool with interactive requests.
  • Fair scheduling: weighted fair queues for background jobs and per-tenant concurrency limits, so one tenant's 10,000 queued jobs cannot starve a tenant with 3. Use priorities so interactive work wins over batch.
  • Shuffle sharding: assign each tenant to a small random subset of workers or cells; a misbehaving tenant can degrade only its subset, and the chance two tenants share the entire subset is tiny.
  • Isolate heavy tenants: move them to dedicated shards, cells or a premium tier.
  • Resource governance in the database: statement timeouts, per-role limits, read replicas for reports.
  • Observe per tenant: top-N tenants by requests, CPU time and database time; alert when a tenant exceeds its share (mind metric cardinality: use top-N or logs for the long tail).
  • Throttle politely: 429 with Retry-After, backoff hints, and shed low-priority work first.

Trade-off. Strict per-tenant reservation wastes capacity when tenants are idle; shared pools with limits and fair queues use capacity better but need good measurement. Be ready to explain how you would detect the culprit within minutes.

Scenario: a customer reports seeing another customer's data in your multi-tenant app. What do you do? Senior
Say this: "Treat it as a Sev1 security incident: contain by disabling the path or rolling back, preserve evidence, find the cause, scope exposure from audit logs, notify as legally required, then fix with central enforcement and cross-tenant tests."
  1. Declare and staff the incident. Open an incident channel with a commander, bring in security and legal early, because cross-tenant exposure may be a reportable breach with contractual and regulatory clocks (GDPR 72 hours). Do not wait to be sure.
  2. Contain first. Turn off the affected feature or endpoint with a feature flag, roll back the latest deploy, or block the suspect route at the gateway. Preserve evidence before it rotates: copy relevant logs, request ids and cache contents.
  3. Find the cause. Common culprits, each worth naming:
    • A cache key without the tenant id (order:9001 instead of t:acme:order:9001) so one tenant gets another's cached response.
    • A new query or report missing the tenant filter.
    • A thread-local tenant context not cleared in a reused worker thread, or lost in an async hop so a default or previous tenant is used.
    • A shared mutable singleton or static field holding per-request data.
    • A CDN or proxy cache keyed on URL but not on the authentication header.
    • A connection-pool session variable (RLS context) left over from the previous borrower.
  4. Scope the damage. Use audit and access logs to list which tenants and records were exposed, to whom, and for how long. If you cannot determine it, assume the worst case for the window.
  5. Notify. Tell affected customers and regulators per contracts and law, with facts and a remediation timeline.
  6. Prevent. Central enforcement (row-level security or mandatory tenant scope in the data layer), tenant id in every cache key by construction, cross-tenant tests in CI, context-propagation tests for async paths, and a blameless post-mortem.

Observability: logs, metrics, traces

What is observability and how is it different from monitoring? Basic
Say this: "Monitoring watches for known failures with predefined checks. Observability is being able to ask new questions about a running system from the telemetry it emits, without shipping new code, which matters for the unknown-unknowns of distributed systems."

Monitoring. You decide in advance what could break and set up checks: "CPU above 90%", "health endpoint returns 200", "disk below 10% free". It works well for failure modes you have already seen. It tells you that something is wrong.

Observability. A system is observable if you can understand its internal state from its external outputs. In practice this means emitting rich, high-detail telemetry (structured logs, metrics, traces with many attributes) and having tools to slice and compare it freely. The test: can you answer a question you did not anticipate when you wrote the code?

An example of the difference. Users complain of slowness. Monitoring shows green dashboards: CPU fine, error rate fine. With observability you can filter traces by tenant=acme, region=eu, app_version=4.2 and discover that requests from that combination wait 4 seconds on a particular database shard, only on Tuesdays when a batch job runs. No predefined alert covered that combination.

Why it matters more in microservices. A request touches ten services; failures are partial, emergent and rarely reproducible on a laptop. You cannot attach a debugger to production, so the telemetry is your debugger. High-cardinality, high-dimensionality data (user, tenant, version, feature flag) is what makes slicing possible.

How to say it. They are complementary: monitoring (alerts on known symptoms) is built on top of the same data, and observability is what lets you investigate once an alert fires. Do not claim monitoring is obsolete.

Newer additions. Some teams add profiles (continuous CPU and memory flame graphs) and events. Rule of thumb: use metrics to alert and measure, traces to locate, logs to explain, and never use logs as the only source for counts.

What is structured logging and why does it matter? Basic
Say this: "Write logs as machine-readable key-value records, usually JSON, rather than free text, so I can filter, aggregate and join them by field instead of parsing sentences with regex."

The problem with free text. A line like Payment failed for order 9912 (card declined) after 412ms reads nicely but to count failures by reason you must write a regex that breaks the moment someone rewords the message, and each service words things differently.

The structured version.

{"ts":"2026-11-17T10:02:11Z","level":"ERROR","service":"checkout","env":"prod",
 "trace_id":"4bf92f35...","tenant":"t-81","order_id":"o-9912",
 "msg":"payment declined","err_code":"CARD_DECLINED","latency_ms":412}

Now a query like "count by err_code where service=checkout in the last hour" is trivial, and clicking trace_id pulls up the trace.

Benefits. Filter and aggregate by any field; join with traces; consistent schema across services (agree on names such as trace_id, tenant, latency_ms); fewer parsing bugs; smaller, cheaper indexes when fields are typed.

Rules of good logging.

  • Stable field names and types; a constant message template with variable data in fields.
  • Consistent levels: ERROR means a human should look; WARN is suspicious but handled; INFO for business-level events; DEBUG off in production by default.
  • One event per line, always UTC timestamps.
  • Log at boundaries (request in and out, external calls, failures), not in tight loops.
  • Include enough context to act on, and never secrets or PII.
  • Log an error once, where it is handled, rather than at every layer as it propagates, otherwise one failure produces five lines and confuses counts.
What are correlation ids and trace ids, and how do they propagate? Intermediate
Say this: "A unique id generated at the edge and passed to every downstream call, so every log line and span for one user request can be found together. It travels in HTTP headers, message headers and gRPC metadata, and must be copied explicitly across threads and queues."

Why. One user click may touch a gateway, six services, a cache and a queue. Each writes its own logs on its own machines. Without a shared key, reconstructing what happened to one request means guessing from timestamps, which fails under load. A correlation id is that shared key.

How it propagates.

  1. The edge (gateway) generates an id if the incoming request has none, e.g. 4bf92f3577b34da6a3ce929d0e0e4736.
  2. It places it in a header on every outbound call. Standard: W3C Trace Context traceparent: 00-<trace-id>-<parent-span-id>-01. Older style: X-Request-Id. Messaging systems carry it in message headers (Kafka record headers); gRPC uses metadata.
  3. Each service reads it on entry, stores it in a request-scoped context (the MDC in Java logging frameworks) so every log line gets it automatically, and forwards it.
  4. The id is returned to the client in a response header or error body, so a support ticket can quote "request id 4bf9..." and an engineer finds the entire journey.

Where it breaks. Context is thread-local in many runtimes, so it is lost when work hops to a thread pool, a scheduled job, a reactive pipeline or a message queue consumer unless you copy it explicitly. Instrumentation libraries (OpenTelemetry) wrap the common clients, executors and frameworks, but custom async code often needs manual propagation. Test that a request through a queue still shows one trace.

Terms. The trace id names the whole journey; a span id names one hop within it; a business correlation id (order id, session id) may be logged as well to join several separate requests belonging to one workflow, such as a retry initiated later.

How does distributed tracing work? Intermediate
Say this: "Each unit of work is a span with a start, duration, attributes and a parent id. The trace id and parent id travel with each call, every service reports its spans to a backend, and the backend assembles them into a tree that shows the critical path."

Why. Metrics tell you checkout is slow; they cannot tell you which of the eight services behind it is responsible. A trace is a per-request breakdown across services, like a stopwatch with lap times for each component.

Mechanism, step by step.

  1. The gateway starts a trace (new trace id) and a root span for GET /checkout.
  2. Before calling checkout-svc it injects traceparent (trace id plus its span id as the parent) into the request headers.
  3. checkout-svc extracts it, starts a child span with the gateway span as parent, and repeats for each downstream call (cart, payment).
  4. Each span records name, start time, duration, status (ok or error) and attributes (http.status_code, db.statement summary, tenant), plus events such as exceptions.
  5. Spans are batched and sent asynchronously to an agent or collector, which forwards them to a backend (Jaeger, Tempo, Zipkin or a vendor APM). The backend joins spans by trace id into the tree shown above.

What you read from the picture. Gateway 620 ms; checkout 470 ms inside it; payment 300 ms of that; the external card processor 240 ms. So the critical path is dominated by a third party. You can also spot calls that run one after another but could run in parallel, N+1 query patterns (the same child span repeated 50 times), retries and timeouts.

Standards and cost. OpenTelemetry is the vendor-neutral standard for APIs, SDKs, the wire protocol (OTLP) and the collector. Tracing adds small overhead per span and storage, which is why sampling exists (next question). Pitfalls: broken propagation creates orphan traces, and clock skew between hosts makes spans look misordered.

Why sample traces, and what are head-based and tail-based sampling? Senior
Say this: "Tracing every request at high traffic costs too much in CPU, network and storage, so I keep a fraction. Head-based decides at the start and is cheap but can drop the interesting traces. Tail-based decides after the trace completes, so it keeps all errors and slow requests, at the price of a stateful collector tier."

Why not keep everything. A service at 20,000 requests per second with 15 spans per request produces 300,000 spans per second. Stored for weeks, that is enormous, and 99% of it shows ordinary successful requests nobody will ever open.

Example. At 1% head sampling and an error rate of 0.1%, you expect to retain only about one error trace per 100,000 requests. With tail sampling every error trace is retained, so you can always inspect a failing request.

Other tools. Always sample specific tenants or requests carrying a debug flag; lower rates for health checks and chatty endpoints; exemplars, which attach a trace id to a histogram bucket so a latency spike on a dashboard links straight to a real example trace; rate-limited per-service sampling to cap cost.

Caveat to say aloud. Sampling biases statistics. Counting spans in a sampled backend undercounts, so compute rates, error ratios and latency percentiles from metrics (which see every request), and use traces for examples and causes.

What types of metrics exist (counter, gauge, histogram) and why are percentiles better than averages? Intermediate
Say this: "Counters only go up and I graph their rate, gauges go up and down, histograms bucket observations so I can compute percentiles that aggregate across instances. Averages hide the slow tail, so I alert and set SLOs on p95 and p99."

The three types.

  • Counter: a cumulative number that only increases (requests_total, errors_total, bytes sent). On restart it resets to zero, which monitoring systems handle. You rarely graph the raw value; you graph its rate (requests per second), and divide two counters for a ratio (errors over requests).
  • Gauge: a value that moves both ways (queue depth, memory in use, active connections, temperature). You graph it directly, or its max.
  • Histogram: counts how many observations fell into each bucket (latency under 50 ms, under 100 ms, under 250 ms...). From buckets the backend estimates p50, p95 and p99. Because bucket counts are additive, you can sum them across instances and compute a correct fleet-wide percentile. Per-instance "summary" percentiles cannot be averaged correctly (the average of p99s is not the p99).

Why percentiles beat averages. Take 100 requests: 99 take 100 ms and 1 takes 10 s. The mean is about 199 ms and looks fine, but one user in a hundred waits ten seconds. Percentiles describe the experience of a group: p99 means 99% of requests were faster than this.

The fan-out effect. A page that calls 100 backends in parallel is as slow as its slowest call. If each call exceeds its p99 one time in a hundred, the chance that at least one is slow is 1 minus 0.99 to the power of 100, about 63%. So a page's typical experience is the backend's tail, which is why large systems care about p99 and above (the "tail at scale" problem).

Measurement pitfalls. Choose histogram buckets that bracket your SLO threshold, or resolution is poor right where it matters. Beware coordinated omission: if a load tester or server waits for a stalled request before sending the next, it never records the requests it would have sent during the stall, understating the tail. Measure at the client or load balancer as well as inside the service.

What are the RED and USE methods? Intermediate
Say this: "RED is for request-driven services: Rate, Errors, Duration, the callers' view. USE is for resources like CPU, disk or a connection pool: Utilization, Saturation, Errors, the bottleneck view. I start from RED and drill down with USE."

Why checklists help. During an incident, you have a thousand possible graphs. A fixed method tells you the few that matter for each kind of thing, so you are fast and do not forget to look at one.

Worked drill-down.

  1. RED shows checkout p99 rose from 300 ms to 2.5 s; rate is steady; errors rising slightly.
  2. Look at checkout's resources with USE. CPU 40% utilised, no saturation. Database connection pool: utilisation 100% (50 of 50 busy) and saturation 200 threads waiting. Found the bottleneck.
  3. Next USE on the database: lock waits, slow queries, disk IO.

Why saturation matters. Utilization can sit at 70% while a queue is building; saturation (waiting work) is the early warning that a resource is the limit, and latency rises sharply as saturation grows. The golden signals (next question) are RED plus saturation, so the two ideas overlap.

Business-level view. Add a few business RED-style signals too (orders per minute, successful payments), because technical metrics can be green while the business is broken.

What are the four golden signals? Basic
Say this: "From the Google SRE book: latency, traffic, errors and saturation. If you can only watch four things per service, watch those."

The four, with the subtle points.

  • Latency: how long requests take. Track successful and failed requests separately: a failed request that returns instantly (a fast 500) improves the average and hides the problem, while a slow error is doubly bad.
  • Traffic: how much demand: requests per second, sessions, messages consumed. Provides context: a latency rise at 10x traffic is a different story from one at normal traffic, and a sudden drop in traffic is itself an alarm (clients cannot reach you).
  • Errors: rate of failed requests, including explicit failures (HTTP 5xx), implicit ones (HTTP 200 with wrong content) and policy failures (anything slower than 1 s counts as an error for the SLO).
  • Saturation: how full the most constrained resource is: memory, CPU, connection pool, disk IO, queue depth. Often it is best expressed as a prediction ("disk full in 4 hours").

How it relates to others. RED covers traffic, errors and duration (latency); adding saturation gives the four golden signals; USE goes deeper on saturation for individual resources.

Using them. Put these four at the top of every service dashboard, base the first alerts and SLOs on them, and refine only when needed. They are deliberately generic: for a database you may add replication lag, for a queue consumer lag.

What is the cardinality problem in metrics? Senior
Say this: "Every unique combination of label values creates a separate time series, so unbounded labels like user id explode memory, query time and cost. Keep metric labels bounded and push high-cardinality detail into logs and traces."

How the cost arises. A metrics system stores one time series per distinct combination of a metric name and its labels. http_requests_total{service, route, status} with 20 services, 50 routes and 5 status classes gives 20 x 50 x 5 = 5,000 series: fine. Add user_id with 10 million values and the multiplication reaches billions of potential series. The index and head memory of the metrics server grow with series count, queries slow to a crawl, the process runs out of memory, and vendors that bill per series send an enormous invoice. Histograms multiply it again: every label combination gets one series per bucket (a 12-bucket histogram means 12 times more).

Rules.

  • Never use unbounded or very high-variety values as labels: user id, email, request id, trace id, full URL with ids, raw error message text, container id churn if unbounded. Use the route template /orders/{id}, not /orders/123.
  • Use bounded sets: status class (2xx, 4xx), region, tier, endpoint name, a few dozen values.
  • Put high-cardinality detail in the right tool: logs and traces (and columnar event stores built for it) are designed for per-user or per-request fields; metrics are not.
  • Per-tenant metrics: record only the top N tenants or by plan tier, or use an event store for the long tail. Exemplars link a metric to a particular trace without making it a label.
  • Guard it: alert on active series growth, set per-service series limits, drop or relabel offending labels in the collector, and review new metrics in code review.

Tell-tale incident. A deploy adds a label containing a raw path, a crawler hits random URLs, and the metrics backend falls over exactly when you need it. Sanitise at the source.

Log volume is exploding and the logging bill doubled. How do you reduce cost without going blind? Senior
Say this: "Measure first to find the few noisy producers, fix levels and remove useless lines, sample the routine successes while keeping every error and slow request, turn counting logs into metrics, tier storage by age, route by value, and add per-service quotas."

Start with data, not guesses. Group volume by service, level and message template. A typical finding is that three or four log statements generate over half the bytes (a per-item loop, a health-check access log, a retry spinning in a tight loop).

  1. Fix the levels and noise. DEBUG off in production by default, with a dynamic switch to turn it on per service for a few minutes during troubleshooting. Remove per-item loop logging and log-and-rethrow duplicates; exclude health checks and probes from access logs.
  2. Sample. Keep 100% of errors, warnings and slow or sampled-trace requests but only, say, 1 in 100 of normal successful request logs. Always sample consistently by trace id so a kept trace has all its lines.
  3. Convert to metrics. If a line exists only so someone can count or graph it ("cache hit"), emit a counter instead of millions of lines.
  4. Tier storage by age. A week or two in the hot, searchable index; then cheap object storage with slower query; then delete per retention policy. Compress; drop unused or oversized fields (stack trace repeated on each line).
  5. Route by value. Audit and security logs retained for years in cheap, durable storage; ordinary debug logs for days. Do not send everything to the most expensive index.
  6. Guardrails. Per-service volume quotas and alerts on sudden growth (a new release doubling volume), cost shown to the owning team.

Worked example. 2 TB per day at 3 USD per GB-ish indexed cost is painful. Dropping health-check logs (30%), 1% sampling of INFO success (35%) and tiering after 7 days can cut index volume by well over half while keeping every error. (Numbers are illustrative.)

Do not go blind. The failure you must debug is often the one you sampled away: keep errors, slow requests and a small random baseline, and keep the ability to raise detail temporarily. Do not delete without checking who reads it (alerts, audit needs).

How do you keep sensitive data out of logs and telemetry? Intermediate
Say this: "Logs are copied widely, kept long and read by many, so a password or card number in a log is a breach. I never log bodies or auth headers by default, allowlist what is logged, redact at the logger and again at the collector, and restrict and expire log access."

Why logs are a favourite leak. Developers add log.info("request: " + body) while debugging and forget it. Those lines flow to a central system, backups, a vendor, dashboards and screenshots, with broad access and long retention, and are not covered by the controls on your production database. Compliance rules (GDPR, PCI DSS) treat that as exposure.

Layers of defence.

  1. Do not log it in the first place. No request or response bodies, no Authorization headers, cookies or tokens by default. Log ids and outcomes, not content.
  2. Allowlist, not blocklist. Build log events from explicit, approved fields; a blocklist of "password" misses pwd, secret_answer and the next field someone invents.
  3. Typed wrappers. Use types that redact themselves: a Secret or Pii wrapper whose string form is ***, so accidental logging is safe.
  4. Redact at the logger by key (password, token, authorization, ssn, card) and by pattern (card number regex with Luhn check), then scrub again in the collector as a second net.
  5. Use ids rather than names or emails, and hash or truncate where a join key is needed.
  6. Detect: periodic or CI scans of sampled logs for sensitive patterns; alert on matches.
  7. Control and retention: restrict access to production logs by role, audit searches, and keep logs that may contain personal data only briefly.

Also remember traces (SQL statements and URLs captured as span attributes can include values), metrics labels, error trackers and crash dumps. If a leak happens, treat it as an incident: purge or re-index the data, rotate leaked credentials.

What makes a good dashboard? Intermediate
Say this: "A good dashboard answers one question. The service overview says 'is it healthy right now?' with the golden signals on top, then dependencies and resources, in a hierarchy from business view to component detail, with deploy markers and percentiles rather than averages."

Why most dashboards fail. They grow by accretion: every incident adds a graph, until there are 60 panels, no one knows which matter, and during an outage the reader is hunting instead of reading. A dashboard is an interface for a person under stress; design it for that moment.

  • One question per dashboard. The overview answers "is this service healthy?"; a separate deep-dive board per component answers "why is the cache slow?".
  • Hierarchy and drill-down: a top-level business and SLO view (orders per minute, error budget remaining), then per-service boards, then per-component, with links between them.
  • Order by importance. User-facing symptoms first (rate, errors, latency percentiles), dependencies next, resource saturation last.
  • Show rates, ratios and percentiles, not raw counters and averages. Include the SLO threshold line on the graph so "bad" is visible without arithmetic.
  • Annotate events: deploys, feature flag changes, config pushes and incidents as vertical markers, so cause and effect line up.
  • Compare to the past: overlay the same time last week, because many metrics are seasonal.
  • Readable: labelled axes and units, sensible time ranges, consistent colours (red means bad everywhere), template variables for service, region and environment instead of copy-pasted boards.
  • Ownership and pruning: every dashboard has an owner and is reviewed; one nobody opens during incidents should be deleted. Dashboards complement alerts; they should not be the way you find out about problems.
Scenario: users say checkout got slow. Walk through how you investigate using observability data. Senior
Say this: "Mitigate first, diagnose second: the goal during an incident is to restore the user experience, not to find the elegant root cause. I scope with metrics, locate with traces, explain with logs, and revert the likely change while I investigate."
  1. Scope it. On the RED dashboard for checkout: since when, which percentile moved (p50 or only p99), which endpoints, regions, tenants, client versions. Look at deploy, config and feature flag markers around the start time; a step change right after a marker is a strong lead.
  2. Find the hop. Open a few slow traces (tail-sampled ones are ideal). Which span grew? Suppose payment-svc calling the external processor went from 240 ms to 3 s while everything else is unchanged.
  3. Check dependencies and resources with USE. Is the connection pool saturated? Thread pool queue growing? CPU throttled by container limits? Garbage collection pauses? Database slow-query log, lock waits, replication lag? Is the third party's status page red?
  4. Read logs for the affected trace ids: timeouts, retries (a retry storm multiplies load), circuit breaker open or closed, connection pool exhaustion messages.
  5. Mitigate before you fully understand. Options in rough order of speed and safety: roll back the suspect change, flip a flag, fail over to a secondary processor, scale out or shed low-priority load. Announce status in the incident channel.
  6. Confirm recovery on the SLI (p99 back below target), not on someone's feeling, then keep the evidence and write the timeline for the post-mortem.
  7. Follow up: why did alerts not catch it before users did? Add an alert on the SLI, add timeouts and a circuit breaker on the external call, and maybe a fallback processor.

SLIs, SLOs and alerting

What are SLI, SLO and SLA? Give a concrete example. Basic
Say this: "The SLI is the measurement, the SLO is the internal target for it, the SLA is the contractual promise with penalties, set looser than the SLO. Example: SLI is the fraction of checkout requests succeeding under 500 ms, SLO is 99.9% over 30 days."

Why they exist. "The system should be reliable" is not testable. These three terms turn reliability into numbers that engineers, product and customers can agree on, and that tell you when to stop shipping features and fix things.

  • SLI (service level indicator): a measured number describing user experience, as a ratio of good events to total events. Example: (checkout requests with status below 500 and latency under 500 ms) / (all checkout requests).
  • SLO (objective): the internal target for the SLI over a window. Example: 99.9% over a rolling 30 days.
  • SLA (agreement): the external contract with consequences (service credits, refunds) if missed, e.g. 99.5%. It is looser than the SLO so that you notice and react well before you owe money.
SLOAllowed downtime per 30 days

Choosing good SLIs. Measure what users feel: availability, latency, correctness, freshness (for pipelines), durability (for storage). Measure at the edge or load balancer, or from the client, not CPU. Pick few (two or three per service).

Reality checks.

  • Each extra nine costs far more than the last, and users often cannot perceive the difference (their own network is less reliable than 99.99%).
  • Dependencies cap you: if a request needs three serial services each at 99.9%, the best you can promise is about 0.999 cubed, roughly 99.7%.
  • 100% is the wrong target. It is infeasible, and it leaves no room for change.

Pitfall. Averaging across all users or all endpoints can hide that one important customer or critical endpoint is failing; define the SLI per critical user journey.

What is an error budget and how does it change behaviour? Intermediate
Say this: "The error budget is 100% minus the SLO: the amount of unreliability you are allowed. While there is budget left we ship and take risks; when it is spent we slow releases and invest in reliability. It replaces opinion fights with data."

The tension it resolves. Product wants to ship quickly, operations wants stability, and each side argues from feelings. The error budget gives both a shared number. A 99.9% monthly SLO leaves 0.1%: about 43 minutes of full outage, or one failed request in every thousand.

How it is used, with a timeline.

  1. Month starts with 43 minutes of budget.
  2. A bad deploy burns 30 minutes in week one; 13 minutes remain.
  3. The team's policy, agreed in advance, says: with under 25% of the budget left, only reliability fixes and low-risk changes ship, risky launches wait.
  4. The budget recovers as the window rolls, and normal velocity resumes. If the budget is unused month after month, the SLO is too tight or the team is too cautious: ship faster or loosen it.

What it changes. Reliability becomes a shared, spendable resource. Risky experiments (chaos tests, big migrations) are allowed when budget exists. It justifies investing in automation when toil or incidents repeatedly burn budget, and gives a principled reason to say no to a launch. It also drives alerting: alerts fire based on how quickly budget is being consumed (the burn rate), see the alert design question.

Pitfalls. A policy without leadership backing is ignored. Counting planned maintenance or client-caused errors as budget burn demotivates teams; define exclusions up front. Budget on a single global number can hide a tenant who is entirely down.

How do you design alerting that does not page for noise? Senior
Say this: "Page only on user-visible symptoms or fast error-budget burn, and only when a human must act now. Use multi-window burn-rate alerts, group and dedupe, link a runbook, and review every noisy alert after each on-call week."

Why noise is dangerous. If most pages are false or unactionable, on-call engineers stop trusting them (alert fatigue), respond slowly to the real one, burn out and leave. A good alert has three properties: urgent, actionable, and about something users care about.

  • Page on symptoms, not causes. Page when users are hurt or the budget is burning ("checkout error ratio breaches SLO"), not when CPU is 85% or one pod restarted. Causes belong on dashboards and tickets.
  • Multi-window, multi-burn-rate alerts. Burn rate is how fast you consume the budget: 1x means exactly on target for the window; 14x means the whole 30-day budget would vanish in about 2 days. A common recipe from Google's SRE workbook: page when the burn rate exceeds about 14x over both 1 hour and 5 minutes (about 2% of a monthly budget gone in an hour); page or ticket at about 6x over 6 hours and 30 minutes; ticket at 1x over 3 days. The long window avoids flapping on blips; the short window makes the alert clear quickly after recovery.
  • Duration clauses, hysteresis and aggregation so one blip or one bad host does not page.
  • Dedupe and group. One incident, one page, not 200: group by service and cause, and suppress downstream alerts when a known dependency (the database) is down.
  • Context in every alert: what is broken, impact, a dashboard link, and a runbook with first steps; severity routes (page, chat, ticket).
  • Hygiene: after each on-call week review every page; delete or fix any that fired without action; track pages per shift (a common target is at most about two incidents per 12-hour shift).
  • Alert on absence of data (a dead-man's switch that must fire constantly) so a broken metrics pipeline is not mistaken for "all green".

Example. Instead of "5xx above 1% for 5 minutes", which pages on a brief blip and misses a slow steady leak, use burn-rate rules on the 99.9% SLO: fast burn pages immediately, slow burn creates a ticket before the budget is gone.

Why is "CPU above 80% for 5 minutes" often a bad page? Intermediate
Say this: "It alerts on a cause, not a symptom. High CPU may be healthy and users see nothing wrong, while a real outage can occur at low CPU. I would page on the SLI and keep CPU as a diagnostic graph or a low-urgency capacity ticket."

False positives. A well-sized service is expected to use its CPU. Batch jobs, GC, compression or a warm cache all push CPU up briefly. If latency and errors are fine and autoscaling is adding capacity, a page wakes someone for nothing.

False negatives. The failures that hurt often do not involve CPU at all: a deadlock (CPU near zero, requests hanging), a full connection pool, a downstream timeout, a bad config, an expired certificate, a memory leak ending in OOM. A CPU alert stays silent during all of them.

What to do instead.

  1. Page on the symptom: error ratio and latency SLI, or budget burn.
  2. Keep CPU, memory and saturation on dashboards for diagnosis (USE method).
  3. Use a ticket or chat alert for slow capacity trends ("p95 CPU above 70% for a week, plan scaling").

Exceptions worth a predictive page. Resources with hard cliffs, no warning and no automatic remedy: disk predicted to fill within a couple of hours (alert on the projected time to full), a TLS certificate expiring in 7 days, a database nearing the transaction-ID wraparound or connection limit. These are causes, but they are reliably followed by user-visible failure and need a human.

The principle to state. Cause-based alerts multiply (one per resource per host), symptom-based alerts are few and meaningful.

Black-box versus white-box monitoring, and what are synthetic checks? Intermediate
Say this: "White-box uses internal metrics the service exposes and finds causes and impending trouble. Black-box tests from outside as a user would and finds what is actually broken for users. Synthetic checks are scripted user journeys run on a schedule from several regions. I use black-box to detect and white-box to diagnose."

White-box. The service reports on itself: error counters, queue depth, cache hit ratio, thread pool usage. It sees inside, so it can warn early ("queue growing") and tell you why. Its blind spot: anything outside the process. If DNS is broken, the CDN is down, a certificate expired or a firewall rule blocks the load balancer, the service's own metrics may look perfect because no requests arrive at all.

Black-box. A probe outside the system calls it like a user would, e.g. an HTTP check from three regions every minute that expects a 200 and a body containing a known string. It sees what the user sees, including DNS, TLS, CDN, routing and the network path.

Synthetic checks (probes or synthetic monitoring). Scripted journeys: log in, search, add to cart, check out with a test card, then verify the order. They matter especially:

  • for low-traffic paths and at 3 a.m., where no real user traffic exists to reveal a break;
  • to measure availability and latency from each region independently (a regional ISP or edge problem);
  • to verify the end-to-end flow after each deploy, as a release gate.

Cautions. Use dedicated test accounts and mark synthetic traffic so it does not pollute business metrics or fire real shipments. Keep probes cheap, and make the check meaningful (assert on content, not just "port open"). Probes can also fail on their own, so run them from more than one location before paging.

Rule. Black-box tells you users are hurt; white-box tells you why. Real user monitoring (RUM) from browsers and apps fills the gap between the two.

On-call, incident response and post-mortems

How is a well-run incident handled from page to resolution? Intermediate
Say this: "Detect, declare with a severity, assign roles (commander, ops lead, comms lead, scribe), mitigate first and investigate later, communicate on a fixed cadence, verify recovery against the SLI, then run a blameless post-mortem and track the actions."

Why a process. Under pressure, ten engineers all debugging in parallel, nobody talking to customers and no record of what was tried makes incidents longer and messier. Defined roles and steps remove the improvisation.

  1. Detect and acknowledge. An alert reaches the on-call, who acknowledges within minutes. If not acknowledged, it escalates to the secondary.
  2. Triage and declare. Quick assessment of impact; set severity (for example Sev1 = major user-facing outage or data risk, Sev3 = minor). Open a dedicated incident channel and a call. Declaring early is cheap; a late declaration is not.
  3. Name roles.
    • Incident commander: coordinates, decides, delegates; does not debug, which keeps the big picture.
    • Operations / tech lead: hands-on diagnosis and fixes, pulling in experts.
    • Communications lead: status page, customer support and stakeholder updates.
    • Scribe: keeps the timeline of actions with timestamps.
  4. Mitigate first. Fastest safe action: roll back, flip a flag, fail over, scale out, shed load, block bad traffic. Root-cause analysis can wait until users are no longer hurt.
  5. Communicate on a regular cadence (every 15 to 30 minutes) even if the update is "no change", so stakeholders do not interrupt the responders.
  6. Resolve and verify that the SLI has recovered, not merely that the fix was deployed; then stand the incident down and note follow-ups.
  7. Post-mortem within days, with tracked action items.

Practices that help. One person at a time changes production, and says so in the channel; hand off the commander role explicitly during long incidents; keep a runbook per alert; avoid heroics and fatigue (rotate people after a few hours).

What is a blameless post-mortem and what goes in it? Intermediate
Say this: "A written review focused on how the system and process allowed the failure, not on who erred. People who are not afraid of blame tell the whole truth, so you find real causes and prevent the whole class of failure. Its value comes from tracked, completed action items."

Why blameless. If engineers are punished for mistakes, they hide them, shade the timeline and avoid risky but necessary work. Then you never learn. "Human error" is a symptom: ask why the system made the error easy and why nothing caught it (no confirmation, no staging check, an unclear runbook, a missing alert).

Typical contents.

  • Summary and impact: duration, affected users or tenants, money, error budget consumed.
  • Timeline with timestamps: first symptom, detection, key decisions, mitigation, recovery.
  • Detection: how long until we knew, and who told us (alert or customer)?
  • Root cause and contributing factors: usually several, found with a causal chain or "five whys". For example: a config change (trigger) went to all regions at once (no staged rollout), a validation was missing, and the alert fired on CPU not errors.
  • What went well, what went badly, where we got lucky.
  • Action items: each with an owner and due date, grouped as prevent (stop recurrence), detect (find sooner) and mitigate (reduce impact), tracked in the ticket system.

Time metrics. MTTD (mean time to detect), MTTA (to acknowledge) and MTTR (to restore or recover). Reducing detection and mitigation time usually pays more than trying to reach zero failures.

Pitfalls. A post-mortem with no follow-through is theatre; a single "root cause" like "engineer typo" ends the thinking too early; sharing it widely and in a standard format spreads learning across teams.

How do you keep on-call sustainable? Intermediate
Say this: "Reasonable rotation size, primary and secondary, follow-the-sun where possible, a runbook for every alert, measured and reduced alert noise, compensation, and engineering time reserved to remove the causes of repeated pages."

Why it matters. On-call burnout causes attrition and worse incidents: a tired engineer makes mistakes. Sustainable on-call is a reliability feature for the whole organisation.

  • Rotation design: weekly shifts with a primary and a secondary (backup and escalation). A rotation of about 6 to 8 people means each person carries the pager roughly one week in six to eight. Smaller rotations burn people out; larger ones lose familiarity. Where teams span time zones, use follow-the-sun so nobody is paged at 3 a.m. routinely.
  • Fair compensation: on-call pay or time off in lieu, and no work expectations right after a night of pages.
  • Runbooks and escalation: every alert links to a runbook with first steps; clear escalation path; handover notes between shifts so context is not lost.
  • Measure and cut noise: track pages per shift, off-hours pages, repeat alerts and time spent on toil. Reserve engineering time (a percentage of each sprint) to fix recurring causes and automate away manual fixes. Google's guidance is to cap operational work (toil) at roughly half of an engineer's time.
  • Ownership: "you build it, you run it" keeps developers close to the pain, which improves design, provided the load is bounded.
  • Training: new joiners shadow, then reverse-shadow (they lead, a veteran watches); game days and drills build confidence.
  • Culture: no heroics, blameless reviews, and permission to escalate early.
Name real outages that teach design lessons. Senior
Say this: "The recurring themes are that config changes are as dangerous as code, rollouts must be gradual, the recovery path must not share a failure domain with the thing that broke, and untested backups are not backups. I can cite S3 2017, GitLab 2017, Cloudflare 2019, Facebook 2021, CrowdStrike 2024 and Knight Capital 2012."

All of these are from public post-mortems. Details are hedged to the headline; if asked for more, say you recall the outline and not the specifics.

  • AWS S3, US-East-1, February 2017. During debugging, an operator ran a command intended to remove a small number of servers from a subsystem; the input removed a larger set than intended. Dependent subsystems needed restarts, which took hours, and many sites, including parts of the AWS status dashboard, were affected. Lessons: guardrails and minimum-capacity limits on dangerous commands, smaller blast radius per command, and do not host your status page on the thing that is down.
  • GitLab database incident, January 2017. While repairing replication, an engineer removed the data directory on the wrong database host; several backup mechanisms turned out not to be working. Lessons: test restores, not just backups; be careful with destructive commands under stress; transparency in the post-mortem builds trust.
  • Cloudflare, July 2019. A regular expression in a WAF rule triggered catastrophic backtracking and pegged CPUs across the global network. Lessons: staged rollout for configuration too, resource limits on rule evaluation, and a global kill switch.
  • Facebook, October 2021. A routine backbone maintenance command withdrew the BGP routes to its DNS servers, taking apps offline for hours; internal tools, even physical access, depended on the same network, slowing recovery. Lessons: audit tooling that validates changes before applying, out-of-band access, and recovery tooling independent of the failing system.
  • CrowdStrike, July 2024. A faulty content update to a security agent crashed a very large number of Windows machines worldwide. Lessons: staged or canary rollout even for "content" updates, validation, and a way to recover without hand-fixing each machine.
  • Knight Capital, 2012. A deployment reached only some servers, and old code behind a repurposed flag became active on one of them, causing very large trading losses within about an hour. Lessons: consistent automated deployments, removing dead code and flags, kill switches.

Common themes to state. Config is code. Roll out gradually with automatic rollback. Recovery paths must not depend on the broken system. Backups must be restore-tested. Blameless transparency helps the whole industry.

CI/CD, configuration and safe rollouts

What does a CI/CD pipeline for a service look like? Basic
Say this: "Every commit is built and tested automatically; one immutable artifact is built once and promoted through environments; production rollout is progressive with automatic health checks and rollback. The goal is frequent, small, boring deploys."

The three terms. Continuous integration (CI): every change is merged to the main branch often (at least daily) and automatically built and tested. Continuous delivery: every merged change produces a deployable artifact that can go to production at the push of a button. Continuous deployment: it goes to production automatically when all checks pass.

Why. Big, rare releases are risky: many changes at once, hard to find which one broke things, painful to roll back. Small frequent changes are easy to review, test and revert.

  1. Commit and review: pull request, lint, unit tests, static analysis, dependency vulnerability scan and secret scan.
  2. Build one immutable artifact (for example a container image tagged with the commit sha), sign it, push it to a registry. Build once, promote the same artifact through environments, so what you tested is exactly what you ship. Configuration differs by environment, the binary does not.
  3. Deploy to staging: integration tests, contract tests against dependencies, smoke tests.
  4. Progressive production rollout (canary or rolling) with automated checks against SLIs, and automatic rollback on regression.
  5. Post-deploy verification: synthetic checks, a deploy marker on dashboards, and a notification.

Principles. Fast feedback (main checks in about 10 minutes, otherwise people stop waiting); reproducible builds; the pipeline defined as code; flaky tests fixed or quarantined, not ignored; deploys decoupled from releases via feature flags.

Measuring delivery: the four DORA metrics: deployment frequency, lead time for changes, change failure rate and time to restore service. Elite teams do well on both speed and stability, which shows they are not a trade-off.

How do you manage configuration across environments? Intermediate
Say this: "Keep config out of the code so the same artifact runs everywhere, version it in git with review, keep secrets in a secrets manager, validate it at startup and in CI, and roll config changes out as carefully as code, because many big outages come from config pushes."

Principle. The twelve-factor approach: strict separation of config (what changes between deploys: database URLs, timeouts, feature toggles, endpoints) from code. The same image runs in dev, staging and prod, and the environment supplies values through environment variables, mounted files or a config service.

  • Versioned and reviewed: config lives in git (GitOps) with code review, history, blame and rollback. Secrets are the exception and go in a secrets manager, referenced by name.
  • Layering: sensible defaults in the app, environment-level overrides, and per-instance or per-tenant overrides only where truly needed. Keep environment differences small and explicit to avoid "works in staging, breaks in prod".
  • Validate: a typed schema; check at startup and fail fast on a bad or missing value rather than limping; lint and dry-run in CI.
  • Dynamic versus static: values that should change without a restart (timeouts, rate limits, flags) are watched from a config service or reloaded; structural ones (ports, database URLs) change with a deploy. Dynamic config is powerful and dangerous, since a bad value takes effect everywhere instantly.
  • Roll out like code: staged (one cell or canary first), observable, with a one-step revert. Many large outages in public post-mortems came from configuration pushes, not code.
  • Audit and drift: know who changed what; detect when running config differs from git.

Example. Changing a request timeout from 2 s to 200 ms goes through a pull request, applies to 5% of instances for 15 minutes while error rate is watched, then widens. If it spikes timeouts, one revert restores it.

What are feature flags and what are the pitfalls? Intermediate
Say this: "A feature flag is a runtime switch that changes behaviour without a deploy, decoupling deployment from release. I use them for gradual rollout, kill switches and experiments, and I manage flag debt, test combinations, and make flag evaluation resilient."

What and why. Instead of releasing code by deploying it, you deploy the code turned off and expose it by changing a flag, evaluated per user, tenant, percentage or region. If something goes wrong you flip the flag back in seconds rather than rolling back a build.

Uses.

  • Gradual rollout: 1%, 10%, 50%, 100% while watching SLIs.
  • Kill switch: disable a risky feature or an expensive dependency instantly.
  • Experiments (A/B tests) and per-customer entitlements.
  • Trunk-based development: merge unfinished work hidden behind a flag.
  • Operational flags: shed load during an incident (turn off recommendations, switch to read-only mode).

A tiny example.

if (flags.isOn("new-pricing", user)) { return newPricing(cart); }
return oldPricing(cart);   // delete this branch once rollout is done

Pitfalls.

  • Flag debt: stale flags multiply code paths and bugs. Give every release flag an owner and an expiry, and remove the flag and dead branch after rollout. Knight Capital is the cautionary tale of reusing an old flag.
  • Combinatorial testing: n flags mean up to 2 to the power n states; keep live flags few and independent, and test the important combinations.
  • The flag service as a dependency: evaluate from a locally cached ruleset with a safe default if the flag service is down; never block requests on it.
  • Consistency: a user should get a stable variant (hash of user id and flag name), and flags across services in one request should agree.
  • Governance: flipping a flag is a production change; audit who changed what and when, and alert on it.
Compare rolling, blue-green and canary deployments. Intermediate
Say this: "Rolling replaces instances gradually; blue-green stands up a full second environment and flips traffic; canary sends a small share to the new version first and grows it while watching SLIs. Blue-green gives the fastest rollback, canary limits exposure, rolling is the cheap default."

What problem they solve. Deploying new code to everyone at once means a bug hits everyone at once. These strategies all reduce that risk, trading off speed, cost and complexity.

  • Rolling: with 10 instances, replace 2 at a time, waiting for readiness. Uses almost no extra capacity, but for a while old and new versions are both live, and rollback means rolling again (slow).
  • Blue-green: build a complete second environment (green) running v2 beside the live one (blue), test it with synthetic traffic, then switch the router. If anything is wrong, switch back instantly. Costs double capacity during the switch, and the flip exposes 100% of users at once.
  • Canary: send 1% to 5% of real traffic to v2, compare its error rate and latency with the baseline (automated canary analysis), then grow stepwise. A bug harms only the canary share, and rollback is setting the canary weight to 0.

When should you roll back versus roll forward? Intermediate
Say this: "Default to rollback during an incident when the deploy is the likely cause and it is reversible, because it is the fastest, best-understood action. Roll forward when rollback is unsafe: data already migrated or written in a form the old code cannot read, or when a trivial fix can ship faster than a revert."

Why rollback is the default. In an incident you want to restore service with the least new risk. The previous version is known and was working. A revert needs no new thinking, whereas a quick fix is untested code written under stress.

When rollback is unsafe or impossible.

  • A migration already dropped or reshaped data the old code needs.
  • New code already wrote data (new enum values, a new message format, a new cache entry layout) that the old code cannot parse, so rolling back would turn a partial bug into a total failure.
  • External side effects happened (emails sent, payments captured, a consumer already processed events with new semantics).
  • The fix is a one-line change that the fast pipeline can ship in minutes with confidence, and the old version has its own known bug.

How to keep rollback possible.

  1. Make every change backward compatible (expand and contract migrations; tolerant readers).
  2. Use feature flags so you can disable behaviour without redeploying, which is often faster than either option.
  3. Keep the previous artifact deployable and prove rollback works regularly (rehearse it).
  4. Use canary with automated analysis that rolls back by itself on SLI regression, removing the human delay.

Example decision. A deploy at 10:00 adds a column and new code writing to it; errors begin at 10:05. Because the column is additive and old code ignores it, rollback is safe: do it, then investigate. If the same deploy had instead migrated 40 million rows to a new format, rollback needs a reverse migration first, so a forward fix may be safer.

How do you change a database schema with zero downtime? Senior
Say this: "Use expand and contract so old and new code both work at every step: add the new structure, write to both, backfill in batches, switch reads, stop writing the old one, and only later remove it. Use online DDL tools and lock timeouts for the risky operations."

Why it is hard. During a rolling deploy two versions of the application run at the same time against one database. A rename or drop that old code does not understand breaks it instantly. And some DDL statements take locks that block reads and writes on a big table for minutes. So you must change the schema in small, individually safe, backward-compatible steps (a parallel change).

Example: rename column name to full_name.

  1. Expand: add a nullable full_name column (cheap, no table rewrite in most engines).
  2. Deploy code that writes both columns and still reads the old one. Both old and new app versions are now valid.
  3. Backfill old rows in small batches (for example 1,000 rows at a time with a short sleep, resumable, watching replication lag), so you do not saturate the primary or replicas.
  4. Deploy code that reads the new column (optionally compare old and new values with shadow reads to verify).
  5. Stop writing the old column, deploy, and wait a safe period (a week) so a rollback is still possible.
  6. Contract: drop the old column in a later release.

Dangerous operations. Adding a column with a default, creating an index, or adding a constraint can lock a large table, depending on engine and version. Use online variants: for example CREATE INDEX CONCURRENTLY in PostgreSQL; online schema change tools such as gh-ost or pt-online-schema-change for MySQL (which copy the table in the background and swap). Check your engine's current behaviour, since newer versions avoid some rewrites. Add constraints as not valid first, then validate separately.

  • Run migrations as a separate pipeline step from the app deploy; version them with Flyway or Liquibase; keep them forward-only in production.
  • Never combine a breaking schema change and the code that needs it in one deploy; always ensure versions N and N+1 are compatible.
  • Test on production-sized data, take a snapshot or backup first, and set lock timeouts so a migration that cannot get its lock fails fast instead of queuing behind a long transaction and blocking everyone.
How do you keep services and messages compatible during rolling deploys? Senior
Say this: "Add, never remove or repurpose; make new fields optional with defaults; consumers ignore unknown fields; sequence the rollout so readers understand a field before writers send it; version for breaking changes; enforce with schema-registry checks and contract tests."

The problem. During a rolling deploy and any rollback, version N and N+1 coexist and talk to each other: N+1 calls an N service, an N producer publishes a message an N+1 consumer reads. In an event-driven system messages may sit in Kafka for days, so even a later consumer must understand old data. Compatibility must hold in both directions: backward (new reads old) and forward (old reads new).

Rules.

  • Add, never remove or repurpose a field. Changing the meaning of an existing field is a silent break (two versions interpret the same value differently).
  • New fields are optional with a safe default, so old data and old clients still work.
  • Tolerant reader: consumers ignore unknown fields and unknown enum values instead of failing.
  • Order the rollout. To add a field: deploy consumers that understand it first, then producers that send it. To remove a field: stop producers sending it, wait until nothing reads it, then remove it from consumers, then from the schema.
  • Version breaking changes: publish /v2 or a new event type and run both until traffic drains and clients migrate; announce deprecation timelines.
  • Automate checks: a schema registry with compatibility modes for Avro or Protobuf enforced in CI, and consumer-driven contract tests (Pact) so a provider learns it would break a consumer before merging.

Easily forgotten places. Cache entry formats (a new version writes an object the old version cannot deserialise), serialised Java objects, queued jobs and database JSON columns all outlive a deploy. Include the schema version in them and handle several versions.

Example. Add currency to a payment event: make it optional defaulting to USD; update all consumers; then update producers; finally make it required in the next major version once all old messages have aged out of retention.

Scenario: 10 minutes after a deploy the error rate climbs from 0.1% to 4%. What do you do? Intermediate
Say this: "Check whether the climb lines up with the deploy marker; if so, roll back or flip the flag immediately without waiting to understand, confirm recovery, preserve evidence, find the cause offline, and then ask why canary and pre-prod did not catch it."
  1. Correlate. Compare the deploy marker with when errors began. Also check other changes at the same time: config pushes, flag flips, a dependency's status, a traffic spike, an expiring certificate. If the deploy fits, act at once: roll back (or turn the new feature's flag off) and say so in the incident channel. Do not delay mitigation to investigate; every minute is 4% of your users failing.
  2. Confirm the SLI recovers after the rollback. If it does not, the deploy was not the (only) cause; widen the search to dependencies, infrastructure and data.
  3. Preserve evidence from the bad version before it disappears: logs, a heap or thread dump, and ideally keep one canary instance out of rotation for inspection. Capture a few failing request ids and traces.
  4. Find the cause offline. Diff the change, reproduce in staging with production-like data, and write a regression test that would have failed.
  5. Ask why it escaped. Did the canary have too little traffic? Different data or config in pre-prod? Missing test? Was the alert threshold right? How long from first error to rollback?
  6. Improve the system: automated canary analysis with auto-rollback so the next regression is stopped at 1% of traffic, plus a post-mortem with owned actions.

Edge case worth stating. If the new version already ran a migration or wrote incompatible data, rollback may be unsafe; that is why backward-compatible changes matter.

Trunk-based development versus long-lived branches, and why does it matter for delivery? Intermediate
Say this: "In trunk-based development everyone merges small changes to the main branch at least daily and hides unfinished work behind flags, so integration is continuous and main is always releasable. Long-lived branches delay integration and make merges risky."

The mechanism of the problem. A feature branch kept for three weeks diverges from main while other people change the same code. When it finally merges, conflicts are large, semantic conflicts (code that compiles but behaves wrongly together) appear late, and the whole feature is tested together at the last moment. The time between writing code and discovering that it fails grows, and so does the cost of fixing it.

Trunk-based practice.

  • Branches live hours to a day or two, merged by small pull requests with fast automated checks.
  • Unfinished work ships dark behind a feature flag (or via branch by abstraction: add the new implementation beside the old and switch later).
  • Main is always green and always deployable; a broken build is fixed or reverted immediately.
  • Releases are cut from trunk (tag or short-lived release branch for hotfixes only).

Capacity, autoscaling, cost and infrastructure as code

How do you do capacity planning? Intermediate
Say this: "Model peak demand with growth and headroom, load test one instance to find its knee, divide with a safety margin, add redundancy for instance and zone failure, find the next bottleneck, and re-check regularly with load and failover tests."

Why. Too little capacity means outages at peak; too much wastes money. Capacity planning replaces guessing with a repeatable calculation, and it is what interviewers expect behind every "how many servers?" question.

  1. Model demand. Take current average and peak rates, the growth trend, daily and weekly seasonality and known events (a sale, a launch, month-end). Plan for peak, not average, plus headroom (often 30 to 50%) for surprises.
  2. Know the capacity of one unit. Load test one instance until latency rises sharply, the "knee" of the curve (for example 800 requests per second at p99 under 200 ms; beyond that queues build). Do not run at 100% of the knee: target 60 to 70%, because queueing delay explodes near saturation.
  3. Compute the fleet. Peak 20,000 requests per second divided by (800 x 0.7 = 560 per instance) is about 36 instances.
  4. Add redundancy. Instance failures and deploys need N+1 or N+2. For zone failure: with 3 zones, if one dies the other two carry the whole load, i.e. 1.5 times each zone's normal share, so each zone must normally run at no more than about 66% of what it can handle. That means roughly 50% over-provisioning against the minimum.
  5. Find the next bottleneck. Compute is rarely the limit: database connections and IOPS, cache memory, network bandwidth, message broker throughput, third-party rate limits, cloud account quotas and IP address space all bite. Scale the whole chain, not only the front.
  6. Review and test. Revisit monthly or before big events; alert on saturation trends ("pool at 80% for a week"); run load tests and failure drills, including a regional failover, before the peak.

Back-of-envelope example. 10 million daily users, 20 requests each: 200 million per day is about 2,300 requests per second average; with a 5x peak factor, about 11,500. State assumptions aloud, because the process matters more than the exact number.

Pitfall. Planning on average load and discovering the p99 peak, retry storms or a cache-cold restart needs three times more.

How does autoscaling work and what can go wrong? Intermediate
Say this: "Autoscaling adds or removes instances based on a metric, on a schedule, or from a forecast. Scale out eagerly and in cautiously, scale on leading indicators, and remember it only helps the tier you scale: protect the database, cap the maximum and keep headroom."

Types.

  • Reactive: track a target metric. For example the Kubernetes Horizontal Pod Autoscaler keeps average CPU near 60%, or requests per pod near a value, by adjusting replicas: desired = ceil(current x currentMetric / target). Cloud auto scaling groups work similarly; KEDA scales on event sources such as queue depth.
  • Scheduled: scale up before known peaks (every weekday at 08:30).
  • Predictive: forecast from history and scale ahead.
  • Scale out quickly, scale in slowly with cooldown periods to avoid flapping.

Failure modes.

  • Too slow. A new instance takes minutes to schedule, boot, pull the image and warm caches; a spike hits first. Fixes: scale on leading indicators (queue depth, request rate), keep headroom, pre-warm, small images, fast startup, scheduled scaling for known peaks.
  • Wrong metric. CPU is meaningless for an IO-bound service waiting on a database; scale on in-flight requests, latency or queue length.
  • Scaling the wrong tier. Adding 50 web instances sends 50 times the connections to a database that cannot scale out, and makes it fall over; the bottleneck just moved down and caused a cascade. Use connection pool limits, backpressure and load shedding.
  • Flapping. Tight thresholds cause constant up and down. Use stabilisation windows and different thresholds for out and in.
  • Cost blow-ups. A bug or an attack can scale to the maximum; set max limits, budgets and alerts. Attack traffic that triggers scaling is a denial-of-wallet.
  • Stateful services scale poorly: they need data rebalancing, shard moves or leader election, so plan them manually or with operators.
  • Limits: cloud quotas, lack of capacity of a given instance type in a zone, and slow node provisioning behind pod autoscaling.

Also consider vertical scaling where sensible (simpler, up to a limit), and test autoscaling in staging with realistic load shapes, not only steady ramps.

What are load shedding and backpressure, and how do they protect a service? Senior
Say this: "When demand exceeds capacity, accepting everything makes everyone slow and then collapses the service. Load shedding rejects some work early and cheaply so the rest succeeds. Backpressure pushes the limit upstream with bounded queues and clients that back off with jitter."

The collapse pattern. A service at capacity queues requests. Queue wait grows, responses become slower than client timeouts, clients retry, retries add load, and the service spends all its effort on requests whose callers have already given up. Throughput (useful work) drops to near zero even though the servers are busy. Once triggered, it can persist after the original spike ends: a metastable failure.

Load shedding. Decide to reject some requests deliberately and early, for example return 503 or 429 immediately when in-flight requests exceed a limit or queue wait exceeds a threshold. Choose what to drop:

  • Low-priority traffic first (batch, background, anonymous) over interactive and paying customers.
  • Expensive requests over cheap ones.
  • Requests already too old to be useful: if a request has waited longer than the client timeout, answering is wasted work (use deadline propagation or a request timestamp).

Prefer fail-fast with a clear signal to a slow death.

Backpressure. Push the limit upstream instead of absorbing it: bounded queues that reject or block producers when full; reactive streams demand signalling; Kafka consumers pausing; TCP's own window. Clients cooperate with exponential backoff plus jitter (random delay so retries do not synchronise into waves) and honour Retry-After.

Supporting measures. Timeouts everywhere; circuit breakers that stop calling a failing dependency; retry budgets (retries limited to, say, 10% of traffic so retries cannot multiply load by 3x); concurrency limits per dependency; priority queues; graceful degradation (serve cached or partial results).

Example. Capacity is 1,000 requests per second but 1,800 arrive. Without shedding, p99 latency climbs to 30 s and almost all requests time out. With shedding at 1,000 in-flight, 1,000 succeed at normal latency and 800 get a fast 503 that clients back off from.

What is FinOps and how do you reduce cloud cost? Intermediate
Say this: "FinOps makes cloud spend visible and a shared engineering responsibility. I track cost per unit of value, then tag and attribute spend, rightsize, buy commitments for the steady baseline, use spot for fault-tolerant work, and cut data transfer, storage and log waste, weighing savings against reliability and engineer time."

Mindset. Cloud makes spending effortless: any engineer can launch resources that bill by the hour. FinOps is the practice of making cost visible, attributable and optimised continuously (inform, optimise, operate). The metric that matters is unit cost (cost per 1,000 requests, per tenant, per order), because total spend rising with revenue is healthy while cost per order rising is not.

  • Visibility. Tag or label every resource by team, service and environment; show cost per service and per tenant; set budgets and anomaly alerts. Untagged spend is unowned spend.
  • Rightsize. Many instances run at under 20% utilisation; match size to load. Switch off dev and test environments at night and weekends; delete orphaned volumes, old snapshots, idle load balancers and unattached IPs.
  • Pricing models. On-demand for spiky or unknown load; commitments (reserved instances, savings plans) for the steady baseline at a significant discount; spot or preemptible instances for fault-tolerant batch and stateless workers, at large discounts but reclaimable on short notice, so design for interruption.
  • Architecture levers. Caching and CDN cut compute and egress; storage lifecycle tiers (hot to cold to archive) and compression; avoid unnecessary cross-zone and cross-region transfer, which is billed per GB; newer or ARM instance generations where compatible; managed services versus self-hosted by total cost including people; log and trace sampling and retention.
  • Autoscaling and scheduling so you pay for what you use.

Trade-offs to state. Spending an engineer-month to save a few hundred dollars a month is a bad deal. Multi-region active-active roughly doubles cost, so justify it with the SLO. Deep spot use lowers cost but adds interruption handling. Cost cutting that removes redundancy trades reliability for money, so decide consciously.

Scenario: the cloud bill jumped 40% this month with no traffic growth. How do you find out why? Intermediate
Say this: "Break the bill down by service, tag and day to find which line grew and when it started, correlate that date with deploys and changes, check untagged resources for orphans, fix, and add budgets, anomaly alerts and policies so it does not recur."
  1. Slice the bill. In the cost explorer group by service type (compute, storage, data transfer, database, logging, NAT gateway), then by tag, account and day. Which line item grew? When exactly did it start? A step change on a date points to a change; a steady slope points to growth (storage that is never deleted).
  2. Correlate with changes. Compare the date with deploys, config changes and new features. Typical culprits:
    • A debug log level left on, or a chatty new log line: log ingestion and storage cost jumps.
    • A retry loop or a job scanning too much data (full table scans, querying a warehouse without partition filters).
    • A cache that stopped working (bad key or eviction), so database and compute load increased.
    • Missing lifecycle rules on a bucket, so data accumulates; versioning with no expiry.
    • Forgotten test clusters, large instances or GPUs left running.
    • Autoscaler stuck at a high count after an incident, or minimum raised "temporarily".
    • Cross-region or cross-zone traffic after a topology change; NAT gateway data processing on traffic that could use a VPC endpoint.
    • Cross-region replication or a new always-on feature (multi-AZ, extra read replicas).
  3. Check untagged resources: orphans and shadow projects hide there.
  4. Fix and quantify. Remove or resize, estimate monthly savings, and confirm in the next days' bill.
  5. Guardrails. Budgets and anomaly detection alerts to the owning team, per-team cost dashboards, quotas, and a policy that forbids untagged resources; add cost to design reviews.
What is infrastructure as code and why use it? Basic
Say this: "IaC defines servers, networks, databases and permissions in versioned files applied by tools, instead of clicking in a console. It gives reproducible environments, reviewed changes, an audit trail and fast disaster recovery."

The problem it solves. Hand-built infrastructure becomes a pile of snowflakes: nobody remembers which console setting made prod work, staging differs from prod, a region cannot be rebuilt, and there is no review or history of changes. IaC treats infrastructure like software.

How it works (declarative). You describe the desired end state in files (Terraform or OpenTofu, Pulumi, CloudFormation, Kubernetes manifests with Helm or Kustomize):

resource "aws_s3_bucket" "uploads" {
  bucket = "acme-prod-uploads"
  versioning { enabled = true }   # newer AWS provider versions use a separate aws_s3_bucket_versioning resource
}

The tool compares this with the state it records of what it manages and with reality, computes a plan (a diff: "will create 1, change 2, destroy 0"), and on approval applies it. You review the plan like a code diff.

Benefits. Reproducible environments (staging equals prod, differing only in variables); code review and audit trail in git; fast disaster recovery (rebuild a region from code and backups); consistent security baselines; fewer snowflake servers; documentation that is always true.

Good practices.

  • Remote, locked state (for example in a bucket with a lock table) so two people cannot apply at once; protect state, as it can contain secrets.
  • Small modules and separate state per environment and blast radius, rather than one giant state for everything.
  • Run plan in CI on pull requests and apply through a pipeline, not from laptops.
  • Policy as code (OPA, Sentinel, tfsec) to block public buckets, wildcard IAM and untagged resources.
  • Detect and fix drift: manual console changes that diverge from code; schedule a drift-detection plan.
  • No secrets in code or plain-text state.

Related ideas. GitOps: git is the source of truth and a controller (Argo CD, Flux) continuously reconciles the cluster to it. Immutable infrastructure: replace servers with new images rather than patching them in place. Pitfall: a destroy in the plan of a stateful resource (a database) must be caught in review; use deletion protection and prevent-destroy flags.

What are RPO and RTO, and how do backup and DR strategies map to them? Intermediate
Say this: "RPO is how much data I can afford to lose, as time; RTO is how long I can be down. Tighter targets need more expensive strategies: backup and restore, pilot light, warm standby, active-active. And a backup only counts if I have actually restored from it."

Definitions with an example. A database fails at 12:00. The last good copy is from 11:55. RPO (recovery point objective) is the maximum acceptable data-loss window: an RPO of 5 minutes means you must be able to restore to within 5 minutes before the failure. RTO (recovery time objective) is the maximum acceptable outage: restored and serving by 12:30 means an RTO of 30 minutes. Business owners set targets; engineers choose the strategy and price.

StrategyTypical RTOTypical RPOCost
Backup and restore (copies stored offsite, rebuild on demand)HoursHours (backup interval)Lowest
Pilot light (data replicated continuously, minimal compute kept off or tiny)Tens of minutesSeconds to minutesLow
Warm standby (scaled-down full copy running)MinutesSecondsMedium
Active-active multi-regionNear zeroNear zeroHighest, plus data consistency complexity

What determines RPO. Backup frequency or replication lag. Asynchronous replication gives a low but non-zero RPO (the unreplicated tail is lost); synchronous replication gives zero RPO at the cost of write latency and availability.

Backups done right.

  • Test restores on a schedule: a backup never restored is a hope, as the GitLab incident shows.
  • Store backups in a separate account and region, protected from deletion (immutable, object lock), so ransomware, a compromised credential or an operator mistake cannot destroy both data and backups.
  • Back up configuration, secrets (securely), schemas and keys too; losing the encryption key loses the data.
  • Rehearse failover with game days and measure the real RTO, which is usually much worse than the planned one.

Note. Replication is not backup: a corrupted or deleted row replicates instantly. You need point-in-time recovery as well.

What is chaos engineering and game days? Intermediate
Say this: "Chaos engineering deliberately injects failures in a controlled way to verify the system degrades as designed and that alerts and runbooks work. Define steady state, form a hypothesis, limit blast radius, run it, observe and fix. A game day is a scheduled team exercise of a realistic incident."

Why. Fault tolerance that has never been exercised is an assumption. Timeouts are set wrong, retry settings amplify load, a "redundant" dependency turns out to be shared, the failover script has bit-rotted, and the on-call has never seen the runbook. It is better to discover this on Tuesday afternoon with everyone awake than at 3 a.m. during a real outage.

Method (the scientific loop).

  1. Define steady state with an SLI (checkout success above 99.9%, p99 under 400 ms).
  2. Hypothesis: "if we kill one cache node, availability drops less than 1% and recovers within 2 minutes".
  3. Limit the blast radius: start in staging, then production with a tiny scope (one instance, 1% of traffic), a time box and a stop button; make sure alerts and on-call know.
  4. Inject the fault: kill instances or pods, add latency or packet loss, make a dependency return errors, exhaust CPU or disk, fail a zone, expire a certificate. Tools exist (Chaos Monkey, Gremlin, Litmus, AWS Fault Injection Service), or a script is enough.
  5. Observe against the hypothesis: did SLIs hold, did alerts fire, did failover work, did people know what to do?
  6. Fix and repeat, then automate the experiment so it keeps being verified.

Game days. A scheduled exercise where the team simulates an incident ("primary database lost", "region unreachable") with a facilitator, using real runbooks. It tests people and process as much as software: communication, roles, escalation, access to tools.

What it typically finds. Missing or too-long timeouts, retry storms, hard dependencies that should be soft, shared failure domains, unrealistic runbooks, alert gaps, and slow cold starts. Pitfall: running chaos without good observability or without a stop condition is just causing outages.

What is the difference between liveness, readiness and startup checks, and what goes wrong with them? Intermediate
Say this: "Liveness asks whether the process is stuck and needs a restart; readiness asks whether it can serve traffic now; startup gives slow starters time before liveness begins. Keep liveness local and cheap, and never make it depend on a shared downstream."

Why three different checks. They trigger different actions. A failing liveness check makes the orchestrator kill and restart the container. A failing readiness check only removes it from the load balancer until it recovers. A startup probe holds off the other two while a slow application (loading a large cache, warming a JVM) boots, so it is not killed before it finished starting.

CheckQuestionAction on failureShould check
LivenessIs the process irreparably stuck (deadlock, wedged event loop)?Restart containerOnly local state, e.g. a simple handler responds
ReadinessCan it serve requests right now?Stop sending trafficWarm-up complete, local resources available, not overloaded
StartupHas it finished starting?Keep waiting, then restart after the limitInitialisation done

How they go wrong.

  • Liveness depends on the database. The database becomes slow; every pod fails liveness; Kubernetes restarts them all at once; they come back, reconnect together and hammer the database, which stays down. A partial problem became a full outage with a restart storm.
  • Readiness depends on a shared downstream. If a dependency blips, all pods become unready simultaneously and the load balancer has no healthy backends, so you return errors even though pods could have served cached or degraded responses. Prefer local readiness with graceful degradation, or at most check hard dependencies that make the service truly useless.
  • Thresholds too tight (a one-second timeout under GC pause) cause flapping and restart loops.
  • Missing readiness during deploys: new pods receive traffic before warm-up, causing errors during every rollout.
  • Too-shallow checks: returning 200 while the app is unable to do anything useful.

Rule. Check local health, not the world. Handle dependency failure with timeouts, circuit breakers and fallbacks inside the request path rather than by killing healthy processes.
