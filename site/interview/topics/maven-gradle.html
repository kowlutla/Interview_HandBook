Mental model: the 8 ideas everything hangs on

One line: a build tool does three jobs: it decides the order of work (lifecycle or task graph), it finds the libraries you need (dependency resolution), and it avoids repeating work (caches). Maven does this by convention and a fixed lifecycle. Gradle does it with a flexible task graph and strong caching.
  1. Coordinates. Every library is named by group, artifact and version (GAV), for example org.slf4j:slf4j-api:2.0.13. Repositories, caches and conflicts are all about finding and choosing GAVs.
  2. Declarative versus programmable. Maven is an XML description plus a fixed lifecycle. Gradle is a real program (Groovy or Kotlin) that builds a graph of tasks.
  3. Lifecycle or task graph. Maven runs phases in a fixed order, and plugin goals attach to phases. Gradle runs tasks in dependency order and skips the ones whose inputs did not change.
  4. Transitive dependencies. You declare 10 libraries and get 200 on the classpath. The tool must pick one version of each. Maven picks the nearest to your project, Gradle picks the highest.
  5. Scopes and configurations. A library may be needed at compile time, at run time, only for tests, or only provided by the server. Maven calls this scope, Gradle calls it configuration.
  6. Repositories and caches. A local cache on your machine, then your company proxy (Nexus or Artifactory), then Maven Central. Most "works on my machine" bugs live in this chain.
  7. Reproducibility. Same input should give the same output: fixed versions, wrappers, no surprise SNAPSHOTs.
  8. Fast feedback. Incremental builds, build caches and parallel modules exist to make the second build much faster than the first.

1. Maven core: lifecycle, goals and project structure

Explain the Maven lifecycle and phases. What happens when you run mvn package? Basic

Maven has three built-in lifecycles: clean, default and site. The default one is an ordered list of phases: validate, compile, test, package, verify, install, deploy. When I run a phase, Maven runs every earlier phase first and then that one, so mvn package runs validate, compile, test and package, and stops. It does not install or deploy.

A phase is only an empty slot. The real work is done by plugin goals bound to it: for jar packaging, compiler:compile sits on compile, surefire:test on test and jar:jar on package. There are also small phases in between (generate-sources, process-resources, test-compile). mvn clean package runs the clean lifecycle up to clean (delete target/), then the default lifecycle up to package. install copies the artifact into your local ~/.m2, and deploy uploads it to a remote repository like Nexus.

Why a lifecycle at all? Without one, every project invents its own build script ("compile, then copy resources, then run tests, then zip"). Maven's idea is convention over configuration: every project goes through the same named stages in the same order, so anyone who knows one Maven project can build any other. You describe what the project is, not how to build it.

What the three lifecycles are for.

  • clean: pre-clean, clean, post-clean. Deletes the target/ directory. It is separate on purpose, so a normal build never wipes your output by surprise.
  • default: the build itself (validate through deploy). This is the one you use all day.
  • site: generates project documentation and reports. Rarely used today.

What mvn package does, step by step for a simple jar project:

  1. validate: check the POM is correct and needed information is present.
  2. process-resources then compile: copy src/main/resources, compile src/main/java into target/classes.
  3. process-test-resources, test-compile, test: compile tests and run them with Surefire. If one fails, the build stops here and no jar is made.
  4. package: jar:jar zips target/classes into target/orders-1.2.0.jar.

Two later phases are worth knowing exactly. verify runs checks on the packaged result (integration tests, quality gates). install copies the jar into ~/.m2/repository so other projects on your machine can use it. deploy uploads it to a shared repository so other people and CI can use it. Mixing these up is a common interview slip.

What changes with packaging. The phases are always the same, but which goals are bound to them depends on <packaging>. For war, package runs war:war. For pom (a parent or aggregator), there is no compile at all. That is how one lifecycle serves many project types.

Pitfall. Running mvn install when you only wanted to compile is slow and pollutes ~/.m2 with half-finished snapshots (see the SNAPSHOT questions below). Use mvn verify or mvn package unless another project on your machine really needs the jar.

Remember: a phase runs all earlier phases; package stops before install and deploy. Phases are slots, goals do the work.

What is the difference between a phase, a goal and a plugin? Basic

A plugin is a package of related actions, like maven-compiler-plugin. A goal is one action inside a plugin, written plugin:goal, for example compiler:compile. A phase is a named step in the lifecycle, and goals are bound to phases. I can run a phase, which triggers all goals bound to it, or run a goal directly, which skips the lifecycle.

Some goals, such as dependency:tree, are not bound to any phase, so they run only when I name them. I can mix both in one command and Maven runs them in the order typed. To run extra work at a certain moment (for example code generation), I add a plugin with an <execution> naming the goal and the phase it should attach to.

mvn package                  # a phase: everything up to package
mvn dependency:tree          # a goal: just that action
mvn clean dependency:tree package   # mixed, runs left to right

Why the split exists. Maven core knows almost nothing about compiling or packaging. It only knows how to run a list of plugin goals in an order. A plugin is a jar of related goals (the compiler plugin, the jar plugin). A goal is one concrete job, a Java method inside that plugin (compiler:compile compiles main code, compiler:testCompile compiles tests). A phase is only a label on the timeline. The binding is what connects a goal to a label. Think of a conveyor belt: the phases are the stations, the goals are the workers standing at them.

Example: attaching your own goal to a phase. Say you want the build to generate source code from an OpenAPI file before compiling. You add the generator plugin and say "run goal generate at phase generate-sources":

<plugin>
  <groupId>org.openapitools</groupId>
  <artifactId>openapi-generator-maven-plugin</artifactId>
  <version>7.5.0</version>
  <executions>
    <execution>
      <phase>generate-sources</phase>
      <goals><goal>generate</goal></goals>
    </execution>
  </executions>
</plugin>

Now every mvn compile, package or install runs the generator first, because generate-sources comes before compile. Many plugin goals have a default phase, so you can often omit <phase>.

Running a goal directly (mvn dependency:tree) executes only that goal, with no lifecycle before it. This matters: mvn compiler:compile does not run validate or process-resources, so it can fail with "no classes" if resources were never copied. The mixed form mvn clean package dependency:tree runs clean, then the package lifecycle, then the goal.

Pitfall. A plugin version you never wrote comes from the built-in defaults, which can be old. Pin versions in <pluginManagement>, otherwise a build run today can behave differently from the same build next year.

Remember: plugin contains goals; phases are slots; a goal bound to a phase runs when that phase runs.

What are the Maven coordinates, and how do you see what Maven is really using? Basic

Coordinates identify an artifact: groupId (the organisation or product), artifactId (the module), version, plus optional packaging (jar, war, pom) and classifier (like sources). To see what Maven really uses, I run mvn help:effective-pom, which prints my POM merged with its parents, active profiles and Maven's built-in defaults.

A repository stores an artifact at a path built from the coordinates, like com/acme/orders/1.2.0/orders-1.2.0.jar, so you can find any jar by hand. Every POM silently inherits from the built-in Super POM, which sets Central as the default repository and the default directory layout. That is why a plugin version or repository you never wrote can still be in effect. Maven's default plugin versions are old, so I pin plugin versions in the POM.

mvn help:effective-pom -Doutput=effective.xml
mvn help:active-profiles
mvn -X package        # debug log: classpath, plugin versions, repos

Why coordinates matter. A repository is just a big directory tree. For Maven to find jackson-databind among millions of files, every artifact needs a unique, predictable address. The address is the coordinates. The path rule is: replace dots in the groupId with slashes, then artifactId, then version, then artifactId-version[-classifier].packaging.

org.slf4j : slf4j-api : 2.0.13 : jar
 -> org/slf4j/slf4j-api/2.0.13/slf4j-api-2.0.13.jar
 -> org/slf4j/slf4j-api/2.0.13/slf4j-api-2.0.13.pom
 -> org/slf4j/slf4j-api/2.0.13/slf4j-api-2.0.13-sources.jar   (classifier: sources)

The classifier distinguishes several files with the same GAV. Common ones are sources, javadoc and tests. Each artifact also has a .pom file next to it, which is how Maven learns its dependencies, and checksum files (.sha1) used to verify the download.

The "effective POM" idea. The POM you write is short, but Maven builds the real one by layering: Super POM (built-in defaults), then your parent POMs, then your own POM, then active profiles, then command-line properties. The result is the effective POM. When someone asks "why is this plugin version used?" or "where does this repository come from?", the answer is almost always visible there.

Properties and interpolation. ${project.version}, ${java.version} and your own <properties> are substituted when the effective POM is built. A child that overrides a property changes every place the parent used it. That is a handy trick (bump one version) and a hidden source of surprise.

Practical example. A new teammate asks why mvn package hits repo.maven.apache.org although no repository appears in the POM. Answer: the Super POM declares Central. Run mvn help:effective-pom and search for <repositories> to prove it.

Pitfall. Do not confuse groupId with package names. They are often similar by habit, but groupId is only a namespace in the repository, usually a reversed domain you own.

Remember: GAV names the artifact; when behaviour is a mystery, read the effective POM.

What is the difference between inheritance and aggregation in Maven? Intermediate

Inheritance is the <parent> element: a child POM gets the parent's properties, dependencyManagement and plugin settings. It answers "what do these projects share". Aggregation is the <modules> list in a packaging-pom project. It answers "which projects do I build together with one command". They are independent ideas, though most multi-module projects use one POM for both.

A parent need not list modules, and an aggregator need not be anyone's parent. The parent can even live outside your repo, like spring-boot-starter-parent, which gives ready-made versions and plugin settings. Maven looks for the parent at ../pom.xml first (relativePath) and otherwise fetches it from a repository. A project has only one parent, which is exactly why BOM imports exist: they let you share version lists without using up your single parent.

Two separate needs. Imagine five services in one repository. You face two different problems. Problem one: they all need the same Java level, plugin versions and a few libraries, and you do not want to copy that into five files. Problem two: you want to type one command and build all five. Maven solves them with two separate mechanisms, and confusing them is the classic mistake.

What is actually inherited. properties, dependencyManagement, pluginManagement, dependencies and plugins declared outside the management sections (these are added to every child, so be careful), repositories, and groupId/version (which the child may omit). What is not inherited: artifactId, name, and the parent's modules list.

Example of a child that inherits but is not in any aggregator:

<parent>
  <groupId>com.acme</groupId>
  <artifactId>acme-parent</artifactId>
  <version>5</version>
  <relativePath/>   <!-- empty: fetch from the repository, not ../pom.xml -->
</parent>
<artifactId>orders-service</artifactId>

This is the usual company setup: a small "company parent" lives in its own repository and is published to Nexus. Services in other repositories inherit from it by version, and a new parent release is how everyone picks up a plugin upgrade.

Pitfall. Putting <dependencies> (not managed) in a parent forces that library onto every child, including ones that do not need it. Prefer dependencyManagement in the parent and let each child opt in.

What an interviewer probes next. "Parent is single, so how do you share more?" Answer: import BOMs (next section) and use pluginManagement in the parent.

Remember: parent = share config down; modules = build together. One parent only, many BOMs.

2. Maven dependencies: scopes, transitive, conflicts, BOMs

Explain the Maven dependency scopes. Basic

A scope says in which classpaths a dependency is present. compile (default) is everywhere and is passed on to users of my library. provided is for compile and test only, because the container supplies it at run time, like the Servlet API. runtime is not needed to compile but is on the run classpath, like a JDBC driver. test is for tests only, like JUnit.

There are two more: system (a file path on disk, deprecated, avoid) and import (only inside dependencyManagement to import a BOM). The habit I follow is to use the narrowest scope: the JDBC driver as runtime so code cannot import its classes by accident, Lombok as provided, test libraries as test. A transitive library's test and provided dependencies are never passed on.

Why scopes exist. Not every library should be everywhere. JUnit has no business inside your production jar. The Servlet API is already supplied by Tomcat, so shipping your own copy would clash with the server's. The scope is how you tell Maven "this library is for these classpaths only". There are three classpaths: compile (building main code), test (compiling and running tests) and runtime (the running application).

Example with a Spring web service on Tomcat.

<dependency>spring-web ...</dependency>                         <!-- compile (default) -->
<dependency>jakarta.servlet-api ... <scope>provided</scope></dependency>
<dependency>postgresql ...          <scope>runtime</scope></dependency>
<dependency>junit-jupiter ...        <scope>test</scope></dependency>

With this, spring-web is in the war. The servlet API is used to compile but left out of the war. The Postgres driver is in the war but your code cannot accidentally write import org.postgresql... because it is not on the compile classpath. JUnit is never packaged.

How scope behaves for transitive dependencies. When library A (your dependency) itself depends on B, the scope you gave A and the scope A gave B combine. Rule of thumb: a compile dependency's compile dependencies stay compile for you, its runtime ones become runtime, and its test and provided ones are dropped. If you declare A as test, everything it brings is also test. That is why a test-only library never leaks to production.

Scope in the final packaged artifact. For a plain jar, nothing is bundled anyway (the dependencies stay separate). For a war, an executable Spring Boot jar or a fat jar, compile and runtime libraries are packaged and provided and test are not. Check by listing the war's WEB-INF/lib.

Pitfall. A very common bug: a library marked provided for Tomcat, but the app is later run as an executable jar with embedded server, and now the class is missing at runtime. Know where your runtime really comes from.

Remember: compile = everywhere, provided = not at run time, runtime = not at compile time, test = tests only.

What are transitive dependencies, and how does Maven choose a version when two paths disagree? Intermediate

A transitive dependency is a library that my dependency needs, which Maven adds for me. When two paths ask for different versions of the same library, Maven uses dependency mediation: the version nearest to my project in the tree wins, and if the depth is equal, the one declared first wins. It is not "newest wins".

So a direct dependency always beats a transitive one, and an old version two hops away can beat a newer one three hops away. That is the cause of many NoSuchMethodError bugs: my code needs the new API, but Maven kept the old copy. To fix it I declare the version I want directly (depth 1), or pin it in dependencyManagement, which applies to the whole tree. Gradle uses a different rule (highest wins).

mvn dependency:tree -Dverbose -Dincludes=com.acme:util
# +- lib-A:1.0
# |  \- util:1.0
# \- lib-B:1.0
#    \- lib-C:1.0
#       \- (util:2.0 - omitted for conflict with 1.0)

Why transitive dependencies exist. You ask for spring-web and, without you listing them, Maven also fetches spring-core, spring-beans, spring-jcl and so on. This is convenient but means the real classpath is a tree that you did not write. Two branches of the tree will sometimes want different versions of the same library, and the classpath can hold only one copy. Mediation is the rule for choosing.

Mediation, in order.

  1. Nearest definition in the tree wins. Depth is counted as hops from your project. Your own declaration is depth 1.
  2. If two candidates are at the same depth, the one whose declaring path appears first in your POM wins. That means reordering two dependencies in your POM can change which version you get. That is fragile.
  3. Anything in dependencyManagement overrides both rules.

Why nearest and not newest? It is predictable and local: you can always win by writing the dependency yourself. The cost is that Maven will happily choose an older version and compile fine, and the error shows at runtime (NoSuchMethodError). That is exactly the situation in the diagram below.

Worked example. App depends on lib-A (which needs util 1.0) and lib-B. lib-B needs lib-C, and lib-C needs util 2.0. util 1.0 is at depth 2, util 2.0 is at depth 3. Maven keeps util 1.0. If lib-C calls a method that exists only in 2.0, you get an error only when that code path runs. Three fixes:

  • Declare util:2.0 directly in your POM (depth 1). Quick and obvious.
  • Manage it in dependencyManagement. Better in multi-module builds because every module agrees.
  • Enforce it: requireUpperBoundDeps makes the build fail whenever mediation chose a version lower than another version somewhere in the tree. This turns a silent runtime bug into a build-time message.

Pitfall. People read mvn dependency:tree without -Dverbose and see only the winning version. Use -Dverbose to see the omitted ones and the reason.

Remember: Maven = nearest wins (then first declared), not newest. Gradle = highest wins.

What is dependencyManagement, and how is it different from dependencies? Intermediate

<dependencies> really adds libraries to the project's classpath. <dependencyManagement> only sets rules: "if anyone in this build uses this library, use this version, scope and exclusions". It adds nothing by itself. Children then declare the dependency without a version.

The strongest feature is that the rule also applies to transitive dependencies. If a library I use pulls in Jackson 2.9, a managed Jackson 2.17 overrides it everywhere, even though I never wrote Jackson myself. So there is one place to change a version for all modules. A child's own explicit version still beats the managed one.

<!-- parent pom -->
<dependencyManagement><dependencies>
  <dependency>
    <groupId>com.fasterxml.jackson.core</groupId>
    <artifactId>jackson-databind</artifactId>
    <version>2.17.1</version>
  </dependency>
</dependencies></dependencyManagement>

<!-- child pom: no version needed -->
<dependency>
  <groupId>com.fasterxml.jackson.core</groupId>
  <artifactId>jackson-databind</artifactId>
</dependency>
Watch out: putting a library only under dependencyManagement does not put it on the classpath.

The problem it solves. In a ten-module build, five modules use Jackson. Without management, each declares its own version, and one day module A has 2.15 and module B has 2.17. Worse, a library you use might pull in an old Jackson transitively. You want a single table that says "in this build, Jackson is 2.17.1, period".

How it works. dependencyManagement is such a table. When Maven resolves the tree, for every artifact it meets (direct or transitive) it looks in the table. If found, it applies the table's version (and scope, exclusions, type, classifier) instead of whatever was requested. Entries in the table never add anything to the classpath on their own.

Sequence for a CVE fix. A scan says jackson-databind 2.9 (brought transitively by an old client library) is vulnerable. You add one entry for 2.17.1 in the parent's dependencyManagement. Now every module, including the ones that never mention Jackson, gets 2.17.1. This is the main reason senior engineers use it.

Pluginmanagement is the same idea for plugins: it fixes plugin versions and configuration but only activates plugins that the child lists (or that the lifecycle binds by default). Pin maven-compiler-plugin and maven-surefire-plugin there.

Pitfall. Forcing a version does not guarantee compatibility. If lib-C was built for util 2.0 and you force 1.0, you can break it. Management gives control, not safety, so test after changing.

Remember: dependencies = what I use; dependencyManagement = which version, including for transitives.

What is a BOM, and how do you import one? Intermediate

A BOM (Bill of Materials) is a POM with packaging pom whose content is a dependencyManagement list of versions that are known to work together, like spring-boot-dependencies. I import it inside my own dependencyManagement with type pom and scope import. Then I declare the libraries without versions.

Unlike a parent, I can import many BOMs. If two BOMs manage the same library, the one listed first wins, and my own explicit entries beat imported ones. The Spring Boot BOM only gives versions. The Spring Boot parent POM also configures plugins and resource filtering, so I use the BOM when I already have my own parent. Gradle has the same idea with platform().

<dependencyManagement><dependencies>
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-dependencies</artifactId>
    <version>3.3.4</version>
    <type>pom</type>
    <scope>import</scope>
  </dependency>
</dependencies></dependencyManagement>

The problem. Spring Boot is 100+ libraries (Spring, Jackson, Hibernate, Netty, Tomcat, ...). Picking compatible versions yourself would be a nightmare. The Spring team tests one combination and publishes a POM, spring-boot-dependencies, that lists every version. That list is a BOM. The same pattern is used by jackson-bom, aws-java-sdk-bom, junit-bom and many others.

Why import and not parent? A project can have only one <parent>. If your company parent is already used, you cannot also extend Spring Boot's parent. Import is the workaround: it copies the BOM's dependencyManagement section into yours, with no inheritance. You may import as many as you like.

Resolution order, concretely. Suppose you import spring-boot-dependencies and jackson-bom, and both manage Jackson.

  1. Your own explicit entry in your dependencyManagement wins over any import.
  2. Among imports, the first listed wins. So list the more specific BOM (jackson-bom) before the general one if you want its version.
  3. A property override works with Spring Boot: <jackson-bom.version>2.17.2</jackson-bom.version> changes the version the BOM uses, because the BOM is written with that property. This is supported when you use the Boot parent, and for an imported BOM only by redefining the entries explicitly.

Parent versus BOM for Spring Boot. The spring-boot-starter-parent also sets java.version handling, UTF-8, resource filtering and plugin configuration (the repackage goal that makes the executable jar). With a BOM import you get versions only, so you must configure the Boot Maven plugin yourself.

In Gradle the equivalent is implementation(platform("org.springframework.boot:spring-boot-dependencies:3.3.4")). Boot's Gradle plugin with the dependency-management plugin does it for you.

Pitfall. A BOM does not add anything. If you forget to list the starter, nothing happens. Also, a BOM is an agreement between libraries, so overriding one entry (say, a newer Jackson) can break Spring's own code. Check the release notes.

Remember: BOM = a shared version list you import (scope import, type pom); many allowed, unlike a parent.

What is the difference between exclusions and optional dependencies? Intermediate

An exclusion is set by the consumer: "I use library X, but do not bring in its dependency Y". It cuts one branch of the tree in my project only. An optional dependency is set by the library author: "I need Z only for a feature, so do not pass it on to my users". The first is the consumer's cut, the second is the author's.

I use an exclusion to remove an old logging backend or a duplicate of a library I supply myself. A typical optional case is a library that supports Jackson or Gson and wants me to pick one. After any exclusion I run the tests and check the tree, because cutting something the code really needs shows up as ClassNotFoundException at runtime. A wildcard exclusion (*:*) gives a bare dependency when I will supply everything myself.

<dependency>
  <groupId>org.apache.hadoop</groupId>
  <artifactId>hadoop-client</artifactId>
  <version>3.3.6</version>
  <exclusions><exclusion>
    <groupId>org.slf4j</groupId>
    <artifactId>slf4j-reload4j</artifactId>
  </exclusion></exclusions>
</dependency>

Why you would cut a branch. Transitive dependencies come with whatever the library author decided. Sometimes that is unwanted: a second logging backend that conflicts with your own, a library that you replace by a patched version, or a huge dependency your feature never touches. An exclusion removes that dependency and everything only it brought, but only for the path you put it on.

How exclusion scope works. The <exclusion> sits inside one dependency. If another dependency elsewhere in your tree also brings the same artifact, it stays. This surprises people: you exclude commons-logging from library A, but library B still brings it. To remove it everywhere, repeat the exclusion on each path, or use a wildcard, or better, override with dependencyManagement or the enforcer rule bannedDependencies.

Optional, from the author's side. Imagine you write my-http-client that supports both Jackson and Gson, but needs only one. You declare both as <optional>true</optional>. They are on your own classpath for compiling and testing, but are not passed to users. Users add the one they want. The trade-off: users must read your docs to know they have to add one, otherwise ClassNotFoundException. Many authors split into separate modules instead (client-jackson), which is cleaner.

Remember: exclusion = consumer cuts a branch; optional = author does not pass it on.

What is the Maven enforcer plugin and which rules would you turn on? Intermediate

The enforcer plugin checks rules about the build itself and fails fast when a rule is broken. I enable rules for the Maven and Java version, convergence of dependency versions (requireUpperBoundDeps), banned dependencies, no SNAPSHOT dependencies in a release, and no duplicate classes. It turns silent classpath problems into clear build failures.

What is the difference between a SNAPSHOT and a release version? Basic

A version ending in -SNAPSHOT means work in progress: the same version string can point to different jars over time. A release version such as 1.2.0 is immutable. Once published it must never change, and if it is wrong I publish 1.2.1.

In the remote repository a snapshot is stored with a timestamp (like 1.2.0-20241114.101500-7), and a metadata file tells Maven which is the latest. Maven checks for a newer snapshot by an update policy, once a day by default, or every time with -U. The danger is that two developers, or CI and a laptop, can hold different jars under the "same" version, so builds are not repeatable. Repositories like Nexus normally refuse to redeploy a release. Many teams also ban SNAPSHOT dependencies in release builds with the enforcer rule requireReleaseDeps. Gradle caches snapshots (it calls them "changing modules") for 24 hours by default, and --refresh-dependencies checks again.

Why SNAPSHOT exists. During development, module A depends on module B, which is still changing every day. Releasing B as 1.2.0 after each fix would waste version numbers. A SNAPSHOT says "this is the latest in-progress build of 1.2.0, fetch it fresh each time you check". After the real release, the version loses the suffix.

Timeline of one library's life.

  1. pricing-1.4.0-SNAPSHOT: CI deploys it many times a day. Nexus stores 1.4.0-20241114.101500-7 style files and a maven-metadata.xml pointing at the newest one.
  2. Consumers resolve 1.4.0-SNAPSHOT; Maven asks the metadata for the newest timestamp and downloads it (at most once a day by default, unless -U).
  3. Release: the version is changed to 1.4.0 (the release plugin or CI-driven versions:set), built, tagged in Git, and deployed once. The repository refuses to overwrite it.
  4. Next development version becomes 1.4.1-SNAPSHOT (or 1.5.0-SNAPSHOT).

Why releases must be immutable. A cached copy of 1.4.0 on thousands of laptops, CI nodes and Docker layers is never re-checked. If you quietly replaced the file, some machines keep the old bytes and some get the new. Debugging that is horrible. The rule is therefore: never change a release, publish a new version.

Pitfall: version ranges and "LATEST". Version ranges ([1.0,2.0)) and the old LATEST/RELEASE keywords have the same problem as snapshots: two builds can resolve differently. Avoid them. What is "jar hell", and how do you detect and fix it? Intermediate

Jar hell is when the classpath holds several versions of the same library, or the same class in several jars. The JVM class loader takes the first matching class it finds and ignores the rest, so behaviour depends on jar order. The symptoms are NoSuchMethodError, NoClassDefFoundError or a method that quietly behaves like the old version.

To detect it, I print the dependency tree for that library, then ask which jar a class was really loaded from (-verbose:class, or Foo.class.getProtectionDomain().getCodeSource()). It compiled fine because the compile and runtime classpaths can differ. Causes are transitive conflicts, a fat jar with its own copy of a library, the same library under two names (google-collections and guava), or a server that ships its own copy. Fixes: pin one version through dependencyManagement, exclude the stale copy, or, only when two incompatible versions must coexist, relocate one by shading. To stop it coming back, the enforcer plugin has requireUpperBoundDeps and (in extra-enforcer-rules) banDuplicateClasses.

Why this happens. The Java class loader reads the classpath as an ordered list of jars. When code asks for com.google.common.base.Preconditions, the loader walks the list and takes the first jar that contains that class. It never compares versions and never warns. So two jars with the same class cause behaviour that depends on order, and order depends on the build tool, the packaging tool and sometimes the file system. That is why jar hell shows up as "works in the IDE, fails in prod".

Step-by-step diagnosis, with a real symptom. Production says NoSuchMethodError: Preconditions.checkArgument(boolean, String, Object).

  1. Find the class in the deployed artifact: unzip -l app.jar | grep guava, or look in WEB-INF/lib.
  2. Ask the JVM which jar it used: run with -verbose:class and search for the class line, or print Preconditions.class.getProtectionDomain().getCodeSource().getLocation().
  3. Print the dependency tree with -Dverbose to see who requested which version and which one lost.
  4. Decide a single version that is compatible with all users (usually the highest, tested), pin it, exclude the others.

Sneaky variants.

  • Duplicate class, same name, different groupId. For example commons-logging and jcl-over-slf4j both provide the same classes on purpose. Or javax.servlet-api and jakarta.servlet-api (different package names after Jakarta EE 9, so Spring 5 and Spring 6 libraries cannot mix).
  • Fat jar without relocation. A shaded jar embeds its own copy of a library, invisible to the dependency tree.
  • Application server shared libs. The server's own lib directory has an older jar that wins by parent-first class loading.

Shading, when nothing else works. If two libraries need incompatible versions of the same one, the maven-shade-plugin (or Gradle Shadow) can relocate one copy into a different package (com.acme.shaded.guava) and rewrite the bytecode references. It is a last resort because it grows the jar and complicates debugging.

Newer alternatives. Java 9 modules and OSGi isolate class loaders properly, but most Spring applications still run on the flat classpath, so the build rules matter.

Remember: the JVM takes the first class it finds. Find who brought the old copy, pin one version.

3. Maven plugins, profiles, repositories and multi-module builds

Surefire versus Failsafe: what is the difference, and why two plugins? Intermediate

Surefire runs unit tests in the test phase, picking classes named *Test, Test* or *Tests. Failsafe runs integration tests in the integration-test phase and checks their result later in verify, picking *IT or IT*. They are split because integration tests need setup and cleanup around them, and the cleanup must run even when a test fails.

pre-integration-test starts a server or container and post-integration-test stops it. If an integration test fails, Failsafe does not fail the build at once. It waits for verify, after cleanup has run. That is why CI runs mvn verify, not mvn integration-test. Testcontainers inside the test itself is the modern way and reduces the need for phase-based setup. If tests silently do not run, suspect a wrong name pattern, or an old Surefire with JUnit 5 (it needs 2.22 or newer). To run one test: mvn test -Dtest=OrderServiceTest#shouldPay.

The problem two plugins solve. A unit test needs only the compiled classes: it can run right after compile. An integration test needs the packaged application, plus a running database, queue or web server. That environment must be started before the tests and stopped afterwards, even if tests fail. A single plugin in the test phase cannot do that: if a test fails, the build stops immediately and the container is left running.

Lifecycle order with Failsafe.

  1. test (Surefire): unit tests, fast, no external system.
  2. package: build the jar or war.
  3. pre-integration-test: start Tomcat, Docker container or a database.
  4. integration-test (Failsafe integration-test goal): run *IT classes against the packaged app. Failures are only recorded.
  5. post-integration-test: stop everything, always.
  6. verify (Failsafe verify goal): read the recorded results and fail the build if any test failed.

Your pom needs both goals bound, or tests run but failures never fail the build:

<plugin>
  <artifactId>maven-failsafe-plugin</artifactId>
  <version>3.2.5</version>
  <executions><execution>
    <goals><goal>integration-test</goal><goal>verify</goal></goals>
  </execution></executions>
</plugin>

Naming defaults. Surefire includes **/Test*.java, **/*Test.java, **/*Tests.java and **/*TestCase.java. Failsafe includes **/IT*.java, **/*IT.java and **/*ITCase.java. A class named OrderRepositoryIntegrationTest ends in Test, so Surefire runs it as a unit test during test, and your fast phase becomes slow. Name carefully or use JUnit tags (@Tag("integration")) with groups configuration.

Modern alternative. With Testcontainers, the test itself starts the database container, so the setup and cleanup are in test code. Many teams then run everything in Surefire, and use tags or separate source sets only to keep runtimes apart. The Failsafe split still makes sense when you must test the final packaged artifact.

Pitfall. mvn integration-test stops before verify and returns success even if ITs failed. In CI always call mvn verify (or later phases).

Remember: Surefire = unit (test), Failsafe = integration (*IT); run mvn verify so cleanup still happens.

What are Maven profiles, how are they activated, and what are the risks? Intermediate

A profile is a named block of POM settings (properties, dependencies, plugins, repositories) that applies only when the profile is active. I activate it with -P name, or automatically by JDK version, operating system, a property (-Denv=prod) or the presence of a file. The risk is that a profile changes what the artifact contains, so the jar built with -Pprod is not the one I tested.

I use profiles for things like "run slow integration tests" or "sign artifacts on release". The safer pattern for environments is to build one artifact once and give it configuration at runtime (environment variables, a config server). One trap: activeByDefault switches off as soon as any other profile in the same POM is activated, which surprises people. Profiles can also live in settings.xml for machine-specific values, which is a common reason why "it works only on my machine".

mvn -Pintegration verify
mvn help:active-profiles
mvn -P '!slow' test       # deactivate a profile

Why profiles exist. Sometimes a build needs to vary: run slow tests only on CI, use a different dependency on JDK 21, sign artifacts only on release, use an internal repository only inside the company network. Profiles let one POM contain those variations and switch them on by a condition.

Activation methods.

A sensible use. A release profile that adds the source, javadoc and GPG-signing plugins, so day-to-day builds are fast and only the release job pays for them. Because it only adds extra artifacts and does not change the code, the tested jar is the same.

A harmful use. A prod profile that swaps the database URL or a dependency. Now the code you tested in the dev profile is not the code that you shipped. A defect found only in prod cannot be reproduced from the tested artifact. The fix is the "build once, configure at runtime" principle: same jar everywhere, with SPRING_PROFILES_ACTIVE, environment variables or a config server selecting behaviour. (A Spring profile is a different thing from a Maven profile, a point interviewers like to check.)

Why activeByDefault surprises. If you run mvn -Pfoo and the POM has another profile with activeByDefault, the default profile is switched off because you activated one explicitly. Teams that depended on the default silently lose settings. Prefer property-based activation with a clear name.

Debug tip. mvn help:active-profiles shows what is in effect, including ones from settings.xml. A profile in ~/.m2/settings.xml that points at a personal repository is a classic cause of "builds only on my laptop".

Remember: one artifact, many environments through runtime config, not through build profiles.

What goes in settings.xml, and how is it different from the POM? Basic

The POM describes the project and is committed to source control. settings.xml describes the machine and the user (~/.m2/settings.xml), and holds credentials, so it is never committed. It has servers (credentials), mirrors (redirect repository requests to the company proxy), proxies, and profiles for this machine.

A server entry is matched to a repository by id. If distributionManagement names the repository company-releases but the server id in settings differs, the upload goes with no credentials and fails with 401. A mirror with mirrorOf * sends every repository request, even ones declared in third-party POMs, to your proxy. That is good for control, but a vendor repository that the proxy does not know about then cannot be found, so add that remote to the repository manager. Since Maven 3.8.1 a built-in mirror also blocks plain http:// repositories, because anyone on the network path could swap a jar. The fix is to use https, not to disable the block.

<settings>
  <servers><server><id>company-releases</id>
    <username>${env.NEXUS_USER}</username>
    <password>${env.NEXUS_TOKEN}</password></server></servers>
  <mirrors><mirror><id>company-all</id><mirrorOf>*</mirrorOf>
    <url>https://nexus.example.com/repository/maven-public/</url></mirror></mirrors>
</settings>

Why two files. Some information is about the project (what depends on what) and everybody needs the same. Other information is about the person or machine (my credentials, my proxy, where the company mirror lives) and must never be committed. Maven separates them so secrets stay off Git and the POM stays portable.

Which file wins. There are two settings files: global (${maven.home}/conf/settings.xml) and user (~/.m2/settings.xml). They are merged and the user file wins. You can pass another file with -s path. CI usually generates its own settings file from secrets at job start.

The authentication chain, step by step when you run mvn deploy:

  1. The POM's distributionManagement says release repository id = company-releases, url = https://nexus.example.com/....
  2. Maven looks for a <server> with <id>company-releases</id> in settings.
  3. It sends those credentials to the URL. No matching id means an anonymous request, and Nexus answers 401.

What a mirror does. A mirror rewrites "ask repository X" into "ask this URL instead". With mirrorOf *, a dependency's POM that declares its own repository still ends at your company proxy. Variants: external:* (everything except localhost and file repos), central (only Central), or *,!special-repo.

Protecting passwords. Do not hard-code. Use environment placeholders (${env.NEXUS_TOKEN}) as above, or Maven's encrypted passwords (mvn --encrypt-password plus a master password file). Many CI systems inject a ready settings file.

Pitfalls. A password with XML special characters (&, <) breaks the file silently. A repository declared in a POM but without a mirror match and without credentials fails with 401 while the same URL works in the browser (browser is logged in, Maven is not). Gradle's counterpart is ~/.gradle/gradle.properties and init.d scripts, with the same rule: secrets live per user, not in the repo.

Remember: POM = project (shared), settings.xml = machine and secrets. Server id must equal repository id.

How does Maven find an artifact? Describe the local repository, the mirror and Central. Intermediate

Maven first looks in the local repository (~/.m2/repository). If it is not there, Maven asks the remote repositories, and if a mirror matches, the request goes to the mirror instead. In companies the mirror is a repository manager such as Nexus or Artifactory that hosts our own releases and snapshots and proxies Maven Central, caching what it fetches.

Once downloaded, an artifact is reused with no network at all. When a download fails, Maven leaves a *.lastUpdated marker and will not retry until the update interval passes. That is why a server problem you already fixed still seems broken until you run mvn -U or delete the marker files. The first debugging step for "Could not resolve" is to check which URL it actually tried, because the mirror usually changed it.

What is being searched. Maven needs two things for each dependency: the .pom (to learn its own dependencies) and the artifact file (the jar). It resolves them using this algorithm for each coordinate.

  1. Look in the local repository. It is a cache, not a "repository" you publish to. If the files and their _remote.repositories marker are right, use them. No network.
  2. If missing, build the list of remote repositories from the POM (and parents), settings profiles and the Super POM, then apply mirror rules to replace URLs.
  3. Ask each remote in order. The first that answers wins and the file is stored in the local repository with a marker recording which repository id it came from.
  4. If a download fails (404 or network), Maven writes *.lastUpdated and will not retry that repo until the update interval has passed (daily by default).

Why a repository manager. Nexus or Artifactory sits between your developers and the internet. It gives you: (a) hosted repositories for your own releases and snapshots, (b) a proxy cache of Central so builds survive an outage and download fast, (c) a single group URL that merges them, so developers configure one mirror, (d) control, such as blocking a vulnerable or malicious package, and (e) an audit trail.

Example of the marker issue. You download vendor-sdk:3.1 once from a vendor repository, then remove that repository from the POM. The jar is still in ~/.m2, but Maven (3.x, with its enhanced local repository manager) may refuse it because the recorded repository id is no longer in the build, and report the artifact as missing. This protects against jars from an unexpected source. Re-adding the repository, or deleting that artifact folder so it is downloaded again, fixes it.

Pitfalls. Never publish a "just for me" jar by running mvn install and telling the team to do the same. Always deploy to the manager. Also, the same group URL cached stale metadata is a common reason a new release "does not exist yet": clear it in the manager UI (invalidate cache), not on every laptop.

Remember: local, then mirror (Nexus), then Central. A failed download is cached until -U.

How does a multi-module Maven build work? What is the reactor? Intermediate

A multi-module project has a root POM with packaging pom and a <modules> list. When I run Maven at the root, the reactor reads all module POMs, builds a graph from how they depend on each other, and builds them in dependency order, not in the order of the list. A cycle between modules is an error.

Inside one reactor build a module can use a sibling's output straight from target/classes (or the packaged jar), with nothing installed into ~/.m2. To build part of the project I use -pl (project list), with -am to also build what they need, or -amd to also build their dependents. -rf :web resumes after a failure and -T 1C builds independent modules in parallel, one thread per core. By default one failure stops the build, and --fail-at-end carries on with independent modules.

mvn -pl service,web -am -DskipTests package   # these two and what they need
mvn -T 1C -B verify                            # parallel
mvn -rf :web verify                            # resume from web

What problem it solves. A real product splits into modules: common, domain, repository, service, web. They depend on each other, so they must be compiled in a specific order, and a change in common must be visible to web immediately. Building each from its own folder and installing in the right order by hand would be error-prone.

What the reactor does, step by step.

  1. Read the root POM and every module POM listed in <modules> (recursively).
  2. Build a graph: module X depends on module Y if X lists Y's coordinates in its dependencies (or parent, or plugin).
  3. Topologically sort it. Modules without relationships keep the order of the list.
  4. Run the requested lifecycle phase on module 1 completely, then on module 2, etc. (or in parallel with -T).

That means the same mvn verify from the root runs compile, test, package, verify for common, then the same for domain, and so on. A failing module causes the rest to be marked SKIPPED in the "Reactor Summary".

Sibling resolution. When web needs common, the reactor supplies common/target/classes (for phases before package) or the packaged jar (for package and later). Nothing is read from ~/.m2. One catch: with only mvn compile, some plugins that expect a packaged jar from a sibling misbehave (for example assembly or shade). Running mvn package or higher avoids it.

Useful flags.

FlagMeaning
-pl service,webonly these modules
-amalso make what they depend on
-amdalso make modules that depend on them
-rf :webresume from module web
-T 1Cone thread per CPU core, independent modules in parallel
-fae / -fnfail at end / fail never

Pitfalls. Running mvn test -pl web without -am makes Maven fetch common from ~/.m2, which may be an old copy. Also, parallel builds expose modules that secretly share a file or port in tests.

Remember: the reactor orders modules by dependencies. Partial build: -pl x -am.

What is a fat (uber) jar, how do you build one with Maven and Gradle, and how does it differ from a thin jar? Intermediate

A thin jar contains only your classes and relies on the dependency jars being supplied separately. A fat jar bundles your classes and all dependency classes into one file, so java -jar app.jar just works. In Maven I use the shade plugin, or for Spring Boot the Boot plugin's repackage goal. In Gradle the Shadow plugin, or Boot's bootJar.

Why it exists. A plain jar gives the JVM no way to find its dependencies. You would have to ship a folder of jars and write a classpath on the command line. A single self-contained file is easy to put in a container or copy to a server.

Two different mechanisms.

  • Shade (unpack and merge). The plugin unpacks every dependency jar and copies all class files into one jar. Problems: two jars with the same resource name (META-INF/services/..., reference.conf, license files) overwrite each other, so you need transformers that merge them. It can also relocate packages to avoid jar hell.
  • Nested jars (Spring Boot). Boot's executable jar keeps dependencies as whole jars inside BOOT-INF/lib, and a special launcher class loader reads them. Nothing is unpacked, so there are no collisions and layers can be extracted for better Docker caching.
<!-- Maven, Spring Boot -->
<plugin>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-maven-plugin</artifactId>
</plugin>   <!-- repackage is bound to package by the Boot parent -->

// Gradle, Spring Boot plugin
./gradlew bootJar      // executable. The plain 'jar' task makes a separate thin jar

Trade-offs. Fat jars are convenient but large, rebuilt entirely for every code change (bad for Docker layers unless you use Boot's layered jars), and they hide dependencies from scanners that only read the POM, so scan the final artifact. A thin jar plus a dependency folder or a layered container image gives better caching.

Pitfalls. A shaded library with signed jars fails with a security exception unless signature files (META-INF/*.SF) are excluded. A missing service-file merge makes a plugin or JDBC driver "disappear" at runtime.

Remember: thin jar = your code only; fat jar = everything in one file. Shade merges classes, Spring Boot nests jars. Scan the final artifact.

4. Gradle core: phases, tasks, incremental build and caching

Explain the three phases of a Gradle build: initialization, configuration, execution. Intermediate

In initialization, Gradle reads settings.gradle(.kts) to find which projects are in the build. In configuration, it runs the build script of every project to create tasks and wire the task graph, but no task action runs yet. In execution, it runs only the tasks needed for the requested one, in dependency order, skipping the up-to-date ones.

The classic trap is code written straight in the build script body or a configure block. It runs at configuration time on every build, even for gradle help, so an exec call or a network request there slows every command. Work belongs inside doLast { } or a task class, which run only at execution time. The configuration cache can skip phase 2 completely when nothing in the build logic changed.

tasks.register("report") {
    println("CONFIG time: runs on every build")      // bad place for work
    doLast { println("EXECUTION time: only when task runs") }
}

Why three phases. Gradle first needs to know what the build is (which projects, which tasks, how they connect) before it can decide what to run. It builds the whole task graph in advance. That allows it to skip tasks, run in parallel, and print --dry-run. Maven by contrast discovers things as it goes.

Timeline for ./gradlew :web:build in a 3-project build.

  1. Initialization: Gradle finds settings.gradle.kts, reads include("core","service","web"), creates three Project objects. Included builds (includeBuild("build-logic")) are processed here.
  2. Configuration: Gradle evaluates build.gradle.kts of each project (or only the needed ones with "configuration on demand"), applies plugins, registers tasks and their dependencies. Task configuration blocks run here, but task actions do not. At the end, Gradle has the DAG.
  3. Execution: from the DAG, select the requested task and everything it depends on, then run each: check UP-TO-DATE or FROM-CACHE, otherwise run the action.

Which lines run when. In this script, only the last println belongs to execution:

println("A: build script top level")              // configuration, always
tasks.register("hello") {
    println("B: task configuration block")      // configuration, only if hello is realized
    doFirst { println("C: before action") }     // execution
    doLast  { println("D: after action") }      // execution
}

With task configuration avoidance (register), line B runs only if some task in the requested graph needs hello. With create it always runs.

Why it matters in practice. A build script that calls git describe with "git describe".execute() at the top level launches a process every time, on every command, including your IDE's sync. Wrap it in a provider (providers.exec) so it is evaluated lazily and is compatible with the configuration cache. Gradle lists such problems in its configuration-cache report.

Also in settings. settings.gradle(.kts) is where repositories for plugins (pluginManagement), the version catalog and dependency repositories can be centralised. Subprojects then inherit and cannot add random repositories if you set repositoriesMode to fail.

Remember: initialize (which projects), configure (build the graph, no work), execute (run tasks). Keep work out of configuration.

What is a Gradle task, and how does the task graph decide the order? Intermediate

A task is a unit of work with inputs, outputs and an action, like compiling Java or running tests. Gradle collects the needed tasks into a directed acyclic graph (DAG: arrows with no cycles), sorts it, and runs independent tasks in parallel if allowed. If I ask for build, it pulls in everything build needs and nothing else.

Order comes from relationships. dependsOn means "run that first, and add it to the graph". mustRunAfter only sets an order when both tasks are already in the graph. finalizedBy runs a cleanup task after me, even if I fail. Most dependencies are inferred: if task B uses the output of task A as its input, Gradle links them without a hand-written dependsOn. Use tasks.register, not tasks.create: register builds the task only if it is needed (configuration avoidance), which keeps configuration fast in a big build.

gradle build --dry-run        # show the tasks that would run, run none
gradle :app:test --tests '*OrderServiceTest'
gradle build -x test          # exclude a task

Anatomy of a task. A task has: inputs (files, properties), outputs (files, directories), and one or more actions (code to run). Because inputs and outputs are declared, Gradle can wire tasks together and skip them. The Java plugin's compileJava has the sources and classpath as inputs, and build/classes/java/main as output.

Three ways dependencies between tasks arise.

  1. Implicit, by wiring outputs to inputs: jar uses the output of classes, so Gradle runs classes first. This is the best way: you cannot forget it.
  2. dependsOn: explicit. "Before I run, those must have run."
  3. Ordering only: mustRunAfter and shouldRunAfter (soft). They do not pull tasks in. finalizedBy says "when I run, also run that afterwards".

Example: a database test with cleanup.

val startDb = tasks.register("startDb") { doLast { /* start container */ } }
val stopDb  = tasks.register("stopDb")  { doLast { /* stop container */ } }
tasks.test {
    dependsOn(startDb)      // start before tests
    finalizedBy(stopDb)     // stop afterwards, even if tests fail
}

A gradle test run goes startDb, test, stopDb. This is Gradle's version of Maven's pre- and post-integration-test phases.

Eager versus lazy. In older scripts you see task foo { ... } or tasks.create: the task and its configuration are created immediately for every project, even for tasks nobody requests. In a 200-project build this adds seconds on every command. tasks.register stores a recipe and builds the task only when needed. Likewise use tasks.named("test") rather than tasks.getByName, and configureEach rather than all.

Cycles and debugging. If task A depends on B and B on A, Gradle fails with "Circular dependency". Use --dry-run to see the order and --scan or gradle :web:build --console=plain to see what ran. Passing -x test removes a task and the tasks only it needed.

Remember: tasks form a DAG. dependsOn adds and orders; mustRunAfter only orders. Prefer register.

How does Gradle know a task is UP-TO-DATE? Intermediate

Before running a task, Gradle fingerprints its inputs (source files, properties, classpath) and its outputs, and compares them with what it stored from the last run. If both are unchanged, the task is marked UP-TO-DATE and skipped. This is the incremental build, and the build cache is built on the same idea.

Fingerprints use file contents, not only timestamps, so touching a file without changing it triggers no rebuild. A custom task that declares no inputs and outputs always runs, because Gradle has nothing to compare. The opposite bug is worse: a task reads a file it did not declare as an input, so Gradle thinks nothing changed and keeps a stale result. So declare everything a task reads and writes. The statuses to know: UP-TO-DATE (local outputs are fine), FROM-CACHE (outputs restored from the build cache), NO-SOURCE (nothing to process). --info tells why a task re-ran.

Why it matters. Running the whole build after every one-line change wastes minutes. If task output is a pure function of its inputs, then same inputs mean the same output, so there is nothing to do. Gradle formalises this and is strict about it.

How the check works, step by step.

  1. At the end of a successful run, Gradle stores in .gradle/ a fingerprint of the task's inputs (hash of each input file's content and path-sensitivity rules, property values, the task implementation class) and of its outputs.
  2. Next run, before executing, it recomputes the input fingerprint and checks the outputs still match what it wrote (so deleted or edited outputs are noticed).
  3. If both match: UP-TO-DATE. Otherwise it runs, and may be incremental (compile only the changed classes if the task supports it).

Example. You change one comment in Foo.java. compileJava re-runs, but because the resulting class file is byte-identical, downstream tasks like jar and the consumer's compileJava see the same inputs and are UP-TO-DATE. (This "compile avoidance" is why Gradle compares the class's ABI, not just file timestamps.) If you change a private method body in an implementation dependency, consumer modules do not recompile.

Declaring inputs correctly in a custom task.

abstract class GenReport : DefaultTask() {
    @get:InputFile  abstract val template: RegularFileProperty
    @get:Input      abstract val env: Property<String>
    @get:OutputFile abstract val result: RegularFileProperty
    @TaskAction fun run() { /* read template, write result */ }
}

If you forget @Input on env, changing the environment will not rerun the task: a stale result. If you declare no outputs at all, the task never counts as up to date. @Internal marks a field that is deliberately not an input.

Debugging a task that always reruns. Run with --info to see "Task ':x' is not up-to-date because: Input property 'timestamp' has changed". Look for current time, random values, absolute paths, or an output directory that another task also writes into (overlapping outputs disable caching).

Remember: same inputs and same outputs means skip. Undeclared inputs cause stale results.

What is the Gradle build cache, and how is it different from the up-to-date check? Senior

The up-to-date check compares only with the last run in the same workspace. The build cache stores task outputs under a key that is a hash of all the inputs, so any build on any branch or machine that reaches the cache can download the outputs instead of running the task. Gradle then marks the task FROM-CACHE. It pays off most on CI and when switching branches.

There is a local cache and an optional remote cache (an HTTP service, typically writable by CI only). For a hit, tasks must be cacheable and deterministic. If a task puts a timestamp or an absolute path into its output, or reads an undeclared input, the key differs, or worse, a wrong output is shared. When the cache never hits on CI, I compare two build scans, which show the input that differs. Usual culprits are absolute paths, timestamps, a different JDK, or environment variables. Enable it with org.gradle.caching=true.

The configuration cache is a different thing: it saves the result of the configuration phase (the task graph) so the next run skips straight to execution. It needs tasks not to touch the live project model at run time. It became stable in Gradle 8.1 and is switched on with org.gradle.configuration-cache=true.

# gradle.properties
org.gradle.caching=true
org.gradle.configuration-cache=true
org.gradle.parallel=true

Three different caches people mix up.

CacheWhat it storesScopeSkips
Up-to-date checkFingerprints of last runThis workspace onlyRe-running a task
Build cacheTask outputs, keyed by input hashLocal machine, optionally shared (remote)Running a task that someone already ran
Configuration cacheThe serialized task graphLocal machineThe whole configuration phase

Why a build cache helps. On CI a fresh clone has no previous run, so up-to-date checks are useless. But if the same inputs were built on the main branch 20 minutes ago, the outputs are in the remote cache. Your pull request build downloads compiled classes and test results instead of recomputing. Developers switching between branches also benefit because outputs for branch A are still in the local cache.

How the key is formed. A hash over the task's type and implementation, all input file contents, input properties, the classpath of the task, and (for compile) the JDK version. Same hash means the output is substitutable. This is why non-determinism is the enemy: a task embedding a build date creates a different output every time, which poisons the cache or means it never hits.

Typical setup. Local cache on by default for all developers (org.gradle.caching=true). A remote cache (Gradle Enterprise or Develocity, or an open HTTP/S3-backed one) where only CI can write and developers read only. That avoids polluted entries from half-broken local builds.

// settings.gradle.kts
buildCache {
    local { isEnabled = true }
    remote<HttpBuildCache> {
        url = uri("https://cache.example.com/cache/")
        isPush = System.getenv("CI") != null    // only CI writes
    }
}

Which tasks are cacheable. Those annotated @CacheableTask (compile, test with useJUnitPlatform, checkstyle, etc.). Tasks that run integration tests with a real network are often not marked cacheable, because their output does not depend only on declared inputs. Test tasks are cacheable, but a test that passed is then not re-run, so a flaky test is not re-tried: consider that when you wonder why a test "did not run".

Configuration cache caveats. A task that reads project at execution time, or uses System.getenv directly, is flagged. Fix by using providers and task properties. Some plugins are not yet compatible; Gradle's report lists them, and you can run in warn mode while migrating.

Remember: up-to-date = same workspace; build cache = shared outputs by input hash; configuration cache = saves the task graph.

What are the Gradle and Maven wrappers, and why commit them? Basic

The wrapper is a small script (gradlew or mvnw) committed to the repo. It downloads the exact Gradle or Maven version named in a properties file and runs it. So every developer and CI use the same tool version and need only a JDK installed.

For Gradle the files are gradlew, gradlew.bat and gradle/wrapper/ (a properties file plus a small jar). I upgrade with ./gradlew wrapper --gradle-version <version> and commit the change. For Maven, mvn wrapper:wrapper creates mvnw and .mvn/wrapper. A safe practice is to add distributionSha256Sum so a tampered download is rejected, since the wrapper jar is executable code. A related point: Gradle runs a background JVM (the daemon) that stays alive for about three hours idle, so later builds start fast. If behaviour looks strange, ./gradlew --stop kills the daemons.

The problem. "It works with Gradle 7.6 on my machine, but CI has 8.4 and breaks." Or a new hire must first install the correct Maven version. Tool versions differ, plugins behave differently, and the build is not reproducible. The wrapper moves the tool version into the repository.

How ./gradlew works, step by step.

  1. The script reads gradle/wrapper/gradle-wrapper.properties, which contains distributionUrl=.../gradle-8.7-bin.zip (and optionally distributionSha256Sum).
  2. If that distribution is not already in ~/.gradle/wrapper/dists, it downloads and unzips it once.
  3. It runs that Gradle with your arguments. Subsequent runs reuse it.

The Maven wrapper (mvnw) behaves the same way, driven by .mvn/wrapper/maven-wrapper.properties, and downloads Maven into ~/.m2/wrapper. Recent versions of the Maven wrapper can run in a script-only mode that does not need the binary jar, which is easier to review.

Security. The wrapper jar is binary code in your repo that runs on every developer's machine. Gradle publishes the checksums of official wrapper jars, and the GitHub action "wrapper-validation" verifies yours. Behind a company proxy point distributionUrl to an internal mirror so builds do not need internet access to services.gradle.org.

Also commit a JDK choice. The wrapper pins the tool, not Java. For Java use Gradle toolchains (java { toolchain { languageVersion = JavaLanguageVersion.of(21) } }) so Gradle finds or downloads the right JDK, or maven.compiler.release in Maven plus a fixed JDK in CI.

The daemon. Starting a JVM and loading Gradle takes seconds. The daemon keeps it warm; it is reused by builds with compatible settings and stops after about 3 hours idle. In CI use --no-daemon only for one-off containers, and note that two builds with different JVM args start two daemons, which doubles memory use. Gradle's org.gradle.jvmargs=-Xmx2g in gradle.properties is the usual tuning.

Pitfall. A teammate runs plain gradle from their PATH instead of ./gradlew and gets different behaviour. Document "always use the wrapper".

Remember: commit gradlew/mvnw so everyone builds with the same tool version. Strange Gradle behaviour: --stop.

5. Gradle dependencies, version control and multi-project builds

What is the difference between api and implementation in Gradle? Intermediate

Both come from the java-library plugin. implementation means "my code uses this library inside, it is not part of my public API", so modules that depend on mine do not get it on their compile classpath. api means "this library's types appear in my public signatures", so consumers need it to compile and do get it. I start with implementation and switch to api only when a type from that library is visible in my public methods.

Two reasons to prefer implementation. It hides internals, so consumers cannot depend on them by accident. And it makes builds faster: when an implementation dependency changes, only my module recompiles, while a change to an api dependency ripples through every consumer. Note the library is still on the consumers' runtime classpath. Maven has no direct equivalent: a Maven compile dependency leaks to all downstream modules like api. The other keywords map to Maven scopes: compileOnly to provided, runtimeOnly to runtime, testImplementation to test. The old compile and runtime configurations were removed in Gradle 7.

plugins { `java-library` }
dependencies {
    api("com.google.code.gson:gson:2.11.0")              // in public signatures
    implementation("com.squareup.okhttp3:okhttp:4.12.0") // internal only
    compileOnly("org.projectlombok:lombok:1.18.34")
    runtimeOnly("org.postgresql:postgresql:42.7.4")
    testImplementation("org.junit.jupiter:junit-jupiter:5.10.2")
}

The idea in one picture. A library module lib has an inside and an outside. Types that appear on the outside (in public method signatures, public fields, superclasses) are the API. A consumer compiling against lib needs those types. Types used only inside method bodies are implementation details.

Concrete example.

// in module lib
public class PriceClient {
    public Gson mapper() { ... }                 // Gson in the signature: api
    public Price fetch(String id) {              // OkHttp only inside: implementation
        OkHttpClient c = new OkHttpClient();
        ...
    }
}

If Gson were declared implementation, the consumer calling client.mapper() would fail to compile with "class file for com.google.gson.Gson not found". If OkHttp were declared api, consumers could start importing OkHttp classes and depend on a library they never chose, so you could never replace it without breaking them.

Why it makes builds faster. Gradle computes each module's compile classpath from api dependencies only (plus the module's own). A change in an implementation dependency changes the module's runtime but not the consumers' compile classpath, so consumers are not recompiled. In a large build this prevents a change in a deep leaf from recompiling everything.

Which configurations exist (Java and java-library plugins).

ConfigurationCompile this moduleConsumers compileRuntime

implementationyesnoyes
compileOnlyyesnono
runtimeOnlynonoyes
testImplementationtests onlynotests only

Pitfall. The plain java plugin has no api configuration. You need java-library for library modules. An application module (one that no one depends on) can just use implementation everywhere. Also, implementation dependencies still appear in the consumer's runtime classpath, so classloader conflicts can still occur.

Remember: api = visible to consumers at compile time; implementation = private. Default to implementation.

How does Gradle resolve version conflicts, how is it different from Maven, and how do you override a version? Intermediate

Gradle builds the whole graph first, then picks the highest requested version of each module. Maven picks the nearest. If my app asks for util 1.0 and a library asks for util 2.0, Maven keeps 1.0 and Gradle uses 2.0. Gradle's rule is usually safer when libraries follow semantic versioning, but a major version can break the API, so I still test.

To override, I use a constraint: "if this library appears anywhere, it must be at least this version". It adds no dependency by itself, so it is Gradle's equivalent of dependencyManagement. A platform(...) imports a BOM as constraints, and strictly in a version is a hard rule that fails the build if it cannot be met. force works but hides the reason, so I prefer a constraint with a because note. To see why a version was chosen, gradle dependencyInsight --dependency name shows who asked for what and which rule won. In gradle dependencies output an arrow like 1.0 -> 2.0 means the request was upgraded.

dependencies {
    implementation(platform("org.springframework.boot:spring-boot-dependencies:3.3.4"))
    implementation("org.springframework.boot:spring-boot-starter-web")  // no version
    constraints {
        implementation("com.acme:util:2.1") { because("CVE fix, see SEC-123") }
    }
}
// ./gradlew :app:dependencyInsight --dependency util --configuration runtimeClasspath

Why "highest wins". Gradle's reasoning: if some library in the graph needs util 2.0, it was tested with at least 2.0 and probably does not work on 1.0. If library semantic versions are honest, newer versions are backward compatible, so choosing the highest satisfies everybody. Maven's nearest-wins gives local control instead. Neither is always right: a major version bump (Guava 20 to 33, or Jackson 2 to 3) can break the API, so "highest" can also break an old library that cannot work with the new API.

How Gradle works through it. First it resolves the whole graph, collecting every requested version of each module. Then it selects. Rich version declarations let you say more than a number: require (a minimum, default), prefer (a soft hint), strictly (a hard limit, build fails if something else needs a higher version), reject (never this one).

implementation("com.acme:util") {
    version { strictly("[2.0, 3.0)"); prefer("2.4") }   // stay in the 2.x line
}

Making conflicts loud. By default Gradle resolves silently. To fail on a conflict (like Maven's enforcer), add:

configurations.all {
    resolutionStrategy.failOnVersionConflict()
}

Then each conflict must be resolved intentionally with a constraint. For repeatable resolution, dependency locking records resolved versions in gradle.lockfile (./gradlew dependencies --write-locks), useful where dynamic versions or ranges are in use.

Reading output. In gradle dependencies, util:1.0 -> 2.0 means requested 1.0, selected 2.0. A (c) marks a constraint, and (*) means "already shown above". dependencyInsight prints the reason ("by conflict resolution", "by constraint", "because: CVE fix").

Compare with Maven for the exam. Same inputs, opposite result: app declares util 1.0 directly, library asks for 2.0. Maven keeps 1.0 (nearest, depth 1). Gradle also resolves to 2.0, because requests are merged and the highest wins, even though you declared 1.0 directly. To pin 1.0 in Gradle you need strictly.

Remember: Gradle highest wins, Maven nearest wins. Override with a constraint or platform, and explain why.

What is a Gradle version catalog, and why use one? Intermediate

A version catalog is a file, gradle/libs.versions.toml, that lists versions, libraries, bundles and plugins in one place. Gradle generates type-safe accessors, so a build file says libs.jackson.databind and the IDE autocompletes it. It gives one place to update a version for all modules and avoids copy-pasted version strings.

The sections are [versions], [libraries], [bundles] (libraries used together, like test libraries) and [plugins]. It has been stable since Gradle 7.4. A catalog only declares coordinates. It does not force versions in the dependency graph, so conflict handling is still done with constraints or platforms. It plays the role that properties in a Maven parent POM play, but type safe.

# gradle/libs.versions.toml
[versions]
jackson = "2.17.2"
[libraries]
jackson-databind = { module = "com.fasterxml.jackson.core:jackson-databind", version.ref = "jackson" }

// build.gradle.kts
dependencies { implementation(libs.jackson.databind) }

The problem. In a 30-module Gradle build, "com.fasterxml.jackson.core:jackson-databind:2.17.2" may appear in 12 files. Updating means search and replace, with typos and drifted versions. Before catalogs, teams used ext properties or buildSrc constants, which worked but were not standard and gave poor IDE support.

What a catalog gives. One file declares names. Gradle generates a libs object, so you write libs.jackson.databind (the dash in the alias becomes a dot). A typo is a compile error in the build script and the IDE autocompletes.

# gradle/libs.versions.toml
[versions]
jackson = "2.17.2"
junit = "5.10.2"

[libraries]
jackson-databind = { module = "com.fasterxml.jackson.core:jackson-databind", version.ref = "jackson" }
junit-jupiter    = { module = "org.junit.jupiter:junit-jupiter", version.ref = "junit" }

[bundles]
testing = ["junit-jupiter"]

[plugins]
spring-boot = { id = "org.springframework.boot", version = "3.3.4" }
// any module's build.gradle.kts
plugins { alias(libs.plugins.spring.boot) }
dependencies {
    implementation(libs.jackson.databind)
    testImplementation(libs.bundles.testing)
}

Catalog versus platform versus constraint. A catalog is only a naming and version lookup at declaration time. If a transitive dependency asks for a different Jackson, the catalog does nothing about it. A platform or constraint influences resolution of the graph. They are often used together: the catalog names the BOM, and the build file passes it to platform(libs.spring.bom).

Sharing across repositories. A catalog can be published as a module (version-catalog plugin) and imported in settings.gradle.kts by coordinates, which is how a company keeps versions the same across services. The default location gradle/libs.versions.toml needs no configuration. Maven has no direct counterpart; the closest is a company BOM or parent.

Pitfall. Keeping versions only in the catalog and also hardcoding one in a module creates a drift again. Make the catalog the only place, and enforce with a review rule or a lint.

Remember: catalog = names and versions in one TOML file; constraints and platforms still decide the graph.

How do you make Gradle dependency resolution repeatable (dynamic versions, locking, verification)? Senior

Avoid dynamic versions such as 1.+ or latest.release, or if you must use ranges, turn on dependency locking, which records the exact resolved versions in a lockfile that is committed. For supply-chain integrity, add dependency verification, which records checksums of the downloaded artifacts and fails if they change.

Why. A build that resolves com.acme:util:1.+ gives a different result the day 1.9 is released. A bug appears with no code change, and an old tag can no longer be rebuilt identically. Reproducibility needs the same graph every time.

Locking, step by step.

  1. Activate it: dependencyLocking { lockAllConfigurations() } in the build script.
  2. Write the lock: ./gradlew dependencies --write-locks creates gradle.lockfile. Commit it.
  3. Normal builds now resolve to exactly those versions and fail if the lock disagrees with what the declarations would resolve to.
  4. To update, run with --update-locks com.acme:util (or rewrite all) and review the diff in the pull request. That diff is the explicit record of what changed.

Verification. ./gradlew --write-verification-metadata sha256 creates gradle/verification-metadata.xml with checksums. A tampered or re-published artifact then fails the build. This complements locking: locking pins which version, verification pins which bytes.

Maven equivalents. Use exact versions, the enforcer's requireReleaseDeps, and avoid ranges. Maven has no native lockfile; teams rely on pinned versions and a BOM. The Maven wrapper and repository manager checksums give integrity.

Trade-off. Locking increases update work (someone must refresh it), so automate with Renovate or Dependabot, which understand lockfiles. Many teams skip locking for libraries (consumers choose versions anyway) and use it for deployable applications.

Remember: no dynamic versions, or lock them (gradle.lockfile); verification pins checksums. Review lock diffs like code.

How does a multi-project Gradle build work, and how do you share build logic across projects? Intermediate

settings.gradle(.kts) names the root project and lists subprojects with include("core", "service", "web"). Each subproject has its own build file, and dependencies between them are written implementation(project(":core")). To share build logic I use convention plugins, not allprojects { } blocks.

Gradle works at the task level, so asking for :web:build builds what web needs from core automatically, with no flag like Maven's -am, and independent tasks can run in parallel (org.gradle.parallel=true). For shared logic, allprojects and subprojects blocks in the root script couple the projects and hide where settings come from. A convention plugin is a small precompiled script plugin (for example acme.java-conventions.gradle.kts) that sets the Java version, test settings and static analysis. Each module just says plugins { id("acme.java-conventions") }. It lives in an included build such as build-logic, or in buildSrc, which is simpler but invalidates caches of the whole build whenever it changes. It plays the role of a Maven parent POM, but a module can combine several conventions.

// settings.gradle.kts
rootProject.name = "shop"
includeBuild("build-logic")
include("core", "service", "web")

// web/build.gradle.kts
plugins { id("acme.java-conventions") }
dependencies { implementation(project(":core")); implementation(project(":service")) }

Why this structure. A multi-project build lets you split a system into modules with a single command and shared configuration. In Maven the root POM is both parent and aggregator. In Gradle those jobs are separated: the settings file says which projects exist, each project file says what it needs, and shared behaviour is a plugin.

What happens for ./gradlew :web:build. Gradle loads the three projects. The task graph for :web:build includes :core:jar and :service:jar because web declares project(":core") and its classes are an input. Those jars are built first, automatically. You never write -am.

Why not allprojects { ... }. It puts configuration in the root script that affects children invisibly. A developer reading web/build.gradle.kts cannot see where the Java version came from. It also forces configuration of all projects in order (blocks configure on demand and parallel configuration) and makes the root know about every module type. Gradle's documentation discourages it.

A convention plugin in practice. Put in build-logic/src/main/kotlin/acme.java-conventions.gradle.kts:

plugins { `java-library` }
java { toolchain { languageVersion = JavaLanguageVersion.of(21) } }
tasks.withType<Test> { useJUnitPlatform() }
repositories { mavenCentral() }

and a second one for Spring services (acme.spring-conventions) that applies the first plus the Boot plugin. A library module applies only the first, an app applies both. You can compose conventions, which is more flexible than Maven's single parent chain.

buildSrc versus included build. buildSrc is automatic and simple, but any change inside it invalidates the build script classpath, so many tasks re-run. A build-logic included build is more granular for caching and can be developed independently. For new projects, prefer the included build.

Other cross-project tools. java-test-fixtures to share test helpers, a java-platform module as your own BOM, and a composite build (includeBuild("../other-repo")) to substitute a published library with local source while you debug it. That last one is the Gradle answer to "install it in .m2 by hand".

Remember: settings lists projects; share logic with convention plugins (build-logic), not allprojects.

6. Maven versus Gradle

Compare Maven and Gradle. When would you choose each? Basic

Maven is declarative with a fixed lifecycle: the POM says what the project is, so every Maven project looks alike and a new engineer is productive at once. Gradle is programmable with a task graph, and is faster on big builds because of incremental work, the build cache and the daemon. I choose Maven for standard services and libraries where uniformity matters, and Gradle for large multi-module repos where build time matters, for Android, and for builds with custom steps.

Gradle's cost is a steeper learning curve and more freedom to write a messy build. Maven's cost is rigidity: unusual builds need plugin configuration. In both, quality comes from discipline: pinned versions, shared conventions, a wrapper, and no heavy logic in the wrong place. The conflict rule is the favourite trap: Maven takes the nearest version, Gradle the highest.

The deeper difference: how each tool thinks. Maven asks "which phase are we in?" and runs the plugin goals bound to it. It has no idea what a goal's inputs are, so it cannot know a step is unnecessary, and a repeated mvn package mostly redoes everything (the compiler plugin does some stale-file detection, but that is limited). Gradle models every step as a task with declared inputs and outputs, so it can prove a step is unnecessary and skip it, restore it from a cache, or run it in parallel.

What this means for a day of work. Change one line in a leaf module of a 40-module system. In Maven you typically rebuild the module and everything after it, and run all tests (unless you carefully use -pl -am). In Gradle the leaf is recompiled, and dependent modules are recompiled only if the public API (ABI) changed, and unchanged tests are skipped. A well-tuned Gradle build often turns minutes into seconds, while a small Maven project can build just as fast and be simpler.

Where Maven wins in reality.

  • Uniformity. Every Maven project has the same layout and the same lifecycle, so tooling (IDEs, Sonar, release jobs, security scanners) integrates with minimal work. A POM is data, so tools can read and edit it, which is how Dependabot and the versions plugin work.
  • Predictability. There is little room for cleverness. Build logic that would be a custom task in Gradle usually becomes "find a plugin" in Maven.
  • Lower risk for libraries published to Maven Central, where the POM format is the standard anyway (Gradle generates POMs for you).

Where Gradle wins.

  • Large monorepos, thanks to incremental builds, the build cache and parallelism.
  • Android (Gradle is the official build tool), Kotlin multiplatform, mixed-language builds.
  • Complex custom pipelines (generate code, run a Node build, package a Docker image) expressed as typed tasks.
  • Fine control of dependency visibility (api versus implementation), feature variants and rich version constraints.

Costs of Gradle. A build script is code, so it can get complicated, slow at configuration, or unreadable. Debugging needs knowledge of the three phases and of the configuration cache. Upgrades between major versions can break plugins. The Kotlin DSL has slower first import than Groovy but gives IDE completion.

How to answer the "which would you choose" question. Say it depends on the team and size, and give a rule: "Default to what the team already knows and what the company tooling supports. Move to Gradle when build time is a measured problem or you need Android or advanced customisation. Do not migrate just for fashion, a migration costs weeks." That judgement impresses more than a partisan answer.

Migration notes. gradle init can convert a Maven project. The conflict rule differs, so run the dependency report on both and compare the runtime classpaths before shipping, because the resolved versions may differ.

Remember: Maven = convention and uniformity; Gradle = flexibility and speed. Nearest wins versus highest wins.

7. Vulnerable and conflicting dependencies

A scanner reports a CVE in a transitive dependency. How do you fix it? Senior

First I read the advisory: which versions are affected, whether a fix exists, and whether my service even uses the vulnerable code. Then I find who brings it with mvn dependency:tree -Dincludes=... or gradle dependencyInsight. Best fix is to upgrade the direct dependency that brings it. If the owner has no fix yet, I override the transitive version and write the CVE id next to it.

In Maven the override goes in dependencyManagement, in Gradle in a constraint with a because note. Patch and minor jumps are usually safe, a major jump needs real testing. Then I prove it: re-run the tree, the scanner and the tests, and scan the final artifact (the fat jar or image), not only the POM, because shaded copies are invisible to the tree. The comment lets someone remove the override later when the parent catches up. If no fixed version exists, I mitigate (disable the feature, validate input) and record an accepted risk with an expiry date. Tools: OWASP Dependency-Check, Snyk, Dependabot or Renovate for update pull requests, and an SBOM (a list of every component in a release) to answer "which services contain this library" quickly.

<!-- pom.xml: override a transitive version, reason documented -->
<dependencyManagement><dependencies>
  <dependency>
    <groupId>org.apache.logging.log4j</groupId>
    <artifactId>log4j-core</artifactId>
    <version>2.17.1</version> <!-- CVE-2021-44228 and follow-ups -->
  </dependency>
</dependencies></dependencyManagement>

Why this is a senior question. A scanner report is a list of names with scary scores. A senior engineer turns it into a decision: is it exploitable here, what is the cheapest safe change, and how do we know it worked. Blindly bumping versions can break production as surely as the vulnerability could.

Step-by-step workflow with an example. Scanner: "jackson-databind 2.9.10, CVE-XXXX, CVSS 9.8, fixed in 2.9.10.8" (an example).

  1. Triage. Read the advisory. Is the vulnerable feature in use (for example default typing enabled, deserialising untrusted input)? Is the service internet-facing? A CVSS 9.8 in an internal batch tool that never parses untrusted data may be less urgent than a 6.5 on your public API. Record the decision.
  2. Find the path. Maven: mvn dependency:tree -Dverbose -Dincludes=com.fasterxml.jackson.core. Gradle: ./gradlew dependencyInsight --dependency jackson-databind --configuration runtimeClasspath. Result: it comes through old-sdk-1.3, which asks for 2.9.10.
  3. Pick the fix, cheapest first.
    • Upgrade the direct dependency (old-sdk 1.3 to 1.8) if that release moved Jackson. Best, because the library is tested with that Jackson.
    • If no such release, override the transitive version in dependencyManagement or a Gradle constraint, with a comment and a ticket link.
    • If a patched version breaks compatibility, mitigate: switch off the risky feature, add input validation or a WAF rule, and plan a real upgrade.
  4. Verify. Rebuild, run the tree again, run unit and integration tests, rerun the scanner against the final artifact (jar, container image). A shaded copy inside a fat jar or an old jar baked into a base image does not appear in the dependency tree.
  5. Prevent recurrence. Automated update pull requests (Dependabot or Renovate), a scheduled scan in CI that fails above a threshold, and an SBOM per release. When the next Log4Shell happens, the SBOM answers "which of our 80 services contain log4j-core 2.14" in minutes, instead of days.

Two traps. First, overrides rot: if the parent later upgrades past your pin, your pin may hold the library back. A comment with the CVE id and an enforcer or lint rule lets someone remove it. Second, false positives: scanners match by name and version, so a library that merely contains a similar-named class, or a CVE that applies only to an unused module, is reported anyway. Suppress with a documented, expiring entry (OWASP Dependency-Check supports suppression files), never silently.

Gradle snippet for the same fix.

dependencies {
    constraints {
        implementation("com.fasterxml.jackson.core:jackson-databind:2.17.2") {
            because("CVE-XXXX, transitive via old-sdk, remove after old-sdk 2.0")
        }
    }
}

Remember: understand it, trace it, upgrade the parent or override the version, re-scan the built artifact, document why.

8. Real-life scenarios

Every answer follows the same shape: situation, what you check first, the fix, and how you prevent it next time. Say this shape aloud in the interview, it shows you work calmly under pressure.

The build passes on your laptop but fails on CI. How do you find the cause? Senior

Almost always the two environments differ: tool or JDK versions, or something that exists only in my local cache or settings. I read the first error in the CI log, then reproduce CI locally with a clean clone, an empty cache and the same JDK, and fix the cause rather than re-running until green.

Situation: same commit, green locally, red in the pipeline (compile error, test failure or missing dependency).

Check first: print mvn -v or ./gradlew --version on CI and compare. Then look for local-only state: a SNAPSHOT or a jar I once mvn installed by hand, a profile or mirror in my own settings.xml, environment variables, file name case (Windows ignores case, Linux does not), time zone, locale, and test order or shared state.

Fix: run the exact CI command in a clean clone with a throwaway cache (-Dmaven.repo.local=/tmp/m2 or GRADLE_USER_HOME=/tmp/g). If a dependency was only in my cache, publish it properly or declare it. Pin the JDK.

Prevent: commit the wrappers, set maven.compiler.release or a Gradle toolchain, and use the same container image locally and on CI.

Watch out: clearing the CI cache and re-running until it turns green hides a dependency on local state.

Why this keeps happening. A build depends on more than your source: the JDK, the tool version, the contents of the local cache, environment variables, files outside the repo, the operating system and time. CI is the one environment with nothing but the repo, which is why it is the honest one. A pass on your laptop only proves that your laptop works.

A systematic way to find the difference. Work from cheapest to most expensive, and change one thing at a time.

  1. Read the first error in the CI log, not the last (the last is usually a consequence).
  2. Compare versions: JDK (java -version, and whether CI uses the compiler's release setting), Maven or Gradle, OS. If CI runs an older JDK than your laptop, or you compile on a new JDK with only -source/-target and not --release, a call to a newer JDK API (for example String.isBlank(), Java 11) compiles on your machine and fails with NoSuchMethodError where the older JDK runs it.
  3. Run a clean clone locally: git clone to a new folder, then mvn -Dmaven.repo.local=/tmp/m2 verify. If it now fails like CI, the cause is something from your cache or a file that is untracked (check git status --ignored, a .gitignored config file is a classic).
  4. Run the build in the same container image as CI.

Frequent causes, with the symptom that points to them.

SymptomLikely cause
"Could not find artifact x-1.0-SNAPSHOT"You installed it locally by hand; CI cannot see it
File not found, only on LinuxCase-sensitivity (Config.java vs config.java)
Test fails only sometimes in CITest order, time zone, parallel execution, port clash, slow machine
Works only with VPNYour settings.xml has an internal mirror that CI lacks, or the reverse
Different dependency versionsVersion ranges, dynamic versions, or Maven versus Gradle conflict rules; compare dependency trees

The "just clear the cache" temptation. If clearing CI's cache makes it green, you have found that the build depends on cache state, not fixed the cause. Look at what was in the stale cache and why a clean run would not have produced it.

Making it hard to recur. One toolchain definition used by both laptop and CI, wrappers, -B (batch mode) for readable logs, a CI step that builds from an empty cache nightly, and a rule that CI is the only place releases are built.

Remember: compare tool versions, then hunt local-only state (cache, settings, hand-installed jars).

After a deploy the service throws NoSuchMethodError, but all tests passed. What do you do? Senior

First I roll back if users are affected. Then I treat it as jar hell: the packaged app has a different version of a library than the one the code compiled against. I find who brings the old copy, pin one version, and add a guard so it cannot return.

Situation: production logs show NoSuchMethodError: com.google.common.base.Preconditions.checkArgument(...) on one code path. Unit tests were green.

Check first: tests ran on the test classpath, which can differ from the packaged runtime (for example the fat jar or application server carries another copy). List the jars that contain the class: unzip -l app.jar | grep guava. Run -verbose:class to see which jar actually loaded it.

Fix: print the verbose tree for that library (mvn dependency:tree -Dverbose -Dincludes=com.google.guava:guava or gradle dependencyInsight) and see who asks for what. Remember Maven keeps the nearest, Gradle the highest. Pin one compatible version in dependencyManagement or a Gradle constraint, or exclude the stale copy.

Prevent: enforcer rules requireUpperBoundDeps and banDuplicateClasses in CI, an integration test that starts the packaged artifact, and no hand-copied jars in the server's shared lib folder.

Why tests were green. A test run uses the test classpath: your modules plus resolved dependencies, built by the build tool. Production runs a packaged thing (fat jar, war inside an application server, container image) with its own, possibly different, set of jars. If two versions of Guava exist and the packager takes the other one, tests never see the problem. Also if the failing path is rarely exercised, no test touches it at all.

Step-by-step response.

  1. Stabilise. If errors are user-visible, roll back to the last good version first. Debugging in production while customers see errors is the wrong order.
  2. Read the message precisely. NoSuchMethodError: ...Preconditions.checkArgument(ZLjava/lang/String;Ljava/lang/Object;)V tells you the exact method signature the code expected. Look at which library version has it (older versions of Guava lacked some overloads).
  3. Look inside the artifact that was deployed, not the source tree: unzip -l app.jar | grep -i guava, or open the war's WEB-INF/lib, or docker run --rm image ls /app/lib. You may find two Guava versions, or one that differs from what you compiled with.
  4. Prove which was loaded. Start the app locally with -verbose:class and search for Preconditions, or expose a debug endpoint printing the class's code source.
  5. Trace who brought it with the verbose dependency tree. Maven nearest wins, Gradle highest wins, so a Maven and a Gradle module in the same company can resolve differently.
  6. Fix and test the artifact. Pin the right version, or exclude the stale one. If an application server provides its own copy, configure parent-last class loading or stop bundling the library. Then start the actual packaged artifact in a test.

Preventing it. The enforcer rule requireUpperBoundDeps fails the build when mediation picked a lower version than someone requested. banDuplicateClasses (extra-enforcer-rules) fails when two jars contain the same class. In Gradle use failOnVersionConflict() or locking. Add a smoke test that boots the packaged jar in CI (for Spring Boot, a @SpringBootTest with a random port that runs against the repackaged jar, or a container startup check).

What to say about root cause in the post-mortem. "The build resolved a different version than the compile and the tests exercised, and nothing asserted that the packaged artifact started and ran the failing path." That frames it as a process gap, not a person.

Remember: compiled against one version, ran on another. Find the loaded jar, then pin one version.

A teammate's build uses a different jar than yours, with the same SNAPSHOT version number. How did that happen? Intermediate

A SNAPSHOT is not one fixed jar. My ~/.m2 probably holds a build I did myself with mvn install, while my teammate has the CI snapshot downloaded yesterday, because snapshots are re-checked only once a day by default.

Situation: pricing-1.4.0-SNAPSHOT is used by your service. Same service commit, but tests pass for you and fail for your colleague.

Check first: where did each jar come from? List ~/.m2/repository/com/acme/pricing/1.4.0-SNAPSHOT on both machines and compare timestamps and the metadata files, then compare jar checksums.

Fix: run mvn -U (or delete that folder) to pull a fresh copy from the repository, so both use the same one.

Prevent: have CI publish every merge to the snapshot repository, build the library through the reactor (or a Gradle composite build) instead of installing by hand, and use real release versions for anything that crosses a team boundary.

What actually happened. The string 1.4.0-SNAPSHOT is a moving label. Two places can legitimately give you different bytes under it:

  • Your local repository: you once ran mvn install inside the pricing project, which wrote your build into ~/.m2/.../1.4.0-SNAPSHOT/ with a name like pricing-1.4.0-SNAPSHOT.jar (no timestamp).
  • The remote repository: CI keeps deploying timestamped snapshots. Your teammate's Maven downloaded yesterday's, and checks again only after the update interval (daily by default).

Which one wins in your build? Maven compares the local copy's timestamp to the remote metadata. If your local install is newer, it keeps yours and does not download. So your tests ran against your own unmerged working copy, while your teammate's ran against CI's older snapshot.

Walkthrough of detection.

  1. On both machines: ls -l ~/.m2/repository/com/acme/pricing/1.4.0-SNAPSHOT. Look at the jar names, dates and maven-metadata-*.xml files. A maven-metadata-local.xml means a local install is present.
  2. Compare checksums: sha256sum pricing-1.4.0-*.jar. Different hash means different content.
  3. Run with -X to see the exact path of the jar used on the classpath.

Cleaning up. Delete that folder and run mvn -U, or use mvn dependency:purge-local-repository -DmanualInclude=com.acme:pricing. Both machines now fetch the same remote snapshot.

Real fixes (beyond clean-up).

  • Build the two projects together in one reactor (multi-module) or, in Gradle, a composite build, so you never need install for development.
  • When the library is owned by another team, depend on a release. Snapshots across team boundaries mean your build is out of your control.
  • In CI, forbid snapshot dependencies in a release build (enforcer requireReleaseDeps).
  • Gradle: snapshot ("changing") modules are cached 24 hours by default, adjustable by cacheChangingModulesFor. Use --refresh-dependencies to refresh.

Remember: same SNAPSHOT name does not mean same jar. Use -U, and prefer releases across teams.

The build takes 25 minutes and everyone complains. How do you make it faster? Senior

I measure first, because guessing wastes time. Then I go after the biggest cost, which is usually tests, then add parallelism, caches, and build-only-what-changed. Slow builds make people skip tests, so I treat it as a bug with an owner.

Situation: multi-module project, slow on both CI and laptops.

Check first: with Gradle, --scan or --profile shows time per task. With Maven, log timestamps or a build-time extension. Typical culprits: tests, slow dependency downloads, no caches, and building everything for every change.

Fix, in order of payoff:

  1. Tests: run fast unit tests on every commit, integration tests in a later stage, parallelise test forks, remove sleeps and heavy shared setup.
  2. Parallel modules: Maven -T 1C, Gradle org.gradle.parallel=true.
  3. Caches: keep ~/.m2 and ~/.gradle between CI runs. In Gradle enable the build cache (with a remote cache for CI) and the configuration cache.
  4. Build only what changed: -pl ... -am in Maven, project-level tasks in Gradle.
  5. Resolve through a nearby repository manager, with no dynamic versions. Skip javadoc and source jars on pull requests.

Prevent: track build time as a metric and review it regularly.

Start by measuring, not by tuning. A 25-minute build is a sum of parts. Without numbers you may spend a week speeding up a step that takes 40 seconds. Collect: total time per stage in the CI log, per module, per task. In Gradle run ./gradlew build --scan (shows a timeline and which tasks were UP-TO-DATE or cached) or --profile for a local HTML report. In Maven, the -T flag with a timing extension, or the timestamps in -B logs (with -Dorg.slf4j.simpleLogger.showDateTime=true) show the module and plugin costs.

A typical breakdown and the action for each part.

Where time goes (example)Action
12 min testsSplit unit and integration. Parallel test forks. Remove sleeps. Share one Testcontainers instance. Run only tests affected by a change on pull requests.
4 min downloading dependenciesCache ~/.m2 or ~/.gradle between jobs, use a nearby proxy, avoid -U and snapshots on every run.
5 min compile of everythingBuild cache, parallel modules, incremental compile, build only affected modules.
3 min packaging, javadoc, static analysisSkip javadoc and source jars on pull requests, run heavy analysis in a parallel CI job.

Specific examples.

  • Maven Surefire in parallel: -DforkCount=1C -DreuseForks=true (the exact tuning depends on how thread-safe tests are).
  • Gradle tests in parallel: tasks.test { maxParallelForks = Runtime.getRuntime().availableProcessors() / 2 }.
  • Gradle remote cache with CI writing and laptops reading, as shown in the cache question. This often cuts pull request builds sharply, because most modules are unchanged.
  • Maven has no built-in task cache. The Maven Build Cache Extension (an Apache extension) exists for it; it is newer, so evaluate it carefully before adopting.

Do not trade correctness for speed. -DskipTests on the main branch, or running tests only on changed modules without a periodic full build, will let a broken dependency between modules slip through. Keep a full build nightly or on merge.

Making it stick. Publish build time as a dashboard with a budget (for example, p90 under 10 minutes), review it in retros, and assign an owner. Builds slow down by small amounts each week unless someone watches.

Remember: measure, then tests, parallel, caches, only what changed.

Maven says "Could not resolve dependencies" or "Could not transfer artifact" for a library that exists. What do you check? Intermediate

I read which URL Maven actually tried, then check the usual suspects in order: a cached failure (*.lastUpdated), the mirror and repository ids, credentials, and for certificate errors the JVM trust store. Most of the time it is the mirror or a cached earlier failure, not a missing library.

Situation: a build fails to download an artifact that you can see in Nexus.

Check first: the error text. was cached in the local repository ... until the update interval has elapsed means an earlier failure is remembered. A 401 means no or wrong credentials, a 403 means no permission (or "release already exists" on deploy), and a 404 usually means the mirror does not proxy the repository that has it.

Fix:

  1. Run mvn -U, or delete that artifact folder and the *.lastUpdated files. Do not wipe all of ~/.m2 first, it hides the real cause.
  2. Run mvn help:effective-settings to see the mirror and servers really loaded, and confirm the server id equals the repository id.
  3. If the mirror is mirrorOf *, add the vendor repository to the repository manager's group.
  4. PKIX path building failed means the JVM does not trust the company CA. The browser uses the operating system store, the JVM uses its own cacerts. Import the company CA into the JDK that runs the build, never disable certificate checks.
  5. If a jar is corrupted ("invalid LOC header"), delete that artifact folder and re-download.

Prevent: a documented dev setup for settings and CA, and build only through the company repository manager.

First, read the message, because there are several different problems behind the same words.

A walk-through example. Build fails: Could not transfer artifact com.vendor:sdk:jar:3.1 from/to company-all (https://nexus.example.com/repository/maven-public/): status code: 404. The URL is the mirror, not Central, so the answer is in Nexus. Search for com.vendor:sdk in the repository manager: if it is only in the vendor's own repository, add that repository as a proxy repository in Nexus and put it into the maven-public group. No change is needed on any developer machine, which is the advantage of a mirror.

PKIX in more detail. The browser trusts the company CA because IT installed it into the operating system's store. Java ships its own trust store ($JAVA_HOME/lib/security/cacerts) which does not have your company CA. Import the CA certificate into the JDK that runs Maven or Gradle (keytool -importcert -alias corp-ca -file corp-ca.pem -keystore $JAVA_HOME/lib/security/cacerts), or point to a custom store with -Djavax.net.ssl.trustStore=... in MAVEN_OPTS. Switching off verification (-Dmaven.wagon.http.ssl.insecure=true) defeats the purpose and must not be used outside a throwaway experiment.

Gradle equivalent. --refresh-dependencies clears the cached metadata. Credentials go in ~/.gradle/gradle.properties and are referenced by the repository block. Offline mode (--offline) fails if something is not already cached, which is a handy test that the cache is complete.

Order of attack. Which URL, then cached failure, then identity of the mirror/ids, then credentials, then TLS, then the artifact itself. Wiping the whole ~/.m2 is the last resort because it throws away the evidence.

Remember: which URL, cached failure (-U), mirror and ids, credentials, trust store.
