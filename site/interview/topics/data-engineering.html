Mental model: the 7 ideas everything hangs on

One line: put bytes in files in a layout that is cheap to scan, add a table layer so many writers and readers stay consistent, then move data with pipelines that can safely run twice.
  1. File format is how bytes are laid out; table format is how files become a table. Avro, Parquet and ORC are file formats. Iceberg, Delta and Hudi are table formats: they track which files make up the table right now.
  2. Row formats suit writing and whole-record reads; column formats suit analytics. Avro is row based (messages). Parquet is columnar (analytics).
  3. A schema is a contract. Who may change it, and in which direction, decides who breaks. Backward, forward and full compatibility are the vocabulary.
  4. Object storage is cheap and immutable. You cannot edit a file in S3. You write new files and swap a pointer. This one fact explains snapshots, delete files and compaction.
  5. Metadata makes queries cheap. Min and max per column, file lists and partition values let an engine skip most files without opening them.
  6. Delivery is at-least-once, so pipelines must be idempotent. Running a step twice must give the same result as running it once.
  7. Time has two meanings. Event time (when it happened) and processing time (when you saw it). Late data lives in the gap.

1. File formats and Parquet

What is the difference between row-oriented and column-oriented storage, and when do you pick each? Basic

A row format stores all fields of one record together; a columnar format stores all values of one column together. I use row formats (Avro, JSON, a normal database) for transactions and messages, where I read or write whole records. I use columnar formats (Parquet, ORC) for analytics, where a query touches a few columns of millions of rows.

Start from the problem. A disk (or an S3 object) is read in bytes, one after another. Whatever sits next to each other on disk is cheap to read together. So the real question is: what do I want to read together, a whole record or a whole column?

Take a table of 100 million orders with 50 columns. Two very different jobs touch it:

  • Job A (transactional): "show me order 12345", "insert this new order", "change its status". One row, all 50 fields, a few times per millisecond. You want all 50 fields of one row packed side by side, so one read returns everything.
  • Job B (analytical): "total amount per city for last month". It needs 2 of the 50 columns but for 100 million rows. If the file is stored row by row, you drag the other 48 columns off disk and throw them away. That is about 25 times more bytes than needed.

A row layout is ideal for job A, a column layout is ideal for job B. That is the whole topic.

Why the column layout also compresses better. Look at one column in isolation: city is "Pune, Pune, Pune, Delhi, Pune ...". Four distinct values in 100 million rows. A dictionary (Pune=0, Delhi=1) turns each city into a tiny number, and run-length encoding turns "0,0,0" into "0 x 3". An order_id that grows 1, 2, 3 can be stored as deltas (+1, +1, +1). Mixed row data (a string, then a number, then a date) cannot be squeezed like this. Typical result: columnar files are several times smaller than the same data as JSON or CSV.

Skipping with statistics. A columnar file keeps min and max per column block. A query WHERE amount > 1000 reads the footer, sees that a block has max 900, and never opens it.

When to choose which (decision rule). If the access pattern is "one record at a time, write often" use rows (a normal database, Avro on Kafka). If it is "many records, few columns, mostly read" use columns (Parquet or ORC in a lake, a warehouse). Many systems use both: events arrive as Avro rows, then a pipeline rewrites them in big batches as Parquet.

Pitfalls the interviewer may probe: "Why not just use Parquet everywhere?" Because you cannot append one row cheaply or read one record fast; each write must build whole column blocks, so you buffer and write in batches. "SELECT * on Parquet?" It loses the advantage, since it reads every column.

Columnar wins on scans for three reasons. First, column pruning: "sum of amount per city" reads two columns and skips the other fifty. Second, compression: one column holds one type and similar values (repeated cities, steadily growing ids), so dictionary, run-length and delta encodings shrink it a lot. Third, statistics: each column chunk stores min and max, so a filter like amount > 1000 can skip whole blocks without reading them. The cost is point work: reading one full row touches every column block, and a single-row insert is expensive, so columnar files are written in big batches.

Remember: rows for transactions and messages, columns for scans and aggregates. Columnar is fast because it reads less, not because it reads faster.

Compare CSV, JSON, Avro, Protobuf and Parquet. How do you choose? Basic

I pick by role. JSON for public APIs and logs, Avro (or Protobuf) for messages on Kafka and ingestion files, and Parquet for analytics tables. CSV only for small human exports. A normal pipeline reads Avro or JSON events from Kafka and writes Parquet tables for analysts.

Why there are so many formats. Each one answers a different question: who reads this, how often, and how much does the structure change? There is no best format, only a good match to the job.

Walk through each one with the same record {"id":7,"name":"Asha","amount":120.5}:

  • CSV 7,Asha,120.5. Smallest in effort, but nothing says whether 7 is a number or text, a comma inside a name breaks the row, and there is no nesting. Fine for a small export to Excel; a bad idea as a pipeline contract.
  • JSON repeats "id", "name", "amount" in every record, so a million records repeat the field names a million times. Parsing text is slow, and a field can be a number in one record and a string in the next. Its strength is that humans and every language can read it, so it suits APIs and logs.
  • Avro stores only the values (7, "Asha", 120.5) in a compact binary form; the field names and types live once in a schema. Small, fast, and the schema rules make safe evolution possible.
  • Protobuf is similar but identifies each field by a number in a .proto file (id = 1; name = 2). It is the natural pairing with gRPC and has excellent code generation.
  • Parquet regroups many records into columns, so it is not something you send message by message; it is something you write in batches and scan later.

The practical pipeline most teams end up with: app emits JSON or Avro to Kafka, a job validates it against a schema, and a batch or streaming job writes Parquet files into the lake (usually managed by Iceberg). Analysts then query the Parquet.

Decision rule. Ask three questions: (1) Is a human or an outside client reading it? JSON. (2) Is it a message or an event that must evolve safely? Avro or Protobuf. (3) Is it a big table scanned by queries? Parquet. If a team already runs gRPC everywhere, Protobuf on Kafka is also reasonable, but data tools (Spark, Hive, the lake) historically have the best support for Avro and Parquet.

Pitfall: storing raw JSON in the lake "because it is flexible". It works until volume grows; queries get slow and expensive, and nobody remembers what each field means. Convert to a typed, columnar format early.

CSV has no types and no nesting, and quoting bugs are common. JSON is self-describing text with nesting, but it repeats field names in every record, is slow to parse and loosely typed. Avro is a compact binary row format where a schema is required, which gives safe evolution. Protobuf is also binary rows, but fields are identified by number, which makes it the usual choice for gRPC; for Kafka I pick Avro if the data ends up in a lake, and Protobuf if services already use gRPC. Parquet is columnar, so it gives the best scan speed and size for analytics but is poor for row writes and point updates.

How is a Parquet file organised inside? Intermediate

A Parquet file is split into row groups (horizontal slices of rows). Inside a row group each column is stored as a column chunk, and each chunk is cut into pages. At the end of the file is a footer with the schema and, for every column chunk, offsets and min, max and null-count statistics. A reader reads the footer first, decides which row groups and columns it needs, and reads only those byte ranges.

Why such a layered layout? Parquet must satisfy two opposing wishes: keep each column together (for pruning and compression) and still allow big files to be processed in parallel. The answer is to cut the table into horizontal slices first (row groups), and inside each slice store column by column.

The four levels, from big to small:

  1. File. One object on S3 or HDFS, wrapped in the 4-byte marker PAR1 at both ends.
  2. Row group. A horizontal slice, for example 1 million rows (sized by bytes, commonly about 128 MB). All columns for those rows live inside it. A query engine can hand one row group to one worker, so this is the unit of parallel reading.
  3. Column chunk. Inside a row group, all values of one column, stored contiguously. This is what lets you read just the amount column.
  4. Page. A column chunk is cut into pages (about 1 MB). Each page is encoded (dictionary, run-length, delta) and then compressed (Snappy, Zstd, and so on) independently, so a reader can decode just a page. A dictionary page, if used, comes first in the chunk.

How a reader works step by step. Suppose you run SELECT sum(amount) FROM t WHERE amount > 1000 on a 1 GB file on S3:

  1. Read the last few bytes to get the footer length, then read the footer (a few KB to a few MB) with a range request. Do not download the file.
  2. From the footer, find each row group's amount chunk and its min and max. Row group 1 has max 900, so skip it entirely. Row group 2 has min 5000 and may match, so keep it.
  3. Read only the byte range of the amount chunk of row group 2, decompress, decode, filter, sum.

Result: a few MB read out of 1 GB. The same layout is also why a Parquet file cannot be written in a pure streaming fashion: the writer buffers a row group in memory, writes it, and only at the end can it write the footer (it needs all offsets).

Nested data. Parquet can store structs, lists and maps in a columnar way using repetition and definition levels (small integers recording nesting and nulls). You do not need the details, but know that nested fields are stored as separate leaf columns, so reading address.city does not read the rest of address.

Tuning knobs and pitfalls. A row group that is too small means many tiny reads and weak statistics; too large means high writer memory and less parallelism. Very wide tables with huge string columns make the footer large. Many tiny Parquet files are worse than the internals suggest, because every file pays for a footer read (the small files problem later on this page).

Row groups are typically around 128 MB by default in common writers, and a row group is the unit of parallelism: one task can take one row group. Pages are about 1 MB by default and are encoded and compressed on their own. The footer is at the end because the writer streams data and only knows sizes when it finishes; the file starts and ends with the magic bytes PAR1. This layout works well on S3, because the reader can fetch just the footer and just the needed column chunks with range requests.

Remember: file, row groups, column chunks, pages; the footer holds the stats that let you skip.

What are predicate and projection pushdown, and why does sorting the data matter? Intermediate

Projection pushdown means the engine tells the reader which columns it needs, so only those column chunks are read. Predicate pushdown means the filter goes into the reader, which uses min and max statistics to skip files, row groups and pages that cannot match. It only works well when the data is clustered: if every file holds a bit of every customer, min and max span everything and nothing can be skipped.

Two ideas, two different savings.

  • Projection pushdown means "read only the columns I selected". It saves bytes by skipping columns. A table with 50 columns where you select 3 reads about 3/50 of the data.
  • Predicate pushdown means "apply the WHERE filter as close to the storage as possible, ideally before reading the data". It saves bytes by skipping whole rows groups, pages or files.

"Pushdown" literally means the query planner pushes the instruction down into the storage reader instead of loading everything into the engine and filtering afterwards.

A worked example. A table of 1 billion events stored in 1000 files, filter WHERE event_date = '2026-11-17'.

  • Unsorted: each file holds events from every day, so every file's min is Nov 1 and max is Nov 30. The statistics say "may contain Nov 17" for every file, so nothing is skipped and 1000 files are read.
  • Clustered by date: each file covers one day (or a narrow range). The file stats say "min = max = Nov 17" for 30 files and other dates for the rest. 970 files are skipped without being opened.

The same data and the same query differ by a factor of 30 purely because of how the data was laid out. That is why sorting matters: min/max statistics only help when values are clustered.

The levels of skipping, coarse to fine:

  1. Partition pruning and table metadata (Iceberg manifests carry per-file min, max) drop whole files.
  2. Parquet footer statistics drop row groups.
  3. The Parquet page index (newer) drops pages inside a row group.
  4. Bloom filters (optional, newer) answer "is this exact value possibly here?" for equality filters on columns like user_id, where min and max are useless because ids are random. A bloom filter can say "definitely not", which skips the chunk; a "maybe" still reads it.

How to get clustering. Sort the data on the common filter column when writing or during compaction (Iceberg supports a table sort order and a sort-based compaction strategy; a multi-column Z-order style clustering helps when you filter on several columns). Choose the column by looking at what queries actually filter on.

Pitfalls. (1) Wrapping the column in a function, WHERE date(ts) = ... or lower(name) = ..., often stops the engine from comparing against stats; filter on the raw column (ts >= X AND ts < Y). (2) Comparing with a mismatched type (string versus int) can cast the column and disable pushdown. (3) Random ids as a sort key give you nothing. (4) Check the query plan: engines show "files scanned" or "bytes read", which is the real proof.

Skipping happens at several levels: table metadata skips whole files (Iceberg manifests hold per-file stats), the footer skips row groups, and the optional page index skips pages. For equality filters on high-cardinality columns such as ids, newer Parquet versions also support bloom filters ("this value is definitely not here"). So I sort or cluster data on the column that queries filter on, usually during compaction: then each file covers a narrow range and a lookup opens one or two files. Filters that wrap the column in a function (lower(name) = 'x') usually cannot use the stats, so filter on the raw column.

Remember: stats only skip what is clustered. Sort on the filter column and keep filters on the raw column.

Can you update a row inside a Parquet file? How do table formats get around that? Intermediate

No, not in place. Parquet files are written once, compressed in blocks, and the footer holds offsets, so changing a value would shift bytes. Object stores such as S3 also cannot modify part of an object. So every update is a rewrite: table formats either rewrite the affected files (copy-on-write) or write small delete files and merge them at read time (merge-on-read), and then switch the table metadata to the new file list atomically.

Why a Parquet file cannot be edited. Three reasons stack up. (1) Column values are encoded and compressed in pages, so changing one value changes the page size and shifts everything after it. (2) The footer stores absolute byte offsets of every chunk, so any shift breaks the map. (3) On S3, an object is replaced as a whole; there is no "overwrite bytes 100 to 200". So even if Parquet allowed it, the store would not.

What you do instead, step by step (example: change order 42 from PENDING to SHIPPED, where the order lives in file-A with 1 million rows):

  1. Copy-on-write: read file-A, produce file-A2 identical except order 42, write it as a brand new object. Record in the table metadata "table now = A2 instead of A". Old file A is untouched, and is deleted later by cleanup.
  2. Merge-on-read: leave file-A alone. Write a tiny delete file saying "order 42 in file A is dead" and a new small data file with the new version of order 42. Readers combine them while reading.

In both cases the visible change is a single atomic step, switching which files form the table. That is what the table format (Iceberg, Delta, Hudi) provides; plain Parquet in a folder has no such step.

Consequence for design. Updates are expensive per row (you rewrite a file to change one row), so batch them. A job that updates one row at a time in a lake will crawl and create thousands of tiny files. The next questions on copy-on-write versus merge-on-read explain the trade-off.

What an interviewer probes next: "so how does a lakehouse do UPDATE and DELETE at all?" Answer: a SQL MERGE or DELETE becomes new files plus a metadata swap, and old versions stay readable until snapshots expire.

Old files are not touched, so readers that started earlier still see a consistent view. That immutability is the root of snapshots, time travel and compaction later on this page.

Remember: immutable files mean "update" is write new files, then swap the pointer.

How does Parquet make data small? What are dictionary, run-length and delta encoding, and how do they relate to compression? Intermediate

Parquet first encodes each column's values using a scheme that fits the data (dictionary, run-length, delta, bit-packing), then compresses the encoded page with a general codec such as Snappy or Zstd. Encoding exploits the structure of one column; the codec squeezes whatever repetition is left. Because each column holds one type of similar values, this works far better than on mixed rows.

Encodings with tiny examples.

  • Dictionary: the column city has 100 million values but 300 distinct ones. Store the 300 strings once (the dictionary page) and then store each value as a small integer index (9 bits is enough). The index list is tiny and fast to compare. Writers fall back to plain encoding if the dictionary grows too large (high-cardinality column such as a UUID).
  • Run-length (RLE) and bit-packing: a sorted or repetitive column like [Pune x 5000, Delhi x 3000] becomes "5000 times 0, 3000 times 1". Sorting the data before writing makes this much more effective, a second reason to sort.
  • Delta: for increasing numbers or timestamps such as 1000, 1001, 1003, 1004 store the first value and the small differences +1, +2, +1.

Compression codecs, the trade-off. Snappy is very fast with a moderate ratio (the long-time default in many engines); Zstd gives a better ratio at a modest CPU cost and is often the best default today; gzip compresses well but is slower; none is only for special cases. A choice of codec changes storage cost and CPU time, not what the data means, and it can be set per file or per column.

Why it matters to you. A table that is 10 times smaller means 10 times fewer bytes over the network, which is where the query time goes. Sorting by a low-cardinality column or by a filter column improves encoding and skipping together. And the effect of the encoding is why Parquet is poor at tiny files: each small file repeats its own dictionaries and footers.

Pitfalls. Very high-cardinality string columns (hashes, UUIDs) compress poorly whatever you do; consider storing them as fixed binary. Over-compressing hot data can make queries CPU bound. Unsure about defaults: they vary by engine and version, so check your writer's settings.

Remember: encode per column (dictionary, RLE, delta), then compress the page. Sorted, low-cardinality columns shrink the most.

2. Avro, schemas and schema evolution

What is Apache Avro, and what does a schema look like? Basic

Avro is a compact, row-oriented binary format where every piece of data is described by a schema written in JSON. The data itself has no field names or type tags, only the values in schema order, so it is small. It is the usual choice for Kafka messages and for event files that must change over time.

The problem Avro solves. JSON is flexible but wasteful and loose; hand-written binary formats are compact but break when a field is added. Avro aims for both: compact bytes and a defined, evolvable structure. Its trick is to separate the schema (the description of the structure) from the data (just the values).

How the bytes look. Take the record {orderId: 7, customer: "Asha", coupon: null} with the schema below. Avro writes the values in schema order with no names and no type markers: the long 7 (variable-length "zigzag" encoding, one byte), then the string as a length (4) followed by the 4 UTF-8 bytes, then the union index that says "branch 0 = null". About 8 bytes in total, against roughly 50 for the JSON text. A million such records save a lot of space and parsing time.

The price. The bytes are not self-describing. If you read them with a different or lost schema you get garbage or an error. So the schema must always travel or be findable with the data. Two common ways:

  • Avro data file (container file): the schema is stored once in the file header, followed by blocks of records, with sync markers so the file can be split for parallel reads. Used for files, Hadoop and the Iceberg manifest files.
  • Single messages on Kafka: the schema is stored in a registry, and each message carries only a small id (next questions).

Types, quick tour. Primitives: null, boolean, int, long, float, double, bytes, string. Complex: record (a named set of fields), enum, array, map (string keys), union (one of several types, written as a JSON array), fixed (fixed-size bytes). Logical types add meaning on top of a physical type: decimal over bytes, date over int (days since epoch), timestamp-millis over long, uuid over string.

Optional field idiom. There is no "nullable" flag; you write a union ["null","string"] with default null. Adding such a field is the standard way to evolve a schema safely.

Generic versus specific. In Java you may read records as a generic map-like object (flexible, no code generation) or generate classes from the schema (type safe). Either way the Avro library does the encoding. Compared with Protobuf: Avro needs the writer schema at read time and matches fields by name, Protobuf matches by field number and can be decoded without the schema (but you lose the names).

Because the bytes carry no description, you cannot decode them without the schema they were written with. A string is a length plus UTF-8 bytes; an int uses a variable-length encoding so small numbers take one byte. The schema lives either in the file header (Avro data files) or in a registry with only a small id sent per message. Types: primitives (null, boolean, int, long, float, double, bytes, string) and complex ones (record, enum, array, map, union, fixed). An optional field is a union with null. Code generation is optional: you can use a generic record or generate Java classes.

{
  "type": "record", "name": "Order", "namespace": "com.shop.events",
  "fields": [
    {"name": "orderId", "type": "long"},
    {"name": "customer", "type": "string"},
    {"name": "coupon", "type": ["null", "string"], "default": null}
  ]
}
Watch out: a union default must match the FIRST branch. ["string","null"] with "default": null is invalid; put "null" first. For money use the decimal logical type with precision and scale, never double.

Remember: Avro = values only plus a separate schema. Lose the schema and the bytes are meaningless.

Explain reader schema versus writer schema. How does Avro schema resolution work? Intermediate

The writer schema is the one the bytes were written with. The reader schema is the one my code wants today. Avro needs both: it decodes using the writer schema, then maps the result to the reader schema by field name. Fields the reader does not know are skipped; fields the writer did not have get the reader's default, and if there is no default the read fails.

Why two schemas? Imagine events written a year ago when an order had id and name. Today your code expects id, name and country. The old bytes were written without a country; your code wants one. Avro's answer is: keep the schema that was used to write (writer schema), declare what you want now (reader schema), and let a resolution step translate between them. Nothing in the old data has to be rewritten.

The resolution rules, simply:

  1. Decode the bytes strictly using the writer schema (it is the only description that matches the bytes).
  2. For each field in the reader schema: if the writer had a field with that name (or an alias), take its value (applying a type promotion if allowed). If the writer did not have it, use the reader's default. If there is no default, resolution fails with an error.
  3. Fields the writer had but the reader does not list are skipped (the decoder knows how many bytes to skip, because it has the writer schema).

Concrete example. Writer v1: {id: long, name: string, nickname: string}. Reader v2: {id: long, name: string, country: string = "unknown"}. Reading the v1 bytes: id and name are mapped, nickname is skipped, country is filled with "unknown". If v2 had declared country without a default, every v1 record would fail to read.

Where each schema comes from in practice. The reader schema is compiled into your application (or loaded from your config); the writer schema comes from the file header or from the registry via the id in the message. That is also why Avro schema changes must be thought of as "what will old data and old code do?".

Renames and type changes. A rename looks like "remove field a, add field b", which fails or loses data, unless the reader declares "aliases": ["a"] on the new name. Allowed promotions (writer to reader): int to long, float or double; long to float or double; float to double; string and bytes to each other. Narrowing (long to int) is never allowed.

Pitfalls. Reading with the same schema as the writer works with no resolution, which hides mistakes until the first evolution; test with old data. Also remember default values are only used for missing fields at read time, not stored in the old bytes.

That is why adding a field with a default is the standard safe change, and why old files stay readable forever as long as you keep the writer schema with the data. A rename needs an aliases entry on the new name. A few type promotions are allowed (int to long, float or double; float to double; string and bytes to each other).

Remember: match by name, fill from the reader default, skip the extras. No default means no read.

What are backward, forward and full compatibility? Which changes are safe? Intermediate

The words describe what the new schema can do. Backward compatible: consumers on the NEW schema can read data written with the OLD one. Forward compatible: consumers on the OLD schema can read data written with the NEW one. Full is both. In practice, if every field I add or remove has a default, the change is full compatible.

First, why this matters. In a real company, producers and consumers are deployed by different teams on different days. For some period, old and new versions of code run at the same time, and old and new messages sit in the same topic. Compatibility rules say which schema changes survive that mixing.

The two directions, in plain words.

  • Backward compatible: new code can read old data. Think "backward in time": I upgrade the reader, it must still understand yesterday's messages.
  • Forward compatible: old code can read new data. Think "forward in time": an old reader must cope with tomorrow's messages.
  • Full: both at once. Safest, nobody has to care about deployment order.

A trap: the names describe the direction of the data, not who deploys first. So BACKWARD usually means "upgrade the consumers first" (they can read both old and new), and FORWARD means "upgrade the producers first" (old consumers must tolerate new data).

Why the table results look as they do. Use the resolution rules from the previous question:

  • Add a field with a default: a new reader reading old data fills the default (backward ok). An old reader reading new data just skips the unknown field (forward ok). So full.
  • Add a field without a default: new reader on old data has nothing to fill and fails (not backward). Old readers skip it (forward ok).
  • Remove a field without a default: new reader no longer asks for it (backward ok). Old reader asks for a field that new data lacks and has no default (forward fails).
  • Remove a field that has a default: old reader falls back to its own default, so both work.

The rule of thumb to say aloud: "Only add or remove fields that have defaults; never rename or change a type without an alias or a promotion; add enum symbols at the end and set an enum default." With that, you stay full compatible.

Pitfall: compatibility checked only against the latest version. A chain of individually compatible steps can still break old data (see the transitive question). Also, "compatible" only means the data can be decoded; the meaning can still change (a field that used to hold dollars now holds cents), which no tool detects. That is what data contracts and review are for.

Backward is what you need when you upgrade consumers first or replay old data from a topic. Forward is what you need when producers upgrade first and old consumers still run. Adding a field without a default is forward only (old readers ignore it, but a new reader cannot fill it for old data). Removing a field without a default is backward only. Renames and incompatible type changes are breaking unless you use aliases or allowed promotions. For enums, add new symbols at the end and give the enum a default symbol so old readers do not fail on an unknown one.

What is a Schema Registry and how does it work with Kafka and Avro? Intermediate

A schema registry is a small service that stores schemas, gives each one a numeric id, and keeps versions per subject (for Kafka, normally <topic>-value). The producer registers its schema, gets an id, and writes each message as a magic byte, a 4-byte schema id and the Avro bytes. The consumer reads the id, fetches the schema once, caches it, and decodes. The registry also rejects a new schema that breaks the subject's compatibility rule, so breakage fails the producer deploy instead of crashing consumers at night.

The problem. Avro bytes are useless without the writer schema. Sending the full schema (often 1 to 5 KB) with each Kafka message of 200 bytes would be absurd. Storing it only in the producer's code means consumers cannot decode old messages, and nobody stops a producer from changing it. A schema registry is a shared, versioned, checked place to keep schemas.

How a message flows, step by step.

  1. At startup (or on the first send) the producer's serializer sends its schema to the registry under a subject, by default orders-value for the value of topic orders.
  2. The registry checks it against the subject's compatibility rule. If it breaks the rule, registration is rejected and the producer fails, before any bad data exists. If it is accepted, the registry returns a global numeric id (say 7), or the existing id if the same schema is already registered.
  3. The serializer writes each message as: byte 0 (magic), 4 bytes with id 7, then the Avro bytes.
  4. A consumer reads the message, sees id 7, asks the registry once for schema 7, caches it, and decodes. From then on no registry calls for that id.

What the registry gives you: small messages, a single source of truth, version history (v1, v2, v3 of the subject), a compatibility gate, and a place to find "what does this topic contain?". It is the technical half of a data contract.

Subject naming. The default (TopicNameStrategy) gives one schema lineage per topic. Other strategies (record name or topic plus record name) allow several event types in one topic, which is useful to keep ordering between related events, but makes compatibility checks per record type.

Operating it. It stores schemas in a Kafka topic (_schemas) and runs as a small cluster with one primary writer; reads are served from memory. Because clients cache, a short outage rarely hurts, but a cold-started consumer or a new schema cannot proceed. Secure it (who can register or change compatibility), and set the compatibility mode explicitly rather than relying on defaults.

Pitfalls. Auto-registering schemas from every producer in production lets accidents through; many teams disable auto-registration and register schemas in CI. Setting compatibility to NONE "to get unblocked" removes the safety net. Also, a consumer that is not using the registry (a script reading raw bytes) must skip the 5-byte header, a classic bug.

Each message carries only 5 extra bytes instead of a whole schema, and clients cache by id, so the registry is called once per new id, not per message. If the registry is down, already-cached clients keep working; new schemas fail, so run it highly available. Confluent Schema Registry is the best known; others (Apicurio, AWS Glue) do the same job, and most also handle Protobuf and JSON Schema.

Each message sent to Kafka then carries only a magic byte, that id and the Avro bytes. The consumer polls the message, reads the id, and fetches the matching schema from the registry (dashed arrow 2) once, then caches it. The moving dashes show the message path from producer to topic to consumer.

Remember: the message carries an id, the registry holds the schema and enforces compatibility at register time.

What is the difference between BACKWARD and BACKWARD_TRANSITIVE, and which would you choose? Senior

Plain BACKWARD checks a new schema only against the latest registered version. BACKWARD_TRANSITIVE checks it against every earlier version. I use the transitive mode when old data stays around or gets replayed (long retention, event sourcing, loading a lake from the start of a topic), because then a consumer must be able to read all versions. BACKWARD is the Confluent default.

What the setting controls. Each time a producer registers a new version, the registry runs a compatibility check. The mode decides (a) the direction (backward, forward, full) and (b) against which earlier versions the new schema is tested: only the latest (plain) or all of them (transitive).

Why plain BACKWARD can still break you. Walk through three versions of an Order schema:

  • v1: id, name.
  • v2: adds country with default "unknown". Checked against v1: new reads old, ok.
  • v3: changes country to be required, no default. Checked only against v2: a v3 reader can read v2 data (v2 always wrote a country), so plain BACKWARD accepts it.

But v1 messages have no country. A consumer on v3 that replays the topic from the beginning, or a job that loads old files, fails on the first v1 record. BACKWARD_TRANSITIVE would have compared v3 against v1 as well, seen that country has no default, and rejected the change.

Decision rule.

SituationChoose
Short retention (days), consumers always near the head, consumers upgraded firstBACKWARD
Long retention, replay, event sourcing, loading old data into a lakeBACKWARD_TRANSITIVE
Producers must upgrade first (many unknown consumers on old versions)FORWARD(_TRANSITIVE)
Many teams, no control over deployment orderFULL_TRANSITIVE

Breaking changes anyway. Sometimes you really must change meaning or type. Create a new topic or subject (orders-v2), dual-write for a period, migrate consumers one by one, then retire the old one. Do not just set compatibility to NONE.

Pitfalls. The mode is per subject (with a global default), so check what is actually set. Plain mode defaults are easy to forget. Transitive checks get stricter as versions pile up, so schemas should evolve additively and rarely.

Example: v1 has no country, v2 adds it with a default, v3 drops that default. v3 is compatible with v2, but it cannot read v1 data, and a replay will crash it. Upgrade order follows the mode: with BACKWARD upgrade consumers first, with FORWARD producers first, with FULL any order. In a multi-team company I prefer FULL (or FULL_TRANSITIVE) because nobody has to coordinate upgrade order. For a truly breaking change, create a new topic or subject, dual-write for a while, migrate consumers, then retire the old one.

Remember: transitive means "against all history". Use it whenever old messages can be re-read.

3. Lakehouse, Iceberg and partitioning

What are a data warehouse, a data lake and a lakehouse? Why did the lakehouse appear? Basic

A warehouse is managed, structured, SQL-first storage with transactions and good speed, but costly and awkward for raw or unstructured data. A lake is cheap object storage full of open files (Parquet, JSON, images): flexible and cheap, but historically with no transactions, no schema enforcement and no safe updates. A lakehouse puts a table format (Iceberg, Delta, Hudi) on top of the lake files, so you get ACID, schema evolution and time travel on cheap open storage, and many engines can read the same tables.

Take them in the order history produced them.

  1. Data warehouse (1990s on). A database built for analytics: structured tables, SQL, transactions, fast queries, central modelling. The problems: storage and compute were expensive and tied together, it handled only structured data well, and data was locked in the vendor's format.
  2. Data lake (2010s). "Just put every file on cheap storage (HDFS, later S3) and decide the structure when you read it." Cheap, handles logs, JSON, images, and many engines can use it. The problems: a "table" is only a folder of files. No transactions, so a reader sees half a write. No safe update or delete, so GDPR and corrections are painful. No schema enforcement, so one bad writer silently changes a column type. Nobody knows which files are current. Teams called the result a data swamp.
  3. Lakehouse (2020s). Keep the cheap open files of the lake, but add a table format (Iceberg, Delta, Hudi), a metadata layer that tracks which files make up the table, with atomic commits. You get the warehouse behaviours (ACID, schema, updates, time travel) on lake storage.

A concrete before and after. Lake only: a nightly job rewrites /sales/dt=2026-11-17/. It first deletes the folder, then writes new files. At 02:03 an analyst's query runs in the middle and sees no data for that day (or half of it). Lakehouse: the job writes new files, then performs one atomic commit "the table is now these files". The analyst sees either the old state or the new state, never in between.

Why not always lakehouse? Operating one means you own catalog, compaction, snapshot cleanup, access control and cost tuning. A managed warehouse hides all that and is often the better answer for a small team with mostly structured data and SQL users. A common modern setup is both: raw and large data in a lakehouse, curated marts in a warehouse that can also read Iceberg tables directly.

Pitfall to mention: "lakehouse" is a pattern, not a product. Ask which table format, which catalog and which engines are involved, because those decide what you can really do.

Lakes turned into "data swamps" because a table was just a folder: readers saw half-written files, two writers overwrote each other, and nobody knew which files were current. The table format fixes that with a metadata layer. The honest trade-off is that you now own more moving parts (catalog, compaction, cleanup) than with a fully managed warehouse. Many companies run both, and major warehouses can read Iceberg tables too.

What is Apache Iceberg, and why use it instead of plain Parquet files in a folder? Basic

Iceberg is an open table format: a specification and library that tracks a set of data files (usually Parquet) as one reliable table. It stores exactly which files make up the table at each moment, plus schema, partitioning and per-file statistics. Compared with a folder of Parquet files, it gives atomic commits, safe concurrent writers, schema and partition evolution, row-level updates, time travel, and no slow directory listing.

What problem is it solving? A folder of Parquet files has no concept of "the table right now". Concretely, these things go wrong:

  • A reader lists the folder while a job is writing: it reads half the files. (No atomic commit.)
  • A job crashes after writing 40 of 100 files: junk files remain and get counted. (No rollback.)
  • Two jobs write the same partition: one overwrites the other. (No concurrency control.)
  • You rename a column: old files use the old name, so values come back null or from the wrong column. (No stable column identity.)
  • A query over 50,000 files first spends a minute listing S3 prefixes. (Listing is slow.)
  • You want yesterday's version of the table: it is gone. (No history.)

The idea. Do not discover the table by listing a folder; keep an explicit, versioned list of data files in metadata files. A change is "write new data files, write a new metadata version, atomically point the table at it". All of the problems above follow from that one design.

What you get, with what it means:

FeaturePlain meaning
Atomic commitsreaders see before or after a write, never half
Snapshot isolationa query keeps one consistent view even while writes continue
Schema and partition evolutionchange columns or layout as metadata, without rewriting data
Row-level update and deleteSQL UPDATE, DELETE, MERGE via new files plus metadata
Time travel, rollbackread or restore an earlier snapshot
Fast planningmin and max per file are in metadata; no listing, and many files skipped

What it is not. It is not a storage engine you deploy and not a query engine. There is no Iceberg server process. You use it through an engine (Spark, Flink, Trino, Hive, Snowflake and others can read it) plus a catalog that stores the pointer. That neutrality is its selling point: the same table can be written by Flink and read by Trino.

Trade-off. You take on table maintenance (compaction, snapshot expiry), and every engine must implement the spec correctly, so version support varies. For a tiny, single-writer, append-only dataset, plain Parquet with partition folders can still be enough.

With a plain folder, a reader can see half a job, a failed job leaves partial files, two writers can overwrite the same partition, columns are matched by name or position (renames go wrong), and every query lists thousands of objects on S3. Iceberg fixes each of these with metadata and one atomic pointer swap. It is not a file format and not a database: there is no server, just the spec plus client libraries, and engines (Spark, Flink, Trino and others) do the work. The data files stay in open Parquet, so you can migrate an existing table in place.

Delta Lake and Hudi solve the same problem. Delta is closely tied to Spark and Databricks, Hudi is strong at record-level upserts and incremental pulls, and Iceberg is the most engine-neutral. I choose Iceberg for a multi-engine platform; the details of the others are specialist knowledge.

Remember: Iceberg = metadata that says which files are the table. Not a file format, not a server.

Walk me through the Iceberg metadata layers, from catalog down to data files. Intermediate

The catalog maps a table name to the current metadata file. That metadata JSON holds the schema, partition specs and the list of snapshots. Each snapshot points to a manifest list, which points to manifest files, and each manifest lists data files with their partition values and column statistics. To plan a query the engine walks down this tree, pruning at each level, so it opens only a few Parquet files and never lists a directory.

Why a tree and not a single file list? A table can have millions of files. A single list file would have to be rewritten on every commit (slow) and read fully by every query (slow). Splitting it into layers means a commit adds only a little, and a query can discard big parts of the tree early.

What each layer holds and what it is for:

  1. Catalog. A tiny directory: db.orders to the location of the current metadata.json. This single pointer is what is swapped atomically at commit. (Hive Metastore, AWS Glue, a database via JDBC, or a REST catalog service.)
  2. Table metadata file (JSON). Table-wide facts: schema versions (with column ids), partition specs, sort order, table properties, the list of snapshots and which one is current. Each commit writes a new numbered file (v12.metadata.json, then v13) and old ones remain for history.
  3. Snapshot. One version of the table. It points to exactly one manifest list.
  4. Manifest list (Avro). Lists the manifest files that belong to this snapshot, with a summary per manifest: how many files, the min and max of each partition column inside it. This lets the planner drop a whole manifest without opening it.
  5. Manifest file (Avro). Lists data files (and delete files), each with: path, partition values, row count, size, and per-column min, max and null counts.
  6. Data files (Parquet usually). The actual rows.

Planning a query, walked through. SELECT ... WHERE event_date = '2026-11-17' AND amount > 1000:

  1. Ask the catalog for the metadata file, read it, pick the current snapshot.
  2. Read the manifest list. Keep only manifests whose partition range could contain Nov 17.
  3. Read those manifests. Keep only files whose partition equals Nov 17 and whose amount max is over 1000.
  4. Launch tasks on just those files. Inside each, Parquet footer stats skip row groups.

No directory listing happens at all, and the cost depends on how much matches, not on the table's total size.

What a commit does. An append writes new data files, one new manifest that lists only them, a new manifest list that references the new manifest plus all unchanged old manifests, a new metadata file, then swaps the catalog pointer. Old manifests are reused, which is why commits stay small.

Pitfalls. Very frequent commits create many small manifests (fix with rewrite_manifests). The metadata, not the data, can become the bottleneck for tables with millions of files. Metadata files accumulate until old snapshots are expired (and optionally old metadata cleaned up).

Two levels (manifest list, then manifests) are there so a new commit can reuse old manifests unchanged and add just one new manifest, which keeps commits small. The manifest list stores partition range summaries, so whole manifests are dropped without opening them. Manifests and the manifest list are Avro files; data files are normally Parquet.

Remember: catalog, metadata.json, manifest list, manifests, data files. Prune at every level, never list a folder.

What is an Iceberg snapshot, and how does time travel work? Intermediate

A snapshot is the complete state of the table after one commit: the set of data files that made up the table at that moment. Every write (append, overwrite, delete, compaction) creates a new snapshot without copying data, because it reuses existing files and manifests. Time travel just starts reading from an older snapshot, so it only needs the old files to still exist.

What a snapshot really is. Not a copy of data. It is a reference to a manifest list, i.e., a precise list of data files, plus a timestamp and a summary ("append, added 12 files, 1.2M rows"). Because data files are immutable, two snapshots can safely share most of their files.

Timeline example.

TimeOperationSnapshotFiles in table
MonappendS1f1, f2
TueappendS2f1, f2, f3
WedcompactionS3f4 (= f1+f2+f3 merged)

The files f1, f2, f3 are not deleted on Wednesday: S1 and S2 still need them. Reading "as of Tuesday" simply uses snapshot S2's file list. Rolling back on Thursday means pointing the table's current snapshot at S3 again, which is metadata only and instant.

Why this matters in practice.

  • Reproducibility: a regulator or analyst asks "what did the report show on the 1st?". Query with TIMESTAMP AS OF.
  • Debugging: compare two snapshots to see which rows a job changed (Iceberg has an incremental read and a changelog view).
  • Safe operations: before a risky job, note the snapshot id; if it goes wrong, roll back.
  • Consistent reads: a long query keeps its snapshot, so concurrent writes do not change its results midway.

Tags and branches. A tag is a named pointer to a snapshot you want to keep (for example end-of-quarter), exempt from the normal expiry. A branch is a movable pointer you can write to independently, enabling the write-audit-publish pattern: write to branch audit, run quality checks, then fast-forward main only if they pass.

The cost and the catch. Time travel is only possible while the old files exist. Each snapshot keeps its unique files alive, so storage grows until you run expire_snapshots. Setting a retention (say 7 or 30 days) is a business decision: longer means more history, but more storage and, for privacy deletes, a longer period in which erased data is still recoverable. Also remember that time travel reads the schema of that snapshot (columns dropped later reappear), which is correct but can surprise people.

It is useful for reproducing a report, auditing, debugging a bad load ("what did the table look like before the job?") and quick rollback. The cost is storage: old data files stay until you expire the snapshots that reference them. Snapshots can also be named: a tag keeps one for audit, and a branch lets you write to a staging copy, check it, and then publish (the write-audit-publish pattern).

-- Spark SQL
SELECT * FROM prod.orders TIMESTAMP AS OF '2026-11-01 00:00:00';
SELECT * FROM prod.orders VERSION AS OF 4928374982374;   -- snapshot id
CALL prod.system.rollback_to_snapshot('orders', 4928374982374);

Remember: snapshot = list of files at one commit. Time travel is free until you expire snapshots.

How does Iceberg give ACID transactions on object storage with no lock server? Senior

Through optimistic concurrency. A writer reads the current metadata, writes its new data files, manifests and a new metadata file, and none of that is visible yet. The commit is one atomic compare-and-swap in the catalog: "move the pointer from v12 to v13, only if it is still v12". If another writer got there first, the swap fails, and the loser re-reads the new state, checks for real conflicts, rebuilds on top of it and retries.

First the vocabulary. ACID means: Atomic (a write is all or nothing), Consistent (rules hold), Isolated (concurrent users do not see each other's half-done work), Durable (committed data survives). Databases get this with locks and logs. Object storage has no locks and no transactions, only immutable objects. So how can a table on S3 be ACID?

Key insight: do all the heavy work invisibly, then make it visible with one tiny atomic operation. Everything a writer produces (data files, manifests, new metadata file) is just unreferenced files until the very last step. If the writer dies, those files are garbage that nobody reads; the table is unchanged (atomicity). The last step is a single compare-and-swap on the catalog pointer.

Commit walkthrough with two writers.

  1. Both writers start from metadata v12. Writer A appends 100 files. Writer B runs a compaction that rewrites files f1 to f20.
  2. A finishes first: it writes metadata v13 and tells the catalog "set pointer to v13 if it currently is v12". That succeeds.
  3. B finishes and asks "set pointer to v13b if it currently is v12". The catalog says no, the pointer is v13 now.
  4. B does not give up and does not lose its data files. It reloads v13 and checks for conflicts: did A's changes touch f1 to f20? A only added new files, so B's rewrite is still valid. B writes v14 (A's files plus its own change) and swaps from v13 to v14. If instead A had deleted f5, B's validation would fail and it would abort (or the job would redo its work).

Isolation for readers. A reader loads the pointer once, and then uses that snapshot for the whole query. New commits create new snapshots; they never modify the one being read. So readers never block writers and never see partial states (snapshot isolation; write operations can be configured for serializable or snapshot validation).

Why optimistic and not locks? Locks need a lock service, hurt performance and risk deadlock or stuck locks when a job dies. Optimistic concurrency assumes conflicts are rare (usually true for append-heavy workloads) and pays only when a conflict happens.

What the catalog must provide. The atomic swap lives in the catalog implementation (a database transaction in Hive or JDBC catalogs, a conditional update in Glue, a server-side check in REST catalogs). S3 historically lacked conditional writes, which is why the plain filesystem catalog is unsafe for concurrent writers there; newer S3 conditional-write support changes that for some setups, but a real catalog is still the normal choice.

Pitfalls and production notes. (1) Many writers committing to the same table cause retry storms; partition the workload or batch commits. (2) Long-running rewrite jobs are the most likely to lose the race and fail validation; run compaction on cold partitions. (3) Retry count and wait are table properties, tune them if you see CommitFailedException. (4) Atomicity is per table, not across tables: updating two tables is two independent commits.

Atomicity comes from the single pointer swap, isolation from snapshots (a reader keeps the snapshot it started with and is never disturbed), and durability from object storage. Appends rarely conflict with each other, but two jobs that rewrite or delete the same files can: that fails with a validation error. Retries default to a small number (about 4) and are configurable. The atomic step lives in the catalog, not in S3, so use a catalog that supports it (Hive, Glue, JDBC, REST, and similar); a plain file-system catalog is unsafe for concurrent writers on S3.

Remember: write files invisibly, then one atomic pointer swap commits. Lose the race, validate, retry.

How does Iceberg handle schema evolution without rewriting data? Intermediate

Every column gets a unique, permanent field id, stored in the metadata and in the data files, and the engine maps columns by id, not by name or position. So add, drop, rename and reorder are metadata-only changes and no data is rewritten. Old files simply return null for a newly added column.

The old problem. In a plain Parquet or Hive table, the engine finds a column in a file by its name (or sometimes by position). That breaks in several ways. Rename cust to customer: old files still say cust, so reading them returns null. Drop region and later add a new, different column also called region: old files now answer with the old column's values. Positional mapping breaks when you insert a column in the middle. To be safe you had to rewrite all data.

Iceberg's fix: identity separate from name. When a column is created it gets a unique integer id (1, 2, 3 ...). The table schema says "id 3 is called cust", and every Parquet file written stores the field id next to each column. The engine reads by id:

  • Rename: id 3 now has the name customer. Old files still carry id 3, so they read correctly. No data changed.
  • Add column: gets a new id (say 9). Old files have no id 9, so the reader returns null (or the declared default) for them.
  • Drop column: id 4 is removed from the schema. Old files still hold it, but it is ignored. If you later add a new column with the same name, it gets a new id (10), so the old values can never leak back in ("zombie columns").
  • Reorder: only the order in the schema metadata changes.

Type changes are limited to lossless promotions: int to long, float to double, decimal precision widening. Anything else (string to int, long to int) needs a new column, a backfill and a switch-over.

Schema evolution and time travel. Each snapshot records the schema id it was written with, so old snapshots keep reading with their own schema.

Compare with Avro. Avro resolves by field name plus aliases and needs defaults; Iceberg resolves by id. Same goal, different mechanism. Iceberg manifests are Avro files, which is why you will meet both.

Pitfalls. Engines and downstream consumers (dashboards, exports) still break on a rename even when the table itself is fine, so a rename is a breaking change for readers by name. Treat evolution as additive when many consumers depend on a table. Also check that a writer does not carry an old schema: Spark sessions with a cached schema or a Flink job started before the change may need a restart or a schema-merge option.

This avoids the classic bug in plain Parquet or Hive tables, where a name or position mapping returns the wrong column's data after a drop and re-add. Ids are never reused. Type changes are allowed only when safe (int to long, float to double, wider decimal precision); string to int needs a new column and a backfill. Each schema version is kept, so old snapshots stay readable.

ALTER TABLE prod.orders ADD COLUMN coupon string;
ALTER TABLE prod.orders RENAME COLUMN cust TO customer;
ALTER TABLE prod.orders ALTER COLUMN qty TYPE bigint;

Remember: columns are tracked by id, so rename and reorder are free and a dropped column never "comes back".

How do you choose a partitioning strategy for a lake table? Intermediate

I partition on the column most queries filter on, usually a time column such as day for event data, and I check that each partition is big enough. Partitions let a query skip whole groups of files. The mistakes are going too fine (partition by user id, or by hour on a small table), which creates millions of tiny files, and too coarse (by year), where every query scans a lot.

What partitioning is for. Splitting a large table into groups so that a query touching one group can ignore the others. In a lake, partitions normally map to groups of files (a folder per day in Hive style; metadata groupings in Iceberg). The engine uses the query's filter to skip every group that cannot match, which is the cheapest speed-up available: files you do not open cost nothing.

Decide in three steps.

  1. Find the dominant filter. Look at real queries or ask the users. For events it is almost always a time range, so day(event_time).
  2. Estimate the partition size. Daily volume 50 GB gives 50 GB per partition, fine. 200 MB per day gives 200 MB per partition, producing small files; use month or no time partition instead. A useful guide: each partition should contain at least hundreds of MB, ideally several GB, spread over files of 128 MB to 1 GB.
  3. Check cardinality and skew. The number of partitions should be thousands, not millions (every partition is metadata the planner must handle). If you also filter by a high-cardinality key such as user_id, add bucket(16, user_id) or sort inside files rather than partitioning by value.

Example. 2 TB per day of clickstream, queries "last 7 days for one customer". Partition by day(ts) (1 partition per day, 2 TB each, plenty), then sort or bucket by customer id so one customer's rows sit in a few files and min/max stats find them. Partition by customer_id would create millions of folders with a few KB each, a catastrophic number of small files.

Too fine versus too coarse.

Too fine (hour, id)Too coarse (year)
Symptommillions of tiny files, slow planningevery query scans big chunks
Fixcoarser partition, compactionfiner partition, plus sort order

Skew. Partitioning by country when one country has 80% of rows creates one huge partition and many tiny ones: the big one limits parallelism. Prefer time or a hash bucket for balance.

Pitfalls. Partitioning does not replace sorting; they work at different levels. Changing partition columns in Hive-style tables means rewriting everything, but Iceberg lets you evolve it (next question). Do not partition by columns that change over time (like status), because updating the value would mean moving the row to another partition.

Rough targets: each partition holds at least a few hundred MB to many GB, and the total number of partitions stays in the thousands, not millions. For a high-cardinality column like user_id do not partition by value: use a bucket transform (hash into N buckets) or sort data inside files so min and max stats work. Watch for skew too: if one country has 80% of the data, partitioning by country does not balance the work. Partitioning prunes folders; sorting narrows min and max within files; use both. In Iceberg you can change the partitioning later, so start simple and measure.

Remember: partition by what queries filter on, in chunks big enough to be worth skipping. Never by an id.

What is hidden partitioning in Iceberg, and what is partition evolution? Intermediate

In Hive-style tables the partition is a folder and an extra column like dt=2026-11-17, and users must filter on it or the query scans everything. In Iceberg you declare a transform of a real column, such as day(event_time), and Iceberg computes and tracks the partition value itself. A filter on event_time is automatically turned into partition pruning, and nobody can forget or mis-fill a partition column.

The Hive-style problem. To partition a Hive table by day you add an extra column dt and the writer must fill it correctly (dt = '2026-11-17'). Then every query author must remember to filter on dt, not on event_time. If an analyst writes WHERE event_time > '2026-11-17', the engine does not know that is related to dt, so it scans the entire table. Also a writer can put the wrong value in dt (time zone errors are classic) and queries then silently miss data.

Hidden partitioning. Iceberg stores the partition as a function of an existing column: PARTITIONED BY (day(event_time)). The table has no extra dt column. On write, Iceberg computes day(event_time) itself and records it per file. On read, when a filter mentions event_time, the planner applies the same function to the filter bounds and prunes partitions. The user writes the natural query and still benefits.

Transforms available: year, month, day, hour (on dates and timestamps), bucket(N, col) (hash modulo N, for spreading ids), truncate(W, col) (first W characters or rounding to a width), and identity (the value itself).

Partition evolution step by step. A table is partitioned by month(ts). Data grows 30x and months are now too big. You run ALTER TABLE t ADD PARTITION FIELD day(ts) (and drop the month field).

  1. Existing files are untouched and keep partition spec 0 (month).
  2. New writes use spec 1 (day). Each manifest records which spec its files use.
  3. A query over both periods is planned in two parts, using month pruning for the old files and day pruning for the new.

Compare with Hive: changing partition columns means a full rewrite of the table. Iceberg: metadata change, then compact the old data later if you wish.

Pitfalls. Mixed specs make planning slightly more complex and compaction should eventually rewrite old data; check that your engine supports the transform you use; and remember hidden partitioning removes the dt column, so any downstream code that expects it breaks (migrating from Hive tables needs care).

Transforms include year, month, day, hour, bucket(N, col) and truncate(W, col). Because layout is metadata, you can also change it: move from monthly to daily partitions with one command. Old files keep the old spec and new files use the new one; each manifest remembers its spec, and the planner prunes each group with its own rules. Nothing is rewritten, though queries spanning both layouts plan a little slower, and you can compact old data into the new layout when convenient.

CREATE TABLE prod.events (id bigint, user_id bigint, event_time timestamp)
USING iceberg
PARTITIONED BY (day(event_time), bucket(16, user_id));

Remember: partition by a transform of a real column. Users filter on the column, Iceberg handles the folders, and the layout can change later.

Explain copy-on-write versus merge-on-read in Iceberg. Senior

Both exist because data files are immutable. Copy-on-write rewrites each data file that holds an affected row: reads stay fast, but one changed row rewrites a whole large file. Merge-on-read leaves data files alone and writes small delete files; writes are cheap, but readers must merge deletes with data until a compaction cleans up. I use copy-on-write for read-heavy tables with infrequent batch updates, and merge-on-read for frequent small updates and CDC.

Why we need two strategies. Since a data file cannot be edited, removing one row from a 512 MB file forces a choice. Do you pay now (rewrite the file) or later (record the deletion and merge on every read)?

Copy-on-write (COW), walked through. You run DELETE FROM orders WHERE id = 42. The engine finds the one file containing id 42, reads all of it, writes a new file without that row, and commits "table = new file instead of old file". Cost: one row changed, 512 MB rewritten (write amplification). Benefit: reads are plain Parquet scans with no extra work. Good for tables that are read a lot and updated in occasional, large batches (nightly corrections).

Merge-on-read (MOR), walked through. Same delete: the engine writes a tiny delete file "file-A, row position 2 is deleted" and commits. Cost: almost nothing. But now every reader of file-A must also open its delete file and filter rows (read amplification), and the number of delete files grows with each change. A later compaction merges them into clean data files. Good for frequent small updates, streaming upserts and CDC.

Two kinds of delete file. Position deletes name a file and row position: precise, cheap to apply, but the writer must know where the row is (it has to read the file or index). Equality deletes say "delete rows where order_id = 42": the writer needs no lookup, so streaming jobs love them, but the reader must compare every row of older files against the set of keys, which is costlier. In spec v3, deletion vectors (a compact bitmap per data file) replace position delete files for cheaper reads.

The mode is configurable per operation (properties such as write.delete.mode, write.update.mode, write.merge.mode), so one table can use COW for deletes and MOR for merges.

Pitfalls. A MOR table without scheduled compaction slowly gets slower until someone complains; monitor the number of delete files per data file. COW on a table with frequent trickle updates burns compute and rewrites the same big files again and again. For GDPR-style erasure, MOR delete files only hide rows, so compaction is also needed for physical removal.

Delete files come in two kinds. A position delete says "in file X, rows 17 and 902 are deleted". An equality delete says "any row with order_id = 42 is deleted", which suits streaming upserts, where the writer does not know file positions. An update is a delete plus a new row. Newer table spec versions replace position deletes with compact deletion vectors, which make merge-on-read reads cheaper. Copy-on-write is typically the default and the mode is a table property.

Remember: COW pays on write, MOR pays on read. Merge-on-read needs compaction.

What is the small files problem, and what maintenance does an Iceberg table need? Intermediate

Small files are data files far below a useful size (say a few MB when the target is a few hundred MB). Every file costs a fixed amount: an object-store request, a footer read, a task launch and a metadata entry, so reading a million 1 MB files is far slower than reading 500 big ones holding the same bytes. The fix is compaction: rewrite many small files into few well-sized ones, on a schedule, plus cleanup of old snapshots.

Why does file size matter so much? Reading a file has a fixed overhead regardless of size: an HTTP request to S3 (tens of milliseconds), opening the footer, planning a task, and a row in the metadata. Reading 1 MB costs almost the same overhead as reading 512 MB. So 1 million files of 1 MB (about 1 TB) can take hours where 2,000 files of 512 MB take minutes, even though the bytes are the same. Compression and min/max statistics are also weaker on tiny files.

Where small files come from, with an example. A Flink job commits to Iceberg every 10 seconds. Each commit writes one or more files for each partition and writes a new snapshot and manifest. After a day: 8,640 commits and often tens of thousands of files of a few MB. Other sources: Spark jobs with 2,000 shuffle partitions writing a 1 GB dataset (2,000 files of 500 KB), very fine partitions, and many writers.

Maintenance toolbox, what each does and when.

  • Compaction (rewrite_data_files, optionally with a sort strategy): read small files, write fewer big ones, commit as a new snapshot. Run on hot partitions often (hourly), cold ones rarely. It can conflict with streaming writes to the same partition, so compact closed partitions or use the engine's partition filter.
  • Expire snapshots: deletes snapshot metadata older than a retention and data files nobody references. Without this, the pre-compaction small files stay forever, so you pay for both the old and new copies.
  • Remove orphan files: deletes files in the table location that no snapshot references (written by failed jobs). Always use an age cutoff (days) so you do not delete a file of an in-flight write.
  • Rewrite manifests: merge many tiny manifests to keep planning fast.

Example call: CALL prod.system.rewrite_data_files(table => 'events', where => 'event_date < current_date') followed by expire_snapshots(older_than => ...).

Prevention beats cure. Commit less often (a 1 to 5 minute interval is common; lower latency needs a different design), use coarser partitions, set a sensible number of shuffle partitions (or let adaptive execution coalesce), and use the writer's file-size target and distribution options (for Spark, a write distribution mode to avoid every task writing to every partition).

Pitfalls. Compaction is itself expensive and creates a snapshot, so not "as often as possible". Forgetting expire_snapshots makes compaction look useless in the storage bill. Managed services (some catalogs and vendors) offer automatic compaction; ask whether it is on.

They come from streaming writes that commit every few seconds, too many shuffle partitions in Spark, and over-partitioning. Prevention: commit every few minutes, not seconds, and choose coarser partitions. Maintenance jobs for an Iceberg table:

  • Compaction (rewrite_data_files): merge small files toward the target size (default about 512 MB), optionally sort, and apply delete files.
  • Expire snapshots (expire_snapshots): drop old snapshots and the files only they use; without it storage and metadata grow forever. It also ends time travel to those snapshots, so keep retention longer than your longest query.
  • Remove orphan files: delete files no metadata knows about (from failed jobs), with an age threshold so a running write is not harmed.
  • Rewrite manifests: regroup thousands of tiny manifests left by frequent commits.

Remember: few big files beat many small ones. Compact often, expire snapshots, clear orphans.

How do Iceberg, Delta Lake and Hudi differ, and how would you choose? Intermediate

All three put a transaction log or metadata tree on top of Parquet files to give ACID, time travel, schema evolution and row-level changes on object storage. They differ in design and ecosystem. Iceberg is the most engine-neutral and has strong partition evolution, Delta Lake is the most natural on Spark and Databricks, and Hudi is built around record-level upserts and incremental pulls. I choose by which engines must read and write, and which update pattern dominates.

How they track the table. Delta keeps an ordered transaction log of JSON action files (add file, remove file) in a _delta_log folder, with periodic checkpoint files; the current table is the log replayed. Iceberg keeps a tree of metadata files, snapshot, manifest list, manifests, reached from a catalog pointer, so planning does not replay a log. Hudi keeps a timeline of commits and an index that maps record keys to file groups, which makes upserts fast.

4. Pipelines, streaming and data quality

Batch versus streaming processing: how do you decide? Basic

I ask "what does it cost the business if this data is one hour old?". If the answer is "nothing", I use batch (or micro-batch every few minutes): it is simpler, cheaper and easy to re-run and test. I use streaming when seconds matter, for things like fraud alerts, live dashboards or keeping a search index fresh.

Definitions first. Batch processes a finite, bounded set of data that already exists ("all of yesterday's orders") and then stops. Streaming processes an unbounded flow of events as they arrive and never really finishes. Micro-batch sits between: small batches every few seconds or minutes.

The deciding question is latency value, not technology. Ask: "if this number is 1 hour old, who is hurt, and how much?" Examples: a monthly finance report (1 day old is fine, batch), a recommendation model retrained nightly (batch), a fraud decision at payment time (must be milliseconds, streaming or request-time), an ops dashboard (a minute is fine, micro-batch), a search index kept in sync with a database (seconds, streaming CDC).

Why streaming is harder. In batch you can sort the data and look at all of it. In streaming you must answer "what is the count for 10:00 to 10:05?" while events for that window may still be on their way (late data), must store running state (counts, joins) and survive a crash without losing or double-counting it (checkpoints), and must keep up when traffic spikes (backpressure).

Architectures people mention. Lambda: run a batch path (accurate, slow) and a stream path (fast, approximate) and merge results. It works, but you maintain the same logic twice, and the two can disagree. Kappa: only a streaming path over a replayable log (Kafka); to reprocess, replay the log with new code. Simpler in code, requires a long retention and a capable stream engine. Today, the lakehouse often gives a third option: stream into Iceberg and let batch and streaming engines read the same table.

Rule I use. Start with batch or micro-batch; move to true streaming only when a measured business need requires seconds, and then keep a batch job for reprocessing and corrections. The pitfall is "real-time" requested because it sounds modern: ask for the actual freshness requirement and its cost.

Batch processes a bounded chunk on a schedule ("every night, process yesterday"). Streaming processes an unbounded flow of events continuously. Streaming costs more in complexity: state, ordering, late events, restarts and exactly-once effects, plus jobs that run all day. Many systems use both: streaming for the freshest slice, batch to reprocess and correct. Engines like Spark and Flink use nearly the same API for both, which narrows the gap. A lambda architecture runs both paths and merges them (two code bases, painful); a kappa architecture uses one streaming path and replays the log to reprocess.

Remember: batch unless freshness really pays for the extra complexity.

ETL versus ELT: what is the difference and why did ELT become popular? Basic

ETL transforms data on a separate processing server before loading only the result into the warehouse. ELT loads raw data first and transforms it inside the lake or warehouse with its own scalable engine (SQL, Spark, dbt). ELT won because cloud storage and compute are cheap and elastic, and keeping raw data means I can change business logic later and re-run without re-extracting from the source.

The two letter orders. E = extract (copy from the source), T = transform (clean, join, aggregate, reshape), L = load (write to the destination). The question is simply where the T runs and when.

ETL (older pattern). A dedicated tool (Informatica, SSIS, a custom Java job) pulls data from sources, transforms it on its own servers, and loads only the finished, modelled result into the warehouse. Reasons it existed: warehouse compute was expensive and fixed, so you did not want to waste it on cleaning, and the warehouse should hold only curated data.

ELT (modern pattern). Copy the raw data into the lake or warehouse first, then transform with SQL (often organised by dbt) or Spark inside it. Reasons it won:

  • Cheap, elastic storage and compute: keeping raw data costs little, and the warehouse or Spark cluster scales for transformations.
  • Re-processing: if the definition of "active customer" changes, you re-run the SQL over the stored raw data; with ETL you would have to re-extract from the sources, which may no longer hold the old values.
  • Simplicity and speed to start: loading raw first means a source can be onboarded quickly, and analysts can start exploring.
  • One engine, SQL skills: transformations are SQL in the warehouse, versioned and tested like code.

Example. Raw orders arrive as JSON. ELT: load them unchanged into raw.orders, then a dbt model builds clean.orders (types fixed, duplicates removed) and marts.daily_revenue. If the revenue logic changes, only the last model is re-run.

When ETL (or "ETL-ish") is still correct. (1) Privacy and compliance: PII must be masked or dropped before it lands in a broadly accessible store. (2) Huge volume of low-value data where you filter before loading to save cost. (3) The destination cannot transform (an operational system). (4) Streaming transforms in flight (parse, validate, enrich) before writing.

Pitfall. "ELT" does not mean "no modelling". An unmodelled raw dump is the data swamp again. Use layers (raw, cleaned, business-ready) with owners, tests and documentation, as in the medallion question below.

ETL is still right when data must be masked or filtered before it may land (privacy rules), or when you must shrink huge volumes before loading. A common practical mix: a little "T" before load (drop PII, validate types), and the main modelling after.

Remember: ETL = shape then load. ELT = load raw, shape later where the compute is.

What is the bronze, silver, gold (medallion) layering, and why keep a raw layer? Basic

It is a way to organise lake tables by how clean they are. Bronze holds raw data exactly as received. Silver holds cleaned, deduplicated, typed and conformed data. Gold holds business-ready tables such as aggregates and marts for dashboards. Each layer is built from the one before, so any mistake can be fixed and replayed from the layer below.

What goes in each layer, with an example (orders from an app):

  • Bronze: the Kafka or file payload stored as it arrived, plus ingestion metadata (arrival time, source file, offset). Append-only, no business logic, nothing dropped. Even broken records are kept (or in a quarantine), so you can investigate them.
  • Silver: one clean row per business entity. Parse JSON into typed columns, fix timestamps to UTC, remove duplicates by order id, apply schema checks, join with reference data (customers). This is what most engineers and data scientists query.
  • Gold: shaped for a purpose: daily_revenue_by_city, a customer 360 table, features for a model. Aggregated and often denormalised so dashboards are fast and numbers have one agreed definition.

Why this helps. (1) Replayability: if a bug in the silver logic is found, fix the code and rebuild silver from bronze; the source may no longer have the data. (2) Separation of concerns: ingestion is fast and dumb, cleaning is careful, business logic is explicit. (3) Trust: consumers know where to look for raw versus certified numbers. (4) Targeted quality checks and access: bronze may contain PII and be restricted; gold is widely shared.

Costs and pitfalls. Storage is multiplied, and more tables to maintain; layers can become a ritual with no ownership. Keep names and ownership clear, apply quality checks at the silver boundary, and do not skip bronze to save space, because you lose the ability to repair. The names are a convention (Databricks popularised them), not a standard; some teams say raw, staging, curated.

Remember: bronze = raw and replayable, silver = clean and conformed, gold = business-ready. Fix bugs by rebuilding from the layer below.

What is Change Data Capture (CDC), and how do you do it? Intermediate

CDC captures every insert, update and delete from a source database as a stream of change events, so a lake, cache or search index can follow it. I prefer log-based CDC: it reads the database transaction log (MySQL binlog, PostgreSQL WAL), sees every change in commit order including deletes, and puts almost no load on the tables. Debezium on Kafka Connect is the best-known tool.

Why CDC exists. Systems need to follow a database without hurting it. Examples: copy orders into the lake, update a search index, invalidate a cache, feed other services. Nightly full copies are slow, heavy, and stale. Doing "dual writes" from the app (write to the DB and also to Kafka) can leave them out of sync when one write fails. CDC solves this by turning the database's own record of changes into a stream.

How log-based CDC works. Every serious database writes all changes first to a transaction log (MySQL binlog, PostgreSQL write-ahead log, Oracle redo log) to be crash safe and replicate to standbys. A CDC connector behaves like a replica: it reads that log and turns each committed row change into an event. Debezium runs inside Kafka Connect, first takes a consistent snapshot of the existing table (events marked as reads, op "r"), then streams changes from the log position where the snapshot started.

An event looks like this (simplified):

{ "op": "u",                       // c=create, u=update, d=delete, r=snapshot read
  "before": {"id": 42, "status": "PENDING"},
  "after":  {"id": 42, "status": "SHIPPED"},
  "source": {"lsn": 91827364, "ts_ms": 1731850000000, "table": "orders"} }

A delete has before and no after, which is exactly what a polling query can never tell you.

Applying CDC downstream. Events for one key must be applied in order, so key the Kafka topic by primary key (same key, same partition). Pitfalls. Schema changes in the source must flow through (the connector emits schema changes; handle with the registry). Initial snapshots of huge tables take time and can lock or stress the DB. Downstream, apply events per key in order with upserts and deletes (MERGE). One operational risk to know: in PostgreSQL an unconsumed replication slot makes the database keep WAL forever and can fill its disk, so monitor slot lag.

Remember: log-based CDC = read the DB log, not the tables. Apply per key in order, and watch the lag.

Explain at-most-once, at-least-once and exactly-once. Is exactly-once real? Intermediate

At-most-once means delivered zero or one time: you can lose data (commit the offset before processing). At-least-once means one or more times: no loss but duplicates after retries (process, then commit). Exactly-once is really exactly-once effect: at-least-once delivery combined with deduplication or idempotent or transactional writes, inside a boundary where I control both sides.

Why this is a question at all. A producer sends a message and waits for an acknowledgement. If no acknowledgement arrives, did the message get lost, or did the acknowledgement get lost? The sender cannot tell. It has only two choices: send again (risk of duplicate) or do not (risk of loss). All delivery semantics come from that choice.

  • At-most-once: never retry. Fast and simple, but data can be lost. Example: a consumer commits its offset first, then crashes before processing. Fine for metrics you can afford to lose.
  • At-least-once: retry until acknowledged. Nothing is lost, but the same message may be processed twice. Example: consumer processes, writes the result, crashes before committing the offset, restarts and processes it again. This is the default in most systems.
  • Exactly-once: each message affects the result exactly one time. A network cannot guarantee delivery once, so this is built from at-least-once plus something that cancels duplicates.

How "exactly-once" is really achieved.

  1. Idempotent writes: make a duplicate harmless. MERGE on a key, INSERT ... ON CONFLICT DO NOTHING, or write to file-name = f(offset range) so a retry overwrites with the same bytes. A bank transfer API uses an idempotency key (the second call with the same key returns the first result).
  2. Transactions that commit output and progress together: Kafka transactions write output records and the consumer offsets in one atomic unit (for Kafka-to-Kafka). If the job dies, both roll back and it reprocesses from the old offset with no visible duplicates (consumers must read with read-committed isolation).
  3. Checkpoint plus two-phase commit: Flink snapshots its state and offsets together; a transactional sink pre-commits data and commits it only when the checkpoint completes. After a crash it restarts from the last checkpoint, and uncommitted output is discarded.
  4. Store the offset with the result in the same database transaction (consumer writes rows and the offset in one DB commit).

Worked example. A job reads offsets 100 to 199 and writes totals to a database. Crash after the write, before the commit. On restart it reads 100 to 199 again. Without protection, totals double. If the job writes (batch_id=100-199, total=...) with a unique key on batch_id, the second write is rejected or overwrites identically, and the result is exactly-once in effect.

Where it breaks. The guarantee covers only the parts inside the protocol. Sending an email, calling a payment API, or writing to an external system that is not transactional is still at-least-once; you need idempotency keys there. Also exactly-once costs latency and throughput (transactions, checkpoints), so use it where duplicates truly hurt, not by reflex.

Over an unreliable network you cannot guarantee a message arrives exactly once, because a lost acknowledgement looks the same as a lost message. Real mechanisms: Kafka's idempotent producer (sequence numbers per partition) and transactions (atomic writes to several partitions plus consumer offsets, for Kafka-to-Kafka flows); Flink checkpoints with a two-phase-commit sink; a checkpointed, idempotent sink in Spark; and an Iceberg MERGE on a key. It breaks at the edge: calling an external API or appending to a plain file has no such guarantee, so use an idempotency key.

Remember: exactly-once = at-least-once + idempotent write.

What is an idempotent data pipeline, and how do you build one? Intermediate

A pipeline is idempotent if running it twice with the same input gives the same final data as running it once. Pipelines are re-run all the time (retries, backfills, replays), so an append-only job turns every retry into duplicates and wrong totals. I make jobs idempotent by overwriting the partition they own, or by upserting with MERGE on a business key, and by passing the run date as a parameter instead of using the wall clock.

Why it matters, with an example. Your nightly job reads yesterday's orders and appends the total to a daily_revenue table. At 03:00 the Airflow task fails at 90% (a network blip), and the retry starts over. If the first run already appended some rows, the table now has duplicates and revenue is overstated. If someone later re-runs last week for a bug fix, it doubles again. Retries, backfills and replays are normal, so a pipeline that gives different results when run twice is a pipeline waiting for an incident.

The definition again. Idempotent means: f(f(x)) = f(x). The final state is the same after one or many runs with the same input.

Patterns, from simplest to most flexible.

  1. Overwrite what you own. The job for date D replaces the whole partition for date D (INSERT OVERWRITE ... PARTITION (dt=D) or Iceberg dynamic overwrite). Running again simply rewrites the same partition. Needs a clear mapping from run to partition.
  2. Upsert on a business key. MERGE INTO target USING source ON t.order_id = s.order_id WHEN MATCHED THEN UPDATE WHEN NOT MATCHED THEN INSERT. Same input twice gives the same table. Needs a stable unique key.
  3. Deterministic output names plus atomic publish. Write to a temp location, then publish with a rename or a table-format commit. A crashed half-write is never visible.
  4. Track processed inputs transactionally. Record (file name or offset range) in the same transaction as the output so already processed inputs are skipped.

Sources of non-determinism to remove: current_date or now() in the query (a backfill for last Tuesday would use today's date; pass the logical run date as a parameter), random ids or UUIDs generated in the job (derive ids from the data, for example a hash of the business key), "first row wins" without ordering, reading a source that changes between runs (read a snapshot, or filter by ingestion time).

Dedup, step by step. Decide what makes two records "the same" (an event id from the producer is best; otherwise a business key such as order_id plus event type). Decide which copy wins (latest updated_at, highest source offset). Add a tie-breaker so ties are resolved the same way on every run. In streaming, remember seen keys in state with a time-to-live bigger than the longest realistic duplicate gap.

How to test it. Run the job twice on the same input and diff the output; kill it in the middle and rerun; run a backfill over a past date. Tools such as Airflow make the logical date available as a template variable so the same code serves the daily run and the backfill.

Pitfalls. Overwrite patterns drop late-arriving rows if you only reprocess the "new" window; partition overwrite replaces the full partition, so the input for it must be complete; side effects (emails, API calls) are not undone by overwriting a table and need their own idempotency keys.

Other techniques: write to a temporary location and commit atomically (Iceberg and Delta do this), so a half-finished run is invisible; track processed inputs (file names, offsets, event ids) in the same transaction as the output; avoid now(), random ids and "pick any row". For deduplication, define what identifies a record (a producer-generated event id or a business key), keep the latest by event time or source offset, and add a tie-breaker so a re-run picks the same row. In a stream, keep seen ids only for a bounded time, longer than the longest expected duplicate gap. The test is simple: run the job twice and compare the output.

-- re-runnable: only touches the day it owns
INSERT OVERWRITE prod.sales_daily PARTITION (dt = '2026-11-17')
SELECT ... FROM raw.sales WHERE sale_date = '2026-11-17';

-- dedup: latest per key, deterministic tie-break
SELECT * FROM (SELECT *, row_number() OVER (PARTITION BY order_id
       ORDER BY updated_at DESC, source_offset DESC) rn FROM bronze.orders) WHERE rn = 1;
Watch out: an append-only task with "retry 3 times", and current_date inside the query so a backfill reads today instead of the run date.

Remember: overwrite the partition or merge on a key. Run it twice and the result must not change.

What are event time, processing time and watermarks? How do you handle late data? Senior

Event time is when something happened; processing time is when my system saw it, maybe minutes later. I group by event time, so results do not depend on network delay and replays give the same answer. A watermark is the engine's moving estimate "I have probably seen all events up to time T" (highest event time seen minus an allowed lateness). When it passes the end of a window, the window is closed and its state dropped; events older than the watermark are late.

The two clocks. Suppose a phone records a click at 10:00:03 but is in a tunnel and uploads it at 10:07:41. Event time = 10:00:03 (when it happened). Processing time = 10:07:41 (when your job sees it). If you count "clicks per 5-minute window" by processing time, the click lands in the wrong window and the result changes with network delays and with replays (replaying yesterday's log would put everything in "now"). If you count by event time, the click goes to the 10:00 to 10:05 window, which is the true answer and is reproducible.

The new problem. With event time, when is the 10:00 to 10:05 window finished? Another phone might still send a 10:02 event. You cannot wait forever (results never emerge, state grows without bound), and you cannot close at 10:05 wall clock (you would miss late events). You need a rule.

Watermark. The engine tracks the highest event time seen, maxEventTime, and defines watermark = maxEventTime - allowedLateness. It means "I believe no events older than this will still arrive". When the watermark passes a window's end, the engine emits the result and drops its state. With a 2-minute allowed lateness: after seeing an event at 10:07, the watermark is 10:05, so window 10:00 to 10:05 closes. A later event with time 10:03 is late.

Choices for late events:

  • Drop them: simple, slightly undercounts. Fine for approximate metrics.
  • Larger allowed lateness: more complete but results are delayed and state is bigger.
  • Side output or late table: collect late events separately, and correct later in batch.
  • Update the result (retractions or upserts): emit a corrected value for the window when late data arrives, if the sink supports upserts.

The trade-off is always latency versus completeness versus cost. A common design is a short watermark for a fast provisional view and a batch recomputation for final numbers (see the late-data scenario).

Operational traps. (1) Idle partitions: in Kafka, if one partition has no data, its watermark does not advance and the minimum across partitions stalls the whole job; configure an idle timeout. (2) A single device with a wrong clock sending a timestamp from the future can push the watermark far ahead and make everything else look late; validate timestamps. (3) Watermark semantics differ slightly between Flink and Spark Structured Streaming (Spark uses it to limit state for aggregations and joins), so read your engine's docs.

For late events I choose among: drop them (simple, counts slightly off), send them to a side output or "late" table for repair, allow more lateness (more delay and more state), or emit corrected results. The trade-off is always latency versus completeness. A batch job that recomputes recent windows from the raw log is a common safety net. One practical trap: an idle Kafka partition does not advance its watermark and can stall the whole job, so configure an idle timeout.

Remember: group by event time, let the watermark close windows, and repair very late data in batch.

How do you assure data quality in a pipeline? What happens when a check fails? Intermediate

I use layers of automated checks and decide the failure action by severity. At ingestion I validate schema, types and required fields. On rows I check not-null, ranges, allowed values, key uniqueness and referential integrity. On the table I check row count versus the usual, freshness and totals reconciled with the source. A critical failure stops the pipeline so bad data never reaches consumers; a minor failure sends the bad rows to a quarantine table with a reason and alerts. I never silently drop rows.

Why this needs design, not just tests. Pipelines usually fail silently: the job succeeds, but half the rows are missing, a currency column is in cents instead of dollars, or a join duplicates rows. Dashboards then show wrong numbers and people lose trust. Data quality is about catching these problems early, before consumers see them, and having a plan for what to do when a check fails.

Types of checks, with examples:

LevelExample checks
Schemaexpected columns and types present; no unexpected new column
Row levelnot null on keys, amount greater than or equal to 0, status in an allowed list, valid email format
Uniqueness and integrityorder_id unique; every order's customer_id exists in customers
Table levelrow count within 20% of the 7-day average; no gap in days; max(event_time) not older than 2 hours (freshness)
Reconciliationsum of amount equals the source system's total for that day
Distributionshare of nulls or mean of a column suddenly changes (anomaly detection)

What to do when a check fails (severity policy).

  • Block (critical): duplicate keys in the revenue table, a count of zero, a failed reconciliation. Stop the pipeline, do not publish, alert the owner. Consumers keep seeing the previous good data, which is better than wrong data.
  • Quarantine (row level): a few rows with an invalid value. Move those rows to a rejected table with the reason and the source, continue with good rows, and alert if the reject rate crosses a threshold.
  • Warn (minor): log and notify, publish.

Never drop bad rows silently: nobody will ever know that 3% of orders vanished.

Write-audit-publish. Write the new data to a place consumers do not read (a staging table, or an Iceberg branch), audit it with the checks, and publish (swap partition, fast-forward the branch) only on success. This gives consumers atomic, verified updates.

Where checks run: dbt tests (not_null, unique, relationships, accepted_values), Great Expectations, Soda, or plain SQL assertions in the orchestrator task. Cheap checks run on every load; expensive reconciliations run daily.

Data contracts. The technical checks catch the symptom; a contract fixes the cause. A data contract is a written, versioned, machine-checkable agreement between the team producing a dataset and the teams consuming it: schema, meaning and units, quality rules, freshness SLA, owner, and how breaking changes are announced. Producers validate against it in CI (for example, a schema registry compatibility check), so a renamed column fails the producer's build, not the consumer's dashboard.

Pitfalls. Too many noisy checks cause alert fatigue and people ignore them; start with a few that map to real incidents. Static thresholds fail on seasonal data (weekend traffic), so compare with the same weekday. Test data in production, not only in staging, since real data is what breaks.

Tools such as dbt tests, Great Expectations or Soda run these checks. A good pattern is write-audit-publish: write new data where consumers cannot see it (a staging table or an Iceberg branch), run the checks, and publish atomically only if they pass. The people side matters as much: a data contract is an explicit, machine-checkable agreement between the producing team and consumers, covering schema, meaning (currency, tax included?), quality rules, freshness, ownership and how breaking changes are announced. Checked in the producer's CI, it stops "an upstream team renamed a column and a dashboard broke two weeks later".

Remember: check early, stop on critical failures, quarantine the rest, and never drop silently.

5. Real-life scenarios

Every answer follows the same shape: situation, what you check first, the fix, and how you prevent it next time. Say this shape aloud in the interview.

A producer team removed a field from the Avro schema on a Kafka topic and consumer jobs crashed in production. What do you do? Senior

Roll the producer back so new messages use the old schema again, then fix the removal in a compatible way. The root cause is a breaking schema change that got through, so I then enforce compatibility in the registry and the producer's CI.

Why this happens. The producer's registry subject was probably on compatibility NONE, or auto-registration let a new schema through without a check, or the producer bypassed the registry. In Avro terms, the removed field had no default, so consumers still using the old reader schema had nothing to fill for it (forward-incompatible). Whatever the cause, the real lesson is that the compatibility gate was not in place.

Order of actions in the first hour (stop the bleeding, then repair).

  1. Roll back the producer deploy, so no new bad messages are written.
  2. Check which consumers fail and why (exception messages like "missing default" or "no field named X"). Stop them from crash-looping, since each restart can retry the same bad record and block a partition (a "poison pill").
  3. Assess the damage in the topic: from which offset do bad-schema messages start, and how many? If consumers can handle both schemas after a quick fix (give the field a default in the reader schema), deploy that and let them continue. Otherwise route bad messages to a dead-letter topic (keep a copy), then skip past them.
  4. Backfill if any messages were skipped: replay from the saved offset after the fix, using idempotent processing to avoid duplicates.
  5. Communicate: which dashboards and tables were stale or wrong, between which times.

The right way to remove a field (an expand and contract migration): step 1, make the field optional with a default in the schema and upgrade producers and consumers; step 2, stop writing it; step 3, once no reader depends on it, remove it. Each step is compatible by itself.

Follow-ups to expect. "How would the registry have stopped it?" With FORWARD or FULL on the subject, removing a field with no default fails at register time (BACKWARD alone would have allowed it; BACKWARD or FULL reject adding a field without a default). "How do you test consumers?" Contract tests that deserialize sample messages of every schema version. "What about the consumers you do not know about?" Use FULL compatibility and a documented deprecation window, and monitor consumer groups to know who is reading.

Situation: consumers fail with a decoding or "missing field" error right after a producer deploy, and messages with the new schema are mixed in the topic with old ones.

Check first: the registry history for the subject (what changed, did the removed field have a default, what compatibility mode was set; NONE would explain how it got through), which consumer groups fail, and how many bad-schema messages exist.

Fix: (1) roll back the producer. (2) Pause stuck consumers; for messages already written, deploy a consumer that handles the new schema or move them to a dead-letter topic after copying them for replay. Do not blindly reset offsets, that loses data. (3) Re-release the change in two steps: make the field optional with a default and upgrade all consumers, then remove it. (4) Replay from the saved offset.

Prevent: BACKWARD or FULL (transitive if you replay) on the subject, a registry compatibility check in the producer's CI, consumer contract tests, and a deprecation process (announce, dual write, remove).

Remember: never remove a field in one step. Make it optional first, upgrade readers, then remove.

After a job retry, the daily revenue is double what the source system says. Find and fix it. Senior

A failed task was retried and appended the rows again, so the job is not idempotent. I would roll the table back to the snapshot before the bad commits, or re-run that day with a partition overwrite from raw data, and then make the job idempotent so it cannot happen again.

The mental model. Revenue exactly doubled, which is a strong clue: the whole day was written twice, not just a few rows. A task partially failing would produce a partial overcount. A full double suggests a complete re-run that appended.

Investigation in order, with the queries.

  1. Confirm the symptom: SELECT sale_date, count(*), sum(amount) FROM sales GROUP BY 1 and compare to the source. Ratio 2.0 means a whole duplicate load.
  2. Prove duplicates: SELECT order_id, count(*) FROM sales WHERE sale_date = '2026-11-17' GROUP BY 1 HAVING count(*) > 1. If rows are exactly identical, it is a double load; if they differ (other timestamp), look for late updates or a join fan-out instead.
  3. Find the cause: orchestrator history (attempt 1 failed or timed out, attempt 2 succeeded), table snapshot history (SELECT * FROM sales.snapshots shows two append commits with the same run id), and the job code (append mode, no key).

Repair options, from least to most invasive.

  • Rollback to the snapshot before the double append (CALL system.rollback_to_snapshot(...)), valid only if nobody else wrote since; otherwise you lose their changes.
  • Re-run the day as a partition overwrite from the raw layer. Safe and clean, assumes raw is intact.
  • Deduplicate in place: write the deduplicated rows to a new table with row_number() over the business key, validate counts and sums against the source, swap, and drop the old.

Then rebuild the downstream tables (marts, caches, exported reports) for that date and notify the people who saw the wrong number, so decisions made from it can be reviewed.

Making it impossible next time. Change the job to overwrite its partition or merge on order_id; pass the logical date as a parameter; add a uniqueness test on the key; add a reconciliation gate (row count and sum versus source within tolerance) that fails before publishing; and avoid blind "retry" on non-idempotent tasks.

What the interviewer wants to hear: that you separate immediate repair from root cause, that you verify against a source of truth, and that you notify consumers.

Situation: a task timed out halfway, the orchestrator retried, and the second attempt appended all rows again.

Check first: compare counts with the source for that date; run SELECT order_id, count(*) ... HAVING count(*) > 1 to confirm exact duplicates; look at the table's snapshot history for two append commits from the same run id.

Fix: on an Iceberg table, rollback_to_snapshot to the one before the bad commits if nothing else has written since, or re-run the day with partition overwrite. If neither works, deduplicate with row_number by business key into a new table, validate totals, then swap. Rebuild downstream tables for the date and tell consumers the numbers were wrong for a period.

Prevent: partition overwrite or MERGE on a key, the logical date as a parameter, a unique-key test, and a reconciliation check (row count and sum versus source) that fails the pipeline before publish.

Remember: retries are normal, so the job must be safe to run twice.

Mobile events arrive up to two days late and your hourly streaming counts keep changing. What do you design? Senior

I run two paths: a streaming job with a short watermark for a fresh but provisional view, and a batch job that recomputes the last few days from the raw table for the final numbers. Every event, including late ones, is kept in the raw layer with both event time and arrival time.

Understand the data first. Mobile devices buffer events when offline and upload later; so the gap between event time and arrival time has a long tail: most events arrive in seconds, some in hours, a few after days. You cannot get both "instant" and "final" for such data, so the design must separate the two.

The design, as a flow.

  1. Ingest everything to a raw table (append only) with event_time, ingest_time, and a unique event id. Late events are not special here: they are simply appended.
  2. Streaming job (fast path): event-time windows with a short watermark (for example 15 minutes). It produces a provisional hourly count for dashboards, available within minutes. Events that arrive after the watermark are not lost: they are already in the raw table.
  3. Batch correction job (accurate path): every hour, recompute the last 3 days of hourly counts from the raw table using event time, and replace those partitions (idempotent overwrite or merge). Run a final recompute after 48 hours or whenever your lateness SLA says data is complete.
  4. Serving table: consumers read the corrected table. The newest hours are labelled "provisional" in the UI because they may still rise.

Why not just a 2-day watermark? The streaming job would hold 2 days of state for every window and key (expensive, slow recovery), and results for any hour would appear only after 2 days. The two-path design gives a fast answer and an eventually correct answer cheaply.

Numbers to measure first. Plot the distribution of (ingest time minus event time): if 95% arrive within 5 minutes and 99.9% within 24 hours, choose a 5 to 15 minute watermark and a recompute window of 2 days. Also agree with the business which reports require exactness (billing) versus approximation (a live dashboard).

Pitfalls. Recompute windows must be larger than the lateness tail or the tail never gets corrected. Be careful with double counting if both paths write to the same table; keep streaming output in a separate provisional table and let the batch job own the final one. Alert on late-event rate, because a sudden jump means an app bug or an outage upstream.

Situation: devices buffer events offline and upload later. A 10-minute watermark drops them; an unbounded one never finalises.

Check first: measure the lateness distribution (what percent arrive within 1 minute, 1 hour, 1 day, 2 days) and ask the business which numbers must be exact and when.

Fix: short watermark (say 15 minutes) for the "fresh, approximate" view; write all events to the raw table; an hourly batch recompute for the last 3 days and a final one after 48 hours, using idempotent partition overwrite or merge. Dashboards read the corrected table and label the newest hours "provisional". Events beyond the cutoff go to a late table, with an alert if their rate is unusual.

Prevent: record event time and ingestion time on every record, and agree a completeness SLA with consumers.

Remember: fast and approximate in streaming, correct in batch, and keep the raw log.

A daily report on an Iceberg table went from 2 minutes to 40 minutes after streaming ingestion was added. What do you check? Senior

Almost certainly small files and metadata growth from frequent streaming commits. I check the table's file and snapshot metadata, compact the hot partitions, rewrite manifests and expire snapshots, then lower the commit frequency and schedule compaction.

Reasoning about the symptom. The query and data volume did not change, only the ingestion style. A big slowdown with identical logic points to overhead rather than compute: the number of files, manifests and snapshots grew. A streaming job committing every 10 seconds produces 8,640 commits a day, each adding at least one small file per partition touched, plus a snapshot and a manifest.

Diagnose with numbers instead of guessing. Iceberg exposes its metadata as tables:

SELECT partition, count(*) AS files, avg(file_size_in_bytes)/1e6 AS avg_mb
FROM prod.orders.files GROUP BY partition ORDER BY files DESC;
SELECT count(*) FROM prod.orders.snapshots;
SELECT count(*) FROM prod.orders.manifests;

Typical bad picture: 30,000 files per day with an average of 2 MB, thousands of snapshots, and thousands of manifests. In the engine UI you will see many short tasks and a long "planning" phase before any data is read.

Fix, in a safe order.

  1. Compact closed partitions first (rewrite_data_files with a target size around 256 to 512 MB, optionally sorted by the filter column). Avoid the partition being written right now to reduce commit conflicts.
  2. rewrite_manifests to reduce the number of manifests.
  3. expire_snapshots with a retention that suits you (for example 3 to 7 days) so old small files are deleted and metadata shrinks. Remove orphan files.
  4. Re-run the report and compare: time, number of tasks, bytes read.

Fix the cause, not just the symptom. Increase the streaming commit interval (for example 2 to 5 minutes), coalesce before writing, use a distribution mode so each task writes few files, and schedule compaction (hourly for the hot partition, daily for the rest). If the report only needs hourly freshness, 10-second commits were never required.

Prevention. Alert on average file size, files per partition, and snapshots count; add a runbook. Also consider merge-on-read delete files if the stream does upserts, since they add their own read cost until compacted.

Situation: the query did not change, only the ingestion: a Flink job now commits every 10 seconds.

Check first: query the metadata tables: file count and average size per partition (expect thousands of files of 1 to 5 MB), the number of snapshots per day, and the number of manifests. The engine UI shows many tiny tasks and long planning time.

Fix: run rewrite_data_files on the affected partitions (old ones, to avoid conflicts with streaming), then rewrite_manifests and expire_snapshots. For the cause, raise the commit interval to a few minutes or stage and merge hourly, and schedule compaction.

Prevent: a layout monitor that alerts when average file size drops below a threshold.

Remember: commit frequency is a cost knob. More commits means more small files.

A user asks to be deleted (GDPR erasure). Their data is in an Iceberg lake with years of history. How do you actually delete it? Senior

A DELETE alone is not enough, because in an immutable table it only hides the rows. I delete the rows, compact so data files are physically rewritten, expire the old snapshots and remove orphans so time travel cannot bring the data back, and then handle every other copy (derived tables, indexes, backups).

Why a plain DELETE is not enough. Iceberg files are immutable. DELETE creates a new snapshot in which the rows are no longer visible, but the old data files still exist and old snapshots still point at them. Anyone with access can run VERSION AS OF and read the "deleted" person. Backups and derived datasets hold copies too. Regulators expect real erasure within a time limit (typically about one month under GDPR; check your legal team).

The sequence of steps, and why each is needed:

  1. Find all the data. Use the PII inventory, the data catalog and lineage to list every table, topic, search index, cache, extract and backup holding this user id. Also decide what must be kept for legal reasons (tax invoices) and anonymise rather than delete those.
  2. Delete the rows in each table: DELETE FROM silver.events WHERE user_id = 'u123'. In copy-on-write, affected files are rewritten without the user. In merge-on-read, delete files merely mask the rows.
  3. Compact (rewrite_data_files with delete files applied) so the physical Parquet files that contained the user are replaced by new ones.
  4. Expire snapshots older than the delete commit, so no snapshot references the old files, then remove orphan files, which physically deletes the original objects. Check also that the object store does not keep versions (S3 versioning) or that lifecycle rules remove them.
  5. Propagate to derived tables (gold aggregates normally do not contain the user, but feature tables or exports do), and to search indexes and caches.
  6. Backups: either they expire within the legal period and you document that, or you restore-and-purge. Write down the policy.
  7. Record proof (what was deleted, when, by whom) without keeping the personal data itself.

Better design for next time. Keep personal data in a small table keyed by a surrogate id; other tables use only the surrogate, so erasure is one delete in one place. Batch requests (run the erasure job daily for all pending users) so compaction cost is shared. Or encrypt per-user data with a per-user key and delete the key (crypto-shredding), which works well for backups and immutable logs.

What an interviewer probes: "what about Kafka topics?" Compacted topics with a tombstone, or short retention, or crypto-shredding; "what about time travel for audits?" That conflicts with erasure, so decide retention up front.

Situation: the user's events, orders and profile are spread across raw, cleaned and gold layers, plus extracts.

Check first: find every place that holds the user id (data catalog, lineage, PII inventory), and check whether the law requires keeping some records, such as invoices, which may need anonymising instead.

Fix: (1) DELETE FROM t WHERE user_id = X on each table: this creates a new snapshot. With copy-on-write the files are rewritten; with merge-on-read only delete files hide the rows. (2) Compact so the data files are rewritten. (3) Expire old snapshots and remove orphan files, since old snapshots still reference the original files. (4) Handle other copies and document backup retention. (5) Keep proof, within the legal deadline.

Prevent: keep PII in a small separate table keyed by a surrogate id, batch deletions into a regular job, or use per-user encryption keys and delete the key.

Watch out: running DELETE and saying "done". The data is still in old snapshots until they are expired.

Remember: delete, compact, expire snapshots, remove orphans. Then the other copies.

CDC events for the same order arrive out of order and the lake table shows an old status. How do you fix it? Senior

Apply changes by source version, not by arrival order. I key the topic by the primary key, dedupe each batch keeping the event with the highest log position, and make the merge conditional so it never moves backwards.

Why this happens. Two updates to the same order (PENDING then SHIPPED) are written in order at the source. Along the way they can be reordered: the topic was not keyed by order id so the updates sit in different partitions and are read by different tasks, or a replay or retry applies an older batch after a newer one. A merge that says "the last row I applied wins" then leaves the older state.

A concrete failure. Events: e1 (lsn 100, PENDING), e2 (lsn 105, SHIPPED). Task 2 processes e2 and writes SHIPPED; task 1, slower, processes e1 and overwrites with PENDING. The lake now disagrees with the source forever, silently.

Fixes in layers:

  1. Keep order at the source: produce the topic keyed by the primary key, so all changes of one order go to one partition, processed by one consumer in order. This alone prevents most cases (CDC tools do this by default).
  2. Never rely on arrival order in the merge. Within each micro-batch, deduplicate by key and keep only the event with the highest version (log position, or commit timestamp with a tie-breaker): row_number() OVER (PARTITION BY order_id ORDER BY lsn DESC) = 1.
  3. Make the merge conditional: WHEN MATCHED AND s.lsn > t.lsn THEN UPDATE. A stale event is then a no-op, whether it is late, duplicated or replayed.
  4. Handle deletes: an old insert arriving after a delete could resurrect a row, so keep a tombstone (soft delete with version) for a retention period.

Repairing existing wrong rows. Detect them by comparing with the source (count of rows per status, or checksums by key range). Replay the raw change events for the affected keys with the version-aware merge, or re-snapshot those keys from the source.

Prevention. Store the source version (lsn or ts) in the target table, add an alert comparing target and source aggregates, and test the pipeline by deliberately shuffling and duplicating input events: the final table must not change.

Situation: the lake shows PENDING while the source says SHIPPED, because two updates were applied in the wrong order (parallel tasks, or a replay).

Check first: is the topic keyed by order id, so all changes for one order sit in one partition in order? Does the merge take whichever row it sees last? Does each event carry a version such as the log position or source timestamp?

Fix: in each batch deduplicate by key, keeping the highest log position (timestamp plus offset as tie-breaker), then MERGE ... WHEN MATCHED AND s.lsn > t.lsn THEN UPDATE. Repair the wrong rows by replaying from raw or re-snapshotting the affected keys.

Prevent: store the source version on every row.

Remember: order by the source version, and never let an older event overwrite a newer one.
