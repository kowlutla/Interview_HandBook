Mental model: the 8 ideas everything hangs on

One line: Kafka is a distributed, replicated, append-only log. Producers append records to the end of a partition. Consumers read at their own pace by remembering an offset. Nothing is removed when it is read, only when retention says so.
  1. It is a log, not a queue. Records are appended and kept. Reading does not delete. Many readers can read the same data independently.
  2. A topic is split into partitions. A partition is one ordered log. Order is guaranteed only inside a partition, never across the whole topic.
  3. The offset is the position. Each record in a partition has a number: 0, 1, 2... A consumer's "progress" is just a stored offset.
  4. Partitions are the unit of parallelism. In one consumer group, a partition is read by at most one consumer at a time. More partitions means more possible parallel consumers.
  5. Replication gives durability. Each partition has a leader and followers on other brokers. The in-sync replica set (ISR) plus acks and min.insync.replicas decide what "safely written" means.
  6. The key chooses the partition. Same key goes to the same partition, so records of one key stay in order.
  7. Delivery guarantees are built by you. Kafka gives at-least-once by default. Exactly-once needs idempotent producers, transactions, and consumers that tolerate duplicates.
  8. Consumers pull. The consumer asks for data, so a slow consumer does not hurt the broker. It just falls behind (lag).

1. Why Kafka, the log, topics, partitions and offsets

What is Kafka and what problem does it solve? Basic

Kafka is a distributed event streaming platform. It stores streams of records in a replicated, append-only log, so many programs can write to it and many others can read from it later, each at its own speed. It solves the tangle of point-to-point connections between systems: a producer writes once to a topic, and any number of consumers pick it up.

What it is, from scratch. Think of Kafka as a very large, very durable, shared notebook that many programs can write into and many other programs can read from. Each entry is a record (also called an event or message): a key, a value, a timestamp and optional headers. Records are grouped into named topics such as orders or page-views, and each topic is stored on a cluster of servers called brokers, with copies on several brokers so one machine failing does not lose data.

Why it exists. Imagine five systems that each need data from each of four other systems. Wiring them point to point gives up to 20 custom integrations, each with its own failure handling, speed mismatch and format. If the receiver is down, the sender must buffer or drop the data. Kafka puts one durable log in the middle: every producer writes once to a topic, every consumer reads what it needs, and neither side knows or cares about the other. A slow consumer simply falls behind without slowing the producer, and a new consumer can be added next month and read history from the beginning.

A tiny walk-through.

  1. The checkout service appends OrderPlaced{orderId=17} to the topic orders. It is now stored, replicated and given an offset.
  2. The billing service reads it and charges the card. The search service reads the same record and updates its index. A new analytics team reads the same topic next week, starting from offset 0.
  3. Nobody had to change the checkout service for any of this.

Typical uses. Event-driven microservices, data pipelines (database to warehouse), change data capture, stream processing (counts, joins, fraud rules), log and metric collection, and audit trails. Strengths: high throughput (millions of records per second across a cluster), durability, replay, ordering per key, and loose coupling between teams.

Limits to say out loud. Kafka is not a database: you cannot query by a field, run a join or update one record in place. It is not a task queue with per-message retry, delay or priority. And a small team needs either a managed offering or platform support to run it. An interviewer often probes "so why not just use a database table as the queue?" The answer is replay, fan-out to many independent readers, throughput, and not putting load on your main database.

Remember: Kafka is a durable, replayable, replicated log that decouples producers from consumers. It is a pipe and a history, not a query store.

Why is Kafka a log and not a queue? Intermediate

A classic queue tracks each message and deletes it once a consumer acknowledges it. Kafka does not track messages at all. It only appends to a log, and each consumer remembers one number, its offset. That makes the broker cheap and fast, and gives replay, many independent readers, and new consumers that can start from the beginning.

The two designs side by side. A classic queue (RabbitMQ, SQS) is a to-do list: the broker remembers every message, hands it to one consumer, waits for an acknowledgement and then deletes it. The broker is doing bookkeeping per message and per consumer. A log is a ledger: the broker only appends new entries at the end and numbers them 0, 1, 2 and so on. Each consumer keeps one number, "the next entry I want", which is its offset. The broker never tracks who has read what.

Why that is a big deal. Because reading changes nothing on the broker:

  • Many independent readers. Billing and search read the same records, each at its own speed, without affecting each other.
  • Replay. A bug in a consumer? Fix it, move the offset back two hours and process again. In a queue the messages are gone.
  • New consumers get history. A new service starts at offset 0 and catches up.
  • Speed. Appending to the end of a file and reading sequentially is the pattern disks and the OS page cache handle best, and no per-message state means the broker does very little work per record.

A small timeline. The log holds offsets 0 to 9. Consumer X is at 3 and Consumer Y is at 7. Producer appends offset 10. X reads 3, 4, 5 and commits offset 6 (next to read). Y is unaffected. Nothing was deleted by either read; old records leave only when retention (time or size) or compaction removes them.

The price you pay. You cannot delete or skip one message in the middle, there is no per-message priority or routing, and one slow or failing record blocks the records behind it in the same partition. Those are exactly the things queues are good at, which is why the choice depends on the workload (see the Kafka vs RabbitMQ question).

Remember: a queue deletes on read and tracks each message; a log keeps data and each consumer just moves its own offset.

What are topics and partitions, and why do partitions exist? Basic

A topic is a named stream of records, like "orders". It is split into partitions, and each partition is one ordered log living on one broker (with copies on others). Partitions exist for scale, because one machine cannot hold or serve everything, and for parallelism, because each partition can be read by one consumer in a group. The cost is that Kafka only promises order inside a partition.

Topic. A topic is a named category of records, like a table name without the query features. Producers write to a topic; consumers subscribe to it.

Why one log per topic is not enough. A single log lives on one machine. That machine limits how much you can store, how fast you can write, and how many consumers can share the work (because within a group, only one consumer can read a single log in order). So Kafka cuts a topic into partitions. Each partition is its own independent, ordered, append-only log with its own offsets starting at 0. Different partitions of the same topic can sit on different brokers, so storage and traffic spread across the cluster.

How records land in partitions. The producer chooses. With a key, hash(key) mod partitionCount decides, so all records for orderId=17 go to the same partition and stay in order. Without a key, records are spread evenly across partitions.

# create a topic with 6 partitions, each stored on 3 brokers
kafka-topics.sh --bootstrap-server b1:9092 --create --topic orders \
  --partitions 6 --replication-factor 3

What this buys and costs.

  • Parallelism: 6 partitions allow up to 6 consumers in one group working at once. A seventh would sit idle.
  • Order only inside a partition. OrderPlaced in partition 2 and OrderPlaced in partition 5 have no guaranteed order relative to each other. That is why you choose the key to match the entity whose order matters.
  • Hard to change later. You can add partitions but never remove them, and adding them changes where keys go (see the partition-count questions in section 7). num.partitions defaults to 1 on a plain install, so set it on purpose.

Analogy. A topic is a motorway; partitions are lanes. More lanes carry more traffic, but cars in different lanes have no fixed order relative to each other.

What an interviewer probes next: "how many partitions?" (throughput divided by per-consumer speed, plus headroom) and "what if I need global order?" (one partition, which caps throughput).

Remember: partition = one ordered log = one unit of parallelism. Order exists only inside it, so choose the key to match the entity whose order matters.

What is an offset, and who owns it? Basic

An offset is the sequence number of a record inside one partition, assigned by the broker when it appends the record. The real address of a record is topic, partition, offset. The consumer group owns its progress: the committed offset, which is the offset of the next record it will read.

What it is. An offset is a record's sequence number inside one partition: the first record is 0, the next 1, and so on. The broker assigns it when it appends the record. So a record is uniquely identified by the triple topic, partition, offset; the offset alone means nothing, because every partition has its own offset 0.

Two different offsets people confuse.

  • The record's offset, fixed forever by the broker.
  • The group's committed offset, which is a bookmark: "this group has finished everything before this number; start from here." By convention it is the offset of the next record to read, so after processing offset 41 you commit 42.

Where the bookmark lives. Kafka stores committed offsets in an internal compacted topic named __consumer_offsets, keyed by group, topic and partition. Because the bookmark belongs to the group and not to one consumer process, when a consumer dies, another one in the group takes over its partitions and continues at the last committed offset. Nothing about the consumer's own memory matters.

Mini example. Group billing has committed offset 1500 on orders-0, and the log end is 1520. Lag is 20. The consumer crashes after processing 1505 but before committing again. The replacement restarts at 1500 and re-reads 1500 to 1505, which is why at-least-once needs idempotent handling.

Gotchas.

  • Offsets are never reused but can have gaps: transaction markers and log compaction leave holes, so never assume "next offset = previous + 1" for validation.
  • If a group has no valid committed offset (new group, or it expired or was deleted by retention), auto.offset.reset decides where to start (see that question).
  • Offsets are per partition, so they cannot be used to order records across partitions.

Remember: offset = position in one partition. The group stores "next offset to read" in __consumer_offsets, so any replacement consumer can resume.

Why is Kafka fast even though it writes to disk? Intermediate

Four things. It only appends sequentially, which is much faster than random disk access. It leans on the operating system page cache, so recent data is served from memory. It batches records and compresses whole batches. And for plain reads it can use zero-copy, sending data from the page cache to the network socket without copying it through the application.

The surprise. People assume "writes to disk" means slow. That is true for random disk access, but Kafka designs everything around the access pattern disks and operating systems are best at.

  1. Sequential I/O. A partition is an append-only file, so writes always go to the end and reads usually go forward. Sequential disk throughput is orders of magnitude better than random, and even competitive with network speeds.
  2. OS page cache. Kafka does not keep its own big cache in the JVM heap. It writes into the operating system's page cache and lets the OS flush to disk. Recent data that consumers read is typically still in memory, so most reads never touch the disk. It also avoids Java garbage-collection pressure, and the cache survives a broker process restart.
  3. Batching and compression. Producers send batches, brokers store the batch as is, and consumers fetch batches. One network round trip and one disk write cover hundreds of records, and compression (lz4, zstd, snappy, gzip) works on the whole batch so it compresses much better than single records.
  4. Zero-copy. For a plain (non-TLS) fetch the broker uses the sendfile system call: bytes go from the page cache straight to the network card, skipping the copy into the application and back into the kernel.

"But is it durable if fsync is not called per message?" Durability comes from replication, not from forcing every write to disk. With replication factor 3 and acks=all, the record sits in the memory of at least two brokers before the producer sees success. A single broker crash loses nothing that was acknowledged. Kafka can be told to fsync more often, but that is rarely needed and costs throughput.

Trade-off to mention. Zero-copy does not work when TLS is on, because the data must be pulled into user space to be encrypted. So encryption in transit costs some broker throughput, and the usual answer is to accept it or terminate TLS carefully.

What this means for you as a developer: producing in bigger batches (linger.ms, batch.size) and consuming sequentially is the fast path; frequent tiny sends and seeking all over the place are the slow path.

Remember: sequential appends + OS page cache + batching and compression + zero-copy. Durability comes from replication, not per-message fsync.

How does retention work, and why was my data not deleted after 7 days? Basic

Retention is a topic setting, not tied to consumption. By default Kafka keeps records for 7 days (retention.ms) and optionally up to a size per partition (retention.bytes), whether or not anyone read them. Whichever limit is hit first causes old data to be deleted. Reading never deletes anything.

The key idea. Kafka decides what to delete based only on age and size, never on whether someone has read the data. That is what lets different groups read at different speeds, and lets you replay. The defaults are time-based: retention.ms is 7 days (log.retention.hours=168 at the broker). You may also set retention.bytes, a size cap per partition (default unlimited). If both are set, whichever is exceeded first triggers deletion.

Why "my data is still there after 7 days" happens. Deletion works on whole segment files, not records. A partition on disk is a folder of segment files, for example 00000000000000000000.log. The newest one is the active segment and takes writes. Kafka never deletes the active segment, and it deletes an older segment only when the newest record in it is older than the retention time. A segment rolls when it reaches segment.bytes (default 1 GB) or segment.ms (default 7 days). So on a quiet topic, the active segment may hold data older than 7 days for a long time, and a closed segment is kept until its newest record expires. A background check runs every few minutes (log.retention.check.interval.ms), so deletion is not instant either.

Example. Topic gets 10 MB a day. Segment size 1 GB means a segment takes 100 days to fill, but segment.ms rolls it at 7 days. The first segment closes on day 7, and then it may only be deleted once its newest record is 7 days old, so roughly day 14. Data can live nearly double the retention on a slow topic. Lower segment.ms if you need tighter expiry (for example for data-protection rules).

# keep 3 days or 50 GB per partition, whichever first
kafka-configs.sh --bootstrap-server b1:9092 --alter --entity-type topics \
  --entity-name orders --add-config retention.ms=259200000,retention.bytes=53687091200

Cleanup policy. cleanup.policy=delete is the default (time and size), compact keeps the latest value per key, and compact,delete does both.

Why consumers care. If a group is down longer than retention, the offsets it needs are gone. On restart it triggers auto.offset.reset and, with the default latest, silently skips the gap. Set retention longer than your worst outage plus time to repair, and alert when lag age gets close to retention.

Remember: retention is by time or size, in whole segments, and independent of who has read what. Active segments are never deleted.

2. Replication, ISR and durability

How does replication work in Kafka? Intermediate

Each partition has one leader broker and some follower brokers. All reads and writes go to the leader. Followers copy the data by sending fetch requests to the leader, just like consumers do. A record counts as committed once every in-sync replica has it, and consumers only see committed records, up to the high watermark.

The goal. A single disk or broker will eventually fail. Replication keeps several copies of each partition on different brokers so a failure does not lose data or stop service. The replication factor (RF) is the number of copies including the leader; 3 is the usual production value.

Roles. For each partition one replica is the leader and the rest are followers. All produce and consume requests for that partition go to the leader (by default). Followers do not serve clients; they continuously send fetch requests to the leader, exactly like a consumer, and append what they receive to their own log. Leaders are spread over brokers, so every broker leads some partitions and follows others, which balances load.

Step by step for one write.

  1. The producer sends a batch to the leader of partition 0 (it learned who that is from cluster metadata).
  2. The leader appends it at offsets 6 and 7 in its local log.
  3. Followers fetch, append 6 and 7, and their next fetch tells the leader how far they have got.
  4. When every in-sync replica has offset 7, the leader advances the high watermark to 8. The records are now committed.
  5. With acks=all the producer gets its success only now. Consumers can read only up to the high watermark.

Why consumers stop at the high watermark. If a consumer could read offset 7 while only the leader had it, and the leader then died, the new leader would not have offset 7. The consumer would have seen a record that "never existed". Capping reads at the watermark guarantees every record a consumer sees survives a leader failure.

How clients find the leader. You give the client a few bootstrap addresses. It asks any broker for metadata (topic, partition, leader, address), caches it, and then connects straight to the right leaders. When leadership changes, the client gets a "not leader" error, refreshes metadata and retries.

Two follow-ups. "Do followers help read performance?" Not by default; since Kafka 2.4 a consumer can opt to read from the closest follower (client.rack and a rack-aware replica selector), mainly to save cross-zone traffic. "What is the cost?" RF 3 means three times the storage and the replication network traffic.

Remember: followers pull from the leader; committed means present on all in-sync replicas; consumers read only below the high watermark.

What is the ISR, and when does a replica drop out of it? Intermediate

The ISR is the set of in-sync replicas: the leader plus the followers that are keeping up. A follower is dropped when it has not fetched up to the leader's end within replica.lag.time.max.ms (default 30 seconds), for example because it is slow, paused in a long garbage collection, or its broker is down. It is added back when it catches up.

What it is. For each partition the in-sync replica set (ISR) is the list of replicas, the leader included, that are fully caught up "enough". The leader maintains the list. Being in the ISR is the condition for (a) counting toward a commit, and (b) being allowed to become leader.

When a replica leaves. If a follower has not fetched up to the leader's log end within replica.lag.time.max.ms (default 30 seconds), the leader removes it from the ISR. Typical reasons: the broker crashed, a long GC or disk stall, a slow or saturated network, or a burst of writes the follower cannot keep up with. When the follower catches up it rejoins automatically. The ISR therefore shrinks and expands by itself, and that is normal during restarts.

A timeline with RF=3, min.insync.replicas=2.

  1. ISR = {1, 2, 3}. Writes with acks=all wait for all three.
  2. Broker 3 stalls for 40 s. The leader drops it: ISR = {1, 2}. Writes now wait for only two brokers, so they still succeed (two is the minimum).
  3. Broker 2 also fails: ISR = {1}. That is below the minimum, so the broker rejects writes with NotEnoughReplicas rather than accept data stored on only one machine.
  4. Brokers 2 and 3 return, catch up and rejoin. Writes resume.

Why it matters. acks=all waits for the current ISR, not for all replicas. If the ISR is just the leader, acks=all is as weak as acks=1. That is the reason min.insync.replicas exists. And since only ISR members hold every committed record, only they are eligible to lead after a failure (unless unclean election is turned on).

Monitoring. A partition whose ISR is smaller than its replication factor is under-replicated, and one below min.insync.replicas is "under min ISR". Both are standard alerts. A frequently flapping ISR points to slow disks, network trouble or GC.

Remember: ISR = leader plus followers that are caught up. It shrinks and grows by itself, and acks=all only waits for whoever is in it.

Explain acks and min.insync.replicas together. How do you get no data loss? Senior

I use replication factor 3, min.insync.replicas=2 and producer acks=all. acks says when the broker answers success; min.insync.replicas says the smallest ISR size for which a write is accepted. With these settings a write is on at least two brokers before I get success, I survive one broker loss with no data loss, and writes stop (with an error) rather than being "safe" on one broker.

Two settings, two different jobs. acks is set on the producer and says how many confirmations the producer waits for before treating a send as successful. min.insync.replicas (min ISR) is set on the topic or broker and says the smallest ISR size for which the broker will accept an acks=all write at all. You need both, because acks=all alone only means "everyone currently in the ISR", and the ISR can shrink to one.

Worked example, RF=3, min ISR=2, acks=all.

  • All healthy: the write is on 3 brokers before success. Losing any one broker loses nothing.
  • One broker down: ISR = 2, which meets the minimum, so writes continue and are on 2 brokers. No acknowledged record sits on a single machine, though one more failure would now stop writes.
  • Two brokers down: ISR = 1, below the minimum. The broker returns NotEnoughReplicas. The producer retries until delivery.timeout.ms and then reports failure to my callback. I lose availability for writes but no data.
# topic level
kafka-configs.sh --bootstrap-server b1:9092 --alter --entity-type topics \
  --entity-name payments --add-config min.insync.replicas=2

# producer
acks=all
enable.idempotence=true
delivery.timeout.ms=120000

The rest of the no-loss recipe. unclean.leader.election.enable=false (default), idempotence on so retries do not duplicate, a send callback that handles failures, and consumers that commit after processing. Spread replicas across racks or availability zones (broker.rack) so one zone failure does not break min ISR.

Choosing min ISR. RF 3 with min ISR 2 is the standard balance: tolerates one broker down for both reads and writes. Min ISR equal to RF means any single broker failure halts writes, which is rarely what you want. Min ISR 1 means acks=all can silently degrade to one copy.

Watch out: acks=all means all in-sync replicas, not all replicas. min.insync.replicas defaults to 1, so if you do not set it, acks=all can end up on one broker.

Remember: RF 3, min ISR 2, acks=all. acks says who must confirm, min ISR says how few confirmers is acceptable.

What happens when a partition leader broker dies? Intermediate

The cluster controller notices the broker is gone and picks a new leader for each of its partitions from the ISR, then publishes the new metadata. Clients get a "not leader" error or a timeout, refresh metadata and retry against the new leader, usually within a few seconds. Because the new leader was in the ISR, no committed data is lost.

What happens, step by step.

  1. Broker 2, which leads partitions orders-0 and orders-4, crashes. Its session with the cluster controller expires (in KRaft mode the controller is a quorum of controller nodes; formerly it was a ZooKeeper-elected broker).
  2. The controller marks broker 2 dead and, for each partition it led, chooses a new leader from that partition's ISR, normally the first live ISR member in the replica list.
  3. The controller writes the new leadership to the cluster metadata and tells the affected brokers. The new leader starts serving.
  4. Clients that were talking to broker 2 get a connection error or a NotLeaderOrFollower error. They refresh metadata, find the new leader and retry. This usually takes from under a second to a few seconds.

Why no committed data is lost. A record is committed only when all ISR members have it, so every ISR member has all committed records, and any of them can be the new leader. Records that were on the old leader only (not yet committed, so never acknowledged to an acks=all producer) are lost, and the producer simply retries them. With the idempotent producer the retry does not create duplicates.

When the old broker returns. It rejoins as a follower, truncates any log beyond what the new leader has (using leader epochs to find the right point), catches up, and re-enters the ISR. Optionally, preferred leader election moves leadership back to the original broker later to rebalance load (auto.leader.rebalance.enable).

If the ISR is empty (all in-sync replicas are down), the partition is offline and produce/consume fail until one returns, unless unclean election is allowed.

What you need to do in the application. Make sure the client survives the failover window: keep delivery.timeout.ms well above it (default 2 minutes is fine), do not set retries=0, and handle callback errors. On the consumer side the same refresh happens automatically, and a brief pause in fetching is normal.

Remember: the new leader comes from the ISR so committed data survives; clients refresh metadata and retry, with idempotence preventing duplicates.

What is unclean leader election, and when would you allow it? Senior

It lets an out-of-sync follower become leader when no in-sync replica is alive. The partition comes back immediately, but records the stale replica did not have are lost. It is off by default. I keep it off for payments, orders and audit data and accept downtime, and consider it only for data like metrics where freshness beats completeness.

The situation it addresses. Normally the new leader must come from the ISR. But suppose every in-sync replica is gone (for example the leader and the only caught-up follower both died, and a third replica that had fallen behind is alive). The partition now has no eligible leader and is offline. Kafka has to pick: wait for an in-sync replica to come back (consistent but unavailable), or promote the stale replica (available but lossy).

What unclean election does. With unclean.leader.election.enable=true the controller promotes the stale replica. Example: the old leader had offsets 0 to 100 committed. The stale follower had only 0 to 80. After the unclean election, the partition's truth is "0 to 80". Offsets 81 to 100 are gone, and new records are written with offsets starting at 81. When the old replicas return they have to truncate their logs to match. Consumers that already read up to 100 might see offsets reused with different content, which is confusing for anything stateful.

false (default)Partition stays offline; no lossPayments, orders, audit, anything where loss is worse than downtime

It is the CAP trade-off in one flag. Consistency (no loss) versus availability (keep serving). It can be set per topic, so you can be strict for payments and lenient for metrics on the same cluster.

The classic mistake. Turning it on in the middle of an incident to "get the partition back". It works, and it silently loses data you cannot easily identify later. Prefer restoring the missing broker (even its disk) when the data matters; if you must enable it, do it deliberately, note the time window, and reconcile with the source system afterwards.

Remember: unclean election trades committed data for availability. Default is off; keep it off for anything important.

3. Producers: batching, keys, idempotence, ordering

What happens inside the producer when you call send()? Intermediate

send() does not write to the network. It serializes the key and value, picks a partition, and puts the record into a per-partition batch in a memory buffer. A background sender thread later groups ready batches per broker and sends them. When the broker answers, the returned future completes and my callback runs. So send is asynchronous and a crash right after it returns can lose buffered records.

The surprise for beginners. producer.send(record) returns almost immediately and does not mean the record reached Kafka. It only hands the record to a buffer inside the client. Network work happens on a separate thread. Understanding this explains most producer settings and most "lost message" bugs.

What happens, in order.

  1. Serialize the key and value to bytes (String, JSON, Avro...). A failure here throws straight to the caller.
  2. Choose the partition: explicit partition, else hash of the key, else the sticky spread for null keys. This needs cluster metadata (topic's partitions and leaders), fetched on first use and refreshed on errors.
  3. Append to a batch for that partition in the record accumulator (a memory pool of buffer.memory, default 32 MB). Records for one partition share a batch.
  4. The sender thread loops: it finds batches that are full (batch.size, default 16 KB) or have waited linger.ms, groups all ready batches that go to the same broker into one request, and sends it. Up to max.in.flight.requests.per.connection (5) requests can be outstanding per broker.
  5. The broker replies. The future returned by send() completes, and the callback runs on the producer's I/O thread (so keep callbacks short).

Consequences to remember.

  • A crash after send() returns but before the batch is sent loses the record. Call flush() (wait for everything buffered) or close() before exiting.
  • If the buffer is full because brokers are slower than you produce, send() blocks up to max.block.ms (60 s) and then throws. That is natural backpressure.
  • Calling send(...).get() makes it synchronous: simple but one record per round trip, so throughput collapses. Use it only for rare, critical sends.
  • Always give a callback (or check the future); otherwise failures after the delivery timeout are invisible.

Probe: "does send guarantee ordering?" Only for records to the same partition, and only with idempotence (or in-flight set to 1) when retries happen.

Remember: send() = buffer, not network. Always handle the callback and flush on exit.

How do batch.size, linger.ms and compression affect throughput and latency? Intermediate

Bigger batches mean fewer requests and better compression, so higher throughput, but each record may wait a little longer. linger.ms is how long the sender waits for a batch to fill before sending it anyway. Setting it to about 5 to 20 ms with a larger batch.size (64 KB or more) and lz4 or zstd compression usually gives a big throughput gain for a few milliseconds of latency.

The core trade-off. Each network request has a fixed overhead (headers, round trip, broker request handling, disk write). Sending one small record per request wastes it. Sending 500 records in one request spreads the overhead and lets compression see more data. The price is that early records wait for the batch to fill.

The three knobs.

  • batch.size (default 16 KB): the maximum size of one batch per partition. It is an upper bound, not a wait target. Raising it to 64 to 256 KB helps when traffic is high.
  • linger.ms: how long the sender may hold a not-yet-full batch hoping for more records. 0 means send as soon as possible. This is the default in Kafka 3.x; I believe the default became 5 from 4.0, so check your version.
  • compression.type: none (default), gzip, snappy, lz4, zstd. The producer compresses a whole batch; the broker stores it compressed (by default) and the consumer decompresses.

Numbers example. 10,000 small records per second spread over 10 partitions: about 1,000 records per partition per second, so about 1 per millisecond per partition. With linger.ms=0 each request may carry 1 to 2 records. With linger.ms=10 each batch carries about 10 records, so there are roughly 10 times fewer requests, the broker CPU drops, and with JSON compressing 3 to 5 times the network volume falls too. Cost: up to 10 ms extra latency per record.

A broker configured with a different compression.type than the producer will recompress, which costs CPU, so leave the topic on producer.

Pitfalls. Tuning linger.ms when records are already arriving fast changes little; it matters when traffic is light and bursty. Many partitions dilute batches (batches are per partition), so very high partition counts can reduce batching efficiency. Measure with the producer's batch-size-avg, records-per-request-avg and request-latency-avg metrics.

Remember: a few ms of linger + bigger batches + lz4/zstd = throughput; linger 0 = lowest latency. Batching is per partition.

How does a producer choose the partition? Basic

If I set a partition on the record, that is used. If the record has a key, the default partitioner hashes the key bytes (murmur2) and takes it modulo the partition count, so the same key always goes to the same partition. With no key, the producer spreads records across partitions in a "sticky" way: it fills a batch for one partition, then moves to the next.

The rules, in order.

  1. If the record names a partition explicitly, that partition is used.
  2. Else, if the record has a key, the default partitioner computes murmur2(keyBytes) mod numPartitions. The same key always produces the same partition as long as the partition count does not change.
  3. Else (null key), the producer uses sticky partitioning (Kafka 2.4 and later; reworked in 3.3): it keeps filling one batch for one partition, and switches to another partition when that batch is sent. This gives full batches and, over time, an even spread. Older clients did strict round robin, which produced many tiny batches.

What the key is for. It does two jobs. First, ordering and grouping: all events of one entity (an order, an account) go to one partition and stay in order, and the same consumer sees them. This also lets a consumer keep per-key state in memory. Second, identity for compacted topics. A key therefore should be the identifier of the thing whose order matters, not a random value, and should have high cardinality (many distinct values) so partitions fill evenly.

A custom partitioner implements Partitioner (partition(topic, key, keyBytes, value, valueBytes, cluster)). Uses: send VIP tenants to a dedicated partition, spread one huge tenant over several partitions by hashing a sub-key, or keep related keys together. It must be deterministic and fast, and everyone producing to the topic must use the same logic, otherwise the same key lands in different partitions.

Things that go wrong.

  • Adding partitions changes mod N, so existing keys move and per-key order breaks across the change.
  • Skewed keys (one tenant dominates) create hot partitions.
  • Different languages hash differently. A Java producer and a librdkafka (C, Python, Go) producer can put the same key in different partitions unless the non-Java one is set to a murmur2-compatible partitioner (murmur2_random). Mixed producers on one topic is a real source of broken ordering.
  • A key you do not need adds hot-spot risk. For independent events use a null key.

Remember: hash(key) mod partitions. Same key, same partition, same order. No key, even spread. Changing the partition count changes the mapping.

What is an idempotent producer, and what does it protect against? Senior

It protects against duplicates caused by the producer's own retries. If a batch is written but the acknowledgement is lost, the producer retries, and without idempotence the batch is stored twice. With enable.idempotence=true each batch carries a producer id and a sequence number per partition, and the broker drops a batch it has already stored while still acknowledging it. It also stops retries from reordering records.

The problem. Suppose the producer sends a batch, the broker writes it and replicates it, but the acknowledgement is lost on the network or the leader fails right after writing. The producer sees a timeout and, being careful, retries. Now the batch is stored twice. Another variant: batch 1 fails, batch 2 succeeds, batch 1 is retried and lands after batch 2, so order is wrong.

How idempotence works.

  1. When the producer starts, the broker gives it a unique producer id (PID) and an epoch.
  2. For each partition the producer numbers its batches with a growing sequence number (0, 1, 2...).
  3. The broker remembers, per PID and partition, the last sequence numbers it accepted. If a batch arrives that it has already stored, it does not append it again but still answers success. If a batch arrives with a gap (sequence 5 when it expected 3), it rejects it with OutOfOrderSequence so ordering is never silently broken.

Timeline. The producer sends batch seq=7. The broker appends it and the ack is lost. The producer retries seq=7. The broker sees "already have 7", skips the append and returns success. The log has the batch once.

Setup. enable.idempotence=true is the default since Kafka 3.0. It requires acks=all, retries above 0 and max.in.flight.requests.per.connection of 5 or less. If you set an incompatible value explicitly, the client throws a configuration error (or, in old versions, silently disables idempotence). The cost is a few bytes per batch and a bit of broker memory for tracking.

What it does not protect against.

  • A restart of the application. A new producer instance gets a new PID, and the broker cannot tell that a re-sent record is the same business event. Transactions with a stable transactional.id solve this for Kafka-to-Kafka flows.
  • Your own double sends. If code publishes OrderPlaced twice, that is two records with different sequence numbers.
  • Multiple partitions or topics atomically. It guarantees per partition only.
  • Consumer-side duplicates. Those come from re-reading after a crash before commit.

So the clean way to say it: idempotence gives "exactly once per producer session per partition" for the append, not exactly-once for your business event.

Watch out: idempotence is not end-to-end exactly-once. It only removes duplicates and reordering caused by the producer's own retries.

Remember: producer id + per-partition sequence numbers let the broker drop retry duplicates. It covers one producer session and one partition, nothing more.

Does retrying a failed send break ordering? What about max.in.flight.requests? Senior

Without idempotence, yes: if batch 1 fails and batch 2 succeeds, batch 1 is retried and lands after batch 2. With the idempotent producer, no. The broker checks sequence numbers and rejects out-of-order batches, so order within a partition is kept even with up to 5 requests in flight.

The failure scenario. The producer has two batches for the same partition in flight at once (allowed when max.in.flight.requests.per.connection is above 1). Batch A fails because of a transient network error; batch B succeeds. The producer retries A, which is now appended after B. The log order is B, A, though the application sent A, B. That is reordering caused by retries.

The old fix and its price. Set max.in.flight.requests.per.connection=1. Only one request is outstanding per broker, so a retry always goes before the next batch. Order is preserved but throughput drops sharply because the producer waits for each response before sending the next batch.

The modern fix. With enable.idempotence=true, each batch has a sequence number per partition. If B arrives before the retried A, the broker sees a gap, rejects B with an out-of-order error, and the producer retries both in the correct order. So order is preserved even with up to 5 requests in flight, and you keep the throughput. This is why idempotence is on by default.

Also needed for end-to-end order. The same key (so the same partition), and a single producer instance (or one writer) per key. Two producers or two services writing events for the same entity cannot be ordered by Kafka relative to each other; only their arrival order at the broker counts.

Another subtle point. Order across a producer restart is the application's concern: unsent buffered records are lost on a crash, and sequence numbers restart. And if you catch an exception and resend manually from your own code, you bypass the idempotence guarantees and can reorder yourself.

Remember: idempotence on + in-flight at most 5 = ordered and no duplicates under retries. Without idempotence you need in-flight 1.

Which producer errors are retried, and what do retries and delivery.timeout.ms do? Intermediate

The producer retries temporary errors by itself: leader change, network failure, NotEnoughReplicas, request timeout. It does not retry permanent ones: record too large, serialization failure, authorization failure. The real limit is delivery.timeout.ms (default 2 minutes), the total time from send() until success or failure is reported. retries defaults to a huge number, so time, not count, ends it.

Retriable versus non-retriable. The client classifies errors. Retriable errors are temporary: NotLeaderOrFollower (leader moved), NetworkException, TimeoutException, NotEnoughReplicas, LeaderNotAvailable. The producer retries them by itself. Non-retriable errors will fail again no matter what: RecordTooLargeException, SerializationException, TopicAuthorizationException, InvalidTopicException. These go to your callback immediately.

Which timers control retrying.

  • retries: defaults to a very large number (2147483647). Do not tune this; bound the time instead.
  • delivery.timeout.ms (default 120000): the upper bound on the whole send, from the call to send() until success or failure is reported. It includes batching wait (linger.ms), all retries and the waits between them. It must be at least linger.ms + request.timeout.ms.
  • request.timeout.ms (default 30000): how long to wait for one request's response before considering it failed and retrying.
  • retry.backoff.ms (default 100): the pause between tries (newer clients also have a max backoff).

Timeline for a leader failover. t=0 send; t=1 s the leader dies, response never arrives; at the request timeout (or sooner on connection loss) the producer refreshes metadata, finds the new leader, and resends; t=5 s success. The callback sees only success. If the cluster was unreachable for more than two minutes, the callback receives a TimeoutException and the record is gone from the producer's buffer.

What your code must do on failure. Log with the key and topic, increment a metric, and decide: fail the user request, park the event in an outbox table for later, or alert. Never ignore it. Also remember send() itself can throw synchronously (serialization errors, a full buffer after max.block.ms, metadata timeout), so a callback is not the only place to catch problems.

producer.send(record, (meta, ex) -> {
    if (ex != null) {
        log.error("send failed key={}", record.key(), ex);
        // store in outbox / alert / fail the request
    } else {
        log.debug("sent to {}-{}@{}", meta.topic(), meta.partition(), meta.offset());
    }
});

Remember: temporary errors retry until delivery.timeout.ms; permanent ones fail at once; always check the callback.

Which producer settings would you set for a reliable, fast service? Intermediate

For reliability: acks=all, enable.idempotence=true, a topic with replication factor 3 and min.insync.replicas=2, default retries with a clear delivery.timeout.ms, and a send callback that handles errors. For throughput: linger.ms 5 to 20, batch.size 64 to 256 KB, and compression.type of lz4 or zstd.

Think in two groups: safety and speed. They are mostly independent, so you can have both.

Safety (no acknowledged loss, no duplicates from retries).

  • acks=all plus topic settings replication factor 3 and min.insync.replicas=2 (the real durability guarantee lives on the topic, not only in the producer).
  • enable.idempotence=true (default in current clients).
  • Leave retries at its default and bound time with delivery.timeout.ms (default 120 s). Raise it if your failovers take long, lower it if the caller cannot wait.
  • A callback that handles failures; flush() or close() on shutdown.

Speed.

  • linger.ms 5 to 20 and batch.size 64 to 256 KB.
  • compression.type of lz4 (cheap CPU) or zstd (best ratio).
  • Reuse one KafkaProducer per application; it is thread-safe and expensive to create. Creating a producer per request is a classic performance bug.

Housekeeping. Set client.id so broker logs, quotas and metrics identify your service. Check max.request.size (default 1 MB) against your biggest record. Leave buffer.memory (32 MB) alone until you see TimeoutException: Failed to allocate memory within max.block.ms, which means you produce faster than the brokers accept, and the fix is usually more batching or more brokers, not just a larger buffer.

Method. Start from these, load test with your real record size, and change one setting at a time while watching the producer metrics (record-send-rate, request-latency-avg, batch-size-avg, buffer-available-bytes). Settings that look good on a laptop with one broker often behave differently on a replicated cluster.

Remember: safe = acks=all + idempotence + RF3/min ISR 2 + callback. Fast = linger + batch + compression + one shared producer.

4. Consumers, consumer groups, rebalancing and offset commits

What is a consumer group and how are partitions assigned? Basic

A consumer group is a set of consumers sharing one group.id that split a topic's partitions between them. Each partition is owned by exactly one consumer in the group at a time. With 6 partitions and 3 consumers, each gets 2; with 8 consumers, 2 sit idle. So the partition count is the upper limit of parallelism. Different groups are independent and each gets every record.

The problem a group solves. One consumer cannot keep up with a busy topic, so you want several instances to share the work. But two instances reading the same partition would process records twice, and nobody would know who owns what. The consumer group is Kafka's answer: all instances with the same group.id are treated as one logical subscriber, and the cluster splits the topic's partitions among them so that each partition has exactly one owner in the group at any moment.

Example. Topic orders has 6 partitions, group billing.

  • 1 consumer: it reads all 6.
  • 3 consumers: 2 partitions each.
  • 6 consumers: 1 each, the maximum useful parallelism.
  • 8 consumers: 6 work, 2 idle (useful only as hot spares for failover).

If a consumer dies, its partitions are handed to the survivors (a rebalance) and they continue from the committed offsets.

Two behaviours from one design. Within a group, records are shared, like a work queue. Across groups, each group independently receives every record, like publish-subscribe. So billing and search each use their own group.id and each sees all orders.

Who does the assigning. A broker acts as the group coordinator. Consumers join, the coordinator picks a leader consumer, and (in the classic protocol) that leader runs the partition assignor (RangeAssignor, RoundRobinAssignor, StickyAssignor, CooperativeStickyAssignor) and sends the plan back. Newer brokers (KIP-848) compute assignments on the broker side.

Alternatives and limits.

  • consumer.assign(partitions) reads specific partitions with no group management: no rebalancing and no automatic failover, but useful for tools or when you manage ownership yourself.
  • If you need more parallelism than partitions, you need more partitions (or in-process parallelism by key).
  • Assignment is by partition, not by load, so one big partition makes one consumer busier than the others.

Remember: in a group, one partition has one owner at a time. Extra consumers beyond the partition count idle. Different groups each get everything.

How does the consumer poll loop work, and what are max.poll.interval.ms and session.timeout.ms? Intermediate

A consumer runs a loop: poll(), process the records, commit, repeat. There are two separate liveness checks. A background thread sends heartbeats, and if the group coordinator hears nothing for session.timeout.ms (45 s default since 3.0) the consumer is declared dead. Separately, I must call poll() again within max.poll.interval.ms (5 minutes default), or the consumer is considered stuck and leaves the group, even though heartbeats were fine.

The shape of a consumer. A Kafka consumer is a loop that you drive. You call poll(); it returns up to max.poll.records (default 500) records, fetched in the background in bigger chunks. You process them, commit, and call poll() again. Nothing is pushed to you, and nothing happens in the group unless you keep calling poll().

while (running) {
    ConsumerRecords<String,String> recs = consumer.poll(Duration.ofMillis(500));
    for (ConsumerRecord<String,String> r : recs) process(r);
    consumer.commitSync();     // after processing = at-least-once
}

Two separate "are you alive" checks. This is the part interviewers love.

  1. Heartbeats are sent by a dedicated background thread every heartbeat.interval.ms (3 s). If the group coordinator receives none for session.timeout.ms (45 s default since Kafka 3.0; 10 s before), it declares the consumer dead and rebalances. This detects a crashed process, a frozen JVM or a network partition.
  2. max.poll.interval.ms (default 5 minutes) is the maximum time between two poll() calls. If your processing of one batch takes longer, the consumer itself leaves the group, even though heartbeats were fine. This detects a process that is alive but stuck in slow work.

Example of the trap. Default 500 records per poll, each takes 1.2 seconds because a downstream API is slow. A batch needs 600 seconds, more than the 300-second limit. The consumer is removed, its commit fails ("group has already rebalanced"), another consumer re-reads the same 500 records, becomes just as slow, and the group churns. The fix is to make a batch fit the interval: lower max.poll.records (to 50 here, giving 60 s), speed up the handler, or raise the interval a bit.

Rules for the loop. Never block in the loop for long. The KafkaConsumer is not thread-safe: one consumer per thread, and the only method you may call from another thread is wakeup(). If you hand work to a pool, keep calling poll(), using pause() so you do not fetch more than you can handle.

Remember: heartbeat = "the process is alive", poll interval = "processing is not stuck". A slow batch means a rebalance.

What is a rebalance, and why can it hurt? Eager versus cooperative? Senior

A rebalance is the group re-deciding who owns which partitions. It happens when a consumer joins, leaves, crashes, misses the poll interval, or partitions change. In the classic eager protocol everyone gives up all partitions, then rejoins, so the whole group pauses and lag builds up. The cooperative protocol moves only the partitions that must move, and the others keep working.

What it is. A rebalance is the group redistributing partition ownership. Triggers: a consumer joins, leaves cleanly, crashes (session timeout), is kicked for missing max.poll.interval.ms, or the topic's partitions change (or a subscribed pattern matches a new topic).

Why it hurts (eager protocol). In the classic eager protocol, every member first revokes all its partitions, then everyone rejoins, the leader computes a fresh plan, and everyone gets the new assignment. During that window nobody processes anything ("stop the world"). With many members, a big group, or repeated rebalances, lag piles up. Also, in-memory state or caches tied to partitions is dropped and rebuilt, and records processed but not yet committed get redone.

Cooperative (incremental) rebalancing. With CooperativeStickyAssignor (Kafka 2.4 and later), the group first agrees on the plan, but consumers give up only the partitions that actually have to move, in two short rounds. Everything else keeps being processed. Sticky means the new plan changes as little as possible.

Walk-through. C1 owns P0 and P1, C2 owns P2 and P3, and C3 joins. Eager: both C1 and C2 revoke everything, pause, rejoin, and get e.g. C1: P0, C2: P2/P3, C3: P1. Cooperative: the plan says only P1 moves, so C1 revokes just P1 in round one, and in round two C3 gets P1. C1 never stops P0; C2 never stops at all.

The new protocol. In Kafka 4.0, KIP-848 (group.protocol=consumer) moves assignment to the broker. There is no group-wide barrier, members get incremental changes, and clients no longer run assignors. It is the strategic answer; the classic protocol remains available.

How to reduce rebalances. Use cooperative or the new protocol, static membership (next question), a max.poll.records that fits the poll interval, graceful shutdown, and slow rolling deploys. Moving an existing group from eager to cooperative requires two rolling restarts: first deploy with both assignors listed (cooperative and the old one), then remove the old one, because mixed eager and cooperative members cannot work together.

Probe: "what should the application do during a rebalance?" Commit or finish in-flight work in onPartitionsRevoked (see the listener question).

Remember: eager = stop the world and reassign everything; cooperative = move only what must move. KIP-848 does it on the broker.

How do you stop restarts and deploys from triggering rebalances? Senior

I use static membership: give each consumer a stable group.instance.id (for example the pod name of a StatefulSet) and a session.timeout.ms longer than a restart. When that consumer restarts within the timeout, it gets its old partitions back and no rebalance happens. I also use the cooperative assignor, shut down gracefully, and roll pods one or two at a time.

The problem. Normally, when a pod restarts, the coordinator treats it as "member left, new member joined". That triggers two rebalances, and the restarted consumer gets a random new set of partitions. During a rolling deploy of 10 pods, that means up to 20 rebalances, each one pausing work and forcing offsets and state to be redone.

The fix: static membership. Give every consumer a stable identity with group.instance.id (for example the StatefulSet pod name billing-3). The coordinator remembers "billing-3 owns P6 and P7". If the member disappears and comes back with the same id before session.timeout.ms passes, the coordinator simply returns the same partitions: no rebalance at all. The trick is that a clean restart is now just a short, invisible blip.

Timeline.

  1. Pod billing-3 receives SIGTERM, closes its consumer without sending a LeaveGroup (static members do not leave on close), and restarts in 20 s.
  2. Session timeout is 60 s, so the coordinator waits.
  3. The new process joins with group.instance.id=billing-3 and instantly gets P6 and P7 back. Other consumers never noticed.

During those 20 s nobody reads P6 and P7, so lag grows slightly; that is the trade.

Trade-offs.

  • A member that is really dead keeps its partitions until the session timeout expires, so failover is slower. Pick a timeout a little longer than a normal restart (for example 1 to 2 minutes), not 10 minutes.
  • The id must be unique and stable per instance. Using the same id in two pods causes a FencedInstanceId error for one of them. In Kubernetes use a StatefulSet or derive the id from a stable ordinal; a Deployment's random pod names defeat the purpose.

Complete quiet-deploy recipe. Static ids, cooperative assignor, graceful shutdown (catch SIGTERM, call consumer.wakeup(), finish the batch, commit, then close()), a termination grace period longer than the longest batch, and maxUnavailable of 1 so only one pod restarts at a time. Without a graceful close, other members must wait for the session timeout to learn that the member is gone.

Remember: static group.instance.id + session timeout longer than a restart + graceful close = quiet deploys, at the cost of slower failover for dead pods.

How do offset commits work? Auto versus manual, sync versus async. Intermediate

Committing an offset tells Kafka "this group has processed everything before this offset", and after a crash the group restarts from there. Auto commit (the plain-consumer default) commits every 5 seconds inside poll() and can mark records done before I finished them, so a crash loses them. I turn it off and commit manually after processing succeeds, which gives at-least-once.

What a commit means. A commit saves, in __consumer_offsets, "for this group, partition P, resume at offset N". After any restart or rebalance, the new owner starts at N. So commit placement decides what happens on failure:

  • Commit before processing: a crash loses the unprocessed records (at-most-once).
  • Commit after processing: a crash causes re-reading some records (at-least-once, with duplicates).

Auto commit. With enable.auto.commit=true (the plain-client default), every auto.commit.interval.ms (5 s) the next poll() commits the offsets returned by the previous poll. The risk: it commits on a timer, not when your work finished. If the process crashes while a batch is half done after such a commit, the rest of the batch is never processed. (Spring Kafka turns auto commit off and commits on its own schedule, by default after each batch is handled.) For important data, set it to false and commit manually after processing succeeds.

Sync vs async.

A common pattern is commitAsync in the loop (cheap, a failure is fixed by the next commit) and one commitSync in the shutdown path.

Which number to commit. The offset of the next record to read, so last processed + 1. Committing N instead of N+1 re-reads one record on every restart; committing a number beyond what you processed skips records.

// commit per partition, after the work for that partition is done
consumer.commitSync(Map.of(
    new TopicPartition("orders", 0),
    new OffsetAndMetadata(lastProcessedOffset + 1)));

Granularity. Per batch is cheap and fine for most cases. Per record is safest for slow, side-effect-heavy work but multiplies requests to the coordinator. Committing a partition's offset after a rebalance took it away fails with CommitFailedException; that is the signal that someone else will redo this work, which again says "be idempotent".

Watch out: committing N instead of N+1 re-reads one record; committing before processing loses records on a crash.

Remember: process, then commit last offset + 1. Auto commit off for anything important.

What do you do in a ConsumerRebalanceListener? Senior

In onPartitionsRevoked I finish or flush in-flight work for those partitions and commit their offsets, so the next owner does not redo them. In onPartitionsAssigned I can load state or seek to a position stored in my own database. onPartitionsLost is called when the group already took the partitions away, where committing is impossible, so I just drop local state.

Why a listener exists. A rebalance can happen between two poll() calls without warning. If your code holds uncommitted progress, in-flight tasks or per-partition state, that all becomes wrong the moment the partition belongs to someone else. ConsumerRebalanceListener gives you hooks at the right moments. You pass it to subscribe(topics, listener).

onPartitionsAssignedAfter you receive partitions, before fetching startsLoad state, or seek() to a position stored in your own database

consumer.subscribe(List.of("orders"), new ConsumerRebalanceListener() {
  public void onPartitionsRevoked(Collection<TopicPartition> parts) {
    workers.awaitDone(parts);                 // finish in-flight work first
    consumer.commitSync(currentOffsets);      // so the next owner starts after it
  }
  public void onPartitionsAssigned(Collection<TopicPartition> parts) { }
  public void onPartitionsLost(Collection<TopicPartition> parts) { workers.cancel(parts); }
});

The failure it prevents. You poll 500 records, give them to a thread pool and move on. A rebalance takes P3 away. Without waiting in onPartitionsRevoked, your workers keep processing P3 records while the new owner starts re-reading them from the last committed offset, so two instances process the same records at once, and your commit later fails.

Cooperative nuance. With cooperative rebalancing, onPartitionsRevoked is called only with the partitions that move, and onPartitionsAssigned with only the newly added ones; partitions you keep never appear in either. Do not assume "assigned" is the full set; track your owned partitions yourself.

Spring Kafka offers the same through ConsumerAwareRebalanceListener, and with a simple single-threaded loop that commits per batch you often need no listener at all.

Remember: revoked = finish and commit; assigned = load state or seek; lost = just drop. Cooperative mode passes only the changed partitions.

How can a consumer rewind, replay or skip data? Intermediate

In code I call seek(partition, offset), seekToBeginning, seekToEnd, or offsetsForTimes to find the offset for a timestamp and seek there. From the command line, with the group stopped, kafka-consumer-groups.sh --reset-offsets moves the group to earliest, latest, a timestamp, a shift, or a specific offset. I always run --dry-run first, then --execute.

Why you would do this. The offset is just a number the group owns, so you can move it. Real reasons: a bug dropped or mis-processed two hours of data and you need to reprocess; a poison record must be skipped; a new consumer group must do a backfill; or you want to test against old data.

In code (inside a consumer).

  • seek(tp, offset): jump to an exact offset on a partition you own.
  • seekToBeginning(parts) and seekToEnd(parts).
  • offsetsForTimes(map of tp to timestamp): returns the earliest offset whose timestamp is at or after the time; then seek to it. This is "replay from 08:00".

Seeks take effect on the next poll(). The change is local until you commit.

From the command line. kafka-consumer-groups.sh --reset-offsets changes the group's committed offsets. The group must have no active members (stop all instances first), otherwise it refuses. Options: --to-earliest, --to-latest, --to-datetime, --to-offset, --shift-by (negative to go back), --by-duration. Always run --dry-run first (the default when you pass neither flag), check the printed new offsets, then repeat with --execute.

kafka-consumer-groups.sh --bootstrap-server b1:9092 --group billing \
  --topic orders --reset-offsets --to-datetime 2026-11-17T08:00:00.000 --dry-run
# looks right? run again with --execute, then restart the group

Examples of intent. Skip one bad record at offset 120: --to-offset 121 --topic orders:3 (partition 3 only). Replay the last 2 hours: --by-duration PT2H (an ISO-8601 duration measured back from now). Start a backfill with a new group id and auto.offset.reset=earliest, which leaves the production group alone.

Cautions. Replay repeats side effects (emails, charges, downstream writes), so the handler must be idempotent or you must route output somewhere safe. You can only go back as far as retention allows. Resetting a group that is running will be rejected, and resetting while a consumer is still alive can be overwritten by its next commit. Record who reset what and why.

Remember: stop the group, dry-run the reset, then execute. Replays need idempotent handlers and are limited by retention.

What is consumer lag and how do you measure it? Basic

Lag for a partition is the log end offset minus the group's committed offset: how many records are waiting that the group has not processed. Total lag is the sum across partitions. A small steady lag is normal. What matters is the trend: growing lag means consumers are slower than producers.

Definition. For one partition: lag = log end offset - group's committed offset. It is how many records exist that the group has not yet marked as processed. Total lag is the sum over the partitions. It is the single most important consumer health number.

What numbers mean. A small, steady lag (say a few hundred records) is normal: records arrive, a batch is in progress. The signal is the trend. Lag that rises while the producer rate is constant means the consumer is slower than the producers; lag that rises and falls in waves suggests rebalances; lag that rises only on one partition suggests a hot key or a stuck consumer or poison pill.

GROUP   TOPIC   PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
billing orders  0          1500            1520            20
billing orders  1          900             5900            5000   <- problem
billing orders  2          2100            2110            10

How to measure.

  • CLI: kafka-consumer-groups.sh --describe --group billing.
  • Client metrics: records-lag-max, records-lag per partition (fetch-manager-metrics), exported via Micrometer or JMX.
  • External: Burrow, Kafka Lag Exporter, Prometheus or cloud dashboards, which compute lag from broker data without touching the app.

Records are not time. Lag 10,000 means 10 seconds at 1,000 records per second but 3 hours at 1 per second. So also track time lag: the age of the oldest unprocessed record (now minus its timestamp) or an end-to-end latency metric. Alert on "age above N minutes", which matches user impact.

Estimating recovery. Lag drains at (consume rate minus produce rate). Lag 600,000, consuming 2,000/s, producing 1,500/s: net 500/s, so 20 minutes. If consume rate is not above produce rate, lag never drains and you must fix or scale.

Caveats. Committed offset is only as fresh as your last commit, so lag can look larger than reality between commits. With transactions the log end includes control markers, so a tiny constant lag can remain. Lag near retention is dangerous: records may be deleted before being read.

Remember: lag = log end offset minus committed offset. Watch the trend, the per-partition shape and the age of the oldest unprocessed record.

What does auto.offset.reset do, and what goes wrong with the default? Intermediate

It decides where a consumer starts when its group has no valid committed offset: latest (the default) jumps to the end, earliest starts from the oldest available record, and none throws an error. The danger of latest is silent data skipping: a brand-new group misses all history, and an old group whose offsets were deleted skips everything it missed.

What it solves. When a consumer joins a group it asks "where do I resume?". Normally there is a committed offset. But sometimes there is none, or it points to data that no longer exists. auto.offset.reset is the fallback rule for those two cases only.

The three values.

ValueBehaviourRisk
latest (default)Start at the end; read only new recordsSilently skips everything that was missed
earliestStart at the oldest record still retainedMay reprocess a lot of history; needs idempotent handling
noneThrow an exception to the applicationConsumer fails until someone decides; loud but safe

When it applies.

  1. A brand-new group.id. A new service deployed today with latest never sees yesterday's events. Often the developer expected the backlog and gets nothing, with no error.
  2. The committed offset is out of range. Either the group was down longer than retention and the segments were deleted, or the group's commits expired. Kafka deletes a group's committed offsets after offsets.retention.minutes (default 7 days) once the group has no active members.

It does not apply when a valid committed offset exists, so changing it on an existing running group does nothing.

Scenario. Retention 3 days, consumer down 5 days. On restart its offset is below the log start. With latest it jumps to the end: it skipped 5 days with no error and no alert. With earliest it would read from the oldest retained record (still a 2-day gap, but you get everything that exists). With none the application fails and you learn about it.

Choosing. For consumers that must not miss data, use earliest plus idempotent processing, or none if you prefer to fail loudly. Use latest only when old data is useless (live dashboards, cache invalidation). For a new service that needs history, also confirm the history is still inside retention, and consider an explicit offset reset or a one-off backfill job instead of relying on the config.

Remember: no committed offset (new group, or out of range) means auto.offset.reset applies. The default latest silently skips data; choose it on purpose.

5. Delivery semantics, exactly-once and transactions

Explain at-most-once, at-least-once and exactly-once delivery in Kafka. Intermediate

At-most-once means a record is processed zero or one time: commit the offset before processing, and a crash loses the record. At-least-once means one or more times: process first, then commit, and a crash between them causes a re-read, so duplicates. Exactly-once means the effect happens once. Kafka can do that inside Kafka with transactions; for outside side effects I use at-least-once plus idempotent processing.

Three guarantees, defined by what happens after a crash. The question is: if the consumer crashes between "I did the work" and "I saved my progress", what happens? It all comes down to the order of two steps, processing and committing the offset.

SemanticsOrderAfter a crash in the middleUse when
At-most-oncecommit, then processRecord is skipped (lost)Metrics, logs where loss is fine
At-least-onceprocess, then commitRecord is processed again (duplicate)The normal default; handlers are idempotent
Exactly-onceprocess, write output and commit as one atomic unitEither all happened or none didKafka-to-Kafka pipelines, Streams

Walk-through. The consumer reads offset 41 (charge card $20).

  • At-most-once: commit 42, then charge. Crash before the charge: restart at 42, the customer is never charged. Loss.
  • At-least-once: charge, then commit 42. Crash after the charge, before the commit: restart at 41, customer charged twice unless the handler dedupes. Duplicate.
  • Exactly-once inside Kafka: the output record "charged" and the input offset 42 commit in one transaction, so a crash leaves neither or both.

Why "exactly-once" has an asterisk. A transaction can cover only things Kafka controls (writes to topics, offset commits). A REST call, an email, or a database write is outside it. For those, the honest and accepted formula is: exactly-once effect = at-least-once delivery + idempotent processing (unique key, upsert, idempotency key to the API).

What producers add. Producer retries can themselves duplicate, so at-least-once on the producing side is made safe by the idempotent producer. End-to-end, you need to look at each hop: producer to broker, broker to consumer, consumer to the external system.

What to say in an interview. Default to at-least-once with idempotent consumers. Explain that exactly-once is real but scoped to Kafka-to-Kafka processing, and that you design handlers so duplicates are harmless instead of trying to prevent them.

Remember: commit first = may lose, process first = may duplicate. Exactly-once = atomic Kafka transaction, or at-least-once + idempotence outside Kafka.

How do Kafka transactions work, and what do isolation.level and transactional.id do? Senior

A transactional producer, identified by a stable transactional.id, begins a transaction, writes to one or more topics, adds the consumer's input offsets to the same transaction, and commits. Either all writes and the offset commit become visible, or none do. Consumers with isolation.level=read_committed only see committed data. This is how Kafka Streams gets exactly-once.

The use case. A "consume, transform, produce" app reads from topic A, writes results to topic B and moves on. Without transactions, a crash after writing to B but before committing A's offset causes the input to be reprocessed and the output to be written twice. A transaction makes "write output records and commit input offsets" atomic.

The moving parts.

  • transactional.id: a stable id you give the producer (one per logical instance, for example app-orders-0). It survives restarts.
  • Transaction coordinator: a broker that owns this id. It records the state of the transaction in the internal __transaction_state topic.
  • Epoch fencing: each time a producer starts with that transactional.id (initTransactions()), the epoch is bumped, and the broker rejects any older producer with the same id (ProducerFencedException). This kills zombies, for example an instance that was paused by GC and woke up after its replacement started.
  • Transaction markers: on commit or abort, the coordinator writes a COMMIT or ABORT control record into every partition the transaction touched.

Step by step.

  1. beginTransaction(); send records to topics B and C (they are written to the log immediately, but marked as part of an open transaction).
  2. sendOffsetsToTransaction(offsets, groupMetadata) adds the input offsets to the same transaction.
  3. commitTransaction(): the coordinator writes markers. Now the outputs and the offset commit all become visible together. abortTransaction() makes the outputs invisible and leaves the offsets alone, so the input is re-read.
producer.initTransactions();
while (true) {
  var recs = consumer.poll(Duration.ofMillis(500));
  producer.beginTransaction();
  try {
    for (var r : recs) producer.send(new ProducerRecord<>("out", r.key(), transform(r.value())));
    producer.sendOffsetsToTransaction(offsetsOf(recs), consumer.groupMetadata());
    producer.commitTransaction();
  } catch (Exception e) { producer.abortTransaction(); }
}

The reader side. isolation.level is read_uncommitted by default, which returns all records including those of open or aborted transactions. With read_committed the consumer only returns records of committed transactions (and non-transactional ones). It is held back at the last stable offset (LSO): the first offset still belonging to an open transaction. So one hung transaction delays everything behind it in that partition until it commits, aborts, or times out (transaction.timeout.ms, default 60 s).

Limits and cost. It only covers Kafka writes and Kafka offset commits. It adds latency (extra round trips and markers) and some overhead, so use fairly large transactions (commit per poll batch, not per record). Kafka Streams uses all this when you set processing.guarantee=exactly_once_v2. Fatal exceptions (such as a fenced producer) require closing the producer, not aborting and carrying on.

Remember: output + input offsets commit atomically; transactional.id plus epoch fences zombies; readers need read_committed.

Is Kafka's exactly-once really exactly once? Where does it stop? Senior

It is exactly-once for a pipeline that lives entirely inside Kafka: read topics, compute, write topics, with offsets committed in the same transaction. It stops at the edge of Kafka. If my code calls a payment API, writes to a database or sends an email inside the loop, that action is not part of the Kafka transaction, so after an abort and reprocess it can happen twice.

The short answer. Yes, exactly-once is real, but it is a statement about Kafka's own data. Inside the box (topics in, topics out, offsets) the transaction guarantees each input record's effect appears in the output exactly once, even across crashes and retries. Outside the box, Kafka has no say.

Where it breaks, with a concrete case. Your transactional loop reads an order, calls a payment provider over HTTP, and writes "PaymentDone" to a topic. The HTTP call is not part of the transaction. Timeline: the call succeeds, then the app crashes before commitTransaction(). On restart the transaction is aborted, the input is re-read, and the HTTP call runs again. The customer is charged twice, and Kafka's "exactly-once" was technically honoured: only one "PaymentDone" record is visible.

Ways to get an exactly-once effect outside Kafka.

  1. Idempotent operation. Pass an idempotency key (for instance the order id) to the payment provider, use an upsert, or rely on a unique constraint, so the second attempt is harmless.
  2. Dedup table. Store processed event ids in the same database transaction as the business change.
  3. Store offsets with the result. For a database sink, write the consumer offset into the same database transaction as the data. On startup, seek() to the stored offset instead of using Kafka's committed offset. The database is the single source of truth, so data and position cannot disagree.
  4. Outbox/CDC for the producing direction: write the event and the data in one local transaction.

Other boundaries. Consumers using read_uncommitted can see aborted data. Non-Kafka-Streams sinks via Connect are at-least-once unless the specific connector supports exactly-once (some do, with newer Connect versions for sources, and sinks via idempotent writes). Exactly-once also does not remove the need to handle duplicates from your producers publishing the same business event twice.

Interview framing. "Kafka transactions give atomicity for read-process-write within Kafka. For anything external I use at-least-once plus idempotent handling, because no broker can make my database write and my offset commit one atomic action."

Remember: exactly-once holds inside Kafka only. Outside, use idempotent writes, a dedup table, or offsets stored in the same DB transaction.

How do you build an idempotent consumer? Senior

I assume every record can arrive twice, then make handling it twice have the same effect as once. The most robust way is a dedup table: in the same database transaction as the business change, insert the event's unique id into a processed_events table with a unique constraint. A duplicate hits the constraint and is skipped.

The mindset. Because delivery is at-least-once, any record can legitimately arrive more than once: after a crash before commit, after a rebalance, after a replay, or because the producer published it twice. You cannot stop that, so you design the handler so that processing a record twice leaves the world in the same state as processing it once. That property is called idempotence.

Technique 1: dedup table (most general). Every event carries a unique id (a UUID created at the source, not the Kafka offset). In the same database transaction as the business change, insert the id into a processed_events table that has a unique constraint. If the insert violates the constraint, this event was already handled, so skip it.

@Transactional
void handle(OrderEvent e) {
  if (!processedRepo.insertIfAbsent(e.eventId())) return;  // unique key: duplicate skipped
  orderRepo.apply(e);                                      // same transaction as the insert
}

Atomicity is the crux. If the id is recorded in a separate step, a crash between "do the work" and "record the id" leaves you either unrecorded (work repeats) or recorded without work (work lost).

Technique 2: naturally idempotent operations. "Set status = SHIPPED" is idempotent; "balance = balance + 10" is not. Prefer absolute writes (upsert by primary key, set a field) over relative ones. Deleting something that is already deleted is fine.

Technique 3: version or sequence check. Each event has an entity version. Apply it only if its version is higher than the stored one (UPDATE ... WHERE version < :v). This also protects against out-of-order delivery.

Technique 4: idempotency keys for calls to other systems. Pass the event id to the payment API or email service so that they dedupe. Many payment APIs support exactly this.

Housekeeping. The dedup table grows; expire ids older than your longest realistic replay or retention window. Using topic, partition and offset as the dedup key is simple and fine for consumer-side duplicates, but a business id also catches duplicates created by the producer side (the same event published twice at different offsets). Test it: deliver the same record twice and assert one effect.

Remember: the dedup check and the effect must commit together, in one transaction. Prefer absolute writes and unique event ids.

Where can a Kafka message be lost end to end? Senior

I walk the path in three places. Producer: acks=0 or 1, an ignored callback, a crash before flush(). Broker: replication factor 1, min ISR 1, unclean leader election, or retention deleting data before a slow consumer read it. Consumer: committing before processing, auto commit, handing work to threads and committing early, or swallowing an exception and moving on.

Method: walk the path. A record travels producer, broker, consumer. For each hop ask "how could it vanish and I would not notice?". That structure also makes a good interview answer.

1. Producer side.

  • acks=0 or 1: the leader dies before followers copied it.
  • Callback ignored: the delivery timeout expired and the failure was invisible.
  • Process killed before the buffered batch was sent (no flush() or close()).
  • Dual write: the database commit succeeded but the app crashed before send(). Fix with the outbox pattern.
  • Non-idempotent retry exhaustion, or a serialization error that was caught and logged only.

2. Broker side.

  • Replication factor 1, or min ISR 1 with acks=all, so only one copy existed.
  • Unclean leader election turned on.
  • Retention or compaction removed data before a slow or stopped consumer read it.
  • Someone deleted or recreated the topic, or reset offsets.

3. Consumer side.

  • Auto commit (or commit before processing) followed by a crash.
  • Handing work to a thread pool and committing before the threads finish.
  • Catching an exception, logging it, and returning normally, so the offset moves on.
  • auto.offset.reset=latest on a new group or after expired offsets.
  • Reading with read_committed while the producer's transaction aborted (the record is correctly invisible, but looks "lost").
  • A filter or deserializer that silently returns null.

Debug in two minutes. Is the record in the topic (console consumer by key, or by partition and offset/timestamp)? Yes: the consumer lost it, so check its logs, dead-letter topic and commit order. No: the producer never delivered it, so check callbacks, acks and the outbox.

The safe recipe. acks=all, RF 3, min ISR 2, unclean election off, idempotence on, handle callbacks, commit after processing, route failures to a dead-letter topic instead of skipping.

Remember: producer acks and callbacks, broker replication and retention, consumer commit order and swallowed errors. First check whether the record is in the topic.

Where do duplicates come from in a Kafka system? Intermediate

Mostly from at-least-once working as designed. On the consumer side: a crash or rebalance after processing but before the commit, a consumer kicked out for exceeding max.poll.interval.ms whose work is redone elsewhere, or an operator replaying offsets. On the producer side: a lost acknowledgement causing a retry (fixed by idempotence), or my application sending the same event twice after a crash or double click.

First principle. Duplicates are not a bug in at-least-once; they are the price of never losing a record. The system prefers "maybe twice" over "maybe never". So the job is to know the sources, shrink the window, and make the effect harmless.

Producer-side sources.

  • Lost acknowledgement and retry. The broker stored the batch, the ack never arrived, the producer retried. Solved by the idempotent producer (default on).
  • Application restart. The app crashed after sending but before recording that it sent, then resends on restart; or a user double-submits. The broker sees two different business events. Solve with a business id and consumer dedup.
  • Producer retries in a pipeline that is not idempotent, such as a Connect source after a restart, or an outbox poller that crashes between publishing and marking rows as sent.

Consumer-side sources.

  • Crash or rebalance after processing but before the commit. The next owner restarts at the last commit and redoes the tail. The window is as long as your commit interval, so committing per batch rather than every 5 minutes keeps it small.
  • Kicked out for exceeding max.poll.interval.ms. The uncommitted batch is redone by someone else while the slow consumer may still be finishing it.
  • Operational replays (offset reset, new group from earliest, reprocessing from a dead-letter topic).
  • Retry topics: a failed record republished for retry may succeed twice if the first attempt partially worked.

Cross-system sources. Replicating clusters with MirrorMaker, Connect sinks that retry, and DLT replays can all re-deliver.

What to do. (1) Idempotent producer on. (2) A unique event id assigned at the source. (3) Idempotent consumers: dedup table, upsert or version check. (4) Commit promptly and in onPartitionsRevoked. (5) Transactions only where the whole flow is Kafka to Kafka.

Interview point: do not promise "no duplicates". Say "duplicates will happen, and my handler is idempotent so they are harmless".

Remember: duplicates are normal in at-least-once. Fix them with idempotent consumers and a unique event id, not hope.

6. Retries, dead-letter topics, poison pills and backpressure

What is a poison pill message and how do you handle it? Intermediate

A poison pill is a record that always fails: a payload that cannot be deserialized, a value that triggers a bug, or a rule violation. Because a partition is processed in order, the consumer cannot skip it on its own. It throws, the offset is not committed, the next poll returns the same record, and the partition is stuck while lag climbs. I retry a few times for temporary problems, then publish the record to a dead-letter topic with the error in headers, commit the offset and move on.

Why it is so damaging. A partition is a strict sequence. A consumer reads offset 100, fails, does not commit, and the next poll() returns offset 100 again. It can never reach 101 until 100 is handled. So one bad record blocks every record behind it in that partition, lag climbs, and (if the handler throws or hangs long enough) the consumer may also be kicked from the group, which just moves the problem to another consumer.

What makes a record "poison".

  • Bytes that cannot be deserialized (corrupt data, wrong schema id, producer using a different format).
  • Valid data that triggers a bug (null where code expects a value) or violates a business rule.
  • Data that breaks a downstream constraint (value too long for the database column).

The standard handling.

  1. Classify. Temporary failure (database timeout) versus permanent (cannot parse, validation failed). Retrying a permanent failure only wastes time.
  2. Retry briefly for temporary failures, with backoff and a limit.
  3. Dead-letter. Publish the record to a dead-letter topic (orders.DLT) with headers: original topic, partition, offset, exception class and message, timestamp.
  4. Commit the offset and continue.
  5. Alert on dead-letter traffic and have a runbook to inspect and replay after the fix.

Deserialization is special. It runs inside poll(), before your code sees the record. A RecordDeserializationException from poll (or an exception from a custom deserializer in older clients) repeats on every poll at the same offset. In Spring, wrap the real deserializer with ErrorHandlingDeserializer: it catches the failure and delivers a record with a null value and the error in a header, so your error handler can dead-letter it. In plain clients, catch the exception and seek past that offset.

What not to do. Do not log and skip silently (data lost with no trace). Do not retry forever (partition blocked). Do not dead-letter without alerting (it becomes a graveyard no one reads).

Prevention. Schema registry with compatibility checks, validation at the producer, and contract tests between teams.

Remember: retry briefly, then dead-letter with headers and commit. Never loop forever, never skip silently.

Design a retry and dead-letter strategy for a consumer. Senior

First I split errors into temporary (database down, timeout) and permanent (bad data). Permanent errors go straight to the dead-letter topic. For temporary ones I choose between blocking retry, which retries in place with backoff and keeps order but stalls the partition, and non-blocking retry topics, which publish the failed record to orders-retry-1, orders-retry-2 and finally orders-dlt so the main topic keeps flowing at the cost of order.

Start from the error type. This decides everything.

  • Permanent (parse error, validation failure, missing required field): retrying cannot help. Send straight to the dead-letter topic (DLT).
  • Temporary (timeout, 503 from a dependency, database failover, lock timeout): will probably succeed later. Retry with backoff.

Option A: blocking (in-place) retry. The consumer retries the same record a few times with backoff (for example 1 s, 2 s, 4 s), then dead-letters it. Pro: order is preserved and it is simple. Con: that partition is stalled during the retries, and long backoff risks exceeding max.poll.interval.ms. Good for short blips and strictly ordered data.

Option B: non-blocking retry topics. On failure, publish the record to orders-retry-1 (delay 1 min), then if it still fails to orders-retry-2 (delay 10 min), and finally to orders-dlt. The main topic keeps flowing. A retry consumer reads each retry topic, pauses the partition until the record's timestamp plus the delay has passed, then processes it. Pro: no head-of-line blocking, long delays are possible. Con: strict order for a key is lost (a later record for the same key can succeed before an earlier one is retried), more topics to manage, and consumers must be idempotent.

AspectBlocking retryRetry topics

Details that matter. Preserve context in headers (original topic, partition, offset, exception, attempt number). Make the same handler idempotent across attempts. Keep a documented, tested way to replay the DLT after a fix (a small tool that republishes to the main topic, perhaps rate-limited). Set DLT retention longer than your on-call response time. Alert on DLT arrival rate, not just presence.

In Spring Kafka, blocking retry is DefaultErrorHandler with a BackOff, and non-blocking is @RetryableTopic with attempts and backoff, which also creates the DLT.

Remember: permanent = dead-letter now; temporary = blocking retry (keeps order) or retry topics (keeps flow, loses order).

How do you handle bad messages and deserialization errors in Spring Kafka? Senior

I wrap the value deserializer in ErrorHandlingDeserializer, so a bad payload becomes a record carrying the failure instead of an exception inside poll(). Then I configure a DefaultErrorHandler with a back-off and a DeadLetterPublishingRecoverer, which publishes failed records, with exception headers, to topic.DLT.

The two layers of failure. (1) The record cannot even be read (deserialization). (2) The record is read but your listener throws. Spring Kafka needs a piece for each.

Layer 1: ErrorHandlingDeserializer. Without it, a corrupt record makes poll() throw on every attempt at the same offset, and the container is stuck. The wrapper takes a delegate (JSON, Avro...), catches its exception, and hands the listener container a record whose value is null with the original bytes and the exception stored in headers. The error handler then dead-letters it like any other failure.

spring.kafka.consumer.value-deserializer=org.springframework.kafka.support.serializer.ErrorHandlingDeserializer
spring.kafka.consumer.properties.spring.deserializer.value.delegate.class=io.confluent.kafka.serializers.KafkaAvroDeserializer

Layer 2: DefaultErrorHandler + DeadLetterPublishingRecoverer. When the listener throws, the DefaultErrorHandler seeks back to the failed record and retries according to a BackOff (for example 3 attempts, 1 s apart). When attempts run out, the DeadLetterPublishingRecoverer publishes the record to <topic>.DLT (same partition by default) with headers for the exception and the original topic, partition and offset, and the offset is committed.

@Bean
DefaultErrorHandler errorHandler(KafkaTemplate<Object,Object> template) {
  var recoverer = new DeadLetterPublishingRecoverer(template);
  var handler = new DefaultErrorHandler(recoverer, new FixedBackOff(1000L, 3));
  handler.addNotRetryableExceptions(IllegalArgumentException.class, ValidationException.class);
  return handler;
}

Marking permanent errors. addNotRetryableExceptions sends those exceptions straight to the recoverer with no retries. Spring already treats some as non-retryable by default (deserialization and conversion exceptions, for example), but declare your own business exceptions explicitly.

Batch listeners. If the listener handles a list, throw BatchListenerFailedException with the index of the failing record, so the container commits the earlier ones and retries only from the bad one onward instead of reprocessing the entire batch.

Other points. Retries by DefaultErrorHandler are blocking; for delayed non-blocking retries use @RetryableTopic. Make sure the DLT producer (the template) has a serializer able to write the failed payload, including raw bytes for deserialization failures. For JSON, restrict spring.json.trusted.packages to your own packages so type headers cannot instantiate arbitrary classes. Default back-off and attempts differ between Spring Kafka versions, so always set them explicitly.

Remember: ErrorHandlingDeserializer + DefaultErrorHandler + DeadLetterPublishingRecoverer, and mark permanent errors non-retryable.

Consumers pull. How do you handle backpressure and a slow downstream system? Senior

Kafka gives natural backpressure: a slow consumer just reads less and lag grows, while the broker is unaffected. The danger is inside my process: polling fast into an unbounded in-memory queue, which ends in an out-of-memory crash. So I bound the queue, and when the downstream is slow or down I use consumer.pause(partitions), which keeps calling poll() (so heartbeats and the poll interval stay healthy) but returns no records, then resume() when it recovers.

What "backpressure" means here. When the consumer is slower than the producers, who absorbs the difference? In Kafka it is the log itself. The broker does not push; the consumer pulls only what it can handle, and unread records wait on disk. A slow consumer just shows rising lag. This is a major advantage over push systems where a slow consumer can be flooded or the broker must drop or block.

Where the danger really is. Inside your process. A common anti-pattern: poll as fast as possible and put records into an unbounded in-memory queue for a thread pool. Poll never slows down, the queue grows without limit, and the JVM runs out of memory. Fixes: a bounded queue or semaphore, so polling stops being useful when the workers are full.

pause and resume. If the downstream (database, API) is slow or down, you want to stop receiving records but keep your group membership. Calling consumer.pause(partitions) makes poll() return nothing for those partitions while still sending heartbeats and satisfying max.poll.interval.ms. When the downstream recovers, resume(partitions).

while (running) {
  var recs = consumer.poll(Duration.ofMillis(200));
  for (var r : recs) {
    if (!queue.offer(r, 1, TimeUnit.SECONDS)) {   // bounded queue is full
      consumer.pause(consumer.assignment());
      break;
    }
  }
  if (queue.remainingCapacity() > LOW_WATERMARK) consumer.resume(consumer.paused());
}

(In real code you also must handle the records returned that did not fit, for instance by seeking back to the first unprocessed offset.) In Spring Kafka the listener container has pause() and resume(), and @KafkaListener containers can be stopped and started by id.

Protecting the downstream. Cap max.poll.records so a batch is bounded, use a circuit breaker and timeouts so you fail fast instead of hanging, and a rate limiter or bulkhead so catching up does not hammer a recovering service. Retry topics or a pause are better than looping.

Producer side. If brokers are slower than you produce, the buffer fills and send() blocks up to max.block.ms, then throws. That is built-in backpressure; handle the exception and slow the source (for example reject new requests).

Remember: bounded queue, pause() while downstream is down, keep calling poll() so you are not kicked out, and cap the batch size.

One consumer thread is too slow for a partition. How do you go faster without breaking order? Senior

The cleanest answer is more partitions and more consumers. If that is not possible, I parallelize inside the consumer: poll a batch, split records by key into lanes, give each lane to a worker so one key stays in order on one lane, and commit only up to the highest offset that is fully done below all unfinished ones.

Why this is hard. A partition is an ordered sequence. If one thread handles every record for a partition, order is trivially kept but throughput is capped by that thread. If you simply hand records to a thread pool, records for the same key may be processed concurrently or out of order, and commits become unsafe, because "offset 105 is done" may be true while 103 is still running; committing 106 would lose 103 if you crash.

First choice: scale with partitions. More partitions plus more consumers is the simplest, safest answer (until you hit practical limits, see partition count). Do this first if you can; it needs no custom code.

If you cannot: parallelism within the consumer, by key.

  1. Poll a batch. Hash each record's key to one of N worker queues ("lanes"), so all records of one key go to one lane and keep their order.
  2. Workers process lanes in parallel.
  3. Track completed offsets per partition. Commit only the highest offset such that every lower offset is finished (the contiguous finished prefix).
  4. Keep calling poll(); use pause() when lanes are full, so you do not fetch faster than you process.

Example. Records 100 to 105 arrive. Offsets 100, 101, 102, 104, 105 are done; 103 still runs. You can commit 103 (next to read = 103), not 106. If the app crashes now, records 104 and 105 are processed a second time, so the handler must be idempotent.

Hard parts. Partial failures (one lane fails, the others progress), rebalances (in onPartitionsRevoked wait for or cancel work on those partitions), shutdown, and the risk of memory growth. This is why people use a library: Confluent's Parallel Consumer implements key-, partition- or unordered-level concurrency with offset tracking.

Cheaper tricks that often suffice. Batch database writes (one bulk insert per poll instead of per record), use bounded asynchronous I/O, or cache lookups. Often the handler is slow because of one round trip per record, not because of one thread.

Remember: first add partitions and consumers; else parallelize by key lanes and commit only the contiguous finished prefix, with an idempotent handler.

7. Ordering, partition count, compaction, hot partitions

What ordering does Kafka guarantee, and how do you design for "process orders in order"? Intermediate

Kafka guarantees that records one producer sends to one partition are appended in the order sent, and consumers read a partition in offset order. There is no order across partitions. So to keep order for one entity I use the entity id (orderId, accountId) as the key, so all its records land in one partition, and one consumer processes that partition sequentially.

The exact guarantee. Kafka promises: records sent by one producer to one partition are appended in the order sent, and every consumer reads that partition in offset order. It promises nothing across partitions, and nothing across different producers (their relative order is just arrival order at the broker).

Designing for "process this customer's events in order". Use the entity id as the key. Example: key = orderId. OrderCreated(17), OrderPaid(17) and OrderShipped(17) all hash to partition 4, are appended in the order sent, and one consumer (the owner of P4) reads them in that order. Orders 18 and 19 may live on other partitions and run in parallel, which is what you want.

Three conditions that must all hold.

  1. Same key, same partition. The partition count must not change, and all producers must use the same partitioning.
  2. Producer does not reorder. Idempotent producer on (default), or in-flight set to 1.
  3. Consumer processes a partition sequentially. A free-for-all thread pool breaks it unless it keeps per-key lanes.

Failure modes.

  • Retries in the consumer. Retry topics or a skipped failed record let later events for the key overtake the failed one.
  • Two producers for one entity. Service A publishes OrderPaid while service B publishes OrderShipped; Kafka keeps only arrival order. Fix: one owner service per entity's events, or carry a version number and have the consumer ignore stale events or park early ones.
  • Adding partitions changes the mapping (see the next questions).

Global order. A total order across the whole topic needs a single partition, which limits you to one active consumer and the throughput of one broker's partition. Most designs settle for per-key order, which is what the business usually needs. If someone claims they need global order, ask what business rule actually requires it.

Remember: order = same key, same partition, idempotent producer, sequential consumer. No global order, and two producers for one key are not ordered.

How do you decide how many partitions a topic needs? Senior

I work from throughput. I measure what one consumer can handle per partition for my real work, divide the target throughput by that, and add headroom, often 2x to 3x, because the count is hard to change later. I also think about the maximum consumer parallelism I may want, since consumers cannot exceed partitions.

Why the number matters. Partitions set the maximum consumer parallelism and the spread of data, and they are hard to change later (you can add, never remove, and adding breaks key order). So you decide with some care and some headroom.

A practical method.

  1. Target throughput T (MB/s or records/s) at peak, including growth for the next year or two.
  2. Measure what one producer partition can take (p) and what one consumer can process (c) for your real handler. Usually the consumer is the slower side.
  3. Partitions needed = max(T/p, T/c). Example: peak 30,000 records/s, one consumer handles 1,500/s, so 20 partitions. With 2x headroom, choose 40, or round to a number with many divisors such as 48 so 2, 3, 4, 6, 8, 12 consumers split evenly.
  4. Check the other constraint: do you want to run more consumers than that someday? The count is your ceiling.

Why not just pick a huge number. Each partition costs: open file handles and memory on the broker, more replicas to track (RF x partitions), longer leader elections and recovery after a broker failure, more metadata, more replication traffic, more rebalance work for the group, and smaller batches per partition on the producer (batching is per partition). Clusters have practical limits per broker (often quoted in the low thousands of partitions per broker; KRaft raised the cluster-wide ceiling, so confirm with your platform team's numbers).

Why not very few. A low count caps parallelism, makes hot spots more damaging, and leaves no room to scale consumers.

Special cases. For keyed, order-sensitive topics, treat the number as a contract; size it up front. For small unkeyed topics, 3 to 6 is often enough. Compacted topics also want a stable count. If you underestimated, the fix is a new topic with more partitions and a migration, not an in-place change.

Remember: partitions = target throughput / per-partition rate, plus headroom. Easy to add, impossible to remove, and adding breaks key mapping.

And what happens to ordering if you add partitions to a keyed topic? Senior

Ordering breaks for existing keys during the change. The partitioner computes hash(key) mod partitionCount, so going from 6 to 12 partitions sends many keys to a different partition. Old records of a key sit in the old partition, new ones go to the new one, and two consumers can process the same key at once, with new records overtaking older ones still in lag.

The mechanism. The default partitioner computes hash(key) mod partitionCount. Change the count and the same key maps to a different partition. Concretely with 6 partitions, key "cust-77" hashes to, say, value 1,234,567,893. 1,234,567,893 mod 6 = 3 (partition 3). After growing to 12, mod 12 = 9, so new records go to partition 9. Roughly half of the keys move when you double the count.

What breaks, timeline.

  1. Before: events E1, E2 for cust-77 sit in partition 3; the consumer for P3 is 5,000 records behind and has not yet processed them.
  2. You add partitions. Event E3 for cust-77 now lands in partition 9, whose consumer is idle.
  3. The P9 consumer processes E3 immediately, while the P3 consumer is still working toward E1 and E2. E3 is handled before E1 and E2. Per-key order is broken, and two consumers may touch the same customer at the same time.

The old records are not moved: Kafka never rebalances existing data between partitions.

Other side effects. A compacted topic can now hold the same key in two partitions, so compaction no longer keeps one latest value per key across the topic, and a new reader that reads all partitions may see two "latest" records. Consumers with in-memory per-key state (Streams stores, caches) find keys have moved and their state is in the wrong place; Kafka Streams in fact does not support changing the input partition count of a running application with state.

Safe options.

  • Size up front with headroom so you never need to.
  • Drain then add: stop producers, wait for lag to reach zero, add partitions, restart. Order is preserved because nothing old remains. Needs downtime or a quiet window.
  • New topic and migration: create orders.v2 with the right count, run a copier or dual-write, move consumers when the old topic is drained, then retire the old one.
  • Defensive consumers: carry a version or sequence on events and ignore or park out-of-order ones.

Adding partitions is perfectly safe for unkeyed topics where order never mattered.

Remember: hash(key) mod N changes when N changes, so keys move and per-key order breaks. Drain first, or migrate to a new topic.

What is a hot partition and how do you fix it? Senior

A hot partition receives far more traffic than the others, usually from key skew: one big tenant or popular product generates most events, or the key has few distinct values. I see one partition's lag growing while others are near zero. I fix it by choosing a higher-cardinality key, or salting a known heavy key (tenant plus a sub-key hash), or giving the heavy tenant its own topic.

What it is. One partition receives much more traffic than the others, so one broker disk, one consumer and one leader do most of the work while the rest are nearly idle. Adding partitions or consumers does not help, because the heavy key is still in a single partition.

Typical causes.

  • Skewed keys: a few very large tenants or popular products generate most events (key = tenantId, one tenant is 60 percent of traffic).
  • Low-cardinality key: keying by country or status (5 distinct values) gives at most 5 busy partitions.
  • A default or null-like key such as "unknown" or an empty string used by many records.
  • A custom partitioner bug that favours some partitions.

How to confirm. Per-partition bytes-in and lag in your dashboards, then sample keys on the hot partition with a console consumer using --partition 7 --property print.key=true. Measure before changing anything.

Fixes, in rising order of effort.

  1. Choose a better key with high cardinality that still gives the order you need (orderId instead of tenantId, if orders are what must be ordered).
  2. Salt the heavy key: for known heavy tenants use tenantId + ":" + (customerId.hashCode() mod 8). The tenant now spreads over 8 partitions. Order is kept per customer but not per tenant, so confirm that is acceptable. Apply via a custom Partitioner or by building the key.
  3. Dedicated topic for the heavy tenant, with its own partitions, consumers and retention.
  4. Consumer-side: process the hot partition with key-lane parallelism, or batch downstream writes.

Cautions. Changing the key function moves records between partitions, which affects order at the cut-over; switch at a clean point after draining. Salting complicates anything that needs all of a tenant's events together (aggregations, compaction by tenant), so a downstream merge step may be needed.

Remember: hot partition = skewed key. Use a higher-cardinality key, or salt or isolate the heavy key, and accept weaker ordering.

What is log compaction, and when would you use it? Intermediate

With cleanup.policy=compact Kafka does not delete by age. A cleaner keeps only the most recent record for each key and drops older ones, so the topic always holds at least the latest value of every key. A new consumer reads it from the start and rebuilds the current state, like a table. I use it for entity state, lookup tables, and changelogs.

The normal cleanup deletes by age. Some data is not about history; it is about the current value. A topic of user profiles does not need ten old versions of a profile after a month; it needs the newest profile of every user, kept indefinitely. Log compaction (cleanup.policy=compact) guarantees exactly that: the log always keeps at least the last record for every key.

How it works. A background cleaner thread scans the closed (not active) segments, finds keys that have a newer record later in the log, and rewrites the segments without the older ones. Surviving records keep their original offsets, so offsets have gaps afterwards. A consumer that reads the topic from the start gets the latest value per key, plus whatever recent records have not been compacted yet, and can rebuild a table in memory.

Deleting a key. Produce a record with that key and a null value, a tombstone. The cleaner removes earlier records for the key, and keeps the tombstone for delete.retention.ms (default 24 hours) so that slow readers can see the delete, then removes it too.

Important behaviours.

  • Every record must have a key. A null key on a compacted topic is rejected.
  • Compaction is eventual. The active segment is never compacted, and the cleaner runs only when the "dirty ratio" (min.cleanable.dirty.ratio, default 0.5) is exceeded or max.compaction.lag.ms forces it. So readers can still see several values per key; the consumer must apply them in order and the last wins.
  • min.compaction.lag.ms guarantees records stay uncompacted for a minimum time.
  • You can combine: cleanup.policy=compact,delete to compact and also drop data older than the retention.

Where it is used. Kafka's own __consumer_offsets and __transaction_state; Kafka Streams changelog topics (state store backups); a "current state" topic of products, prices, customers; configuration distribution; and CDC topics when only the latest row image matters.

Not for: event history or audit trails, because older events are discarded. And the same-key order across partitions depends on the partition count never changing.

Remember: compaction = keep the latest value per key; a null value deletes the key. Good for current state, not for event history.

How do you design topics for a new domain: one topic per event type or one big topic? Senior

The deciding question is ordering. Events that must stay in order relative to each other (OrderCreated, OrderPaid, OrderShipped for one order) go in one topic keyed by the order id, because order exists only inside a partition. Unrelated event types with different consumers, volumes and retention go in separate topics. A topic per entity type, keyed by entity id, is a good default.

Start from ordering and ownership. Because order exists only within a partition, events that must be seen in sequence relative to each other must be in the same topic with the same key. OrderCreated, OrderPaid and OrderCancelled for order 17 must be ordered, so they share one topic (orders) keyed by orderId. If they were in three topics, a consumer could see "cancelled" before "created" and there is no way to restore the order.

Rules of thumb.

  • One topic per entity or aggregate type, with all its event types inside, is the best default. Consumers can read the whole lifecycle in order.
  • Separate topics for unrelated streams, different consumer sets, very different volumes, different retention or access control, or different compaction needs (events deleted by time versus state compacted by key).
  • Do not make one giant topic for everything. Every consumer then reads and filters all traffic, and you cannot tune retention or permissions per stream.
  • Do not make a topic per tenant or per schema version (thousands of topics are costly). Use the key for tenancy and the schema registry for versions, and use a dedicated topic only for a heavy or regulated tenant.

Event vs command vs state. Name events in the past tense (OrderPlaced) as facts. For "current state" topics (a customer's address), use compaction. Put an event id, a version or timestamp, and a trace id in every payload or header so consumers can dedupe and order.

Ownership. One team owns each topic's schema and publishes it; consumers must not write to someone else's topic.

Remember: events that must stay in order share a topic and a key; unrelated streams get their own topic; do not create one topic per tenant or version.

8. Schema Registry, Avro and schema evolution

What is the Schema Registry, and why use Avro or Protobuf instead of plain JSON? Intermediate

Kafka only moves bytes, so the contract lives in my serializers. The Schema Registry is a service that stores schema versions and gives each an id. The producer writes each record as a magic byte, the 4-byte schema id and a compact binary body, and the consumer fetches the schema by id (cached) to decode it. The registry also rejects a new schema that is incompatible with the old ones, so a breaking change fails at deploy time instead of breaking consumers at night.

The problem. Kafka stores bytes. It does not know or check what is inside. If the producing team renames customerId to custId in their JSON, the broker accepts it, and every consumer breaks at runtime, maybe at 3 a.m. You need a contract that is shared, versioned and enforced before deployment.

What the Schema Registry does. It is a separate service (Confluent Schema Registry or compatible ones) that stores schemas (Avro, Protobuf, JSON Schema) under a subject, typically <topic>-value, assigns every version a global schema id, and checks each new version against the configured compatibility rule before accepting it.

How a record travels.

  1. The producer's serializer, on first use, registers (or looks up) the schema and gets an id, say 42. It caches it.
  2. Each record is written as: a magic byte 0, the 4-byte schema id, then the compact binary body (no field names inside).
  3. The consumer's deserializer reads the id, asks the registry for schema 42 once, caches it, and decodes the bytes.

Why not plain JSON.

AspectPlain JSONAvro / Protobuf with registry

Evolution rulesNoneCompatibility modes (backward, forward, full)

Operational points. The registry is on the critical path only at startup and when a new schema id appears; clients cache, so a short outage is survivable but a cold start during an outage is not. Registry data is itself stored in a Kafka topic (_schemas). Disable auto-registration in production (auto.register.schemas=false) and register from CI, so a developer's local change cannot publish a new schema by accident. Choose the subject naming strategy deliberately if one topic holds several event types (RecordNameStrategy or TopicRecordNameStrategy).

Deserialization can still fail (wrong id, corrupt bytes), so plan for poison pills.

Remember: the schema id travels in every record, the schema lives in the registry, and compatibility is checked before deploy.

Explain schema compatibility: backward, forward, full. How do you roll out a breaking change? Senior

Backward compatible means consumers on the new schema can read old data, so I upgrade consumers first; allowed changes are adding a field with a default or deleting a field. Forward compatible means consumers on the old schema can read new data, so I upgrade producers first. Full means both directions. The registry default is backward. For a truly breaking change I do not force it: I create a new topic or version, dual-write for a while, move consumers over, then retire the old one.

First, who reads what. Records already in the topic were written with older schemas, and new ones with newer ones, and consumers and producers upgrade at different times. Compatibility rules say which combinations are guaranteed to decode.

ModeGuaranteeUpgrade orderAllowed changes (Avro)
BACKWARD (default)New schema can read data written with the previous oneConsumers firstAdd a field with a default; delete a field
FORWARDOld schema can read data written with the new oneProducers firstAdd a field; delete a field that has a default
FULLBothAny orderAdd or delete only fields with defaults
*_TRANSITIVESame, but checked against all earlier versionsAs aboveAs above
NONENo checksCoordinate by handAnything

Why "backward" means upgrade consumers first. A consumer upgraded to schema v2 must still read the old v1 records sitting in the topic. If v2 only added an optional field with a default, then for old records the default is used, so it works. The reverse is not needed because no producer writes v2 yet.

Transitive matters because of replay. If a consumer replays a topic from the start, it meets records of every historical version. A non-transitive check compares only with the immediately previous version and can let incompatibility with v1 slip through. With long retention or replay, use BACKWARD_TRANSITIVE or FULL_TRANSITIVE.

Rolling out a breaking change. Do not force it.

  1. Prefer a non-breaking path: add the new field alongside the old one, migrate consumers, then remove the old field in a later version ("expand and contract").
  2. If it is truly incompatible (type change, restructure): create a new topic or subject (orders.v2), publish to both for a while (dual write or a translator), move consumers over, retire the old topic.

Practical rules. Give every new field a default ("default": null with a union type). Never rename or change the type of an existing field (an alias exists for renames, but treat it as risky). Use enums carefully, since adding a symbol can break old readers. The registry checks structure, not meaning: changing amount from dollars to cents passes every check and still corrupts everything downstream. Combine registry checks, CI gates and consumer-driven contract tests.

Watch out: people mix up backward and forward, and add required fields without a default.

Remember: backward = upgrade consumers first, forward = producers first, full = either. New fields need defaults; never rename or retype.

9. Kafka Streams, Connect, CDC and the outbox pattern

What is Kafka Streams, and how is it different from a plain consumer or from Spark and Flink? Intermediate

Kafka Streams is a Java library, not a cluster. I add it to my normal application, define a topology (read topics, filter, map, join, aggregate, write topics), and run as many app instances as I like; they share the work using the same partition assignment as a consumer group. State lives in local stores (RocksDB) backed by compacted changelog topics, so a replacement instance can rebuild it.

What it is. Kafka Streams is a client library, shipped as a JAR, for building stream processing apps in Java or Scala. There is no separate cluster to install: you embed it in an ordinary service, define a topology (read topics, transform, join, aggregate, write topics), start it, and scale by starting more copies of the same application (same application.id).

How it scales and recovers. Internally each instance runs a consumer group. The topology is split into tasks, one per input partition, and tasks are spread over instances and threads. Stateful operations (counts, aggregations, joins) keep their state in a local store (RocksDB by default) next to the task. Every change to that store is also written to a compacted changelog topic in Kafka. If an instance dies, the task moves to another instance, which rebuilds the store by replaying the changelog (standby replicas, num.standby.replicas, make this fast).

Core abstractions. A KStream is an unbounded sequence of events (each record is an independent fact). A KTable is a changelog viewed as a table: the latest value per key (an update replaces the previous). A GlobalKTable is fully replicated to every instance for lookups. Windowing (tumbling, hopping, session) groups events by time. Stream-stream and stream-table joins need both inputs co-partitioned: the same number of partitions and the same key partitioning, otherwise matching keys land on different tasks.

builder.stream("clicks")
       .filter((k, v) -> v != null)
       .groupByKey()
       .windowedBy(TimeWindows.ofSizeWithNoGrace(Duration.ofMinutes(5)))
       .count()
       .toStream().to("click-counts");

Exactly-once. processing.guarantee=exactly_once_v2 uses transactions so that input offsets, state changelog writes and output records commit atomically.

What is Kafka Connect, and why use it instead of writing producers and consumers? Intermediate

Kafka Connect is a runtime for moving data between Kafka and other systems using ready-made connectors configured in JSON, with no code. A source connector pulls data into Kafka (a database, files, an API); a sink connector pushes it out (Elasticsearch, S3, a warehouse, JDBC). It handles batching, retries, offset tracking, scaling across workers and restarting failed tasks, so I write code only when no connector fits.

The problem. Moving data between Kafka and a database, S3, Elasticsearch or a SaaS API looks easy, but doing it properly means: batching, retries, tracking where you stopped, handling schema, scaling out, restarting after a crash, and monitoring. Every team rewrites this poorly. Kafka Connect is a ready-made runtime that does all of it, and you only supply configuration.

Concepts.

  • Worker: a JVM process. Several workers form a Connect cluster (distributed mode), sharing the load and failing over.
  • Connector: a configured job (for example "JDBC sink for topic orders"). A source connector reads an external system into Kafka; a sink connector writes from Kafka out.
  • Task: the unit of parallelism; a connector is split into up to tasks.max tasks spread across workers.
  • Converter: turns Connect's internal data into bytes (Avro, JSON, Protobuf).
  • SMT (Single Message Transform): a small per-record change such as rename, mask, route, add timestamp. Anything more complex belongs in a Streams app.

You manage it by REST. Create with POST /connectors, check GET /connectors/x/status, restart a failed task with POST /connectors/x/tasks/0/restart.

{ "name": "orders-sink",
  "config": {
    "connector.class": "io.confluent.connect.jdbc.JdbcSinkConnector",
    "topics": "orders",
    "insert.mode": "upsert",
    "pk.mode": "record_key",
    "errors.tolerance": "all",
    "errors.deadletterqueue.topic.name": "orders-sink-dlq",
    "errors.deadletterqueue.context.headers.enable": "true" } }

Delivery and state. Connector progress (source offsets, config, status) is stored in internal Kafka topics. Sinks are at-least-once by default, so a restart can re-deliver; choose upsert modes or idempotent writes. Exactly-once is available for some source connectors in newer Connect versions, depending on the connector.

Error handling. errors.tolerance=none (default) fails the task on a bad record, which is safe but stops the pipeline. all skips bad records and, with a dead-letter queue configured (sink connectors only), writes them to a DLQ topic with error headers. Combine with errors.retry.timeout for temporary failures.

When to write code instead. If no connector fits, if you need complex business logic, or if you need exact control, write a consumer or producer. Otherwise Connect saves weeks and removes a class of bugs.

Remember: source in, sink out, configuration not code. Delivery is at-least-once, so use upsert on sinks and a dead-letter queue for bad records.

What is change data capture (CDC) and how does Debezium use Kafka? Intermediate

CDC turns every insert, update and delete in a database into an event. Debezium does it by reading the database's own transaction log (MySQL binlog, PostgreSQL write-ahead log) instead of querying tables. That is light on the database, captures deletes, and keeps commit order. Each table becomes a topic keyed by primary key, with before and after rows in each event.

What CDC is. Change data capture turns every committed insert, update and delete in a database into an event, so other systems can react without the application having to publish anything. Typical uses: keep a search index or cache in sync, feed a data warehouse, replicate to another database, and implement the outbox pattern.

Why log-based CDC beats the alternatives. Polling a table (WHERE updated_at > ?) misses deletes, misses intermediate updates between polls, loads the database, and needs an indexed timestamp column. Triggers add cost to every write and live inside the application's transaction. Debezium reads the database's own transaction log (MySQL binlog, PostgreSQL write-ahead log via a logical replication slot, SQL Server and Oracle equivalents). That is cheap for the database, sees every change in commit order, includes deletes, and requires no change to the application.

How Debezium uses Kafka. It runs as a Kafka Connect source connector.

  1. Snapshot: on first start it reads the existing rows of captured tables as events.
  2. Streaming: it then reads the log. Each table gets a topic (for example shop.public.orders), keyed by the row's primary key, so changes to one row stay ordered.
  3. Each event has before and after images, the operation (c, u, d), a timestamp, and the log position. A delete is followed by a tombstone so compaction can drop the key.
{ "op": "u",
  "before": {"id": 17, "status": "NEW"},
  "after":  {"id": 17, "status": "PAID"},
  "source": {"table": "orders", "lsn": 23456789} }

Operational points.

  • At-least-once: after a restart a few events can repeat, so consumers must be idempotent (dedupe by key and log position).
  • PostgreSQL replication slot: the database keeps WAL files until the connector confirms them. If the connector is stopped or stuck, WAL accumulates and can fill the disk. Monitor slot lag and set max_slot_wal_keep_size (PostgreSQL 13 and later) as a safety valve.
  • Schema changes in the source table flow into events, so combine with a Schema Registry and compatibility rules.
  • Security: the topics can contain full row data, including sensitive columns; mask or exclude columns.
  • Large transactions and initial snapshots of huge tables need planning.

Remember: CDC reads the database log, not the tables. Consumers must be idempotent; watch the replication slot if the connector stops.

What is the outbox pattern and why do we need it? Senior

It solves the dual-write problem: a service must save to its database and publish an event to Kafka, and those are two systems. If it writes the database then crashes before sending, the event is lost; if it sends first and the database rolls back, the event describes something that never happened. With the outbox, I insert the event into an outbox table in the same local database transaction as the business change, and a separate process publishes outbox rows to Kafka afterwards.

The problem: the dual write. An order service must (1) save the order in its database and (2) tell the world by publishing OrderPlaced to Kafka. These are two different systems, so there is no shared transaction. Whatever order you pick, a crash in the middle is a bug:

  • Save then publish: crash in between. The order exists but no event was ever sent; downstream never learns.
  • Publish then save: the save fails or rolls back. An event announces an order that does not exist.

Retrying does not solve it, because the process that would retry may be the one that died.

The outbox solution. Put the event into the database too, in the same transaction.

  1. One local transaction: insert the order row and insert an event row into an outbox table (id, aggregate id, type, payload, created time).
  2. The transaction commits atomically. Either both rows exist or neither does.
  3. A separate relay reads new outbox rows and publishes them to Kafka. If it crashes, it resumes and publishes again; the event is delayed, never lost.
BEGIN;
INSERT INTO orders(id, status, total) VALUES (17, 'NEW', 99.0);
INSERT INTO outbox(id, aggregate_id, type, payload)
  VALUES (gen_random_uuid(), '17', 'OrderPlaced', '{"orderId":17,"total":99.0}');
COMMIT;

Two ways to relay.

RelayHowTrade-off
Polling publisherA scheduled job selects unsent rows, publishes, marks sentSimple; adds database load and latency; must handle crashes between publish and mark (duplicates)
CDC (Debezium Outbox Event Router)Reads the database log for the outbox table and routes to topicsLow latency, no polling load, ordered; needs Connect and Debezium

Rules for doing it well. Delivery is at-least-once, so give each event a unique id and let consumers dedupe. Use the aggregate id as the Kafka key so one entity's events stay ordered. Delete or archive published outbox rows regularly (with CDC you can even delete immediately, since the log already captured the insert). Keep the payload a stable, versioned contract, not your internal table shape.

Related patterns. The mirror problem on the consuming side is solved by the idempotent consumer. Event sourcing treats the log itself as the source of truth, but needs more discipline. Kafka transactions do not help here because the database is outside Kafka.

Remember: one database transaction writes the data and the event; a relay publishes it later at-least-once; consumers dedupe by event id.

10. Spring Kafka, testing and monitoring

How do you use Kafka with Spring Boot? What does @KafkaListener do? Intermediate

Spring for Apache Kafka gives me KafkaTemplate to send and @KafkaListener to receive. Behind a listener is a listener container that owns one or more real KafkaConsumer threads, runs the poll loop, calls my method per record (or batch) and commits according to an ack mode. concurrency sets the number of consumer threads, so it is useless above the partition count.

The pieces. Spring for Apache Kafka wraps the plain clients. For sending you inject KafkaTemplate<K,V>, which owns a shared producer and returns a future (CompletableFuture in recent versions). For receiving, the annotation @KafkaListener registers a method with a listener container: a managed component that runs real KafkaConsumer threads, executes the poll loop, deserializes, calls your method, handles errors and commits offsets.

@KafkaListener(topics = "orders", groupId = "billing", concurrency = "3")
void on(ConsumerRecord<String, OrderEvent> rec) {
   billingService.charge(rec.value());   // exception triggers the error handler
}

@Bean
DefaultErrorHandler errorHandler(KafkaTemplate<Object,Object> t) {
  var recoverer = new DeadLetterPublishingRecoverer(t);
  return new DefaultErrorHandler(recoverer, new FixedBackOff(1000L, 3));
}

Key behaviours.

  • concurrency = number of consumer threads in this application instance. Total consumers across all pods is concurrency times pods, and anything above the partition count idles.
  • Thread model: your method runs on the consumer thread. A slow method delays polling and can breach max.poll.interval.ms, causing a rebalance.
  • Ack mode (spring.kafka.listener.ack-mode): default BATCH (commit after the whole poll batch was processed without error). RECORD commits after each record, MANUAL / MANUAL_IMMEDIATE let you call ack.acknowledge(). Spring sets the client's enable.auto.commit to false unless you explicitly enable it.
  • Errors: an exception goes to the DefaultErrorHandler. It retries per its back-off, then calls a recoverer (for example dead-lettering). With a batch listener, use BatchListenerFailedException.
  • Retry topics: @RetryableTopic creates delayed non-blocking retry topics and a DLT.
  • Transactions: set a transaction-id-prefix to get producer transactions with the listener container.
  • Serialization: JsonSerializer/JsonDeserializer (restrict trusted packages), or Avro with the registry.

Common pitfalls. Setting concurrency above the partition count; doing slow blocking work in the listener; forgetting a unique groupId per logical subscriber; relying on defaults for retries; creating many KafkaTemplate producers by hand. Start and stop listeners by id (KafkaListenerEndpointRegistry) for pause and maintenance.

Remember: listener = container + real consumer threads. concurrency up to the partition count; the default ack mode commits after each batch; failures go to the error handler.

How do you test Kafka code? Intermediate

In layers. I keep business logic free of Kafka types so handlers are plain methods with unit tests. For integration I run a real broker with Testcontainers (a Kafka container), produce a record and wait with a timeout (Awaitility) for the effect. Spring's @EmbeddedKafka is a lighter in-JVM alternative, and Kafka Streams has TopologyTestDriver that needs no broker.

Think in layers, with the fastest layer doing most of the work.

  1. Unit tests on the handler. Keep the business logic in a plain method that takes your event object, not a ConsumerRecord. Test it directly, including duplicates (call it twice and assert one effect), null fields and out-of-order versions. Mock the database or API.
  2. Component test with a real broker. Use Testcontainers to start a Kafka container (a real broker, same behaviour as production), produce a record, and use Awaitility to wait, with a timeout, for the visible effect. Never use Thread.sleep; it makes tests slow and flaky. Spring's @EmbeddedKafka runs a broker inside the JVM and is lighter but less realistic. Both let you test serialization, group behaviour, error handling and dead-lettering.
  3. Topology tests for Streams. TopologyTestDriver runs a Streams topology with no broker and a controlled clock, ideal for windows and joins.
  4. Contract tests between teams. Run the schema compatibility check in CI against the registry, and share consumer-driven contract tests or sample payloads so that a producer change that breaks a consumer fails the producer's build.
@Container static KafkaContainer kafka = new KafkaContainer(DockerImageName.parse("apache/kafka:3.8.0"));

@Test void poisonRecordGoesToDlt() {
  template.send("orders", "k1", "not-json");
  await().atMost(10, SECONDS).untilAsserted(() ->
      assertThat(readAll("orders.DLT")).hasSize(1));
}

The unhappy paths worth testing deliberately. The same record twice; a poison record reaching the DLT and the partition continuing; an out-of-order event; a consumer restart mid-batch (no loss, bounded duplicates); the downstream failing then recovering (retry or pause behaviour); a rebalance during processing.

Tips. Use a unique topic and group id per test to avoid interference, set auto.offset.reset=earliest in tests so the consumer sees records sent before it started, and keep the number of integration tests modest because each one pays broker start-up cost (share one container per test class).

Remember: unit-test the handler, integration-test with Testcontainers and Awaitility, and always test duplicates and poison records.

What would you monitor for a Kafka-based service you own? Intermediate

On the consumer side: lag per partition and its trend, the age of the oldest unprocessed record, rebalance count, handler latency, error and dead-letter counts, and how close I am to max.poll.interval.ms. On the producer side: send error rate, request latency, retries, and buffer wait time. The platform team usually owns under-replicated and offline partitions, but I should know to watch them.

Approach. Monitor what your service owns and what a user would notice. The platform team watches the brokers; you watch your producers, your consumers and your data flow.

Consumer side (the most important).

  • Lag per partition and its trend, plus time lag (age of the oldest unprocessed record). Alert on "lag older than 5 minutes for 10 minutes", not on a raw number.
  • Rebalance rate and group state. Frequent rebalances mean slow batches, GC, crash loops or a bad deploy.
  • Handler latency (p50, p99) and throughput, and the time between polls versus max.poll.interval.ms (last-poll-seconds-ago).
  • Error counts by type, retry and dead-letter topic arrivals. Any DLT message deserves a look.
  • Commit failures (commit-failed style errors), which signal that a rebalance took the partition.

Producer side. Send error rate and callback failures, record-error-rate, request latency, retry rate, buffer-available-bytes and time blocked waiting for metadata or buffer, and batch size and compression ratio (efficiency).

Cluster health you should know about. Under-replicated partitions, partitions under min ISR, offline partitions, active controller count, request latency and disk usage. You rarely fix these yourself, but they explain symptoms such as NotEnoughReplicas.

Tools. Micrometer metrics from Spring Kafka (kafka.consumer.*, listener timers), JMX, Prometheus with Grafana, Kafka Lag Exporter or Burrow for lag, and the Confluent or cloud provider consoles.

Traceability. Log topic, partition, offset, key and a trace or correlation id on every send and receive, and propagate a trace id in a record header (OpenTelemetry does this) so a single business request can be followed across services. When a record goes missing, the first question is "was it produced, and at which offset?", which these logs answer.

Alert design. Alert on user-visible symptoms (stale data, DLT traffic, growing time lag, rebalance storm) and keep a short runbook for each.

Remember: lag trend and age, rebalances, dead-letter counts, handler latency, producer errors. Log topic-partition-offset and a trace id.

11. Kafka versus RabbitMQ and others

Kafka versus RabbitMQ (or SQS): how do you choose? Intermediate

I choose Kafka for event streaming, data pipelines, event sourcing, CDC, replay, and many independent readers of the same events, with high throughput and per-key ordering. I choose RabbitMQ or SQS for job queues where each message is handled once and forgotten, with per-message acknowledgement, retries, delays, priorities or complex routing.

The two mental models.

  • RabbitMQ (a "smart broker, simple consumer"): producers publish to an exchange, which routes messages by rules (direct, topic, fanout, headers) into queues. The broker pushes messages to consumers, tracks acknowledgements per message, redelivers on failure, and deletes after ack. It offers priorities, per-message TTL, delayed delivery plugins, and flexible routing.
  • Kafka (a "simple broker, smart consumer"): a replicated log. The broker appends and serves ranges; consumers pull and track their own offset. Data stays for the retention period. Fan-out is just another consumer group.
  • SQS: a fully managed queue (no servers). Standard queues are at-least-once and unordered; FIFO queues give ordering per message group. It has visibility timeouts, delays and dead-letter queues, but no replay.

Decision rule. Ask: "do I need history, replay, many readers, high volume and per-key order?" Then Kafka. "Do I just need to hand a job to one worker, retry it, delay it, route it by rule, and forget it?" Then a queue.

Pitfalls. Using Kafka as a task queue: one slow or failing record blocks its partition (head-of-line blocking), and per-message delay and retry are not built in. Using RabbitMQ for a huge replayable event stream: queues are not meant to retain terabytes, and replay is limited. Pulsar is a log-style alternative with built-in multi-tenancy and tiered storage but a smaller ecosystem. Kafka is also adding queue-like "share groups" (KIP-932), which are early in recent 4.x releases, so check their status before relying on them.

Remember: need history, replay and many readers: Kafka. Need a task queue with per-message retry, delay and routing: RabbitMQ or SQS.

When should you NOT use Kafka? Senior

I would not use Kafka for a small number of simple jobs that need delay, per-message retry or priority (use SQS or RabbitMQ), for synchronous request and response (use HTTP or gRPC), as a database for lookups by key or ad hoc queries, or when a small team has no platform support to run a cluster and no managed option.

Situations where Kafka is the wrong tool, and what to use instead.

The deeper reasoning. Kafka's strengths come from being simple and append-only, so anything that needs the broker to be clever about individual messages (retry timing, priorities, selective acknowledgement) is outside its design. Also, "we might need it later" is not a reason: a database or a managed queue is cheaper to run and easier to debug until you have real streaming needs such as many consumers, replay and high throughput.

Ways Kafka is still used alongside these. Kafka feeds a database or search index (via Connect), while HTTP handles request-reply; the claim-check pattern keeps payloads small.

Interview angle. Saying "it depends, here is when I would not use it" shows judgment. Anchor on the requirement (volume, replay, fan-out, ordering, team capacity), not on the technology.

Remember: not for task queues, request-reply, random lookups, huge payloads, or when you cannot operate it. Pick from the requirement.

12. Real-life scenarios

Every answer follows the same shape: situation, what you check first, the fix, and how you prevent it next time. Say this shape aloud in the interview, it shows you work calmly under pressure.

After a release, consumer lag on the orders topic grows every minute. What do you do? Senior

I look at the shape of the lag first. All partitions growing means the handler got slower or traffic spiked; one partition means a hot key or a stuck consumer; lag in waves means a rebalance loop. Then I find the bottleneck, usually a slow call added in the release, and roll back or fix it before scaling anything.

Situation. Producers write at the same rate as yesterday, but after a release the billing group falls behind. Lag grows by thousands per minute and an alert fires. Say this shape aloud: situation, check, fix, prevent.

Step 1: read the lag shape. The shape of the lag points at the cause before you open any code.

Step 2: find what changed in the release. A new database call or lookup per record, a bigger payload, an extra log line at INFO, a lowered max.poll.records, a changed concurrency, fewer pods or lower CPU limits, a new synchronous HTTP call. Compare handler latency (p99) before and after, and check CPU, GC and the downstream's latency.

Worked numbers. Before: each record took 5 ms, so one consumer did 200 per second; with 6 partitions and 6 consumers that is 1,200/s, above the 1,000/s input. After the release a new lookup adds 8 ms: 13 ms per record, 77/s per consumer, 460/s total against 1,000/s in. Lag grows by 540 records per second, about 32,000 per minute.

Fix. Roll back if the cause is clear and risk is high. Otherwise fix the slow call: batch the lookups, add an index or a cache, do bulk inserts. Scaling consumers helps only up to the partition count; beyond it extra consumers idle. Rate-limit if the downstream is the bottleneck so you do not take it down while catching up. To tell stakeholders when it recovers: time to drain = lag / (consume rate - produce rate).

Prevent. Load test the consumer at production rate after changes, alert on lag trend and age, track handler p99 latency, and use canary deploys for consumers.

Remember: read the lag shape first (all, one, or waves), then find the slow step. Never add consumers beyond the partition count.

Customers were charged twice because the payment consumer processed some messages two times. Why, and how do you fix it? Senior

It is almost always at-least-once working as designed: a pod was killed or a partition moved after the charge but before the offset commit, so the next owner re-read the record. The fix is an idempotent handler: dedupe by event id in the same database transaction as the payment, and pass the same id to the payment provider as its idempotency key.

Situation. A few customers were charged twice. They cluster around deployments and slow periods.

The likely story. This is at-least-once behaving as designed. Timeline of one duplicate:

  1. Consumer A reads PaymentRequested(id=e-91) at offset 5,000 and charges the card.
  2. Before A commits offset 5,001, the pod is killed (deploy), or a rebalance revokes its partition, or the batch exceeded max.poll.interval.ms and A was removed.
  3. Consumer B takes the partition, starts at the last committed offset (before 5,000), and reads e-91 again.
  4. B charges the card again.

What to check first.

  • Do duplicate times match restarts, rebalances or long batches? Look at group logs for "revoking partitions" and "commit failed".
  • Where is the commit relative to the charge? (Must be after.) Is auto commit on? How long is the commit interval?
  • Do the duplicates have the same event id (consumer re-delivery) or different ids for the same order (the producer published twice, or the user clicked twice)? This decides whether the fix is in the consumer or at the source.

Fix. Make the handler idempotent. In one database transaction, insert the event id into a processed_events table with a unique constraint and write the payment record; a duplicate fails on the constraint and is skipped. Pass the same id as the idempotency key to the payment provider so even if your database step is skipped, the provider refuses the second charge. Also shrink the window: commit right after processing, commit in onPartitionsRevoked, and shut down gracefully. Refund the existing duplicates using a reconciliation query (group by order id having count above 1).

SELECT order_id, COUNT(*) FROM payments GROUP BY order_id HAVING COUNT(*) > 1;

Prevent. Idempotency by design for every side effect, a unit test that delivers the same message twice, a chaos test that kills a pod mid-batch, and a reconciliation job as a safety net.

Remember: at-least-once means duplicates happen. Dedupe by event id in the same transaction as the effect, and send an idempotency key to the provider.

The consumer group keeps rebalancing every few minutes and almost no work gets done. What is going on? Senior

Members keep leaving the group, usually because a poll batch takes longer than max.poll.interval.ms, because GC or CPU starvation misses heartbeats, or because pods keep restarting. The fix is to make each batch fit the interval (lower max.poll.records), use cooperative rebalancing and static membership, and stop the crash loops.

Situation. The group rebalances every few minutes. Logs show lines like "Revoking previously assigned partitions", "Attempt to heartbeat failed since group is rebalancing" and "Commit cannot be completed since the group has already rebalanced". Lag rises and falls in waves and almost no real progress is made.

Why this is a loop. Records are processed but not committed because the consumer is removed from the group; then somebody else redoes them; they are slow too, so the cycle repeats.

Check first: why do members leave? There are only a few reasons, each with a signature.

A producer team says they sent an event but the consumer never got it. Where do you look? Senior

I first prove which side is wrong by looking for the record in the topic by key and time window with a console consumer. If it is there, the consumer skipped it or it went to a dead-letter topic. If it is not there, the producer never delivered it.

Situation. The producing team says "we sent OrderPlaced(17)" and the consuming team says "we never received it". Both are confident. Your job is to prove which side is wrong quickly.

Step 1: look at the log itself. The topic is the source of truth, so search it: by key and time window, or by partition and offset if the producer logged the metadata.

  --partition 3 --offset 120000 --max-messages 50 \
  --property print.key=true --property print.offset=true --property print.timestamp=true

A single bad record has stopped a partition for an hour. How do you unblock and prevent it? Senior

I read the bad offset with a console consumer to see why it fails. If it is bad data, I copy it to a quarantine topic, stop the group and reset its offset to just past the bad record. If it is a bug in my code, I fix and redeploy. Then I add a dead-letter flow so it never blocks again.

Situation. One partition has been stuck for an hour. Lag on it is climbing, other partitions are fine, and the logs repeat the same stack trace and the same offset every few seconds.

Check first. Take the offset from the log line and read exactly that record.

kafka-console-consumer.sh --bootstrap-server b1:9092 --topic orders \
  --partition 3 --offset 4812 --max-messages 1 \
  --property print.key=true --property print.headers=true

Decide the category: corrupt bytes or wrong schema (data problem), valid data that exposes a bug (code problem), or a valid record failing because a dependency is down (temporary, not poison at all; look at the exception).

Unblock now (data problem).

  1. Save the record: copy it to a quarantine topic or a file, with its offset, so nothing is lost.
  2. Stop the consumer group (the CLI refuses to change offsets for an active group).
  3. Move the offset just past the bad record, only on that partition:
kafka-consumer-groups.sh --bootstrap-server b1:9092 --group billing \
  --topic orders:3 --reset-offsets --to-offset 4813 --dry-run
# then --execute, and start the group again

Unblock now (code problem). Fix and redeploy; the record then processes normally and nothing is skipped. If the fix will take hours and the business can wait, skipping plus later replay of the quarantined record is an option.

Prevent for good.

  • ErrorHandlingDeserializer so deserialization failures become values, not poll exceptions.
  • A DefaultErrorHandler with a short back-off and limited attempts, and a DeadLetterPublishingRecoverer to orders.DLT with headers.
  • Mark permanent exceptions as not retryable.
  • Validate at the producer and enforce schema compatibility so bad data does not get in.
  • Alert on DLT arrivals and on lag age on any single partition; keep a replay tool and runbook.

The point to make aloud: one record must never be able to block a partition for an hour, and nothing may be skipped silently.

Remember: quarantine the record, skip one offset (or fix the bug), then add dead-letter handling so one record can never block a partition again.

One partition has ten times the lag of the others and one broker is at 90 percent CPU. What is happening? Senior

Key skew: one key, often a big tenant, produces most of the traffic and all of it lands in one partition. I confirm by sampling the keys on that partition, then spread the heavy key by salting it with a sub-key, or give that tenant its own topic.

Situation. A topic with 12 partitions is keyed by tenantId. Partition 7 has ten times the lag of the others, and the broker leading it is at 90 percent CPU while the others are calm.

Diagnose. Confirm it is key skew and not a stuck consumer.

  1. Per-partition bytes-in and message counts: partition 7 is far above the rest, so the data really is uneven (a stuck consumer would show equal bytes-in but growing lag).
  2. Sample the hot partition and count keys: 
    kafka-console-consumer.sh --bootstrap-server b1:9092 --topic events \
  --partition 7 --max-messages 5000 --property print.key=true | cut -f1 | sort | uniq -c | sort -rn | head
  3. If one tenant shows 80 percent of the sample, that is the culprit.

Why scaling does not help. Adding consumers or partitions will not split a single key; all records of one tenant hash to one partition, and one partition is read by one consumer. The leader broker for partition 7 also takes all that write and replication traffic.

Short-term relief. Give partition 7's consumer more headroom (faster pod, more CPU), parallelize inside the consumer by sub-key lanes if per-key order allows, batch downstream writes, and move other partition leaders off that broker (preferred leader and reassignment) to even broker load.

Real fix. Spread the heavy tenant. Change the key for heavy tenants to tenantId + ":" + (customerId.hashCode() mod 8) (via a custom partitioner or by building the key). The tenant now covers 8 partitions. Per-tenant order becomes per-customer order, so confirm the business can live with that. Switch at a clean point: drain the topic first, because records for a key before and after the change land on different partitions and may be processed out of order. For a very large or regulated tenant a dedicated topic is also reasonable.

Prevent. Choose a high-cardinality key at design time, load test with a realistic skew (the real tenant distribution, not uniform), and chart per-partition bytes and lag.

Remember: one partition lagging = skewed key. Salt the heavy key (or isolate the tenant) and accept weaker ordering; scaling consumers cannot split one key.

After the team added partitions to scale, events for the same customer are processed out of order. Why? Senior

Because the key-to-partition formula, hash(key) mod partitionCount, changed. For roughly half of the keys, new events go to a new partition while older events still wait in the old one, so two consumers handle the same customer at once. I make consumers version-aware to protect order, and in future drain the topic before adding partitions, or migrate to a new topic.

Situation. The team grew the accounts topic from 6 to 12 partitions to scale. Since then, for some customers, AccountClosed is occasionally processed before the earlier PaymentPosted.

Why. The producer chooses the partition with hash(key) mod partitionCount. The count changed from 6 to 12, so roughly half of the keys now map to a different partition. Example for customer 77: hash mod 6 = 3, but hash mod 12 = 9.

  1. At 10:00 PaymentPosted(77) goes to partition 3, where the consumer is 30 seconds behind.
  2. At 10:01 partitions are added.
  3. At 10:02 AccountClosed(77) goes to partition 9, whose consumer is idle and processes it at once.
  4. At 10:03 the P3 consumer reaches PaymentPosted(77): processed after the account closed.

Kafka never moves old records between partitions, so for a while the same key lives in two places and two consumers handle it independently.

Fix for the damage. Identify affected customers by comparing event timestamps or versions with the processing order in the logs or the database. Make the consumer defensive: store the last applied version per entity and ignore (or re-queue) events with an older version; re-apply the correct sequence for affected entities from the topic or the source system.

Strict order going forward. Options: (a) stop producers, let lag drain to zero, add partitions, restart (old data is no longer in play); (b) create a new topic with the right count, migrate producers and consumers, retire the old one; (c) carry a monotonic version or sequence in every event and enforce it in the consumer.

Prevent. Size partitions with headroom up front and treat the count of a keyed topic as fixed. If you must scale, use the drain procedure and announce it. Also check that other producers and languages use the same partitioner.

Remember: change N and the keys move. Drain first or migrate to a new topic, and carry a version in events so consumers can survive it.

Producers suddenly throw NotEnoughReplicasException. What does it mean and what do you do? Intermediate

It means at least one partition's in-sync replica set has fewer members than min.insync.replicas, and the producer uses acks=all, so the broker refuses the write on purpose to protect durability. The cause is usually a broker that is down or lagging. I restore it, and meanwhile retry or queue events instead of lowering min ISR.

Situation. Sends to the payments topic start failing with NotEnoughReplicasException (or NotEnoughReplicasAfterAppendException), while other topics keep working.

What it means. The topic has min.insync.replicas=2 (say), the producer uses acks=all, and the number of in-sync replicas of at least one partition has dropped to 1. The leader refuses the write on purpose, so that no acknowledged record ever exists on only one broker. The guard is doing its job; the question is why a replica is out.

Check first.

kafka-topics.sh --bootstrap-server b1:9092 --describe --under-min-isr-partitions
kafka-topics.sh --bootstrap-server b1:9092 --describe --topic payments

The describe output shows each partition's leader, replicas and ISR. Find the missing broker and why it is out: crashed or restarting, a full or slow disk, a network issue between brokers, a long GC pause, or an overloaded broker where followers cannot keep up. Only some partitions are affected: those that had a replica on the troubled broker.

Application side while it lasts. The producer retries for delivery.timeout.ms (default 2 minutes), so a quick recovery is invisible. For longer outages, do not lose the events: write them to an outbox table or a local buffer and retry later, or return "temporarily unavailable" to the caller. Make sure your callback handles the error.

What not to do. Do not lower min.insync.replicas to 1 just to silence the errors, because that quietly turns on the exact risk the setting prevents, unless the business explicitly accepts it for a time. Do not switch to acks=1 for the same reason.

Fix and prevent. The platform team brings the broker or disk back; wait until the ISR is full again. Alert on under-replicated partitions early (before they drop under the minimum), spread replicas across zones with rack awareness, keep brokers' disks and GC healthy, and run RF 3 so one broker failure still leaves min ISR 2 satisfied.

Remember: ISR below min.insync.replicas means writes are refused by design. Fix the broker; do not lower the guard.

A consumer was down over a long weekend and, after restart, it silently skipped a large chunk of data. Why? Senior

The data it needed aged out of retention while it was down, so its committed offset no longer existed. With auto.offset.reset=latest it jumped to the end and silently dropped everything it missed. I recover the gap from another source and set the reset policy to earliest or none.

Situation. A consumer service was down for a long weekend (4 days). Topic retention is 3 days. After restart it quietly continued from "now" and a large chunk of events was never processed. No exception, and no alert.

What happened.

  1. The group had committed offset 50,000 when it stopped.
  2. During the 4 days, retention deleted the oldest segments. The oldest remaining record is now offset 64,000.
  3. On restart the committed offset 50,000 is out of range (below the log start offset).
  4. The consumer applies auto.offset.reset. With the default latest it jumps to the end of the log, skipping both the deleted data and everything that still existed (64,000 up to now). With earliest it would start at 64,000, losing only the data already deleted.

The same thing happens for a group whose committed offsets expired: Kafka drops the committed offsets of a group with no members after offsets.retention.minutes (default 7 days).

Check and recover. Compare the group's committed offset and the topic's earliest offset (kafka-get-offsets.sh --time -2 and -1) to size the gap in records and time. Recover the missing data from another source: the producing system's database (replay the events or rebuild via a reconciliation), a downstream sink archive such as S3, a mirrored cluster, or backups. Then replay into the consumer with idempotent handling, using a separate group or temporary offset reset.

Prevent.

  • Set retention longer than your worst realistic outage plus time to react (and longer than the offset expiry assumption).
  • Choose auto.offset.reset=earliest (with idempotent consumers) or none so a gap is loud, not silent.
  • Alert when lag age approaches 50 to 70 percent of retention.
  • For critical topics keep an archive (a sink connector to object storage) or use tiered storage to retain more cheaply.

Remember: retention shorter than downtime plus auto.offset.reset=latest means silent data loss. Choose earliest or none, and alert on lag age against retention.

A producer team deployed a schema change and three consumers crashed. How do you respond and prevent it? Senior

I roll the producer back to stop new bad records, then deal with the records already written: skip them to a dead-letter topic or ship a consumer fix that reads both shapes. To prevent it, enforce schema compatibility checks in the registry and in CI so an incompatible change is rejected before deploy.

Situation. A producer team deployed a new version. Minutes later three consumer services crash with deserialization errors or NullPointerException. In the change, amount went from int to string, or customerId was renamed.

Immediate response (stop the bleeding).

  1. Roll back the producer (or disable the feature flag), so no more bad records are written.
  2. Bound the damage. Each record's schema id (or the producer's deploy time) tells you which offsets are in the new, broken shape. Note the partition and offset range per partition.
  3. Unblock consumers. For consumers stuck on a poison record, route those offsets to a dead-letter topic or skip them (reset offsets past the range after saving the records), or ship a quick consumer fix that can read both shapes.
  4. Repair and replay. Fix or transform the bad records and reprocess them with idempotent handlers. Alternatively have the producer republish the affected events in the old format.

Why did the registry not stop it? Either compatibility checking was set to NONE, the producer used auto-registration with a lax mode, a different subject was used, plain JSON had no registry at all, or the change was structurally compatible but semantically different (for example amount in dollars became cents; no registry can catch that). Find out which one.

Prevent.

  • Registry compatibility at BACKWARD_TRANSITIVE or FULL_TRANSITIVE for shared topics.
  • Disable auto-registration in production; register schemas from CI after a compatibility check against the registry.
  • A rule: never rename or retype fields; add a new optional field, migrate consumers, then remove the old one.
  • Consumer-driven contract tests and a staging environment where consumers replay real samples.
  • Tolerant readers (ignore unknown fields) and ErrorHandlingDeserializer plus dead-letter, so one bad record does not stop the service.
  • Talk to consumers before any semantic change.

Remember: roll back, bound the bad offsets, repair and replay, then make compatibility checks a deploy gate.

Every deployment causes duplicate processing and a burst of lag. How do you make deployments quiet? Senior

Pods are being killed mid-batch, so offsets are not committed and each restart triggers rebalances. I make shutdown graceful (catch SIGTERM, finish the batch, commit, close), use static membership with the cooperative assignor, and roll pods one or two at a time. The handler stays idempotent for leftover duplicates.

Situation. A rolling update of 10 consumer pods causes a wave of duplicate processing and a burst of lag every deploy. Logs show many rebalances and pods exiting in the middle of a batch.

Why it happens. Kubernetes sends SIGTERM and, after the grace period, SIGKILL. If the app ignores the signal, the process dies mid-batch: processed records are uncommitted (duplicates later), and the consumer never leaves the group, so the others wait for the session timeout before the partitions move, which makes lag spike. Each of 10 pods restarting also triggers its own rebalance, and under the eager protocol each one pauses the whole group.

The shutdown sequence to implement.

  1. On SIGTERM, stop accepting new work: call consumer.wakeup() (the only thread-safe consumer method), which makes a blocked poll() throw WakeupException.
  2. Finish the batch in progress (or hand it back safely).
  3. Commit the offsets of what was processed (commitSync()).
  4. consumer.close(), which leaves the group cleanly (unless static membership is used) so partitions are reassigned immediately.
try {
  while (true) { process(consumer.poll(Duration.ofMillis(500))); consumer.commitSync(); }
} catch (WakeupException e) {
  // expected on shutdown
} finally {
  try { consumer.commitSync(); } finally { consumer.close(); }
}

Spring Kafka does this on context close; make sure terminationGracePeriodSeconds is longer than your longest batch plus the container shutdown timeout (spring.kafka.listener.shutdown-timeout), and that the app handles SIGTERM (use a proper entry point so the JVM receives it).

Reduce rebalances. Static membership with group.instance.id from the StatefulSet pod name and a session timeout covering a restart (a restarted pod gets its partitions back with no rebalance), the cooperative assignor (or the new protocol), and maxUnavailable: 1 with maxSurge low so pods roll one at a time. Add readiness checks that wait until the consumer has joined before the next pod is taken down.

Plus. The handler stays idempotent for leftover duplicates. Prevent: a "deploy under load" test in staging, and rebalance count as a release metric.

Remember: wakeup, finish, commit, close. Static ids, cooperative assignor, and slow rolling updates.

Producers fail with RecordTooLargeException for some documents. What are your options? Intermediate

The default limit is about 1 MB. My preferred fix is the claim-check pattern: store the large payload in object storage and send a small event with the link, size and checksum. Raising the limits works but must be done consistently in several places and large records hurt memory and latency. Compression helps only if the data compresses well.

Situation. Some producers fail with RecordTooLargeException for documents of a few MB. The defaults allow roughly 1 MB per record.

Why there is a limit. Big records mean big batches, more memory in the producer, broker and consumers, slower replication and fetches, and head-of-line blocking (one large record delays smaller ones in the same partition). Kafka is tuned for many small and medium records, not files.

Option 1 (preferred): claim check. Store the large payload in object storage (S3, GCS, a file store) and publish a small event containing the location, size, content type and a checksum.

  1. Producer uploads invoice-9981.pdf to the bucket and gets a key.
  2. Producer sends {"invoiceId":9981,"uri":"s3://bucket/invoices/9981.pdf","bytes":5242880,"sha256":"..."} to Kafka (a few hundred bytes).
  3. Consumers that need the file fetch it on demand; others ignore it.

Remember to secure access (short-lived pre-signed links, not public URLs), set a lifecycle on the bucket to match your retention, and handle the case where the upload succeeded but the send failed (orphan files) or the other way round (upload first, then send).

Option 2: raise the limits. This works but must be consistent everywhere, or something will still fail:

WhereSetting
Producermax.request.size
Topic (or broker default)max.message.bytes (message.max.bytes on the broker)
Replicationreplica.fetch.max.bytes on the brokers
Consumermax.partition.fetch.bytes, fetch.max.bytes

If you miss one, producers or consumers get stuck (a consumer that cannot fetch a record bigger than its limit can wedge a partition on older clients).

Option 3: compression, or splitting. Compression helps if the data is compressible (JSON, text) but not for already-compressed files. Splitting a document into chunks with sequence numbers and reassembling it is complex and error-prone, so use it only if nothing else fits.

Decision. Payloads up to a couple of MB occasionally: raise limits carefully. Regularly large or unbounded: claim check.

Remember: keep Kafka records small. A big payload goes to object storage and Kafka carries the link, size and checksum.
