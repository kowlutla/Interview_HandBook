How to use this page

Each question is a collapsible. Try to answer aloud first, then open it. Every answer starts with a short "Say this" line you can speak in about 20 seconds, then explains the idea from scratch: what it is, why it exists, how it works with a small example, and what goes wrong in production.

Resilience questions are rarely about a single technique. Interviewers want to hear that you know what fails, how failure spreads, and which small mechanism stops it from spreading. A good habit: for any design, say "what happens when this dependency is slow, not just down?" Slow is worse than down, because slow ties up threads and connections, while down fails fast.

Availability math, SPOFs and redundancy

What is availability, and how is it measured? Basic

Say this: "Availability is the fraction of time, or better the fraction of requests, in which the system does its job correctly. I prefer the request-based form: good requests divided by valid requests, measured as close to the user as possible."

What it is. Availability answers one question: "when a user tries to use the system, does it work?" There are two common ways to turn that into a number.

  • Time-based: uptime / (uptime + downtime). Simple, but it needs a yes/no verdict for every minute.
  • Request-based: successful requests / valid requests. Large companies prefer this because real outages are rarely all-or-nothing.

Why request-based is better. Suppose a bug fails 30 percent of calls for one hour. In a time-based view the system was "up" (it answered something) or "down" (it was broken), and neither label fits. In a request-based view you simply count: 30 percent of one hour of traffic was bad. It also weights busy hours more than quiet ones, which matches what users feel.

Worked example. Last month the API served 100,000,000 valid requests. 40,000 returned 5xx or timed out. Availability = 99,960,000 / 100,000,000 = 99.96 percent.

Two decisions people forget:

  1. What counts as "successful"? A 200 response that takes 40 seconds is a failure for the user. So define success as "correct response within the latency target" (for example under 500 ms). A 404 for a missing item is a correct answer, but a 500 is not. Client errors (4xx) caused by the caller are usually excluded from the "valid" set.
  2. Who measures it? Measuring inside the service misses problems upstream of it: DNS, the load balancer, a broken TLS certificate, a network path. A probe from outside, or client-side telemetry, catches those. Large systems use both: server-side for diagnosis, external/client-side for the number you promise.

What an interviewer probes next: "How does this link to an SLO?" Availability is the SLI (the measurement); the SLO is the target (for example 99.9 percent over 30 days); the error budget is what is left (0.1 percent of requests may fail).

How much downtime does each "nine" allow? Basic

Say this: "99.9 percent is about 43 minutes a month, and every extra nine divides that by ten. Four nines is about four minutes a month, so you cannot reach it with humans in the loop. It needs automatic failover and automatic rollback."

Where the numbers come from. A 30-day month has 30 x 24 x 60 = 43,200 minutes. The allowed downtime is simply (1 - availability) x 43,200. For 99.9 percent: 0.001 x 43,200 = 43.2 minutes. For a year (525,600 minutes) the same 0.1 percent gives about 8.8 hours.

AvailabilityDowntime per yearPer 30-day month

99.9%about 8.8 hoursabout 43 minutes
99.95%about 4.4 hoursabout 22 minutes

99.999%about 5.3 minutesabout 26 seconds

Why this matters for design. Look at the time budget against the human response chain: an alert fires (1 to 5 minutes of detection), a person is paged and wakes up, logs in, understands the problem and acts (often 15 to 30 minutes). With a four-minute monthly budget, one slow human response already uses the whole year of budget. So the architecture decides:

  • Up to about 99.9 percent: a good on-call process plus redundancy is realistic.
  • 99.99 percent: automatic failover, automatic rollback of bad deploys, multi-AZ everywhere, no manual steps in the common failure paths.
  • 99.999 percent: multi-region active-active, cell-based isolation, and very strict change management. Very few services really need this, and it costs a lot.

Pitfall. Do not promise more nines than your dependencies allow (next question). Also ask whether planned maintenance counts; "five nines excluding maintenance windows" is a weaker promise than it sounds.

How do you compute the availability of a system built from several components? Intermediate

Say this: "Components in series multiply their availabilities, so the chain is always worse than its weakest link. Redundant components in parallel multiply their failure probabilities, so they get better. The catch is that the parallel math assumes independent failures, and shared parts break that assumption."

In series (every component must work). The request only succeeds if the load balancer, app and database are all up, so you multiply:

LB 99.99% x App 99.95% x DB 99.95%
= 0.9999 x 0.9995 x 0.9995 = 0.99890  (about 99.89%)

Every extra hard dependency costs you. Five dependencies at 99.9 percent each give 0.999^5 = about 99.5 percent, which is 3.6 hours of downtime a month before your own code even runs.

In parallel (any one is enough). The system fails only if all copies fail at once, so multiply the failure probabilities:

two replicas, each 99%:   failure = 0.01 x 0.01 = 0.0001   -> 99.99%
three replicas, each 99%: failure = 0.01^3       = 0.000001 -> 99.9999%

How to read this diagram. Top row: a request must pass through the load balancer, the app and the database in turn (the moving dashes), so all three must be up and their availabilities multiply. Bottom row: two replicas of the same thing sit side by side and either one can answer, so the service is down only when both fail at once, which is why the failure probabilities multiply instead.

Trap: the parallel formula assumes failures are independent. Two replicas in the same rack, same AZ, same deployment pipeline, or reading the same config file fail together. Real availability of "redundant" systems is capped by the shared parts: the deploy tool, DNS, the config store, and the human operator who can push one bad change to both copies.

How to improve a series chain. (1) Add redundancy to the weak link. (2) Turn hard dependencies into soft ones with fallbacks (cache, default, queue). (3) Remove steps from the critical path.

Say: "If my service has five hard dependencies each at 99.9 percent, I cannot promise better than about 99.5 percent unless I make some of them soft dependencies with fallbacks."
What is a single point of failure, and how do you find them in a design? Basic

Say this: "A single point of failure is any component whose loss takes the whole system down because there is no alternative. I find them by walking the request path and asking, for each box, 'if this vanished right now, what happens?' Then I remove each one with redundancy plus automatic failover, or by making the dependency optional."

Why it matters. A system is only as available as its worst SPOF. Putting five replicas of the app behind one load balancer gives you five-way redundancy for a tier that was never the weak point.

How to hunt for them. Draw the path of one request from the user to the data and back, then check three categories:

  • Obvious: one database primary, one load balancer, one app server, one cache node.
  • Hidden infrastructure: one DNS provider, one TLS certificate that can expire, one config or feature-flag service, one auth service, one message broker, one AZ, one cloud region, one CI/CD pipeline you need to ship a fix, one secrets store.
  • Logical SPOFs: a bad config pushed to all nodes at once, a shared library bug, a poison message that crashes every consumer in turn, a single account or credential used by everything.
  • People and process: one engineer who knows the runbook, one person with the keys.

Example. A design has three app servers, a replicated database and two load balancers. Looks fine. Walking the path reveals: all traffic enters through one DNS name hosted at one provider; the app reads feature flags from one service; a nightly job holds a lock in one Redis node. Three SPOFs, none of them in the main diagram.

Removing a SPOF. Either add redundancy (N+1 or more) with automatic failover, or demote it to a soft dependency (the app keeps the last known flags if the flag service is down).

Pitfall. Redundancy you never test is a SPOF you believe is gone. Fail over on purpose regularly (game days) to prove the spare works.

What types of redundancy exist (N+1, N+2, 2N, active-active)? Intermediate

Say this: "N+1 is one spare for N units, cheap and enough for one failure. N+2 also covers a failure during maintenance. 2N is a full duplicate. Active-active versus active-passive describes whether the spare serves traffic or sits idle. The key sizing point: surviving the loss of one of K zones means the others must absorb that share of traffic."

Let N be the number of units needed to carry peak load.

  • N+1: N units carry the load plus one spare. Cheap; survives a single failure. While one is down you run at full utilization of what is left, with no cushion.
  • N+2: survives one failure while another unit is being deployed or patched. Common for stateless tiers where rolling deploys take units out of service.
  • 2N: a full duplicate of everything. Expensive; used for critical facilities or entire regions.
  • Active-active: every copy serves traffic, so spare capacity is spread out rather than idle.
  • Active-passive: a standby sits idle until needed.

Sizing example across zones. You want to survive the loss of one AZ. Peak load is 300 units of work.

SetupEach AZ must carry after a lossMax normal utilizationTotal capacity needed
2 AZs100% of load (300)50%600
3 AZs150 each (50% more than 100)about 67%450
4 AZs100 each (33% more than 75)75%400

The pattern: more zones means less wasted headroom, since the spare share is 1/K. This is why "N+1 across AZs" costs more headroom than it sounds, and why three zones is the common default.

Pitfall. Autoscaling does not replace headroom: scale-up takes minutes, and a failover needs capacity immediately. Also remember the dependencies (database connections, downstream limits) must handle the shifted traffic too.

Why is making a stateless tier highly available easy but a stateful tier hard? Intermediate

Say this: "Stateless servers are interchangeable, so you run N behind a load balancer and nothing is lost when one dies. Stateful systems must keep copies of data consistent, and failover forces a choice between possibly losing recent writes or paying latency and availability to avoid it."

Stateless. A stateless server keeps nothing between requests that cannot be rebuilt (sessions live in a shared store or a signed token). Any instance can serve any request. If one dies, the load balancer stops sending it traffic, and the next request goes elsewhere. Scaling means adding more of the same.

Stateful. A database, queue or cache with data has a "memory" that matters. To survive a node loss, it must have copies. That immediately raises hard questions:

  1. How fresh is the copy? With asynchronous replication, the replica may be a few hundred milliseconds behind. Promote it and you lose those writes (non-zero RPO).
  2. Can we pay for fresher? Synchronous or quorum replication guarantees the copy has the write, but every write now waits for a remote acknowledgement (higher latency), and if the replicas are unreachable writes may be refused (lower availability). This is the CAP and PACELC trade-off.
  3. Who is the leader? Two nodes must never both accept writes. Detecting a dead leader versus a partitioned one is hard, hence split brain and the need for quorum and fencing.
  4. Recovery: a failed stateful node cannot simply be replaced by a blank one; it must resync gigabytes of data, which takes time and load.

Design rule. Push state into a small number of well-understood replicated stores (managed database, Kafka, object storage), and keep everything else stateless. Then HA effort goes to those few places.

Example. A web app stores sessions in memory on each server. A server dies, and those users are logged out. Moving sessions to a replicated store (or into signed cookies) makes the web tier stateless again, and the HA problem is reduced to that one store.

Failover, standby modes and health checks

Compare active-active and active-passive. When do you pick which? Intermediate

Say this: "Active-passive has one node serving and a standby waiting, so it is simple for consistency but has a failover gap and an untested standby. Active-active has all nodes serving, so failover is almost instant and hardware is used, but stateful data then needs partitioned ownership or conflict resolution. I pick active-active for stateless tiers and partitionable data, active-passive for strongly consistent single-writer data."

Active-passiveActive-active
TrafficPrimary serves, standby waitsAll nodes serve
Capacity useStandby idle (waste)Good use of hardware
FailoverNeeds detection and promotion, so a gap of seconds to minutesNear instant, remaining nodes absorb the load
Hidden riskStandby is untested and may not work when neededRemaining nodes may be overloaded after a loss; data conflicts if stateful
DataSingle writer, simple consistencyMultiple writers need conflict resolution or partitioned ownership

Walking through the difference. In active-passive, when the primary dies, something must notice, decide, promote the standby, and redirect clients. That chain is the gap, and each step can fail. In active-active, a load balancer simply stops sending to the dead node; the others already have warm caches and connections.

The catch with data. If two regions both accept writes to the same row, you need a rule for conflicts: last-write-wins (can silently lose an update), CRDTs (merge automatically, only for certain data shapes), or application merge logic. Many "active-active databases" avoid this by giving each partition one owner: users in Europe are owned by the EU region, US users by the US region. Each region is active, but each piece of data has a single writer.

Decision rule. Stateless or read-heavy: active-active. Relational primary with strong consistency: active-passive within a region (with sync replica in another AZ), and think hard before going multi-writer across regions. Whichever you pick, test the failover path regularly, because a standby that has never taken traffic is a hypothesis, not a fact.

What are hot, warm and cold standby? Basic

Say this: "Hot standby is running with continuously replicated data and takes over in seconds. Warm is running at reduced size and needs scale-up, so minutes. Cold is only backups and infrastructure code, so hours. It is a cost versus recovery-time trade-off set by the business RTO and RPO."

  • Hot: a full copy of the environment is running and data is replicated continuously. It can take traffic in seconds. Highest cost (you pay for two environments), lowest recovery time and data loss.
  • Warm: the environment exists but scaled down: a small replica, or servers at minimum size, with data replicated but maybe delayed. On failover you scale up and then switch traffic. Typical recovery: minutes to tens of minutes.
  • Cold: nothing runs. You have backups and infrastructure-as-code. In a disaster you build the environment, restore data, and switch. Cheapest to hold; recovery is hours or more, and data loss is as old as the last backup.

Example. A payments API with an RTO of 1 minute needs hot (or active-active). An internal reporting tool that can be down for a day can be cold: backups copied to another region and Terraform to rebuild.

Rule. Match the standby type to the cost of downtime. Do not pay hot-standby prices for systems whose outage costs little, and do not leave cold standby on systems whose outage costs millions an hour. Also note a warm standby must be proven to scale up in time; many have found at the moment of need that the account limits or capacity were not there.

Walk through what actually happens during an automatic database failover. What can go wrong? Senior

Say this: "Detect the failure, confirm with a quorum so it is not just a partition, fence the old primary, promote the most up-to-date replica, redirect clients, then re-attach the old primary as a replica. What goes wrong: false positives and flapping, lost async writes, split brain if fencing fails, stale DNS and connection pools, and a cold new primary getting hit by a retry storm."

  1. Detect. A monitor misses heartbeats from the primary for N seconds (for example 10 s).
  2. Confirm. A quorum or consensus service (several independent observers) agrees the primary is gone, to avoid acting on one observer's bad network view.
  3. Fence. Cut the old primary off so it cannot accept writes if it wakes up: revoke its storage access, remove it from the network, or power it off (STONITH). Without this you risk two primaries.
  4. Promote. Choose the replica with the most recent log position (least data loss) and make it writable.
  5. Redirect. Clients must find the new primary: DNS update, a virtual IP moves, a proxy repoints, or the client library rediscovers through a cluster endpoint.
  6. Repair. Other replicas follow the new primary. The old primary comes back as a replica after catching up, or after rewinding any writes it had that the new primary does not have.

What goes wrong, and how each is handled.

  • False positive / flapping: a network blip triggers a needless failover, and then another. Use quorum, a minimum time, and a cool-down between failovers.
  • Lost writes: with asynchronous replication the promoted replica may lack the last moments of commits. Accept it (RPO above zero), or use semi-synchronous replication so at least one replica acknowledged each commit.
  • Split brain: fencing failed, both accept writes. Prevent with fencing tokens and majority quorum.
  • Stale clients: DNS caches and long-lived connection pools still point at the old primary and error out. Use low TTLs, drop connections on failover, and use client libraries that re-resolve.
  • Promoted replica far behind: large replication lag means big data loss or a long catch-up. Monitor lag and refuse to promote very stale nodes automatically.
  • Cold new primary: its caches and buffer pool are empty, so it is slow exactly when load is shifted to it.
  • Retry storm: clients that failed for 30 seconds all retry at once and overload the fresh primary. Use backoff with jitter and connection limits.

Tuning trade-off. A short detection window means faster recovery but more false failovers; a long one means longer outages. Most managed databases take from tens of seconds to a couple of minutes end to end. Quote a number only for the specific product, and hedge it.

What is split brain and how do you prevent it? Intermediate

Say this: "Split brain is two nodes both believing they are the leader and both accepting writes, so the data diverges. It is caused by treating a network partition as a node death. I prevent it with majority quorum, fencing tokens, and sometimes STONITH, using an odd number of voters."

How it happens. A cluster has primary P and standby S. The network link between them breaks (P is fine, just unreachable). S sees no heartbeats and concludes P is dead, and promotes itself. Now P still serves its local clients, and S serves others. Both accept writes; later, when the link heals, you have two different histories to merge, and no automatic way to know which to keep.

Prevention techniques.

  • Majority quorum: a node may be leader only if it can talk to more than half of the voters. In a partition of 5 nodes into 3 and 2, only the 3 side has a majority, so only one leader can exist. This is why you use an odd number of voters (3 or 5): with 2 nodes, a partition leaves neither with a majority.
  • Fencing tokens: each new leader gets a number that grows by one (1, 2, 3...). The storage layer remembers the highest token it has seen and rejects writes with an older one. A paused old leader that wakes up with token 4 is refused because token 5 already exists. This also defends against long GC pauses, where a leader does not know its lease expired.
  • STONITH (shoot the other node in the head): power off or isolate the other node through a separate path before taking over.
  • Leases: leadership expires unless renewed; the old leader must stop acting when its lease time passes. This relies on bounded clock drift, so give a safety margin.

Pitfall. A two-node cluster with no tie-breaker cannot be both safe and automatic. Add a third voter (a witness, which can be a tiny node holding no data) in a third failure domain.

What is a health check? How do liveness, readiness and deep checks differ? Basic

Say this: "A health check is a probe that tells the load balancer or orchestrator whether to send traffic to an instance or restart it. Liveness means restart me, readiness means do not send me traffic yet, and the danger is deep checks that call dependencies, because a shared dependency problem can then remove every instance at once."

  • Liveness: is the process alive and not stuck? Failure means the orchestrator restarts it. Keep it trivial (return 200 from the event loop; no dependency calls).
  • Readiness: can it serve traffic right now (warmed up, config loaded, connections ready)? Failure means remove it from the load balancer, but do not restart it. It may recover by itself.
  • Startup: gives slow-booting apps time before liveness checks begin, so they are not killed during boot.
  • Shallow vs deep: shallow checks only the process. Deep checks exercise dependencies such as the database.

Why the distinction exists. "Restart" and "stop sending traffic" are different remedies for different problems. A deadlocked process needs a restart. A process that is busy loading a cache only needs to be left alone for a while.

The deep-check disaster, step by step.

  1. The database slows down for 20 seconds.
  2. Every app instance's health check (which runs a DB query) times out.
  3. The load balancer marks all instances unhealthy and removes them.
  4. Users now get errors from the load balancer itself, even for pages that did not need the database.
  5. When the DB recovers, all instances come back at once into a thundering herd.
Trap: a partial dependency problem becomes a total outage, and a liveness probe that fails because a dependency is down creates a restart loop that makes things worse. Prefer shallow liveness, readiness that checks only local state, and handle dependency failures inside the request path with timeouts, breakers and fallbacks. Many load balancers also have a "panic" or fail-open mode: if all targets look unhealthy, send traffic to all of them anyway.
How do you tune health check interval, threshold and timeout? Intermediate

Say this: "Detection time is roughly interval times the unhealthy threshold. Faster detection costs false positives. I use a threshold of 2 to 3 to filter noise, a probe timeout shorter than the interval, and I combine active probes with passive outlier detection on real traffic."

The arithmetic. Check every 5 s, eject after 3 consecutive failures: detection takes about 15 s (up to 20 s depending on where in the cycle the failure begins). During that window, roughly 15 s of traffic to that node fails or is slow.

SettingToo lowToo high
IntervalProbe load, noiseSlow detection
Unhealthy thresholdOne dropped probe or GC pause ejects a good node (flapping)Long time sending traffic to a dead node
Healthy thresholdNode rejoins before it is truly ready, then flapsSlow recovery of capacity
Probe timeoutSlow-but-fine nodes ejectedProbes overlap, hide failures

Keep the probe timeout shorter than the interval, and generally require more successes to rejoin than failures to eject (asymmetry avoids flapping).

Passive checks. Active probes only test the probe endpoint, not real requests. Passive health checking (outlier detection) watches actual traffic: if a host returns, say, five 5xx in a row or has a latency far above its peers, eject it for a while. It detects failure at request speed with no extra load, and catches problems a simple endpoint hides. Use both: active for idle hosts and startup, passive for real behaviour.

Pitfall. Do not eject more than a fraction (for example 50 percent) of hosts by outlier detection, otherwise a fleet-wide problem makes the remaining hosts overloaded.

What is a gray failure and why is it hard? Senior

Say this: "A gray failure is a component that is neither fully up nor fully down. It passes health checks but is slow, drops some requests, or has one bad disk. Binary detection misses it, and it keeps getting its full share of traffic. Defences are outlier detection on real traffic, client-side observation, comparing against peers, and balancing that favours fast nodes."

What it looks like. A host's health endpoint returns 200 in 2 ms, but real requests that touch a failing disk take 3 seconds. Or a network card drops 5 percent of packets. Or a node has a memory leak and spends most of its time in GC. The monitoring system says "healthy", while users on that node suffer.

Why it is hard.

  • The probe and the real workload exercise different code paths, so the probe says fine.
  • The component reports on itself, and its self-view is wrong.
  • Impact is partial: averages hide it, only tail latency (p99) and per-host error rates reveal it.
  • With many hosts, one in a hundred being bad is just a small bump in the fleet-wide average.

Defences.

  1. Outlier detection: compare each host with the fleet and eject hosts whose error rate or latency is far above the median, for a back-off period.
  2. Observe from the client side: the caller sees what users see. Look at per-target error and latency from the callers' perspective.
  3. Smart load balancing: least outstanding requests or power-of-two-choices naturally send less traffic to slow nodes.
  4. Hedged requests: send a second copy of a read after the p95 delay, so the caller is masked from one slow host.
  5. Deep, realistic synthetic probes that do a representative operation, used for alerting (not for removing hosts from the load balancer).

Example. Cloud providers have published that many large incidents began as gray failures: the failure detector said "alive", yet applications were failing. This is why modern fleets look at per-instance request metrics, not just heartbeat.

Can you use DNS for failover? What are the limits? Intermediate

Say this: "Yes, health-checked DNS can steer clients to a healthy endpoint, but failover takes tens of seconds to minutes because of TTLs and clients that cache beyond them. For faster switching I use anycast or a global load balancer, or a virtual IP inside a site."

How it works. A DNS service health-checks your endpoints. Normally the name api.example.com resolves to the primary's IP. When the primary fails its checks, DNS starts returning the secondary's IP (failover routing), or removes the unhealthy IP from a weighted set.

Why it is slow and imperfect.

  • TTL: resolvers cache an answer for the TTL (say 60 s), so some clients keep using the dead IP for up to a minute.
  • Caching beyond the TTL: some resolvers, operating systems and applications ignore or extend TTLs. A JVM caches DNS answers for a long time in some configurations, and long-lived connection pools never re-resolve.
  • Detection time: the DNS health checks themselves need a few cycles, adding 30 to 90 seconds before the record even changes.
  • Granularity: you cannot easily steer one user's flow; DNS gives each resolver one answer for a while.

Mitigations. Use short TTLs (30 to 60 s) on failover records, accept the extra DNS query volume, make clients re-resolve and recycle connections periodically, and for sub-second switching use something that does not depend on DNS cache: anycast IPs (the same IP announced from several places; routing sends users to a healthy one), a global load balancer, or inside a data centre a floating virtual IP that moves between nodes.

Rule of thumb. DNS failover is fine for regional DR where a minute or two is acceptable. It is the wrong tool when your RTO is seconds.

Timeouts and retries

Why must every remote call have a timeout? Basic

Say this: "Without a timeout, a call to a hung dependency holds a thread, connection or socket forever. In-flight work grows until the pool is exhausted, and a dependency failure becomes my own outage. Timeouts turn an unbounded wait into a bounded, handled error."

The mechanism, with Little's law. Little's law says the number of requests in flight = arrival rate x time each takes. At 500 requests per second and a normal latency of 20 ms, you have 500 x 0.02 = 10 busy threads. Now the dependency hangs and each call takes "forever":

  1. Time 0: dependency stops answering. 10 threads are stuck.
  2. After 0.1 s: 50 requests have arrived, 50 threads are stuck.
  3. After 0.4 s: all 200 threads of the pool are stuck.
  4. From then on every request, even ones that never touch that dependency, waits for a free thread and fails.

Your service is now down, though only a dependency failed. That is how a slow service becomes a cascading outage. With a 200 ms timeout the same calls free their threads after 0.2 s, and the thread count stays bounded at roughly 500 x 0.2 = 100.

What to set. Many default client timeouts are infinite or very long (some HTTP clients, JDBC without a socket timeout, some DNS and TLS paths). Set explicitly:

  • Connect timeout: how long to establish the connection (short).
  • Read (response) timeout: how long to wait for data.
  • Overall deadline: a cap on the whole operation including retries.
  • Pool-acquire timeout: how long to wait for a connection from the pool. This is easily forgotten.

Pitfall. A timeout only frees the caller. The server may still be doing the work, and the effect may still happen. So a timeout is not a "no": it is an "I do not know", which is why retries need idempotency.

How do you choose a timeout value? Intermediate

Say this: "I base it on the measured latency distribution of the dependency, slightly above its healthy p99 or p99.9, and make sure it fits inside the caller's total budget including any retry. I do not guess, and I revisit it with real data."

Step by step.

  1. Measure. Look at the dependency's latency percentiles when healthy. Example: p50 = 15 ms, p99 = 80 ms, p99.9 = 150 ms.
  2. Pick a value above the healthy tail. A timeout of 200 to 300 ms here cuts off genuine failures but rarely healthy requests.
  3. Check the budget. If your API promises 1 s total and calls three dependencies in sequence, the sum of their timeouts (plus one retry for some) must stay below 1 s. Maybe 250 ms each, with a deadline for the whole request.
  4. Separate connect from read. Connect inside a data centre should be tiny (tens to hundreds of ms): if a TCP connection takes a second, something is wrong.
  5. Review. Alert when calls get close to the timeout; that is an early warning.

Pitfall. One timeout for everything. A cheap key lookup and a heavy report query need different values. Use per-operation timeouts.

What is deadline propagation and why use it instead of per-hop timeouts? Senior

Say this: "The entry point sets one deadline for the whole request and passes the remaining time down the call chain. Each service uses only what is left and stops when it passes, instead of every hop having its own independent timeout. This stops layers from working on a request the user abandoned long ago."

The problem with independent timeouts. Suppose A calls B with a 1 s timeout, B calls C with a 2 s timeout, and C is slow (takes 5 s).

  1. At 1 s, A gives up and (often) retries. The user may have given up too.
  2. B is still waiting on C until 2 s, and C is still working until 5 s.
  3. All of that work is for a request no one is waiting for, and A's retry creates a new copy of it. This is amplification, and it happens at exactly the moment capacity is scarce.

How a deadline works.

User -> A: deadline = now + 1000 ms        (sent as header or context)
A -> B:   remaining = 1000 - 40  = 960 ms
B -> C:   remaining =  960 - 100 = 860 ms
C: if remaining <= 0, refuse to start; if work needs 300 ms and only 200 ms remain, fail early

Each service subtracts its own time and passes on the rest. If the deadline has passed, work stops right away and the server can drop queued requests whose deadline is already over. gRPC supports this natively (deadlines propagate in the context); with HTTP you pass a header such as a remaining-time-in-ms value, and propagate it in your client library.

Implications. Nested timeouts must decrease as you go down the chain. A call should not start a retry if the remaining time is less than a typical call. Convert between absolute times carefully (clock skew), so many systems pass "remaining milliseconds" rather than a wall-clock instant.

When should you retry a failed request, and when should you not? Basic

Say this: "Retry only when the failure is probably transient and the operation is safe to repeat. Do not retry client errors, deterministic bugs, or non-idempotent operations without an idempotency key, and never retry without bounds on a system that may be overloaded."

RetryDo not retry

Why not always retry? A retry is extra load. If a dependency is failing because it is overloaded, every retry makes things worse. With 1,000 clients each retrying 3 times, the failing dependency sees up to 4x its normal load at the worst moment.

Rules of a safe retry policy.

  1. Limit attempts (2 to 3 total is typical).
  2. Use exponential backoff with jitter.
  3. Use a retry budget so a mass failure does not multiply traffic.
  4. Retry at one layer of the call chain only.
  5. Respect the overall deadline.
  6. Honour Retry-After from the server.

Example. A payment call times out. Is it safe to retry? Only if it carries an idempotency key; otherwise the first call may have charged the card and the retry charges again.

What is exponential backoff with jitter, and why do you need the jitter? Intermediate

Say this: "Backoff waits longer after each failed attempt, doubling up to a cap, giving the dependency time to recover. Jitter randomizes the wait so thousands of clients do not retry in synchronized waves. Backoff controls how long, jitter controls when, and a cap plus attempt limit controls how much."

Backoff. Wait 100 ms, then 200, 400, 800, and so on, never above a cap such as 20 s, and give up after a max number of attempts.

Why jitter. Imagine 10,000 clients all fail at the same instant (the server blipped). Without jitter they all retry at +100 ms, then all at +300 ms, then +700 ms. The server sees spikes of 10,000 requests at exact intervals, each large enough to knock it over again. Jitter spreads each wave over a window, so the load arrives as a smooth stream instead of a spike. That is the difference between a thundering herd and a trickle.

full jitter:         sleep = random(0, min(cap, base * 2^attempt))
equal jitter:        t = min(cap, base * 2^attempt); sleep = t/2 + random(0, t/2)
decorrelated jitter: sleep = min(cap, random(base, prev_sleep * 3))

Worked example (full jitter, base 100 ms). Attempt 1: random between 0 and 200 ms. Attempt 2: between 0 and 400 ms. Attempt 3: between 0 and 800 ms. Different clients get different values, so retries are spread out.

AWS's well-known analysis found full jitter completes the total work in the least time under contention. Equal jitter keeps a minimum wait, which gives the server a guaranteed pause but with less spreading.

Pitfalls. Backoff without a cap can reach minutes; a cap without an attempt limit retries forever. Do the same for reconnects (websockets, Kafka clients, database pools), where a restart makes every client reconnect simultaneously.

What is retry amplification? Give a numeric example. Senior

Say this: "If every layer of a call chain retries independently, the attempts multiply. With a chain of four services where each caller tries 3 times, the deepest dependency can see 27 attempts for one user request. A dependency that is merely struggling then gets several times its normal load, and cannot recover."

Numbers. Chain: User calls A, A calls B, B calls C, C calls D. Each caller makes up to 3 attempts (1 original plus 2 retries) when its call fails. D is failing.

  • A tries B 3 times.
  • For each of those, B tries C 3 times, so 3 x 3 = 9 attempts at C.
  • For each of those, C tries D 3 times, so 27 attempts at D.

One user request has become 27 load units on D. If 1,000 users per second arrive, D sees up to 27,000 per second instead of 1,000. And since D was failing because of load, this pushes it down for good.

How to read this diagram. Each box is a service in a call chain, and each one retries its downstream call up to 3 times. The numbers underneath count the attempts reaching each hop for one user request: 1 at A, 3 at B, 9 at C and 27 at the failing service D. The arrows animate from left to right to show the load growing as it moves toward the service that can least afford it.

Fixes.

  1. Retry at one layer only (usually the edge or the layer that understands the operation best). Lower layers fail fast.
  2. Retry budgets so retries stay a small fraction of traffic.
  3. Propagate hints such as a retry-attempt count or "do not retry" header, so servers can shed retried traffic first.
  4. Deadlines so abandoned requests are dropped.
  5. Circuit breakers to stop calls to D altogether.
What is a retry storm and how does it keep an outage going after the root cause is fixed? Senior

Say this: "A retry storm is a feedback loop. A slowdown causes timeouts, clients retry, the retries raise load, which causes more timeouts. The system settles into a metastable state where the retry load alone keeps it overloaded even after the original trigger is gone. Recovery needs active action to cut load."

The loop, step by step.

  1. A database failover or deploy makes the service slow for 40 seconds.
  2. Clients' requests time out. Each client retries (3 attempts), so the load becomes about 3x normal.
  3. The service has capacity for 1x. It cannot catch up, and queues grow. Latency stays high, and requests keep timing out.
  4. The original trigger ended long ago, but offered load (new requests plus retries plus abandoned work still in queues) is still above capacity. The service stays down.

This is a metastable failure: the system has two stable states (healthy, overloaded) and a trigger pushed it into the bad one; it will not return by itself.

How to recover. Break the loop by reducing load below capacity: shed load aggressively, turn off retries (config flag or at the proxy), stop or throttle non-critical clients, scale out if it helps, restart in a throttled, staged way, and ramp traffic back in steps (10, 25, 50, 100 percent).

How to prevent it. Backoff with jitter, retry budgets, circuit breakers, server-side load shedding and queue-age limits, deadlines, and capacity headroom. Google's SRE writing and AWS's builders library describe this; several well-known outages have had a retry or reconnect storm as the amplifier.

What is a retry budget? How is it different from a fixed retry count? Senior

Say this: "A fixed count says each request may retry 3 times, so a full outage triples traffic. A retry budget caps retries as a fraction of overall traffic, for example at most 10 percent of requests in the last minute. During an outage the budget empties and clients just fail fast, so load rises by at most about 10 percent."

Compare under two situations. Normal: 100 requests per second, 1 percent fail transiently.

Fixed count (3 retries)Budget (10 percent)
Normal day (1 percent fail)about 1 retry per second addedabout 1 retry per second added (under the cap)
Full outage (100 percent fail)100 x 3 = 300 extra per second, 4x totalcapped at 10 extra per second, 1.1x total

How to build one. A token bucket where each successful (or each original) request adds a fraction of a token (say 0.1) and each retry takes a whole token. When failures are rare the bucket has tokens; when everything fails, successes stop refilling it and retries stop. Alternatively a sliding-window ratio: allow a retry only if retries / total requests over the last minute is below 10 percent. Often a small minimum (a few retries per second) is allowed so low-traffic clients can still retry.

Where it exists. Envoy has retry budgets (and a limit on concurrent retries), gRPC has retry throttling using a token bucket, and Finagle has a retry budget. The budget is shared per client or per upstream cluster, not per request.

Why it works. It encodes the right insight: retries help with rare independent failures, and hurt with systemic ones. The budget lets the first help while limiting the second.

What is idempotency and why is it required for safe retries? Basic

Say this: "An operation is idempotent if doing it several times has the same effect as doing it once. It matters because on a timeout the client cannot know whether the server did the work. A retry of a non-idempotent call may charge the customer twice, so either the operation is naturally idempotent or it carries an idempotency key."

Examples.

  • Naturally idempotent: "set the email to a@b.com" (HTTP PUT), "delete order 17" (DELETE), "mark task done". Repeating gives the same final state.
  • Not idempotent: "add 100 dollars to the balance", "create an order", "send an email", POST in general.

Why timeouts make it essential. The client sends "charge 50 dollars". The server charges, but the response is lost (network drop) or slow. The client sees a timeout. There are three possible truths: the request never arrived, it arrived and did nothing yet, or it completed. The client cannot tell which. If it retries a plain POST, in the third case the customer is charged twice. If it does not retry, in the first case the customer is never charged.

Making a non-idempotent operation safe. The client creates a unique idempotency key for the logical operation and sends it on every attempt. The server remembers keys it has processed and returns the saved result instead of doing the work again (next question gives the mechanism). Message consumers on at-least-once queues need the same: dedupe on message id.

Another approach. Reshape the operation to be idempotent: instead of "add 100", send "set balance to 600 given version 7" (a conditional update), or "apply transaction T123" where T123 is recorded once.

How do you implement idempotency keys on the server? Intermediate

Say this: "The client sends a unique key with every attempt of the same logical operation. The server atomically claims the key in a store with a unique constraint, ideally in the same transaction as the business write, saves the response, and returns that saved response for any repeat. The check and the claim must be one atomic step."

  1. Client generates a unique key (a UUID) per logical operation, and sends the same key on the first try and every retry (for example an Idempotency-Key header).
  2. Server does an atomic insert of the key into a table with a unique constraint, together with the business write in one transaction where possible.
  3. If the key is new: process the request and store the response (or its outcome) with the key.
  4. If the key exists and is complete: return the stored response without redoing the work.
  5. If the key exists and is still in progress: return a conflict, or make the caller wait briefly.
  6. Expire keys after a window (for example 24 hours) so the table does not grow forever.
BEGIN;
INSERT INTO idempotency(key, request_hash, status) VALUES ('k-123', 'h', 'in_progress');  -- fails if key exists
INSERT INTO payments(...);                                 -- the actual work
UPDATE idempotency SET status='done', response='...' WHERE key='k-123';
COMMIT;
Trap: checking "have I seen this key?" with a SELECT and then doing the work is a race: two concurrent retries both see "not seen". The check and the claim must be atomic (unique-constraint insert or a conditional write). Also store a hash of the request body: if a key is reused with a different body, return an error instead of the old response. And what about the call to a third party that is not idempotent? Pass your key to them if they support it, or record intent before and reconcile afterward.

For queue consumers: the same idea appears as a dedupe table keyed by message id, written in the same transaction as the side effect.

What are hedged requests and when do they help? Senior

Say this: "A hedged request sends the same read to a second replica if the first has not answered within about the p95 latency, uses whichever replies first and cancels the other. It cuts tail latency for about 5 percent extra load. Use it only for idempotent reads, with cancellation, within a retry budget, and not when the system is already overloaded."

Why tail latency matters. If one request fans out to 100 backends, and each has a 1 percent chance of being slow, then the chance at least one is slow is 1 - 0.99^100 = about 63 percent. So the user-visible slowness is dominated by the tail of the backends (Google's "The Tail at Scale").

How it works.

  1. Send the request to replica 1.
  2. Wait for the p95 latency (say 10 ms).
  3. If no answer yet, send the same request to replica 2.
  4. Take the first answer, cancel the other request.

Only about 5 percent of requests wait past p95, so only about 5 percent of requests produce a second copy: a small cost. But a slow request now has a second chance on a different host, so the 99.9th percentile drops sharply. Google reported large p99.9 reductions from hedging in some benchmark cases.

Conditions.

  • Idempotent and side-effect free (reads, or writes with idempotency keys).
  • Send to a different replica, not the same one.
  • Cancel the loser to free capacity.
  • Keep hedges inside the retry budget, and disable them under overload (otherwise they amplify).

It also helps with gray failures: one slow node is masked because the second copy goes to a healthy one.

Circuit breakers and bulkheads

What is a circuit breaker and what problem does it solve? Basic

Say this: "A circuit breaker wraps calls to a dependency and watches their failures. When failures pass a threshold, it opens and rejects calls immediately, instead of letting each caller wait for a timeout. That protects the caller from tied-up threads and gives the sick dependency a break so it can recover."

The problem. A dependency is failing. With only timeouts, every request still tries the call and waits the full timeout (say 2 s) before failing. At 500 requests per second, that is up to 1,000 threads tied up, and the dependency keeps receiving full load while it is trying to recover. The caller is slow and the dependency is not helped.

What the breaker does. It counts recent failures. When they cross a threshold (for example 50 percent of the last 20 calls), it "trips". For the next 30 seconds, calls fail instantly (microseconds) or return a fallback, without touching the dependency. After that, it lets a few trial calls through to check whether things are better.

Benefits.

  • The caller does not waste threads and latency on doomed calls (fail fast).
  • The dependency gets relief from load, helping it recover.
  • Failures become a clear, measurable signal (breaker state is a metric and alert).
  • A natural place to attach a fallback.

The name comes from the electrical breaker, which trips to prevent damage and is later reset. In Java, libraries include Resilience4j (and the older Hystrix); service meshes and proxies such as Envoy offer outlier detection which has similar effect.

Explain the three states of a circuit breaker. Intermediate

Say this: "Closed means calls flow and failures are counted. Open means calls are rejected immediately for a cool-down. Half-open means after the cool-down a few trial calls are allowed: if they succeed the breaker closes, if one fails it reopens, often with a longer wait."

How to read this diagram. Start at CLOSED (normal). Too many failures move it right to OPEN, where calls are rejected at once. After the wait expires it moves to HALF-OPEN and lets a few trial calls through. The green curved arrow back to CLOSED means the trials succeeded; the red arrow back to OPEN means a trial failed and the wait starts again.

A timeline example. Settings: trip at 50 percent failures over the last 20 calls, open for 30 s, 3 trial calls.

  1. t=0 to 100 s, CLOSED: normal. A dependency problem starts at t=100.
  2. t=104: 10 of the last 20 calls failed. Breaker goes OPEN. Callers now get an instant error or fallback.
  3. t=134: 30 s passed. Breaker goes HALF-OPEN and allows 3 calls.
  4. If those 3 succeed: breaker goes CLOSED, counters reset. If one fails: back to OPEN for another cool-down (possibly longer, for example 60 s).

Why half-open exists. Without it, you would either never reopen (the dependency recovers but you never know) or reopen fully and send all traffic into a service that may still be weak. Half-open is a controlled test with minimal load.

How do you tune a circuit breaker? What mistakes are common? Senior

Say this: "Use a failure rate over a sliding window with a minimum call volume, count timeouts and slow calls as failures, exclude client errors, set an open duration long enough for recovery, allow few half-open probes, have one breaker per dependency, and define a real fallback. The common mistakes are too-sensitive breakers that flap, global breakers, no fallback, and per-process breakers that do not share state."

  • Failure measure. Use the failure rate over a sliding window (for example 50 percent of the last 20 calls, or of the last 10 s). Require a minimum request volume (for example at least 20 calls) so that two failures out of three at 3 AM do not trip it. Also count slow calls using a slow-call-rate threshold: a dependency answering in 8 s is as bad as one failing.
  • Which errors count. 5xx, timeouts and connection errors. Do not count 4xx caused by a bad request or a business "not found": that is the caller's issue, not dependency health.
  • Open duration. Long enough to recover (seconds to a minute), possibly growing with each failed probe (exponential).
  • Half-open probes. A few, so a recovering service is not slammed.
  • Granularity. One breaker per dependency (or per endpoint or per host), not one global one. A breaker per host isolates one bad instance; a breaker per service reacts to whole-service failure. A single breaker for "all external calls" lets one bad API shut off the healthy ones.
  • What happens when open. Have a defined fallback: cached value, default, queue for later, or a clear fast error. A bare exception is only half a solution.
Trap: breakers that live in each client process do not share state. A fleet of 1,000 clients each needs to see failures before tripping, and they probe at different times. A too-sensitive breaker flaps open and closed and becomes the cause of an outage itself. A breaker on a low-traffic dependency never gathers enough samples to trip (or trips on noise). Always emit breaker state as a metric and alert when it opens.
How do circuit breakers, timeouts and retries fit together? Intermediate

Say this: "Timeouts bound each call. Retries cover transient errors. The breaker notices persistent errors and stops both calls and retries. Typical nesting, outermost first: fallback, bulkhead, circuit breaker, retry with backoff and budget, timeout around each attempt."

fallback( bulkhead( circuitBreaker( retry( timeout( call ) ) ) ) )

What each contributes.

  • Timeout: turns a hang into a failure the others can see. Without it, the breaker never records slow failures.
  • Retry: masks brief, random failures (one dropped connection).
  • Breaker: stops the retry-fueled hammering when the failure is not brief. When open, retries must not run: rejecting immediately is the whole point.
  • Bulkhead: caps how much of your capacity this dependency can ever use.
  • Fallback: what the user sees when all else fails.

Why none is enough alone. Retries without a breaker amplify load on a failing dependency. A breaker without timeouts never sees the slow failures. Timeouts without retries expose users to every blip. Without a bulkhead, one dependency can still use all threads before the breaker trips.

Subtle point. Does a retry-exhausted failure count as one failure or several for the breaker? Decide: usually the breaker sits outside the retry and counts the final result, but some libraries count each attempt. Know which yours does.

What is the bulkhead pattern? Give an example. Intermediate

Say this: "Bulkheads isolate resources so a failure in one part cannot sink everything, like watertight compartments in a ship. Give each dependency, tenant or request class its own thread pool, connection pool, semaphore or queue with a hard cap."

Example, step by step. A service calls Payments and Recommendations, sharing one pool of 200 threads.

  1. Recommendations becomes slow (each call takes 20 s).
  2. Requests keep arriving, each grabbing a thread that then waits on Recommendations.
  3. Within seconds all 200 threads are stuck waiting.
  4. Checkout requests (Payments) cannot get a thread, and the whole service is down, because of a nonessential feature.

With separate pools (for example 150 for Payments, 30 for Recommendations, 20 reserved) the Recommendations pool fills up and starts rejecting immediately (fail fast), but Payments still has its 150 threads and checkout keeps working.

How to read this diagram. One service splits its worker threads into separate pools, one per dependency. The Recommendations pool is full because that dependency is slow, so new calls to it are rejected immediately (red arrow). The Payments pool is untouched and keeps serving (green arrow), so the slow dependency cannot use up the threads checkout needs.

Other bulkheads.

  • Separate clusters for internal versus public traffic.
  • Per-tenant quotas, so one noisy tenant cannot starve the others.
  • Separate processes, AZs or cells.
  • Separate queues per priority class.
  • Per-dependency database connection pools.

Trade-off. Bulkheads reduce statistical multiplexing: a pool for Recommendations may sit mostly idle while Payments is saturated. Size by measured need and critical importance, not equally.

Thread-pool bulkhead versus semaphore bulkhead? Senior

Say this: "A thread-pool bulkhead runs the call on a dedicated pool, so a hung call can be abandoned on timeout and the pool size is the cap. A semaphore bulkhead just counts concurrent calls in the caller's thread and rejects above N. Pools cost handoff and context but isolate hung calls; semaphores are cheap but the caller thread is still stuck on a hung call."

Overload, load shedding, rate limiting and backpressure

What happens to a server as load goes past its capacity, and what should it do? Intermediate

Say this: "Without protection, throughput does not plateau, it collapses: queues grow, latency rises past client timeouts, and the server keeps working on requests nobody is waiting for. A well-behaved server holds throughput at its maximum and rejects the excess quickly and cheaply."

What happens, step by step. A server handles 1,000 requests per second at best.

  1. Offered load rises to 1,200 per second. The extra 200 per second go into a queue.
  2. The queue grows by 200 each second, so waiting time grows too: after 10 s, 2,000 requests are waiting, which is 2 s of delay.
  3. Clients time out after, say, 1 s and retry. But the server still processes the abandoned requests (wasted work) and now also the retries.
  4. Goodput (useful work that reached a live client) falls toward zero even though the server is 100 percent busy. Memory pressure and GC rise too, which slows the server further.

The right behaviour. Keep serving 1,000 per second of useful work and refuse the other 200 cheaply:

  • Bounded queues and concurrency limits.
  • Load shedding: a fast 503 or 429 with Retry-After.
  • Dropping requests whose deadline already passed.
  • Prioritizing important traffic (health checks, checkout) over unimportant.

Principle: "fail fast on the excess to keep serving the rest." The key metric to watch is goodput, not raw throughput.

What is load shedding? How is it different from rate limiting? Intermediate

Say this: "Rate limiting enforces a per-client quota for fairness and abuse protection. Load shedding reacts to the server's actual health and drops excess work, lowest priority first, to survive overload. I need both, since everyone can be within quota and the system can still be overloaded."

Rate limitingLoad shedding
TriggerA per-client or per-key policy (quota)Actual server health (CPU, queue length, latency)
PurposeFairness, abuse prevention, costSurvive overload
Who is rejectedThe client exceeding its shareLowest-priority or newest requests, regardless of client

Why both. After a region failover, traffic doubles on the surviving region. Every client is still within its quota, yet the region is over capacity. Only shedding, which looks at the server's state, helps.

Shedding choices.

  • By priority: drop analytics before search before checkout; never drop health checks.
  • By deadline: drop requests that have already expired in the queue.
  • By age: under overload, serving the newest first (LIFO) helps, since old requests are likely abandoned and fresh ones still have a live caller.
  • Cheaply: return a quick error (503, with Retry-After) and not a slow one.

Client side. The error must tell clients not to hammer: a Retry-After hint and clients obeying backoff. Otherwise shed traffic just returns as retries.

How do you decide when to start shedding? Senior

Say this: "Use signals that reflect overload directly: a concurrency limit derived from load tests or learned adaptively, queue wait time (not length), and CPU or memory with hysteresis. Shed lowest priority first, and shed as early and as cheaply as possible."

  • Concurrency limit. Cap in-flight requests at a number from load tests (by Little's law, concurrency = throughput x latency). Adaptive limiters work like TCP congestion control (AIMD, or gradient-based algorithms in Netflix's concurrency-limits library): raise the limit while latency stays flat, cut it when latency rises.
  • Queue delay. If a request has waited more than X ms, drop it (CoDel-style). Queue length alone is a poor signal because a long queue of fast work is fine and a short queue of slow work is not. Wait time is the signal.
  • CPU or memory thresholds, with a small hysteresis band (start shedding at 85 percent, stop at 75) to avoid oscillation.
  • Per-priority thresholds. Shed low-priority traffic at 70 percent utilization, medium at 85, high at 95, so critical traffic is the last to go.

Make shedding cheap. Reject before parsing the body or authenticating, as early as possible (at the load balancer or edge if you can). If rejecting costs nearly as much as serving, shedding does not help.

Pitfall. CPU-only triggers can miss problems that are not CPU-bound (a slow database holding threads). Combine concurrency with latency signals.

How do rate limits and quotas protect a system from overload, and where should they be applied? Intermediate

Say this: "They bound the maximum load any one caller can create, so one buggy client or abusive tenant cannot starve everyone. Apply them in layers: edge or gateway per API key and IP, per service per upstream caller, and per expensive operation. Return 429 with Retry-After."

The noisy neighbour. Without per-caller limits, one tenant running a runaway script can use 90 percent of capacity, and everyone else sees errors. A quota of, say, 100 requests per second per tenant bounds the damage.

Where to apply.

  • Edge or API gateway: per API key, per IP, per user.
  • Service to service: per upstream caller, so one internal client cannot overload a shared service.
  • Per expensive operation: exports, search, report generation get much tighter limits than simple reads.

Sizing sanity. The sum of all per-client quotas can exceed total capacity (clients rarely peak together), but it should not be absurdly high; otherwise quotas give no real protection. Base quotas on the capacity you can deliver with one AZ lost.

Algorithms.

  • Token bucket: allows bursts, steady refill. The usual default.
  • Leaky bucket: smooths output to a constant rate.
  • Fixed window counter: simple but allows a 2x burst at the window boundary (100 at 0:59, 100 at 1:00).
  • Sliding window log or counter: accurate, more memory or computation.

Distributed setup. Keep counters in a shared store like Redis (accurate, extra hop, new dependency), or have each node enforce its share locally (fast, slightly inaccurate). If the limiter store is down, fail open (see the fail-open question).

How does a token bucket work? Basic

Say this: "A bucket holds up to B tokens and refills at R tokens per second. Each request takes a token; if the bucket is empty the request is rejected or delayed. So I allow a sustained rate R with bursts up to B."

Example. R = 10 per second, B = 50.

  1. The client is idle for 5 seconds. The bucket fills to 50 (refill 50, capped at B).
  2. It sends 50 requests at once: all succeed, bucket is 0.
  3. It sends a 51st request immediately: rejected (429).
  4. One second later 10 tokens have arrived, so 10 more requests can pass. From then on the sustained rate is 10 per second.

Implementation, lazily. You do not need a timer. Store two numbers per key: tokens and last_refill_time. On each request:

now = time()
tokens = min(B, tokens + (now - last_refill_time) * R)
last_refill_time = now
if tokens >= 1: tokens -= 1; allow
else: reject

Parameters. R is the average rate you want to allow; B is the burst you tolerate. A big B is friendly to bursty clients but lets a large spike through; B = R means almost no burst allowed.

In a distributed store the read-modify-write must be atomic (a Lua script in Redis, for example), or two concurrent requests can both take the last token.

What is backpressure and how do you implement it? Intermediate

Say this: "Backpressure is a signal from a slow consumer to a fast producer to slow down, so data does not pile up without bound. Without it, an unbounded queue just converts overload into memory exhaustion and huge latency. I implement it with bounded queues, pull-based consumption, credits or windows, and explicit 429/503 signals."

The problem. A producer generates 1,000 messages per second; the consumer handles 800. With an unbounded queue, the backlog grows by 200 per second: after an hour, 720,000 messages in memory, delays of 15 minutes, and eventually an out-of-memory crash. The system looks healthy until it suddenly is not.

  • Bounded queues: when full, either block the producer (slowing it), or reject.
  • Pull-based consumption: the consumer asks for work when ready (Kafka consumers poll; Reactive Streams request(n)).
  • Credits or windows: TCP flow control and HTTP/2 flow-control windows: the receiver tells the sender how much it may send.
  • Explicit signals: 429 or 503 plus Retry-After, gRPC RESOURCE_EXHAUSTED.
  • Drop policies when the data is lossy: drop oldest, drop newest, sample, or coalesce (keep only the latest value per key, good for metrics and telemetry).
Trap: an unbounded in-memory queue between threads (for example an executor with an unlimited work queue) is the classic hidden backpressure bug: everything seems fine until memory blows up. Always bound queues, and decide the full-queue policy on purpose (block, reject, or drop).

Chain effect. Backpressure must propagate all the way back to the source (user or upstream system). If one stage in the middle absorbs it into a huge buffer, the signal is lost.

What is queue-based load leveling and when do you use it? Intermediate

Say this: "Put a durable queue between a bursty producer and a consumer that works at a steady rate. The queue absorbs spikes and the backend is sized for average load, not peak. It only works when the work can be asynchronous, and it handles bursts, not sustained overload."

Example. A flash sale sends 20,000 orders per second for one minute, while fulfilment can process 2,000 per second.

  1. The API validates the order, writes it to the queue, and returns 202 Accepted with a status link. Fast and cheap.
  2. 20,000 x 60 = 1.2 million messages sit in the queue.
  3. Fulfilment drains at 2,000 per second: 600 seconds, ten minutes, to clear.

Without the queue you would need 10x the backend, idle most of the day, or you would drop orders.

Conditions for using it.

  • The user does not need an immediate result (return 202 and let them poll or be notified).
  • Monitor queue depth and, more importantly, the age of the oldest message, and alert on it.
  • A dead-letter queue exists for poison messages.
  • A cap on how stale a message may become (an order older than an hour may need re-validation).

Trade-offs. Latency rises during bursts. You operate one more system, and ordering and duplicates need handling. If the queue grows without bound, consumers are simply under capacity: leveling handles bursts, not sustained overload; then scale consumers or shed load.

What is a poison message and how do you stop it from taking a consumer fleet down? Intermediate

Say this: "A poison message is one that always fails processing, because of bad format or a bug it triggers. Under at-least-once delivery it gets redelivered forever. I cap retries with backoff, then move it to a dead-letter queue with error context, alert on DLQ depth, and give operators a way to inspect and replay after the fix."

What happens without protection. Consumer reads message M, throws an exception, does not acknowledge. The broker redelivers M. In a partitioned log (Kafka), M blocks everything behind it in that partition, because the consumer cannot move past it. In a queue, M cycles forever, burning capacity, and sometimes crashing each consumer that touches it (an out-of-memory or a parser crash), so the fleet restarts in a loop.

The defence.

  1. Catch exceptions per message, so one bad record does not kill the process.
  2. Retry a limited number of times (for example 3 to 5), with backoff, since some failures are transient.
  3. After that, publish the message plus error details (exception, attempt count, source) to a dead-letter queue and acknowledge the original, so the stream moves on.
  4. Alert on DLQ depth and rate.
  5. After a fix, replay from the DLQ into the main queue.

Distinguish transient errors (dependency down: retry with backoff, perhaps pause consumption) from permanent errors (malformed: DLQ immediately). If a downstream dependency is down, sending every message to the DLQ is wrong; pause instead.

Pitfall. A DLQ nobody watches is a black hole where data is lost silently. Treat it as an alerting source.

Graceful degradation, fallbacks and cascading failures

What is graceful degradation? Give examples. Basic

Say this: "When a part fails or load is too high, the system keeps delivering its core function with reduced features instead of failing completely. At design time I classify each dependency as hard or soft and make as many of them soft as possible."

Examples.

  • A product page loads without recommendations, reviews or live stock count if those services are down.
  • Search falls back from personalized ranking to a simple popular-items list.
  • A video player lowers resolution instead of stopping.
  • The write path accepts an order and queues the confirmation email for later.
  • A site goes read-only during a database failover.

How to design for it.

  1. List the user journeys and mark the core one (for example "search, add to cart, pay").
  2. For each dependency on that path, ask: can the journey still complete without it? If yes, it is soft: add a timeout, a breaker and a fallback. If no, it is hard: invest in redundancy.
  3. Make the degraded mode visible: a banner, a metric, an alert, so you know you are running degraded and are not hiding a failure.
  4. Test degraded modes regularly (chaos tests, kill switches).

Link with availability math. Each hard dependency multiplies in the series chain; each dependency turned soft removes a factor. Degradation is the cheapest way to gain nines.

What kinds of fallbacks exist, and what are the risks of each? Intermediate

Say this: "Common fallbacks are stale cached data, default values, an alternate provider, queueing for later, and fail open or closed. Each trades correctness or cost for availability. The trap is a fallback that is never exercised, or one heavier than the primary path."

Choosing. Ask what is the worst outcome of the fallback being wrong. Showing a price that is 5 minutes old on a catalogue is fine; showing a stale price at checkout is not. A default for a recommendation list is fine; a default for "is this user authorized" is not.

Trap: a fallback that is never exercised usually does not work when needed (a second payment vendor whose credentials expired months ago). And a fallback path that is heavier than the main path, for example falling back to a full database query when the cache dies, can itself cause the cascade. When should a protective component fail open and when fail closed? Senior

Say this: "I decide by comparing the cost of a wrong decision with the cost of unavailability. Fail closed for security-critical checks. Fail open where the check is a safeguard rather than the function itself. I document the choice per component and alert whenever something runs in fail-open mode."

Definitions. When the protective component itself breaks (cannot decide), fail closed means deny or block; fail open means allow or pass through.

Operational rules. Alert loudly while in fail-open (it is an uncovered risk window), time-limit it if possible, and log all decisions made in that mode for later review.

What is a cascading failure and what are the common ways it starts? Senior

Say this: "A failure in one component raises load or latency elsewhere, which then fails and pushes the problem further, like dominoes. Get it under control by cutting load first (shed, stop retries, scale up, disable nonessential features), then fix the root cause."

A classic example. Five servers each at 70 percent load. One crashes. Its traffic spreads over four: each goes to 87.5 percent. One of them, now slower, hits a latency problem and gets restarted by its health check. Three servers now carry the whole load at 117 percent: they all fail. Each failure made the next one more likely.

Common triggers and amplifiers.

  • Server overload: one node dies and its traffic moves to the rest, which then overload.
  • Resource exhaustion: threads, connections, file descriptors or memory used up while waiting on a slow dependency.
  • Retry storms and amplification.
  • Cold caches or restarts: an empty cache sends all reads to the database.
  • Health-check or autoscaler reactions that remove capacity during high load.
  • Shared dependency: everyone calls the same auth service, DNS or config store.
  • Leader or coordinator failure that triggers expensive rebalancing on every node.

Defences. Load shedding, timeouts and deadlines, circuit breakers, bulkheads, retry budgets, capacity headroom (N+2), cache warm-up and request coalescing, and slow, staged rollouts of changes.

During an incident. Resist the urge to find the root cause first. Stop the spread: cut incoming load, block retries, turn off optional features, add capacity if it helps, and only when the system is stable investigate why.

What is the thundering herd problem and how do you mitigate it? Intermediate

Say this: "Many clients or processes act at the same moment against one resource: a hot cache key expires and everyone rebuilds it, everyone reconnects after a restart, cron jobs all fire at minute zero. I mitigate with jitter, single-flight coalescing, serve-stale-while-revalidate, and staged ramp-up."

Examples.

  • A hot cache key expires and 5,000 concurrent requests all miss and query the database for the same value.
  • All clients reconnect immediately after a server restarts.
  • Cron jobs on 500 hosts all start at 00:00.
  • A lock is released and every waiter wakes at once.
  • A mass retry after an outage.

Mitigations, with why.

  • Jitter on TTLs, cron schedules, retry timers and reconnects: spreads the herd over time.
  • Request coalescing (single-flight): the first request to miss rebuilds the key; the others wait for its result. 5,000 database queries become 1.
  • Serve stale while revalidating: return the old value to everyone while one background fetch refreshes it.
  • Probabilistic early refresh: each request has a small chance to refresh before expiry, with chance rising as expiry nears, so refreshes are spread out.
  • Staged ramp-up after recovery, connection rate limits, and exponential backoff on reconnect.
  • Pre-warming caches before shifting traffic.

A cache fronts a database. The cache cluster dies and restarts empty. What happens and how do you protect the database? Senior

Say this: "All reads miss and hit the database. If the cache absorbed 95 percent of reads, the database suddenly sees 20 times its normal read load and falls over, and then the cache cannot be refilled: a cold-start cascade. Protect the database independently with concurrency limits and load shedding, coalesce per key, warm gradually, and use replicated or sharded caches."

The arithmetic. Normal: 100,000 reads per second at the app, 95 percent cache hits, so the database serves 5,000. Cache restarts empty: hit rate falls to near 0, so the database sees up to 100,000 per second, 20x. A database sized for 5,000 to 10,000 falls over. While it is down, no misses can be filled, so the cache stays empty. The system is stuck in a metastable failure.

Protection, in layers.

  1. Protect the database directly: a concurrency limit and load shedding in front of it, so it serves what it can instead of collapsing. Fail some requests quickly rather than all slowly.
  2. Single-flight per key: one database query per missing key, not one per request.
  3. Warm gradually: ramp traffic by percentage to the new cache, or preload hot keys before cutting over.
  4. Reduce the chance of total loss: a replicated or sharded cache so losing one node loses only a fraction of keys.
  5. A small in-process local cache as a second layer, so even with the shared cache gone, hot keys are served locally.
  6. Serve stale on error: keep expired entries around to use if the origin is struggling.
  7. Design the key paths to survive with a hit rate near zero, or to shed everything else.

The lesson. A cache that the system needs in order to survive is not a cache, it is a hard dependency, so treat it as one: replicate it, test its loss, and protect what sits behind it.

Multi-AZ, multi-region, disaster recovery

What is the difference between an availability zone and a region, and why design for AZ failure first? Basic

Say this: "A region is a geographic area. An availability zone is one or more physically separate data centres inside a region, with independent power, cooling and networking, joined by low-latency links. Spreading across AZs protects against a data-centre failure cheaply, so it is the baseline. Multi-region protects against a whole region failing, but costs much more in money and complexity."

Terms.

  • Region: a geographic area (for example "us-east" or "eu-west") containing several AZs.
  • AZ: a failure domain inside a region. AZs are far enough apart that a fire, flood or power failure hits one, but close enough that latency between them is a few milliseconds or less, so synchronous replication between AZs is practical.

Why AZ first. The most common physical failures (a power or cooling failure, a network device failure, a bad rack) hit one data centre. Surviving those costs little: instances in 3 AZs, a database with a synchronous standby in a second AZ. Latency barely changes and the extra cost is mostly spare capacity.

Why multi-region is a bigger step.

  • Cross-region latency is tens to hundreds of ms, so synchronous replication is usually too slow for writes. You accept asynchronous replication and non-zero data loss, or conflict handling.
  • Two of everything to run, deploy and pay for.
  • It protects against rarer events: a regional outage, often caused by software or control-plane problems more than by physical disaster. It also helps users close to another region (lower latency) and compliance needs (data residency).

Rule. Every tier across at least 2, preferably 3 AZs, with enough spare capacity to lose one. Go multi-region when your availability target or RTO requires it, not by default.

How do you design a typical web service to survive loss of an AZ? Intermediate

Say this: "Spread every tier across three AZs, size capacity so any two can carry the full load, use a managed database with a synchronous standby and automatic failover, cluster caches and queues across AZs, avoid AZ-specific singletons, keep zone affinity soft, and prove it by draining an AZ."

How to read this diagram. The load balancer spreads traffic over three availability zones. Each zone holds its own app instances and cache node, and the database is spread across them: a primary in AZ-a, a synchronous standby in AZ-b and a read replica in AZ-c. If one zone disappears, the other two still hold every tier and can take over.

  • Load balancer and compute: the load balancer spans 3 AZs and instances sit in an autoscaling group across 3 AZs.
  • Capacity: each AZ should be sized so the remaining two can carry the full load. With three AZs, each must be able to take 50 percent more than its normal share, so total utilization should stay under about 66 percent.
  • Database: a synchronous standby in another AZ (managed services do this) with automatic failover; read replicas across AZs.
  • Caches and queues: clustered across AZs with replicas in different AZs, so a node loss is a partial loss.
  • Cross-AZ chatter: avoid unneeded cross-AZ calls (cost and latency), but keep zonal affinity soft: if the local AZ's backend is dead, calls must route elsewhere.
  • No AZ-specific singletons: one NAT gateway, one NFS server, one self-hosted CI or admin tool, one cron box are all hidden SPOFs.
  • Prove it: actually drain an AZ (shift all traffic away) in a game day and watch latency, errors and database failover.

What the interviewer probes next. "What about the database connections after failover?" Pools must reconnect to the new primary; DNS TTLs must be short. "What about the stateful service in a single AZ, like a self-managed Kafka?" Replicas must be rack or AZ aware, so no partition has all its copies in one AZ.

What are the main multi-region architectures and their trade-offs? Senior

Say this: "There is a spectrum: backups in another region (cheap, hours to recover), active-passive with a pilot light or warm standby, active-active with each user homed to one region, and fully replicated multi-writer. Each step buys lower RTO and lower latency at the price of cost and consistency complexity. The hardest part is not compute but data replication across regions."

PatternHowProsCons
Single region, backups elsewhereBackups copied cross-regionCheapRTO of hours
Active-passive (pilot light, warm standby)Data replicated, second region scaled down or minimalModerate cost, simple data modelFailover is a big event; standby may rot
Active-active, partitionedEach user or tenant homed in one region, other region is its backupFull use, simpler consistencyFailover re-homes users; routing layer needed
Active-active, fully replicated writesWrites in every region, replicated and mergedLowest latency, best resilienceConflict resolution, eventual consistency, hardest to build and reason about

The physics. Cross-region latency is tens to hundreds of ms (about 70 ms between US coasts, more across oceans). A synchronous write that must reach a second region adds that round trip to every commit. So most systems replicate asynchronously across regions, which means a non-zero RPO: when a region dies, the last moments of writes may be lost. To get zero RPO you must accept slower writes (quorum across regions, Spanner-style), which is acceptable only for some workloads.

Walking through "partitioned active-active". Alice's account lives in region EU, Bob's in US. Each region handles its own users' reads and writes locally, with a copy replicated to the other region. If EU fails, Alice's account is promoted in US (with possible loss of the last few seconds), and the router sends her there. No two regions write the same record at the same time, so no conflict handling is needed.

Decision rule. Choose the least-complex pattern that meets the RTO, RPO and latency targets. Most business systems are fine with warm standby or partitioned active-active; fully replicated multi-writer is justified only for the few that truly need it, and then with data types designed for it (CRDTs, append-only logs).

What commonly breaks multi-region designs in practice? Senior

Say this: "Hidden single-region dependencies, failover that needs the control plane of the failing region, a standby that never took real traffic, capacity and quota shortfalls, replication lag losses, no failback plan, and the cost of running two of everything."

  • Hidden dependency on one region. A "global" service homed in one region: IAM, config, the DNS control plane, a shared database, a CI system, a third-party SaaS. When that region fails, "region B" cannot function either.
  • Control plane in the failing region. Failover steps like "create instances", "change DNS", "assume this role" call APIs that may be impaired during the incident. Prefer data-plane-only failover that needs no new resources to be created (see static stability).
  • The standby has never taken real traffic. Capacity quotas not raised, certificates missing, secrets not replicated, feature flags different, IAM roles absent, data not fully replicated, or config drift from production.
  • Capacity. When one region fails, the other must absorb 100 percent. Quotas and scale-up speed matter, and other customers of the same cloud may be failing over at the same moment, competing for capacity.
  • Replication lag. Failing over loses the unreplicated tail of writes, or serves stale reads. There is often no plan for reconciling writes that were in flight, or for telling users what happened.
  • Failback. Returning to the original region is harder than failing over (data must flow back and merge), and is often not designed, leaving the system "temporarily" on the standby for months.
  • Cost and operations. Two of everything and twice the deploys, with more places for drift.

Mitigations. Continuous small real traffic through the standby, infrastructure as code deployed identically to both, an explicit list of global dependencies reviewed per design, game-day failovers, and capacity reservations in the standby region.

How is traffic steered between regions? Intermediate

Say this: "Geo or latency-based DNS with health checks, anycast IPs with a global load balancer or CDN edge that fail over in seconds without waiting on DNS caches, or client-side logic where the SDK tries the next region. Health checks should reflect real user success, and I keep a manual 'drain region X' control."

  • DNS-based (geo, latency, weighted, failover routing). Simple and widely available. The resolver returns the nearest or healthiest region. Failover is bounded by TTLs and client caching (see the DNS question), so seconds to minutes.
  • Anycast with a global load balancer or CDN edge. The same IP is announced from many locations; the network routes each user to a nearby entry point, which proxies to a healthy region. Failover takes seconds and does not depend on DNS cache expiry, and it terminates TLS near the user.
  • Client-side routing. The SDK or app knows several regional endpoints and tries the next on failure. Useful for mobile apps and service-to-service calls, but every client needs the logic.

Health checks that mean something. A region may answer a ping but be unable to complete orders. Use synthetic transactions (log in, add to cart) from outside, and decide with several observers, not one.

Manual override. A switch to drain a region is used far more often than automatic failover: for planned maintenance, risky deploys, or when you suspect trouble before health checks do. Automatic failover can also be dangerous (a false alarm could shift all traffic to a region that cannot take it), so many teams automate detection but require a human click, or put limits on how much traffic may be shifted automatically.

Define RTO and RPO. How do they drive the design? Basic

Say this: "RTO is the maximum acceptable time to restore service after a disaster. RPO is the maximum acceptable data loss measured in time. RPO drives the data replication strategy and RTO drives the compute strategy. Both are business decisions with a cost, so I ask what an hour of downtime or a minute of lost orders costs."

  • RTO (Recovery Time Objective): "We must be back in 15 minutes."
  • RPO (Recovery Point Objective): "We can lose at most 5 minutes of writes."

How to read this diagram. Time runs left to right. The first mark is the last good copy of the data, the second is the disaster, and the third is when service is restored. The gap from the last good copy to the disaster is RPO, the data you lose. The gap from the disaster to restoration is RTO, the time you are down.

How RPO shapes data strategy.

How RTO shapes compute strategy. Hours: rebuild from infrastructure code. Minutes: a running (warm or hot) standby with automated cutover. Seconds: active-active.

Cost link. Each step down in RTO and RPO costs sharply more. So do not default to zero. Ask the product owner what an outage costs, and tier the services: payments might get RPO 0 and RTO 1 minute; an internal wiki RPO 24 hours and RTO 1 day.

Pitfall. RTO and RPO are objectives. What a drill shows is the actual recovery time and data loss, and it often differs. Also RTO includes detection, decision, and verification time, not only the technical restore.

The names, in plain words. The "pilot light" is the small flame in a gas heater that can light the full burner quickly: only the critical core (the database) is running; to recover you start the servers around it. "Warm standby" is a complete but small copy; recovery means scaling it up and switching traffic.

Walkthrough: pilot light recovery. The primary region is lost. (1) Declare disaster. (2) Promote the replicated database in the DR region. (3) Launch application servers from prebuilt images with infrastructure code. (4) Scale up. (5) Switch DNS or routing. That takes tens of minutes, mostly in steps 3 to 4.

This is the model AWS documents in its disaster recovery whitepaper; the idea applies on any cloud.

Decision rule. Match the strategy to the cost of downtime. And whichever you choose, rehearse it: the paper RTO of a pilot light is often much worse in practice because step 3 hits quotas or missing images.

Why does "we have backups" not equal "we can recover"? Intermediate

Say this: "A backup is only proven by a successful restore. Backups fail silently, and replication is not backup, since a dropped table replicates in seconds. I want automated restore tests, isolated and immutable copies, point-in-time recovery, and a timed runbook."

How backups fail without anyone noticing.

  • Wrong paths, empty or partial files, or corrupted data.
  • Expired credentials, so the job fails every night and nobody reads the logs.
  • The backup is encrypted with a key that lived in the lost system.
  • Restore takes far longer than expected: pulling 20 TB over a network is hours or days, which blows the RTO.
  • Versions of schema or tooling no longer match what the backup contains.

Replication is not backup. A replica copies everything, including a mistake. If someone runs DROP TABLE or a bug corrupts rows, the damage reaches the replica within seconds. Backups give you a point in the past to return to.

Good practice.

  1. Automated periodic restore tests with integrity checks (row counts, checksums, app smoke tests).
  2. Copies in a separate account or region with separate credentials, and immutable (object lock or write-once) against ransomware and operator error.
  3. Point-in-time recovery for databases (base snapshot plus log archive).
  4. A documented, timed restore runbook.
  5. Monitoring and alerts on backup age and size.

A well-known example. In 2017 GitLab accidentally deleted a production database directory while handling a replication problem, and found several of its backup methods had not been working. It recovered from a snapshot taken some hours earlier and lost several hours of data. (Details hedged; the lesson is that untested backups failed.)

How do you keep a DR plan real over time? Intermediate

Say this: "A DR plan decays unless it is exercised. I run scheduled exercises that fail over for real and measure actual RTO and RPO, keep the DR site built by the same infrastructure code and pipeline as production, send a little real traffic through it continuously, and keep short, rehearsed runbooks."

  • Exercises: schedule them (for example twice a year), ideally by really failing over production or a production-like environment. Record actual RTO and RPO, and compare to the target.
  • No drift: infrastructure as code deployed to both sites through the same pipeline. Manual changes in production quietly make the DR copy invalid.
  • Real traffic: run 1 to 5 percent of production through the DR site continuously. If it breaks, you find out on a Tuesday, not during the disaster.
  • Runbooks: short and executable, rehearsed by people who did not write them, with a clear owner of the decision to "declare a disaster" (the delay in deciding is often the longest part of RTO).
  • Out-of-band tools: do not keep the runbook, credentials, chat or monitoring only inside the infrastructure that failed. A common failure: the wiki with the recovery steps is down with the region.
  • Failback: practise returning to normal too, since it is a second risky migration.
  • Follow-up: turn each exercise's findings into tracked fixes.
What is static stability? Senior

Say this: "A statically stable system keeps working through a dependency failure without taking any new action: no control-plane calls, no scaling up, no failover decision. I get there by pre-provisioning capacity, caching last known configuration, and separating a simple data plane from a complex control plane."

Why. During an incident, the tools that fix things (APIs to launch servers, change DNS, rotate credentials) are often impaired themselves, or overloaded by everyone reacting at once. A design that needs those tools to recover is least reliable exactly when you need it.

Examples.

  • Pre-provisioned capacity: instead of relying on autoscaling to replace a lost AZ's capacity (needs APIs that may be impaired), run enough capacity in the remaining AZs ahead of time. When an AZ dies, the load balancer just stops sending to it and nothing else has to happen.
  • Cached configuration: data-plane components keep the last known configuration and continue to serve if the control plane is down.
  • Cached credentials and DNS: keep using them until they truly expire, rather than failing as soon as the refresh service is unreachable (with sensible limits).

The rule. Separate the control plane (creates and changes things; complex; less available) from the data plane (does the work; simple; highly available), and make recovery depend only on the data plane.

Trade-off. Static stability costs money, since you hold spare capacity all the time. You pay it for the paths whose availability matters most.

Deployment safety

Why are deployments one of the top causes of outages, and what is the general defence? Intermediate

Say this: "Most incidents in mature systems trace back to a change: a code release, config push, schema migration, or certificate or dependency upgrade. The defence is to make every change small, gradual, observable and reversible."

Why change is risky. A running system with stable traffic has a known behaviour. Every change introduces something not yet proven against real traffic and real data: staging never has exact production data shape, load, or odd clients. And as hardware failures are now rare thanks to redundancy, change is what is left.

The defence, as a pipeline.

  1. Small changes so cause and effect are clear and rollback is cheap.
  2. Staged rollout: first one instance, then 1 percent, then one AZ, one region, then everything, with bake time between stages.
  3. Automatic signals: compare error rate, latency and business metrics of new versus old, and halt or roll back automatically.
  4. Reversible: rollback in minutes, feature flags as kill switches.
  5. Never hit every region and AZ at once.

Config is code. Config and feature-flag pushes need the same staging, validation and rollback as binaries. Several well-known large outages were a global configuration change pushed everywhere at once with no staged rollout.

How does blue-green deployment work and what are its limits? Basic

Say this: "Two identical environments: Blue runs the current version and takes traffic, Green gets the new version and is tested. I then switch the router from Blue to Green. If something is wrong I switch back immediately. It gives near-zero downtime and instant rollback, but needs double capacity and is all-or-nothing for users unless I shift gradually."

  1. Blue (v1) serves 100 percent of traffic.
  2. Deploy v2 to Green, which gets no user traffic. Run smoke tests, maybe shadow traffic.
  3. Flip the load balancer or router target to Green. Users now see v2.
  4. Keep Blue running for a while as an instant rollback (flip back).
  5. Later, decommission or reuse Blue as the next Green.

Strengths. Near-zero downtime, simple mental model, fast rollback, and you can test the new environment fully before users see it.

Limits.

  • Double capacity during the switch (cost, quota).
  • All-or-nothing exposure if you flip at once: a bug reaches everyone. You can reduce this by shifting traffic gradually (that turns it into a canary).
  • The database is shared. Blue and Green normally use one database, so schema changes must work with both versions (see expand and contract). A flip back does not undo data written by v2.
  • In-flight work: long requests, sessions, and background jobs must be drained or handed over.
  • Warm-up: Green's caches are cold at the flip.
What is a canary release? How is it different from blue-green and from a rolling update? Intermediate

Say this: "A canary sends a small share of real traffic to the new version while most users stay on the old one, and compares key metrics of canary versus baseline. If they degrade, it rolls back automatically. A rolling update replaces instances in batches with no isolated comparison; blue-green is a whole-environment switch. Canary gives the best blast-radius control."

How it works.

  1. Deploy v2 to a few instances. Route 1 percent of traffic to them.
  2. Compare for a bake period: error rate, p99 latency, saturation, and business metrics like checkout success, against the v1 baseline on the same traffic.
  3. If healthy, step up: 5, 25, 50, 100 percent. If metrics degrade, automatically roll back and page nobody at 3 AM.

What makes a rollback safe, and when is rolling forward better? Senior

Say this: "Rollback is safe when the previous version can still read everything the new version wrote. So I keep data formats, schemas, messages and APIs backward-compatible for at least one release, keep the old artifact deployable, and use feature flags so the first remedy is 'turn it off', not 'redeploy'. I roll forward when rollback is impossible because data changed irreversibly, or the fix is tiny and well understood."

How rollback goes wrong. v2 writes a new column format or a new message shape. You roll back to v1. v1 cannot parse v2's data and crashes, or silently corrupts it. Now you have a worse incident than the original bug.

Rules.

  • Backward compatibility for one release: v(N) can read what v(N+1) writes. Add new fields without removing old ones. Tolerate unknown fields.
  • Keep the previous artifact deployable and rehearsed; target rollback time in minutes.
  • Never mix an irreversible migration with a code release. Do them in separate steps (see expand and contract).
  • Decouple deploy from release with feature flags: the new code ships dark and is turned on gradually. A bad behaviour is fixed by flipping a flag, which is faster and safer than a redeploy.

When to roll forward.

  • The release already made an irreversible data change.
  • The bug is understood and the fix is tiny and quick to ship through the staged pipeline.
  • Rolling back itself is riskier (for example many dependent services already moved).

Whichever you choose, decide quickly, and keep the fix flowing through the same safeguards, not around them.

How do feature flags help resilience, and what risks do they add? Intermediate

Say this: "Flags separate deploying code from enabling behaviour. I can ship dark, enable for internal users then 1 percent then everyone, and have an instant kill switch without a deploy. The risks are state explosion, stale flags, the flag service becoming a dependency, and flag changes being unreviewed production changes."

Benefits.

  • Ship code turned off, so deploys carry no behaviour change.
  • Gradual exposure: internal staff, 1 percent, 10 percent, everyone.
  • Instant off-switch ("kill switch") without a deploy or rollback.
  • Degrade under load by turning off expensive features.
  • A/B testing.

Risks and how to manage them.

  • Combinatorial states: n flags means up to 2^n combinations, only a few of which are tested. Keep flags independent and few.
  • Stale flags: remove the flag and the dead code after rollout is complete; otherwise hidden behaviour accumulates.
  • The flag service as a dependency: evaluate flags from a local cache with safe defaults, so if the service is down the app keeps the last known values.
  • Flags are production changes: they need audit logs, review, and staged rollout like code.

A cautionary tale. Knight Capital in 2012: a new release reused an old flag that, on one server where the deployment was incomplete, still triggered old test code. It sent a flood of erroneous orders and lost a huge sum in about 45 minutes (widely reported at roughly 440 million dollars). It is usually quoted as a lesson about incomplete deployment, dead code left in place, and having no kill switch.

What is the expand and contract (parallel change) pattern for database migrations? Senior

Say this: "I change a schema over several releases so old and new code both work at every step, with no downtime and a possible rollback each time: expand by adding the new thing, migrate code and data, then contract by removing the old thing in a later release."

Why a single step fails. During a rolling deploy, old and new code run at the same time. A rollback means old code runs against the new schema. If you rename a column in one step, either old code (expecting the old name) or new code (expecting the new name) breaks.

Example: rename column name to full_name.

  1. Expand: add full_name (nullable). Old code ignores it. Nothing breaks.
  2. Deploy code that writes both columns and reads the old one (or reads new with fallback to old).
  3. Backfill existing rows in small, throttled batches so the database is not overloaded and locks are short.
  4. Switch reads to the new column. Verify with comparison checks.
  5. Stop writing the old column.
  6. Contract: drop the old column in a later release, once nothing uses it and rolling back to the old code is no longer needed.
-- step 1 (expand)
ALTER TABLE users ADD COLUMN full_name text;
-- step 3 (backfill, in batches)
UPDATE users SET full_name = name WHERE id BETWEEN 1 AND 10000 AND full_name IS NULL;
-- step 6 (contract, a release later)
ALTER TABLE users DROP COLUMN name;

Related care. Avoid long table locks (use online schema change tools), build indexes concurrently, and never combine a destructive change with a feature release. The same idea applies to APIs and message formats: add the new, support both, then remove the old.

What automated safeguards should a deployment pipeline have? Intermediate

Say this: "Automated tests, progressive delivery with bake time and automatic rollback on alarms, health and business-metric gates, change freezes at peak times, one change at a time per service, config validated and staged like code, and a global halt button."

  • Tests and staging: automated unit, integration and smoke tests, and a staging environment with realistic data shape.
  • Progressive delivery: stages with bake time between them, and automatic rollback on alarms, so a bad build is stopped by machines in minutes.
  • Health and business gates: error rate, p99 latency, and business metrics such as orders per minute. A release that returns 200 but halves checkouts should be blocked.
  • Windows and freezes: avoid risky deploys at peak business times or right before the team goes home on a Friday. It is partly a staffing guardrail: you want people available to respond.
  • One change at a time per service: so the cause of a regression is clear. Annotate dashboards with deploy and config events.
  • Config validation: lint and schema-check config before push, and roll config out in stages like code.
  • A global halt: the ability to stop all in-flight rollouts at once when an incident starts.

Pitfall. Gates that nobody trusts get bypassed. Keep them fast, reliable (few flaky tests), and make bypassing visible and rare.

Blast radius, cells, chaos engineering, SLOs

What is blast radius, and how do you limit it? Intermediate

Say this: "Blast radius is how much of the system, or how many users, are affected when something fails or a bad change ships. I limit it by splitting along fault boundaries, staging rollouts, setting per-tenant quotas, separating control and data planes, and not sharing databases, caches or queues between unrelated features."

Why think about it. You cannot prevent every failure, but you can decide whether a failure hits 100 percent or 2 percent of customers. Two designs with the same failure rate can have very different impact.

Ways to shrink it.

  • Fault boundaries: AZs, regions, cells, shards, tenants. A failure stays inside its boundary.
  • Staged rollouts: a bad release hits 1 percent before it reaches 100.
  • Per-tenant quotas and bulkheads: a noisy tenant cannot consume shared resources.
  • Control plane versus data plane: a control-plane failure should not stop existing traffic.
  • No sharing of unrelated state: one shared database or cache for ten features means one feature's problem is ten features' problem.

The question to ask per component. "If this breaks, what percent of customers see it?" Then reduce that number by design. Example: one global database serving all tenants has a blast radius of 100 percent; sharding tenants across 20 independent databases gives 5 percent per shard failure.

What is cell-based architecture? How does it differ from simply having more replicas? Senior

Say this: "A cell is a complete, self-contained copy of the service (compute, storage, queues) serving a fixed subset of customers, with nothing shared at runtime. A thin router maps each customer to a cell. A cell failure hits about 1/N of customers, whereas in one big fleet of replicas a poison request or noisy tenant can take down everyone."

How to read this diagram. The thin router looks up which cell owns each customer and sends the request there (the moving arrows). Every cell has its own app, cache and database and shares nothing at runtime. Cell C is marked bad, but Cells A and B keep serving their tenants, so only about one third of customers are affected.

Replicas versus cells. With one big fleet of 90 identical replicas behind a load balancer, they all share the same database, caches and queues, and any customer's request can land on any replica. If one customer sends a request that triggers a crash bug, the crash spreads across the whole fleet as that request is retried on replica after replica. The failure domain is everything. With 3 cells of 30, the poison request only ever reaches the cell its customer is mapped to; the other two thirds of customers do not notice.

Benefits.

  • Bounded blast radius (about 1/N of customers).
  • Safer deploys: roll out cell by cell, starting with a small one. A bad release hits one cell, and you stop.
  • Each cell has a fixed, tested maximum size, so scaling means adding cells. There are no surprise limits at 10x scale.
  • Easier to reason about and to test, since each cell is the same small thing.

Costs.

  • A routing layer and customer-to-cell mapping to build and operate. It must be extremely simple and highly available, since it is the one shared part.
  • Uneven utilization across cells (a big tenant fills one cell).
  • Cross-cell operations (global reporting, moving a tenant between cells) are harder.
  • More infrastructure to manage.

Related: shuffle sharding (next question) gives each customer a random subset of workers, so two customers rarely share an identical full set.

What is shuffle sharding with a quick numeric intuition? Senior

Say this: "Instead of every customer using all workers, or customers pinned to fixed groups, I give each customer a random small subset of workers. A poison customer can only damage its own subset, and the chance that another customer has exactly the same subset is tiny, so everyone else still has healthy workers."

Intuition with small numbers. A pool of 8 workers. Each customer is assigned 2 of them.

  • Number of distinct pairs: 8 choose 2 = 28.
  • A bad customer crashes its 2 workers. Customers whose pair shares one worker with it still have one healthy worker (a good client that retries across its workers keeps working).
  • Only the customers with exactly the same pair (about 1 in 28) lose both workers.

Compare: with no sharding, one bad customer takes down all 8 workers and 100 percent of customers. With 4 fixed groups of 2, it takes down its group: 25 percent of customers.

Scaling the idea. 100 workers, each customer gets 5: the number of distinct subsets is 100 choose 5 = about 75 million. Two customers having the exact same set is very unlikely, so the blast radius of one bad customer becomes a tiny fraction.

Requirement. Clients must retry or fail over across their assigned workers (otherwise losing one worker still hurts them), and workers should be stateless or equivalent. AWS describes Route 53 and other services using this idea.

What is chaos engineering and how do you start doing it safely? Intermediate

Say this: "Chaos engineering is deliberately injecting failures to test that the system handles them and to find weaknesses before real incidents do. It is science, not random destruction: define steady state, hypothesise it will hold, inject, observe, and fix. I start small in staging, with monitoring, an abort button and a limited blast radius."

The scientific loop.

  1. Steady state: pick measurable normal behaviour (orders per minute, error rate, p99).
  2. Hypothesis: "if one instance of service X dies, orders per minute stay within 2 percent."
  3. Inject the failure.
  4. Observe whether the hypothesis held.
  5. Fix what did not, then repeat (and automate the experiment as a regression test).

Netflix popularised it with Chaos Monkey (randomly terminate instances), and later a family of tools such as Chaos Kong (simulate losing a region).

Starting safely.

  1. Begin in staging with a small, known experiment (kill one instance, add 200 ms latency to one dependency, block one dependency).
  2. Have monitoring in place, a clear abort button, and a limited blast radius (a small percent of traffic, off-peak).
  3. Run it with the team present, as a game day.
  4. Move to production gradually when staging results are boring.
  5. Turn findings into fixes.

Common mistake. Breaking things before you can see them. If you cannot detect and measure the impact, the experiment teaches nothing and risks a real incident.

What failures would you inject, and what do you expect to learn from each? Intermediate

Say this: "Kill instances, add latency (not only errors) to dependencies, drop packets, take down a cache, block an AZ, expire a certificate, exhaust a disk or CPU, skew clocks, and kill a cluster leader. Each experiment answers a specific resilience question, and latency is the most revealing because slow is worse than down."

What is a game day, and what makes one useful? Basic

Say this: "A game day is a scheduled exercise where the team simulates a failure, real or tabletop, and practises detection, diagnosis and recovery. It tests people, runbooks, dashboards, paging and communication, not only software."

What a good one contains.

  • A written scenario and a hypothesis ("if the primary database fails over, checkout recovers in 2 minutes").
  • Defined roles: incident commander, communications lead, scribe, and the people who operate the fix.
  • Real alerts that must be noticed (the exercise should start from an alert, not from "we are about to break X").
  • A blameless review afterward with tracked action items and owners.
  • Rotating participants, so new on-call engineers have rehearsed before their first real incident.

Two forms. A tabletop is talking through a scenario around a table, cheap and good for process gaps. A live game day really injects failure in staging or production with safeguards, and tests the system as well.

Common findings. The runbook is out of date. The dashboard needed does not exist. Nobody has permission to do the fix. The pager goes to someone who left the team. The failover takes 10 minutes, not 1. These findings are the point: they are far cheaper to discover on a planned Tuesday than in a real incident.

How much capacity headroom should you keep, and why? Intermediate

Say this: "Enough to survive the worst failure I have promised to survive, plus growth, deploys and spikes while scaling reacts. With three AZs and a promise to survive one AZ loss, that means peak utilization under about 66 percent; with two AZs under 50. Queueing theory also says latency rises sharply as utilization nears 100 percent."

Where the headroom goes.

  • Failure tolerance: losing 1 of 3 AZs means the other two carry 1.5x their normal share.
  • Deploys: rolling updates take instances out of service temporarily.
  • Autoscaling lag: minutes to launch and warm new instances, during which the spike must be absorbed by what already exists.
  • Bursts and growth between capacity reviews.

Why not run at 90 percent. In a simple queueing model (M/M/1) the average time in the system is service time / (1 - utilization). At 50 percent utilization that is 2x service time; at 90 percent it is 10x; at 95 percent it is 20x. Tail latency is even worse. A system at 90 percent has no room for any burst, and any slow-down tips it into queue collapse.

Why is autoscaling not a substitute for overload protection? Intermediate

Say this: "Autoscaling reacts in minutes, overload kills in seconds. It also depends on the control plane, can be capped by quotas or by a downstream dependency, and new instances start cold. So I use autoscaling for gradual change and keep load shedding, concurrency limits and headroom for sudden spikes."

The timeline problem. A spike doubles traffic at t=0.

  1. t=0 to 60 s: metrics are collected and aggregated; the alarm needs a few data points before firing.
  2. t=60 to 120 s: the scaler decides and requests new instances.
  3. t=120 to 300 s: instances launch, boot, pass health checks, warm caches and JIT.

For up to five minutes the existing fleet is overloaded. Without shedding, it collapses before help arrives, and new instances then join a system in crisis.

Other limits.

  • Control plane dependency: scaling needs APIs that may be impaired in the very incident that causes the spike.
  • Quotas and capacity: account limits, or no capacity available in the zone.
  • Downstream bottleneck: scaling the app tier just pushes more load onto the same database or third-party API, making the real bottleneck worse. More connections can kill a database.
  • Cold start: new instances may be given full traffic immediately, before they are warm.

Practice. Scale on a leading indicator (queue depth, concurrency, request rate) rather than CPU alone, scale out early and in slowly, use slow-start for new instances at the load balancer, and combine it with the protections above.

What is the difference between an SLI, SLO and SLA? Basic

Say this: "The SLI is the measurement, the SLO is the internal target for it, and the SLA is the external contract with consequences if broken, set looser than the SLO so there is a margin."

  • SLI (indicator): a measured number, such as the fraction of requests that succeed in under 300 ms.
  • SLO (objective): the internal target for it, such as 99.9 percent over 30 days.
  • SLA (agreement): the contract with customers, with consequences (service credits, penalties) if broken. For example an SLA of 99.5 percent while the internal SLO is 99.9 percent, so you have warning time before you owe money.

Example chain. SLI: share of checkout requests returning success within 500 ms, measured at the load balancer. SLO: 99.9 percent of them over a rolling 30 days. SLA: customers get a credit if monthly availability falls below 99.5 percent.

Choosing SLIs. Pick what users feel: availability (good requests / valid requests), latency percentiles, freshness (age of data), correctness, durability. Prefer percentiles to averages, because averages hide tails: an average of 100 ms can hide 1 percent of users waiting 5 s.

Pitfall. Too many SLIs. Have a few per service that map to user journeys; more than that, nobody looks at them.

What is an error budget and how does it change team behaviour? Intermediate

Say this: "Error budget is 100 percent minus the SLO: the amount of unreliability you are allowed. While budget remains, the team ships and takes risks; when it is spent, the team slows feature releases and invests in reliability until it recovers. It settles the speed versus safety argument with data."

Numbers. A 99.9 percent monthly SLO gives a budget of 0.1 percent. In request terms: of 100 million requests, 100,000 may fail. In time terms: about 43 minutes of full outage per 30 days.

How it works in practice.

  1. Track the budget burned this month: bad requests / allowed bad requests.
  2. Plenty left: release freely, run experiments, take on risky migrations.
  3. Nearly spent or exhausted: freeze risky releases and focus on reliability (fix top causes, add tests, improve rollbacks) until the window recovers.

Why it helps.

  • It replaces opinion ("we ship too fast" vs "we are too slow") with a shared number agreed in advance.
  • It shows that a 100 percent target is wrong: it is nearly infinitely expensive, and leaves no room for any change, since every change carries risk.
  • It also stops over-investing in reliability: if the SLO is met comfortably with budget left over, you can afford more speed or take on more risk.

Pitfall. An SLO that no one has agreed to enforce. The policy ("what happens when the budget is gone") must be agreed with product and management beforehand, or the budget is just a graph.

How do you alert on SLOs without drowning in noise? Senior

Say this: "I alert on burn rate, how fast the error budget is being consumed compared with the rate that would exactly use it up by the end of the window, using multi-window, multi-burn-rate alerts: page on a fast burn over both a long and a short window, and ticket on a slow burn. That pages only for what matters to users."

Definition. Burn rate 1 means you are spending the budget exactly as fast as the window allows, ending at zero when the window ends. Burn rate 14.4 means a 30-day budget would be gone in 30 / 14.4 = about 2 days (and consuming 2 percent of the monthly budget in one hour).

Why not alert on raw error rate? A fixed threshold either pages for every blip (noisy) or misses a slow steady leak (silent). Burn rate ties the alert directly to the budget.

The multi-window approach (from Google's SRE workbook).

The long window shows the problem is sustained and significant; the short window makes the alert reset quickly after you recover, so it does not keep firing for an hour after the fix.

Result. A brief 2-minute blip that costs little budget does not page anyone; a real incident that is eating the month's budget pages within minutes; a slow leak becomes a ticket.

Your service has a 99.99 percent SLO but depends on a third-party API with a 99.9 percent SLA. What do you do? Senior

Say this: "I cannot exceed my hard dependencies' availability, so I turn the hard dependency into a soft one or reduce reliance on it: cache and serve stale, make the call asynchronous with a queue, add a second provider, and put a breaker with a fallback around it. Or I honestly set the SLO to what is achievable."

The math. If every request needs the third party, my availability is at most 0.9999 x 0.999 = about 99.89 percent: the dependency's 43 minutes a month of allowed downtime is ten times my entire 4.3 minute budget.

Options, most to least effective.

  1. Take it off the critical path. Do the call asynchronously: accept the order now, charge or notify when the provider is back (a queue with retries). The user path no longer depends on it.
  2. Cache and serve stale on error for data that tolerates it (exchange rates, geocoding results).
  3. Second provider with failover. Two providers each at 99.9 percent (independent) in parallel give about 99.9999 percent. Costs: integration work and behaviour differences, and the secondary must be tested regularly.
  4. Circuit breaker plus fallback to give a fast degraded answer.
  5. Define the SLI honestly. You may exclude the dependency's failures from your SLI only if the contract and users accept it (rarely accepted); otherwise set the SLO to what is achievable.

What to say in the interview. Show the multiplication, then pick an architecture that makes the dependency soft. And mention measuring the vendor's actual performance, not just the SLA on paper (SLAs usually pay credits, they do not give you uptime).

What is your general checklist for handling any dependency failure? Intermediate

Say this: "Classify hard or soft, set timeouts and propagate deadlines, retry only idempotent calls with backoff, jitter and a budget at one layer, add a breaker and bulkhead, define and test the fallback, add per-dependency metrics, test slow and down in load and chaos tests, and decide what happens at startup when the dependency is down."

  1. Classify: hard (cannot work without it) or soft (can degrade).
  2. Timeouts: connect and read timeouts, plus a propagated deadline.
  3. Retries: only for idempotent calls, with backoff, jitter and a budget, at a single layer.
  4. Circuit breaker and bulkhead: to stop calls to a failing dependency and cap its resource use.
  5. Fallback: define it (stale, default, queue, fail open or closed) and test it.
  6. Metrics: latency histograms, error rates per dependency, breaker state, pool saturation. You cannot manage what you cannot see.
  7. Load and chaos test: the dependency being slow and being down, not only fast and up.
  8. Startup behaviour: what happens if the dependency is down while this service boots? Do not crash-loop; start in a degraded mode and keep retrying in the background.

Example application. A new "fraud score" call in checkout: classify as soft for low amounts (default to allow, fail open) and hard for high amounts (fail closed); timeout 150 ms; one retry; breaker; metrics; chaos test with 5 s latency.

What is a metastable failure? Senior

Say this: "A metastable failure is a state where the system stays broken even after the original trigger is gone, because a sustaining feedback loop, usually retries, cache misses with expensive recomputation, or queue backlogs, keeps load above capacity. Recovery means breaking the loop: shed load, disable retries, pre-warm, and ramp back gradually."

The shape. The system has two stable states: healthy and overloaded. In the healthy state it handles load easily. A trigger (a deploy, a short outage, a traffic spike) pushes it into overload. Normally it would return when the trigger ends. But the overloaded state itself generates load that sustains it, so it stays there.

Example. A brief database slowdown causes cache entries to fail to refill. The high miss rate sends more queries to the database, which keeps it slow, which keeps the cache from refilling. Even after the slowdown's cause is fixed, the loop sustains itself. Other loops: clients retrying timed-out requests, or a backlog whose items are expensive and time out before finishing.

Recovery.

  • Cut load below capacity: shed aggressively, block non-critical callers.
  • Disable retries, or lower retry limits.
  • Pre-warm caches before readmitting traffic.
  • Shrink the request rate, then ramp back gradually (10, 25, 50, 100 percent).

Prevention. Do not rely on caches for survival; keep retry loops bounded with budgets; keep headroom; use admission control and queue-age limits; and drop work whose caller has given up. The research literature on this (Bronson, Huang and colleagues) describes how common it is in large systems.

Why is a long queue in front of a service a hidden danger? Intermediate

Say this: "By Little's law, wait time is queue length divided by throughput. A long queue means long delays that exceed the caller's timeout, so the server does work no one is waiting for. I use short bounded queues, drop items past their deadline, and reject fast so the client can try elsewhere."

Numbers. A queue of 10,000 requests in front of a service that completes 1,000 per second means the last request waits 10 seconds. If clients time out after 2 seconds, every request beyond the first 2,000 in the queue will have been abandoned by the time it is served. The server happily spends its capacity on dead requests, and the useful throughput (goodput) is close to zero while it looks 100 percent busy.

Why it is hidden. A large queue seems like a safety buffer ("nothing is dropped"). In reality it only converts overload into latency and wasted work, and delays the signal clients need to back off.

Better design.

  • Small, bounded queues sized from the latency you can tolerate: max wait = length / throughput.
  • Drop requests older than their deadline when they reach the front.
  • Reject fast when full, with Retry-After, so clients can fail over or back off.
  • Consider serving newest first (LIFO) under overload.

The exception. In batch or background workloads (no waiting caller) long queues are fine and even desirable, since throughput matters more than latency there.

Situational and real-life scenarios

Your checkout service suddenly has p99 latency of 30 s and thread pools full. The only change is that the recommendation service got slow. What do you do, and what should have prevented it? Senior

Say this: "First stop the bleeding: kill-switch or open the breaker for recommendations so checkout stops waiting on it. Then explain why it happened: a soft dependency was treated like a hard one, with no timeout, a shared thread pool and no fallback. Then fix it with a short timeout, a bulkhead, a breaker with an empty-list fallback and a chaos test."

What is happening. Each checkout request calls recommendations, which now takes 20 to 30 s. Threads wait on it, the pool fills, and new requests queue for a thread. Even requests that would have succeeded wait in line, so p99 jumps to 30 s. Little's law: threads in use = arrival rate x time per request, so a 1000x slower call means 1000x more threads needed.

Right now (mitigate before diagnosing).

  1. Turn off the recommendation call with a feature flag or kill switch, or open its breaker manually. Checkout does not need it to take payment.
  2. Restart or scale only if the pool does not drain by itself; scaling alone will not help because new threads also block.
  3. Confirm checkout p99 and error rate recover, then tell stakeholders.

Root cause. A soft dependency was handled as a hard one: no (or a long) timeout, shared the thread pool with checkout, no fallback.

Permanent fixes.

  • A 100 to 200 ms timeout on the recommendation call.
  • A separate bulkhead (own pool or concurrency limit) so it can never take more than, say, 20 threads.
  • A circuit breaker with an empty-list or popular-items fallback.
  • A chaos test: "recommendations return in 10 s" must leave checkout latency unchanged.
  • Alerts on pool saturation and breaker state.

The deeper lesson to state aloud: every dependency needs a classification (hard or soft) at design time.

A database failover took 40 seconds. After it completed, the new primary stayed overloaded for 30 minutes. Why, and what do you do next time? Senior

Say this: "That is a metastable failure caused by a retry storm and a thundering herd. During the 40 seconds, requests timed out and were retried, connection pools reconnected all at once, and queues filled, so the new primary got the backlog plus fresh traffic plus retries on cold caches. I shed load, cap retries, restart the app tier in waves and ramp traffic up in steps, and I prevent it with budgets, jitter and a failover game day."

Why it stayed overloaded.

  1. For 40 s the database was unavailable. Clients' calls timed out; many retried (3 attempts each).
  2. App-level queues and thread pools filled with waiting requests.
  3. Connection pools in hundreds of app instances all reconnected at the same instant.
  4. The new primary came up with cold caches (empty buffer pool) so each query was slower than usual.
  5. It received: the backlog, plus the new normal traffic, plus the retries. Offered load was well above capacity. Slower queries mean more timeouts, which means more retries: a loop that sustains itself.

Handle it live.

  • Shed load at the edge: lower rate limits, reject non-critical traffic, drop old queued work.
  • Disable or cap retries (a config flag helps greatly here).
  • Restart or drain the app tier in waves so connections return gradually.
  • Ramp traffic up in steps (10, 25, 50, 100 percent) while watching database latency.

Prevent it.

  • Retry budgets, exponential backoff and jitter.
  • Connection pool limits and slow, jittered reconnect.
  • A server-side concurrency limit on the database proxy.
  • A failover game day that measures what happens after the failover completes, not only that it completes.
  • A runbook step: "ramp traffic gradually after failover".
One of three AZs loses power during peak. Your service is at 80 percent utilisation. What happens? Senior

Say this: "Two AZs now carry the load three were carrying: 80 percent divided by two thirds is 120 percent of their capacity. They overload, latency climbs, timeouts and retries pile on, and the survivors fail too. I shed low-priority traffic and degrade features immediately, scale out by hand, and the design fix is to stay under about 66 percent at peak and drain an AZ in game days."

The arithmetic. Capacity of 3 AZs = 3 units; load = 80 percent of 3 = 2.4 units. After losing one AZ, capacity is 2 units. Load / capacity = 2.4 / 2 = 120 percent. The remaining AZs cannot carry it.

What happens next.

  1. Queues grow and latency rises beyond timeouts.
  2. Clients retry, adding more load (a retry storm).
  3. Health checks start to fail on overloaded instances, removing even more capacity: a cascade.
  4. Autoscaling begins, but launching instances takes minutes, and every other customer in that region failing over at the same time competes for the same spare capacity.

Immediate actions. Shed lowest-priority traffic and turn off expensive features to bring demand below 100 percent of the remaining capacity (for example, less than 2 units), scale out manually and fast, block retries, and keep health checks from removing healthy-but-busy instances.

Design fix.

  • Keep peak utilization below about 66 percent in a 3-AZ design (50 percent in a 2-AZ design).
  • Pre-provision for the AZ loss (static stability) rather than relying on scale-up at the time of the incident.
  • Have load shedding and priorities in place.
  • Prove it by draining an AZ in a game day.
Every day at exactly 09:00 your database CPU spikes to 100 percent for a minute. Why might that be, and how do you fix it? Intermediate

Say this: "A spike at a precise clock time means something is synchronized: many cache keys with the same TTL set at the same moment, cron jobs started by many nodes together, a scheduled campaign hitting a hot key, or clients reconnecting. That is a thundering herd. I find the pattern in logs, then add jitter, single-flight and staggering."

Find it first. Look at the queries and keys at 09:00 in the database slow log, cache miss metrics and scheduler logs. Common culprits:

  • A cache warm-up or batch job at 08:00 set 100,000 keys with a 1-hour TTL. At 09:00 they all expire together, and all requests miss at once.
  • A cron job configured as "0 9 * * *" on every node.
  • A marketing email or push notification at 09:00 sends thousands of users to the same page.
  • Daily reports or exports scheduled at the same time.

Fixes, matching the cause.

  • Jitter TTLs: ttl = 3600 + random(0, 360) so keys expire over six minutes, not one second.
  • Single-flight cache rebuild: one request rebuilds, others wait.
  • Refresh ahead of expiry or serve stale while revalidating.
  • Stagger cron jobs with a random delay or hash of the hostname.
  • Rate limit or run the batch job off peak and throttle it.

Verify afterwards by checking that the 09:00 spike flattens in the CPU graph.

A config change pushed to all servers at once makes every instance crash on startup. How could you have avoided it, and how do you recover? Senior

Say this: "Treat config as code: review, schema validation, tests, and a staged rollout with automatic revert to last known good. To recover, roll back centrally, and make sure there is an out-of-band path to fix crash-looping nodes, since the tools you need must not depend on the thing that is broken."

How to avoid it.

  1. Validate before push: schema checks and a dry-run load of the new config in a test instance.
  2. Stage the rollout: canary, then one AZ, then one region, with bake time and health checks between stages. A crash on the canary stops the rollout at 1 percent.
  3. Last known good: instances keep the previous config and automatically revert if the new one fails to load or fails health checks.
  4. Tolerant parsers: ignore unknown fields and do not crash on a bad optional value; fall back to defaults and alert.
  5. Review and audit: the same discipline as for code.

How to recover.

  • Roll back the config in the central store.
  • Crash-looping instances may not be able to fetch the fix. They need a path that works while they are down: config distribution that does not depend on the failing service, or an out-of-band way to push the previous version.
  • Restart in waves, not all at once, to avoid a thundering herd on dependencies.

Why out-of-band access matters. Several well-known outages were prolonged because the recovery tools depended on the broken system. Facebook's October 2021 outage was reported as triggered by a configuration change to backbone routers, and it also disrupted internal tools engineers needed to fix it. Recovery access (consoles, credentials, comms) should live outside the blast radius.

A major cloud provider has a regional service outage. Your app is multi-AZ but single-region. What can you do during the event, and what do you do afterwards? Senior

Say this: "During the event I cannot add capacity in the failing region, so I focus on communication, shedding load and degrading features, and decide on failover to another region if a warm standby or restore path exists and the outage looks long compared with my RTO. Afterwards I decide with the business whether multi-region is worth its cost, and at minimum add cross-region backups, a pilot light for the critical path, and recovery without control-plane dependency."

During.

  • Communicate: status page, customer messages, internal incident channel.
  • Shed load and degrade: read-only mode, serve from cache, disable non-essential features.
  • Check which of your own dependencies live in the same failing region: CI/CD, monitoring, logging, status page, login, the runbooks themselves. They may be unavailable too.
  • Decide on failover: compare the expected outage duration (the provider's estimates are often optimistic) with your RTO. If you have a standby or restorable backups elsewhere, the cost of failing over versus waiting should be an explicit call by the incident commander.

Afterwards.

  1. Quantify the impact and compare with the cost of multi-region (money and complexity). Decide with the business.
  2. At minimum: cross-region backups, and a pilot light or warm standby for the critical path.
  3. Make recovery not depend on the failing region's control plane.
  4. Inventory hidden dependencies on that region.
  5. Rehearse the failover.

A well-known example. The 2017 AWS S3 outage in us-east-1 was widely reported as caused by an operator command that removed more servers than intended. It hit many sites whose own status pages or tools depended on S3. The lesson is hidden dependencies and the need for tested recovery of foundational services.

Your circuit breaker opens and closes every few seconds ("flapping") and users see intermittent errors. What do you check? Senior

Say this: "I check the minimum request volume, the open duration and half-open probe count, which errors are being counted, how widely the breaker is shared, and whether the threshold matches the normal error rate. Usually the breaker is too sensitive or too coarse."

What flapping looks like. Closed, then a few failures trip it, open for a few seconds, half-open probes, close, a few failures, open again. During each open window users get errors or fallbacks, even though the dependency is mostly healthy.

  • Minimum request volume too low: 3 failures out of 4 calls trips it. Require a minimum number of calls (for example 20) in the window.
  • Open duration too short: half-open probes hit a still-sick dependency, fail, reopen. Lengthen it or back off exponentially.
  • Counting the wrong errors: 4xx responses and business exceptions are not dependency health. Count 5xx, timeouts and connection errors.
  • Shared across too many hosts or endpoints: one bad endpoint opens the breaker for all. Split per endpoint or per host.
  • Threshold too sensitive: if the dependency normally has 2 percent errors, a 5 percent trip point is noise. Set from data.
  • Too many half-open trial calls overload a recovering service; allow only a few.
  • Slow-call threshold too strict: normal variation counts as failure.

How to confirm. Plot breaker state changes against the dependency's error and latency metrics. If the dependency graph is flat while the breaker flips, the configuration is wrong, not the dependency.

Customers report being charged twice. Payments timed out and the client retried. How do you fix it properly? Intermediate

Say this: "The retried POST was not idempotent. I add a client-generated idempotency key per payment attempt, store it atomically with the result using a unique constraint, return the stored result for repeats, and pass the key to the payment provider. I add reconciliation for cases that slip through, refund the duplicates, and I do not rely on the UI to prevent it."

What happened. The client sent "charge 50 dollars". The server charged, but the response was slow or lost, and the client timed out. The client could not know the result, so it retried, and the server charged again.

The proper fix.

  1. Idempotency key: the client generates a UUID per payment attempt and sends the same one on every retry.
  2. Atomic claim: the server inserts the key in the same transaction as the charge record, with a unique constraint. A duplicate insert fails and the stored result is returned instead.
  3. Pass the key downstream: to the payment provider, if it supports idempotency, so the card network sees only one charge.
  4. Reconciliation: a nightly job compares our ledger with the provider's records and flags duplicates or missing charges.
  5. Refund the affected customers and communicate.
  6. UI guard: disable the pay button after a click, to reduce accidental double submits. Useful, but never the only protection, since retries also come from proxies, mobile networks and client libraries.

Mention the timeout-handling policy too: on timeout, query the status of the payment by key before deciding to retry.

One tenant's batch job runs a heavy query pattern and slows every other tenant. What do you do short and long term? Intermediate

Say this: "Short term, throttle or block that tenant and kill the offending queries. Long term, per-tenant rate limits and concurrency caps, separate pools or queues for batch versus interactive traffic, query cost limits, moving big tenants to their own cell or shard, and per-tenant metrics so I see it quickly."

Short term (stop the harm).

  • Apply a rate limit or quota to that tenant, or temporarily pause its job.
  • Kill or cancel the heavy queries in the database.
  • Confirm other tenants recover.

Long term (stop it recurring).

  1. Per-tenant limits: request rate and concurrency caps (a bulkhead per tenant), so one tenant can use only its fair share.
  2. Separate lanes: distinct pools, queues or replicas for batch and for interactive traffic, so batch cannot starve interactive.
  3. Priority scheduling so interactive requests win when resources are tight.
  4. Query protection: cost limits, statement timeouts, and maximum rows scanned.
  5. Isolation for the biggest tenants: their own cell, shard or dedicated resources.
  6. Visibility: per-tenant metrics (requests, latency, resource use) and alerts, so the offender is obvious in minutes.

This is the noisy-neighbour problem in multi-tenant systems, and the answer is always some form of isolation plus limits.

An interviewer asks: "Your design depends on an auth service in the request path. What if it is down?" How do you answer? Senior

Say this: "I reduce how often the auth service is called, with signed tokens verified locally, and I cache decisions briefly. I build the auth service to the highest availability, since everything depends on it. If it is unreachable, existing valid tokens keep working until expiry, new logins show a clear error, and risky actions fail closed while low-risk reads continue."

  1. Reduce calls. Use signed tokens (JWT or similar) that every service verifies locally with cached public keys. The auth service is then needed only at login and at token refresh, not on every request.
  2. Cache authorization decisions for short periods (seconds to minutes), accepting a small window of stale permissions.
  3. Build auth for availability: multi-AZ and multi-region, with its own bulkheads and headroom, and the highest SLO in the company, since an auth outage is a total outage.
  4. Define degraded behaviour when it is unreachable:
    • Existing valid tokens continue to work until they expire (static stability), so short outages are invisible. Choose token lifetimes with this in mind: long enough to ride out outages, short enough to limit damage from a stolen token.
    • New logins show a clear error.
    • Risky actions (payments, admin changes) fail closed; low-risk reads can continue.
  5. Protect it from itself: rate limit and cache negative results, so a retry storm after recovery (everyone logging in again at once) does not knock it down again; use jittered token refresh.

Trade-off to mention. Local token verification makes immediate revocation harder; mitigate with short lifetimes, or a small revocation list distributed to services.

You are on call and a dashboard shows error rates climbing across the fleet. What are the first steps? Intermediate

Say this: "Assess impact and declare an incident with a commander and a communicator. Ask what changed and roll it back if something correlates. Mitigate before diagnosing. Isolate the bad part, communicate on a regular cadence, and afterwards write a blameless postmortem with owned actions."

  1. Assess and declare. How many users are affected, how badly? Declare an incident; assign an incident commander (coordinates, decides) and a communicator (updates stakeholders), so engineers can focus on fixing.
  2. Ask "what changed?" Deploys, config pushes, feature flags, traffic shifts, dependency changes, certificate expiries. Check the change log first. If a recent change correlates, roll it back or flip the flag off. This resolves a large share of incidents in minutes.
  3. Mitigate before diagnosing. If it is load: shed or throttle, scale, disable expensive features, block retries. The goal is restoring service; root cause can wait.
  4. Isolate. Is it one AZ, one region, one dependency, one tenant, one version? Drain or disable the bad part.
  5. Communicate status at a steady cadence (for example every 15 to 30 minutes), even when there is nothing new.
  6. Afterwards: a blameless postmortem with a timeline, root causes and contributing factors, what went well, and action items with owners and dates.

Mindset to show. Calm, structured, mitigation first, no hero debugging alone, and learning from it.

More conceptual questions

What does "fail fast" mean, and is it always right? Basic

Say this: "Fail fast means detecting a problem as early as possible and reporting it immediately, instead of continuing in a bad state or waiting a long time. It saves resources and makes problems visible. It is not right when a short wait or retry would likely succeed, or when failing a whole startup for a nonessential dependency makes things worse; there I prefer degraded mode."

Examples where it is right.

  • Validate input at the edge and reject bad requests before doing expensive work.
  • Refuse to start if required config is missing, rather than running with a wrong default and corrupting data.
  • Reject requests immediately when overloaded (load shedding) instead of queueing them.
  • An open circuit breaker rejecting calls to a dead dependency.

The benefit: the caller learns quickly, can choose another path, and no resources are held.

Where it is wrong.

  • Transient blips: a single dropped connection that a quick retry would fix.
  • Startup with an optional dependency down: crashing the whole service because a nonessential component is unavailable turns a minor problem into an outage, and a crash-loop adds load. Start degraded and retry in the background.
  • When failing means losing data that could still be saved with a brief wait.

Rule. Fail fast on conditions that are certain to be bad (invalid input, missing mandatory config, known overload). Be patient, with bounded retries, on conditions that are likely temporary.

What are MTBF and MTTR, and why do many teams focus on MTTR? Intermediate

Say this: "MTBF is mean time between failures; MTTR is mean time to recover. Availability is roughly MTBF / (MTBF + MTTR). To gain a nine you can make failures ten times rarer, which is very hard, or recover ten times faster, which automation, fast rollback and redundancy often make more achievable."

Worked example. A service fails on average once every 1,000 hours (MTBF) and takes 1 hour to recover (MTTR): availability = 1000 / 1001 = 99.9 percent.

ChangeMTBFMTTRAvailability
Baseline1,000 h1 h99.90%
Failures 10x rarer10,000 h1 h99.99%
Recover 10x faster1,000 h0.1 h (6 min)99.99%

Both give four nines, but they are not equally easy.

Why MTTR often wins.

  • In complex systems failures are inevitable. Bugs, human errors, and dependencies mean you cannot push the failure rate to zero, and every new feature adds failure modes.
  • Recovery speed is something you can engineer and rehearse: better detection (alerts within a minute), automatic failover, one-click rollback, feature flags, runbooks.
  • Reducing blast radius (cells, canaries) is a form of improving MTTR-weighted impact, since fewer users are affected for the same duration.

Nuance. MTTR is made of detect, diagnose, fix, verify. Each can be shortened: detection with good alerting, diagnosis with observability, and fix with rollback. Also, means hide the distribution: one 8-hour outage and many small ones both give the same average, but customers feel them differently. Track percentiles and the worst cases.

With at-least-once delivery and retries, how do you get effectively-once results? Intermediate

Say this: "True exactly-once delivery over an unreliable network is not possible in general. What I build is at-least-once delivery plus an idempotent consumer, and, on the producer side, an outbox so the database change and the publish cannot diverge."

Why not exactly-once delivery. If a consumer processes a message and the acknowledgment is lost, the broker cannot tell whether the work was done. It must redeliver (at-least-once) or risk losing the message (at-most-once). So duplicates are a fact of life.

Consumer side: idempotency. Make the effect of processing the same message twice equal to processing once.

  • Dedupe table: record the message id in the same database transaction as the side effect. On redelivery, the insert of the id fails (unique constraint), so skip.
  • Natural idempotency: operations like "set status to shipped" or "upsert by key" are safe to repeat.
BEGIN;
INSERT INTO processed(msg_id) VALUES ('m-42');   -- fails if already processed
UPDATE orders SET status='shipped' WHERE id=7;
COMMIT;

Producer side: the outbox pattern. A service updates its database and must publish an event. Doing both separately can leave them inconsistent (the database commit succeeds, the publish fails). Instead, write the event to an "outbox" table in the same transaction as the business change, and a separate relay publishes outbox rows to the broker (with retries, so at-least-once). Consumers dedupe.

Note. Some systems (Kafka transactions, for example) advertise exactly-once semantics within their own boundary (read, process, write back to Kafka). That does not extend to arbitrary external side effects, which still need idempotency.

Which signals tell you a service is becoming unhealthy before users complain? Intermediate

Say this: "The four golden signals from Google SRE: latency, traffic, errors and saturation. Saturation is the leading indicator and errors are lagging. For resilience I add p99 latency per dependency, queue depth and age, pool saturation, retry rate, breaker state changes, shed counts, replication lag, burn rate and cache hit rate."

The four golden signals.

  • Latency: how long requests take, with successful and failed requests separated (a fast error can hide a slow problem).
  • Traffic: demand, such as requests per second.
  • Errors: rate of failed requests, including implicit failures like wrong or too-slow answers.
  • Saturation: how full the most constrained resource is (CPU, memory, threads, connections, queue length).

Why saturation leads. As a resource approaches full, latency rises first, and errors appear only at the end. Alerting on saturation (for example thread pool at 80 percent, queue age rising) gives minutes of warning.

Resilience-specific signals.

  • p99 latency per dependency (to catch a slow dependency early).
  • In-flight requests, queue depth, and age of the oldest item.
  • Thread and connection pool saturation.
  • Retry rate, and retries as a share of traffic (a rising ratio indicates trouble or a storm).
  • Circuit breaker state changes.
  • Shed or rejected request counts.
  • Replication lag.
  • Error budget burn rate.
  • Cache hit rate (a falling rate predicts database overload).

Practice. Alert on symptoms users feel (SLO burn) with page-level urgency, and use the cause-oriented signals above for dashboards and early tickets.

How do you shut down or deploy instances without dropping requests? Intermediate

Say this: "On a termination signal the instance marks itself not ready so the load balancer stops sending new work, finishes in-flight requests within a grace period, closes connections and releases leases, then exits. Pitfalls are the load balancer's lag in noticing, long-lived connections, and unacknowledged messages."

  1. The instance receives a termination signal (SIGTERM).
  2. It marks itself not ready, so the load balancer stops sending new requests (deregistration delay).
  3. It finishes in-flight requests, up to a grace period (for example 30 s).
  4. It closes connections, flushes buffers, and releases leases or locks.
  5. It exits. It is killed forcefully (SIGKILL) only if the grace time runs out.

Pitfalls and fixes.

  • Load balancer lag: the balancer keeps routing for a few seconds after deregistration or readiness failure, since it needs time to notice. Sleep briefly (several seconds) after becoming not-ready before closing listeners.
  • Grace period too short for the longest legitimate request, causing aborted requests. Keep request timeouts below the grace period.
  • Long-lived connections (websockets, streaming, gRPC streams): send a close or go-away signal and have clients reconnect with jitter, so they do not all reconnect to the same instance.
  • Message consumers: stop polling, finish or return unacknowledged messages so they are redelivered, and commit offsets properly.

On startup, the reverse. Warm up (load caches, JIT, connection pools) before reporting ready, and use slow start so the load balancer ramps traffic to the new instance instead of sending it full traffic cold.

How does moving from synchronous calls to asynchronous messaging improve resilience, and what does it cost? Intermediate

Say this: "With synchronous calls availability multiplies down the chain and latency adds up. With a durable queue or log in between, the producer succeeds once the message is stored, and the consumer can be down, slow or deploying with no user impact. That is temporal decoupling. The costs are eventual consistency, extra components, idempotent consumers and backlog management."

Synchronous chain. Order service calls Inventory, which calls Pricing, which calls Tax. All four must be up at the same moment, and the user waits for all. If each is 99.9 percent available, the chain is about 99.6 percent, and latency is the sum.

With a queue. The order service validates and writes an "OrderPlaced" event to a durable log, and returns. Inventory, billing and email consume at their own pace. If the email service is down for an hour, messages wait and are delivered after recovery; no customer sees an error. A slow consumer slows only its own backlog.

Costs and what you must handle.

  • Eventual consistency: the result is not available immediately. The user sees "order received" before it is fulfilled.
  • No immediate answer: unsuitable where the user needs an answer now.
  • A new system to operate and monitor (the broker), and it becomes a critical dependency to make highly available.
  • Idempotent consumers (at-least-once means duplicates) and ordering decisions.
  • Backlog management: bound and monitor the age of the oldest message, and have a dead-letter queue.
  • Harder debugging: tracing across an asynchronous hop needs correlation ids.

Decision rule. Use synchronous where the user needs the answer now (checking a balance, authorizing a card), asynchronous where the work can be deferred (emails, analytics, fulfilment, notifications).
