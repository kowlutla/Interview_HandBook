How to use this page

Each question opens to reveal a model answer. Try to answer out loud first, in about 60 seconds, then open it. Questions are tagged Basic, Intermediate or Senior. In an interview, the pattern that impresses is: state the principle, give a concrete failure example, then name the trade-off you would accept. The theory here is the vocabulary you use when defending any design. Where a number or a product detail varies by version, the answer says so.

1. Why distributed systems are hard

Why is a distributed system fundamentally harder than a single-machine program? Basic
In one line: on one machine a call either returns or the whole process dies; across machines parts fail independently, the network lies about what happened, and nobody shares a clock.

What it is. A distributed system is a set of computers that cooperate over a network and present themselves as one service. Everything that was free on one machine (a function call that either works or crashes, shared memory, one clock) has to be rebuilt on top of unreliable parts.

Why it is harder. Three problems appear that you cannot engineer away:

  • Partial failure. Node B can be dead while node A is fine. On one machine a crash takes everything down together, so there is no in-between state. Across machines the caller often cannot tell what happened to its request.
  • Unreliable networks. Messages can be lost, delayed, duplicated or reordered, and there is no upper bound on delay. "Slow" and "dead" look the same from outside.
  • No shared clock, no shared memory. Each node only knows its own state plus what it was told, and what it was told may already be stale. Two nodes cannot reliably agree on "which happened first" just by comparing timestamps.

A tiny example. On one machine, balance -= 100; shipping.start() either both run or the process dies and you restart from a known state. Across two services, the payment call can succeed while the shipping call times out. Now the system is in a state that no single-machine program could ever be in, and you must decide what to do about it.

What the field does about it. Most of distributed systems theory is a toolbox for building something reliable out of unreliable parts: replication (survive node loss), consensus (agree despite failures), timeouts and retries (cope with silence), idempotency (make retries safe) and careful consistency choices (decide how stale is acceptable).

Pitfall. Treating a remote call like a local call (same error handling, no timeout, no retry policy). That is the single most common source of production incidents in microservice systems.

What is partial failure, and why is it the root of most distributed bugs? Basic
Say: "A timeout does not mean failure. It means I do not know. So every write that crosses a network needs an idempotency key or a way to query its outcome."

What it is. Partial failure means one part of the system is broken while the rest works. The danger is not the failure itself but the ambiguity it creates for whoever is waiting.

The classic example. Your order service sends "charge 500" to the payment service and gets a timeout. Three different worlds are possible, and from your side they look identical:

  1. The request never arrived. Nothing was charged.
  2. The payment service processed it, but the response was lost on the way back. The customer was charged.
  3. The payment service is still working on it, slowly. It will charge in a moment.

If you retry blindly, then in worlds 2 and 3 you charge twice. If you give up and tell the user "failed", then in world 2 you took money and gave nothing. You cannot pick the right action because you lack the information.

The fix is to remove the need to know.

  • Idempotency: attach a unique key (say pay-order-8841) to the request. The payment service stores the key and result, so a retry returns the original result instead of charging again. Now retrying is always safe.
  • Outcome query: expose "what happened to request X?" so the caller can look it up after a timeout.
  • Reconciliation: a background job compares both sides and repairs differences.

Why it is "the root". Almost every distributed bug (double charges, lost updates, orphaned records, stuck workflows) is a handling mistake for one of the three worlds above. Interviewers often start with this because it shows whether you think in "unknown outcome" rather than "success or failure".

Pitfall. Believing a short timeout makes the problem go away. A shorter timeout only makes the ambiguity happen more often.

What are the fallacies of distributed computing? Basic
In one line: eight comfortable but false assumptions (network reliable, latency zero, and so on) that new distributed-system builders make; each one maps to a design rule.

What it is. A list compiled at Sun Microsystems (originally by Peter Deutsch and colleagues, with the eighth added by James Gosling). Programmers coming from single-machine code silently assume these things are true. Each assumption breaks in production and creates bugs that are hard to reproduce.

Why it matters. The list doubles as a design checklist. If you can say, for each fallacy, "so I add X", you are showing the habits of someone who has operated these systems.

Concrete example. A page that makes 40 sequential service calls at 0.5 ms each looks fine on a laptop. In production at 20 ms cross-zone, that is 800 ms of pure waiting. Fallacy 2 in action.

Pitfall. Reciting the list without examples. Pick two or three and tell a short story about each.

What is the Two Generals problem, and what does it tell us about acknowledgements? Intermediate
Say: "Over a channel that can lose messages, no finite number of acks gives both sides certainty. So we settle for at-least-once delivery plus an idempotent receiver."

The story. Two armies sit on opposite sides of a valley and must attack at the same time to win; if only one attacks, it loses. They can only communicate through messengers who might be captured. General A sends "attack at dawn". Did B get it? Only if B replies. But B's reply might be lost, so A cannot be sure B knows that A knows. If B acks, then A must ack B's ack, and so on forever.

Why no solution exists. Imagine any protocol that finishes after N messages. Look at the last message. The sender cannot know whether it arrived. If the protocol still works when that last message is lost, the message was unnecessary and we can drop it. Repeat the argument and you strip the protocol down to nothing. So no finite exchange creates certainty (what theorists call common knowledge).

What it means in practice.

  • You cannot build "exactly-once delivery" as a pure network property. The sender never knows if a message arrived, so it must resend when in doubt, which produces duplicates.
  • Practical protocols use at-least-once delivery plus an idempotent receiver (dedupe by id), which together give the effect of exactly-once.
  • TCP acknowledges that bytes reached the peer's kernel, not that the application processed them. If the app crashes after the ack but before processing, the data is gone. Application-level acks (commit offsets, HTTP 200 after commit) are needed.
  • Commit protocols such as 2PC do not solve this problem; they trade it for blocking when the coordinator fails.

Pitfall. Do not confuse this with the Byzantine Generals problem (nodes that lie); here the only issue is lost messages.

What does the FLP impossibility result say, and does it mean consensus is impossible in practice? Senior
Say: "FLP says no deterministic algorithm can guarantee both safety and termination in a fully asynchronous system with even one crash. Real systems keep safety always and get liveness only when the network is behaving, using timeouts and randomization."

What it says. Fischer, Lynch and Paterson (1985) proved that in an asynchronous system (no bound on message delay or on relative processing speed), no deterministic consensus algorithm can guarantee it will always terminate if even one process may crash. The root reason: you cannot tell a crashed node from a very slow one. Wait forever for a node and you never decide; give up on it and it may come back and disagree.

Why it does not kill practice. FLP is a worst-case statement. It says an adversarial schedule exists in which the algorithm never finishes. It does not say it fails normally. Practical systems escape by relaxing an assumption:

  • Partial synchrony. Assume the network is eventually well behaved for long enough. Use timeouts to suspect failures.
  • Randomization. Raft randomizes election timeouts (for example 150 to 300 ms) so that, with high probability, one candidate wins before others start.
  • Failure detectors. An imperfect detector that is "eventually right" is enough.

The trade made. Paxos and Raft always keep safety (never two different decisions, even under delay, loss or partition) and give up guaranteed liveness (progress) during bad periods. A cluster with a flapping network may spend a while in repeated elections and make no progress, but it will never corrupt data.

Why it is asked. It shows you know the difference between safety and liveness and why a consensus system may stall rather than lie.

Pitfall. Saying "consensus is impossible". It is impossible to guarantee termination in the pure asynchronous model, and it is routinely solved under realistic assumptions.

What is the difference between synchronous, asynchronous and partially synchronous system models? Intermediate
Say: "I prove safety under the asynchronous model, which assumes nothing about timing, and rely on partial synchrony only for liveness."

What a system model is. Before proving an algorithm correct, theorists state what they assume about timing. The assumptions decide what is solvable.

ModelAssumptionConsequence
SynchronousKnown upper bounds on message delay, processing time and clock drift.Failure detection is perfect: no reply within the bound means dead. Easy algorithms. Real networks rarely give this guarantee.
AsynchronousNo bounds on anything.Very pessimistic. FLP applies: no deterministic consensus with guaranteed termination.
Partially synchronousBounds exist but are unknown, or hold only after some unknown time. Behaviour is usually timely, with stretches of misbehavior.Consensus is solvable. This is the realistic model.

Why partial synchrony matches reality. Most of the time a request takes 2 ms. Occasionally a GC pause, a noisy neighbour, a congested link or a VM live-migration makes it 5 seconds. A purely synchronous model would declare the node dead during that pause; a purely asynchronous model gives up on ever deciding.

How Raft uses this. Safety rules (term numbers, majority votes, log matching) hold regardless of timing. Timeouts only drive liveness: a follower that hears no heartbeat for its election timeout starts an election. If timing is bad, you get extra elections, not wrong answers.

Design rule. Never let correctness depend on timing (for example "the lock is held for 10 seconds, so nobody else can have it"), only liveness. Distributed lock leases without fencing violate this and are a favorite interview probe.

What is a gray failure, and why is it worse than a clean crash? Senior
Say: "A gray failure is a node that is up by the health check but broken for real users. Binary up/down detection misses it, so I use latency-based ejection, deeper health checks and timeouts."

What it is. A gray (or partial, or "limping") failure is a component that is neither fully up nor fully down. It answers health pings but is very slow, drops 5 percent of requests, has a failing disk, a congested NIC, a memory leak, or a bad connection to just one dependency. The health check says "healthy" while real traffic suffers.

Why worse than a crash. A clean crash is easy: the node disappears, a failure detector notices within seconds, the load balancer routes around it and the system heals. A gray failure keeps receiving a full share of traffic. Its slow responses tie up caller threads and connections, callers time out and retry, retries add load to the remaining nodes, and a small degradation becomes a cascading failure.

Example. One of 10 app servers has a disk that now takes 2 seconds per write. The load balancer's /health endpoint (which does not touch the disk) returns 200. Ten percent of users see 2 s latency, clients time out at 1 s, retry, hit other servers, and total load rises.

Mitigations.

  • Health checks that exercise a real path (read and write a canary row), not only "process is alive".
  • Passive outlier ejection: remove a host whose error rate or p99 latency stands out from its peers.
  • Timeouts, circuit breakers and bulkheads to contain slowness.
  • Hedged requests (send a second copy after the p95 delay and use the first reply).
  • Accrual failure detectors (phi accrual) that output a suspicion level rather than a yes/no.
  • Client-side observation: compare what clients see with what the node reports about itself.

Pitfall. Blind retries amplify gray failures; always combine retries with budgets and backoff.

How should timeouts and retries be designed, and what can go wrong? Intermediate
Say: "Timeout on every call, retry only idempotent operations, exponential backoff with jitter, a retry budget, and a propagated deadline."

Why it matters. Timeouts and retries are the first line of defence against partial failure, and also the most common way a small problem becomes an outage. Done badly they multiply load exactly when the system is weakest.

The rules, with the reason for each.

  1. Always set a timeout. With no timeout, a hung dependency holds a thread and a connection forever. After enough such requests your own pool is exhausted and you fall over. Choose it from the dependency's p99 or p99.9 plus margin, not a round guess.
  2. Retry only what is safe. Reads and idempotent writes are fine. For non-idempotent writes, attach an idempotency key first (see the idempotency chapter).
  3. Exponential backoff with jitter. Wait 100 ms, 200, 400, ... each multiplied by a random factor. Without jitter, 10,000 clients that failed at the same moment retry at the same moment, again and again (a retry storm, or thundering herd).
  4. Cap attempts and use a retry budget. Allow retries to add at most, say, 10 percent extra requests over a window. Without a budget, retries multiply across layers: if A retries B 3 times and B retries C 3 times and C retries D 3 times, one user request can become 27 calls to D. D is already struggling, so you bury it.
  5. Propagate a deadline. If the user's request must finish in 2 s and 1.5 s is gone, downstream calls should know only 0.5 s remains and should not start work whose result will be discarded.
  6. Retry only on retryable errors. A 400 Bad Request will never succeed; a 503 or a connection reset might.

Snippet of the idea.

delay = min(cap, base * 2^attempt)
sleep(random(0, delay))      // "full jitter"

Pitfalls. Timeouts shorter than the legitimate p99 cause self-inflicted failures; retries at every layer cause amplification; retried non-idempotent POSTs cause duplicates. A circuit breaker complements retries by stopping calls to a dependency known to be down.

2. CAP and PACELC

State the CAP theorem precisely. Basic
In one line: when the network partitions, a replicated store must choose between consistency (linearizability) and availability. It cannot give both.

History. Eric Brewer conjectured it in 2000; Seth Gilbert and Nancy Lynch proved a formal version in 2002. It is about a replicated data store, meaning the same data on several nodes.

The three properties, with the precise meaning that matters.

  • Consistency (C) means linearizability: every read sees the most recent completed write, as if there were a single copy of the data and operations happened one at a time.
  • Availability (A) means every request sent to a non-failing node gets a non-error response, in finite time. It does not promise the data is the latest.
  • Partition tolerance (P) means the system keeps operating even when the network drops or delays arbitrary messages between nodes.

Why "pick two" is misleading. In a real network, partitions happen (a switch fails, a cable is cut, a GC pause makes a node look gone). You do not get to choose to avoid P. So the honest statement is: if there is a partition, you must choose C or A. If there is no partition, you can have both.

Why it is true (intuition). Suppose two replicas cannot talk. A write arrives at one of them. To stay consistent, the other replica must not answer reads until it hears about the write, so it must refuse or wait (sacrifice A). To stay available, it must answer with what it has, which is stale (sacrifice C). There is no third option because the replicas cannot exchange information.

Pitfall. Describing CAP as a static label on a database. It is a statement about behaviour during a partition, and many systems let you choose per request.

Walk through CAP with a concrete example of two nodes. Basic
Say: "Two replicas, link cut, a write on one, a read on the other. Either the reader errors (CP) or returns stale data (AP)."

Setup. Two replicas: N1 in Mumbai and N2 in Frankfurt. Both hold x = 1. The link between regions breaks, but both nodes are alive and clients can still reach their local node.

t0  client A writes x = 2   -> N1  (N1 cannot replicate to N2)
t1  client B reads  x       -> N2

Option 1: choose consistency (CP). N2 knows it may be missing updates but cannot check. To avoid returning wrong data it refuses or times out the read. Equally, N1 may refuse the write because it cannot reach a majority. Everything that is returned is correct, but some requests fail. Systems like etcd and ZooKeeper work this way: the side without a majority stops serving.

Option 2: choose availability (AP). N2 answers x = 1, which is stale. N1 accepts the write x = 2. Both stay up, but now the replicas hold different values. When the link heals they must reconcile (last-write-wins, vector clocks, CRDT merge, or application logic). Dynamo-style stores do this.

What to emphasize. The user-visible difference is: CP shows an error or a delay; AP shows an old answer. Which is right depends on the operation. A bank balance shown 30 seconds old on a screen is tolerable; two withdrawals both succeeding against the same balance is not.

Pitfall. Forgetting the last line: with no partition, a system can offer both C and A. CAP only bites during the failure.

What are the most common CAP misconceptions? Intermediate
Say: "CAP is not pick-two. P is forced. It only applies during a partition, C means linearizability not ACID, and real systems are tunable."

Interviewers use CAP to see whether you have gone past the slogan. These are the mistakes they are listening for.

  1. "Pick any two of three." You cannot drop P, because networks fail. A "CA system" only makes sense on a single node or on a network you assume never partitions. In a distributed system the real choice is CP or AP.
  2. "A system is either consistent or available, always." The trade-off exists only during a partition. In normal operation you can have both. It can also be made per operation: a bank may reject a transfer during a partition while still allowing balance reads.
  3. CAP's C is not ACID's C. CAP consistency is linearizability (a recency guarantee across replicas). ACID consistency means application invariants (for example "balance never negative") are preserved by a transaction. Different ideas, same letter.
  4. CAP's A is a strict definition. Every non-failing node must respond. A system with 99.99 percent measured uptime is not automatically "A" in CAP's sense. Conversely, a CP system such as a Raft cluster is still highly available in practice as long as a majority can talk to each other; only the minority side refuses.
  5. It ignores latency and normal operation. CAP says nothing about how slow a consistent read is when there is no partition. That is what PACELC adds.
  6. Labels are not absolute. Most databases are configurable per query (consistency levels, read and write concerns), so "Cassandra is AP" is a default tendency, not a law. Cassandra with QUORUM reads and writes behaves much more like a CP system.
Trap: saying "MongoDB is CP, Cassandra is AP" as if it were fixed. Say "by default, and tunable per operation".
When would you choose a CP design and when an AP design? Intermediate
Say: "Ask what costs more for this operation: being wrong or being down. Money and uniqueness lean CP, feeds and carts lean AP. Most products use both."

The decision rule. For each operation ask: "If a user sees an old or conflicting answer, how bad is that, compared with the user getting an error?" If wrong answers are expensive (double-spend, oversell, two leaders), choose CP and accept errors or latency. If errors are expensive and stale data is tolerable (a feed, a cart, a like count), choose AP and accept reconciliation work.

CP (consistency first)AP (availability first)
During a partitionMinority side rejects or blocks requestsBoth sides keep serving and may diverge
Good fitAccount balances, inventory with no overselling, leader election, config, locks, unique usernamesShopping cart, social feed, likes, presence, caches, sensor ingestion
CostErrors or higher latency; needs a quorumNeeds conflict resolution; users may see stale data
Examples (typical defaults)ZooKeeper, etcd, Spanner, HBaseDynamo-style stores, Cassandra and Riak at low consistency levels, DNS

Worked example. An e-commerce site. Payment and inventory decrement: CP (a relational DB or a consensus-backed store), because overselling the last item costs a refund and an angry customer. The product catalog and recommendations: AP (replicated, cached), because showing a price 5 seconds old is harmless. The shopping cart: Amazon's original Dynamo paper chose AP and merged conflicting carts, preferring an extra item in the cart to a refused add-to-cart.

Pitfall. Choosing one global answer. A good answer splits the system by operation and names the failure behaviour in each part.

What is PACELC and why is it a better model than CAP? Intermediate
Say: "If Partition, choose Availability or Consistency; Else, choose Latency or Consistency. The 'else' half is the one that matters every day."

What it is. Daniel Abadi (2012) extended CAP into a sentence: if there is a Partition (P), choose Availability or Consistency (A or C); Else (E), choose Latency or Consistency (L or C).

Why it exists. CAP only talks about the rare partition. But replication has a cost all the time. Take a write to 3 replicas across regions:

  • Wait for all or a majority to confirm (strong consistency): the write takes a cross-region round trip, perhaps 80 to 150 ms.
  • Reply after the local copy is written and replicate in the background (low latency): the write takes 2 ms, but a read from another replica may be stale for a while.

So even when everything is healthy, you trade latency against consistency. That is the "ELC" half, and it is the trade-off engineers face on every request. Partitions might happen once a quarter.

System (typical default)PACELCMeaning
Dynamo, Cassandra, RiakPA/ELStay available in partition; low latency otherwise
Spanner, VoltDB, most majority-replicated storesPC/ECConsistent in both cases; pays latency
MongoDB (default settings, as usually classified)PA/ECMixed; depends on read and write concern
PNUTS (Yahoo)PC/ELConsistent in partition; fast reads otherwise

How to use it in an interview. Describe a system with both halves: "Under partition it refuses writes on the minority side; otherwise it uses synchronous quorum replication, so writes cost one round trip to a majority."

Pitfall. These labels depend on configuration and version. Present them as defaults, not facts.

Is latency part of CAP? How does "slow" relate to "unavailable"? Senior
Say: "Formally no, but a reply after the client timeout is the same as no reply, so slowness is how partitions show up in practice."

The formal answer. In the CAP proof, availability only demands that a response eventually comes back. There is no time limit, so latency is not part of the theorem.

The practical answer. A client has a timeout, say 500 ms. A response arriving at 2 seconds is useless; the client has already given up and shown an error. From the user's point of view, "very slow" and "unavailable" are the same. Likewise, most real "partitions" are not cut cables but a congested link, a paused JVM or an overloaded node: messages are delayed, not lost.

What follows.

  • Failure detection is always a timeout decision: "no answer within T means partitioned". Choose T too small and you declare healthy nodes dead; too large and you wait too long.
  • This is why Abadi added latency to the model (PACELC), and why day-to-day tuning is about consistency versus latency: quorum reads versus reading from the nearest replica, synchronous versus async replication.
  • Because a slow node can look dead, a CP system can briefly stall while it decides whether the leader is gone (an election timeout), which is a visible availability dip.

Pitfall. Claiming CAP availability is the same as SLA uptime. They are different definitions.

Is a single-leader relational database with async replicas CP or AP? Senior
Say: "It depends on what you read and how failover works: strong on the leader, eventually consistent on followers, and async failover can lose acknowledged writes."

Setup. One leader takes all writes and ships a log to followers asynchronously. Reads can go to the leader or followers. The leader may fail and a follower may be promoted.

Reading from the leader. Single copy of the truth, so reads and writes are linearizable. If the leader is cut off from some clients, those clients get errors, so it behaves CP on that side.

Reading from followers. A follower may be 50 ms or 5 minutes behind. A user who writes on the leader and then reads from a replica may not see their own write. This is stale even with no partition at all, so it is not linearizable. In this mode it is closer to AP/EL: fast and available, but only eventually consistent.

Failover. Suppose the leader acknowledged a write to the client, then died before shipping it. A follower is promoted without that write. The write is now lost, and if the old leader comes back it holds data the new leader never saw (a divergence that must be discarded or reconciled). With synchronous replication (at least one follower must confirm) this loss is avoided, at the cost of write latency and of blocking writes if that follower is down.

ModeBehaviour
Leader reads and writesLinearizable. Errors if leader unreachable.
Async follower readsStale. Fast and available.
Async failoverPossible loss of acknowledged writes, possible split brain without fencing.
Sync replica / quorum commitNo loss on failover; higher latency and lower availability.

Pitfall. One-word labels. State the configuration, then the guarantee.

3. Consistency models

Explain the spectrum of consistency models from strongest to weakest. Intermediate
Say: "Linearizable, then sequential, then causal, then session guarantees, then eventual. Each step down gives up some ordering promise in exchange for lower latency and better availability."

What a consistency model is. When data is copied across replicas, different clients may see different things at the same moment. A consistency model is the contract that says which observations are allowed. A stronger model is easier to program against but needs more coordination between replicas, which costs latency and availability.

ModelGuaranteeCost
Strict serializability / linearizabilityEach operation appears to happen instantly at one point between its call and its return, consistent with real timeCoordination on every op; higher latency; unavailable on the minority side of a partition
Sequential consistencyAll nodes see operations in one single order that respects each client's own program order, but the order need not match real timeSlightly cheaper
Causal consistencyIf A could have influenced B, everyone sees A before B; unrelated (concurrent) operations may be seen in different ordersCan stay available during partitions
Session guarantees (read-your-writes, monotonic reads, monotonic writes, writes-follow-reads)Sensible behaviour for one client or sessionCheap with sticky routing or version tokens
Eventual consistencyIf writes stop, all replicas converge. Nothing about what you read in the meantimeCheapest, fastest, highly available

How to remember it. Think of a group chat. Linearizable: everyone sees every message at once, in the true order. Causal: nobody sees a reply before the message it answers, but two independent messages may appear in different orders for different people. Eventual: eventually everyone has the same history, but meanwhile your screen may be behind or out of order.

How to choose. Pick the weakest model that keeps your invariants true. Use linearizable only for things like locks, unique constraints and leader election; use causal or session guarantees for user-facing data; use eventual for counters, feeds and caches.

Pitfall. Calling everything "strong consistency". Interviewers will ask "which one: linearizable, serializable or just read-your-writes?"

What exactly is linearizability, with an example of a violation? Intermediate
Say: "Linearizability is a recency guarantee: once a write completes, every later read by anyone sees it. The system behaves as if there is one copy."

What it is. A guarantee about single operations on a single object (a key, a register). Each operation takes effect atomically at some instant between when it was invoked and when it returned, and these instants respect real time. So if write W returned before read R was even sent, R must see W or something newer.

A violation, step by step.

12:00:00.0  Alice sets photo = new.jpg         -> leader, returns OK at 12:00:00.1
12:00:00.5  Alice phones Bob: "look at my profile"
12:00:03.0  Bob reads photo from replica R2    -> sees old.jpg   (R2 lags)

Alice's write had completed before Bob's read began, yet Bob saw the old value. Real-time order was broken. Eventual consistency allows this; linearizability forbids it.

Why it is hard. To provide it, a read must either go through the leader or a quorum, or confirm with the leader that it is still the leader. This costs round trips, which is the "else" half of PACELC. During a partition, the minority side must refuse requests, which is the CAP "C".

Where it is truly needed.

  • Leader election and distributed locks: two nodes must never both believe they hold the lock.
  • Uniqueness constraints (one account per username, one seat per passenger).
  • Any case where two parties must agree on the single current value.

Pitfall. Believing quorum reads give linearizability for free. They do not always (see the quorum question).

What is the difference between linearizability and serializability? Senior
Say: "Linearizability is about one object and real-time recency. Serializability is about multi-object transactions and equivalence to some serial order. Strict serializability is both."

Two different axes.

  • Linearizability (a "recency" property): single operations on single objects, and the order must match real time.
  • Serializability (an "isolation" property): a set of multi-object transactions behaves as if they ran one at a time in some order. That order does not have to match the clock.

Example of serializable but not linearizable. Transaction T1 writes x = 1 and commits at 10:00. Transaction T2 starts at 10:01 and reads x, getting 0. This is serializable if the database picks the order "T2 then T1", because the result is as if T2 ran first. But in real time T1 finished before T2 began, so T2 should have seen it. Not linearizable.

Example of linearizable but not serializable. A key-value store with atomic single-key operations is linearizable per key, but it gives no multi-key transactions, so two keys can be updated inconsistently.

Real systems. Spanner provides strict serializability (it calls it external consistency), using TrueTime to wait out clock uncertainty. Snapshot isolation is weaker than both: it avoids dirty and non-repeatable reads but allows write skew (two transactions each read overlapping data and write different rows, jointly breaking an invariant such as "at least one doctor on call").

Pitfall. Using the two words interchangeably. This is a classic senior-level probe.

How does sequential consistency differ from linearizability? Senior
Say: "Both need one global order that keeps each client's order. Linearizability also needs that order to match real time; sequential does not."

What they share. There is one total order of all operations. Every process sees this same order. Each process's own operations appear in the order it issued them.

What differs. Linearizability adds the real-time rule: if A finished before B started (by a wall clock), A is before B in the order. Sequential consistency drops that rule, so the system may "slide" one client's operations earlier or later relative to others, as long as nobody sees contradictions.

Example.

client 1: write x = 1   (completes at 10:00:00)
client 2: read  x       (starts at 10:00:05) -> returns 0

Sequentially consistent: acceptable, because the global order can be "read x, then write x = 1" and client 2's own order is not violated. Linearizable: forbidden, because the write finished before the read began.

Why it matters. Sequential consistency is cheaper to implement because it does not need synchronized notions of "now". It is the model many CPU memory models and some caches aim for. The practical gap shows up when users communicate outside the system (the phone-call example), which is when real-time order becomes visible.

Pitfall. Saying "sequential" when you mean "eventual". Sequential still has a single agreed order; eventual does not.

What is causal consistency and why is it attractive? Intermediate
Say: "Causal consistency means effects are never seen before their causes. It is the strongest model that can stay available during a partition."

What it is. If operation A could have influenced operation B (A happened-before B: same client in order, or B read what A wrote, or a chain of those), every node shows A before B. Operations with no such link are concurrent, and different nodes may show them in different orders.

Example. A comment thread. Alice posts "Anyone want lunch?" Bob sees it and replies "Yes, 1 pm." A third user must never see Bob's reply without Alice's post. But if Carol independently posts "Nice weather", it may appear before or after those two for different readers, and that is fine.

Why attractive.

  • It matches human intuition of cause and effect, which eventual consistency does not.
  • Research results show it is the strongest model achievable while remaining available under partitions, so you do not pay the CAP availability penalty.
  • It is cheaper than linearizability: no global coordination, only dependency tracking.

How it is implemented. Each write carries metadata about what it depends on: version vectors, a dependency list, or hybrid logical clocks. A replica delays making a write visible until its dependencies are visible there too. Examples: MongoDB causally consistent sessions, and the COPS and Eiger research systems.

Cost. Metadata overhead and delayed visibility while waiting for dependencies. It cannot enforce uniqueness constraints, because two concurrent "claim username X" writes are unordered.

What is read-your-writes consistency and how do you implement it cheaply? Basic
Say: "After I write, my own later reads must show it, even if others still see the old value. I implement it by sending that user's reads to the leader for a short window, or with a version token."

The problem it fixes. Replicas lag. You edit your profile, the page reloads, the read lands on a replica that has not received the change, and your edit appears to have vanished. Users then edit again or complain. Others seeing old data for a second is fine; you not seeing your own change is not.

Implementation options, cheapest first.

  • Read from the leader for data the user just changed, or for any read within a window (say 10 seconds, longer than typical replica lag) after that user's last write. Simple and often enough.
  • Sticky sessions to one replica so the same node serves your reads and (via the leader) your writes.
  • Version token. The write returns a log position (LSN, version or timestamp). The client sends it with later reads, and the replica waits until it has applied at least that position (or forwards to the leader). Precise and scalable.
  • Write-through cache keyed per user, populated by the write itself.

Example flow.

POST /profile -> leader, commit at LSN 9041, response carries token=9041
GET  /profile  (token=9041) -> replica R2 at LSN 9038: waits or redirects to leader
Trap: with several devices (phone and laptop) a per-connection or per-session approach fails, because the second device does not know the first one wrote. The token or the "recently wrote" rule must be per user, stored server-side or in a shared store.
Name the four session guarantees and what each prevents. Intermediate
Say: "Read your writes, monotonic reads, monotonic writes, writes follow reads. They are the minimum so a single user does not see time run backwards."

What they are. Weak global models like eventual consistency can feel broken to a single person. The session guarantees (from the Bayou system research) are cheap, per-client rules that remove the worst surprises without global coordination.

Relationship to causal consistency. Together, the four guarantees are equivalent to causal consistency in terms of what a single client observes.

Pitfall. Implementing them per connection instead of per user when users have multiple devices or load-balanced backends.

What does "eventual consistency" really promise, and what does it not? Basic
Say: "Only convergence: if writes stop, all replicas end up equal. It says nothing about how long that takes, what you read meanwhile, or who wins a conflict."

What it is. The weakest useful model. Writes are accepted at some replica and propagated in the background. If no new writes arrive, all replicas eventually hold the same value.

What it does not promise.

  • How long. Usually milliseconds to seconds, but formally unbounded.
  • What you read meanwhile. You may see old values, and different replicas may disagree. Reads may even go backwards unless you add session guarantees.
  • Which value wins when two replicas accept concurrent writes to the same key. You must add a conflict rule: last-write-wins (simple but can silently drop a write), version vectors (detect conflicts and let the app merge), or CRDTs (merge automatically).

Example. Two users like the same post at once on two different replicas, each starting at 100 likes. Naive last-write-wins gives 101 instead of 102. A counter CRDT would give 102.

When to use it. Good: like counts, feeds, DNS, caches, shopping carts, metrics. Bad: anything where reading a stale value causes an irreversible wrong action, such as double-spending, overselling the last seat, or granting access that was just revoked.

Why people choose it. Lowest latency (answer from the nearest replica), best availability, easy multi-region writes.

Pitfall. Describing it as "consistent after a while" and stopping. Always mention conflict resolution and the staleness window.

How do quorum reads and writes (R + W > N) work, and do they guarantee linearizability? Senior
Say: "R plus W greater than N makes every read set overlap every write set, so a read touches at least one replica with the latest acknowledged write. But that alone is not linearizability."

The mechanism. Keep N copies of each item. A write is acknowledged once W replicas have it. A read asks R replicas and returns the value with the highest version. If R + W > N, any group of R replicas and any group of W replicas must share at least one member (pigeonhole), so the read always meets a replica that has the newest acknowledged write.

Worked example, N = 3.

W=2, R=2  (2+2 > 3)  balanced; tolerates 1 replica down for both
W=3, R=1             fast reads, writes need all replicas
W=1, R=3             fast writes, reads need all replicas
W=1, R=1  (2 <= 3)    fastest, but reads can miss the latest write

Why it is not automatically linearizable.

  • A write that fails after reaching only some replicas leaves partial state. A later read may or may not see it, and two reads may disagree (one sees it, the next does not).
  • Sloppy quorums and hinted handoff accept writes on stand-in nodes outside the normal replica set during failures, so the overlap guarantee no longer holds until the data is handed back.
  • Last-write-wins with skewed clocks may choose the wrong winner.
  • Read-modify-write races: two clients read the same value and both write, so one update is lost.
  • Without read repair or write-back, a read can return the new value from one replica and a later read the old value from another before the system catches up.

How real systems cope. Dynamo-style stores run read repair and anti-entropy in the background. For real linearizable operations they add consensus: Cassandra lightweight transactions use Paxos for compare-and-set.

Pitfall. Saying "quorum means strong consistency" in an interview. Say "it gives recency under a stable replica set; it is not full linearizability".

What is tunable consistency? Give an example. Intermediate
Say: "The client picks a consistency level per operation, trading latency and availability against freshness."

What it is. Instead of one system-wide guarantee, each read or write names how many replicas must respond. This turns the PACELC trade-off into a per-request dial.

Cassandra example, replication factor 3.

How to choose. Make the choice per use case: checkout and account data strong, product browsing eventual. Document it so the next engineer does not "optimize" a strong read into a weak one.

Pitfall. Mixing levels inconsistently (write at ONE, read at ONE) and then expecting read-your-writes.

4. Consensus: Paxos, Raft, quorums

What is consensus and why do we need it? Basic
In one line: consensus is getting a group of nodes to agree on one value, even when some crash and messages are delayed. It is how you get "exactly one winner" without a single point of failure.

What it is. A set of nodes each propose a value; the protocol makes them all decide the same one. Formally it needs three properties:

  • Agreement: no two nodes decide differently.
  • Validity: the decided value was actually proposed by someone (no inventing values).
  • Termination: every live node eventually decides.

Why we need it. Replication without agreement gives split brain. Imagine three servers and a leader that dies. Two servers each think they should become the new leader. Without a protocol to force a single answer, you get two leaders accepting conflicting writes. Consensus is the machinery that makes "who is the leader now?" have exactly one answer, even if servers or links fail mid-vote.

Where it is used.

  • Electing a single leader.
  • Replicating a log so every replica applies the same commands in the same order (replicated state machine).
  • Atomic commit and configuration or membership changes.
  • Locks, leases and uniqueness guarantees (unique username, one owner per shard).

The catch. Consensus needs a majority of nodes to be alive and connected, and it cannot guarantee progress in a fully asynchronous network (the FLP result). It also costs a round trip to a majority per decision, so you use it for small, critical data (metadata, locks, config), not for bulk data.

Pitfall. Rolling your own. In an interview, say you would use a system built on Raft or Paxos (etcd, ZooKeeper, Consul) rather than implement it.

What is a replicated state machine? Intermediate
Say: "Same start state plus same commands in the same order gives the same end state. So to replicate any service, I only need consensus on the order of a command log."

The idea. A state machine is anything that takes a command and updates its state deterministically: a key-value map, a lock table, a metadata catalog. If several machines start identical and apply the identical sequence of commands, they stay identical.

Why this is powerful. It reduces the hard problem "keep this whole service consistent across nodes" to a simpler one: "agree on one ordered log of commands". That is exactly what a consensus protocol (Raft, Multi-Paxos, Zab) provides.

How it works.

  1. A client sends command set x=5 to the leader.
  2. The leader appends it to the log at index 17 and replicates it to followers.
  3. Once a majority has stored entry 17, it is committed.
  4. Each node applies committed entries, in order, to its local state machine. Every node's map now has x=5.
  5. The leader replies to the client.

Determinism rule. The commands must produce the same result on every node. A command that says "set timestamp = now()" or "pick a random id" would give different results on each replica. The leader must resolve these values first and put the concrete result into the log.

Practical extras. The log grows forever, so nodes take snapshots of state and truncate old log entries. A new or lagging node installs a snapshot, then replays the tail.

Examples. etcd, Consul, ZooKeeper, CockroachDB ranges and TiKV regions are all replicated state machines driven by a consensus log.

What is a quorum, and why does it need to be a majority? Basic
Say: "A quorum is a majority, floor(N/2)+1. Any two majorities share a node, so two conflicting decisions can never both win."

What it is. The minimum number of nodes that must agree for a decision to count. For consensus it is a strict majority.

Why a majority. Take 5 nodes. A majority is 3. Any two groups of 3 out of 5 must overlap in at least one node (3 + 3 = 6 > 5). That overlapping node witnessed both decisions, so it will refuse to allow a second, conflicting one. Two different majorities cannot exist in separate partitions at the same time, which is exactly what prevents split brain.

The split argument. With 4 nodes, a clean 2-2 network split leaves neither side with a majority (needs 3), so the whole cluster stops. With 5 nodes, any split gives one side at least 3, so one side always keeps running. Odd sizes avoid a deadlocked tie.

Why not more. More voters mean more acknowledgements per write and more heartbeat traffic, so writes get slower. Decision rule. 3 nodes survive one failure (fine for most). 5 nodes survive two (allows one planned maintenance plus one unplanned failure). Spread them across failure domains: 3 zones for 3 nodes, or 2-2-1 for 5.

Explain Paxos at a conceptual level. Senior
Say: "Two phases. Prepare gets a majority to promise to ignore older proposals and reveals any value already accepted. Accept then proposes that value, or its own if none. Majority overlap makes it safe."

What it is. Leslie Lamport's protocol for agreeing on a single value (single-decree Paxos). Roles: proposers suggest values, acceptors vote, learners find out the result. In real systems one node plays all three.

The two phases.

  1. Phase 1, prepare and promise. A proposer picks a unique, increasing proposal number n and sends prepare(n) to a majority of acceptors. An acceptor that has not promised something higher replies promise(n): "I will never accept a proposal numbered below n". It also reports the highest-numbered proposal it has already accepted, if any.
  2. Phase 2, accept and accepted. The proposer looks at the replies. If any acceptor reported an accepted value, the proposer must propose the value with the highest proposal number among them. Only if none did may it use its own value. It sends accept(n, value). Acceptors accept unless they have since promised a higher number. When a majority accepts, the value is chosen.

Tiny walkthrough, 3 acceptors. P1 sends prepare(1); A1, A2 promise (nothing accepted yet). P1 sends accept(1, "X"); A1 accepts, then P1 crashes before A2 does. P2 now sends prepare(2) to A2, A3. A3 has nothing; A2 has nothing. P2 could pick its own value "Y", but if it had reached A1, it would learn "X" from A1's report and be forced to re-propose "X". Either way only one value is chosen.

Why it is safe. If a value was chosen, a majority accepted it. Any later phase-1 majority overlaps with that majority, so the new proposer hears about the chosen value and must adopt it. Safety never depends on timing.

Why it can stall. Two proposers can keep pre-empting each other with higher numbers (dueling proposers, a liveness problem, consistent with FLP). Practical systems elect a stable leader to avoid this.

Multi-Paxos. Runs many instances for a log. With a stable leader, phase 1 is done once and skipped for later entries, so each command needs only one round trip to a majority.

Pitfall. Paxos is famously hard to turn into a full system (log gaps, membership changes, snapshots), which is the reason Raft was designed.

Explain how Raft works. Intermediate
Say: "One elected leader per term appends commands to its log, replicates to followers, and commits once a majority has stored the entry. If the leader goes silent, a follower runs an election."

What it is. Raft (Ongaro and Ousterhout, 2014) is a consensus algorithm designed to be understandable. It breaks the problem into three parts: leader election, log replication and safety. Time is divided into numbered terms, and each term has at most one leader. Every node is in one of three roles: follower (passive), candidate (running for leader) or leader.

Normal operation, step by step.

  1. A client sends a command to the leader.
  2. The leader appends it to its own log and sends AppendEntries RPCs to followers.
  3. Once a majority (leader included) has stored the entry, it is committed.
  4. The leader applies it to its state machine, replies to the client, and tells followers the new commit index so they apply it too.

Keeping leadership. The leader sends periodic heartbeats (empty AppendEntries). A follower that hears nothing for a randomized election timeout (the paper suggests about 150 to 300 ms) assumes the leader is gone, becomes a candidate and starts an election in a new term.

How to read this diagram. Every node starts as a follower (left). If it hears no heartbeat before its randomized election timeout, it becomes a candidate (middle) and asks the others for votes in a new term. With votes from a majority it becomes the leader (right, the moving green arrow). If at any point it sees a higher term, for example from a newer leader, it takes the red dashed path back to follower.

Safety summary. Only a candidate whose log is at least as up to date as a majority can win, so a new leader always has every committed entry. Entries are never lost once committed.

Example. 3-node cluster, leader L has log [1,2,3]. A client write becomes entry 4. L sends it to F1 and F2. F1 acks, so a majority (L plus F1) has it: commit. F2 was slow and gets it later. If L crashes, F1 or F2 can only win if its log is at least as current; F2 without entry 4 can still win with F1's vote only if F1 considers F2 up to date, which it will not.

How does Raft leader election work, and how are split votes avoided? Intermediate
Say: "A timed-out follower bumps its term and asks for votes. Each node votes once per term, only for a candidate with an up-to-date log. Random timeouts make split votes rare."

Step by step.

  1. A follower's election timer fires (no heartbeat). It increments its term, becomes a candidate, votes for itself and sends RequestVote to every other node.
  2. Each node votes for at most one candidate per term, first come first served. It also refuses unless the candidate's log is at least as up to date as its own (compare last log term first, then last log index). This protects committed entries.
  3. A candidate that gets votes from a majority becomes leader and immediately sends heartbeats so others stay followers.
  4. If another candidate wins first, this one sees a heartbeat with an equal or higher term and falls back to follower.
  5. If nobody gets a majority (a split vote), timers expire again and a new term starts.

How split votes are avoided. Each node's election timeout is randomized (for example between 150 and 300 ms). Usually one node times out first, wins the vote before others even start, and sends heartbeats that reset everyone's timers. If two time out together and split the votes, the random timeouts differ next round, so a winner emerges within a round or two.

Example. 5 nodes, leader dies. Node C times out at 170 ms, becomes candidate for term 8, requests votes. Nodes A, B, D grant it (each had not voted in term 8, and C's log is current). C has 4 of 5 and becomes leader.

Pre-vote. Many implementations add a pre-vote phase: a node first asks "would you vote for me?" without changing the term. This stops a node that was just partitioned away (and kept timing out, inflating its term) from forcing a healthy leader to step down when it rejoins.

Pitfall. Timeouts that are too short relative to network jitter or GC pauses cause repeated needless elections; too long makes failover slow.

What is a term (epoch) and why is it important? Intermediate
Say: "A term is a logical clock for leadership. Stale terms are rejected, so an old paused leader cannot do harm when it wakes up."

What it is. A monotonically increasing integer. Each election starts a new term. Each term has at most one leader. Every message carries the sender's term.

The rules.

  • A node that sees a higher term than its own updates its term and, if it was leader or candidate, steps down to follower.
  • A node that receives a message with a lower term rejects it and tells the sender its newer term.

Why it matters, with a story. Leader L (term 5) hits a 20-second GC pause. The others stop hearing heartbeats and elect L2 in term 6, which commits new writes. L wakes up, still believing it is leader, and tries to send AppendEntries with term 5. Followers see term 5 < 6 and reject it; L learns the new term and steps down. Without terms, L would overwrite committed data: a classic split-brain.

The same idea in other systems. It appears under many names: epoch numbers (ZooKeeper, Kafka controller and leader epochs), generation IDs, ballot numbers (Paxos) and fencing tokens (for locks). All of them are the same trick: a number that only goes up, which lets the receiver reject anything from a stale leader.

Pitfall. A wall-clock time is not a safe substitute, because clocks can be skewed or jump backward; terms are logical and persisted.

How does Raft replicate the log, and what happens when follower logs differ? Senior
Say: "AppendEntries carries the previous index and term. The follower rejects if it does not match, and the leader backs up until the logs agree, then overwrites the follower's conflicting tail."

The consistency check. Each AppendEntries message includes the index and term of the entry immediately before the new ones (prevLogIndex, prevLogTerm). A follower accepts only if its own log has an entry at that index with that term. This gives the log matching property: if two logs have an entry with the same index and term, then all earlier entries are identical.

Repairing a lagging or divergent follower.

leader   : 1:a  2:a  3:b  4:b  5:c        (index:term)
follower : 1:a  2:a  3:b  4:x  5:x  (extra uncommitted entries from an old leader)

1. Leader tries prev=(index 5)  -> follower rejects (no match)
2. Leader steps nextIndex back to 4, tries prev=(3,b) -> match
3. Follower deletes its conflicting entries after 3
   and appends leader's 4:b, 5:c

Why deleting is safe. The overwritten entries were never committed, so no client was told they succeeded.

Leader completeness. Any elected leader contains all committed entries. Because the voting rule only grants votes to candidates with an up-to-date log, and any majority that voted overlaps with the majority that committed an entry, at least one voter has that entry and blocks any candidate lacking it.

A subtle rule. A leader commits entries from earlier terms only indirectly: it must first commit a new entry from its own term, which then also commits everything before it. Counting replicas for an old-term entry is not enough, since a later leader without it could still be elected and overwrite it (the scenario in Figure 8 of the Raft paper).

Pitfall. Forgetting persistence: term, vote and log must be fsynced before replying, otherwise a restart could vote twice in one term.

How can a Raft cluster serve linearizable reads without writing to the log every time? Senior
Say: "ReadIndex: the leader records its commit index, confirms leadership with a majority heartbeat, waits to apply that index, then answers. Leases are faster but rely on bounded clock drift."

The problem. Reading from any follower can be stale. Reading from the leader alone is also unsafe: a deposed leader (isolated by a partition, unaware that a new term started) may still answer from its old state. Writing every read into the log is correct but slow.

Fix 1, ReadIndex.

  1. The leader notes its current commit index as the "read index".
  2. It sends a heartbeat round and waits for a majority to answer, proving it is still leader (no higher term exists).
  3. It waits until its state machine has applied at least the read index.
  4. It runs the read locally and replies.

Cost: one heartbeat round trip per batch of reads, but no disk write. Many reads can share one confirmation.

Fix 2, leader leases. After a successful majority heartbeat, the leader assumes it remains leader for a lease period (shorter than the election timeout) and answers reads with no extra round trip. It is faster, but correctness depends on clocks running at a bounded drift, so a skewed or paused clock can produce a stale read.

Follower reads. A follower can also serve linearizable reads by asking the leader for the current read index, then waiting to catch up. This offloads work from the leader.

In practice. etcd defaults to linearizable reads (using ReadIndex) and offers serializable reads, which are served from the local member, possibly stale, and faster.

Pitfall. Assuming "I am the leader" is a stable fact. It is only true as of the last time you checked with a majority.

What these have in common. All of them make a group of replicas agree on an order of commands. The differences are: who proposes (one leader or any replica), what failures they tolerate (crash only or arbitrary), and how many message delays a commit needs.

How to answer in an interview. Say that the crash-fault-tolerant ones (Paxos, Raft, Zab, VR) need 2f + 1 nodes to tolerate f failures, and the Byzantine ones need 3f + 1. Leaderless protocols reduce latency across regions at the price of complexity.

Pitfall. Bringing up EPaxos as "the better Paxos" without noting how rarely it is deployed in production compared with Raft.

What are the dangers of changing cluster membership, and how does Raft handle them? Senior
Say: "Switching configurations at once can create two disjoint majorities and two leaders. Raft uses joint consensus or one-server-at-a-time changes, and new members join as learners first."

The danger. Each node learns about a new configuration at a different moment. Suppose you go from 3 nodes {A,B,C} to 5 nodes {A,B,C,D,E}. At one instant, A and B still use the old config (majority = 2 of 3) while C, D and E use the new one (majority = 3 of 5). Then {A,B} can elect a leader under the old rules and {C,D,E} can elect another under the new rules, in the same term. Two leaders, split brain.

How Raft avoids it.

  • Joint consensus. First commit a transitional configuration (old and new combined). During this phase, any decision needs a majority of the old set and a majority of the new set, so the old and new groups cannot decide independently. Once that is committed, switch to the new configuration.
  • Single-server changes. Add or remove only one node at a time. Majorities of N and N+1 nodes always overlap, so no disjoint majorities appear. This is simpler and used by many implementations (the Raft thesis recommends it).

Operational practice.

  1. Add the new node as a non-voting learner. It copies a snapshot and the log until it catches up.
  2. Promote it to a voting member.
  3. Only then remove an old node, one at a time.

This avoids a state where a fresh empty node counts toward quorum and a failure of one old node loses availability.

Pitfalls. Replacing a node by removing and adding together without the safe procedure; permanently losing a majority (needs a disaster-recovery force-new-cluster, which risks data loss); and removing the current leader without a hand-off.

What are the performance limits of consensus-based systems? Senior
Say: "Each write costs a majority round trip plus an fsync, all writes go through one leader, and cross-region quorums cost tens of milliseconds. You scale by sharding into many consensus groups."

Where the time goes. A committed write needs: leader appends and fsyncs to disk, sends to followers, followers fsync and ack, and the leader waits for a majority. So latency is roughly disk sync time plus the round trip to the second-fastest node (in a 3-node group) rather than to the slowest.

  • Disk. Raft and Paxos must make log entries durable before acknowledging. A slow disk (or a noisy one) directly hurts every write. SSDs and batching of fsyncs help.
  • Single leader bottleneck. All writes are serialized through one node, so adding more nodes to a group does not raise write throughput; it lowers it slightly. Scale by sharding into many independent groups, each with its own leader. Spanner, CockroachDB and TiKV do exactly this, with thousands of small groups.
  • Geography. If the replicas are in different regions, a majority round trip can mean 50 to 150 ms. Designs keep the quorum in nearby zones, or place the leader near the writers, or pay the cost knowingly for global strong consistency.
  • Batching and pipelining. Packing many commands into one AppendEntries and sending the next before the previous is acked raises throughput a lot.

Reads. Linearizable reads also need leadership confirmation (ReadIndex); follower or lease reads reduce that cost at some risk.

Decision rule. Put small, critical metadata through consensus. Put bulk data on cheaper replication, and keep only its metadata or pointer in the consensus store.

Pitfall. Using etcd or ZooKeeper as a general database or a high-rate message queue. They are meant for small data and low write rates.

5. ZooKeeper and etcd

What do ZooKeeper and etcd do, and why not just use a database? Basic
In one line: small, strongly consistent, replicated stores for coordination metadata (config, leaders, locks, membership), with watches and auto-expiring entries that a normal database does not offer.

What they are. ZooKeeper (uses the Zab protocol) and etcd (uses Raft) are clusters of 3 or 5 nodes that run consensus and expose a tiny key-value style API. Everything written is linearizable and replicated to a majority before it is acknowledged.

What problem they solve. In a distributed application many nodes need to agree on small facts: "who is the leader right now?", "which servers are alive?", "what is the current config?", "who holds this lock?". Building that correctly on top of a normal database is hard. These tools give you the right primitives:

  • Watches: be notified when a key changes, so no polling.
  • Ephemeral entries tied to a session or lease: if the owner dies, its entry disappears automatically. That is how liveness and leader election work.
  • Ordered, linearizable updates plus compare-and-swap, so you can build locks and uniqueness safely.

Example. Ten workers each try to create /leader with an ephemeral flag. Exactly one succeeds. The others watch the key. If the leader process dies, its session expires, the key vanishes, watchers are notified and one of them takes over.

Why not a general database. The data set is small (etcd has a default storage quota of about 2 GB, recommended up to about 8 GB; a ZooKeeper znode defaults to about 1 MB), held in memory or a small store, and every write costs a consensus round with an fsync, so throughput is modest. They are tuned for correctness and notifications, not for volume.

Pitfall. Using them as a general datastore or a queue.

What are ZooKeeper's core primitives, and how do you build leader election with them? Intermediate
Say: "Each candidate creates an ephemeral sequential znode; the lowest number leads; each candidate watches only its predecessor so a failure wakes only one node."

The data model. Data lives in a tree of znodes (like a small filesystem). A znode holds a few bytes of data and can have children. Types:

  • Persistent: stays until deleted.
  • Ephemeral: deleted automatically when the client's session ends (crash, network loss past the session timeout). Cannot have children.
  • Sequential: ZooKeeper appends a monotonically increasing number to the name, so concurrent creators get distinct ordered names.

Clients can set watches: one-time notifications when a znode changes or is deleted (you must re-register after each trigger).

Leader election recipe.

  1. Each candidate creates /election/n_ as ephemeral and sequential, getting e.g. n_0000000007.
  2. It lists the children of /election. If its own number is the lowest, it is the leader.
  3. Otherwise it sets a watch on the znode with the next lower number (its immediate predecessor) only.
  4. When the leader's session ends, its znode vanishes. Only the candidate watching it wakes up, re-checks the list, and becomes leader if it is now lowest.
/election/n_0000000005  (leader, client A)
/election/n_0000000006  (client B, watches 5)
/election/n_0000000007  (client C, watches 6)

Why watch only the predecessor. If everyone watched the leader, its death would wake all 1000 candidates at once, who would all hit ZooKeeper (the herd effect). Chaining the watches wakes exactly one.

Pitfall. A GC pause longer than the session timeout makes the leader lose its znode while it still thinks it leads. Protect the real resource with a fencing token (see the locks chapter).

What are etcd's key features, and who depends on it? Intermediate
Say: "etcd is a Raft-based, multi-version key-value store with leases, transactions and watches. Kubernetes keeps all of its state in it."

Core features.

  • Flat key-value space with range reads. Hierarchy is just a key prefix (/services/web/1), and you can read a whole prefix in one call.
  • Multi-version (MVCC). Every change bumps a global revision. You can read the value as of an older revision and, importantly, watch from a revision, so a client that disconnected can resume and miss no events (subject to compaction).
  • Leases. A key attached to a lease with a TTL is deleted when the lease expires without keep-alive. Used for liveness, service registration and leader election.
  • Transactions. "If the key's version is v (or it does not exist) then put, else get": compare-and-swap in one atomic step. This is the basis for locks and leader election.
  • Watch streams of changes, with ordering guarantees.

Example, a tiny lock.

txn: if create_revision("/lock/db") == 0
     then put("/lock/db", owner-id, lease=L)
     else get("/lock/db")

Who depends on it. Kubernetes keeps all cluster state (pods, nodes, secrets, configs) in etcd; the API server is the only direct client. If etcd is slow or loses quorum, the cluster cannot change: already-running pods keep running, but scheduling, scaling and updates stop. This is why etcd disks and backups are critical.

Pitfall. Forgetting to compact and defragment, so the database hits its quota and the cluster goes read-only.

What are common operational pitfalls with ZooKeeper or etcd? Senior
Say: "Disk latency, session timeouts versus GC pauses, quorum placement across sites, size limits, and treating a lease as a safe lock without fencing."

These systems fail in characteristic ways. Know the list and the reason for each.

  • Slow disk. Every committed write needs an fsync. If fsync takes hundreds of milliseconds (a shared or busy disk), the leader misses heartbeat deadlines, followers start elections, and the cluster churns leaders. Use fast dedicated SSDs and keep the log on its own device.
  • Too much data or too many watches. Large znodes, huge key counts or tens of thousands of watches slow snapshots, recovery and notifications. Keep values tiny.
  • Session or lease timeout tuning. Too short: a 10-second GC pause in a client expires its session, its ephemeral lock vanishes and another node takes over while the old one still believes it holds it. Too long: after a real crash, failover waits for the full timeout.
  • Two-site deployments. With 2 + 1 nodes across two data centers, losing the site with two nodes loses quorum. Use three sites (even a small witness at the third) or accept that one site's loss stops writes.
  • Used as a database or queue. Heavy write rates and large payloads degrade the whole cluster that other systems depend on.
  • Lease as a safe lock. A lease can expire while the holder is paused, so two clients may act as holder. Resource-side fencing tokens are needed.
  • Storage growth. In etcd, forgetting compaction and defragmentation hits the space quota, after which the cluster rejects writes.

Operational basics. Monitor leader changes, fsync and commit latency, backend size and pending proposals, take regular snapshots, and rehearse restoring from backup.

6. Clocks, time and ordering

Why can't we just use timestamps to order events in a distributed system? Basic
Say: "I use wall clocks for humans and logs, monotonic clocks for measuring durations on one machine, and logical or hybrid clocks for ordering across machines."

The problem. Each machine has its own quartz-crystal clock. These drift (commonly tens of parts per million, which is a second or more per day, tens of seconds per month if uncorrected). A service like NTP nudges clocks back toward true time, but only to within milliseconds or worse, and sometimes with a sudden step, including backward jumps.

A concrete failure.

Node A (clock 5 ms fast):  writes x=1  stamped 10:00:00.008   (really at .003)
Node B (clock correct):    writes x=2  stamped 10:00:00.005   (really at .005, after A)
Last-write-wins keeps x=1.  The newer write silently loses.

Anything that compares timestamps from different nodes is exposed to this: last-write-wins conflict resolution, lock or lease expiry checked on another host, cache TTLs, "is this token expired?" checks, ordering of log lines in an incident.

The right tool for each job.

  • Wall clock for human-facing times and rough audit logs.
  • Monotonic clock for measuring elapsed time on one machine (timeouts, latency).
  • Logical clocks (Lamport, vector) for causal ordering.
  • Hybrid logical clocks when you want both causality and nearness to real time.
  • Bounded-uncertainty clocks (TrueTime) when you can afford hardware and need external consistency.

Pitfall. Believing NTP makes the clocks "the same". It makes them roughly close, and the error is unknown at any moment.

What is NTP, how accurate is it, and what can go wrong? Intermediate
Say: "NTP syncs clocks to within roughly a millisecond on a good LAN and tens of milliseconds over the internet. It can step clocks, and leap seconds and VM pauses have caused real outages."

What it is. Network Time Protocol is how machines synchronize their clocks with a hierarchy of time servers (strata; stratum 0 is a GPS or atomic source). The client exchanges timestamps with a server, measures round-trip delay, assumes the delay is symmetric, and estimates its own offset. It normally adjusts the clock gradually (slewing) and only steps it when the offset is large.

Accuracy. About 1 ms or better with a local server on a quiet LAN, tens of ms (sometimes more) over the public internet. It degrades with congestion and asymmetric routes, because the symmetry assumption fails.

What goes wrong.

  • Clock steps (including backward jumps) when the offset is big, breaking code that assumes time moves forward.
  • VM pause, resume or live migration that suddenly changes the offset.
  • Misconfigured or faulty servers that serve a wrong time to many clients.
  • Leap seconds: an extra second inserted at the end of a UTC day. Real outages: around the 2012 leap second many Linux hosts spun at high CPU, hanging Java and database processes; around the 2016 to 2017 leap second Cloudflare reported a negative time difference crashing part of its DNS code (as publicly reported).

Mitigation. Many cloud providers use leap smearing: spreading the extra second across many hours so there is no jump. Use monotonic clocks for durations, avoid mixing smeared and non-smeared time sources, and alert on clock offset.

Pitfall. Trusting "synchronized by NTP" as a guarantee for correctness of ordering or leases.

How do Lamport logical clocks work, and what do they guarantee? Intermediate
Say: "A counter per process, bumped on every event, and on receive set to max(local, message) + 1. If a happened before b then L(a) is less than L(b), but not the other way around."

The idea. Instead of asking "what time is it?", just count events in a way that respects cause and effect. Each process keeps one integer L.

  1. Before each local event or message send, L = L + 1.
  2. A message carries the sender's L.
  3. On receiving a message with timestamp T, L = max(L, T) + 1.

Example.

P1: a(1)  send(2) ------------------.
P2:        b(1)       c(2)            \--> receive: max(2,2)+1 = 3
                                          d(3)

The receive on P2 gets 3, ensuring it is after the send (2). Events b and c on P2 have small numbers but are not related to P1's a.

The guarantee. If event a happened-before b (same process order, or via a message chain), then L(a) < L(b).

What it does not guarantee. The converse is false. L(x) < L(y) does not mean x caused y; they might be concurrent. So you cannot detect concurrency with a Lamport clock. To get a total order, break ties with process ID, giving (L, pid) pairs. This is useful for things like distributed mutual exclusion or ordering updates deterministically.

When to use. When you need a cheap order consistent with causality, but do not need to detect conflicts. For conflict detection use vector clocks.

How do vector clocks work, and how do they detect concurrency? Senior
Say: "One counter per node. If one vector is less than or equal to another everywhere, one happened before the other; if neither dominates, the events are concurrent and need merging."

The rules. Each process keeps a vector with one counter per process.

  • Local event or write: increment your own entry.
  • Send: attach the vector.
  • Receive: take the element-wise maximum of your vector and the incoming one, then increment your own entry.

Comparing two vectors. V1 happened-before V2 if every entry of V1 is less than or equal to V2 and at least one is strictly smaller. If neither dominates, the events are concurrent.

Worked example, replicas A and B.

A writes cart=[milk]        -> [A:1, B:0]
B (has not seen it) writes cart=[eggs] -> [A:0, B:1]
Compare: A:1 > 0 but B:0 < 1  -> neither dominates -> CONFLICT (concurrent)
Merge (union): cart=[milk, eggs]  -> new version [A:1, B:1] (then incremented by the merger)

Had B first read A's version [A:1, B:0] and then written, it would be [A:1, B:1], which dominates A's, so B's write simply supersedes it. No conflict.

Why it matters. It is how a leaderless store can tell "this update overrides that one" from "these two were made independently". Amazon's original Dynamo paper used vector clocks for shopping-cart versions and returned multiple conflicting versions to the application for merging.

Costs. The vector grows with the number of writers (clients or nodes). Real systems prune old entries, track per-replica version vectors instead of per-client, or use dotted version vectors to keep size bounded and avoid false conflicts. Pruning can create false conflicts or lose causality, a known trade-off.

In words. A Lamport clock is a single number: it tells you an order that is consistent with cause and effect, but two events with L = 5 and L = 9 might be unrelated. What is a hybrid logical clock and why do databases use it? Senior
Say: "An HLC is a pair of the highest physical time seen and a counter. It behaves like a Lamport clock but stays within the clock-skew bound of real time."

The problem it solves. Lamport clocks give correct ordering but the numbers mean nothing to humans and cannot support "show me the data as of 10:00". Wall clocks have the meaning but not the guarantee. An HLC combines them.

What it is. A timestamp (l, c). l is the largest physical time this node has seen so far, from its own clock or from any received message. c is a small logical counter used when l does not advance.

Update rules.

  • Local event or send: l' = max(l, physical_now). If l' equals the old l, increment c; otherwise reset c to 0.
  • Receive (message has l_m, c_m): l' = max(l, l_m, physical_now), then set c to one more than the largest counter among the values that tied l'. If only physical_now was largest, c = 0.

Example. Node A's clock reads 100 and it sends (100, 0). Node B's clock reads 98 (behind). On receive, B computes l' = max(98, 100, 98) = 100 and c = 1, so B's next timestamp is (100, 1), correctly after A's send even though B's own clock is behind. Later, when B's clock passes 100, l follows the physical clock again.

Properties. It keeps Lamport's causality guarantee, and l never drifts further from true time than the clock-synchronization error, so values are readable, bounded and need no special hardware.

Who uses it. CockroachDB and YugabyteDB use HLC-style timestamps; MongoDB uses a similar cluster-time concept for causally consistent sessions.

Limit. Without bounded skew it cannot give external consistency (real-time ordering across nodes). Systems add uncertainty intervals: a read that finds a value within the interval around its timestamp restarts at a later timestamp. This is cheaper than TrueTime but less strict.

What is Google's TrueTime and how does Spanner use it? Senior
Say: "TrueTime returns a time interval guaranteed to contain true time. Spanner waits out the interval before committing, so timestamp order matches real-time order and it achieves external consistency worldwide."

What it is. An API in Google's data centers where TT.now() returns an interval [earliest, latest] guaranteed to contain the true absolute time. The honest uncertainty is exposed instead of being hidden. Google keeps the width small (the Spanner paper reports a few milliseconds typically) using GPS receivers and atomic clocks as time masters in each data center, polled by every server.

How Spanner uses it: commit wait.

  1. A transaction decides its commit timestamp s, at least TT.now().latest at commit time.
  2. Before making the commit visible, it waits until TT.after(s) is true, meaning s is definitely in the past on every clock. That wait is about the width of the uncertainty (a few ms).
  3. Any transaction that starts after this commit is visible will therefore get a larger timestamp.

Result. Timestamp order equals real-time order, which is external consistency (strict serializability) across the globe, with no central timestamp server and with lock-free consistent snapshot reads at a given timestamp.

Cost. Extra commit latency roughly equal to the uncertainty, and the need for expensive time hardware. Systems without such hardware either settle for weaker guarantees (snapshot isolation or serializability without real-time order) or manage uncertainty explicitly. CockroachDB uses a configured maximum clock offset with read-uncertainty restarts; some cloud providers now offer time-sync services with bounded error that make similar designs possible.

Pitfall. If a node's clock violates the assumed bound, correctness breaks; Spanner and CockroachDB both kick out nodes whose clocks drift too far.

What is the happens-before relation, and what does "concurrent" mean? Intermediate
Say: "Happens-before is causal order: same-process order, send before receive, and transitivity. Concurrent means neither could have known about the other, not 'at the same instant'."

What it is. Lamport (1978) defined a partial order on events, written a → b ("a happened before b"):

  1. If a and b are on the same process and a comes first, a → b.
  2. If a is sending a message and b is receiving that message, a → b.
  3. It is transitive: if a → b and b → c, then a → c.

If neither a → b nor b → a, the events are concurrent.

Why "partial". Some pairs are ordered, some are not. Two events on different machines that never exchanged any message (directly or indirectly) are unordered.

Example. Alice posts on node 1 at "10:00:00.2". Bob, on node 2, writes a comment "at 10:00:00.1" by his clock. If Bob never saw Alice's post, the two are concurrent; his earlier timestamp means nothing. If Bob had read Alice's post first and then replied, her post happened-before his reply regardless of timestamps.

Why it matters. It is the formal basis for causal consistency, version vectors, CRDT merge rules and conflict detection. "Concurrent" is exactly the situation that creates a conflict needing resolution.

Pitfall. Confusing concurrent with simultaneous. Two events can be minutes apart in wall-clock time and still be concurrent, if neither information path connects them.

What is total order broadcast and how does it relate to consensus? Senior
Say: "Total order broadcast delivers every message to every node, reliably and in the same order. It is equivalent to consensus, and it is what a replicated state machine is built on."

What it is. Also called atomic broadcast. Two guarantees: reliable delivery (if one correct node delivers a message, all do) and total order (all nodes deliver messages in the same sequence). Plain multicast gives neither: different replicas see messages in different orders and diverge.

Equivalence with consensus. You can build total order broadcast from repeated consensus (each log slot is one consensus instance), and you can build consensus from total order broadcast (everyone broadcasts a proposal, and all decide on the first delivered). So they are equally hard and equally solvable in the same models.

What you get from it.

  • A replicated state machine: apply the ordered log everywhere.
  • Linearizable compare-and-set and uniqueness: the first claim in the log wins.
  • Unique, monotonically increasing sequence numbers (log position).

Real-world forms. The Raft or Zab log; a single Kafka partition behaves like a total-order log for its consumers (but ordering is per partition, not across partitions, and Kafka's own consensus is for its metadata).

Pitfall. Believing a message queue with multiple partitions gives total order across all messages. It does not; only per partition.

How can you generate unique, roughly sortable IDs across nodes without coordination? Intermediate
Say: "Snowflake-style: timestamp bits, worker id bits and a per-millisecond sequence, packed in a 64-bit integer. Unique and time-sortable with no central call, provided worker ids are unique and clocks do not go backward."

The problem. Many services insert rows or create events at once, and you want unique IDs without a single database sequence as a bottleneck. You also want IDs that sort roughly by creation time, because that keeps B-tree indexes insert-friendly (appending at the end instead of random page splits).

Snowflake layout (Twitter's design, commonly 64 bits).

| 1 sign | 41 bits timestamp (ms since custom epoch) | 10 bits worker id | 12 bits sequence |

Each worker can issue 4096 IDs per millisecond (12 bits). 41 bits of milliseconds is roughly 69 years. The three parts mean no two workers can produce the same ID (worker ids differ), and the same worker never repeats in one millisecond (sequence increments).

Risks.

  • Clock moves backward (NTP step): the worker could reissue old timestamp plus sequence combinations. Good implementations refuse to issue IDs until the clock catches up, or use the last timestamp.
  • Worker-id assignment. Two nodes with the same id produce duplicates. Assign ids through ZooKeeper or etcd, from config, or from a lease, and be careful when containers restart.

7. Distributed transactions

Why are transactions across services or shards hard? Basic
In one line: atomicity comes from one engine with one log and one lock manager; once two databases or services are involved, nobody owns "all or nothing", so you must pick 2PC, sagas, or redesign.

What a local transaction gives you. ACID (atomic, consistent, isolated, durable) works because a single database engine has one write-ahead log, one lock manager and one commit point. Either the commit record reaches the log or it does not.

What breaks across boundaries. Debit an account in service A, credit one in service B. Each service commits its own local transaction. No single engine can make the pair atomic.

1. A: debit 100   -> committed
2. (crash or timeout)
3. B: credit 100  -> never happens     => money vanished

Retrying step 3 might double-credit if the first attempt actually succeeded but the reply was lost (partial failure). Doing step 3 first just flips the problem.

Your three options.

  1. Distributed atomic commit (2PC). Keep all-or-nothing, pay with blocking, latency and coupling.
  2. Sagas or compensations. Give up atomicity and isolation; commit each step locally and undo with a compensating step on failure.
  3. Redesign so the data that must change together lives in one shard or service. The best option when possible: pick aggregate boundaries and shard keys around transactions.

Pitfall. Splitting a database into microservices along technical lines and then discovering that every business operation needs a cross-service transaction. That is a design smell about boundaries.

How does two-phase commit (2PC) work? Intermediate
Say: "Phase 1: the coordinator asks everyone to prepare and vote. Phase 2: if all say yes, commit; otherwise abort. A yes vote is a durable promise to be able to commit."

Cast. One coordinator (transaction manager) and several participants (resource managers, each a database or service that supports prepare).

Phase 1, prepare (voting). The coordinator sends PREPARE to every participant. Each participant does the work, writes its changes and a "prepared" record durably to its log, takes and keeps its locks, then votes yes or no. A yes is a promise: "I can commit this even if I crash and restart, I will not change my mind."

Phase 2, commit (decision). If every vote is yes, the coordinator durably logs COMMIT (this write is the real commit point) and tells every participant to commit. If any voted no or timed out, it logs ABORT and tells all to roll back. Participants then apply the decision, release locks and acknowledge.

How to read this diagram. Time runs left to right across the arrows. (1) The coordinator on the left sends PREPARE to both participants (solid blue arrows). (2) Each participant writes a prepared record, keeps its locks and sends back a YES vote (green dashed arrows). (3) Once both YES votes are in, the coordinator logs COMMIT, sends it, and the participants apply it, release locks and acknowledge, as the bottom line says. Between steps 2 and 3 the participants are blocked, which is the weakness of 2PC.

Money transfer example. Coordinator asks Bank A and Bank B to prepare. A checks the balance, reserves 100 and votes yes. B checks the account is open and votes yes. Both yes, so the coordinator logs COMMIT and both apply. If B said no, A would roll back its reservation.

Why it is correct. No participant commits before all have promised, and no one aborts after a commit decision exists. Every participant ends with the same outcome.

Cost. Two round trips, several forced log writes, locks held across both phases. See the next question for the blocking problem.

Why is 2PC called a blocking protocol? What are its weaknesses? Senior
Say: "If the coordinator dies after participants voted yes, they are in doubt: they can neither commit nor abort, and keep their locks until the coordinator returns."

The in-doubt window. After a participant votes yes, it has given up the right to decide alone. Suppose the coordinator crashes right then, before sending the decision. The participant does not know whether the others voted yes (so the answer should be commit) or someone voted no (so the answer is abort). Committing might contradict an abort; aborting might contradict a commit. It must wait, holding row locks on the prepared data. Every other transaction touching those rows queues behind them.

coordinator: PREPARE -> A yes, B yes -> [CRASH before writing decision]
A, B: both prepared, locks held, waiting... other requests pile up

Recovery: the coordinator restarts, reads its log, and re-sends the decision. Until then, the rows stay locked.

Other weaknesses.

  • Latency. Two synchronous round trips plus forced log writes, with locks held throughout. This limits throughput under contention.
  • Availability. Any participant down means the transaction fails. If each is 99.9 percent available and you span 5, you are roughly at 99.5 percent.
  • Coordinator as a single point of failure unless replicated. Spanner makes the coordinator and participants Paxos groups, so a replica takes over and no one blocks.
  • Heterogeneous participants. Queues, third-party APIs and many NoSQL stores do not support a prepare phase, so they cannot join.
  • Heuristic decisions (an operator forces a commit or abort on an in-doubt branch) can break atomicity.

Where it works. Inside one organization's database tier (XA transactions between a few databases), and in distributed SQL engines where participants are replicated groups. It is rarely used across independently owned microservices.

What is three-phase commit and why is it rarely used? Senior
Say: "3PC adds a pre-commit phase and timeouts so participants can decide without the coordinator. It is only non-blocking if the network never partitions, so production systems use 2PC with a consensus-replicated coordinator instead."

What it adds. Phases: can-commit (vote), pre-commit ("everyone voted yes, get ready"), then do-commit. Participants use timeouts to decide alone if the coordinator disappears:

  • If a participant never received pre-commit, it is safe to abort (nobody can have committed yet).
  • If it received pre-commit, everyone voted yes, so it is safe to commit.

This removes the in-doubt blocking of 2PC.

Why it fails in practice. The reasoning assumes a synchronous network with bounded delays, so a timeout reliably means "dead". Real networks partition. If the network splits, one group (saw pre-commit) may time out and commit while the other (did not see it) times out and aborts. Atomicity is broken, which is worse than blocking. It also costs another round trip.

What is used instead. 2PC with a coordinator whose state is replicated by Paxos or Raft, so a crash is recoverable by a replica without blocking, and safety never depends on timing. That is the Spanner approach.

Why interviewers ask. To see if you understand that you cannot get atomic commit, non-blocking and partition tolerance together, a close cousin of FLP and CAP.

What is the saga pattern? Basic
Say: "A saga is a sequence of local transactions, each committed on its own. If one fails, we run compensating transactions for the earlier steps in reverse order."

Origin and idea. Garcia-Molina and Salem (1987) proposed sagas for long-lived transactions that would hold locks too long. Instead of one big atomic transaction, break the work into steps T1, T2, ... Tn. Each Ti commits locally in its service. For each Ti there is a compensation Ci that semantically undoes it. If step Tk fails, run C(k-1), ... C1 in reverse order.

Example: an order flow.

StepActionCompensation
1Create order as PENDINGMark order CANCELLED
2Reserve inventoryRelease inventory
3Charge paymentRefund payment
4Mark order CONFIRMED(final step, none)

If the payment (step 3) is declined, we run: release inventory, cancel order. The customer is never charged.

What you lose. Isolation. Between steps, other transactions can see intermediate states (inventory reserved but the order not yet paid, or an order PENDING that will be cancelled). You get atomicity only "eventually" and in the semantic sense. You handle this with semantic locks (PENDING flags), commutative operations, and re-reading values.

Why choose it. No distributed locks, no blocking coordinator, each service keeps its own database, and it scales to long-running flows (minutes to days).

Pitfall. Treating compensation as rollback. A refund is a new, visible transaction.

Compare saga orchestration and choreography. Intermediate
Say: "Orchestration has a central coordinator that drives the steps; choreography has services react to each other's events. I use choreography for 2 to 4 simple steps and orchestration for anything with branches or compensation logic."

The two styles.

  • Orchestration: a saga orchestrator sends commands ("reserve inventory", then "charge payment") and keeps the state of the flow. On failure it sends the compensating commands.
  • Choreography: no central controller. Order service publishes OrderCreated; inventory reacts and publishes InventoryReserved; payment reacts and publishes PaymentCompleted, and so on. Failure events trigger compensation in the others.

Tooling. Workflow engines such as Temporal, AWS Step Functions or Camunda implement orchestration with durable state, retries and timers, so you do not hand-roll them.

What makes a good compensating action, and what cannot be compensated? Intermediate
Say: "Compensations must be idempotent, retried until they succeed, and safe against out-of-order messages. Non-compensable steps go last."

Requirements.

  • Idempotent. It will be retried (the orchestrator crashes, messages are redelivered). Releasing a reservation twice must be harmless.
  • Must eventually succeed. You cannot abandon a half-undone saga. Retry with backoff, and if it keeps failing, alert a human. A compensation that can fail for business reasons is a design defect.
  • Safe against out-of-order delivery. A "cancel" can arrive before the "reserve" it cancels (slow message, retries). The service should record "cancelled for order 17" and, when the late reserve arrives, ignore it. This is the "empty compensation" or tombstone idea.
  • A semantic undo, not a rollback. A payment refund is a new transaction; the customer sees both the charge and the refund on their statement. Intermediate states were visible to others.

What cannot be compensated. Sending an email or SMS, shipping a parcel, calling an external API that has no cancel, publishing information to an outside party. You cannot unsend them.

How to design around it. Order the steps so that anything that can fail comes first, and the non-compensable step (the pivot) comes after all the risky ones. Use "pending" or "reserved" states first and only finalize at the end. For example, reserve inventory, authorize (not capture) payment, and only then send the confirmation email and ship.

Pitfall. Assuming a compensation is always simply the inverse. Refunding a payment does not undo a fee, a rate-limit hit, or a notification already sent.

What is Try-Confirm-Cancel (TCC)? Intermediate
Say: "TCC reserves resources in a Try step, then finalizes everywhere with Confirm, or releases everywhere with Cancel. It gives better isolation than a plain saga, at the cost of three operations per service."

The contract. Each participant exposes three operations:

  • Try: check and reserve resources without finalizing (hold 100 on the account, reserve 1 seat for 10 minutes). The reservation is visible as a held amount, not as a final change.
  • Confirm: turn the reservation into the real thing. Must be idempotent and must not fail for business reasons (the reservation already checked everything).
  • Cancel: release the reservation. Idempotent, and must tolerate being called with no earlier Try (an "empty rollback") or after a timeout.

Flow. A coordinator calls Try on all participants. If every Try succeeded, it calls Confirm on all; otherwise Cancel on all. Reservations that are not confirmed or cancelled expire by timeout, to avoid leaks.

Example, a trip booking. Try: hold a flight seat, hold a hotel room, authorize the card for 700. Confirm: issue ticket, confirm room, capture payment. If the hotel Try fails: Cancel the seat hold and the authorization.

Compared with a saga. TCC avoids exposing final committed changes that may later be undone, so other transactions see "held" rather than "committed". It resembles 2PC but at the application level and without holding database locks. The price: every service must be written for the three-step contract, and you must handle duplicates, empty cancels and "Cancel arriving before Try".

Where seen. Payment and booking systems, where holds and authorizations are natural.

What is the dual write problem? Intermediate
Say: "Updating a database and publishing a message are two separate systems with no shared transaction, so a crash between them loses or invents events. The fix is the transactional outbox."

The problem. A service often must do two things when something happens: save a change in its database and tell others via a message broker (or update a cache or a search index). There is no atomic operation covering both systems.

OrderCrash between the twoResult
Write DB, then publishAfter DB commit, before publishThe change exists but nobody is told. Lost event.
Publish, then write DBAfter publish, DB write failsOthers act on something that never happened. Phantom event.

Retrying does not fix it, because the process that would retry is the one that died.

Why not 2PC? Most brokers and many stores do not support XA, and it would couple availability of both systems.

The same problem appears with DB plus cache, DB plus search index, and DB plus external API call.

Solution. Make the DB the single source of truth: write the event into the same database, in the same local transaction, then publish from there (transactional outbox, next question), or tail the database's own change log (change data capture).

Pitfall. Wrapping the publish in a try/catch and "compensating" does not help if the process crashes before the catch runs.

How does the transactional outbox pattern work? Intermediate
Say: "Write the business row and an outbox event row in one local transaction; a relay publishes outbox rows to the broker at least once; consumers deduplicate."

Steps.

  1. One local transaction. Insert the order row and a row in an outbox table (event id, aggregate id, type, payload). The database makes both atomic: either both exist or neither. 
    BEGIN;
  INSERT INTO orders (...) VALUES (...);
  INSERT INTO outbox (id, aggregate_id, type, payload) VALUES (...);
COMMIT;
  2. Relay. A separate process reads new outbox rows (by polling, or by change data capture on the transaction log, for example Debezium) and publishes them to the broker, then marks them sent (or deletes them).
  3. Consumers. Delivery is at least once (the relay may crash after publishing but before marking), so consumers must be idempotent or deduplicate by event id. The mirror image is an inbox table: record processed message ids in the same transaction as the consumer's own side effects.

Guarantees. No lost events (the event exists if and only if the change committed). Events may be delivered more than once. Per-aggregate ordering is preserved if the relay publishes in commit order and uses the aggregate id as the partition key.

Polling versus CDC. Polling is simple but adds load and latency and must pick rows carefully to preserve order. CDC reads the database log, has low latency and no extra table scans, but adds infrastructure (Kafka Connect and Debezium).

Pitfall. Letting the outbox table grow forever; delete or archive sent rows. Also, relay instances racing on the same rows can reorder events; use one relay per partition of rows or row locking.

What happens if the saga orchestrator crashes midway? Senior
Say: "The orchestrator persists its state before and after every step, so a new instance resumes. Since it may repeat the last command, every participant command must be idempotent."

The risk. A saga may have reserved inventory and charged the card when the orchestrator process dies. If its progress lived only in memory, nobody knows to continue or to compensate. The customer is charged but no order exists.

What a robust orchestrator does.

  • Durable state. Persist the saga instance (current step, results so far, status) in a database, before and after each step, often via event sourcing (an append-only history of what happened).
  • Resume. A new instance loads unfinished sagas and continues from the last recorded step.
  • Idempotent commands with stable ids. After a crash, the orchestrator does not know if its last command was delivered. It re-sends the same command with the same command id; participants dedupe.
  • Timeouts per step and retries with backoff.
  • Dead-letter and alerting for sagas stuck beyond a threshold, with a manual repair path.
  • Monitoring of "age of oldest running saga" as a key metric.

Durable execution engines (Temporal and similar) make this a platform feature: they record the workflow history and, after a crash, replay the deterministic workflow code against that history to rebuild its state. Your workflow code must be deterministic (no direct clock or random calls); side effects go in activities that can be retried.

Pitfall. Storing saga state and publishing the next command as two separate non-atomic actions. Use the outbox pattern for the orchestrator itself.

When would you choose 2PC over a saga, and a saga over 2PC? Intermediate
Say: "2PC when I need real atomicity and isolation inside one trust domain with short transactions; sagas for cross-team, long-running or third-party flows. Best of all is avoiding the cross-boundary transaction."
Choose 2PC whenChoose a saga when
Same organization and a database technology with XA support, or a distributed SQL engineServices owned by different teams, different datastores, third-party calls
Short transactions, strong isolation required, low contentionLong-running business flows (minutes to days), such as trip bookings
It is acceptable for one participant failure to block or fail the transactionYou need high availability and can accept temporary inconsistency
You cannot tolerate visible intermediate states (e.g., a ledger)Intermediate states are tolerable (PENDING), compensation is possible

In words. 2PC keeps the illusion of one big atomic transaction, at the price of locks held across services and blocking when something fails. A saga accepts that the world is eventually consistent, and handles failures by business-level undo. 2PC is a database-level tool; sagas are an application-level tool.

The often best third option. Avoid the problem by keeping data that must change atomically within one service or shard. Design aggregates (in DDD terms) and shard keys around transactions: for example, shard by account id so a transfer within one account family is local; for transfers across accounts, use a ledger with two entries and a saga or a single-database transfer.

Interview decision rule. Ask: "Do these steps belong to the same owner and database?" If yes, one local transaction. If they must be atomic across owners and are short, consider 2PC or a distributed SQL database. If they cross teams or vendors, or are long, use a saga with an outbox.

8. Idempotency, delivery guarantees, deduplication

Explain at-most-once, at-least-once and exactly-once delivery. Basic
Say: "At-most-once may lose, at-least-once may duplicate, and exactly-once is really at-least-once plus idempotent processing."

Why there are three. When a sender transmits a message and gets no reply, it faces the partial-failure question: did it arrive? It can choose to not retry (risk loss) or to retry (risk duplicates). Delivery semantics are just the name of that choice.

SemanticsSender behaviourFailure outcomeUse for
At-most-onceSend, never retryMay be lost, never duplicatedMetrics, logs, telemetry where a drop is tolerable
At-least-onceRetry until acknowledgedNever lost, may be duplicated (ack lost, so resend)Default for most reliable systems; pair with idempotent consumers
Exactly-onceRetry plus dedupe/atomic commitEffect happens oncePayments, counters, inventory

The honest truth about exactly-once. Over a lossy network, delivery itself cannot be guaranteed to happen exactly once (the Two Generals problem). What you can achieve is effectively-once: at-least-once delivery combined with idempotent or deduplicated processing, so the visible effect occurs once.

Example. A consumer reads "add 10 to balance", applies it, and crashes before committing its offset. On restart it reads the same message again. At-least-once means it is reprocessed; without idempotency the balance is +20. With a processed-ids table or an upsert, the second run does nothing.

Order of consumer actions matters. Commit offset before processing gives at-most-once (crash after commit loses the message). Process then commit gives at-least-once (crash before commit repeats it).

Is exactly-once delivery possible? How do Kafka's "exactly-once" semantics fit in? Senior
Say: "Not as a network property. Kafka offers exactly-once processing inside Kafka (idempotent producer plus transactions); the guarantee stops at the boundary, so external effects still need their own idempotency."

The theory. Between two independent parties over a lossy network, exactly-once delivery is impossible. But exactly-once processing semantics are achievable inside a closed system that controls both ends and can commit "I consumed this" and "I produced that" atomically.

What Kafka provides.

  1. Idempotent producer. The broker deduplicates retries using a producer id and a per-partition sequence number. If a send is retried after a lost ack, the broker recognizes the sequence and does not append a second copy. This removes duplicates and keeps order within a partition.
  2. Transactions. A producer can atomically write records to several partitions and commit the consumer offsets of the input it consumed. A consume-transform-produce pipeline (for example Kafka Streams) is then exactly-once: either the output and the offset advance both happen or neither does. Downstream consumers use isolation level read_committed so they ignore aborted transactions.

Flink gives similar end-to-end semantics through checkpoints and two-phase-commit sinks.

Where it ends. Kafka's guarantee covers data inside Kafka. If your consumer also writes to an external database, sends an email or calls a payment API, that side effect is outside the transaction. A crash after the call but before the offset commit repeats it.

consume msg(offset 42) -> call payment API (charged) -> CRASH before commit
restart: consume offset 42 again -> charged twice unless you pass an idempotency key

Fix: use an idempotency key (the message id or business id) with the external system, or write results into a store that supports upserts by key.

Trap: answering "Kafka gives exactly-once so we are fine" for a flow that writes to an external database or an HTTP API.
What is idempotency and how do you make a payment API idempotent? Basic
Say: "Idempotent means repeating has the same effect as doing once. For a payment POST, the client sends a unique idempotency key and the server stores the key with the result, returning the stored result on retries."

What it is. An operation is idempotent if performing it many times leaves the system in the same state as performing it once. "Set balance to 100" is idempotent; "add 10 to balance" is not. By HTTP definition GET, PUT and DELETE are idempotent; POST is not, unless you make it so.

Why it exists. Because of the timeout ambiguity: the client cannot know whether the first request worked, so it must be able to retry safely.

The pattern for POST /payments.

  1. The client generates a unique idempotency key (a UUID) per logical operation and sends it in a header, for example Idempotency-Key: 7f3a.... Retries reuse the same key; a new order gets a new key.
  2. The server, in one transaction, inserts the key in a table with a unique constraint along with the result. If the key already exists, it returns the stored response and does not charge again.
  3. It stores a hash of the request body with the key. If the same key arrives with a different body, that is a client bug: return an error.
  4. In-flight case: a retry arriving while the first request is still running should wait or get 409 Conflict, not start a second charge.
  5. Keep keys for a retention window (for example 24 hours) then expire.
CREATE TABLE idem (key TEXT PRIMARY KEY, req_hash TEXT, status TEXT, response JSONB, created_at TIMESTAMP);

Flow. First call: key absent, row inserted as STARTED, charge executed, row updated to DONE with response. Retry: key present and DONE, return the same response, status code and body.

This is the approach used by well-known payment APIs such as Stripe's.

Pitfall. Generating the key on the server per request defeats the purpose; it must be created once by the caller and reused on retries.

What race conditions break naive idempotency checks? Senior
Say: "Check-then-act is racy. Claim the key atomically with a unique insert so only one request proceeds, and make the downstream call carry the same key."

Race 1: check then act.

Request 1: SELECT key  -> absent
Request 2: SELECT key  -> absent         (concurrent retry)
Request 1: charge card; INSERT key
Request 2: charge card; INSERT key       -> charged twice

Both saw "absent". The check and the claim are separate steps. Fix: make the claim atomic. INSERT the key first with a unique constraint; only the request whose insert succeeds proceeds, and the other gets a conflict. In Redis use SET key value NX; in DynamoDB a conditional put.

Race 2: key recorded, effect not done (or the reverse). The process claims the key, then crashes before charging. A retry sees the key and wrongly assumes the work is done. Or it charges, then crashes before recording the key; the retry charges again. Two ways to deal with it:

  • If the key and the effect live in the same datastore, write both in one transaction. Then either both exist or neither.
  • Otherwise record a state (STARTED, DONE). On retry of a STARTED request, resume safely, which requires the downstream call to be idempotent too: pass the same key to the payment provider. The provider then dedupes the charge.

Race 3: expiry. If keys expire after 24 hours but a client retries after 25, the duplicate slips through. Choose retention longer than the longest plausible retry.

Pitfall. Treating idempotency as only an API concern. Message consumers, scheduled jobs and saga steps all need the same care.

How do you deduplicate messages in a consumer? Intermediate
Say: "Prefer natural idempotency (upserts, conditional updates). Otherwise record processed message ids in the same transaction as the side effect."

Why it is needed. At-least-once delivery means the consumer will sometimes see the same message twice (after a rebalance, crash before the offset commit, or broker retry). Deduplication makes the second delivery harmless.

TechniqueHowTrade-off

Example of an inbox transaction.

BEGIN;
  INSERT INTO inbox(msg_id) VALUES ('m-81');   -- fails on duplicate
  UPDATE accounts SET balance = balance + 10 WHERE id = 7;
COMMIT;

If the insert violates the unique constraint, skip the work. Because both statements are in one transaction, you never record the id without the effect, or the effect without the id.

Pitfall. Keeping the dedupe record in a different store from the side effect: you recreate the dual-write problem.

How do retries and duplicates interact with message ordering? Senior
Say: "Retries can reorder messages. Keep order per key by routing, limiting in-flight sends, or by versioning and discarding stale updates. Global ordering is rarely needed."

How a retry reorders. The producer sends M1 then M2. M1 fails (timeout), M2 succeeds, then M1 is retried and succeeds. The broker has M2, M1: the consumer applies "balance = 50" after "balance = 80" and ends on the wrong value.

Ways to protect order.

  • One in-flight message per key. In Kafka, with the idempotent producer, up to 5 in-flight requests per connection keep order within a partition because the broker uses sequence numbers to reject gaps and duplicates. Without idempotence, retries with several in-flight batches can reorder.
  • Route by key. All messages for one entity (an account id) go to the same partition or queue consumer, so they are processed in sequence.
  • Version numbers. Attach a monotonically increasing version to each update; the consumer applies only if the version is greater than the current one (UPDATE ... WHERE version < ?), discarding stale or duplicate messages.

Parallel consumers. A pool of consumer threads pulling from one partition destroys order. Parallelize by key (hash into worker queues), not by message.

Decision rule. Global order is expensive and rarely needed. Per-entity order is usually enough and cheap. Ask: "Which two messages must never be swapped?" Usually only those for the same entity.

Pitfall. Retry topics and dead-letter queues break order by design; if order matters, a failed message may need to block the key instead of being parked.

9. Distributed locks and leader election

When do you need a distributed lock, and what are the alternatives? Basic
Say: "A lock gives mutual exclusion across processes. I prefer to avoid it: a unique constraint, optimistic locking, per-key queues or idempotency often remove the need. And I ask whether the lock is for efficiency or for correctness."

What it is. A distributed lock ensures that only one process, across several machines, runs a critical section at a time. Examples: only one worker runs the nightly report, only one instance rebuilds the cache, only one process handles a given customer's account at once.

Why avoid it if you can. A distributed lock adds a dependency, adds latency, and has subtle failure modes (leases that expire while the holder is still working). Alternatives are often simpler and safer:

  • Database unique constraint or conditional update. "Insert a row for job 2026-11-18; if it exists, someone else has it."
  • Optimistic locking. A version column: UPDATE ... SET x = ?, version = version + 1 WHERE id = ? AND version = ?. If 0 rows change, someone else won; retry.
  • Single-partition queue per key. If all work for key K is delivered to one consumer at a time, no lock is needed.
  • Idempotent operations. If running twice is harmless, a rare double-run does not matter.

Two purposes, two requirements.

Efficiency lockCorrectness lock
GoalAvoid duplicate workPrevent data corruption
If two holders occurWasted effort, harmlessCorrupted data, double payment
NeedsA simple lock with TTL (even single Redis)Consensus-backed lock plus fencing tokens

Interview move. Ask "what happens if two processes briefly both think they hold it?" The answer decides which kind you need.

Why are distributed locks tricky? Describe the classic failure. Senior
Say: "A lock must expire if its holder dies, so it has a lease. But the holder can be paused after checking the lease and before acting, so it may act after the lease expired. The lock service alone cannot prevent that; the resource must."

Why a lease at all. If a holder crashes while holding a lock with no expiry, everyone waits forever. So locks carry a TTL: if the holder does not renew, the lock service gives the lock to someone else.

The failure. A client cannot know its lease is still valid at the instant it writes. Between "check lock" and "write", it may be paused: a long GC pause, VM stall, page fault, CPU starvation, or a slow network that delays the request.

Timeline:
1. Client A acquires the lock with a 30 s lease.
2. A hits a long GC pause (or is partitioned) for 40 s.
3. The lease expires; client B acquires the lock and writes to the storage.
4. A wakes up, still believes it holds the lock, and writes stale or conflicting data.
Result: two holders, lock violated, data corrupted.

Why a better lock service does not help. The pause happens inside A, after the lock was checked, and A has no way to notice time passed. Even checking the clock right before the write does not help, since a pause can occur between that check and the write itself. Timing assumptions fail.

The fix is at the resource. The protected resource must reject stale holders: a fencing token (next question).

Pitfall. Writing "if (lock.isValid()) write()" and thinking you are safe. That is a check-then-act race against time.

What is a fencing token and how does it solve this? Senior
Say: "Each lock grant carries a strictly increasing number. The resource remembers the highest it has seen and rejects lower ones, so a stale holder is refused even if it still thinks it holds the lock."

Mechanism. Every time the lock service grants the lock, it returns a number that always increases: 33, then 34, then 35. The client includes that token in every write to the protected resource. The resource keeps the highest token seen so far and rejects any request with a lower token.

In the timeline above. B got token 34 and wrote. When the paused A wakes up and writes with token 33, the storage rejects it.

Requirements.

  • The resource must check the token: a database with a version column or conditional write (UPDATE ... WHERE token < ?), an object store with conditional put or generation numbers, or a file server that supports it. A resource that cannot check tokens cannot be protected this way.
  • The token must come from a linearizable source: a ZooKeeper zxid or sequential node number, an etcd revision, or a Raft term.

Relation to other ideas. Fencing is the same idea as Raft terms and epoch numbers: a number that only goes up, used to reject stale actors.

Pitfall. Passing the token but never validating it at the resource, so fencing exists only on paper.

What is Redlock and what is the debate around it? Senior
Say: "Redlock takes a lock on a majority of independent Redis nodes. Critics note it has no fencing token and depends on timing, so it is fine for efficiency locks but not for correctness locks."

What it is. An algorithm proposed by Salvatore Sanfilippo (author of Redis) for locking with several independent Redis instances, typically 5.

  1. Note the start time. Try to acquire the lock on each instance with the same random value and a TTL, using a short per-instance timeout.
  2. The lock is acquired if a majority (3 of 5) granted it and the elapsed time (plus a clock-drift allowance) is less than the TTL. The remaining validity is TTL minus elapsed.
  3. If it failed, release on all instances.

The debate. In 2016 Martin Kleppmann published a critique; Sanfilippo replied. Kleppmann's main points:

  • It does not produce a fencing token, so it cannot protect against the pause scenario described above.
  • It depends on timing assumptions (bounded clock drift, bounded pauses, bounded network delay) that real systems can violate. For example, a clock jump on a Redis node can make the lock expire early; a restart without persistence can lose it.
  • For efficiency-only locks it is heavier than needed (one Redis node is enough); for correctness locks it is not safe enough (use a consensus system with fencing).

Sanfilippo argued that the timing assumptions are reasonable in practice and that a client can check validity time after acquiring.

Balanced takeaway.

  • Efficiency lock: a single-instance Redis lock is fine: SET key value NX PX ttl, and release with a script that checks the value first.
  • Correctness lock: use ZooKeeper, etcd or the database itself, with fencing tokens on the protected resource.

Pitfall. Presenting Redlock as "the distributed lock". In an interview, name the trade-off and the fencing alternative.

How do you implement a safe lock release and renewal? Intermediate
Say: "Store a unique value, release only if it matches (atomic compare-and-delete), always set a TTL, renew at about a third of the TTL, and stop work if renewal fails."

Release must be conditional. Imagine A takes the lock, its TTL expires while it works, B takes the lock, then A finishes and runs DEL lock. A has deleted B's lock. Fix: store a unique random token on acquire and delete only if the stored value equals yours, atomically.

-- Redis Lua script (runs atomically)
if redis.call("get", KEYS[1]) == ARGV[1] then
  return redis.call("del", KEYS[1])
else
  return 0
end

In etcd use a transaction: "if value equals mine then delete".

Always set a TTL. A crashed holder must not deadlock everyone.

Renewal (watchdog). If work may outlast the TTL, a background thread extends the lease at about a third of the TTL (for a 30 s TTL, every 10 s). If a renewal fails or comes back "not owner", stop the protected work immediately; you may have lost the lock. Libraries such as Redisson implement a watchdog.

Keep the protected work short and idempotent so a double-run after a lost lock is harmless.

Pitfalls. Renewing from a thread that keeps running while the main thread is stuck (the lock stays alive but no work happens); a renewal thread that continues after the process lost connectivity; and any design where correctness relies on the lease not expiring (use fencing).

Can you use the database as a distributed lock? Intermediate
Say: "Yes, and it is often the safest choice when the data already lives in that database. Use row locks, advisory locks, a unique-key lock row, or optimistic versioning."

Why it is attractive. If the lock protects data in the same database, a transaction gives you atomicity between "hold the lock" and "change the data" with no separate lock service and no fencing problem, since the database itself is the arbiter.

Options.

  • Row lock: SELECT ... FOR UPDATE on a row; others block until you commit. Add SKIP LOCKED to let workers pick different rows (a job queue).
  • Advisory locks: PostgreSQL pg_advisory_lock, MySQL GET_LOCK. Named locks not tied to a row.
  • Lock table: INSERT a row with a unique key and an expiry column; delete or let it expire. Acquire by insert-or-take-over-if-expired.
  • Optimistic concurrency: UPDATE ... WHERE id = ? AND version = ?, no lock held at all.

Caveats.

  • It adds load to the primary and ties lock availability to the database.
  • Session-level locks live as long as the connection. With connection pools, a connection returned to the pool may still hold the lock, or a dropped connection may release it unexpectedly. Prefer transaction-level locks (pg_advisory_xact_lock) where possible.
  • Long transactions hold locks and bloat the database; keep the critical section short.
  • Across a replica failover, an uncommitted lock state is lost.

Decision rule. If the protected resource is in the database: use the database. If it is outside (a file, an external API), use a consensus-backed lock with fencing, or redesign.

How can a group of services elect a single leader? Intermediate
Say: "Use a coordination service or lease: candidates race to create an ephemeral key, the winner is leader and the rest watch. Always pair with fencing because an old leader may keep acting briefly."

Why you need a leader. Some work must be done by exactly one instance: running a scheduler, assigning partitions, being the single writer to a resource. You run N instances for availability but only one acts, and another must take over if it dies.

Approaches.

  • Coordination service: candidates try to create an ephemeral node (ZooKeeper) or a key bound to a lease (etcd). The creator is leader; the others watch for its disappearance. Kubernetes controllers use a Lease object that the leader keeps renewing; if renewals stop, another replica takes it.
  • Built into consensus: Raft elects its own leader by votes and terms. Useful if your system is the replicated store itself.
  • Database row: a "leader" row holding an owner id and expiry; the leader renews it with a compare-and-swap update, and others try to take it over after expiry.
  • Classic algorithms: the bully algorithm (the highest id wins) and ring election. Mostly textbook; they assume reliable failure detection and are unsafe under partitions.

The failure mode. Leadership is time-bounded, but an old leader may not yet know it lost: it might be paused or partitioned, still acting for a few seconds. Downstream resources should check a term or fencing token so stale leaders are rejected.

Pitfalls. Using local wall-clock comparison for expiry; election timeouts shorter than GC pauses cause flapping leadership; and doing slow work in the leader's heartbeat thread.

What is a leader lease and what is the risk? Senior
Say: "A leader lease lets the leader serve reads locally without a quorum round trip, during a time window in which no other leader can be elected. It is only safe if clocks and pauses stay within bounds."

What it is. After the followers grant it, the leader holds a lease of, say, 10 seconds. Followers promise not to vote for another leader during that period (they wait out the lease). Therefore, for the lease duration, the current leader knows no one else can be leader, and it can answer linearizable reads from local state with no network round trip.

Benefit. Much faster reads, lower load on followers, no ReadIndex confirmation each time.

The risk. It is a timing-based argument.

  • The leader measures the lease on its own clock, the followers on theirs. If the leader's clock runs slower than the followers' by more than the allowed drift, the leader believes it still has the lease after the followers consider it expired and elect a new leader.
  • If the leader is paused (GC, VM stall) past its lease, it may wake up and serve a stale read before noticing.

Mitigations. Choose the lease shorter than the election timeout by a safety margin, assume a bounded drift rate, renew well before expiry, and use monotonic clocks to time the lease on the leader. These reduce but do not remove the risk. Writes should still go through consensus and carry terms, so a stale leader cannot commit anything.

Trade-off. Leases give performance; ReadIndex gives safety without clock assumptions. Systems like Spanner can use leases confidently because TrueTime bounds the uncertainty.

What goes wrong when many nodes wait for the same lock or leader key? Intermediate
Say: "When the lock is released, every waiter wakes at once and stampedes the lock service. Queue the waiters so each watches only its predecessor, and add jitter to retries."

The herd effect. Suppose 1,000 workers watch one key. The holder releases. All 1,000 get notified at the same instant, all try to acquire, one wins, 999 fail and many re-register watches or retry. The coordination service sees a spike of thousands of requests, it slows, other tenants suffer, and under failure it can cascade.

Fixes.

  • Queue-based lock (ZooKeeper recipe). Each waiter creates an ephemeral sequential node and watches only the node just before its own. A release wakes exactly one waiter. The cost of a release is O(1) instead of O(N).
  • Random jitter and exponential backoff on retries, so waiters do not move in lock step.
  • A single-consumer queue. Instead of many workers competing for a lock, put work on a queue with one consumer per key.
  • Reduce contention at the design level: shard the lock by key so there are many small locks.

Related problem. Many clients with a very short TTL all sending renewals create a steady load of heartbeats. The lock service itself becomes the bottleneck. Use reasonable TTLs, batch keepalives (etcd lets many keys share one lease), and keep the number of locks small.

Pitfall. Polling in a tight loop (while(!tryLock()) {}) turns every waiter into continuous load.

10. Gossip and failure detection

What is a gossip (epidemic) protocol and why is it used? Intermediate
Say: "Each node periodically exchanges state with a few random peers, so information spreads like a rumor in O(log N) rounds with no central coordinator and constant load per node."

What it is. A decentralized way to spread information. Every second or so, each node picks a few random peers and shares what it knows (membership list, a config version, load numbers). The peers merge it and repeat the process with their own random picks.

Why it spreads fast. Like an epidemic, each round roughly doubles the number of informed nodes. One node knows after round 0; about 2 after round 1; 4, 8, 16, and so on. A cluster of N nodes is informed in about O(log N) rounds. With 1,000 nodes and a 1 s period, that is on the order of 10 to 20 seconds, with very high probability.

Why use it.

  • No central coordinator, so no single point of failure.
  • Robust to node failures and message loss: if one message is dropped, other paths deliver the news.
  • Constant, small load per node regardless of cluster size.
  • Scales to thousands of nodes.

Costs. Only eventual consistency, some redundant traffic, and convergence time is probabilistic rather than guaranteed.

Variants. Push (send what I know), pull (ask what you know) and push-pull (both). Push is fast early when few know; pull is fast late when most know; push-pull converges fastest.

Where used. Cluster membership and failure information (Cassandra, Consul's Serf, Akka cluster, Dynamo), spreading configuration or schema versions, aggregating metrics.

Pitfall. Using gossip for data that needs strong consistency. It tells you what the cluster probably looks like, not the one agreed truth.

How does SWIM-style failure detection work? Senior
Say: "SWIM pings one random member per round, asks k others to ping indirectly if there is no ack, marks the target suspect before declaring it dead, and piggybacks membership updates on the pings. Load per node is constant."

The problem with heartbeats. If every node heartbeats every other node, a cluster of N nodes sends O(N squared) messages per period. At 1,000 nodes that is a million messages per round. It does not scale.

What SWIM does. It separates failure detection from dissemination.

  1. Each protocol period, a node picks one random member and sends it a ping.
  2. If no ack arrives, it asks k other random members to ping the target for it (ping-req, an indirect probe). This protects against a problem on just the direct link between the two.
  3. If still nothing, the target is marked suspect, not dead, and this is gossiped.
  4. The suspect can refute the suspicion by announcing it is alive, with an incremented incarnation number that overrides the suspect message.
  5. If no refutation arrives within a suspicion timeout, the node is declared failed and removed.

Dissemination. Membership changes (joined, suspect, alive, failed) are piggybacked on the ping and ack messages that are already being sent, not sent separately.

Why it is good. Load per node is constant (about one probe per period) regardless of cluster size; detection time is bounded and independent of N in expectation; the indirect probe and the suspect state cut false positives from a single flaky link.

Where used. Consul and Serf (with Lifeguard extensions that adapt to a slow local node), and many membership libraries, often with modifications.

Pitfall. A node that is slow itself (its own CPU starved) can wrongly suspect healthy peers; extensions such as Lifeguard make nodes aware of their own health.

How do heartbeats and timeouts detect failure, and what is the trade-off? Basic
Say: "A node sends 'I am alive' every T seconds; silence beyond a timeout means failed. Short timeouts detect fast but flag healthy-but-slow nodes; long timeouts are stable but slow to react."

How it works. The monitored node sends a small heartbeat every T seconds (say 1 s). The monitor remembers when it last heard one. If no heartbeat arrives for the timeout (often a small multiple of T, such as 3 to 10 times), the node is declared failed.

Why it is hard to tune.

Short timeoutLong timeout
Detection of a real crashFastSlow; clients keep hitting a dead node
False positivesMany: GC pauses, network blips, CPU spikes get flaggedFew
Cost of a false positiveNeedless failover, data movement, flappingLow

Example. Timeout = 5 s. A JVM node has a 6 s stop-the-world GC. The monitor removes it, shards are re-replicated, then the node returns and the cluster rebalances again. Churn for no reason.

The theoretical limit. In an asynchronous network, a failure detector can never be both complete (detects every crash) and accurate (never wrongly suspects) with certainty, because a slow node and a dead node look identical.

Practical improvements. Use several missed heartbeats, not one; adapt to observed jitter (phi accrual, next question); use indirect probes from other nodes (SWIM); and separate detection from action (first mark suspect, then act after more evidence).

What is the phi accrual failure detector? Senior
Say: "Instead of yes or no, it outputs a suspicion level phi computed from how late the heartbeat is compared with its usual arrival pattern. You choose a threshold, and it adapts to network jitter."

The idea. A fixed timeout treats a LAN node and a satellite-link node the same. Phi accrual (Hayashibara et al.) learns what "normal" looks like for each monitored node.

How it works.

  1. Keep a sliding window of recent heartbeat inter-arrival times.
  2. Fit a distribution to them (for example a normal distribution with the window's mean and variance).
  3. When a heartbeat is late by t, compute P(t): the probability that a heartbeat would still arrive after waiting this long.
  4. Output phi = -log10(P(t)).

How to read phi.

phiMeaning
1About a 10 percent chance the node is alive and merely late
2About 1 percent
8About one in 10^8

Using it. The application picks a threshold. Cassandra's default phi_convict_threshold is 8 (typically raised in cloud environments with noisy networks). Akka uses the same family of detector.

Why better. On a noisy link, inter-arrival times have high variance, so the same 3 seconds of silence produces a lower phi than on a steady link. It adapts automatically. Also, one monitor can serve several consumers: a low threshold to raise an alert, a higher one to trigger failover.

Pitfall. It still cannot tell a long pause from a crash; it only quantifies how unlikely the silence is.

What properties describe a failure detector? Senior
Say: "Completeness (every crash is eventually suspected) and accuracy (correct nodes are not suspected). Chandra and Toueg showed an eventually accurate detector is enough to solve consensus."

The two formal properties.

  • Completeness: every crashed node is eventually suspected by every correct node. (Strong: by all. Weak: by at least one.)
  • Accuracy: correct nodes are not suspected. Strong accuracy: never. Eventual accuracy: there is a time after which correct nodes are no longer suspected. Real networks can only offer the eventual forms.

Practical metrics.

  • Detection time: how long from the crash to suspicion.
  • False-positive rate: how often healthy nodes are suspected (and how long the mistake lasts).
  • Message load: heartbeats and probes per node per second.

Why it matters in theory. Chandra and Toueg showed that consensus is solvable in an asynchronous system if you add a failure detector that is complete and eventually accurate (class "eventually strong", usually written as diamond-S), assuming a majority of correct nodes. This is the theoretical basis for timeout-based leader election in Paxos and Raft: the timeout is an imperfect failure detector; safety never depends on it, only liveness does.

In an interview. Say: "Our detector may be wrong sometimes, so correctness must not depend on it; it only decides when to try to make progress."

What are anti-entropy, read repair and hinted handoff? Intermediate
Say: "Three ways a Dynamo-style store heals replicas that missed writes: read repair on reads, hinted handoff during outages, and Merkle-tree anti-entropy in the background."

Why needed. In an AP system a write is acknowledged after W replicas confirm. Others may be down or slow and miss it. Replicas drift apart and must be brought back in sync, otherwise stale copies live forever.

MechanismWhenHow
Read repairDuring a readThe coordinator reads from several replicas, compares versions, returns the newest, and writes it back to stale replicas.
Hinted handoffDuring a write while a replica is downAnother node stores a "hint" (the write plus the intended target) and forwards it when the replica returns. This is what makes a quorum "sloppy".
Anti-entropy (Merkle trees)Background, periodicReplicas build hash trees over key ranges, compare root hashes, and descend only into subtrees whose hashes differ, finding exactly which keys to sync, cheaply.

Merkle tree idea. Hash each key range's data; hash pairs of hashes upward until one root. If two replicas have the same root, they are identical, with one comparison. If not, compare children, and repeat down to the differing leaf ranges. Cost is proportional to the number of differences, not the data size.

How they complement each other. Read repair fixes hot data quickly but never touches rarely read data. Hinted handoff covers short outages but hints expire after a limit. Anti-entropy is the safety net that eventually fixes everything, including permanent divergence.

Pitfall. Running repair rarely (or never): deleted data (tombstones) may be garbage collected on some replicas before others learn of the delete, so deleted rows can reappear ("zombie data"). Cassandra advises running repair within the tombstone grace period.

11. CRDTs and conflict resolution

Why do conflicts occur, and what are the strategies to resolve them? Intermediate
Say: "Conflicts occur when replicas accept writes to the same item without coordinating. I first try to avoid them, then pick a resolution rule per data type: LWW, version vectors with merge, or CRDTs."

Why they happen. Whenever two replicas can accept a write to the same item independently, they may disagree. That arises in multi-leader replication, leaderless stores, offline-capable clients that sync later, and any AP system during a partition. With a single leader there are no write conflicts, because the leader serializes everything.

Example. Two people edit the same contact: one changes the phone while offline in a tunnel, another changes the email. Both versions later sync. What is the correct result?

StrategyHow it worksTrade-off
AvoidRoute all writes for a key to one leader or home region (a user's home region)Best option when possible; less write availability
Last-write-wins (LWW)Highest timestamp winsSimple, converges, but silently loses data
Version vectors with siblingsDetect concurrency, keep all concurrent versions, let the app or user mergeNo silent loss, but the app must merge
Application-specific mergeFor example, union of shopping cartsCorrect for that domain, custom code
CRDTsData types whose merge gives the same result in any orderAutomatic and convergent; limited types and cannot enforce invariants

Decision rule. Can I make conflicts impossible with a single writer? Do that. If not, is losing one of two concurrent updates acceptable (last-seen time)? LWW. Otherwise, use a merge that is deterministic and safe for the data (CRDT or app-level merge).

Pitfall. Defaulting to LWW without noticing that it drops one of two updates silently.

What is last-write-wins and what are its dangers? Intermediate
Say: "LWW keeps the write with the highest timestamp and discards the other. It converges and is cheap, but it loses data and trusts clocks."

What it is. Each write carries a timestamp. When two replicas hold different values for the same key, the one with the larger timestamp wins; the other is dropped. All replicas apply the same rule, so they converge. Cassandra uses it per cell by default.

Dangers.

  • Silent data loss. Two concurrent updates (user A changes the phone, user B changes the email) are resolved at the record level: one full update is thrown away, and nobody is told.
  • Clock skew picks the wrong winner. A node whose clock is 5 seconds ahead will beat a causally later write from a correct node. A write made after reading the other can still lose.
  • Ties need a deterministic tiebreaker (for example, node id), or replicas could keep different values.
  • Deletes and resurrection. A delete is just a write; an old write with a higher clock can bring data back.
Replica 1 (clock +5s):  set name="Alice"   ts=100.005
Replica 2 (correct):    set name="Alicia"  ts=100.002  (really happened later)
Merge: ts 100.005 wins -> "Alice"; the later edit is lost

Mitigations.

  • Resolve at field level, so independent fields both survive.
  • Use server-assigned or hybrid logical timestamps rather than raw client clocks.
  • Use LWW only where losing an update is fine: last-seen time, cache entries, idempotent state.
  • In Cassandra practice: avoid concurrent overwrites of the same cell; prefer immutable inserts with unique keys (time-series style).
How do version vectors differ from vector clocks, and how are siblings handled? Senior
Say: "Vector clocks track causality between events or processes; version vectors track the versions of one data item per replica. If neither dominates, you keep both as siblings and merge."

The difference.

  • Vector clocks timestamp events (each process increments its own entry on every event, including messages), so they describe causality between events.
  • Version vectors label versions of a data item: one counter per replica that coordinated writes to that key, incremented only when the replica updates that item. They are used for the same comparison but represent data versions, not all events. In practice the two names are often used loosely.

Comparison. If vector V1 is less than or equal to V2 in every entry, V1 is an ancestor and can be discarded. If neither dominates, the versions are concurrent siblings, and the store keeps both.

Example, the Dynamo shopping cart.

client 1 reads cart [A:1], adds a book    -> writes via node A -> version [A:2]
client 2 reads cart [A:1], adds a pen     -> writes via node B -> version [A:1, B:1]
Neither dominates  -> store returns both siblings on next read
client merges (union: book + pen), writes with vector [A:2, B:1], which dominates both

Merge caveat. A naive union with a remove operation can resurrect deleted items: if one sibling deleted the book and the other kept it, the union brings it back. Use tombstones or an OR-Set-like structure for removes.

Vector size. The vector grows with the number of replicas (or clients) that coordinate writes. Implementations prune old entries, or use dotted version vectors, which keep the metadata small and avoid false siblings.

Pitfall. Leaving sibling resolution to every reader; they should be merged and written back (that is what read repair or the client does).

What is a CRDT and why does it need no coordination? Intermediate
Say: "A CRDT is a data type designed so that replicas can be updated independently and always converge, because its merge is commutative, associative and idempotent."

What it is. A Conflict-free Replicated Data Type is a data structure (counter, set, register, map, text) whose replicas accept updates locally, with no locks and no consensus, and can be merged later. When all replicas have received all updates, they have the same state, whatever the order.

Why it works: the math. States form a join semilattice and the merge (join) function has three properties:

  • Commutative: merge(a, b) = merge(b, a). Order of arrival does not matter.
  • Associative: merge(merge(a, b), c) = merge(a, merge(b, c)). Grouping does not matter.
  • Idempotent: merge(a, a) = a. Receiving the same update twice is harmless.

So duplicates, reordering and different network paths cannot cause divergence. This is the reason CRDTs fit AP systems: they turn "conflict resolution" into a built-in property of the type.

Two families.

State-based (CvRDT)Operation-based (CmRDT)
What is sentThe full state (or a delta of it)The operations (such as "increment")

Tiny example. Two replicas of a "likes" G-Counter: A has {A:3, B:0}, B has {A:0, B:2}. Merge takes the element-wise maximum, {A:3, B:2}, total 5, no matter which merges first.

What are the limitations of CRDTs? Senior
Say: "They cannot enforce global invariants, they carry metadata that needs cleanup, and a merge that converges may not match user intent. Use them where availability beats strict invariants."
  • No global invariants. A CRDT cannot ensure unique usernames, a non-negative balance or "only one winner". Two replicas each approve a withdrawal of 80 from a balance of 100; after the merge the balance is -60, which the type cannot prevent. Invariants need coordination (consensus, or escrow-style reservations).
  • Metadata growth. Tombstones (for removes) and per-replica or per-element tags grow over time. Garbage collection needs to know that all replicas have seen an update (causal stability), which itself needs some coordination or membership knowledge.
  • Convergent is not the same as intended. The result is deterministic, but concurrent edits to text can interleave oddly, or an "add wins" rule may not match what the user expects.
  • Limited and hard to extend. A small catalogue of types; designing a correct custom CRDT is difficult and easy to get subtly wrong.
  • Cost. State-based CRDTs may send large states (deltas help); operation-based ones need reliable causal delivery.

When to choose. Availability, low latency and offline writes matter more than strict invariants (counters, sets, collaborative docs, presence). Otherwise use consensus for the part that has an invariant, and CRDTs for the rest.

How would you handle conflicting updates in a multi-region active-active database? Senior
Say: "Reduce conflicts first with home regions, choose a merge rule per data type, make operations commutative, detect and audit conflicts, and route invariants through one owner or consensus."

Context. Active-active means several regions accept writes at once. A round trip between regions is 50 to 150 ms, so waiting for global agreement on every write is slow. But concurrent writes to the same item will happen, and you need a plan.

  1. Reduce conflicts at the source. Pin each entity (a user, a tenant) to a home region for writes. Other regions read locally or forward writes to the home. Most items are only ever written in one place, so most conflicts cannot occur. Failover moves the home.
  2. Choose a merge rule per data type.
    • Counters and sets: CRDTs.
    • Free-form fields: field-level LWW with hybrid logical timestamps.
    • High-value records (money, inventory): a single owner region or a consensus-backed store.
  3. Detect and log conflicts. Use version vectors or conflict counters so you can audit, alert and repair, instead of silently losing data.
  4. Prefer commutative operations. Record deltas and events ("add 3 to stock", "item added") instead of overwriting final values ("stock = 17"). Deltas merge naturally.
  5. Invariants through one place. For unique usernames, balances and "only one", route the decision to one region or use a globally consistent store (Spanner-like) for those rows only.

Example. A profile service: name and avatar are LWW per field; "followers count" is a PN-Counter; "username" claims go through a single globally consistent table; "owner region" of each profile decides where edits are made.

Pitfall. Using one global rule (everything LWW) for the whole database. Money and uniqueness need stronger tools.

12. Fault models, Byzantine faults and split brain

What fault models do distributed algorithms assume? Intermediate
Say: "Crash-stop, crash-recovery, omission, timing and Byzantine, from mildest to worst. Real consensus systems assume crash-recovery, and stronger models cost more nodes and messages."

What a fault model is. Every algorithm is proven correct against a stated list of ways nodes may misbehave. If reality is worse than the model, the proof does not apply. So the first question for any protocol is "what failures does it assume?"

ModelWhat a faulty node doesExample
Crash-stopWorks correctly until it halts and never returnsIdealized; simplest to reason about
Crash-recoveryMay crash and restart, keeping only what is on durable storageWhat Raft and Paxos assume; hence fsync before replying
OmissionFails to send or receive some messagesDropped packets, full queues
Timing / performanceResponds, but too lateGC pauses, overloaded node (gray failure)
Byzantine (arbitrary)Anything: lies, sends conflicting messages, colludesMalicious nodes, memory corruption, buggy software

Why crash-recovery matters. A node that restarts and forgets its vote could vote twice in the same term, breaking safety. Raft therefore persists term, vote and log before replying.

Cost of stronger models. Crash faults need 2f + 1 nodes to tolerate f failures; Byzantine ones need 3f + 1 and more message rounds.

Pitfall. Assuming "crash-stop" and then forgetting that a restarted node may come back with old state, or that a "dead" node may only be slow.

What is a Byzantine fault and when do you need to tolerate it? Senior
Say: "A Byzantine node can behave arbitrarily, including lying differently to different peers. Tolerating f of them needs 3f + 1 nodes. Inside one trusted data center crash tolerance suffices; Byzantine tolerance is for mutually distrusting parties."

The story. From the Byzantine Generals problem (Lamport, Shostak and Pease, 1982): several generals surround a city and must agree to attack or retreat. Some generals may be traitors who tell one general "attack" and another "retreat", so the loyal generals may end up acting differently.

What it is. A Byzantine node can send conflicting information to different peers, forge data, stay silent selectively or collude with others. Crash faults are polite; Byzantine faults are adversarial.

Why 3f + 1. To tolerate f Byzantine nodes you need at least 3f + 1 nodes and a quorum of 2f + 1. Intuition: when you wait for answers from n - f nodes (because f may be silent), up to f of those answers may be lies, and you still need the honest answers to outnumber the lies. For f = 1 that is 4 nodes, quorum 3.

Protocols. PBFT (Castro and Liskov) is the classic practical one; modern blockchain consensus protocols (Tendermint and others) descend from it.

When you need it.

  • Participants who do not trust each other: public or consortium blockchains.
  • Safety-critical hardware where bit flips and software bugs may cause arbitrary behaviour (aerospace).

When you do not. Inside one company's data center the nodes run your code and are trusted, so crash fault tolerance with 2f + 1 nodes is the norm. Cheaper defenses cover most "arbitrary" problems: checksums, authentication, signatures and TLS.

Cost. More nodes, more message rounds, signature checks, lower throughput.

Why the difference. With crash faults, a node that answers is telling the truth, so a majority (f + 1 out of 2f + 1) always includes at least one correct node that has the latest value. With Byzantine faults, some of the answers can be lies, so the quorum must be big enough that two quorums overlap in at least one honest node: two quorums of 2f + 1 out of 3f + 1 overlap in at least f + 1 nodes, at most f of which are faulty.

Other costs.

  • BFT protocols need more message rounds and, in the usual form, a quadratic number of messages per decision.
  • Signature creation and verification add CPU cost, so throughput is lower.

Rule of thumb. Pay for BFT only when you must. Note also that the f faulty nodes must be independent: if the same bug or the same attacker takes out all replicas, neither model helps (use diversity in code and operations).

What is split brain and how do you prevent it? Intermediate
Say: "Split brain is two parts of a cluster both acting as leader, so writes diverge. Prevent it with majority quorum, fencing of the old leader, and consensus-based election."

What it is. A network partition or a falsely detected failure leaves two groups each believing the other is dead and each acting as the active primary. Both accept writes and the data diverges. Merging afterwards is painful or impossible without data loss.

Examples. A database with automatic failover where the old primary is merely unreachable (it is still alive and taking writes from clients who can reach it) while a replica was promoted. An old Elasticsearch cluster with two master-eligible nodes, one in each half of a partition.

Prevention.

  • Majority quorum. Only the side with a majority may operate; the minority steps down or goes read-only. This needs an odd number of voters or a tie-breaker (a witness or arbiter node, possibly in a third location).
  • Fencing. Ensure the old primary cannot write after it was replaced: fencing tokens checked at the storage, revoking its access (cloud API detaching its disk, revoking credentials), or STONITH ("shoot the other node in the head": power it off or cut it off through a management interface).
  • Leases that expire, with clocks assumed bounded; the leader stops serving when its lease lapses.
  • Consensus-based election rather than ad hoc scripts. A leader can only be chosen with a majority vote, so two simultaneous leaders in the same term are impossible.

Elasticsearch note. Before version 7 you had to set minimum_master_nodes to a majority to avoid it; version 7 and later manage the voting configuration automatically.

Pitfall. A "failover" script that promotes a replica after a few missed pings, with no check that the old primary is really down or fenced.

Describe a real incident caused by a partition and automated failover. Senior
Say: "GitHub in October 2018: a brief network loss made an automated failover tool promote MySQL primaries on the other coast. Both coasts took writes, and reconciling took about a day."

What happened (from GitHub's public post-mortem, from memory).

  1. A brief loss of connectivity, on the order of tens of seconds, between GitHub's US East Coast network hub and its primary East Coast data center.
  2. The automated topology and failover tool (Orchestrator) saw the primaries as unreachable and, using its Raft-based view of the topology, promoted MySQL primaries in the US West Coast data center.
  3. Connectivity came back, but now both coasts had accepted writes that the other lacked: the data had diverged.
  4. Because of cross-country latency, simply failing back made the application slow and broke assumptions, and doing so would have lost writes made on the West Coast. Engineers chose to preserve data integrity, which meant many hours (roughly a day) of degraded service while the data was reconciled.

Lessons.

  • Automated failover over high-latency links can be worse than the original brief blip.
  • Do not promote on a short partition; require sustained failure and extra evidence.
  • Keep topology management consensus-backed and aware of data-center locality.
  • Have a plan and tooling for reconciling diverged data, and prefer integrity over speed of recovery.
  • Cross-region replication with async writes means a failover can lose or fork recent writes.

Caveat. Details above are from memory of the public write-up; verify exact figures before quoting them in an interview.

What is a zombie or stale leader and how do you neutralize it? Senior
Say: "A zombie leader is one that was replaced but does not know it. Terms and fencing tokens make everyone else reject it, and it should step down if it cannot reach a quorum."

What it is. A node that was leader, then got paused (GC, VM stall) or partitioned, while the cluster elected someone else. When it resumes, it still believes it is leader and may keep issuing commands, answering reads from stale state, or running the singleton job.

Layers of defence.

  1. Terms or epochs on every message. Followers reject any message with a lower term than they have seen, and the zombie learns the new term and steps down on its first reply.
  2. Fencing tokens at downstream resources. A storage system that remembers the highest token rejects writes from the old one, even if it never talks to the cluster.
  3. Leases checked right before acting, and short enough that the window is small. A lease check is only a mitigation (a pause can happen after the check).
  4. Self step-down. The leader stops serving if it cannot reach a quorum of followers within an election timeout (Raft's check-quorum option does this), so an isolated leader goes quiet rather than answering reads as if it were still in charge.
  5. Reads via ReadIndex or quorum instead of local state.

Example. Leader L at term 7 pauses 20 s. Followers elect L2 at term 8. L resumes, sends AppendEntries(term 7); followers answer "term 8". L steps down. If L had also written to an external store, the store sees token 7, which is below the token 8 it already stored, and rejects it.

Pitfall. Protecting only the consensus log and forgetting side effects outside it (emails, external APIs, files). Those need their own fencing or idempotency.

Is a two-node cluster highly available? Intermediate
Say: "Not with strong consistency. A majority of two is two, so losing either node loses quorum, and the survivors cannot tell a dead peer from a broken link. Add a witness as a third voter."

Why not. With 2 nodes, the majority is 2. If either node dies, the remaining one cannot form a quorum and must stop accepting writes (or risk split brain). Worse, if both nodes are alive but the link between them breaks, each side sees silence and cannot tell whether the peer died or the link failed. If both continue, you get split brain; if both stop, you are down. A two-node cluster is actually less available than a single node (twice the chance that something breaks).

Options.

  • Add a third voter (witness or arbiter) that stores no data, just votes. A 2-plus-witness design is standard: any one of the three can fail and two remain. Put the witness in a third failure domain (zone, site).
  • Choose availability over consistency: both sides continue to serve and reconcile later (needs a conflict strategy, not suitable for a primary-key uniqueness or money).
  • External arbiter: a shared cloud lock, a quorum disk or a cloud load-balancer health decision that picks the winner.
  • Manual failover: a human decides which node is primary. Safe but slow.

Example. MongoDB replica sets use primary, secondary and arbiter; SQL Server and Windows failover clusters use a file-share or cloud witness; PostgreSQL HA tools use etcd or Consul as the third party.

13. Situational and real-life scenarios

A payment service times out calling the bank API. The customer clicks pay again. How do you avoid charging twice? Intermediate
Say: "Treat the timeout as unknown, not failed. Use an idempotency key end to end, query the bank before retrying, and reconcile periodically."

The situation. You called the bank, nothing came back in time. The charge may have happened (response lost), may be in progress, or may never have arrived. The customer, seeing a spinner, clicks again. That is the partial-failure ambiguity in its purest form.

Design, step by step.

  1. Treat the attempt as PENDING, not failed. Store a payment record in state PENDING before calling the bank.
  2. Idempotency key per payment attempt, generated once (by the client or when the order is created) and forwarded to the bank if it supports one. The bank then ignores a repeated key.
  3. The retry reuses the key. Your server returns the stored result if the first attempt completed, or joins/returns the in-flight attempt, rather than starting a new charge.
  4. If the bank has no idempotency support: query the bank by your reference id ("did a charge for ref R-8841 exist?") before ever retrying. Never retry blind.
  5. Reconciliation job. Periodically compare your PENDING and COMPLETED records with the bank's settlement report. Resolve mismatches (refund duplicates, complete stuck ones).
  6. UI. Disable the button after click, show "processing", and poll the payment status instead of submitting again.
POST /payments  Idempotency-Key: ord-8841-attempt-1
-> server: INSERT key (unique); state=PENDING; call bank with same key
-> timeout: leave PENDING; background job queries bank by ref
-> customer clicks again: same key -> returns "PENDING" or final result

What an interviewer probes. "What if the bank also times out on the status query?" Keep the record PENDING, retry the query with backoff, and let reconciliation settle it. Do not tell the customer "failed" until you know.

You find two instances of a singleton job running at once, both writing. What do you investigate? Senior
Say: "I look at how exclusivity is enforced and how it can be violated: lease shorter than a pause, partition from the lock store, clock reliance. Then I add fencing and idempotency rather than just lengthening the TTL."

Investigation questions.

  • How is exclusivity enforced? A TTL lock in Redis? A DB row? A framework scheduler lock (for example a Quartz or ShedLock-style lock)? Which store, which TTL?
  • Was the TTL shorter than a possible pause or a slow step? A GC pause, a slow database call or a stuck network request can outlast the TTL, letting the lock expire while the first instance is still working. Check logs for lock acquisition and expiry times against the job's run time.
  • Was an instance partitioned from the lock store? If it only checks the lock at the start, or its renewal fails silently, it keeps running without a valid lock.
  • Clock issues. If expiry is judged using wall clocks of different hosts, skew can end the lock early on one side.
  • Was the lock itself duplicated? A failover of a single, non-replicated Redis loses its keys, so the new instance sees no lock.

Fix, in order of importance.

  1. Make the job idempotent so a double run is harmless.
  2. Fencing tokens on the target writes, so a stale instance is rejected by the data store.
  3. Abort on renewal failure: the job must stop immediately if it cannot renew, rather than finishing.
  4. Use a consensus-backed lock (etcd, ZooKeeper) or a DB row with conditional update instead of a single Redis node, when correctness (not just efficiency) matters.
  5. Tune the TTL above the realistic pause and renew at about a third of it.

Pitfall. "Just set a longer TTL" reduces frequency but not the possibility; it also slows recovery after a real crash.

Users report that after editing their profile they sometimes see the old data. How do you diagnose and fix it? Intermediate
Say: "Almost certainly replication lag or a stale cache. I confirm with metrics, then give users read-your-writes rather than global strong consistency."

Diagnosis.

  1. Where do reads go? Writes hit the primary, but reads may be load-balanced across async replicas, or served from a cache that is not yet updated or invalidated.
  2. Check replica lag metrics (seconds behind primary) during the reports.
  3. Reproduce: write, then immediately read, and log which replica or cache answered. "Sometimes" suggests it depends on which replica the load balancer picked.
  4. Check cache TTLs and invalidation order (delete cache before the DB commit lets a concurrent reader re-fill with old data).

Fixes, ranked by cost.

  • Read your own writes from the primary for a short window (say 10 s) after the user's write. Cheap and effective.
  • Version or LSN token. The write returns a token; reads carry it, and a replica serves the read only once it has caught up, else the read goes to the primary.
  • Sticky routing of the user to one replica (helps monotonic reads, not always read-your-writes).
  • Update or invalidate the cache on write (and invalidate after commit).
  • Last resort: send that read path to the primary.

Why this choice. Explain you picked read-your-writes (a session guarantee) rather than global strong consistency, to keep read scalability: other users seeing the old photo for a second is acceptable; the author seeing their own edit vanish is not.

Your 5-node etcd or ZooKeeper cluster is split 3 and 2 by a network issue. What happens to each side and to dependent services? Intermediate
Say: "The 3-node side keeps working; the 2-node side rejects writes and linearizable reads. Services stuck on the minority side lose their leases and leadership moves to the majority. Nothing diverges."

The two sides.

SideQuorum?Behaviour
3 nodesYes (3 of 5)Keeps or elects a leader; serves reads and writes normally.
2 nodesNoCannot commit. Rejects writes and linearizable reads; clients connected here get errors or timeouts. If the old leader was here, it steps down.

Effect on dependent services.

  • Services connected to the minority side cannot renew leases or sessions, so their locks and leadership expire. Those roles are picked up by nodes that can reach the majority. Make sure the old holders stop working (fencing).
  • Clients should be configured with endpoints for all members and fail over to one that responds; otherwise they hang on the minority side.
  • Applications should treat "coordination unavailable" as "stop acting as leader", not "carry on".

On healing. The minority nodes see the higher term, catch up from the leader's log (or a snapshot), and rejoin. No divergent data exists, because the minority could never commit. That is the entire point of majority quorum.

Follow-ups. "What if it split 2-2-1 across three sites?" Any two sites together form a majority, so losing one site is survivable. "Would serializable (local) reads on the minority still work?" Yes, but may be stale.

Data written to a Cassandra table keeps getting overwritten by older values. What could be going on? Senior
Say: "Last-write-wins with skewed clocks: one writer's clock is ahead, so its older writes carry bigger timestamps and beat newer writes from correct clocks."

How Cassandra decides. Every cell carries a write timestamp (supplied by the client driver or the coordinator, in microseconds). On conflict, the higher timestamp wins; nothing looks at real order of arrival.

The bug pattern.

App server X (clock +5 s): UPDATE ... at ts = 10:00:05  (really 10:00:00)
App server Y (correct):    UPDATE ... at ts = 10:00:02  (really 10:00:02, later)
Cassandra keeps X's value; Y's newer update looks "lost"

Typical triggers: NTP not running or broken, a VM clock jump after live migration or resume from pause, containers sharing a mis-set host clock.

Investigation.

  1. Check clock offsets on every writer and on Cassandra nodes (chrony or ntp status).
  2. Query WRITETIME(column) for the affected cells and compare to the real time the write happened.
  3. Identify which writer's timestamps are in the future.

Fixes.

  • Fix NTP and monitor offset with alerts.
  • Use server-side timestamps (the coordinator's time) instead of client-supplied, or at least from a small, well-synced set.
  • Use lightweight transactions (compare-and-set via Paxos) for contested rows.
  • Redesign to avoid overwriting the same cell concurrently: append events or use unique clustering keys (immutable inserts) and a version column.

Pitfall. A future-dated write can be hard to override: to fix it you may have to write with an even bigger timestamp or delete it explicitly.

An order flow spans inventory, payment and shipping services. Payment succeeds but shipping fails. What should happen? Intermediate
Say: "Run the saga's compensation: refund payment, release inventory, mark the order failed and tell the customer. First retry shipping if the failure is transient."

First, classify the failure. If shipping was temporarily down (timeout, 503), retry with backoff for a bounded time before compensating; the order is still valid. If it is a permanent failure (undeliverable address, no carrier), compensate.

Compensation, in reverse order.

  1. Refund the payment. A new refund transaction, idempotent (keyed by order id), retried until it succeeds. The customer will see both the charge and the refund.
  2. Release the inventory reservation.
  3. Mark the order FAILED or CANCELLED and notify the customer.

Making it reliable.

  • Each step's command is idempotent with a stable id, because retries will happen.
  • Saga state is persisted durably (orchestrator or event log), so a crash mid-compensation resumes.
  • Events are published via a transactional outbox, so no step silently disappears.
  • Alert if a compensation keeps failing; a human repairs it.

Design tip. Put the least reversible step last. Authorizing payment and reserving stock are reversible; physically shipping is not. Some designs authorize first and only capture when shipping is confirmed, which makes the "refund" a simple release of an authorization.

What interviewers probe. "What if the refund fails?" Retry forever with backoff, then escalate. "What about isolation?" Other flows may see the reserved stock as unavailable meanwhile; that is the accepted cost of a saga.

A leader node had a 20 second GC pause and the cluster elected a new leader. What are the risks when the old one wakes up? Senior
Say: "It may act on stale beliefs: write, or answer reads as leader. Terms make followers reject it, fencing tokens protect storage, and reads should use ReadIndex or quorum rather than a local lease."

What the old leader believes. From its own perspective no time passed. It still thinks it is leader for its term, and it may immediately send AppendEntries, accept client writes, serve reads from local state, or run the singleton work.

Risks and protections.

RiskProtection
It sends writes to followersFollowers have a higher term and reject the stale term; the old leader learns the new term and steps down.

Long-term fixes.

  • Tune the JVM: smaller heaps, a low-pause collector (G1 with a pause goal, ZGC, Shenandoah), avoid huge allocation spikes.
  • Set election and session timeouts above the realistic worst pause so you do not elect needlessly, balanced against failover speed.
  • Alert on long pauses and log them, so the next incident does not look like a network problem. GC logs and pause metrics are key.

Your consumer reads from Kafka and writes to a database; after a crash you see duplicate rows. Why, and how do you fix it? Intermediate
Say: "The consumer wrote to the DB, crashed before committing the offset, and on restart read the same messages again. Make the write idempotent or tie the offset to the same DB transaction."

Why it happens. The consumer loop is: poll, write to DB, commit offset. If it crashes between the DB write and the offset commit, Kafka resumes from the last committed offset, redelivering messages whose effects are already in the database. That is normal at-least-once behaviour. A rebalance mid-processing causes the same thing.

poll offsets 100..109 -> insert 10 rows -> CRASH (offset still 100)
restart -> poll 100..109 -> insert 10 rows again => 10 duplicates

Fixes.

  1. Idempotent write. Upsert on a business key, or use the message's identity (topic, partition, offset) as a unique key: INSERT ... ON CONFLICT DO NOTHING. A redelivery then changes nothing.
  2. Store the offset in the same DB transaction as the data and, on startup, seek to the stored offset instead of using Kafka's committed offset. Both succeed or neither does.
  3. Inbox table: record processed message ids in the same transaction and skip any already seen.

The tempting wrong fix. Committing the offset before processing flips the problem: a crash after the commit but before the DB write loses the message (at-most-once). Prefer duplicates handled safely over losses.

Extras. Keep processing time shorter than max.poll.interval.ms to avoid needless rebalances, and commit offsets after a batch is stored. If you write to Kafka and a DB, Kafka transactions do not cover the DB, so use the techniques above.
