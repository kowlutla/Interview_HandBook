Mental model: the 8 ideas everything hangs on

One line: microservices trade the simplicity of one process for independent deployment and scaling. You pay with the network: every call can be slow, fail, or arrive twice, and every piece of data has exactly one owner.
  1. Boundaries come from the business, not from technology. A service owns one business capability. If two services must always change and deploy together, the boundary is wrong.
  2. The network is not a function call. Calls can be slow, lost, duplicated or answered after you gave up. Every call needs a timeout and a failure plan.
  3. Each service owns its data. Nobody reads another service's tables. You ask through an API or an event.
  4. No distributed ACID, so think in sagas. A business operation across services is a chain of local transactions plus compensating actions. Data is eventually consistent.
  5. At-least-once is the real world. Retries and brokers produce duplicates, so consumers and write APIs must be idempotent (safe to repeat).
  6. Contain failure. Timeouts, circuit breakers, bulkheads and load shedding stop one slow service from taking everything down.
  7. You cannot debug what you cannot see. Correlation ids, structured logs, metrics and traces are not optional.
  8. Contracts are promises. Once a client depends on your API you may add things, but not remove or change meaning.

1. Monolith and service boundaries

What is the difference between a monolith and microservices, and what does each cost? Basic

A monolith is one deployable unit: one process, usually one database, and modules call each other as plain method calls. Microservices split the system into many small services, each owning one business capability and its own data, talking over the network. Microservices solve an organisation and scaling problem, and in return they create a distributed-systems problem.

The monolith is simpler to build, test, debug and deploy, and one transaction can cover everything. Its cost is that everything ships together, one bad module can crash the whole thing, and a big team trips over itself. Microservices give independent deployment, independent scaling and clear team ownership. The price is network failures, eventual consistency, many pipelines, and harder debugging. Every method call that becomes a network call can now be slow, fail, or arrive twice.

The same call, before and after

Take "place an order". In a monolith, OrderService calls paymentService.charge(...) and inventoryService.reserve(...) as ordinary method calls inside one process, inside one database transaction. It either all commits or all rolls back, and a call takes microseconds. In microservices the same two calls become HTTP or gRPC requests to other processes. Each can now time out, fail halfway, or be answered after you gave up, and there is no single transaction any more. That one change, "a method call became a network call", is the root of almost every cost on this page.

Decision rule: the benefit is mostly organisational (teams ship without waiting for each other) and partly about scaling hot spots. If you do not have that problem yet, you are paying for something you do not use. Interviewers often probe with "what would make you split the first service out?". A good answer names a concrete pain: one module needs 10 times the capacity, or two teams keep blocking each other's releases.

Remember: microservices buy team independence and pay for it with distributed-systems pain.

When should you NOT use microservices? Senior

I would not use them for a small team (roughly under 10 to 15 engineers), a new product whose domain is still changing, or an organisation with no automated deployment, monitoring and on-call. In a young product we do not yet know the real boundaries, so we would draw them wrong and pay the full cost for none of the benefit.

Splitting also does not fix slow code or a slow database. My rule: start with a well-structured modular monolith, measure, and extract a service only for a clear reason: a very different scaling profile, a team that needs its own release cycle, or a security or compliance isolation need. Several well-known companies have merged services back for exactly this reason.

Watch out: splitting by technical layer (a "UI service", a "database service") instead of by business capability, or starting with 30 services for a team of 5.

The hidden prerequisites

Microservices need a platform that a monolith does not: automated CI/CD per service, centralised logs, metrics and tracing, a way to run many environments, on-call that understands distributed failures, and API versioning discipline. Without them each new service adds toil. A rough sanity check is to ask: "can we deploy any single service to production on a Tuesday afternoon, with no human steps, and see its health within minutes?" If not, more services will make life worse, not better.

Worked example

A team of six builds a booking product. They split into Users, Bookings, Payments, Notifications and Search services in month one. Over the next months, nearly every feature touches three services, a release needs four pull requests merged in order, local development needs eight containers, and a single bug takes a day to trace across logs. They have all the costs and none of the benefit, because six people can happily share one codebase. The better path: one deployable with modules users, bookings, payments, and so on, strict interfaces between them. Extract Notifications first later, because it is naturally asynchronous and loosely coupled.

Legitimate reasons to split early are narrow: a component with a very different runtime (a GPU image-processing job), a hard compliance boundary (card data in its own scope), or a team in another company or time zone that must release independently. Say that you would look for evidence (deployment conflicts, scaling cost, incident blast radius) before splitting, not follow fashion.

Remember: split when you feel the pain of the monolith, not before.

What is a modular monolith and why is it often the best starting point? Intermediate

It is one deployable application whose code is split into strict modules. Each module has a public interface and hides its internals, including its own tables, and other modules may call only that interface. You get clear business boundaries with simple operations, and if a module must later become a service, extraction is mostly putting a network call behind the interface that already exists.

Boundaries are enforced with package visibility, build rules, or architecture tests (ArchUnit in Java), plus a separate schema per module so nobody joins across them. While the product is young, a transaction can still span modules and refactoring a boundary is cheap. It is the cheapest way to learn where the true boundaries are before paying the microservice tax.

What "strict" looks like in code

Suppose the app has modules orders and billing. Only a small public package of each is visible to others:

orders/
  api/        OrderFacade.java, OrderDto.java     // public: other modules may use
  internal/   OrderRepository.java, Order.java    // package-private: hidden
billing/
  api/        BillingFacade.java
  internal/   ...

orders may call BillingFacade.charge(orderId, amount) but may not import billing.internal.* or query billing tables. A build rule or an ArchUnit test fails the build when someone breaks this. Each module gets its own schema (orders.*, billing.*), and cross-module data is read through the facade, never by a SQL join. In the Java world, Spring Modulith and Java modules support exactly this style.

Why it pays off, and its limits

If billing later becomes a service, BillingFacade becomes an HTTP client with the same method signature. Callers barely change. The limits are real, though: one deployment means one release cycle, one runtime to scale, and a bad memory leak in one module still hurts all. Discipline is also only enforced if you automate the check, otherwise it quietly erodes into a "big ball of mud". Use it by default, and move to services only when independent deployment or scaling becomes a proven need.

Remember: same deployment, strict boundaries, separate data: microservices-ready without the network.

What is a bounded context, and how does it help decide service boundaries and size? Intermediate

In Domain-Driven Design (DDD), a bounded context is a part of the business where every word has one clear meaning and one model. It is the best first guess for a service boundary because it already has its own language, rules and usually its own team. A service may sit inside one context, but it should not span two.

"Customer" means a lead with a contact in Sales, a legal entity with a tax id in Billing, and just an address in Shipping. One shared Customer class for all three becomes a tangled model nobody dares touch. So each context keeps its own model and data and translates at the edges. To find contexts I talk to domain experts, run an event storming session (business events on a wall, grouped), and watch where the same word changes meaning.

For size, forget lines of code. A good service is one a small team can own and understand fully. Too big: many unrelated reasons to change, several teams editing it. Too small: one feature needs edits in three services, or a service just wraps one table with CRUD.

A tiny example of one word, three models

An e-commerce company has three contexts. Each keeps only what it needs:

Context"Customer" holdsCares about
Salesname, email, lead score, ownerconversion
Billinglegal name, tax id, billing address, payment termsinvoicing correctly
Shippingrecipient name, delivery address, phonedelivering the parcel

They are linked by a shared id (customerId), not by a shared class. When Sales converts a lead, it publishes CustomerRegistered{customerId, name, email}. Billing and Shipping each build their own record from it. If the same Customer table served all three, every team would need to coordinate each column change.

Context mapping and anti-corruption layer

Contexts still need to talk. The relationship matters: if you depend on another team's model and cannot change it (for example a legacy system), put an anti-corruption layer between: a small adapter that translates their model into yours, so their awkward names and rules never leak into your code. Typical relationships are customer/supplier (you ask them for what you need), conformist (you accept their model as is), and shared kernel (a small agreed shared part, kept tiny because it couples teams).

Red flags in a service boundary

  • One business feature always needs changes in three services: boundaries are too fine, or cut the wrong way.
  • A service is a thin CRUD wrapper over one table with no rules: it is an entity, not a capability.
  • A "common" or "core" service every other service calls for everything: a hidden monolith.

Remember: things that change together live together; one service per business capability, not per table.

How do you migrate a monolith to microservices safely? Senior

I use the strangler fig pattern. I put a router (gateway or proxy) in front of the monolith, pick one capability at a time, build it as a new service, and move its traffic over. The monolith shrinks until it can be retired, and every step is reversible because the router can send traffic back.

The hard part is data. First I make the module boundary clean inside the monolith. Then the new service gets its own database, data is copied across (change data capture or dual writes with reconciliation while both run), and finally the source of truth switches. I start with something loosely coupled and low risk, such as notifications, not the core. I also invest early in CI/CD, logging, tracing and monitoring, otherwise the first services hurt. A big-bang rewrite usually runs late and loses features.

The route-by-route mechanics

Imagine a monolith with /orders, /catalog, /notifications. You want to extract notifications first.

  1. Put the router in front. A gateway or reverse proxy sends 100 percent of traffic to the monolith. Nothing changes for users, but now you have a switch.
  2. Carve the seam inside the monolith. Make notifications a module with one interface, and remove direct table access from other modules.
  3. Build the new service with the same behaviour. Run it in "shadow" mode: the router copies traffic to it and compares answers without returning them.
  4. Shift traffic gradually: 1 percent, 10 percent, 50 percent, 100 percent, watching error rates. Rollback is one config change.
  5. Move the data: the service gets its own database, filled by a one-off copy plus change data capture. Then flip the source of truth, and finally delete the old code and tables.

Pitfalls

The monolith still calls the extracted code, so you need either an anti-corruption layer or events for the calls that go the other way. Teams often forget to remove the old code, leaving two copies that drift apart. Data is the riskiest step, because dual writes cause inconsistency: pick a single writer at any moment. Choose the first candidate for low coupling and low business risk, so the team learns the platform skills on something forgiving. A common interviewer follow-up is "how do you handle a transaction that used to span the module you extracted?". The answer is that it becomes a saga, which should be designed before the split, not after.

Remember: strangle, do not rewrite: one capability at a time behind a router, data moves last.

What is a distributed monolith and how do you recognise one? Senior

It is many services that are so tightly coupled they behave like one application that is harder to run: all the cost of the network, none of the independence. The tell-tale signs are that services must be deployed together in a fixed order, one change touches many repositories, and they share a database or a big common library full of business objects.

Other symptoms: a long chain of synchronous calls so one failure breaks everything, and nothing can be tested without a full staging environment. The fix is about boundaries and data. Redraw services around business capabilities, give each its own data, replace chatty synchronous calls with events or a local copy of the data it needs, make API changes backward compatible so deploys are independent, and use consumer-driven contract tests. Sometimes the honest fix is to merge services back together.

A concrete picture

Five services Orders, Customers, Pricing, Stock and Shipping, all reading the same customers table, all depending on a shared common-domain.jar that holds the Order and Customer classes. Changing one field in that jar forces a rebuild and redeploy of all five, in the right order, in the same release window. Orders calls Customers, which calls Pricing, which calls Stock, in a chain: if Stock is slow, the user's page times out. You have five pipelines, five sets of logs, and one deployable's worth of freedom. That is a distributed monolith.

A quick diagnostic checklist

  • Can you release one service today without telling any other team? If not, coupled.
  • Does a single feature routinely need pull requests in several repos? Coupled.
  • Do two services read or write the same tables? Coupled through data.
  • Does a call graph depth of four or more synchronous hops sit on the user's path? Coupled through runtime.
  • Is there a shared library of domain objects (not just utilities)? Coupled through code.

How to untangle

Work on the biggest coupling first, which is usually the shared database. Give each service its own data, and for what it used to read from others, either call an API for it or keep a small local copy updated by events. Replace the shared domain jar with each service owning its own small model, and publish API schemas (OpenAPI, protobuf) as the contract. Add consumer-driven contract tests so a provider knows who it would break. And be honest: if two services always change together, merge them, and call it a single service.

Remember: if services cannot be deployed alone, you have a monolith with network latency.

2. Communication, gateway and discovery

Synchronous versus asynchronous communication between services: how do you choose? Intermediate

I use synchronous calls (REST or gRPC) when the caller needs the answer right now to continue, such as looking up a user's price. I use asynchronous messaging or events when the work can happen later, when several services care about one fact, or when I want a service to survive another one being down. Sync is simpler to reason about, async is more resilient and decoupled.

The key difference is temporal coupling. With sync, if Payment is down, Order fails too, and the availability of a chain is the product of each link (five services at 99.9 percent each give about 99.5 percent). With async, Order writes to a broker and moves on. The price is eventual consistency, harder debugging, duplicates and ordering issues. In practice I mix them: sync for queries the user waits on, events for state changes that others react to.

Synchronous request and response, concretely

With sync, Order calls POST /payments and waits. The user's browser is also waiting, so the total time is the sum of the call chain, and the error is the first failure anywhere in it. Use it for questions ("what is the price of SKU 42?") and for commands where the user needs the outcome on the screen ("is my card accepted?").

Asynchronous, concretely

With async, Order writes OrderPlaced{orderId:42, total:99} to a broker (Kafka, RabbitMQ, SQS) and returns "received" to the user. Payment, Inventory, Email and Analytics each consume it at their own pace. Adding a fifth consumer needs no change in Order, which is the decoupling benefit. If Inventory is down for ten minutes, messages queue up and are processed later.

Two kinds of messages

  • Command ("ChargeCard"): addressed to one service, which is expected to act. The sender cares about the outcome.
  • Event ("OrderPlaced"): a fact about the past, broadcast to whoever is interested. The publisher does not know who listens.

Events give the loosest coupling. Commands over a queue are async but still coupled to a specific receiver.

The honest costs of async

You lose the immediate answer, so the UI must handle "pending". Debugging means following a message across queues, which needs correlation ids. You must handle duplicates and ordering. And a queue can hide a problem: a growing backlog is a silent outage, so alert on consumer lag. A frequent mistake is "async over HTTP", where Order calls Payment's endpoint and does not wait. That has the coupling of sync but none of the reliability of a broker, because if Payment is down the message is simply lost.

Remember: sync when the user waits for the answer, async when others only need to know it happened.

At-most-once, at-least-once and exactly-once: what do they mean and what do you really get? Senior

At-most-once means a message is delivered zero or one times, so it can be lost. At-least-once means it is never lost but can be delivered more than once. True exactly-once delivery over an unreliable network is not possible in general, so I build "effectively once": at-least-once delivery plus an idempotent consumer.

The reason is simple: if I send and get no acknowledgement, I cannot tell whether the message or the ack was lost. To be safe I resend, and that creates duplicates. Brokers with "exactly-once" features (Kafka transactions, for example) give it only inside their own boundary, such as read-process-write between Kafka topics. Once I touch a database or an HTTP call, I need my own dedupe. The usual technique is an inbox table: store the message id with a unique constraint in the same transaction as the business change, and skip the message if the insert fails.

BEGIN;
INSERT INTO processed_messages(message_id) VALUES (:id);  -- unique, fails on duplicate
UPDATE account SET balance = balance - :amt WHERE id = :acc;
COMMIT;

Walking through a duplicate

  1. Broker delivers Withdraw 50, id=m-17 to the consumer.
  2. Consumer updates the database successfully.
  3. Consumer crashes before sending the ack.
  4. Broker never got the ack, so after the timeout it redelivers m-17.
  5. The consumer processes it again. Without a dedupe check, 50 is withdrawn twice.

That is the whole reason for the inbox table in the snippet above: the unique constraint on message_id makes step 5 fail harmlessly, and the consumer simply acks. Because the insert and the balance update are in one transaction, either both happen or neither, so a crash cannot leave the id recorded without the change.

What about Kafka "exactly-once"?

Kafka offers an idempotent producer (no duplicates from producer retries within a partition) and transactions (consume, process and produce atomically across topics, with isolation.level=read_committed for readers). That holds only while all state lives in Kafka. Writing to an external database or calling an HTTP API is outside the guarantee. So say "exactly-once processing within Kafka, effectively-once everywhere else via idempotent consumers".

Remember: at-least-once plus idempotent consumer equals effectively once.

What is a dead letter queue and how do you handle poison messages? Intermediate

A dead letter queue (DLQ) is a side queue where a message goes after it failed processing a set number of times. A poison message is one that can never succeed, such as bad JSON, and without a DLQ it would be retried forever and block everything behind it. I retry a few times with backoff, move it to the DLQ with the error and original headers, alert on DLQ size, and fix and replay it later.

Distinguish the failures. Transient ones (database briefly down) deserve retries. Permanent ones (invalid payload, business rule violated) should go straight to the DLQ. Replaying needs the consumer to be idempotent, since the same message may already have partly succeeded. In Kafka there is no built-in DLQ, so you publish to a separate topic yourself, and Spring Kafka's DeadLetterPublishingRecoverer does this.

The flow of a failing message

  1. Consumer reads message M from orders.
  2. Processing throws. It is classified: transient (timeout, deadlock) or permanent (cannot deserialise, a rule violation).
  3. Transient: retry with backoff, for example after 1 s, 5 s, 30 s. Often done through retry topics (orders.retry.1m) so the main queue keeps flowing and is not blocked by one slow message.
  4. After the maximum attempts, or immediately for permanent errors, publish M to orders.dlq with headers: original topic, partition, offset, exception text and stack, attempt count.
  5. An alert fires when the DLQ is non-empty. An engineer inspects, fixes the bug or data, and replays the messages to the main topic.

Why not just retry forever?

In an ordered queue (a Kafka partition) one bad message blocks every message behind it, because the consumer cannot advance past it. This is head-of-line blocking, and it can silently stall a whole partition. A DLQ trades strict order for progress. If order truly matters per key, you may need to park all later messages for the same key too.

Operational points

  • A DLQ nobody watches is just a slow way to lose data: alert, own it, set a retention period longer than your response time.
  • Keep the original payload byte for byte, so replay is faithful.
  • Replays can reorder events relative to newer ones, so consumers should tolerate stale versions (compare version numbers).
  • SQS and RabbitMQ have native DLQ support with a max-receive count. Kafka does not, hence the separate topic.

Remember: retry the transient, park the poison, alert on the parking lot, replay safely.

What does an API gateway do, and what should it NOT do? Basic

An API gateway is the single front door for clients. It handles cross-cutting concerns once: routing, authentication, TLS, rate limiting, request logging, and sometimes response caching or protocol translation. It should not contain business logic, because then it becomes a shared bottleneck that every team has to change.

The benefits are that clients know one address, and services do not each re-implement auth and throttling. The risks are a single point of failure (so run it highly available and keep it thin), extra latency, and the "god gateway" where every team queues to edit routing rules. Typical choices are Spring Cloud Gateway, Kong, NGINX, Envoy-based gateways, or the cloud-managed ones. The gateway checks the token, but each service must still do its own authorisation, since internal calls can bypass the gateway.

What happens to one request

A mobile app calls GET /api/orders/42 with a bearer token. The gateway (1) terminates TLS, (2) validates the JWT signature and expiry, (3) checks the per-client rate limit, (4) maps /api/orders/** to the Order service address, (5) adds a correlation id header and forwards, and (6) logs the request and latency. Order service then receives a request that has already been authenticated and carries user identity in a header or the forwarded token. Order must still check that user X may see order 42.

Gateway versus load balancer versus BFF versus mesh

PieceJob
Load balancerSpread traffic across instances of one service, mostly layer 4 or 7 forwarding
API gatewayEdge policy for external clients: auth, throttling, routing, API keys, versions
BFFShape data for one client type, with some aggregation
Service meshService-to-service (east-west) traffic policy inside the cluster

The gateway is north-south (outside to inside), the mesh is east-west (inside to inside). They overlap a little but they are not the same thing.

Failure modes

Gateway outage means everything is down, so deploy several replicas across zones, and keep config changes safe with staged rollout. Never put orchestration of many services or domain rules there: when one team wants to change an aggregate rule they must change shared infrastructure, and it becomes the new monolith. Also watch for gateway timeouts that are longer than the clients', which leaves wasted work running.

Remember: gateway = policy and routing, not business logic. Services still authorise.

What is the Backend for Frontend (BFF) pattern, and what do you do when a mobile screen needs eight REST calls? Intermediate

A BFF is a thin backend built for one kind of client (web, mobile, partner). It calls the internal services, combines and trims the data, and returns exactly what that client's screen needs in one call. I use it when different clients need very different shapes of data, or when a screen would otherwise need many round trips.

Eight calls from a phone are slow because each round trip costs latency on a weak network and every call carries headers and auth. The BFF does the fan-out inside the data centre over a fast network, in parallel where possible, then sends one response. The alternatives are GraphQL (the client asks for what it needs) or a coarser API. The trade-off is one more component per client, owned ideally by the client team. Keep business rules out of it, or the duplication between BFFs becomes a problem.

The eight calls example, worked

A mobile "home" screen needs: user profile, cart, three recommendation carousels, promotions, notifications count, and loyalty points. Eight REST calls. On a 4G phone with 80 ms round trip each, sequential calls cost roughly 640 ms of network alone, plus TLS and header overhead, plus a battery cost from waking the radio. With a BFF, the phone makes one call, GET /mobile/home. The BFF fires all eight calls in parallel inside the data centre (a few milliseconds each), applies a time budget so a slow recommendation does not block the page (it returns the page without that carousel), trims fields the phone does not show, and returns one compact JSON.

// BFF sketch: parallel calls with a per-call timeout and graceful degradation
var profile = async(userSvc.get(id));
var cart    = async(cartSvc.get(id));
var recs    = async(recSvc.get(id)).timeout(200ms).orElse(emptyList);
return HomeDto.of(await(profile), await(cart), await(recs));

Why one BFF per client

Web wants large payloads and pagination, mobile wants small payloads and few round trips, a partner API wants stability and versioning. A single "general" backend ends up with flags and special cases for each. A BFF per client keeps each simple and lets the client team change it without a cross-team meeting.

BFF versus GraphQL

GraphQL lets the client ask for exactly the fields it needs from one endpoint, which solves over-fetching and many round trips in one stroke, at the cost of query-complexity limits, caching difficulty and N+1 resolver problems. A GraphQL server is often itself the BFF. Choose a plain BFF when you have two or three well-known clients; choose GraphQL when many clients need many shapes.

Remember: one gateway for shared policy, one BFF per client type for shaping data.

How does service discovery work, and what are client-side and server-side discovery? Intermediate

Service instances come and go with autoscaling and deployments, so their IPs keep changing and callers cannot hard-code them. Services register themselves in a registry, or the platform tracks them. In client-side discovery the caller asks the registry and picks an instance itself. In server-side discovery the caller hits a stable address, such as a load balancer or Kubernetes Service, which picks the instance.

Client-side (Eureka with Spring Cloud LoadBalancer, Consul) gives smart routing and no extra hop, but every client needs the library. Server-side hides everything, works for any language, and is what Kubernetes does: you call http://payment and cluster DNS plus kube-proxy pick a healthy pod, using the readiness probe to exclude unready pods. On Kubernetes I normally use the platform and skip a separate registry. Registries drop instances that stop sending heartbeats or fail health checks.

The two registration styles

  • Self-registration: the instance tells the registry "I am payment at 10.0.3.7:8080" on start and sends heartbeats (Eureka, Consul agents). If heartbeats stop, the entry expires.
  • Third-party registration: the platform watches instances and registers them (Kubernetes does this: the control plane tracks pods that match a Service selector and are ready).

What really happens in Kubernetes

  1. You create a Deployment of 3 payment pods and a Service called payment.
  2. The cluster DNS resolves payment (or payment.shop.svc.cluster.local) to a stable virtual IP, the ClusterIP.
  3. The cluster networking layer (kube-proxy rules or an eBPF dataplane) forwards connections to one of the ready pod IPs behind it.
  4. When a pod fails readiness, it drops out of the endpoint list and gets no new traffic.

A subtle point: load balancing happens per connection, not per request. A client that keeps one long-lived HTTP/2 or gRPC connection will pin to one pod, and new pods get no traffic. For gRPC you use a headless Service with client-side balancing, or a mesh or L7 proxy that balances per request.

Pitfalls

Stale entries (a registry that still lists dead instances for a few heartbeat periods), DNS caching in the JVM (networkaddress.cache.ttl) that keeps pointing to an old IP, and registry outages. Client-side registries should cache the last known list so the system keeps running when the registry itself is down.

Remember: on Kubernetes, DNS name plus readiness probe is your service discovery.

What is a service mesh and do you need one? Senior

A service mesh moves network concerns out of application code into a sidecar proxy next to each service (or a per-node proxy). The proxy handles mutual TLS, retries, timeouts, load balancing, traffic splitting and telemetry, and a control plane configures them all. I would only adopt one when I have many services, several languages, and a real need for uniform mTLS and traffic policy.

The benefit is consistency without a library in every language. The cost is operational complexity, extra latency per hop, resource use, and a hard-to-debug layer. For a handful of services, a library like Resilience4j plus cluster TLS is simpler. Mesh operation is platform-team work, so for developers the important point is: do not stack retries in the mesh and in the app, or you multiply them.

How a sidecar mesh works, step by step

  1. Each pod gets an extra proxy container (Envoy in Istio and others). Iptables rules redirect all inbound and outbound traffic of the app through it, so the app code does not change.
  2. When Order calls http://payment, the call leaves Order's proxy, which picks a Payment pod, starts a mutual TLS connection using a certificate the mesh issued to each workload, and enforces timeouts and retries configured centrally.
  3. Payment's proxy verifies Order's identity, checks an authorisation policy ("only the order service may call POST /charge"), and passes the request to Payment.
  4. Both proxies emit metrics and trace spans, so you get uniform golden-signal dashboards for free.

What you get, what you pay

Newer "ambient" or sidecarless designs move the proxy to per-node, trying to cut the overhead, but the idea is the same. Check what your platform team runs before claiming specifics.

Rule of thumb

Under about ten services in one language, a library (Resilience4j, Spring Cloud) plus TLS from your platform is enough. Reach for a mesh when security mandates mTLS for all internal traffic, or many teams in many languages need the same resilience and observability without each writing it. The classic bug: the app retries 3 times and the mesh also retries 3 times, giving 9 attempts, so decide which layer owns retries.

Remember: a mesh is for scale and uniform policy; small systems do not need one.

3. Resilience: timeouts, retries, breakers and friends

Why must every remote call have a timeout, and how do you pick the value? Basic

Without a timeout a slow dependency holds a thread, a connection and memory for as long as it likes, and enough stuck calls exhaust the caller's pool so it fails too. I set a connect timeout (short, around one second) and a read timeout based on the dependency's measured latency, typically a bit above its p99, and always lower than my own caller's timeout.

Many HTTP clients default to no timeout or to a very long one, so you must set it explicitly. The timeouts must nest: if the user-facing call allows 3 seconds, an inner call of 5 seconds is pointless because the outer caller has already given up and the work is wasted. Better still, pass a deadline down so each hop knows how much time is left. Note that a timeout does not mean the work failed; the server may still finish, which is why retried writes need idempotency.

Seeing how a missing timeout becomes an outage

Say Order has a pool of 100 worker threads and each request calls Payment. Normally Payment answers in 50 ms, so 100 threads handle about 2,000 requests per second. Now Payment slows to hang for 60 seconds. With no timeout, each incoming request grabs a thread and holds it. In a few seconds all 100 threads are stuck waiting, and Order cannot serve anything, even the endpoints that never call Payment. One slow dependency has turned into a full outage of Order, and then of whoever calls Order. This is how cascading failures start.

Which timeouts exist

  • Connect timeout: how long to wait to open the TCP/TLS connection. Short (hundreds of ms to 1 s), because a healthy host connects almost instantly.
  • Read (response) timeout: how long to wait for data once connected. Based on the dependency's latency distribution.
  • Connection-pool acquire timeout: how long to wait for a free connection from the pool. Often forgotten, and it hides queueing.
  • Overall deadline: a cap for the whole operation including retries.

Choosing the number

Measure the dependency's p99 or p99.9 under normal load, add some headroom, and ask what the user can tolerate. If Payment's p99 is 300 ms, a read timeout of 500 ms to 1 s is reasonable; 30 s is a bug. If the page must render in 2 s and you make a call plus one retry, each attempt may only get about 700 ms. Deadline propagation (gRPC deadlines, or a header such as X-Request-Deadline) lets each hop compute "time left" instead of using its own fixed guess.

Gotcha

A timeout only stops you waiting. The remote side may still be working and may still complete the payment. So after a write timeout you do not know the outcome: either query the status, or retry with an idempotency key. Also, in Java many clients take the timeout on the request builder, and the JDK HttpURLConnection historically had infinite defaults, so always set them in config and test them by injecting latency.

Remember: no timeout means no resilience. Inner timeouts must be shorter than outer ones.

How should retries work? Explain exponential backoff and jitter, and how retries can make an outage worse. Intermediate

I retry only transient failures (timeouts, 502, 503, 504, 429), only for idempotent calls, with a small cap on attempts, and with exponential backoff plus jitter. Backoff means waiting longer each time (for example 100 ms, 200 ms, 400 ms). Jitter means adding randomness so thousands of clients do not all retry at the same instant.

Retries can amplify an outage: if a service is struggling and every caller retries three times, the load on it quadruples just when it can least cope. This is a retry storm. It gets worse when retries stack across layers: three layers with three attempts each produce 27 calls at the bottom. So I retry at one layer only, use a retry budget (for example at most 10 percent extra traffic), honour Retry-After, and pair retries with a circuit breaker. Never retry 400, 401, 403 or 404, they will not change.

Watch out: retrying a non-idempotent POST (payment) without an idempotency key charges twice.

A retry in numbers

Suppose a service handles 1,000 requests per second and starts failing 50 percent of them. If each client retries a failed call up to 3 times with no delay, the incoming load becomes roughly 1,000 + 500 + 250 + 125, about 1,875 requests per second against a service that was already at its limit. It fails more, so there are even more retries. Without backoff the retries hit within milliseconds, so the recovering service is knocked down again each time. This positive feedback loop is a retry storm.

Backoff and jitter, explained with real values

With base 100 ms and a cap of 5 s, the exponential ceiling doubles per attempt: 100, 200, 400, 800 ms and so on. Plain exponential backoff still has all clients waiting the same time, so they retry together. Jitter randomises the wait. "Full jitter" waits a random time between 0 and the ceiling, which spreads the load most evenly. "Equal jitter" waits half the ceiling plus a random half. Either is far better than none.

// Resilience4j-style config (typical)
RetryConfig.custom()
  .maxAttempts(3)                                       // total, including the first
  .intervalFunction(IntervalFunction.ofExponentialRandomBackoff(100, 2.0, 0.5))
  .retryOnException(e -> e instanceof IOException || is5xxTransient(e))
  .build();

What to retry, and what not

RetryDo not retry
Timeouts, connection reset, 502/503/504, 429 after Retry-After400, 401, 403, 404, 409, 422: the same request will fail again
GET, PUT, DELETE (idempotent)POST without an idempotency key

Also a retry must fit inside the overall deadline. If the caller has 1 s left and the backoff is 2 s, do not retry. For batch and queue consumers, retry with long delays is fine because nobody is waiting. Say "retry budget" in an interview: allow retries to be at most about 10 percent of normal traffic, so a widespread failure cannot multiply load.

Remember: retry few, retry late, retry randomly, retry at one layer only.

Explain the circuit breaker pattern and its states. Intermediate

A circuit breaker wraps a remote call and watches its failures. While healthy it is closed and calls pass through. When the failure rate crosses a threshold it opens, and calls fail immediately without touching the sick service. After a wait it goes half-open and lets a few trial calls through: if they succeed it closes, if they fail it opens again.

It protects both sides. The caller stops burning threads on calls doomed to time out, and the struggling service gets breathing room to recover. Resilience4j typically defaults to a 50 percent failure rate over a sliding window of 100 calls, about 60 seconds open, and 10 trial calls (check your version). Slow calls should count as failures too, since slowness is how most outages start. When the breaker is open I return a fallback (cached value, default, or clear error) rather than hang. Hystrix was the early Netflix library and is in maintenance mode; Resilience4j is the usual choice.

A timeline of one breaker

  1. Payment normally answers in 40 ms. Breaker is closed, counting results in a sliding window (the last 100 calls, or the last 10 seconds).
  2. Payment's database degrades. Calls take 8 s and time out. After the failure rate passes 50 percent (and a minimum number of calls has been seen so one error cannot trip it), the breaker opens.
  3. For the next 30 to 60 seconds every call fails instantly with a "circuit open" error. No threads wait, Order can show "payments temporarily unavailable" or fall back to "pay later", and Payment gets quiet time to recover.
  4. After the wait, the breaker goes half-open and lets, say, 5 test calls through. If most succeed it closes. If they fail it opens again for another wait.

Choosing the fallback

  • Cached or stale data for reads (product details from a local cache).
  • Default or degraded response (recommendations replaced by "popular items").
  • Queue for later for writes that can wait (store the request, process when healthy).
  • Clear error when no safe fallback exists, such as charging a card. Never fake a success.

Practical points

One breaker per dependency (and often per operation), not one global one, or a failing report endpoint would block payments. Do not count business errors (a 404 or a 422) as failures. Combine breaker, timeout, retry and bulkhead deliberately, because the order matters. In Resilience4j's Spring aspects the default nesting is Retry outermost, then CircuitBreaker, RateLimiter, TimeLimiter, with Bulkhead innermost (check your version). That way each retry attempt is counted by the breaker. Expose breaker state as a metric and alert when it opens.

Remember: closed, open, half-open. Count slow calls as failures and always have a fallback.

What is the bulkhead pattern? Intermediate

Like the watertight compartments of a ship, a bulkhead gives each dependency its own limited pool of resources (threads, connections or semaphore permits). If one dependency becomes slow it can fill only its own pool, and calls to other dependencies keep working.

Without it, one shared thread pool is the weak spot. Imagine a service with 200 threads calling Payment, Catalog and Recommendations. If Recommendations hangs, all 200 threads wait on it and even Payment calls cannot run. With a separate pool of, say, 20 for Recommendations, only those 20 are stuck and the rest still work. You can also bulkhead per tenant or per client, so a noisy customer cannot eat all capacity. The cost is some unused capacity and more tuning. Thread-pool bulkheads isolate better but cost context switches. Semaphore bulkheads are lighter but cannot abandon a stuck thread.

An example with numbers

Product page service has 100 worker threads. It calls Catalog (fast), Reviews (usually fast) and Recommendations (a flaky third-party ML service). Without isolation, if Recommendations starts taking 30 s, after about 100 concurrent page views every thread is waiting on it. Catalog and Reviews are fine, but nobody can reach them. With a bulkhead, you give Recommendations a limit of 10 concurrent calls. The 11th concurrent call is rejected immediately (or served the fallback), so at most 10 threads are lost, and 90 stay free for everything else. The page degrades (no recommendations) instead of dying.

The same idea applies elsewhere: separate connection pools per downstream, separate queues or consumer groups for premium versus free tenants, separate deployments for critical and non-critical endpoints (so a heavy export job cannot starve the login API). In Kubernetes, resource requests and limits plus separate node pools are bulkheads at the infrastructure level.

Trade-off

Pools sized too small reject healthy traffic, too large give no protection. Size from measured concurrency (throughput times latency, by Little's law: 200 calls/s at 50 ms needs about 10 concurrent slots) with headroom, and expose "bulkhead full" rejections as a metric.

Remember: separate pools per dependency, so one leak does not sink the ship.

What is rate limiting and which algorithms are common? Intermediate

Rate limiting caps how many requests a client may make in a time window, to protect the service from overload and abuse and to share capacity fairly. The usual algorithms are token bucket (allows bursts, the most common), leaky bucket (smooth output), fixed window (simple but allows double bursts at the window edge) and sliding window (accurate, more memory). Over the limit I answer 429 Too Many Requests with a Retry-After header.

A token bucket holds up to N tokens and refills at R per second, and each request takes one, so a client can burst N but averages R. Across many instances the counters must be shared, typically in Redis with an atomic script, or approximated per instance. Limit per API key or tenant, not just per IP, and send headers so clients can back off. Rate limiting protects against too many requests; load shedding protects when the server is already overloaded.

Token bucket, step by step

A bucket holds up to 10 tokens and refills at 5 tokens per second. A client sends 10 requests at once: all pass (burst), the bucket is empty. The 11th immediately gets 429. After 1 second 5 tokens are back, so 5 more requests pass. Over time the average is 5 per second, with allowed bursts of 10. You store only two numbers per client: the token count and the last refill time. The refill is computed lazily on each request, so no timer is needed.

In a multi-instance deployment

If you run 5 gateway instances each allowing 100 per minute, the client really gets 500. Options: a shared counter in Redis updated by an atomic Lua script or INCR with expiry (accurate, adds a network hop and a dependency), or per-instance limits set to total divided by instance count (cheap, imprecise). Decide what to do when Redis is down: usually "fail open" with a local fallback for non-critical APIs.

Return 429, Retry-After: 12 (seconds), and optionally the draft-standard RateLimit headers or the common X-RateLimit-Remaining. Layer the limits: per IP at the edge for abuse, per API key for fairness, per endpoint for expensive routes (search, export). Related but different: load shedding drops low-priority work when the server itself is overloaded, whoever sends it.

Remember: token bucket allows bursts; return 429 with Retry-After; limit per client, not globally.

What is the difference between liveness, readiness and startup health checks? Intermediate

Liveness asks "is this process stuck, should I restart it?". Readiness asks "can this instance take traffic right now?". Startup asks "has it finished booting?", and holds the other two off until it has. On Kubernetes a failing liveness probe restarts the container, and a failing readiness probe only removes the pod from the Service endpoints.

The classic mistake is putting a dependency check, such as the database, in the liveness probe. When the database blips, every pod fails liveness, all restart together, and a small problem becomes an outage. Liveness should check only the process itself. Readiness may include dependencies the service cannot work without, though careful: if all instances become unready at once, you lose everything. In Spring Boot use Actuator health groups for this split.

What each probe does in Kubernetes

The database-in-liveness outage, as a timeline

  1. The shared database has a 30-second failover.
  2. Liveness checks call the DB, so every pod fails liveness for 30 s.
  3. Kubernetes restarts all pods at once. Each takes 60 s to boot and warm caches.
  4. Even after the DB is back, the service is down for another minute and then hammers the DB with a cold-start stampede.

A 30-second blip became a multi-minute outage because the check asked the wrong question. Restarting a pod does not fix someone else's database.

Using readiness well

Use readiness to hold back traffic during startup and warm-up, and to take a pod out during a graceful shutdown: on SIGTERM, first fail readiness, wait a few seconds for endpoints to update, then finish in-flight requests and exit. Without that, rolling deployments drop requests. Keep checks cheap and fast with a short timeout, and do not call dependencies on every probe (cache the result for a few seconds). With Spring Boot Actuator, /actuator/health/liveness and /actuator/health/readiness are separate groups so you can choose which indicators go where.

Remember: liveness means restart me, readiness means send me traffic. Never check the database in liveness.

What are backpressure and load shedding, and how are they different from rate limiting? Senior

Backpressure is a signal from a slow consumer to its producer to slow down, so queues do not grow without limit. Load shedding is a service deliberately rejecting some work early when it is overloaded, so the work it does accept still finishes quickly. Rate limiting caps what each client may send; shedding protects the server whoever is sending.

Without either, an overloaded service accepts everything, queues it, and answers every request slowly. By the time a response is ready the caller has timed out, so the work was wasted and the service is busier than ever. A service that is 20 percent over capacity can end up serving nobody usefully (goodput falls to near zero) while a service that rejects the extra 20 percent serves 100 percent of the rest well.

How to apply it

  • Bounded queues: a thread pool with a queue of 100, not an unbounded one. When full, reject immediately (HTTP 503 with Retry-After, or a gRPC RESOURCE_EXHAUSTED).
  • Concurrency limits: cap in-flight requests (adaptive limits such as AIMD or Little's law based limiters adjust to observed latency).
  • Priority: shed low-value traffic first (analytics, prefetch, batch) and keep checkout and login.
  • Queue age: drop requests that have already waited longer than the caller's deadline, since nobody is listening.
  • Streams and consumers: in Kafka, a consumer controls its own pace by polling, which is natural backpressure; with reactive streams (Reactor, RxJava) the subscriber requests N items at a time.

What is idempotency and why is it essential in microservices? Intermediate

An operation is idempotent when doing it many times has the same effect as doing it once. It is essential because in a distributed system I can never be sure whether a call or message arrived, so I retry, and brokers redeliver. Without idempotency, retries create duplicate orders, double charges and repeated emails.

Some operations are naturally idempotent ("set status to SHIPPED", delete by id). Others, like "add 100 to the balance", are not, and need a deduplication key: the client or producer sends a unique id, and the receiver stores it with a unique constraint in the same transaction as the change. A second delivery hits the constraint and is ignored or answered with the stored result. Make the check atomic, since a "check then insert" has a race. Expire old keys after a sensible window. For HTTP APIs this becomes the Idempotency-Key header, covered in the REST section.

Naturally idempotent versus not

OperationIdempotent?Why
Set status = SHIPPEDYesSame final state however many times
Delete order 42Yes (effect)Already gone is still gone
Add 100 to balanceNoEach run adds again
Send welcome emailNoEach run sends another
Insert row with generated idNoEach run creates a new row

Making a non-idempotent operation safe

There are two ways. First, change the shape of the operation: "set balance to 500 given version 7" instead of "add 100". Second, add a deduplication key. A message or request carries a unique key (UUID created by the client or producer, or a business key like orderId + step). The receiver does the following in one transaction:

INSERT INTO processed_keys(key, response) VALUES (:key, NULL);  -- unique
-- if this insert violates the constraint, it is a duplicate: stop,
-- and return the saved result (or just ack the message)
UPDATE accounts SET balance = balance + 100 WHERE id = :acc;
UPDATE processed_keys SET response = :result WHERE key = :key;

Pitfalls

  • "SELECT then INSERT" without a unique constraint is a race; two parallel duplicates both pass the check.
  • A key stored outside the transaction (in Redis, say) can say "done" when the DB commit failed, or the reverse. Prefer the same database, or accept and document the gap.
  • Side effects that leave your system (email, card charge at a provider) need the provider's own idempotency key. Pass yours through.
  • Keep keys long enough to cover your longest retry window (for example 24 hours or more), and decide what a same-key request with a different body does (reject it).

Remember: assume every message arrives twice; dedupe with a unique key in the same transaction.

4. Data ownership, transactions and consistency

Why should each microservice own its database? A team wants to share one database "just for now". What do you say? Basic

Because the database is the strongest form of coupling. If two services read and write the same tables, a schema change in one breaks the other, neither can be deployed or scaled alone, and you have a distributed monolith. So each service owns its data and others get at it only through its API or its events. I would say no to "just for now", because temporary shared databases become permanent.

Own data also lets each service pick the right store (SQL, document, search) and enforce its own invariants. "Own" does not need a separate server: separate schemas or databases with separate credentials are enough, as long as nobody reaches across. The cost is that you lose cross-service joins and ACID transactions, and must use APIs, events, copies of data and sagas instead. If a shared database is really unavoidable in a migration, make it read-only for the other side, hide it behind a view, and set an end date.

What goes wrong when the database is shared

Orders and Billing share a database. Billing renames orders.total to orders.amount_net as part of its own change. Orders breaks at runtime, a week later, in production, because nobody saw the dependency. Or Reports runs a heavy query and locks rows Orders needs. Or Orders wants to move to a document store but cannot, because three other services read its tables. The shared schema is an undocumented, unversioned API with no owner.

What "owning" a database means in practice

  • Only the owning service holds credentials for its schema. Others physically cannot read it.
  • Other services use the owner's API (versioned, with a contract) or subscribe to its events.
  • The owner can refactor tables freely, because only it depends on them.
  • It can be separate servers, or one server with separate schemas and users, a common cost-saving compromise. What matters is the access rule.

The consequences you must plan for

If the team insists, show them the cost in their own terms: "you can no longer deploy on your own, and we need a sign-off from the other team for every column change." Offer a path: if it must be shared temporarily, restrict the other service to read-only access through a view, document the owner, and put a removal date in the backlog.

Remember: never share tables; share data through APIs and events.

How do you query data that lives in several services (the "join" problem)? Intermediate

There are two options. For a small number of items I use API composition: a gateway or BFF calls the services and joins the results in memory. For heavy or frequent queries I build a read model: a service or search index that keeps its own denormalised copy of the needed data, updated from events (CQRS).

Composition is simple and always fresh, but latency adds up, one slow service slows the page, and it cannot do large filtering or sorting across services (you cannot efficiently sort orders by customer name when names live elsewhere). A read model answers fast, with one query on one store, but is eventually consistent and needs maintenance. Another cheap option is to copy a few stable fields you always need (the customer name on the order) at write time, accepting that they may be slightly stale.

API composition, worked example

The page "My orders" needs, for each of the last 10 orders, the customer name, product titles and delivery status. Orders owns the order rows. Customers, Catalog and Shipping hold the rest. The composer:

  1. Calls Orders for the 10 orders.
  2. In parallel, calls Customers once (batched ids), Catalog with the product ids, Shipping with the order ids. Batching matters: 10 separate calls per service would be the N+1 problem across the network.
  3. Joins in memory and returns the page. If Shipping is slow, return the page with "status unavailable" rather than failing.

Read model, worked example

Support staff need to search orders by customer email, product name and date range, sorted by total. No single service can answer this. So an "order search" read model subscribes to OrderPlaced, CustomerUpdated and ProductRenamed events and writes one flat document per order into Elasticsearch or a SQL table. One indexed query now answers it in milliseconds. The cost: it can be seconds behind, you need replay or rebuild tooling when the shape changes, and you must handle out-of-order and duplicate events.

Choosing

Use composition whenUse a read model when
Few records per request, data must be fresh, queries are simple lookupsFiltering, sorting or searching across services, high read volume, many pages need the same join

A third option is copying a few stable fields at write time (customer name inside the order). It is cheap and avoids runtime calls, but you must decide what "stale" means: an invoice should keep the name at purchase time, while a profile page should show the current one.

Remember: few items, compose at runtime; heavy queries, build a read model from events.

What is eventual consistency and how do you live with it as a developer? Intermediate

Eventual consistency means different services may briefly disagree, but if no new updates arrive they all converge to the same state. It is the price of not using distributed transactions. I live with it by designing the user experience and the code for the gap, not by pretending it does not exist.

Practical techniques: show an honest status ("payment pending") rather than a final-looking answer; after a write, return the new state to the caller (or read from the writer) so users see their own changes; make every consumer idempotent and tolerant of reordering; use version numbers or timestamps to ignore stale events; and run reconciliation jobs that detect and repair drift. Also ask the business: most "must be instant" requirements are really "within a few seconds is fine", and only a few things, like not overselling the last item, need strict handling.

A timeline of the gap

  1. t=0: user changes their shipping address in Profile service. Profile's database is updated and it publishes AddressChanged.
  2. t=0.2 s: the user opens "checkout". Order service still holds the old address, because it has not consumed the event yet. The user sees the old address.
  3. t=0.5 s: Order consumes the event and updates its copy. From now on everything agrees.

For half a second the system disagreed. That is acceptable for an address. It would not be acceptable for "reserve the last ticket", which is why you pick the consistency level per use case, not one policy for everything.

Techniques that make the gap harmless

  • Read your own writes: after the update, the API returns the new representation, and the UI shows it directly without a re-fetch from a lagging replica. Or route that user's next reads to the primary for a short time.
  • Versioning: each event carries a version or timestamp, and a consumer ignores anything older than what it holds, so late or reordered events cannot overwrite newer state.
  • Honest states: PENDING, PROCESSING, CONFIRMED instead of a silent lie.
  • Reconciliation: a periodic job compares two sources (orders versus payments) and fixes or flags differences. It is your safety net for the bugs you did not foresee.
  • Strong consistency where needed: inside one service (one database transaction), or with a conditional update (UPDATE stock SET qty = qty - 1 WHERE qty > 0) so the last item cannot be oversold.

The interview-level insight: eventual consistency is not "sloppy". It is a deliberate trade for availability and independence, and you protect the few invariants that really need it inside a single service's boundary.

Remember: convergence takes time. Show pending states, be idempotent, and reconcile.

Why is two-phase commit (2PC) usually avoided in microservices? Senior

2PC makes several databases commit or abort together: a coordinator asks all to prepare, then tells all to commit. It is avoided because it blocks: participants hold locks while waiting, and if the coordinator dies between the phases they are stuck. It also needs every participant to support the protocol, and it lowers availability and throughput, which defeats the point of independent services.

In the prepare phase each participant promises it can commit and keeps its locks. If the coordinator crashes after prepare, those locks stay until it recovers. Availability is the product of all participants being up. Most modern stores, REST APIs and message brokers do not take part in 2PC anyway. It is still used inside one platform, for example XA transactions across a database and a JMS broker in a Java application server. Across services I use sagas and the outbox instead, accepting eventual consistency.

How 2PC works, and where it hurts

Phase 1 (prepare): the coordinator asks each participant "can you commit transaction T?". A participant that answers yes has written its changes to a durable log and is now bound: it holds locks and may not unilaterally abort. Phase 2 (commit): if all said yes, the coordinator sends commit, and everyone finishes; if any said no, everyone rolls back. The weak point is the window between the phases. If the coordinator crashes there, participants that voted yes are "in doubt": they cannot commit (maybe someone voted no) and cannot abort (maybe the others committed). They wait, holding row locks, and other transactions pile up behind those locks.

Why it clashes with microservices

  • Availability: the operation needs all participants up at the same time. Three services at 99.9 percent give about 99.7 percent for the combined operation, and every added one lowers it.
  • Latency and locks: locks are held across network round trips and a log flush on each side, so throughput drops, and deadlocks across services are hard to detect.
  • Support: REST APIs, Kafka (outside its own transactions), most SaaS APIs and many NoSQL stores do not offer a prepare phase.
  • Coupling: services must share a transaction manager and a protocol, the opposite of independence.

What to say in place of it

Use a saga for multi-service business operations, the outbox for "update my data and publish an event", and idempotent consumers for safety. XA/2PC is still fine in a narrow case: one application server coordinating a database and a JMS queue inside a single deployment, where both are reliable and under your control. Also mention newer research-grade systems (Spanner, CockroachDB) that give distributed transactions inside one database product, which is different from spanning independent microservices.

Remember: 2PC blocks and couples availability. Across services use sagas.

What is the saga pattern? Walk through an example. Intermediate

A saga is a business transaction across several services, done as a sequence of local transactions. Each step commits in its own service and triggers the next. If a step fails, the saga runs compensating actions that undo the earlier steps, such as refunding a payment, so the system returns to a consistent state without a distributed lock.

Example, placing an order: (1) Order service creates the order as PENDING. (2) Payment charges the card. (3) Inventory reserves stock. (4) Order marks it CONFIRMED. If Inventory finds no stock at step 3, the saga runs Payment's refund and then marks the order CANCELLED. A saga gives atomicity (all or compensated) and eventual consistency, but not isolation: other requests can see the half-finished PENDING order. Countermeasures include "semantic locks" (the PENDING state), ordering steps so the hardest-to-undo step comes last, and re-reading before acting.

The order saga as a table of state

StepServiceLocal actionCompensation
1OrderCreate order, status PENDINGMark CANCELLED
2PaymentAuthorise or charge cardVoid or refund
3InventoryReserve itemsRelease reservation
4OrderMark CONFIRMEDnone (last step)

If step 3 fails, run the compensations of the steps that completed, newest first: refund the payment (2), then cancel the order (1). Step 4 never ran, so it needs none. Each step and each compensation commits only in its own service's database.

Why "no isolation" bites

Between step 1 and step 4 the order is visible as PENDING, and the card is charged though stock is not yet reserved. Another process may read this half-done state. Practical countermeasures:

  • Semantic lock: the status field itself (PENDING) tells everyone "this is in flight, do not act on it".
  • Reorder steps: reserve stock before charging, since releasing stock is cheaper to undo than a refund (which has fees and customer-visible delay).
  • Pivot step: the point after which the saga must go forward. Steps before it are compensatable, steps after it are retryable until they succeed.
  • Commutative updates and version checks so interleaved sagas do not corrupt each other.

Saga state is data

Persist where each saga is (a row saga_id, current_step, status, payload), because the process coordinating it can crash. On restart it continues from the stored step. Each step must be idempotent, since after a crash you might send the same command again. Sagas also need timeouts: if Inventory never replies, the saga should eventually fail and compensate, not wait forever.

Remember: saga = local transactions + compensations. Atomic in outcome, not isolated.

Saga choreography versus orchestration: how do you choose? Senior

In choreography there is no central controller: each service reacts to events and publishes its own, like dancers following each other. In orchestration one orchestrator tells each service what to do and tracks the state. I use choreography for short sagas of two or three steps, and orchestration for longer flows, branching, timeouts or anything the business wants to see.

Choreography is loosely coupled and has no single point of failure, but the flow lives nowhere: it is spread over many event handlers, hard to follow, and cyclic dependencies creep in. Orchestration puts the flow in one place so it is explicit, testable and easy to monitor ("which step is order 42 on?"), at the cost of a central component that can become a bottleneck or accumulate logic. Keep the orchestrator dumb: it sequences, it does not hold business rules. Tools: Temporal, Camunda, AWS Step Functions, Axon, or a hand-written state machine with a saga table.

The same flow both ways

Choreography: Order publishes OrderPlaced. Payment listens, charges, publishes PaymentCompleted (or PaymentFailed). Inventory listens to PaymentCompleted, reserves, publishes StockReserved or StockFailed. Order listens to the results and sets CONFIRMED or CANCELLED. Compensation is also events: Payment listens to StockFailed and refunds.

Orchestration: an OrderSaga component stores state and sends commands: ChargeCard to Payment, waits for the reply, then ReserveStock to Inventory, waits, then marks done. On failure it sends RefundCard. The services just do what they are told and reply.

What interviewers listen for

That the orchestrator is not a distributed transaction monitor with business logic. Services keep their rules; the orchestrator only decides the order and the error path. Mention durable execution engines (Temporal, Cadence, Step Functions) which persist the workflow state and resume after crashes, so you write the flow as normal code and do not build the saga table by hand. Also, whichever style you pick, each step must be idempotent and the saga state must be persisted.

Remember: choreography for 2 or 3 simple steps, orchestration for long or visible flows.

What makes a good compensating action, and what if the compensation itself fails? Senior

A compensation must be idempotent, retryable until it succeeds, and a business-level undo, not a database rollback: "refund the payment", not "delete the payment row". If it fails, I retry with backoff, and if it still fails I park the saga for manual attention with an alert. A compensation is not allowed to just give up.

Some steps cannot be undone (an email already sent, money already shipped to a partner). So I order the steps: put risky or irreversible ones last, and put cheap, reversible ones first. Where a step cannot be undone, the compensation is a new action, such as a corrective email. The compensating command must tolerate being run when the original step never happened or only partly happened, since a timeout makes it unclear. Persist saga state so a crash does not lose where you were.

Semantic undo, with an example

The undo of "charge 50 dollars" is not "delete the charge row". The card network has already seen the charge, the customer's bank statement shows it, and an audit needs the history. The correct compensation is a new business action: "refund 50 dollars", linked to the original payment id. Similarly the undo of "reserve 3 units" is "release reservation R-77", and of "send email" is, at best, a follow-up email.

Properties of a good compensation

  • Idempotent: running it twice refunds once. It keys on the original payment id and stores "already refunded".
  • Commutative with the original: it must be safe if it arrives before the original step finished (a timeout where we are not sure the charge happened). A common design is to record "cancel requested for payment P", and if the charge arrives later it sees the cancellation and does nothing.
  • Retriable: transient failures retry with backoff, as long as needed. Business failures (refund window closed) go to a human queue.
  • Observable: every compensation is logged and visible on a saga dashboard.

When compensation fails

The saga is then stuck in an "inconsistent but known" state. You must not silently drop it. Mark it FAILED_COMPENSATION with the context needed to fix it, raise an alert, and provide an admin action to retry or resolve manually. This is a normal part of running sagas, so budget operations time for it.

Design tip: use a two-step "reserve then confirm" instead of "do then undo" where you can (card authorisation then capture, stock hold then commit). Cancelling a reservation is cheaper, safer and often free, and the irreversible part happens last.

Remember: compensate with a business undo, make it idempotent, retry forever, put irreversible steps last.

What is the dual-write problem? Senior

It happens when a service must update its own database and also publish an event or call another system, and there is no transaction covering both. If the database commits and the publish fails, the world never hears about the change. If the publish succeeds and the commit fails, the world hears about something that never happened. Either way the two systems disagree.

Ordering the two calls does not fix it, and a crash can always land between them. Retrying the publish helps only if the intent to publish survived the crash. The reliable fixes are the transactional outbox (write the event to a table in the same transaction as the data, publish it later) or event sourcing (the event is the data). Change data capture (CDC) is another way to get the same effect by reading the database log.

The failure cases, laid out

1. db.save(order)          // commits
2. broker.publish(event)   // process crashes before this line
=> order exists, nobody was told. Payment never starts.

1. broker.publish(event)   // succeeds
2. db.save(order)          // fails (constraint, crash, deadlock)
=> event says an order exists, but it does not. Payment charges for nothing.

Wrapping both in a try/catch does not help: if the process dies after step 1, there is no code left running to do step 2 or to undo step 1. Putting the publish inside the database transaction block is also not atomic, because the broker is not part of that transaction: the commit can still fail after the publish.

Same problem, other places

  • Updating the database and a cache (stale cache after a partial failure).
  • Updating the database and a search index.
  • Writing to two databases or two services in one request handler.

The fixes, compared

The common thread: make a single atomic write the source of truth, and derive every other write from it with retries.

Remember: two systems, two commits, a crash can fall between them. Fix it with the outbox.

Explain the transactional outbox pattern. Senior

In one local database transaction I save the business change and also insert the event into an outbox table. Both commit or neither does. A separate relay then reads unpublished rows and publishes them to the broker, marking them sent. This guarantees that every committed change eventually produces its event, without needing a distributed transaction.

The relay is either a polling publisher (a scheduled job selecting unsent rows, simple but adds a little delay and database load) or change data capture such as Debezium reading the database log, which has lower latency and no polling. The relay can crash after publishing but before marking the row, so delivery is at-least-once: consumers must dedupe using the event id. Ordering is preserved per aggregate if the relay publishes in order and uses the aggregate id as the message key. Clean up old outbox rows with a retention job.

What the code looks like

@Transactional
public void placeOrder(Order o) {
    orderRepo.save(o);
    outboxRepo.save(new OutboxEvent(
        UUID.randomUUID(),            // event id, used by consumers to dedupe
        "Order", o.getId(),           // aggregate type and id (message key)
        "OrderPlaced", toJson(o)));
}   // one commit: both rows, or neither

// relay (separate thread or process)
List<OutboxEvent> batch = outboxRepo.findUnsentOrderByIdLimit(100);
for (e : batch) { broker.send(e.aggregateId(), e.payload()); outboxRepo.markSent(e.id()); }

Polling versus CDC relay

Detail that interviewers probe

  • Why at-least-once? Relay sends, then crashes before marking sent. After restart it sends again. Consumers dedupe by event id (inbox table).
  • Ordering: use the aggregate id as the Kafka key so all events of one order land in one partition in order. With multiple relay instances polling, use SELECT ... FOR UPDATE SKIP LOCKED carefully or one relay per partition to avoid reordering.
  • Table growth: delete or archive sent rows after a retention period; index on the unsent flag.
  • Inbox on the receiving side: the mirror image of the outbox, giving effectively-once handling.

Remember: write data and event in one transaction, publish later, dedupe on the consumer.

What is CQRS, and when is it worth using? Intermediate

CQRS (Command Query Responsibility Segregation) separates the write model, which handles commands and enforces rules, from the read model, which is shaped and stored for fast queries. The read side is updated from the write side, usually through events. It is worth it when reads and writes have very different shapes or scale, or when you need cross-service query views. For plain CRUD it is overkill.

The simplest form uses one database and different classes for commands and queries. The full form uses separate stores: for example a relational write store and an Elasticsearch or denormalised read store, kept in sync by events, so the read side is eventually consistent. Benefits are fast tailored reads and independent scaling. Costs are more moving parts, lag between write and read, and the need to rebuild read models. CQRS does not require event sourcing, and event sourcing does not require CQRS, though they combine well.

Why bother separating them

A write model protects rules: "an order cannot ship before it is paid". It is shaped around aggregates and consistency. A read model answers screens: "order list with customer name, total, status, sorted by date". It wants denormalised, indexed, precomputed data. One model doing both turns into a compromise, with huge joins on the read path and fragile entities on the write path. CQRS lets each be shaped for its job.

A flow, with an example

  1. Command PlaceOrder goes to the write model, which checks rules and saves to the relational store.
  2. It emits OrderPlaced (through an outbox).
  3. A projector consumes it and updates order_list_view, one flat row per order with the customer name and totals ready to show.
  4. Query GET /orders?customer=7 reads that view with one indexed lookup.

The user who just placed the order might fetch the list before the projector ran, so either return the created order in the command response, or let the UI add it locally, or read from the write side briefly.

Levels of CQRS

  • Level 1: separate command and query code paths, same database. Cheap and often enough.
  • Level 2: separate read tables or views in the same database, updated in the same transaction (still consistent).
  • Level 3: separate stores and technologies, fed by events (eventually consistent).

Do not apply it to a simple admin CRUD screen. Use it where read load is much higher than write load, where views need cross-service data, or where the read shape differs greatly from the write shape. Mention the operational cost: you must be able to rebuild a read model from scratch (replay events or re-read the source) when its design changes.

Remember: CQRS splits write rules from read shapes; the read side is eventually consistent.

What is event sourcing, and what are its benefits and risks? Senior

Event sourcing stores the state of an entity as an append-only list of events (OrderPlaced, ItemAdded, OrderShipped) instead of only its current row. The current state is computed by replaying the events. It gives a perfect audit trail, the ability to rebuild any past state or new read model, and it solves the dual-write problem because the event is the data.

The risks are real. Replay gets slow, so you keep snapshots. Events are permanent, so changing their schema needs upcasting or versioning forever. Queries need projections (read models), which makes the system eventually consistent. Deleting personal data (GDPR) is hard in an immutable log, so people use crypto-shredding (delete the encryption key). And the team needs a new mental model. I use it where history is the business (ledgers, bookings, audit-heavy domains), not by default.

Example: a bank account

Instead of a row balance = 70, store the events:

AccountOpened   {id: A1}
MoneyDeposited  {id: A1, amount: 100}
MoneyWithdrawn  {id: A1, amount: 30}
=> state = fold(events) = 100 - 30 = 70

To handle a command, load the account's events, rebuild its state, check the rule (enough balance?), and append a new event. Appends use optimistic concurrency: "append at version 3, fail if the stream is no longer at 3". The event store is append-only; nothing is updated or deleted.

What you gain

  • Audit by construction: you know exactly how you got here, who and why.
  • Temporal questions: "what was the balance last Tuesday?" is a replay up to that time.
  • New read models later: start a fresh projection from event zero when a new report is needed.
  • Natural fit with events and the outbox: the append is the only write.

What it costs

ProblemUsual answer
Long streams replay slowlySnapshots every N events
Event schema evolves, old events stay foreverVersioned events, upcasters that translate old to new when reading
Cannot query current state easilyProjections (read models), which are eventually consistent
Personal data deletionCrypto-shredding, or keep PII outside the events and reference it
Wrongly recorded eventAppend a correcting event; never edit history

Events must record business facts in past tense ("MoneyWithdrawn"), not technical changes ("RowUpdated"). A good rule: if you cannot explain why you need to replay history, do not use event sourcing. A plain table plus an audit log gets you most of the audit value at a fraction of the complexity.

Remember: state is the sum of events: great for audit and rebuilds, costly for schema change and queries.

5. Evolution, testing, observability and security

How do you change an API or event schema without breaking consumers? Senior

I make only backward-compatible changes and use the expand and contract approach: add the new thing alongside the old, migrate consumers, then remove the old thing once nobody uses it. Adding optional fields is safe. Removing a field, renaming it, changing its type or changing its meaning is breaking and needs a new version or a migration.

Consumers should follow the tolerant reader rule: ignore unknown fields and do not fail on new enum values, otherwise even additive changes break them. For a rename, say fullName to name: (1) add name and keep writing both, (2) move all consumers to name, confirmed by contract tests or usage metrics, (3) stop writing fullName. For events, use a schema registry (Avro or Protobuf) with compatibility checks in CI, and rolling deployment means old and new code run together, so every release must tolerate both versions. When a break is unavoidable, run /v2 next to /v1 with a sunset date.

Why this is hard in microservices

You cannot upgrade all services at once. During a rolling deployment, old and new instances of the same service run side by side, and consumers on old and new releases call them. So at any moment, every producer must be understood by every consumer version in flight. The safe rule is that each deploy is compatible with the one before and the one after.

Which changes are safe

The full expand and contract for a database or event rename

  1. Expand: add name. Producers write both fullName and name. Readers still use fullName.
  2. Migrate: backfill old data, then switch each consumer to read name. Verify via metrics or contract tests that nobody reads fullName any more.
  3. Contract: stop writing fullName, then delete it in a later release.

The same approach applies to database columns: add column, dual write, backfill, switch reads, drop old column, each as its own deploy. For events, remember they are stored for a long time, so old events may be replayed through new code. A schema registry (Confluent, Apicurio) configured for BACKWARD or FULL compatibility rejects a breaking schema in CI. When you truly must break, publish a new topic or a new version (OrderPlaced.v2), run both for a deprecation period, and announce a sunset date with the Deprecation and Sunset headers.

Remember: expand, migrate, contract. Add freely, never remove or repurpose in one step.

What is contract testing and why use it instead of end-to-end tests? Intermediate

A contract test checks that a provider and a consumer agree on the API shape without running both together. In consumer-driven contract testing (Pact, Spring Cloud Contract) each consumer records what it needs from the provider as a contract. The provider's build replays all contracts against its real code, so a breaking change fails the provider's pipeline before release.

Full end-to-end tests across many services are slow, flaky, need a shared environment, and when they fail it is unclear who broke what. Contract tests are fast and run per service, so teams can deploy independently, which is the whole point of microservices. They check shape and basic behaviour, not business logic, so you still keep a few end-to-end smoke tests for the critical journeys.

The flow of a consumer-driven contract, step by step

  1. The Order team writes a consumer test against a Pact mock of Payment: "when I call GET /payments/9, I expect 200 and a body with status as a string and amount as a number".
  2. Running that test produces a contract file (a pact) and publishes it to a broker (Pact Broker or PactFlow).
  3. In Payment's pipeline, the provider verification fetches all pacts from consumers, replays each request against the real Payment code (with test data prepared by "provider states" such as "payment 9 exists"), and checks the responses fit.
  4. If Payment removes status, verification fails in Payment's build, before it ships. The failure names exactly which consumer needs it.
  5. A "can I deploy?" check against the broker tells you whether a given version is compatible with what is running in production.

What it does and does not cover

  • Covers: field names, types, status codes, required headers, message shapes (Pact also supports async messages).
  • Does not cover: business correctness, performance, or the full journey. That is why you keep some component and end-to-end tests.
  • Consumer-driven means contracts only contain what the consumer actually uses, so the provider is free to change the rest. Contrast with provider-driven contracts (an OpenAPI file validated in CI, Spring Cloud Contract stubs written by the provider), which are simpler but do not tell you who uses what.

Say the cost honestly: contract testing needs discipline and tooling, and the benefit shows when many teams deploy often. For three services owned by one team, an OpenAPI diff in CI may be enough.

Remember: the consumer states what it needs, the provider proves it still delivers. Few end-to-end tests, many contract tests.

How do you test a microservice? Describe the layers. Intermediate

Mostly fast tests on the inside, a few on the outside. Many unit tests for business logic. Component or integration tests that run the service with real infrastructure (a database in Testcontainers) and fake downstream services. Contract tests for each integration. And a very small number of end-to-end tests for critical user journeys.

The important point is to test the service in isolation: stub the services it calls (WireMock or similar) and test failure paths too, such as timeouts and 503, so you know the circuit breaker and fallback work. Use real databases rather than in-memory fakes, since SQL dialect and constraint differences hide bugs. Messaging needs tests for duplicates and out-of-order delivery. In production, add canary releases and monitoring as the last safety net.

The layers with an example service

Take Order service. It has domain rules, a Postgres database, calls Payment over HTTP, and publishes events to Kafka.

  • WireMock returns a 5-second delay: assert the timeout fires, the breaker opens, and the fallback is used.
  • Payment returns 503 twice then 200: assert the retry happens and an idempotency key is reused.
  • The same Kafka message is delivered twice, and out of order: assert the state is correct.

Avoid mocking the database: in-memory H2 hides dialect, locking and migration issues that Postgres shows. Keep end-to-end tests few because each failure means an investigation across teams.

How do you deploy a microservice with zero downtime? Compare rolling, blue-green and canary. Intermediate

In a rolling deployment, new instances replace old ones a few at a time. In blue-green, a full new environment runs next to the old one and traffic switches at once. In a canary release, a small slice of traffic goes to the new version first, and it is widened only if metrics stay healthy. Whatever the method, the old and new versions must be compatible, since they run together at some point.

What makes it truly zero downtime

  1. Readiness probe: a new pod gets traffic only after it has warmed up and passes readiness.
  2. Graceful shutdown: on SIGTERM the old pod first fails readiness so the load balancer stops sending new requests, waits a few seconds for endpoints to propagate, finishes in-flight requests (and consumes no new messages), then exits. Set the termination grace period longer than your longest request. Without this, rolling restarts produce a burst of 502 errors.
  3. Backward-compatible schema and API: old and new versions share the database and message topics during the rollout (expand and contract).
  4. Automatic gates: the pipeline watches error rate and latency of the new version and rolls back on regression. Tools: Argo Rollouts, Flagger, a mesh.

Also separate deploy from release using feature flags: the new code ships dark and is switched on for 1 percent of users, then more, and can be turned off without a redeploy. The risk: flags left forever create dead code and untested combinations, so remove them after rollout.

Remember: small blast radius first, fail readiness before shutdown, and both versions must run side by side.

What are logs, metrics and traces, and why do microservices need all three? Basic

Metrics are numbers over time that tell me something is wrong (error rate, latency, saturation). Logs are detailed events that tell me what happened in one place. Traces follow one request across services and show where the time or the failure was. Metrics find the problem, traces locate the service, logs explain the cause.

In a monolith a stack trace is often enough. With many services one user request touches ten of them, so without a trace I cannot tell which hop was slow. For metrics I use the RED method for services (rate, errors, duration) and USE for resources (utilisation, saturation, errors). Alert on symptoms users feel (error rate, p99 latency) rather than on every CPU spike. Keep cardinality low in metric labels, since per-user labels blow up the metrics store.

An incident, in order of tools

  1. An alert fires: checkout p99 latency above 3 s (a metric, on a symptom users feel).
  2. A dashboard shows Order's errors normal but its duration high. Open a slow trace from the time window: the span for inventory.reserve takes 2.9 s.
  3. Filter Inventory's logs by that trace id: "lock wait timeout on table stock_reservations". Root cause found.

Practical guidance

  • Golden signals / RED: for each service watch rate, errors and duration; for resources watch utilisation, saturation and errors (USE). Add queue lag for async consumers.
  • Structured logs: JSON with fields such as traceId, service, level, orderId. Never log secrets or personal data.
  • Cardinality: a metric label with a user id or order id creates millions of time series and can take the metrics store down. Put high-cardinality data in logs and traces.
  • Alert on SLOs (for example 99.9 percent of requests under 500 ms over 30 days, burn rate alerts), not on every CPU blip, to avoid alert fatigue.
  • Sampling: trace 1 to 10 percent of normal requests but keep all errors and slow ones (tail-based sampling) if your tooling supports it.

Remember: metrics say that, traces say where, logs say why.

What is a correlation id, and how does distributed tracing propagate context? Intermediate

A correlation id (or trace id) is a unique id created at the edge for each request and passed to every service and message it touches, and written in every log line. Searching for it shows the whole journey. Distributed tracing extends this with spans (one per hop, with timings) linked by parent ids, passed in the W3C traceparent header.

The header looks like traceparent: 00-<trace-id>-<parent-span-id>-01. Each service reads it, creates a child span, and forwards it on outgoing calls, including message headers for Kafka or queues. Libraries (OpenTelemetry, Micrometer Tracing in Spring Boot 3) do this automatically for HTTP clients, but it breaks when work moves to another thread or async executor unless the context is propagated. Put the trace id into the log context (MDC in Java) so every log line carries it, and return it in error responses so support can quote it.

A request walked through

  1. The gateway receives a request without a traceparent, creates one: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01. The fields are version, trace id (16 bytes in hex), parent span id (8 bytes), and flags (01 means sampled).
  2. It forwards the header to Order. Order starts its own span, with the same trace id and a new span id, remembering the gateway's span as its parent.
  3. Order calls Payment with an updated traceparent carrying Order's span id as the parent. Payment does the same for its database call.
  4. Every span is sent to a collector (OpenTelemetry Collector, then Jaeger, Tempo, Zipkin or a vendor). The backend groups spans by trace id and draws the waterfall.
  5. Every log line includes the trace id, so a search in the log system returns all lines from all services for that request.

Where propagation breaks

  • Thread hops: the context lives in a thread-local; @Async methods or custom executors lose it unless wrapped (Micrometer context-propagation, or OpenTelemetry's context-aware executors).
  • Messaging: put the header in the message headers when publishing, and restore it on the consumer. Instrumentation libraries for Kafka and RabbitMQ usually do this. A consumer span is typically linked to the producer's span.
  • Edges that strip headers: a proxy or a third-party that drops unknown headers.
  • Batch jobs and scheduled tasks: there is no incoming request, so start a new trace explicitly.

Correlation id versus trace id: a plain correlation id (custom X-Request-Id) only lets you group logs. A trace adds structure (parent and child, timing). Prefer W3C Trace Context since every modern tool understands it. Also return the id in the error response body or an X-Trace-Id header, so a user can quote it to support.

Remember: create the id at the edge, forward it everywhere, log it in every line.

How do you secure service-to-service calls? Senior

I never trust a call just because it comes from inside the network (zero trust). I encrypt traffic with TLS and prove which service is calling, either with mutual TLS (mTLS), where both sides present certificates, or with a signed token such as a JWT from OAuth2 client credentials. Then each service authorises the call, checking that this caller may do this action.

mTLS gives encryption plus strong service identity, with certificates usually issued and rotated by a mesh or platform. Client-credentials tokens carry scopes and work across networks, and I cache them until they expire. I often use both: mTLS for transport identity and a token for the user context and fine-grained permissions. Network policies then limit which pods can talk at all. Secrets such as keys and passwords come from a secret manager, never from Git or images.

Three questions every internal call must answer

  1. Is the channel private? TLS, so nobody on the network can read or change the traffic.
  2. Who is calling? Service identity: mTLS certificate or a signed token for the calling workload.
  3. Is this caller allowed to do this action on this data? Authorisation, inside the called service.

Defence in depth

  • Network policies (default deny, allow only needed paths), so a compromised pod cannot reach everything.
  • Least-privilege credentials per service (its own DB user, its own cloud role).
  • Secrets in a vault or the platform secret store, rotated, not in images or Git.
  • Audit logging of who called what.

Common failure: trusting the gateway and skipping authorisation inside services. One misrouted internal call, or a compromised service, then reaches everything.

Remember: encrypt, authenticate the caller (mTLS or token), then authorise per service.

Explain OAuth2 and JWT in the context of APIs. Which flows do you use, and should a service pass the user's token on? Intermediate

OAuth2 is a framework for getting an access token that lets a client call an API on a user's behalf, or on its own behalf, without sharing passwords. For browser and mobile apps I use authorization code with PKCE. For service to service I use client credentials. A JWT is a common token format: three base64 parts, header, claims and signature, which the API validates locally using the issuer's public key.

A JWT is signed, not encrypted, so anyone can read the claims and no secrets belong in it. The API must check the signature, the issuer (iss), the audience (aud), the expiry (exp) and the scopes, and must reject alg: none. Keep access tokens short-lived (minutes) and use refresh tokens to renew. The catch with JWT is that you cannot revoke one before it expires, so keep lifetimes short, or check a deny list for sensitive actions. The implicit flow and the password grant are deprecated.

When service A calls B on behalf of a user, there are two choices. Passing the user's token on keeps the user identity, but B then trusts every token A holds (risky, and the audience is wrong). A better way is token exchange, giving B a token with the right audience and the user as subject, or A calls with its own client credentials and passes the user id as context for B to authorise.

The authorisation code with PKCE flow, step by step

  1. The app generates a random code_verifier and sends its hash (code_challenge) with the user to the authorisation server's login page.
  2. The user logs in there (the app never sees the password) and consents.
  3. The server redirects back to the app with a short-lived one-time code.
  4. The app sends the code plus the original code_verifier to the token endpoint. The server checks that the hash matches, which proves the same app that started the flow is finishing it, so a stolen code is useless.
  5. It returns an access token (minutes) and usually a refresh token. The app sends Authorization: Bearer <access_token> to the API.

Client credentials is simpler: a backend service posts its client id and secret (or a signed assertion) to the token endpoint and gets a token for itself, with no user involved.

Anatomy of a JWT, and what the API must check

header   {"alg":"RS256","kid":"key-2024-1"}
claims   {"iss":"https://login.example.com","sub":"user-7","aud":"orders-api",
          "exp":1735689600,"scope":"orders:read orders:write"}
signature  = sign(base64(header) + "." + base64(claims), issuer private key)
  • Verify the signature with the issuer's public key (fetched from its JWKS endpoint, cached, selected by kid), and fix the allowed algorithm yourself.
  • Check iss is your issuer, aud is this API, exp and nbf are valid (allow tiny clock skew).
  • Check scopes or roles for the action, then still check object-level ownership in the code.

Opaque versus JWT, and revocation

An opaque token is a random string that the API checks by calling the authorisation server's introspection endpoint. It is revocable instantly but adds a call per request (cache it briefly). A JWT is checked locally and is fast but cannot be recalled before exp. Mitigate with short lifetimes, refresh token rotation, and a small deny list for high-risk events such as password change. Do not store tokens in browser local storage if XSS is a risk; a backend-for-frontend with an HttpOnly cookie is safer for browser apps. Note that OAuth 2.1 is a draft; PKCE for all clients and no implicit or password grants are the current best practice.

Remember: code plus PKCE for users, client credentials for services; JWT is signed, not secret; validate iss, aud, exp.

6. REST design basics

What is REST, and what makes an API RESTful? What does "stateless" mean? Basic

REST is an architectural style where the API is built around resources (things like orders and customers) identified by URLs, and manipulated with the standard HTTP methods. The key constraints are a uniform interface, client-server separation, statelessness, cacheability and layering. Stateless means every request carries everything the server needs, so the server keeps no session between requests.

Stateless matters because any instance can serve any request, which makes load balancing and scaling trivial and lets instances die without losing a user. The state goes to the client (a token), or to a shared store such as a database or Redis, never to the memory of one server. In practice, most "REST" APIs are really HTTP and JSON APIs with resource URLs, which is fine. The fully RESTful part many skip is hypermedia (HATEOAS).

The six constraints in plain words

  • Client-server: UI and data storage are separate concerns and evolve independently.
  • Stateless: each request is self-contained. The server does not remember the previous one.
  • Cacheable: responses say whether they may be cached, so repeated reads are cheap.
  • Uniform interface: resources are identified by URLs, handled by representations (JSON), manipulated by standard methods, and self-descriptive messages. The last part is hypermedia as the engine of application state (HATEOAS): responses contain links to next actions.
  • Layered system: proxies, gateways and caches can sit in between, invisibly.
  • Code on demand (optional): server can send executable code, rarely used.

Stateless, with before and after

Stateful (bad for scaling): POST /login creates a session in server memory, then GET /cart works only if the load balancer sends you to the same server again (sticky sessions). If that server restarts, the user is logged out.

Stateless: the login returns a signed token. Every request sends Authorization: Bearer ..., and any of 20 instances can validate it and answer. State that must persist (the cart) lives in a shared database or Redis, keyed by user. This is what makes autoscaling and rolling restarts painless.

Note "stateless" refers to the protocol conversation, not to the application having no data. A REST API is happily backed by a database.

REST versus RPC-over-HTTP

If your API is POST /doSomething with action names in the body, it is RPC using HTTP as a tunnel. That can be fine (gRPC is RPC), but it loses caching, tooling and uniformity. Be ready to say "Richardson maturity model": level 0 one endpoint, level 1 resources, level 2 HTTP verbs and status codes (where most real APIs sit), level 3 hypermedia.

Remember: resources plus HTTP verbs plus stateless requests. Any server can answer any call.

How do you design resource URLs? Give examples of good and bad ones. Basic

URLs name things (nouns, usually plural), and the HTTP method says the action. So GET /orders/42 and POST /orders, never /getOrder or /createOrder. I use hierarchy for real ownership, like /orders/42/items, and keep nesting to about two levels.

GOOD  GET    /customers/7/orders?status=open&limit=20
GOOD  POST   /orders              -> 201 Created, Location: /orders/42
GOOD  DELETE /orders/42
BAD   POST   /createOrder
BAD   GET    /orders/42/delete
BAD   GET    /getAllOrdersForCustomer?id=7

For actions that do not fit CRUD, model the action as a sub-resource or a state change: POST /orders/42/cancellation or POST /orders/42/cancel, which is pragmatic and fine. Use lowercase and hyphens, keep ids opaque, and do not leak database details. Filtering, sorting and paging go in query parameters, not the path. Never put sensitive data in URLs, since they end up in logs.

A small design walkthrough

Requirements: customers place orders, orders have items, an order can be cancelled and paid. The resource model:

/customers                    collection
/customers/7                  one customer
/customers/7/orders           that customer's orders
/orders                       all orders (admin, or filtered)
/orders/42                    one order
/orders/42/items              line items of order 42
/orders/42/items/3            one item
/orders/42/payment            the payment of this order (a singleton sub-resource)
/orders/42/cancellation       POST creates a cancellation (an action as a noun)

Rules and the reasons behind them

  • Plural nouns for collections: consistent and predictable: /orders and /orders/42.
  • Shallow nesting: /orders/42/items is good. /customers/7/orders/42/items/3/options/9 is a maintenance burden; give deep items their own top-level path and a filter instead.
  • Query parameters for filtering, sorting, paging, field selection: /orders?status=open&sort=-createdAt&limit=20. They are not part of the identity of the resource.
  • Stable, opaque ids: do not expose sequential database keys if enumeration matters (use UUIDs or ULIDs), and do not rely on ids for security.
  • Consistent casing: lowercase with hyphens in paths, one convention for JSON fields (camelCase or snake_case), not both.

The RPC-like exceptions

Not everything is CRUD. For "calculate shipping", "send", "convert", a verb-like endpoint is acceptable if you keep it consistent: POST /orders/42/cancel or POST /shipping-quotes. The test: is the action creating a thing (a quote, a cancellation record) you can later fetch? Then name that thing. If not, a clear action sub-path is more honest than a contorted noun. Avoid putting secrets, tokens or personal data in URLs because they get written to access logs, proxies and browser history.

Remember: nouns in the URL, verbs in the method; plural collections, shallow nesting.

Which HTTP methods are safe and which are idempotent? Why does it matter? Basic

Safe methods do not change server state: GET, HEAD, OPTIONS. Idempotent methods give the same end state if repeated: GET, HEAD, OPTIONS, PUT and DELETE. POST and PATCH are not guaranteed idempotent. It matters because clients, proxies and retry libraries may automatically repeat idempotent requests after a timeout, but must not blindly repeat POST.

MethodSafeIdempotentTypical use
GETyesyesread
PUTnoyesreplace whole resource
DELETEnoyesremove
POSTnonocreate, run action
PATCHnonot guaranteedpartial update

Idempotent means the server state ends the same, not that the response is the same: a second DELETE may return 404 while the first returned 204. Never change state with GET, since crawlers, prefetchers and caches fire GETs freely. To make POST safe to retry, add an idempotency key (see below).

Definitions with examples

  • Safe: the client does not ask for, and the server does not promise, any state change. Calling GET /orders/42 a hundred times changes nothing (logging and counters aside).
  • Idempotent: sending the identical request N times leaves the server in the same state as sending it once. PUT /users/7 with the same body ten times gives the same user. DELETE /orders/42 repeated still ends with the order gone.

Safe implies idempotent, not the other way round: DELETE is idempotent but not safe.

Why this affects real behaviour

  • Automatic retries: an HTTP client, a proxy or a service mesh may resend a request after a connection reset. It is only safe to do so for idempotent methods. A retried POST /payments can charge twice.
  • Prefetch and crawlers: browsers, link previews and search bots fire GETs. A GET like /orders/42/cancel in an email link would be triggered by a virus scanner that follows links.
  • Caching: only safe responses (mostly GET and HEAD) are cached by default.

Subtle cases an interviewer probes

First, a PATCH {"op":"add","path":"/tags/-","value":"x"} appends each time, so it is not idempotent, while {"status":"shipped"} is. Second, PUT is idempotent in effect but a PUT that also sets updatedAt = now() changes the stored timestamp each time; the business state is the same, so it is still considered idempotent, but be clear about what you mean. Third, idempotent does not mean the response is identical: DELETE gives 204 first and 404 second. Fourth, for POST you create idempotency yourself with a key header, described in the idempotency-key question below.

Remember: GET never changes data; PUT and DELETE are repeatable; POST is not, unless you add a key.

What is the difference between PUT and PATCH, and when do you use POST versus PUT to create? Basic

PUT replaces the whole resource with the body I send, so omitted fields are cleared, and it is idempotent. PATCH changes only the fields I send. To create, I use POST on the collection when the server chooses the id (POST /orders returns 201 with a Location header), and PUT on a known URL when the client picks the id (PUT /files/report.pdf).

PATCH comes in two formats. JSON Merge Patch (RFC 7396) sends just the changed fields, and null means remove, which is simple but cannot express "set to null" versus "remove". JSON Patch (RFC 6902) sends a list of operations like {"op":"replace","path":"/email","value":"x"}, which is precise and can be conditional. A partial PATCH can be idempotent or not depending on the operation (setting a field is, appending to an array is not). PUT with a full body is simple but wasteful and risks overwriting a field the client does not know about, so pair writes with ETag and If-Match.

PUT versus PATCH with the same user record

Stored: {"id":7,"name":"Asha","email":"a@x.com","phone":"555"}. The client wants to change only the email.

PUT /users/7   {"name":"Asha","email":"new@x.com"}
  -> phone is now gone (the body replaced the resource)

PATCH /users/7 (merge patch)  {"email":"new@x.com"}
  -> name and phone stay as they were

PATCH /users/7 (JSON Patch)   [{"op":"replace","path":"/email","value":"new@x.com"}]
  -> same effect, but explicit

That "phone is gone" example is exactly the lost-field risk: an old client that does not know the phone field would erase it with PUT. PATCH avoids that. Use PUT when clients always hold the full representation (a settings document), and PATCH for field-level edits on large or evolving resources.

Which HTTP status codes do you use and when? Basic

The class tells who is at fault: 2xx success, 3xx redirect or cached, 4xx the client got it wrong, 5xx the server failed. I use 200 for a successful read or update, 201 with a Location header on create, 204 for success with no body, 202 for accepted but not finished, 400 for a malformed request, 401, 403, 404, 409 for a conflict, 422 for a semantic validation failure, 429 for rate limiting, 500 for a server bug, and 502, 503, 504 for upstream trouble.

How to decide quickly

Ask three questions in order. Did the request succeed? Use 2xx, and pick the precise one: created (201), nothing to return (204), accepted but not done (202). If not, is it the caller's fault? Use 4xx and say which kind: cannot parse (400), not logged in (401), not permitted (403), no such thing (404), clashes with current state (409), fails business rules (422), too fast (429). If the server is at fault, use 5xx: 500 for our bug, 502 for a bad answer from upstream, 503 for overload or maintenance (with Retry-After), 504 for upstream timeout.

A short worked example

POST /orders  {...valid...}                -> 201 Created, Location: /orders/42
POST /orders  {...bad json...}             -> 400 Bad Request
POST /orders  {"qty": -3}                  -> 422 Unprocessable Content
POST /orders  (no token)                   -> 401 Unauthorized
POST /orders  (token lacks scope)          -> 403 Forbidden
GET  /orders/999                           -> 404 Not Found
POST /signup  {email already registered}   -> 409 Conflict
POST /reports (takes minutes)              -> 202 Accepted, Location: /jobs/55
GET  /orders/42  If-None-Match: "v3"       -> 304 Not Modified (no body)

Why it matters beyond style

  • Clients and retry libraries decide on the code: 4xx is never retried, 503 and 429 are.
  • Monitoring computes error rates from 5xx. A 200 with an error body hides outages. A flood of 4xx caused by a client bug should not page the on-call, while 5xx should.
  • Caches and CDNs treat codes differently (404 can be cached briefly, 5xx should not).

Two details: 301 and 302 may turn a POST into a GET on redirect, while 307 and 308 keep the method. And for 204 and 304 there must be no body. Do not invent codes or abuse 418 in production.

Remember: 2xx worked, 4xx you fix it, 5xx we fix it. Never hide errors inside a 200.

What is the difference between 401 and 403, and when do you return 404 instead? Basic

401 means "I do not know who you are": the credentials are missing, expired or invalid. The name is misleading, it really means unauthenticated. 403 means "I know who you are, but you are not allowed to do this". I return 404 instead of 403 when I do not want to reveal that a resource exists, such as another tenant's order.

A 401 should include a WWW-Authenticate header, and the client can fix it by logging in or refreshing the token. A 403 cannot be fixed by logging in again. The 404 trick prevents attackers from probing which ids exist, and is common in multi-tenant APIs. Authorisation must be checked on every object, not only on the endpoint: changing /orders/42 to /orders/43 and getting someone else's data is the top API vulnerability (broken object-level authorisation).

The sequence of checks inside an API

  1. Authenticate: is there a valid token? If not, 401 with WWW-Authenticate: Bearer. The client should obtain or refresh credentials and try again.
  2. Authorise the action: does this identity have the scope or role for this operation (orders:write)? If not, 403.
  3. Authorise the object: may this user touch this specific record? If order 43 belongs to another customer, return 403 or, to avoid revealing it exists, 404.

Choosing between 403 and 404 for object access

Returning 403 for "that order belongs to someone else" confirms the order exists, which lets an attacker enumerate valid ids. Returning 404 gives away nothing. The trade-off is slightly more confusing debugging for legitimate users (a developer sees 404 for something they know exists). A reasonable rule: use 404 for cross-tenant or private resources, 403 where existence is public but the action is not allowed (a read-only user trying to delete a visible resource).

Frequent mistakes

  • Returning 403 when the token is expired. That is 401, and a client library will not know to refresh.
  • Returning 401 for wrong permissions, which causes a client to loop on login.
  • Doing the check only on list endpoints and forgetting direct-id endpoints. This is broken object level authorisation (BOLA, the top item on the OWASP API Security list). Prevent it by always loading data through the caller's scope (WHERE id = :id AND tenant_id = :tenant) rather than loading by id and then checking.
  • Different error text or timing for "no such user" versus "wrong password", which leaks which accounts exist.

Remember: 401 = who are you, 403 = you may not, 404 = hide that it exists.

400, 422 or 409: how do you choose for validation and conflict errors? Intermediate

I use 400 when the request cannot be parsed or has the wrong structure, 422 when it parses fine but fails business or field validation, and 409 when the request conflicts with the current state of the resource, like a duplicate email or an edit on a version that has moved on.

Many teams use 400 for all validation, which is also acceptable. What matters is being consistent and returning field-level details in the body. 422 comes from WebDAV but is now in RFC 9110. For optimistic locking failures, 412 Precondition Failed (when If-Match does not match) or 409 are both used. Whichever you pick, document it in the OpenAPI file.

How should an API return errors? What is problem+json? Intermediate

Return the right status code plus a consistent, machine-readable body. The standard is Problem Details (RFC 9457, formerly 7807) with media type application/problem+json, with fields type, title, status, detail and instance, and you can add your own, such as a field-error list and a trace id.

HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{ "type": "https://api.example.com/errors/validation",
  "title": "Validation failed",
  "status": 422,
  "detail": "2 fields are invalid",
  "traceId": "4bf92f3577b34da6",
  "errors": [ {"field": "email", "message": "must be a valid email"} ] }

Clients should switch on the stable type (or an error code), not on the human message. Never leak stack traces, SQL or internal hostnames. Spring 6 and Spring Boot 3 support this through ProblemDetail.

Why a standard shape helps

If every endpoint invents its own error JSON ({"err":"x"} here, {"message":"y","code":5} there), every client needs special code per endpoint, and a gateway or monitor cannot interpret errors. A single shape lets one error handler in the client work for the whole API, and lets docs describe errors once.

  • Never include stack traces, SQL, class names, internal hostnames or whether a user exists. Log those server-side under the trace id.
  • Do include a trace or request id so support can find the log line.
  • Keep 5xx messages generic ("Something went wrong, quote id 4bf9...") and 4xx messages actionable.
  • Use a single exception handler (@RestControllerAdvice in Spring) that maps exceptions to problem details, so no controller formats errors itself.

Remember: status code for machines, stable error type for programs, message for humans, trace id for support.

How do you paginate a large collection? Compare offset and cursor pagination. Intermediate

Offset pagination (?page=5&size=20 or LIMIT 20 OFFSET 100) is simple and allows jumping to a page, but it gets slower for deep pages and can skip or repeat rows when data changes between requests. Cursor (keyset) pagination returns "the 20 items after this position" using a cursor, which stays fast and stable. I use offset for small admin screens and cursor for large or fast-changing feeds.

Offset is slow because the database must read and throw away all the earlier rows, so cost grows with the offset. If a row is inserted while the user pages, items shift and show twice or vanish. Keyset uses the sort key itself, and needs a unique, indexed ordering, usually with a tie-breaker:

SELECT * FROM orders
WHERE (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 20;

The cursor is an opaque (often base64) token holding the last key, returned as next_cursor (or a Link header). The downside is no "jump to page 50" and no easy total count, which is itself an expensive query, so offer it only if needed. Always cap the maximum page size.

Seeing why offset drifts

A feed is sorted newest first, 20 per page. The client loads page 1 (items 1 to 20). Meanwhile 3 new items are inserted at the top. Page 2 is OFFSET 20, but every old item moved down by 3, so items 18, 19, 20 appear again at the start of page 2: duplicates. If instead 3 items were deleted, 3 items are skipped. A cursor avoids this because "after the item with key K" does not depend on how many items are before it.

Why offset gets slow

For OFFSET 100000 LIMIT 20 the database must walk and discard 100,000 rows, even with an index, so latency rises with page depth. Keyset pagination seeks straight into the index at the last seen key, so every page costs about the same. It needs an index matching the sort, for example (created_at DESC, id DESC), and the tie-breaker id so rows with identical timestamps are not skipped or repeated.

A response shape

The cursor is opaque to the client, which lets you change the internal key later without breaking anyone. Sign or at least validate it, so a client cannot craft an expensive or unauthorised query.

7. REST in depth: versioning, caching, concurrency and security

What are the ways to version a REST API, and which do you prefer? Intermediate

There are three common ways: in the URL (/v1/orders), in a header (API-Version: 2), or in the media type (Accept: application/vnd.example.v2+json). I prefer the URL for public APIs because it is visible, easy to route, cache and test in a browser. But the best strategy is to avoid new versions: evolve the API in backward-compatible ways, and cut a new major version only for real breaking changes.

URL versioning is blunt but practical. Header or media-type versioning keeps URLs stable and is considered purer, but it is harder to discover, cache and debug. Whichever you use, version the whole API rather than single endpoints, support at most two or three versions, publish a deprecation policy (announce, add Deprecation and Sunset headers, watch usage, then retire), and keep the shared business logic below a thin versioned layer so you do not fork the whole codebase.

The three styles side by side

URL pathGET /v2/orders/42Visible, easy to route at the gateway, cache and try in a browser or curlThe URL of the same resource changes; "v2" suggests the whole API moved
Custom headerAPI-Version: 2Stable URLsInvisible in links and logs, caches must Vary on it
Media typeAccept: application/vnd.example.v2+jsonPurist: versions the representation, not the resourceHardest to discover and test, tooling support is patchy
Date-based (Stripe style)Stripe-Version: 2024-06-20Each account pinned to a date; fine-grainedNeeds a lot of server compatibility code

What actually counts as a new version

Adding an optional field or a new endpoint is not a new version. Removing a field, changing a type, tightening validation or changing meaning is. The most useful discipline is to make non-breaking changes the default, so a new major version is rare (years, not months). Document the compatibility promise: "we may add fields and enum values, clients must ignore what they do not know".

How to run two versions without duplicating the system

Keep one domain core. The /v1 controllers and /v2 controllers are thin adapters that map to the same service layer, each with its own DTOs. Old versions are then mostly mapping code, cheap to keep. Log version usage per client, announce a deprecation date, send Deprecation and Sunset headers, email the top users, and only retire when traffic is near zero. For internal service APIs, prefer compatible evolution plus contract tests over URL versions, since you control all consumers.

Remember: URL version is the pragmatic choice; additive changes avoid needing a new version at all.

What is HATEOAS and the Richardson maturity model, and do you actually use them? Intermediate

HATEOAS means each response includes links to the actions available next, so a client follows links instead of building URLs from documentation. The Richardson model rates an API in four levels: 0 one endpoint, 1 resources, 2 proper HTTP verbs and status codes, 3 hypermedia (HATEOAS). Most real APIs stop at level 2, and I do too, except for pagination links and workflow links where they clearly help.

{ "id": 42, "status": "PENDING",
  "_links": { "self":   {"href": "/orders/42"},
              "cancel": {"href": "/orders/42/cancel", "method": "POST"},
              "pay":    {"href": "/orders/42/payment"} } }

The benefit is that the server controls the workflow: the "cancel" link simply disappears once the order has shipped, so clients need no duplicated business rules. The reason adoption stays low is that clients are usually written against documentation and an OpenAPI file anyway, and links add payload and tooling effort. Spring HATEOAS and formats like HAL support it.

The Richardson maturity model, with one example per level

LevelWhat it looks like
0One endpoint, one verb: POST /api with {"action":"getOrder","id":42} (like SOAP or simple RPC)
1Separate resources: POST /orders/42, but still using POST for everything
2Resources plus the right verbs and status codes: GET /orders/42 returns 200, POST /orders returns 201, missing returns 404
3Responses carry links that tell the client what it can do next

What the links buy you

With level 3, the order response for a shipped order has no cancel link. A client that shows a "Cancel" button only when the link exists never needs to copy the rule "orders can be cancelled until shipped". If the rule changes to "within 24 hours", only the server changes. URLs can also move (the server may point to a different host or path) without breaking clients that follow links rather than build URLs.

Why most teams stay at level 2

  • Developers read documentation and generate clients from OpenAPI, so they hard-code paths anyway.
  • Mobile and single-page apps usually know their screens, and a generic link-following client is rare.
  • No universal standard: HAL, JSON:API, Siren, Hydra all differ, and links add payload.

Where links are worth it: pagination (next, prev), long-running job status, and state-machine style workflows (order, approval) where available actions depend on state. Be honest in an interview: Roy Fielding, who defined REST, says an API without hypermedia is not truly REST, but "REST API" in industry commonly means level 2 and that is a defensible engineering choice.

Remember: level 2 (resources, verbs, status codes) is the practical default; links are a bonus.

How does HTTP caching work? Explain Cache-Control, ETag and conditional requests. Intermediate

The server tells caches how long a response is fresh with Cache-Control, and how to check it afterwards with an ETag validator. While fresh, the browser or CDN reuses the response with no network call. When stale, the client revalidates by sending If-None-Match: <etag>, and if nothing changed the server answers a small 304 Not Modified with no body.

  • max-age=60: fresh for 60 seconds. public allows shared caches (CDN), private only the user's browser.
  • no-cache: may store it but must revalidate every time. no-store: never store (sensitive data). The names are confusing, no-cache does not mean "do not cache".
  • ETag is a fingerprint of the response (a hash or version). Last-Modified with If-Modified-Since is the older timestamp version.
  • Vary: Accept-Language tells caches the response depends on that request header.

Freshness first, then validation

Think of two separate ideas. Freshness answers "do I even need to ask the server?" and is controlled by Cache-Control: max-age. Validation answers "I have a stale copy, is it still good?" and is controlled by ETag or Last-Modified. If a response is fresh, the cache replies instantly without any network. If stale, it sends a conditional request. A 304 means "your copy is current", saving the body bytes but not the round trip.

Which header for which situation

DataHeaderWhy
Versioned static asset (app.3f9a.js)public, max-age=31536000, immutableFilename changes when content changes, so cache for a year
Product catalogue read by manypublic, max-age=60 plus ETagOne minute of staleness is fine, CDN absorbs load
Personalised data (my cart)private, max-age=0, must-revalidate or no-cacheOnly my browser may store it, always check
Bank balance, tokensno-storeNever written to disk or shared caches

Details that matter

  • Which methods: GET (and HEAD) are cacheable by default. POST responses are rarely cached.
  • Vary: if the body depends on Accept-Language or Accept-Encoding, the cache needs Vary so it does not serve French to an English user. Never use Vary: * or Vary: Cookie on public content, because it destroys hit rates.
  • Shared cache danger: a response with user data marked public may be served to another user through a CDN. Use private or no-store, and check the Authorization header behaviour of your CDN.
  • Strong versus weak ETag: "abc" means byte-identical, W/"abc" means semantically the same. A cheap ETag can be the row's version column, so the server answers 304 without even building the body.
  • stale-while-revalidate lets a cache serve a slightly old response while refreshing in the background, hiding latency.

Ties to microservices: caching at the gateway or CDN for public reads, and a local cache or Redis in front of slow dependencies, each with an explicit expiry so a stale value cannot live forever.

Remember: max-age avoids the call; ETag with 304 avoids the body. no-store for secrets.

How do you stop two clients from overwriting each other's updates in a REST API? Senior

I use optimistic concurrency. The GET returns a version (an ETag, or a version number). The client sends the update with If-Match: <etag>. The server applies it only if the version still matches, otherwise it answers 412 Precondition Failed (or 409), and the client must re-read, merge and try again. No locks are held, so nothing blocks while a user is thinking.

Inside the service the same idea is a version column: UPDATE customer SET ..., version = version + 1 WHERE id = ? AND version = ?, and zero rows updated means someone else got there first (JPA gives this with @Version). Without it, last write wins and one editor's changes silently vanish. Require If-Match on PUT and PATCH (answer 428 Precondition Required if it is missing). Pessimistic locks across services or a distributed lock are fragile, because a client can crash while holding the lock.

The lost update, in numbers

Product 7 has price 100 and stock 10, version 5. Alice and Bob both load it. Alice changes the price to 120 and saves. Bob, who still sees price 100, changes the stock to 8 and saves the whole object. Without version checks Bob's PUT replaces the entire record and the price goes back to 100. Alice's change is silently lost, and nobody gets an error. With If-Match: "5", Bob's request is refused because the record is now version 6, so Bob re-reads, sees price 120, applies his stock change and saves again.

Optimistic versus pessimistic

Optimistic (version check)Pessimistic (lock first)
AssumptionConflicts are rareConflicts are common or costly
CostRetry on conflict, no waitingOthers wait, locks can be held too long or leak
Over HTTPNatural: ETag, If-Match, 412Awkward: lock endpoints, expiry, crashed clients
Use forAlmost all web and API updatesShort database transactions, a hot row such as a counter or inventory

In the service and database

-- JPA: @Version long version;  generates:
UPDATE product SET price = ?, stock = ?, version = version + 1
 WHERE id = ? AND version = ?;       -- 0 rows updated => OptimisticLockException => 409/412

Use the version column as the ETag ("6") for a cheap strong validator. For counters and stock, a conditional atomic update (SET stock = stock - 1 WHERE stock > 0) beats read-modify-write. The same pattern also protects you from client retries re-applying a stale edit. When a conflict occurs, return the current state (or a problem+json with the current version) so the client can merge automatically for non-overlapping fields, or ask the user to resolve. Distributed locks (Redis, ZooKeeper) are a last resort: they need fencing tokens, otherwise a paused process that lost its lock can still write.

Remember: send the version back with If-Match; stale version means 412 and a re-read.

How do you make a POST safe to retry? Explain idempotency keys, with the duplicate payment case. Senior

The client generates a unique key (a UUID) per logical operation and sends it in an Idempotency-Key header, reusing the same key on every retry. The server stores the key with the result in the same transaction as the work. If the same key comes again, it returns the stored result instead of doing the work again. A customer who double-clicks or a client that retries after a timeout then pays only once.

The server flow: look up the key; if there is a stored response, return it; if the key is in progress, return 409 or wait; otherwise run the operation and save key plus response atomically. The key table needs a unique constraint, because two simultaneous requests would otherwise both pass a "check then insert". Also store a hash of the request body, and reject (422 or 400) a reused key sent with a different body. Keep keys for a limited time such as 24 hours. Stripe popularised this header, and an IETF draft is standardising it.

The duplicate payment case, in full

  1. The user taps Pay. The app creates key K1 (a UUID) and calls POST /payments with Idempotency-Key: K1.
  2. The server charges the card and stores (K1, request hash, response) in the same transaction as the payment row. Then the network drops the response.
  3. The app times out and retries with the same K1.
  4. The server finds K1, sees the same request hash, and returns the saved 201 response. No second charge.

The key must be generated once per user intention and reused for each retry. Creating a new UUID on every attempt defeats the whole purpose, and is a very common bug.

Server states for a key

SituationResponse
New keyInsert as IN_PROGRESS, do the work, save the response, mark COMPLETE
Key exists and COMPLETE, same bodyReplay the stored status and body
Key exists and IN_PROGRESS (a parallel retry)409 Conflict (or 425), client retries shortly
Key exists, different bodyReject with 422 or 400: key reused for a different request

The insert of the key must use a unique constraint so two parallel requests cannot both start the work. If the process crashes while IN_PROGRESS, you need an expiry or recovery rule, and ideally the key row and the business writes are in one database transaction so there is no half state. For side effects outside your database (calling a card processor), pass your key on to them too, since their idempotency protects the call that your own transaction cannot cover.

Related, but different

The idempotency key dedupes a client retry of one request. It is not a general uniqueness rule: two genuinely different orders for the same cart should have different keys. For message queues the equivalent is the message id with an inbox table (earlier in this page).

Remember: same key means same result: save the key with the work, atomically, and compare the body.

What are the main security risks for a REST API and how do you defend against them? Senior

The biggest one is broken object-level authorisation: a user changes an id in the URL and reads someone else's data, so I check ownership on every object access, not just login. Other main risks are broken authentication, excessive data exposure, missing rate limits, mass assignment, injection and misconfiguration. The OWASP API Security Top 10 is the checklist.

  • Authentication: OAuth2 / OIDC, short-lived tokens, validate signature, iss, aud, exp. Never put tokens in URLs.
  • Authorisation: per object and per property. Deny by default. Do not rely on the UI hiding buttons.
  • Data exposure: return explicit response DTOs, not entities. Mass assignment: never bind the request straight to an entity, or a client can set isAdmin.
  • Input: validate type, size, range; parameterised queries; limit body size and page size.
  • Abuse: rate limits and quotas, per client. Always HTTPS, with HSTS.
  • Hygiene: no stack traces, generic login errors, audit logs, no secrets in logs.

What is CORS and why does it cause errors in browser calls? Intermediate

CORS (Cross-Origin Resource Sharing) is a browser rule: a page from one origin (scheme, host, port) may not read a response from another origin unless that server opts in with Access-Control-Allow-Origin. The error appears in the browser, not on the server, so tools like curl and Postman work fine. The fix is on the server: allow the specific origins that need access.

For non-simple requests (JSON content type, custom headers like Authorization, or methods like PUT and DELETE) the browser first sends a preflight: an OPTIONS request asking "may I?". The server answers with Access-Control-Allow-Origin, -Allow-Methods and -Allow-Headers, and Access-Control-Max-Age lets the browser cache that answer. With cookies you need Allow-Credentials: true and a specific origin, not *. CORS is not a security feature for your API: it protects users' browsers, and a malicious server-side client ignores it.

What the browser actually does

The same-origin policy stops script on https://app.example.com from reading responses from https://api.example.com (a different host, so a different origin). CORS is the controlled exception: the API replies with headers that say which origins may read it. The request often still reaches the server, but the browser hides the response from the page if the headers are missing, which is why you see the call in your server logs and a red console error at the same time.

A preflight, step by step

1. Browser: OPTIONS /orders
            Origin: https://app.example.com
            Access-Control-Request-Method: PUT
            Access-Control-Request-Headers: authorization, content-type
2. Server:  204
            Access-Control-Allow-Origin: https://app.example.com
            Access-Control-Allow-Methods: GET, PUT, DELETE
            Access-Control-Allow-Headers: authorization, content-type
            Access-Control-Max-Age: 600
3. Browser: PUT /orders/42  (the real request, now allowed)

"Simple" requests (GET or POST with basic headers and form-like content types) skip the preflight. A JSON body with Authorization triggers one, so every first call carries an extra round trip, which Max-Age reduces by caching.

Common mistakes

  • Using * together with credentials: not allowed by the browser, you must echo a specific origin and set Allow-Credentials: true.
  • Reflecting any incoming Origin back as allowed: this effectively disables the protection. Check against an allow-list.
  • Preflight blocked by the auth filter: OPTIONS requests carry no token, so the security layer must let them through to the CORS handler.
  • Setting CORS in both the gateway and the service, giving duplicate headers that the browser rejects. Set it in one place.
  • Thinking CORS protects the API. It does not: curl, scripts and other servers ignore it. Real protection is authentication, authorisation and CSRF defence (SameSite cookies, tokens).

The simplest way to avoid CORS entirely is to serve the front end and API under one origin, or proxy /api through the same host.

Remember: CORS is enforced by the browser; fix it with explicit allowed origins on the server; it is not API security.

8. REST, gRPC, GraphQL and special cases

Compare REST, gRPC and GraphQL. When do you pick each, and why REST outside and gRPC inside? Intermediate

I use REST for public and partner APIs because it is simple, cacheable, and works with any client. I use gRPC between internal services when I want speed, strict contracts and streaming. I use GraphQL when many different clients need different slices of data and I want to avoid over-fetching and many round trips.

RESTgRPCGraphQL

StrengthCaching, simplicity, toolingFast, small, streaming, deadlinesClient picks fields, one round trip
WeaknessOver/under-fetchingNot browser-native (needs gRPC-Web), hard to debug by eyeHTTP caching is hard, N+1 and expensive-query risks

gRPC's binary format and long-lived HTTP/2 connections give lower latency, but load balancing needs care because one connection carries many calls, so balance per request, not per connection. GraphQL's classic trap is the N+1 problem: a resolver for each item fires its own query, so you batch with DataLoader, and protect the server with query depth, complexity limits and persisted queries.

How each one works in a sentence, with an example

REST: GET /orders/42 returns the whole order representation the server decided on. gRPC: the client calls a generated method orderClient.getOrder(GetOrderRequest{id:42}) and the framework sends a compact Protobuf message over HTTP/2. GraphQL: the client posts a query naming exactly the fields it wants:

query { order(id: 42) { status customer { name } items { sku qty } } }

One round trip returns just those fields, even though they come from three backend services.

Why gRPC inside and REST outside

  • Inside you control both ends, so the strict .proto contract, generated clients in many languages, small binary messages, deadlines, streaming and HTTP/2 multiplexing pay off. Protobuf also has good rules for evolving schemas (add fields with new numbers, never reuse numbers).
  • Outside you do not control the clients. REST works in every browser, with curl, with every language and every API gateway, and its caching semantics are free. Debuggability by a person with a plain tool matters for partners.

Choosing, and the traps

They also combine: a GraphQL or REST BFF at the edge calling gRPC services behind it. Mention that REST versus gRPC is also about evolution: with gRPC a missing field returns a default value rather than an error, so make "unset" meaningful (use wrapper or optional types) to avoid silent bugs.

Remember: REST for outside, gRPC for fast inside, GraphQL for flexible clients. Batch GraphQL resolvers.

What is OpenAPI and how do you use it in practice? Intermediate

OpenAPI is a standard, language-neutral description of a REST API: paths, methods, parameters, schemas, responses and security, written in YAML or JSON. One file generates documentation (Swagger UI), client SDKs, server stubs, mock servers and request validation, and it is the base for contract and breaking-change checks.

There are two workflows. Design-first: write the spec, agree it with consumers, then generate stubs. It gives the best contract and lets frontend work start early. Code-first: annotate the code and generate the spec (springdoc-openapi in Spring Boot), which is quick, but the API can drift by accident. In CI I diff the new spec against the last released one with a tool such as oasdiff or openapi-diff, and fail the build on breaking changes. Describe error responses and examples too, not only the happy path.

What a spec looks like

openapi: 3.0.3
info: { title: Orders API, version: 1.2.0 }
paths:
  /orders/{id}:
    get:
      operationId: getOrder
      parameters:
        - { name: id, in: path, required: true, schema: { type: string } }
      responses:
        '200': { description: OK, content: { application/json: { schema: { $ref: '#/components/schemas/Order' } } } }
        '404': { description: Not found, content: { application/problem+json: {} } }
components:
  schemas:
    Order: { type: object, required: [id, status], properties: { id: {type: string}, status: {type: string, enum: [PENDING, PAID]} } }

What you do with it

  • Docs: Swagger UI or Redoc rendered from the file, always in sync with the API.
  • Clients and servers: generate typed SDKs (openapi-generator) and server interfaces, reducing hand-written mapping bugs.
  • Mocks: a mock server (Prism, WireMock from the spec) lets front-end teams start before the backend exists.
  • Validation: the gateway or a filter can reject requests and responses that violate the schema.
  • Breaking-change gate in CI: compare the spec on the branch to the last released one, and fail on removed fields or tightened types.
  • Linting: Spectral rules to enforce naming, error format and pagination conventions across teams.

Design-first versus code-first

Design-first fits public APIs and cross-team work: the spec is reviewed like code before anyone implements it, and it is the contract. Code-first is faster for internal services, but the generated spec describes what the code happens to do, including accidents. Whichever you choose, treat the spec as an artifact that must be correct: add examples, describe every error response, mark deprecated operations, and keep the version in info.version. Note that OpenAPI describes synchronous HTTP APIs; for events use AsyncAPI, and for gRPC the proto file is the contract.

Remember: the spec is the contract: generate from it or verify against it, and diff it in CI.

How do you design an API for a long-running operation, such as generating a report? Senior

I do not hold the HTTP request open. The client posts the job, the server validates it and answers right away with 202 Accepted and a Location header pointing to a status resource. The client polls that URL (or gets a webhook or event), and when the job is done the status points to the result. This keeps requests short and avoids timeouts at the gateway, load balancer and client.

POST /reports                 -> 202 Accepted
                                 Location: /reports/r-91
GET  /reports/r-91            -> 200 {"status":"RUNNING","progress":40}
GET  /reports/r-91            -> 200 {"status":"DONE","result":"/reports/r-91/file"}
                                 (or 303 See Other to the file)
DELETE /reports/r-91          -> cancel

Make job creation idempotent with an idempotency key, run the job from a queue so it survives a restart, and put a Retry-After hint on the status responses so clients do not hammer it. Return a failure state with a problem+json error, and expire old results. Polling is simplest, a webhook or Server-Sent Events avoids polling.

The flow from the client's side

  1. POST /reports with the parameters and an Idempotency-Key. The server validates, stores the job as QUEUED, publishes it to a queue, and returns 202 Accepted with Location: /reports/r-91. This takes milliseconds.
  2. A worker picks up the job, runs it (minutes), updates progress and then status.
  3. The client polls GET /reports/r-91. While running it gets 200 with a state and perhaps Retry-After: 5. When done, either the body includes a link to the result, or the server answers 303 See Other pointing at the result resource.
  4. If the user changes their mind, DELETE /reports/r-91 or POST /reports/r-91/cancel.

Choices for how the client learns it finished

MethodGoodBad
Polling the status URLSimplest, works everywhereWasteful if too frequent; use backoff and Retry-After
WebhookNo polling; good between serversNeeds a public receiver, signing, retries
SSE or WebSocketLive progress for a browser userOpen connections to manage
Email or notificationFor very long jobs where the user leavesNot for machine clients

Server-side details

  • The job record is the source of truth: id, owner, parameters, state (QUEUED, RUNNING, SUCCEEDED, FAILED, CANCELLED), timestamps, result location or error.
  • Authorise the status URL like any resource (only the owner may see it) and use unguessable ids.
  • Make workers idempotent and resumable, since a job may be picked up twice after a crash. Use a lease or heartbeat so stuck jobs are retried.
  • Store large results in object storage and return a time-limited signed URL, not bytes through your API.
  • Delete old jobs and results after a retention period.

Remember: 202 plus a status URL; job id out, result later; never keep the request open.

How do webhooks work, and how do you make them reliable and secure? Intermediate

A webhook is a callback: instead of the client polling, my service sends an HTTP POST to a URL the client registered when an event happens. To make it reliable I treat delivery as at-least-once: retry with exponential backoff on failures, include an event id so receivers can dedupe, and offer a way to replay missed events. To make it secure I sign each payload.

The sender signs the body with a shared secret (HMAC-SHA256) and sends the signature and a timestamp in headers. The receiver recomputes it, compares in constant time, and rejects old timestamps to stop replay attacks. Receivers should answer 2xx quickly and process asynchronously, so slow handlers do not cause timeouts and retries. As sender, set a short timeout, disable a consistently failing endpoint after many attempts, and protect against SSRF (a client registering an internal URL) by blocking private IP ranges.

A delivery, step by step

  1. The customer registers https://shop.example/hooks/orders and receives a signing secret.
  2. An order is paid. The sender writes an event row (id evt_123, type order.paid, payload) and queues a delivery. (Use the outbox so the event cannot be lost.)
  3. A worker POSTs the payload with headers X-Event-Id: evt_123, X-Timestamp: 1735689600 and X-Signature: sha256=..., computed as HMAC-SHA256 over timestamp + "." + body using the secret.
  4. The receiver verifies the signature in constant time and checks the timestamp is within, say, 5 minutes (stops replays), stores the event id (dedupes), returns 200 immediately, and processes the payload in the background.
  5. If the receiver returns non-2xx or times out, the sender retries with exponential backoff and jitter (for example over 24 to 72 hours), then marks the endpoint as failing, and alerts the owner or disables it.

Sender side responsibilities

  • At-least-once and unordered: say so in the docs. Include a monotonically increasing version or timestamp so receivers can ignore stale events, or tell receivers to fetch the current state from your API using the id in the event ("thin events").
  • SSRF protection: a customer could register http://localhost:8080/admin or a cloud metadata address. Resolve and check IPs, block private ranges, limit redirects, set short timeouts.
  • Visibility: a delivery log with response codes and a "resend" button in the dashboard, which makes support far easier.
  • Secret rotation: support two active secrets during a changeover.

Webhooks versus polling versus streaming

Webhooks are cheap and near-real-time for server-to-server notifications, but they put the burden of availability on the receiver. For guaranteed ordering and replay, consider offering an events API or a stream the receiver can read from at its own pace, as well as webhooks as a nudge.

Remember: webhooks are at-least-once: sign them, give them ids, retry with backoff, ack fast.

How do you push updates to clients: polling, long polling, SSE or WebSocket? Intermediate

Polling asks repeatedly and is simplest but wasteful. Long polling holds the request open until there is news. Server-Sent Events (SSE) is a one-way stream from server to browser over plain HTTP with automatic reconnect. WebSocket is a two-way persistent connection. I choose SSE for server-to-client updates like notifications and progress, and WebSocket when the client also sends frequent messages, such as chat or collaborative editing.

SSE is easy to scale and proxy-friendly, and reconnects with Last-Event-ID so no events are lost. WebSocket gives the lowest latency in both directions but needs sticky connections, heartbeats, reconnect logic and more care with load balancers and authentication. At scale, the number of open connections becomes the constraint, so connection handling is spread over several nodes with a shared pub-sub (for example Redis or Kafka) behind them. For rare updates, plain polling with a sensible interval is often enough.

Choosing with examples

  • "Your export is ready" or a progress bar: SSE, or even a 5-second poll.
  • Live order status, notifications, dashboards, stock price ticker for viewers: SSE.
  • Chat, multiplayer, collaborative editing, live cursor positions: WebSocket.
  • Updates every few minutes: polling with a conditional GET (ETag) is cheapest to build and run.

Scaling it

Each connected client holds an open connection and some memory, so one node handles tens of thousands, not millions. Run many nodes. When something happens on a backend, it must reach the node holding that user's connection, so publish it on a pub-sub channel (Redis, Kafka, NATS) that every connection node subscribes to, and each node forwards to its own clients. Authenticate when the connection opens and again on token expiry, apply per-user connection limits, send heartbeats to detect dead connections, and on reconnect let the client say what it last saw (Last-Event-ID in SSE, a cursor in WebSocket) so it can catch up without gaps. Remember that delivery over a push channel is best effort: the client should always be able to fetch the true state from the normal API.

Remember: SSE for one-way pushes, WebSocket for two-way chat, polling when updates are rare.

9. Real-life scenarios

Each one follows the same shape: the diagnosis in one line, what I check first, the fix, and how I stop it happening again.

One service becomes slow and within minutes the whole platform is down (cascading failure). What do you do? Senior

A slow dependency holds callers' threads until their pools are full, so the slowness spreads upward. I stop the bleeding first (shed load, disable the sick feature, roll back a recent deploy), then fix it properly with timeouts, circuit breakers and bulkheads so the next slow service stays contained.

Situation: Recommendations starts answering in 30 seconds instead of 50 ms. Product page calls it with no timeout, threads pile up, then the gateway and every service that calls the product page run out of threads.

Check first: traces and dashboards to find the first slow service (not the loudest one), thread pool and connection pool saturation, and what changed recently (deploy, config, traffic, database).

Fix: now: disable or fall back for the failing feature (feature flag), scale or restart only if it helps, roll back the change. Then: timeouts on every client, a circuit breaker with a fallback (hide recommendations), a separate thread pool for non-critical calls, bounded queues, and load shedding at the edge.

Prevent: load and chaos tests that make one dependency slow, an alert on thread-pool saturation, and a rule that every new remote call ships with a timeout and a fallback.

A minute-by-minute timeline

  1. 14:00 Recommendations' database has a slow query. Its latency goes from 50 ms to 30 s. It is still "up", which is the dangerous kind of failure, because a health check on port or process passes.
  2. 14:01 Product page has 200 threads. Each page view calls Recommendations without a timeout. At 100 page views per second, all 200 threads are stuck within 2 seconds.
  3. 14:02 Product page cannot answer anything, including calls that never touch Recommendations. Its health check may now time out, so Kubernetes marks pods unready, and the remaining pods take even more load.
  4. 14:03 Gateway threads wait on Product page, and the gateway fills up. Now login and checkout fail too. A non-critical widget has taken down the whole platform.

Stopping it, in priority order

  1. Restore service: flip a feature flag to hide the widget, or block the call at the gateway. Rolling back a recent change is the next best step. Restarting the healthy services alone does not help; they refill within seconds.
  2. Find the origin: follow traces from the slowest hop. The loudest alarms are at the top of the chain (Gateway), but the cause is at the bottom (Recommendations database).
  3. Fix the root cause (the slow query, a missing index, a bad deploy) while the protection holds.

The structural fix, layer by layer

MechanismWhat it does here
Timeout (200 ms)A call can occupy a thread for at most 200 ms, not 30 s
Circuit breakerAfter enough failures, calls are rejected instantly without waiting
BulkheadRecommendations may use at most 10 of the 200 threads

Load shedding / rate limitIf the whole thing is saturated, reject some requests early rather than fail all of them slowly

The lesson: classify dependencies as critical or optional. A failing optional dependency must degrade a feature, never the page. Back this with chaos testing: inject latency (not just errors) into one dependency in staging and verify the page still serves.

Remember: slow is worse than down. Timeout, break, isolate, degrade.

A customer was charged twice for one order. How did it happen and how do you fix and prevent it? Senior

Almost certainly a retry or a redelivery of a non-idempotent charge: the first call succeeded but the response was lost, or the message was delivered twice. I refund the duplicate, find the duplicate path in the logs, and fix it with an idempotency key stored together with the charge.

Situation: the Order service called Payment, the call timed out after the charge had gone through, the retry library repeated the POST, and Payment charged again. Other causes: a user double-click, or a broker redelivering the "charge" command.

Check first: the trace id for both charges: same order id, two Payment requests, how far apart in time, who sent them (user, retry, message redelivery). Check if the provider (card gateway) has the same idempotency concept.

Fix: refund the duplicate now. Then send an Idempotency-Key (derive it from the order id and attempt) and enforce it in Payment with a unique constraint written in the same transaction as the charge record. Pass the key on to the card provider too, so it dedupes as well. Disable the UI button after one click.

Prevent: make "retry safe" a design rule for every write endpoint and consumer, add a reconciliation job that finds duplicate charges per order, and test with duplicated and delayed messages.

Reconstructing the incident

Pull the logs by order id. A typical pattern looks like this:

10:00:00.100 Order -> Payment POST /charges  (order 42)            attempt 1
10:00:00.350 Payment: charged card, commit, 201                      (response in flight)
10:00:02.100 Order: read timeout (2 s), retry
10:00:02.150 Order -> Payment POST /charges  (order 42)            attempt 2
10:00:02.400 Payment: charged card again, 201

The charge succeeded within 250 ms, but Order's timeout was set slightly too tight or the network dropped the response. The retry library repeated a POST that had no idempotency key. The other common routes give the same symptom: the user double-clicked "Pay", two browser tabs, or a broker redelivered a ChargeRequested message after the consumer crashed before acknowledging it.

Fix and prevention in practice

  1. Contain: refund the duplicate (that itself must be idempotent: refund keyed on the charge id), notify the customer, and find all other duplicates with a query such as SELECT order_id, count(*) FROM charges GROUP BY order_id HAVING count(*) > 1.
  2. Key: build the idempotency key from something stable and unique per intent, such as "charge:" + orderId (one charge per order), not a random value created per attempt.
  3. Server: a unique constraint on (idempotency_key) or order_id in the charge table, written in the same transaction as the charge record. On a duplicate, return the original charge result.
  4. Provider: pass the same key to the card gateway, because your own database cannot protect an HTTP call that already left.
  5. UI: disable the button on click and show progress. This is a convenience, not the protection.
  6. Detect: daily reconciliation of orders against provider settlement files, alerting on any order with more than one successful charge.

An interviewer may probe "what if the first request is still running when the retry arrives?". The answer: the key row exists as IN_PROGRESS, so the second request gets a 409 (or waits) instead of starting a second charge.

Remember: a timeout does not mean the work failed. Retrying a write needs an idempotency key.

You deployed an API change and another team's service starts failing in production. What now, and how do you stop it happening again? Senior

Roll back first to restore service, then find what contract the change broke, and then fix it forward in a backward-compatible way. Afterwards I add contract tests so the provider's build fails for this kind of change.

Situation: I renamed customerName to name in a response. Billing still reads customerName and now gets null.

Check first: error rate and logs in the consumer, the diff of my release, and whether a rollback is safe (no data migration that cannot go back).

Fix: roll back (or redeploy with both fields). Redo the change as expand and contract: return both names, tell consumers, watch the usage of the old one, and remove it only when nobody reads it. For events, check compatibility with the schema registry.

Prevent: consumer-driven contract tests (Pact) in the provider pipeline, an OpenAPI diff check in CI, canary releases that watch consumer error rates, and the tolerant reader rule in consumers.

The first 15 minutes

  1. Confirm the link: error rate in Billing started right after your deploy time. Check the deploy log and the diff.
  2. Roll back now if it is safe: no data migration that older code cannot read. Restoring service beats understanding the cause. If a rollback is not possible, ship a hotfix that returns both customerName and name.
  3. Tell people: post in the incident channel, tell Billing's owners, so they do not debug their own code for an hour.
  4. Repair the damage: Billing received nulls for some time. Which records were produced wrongly (invoices without a name, failed events)? Re-run them idempotently once the contract is restored.

Order says PAID but the Inventory service never reserved stock. How did the data get inconsistent and how do you repair it? Senior

Probably a lost event or a failed saga step: the payment committed, but the event telling Inventory was never published (dual write), was lost, or Inventory failed and nothing compensated. I repair the affected orders from the source of truth and fix the cause with an outbox and idempotent consumers.

Situation: Payment saved "paid" and then published PaymentCompleted directly to the broker. The service crashed in between, so Inventory never heard.

Check first: is the event missing at the producer (no outbox row), in the broker, or failed at the consumer (in the DLQ or an error log)? Find all affected orders by comparing the two databases or the saga state table.

Fix: for existing orders, replay the events or run a repair job that triggers the missing reservation (idempotent, so it is safe to run twice), and refund or notify where stock is gone. Going forward, use the transactional outbox, idempotent consumers, a DLQ with alerts, and a saga with timeouts.

Prevent: a scheduled reconciliation job comparing the services, and an alert for sagas older than a set time.

How to find out where the chain broke

The flow should be: Payment commits "PAID", an event PaymentCompleted goes to the broker, Inventory consumes it and reserves stock, then publishes StockReserved. Walk the chain and ask at each point whether the evidence exists.

  1. Stop the bleeding: if it is still happening, fix or temporarily route around the broken link before repairing old rows.
  2. Build the list: query orders PAID with no reservation in Inventory (a cross-database comparison done through exports or the data warehouse, not by joining the live databases).
  3. Repair using the system's own idempotent commands: re-publish PaymentCompleted for each id, or call a reconcile endpoint. Do not edit Inventory's tables by hand.
  4. For orders that cannot be fulfilled (no stock left), run the compensation: refund and notify.
  5. Record what you did for audit.

Longer-term controls: outbox, inbox, DLQ with alert, saga timeout, and a scheduled reconciliation (every night, or every few minutes for money) that compares counts and statuses between services and raises an alert on mismatch. Assume some inconsistencies will always slip through, and make detection and repair routine, not heroic.

Remember: eventual consistency needs reconciliation. Outbox so events are not lost, idempotency so replays are safe.

Your team says "we have 25 microservices but every release needs five teams on a call". What is wrong and what do you do? Senior

That is a distributed monolith: the boundaries are wrong or the data and API coupling is too tight, so services cannot change independently. I map which services change together, merge or redraw those, give each its own data, and make interfaces backward compatible and contract-tested.

Situation: a typical feature needs changes in 5 services with a fixed deployment order, because they share a database or use lock-step API changes.

Check first: use Git history and release logs to find pairs of services that always change together, look for shared databases and shared libraries with business objects, and map the synchronous call chains.

Fix: merge the services that always move together (fewer, larger services are fine), split by business capability instead of by layer, remove shared tables with an API or events, adopt expand and contract and consumer contract tests so deploys do not need coordination, and pick one team as owner of each service.

Prevent: a design review for new boundaries, and a metric for "releases needing more than one team".

Gathering evidence before reorganising

Opinions about coupling are cheap, data is persuasive. Do this analysis:

  • Change coupling from Git: for the last 6 months, list pull requests or commits that touch more than one service repo, and count pairs. Pairs that show up together in 70 percent of changes are one service in disguise.
  • Release logs: how many releases had a mandatory ordering or needed more than one team? That is the metric to push down.
  • Data coupling: which services read tables they do not own (grep connection strings and queries, review database grants).
  • Runtime coupling: a trace-based dependency graph, showing synchronous call depth and fan-out per user request.
  • Code coupling: which shared libraries contain domain classes that change often.

After a short database outage, the service stays down for 30 minutes even though the database is back. Why? Senior

Typically a retry storm or a pile-up of work: during the outage clients kept retrying and queues grew, so when the database returned the flood of retries and backlog overloaded it again and the system never got to recover. I shed load, drain the backlog gradually, and add backoff with jitter, retry budgets and breakers.

Situation: every client retries three times with no jitter, three layers deep, so one failed request becomes up to 27 attempts. Connection pools are also exhausted and the pods are restarting in a loop.

Check first: request rate against normal, retry counts, queue depth, connection pool usage, and whether the readiness probe is flapping pods in and out.

Fix: now: reduce load (reject or rate limit at the edge, pause consumers, stop non-essential batch jobs), bring capacity back gradually, then let the backlog drain at a controlled pace. Later: retry at one layer only, exponential backoff with jitter, a retry budget, circuit breakers, bounded queues, and pool sizes that match what the database can take.

Prevent: a game-day that kills the database and watches the recovery, not just the failure.

Why recovery is harder than the outage

During the 2 minutes the database was down, three things piled up. First, clients kept retrying, so request counters rose. Second, message queues grew because consumers could not finish. Third, connection pools filled with dead connections, and some services restarted, losing their warm caches. When the database comes back, it sees a burst far above normal traffic: the backlog plus all clients retrying together plus cold caches. At that load it slows down, requests time out, and retries make it worse. The system sits in a stable bad state (a metastable failure) that does not clear on its own, because the extra load that triggered it keeps sustaining it.

A concrete bad arithmetic

Normal load 1,000 requests per second, database capacity about 1,500. During the outage 600,000 requests failed and queued. After recovery the database receives 1,000 normal plus retries at 3 attempts each (3,000) plus backlog drain at full speed. That is more than 4,000 requests per second against a capacity of 1,500, so it fails again, now with fresh retries on top.

Recovery playbook

  1. Cut the demand: rate limit or reject a share of traffic at the edge (return 503 with Retry-After), disable non-critical consumers and batch jobs, and scale clients down if they are the flood.
  2. Ramp up gradually: allow 10, 25, 50, 100 percent while watching latency and error rate. Warm caches and connection pools before full traffic.
  3. Drain the backlog slowly: run consumers at a limited rate, and drop messages whose result is no longer useful (stale requests).
  4. Check the probes: make sure readiness is not flapping and that liveness does not restart pods during the recovery.

Design that avoids it

  • Retries only at one layer, with exponential backoff and full jitter, and a retry budget.
  • Circuit breakers so clients stop sending to a database known to be down, with a gradual half-open probe on recovery.
  • Bounded queues and timeouts so backlog does not hold work that nobody wants any more (a request whose caller gave up long ago).
  • Connection pools sized for what the database can accept in total across all instances, not per instance.
  • A game day that includes the recovery phase, since this is where hidden loops show up.

Remember: recovery needs less load than normal. Shed first, ramp slowly.

Customers complain that orders stay in PENDING forever. How do you find and fix stuck sagas? Senior

Some saga step never completed or never reported back. I query saga state for orders stuck in PENDING beyond a time limit, find the step they are waiting on, and either retry it, compensate, or escalate. Then I add step timeouts so no saga can wait forever.

Situation: a reply event from Inventory was lost, the consumer crashed on a poison message, or an orchestrator instance died holding state in memory.

Check first: SELECT ... WHERE status='PENDING' AND updated_at < now() - interval '15 minutes', grouped by current step. Then check the DLQ, consumer lag, and error logs for that step, with traces by order id.

Fix: for each stuck order re-send the pending command (idempotent) or run the compensation and cancel. Fix the root cause (a poison message, a bug, a down consumer). Add a timeout per saga step with a defined action (retry N times, then compensate), keep saga state in a database, not memory, and alert on count of old PENDING orders.

Prevent: test the unhappy paths: lost reply, duplicate reply, slow reply.

  • Every step has a deadline. A watchdog (a scheduled job or a durable timer in Temporal or Camunda) wakes up on timeout and decides: retry the step up to N times with backoff, then compensate.
  • Saga state lives in the database with an updated timestamp and a version, so a restarted instance can resume any saga.
  • Commands are idempotent, so re-sending is always safe. Replies that arrive late for a saga already compensated are ignored (check the state before acting).
  • Expose a metric "sagas older than X minutes" and alert on it, plus an admin screen to inspect and manually push a saga forward or back.

Events arrive out of order: a "ProfileUpdated" event overwrote a newer value with an older one. What do you do? Senior

Ordering is only guaranteed within one partition or queue key, and retries and parallel consumers can reorder things. I make the consumer reject stale events: each event carries a version or timestamp for the entity, and the consumer applies it only if it is newer than what it already stored.

Situation: v7 of the profile was processed, then a delayed v6 arrived (a retry, or a different partition) and overwrote it.

Check first: is the event keyed by entity id (same key means same partition and order)? Are there multiple producers, or a retry topic that breaks order? Does the event carry a version at all?

Fix: add a monotonic version (or sequence) per entity at the producer, and a conditional write at the consumer: UPDATE profile SET ..., version=:v WHERE id=:id AND version < :v. Key messages by entity id. Use "state" events carrying the full latest state, so skipping an old one is safe, and keep delivery of one entity serial per partition.

Prevent: tests that shuffle and duplicate events.

How the reordering happens

Kafka guarantees order only within one partition, and only for messages sent by one producer on one connection without in-flight retry reordering. So reordering appears when: (a) messages for the same entity go to different partitions because the key was missing or different; (b) a producer retry sends message 6 after 7 succeeded (when idempotence is off and several requests are in flight); (c) a retry topic or DLQ replay delivers an old message later; (d) a consumer handles records of one partition in parallel with a thread pool; (e) two producers (two services, or an old and a new instance) emit versions of the same entity.

The consumer-side guard

UPDATE profile
   SET email = :email, name = :name, version = :v
 WHERE id = :id AND version < :v;      -- stale event: 0 rows updated, ignore it

-- first time we see this id: INSERT ... ON CONFLICT DO NOTHING (or upsert with the same guard)

The version must come from the producer, from the entity itself (the row's version or an event sequence number), because consumer arrival time or a wall clock timestamp from different machines can lie. If you must use timestamps, use the time the source database committed the change.

Design choices that make order less important

  • Full-state events ("ProfileUpdated carries the whole profile"): skipping a stale one loses nothing. Delta events ("EmailChanged") require every delta in order, so they need stricter handling.
  • Key by entity id so all events of one entity share a partition. Choose the number of partitions up front, because changing it later remaps keys.
  • Serial processing per key: parallelise across keys, never inside one key.
  • Producer settings: enable idempotence, and in Kafka that keeps order with retries when acks=all (and a limited number of in-flight requests, which modern clients handle for you).
  • Gap detection: with a sequence number per entity, a consumer that sees 5 then 7 knows 6 is missing and can wait or refetch the entity from the source API.

Remember: never assume order across keys. Version every event and ignore the stale.

You must rename a database column used by a service running with ten instances and zero downtime. How? Senior

I never rename in one step, because during a rolling deploy old and new code run at the same time. I use expand and contract in several releases: add the new column, write to both, backfill, switch reads, stop writing the old one, and only then drop it.

Check first: who reads the column (other services, reports, ETL jobs), and how long a rollback window I need.

Fix: (1) migration adds name alongside full_name. (2) Release A writes both and reads the old one. (3) Backfill old rows in small batches. (4) Release B reads the new column, still writes both. (5) Release C stops writing the old column. (6) Later, a final migration drops it. Each step is backward compatible with the one before, so rollback is always possible. Run migrations with Flyway or Liquibase and avoid long locks, such as a table rewrite, on a big table.

Prevent: a team rule that migrations must be compatible with both the old and new code version.

The reason for the multiple steps

During a rolling deploy with ten instances, for a few minutes some run release N (old code, expects full_name) and some run N+1 (new code, expects name). A single-step rename breaks one group immediately: either the old code gets "column not found" or the new code does. The same logic applies to a rollback, where you go back to old code after the schema changed.

Operational details that matter at scale

  • Backfill in batches (for example 1,000 rows per transaction with a short pause), not one huge UPDATE that locks the table, floods replication and blows up the transaction log. Make it resumable.
  • Locks: adding a nullable column is usually cheap, but adding a column with a default, creating a non-concurrent index, or changing a type can rewrite the table or block writes in some databases and versions.   • Verify before contract: check that no query still touches the old column (database statistics, query logs, other services and reports), and keep a rollback window before the drop. The drop is the one irreversible step, so take a backup.
  • Tools: Flyway or Liquibase run versioned migrations on deploy. Prefer running migrations as a separate step before the app rollout, so ten instances do not race to migrate.

The principle generalises: every change to a shared contract (column, API field, event schema) is split into additive steps, each compatible with the previous and next version of the code.

Remember: expand, migrate, contract. Old and new code run side by side during any deploy.

One customer's batch job floods your API and other customers see timeouts. What do you do? Senior

This is a noisy neighbour. I apply per-client rate limits and quotas so one tenant cannot take all the capacity, return 429 with Retry-After for the excess, and isolate heavy traffic into its own pool or queue. Then I talk to the customer about a bulk API.

Check first: metrics broken down by tenant or API key: who is sending, which endpoint, how many requests per second, and what resource saturates (threads, database connections, CPU).

Fix: now: temporarily throttle that key at the gateway. Longer term: token-bucket limits per tenant (and per endpoint for expensive calls), bulkheads or separate worker pools for batch work, a fair queue, and an asynchronous bulk endpoint (202 plus a status URL) so large jobs do not use the interactive path. Make clients back off by honouring Retry-After.

Prevent: usage dashboards per tenant, and quotas written into the plan.

Confirming and containing it

First confirm that it is one tenant. Break the request rate and latency down by API key or tenant id. A typical result: tenant 88 sends 4,000 requests per second to /orders/search while all others together send 800. The database CPU is at 95 percent and the connection pool is full, so everyone queues. Containing it quickly: at the gateway, set a temporary limit for key 88 (for example 200 requests per second) and return 429 with Retry-After for the rest. Contact the customer with data: what they sent and when.

Giving the customer a better path

A batch job that makes thousands of small calls wants a bulk API: POST /orders/bulk or an asynchronous import returning 202 and a job id, or a data export feed. This reduces overhead for both sides. Also help the client behave well: publish rate limit headers, document limits per plan, and make clients honour Retry-After with backoff and jitter.

Remember: limit per tenant, not globally. Give heavy users a bulk path of their own.

Two support agents edit the same customer record and one agent's changes silently disappear. How do you fix it in the API? Intermediate

That is the lost update problem: both read version 5, both wrote, and the last write won. I add optimistic locking: the GET returns an ETag or version, updates must send it in If-Match, and a stale version gets 412, so the second agent sees a conflict instead of silently overwriting.

Check first: is there any version on the record? Do updates replace the whole object (PUT) or only the changed fields (PATCH)? Using PATCH with changed fields only already reduces the clash, but not for the same field.

Fix: add a version column (JPA @Version), expose it as an ETag, require If-Match on PUT and PATCH (428 if missing), return 412 on a mismatch, and have the UI show "this record changed, here are the differences".

Prevent: make the conflict message friendly, and audit changes so lost data can be recovered.

Reproducing and fixing it in code

The symptom is easy to reproduce with two terminals: both GET customer 7 (version 5), agent A changes the phone number and saves, agent B changes the address and saves the full record. B's save carries the old phone number, so A's change vanishes. There was no error and nothing in the logs, which is why the data seems to "disappear".

GET  /customers/7        -> 200  ETag: "5"   {...}
PUT  /customers/7        If-Match: "5"    {...A's edit...}   -> 200 ETag: "6"
PUT  /customers/7        If-Match: "5"    {...B's edit...}   -> 412 Precondition Failed
                                                          (body: current version and data)

Choices when a conflict happens

  • Reject and reload: simplest. B sees "this record changed", reloads and re-applies the edit. Fine for small forms.
  • Field-level merge: if A changed the phone and B changed the address, the changes do not overlap, so the server or the UI can merge them. Use PATCH with only changed fields plus a version, and merge when fields differ.
  • Show a diff and let the user decide in a three-way merge for the same field.

Implementation notes

  • With JPA/Hibernate, annotate a long version with @Version. Spring Data surfaces the failure as an optimistic locking exception, which you map to 409 or 412 in your exception handler.
  • Do not rely on a timestamp as the version if its resolution is coarse; two updates within the same millisecond or second would pass the check. A counter is safer.
  • Apply the same check inside the service when it updates in a loop or from a message, since the lost update can come from internal code too.
  • Add an audit table or history so any overwritten value can be recovered during support.
  • For counters and stock, use atomic updates (SET qty = qty - 1) rather than read, change and write back.

Remember: read version, write with that version, reject if it moved.

A list endpoint was fast in testing but times out in production with a big customer. How do you investigate and fix it? Intermediate

Test data was small. In production, the query probably scans too many rows, has no index for the filter and sort, uses deep offset paging, or hits an N+1 query pattern. I measure first with a trace and the query plan, then fix the index, switch to cursor pagination, cap page size, and fix N+1.

Check first: the trace to see where the time goes (database, a downstream call, serialisation), the actual SQL and its EXPLAIN plan for that customer, and the number of queries per request (one per row is the N+1 sign).

Fix: add a composite index matching the filter and sort order; replace OFFSET with keyset pagination; enforce a maximum page size (say 100) and return fewer fields; fix N+1 with a join fetch or a batch query; avoid COUNT(*) over millions of rows on every call; cache stable results. If the query is truly heavy, move it to a read model or search index, or make it an asynchronous export.

Prevent: load-test with production-sized data for the biggest tenant, and alert on slow queries.

An investigation in order

  1. Reproduce with the big tenant's data (or a masked copy). Test data of 200 rows hides everything that matters.
  2. Look at the trace: which span dominates? If it is the database span, go to SQL. If it is many short calls to another service, it is an N+1 across the network. If it is the serialisation, the response is simply too big.
  3. Count queries per request. One query to load 50 orders plus 50 queries to load each order's customer is 51 queries (N+1). Hibernate's statistics, a SQL log, or the APM tool shows this.
  4. Run EXPLAIN (ANALYZE) on the slow query with the tenant's parameters. Look for a sequential scan over millions of rows, a sort that spills to disk, or a large offset.

Then verify under load with production-sized data, and compare p95 and p99, not the average. Add a slow query log threshold and an alert, plus a test or lint rule that fails when an endpoint returns an unbounded list. A frequent interview probe: "how do you know an index is used?". Answer: the plan shows an index scan or index-only scan, and the buffers and rows read drop sharply.

Remember: measure first. Usual culprits: missing index, deep offset, N+1, unbounded page size.
