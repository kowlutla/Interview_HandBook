How to use this page

Every question is a collapsible. Try to answer out loud first, then open it. In a design interview the storage choice is rarely judged on the product name. It is judged on whether you start from the access pattern (what is read and written, how often, how big, how consistent) and then pick the store that makes those operations cheap. Practice phrasing: "The workload is X, so the dominant operation is Y, which suggests Z, and the cost I accept is W."

Choosing a database

How do you choose a database for a new system? Basic

In one line: I start from the workload (what is read and written, how often, how big, how consistent), not from a product name, and I default to a relational database unless a requirement forces something else.

Why this matters. Every database is a set of trade-offs. Postgres is great at flexible queries and transactions but has one write primary. Cassandra is great at huge write volume but cannot join. If you pick the product first, you discover the trade-off in production. If you pick the access pattern first, the product choice almost falls out by itself.

Ask these questions in order:

  1. Data shape and relationships: rows with joins, nested documents, a graph, a time series, large blobs? A shape that fits badly into tables (a social graph, a metric stream) is an early hint to go elsewhere.
  2. Access patterns: only "get by key"? Range scans? Ad hoc queries on any column? Full-text? Aggregations over billions of rows? This is the single most important question, because each store makes only some operations cheap.
  3. Read/write ratio and volume: 100 writes per second or 500,000? How big is the data today and in three years? One node comfortably holds a few TB and tens of thousands of simple operations per second; beyond that you need partitioning.
  4. Consistency needs: may two users briefly see different values (a like counter), or is this money or inventory where a stale read causes a real loss?
  5. Latency and availability targets: single-digit milliseconds? Must it survive the loss of a whole region?
  6. Operational reality: what does the team already run, back up and debug well? A boring database you know beats an exotic one you do not.

A tiny worked example. "Shopping cart for 20 million users." Dominant operation: get and put the whole cart by user id. No joins, short-lived data, must always accept writes. Answer: a key-value store (DynamoDB or Redis with persistence). Now "monthly revenue report by region": big scans and aggregations over many rows, so a column store or warehouse. Same company, two different answers, because the access patterns differ.

Say: "Default to a relational database unless a requirement forces otherwise: scale beyond one primary, a very simple access pattern at huge volume, or a data shape that fits badly into tables. The workload is X, so the dominant operation is Y, which suggests Z, and the cost I accept is W."

What an interviewer probes next: "What would make you change your mind?" Good answers name a measurable trigger (write rate above what one primary sustains, working set larger than RAM, analytics hurting OLTP), not a vague "when it gets big".

SQL versus NoSQL: how do you decide? Basic

In one line: pick SQL when data is relational, queries vary and integrity matters; pick a NoSQL family member when the access pattern is narrow and known, or volume exceeds one primary, or the shape is a document, graph or time series.

What the words mean. A relational (SQL) database stores data in tables with a fixed schema, links them with foreign keys, lets you ask any question with joins, and gives multi-row ACID transactions by default. "NoSQL" is not one thing; it is a family of stores (key-value, document, wide-column, graph) that gave up some of those features to gain scale, flexibility or speed for a narrower job.

Relational (SQL)NoSQL (broad family)
ModelTables, foreign keys, joinsKey-value, document, wide-column, graph
SchemaEnforced up front by the databaseOften flexible, enforced by the application
QueriesAd hoc, any column, joinsDesigned around known access patterns
TransactionsMulti-row ACID is the defaultOften single-key or single-partition only (varies by product)
ScalingVertical plus read replicas; sharding is real workHorizontal partitioning is built in

The real difference is in how you design. In SQL you model the entities first and write queries later; the database figures out how to answer them. In most NoSQL stores you list the queries first and shape the data so each query is one cheap lookup. That is why a NoSQL store is fast for what you planned and painful for the question you did not plan.

Decision rule. Money, orders, inventory, anything with relationships and invariants: SQL. A narrow known pattern at very high volume (sessions, carts, event logs, messages): NoSQL. Genuinely unsure: SQL, because you can always ask a new question later.

"NoSQL scales, SQL does not" is a myth. A well-tuned Postgres or MySQL handles tens of thousands of transactions per second on one node, and many large companies run sharded MySQL. The honest statement is that NoSQL makes horizontal scaling a built-in property, while SQL makes it your project.

Trap: choosing NoSQL "for scale" with 50 GB of data, and then needing joins, ad hoc reports and transactions. Choose by need, not fashion. The opposite trap also exists: forcing 2 million writes per second onto one Postgres primary.
When is a key-value store the right choice, and what are its limits? Basic

In one line: use a key-value store when every access is "get, put or delete by one key" and you want it in about one network hop; its limit is that you can only ask questions the key can answer.

What it is. A key-value store is a giant dictionary: a key maps to an opaque value (the store does not look inside it). Because the lookup path is so simple, it can be extremely fast, easy to partition across nodes (hash the key to pick the node), and highly available. Examples: DynamoDB, Redis, Riak, etcd (small config data).

Good fits. Sessions, shopping carts, feature flags, user profile by id, idempotency keys, rate-limit counters and caches. A concrete case: cart:user42 maps to a JSON blob of items. One GET loads the cart, one PUT saves it, and a thousand nodes can serve a million users because each user lives on exactly one partition.

Limits, and why they hurt.

  • You cannot ask "find all carts containing product 9" or "all users in Berlin" without building your own secondary index or scanning everything.
  • Very large values hurt (every read moves the whole blob, and many stores cap value size; DynamoDB items are limited to 400 KB, for example).
  • Cross-key transactions are limited or missing, so updating two users atomically is hard.
  • Updating one field inside the value means read-modify-write unless the store has atomic field operations.

Decision rule. If the product has one or two access paths and all are by key, key-value is ideal. If you find yourself adding a third and fourth access path, you are slowly rebuilding a database on top, and a document or relational store is the better fit.

What is a document database and when would you use it over relational? Basic

In one line: a document database stores self-contained JSON-like documents looked up by id; choose it over relational when an entity is read and written as one unit and its shape varies.

What it is. MongoDB, Couchbase, Firestore and DocumentDB store one document per entity, for example a whole order with its line items nested inside. You can index fields inside the document and query on them, but there are no cross-document joins in the relational sense (some offer limited lookups).

Why it exists. In a relational model, an order is spread across orders, order_lines, addresses, so rendering one order page needs a join of several tables. If you almost always read the order as a whole, it is cheaper and simpler to store it as one document so one read returns everything and one write saves it atomically.

{ "_id": "order-9001", "customer": "cust-42",
  "lines": [ {"sku": "A1", "qty": 2, "price": 9.99},
             {"sku": "B7", "qty": 1, "price": 24.00} ],
  "ship_to": {"city": "Pune", "pin": "411001"} }

The key design idea: embed or reference. Embed data that is always read together and is bounded in size; reference (store an id) data that is shared or unbounded. Details are in the embed-versus-reference question below.

Costs.

  • Duplicated data is harder to keep consistent (if a product name is copied into a million orders, renaming it is a big job).
  • Many-to-many relationships are awkward.
  • A document that grows without bound (a comment array with millions of entries) hits size limits and rewrites the whole document on each change.

Honest caveat. Postgres has a jsonb column type with indexing, so "flexible schema" alone is no longer a strong reason to leave SQL. A document store is justified when the aggregate-as-a-unit model fits and you want built-in horizontal scaling.

What is a wide-column store (Cassandra, Bigtable, HBase) and what is it good at? Intermediate

In one line: a wide-column store spreads data across many nodes by a partition key and keeps rows sorted inside each partition, giving huge write throughput and cheap "latest N for this entity" reads, at the price of designing tables per query.

How data is addressed. Each row has a partition key (decides which node owns it, via hashing) and a clustering key (the sort order within the partition). Rows of one partition are stored together and sorted, so a query like "last 100 events for device 42" is one sequential read on one node.

CREATE TABLE events_by_device (
  device_id text, ts timestamp, payload text,
  PRIMARY KEY ((device_id), ts)
) WITH CLUSTERING ORDER BY (ts DESC);
-- fast: SELECT * FROM events_by_device WHERE device_id='42' LIMIT 100;

Why writes are fast. Most of these (Cassandra, ScyllaDB, HBase, Bigtable) use an LSM tree: a write is a sequential append plus an in-memory insert, no random disk update (see the B-tree versus LSM question). Cassandra has no single primary at all (any replica node can take the write), while Bigtable and HBase assign each key range to one server.

  • Good at: massive write throughput, time-ordered data per entity, messaging inboxes, event logs, IoT, always-on multi-datacenter replication.
  • Bad at: ad hoc queries, joins, strong multi-row transactions, and any query you did not design a table for. The rule is "one table per query", duplicating data on purpose.
  • Danger: a hot partition (one key takes most traffic) and an unbounded partition (one key grows forever). Fix by bucketing the key, for example (device_id, day), so a partition covers a bounded slice.

Decision rule. Choose it when write volume or multi-region availability is the main problem and you know your queries in advance. Do not choose it for a CRUD app with changing reporting needs.

When do you need a graph database? Intermediate

In one line: use a graph database when the main question is about relationships and paths (friends of friends, "connected to a fraud account within 3 hops"), because traversal cost depends on the part of the graph you touch, not on total data size.

The problem it solves. In SQL, "friends of friends of friends" is a chain of self-joins on a friendship table. Each extra hop multiplies the intermediate rows, and the join must look through an index each time, so cost grows quickly with depth. A graph database (Neo4j, Neptune, JanusGraph) stores each edge as a direct pointer from node to node ("index-free adjacency"), so moving one hop is a pointer follow.

Tiny example. Fraud ring query in a graph language such as Cypher:

MATCH (a:Account {flagged:true})-[:SHARES_DEVICE|SHARES_CARD*1..3]-(b:Account)
RETURN DISTINCT b;

"Variable depth 1 to 3" is one line here; in SQL it is a recursive query that gets slow and hard to read.

When to use. Depth is variable or more than about 2 or 3, and traversal is the main query: recommendations by shared neighbours, fraud rings, permission or dependency graphs, knowledge graphs. For a plain "list my friends" lookup, a join table is perfectly fine.

Limits. Graph stores are hard to shard because an edge usually connects nodes on different partitions, so a traversal hops across machines. That is why the very largest social graphs are custom-built on sharded key-value or MySQL storage with their own traversal layer. Also, graph engines are weaker at heavy aggregations and bulk analytics.

What makes a time-series database different, and when do you use one? Intermediate

In one line: a time-series database is built for append-mostly, timestamped data queried by time range and aggregated, giving cheap retention, strong compression and fast ingestion; the main danger is high label cardinality.

The workload. Metrics, IoT readings, stock ticks and monitoring data are written once in time order and almost never updated. Typical queries: "average CPU per minute over the last day". A general-purpose database can do it, but a specialised store (InfluxDB, TimescaleDB, Prometheus, VictoriaMetrics, or ClickHouse used this way) is much cheaper at scale because it exploits that shape:

  • Time-partitioned storage: data is split into time chunks, so a query for "last hour" touches one chunk and old chunks can be dropped or moved in one cheap operation.
  • Strong compression: timestamps are stored as deltas (and delta-of-delta, so a steady 10-second interval costs almost nothing), floats are XOR-encoded against the previous value. Ten times or more compression is common.
  • Retention and downsampling built in: "keep raw 15 days, hourly rollups for 2 years" is configuration, not a custom job.
  • Fast ingestion of many small writes, batched internally.

Cardinality, the classic production problem. A series is one unique combination of metric name and labels, such as cpu{host=a, region=eu}. If you add a label with millions of values (user id, request id), you create millions of series, and the index and memory blow up even though the data volume is small. Rule: labels are for bounded sets (host, region, status code), never for unbounded identifiers.

Decision rule. Use one for metrics, IoT and monitoring. Do not use it for transactional data, and do not expect good point updates or joins.

Why is a search engine like Elasticsearch not your primary database? Intermediate

In one line: a search engine gives relevance-ranked text search, filters and facets through an inverted index, but it is a derived, near-real-time view, so the primary database stays the source of truth.

What it does well. Elasticsearch, OpenSearch and Solr build an inverted index: for each word, a list of documents containing it. That makes "find documents matching these words, ranked by relevance, filtered by category, with counts per brand" fast, which a normal database does badly (see the full-text search question).

Why it is not a primary database.

  • Near real-time, not immediate: a document becomes searchable only after a refresh (about one second by default), so "write then immediately query" may miss it.
  • No multi-document transactions and weaker guarantees around durability and consistency; replicas and shards can diverge in failure cases.
  • Mappings are hard to change: changing a field type usually needs a full reindex into a new index.
  • Updates are internally delete plus insert of a whole document, which is expensive for frequently changing fields.

The standard pattern. The primary database (Postgres, DynamoDB) is the source of truth. A pipeline (change data capture, or an outbox table plus a queue) feeds the search index. The index is a rebuildable derived view: if you lose it, you rebuild it from the source.

Pitfalls. Dual-writing from the application to both stores can diverge; use CDC or outbox. Users may not see their own write instantly; handle that (see the search-sync question).

Where do in-memory stores fit, and what do you risk by using one as a database? Basic

In one line: in-memory stores give sub-millisecond reads and are ideal for caches, counters, leaderboards, sessions and locks, but as a primary database you risk losing recent writes and you pay a lot per GB.

What they are. Redis, Memcached, Hazelcast and (partly on flash) Aerospike keep data in RAM, so a read costs microseconds instead of the milliseconds of a disk-based database. Redis also offers rich structures: sorted sets for leaderboards, counters, lists, streams, geo.

Good uses. Cache in front of a database, rate-limit counters (INCR with expiry), leaderboards (ZADD, ZRANGE), session data, distributed locks, short-lived state such as OTP codes.

Risks as a primary store.

  • Cost: RAM per GB costs many times more than SSD, so large data sets are expensive.
  • Durability: a restart can lose everything unless persistence is configured. Redis offers RDB snapshots (periodic, may lose minutes) and AOF (an append log, fsync every second or every write, trading speed for safety).
  • Replication is usually asynchronous, so when the primary dies and a replica is promoted, the last few acknowledged writes can vanish.
  • Memory is the hard capacity limit; eviction policies silently delete keys when full (good for a cache, disastrous for a database).

Decision rule. Use it as a primary only when losing the last second or so of writes is acceptable or the data can be rebuilt from elsewhere. Otherwise, keep a durable store as truth and use memory as an accelerator.

OLTP versus OLAP: what is the difference and why separate them? Basic

In one line: OLTP runs the business with many small reads and writes of a few rows; OLAP analyses the business with few huge scans over millions of rows. They are separated so heavy analytics do not slow customers down, and because the best storage layout differs.

OLTPOLAP
PurposeRun the business: place order, update profileAnalyse the business: revenue by region by month
Query shapeMany small reads and writes touching a few rowsFew huge scans aggregating millions or billions of rows
Storage layoutRow-orientedColumn-oriented
Latency goalMillisecondsSeconds to minutes
ConcurrencyThousands of short transactionsTens of heavy queries
ExamplesPostgres, MySQL, DynamoDBSnowflake, BigQuery, Redshift, ClickHouse

Why separate them. Imagine the finance team runs SELECT region, SUM(amount) ... GROUP BY region over 2 billion order rows on the production database. It scans for ten minutes, evicts hot pages from memory, saturates disk I/O and CPU, and customers' checkout queries slow down or time out. Moving analytics to its own system removes that interference.

The second reason is physical: a row store is built for "fetch or update this one record", a column store for "read two columns of every record" (next question). One engine cannot be optimal for both.

How data moves. OLTP data flows to OLAP by batch ETL/ELT, or continuously by change data capture (CDC) streaming row changes from the database log. The analytics copy is allowed to be minutes or hours behind; that staleness is the price of isolation.

Middle ground. For small scale, a dedicated read replica can serve reports. HTAP databases (for example TiDB, SingleStore) try to do both in one system, with trade-offs.

Why are column stores faster for analytics? Intermediate

In one line: a column store keeps each column's values together, so an analytic query reads only the columns it needs, compresses better, and processes values in fast vectorised batches; the cost is slow single-row writes and lookups.

Picture it. A sales table with 50 columns and 1 billion rows. The query SELECT SUM(amount) FROM sales WHERE year = 2025 needs only amount and year.

  • Row store: bytes on disk are row after row (all 50 columns of row 1, then row 2...). To read two columns you must read every page and throw away 48 of 50 columns, so you move about 25 times more data than needed.
  • Column store: there is a file (or segment) per column. The query reads the amount and year columns only.

Further wins.

  • Compression: values in one column have the same type and often repeat (country, status). Run-length encoding turns "IN, IN, IN, IN..." into "IN x 4000"; dictionary encoding replaces strings with small integers. Ratios of 5x to 10x are common.
  • Vectorised execution: the CPU processes thousands of values of one type in a tight loop, using SIMD instructions and cache well.
  • Data skipping: per-block min and max values let the engine skip blocks that cannot match the filter.

The cost. Reconstructing or updating a single row touches many column files, so point lookups and single-row inserts are slow. That is why column stores take bulk loads (batches, or an internal write buffer merged later) and OLTP stays on row stores.

Decision rule. "Get order 123" means rows. "Sum revenue by month" means columns.

What is NewSQL and when would you consider it? Senior

In one line: NewSQL systems (Spanner, CockroachDB, YugabyteDB, TiDB) give you SQL and ACID transactions on a database that scales horizontally and replicates with consensus; consider them when one primary is not enough but you cannot give up relational semantics.

The gap they fill. Classic SQL gives transactions but scales writes only vertically. NoSQL scales horizontally but gives up joins and multi-row transactions. NewSQL tries to have both: the data is split into ranges or shards, each replicated by a consensus protocol (Paxos or Raft), and a distributed transaction protocol makes multi-shard changes atomic.

How a write works. A write goes to the leader of the shard, which replicates it to a quorum (2 of 3 replicas) before acknowledging. So a committed write survives the loss of a node, and with replicas in three regions, often a whole region, with no data loss. Spanner adds TrueTime (GPS and atomic clocks giving a bounded clock uncertainty) so transactions are ordered consistently worldwide.

Costs.

  • Higher write latency: a commit needs a quorum round trip; across regions that is tens to hundreds of milliseconds.
  • Cross-shard transactions are slower than single-shard ones, so key design still matters.
  • More operational complexity than a single Postgres, and some SQL features or extensions are missing or differ.

Decision rule. Consider NewSQL when you need relational semantics and either a write load or data size beyond one primary, or multi-region active-active with strong consistency. If one big Postgres with replicas meets the need, it is simpler and cheaper; say so, because interviewers like candidates who do not over-engineer.

What is polyglot persistence and what does it cost? Intermediate

In one line: polyglot persistence means using different stores for different jobs in one system; each part becomes cheap and fast, but you operate more systems and must manage consistency between them.

Example. Postgres for orders (transactions), Redis for sessions and cache, Elasticsearch for product search, S3 for images, ClickHouse for analytics, Kafka as the event log. Each store is picked for its dominant operation.

What it costs.

  • More systems to run, monitor, secure, upgrade and back up, and more skills the team needs.
  • Data must be copied between stores, so you need a clear source of truth per entity and a propagation mechanism (CDC or an outbox), with eventual consistency between copies.
  • There are no transactions across stores. "Order saved but search index not updated" is a normal state you must tolerate and repair.

How to read this diagram. The service writes once, to Postgres, which is the source of truth (solid arrow). The moving dashes show change events leaving Postgres through CDC or a queue and then fanning out to the search index, the cache and the warehouse. Those three are derived copies: they can lag, and they can be rebuilt from Postgres if lost.

Rule of thumb. Write to exactly one place (the source of truth), and let everything else be derived and rebuildable. Add a new store only when a real requirement (latency, scale, a query shape) justifies its operational price. The first extra store people usually add is a cache, the second a search index.

Walk me through picking storage for: a product catalog, a shopping cart, an audit log, and user-uploaded photos. Intermediate

Say this: "For each data set I name the dominant operation first, then choose the store that makes that operation cheap."

DataDominant operationChoice and reason
Product catalogRead by id, filter and search, attributes vary per categoryDocument store or Postgres with jsonb as source; Elasticsearch for search and facets; cache for hot items. Read-heavy, rarely written.
Shopping cartGet and put by user id, short-lived, high availabilityKey-value (DynamoDB or Redis with persistence). The classic Dynamo-paper use case: prefer always accepting writes.
Audit logAppend-only, rarely read, must be tamper-evident and kept for yearsAppend to a log or queue, then store in object storage (Parquet) with a write-once policy; a searchable recent window in a search or column store.
PhotosLarge immutable blobs, served by URLObject storage (S3-like) plus CDN; metadata (owner, size, path) in a database.

Reasoning, one by one.

  • Catalog: read-heavy with many access paths (browse by category, filter by brand and price, text search). No single store does all of it, so keep one source (document or relational), derive a search index from it, and cache the hottest products. Updates are rare, so eventual consistency of the index is fine.
  • Cart: the key is the user id, the value is the whole cart. A cart that fails to save loses a sale, so availability matters more than strict consistency; the Dynamo paper was motivated by exactly this. If two devices edit simultaneously, merge the item sets instead of rejecting a write.
  • Audit log: never updated, rarely read, long retention. Cheap object storage with immutability (object lock) satisfies tamper-evidence; keep only the recent window in something queryable.
  • Photos: large and immutable, so a database wastes expensive I/O. Object store for bytes, CDN for delivery, database row for metadata and permissions.

Notice that each answer names the dominant operation first and states what is derived versus what is the source of truth. That reasoning is what interviewers listen for.

An interviewer asks "why not just use Postgres for everything?" How do you respond? Senior

Say this: "It is a legitimate default. I would start with Postgres and add specialised stores only when a measured limit forces it."

Why the position is strong. Postgres gives transactions, joins, jsonb, full-text search, geospatial queries (PostGIS), queues (SKIP LOCKED) and extensions for time-series. One database means one backup and restore story, one set of skills, one on-call runbook, and consistent transactions across all your data. Early-stage systems that split into six stores on day one pay a large operational tax for scale they do not have.

Then name the limits that make you add something. This is the part that shows judgement:

Limit you hitWhat you add
Write rate or data size beyond one primarySharding, or a distributed store (NewSQL, Cassandra, DynamoDB)
Analytics scans hurting OLTPRead replica, then a warehouse
Relevance-ranked search, facets, typo tolerance at scaleA search engine fed by CDC
Sub-millisecond reads for hot keysA cache (Redis)
Large filesObject storage (blobs bloat tables and backups)
Metrics at very high cardinality and ingestA time-series store

Each row is a trigger you can measure (CPU, p99 latency, table size, disk growth), so the answer becomes "scale the architecture when evidence demands it, not before".

Pitfall. Do not pretend there are no limits. A single primary is a write bottleneck and a failure domain; mention replicas for availability and backups with tested restores, and that migrating later is easier if you keep data access behind clear module boundaries.

ACID, BASE, transactions and isolation

What does ACID mean, with an example for each letter? Basic

In one line: ACID is the four guarantees of a database transaction: Atomicity (all or nothing), Consistency (constraints hold), Isolation (concurrent work does not interfere) and Durability (committed data survives a crash).

What a transaction is. A group of reads and writes that the database treats as one unit of work. Without that idea, a crash halfway through a multi-step change would leave data in a state nobody intended. ACID is what makes "the database is correct" something you can rely on instead of re-checking in every application.

Walk one example: transfer 100 from account A (balance 500) to B (balance 200).

BEGIN;
UPDATE acct SET bal = bal - 100 WHERE id = 'A';
UPDATE acct SET bal = bal + 100 WHERE id = 'B';
COMMIT;
  • Atomicity: both updates happen, or neither. If the server crashes after the first update, recovery rolls the debit back, so you never lose 100. Implemented with an undo log or by discarding uncommitted versions.
  • Consistency: the transaction moves the database from one valid state to another, respecting rules such as bal >= 0, foreign keys and unique constraints. Be honest in an interview: this letter is partly the application's job (you define the invariants); the database only enforces the constraints you declare. It is also a different "consistency" from the one in CAP (replicas agreeing).
  • Isolation: while the transfer runs, another transaction summing all balances must not see 400 + 200 (money missing in flight). How strictly this is enforced depends on the isolation level (next questions).
  • Durability: once COMMIT returns, the change survives power loss. Implemented with a write-ahead log flushed to disk (fsync) before the acknowledgement; see the WAL question.

Pitfall. People say "ACID" as if it were one switch. In reality isolation is a dial with several settings and durability can be relaxed for speed, so ask "which isolation level, and is fsync on?".

What is BASE and how does it contrast with ACID? Basic

In one line: BASE (Basically Available, Soft state, Eventually consistent) is the stance of large distributed stores that prefer staying up and fast over every replica agreeing instantly; it is a design discipline, not "no guarantees".

What each word means.

  • Basically Available: the system keeps answering requests during failures, possibly with stale or partial data.
  • Soft state: stored values may still be changing as replicas catch up, even with no new user input.
  • Eventually consistent: if no new writes arrive, all replicas converge to the same value after some time.

Why it exists. Strict ACID across many machines needs coordination (locks, two-phase commit, quorum on every write), which adds latency and makes the system unavailable when a network partition cuts nodes off. Systems such as Dynamo, Cassandra and many caches chose to accept writes at any replica and reconcile later (the CAP trade-off).

Example. A like counter replicated on three nodes. You press like, node 1 stores 101; node 2 still says 100 for half a second. Nobody is harmed, and all nodes say 101 soon after. For a bank balance the same behaviour would be a bug.

How you live with it.

  • Make writes idempotent so retries are safe.
  • Use version numbers or vector clocks to detect concurrent updates, and a conflict resolution rule: last-write-wins (simple, can silently drop data), CRDTs (merge automatically, for counters and sets), or an application-level merge (the Dynamo shopping cart unions items).
  • Add read-your-writes tricks where users would notice (read from the primary right after a write).

List the common concurrency anomalies. Intermediate

In one line: the anomalies are the different ways concurrent transactions can produce a result that no one-at-a-time ordering could: dirty read, non-repeatable read, phantom read, lost update and write skew.

Why they exist. Running transactions strictly one after another would be correct but slow. Databases let them overlap, and each isolation level decides which strange outcomes you tolerate. You need to recognise the outcomes by name.

  • Dirty read: you read data another transaction has not committed yet. If it rolls back, you acted on something that never existed. Example: T1 sets balance 500 to 0 (uncommitted), T2 reads 0 and sends a "low balance" email, T1 rolls back.
  • Non-repeatable read: you read the same row twice in one transaction and get different values because another transaction committed a change in between. Example: you read price 10, someone commits 12, you read again and see 12.
  • Phantom read: you run the same range query twice and the set of rows differs because someone inserted or deleted matching rows. Example: SELECT COUNT(*) WHERE status='NEW' returns 5, then 6. The rows you read did not change; new ones appeared.
  • Lost update: two transactions read the same value, each computes a new one, and the second write overwrites the first. Example: both read balance 100, one adds 10, the other adds 20; the final value is 110 or 120, never 130.
  • Write skew: two transactions read an overlapping set, each decides based on it, and they write different rows, so together they break an invariant that neither broke alone. Example: two doctors both on call check "at least 2 are on call", both see 2, both go off call, leaving zero.

How to remember. Dirty: uncommitted data. Non-repeatable: same row, new value. Phantom: same query, new rows. Lost update: same row, both write. Write skew: different rows, shared rule.

Interview note. Lost update and write skew are the dangerous ones in real applications because they do not throw errors; they silently corrupt data, and the standard SQL levels name them poorly or not at all.

Explain the SQL isolation levels and which anomalies each prevents. Intermediate

Plain-English reading of each level.

  • Read uncommitted: no isolation; you may see others' uncommitted work. Almost never used.
  • Read committed: each statement sees only committed data as of the statement start. Two statements in one transaction may see different data. The default in Postgres and Oracle.
  • Repeatable read: the transaction sees one consistent snapshot for its whole life. Default in MySQL InnoDB.
  • Serializable: the result is as if transactions ran one at a time. Implemented by locking (2PL) or by optimistic detection (Postgres SSI aborts one of two conflicting transactions, so you must retry).

Engine differences matter. The SQL standard defines levels by which anomalies are allowed, but engines implement them differently. Postgres "repeatable read" is snapshot isolation: no phantoms in practice, but write skew is still possible. InnoDB "repeatable read" uses next-key locks that block many phantoms for locking reads but has its own quirks (plain reads use the snapshot, locking reads see the latest data). Hedge in an interview: "check the engine's documentation".

Practical advice. Most apps run at read committed and fix specific races with atomic updates, SELECT ... FOR UPDATE, version columns or unique constraints. Use serializable for tricky invariants, and be ready to retry on serialization failures.

Say: "Higher isolation costs throughput and causes aborts or lock waits, so I use the lowest level that protects my invariant, and I use explicit locking or constraints for the specific hot spots."
What is MVCC and why do databases use it? Intermediate

In one line: MVCC keeps several versions of a row so readers see a consistent snapshot while writers create new versions; as a result readers do not block writers and writers do not block readers.

The problem it solves. With plain locking, a long report that reads a table blocks every update to it, or updates block the report. That is a throughput disaster for mixed workloads.

How it works.

  1. Every transaction gets an id or timestamp when it starts (or when each statement starts, at read committed).
  2. An update does not overwrite the row. It writes a new version tagged with the writer's transaction id, and marks the old version as superseded.
  3. A reader looks at the versions and picks the newest one that was committed before its snapshot. It never waits for the writer.
  4. Old versions nobody can see any more are cleaned up. Postgres keeps versions in the table itself and removes dead ones with vacuum; InnoDB keeps old versions in undo logs and purges them.

Example. Row price = 10. T1 (reporting, snapshot at time 100) starts. T2 updates price to 12 and commits at time 105. T1 reads again and still sees 10, because 12 was committed after its snapshot. A new T3 sees 12.

Costs and pitfalls.

  • A long-running or forgotten open transaction pins its snapshot, so the database cannot clean any version newer than it. Tables and indexes bloat, scans slow down, disk fills. This is a well-known production problem (Postgres "idle in transaction", InnoDB history list growth).
  • Writers still conflict with other writers of the same row; MVCC removes read-write blocking, not write-write.
  • Updates create new row versions, which means more write work (and in Postgres, index entries too unless the update can be "heap only").
How do you prevent lost updates? Intermediate

In one line: prevent lost updates by never doing read-modify-write in the application without protection: use an atomic SQL update, a row lock, a version check (optimistic locking), a stricter isolation level, or compare-and-set in key-value stores.

The failure. Two clients read balance 100. Client A computes 110 and writes it. Client B computes 120 and writes it. A's deposit is lost. It happens because both decisions were made on the same stale read.

  1. Atomic update in the database (best when possible): UPDATE acct SET bal = bal - 100 WHERE id = 1 AND bal >= 100. The database applies the arithmetic under its own row lock, so there is no gap between read and write. Check the affected row count: zero means the condition failed (insufficient funds).
  2. Pessimistic lock: SELECT ... FOR UPDATE locks the row until commit, so the second client waits for the first, then reads the new value. Simple and safe; costs lock waiting and risks deadlock if you lock several rows in different orders.
  3. Optimistic concurrency: keep a version column and write UPDATE doc SET body = ?, version = version + 1 WHERE id = ? AND version = ?. If the row count is zero, someone else changed it first; re-read and retry (or tell the user). Good when conflicts are rare (editing a profile); poor on hot rows where retries pile up. This is what JPA @Version does.
  4. Higher isolation: serializable, or Postgres repeatable read, aborts the loser so you retry. The app must handle the failure.
  5. Key-value stores: conditional writes or compare-and-set (DynamoDB condition expressions, Redis WATCH or Lua script, etcd transactions).

Decision rule. Express the change as an atomic operation if you can; otherwise optimistic for low contention, pessimistic for high contention. Note that read committed alone does not prevent lost updates in read-modify-write code (some engines do detect it at repeatable read).

How would you handle write skew, such as "at least one doctor on call"? Senior

In one line: write skew slips past snapshot isolation because the two transactions write different rows, so you fix it with true serializable isolation, by locking the rows you read, by funnelling both into one row that conflicts, or by a database constraint.

Why it is subtle. Rule: at least one doctor must stay on call. Alice and Bob are both on call. Each transaction reads "2 on call", decides it is safe to leave, and sets its own row to off. They update different rows, so there is no write-write conflict and snapshot isolation lets both commit. Now zero doctors are on call, and each transaction was valid when it ran.

Fixes, from strongest to most targeted:

  1. Serializable isolation: Postgres SSI tracks read-write dependencies, detects the dangerous pattern and aborts one transaction with a serialization failure. You must catch it and retry. Simplest to reason about; costs some aborts.
  2. Lock what you read: SELECT ... FROM oncall WHERE shift = 7 FOR UPDATE locks all on-call rows, so the second transaction waits, then sees only one doctor and refuses.
  3. Materialise the conflict: make both transactions update one shared row (for example a shift row with a counter or a lock row). Now it is an ordinary write-write conflict.
  4. Constraint: when the rule fits a constraint, let the database enforce it. Double-booking a meeting room: a unique constraint on (room_id, time_slot) is the cleanest guard; an exclusion constraint (Postgres) handles overlapping time ranges.

Pitfall. The "check then insert" pattern in application code (select to see if the username is free, then insert) is write skew in disguise. Only a unique index is truly safe there.

What is a deadlock in a database and how do you reduce it? Intermediate

In one line: a deadlock is a cycle of transactions each waiting for a lock another holds; the database detects it, kills one transaction as the victim, and the application must retry. Reduce them with consistent lock order, short transactions and good indexes.

How it happens.

T1: UPDATE acct SET ... WHERE id = 1;   -- holds lock on row 1
T2: UPDATE acct SET ... WHERE id = 2;   -- holds lock on row 2
T1: UPDATE acct SET ... WHERE id = 2;   -- waits for T2
T2: UPDATE acct SET ... WHERE id = 1;   -- waits for T1  -> cycle: deadlock

Neither can proceed. The database runs a deadlock detector (or a lock timeout), picks a victim, rolls it back, and returns an error (Postgres 40P01, MySQL 1213). The survivor continues.

Ways to reduce them.

  • Consistent lock order: always lock the lower account id first. Two transfers 1-to-2 and 2-to-1 then both lock row 1 first, and one simply waits. This removes the cycle.
  • Short transactions: hold locks briefly; do no user think-time or remote calls inside a transaction.
  • Proper indexes: an update without a usable index may lock many rows or a range, widening the conflict surface (in InnoDB, gap and next-key locks make this worse).
  • Retry with backoff on deadlock errors; treat them as a normal, expected outcome under load, not a bug.
  • Lock everything you need up front (SELECT ... FOR UPDATE in a fixed order) instead of discovering it step by step.

Diagnose. Read the deadlock report (Postgres log, SHOW ENGINE INNODB STATUS) to see the two statements involved; the fix is usually ordering or an index.

How do you do a transaction across several databases or services? Senior

In one line: across several databases or services you rarely use a real distributed transaction; you use a saga (local transactions plus compensations), the outbox pattern for "update and publish", or you design so data that must change together lives in one place.

The problem. "Reserve stock in the inventory service, charge the payment service, create the order" touches three databases. A local ACID transaction cannot span them, and any step can fail after earlier ones succeeded.

  • Two-phase commit (2PC): a coordinator asks every participant to prepare (promise it can commit and hold locks), and if all say yes, tells them to commit. It gives true atomicity, but participants hold locks while waiting, and if the coordinator dies after prepare they are stuck (in doubt). It adds latency and many modern stores and message brokers do not support it. Used inside distributed databases and XA setups.
  • Saga: a sequence of local transactions, each with a compensating action if a later step fails: charge failed, so release stock; shipping failed, so refund. Either choreographed (events) or orchestrated (a coordinator service). It is eventually consistent, and intermediate states are visible to others (stock is reserved but the order is not confirmed), so design for them. Compensations must be idempotent and retryable.
  • Outbox pattern: to "update my database and publish an event" without 2PC, write the business row and an event row in the same local transaction; a relay (poller or CDC) publishes outbox rows to the broker, at least once. Consumers must be idempotent.
  • Avoid it: choose partition keys and service boundaries so data that must change together lives in one database or shard. This is often the best answer.
Say: "I avoid distributed transactions: same shard where possible, otherwise saga plus outbox plus idempotent consumers, and I accept eventual consistency and design the visible in-between states."
What is a write-ahead log and why does it give durability? Intermediate

In one line: a write-ahead log records each change in a sequential file and flushes it to disk before the change is considered committed, so after a crash the database can replay the log and recover exactly the committed work.

The problem it solves. Updating data pages in place is random I/O (slow), and a crash in the middle of writing a page leaves it half-written. Flushing every modified page at every commit would make commits very slow. We still must promise that committed data is never lost.

The trick. Appending to a log is a fast sequential write. So at commit time only the log record is forced to disk. The modified data pages stay in memory and are written lazily later (in checkpoints). The rule is "log first, data later" (hence write-ahead).

  1. Change a page in memory and append a log record describing it.
  2. On commit, flush the log up to this record to disk (fsync). Then acknowledge.
  3. Data pages reach disk later, in the background.
  4. Crash recovery: start from the last checkpoint and replay the log. Redo changes of committed transactions that never reached the data files; undo (or ignore) changes of uncommitted ones.

Other uses of the same log. Shipping it to replicas (physical replication in Postgres), point-in-time recovery (restore a backup, then replay the log up to a chosen second), and change data capture (Debezium reads the log to emit row changes).

Tuning knob and trade-off. How often to fsync. Flushing on every commit is safest; group commit batches several transactions into one flush for throughput; turning it off (Postgres synchronous_commit = off) is faster but a crash can lose the last fraction of a second of acknowledged commits (data stays consistent, only recent commits vanish). Choose per workload.

Why do storage designs need idempotent writes? Intermediate

In one line: because networks time out and clients retry, writes must be idempotent, meaning that repeating the same request has the same effect as doing it once; the standard tool is a unique idempotency key stored with a unique constraint.

The failure it prevents. A client calls "charge 50". The server charges, but the response is lost. The client times out and retries. Without protection, the customer is charged twice. The client cannot know whether the first attempt worked, so safe retry is only possible if the server can recognise a repeat.

How it works.

  1. The client generates a unique idempotency key per logical operation (a UUID) and sends it on every attempt.
  2. The server stores the key with the result under a unique constraint, in the same transaction as the business change.
  3. On a retry with the same key, the insert conflicts, so the server returns the stored result instead of repeating the work.
INSERT INTO payments (idem_key, order_id, amount, status)
VALUES ('b7e1-...', 42, 50, 'DONE')
ON CONFLICT (idem_key) DO NOTHING;
-- 0 rows inserted => this is a retry; return the saved payment

Naturally idempotent versus not. "Set status = shipped" and "put object at key K" are safe to repeat. "Increment by 1" and "append a row" are not, unless you attach a key. The same applies to message consumers: with at-least-once delivery, a consumer must dedupe by message id or make its effect idempotent.

Pitfalls. Keep keys long enough to cover the retry window (and clean them up later); make sure the key check and the effect are atomic (otherwise two concurrent retries both pass); and reject the same key with a different payload as a client error.

Indexing

What is a database index and why does it speed up queries? Basic

In one line: an index is a separate sorted (or hashed) structure that maps column values to row locations, so the database can jump to matching rows instead of scanning the whole table.

The problem. Without an index, SELECT * FROM users WHERE email = 'a@b.com' must read every row and compare: O(n). On 100 million rows that is a full table scan, seconds or minutes, and it gets worse as the table grows.

The idea: a book index. A book's index lists terms in sorted order with page numbers. You do not read the book to find "mutex"; you look it up in the sorted list and jump to the page. A database index is the same: a sorted list of (value, row pointer) pairs that you can search quickly.

How fast. A B-tree index (the default almost everywhere) is a wide tree where each node holds hundreds of keys. Searching is O(log n) with a huge base: for a billion rows it is roughly 3 or 4 page reads, and the top levels are always cached in memory, so often only one or two disk reads remain.

CREATE INDEX idx_users_email ON users (email);
-- now: WHERE email = 'a@b.com'  -> 3-4 page reads instead of a full scan

Bonus effects. Because keys are stored sorted, the same index also serves ORDER BY email (no sort step), range queries (email >= 'a' AND email < 'b'), and a unique index enforces uniqueness cheaply.

Price. Every write must also update the index, and the index takes space (see the "why not index every column" question). So indexes are a trade: faster reads for slower writes and more storage.

How does a B-tree index work and why is it used so widely? Intermediate

In one line: a B-tree (really a B+ tree) is a balanced, very wide tree of fixed-size pages where leaf pages hold the sorted keys and row pointers; being shallow it needs only 3 to 4 page reads for billions of rows, and the linked leaves make range scans fast.

Structure. The tree is built from fixed-size pages (often 4 to 16 KB; 8 KB in Postgres, 16 KB in InnoDB). Internal pages hold separator keys and child pointers; leaf pages hold the actual keys with row pointers (or the full rows in a clustered index like InnoDB's primary key). Leaves are linked left to right.

Lookup, step by step. Find key 55: the root says "between 40 and 80, go middle"; the middle page says "between 50 and 60"; that points to the leaf containing 55. With about 500 keys per page, 3 levels address 500 x 500 x 500 = 125 million keys and 4 levels about 60 billion, so the depth stays tiny.

Insert. Walk to the correct leaf and insert in order. If the leaf is full, split it into two half-full pages and push a separator key up to the parent (which may itself split). The tree stays balanced automatically.

Strengths: fast point lookups and range scans, predictable read latency, mature and well understood.

Weaknesses: updates are in place (random writes, page splits, write-ahead log plus page writes), so write throughput is lower than an LSM tree; and random keys such as UUID v4 insert into random leaves, causing splits, half-empty pages and cache misses. Time-ordered keys (UUID v7, ULID, sequences) are friendlier.

B-tree versus LSM tree: compare them. Senior

In one line: a B-tree updates data in place and gives low, predictable read latency; an LSM tree turns all writes into sequential appends and merges them later, giving very high write throughput at the cost of slower, more variable reads and background compaction.

Why two designs exist. Disks (even SSDs) are much better at sequential writes than random ones. A B-tree must find the right page and modify it, which is random I/O. An LSM tree (log-structured merge tree) never modifies data on disk: it buffers writes in memory, writes them out as new sorted files in big sequential chunks, and merges files in the background.

Pitfall to mention. LSM latency spikes happen when compaction falls behind or competes with reads; B-tree problems show up as random-write saturation and bloat. Benchmark with your own mix.

Walk through an LSM write and read. Senior

In one line: an LSM write is a log append plus a memory insert; reads check memory then files newest to oldest, helped by Bloom filters; compaction merges files in the background.

How to read this diagram. Left to right is the life of a write. First the write goes to the WAL on disk (for crash safety) and to the memtable in RAM at the same time. When the memtable is full it is flushed as an immutable sorted file (an SSTable at level 0). Later, compaction merges several small files into one larger sorted file at the next level. The faster dashes are the foreground write; the slower ones are background work.

Write path.

  1. Append to the WAL on disk (sequential) so the write survives a crash.
  2. Insert into the memtable, a sorted in-memory structure (skip list or tree). Acknowledge the client. No random disk write happened.
  3. When the memtable reaches a size limit (for example tens of MB), flush it to disk as an immutable sorted file, an SSTable (sorted string table), and start a new memtable. The WAL segment for it can be discarded.

Read path. Look in the memtable first, then SSTables from newest to oldest, stopping at the first hit (the newest version wins). Without help this could mean opening many files, so each SSTable has a Bloom filter that says "definitely not here" for most files, plus a sparse index to locate the block quickly. Hot blocks sit in a block cache.

Compaction. Background jobs merge several sorted files into one bigger sorted file (a cheap merge sort of already-sorted inputs). During the merge they drop older versions of overwritten keys and, eventually, drop deleted data.

Deletes. You cannot remove a key from an immutable file, so a delete writes a tombstone marker. Reads honour the tombstone; compaction removes both tombstone and data later (after a grace period, so replicas agree). A delete-heavy workload accumulates tombstones that every read must skip, which slows reads.

Tiny timeline. Put(a=1), Put(b=2), flush gives SSTable1 {a=1,b=2}. Put(a=5), flush gives SSTable2 {a=5}. Get(a) checks SSTable2 first and returns 5. Compaction merges both into {a=5,b=2}, discarding the stale a=1.

How do composite indexes work and why does column order matter? Intermediate

In one line: a composite index is sorted by its first column, then its second within the first, and so on, so it can be used for queries on a leftmost prefix; put equality columns first and the range or sort column last.

How it is stored. Think of a phone book sorted by last name, then first name. An index on (country, city, created_at) is sorted by country; within a country by city; within a city by created_at.

(IN, Mumbai, 2026-01-02)
(IN, Mumbai, 2026-03-09)
(IN, Pune,   2026-02-11)
(US, Austin, 2026-01-05)

This order helps queries that fix the leading columns:

  • WHERE country = 'IN': yes (one contiguous region).
  • WHERE country = 'IN' AND city = 'Pune': yes.
  • WHERE city = 'Pune' alone: no, because Pune entries are scattered under every country, so the database cannot jump to them (it may fall back to scanning the whole index).

Ordering rule of thumb: equality columns first, then the range or sort column last. For WHERE user_id = ? AND created_at > ? ORDER BY created_at, index (user_id, created_at): the equality narrows to one user's contiguous slice, and inside it rows are already sorted by time, so there is no extra sort step. Reversing to (created_at, user_id) would put all users interleaved by time and force a wide scan.

Other considerations. Among equality columns, put the more selective (or most commonly used alone) first. One composite index often replaces several single-column ones: (a, b) already serves queries on a, so a separate index on a is redundant. Check with EXPLAIN.

What is a covering index? Intermediate

In one line: a covering index contains every column the query needs, so the database answers from the index alone and never visits the table (an index-only scan), saving one random lookup per row.

Why it helps. A normal index lookup has two steps: find matching entries in the index, then for each entry follow a pointer to the table page to fetch the other columns. For 1,000 matching rows that is up to 1,000 random table reads. If the index already holds the needed columns, step two disappears.

-- query
SELECT status FROM orders WHERE user_id = 42;
-- covering index (both styles)
CREATE INDEX idx_o ON orders (user_id, status);
CREATE INDEX idx_o2 ON orders (user_id) INCLUDE (status);  -- Postgres 11+, SQL Server

The INCLUDE style adds the payload column to the index leaves without making it part of the sort key, which keeps the key narrow. In EXPLAIN you look for "Index Only Scan" (Postgres; note it also depends on the visibility map being fresh, so vacuum matters) or "Using index" (MySQL).

Cost. A wider index uses more disk and RAM and costs more on every write to those columns. So cover only your hottest, most frequent queries, not everything.

InnoDB note. Secondary indexes there store the primary key too, so a query needing only indexed columns plus the primary key is automatically covered.

What is the difference between a clustered (primary) index and a secondary index? Intermediate

In one line: a clustered index stores the table rows themselves in the index order; a secondary index is a separate structure that stores the indexed value plus a pointer (a row id, or the primary key) back to the row, so using it costs an extra lookup unless it covers the query.

Clustered (InnoDB primary key, SQL Server clustered index). The leaf pages of the primary-key B-tree are the table. Rows with neighbouring keys sit next to each other on disk, so range scans on the primary key are very efficient, and a lookup by primary key reads the row directly. There is only one clustered index per table, because rows can be in only one physical order.

Secondary index. Its leaves hold (indexed value, pointer). In InnoDB the pointer is the primary key value, so a lookup by a secondary index first finds the primary key and then does a second descent through the clustered index (a "double lookup"). In Postgres the table is a heap (not clustered) and secondary indexes point to the physical row location (ctid), so there is one extra heap fetch.

If indexes make reads fast, why not index every column? Basic

In one line: every index makes writes slower and uses memory and disk, so you index for real query patterns, confirm with EXPLAIN, and drop unused indexes.

  • Write amplification: every insert and delete must update every index, and an update of an indexed column updates that index. A table with 8 indexes does roughly 9 structure writes per insert (the table plus 8 trees), each maybe splitting pages and logging to the WAL. Bulk loads often drop indexes first and rebuild after.
  • Memory pressure: indexes are read through the buffer cache. If hot index pages no longer fit in RAM, every lookup hits disk and latency jumps for everything, not only for that table.
  • Storage: indexes can be as large as the table itself, which also means larger backups and slower replicas.
  • Planner confusion: more indexes mean more plans for the optimizer to weigh, with a bigger chance of a poor choice and more maintenance statistics.
  • Low selectivity gives little benefit: an index on a boolean or a status with three values still matches a large share of rows; the planner may ignore it, because a sequential scan is cheaper than millions of random lookups. (Exception: a partial index on the rare value.)

What to do instead. Start from the actual queries (slow query log, pg_stat_statements), add the index that serves them, verify with EXPLAIN that it is used, and periodically list indexes with zero scans (pg_stat_user_indexes, MySQL sys.schema_unused_indexes) and drop them. Merge overlapping indexes into one composite.

A query has an index on the column, yet the database does a full scan. Why? Intermediate

In one line: the usual causes are an expression wrapped around the indexed column, a leading wildcard, a type mismatch, a violated leftmost prefix, low selectivity, stale statistics, or an OR across columns.

The index is a sorted list of the raw column values. Any time the query does not compare the raw value in a way that matches the sort order, the index cannot be used. Go through the usual suspects:

  • Function or cast on the column: WHERE LOWER(email) = 'a@b.com' or WHERE DATE(created_at) = '2026-01-01'. The index has emails, not lowercased emails. Fix: a functional (expression) index on LOWER(email), or rewrite as a range: created_at >= '2026-01-01' AND created_at < '2026-01-02'.
  • Leading wildcard: LIKE '%abc' cannot use a B-tree (the sort order starts from the first character). LIKE 'abc%' can. For contains-search use full-text or trigram indexes.
  • Type mismatch: comparing a string column to an integer forces an implicit cast on the column side, disabling the index (classic MySQL gotcha).
  • Leftmost-prefix violation on a composite index.
  • Low selectivity: the planner estimates most rows match, and a sequential scan is cheaper than many random lookups. This is a correct decision, not a bug.
  • Stale statistics: the planner thinks the table is tiny or the value is rare, so it picks the wrong plan. Run ANALYZE (or let autovacuum do it).
  • OR across different columns and NOT IN / != patterns often defeat single indexes (rewrite as UNION, or use a bitmap OR if supported).

Method: run EXPLAIN (ANALYZE), compare estimated and actual rows, and look at the scan type. Do not force an index until you know why the planner avoided it.

When would you use a hash index, a bitmap index, or a partial index? Senior

In one line: B-tree is the general default; hash indexes do equality only; bitmap indexes suit low-cardinality columns in read-mostly analytics; partial indexes cover only a slice of rows, which is great for "pending" or "active" subsets; unique indexes enforce constraints.

  • Hash index: hashes the key to a bucket, so an equality lookup is O(1). It cannot do ranges, ordering or prefix matches. A B-tree is already 3 to 4 reads and supports everything, so a hash index is rarely worth it. (Hash partitioning of data across nodes is a different thing and common.)
  • Bitmap index: one bitmap (a bit per row) for each distinct value, such as gender or status. Combining conditions is a fast bitwise AND/OR over bitmaps, which suits read-mostly analytic tables with low-cardinality columns (Oracle, some warehouses; Postgres builds bitmaps on the fly from B-trees). Bad under heavy concurrent writes, because updating one row locks a whole bitmap segment.
  • Partial (filtered) index: indexes only rows matching a condition. 
    CREATE INDEX idx_pending ON orders (created_at) WHERE status = 'PENDING';
    If 1 percent of orders are pending and a worker polls for them, this index is tiny, stays in memory and is cheap to maintain, since non-pending rows do not touch it. Also handy for "unique among non-deleted" (see soft delete).
  • Unique index: enforces a constraint and speeds lookup at once. It is the only reliable guard against duplicates under concurrency, since "check then insert" in code races.

Other specialised ones worth naming: GIN (arrays, jsonb, full-text), GiST/R-tree (geospatial), BRIN (huge append-only tables with naturally ordered values, tiny index).

How do secondary indexes work in NoSQL stores, and what are the trade-offs? Senior

In one line: a secondary index in a partitioned store is either local (each partition indexes its own rows; writes are cheap, reads must ask every partition) or global (one index partitioned by the indexed value; reads hit one partition, writes touch several and are often eventually consistent).

The problem. Data is placed by primary key. If you ask "all orders with status = SHIPPED", rows are scattered across every partition. A secondary index gives you a way to ask on another attribute, and there are two designs.

Local (document-partitioned)Global (term-partitioned)
Where the index livesEach partition indexes only its own rowsOne index partitioned by the indexed value, across the cluster
Write costCheap, one partitionA write touches the data partition and one or more index partitions; often updated asynchronously
Read costScatter-gather: query every partition; tail latency grows with cluster sizeOne partition read, but may be slightly stale
ExamplesCassandra local indexes, MongoDB, Elasticsearch shardsDynamoDB global secondary indexes (eventually consistent), Cassandra materialised views (with caveats)

In words. Local indexes are easy to keep consistent because the row and its index entry live on the same node, but a query on the indexed value has to fan out to all N partitions and wait for the slowest, so the more nodes, the worse the p99. Global indexes make the read cheap by pre-grouping all rows with the same value on one index partition, but one logical write now becomes several physical writes on different nodes, which is slow, risks partial failure, and is therefore usually applied asynchronously (so a just-written item may be missing from the index briefly).

Practical guidance. Prefer designing the table to answer the query (one table per access pattern, duplicating data). Use a secondary index for low-volume or less critical lookups, and for high-cardinality lookups prefer a global index. Mention that a hot index key can throttle just like a hot partition key.

How does primary key choice (auto-increment, UUID, snowflake id) affect storage? Senior

In one line: sequential ids are compact and B-tree friendly but need central coordination; random UUID v4 is coordination-free but scatters inserts and bloats indexes; time-ordered ids (UUID v7, ULID, snowflake) give uniqueness without coordination and good insert locality.

  • Auto-increment (bigint): new keys always go to the right edge of the B-tree, so pages fill fully and stay in cache. 8 bytes, compact in every secondary index (InnoDB copies the primary key into each secondary index entry). Downsides: a single-writer bottleneck when sharded (the sequence lives on one node), guessable ids (enumeration attacks, leaks business volume), and a hot right-most page under extreme insert rates.
  • Random UUID v4: 16 bytes, unique without coordination, safe to expose. But each insert lands on a random leaf, so once the index is bigger than RAM nearly every insert is a disk read plus a page split, pages end up about half full, cache locality is poor, and the 16-byte key is copied into every secondary index.
  • Time-ordered ids (UUID v7, ULID, snowflake): the high bits are a timestamp, so new ids are roughly increasing: inserts cluster at the right edge like a sequence, yet any node can generate ids independently. A snowflake id packs timestamp, machine id and a sequence into 64 bits. Caveat: in range-sharded stores, monotonic keys send all writes to the last shard (hot shard); hash the key, or prefix with a bucket, when the write rate is huge. Also, ids reveal creation time.

Decision rule. Single database: bigint or UUID v7. Many writers, no coordinator, needs to be unguessable externally: UUID v7 or ULID (or expose a separate public id). Hash-partitioned distributed store: random keys are fine, even good, for spreading load.

Storage engines and amplification

What are write, read and space amplification? Senior

In one line: write amplification is bytes physically written per byte the application wrote; read amplification is disk reads per logical read; space amplification is disk used per logical byte. You cannot minimise all three, so engine and compaction choices pick which one hurts least.

  • Write amplification: in a B-tree, changing a 100-byte row writes a WAL record and later a whole 8 KB page, so about 80x for tiny updates (checkpoints and full-page writes add more). In an LSM, data is rewritten every time compaction moves it to a deeper level; leveled compaction can reach roughly 10x to 30x or more depending on workload. It matters because it consumes disk bandwidth and wears out SSDs (limited program/erase cycles).
  • Read amplification: a B-tree reads about one page (or a few levels) for one row; an LSM may check the memtable and several SSTables (Bloom filters cut this).
  • Space amplification: disk used divided by logical data size, caused by old row versions, fragmentation (half-empty B-tree pages), and not-yet-compacted duplicates in an LSM.
StrategyWrite ampRead ampSpace amp
Leveled compactionHighLowLow
Size-tiered compactionLowerHigherHigher (temporary 2x during merges)
B-treeMedium (page granularity)LowMedium (fragmentation)

Decision. Write-heavy with spare reads: tiered or time-window. Read-latency-sensitive: leveled. SSD endurance and cost matter: watch write amplification. This is the RUM trade-off (Read, Update, Memory): improving two worsens the third.

Row-oriented versus column-oriented storage: when each? Intermediate

In one line: row storage keeps a whole record together, so it is ideal for fetching or updating full rows by key (OLTP); column storage keeps each column together, ideal for aggregating a few columns across many rows (OLAP).

Mental picture. A table of users with id, name, email, country, age. Row layout on disk: [1, Ann, a@x, IN, 31][2, Bo, b@x, US, 28].... Column layout: ids: 1,2,3..., names: Ann, Bo..., ages: 31, 28....

  • Row store: "get user 2" reads one contiguous chunk, "update email" rewrites one place, inserting one row is one append. But "average age" has to read all columns of all rows.
  • Column store: "average age" reads only the ages column and compresses it well. But "get user 2" must pull the value from every column file, and an insert touches every column.

Hybrid designs exist: Postgres columnar extensions, SingleStore and others combine a row-oriented write buffer with column-oriented segments; wide-column stores (Cassandra, Bigtable) group columns into column families but are still row-keyed and are not analytic column stores in the warehouse sense. Parquet and ORC are columnar file formats for the same reason.

Rule. If queries say "get order 123", use rows. If they say "sum revenue by month", use columns. For both, keep an OLTP row store and replicate into a column store.

Why does RAM size matter so much for a database? Intermediate

In one line: reading from RAM is thousands of times faster than from SSD, so a database is fast while its working set (the data and indexes touched regularly) fits in memory, and latency jumps sharply when it stops fitting.

Rough latencies (orders of magnitude): RAM about 100 ns; SSD about 100 microseconds; spinning disk several milliseconds. So an SSD read is about 1,000 times slower than RAM, and a disk read about 50,000 times.

How it works. Databases keep recently used pages in a buffer pool (InnoDB, Postgres shared_buffers) and also benefit from the OS page cache. A query first checks memory; only a miss goes to disk. With a 99 percent hit ratio and 100 microseconds per miss, average read time is dominated by the 1 percent of misses; at 90 percent it is about ten times worse, even though the change looks small.

The cliff. Suppose hot data is 40 GB and RAM for cache is 64 GB: nearly all reads hit memory. Data grows to 80 GB: the hit ratio falls, I/O rises, queries queue behind disk reads, and latency can go from 2 ms to 50 ms without any code change. This is the "it was fine last month" incident.

Sizing rule. Keep all hot indexes in memory; ideally the whole working set. Monitor cache hit ratio, disk reads per second and read latency as data grows. Remedies when it no longer fits: more RAM, drop unneeded indexes, partition so the active part is small, archive cold data, or shard. Also note that RAM is shared with connection memory and sorts, so do not size it to the last gigabyte.

What can go wrong with LSM compaction in production? Senior

In one line: LSM compaction can fall behind the write rate, compete with reads for I/O, pile up tombstones, and temporarily need extra disk; you tune strategy, rate limits and disk headroom, and avoid delete-heavy modelling.

Why it is the weak spot. LSM trades cheap writes for deferred merging work. That work is a bill that must be paid, in disk I/O and CPU, continuously. If the bill grows faster than you can pay, trouble starts.

  • Compaction falls behind: SSTable count grows, each read must check more files, read latency rises, and eventually the engine throttles or stalls writes to protect itself (RocksDB "write stall", Cassandra pending-compactions backlog). Symptom: climbing pending compactions and file counts.
  • I/O contention: compaction reads and rewrites gigabytes, competing with foreground reads and producing p99 latency spikes that show up at regular times.
  • Tombstone buildup: deletes, TTL expiry and queue-like usage (insert, process, delete) leave many tombstones that every read of that range must scan past; Cassandra even aborts queries scanning too many tombstones. The "queue as a table" is a well-known anti-pattern.
  • Space spikes: size-tiered compaction merging the largest files can temporarily need up to about double the data size, so a disk at 80 percent full can fill during a compaction.

Mitigations. Rate-limit compaction throughput; pick a strategy that fits the workload (time-window compaction for TTL time-series, leveled for read-heavy); keep disks below about 50 to 70 percent full; separate heavily deleted data into its own table with time bucketing so whole SSTables expire; and alert on pending compactions, SSTable count per read and tombstones scanned.

What is a Bloom filter and where do storage systems use it? Intermediate

In one line: a Bloom filter is a tiny bit array plus hash functions that answers "is key X in this set?" with "definitely not" or "probably yes"; it never has false negatives, so storage engines use it to skip files that cannot contain a key.

How it works. Start with a bit array of m bits all zero and k hash functions. To add a key, hash it k ways and set those k bits to 1. To test a key, hash it and check the k bits: if any is 0, the key was definitely never added; if all are 1, it was probably added (those bits may have been set by other keys, which causes a false positive).

Example with 10 bits and 2 hashes: add "cat" sets bits 2 and 7; add "dog" sets bits 4 and 7. Test "cow" hashes to bits 2 and 4: both are 1, so "probably yes", a false positive. Test "bee" hashes to bit 5, which is 0: definitely not present.

Why storage systems love it. An LSM read for a missing or old key would otherwise open every SSTable. A Bloom filter per SSTable, small enough to keep in memory, rejects almost all files with no disk read. With about 10 bits per key the false-positive rate is around 1 percent (more bits means fewer false positives). Used in Cassandra, HBase, Bigtable, RocksDB, and also to avoid caching "one-hit wonders" at CDNs and to check if a username or URL was seen.

Limits. You cannot delete a key (use a counting Bloom filter or cuckoo filter), it does not return the value, and it must be sized for the expected number of keys; an overfull filter degrades into "always yes". Range scans cannot use it, only point lookups.

Normalization, data modelling and schema evolution

What is normalization and what problem does it solve? Basic

In one line: normalization organises tables so each fact is stored exactly once, which removes duplication and update anomalies at the price of needing joins to read it back together.

The problem. Suppose one orders table stores, on every row, the customer's name and address:

order_id | customer | address       | item
1        | Ann      | 12 Park St    | pen
2        | Ann      | 12 Park St    | ink
3        | Ann      | 12 Park St    | pad

Ann moves. You must update every row. If you miss one, the database now says Ann lives in two places (an update anomaly). Deleting Ann's only order also deletes her address (delete anomaly), and you cannot store a customer who has no order yet (insert anomaly).

The fix. Split by fact: customers(id, name, address) and orders(id, customer_id, item). Ann's address now lives in one row; orders reference it by id.

The normal forms in plain words.

  • 1NF: each column holds one atomic value (no comma-separated lists or repeating groups).
  • 2NF: every non-key column depends on the whole key (matters for composite keys).
  • 3NF: every non-key column depends on the key and nothing but the key (no column that is determined by another non-key column, such as storing both zip code and city).

"The key, the whole key, and nothing but the key" is the one-line memory aid.

Benefits: no duplication, consistent updates in one place, smaller rows, a single source for each fact. Cost: reads that need data from several entities require joins, which can become the bottleneck at scale (that motivates controlled denormalization, next question).

When do you denormalize, and what do you pay? Intermediate

In one line: denormalize deliberately, for measured hot read paths or in stores without joins, by copying data so reads need no join; you pay with more complex writes and possible staleness.

Why. Normalised data needs joins; joins cost CPU and I/O and do not span shards or most NoSQL stores. If a page is read 1,000 times for every one write, it is worth doing the work once at write time so each read is a single lookup.

Examples.

  • Store author_name inside each post, so rendering a feed needs no join to the users table.
  • Keep an order_total column instead of summing line items on every view.
  • Maintain a like_count counter on the post instead of counting like rows.
  • A precomputed per-user timeline (fan-out on write).

What you pay. Every copy must be updated when the source changes. Options: do it in the same transaction (safe, but couples writes), a trigger (hidden magic), or an async pipeline such as CDC or events (eventually consistent, can lag or fail). You also need a way to repair drift, for example a periodic reconciliation job that recomputes derived values.

Decision per field: how bad is staleness? The author's display name being stale for a few seconds is fine. A stale price at checkout is not; read the price from the source of truth there. A frozen snapshot (the price at time of order) is not even denormalization-drift, it is the correct historical fact.

Rule. Start normalised; measure; denormalize the specific hot path; document the source of truth and how copies are refreshed.

What does "model data for access patterns" mean in NoSQL? Intermediate

In one line: in stores like DynamoDB and Cassandra you write down your queries first and then design keys so that each query is a single-partition read; that is the opposite of the relational habit of modelling entities first.

Why. These stores cannot do joins or efficient ad hoc filtering, and data is placed by partition key. A query that does not include the partition key must scan or scatter across all nodes. So the schema must be shaped by the questions.

Worked example on DynamoDB (single-table design). Access patterns:

  1. Q1: get a customer profile. Key: PK=CUST#42, SK=PROFILE.
  2. Q2: list a customer's orders, newest first. Items PK=CUST#42, SK=ORDER#2026-11-17#9001. A query on PK=CUST#42 with SK begins_with ORDER# returns the orders already sorted; with no sort prefix filter, one query returns profile and orders together.
  3. Q3: find an order by order id alone. The base table cannot (the partition key is the customer), so add a global secondary index with order id as its key.

Item collection for one customer in sort-key order:

PK=CUST#42  SK=ORDER#2026-11-17#9001   {total: 40}
PK=CUST#42  SK=ORDER#2026-11-02#8800   {total: 12}
PK=CUST#42  SK=PROFILE                 {name: "Ann"}

Habits that follow. Duplicate data per access pattern (one table or item type per query), choose partition keys with high cardinality and even traffic, use sort keys for ordering and range queries, and use composite sort keys ("type#date#id") to encode hierarchy.

Pitfalls. A new query nothing supports means a scan or a migration, so confirm access patterns before committing and keep them in a document; hot partition keys throttle; single-table design is hard to read and onboard, so use it deliberately.

Embed or reference in a document model? Intermediate

In one line: embed child data inside the parent document when it is read with the parent, owned by it, small and bounded; reference it by id when it is shared, unbounded, or changes independently.

Embed whenReference when
Child data is read with the parent and belongs to it (order lines)Child is shared by many parents (a product used in many orders)
Child list is bounded and smallList is unbounded (all comments on a viral post)
Child rarely changes independentlyChild changes often and must be consistent everywhere

The reasoning. A document store reads and writes one document atomically and quickly. Embedding exploits that: one read returns the order and its lines, and one write updates both consistently. But embedding copies data. If the child is shared (a product), you have a copy in every parent, and changing it means updating all of them. If the list is unbounded, the document grows without limit, hits size limits (MongoDB documents are limited to 16 MB) and every append rewrites more and more.

Examples.

  • Order with lines: embed (one order owns its lines; read together; at most dozens).
  • Blog post with comments: reference (comments are unbounded and written often); store them in their own collection keyed by post id, page them.
  • Order line with product: hybrid. Embed a snapshot (name and price at order time, which must be frozen for history anyway) plus the product id as a reference for navigation.

Decision questions: "Is it read together? Is it bounded? Does it change independently? Do I need to query it on its own?" Two or more "no"s on the first two and "yes" on the last two point to reference.

How do you model many-to-many relationships (for example users and groups) across SQL and NoSQL? Intermediate

In one line: in SQL use a join table with indexes in both directions; in NoSQL store the relationship twice, once per direction, keyed so each direction is a single-partition query, and update both together.

SQL. Users and groups are many-to-many: a user is in many groups and a group has many users. Add a link table:

CREATE TABLE membership (
  user_id  bigint REFERENCES users(id),
  group_id bigint REFERENCES groups(id),
  PRIMARY KEY (user_id, group_id)
);
CREATE INDEX ON membership (group_id, user_id);  -- the reverse direction

The primary key serves "groups of user"; the extra index serves "users of group". Joins fetch the details.

NoSQL (DynamoDB or Cassandra style). There are no joins, and a query needs the partition key. So store each edge twice:

PK=USER#1   SK=GROUP#7     -- "which groups is user 1 in?"
PK=GROUP#7  SK=USER#1      -- "who is in group 7?"

Both rows must be written together. Use a transactional write if the store offers it (DynamoDB TransactWriteItems), otherwise an idempotent pair of writes plus a repair job for the case where only one succeeds.

Scale pitfalls. A group with 50 million members makes PK=GROUP#7 a giant, hot partition. Page the query, bucket the key (GROUP#7#bucket3), and store large memberships in a separate structure. Also decide where "who is in group 7" counts come from (a maintained counter rather than counting rows).

How do you change a schema with no downtime? Senior

In one line: use expand and contract (parallel change): add the new structure, dual-write, backfill, switch reads, then remove the old one, so that old and new application versions both work with the database at every step.

Why not a one-step change? During a rolling deploy, old and new application versions run at the same time. If a migration renames a column in one step, either old servers break (they still use the old name) or new servers break (if they deployed first). Zero downtime means every intermediate state must work for both versions.

Example: rename name to full_name.

  1. Expand: add nullable full_name (no table rewrite in most engines when there is no default or the default is a constant).
  2. Deploy code that writes to both columns and still reads the old one. Now new rows are consistent in both.
  3. Backfill old rows in small batches by primary key range, throttled with pauses so it does not saturate the primary or lag replicas.
  4. Verify equality (a comparison query, or shadow reads logging mismatches), then deploy code that reads from the new column.
  5. Stop writing the old column. After a safe period, contract: drop the old column in a separate later release.

Each step is separately deployable and reversible: if step 4 shows problems, roll back to reading the old column with no data loss.

Trap: a single migration that renames the column while old servers still run causes errors during the rolling deploy. Also never mix a risky schema change and a code change in the same release. And remember that dropping a column is irreversible, which is why it comes last.

Same pattern works for splitting a table, changing a type, or changing a primary key: build the new thing alongside, dual-write, copy history, cut over, retire the old.

Which schema changes are dangerous on a big table, and how do you do them safely? Senior

In one line: on a big, busy table the dangerous changes are those that take long locks or rewrite the table (indexes, defaults, type changes, NOT NULL, foreign keys, big backfills); do them online, in small steps, with a lock timeout.

  • Adding an index: a plain build may block writes for the duration. Use online variants (Postgres CREATE INDEX CONCURRENTLY, MySQL online DDL) and watch I/O and replication lag; note that a failed concurrent build leaves an invalid index to drop.
  • Adding a column with a default or changing a type: older engines rewrite the whole table under an exclusive lock. Newer ones avoid it for some cases (Postgres 11 and later for constant defaults); check your version.
  • Adding NOT NULL or a foreign key: validation scans all rows while holding a lock. Add as NOT VALID (Postgres) or as a check constraint, backfill, then VALIDATE separately, which takes a weaker lock.
  • Large backfills: a single huge UPDATE bloats the log, lags replicas, holds locks and can run for hours. Batch by primary key range (a few thousand rows per transaction) with pauses.
  • Online schema-change tools: gh-ost and pt-online-schema-change (MySQL) build a shadow copy of the table with the new schema, copy rows in chunks, tail the change stream so new writes land too, then swap table names in one quick step.
  • Lock timeout: a DDL needing an exclusive lock waits for running queries. While it waits, every new query queues behind it, so one long query plus one ALTER can stall the whole table. Set lock_timeout so the DDL fails fast instead, and retry.

Checklist for review: What lock does it take, and for how long? Does it rewrite the table? Is it reversible? Have I rehearsed on production-sized data? What is the replication impact?

How do you evolve schemas in schemaless stores and in event or file formats? Senior

In one line: "schemaless" really means schema-on-read: the code must handle every shape ever written, so version your data, make new fields optional, migrate lazily or in the background, and follow compatibility rules for serialized formats.

The problem. A document store will happily accept whatever you write. After a year, documents exist in five shapes (some with name, some with first and last). Old records do not upgrade themselves, and the application code that reads them has to cope with every version, forever, unless you manage it.

Practical approach.

  1. Add a schemaVersion field to documents.
  2. Make new fields optional with sensible defaults, and write reader code that handles old versions.
  3. Lazy migration: when reading a version 1 document, upgrade it in memory and write it back as version 2. Cheap, spreads cost over time, but documents never touched stay old.
  4. Background migration: a throttled job upgrades all documents, after which the old-version reading code can be deleted.

Serialized data (events, Kafka messages, files). Formats like Avro, Protobuf and Parquet have explicit schemas; use a schema registry and enforce compatibility.

ChangeSafe?
Add an optional field with a defaultYes, backward and forward compatible
Remove an optional fieldUsually yes (with defaults)
Rename a field or change its typeNo, it breaks old readers or writers
Reuse a field number or name for a new meaningNever: old data gets misread silently

Rule: backward compatible means new readers read old data; forward compatible means old readers read new data. With rolling deploys and replayable event logs you need both.

What is soft delete, and what are its pitfalls? Intermediate

In one line: soft delete marks a row as deleted (deleted_at) instead of removing it, which gives undo and audit but adds filtering bugs, unique constraint problems, unbounded growth and compliance issues.

Why people do it. Users hit "delete" by mistake; other tables still reference the row; auditors want history; sync clients must learn what was deleted (a missing row cannot tell them). Setting deleted_at = now() keeps everything and is easily undone.

Pitfalls and fixes.

  • Forgotten filters: every query must say WHERE deleted_at IS NULL; one missing filter leaks deleted data (a privacy bug). Hide it behind a view, an ORM default scope (Hibernate @Where or @SQLRestriction) or row-level security.
  • Unique constraints break: a deleted user's email still occupies the unique index, blocking re-registration. Use a partial unique index: CREATE UNIQUE INDEX ON users (email) WHERE deleted_at IS NULL.
  • Growth: deleted rows stay in tables and indexes forever, slowing scans. Add a purge or archive job (move rows older than N days to cold storage).
  • Compliance: laws such as GDPR require real erasure on request, so soft delete alone is not enough. Add a hard-delete or anonymisation path with a defined delay, and remember backups and derived stores (search index, caches, warehouse).
  • Foreign keys and cascades: the database will not cascade a soft delete; you implement it yourself, and children must be hidden too.

Alternative. Move deleted rows into an archive table (delete from main, insert into users_deleted): keeps live tables small and queries unfiltered, at the cost of a move on delete.

How do you store a counter, such as likes or view counts, at scale? Senior

In one line: use an atomic increment for normal rates; for a hot counter, shard it into several sub-counters, or buffer increments in Redis or a stream and flush totals, and accept eventual consistency in the displayed number.

  • Low rate: UPDATE posts SET likes = likes + 1 WHERE id = ? is atomic and fine. Never do read, add, write in app code (lost updates).
  • The hot row problem: a viral post receives thousands of likes per second, all updating one row. Each update takes the row lock, so they serialise: throughput is capped at roughly one over the transaction time, and latency queues up. Fix by sharding the counter: keep N rows (post_id, shard 0..9), increment a random shard, and sum them on read (cache the sum). Writes now spread across N locks.
  • Buffering: increment in Redis (INCR, very fast) and flush totals to the database every few seconds; or stream every like event to Kafka and aggregate per post in a consumer. You trade a little durability and freshness for large throughput.
  • Exact distinct counts (unique viewers) need a set per item, which is huge. Use an approximate structure: HyperLogLog (about 12 KB per counter in Redis with roughly 1 percent standard error, regardless of cardinality).
  • Authoritative record: keep the facts (a likes row per user and post, unique on both) separately so the counter can be recomputed and duplicates prevented; the counter is a derived, cached summary.

Say: "The displayed count is eventually consistent; the like rows are the truth, and a periodic job reconciles drift."

When is a JSON column in a relational table a good idea? Intermediate

In one line: a JSON column fits sparse, rarely queried or user-defined attributes and raw payloads kept next to parsed columns; use real columns for anything you filter, join or constrain constantly.

Good uses. Per-tenant custom fields, a vendor webhook payload stored for audit and replay, feature settings that vary by plan, or a product's rarely used extra attributes. Postgres jsonb supports GIN indexing and operators such as containment (@>), and MySQL has a JSON type with generated columns you can index.

CREATE TABLE products (id bigint PRIMARY KEY, name text, price numeric, attrs jsonb);
CREATE INDEX ON products USING gin (attrs);
SELECT * FROM products WHERE attrs @> '{"color":"red"}';

What you give up for fields inside the JSON.

  • No type checking or NOT NULL, no foreign keys, weak constraints.
  • Poor planner statistics (the optimizer cannot estimate selectivity well), so queries on JSON fields can pick bad plans.
  • Updating one key rewrites the whole value in most engines.
  • Every query must know the shape, and the schema is in the code, not the database.

Rule of thumb. Columns for what you query and constrain, JSON for the long tail. If a JSON field becomes something you filter on all the time, promote it to a real column (expand and contract).

  • Block: the operating system sees a disk and puts its own file system on it. Lowest latency and supports random in-place writes, which databases need. Usually attached to one server at a time, and you pay for the provisioned size.
  • File: many servers mount the same tree and use normal file operations (open, seek, append, rename, locks). Convenient for shared content and lift-and-shift apps, but throughput and metadata operations are limited by the file server, and it costs more than object storage.
  • Object: no directories (a "folder" is just a key prefix), no partial in-place edit, access by HTTP with keys like photos/2026/cat.jpg. Each object carries metadata. It scales almost without limit, is replicated across zones, and is the cheapest per GB. Latency is tens of milliseconds, not microseconds.

Decision rule. Databases and anything needing random in-place I/O: block. Shared POSIX-style access: file. User content, backups, logs, analytics data: object. Never run a database on object storage directly.

Why not store images in the database? Basic

In one line: large blobs bloat the database, its cache and backups and cost expensive I/O for data you never query, so store bytes in object storage and keep the key and metadata in the database.

What goes wrong with blobs in a table.

  • Size and backups: a 50 GB table of rows becomes 5 TB of images; backups, restores and replica builds take days instead of minutes.
  • Cache pollution: big values flow through the buffer pool and evict useful index and row pages, slowing every other query.
  • Replication and WAL volume: each upload is logged and shipped to every replica, causing lag.
  • Cost: database storage (fast SSD, replicated, with IOPS) costs far more per GB than object storage.
  • Serving: every image view goes through your app and database connection instead of a browser fetching directly from a CDN.

What object storage gives you. Cheap capacity, effectively unlimited scale with no sharding work, built-in cross-zone durability, direct delivery to browsers (pre-signed URLs) and CDN integration, lifecycle rules for tiering and expiry, and versioning.

The pattern. Upload bytes to the object store; save a row (id, owner, key, size, content_type, checksum, created_at) in the database. Reads: look up the row for permissions, then redirect to a signed URL or CDN path.

Honest exception. Very small blobs (a few KB, such as tiny avatar thumbnails or an encrypted key) can live in the database for simplicity and transactional consistency with their row. Cross over to object storage when values get into hundreds of KB or when volume grows.

How does an object store such as S3 achieve its durability and scale? Senior

In one line: an object store splits and redundantly stores each object across many disks and availability zones (replication or erasure coding), keeps key-to-location metadata in a separate partitioned index, and continuously verifies and repairs data; that is how it reaches very high durability and nearly unlimited scale.

Durability by redundancy.

  • Replication: keep 3 full copies in different failure domains. Simple, reads are easy, storage cost is 3x.
  • Erasure coding: split an object into k data fragments and compute m parity fragments; any k of the k+m fragments can rebuild the object. For example k=10, m=4 tolerates losing any 4 fragments and costs only 1.4x storage instead of 3x. The cost is CPU for encoding and more complex, slower repair and small-object reads.

Fragments are spread over many disks, racks and (for zonal classes) several availability zones, so a disk, rack or zone failure loses at most a few fragments.

Metadata and scale. The mapping from key to fragment locations lives in a separate, partitioned index service. Listing and lookup are range operations over the key space, and a single very hot key prefix can concentrate load on one index partition, which is why access patterns (and sometimes prefix design) matter at huge request rates. Data nodes scale out independently from the index.

Self-healing. Background scrubbers read data, verify checksums, detect bit rot and silently re-create lost or corrupt fragments. Durability comes from the repair rate outpacing the failure rate.

Numbers to quote carefully. AWS advertises 11 nines (99.999999999 percent) of annual durability for S3 standard, meaning an extremely low chance of losing an object; this is not availability, which is a separate and lower figure. S3 has offered strong read-after-write consistency for all operations since December 2020. Durability does not protect you from your own bug or an accidental delete, so use versioning, object lock and cross-region replication when needed.

How do you design uploads of large files (for example 5 GB videos)? Senior

In one line: never stream large files through your app servers; give the client a pre-signed URL for a multipart upload straight to object storage, track parts for resume, verify checksums, and trigger processing from a completion event.

Why not through the app? A 5 GB upload pinned to an app server ties up a connection, bandwidth and memory for minutes, and one failed connection restarts everything. Object storage is built to absorb exactly this load, in parallel.

  1. Authorise and presign. The client asks your API to upload (file name, size, type). The API checks permissions, quota and limits, creates a metadata row in PENDING, and returns a pre-signed URL (a time-limited URL bound to one key, method and sometimes size and content type). The bytes never touch your servers.
  2. Multipart upload. Split the file into parts (for example 8 to 100 MB). Upload parts in parallel, each with its own URL; retry only failed parts; finish with a "complete" call that assembles them. S3 allows up to 10,000 parts per object (parts of 5 MB to 5 GB, with up to 5 TB object size).
  3. Resumability. After a crash or network loss the client asks which parts are already stored (S3 ListParts) and continues with the rest. The tus protocol standardises this for resumable uploads.
  4. Integrity. Each part carries a checksum (MD5, CRC32C or SHA-256) verified by the store; the whole-file checksum is recorded in the metadata.
  5. Completion event. The store emits an event (to a queue or function) that triggers post-processing: virus scan, transcoding, thumbnail, metadata update to READY. The item shows "processing" until then.
  6. Cleanup. A lifecycle rule aborts incomplete multipart uploads after N days; otherwise orphaned parts silently cost money. A sweeper removes stale PENDING rows.
  7. Security. Enforce type and size limits at presign time and again after upload, scan before serving, and serve user content from a separate domain so scripts cannot read your cookies.

How to read this diagram. (1) The client asks the API service for permission and receives a pre-signed URL (top arrow). (2) The client then sends the file parts straight to the object store (moving dashes), so the large bytes never pass through the API. (3) When the upload completes, the store puts an event on the queue. (4) Workers take the event and run post-processing such as a virus scan or transcoding.

Pitfalls. Presigned URLs leak if logged or shared, so keep expiry short; very small files do not need multipart; clients on mobile networks need resumability more than anything else.

How do you serve large or popular files efficiently? Intermediate

In one line: put a CDN in front of object storage, use long-lived caching with versioned file names, support HTTP range requests, use signed URLs for private content, and use adaptive bitrate streaming for video.

  • CDN: popular files are cached at edge locations near users, so most requests never reach your origin and latency drops. Set Cache-Control headers appropriately.
  • Versioned or content-hashed names: publish app.3f9a2c.js or video/9001/v3.mp4. Because the name changes with the content you can cache for a year, and "invalidate" by simply referencing a new name, which avoids slow, expensive and unreliable purge operations.
  • Range requests: Range: bytes=1000000-1999999 lets a player seek and a download resume after failure, and lets clients fetch parts in parallel. Make sure the origin and CDN support partial content (206).
  • Private content: signed URLs or signed cookies with an expiry, checked at the CDN edge, so the CDN can still cache but only authorised users can fetch.
  • Video: pre-transcode into several resolutions and bitrates, chopped into few-second segments listed in a manifest (HLS or DASH). The player picks a quality that fits the current bandwidth and switches mid-stream (adaptive bitrate), so playback starts quickly and does not stall.
  • Protect the origin: use an origin shield or a mid-tier cache so a cold popular file results in one origin fetch, not thousands.
How would you avoid storing duplicate files? Intermediate

In one line: use content-addressable storage: name each blob by the hash of its bytes, so identical files share one stored copy, and track who references it with a reference row and reference counting or garbage collection.

How it works.

  1. Compute SHA-256 of the file (client side or server side).
  2. Check if an object with key sha256/ab/cd... exists. If yes, skip the upload entirely and just insert a row (user_id, file_name, content_hash). If no, upload it.
  3. Deleting a user's file removes only their row. The blob is deleted when nothing references it: either a reference count that reaches zero, or a periodic garbage-collection sweep (mark referenced hashes, delete the rest after a grace period). A race between "upload dedupes against existing blob" and "GC deletes that blob" is the classic bug, so use a grace period or transactional reference increments.

Chunk-level deduplication. For large files and sync tools (Dropbox-like), split into chunks (for example 4 MB), hash each chunk, and upload only the chunks the server does not have. Editing a small part of a big file then uploads one chunk. Fixed-size chunks are simple; content-defined chunking survives insertions at the start of a file better.

Benefits. Large storage and bandwidth savings (many users upload the same popular file), automatic integrity checking (the name is the checksum), and free immutability.

Privacy caveat. If the server tells a client "this hash already exists, skip upload", an attacker can test whether someone has a given file (a confirmation-of-file attack). Mitigate by requiring proof of possession (hash of random file ranges requested by the server) or by only deduplicating within one user or tenant. Also, per-user encryption defeats cross-user dedupe; that is a design choice.

How do you structure file metadata versus file data? Intermediate

In one line: keep file metadata in a database where you can query and enforce permissions, keep the bytes in object storage under a key you generate, and keep the two consistent with a PENDING to READY lifecycle plus a sweeper.

What goes where.

  • Metadata table: id, owner_id, display_name, size, content_type, checksum, storage_key, status, created_at, version. It supports listing, search by name, sharing rules, quotas and audit with ordinary queries and transactions.
  • Object store: only bytes. Key it by something you control, such as files/{tenant}/{uuid}, never by the user-supplied file name (names collide, can contain odd characters or path tricks such as ../, and leak information). Keep the original name as metadata only.

The consistency problem. A database and an object store cannot share a transaction. If you upload first and the metadata insert fails, you have an orphan object. If you insert metadata first and the upload fails, you have a row pointing at nothing. Use an order of operations with explicit states:

  1. Insert metadata with status = PENDING and the planned storage key.
  2. Upload the bytes (direct from client with a presigned URL).
  3. On the completion event (or after the client confirms and the server verifies with a HEAD request), set status = READY.
  4. A sweeper job deletes PENDING rows older than a threshold, and a second job lists objects with no matching row (orphans) and removes them after a grace period.

Only READY rows are visible to users. Deletion is the reverse: mark DELETING, delete the object, then remove the row (idempotently, because either step can fail and be retried).

Retention, tiering, time-series, analytics and search

How do you design data retention and archival? Intermediate

In one line: start from legal, business and privacy requirements, define hot, warm, cold and archive tiers with automated moves, delete by dropping partitions or lifecycle rules (never mass deletes), and test restores.

Why design it at all. Data grows forever if nobody decides otherwise. Keeping everything on fast replicated SSD is expensive, makes every query and backup slower, and can break privacy rules that require deletion. But deleting too early breaks audits. So retention is a product, legal and cost decision encoded in the storage design.

Step 1: requirements. For each data class (orders, audit logs, metrics, clickstream, chat) answer: how long must it be kept (legal or audit minimum), how long must it be fast (the product need), and when must it be deleted (privacy maximum).

Step 2: tiers.

Step 3: mechanism. Moving data is a copy, verify, then delete-from-source process, run as lifecycle policies (object storage transitions and expiry) or scheduled jobs. Partition tables by time so the "delete" is a cheap partition drop. Keep a catalog or index so archived records can still be found, for example "order 9001 is in archive file X".

Pitfalls.

  • An archive that cannot be read back is not an archive: schedule restore drills, and keep the readers for old file formats working.
  • Retention must reach all copies: backups, search index, caches, warehouse, logs. "Deleted" in the primary but alive in a backup is a compliance gap; define backup expiry too.
  • Make retention a per-data-class setting, not a hard-coded constant, so legal changes are a config change.
  • Legal hold: some records must pause deletion; build in a flag.
Why partition big tables by time, and how does it help retention? Intermediate

In one line: range-partition big tables by time so queries touch only relevant partitions (pruning), indexes stay small, and old data leaves through an instant partition drop instead of a giant delete.

What it is. One logical table is physically split into pieces, for example one partition per day or month, by the value of a timestamp column. To the application it is still one table.

Benefits.

  • Partition pruning: WHERE ts >= '2026-11-01' scans only November's partition(s), not the history.
  • Small per-partition indexes: the active partition's index fits in memory, so inserts stay fast (and avoids the random-insert slowdown of one giant index).
  • Cheap retention: ALTER TABLE events DETACH PARTITION events_2024_01; DROP TABLE events_2024_01; is a metadata operation that takes milliseconds and frees space immediately.
  • Maintenance: vacuum, reindex and backup can run per partition.

Compare with the alternative. DELETE FROM events WHERE ts < '2024-02-01' on 2 billion rows runs for hours, writes huge WAL, creates dead rows (table bloat and vacuum pressure), lags replicas and may hold locks. Dropping a partition avoids all of it.

The same idea elsewhere. Cassandra: TTL plus time-window compaction, so whole SSTables expire together. Elasticsearch: one index per day (or ILM rollover), then delete old indices. Time-series databases: chunks. Kafka: segment files and retention. Pattern: make the unit of deletion match the unit of storage.

Pitfalls. Create future partitions ahead of time (automate it, or inserts fail); queries without a time filter touch all partitions; a primary or unique key usually must include the partition column; too many tiny partitions hurt the planner.

What is downsampling and why do metric systems use it? Intermediate

In one line: keep raw data at full resolution for a short window and keep aggregated rollups (min, max, sum, count per interval) for longer, so long-range charts stay cheap while storage drops by orders of magnitude.

Why. A metrics system with a point every 10 seconds produces 8,640 points per series per day. A chart of the last year does not need them: the screen has maybe 1,000 pixels across, so one point per hour is plenty. Storing and querying raw data for a year would be hugely wasteful.

How. Define retention levels, for example:

A background job (or the database's continuous aggregation, such as Timescale continuous aggregates, Prometheus recording rules, Thanos or Mimir compaction) rolls each finer level into the next. Reading a year-long dashboard hits the hourly table: 360 raw points become 1 rollup per hour, a 360x reduction.

Do it correctly. Store sum and count (and min, max), not only the average. Averaging averages is wrong when the groups have different sizes, while sum and count can always be combined exactly. For latency percentiles, you cannot average p99s; store histograms or sketches (t-digest, HDR histogram) that merge.

Trade-off. You cannot recover short spikes inside a rolled-up interval, and ad hoc questions about old raw events are impossible. Keep max and percentile sketches when spikes matter, and archive raw data to cheap object storage if you might need it.

How does data get from the operational database into analytics storage? Intermediate

In one line: get operational data into analytics storage with batch ETL/ELT or, better for freshness and low source load, change data capture streaming from the database log into a lake or warehouse; never run heavy analytics on the primary.

  • Batch ETL or ELT: a nightly or hourly job extracts (queries tables), loads into a warehouse, and transforms with SQL (ELT does the transform inside the warehouse, which is the modern default). Simple and robust, but data is hours old, extracts add load to the source, and hard deletes can be missed unless handled.
  • Change data capture (CDC): a tool such as Debezium reads the database's replication log (binlog or WAL) and emits every insert, update and delete as an event to Kafka; sinks write them into the warehouse or lake. Low latency (seconds to minutes), almost no extra load on the primary (it reads the log, not the tables), and it preserves deletes and ordering per row.
  • Dual write from the application (write to the OLTP database and also publish to analytics): avoid it. The two writes are not atomic, so they diverge on partial failure. If the app must publish events, use the outbox pattern.

Where it lands. Raw data goes to object storage as Parquet partitioned by date (a data lake), so it is cheap and replayable; then query with Spark, Trino, Athena or load into a warehouse. A medallion layout is common: raw (bronze), cleaned (silver), modelled (gold).

Details that bite. Schema changes in the source must propagate (schema registry, compatibility rules); reconciling "latest state" from a stream of changes needs merge or upsert logic (Iceberg, Delta and Hudi support it); initial snapshot plus streaming must be stitched without gaps; and PII must be masked before it lands.

Rule. Heavy analytics belong on a separate system. At most, use a dedicated read replica for modest reports, and know that long queries on a replica can conflict with replication replay or hold back cleanup.

In one line: a warehouse stores curated, structured data for fast, governed SQL and BI; a lake stores raw data of any form in cheap object storage for reprocessing and data science; lakehouse table formats blur the line.

Why both exist. A warehouse gives analysts quick, consistent answers, but loading everything into it first is expensive and forces decisions early. A lake lets you dump everything cheaply now and decide later, but without discipline it becomes a "data swamp" (unknown, untrusted files) and plain files have no transactions, so concurrent writers or updates are unsafe.

Lakehouse. Open table formats (Apache Iceberg, Delta Lake, Hudi) add a metadata layer over Parquet files in object storage: ACID commits, schema evolution, time travel, upserts and deletes, partition evolution. How does full-text search work at a conceptual level? Intermediate

In one line: full-text search analyses text into tokens, stores an inverted index (term to list of documents), ranks matches with a relevance score such as BM25, and splits the index into shards so queries fan out and merge.

  1. Analysis: split text into tokens, lowercase, remove stop words ("the", "a"), and stem ("running" becomes "run") so word variants match. The same analysis is applied to the query.
  2. Inverted index: like the index at the back of a book. For each term, a posting list of document ids (and positions, for phrase search). 
    doc1: "red running shoes"   doc2: "blue shoes"   doc3: "red shirt"
red   -> [doc1, doc3]
shoes -> [doc1, doc2]
run   -> [doc1]
Query "red shoes": red AND shoes -> [doc1]  (OR would give doc1, doc2, doc3)
    Intersecting sorted lists is fast.
  3. Ranking: rank results by relevance, classically TF-IDF and now BM25: more occurrences of a term in the document raise the score (with diminishing returns), terms rare across the corpus count more ("shoes" matters more than "the"), and shorter fields score higher. Add boosts (title over body, recency, popularity).
  4. Scale: the index is split into shards across nodes; a query fans out to all shards, each returns its top results, and a coordinator merges them. Replicas give availability and read capacity.

Why not SQL. LIKE '%shoe%' cannot use a B-tree (leading wildcard) and scans every row, with no relevance and no stemming. Postgres full-text search (tsvector with GIN) is enough for modest needs and keeps one database.

When to use a dedicated engine. Faceting and filtering at scale, fuzzy matching and typo tolerance, autocomplete, multiple languages, relevance tuning, very large corpora. Remember the engine is a derived index (see the search-engine and search-sync questions).

How do you keep a search index in sync with the primary database? Senior

In one line: feed the index from the source of truth with outbox or CDC events, index with external versions so late events cannot overwrite newer state, handle deletes explicitly, plan reindexing with aliases, and expect (and design for) lag.

  • Outbox or CDC: the primary database emits a change event for every committed write (outbox row in the same transaction, or log-based CDC). An indexer consumes the events and updates the search index. Events are ordered per key and survive crashes, unlike dual writes from application code that can diverge when one write fails.
  • Use versions: events can arrive late, duplicated or out of order (retries, parallel consumers). Index with an external version, such as a row version or updated_at; the engine then rejects an older version. This makes the indexer idempotent. In Elasticsearch use version_type=external.
  • Handle deletes: a delete is an event too (a tombstone). If you only handle upserts, deleted products stay searchable forever. Use soft-delete flags or delete events.
  • Reindex plan: mapping changes (field type, analyzer) need a new index. Build the new index in parallel from the source (a backfill) while also applying live changes, then switch an alias atomically from the old index to the new one, keep the old for rollback, and delete it later. Reads never notice.
  • Expect lag (seconds or more under load): monitor it. Where users must see their own write (the post they just created), read that item from the primary or merge it in optimistically, instead of waiting for the index.
  • Reconciliation: periodically compare counts or checksums between source and index to catch missed events, and keep a way to rebuild fully.
How would you store and query location data ("restaurants within 2 km")? Senior

In one line: use a geospatial index (R-tree style) or map points to geohash, S2 or H3 cells so nearby points share a cell; query the target cell plus its neighbours, then filter by exact distance.

The problem. Two plain columns lat and lon with a B-tree index let you filter ranges on one column, but "within 2 km" is a 2D region. The database can use the index for latitude, then scan all rows in that horizontal band at every longitude. That is far too many rows. We need an index that is 2D-aware.

Options.

  • Geospatial index in a database: PostGIS with GiST (R-tree), MongoDB 2dsphere, Redis GEO (a sorted set over geohash scores), Elasticsearch geo_point. You write ST_DWithin(location, point, 2000) and the index handles it.
  • Cell-based mapping: convert each point to a cell id on a space-filling curve or grid: geohash (a base-32 string where a longer prefix means a smaller cell and shared prefixes mean nearby), Google S2 or Uber H3 (hierarchical cells, hexagons for H3). Store the cell id as an ordinary indexed column, which also works in key-value and wide-column stores that have no spatial index.

Query steps for "restaurants within 2 km".

  1. Pick a cell size close to the radius (a geohash of about 5 characters is roughly a 5 km cell).
  2. Compute the user's cell and its 8 neighbours.
  3. Fetch restaurants in those 9 cells by an indexed lookup.
  4. Compute exact distance (haversine) for each candidate, keep those within 2 km, sort by distance.

Pitfalls. Geohash has edge effects: two close points on either side of a cell boundary may have totally different prefixes, so checking only the user's cell misses results; always include neighbours. Dense areas (city centres) put thousands of points in one cell, and sparse areas few, so use adaptive subdivision (quadtree) or finer cell levels. Also account for the Earth's curvature in distance and for the date line and poles.

Connection pooling, N+1 and slow queries

What is connection pooling and why is it needed? Basic

In one line: a connection pool keeps a bounded set of open database connections that application threads borrow and return, avoiding the expensive setup cost per request and protecting the database from too many connections.

Why connections are expensive. A new connection needs a TCP handshake, TLS negotiation, authentication, and session setup; in Postgres each connection is a separate server process with its own memory (several MB). The database can hold only so many: often a few hundred before performance drops. Opening one per request adds 10 to 50 ms of latency and can exhaust the server in a traffic spike.

How a pool works.

  1. At startup the pool opens a few connections (minimum idle).
  2. A request borrows one (dataSource.getConnection()), runs its queries, and "closes" it, which actually returns it to the pool.
  3. If all connections are busy, the caller waits up to a timeout, then fails.
  4. The pool replaces dead or too-old connections.

Key settings.

  • Maximum pool size: hard cap on connections from this process.
  • Minimum idle: connections kept warm.
  • Connection timeout: how long a caller waits for a free connection before an error.
  • Idle timeout and max lifetime: retire old connections; max lifetime should be shorter than any firewall, load balancer or database idle cut-off, otherwise you get stale connections that fail on first use.
  • Validation or keepalive: detect dead connections after a failover.
  • Leak detection threshold: log when a connection is held too long.

Examples. HikariCP is the standard in-process pool in Java. PgBouncer and RDS Proxy are external poolers that multiplex many client connections onto fewer server connections; useful with many app instances or serverless functions.

How do you size a connection pool? Senior

In one line: a small pool is usually faster than a big one; size it from the database's real parallelism, and make sure instances times pool size stays below the database's max connections.

Why bigger is not better. A database does real work in parallel only as far as it has CPU cores and disk parallelism. Say it has 8 cores. With 200 active connections, 192 are just waiting in queues inside the database, burning memory and context switching, so total throughput drops and every request gets slower. A well-known benchmark and the HikariCP "About Pool Sizing" note show a small pool outperforming a large one by a wide margin.

Starting point. A common formula is about (2 x cores) + effective spindles for the total number of useful connections to one database (for an SSD-backed database that means a figure in the tens, not hundreds), then test under load. This is a starting point, not a law.

Little's law for the demand side. Connections busy at once is about arrival rate times time per query: 200 queries per second x 0.02 seconds = 4 busy connections. A pool of 10 is plenty; the pool exists mostly for bursts.

The multiplication trap. The limit is on the database, but the pool is per application instance. Instances x pool size must stay under the database's max connections (and leave room for admin, migrations and replicas). With 50 pods and a pool of 20 you demand 1,000 connections. An autoscaler that adds pods during a traffic spike can then push the database past its limit and take it down exactly when it is busiest.

Options. Reduce the per-instance pool (3 to 10 is often enough); put PgBouncer in transaction mode in front (clients hold a server connection only during a transaction; note that session-level features such as session variables, advisory locks and some prepared statements need care); cap autoscaling; give batch jobs their own small pool.

Requests suddenly hang with "timeout waiting for connection from pool". What happened? Senior

In one line: the pool ran out of free connections because they are held too long or leaked; find out which with pool metrics and slow-query logs, fix the cause, and do not just raise the pool size.

What the error means. "Timeout waiting for connection from pool" means every connection is checked out and a new request waited past the connection timeout. Requests hang, then fail; users see timeouts across the whole app, even for endpoints that have nothing to do with the cause, because they share the pool.

Causes, roughly in order of frequency.

  • Connection leak: code borrows a connection and never returns it (missing close, exception path, a stream not closed). Pool "active" count climbs and never falls even at low traffic. Enable leak detection (HikariCP leakDetectionThreshold), which logs the stack trace that borrowed it. Use try-with-resources or managed transactions.
  • Slow queries or a lock: connections stay busy longer, so the pool's throughput drops. A single long transaction blocking others makes requests pile up waiting on locks while holding connections.
  • Holding a connection during slow non-database work: an external HTTP call inside a transaction (or inside an open JPA session with open-in-view) ties up a connection for the duration of that call.
  • Traffic spike or retry storm: demand briefly exceeds capacity and timeouts cause retries that make it worse.
  • Failover: after a database failover the pool holds dead connections; each fails on use and is slow to be replaced.

Investigation. Look at pool metrics (active, idle, pending threads), database view of sessions (pg_stat_activity: who is idle in transaction, who waits on locks), and slow-query logs.

Fixes. Fix the leak or the slow query; keep transactions short and database-only; set statement timeout and idle-in-transaction timeout; add circuit breaking so retries back off. Raising the pool size just moves the overload to the database, which makes things worse.

What is the N+1 query problem and how do you fix it? Basic

In one line: N+1 is loading a list with one query and then issuing one extra query per item for related data; fix it with a join, a batched IN query, or the ORM's batch or eager fetching, and detect it by counting queries per request.

Example. Show 100 orders with each customer's name.

SELECT * FROM orders LIMIT 100;               -- 1 query
SELECT * FROM customers WHERE id = 7;         -- repeated 100 times
...                                           -- total 101 queries

Each small query takes about 2 ms and one network round trip, so 100 of them cost about 200 ms of latency plus 100 times the per-query overhead on the database, instead of one or two queries taking maybe 10 ms. It stays invisible with 5 rows in a dev database and becomes a production incident with 5,000 rows. It is common with ORMs because lazy loading hides the extra query behind a getter call (order.getCustomer()).

Fixes.

  • Join or fetch join: SELECT o.*, c.* FROM orders o JOIN customers c ON c.id = o.customer_id; in JPA, JOIN FETCH or an entity graph.
  • Batched second query: load the orders, collect the customer ids, then SELECT * FROM customers WHERE id IN (...) and match in memory: 2 queries total. Hibernate offers @BatchSize to do this automatically.
  • Data loader pattern: batches and caches lookups within one request (common in GraphQL resolvers).

Caveat. Joining several collections at once multiplies rows (orders x lines x payments) and can be worse than N+1; then use separate batched queries per collection.

Detection. Log SQL count per request, assert a maximum number of queries in integration tests, and look at APM traces for repeated identical statements.

A query became slow in production. How do you investigate? Senior

In one line: confirm and scope, read the execution plan, check the environment (locks, cache, I/O, replication), apply the cheapest effective fix, then add prevention.

  1. Confirm and scope: which query, since when, how often, how slow (compare p50 and p99)? Use the slow query log or pg_stat_statements to rank by total time (calls x average), since a moderately slow query called a million times hurts more than a rare very slow one. Ask what changed: a deploy, data growth, new traffic, schema change, index dropped, new database version?
  2. Look at the plan: EXPLAIN (ANALYZE, BUFFERS) shows what actually happened. Signals: a sequential scan on a big table where you expected an index; estimated rows versus actual rows far apart (stale statistics or a correlation the planner cannot see); a sort or hash spilling to disk; a nested loop over a large set; many rows fetched and then discarded by a filter (the index is not selective on the right column).
  3. Check the environment: lock waits, long-running or idle-in-transaction sessions, cache hit ratio, I/O saturation, replication lag, connection count, a noisy neighbour, a vacuum or compaction in progress. The same query can be fast alone and slow under contention.
  4. Fix by the cheapest effective action: add or reshape an index (composite, covering, partial); rewrite the query (select only needed columns, remove functions on indexed columns, replace OFFSET with keyset); update statistics (ANALYZE); batch or paginate; cache or precompute; only then consider schema redesign or sharding.
  5. Prevent: alert on query latency percentiles, load-test with production-sized data, review plans for new queries in code review, and keep a regression check on top queries.

Habit to mention: change one thing at a time and re-measure, and test an index on a copy before creating it on a busy production table.

How do you read an EXPLAIN plan? What are the first things you look for? Intermediate

In one line: EXPLAIN shows how the database intends to run the query (scan types, join methods, estimated cost and rows); EXPLAIN ANALYZE also runs it and shows actual time and rows, and the gap between estimate and actual is the most useful clue.

What the planner does. For each query the optimizer considers several ways to run it (which index to use, which join order, which join algorithm) and picks the one with the lowest estimated cost, using table statistics. The plan is a tree: leaf nodes read data, parent nodes combine it.

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE user_id = 42 ORDER BY created_at DESC LIMIT 20;

Limit  (cost=0.43..8.9 rows=20) (actual time=0.05..0.09 rows=20 loops=1)
  -> Index Scan Backward using idx_orders_user_created on orders
       Index Cond: (user_id = 42)

What to look for.

  • Scan type: Seq Scan on a big table when you expected an index; Index Scan or Index Only Scan is the good sign; Bitmap Heap Scan is a middle ground for medium selectivity.
  • Estimated versus actual rows: if the planner expected 10 rows and got 1,000,000, its statistics are stale or it cannot see a correlation, and it probably chose a bad join order or algorithm. Run ANALYZE or add extended statistics.
  • Join method: a nested loop over a large set is a red flag; hash join and merge join suit big inputs.
  • Sort and hash spilling to disk ("external merge", "Disk: ..."): needs an index or more memory.
  • Rows removed by filter: many rows read but few kept means the index is not selective on the right column.
  • Loops: a cheap node executed a million times (the inner side of a nested loop) is the real cost: multiply time by loops.
  • Buffers: shared read versus hit shows cache misses and disk I/O.

Caveats. Plain EXPLAIN is only an estimate; ANALYZE actually executes the statement (wrap writes in a transaction you roll back). Plans can differ between development and production because of data size and statistics, and a plan can flip when statistics change, which is a classic "it was fast yesterday" cause.

Why does LIMIT 20 OFFSET 1000000 get slower, and what is the alternative? Intermediate

In one line: OFFSET pagination must produce and throw away all earlier rows, so it gets slower with every page; keyset (seek) pagination continues from the last seen key and costs the same on every page.

Why OFFSET is slow. LIMIT 20 OFFSET 1000000 makes the database walk through (and sort, if needed) 1,000,020 rows and discard the first million. Page 50,000 is 50,000 times as much work as page 1. Another flaw: if rows are inserted or deleted while the user browses, the page boundaries shift, so rows are repeated or skipped.

Keyset pagination. Remember the sort key of the last row on the current page and ask for rows after it:

-- first page
SELECT * FROM posts ORDER BY created_at DESC, id DESC LIMIT 20;
-- next page, given last row (created_at = T, id = 9731)
SELECT * FROM posts
WHERE (created_at, id) < (:T, :9731)
ORDER BY created_at DESC, id DESC LIMIT 20;
-- supported by: CREATE INDEX ON posts (created_at DESC, id DESC);

The index lets the database jump straight to the position and read 20 rows: constant cost per page. The id is a tie-breaker so that rows with equal created_at are not skipped; the sort key must be unique and deterministic. The API returns an opaque cursor token encoding the last key.

Trade-off. No random access ("jump to page 500") and no cheap total count; but feeds, timelines and infinite scroll do not need those. If you need page numbers on a modest table, OFFSET is acceptable; cap the maximum offset.

Name common query-level mistakes that hurt performance. Intermediate

In one line: the usual query-level mistakes are fetching more than you need, doing work row by row instead of set-based, defeating indexes, running unbounded or counting queries on hot paths, and holding transactions open.

  • SELECT * when you need 3 columns: more I/O, more network and memory, wide or large columns dragged along, and covering indexes become impossible. Name columns.
  • Queries in a loop instead of one set-based query (N+1), and row-by-row inserts instead of batches. Inserting 1,000 rows in one multi-row statement or batch, or with bulk load (COPY), can be 10x to 100x faster because it saves network round trips and per-statement and per-commit overhead.
  • Functions on indexed columns and implicit type casts, which disable the index.
  • Unbounded queries with no LIMIT: one careless endpoint loads millions of rows into memory.
  • Huge IN lists and COUNT(*) on a very large table on the hot path (an exact count scans). Keep a maintained counter, use approximate counts (planner statistics), or avoid showing totals.
  • Long transactions and holding locks while calling other services, which block others and hold pool connections.
  • Sorting large result sets without an index, spilling sorts to disk.
  • Fetching then filtering in the application what the database could filter, so you transfer rows only to discard them.

Each of these looks harmless on a small development database and only fails at production volume, which is why you test with realistic data sizes.

Read-heavy versus write-heavy design

What are the main levers for a read-heavy workload? Intermediate

In one line: for a read-heavy workload apply the cheapest levers first: fix queries and indexes, add caching, add read replicas, precompute and denormalize, use a search or column store for complex reads, and shard last.

  1. Indexes and good queries: the cheapest and most effective. A missing index can be a 1000x difference; nothing else comes close in cost-benefit.
  2. Caching: an application cache (Redis) for hot objects, HTTP and CDN caching for public content. Highest leverage, because most reads never reach the database. A 95 percent hit rate means the database sees 5 percent of the reads (a 20x reduction). Cost: invalidation and staleness.
  3. Read replicas: scale reads horizontally; the cost is replication lag (a read after a write may see old data), so route read-your-writes traffic to the primary for a short time.
  4. Denormalize or precompute: materialised views, summary tables, precomputed feeds, so reads do no joins or aggregation.
  5. Search engine or column store for complex read patterns (text search, faceting, analytics) that a row-store B-tree does badly.
  6. Sharding when even this is not enough, mainly when the data or working set no longer fits one node.

Storage of choice: a B-tree based relational store with replicas plus a cache. Say what each lever costs (staleness, complexity) and that you measure the hit rate and replica lag.

What are the main levers for a write-heavy workload? Intermediate

In one line: for a write-heavy workload use a write-optimised engine, shard writes by a well-distributed key, put a queue or log in front to batch and smooth spikes, make each write cheaper, aggregate before storing, and be explicit about durability trade-offs.

  1. Write-optimised engine: LSM-based stores (Cassandra, ScyllaDB, HBase, RocksDB-based systems) turn writes into sequential appends and sustain far higher ingestion than a B-tree primary.
  2. Shard (partition) writes by a key with good distribution so no hot partition forms. Read replicas do not help writes, because every replica must apply every write; only partitioning splits the write load.
  3. Batch and buffer: put a queue or log (Kafka) in front. Producers are acknowledged quickly, spikes are absorbed, and consumers write in batches (one commit for 1,000 rows) at the store's own pace. Group commit does the same inside the database.
  4. Reduce the cost per write: fewer indexes (each index is another write), narrower rows, append-only models instead of update-in-place, and building secondary structures asynchronously.
  5. Aggregate before storing when raw events are not needed individually (counters, rollups, sampled metrics).
  6. Mind durability settings: relaxing fsync or replication acknowledgement buys speed at the cost of possible loss of recent writes; do it only where acceptable and say so.

What to watch. Partition skew, compaction backlog, replication lag and queue depth. Also decide how reads will work: write-optimised stores often make reads and ad hoc queries harder, so plan a derived read model if needed.

How do you quickly estimate whether one database node can handle the load? Intermediate

In one line: convert business numbers into requests per second, payload and data volume, compare each against one node's rough capacity (hedged), and plan sharding or a distributed store as soon as writes, storage, or the RAM working set exceed a single node.

Rough single-node figures (hedge them, hardware varies widely): a well-tuned relational node on SSD handles on the order of 1,000 to 10,000 simple writes per second and maybe 10,000 to 50,000 indexed reads per second; an LSM store node often ingests tens of thousands of writes per second.

Worked example.

  1. 100 million daily active users x 10 requests = 1 billion requests per day.
  2. 1,000,000,000 / 86,400 seconds is about 11,600 requests per second on average; assume peaks of 2x to 5x, so 25,000 to 60,000 per second.
  3. Split read versus write: if 10 percent are writes, about 1,200 writes per second average, peak maybe 6,000. Reads at 10,000 to 50,000 per second need replicas or a cache.
  4. Storage: 1,200 writes per second x 1 KB x 86,400 seconds is about 100 GB per day, about 36 TB per year before indexes and replicas, times retention. Compare to a node's disk (a few TB) and RAM for the working set.

Conclusion for that example: writes fit one strong node on throughput, but yearly storage and read volume say: partition by time, use replicas and a cache, plan to shard if retention is long.

Rule. Check each axis separately: write rate, read rate, data size, and working set in RAM. Exceeding any one means moving beyond a single node. Always ask for the read/write split, payload size and retention first, since they drive everything.

What is a materialized view and when do you use one? Intermediate

In one line: a materialized view stores the result of a query as a physical table that is refreshed on a schedule or incrementally, trading storage and refresh work for fast reads of an expensive aggregation.

Normal view versus materialized view. A normal view is a saved query: every read re-runs it. A materialized view runs the query once, stores the rows, and later reads just read them.

CREATE MATERIALIZED VIEW daily_sales AS
  SELECT date_trunc('day', ts) AS day, region, SUM(amount) AS revenue
  FROM orders GROUP BY 1, 2;
REFRESH MATERIALIZED VIEW CONCURRENTLY daily_sales;  -- needs a unique index

When it fits. An expensive aggregation or join (scanning hundreds of millions of rows) is read often, and being a little stale is acceptable: a daily sales dashboard, a leaderboard refreshed every minute, a report table.

Caveats.

  • Staleness: data is only as fresh as the last refresh.
  • Refresh cost: a full recompute can be heavy. Some databases support incremental refresh (Oracle, some warehouses, Timescale continuous aggregates); Postgres built-in materialized views refresh fully. Check whether refresh blocks reads (CONCURRENTLY in Postgres avoids that at extra cost).
  • It is extra storage that also needs indexes.

Alternatives. A summary table maintained by your own job or by triggers or stream processing (more control, more code), or a cache. Choose a materialized view for simplicity, a stream-maintained table for freshness.

What is the idea of separating the write model from the read model (CQRS) in storage terms? Senior

In one line: CQRS in storage terms means writes go to a store shaped for correctness (normalised relational or an event log), and a pipeline projects changes into read stores shaped for each query (denormalised documents, search index, cache, column store); you gain independent scaling and pay with eventual consistency and extra parts.

The idea. One data model rarely suits both writing and reading. Writing wants normalised data, constraints and transactions so the rules are enforced once. Reading wants data pre-joined and pre-shaped for each screen or API. CQRS (Command Query Responsibility Segregation) separates the two: commands change state through the write model; queries read from one or more read models.

Flow.

  1. A command (place order) is validated and saved in the write store, in a transaction; this also emits an event (outbox or log).
  2. Projectors consume events and update read models: an order-list table for the user page, a search index, a cache entry, an analytics store.
  3. Queries read the read models directly: no joins, tuned indexes, horizontally scalable.

Benefits. Each side scales and is tuned independently (a read-heavy product can have many read replicas and caches); each read model uses the best store for its query; you can add a new read model by replaying the event log into it.

Costs.

  • Eventual consistency: the read side lags the write side; users may not see their change immediately (handle with read-your-writes routing or optimistic UI).
  • More moving parts: pipeline, projectors, monitoring, rebuild tooling.
  • Rebuilding a projection from the log when a read model changes needs the log to be retained and replay to be fast.

When to use it. When read and write shapes or loads differ greatly or you need several different read models. Do not use it by default; a single database with indexes and a cache covers most systems. CQRS does not require event sourcing, though they are often combined.

Scenarios and real-life problems

Your primary database CPU is at 95 percent every afternoon and latency is climbing. What do you do? Senior

Say this: "Measure first, change one thing at a time, and fix in order: stop the bleeding, cheap fixes, structural fixes."

  1. Triage now (minutes): rank queries by total time (calls x average) in pg_stat_statements or the slow log, not only by slowest single query. The afternoon pattern points to a scheduled job, a traffic peak in some region, or a report. Check what changed: a deploy, a new feature, a dropped index, a plan flip after statistics changed. Throttle or kill the offending job; shed non-essential load (pause batch work, disable a heavy endpoint, serve stale cache).
  2. Short-term fixes (hours): add the missing index online (concurrent build, lock timeout); move reports to a replica; cache the hottest read; lower pool sizes if too many connections are thrashing the CPU with context switching; fix the N+1 or the unbounded query.
  3. Medium term (weeks): read replicas for read traffic, rewrite heavy queries, denormalise hot paths, partition large tables, add a queue to smooth write spikes.
  4. Long term: scale up the instance if it is the cheap option, then sharding or moving specific workloads (search, analytics, sessions) to better-fit stores.

Worked example. Top query by total time is SELECT ... FROM events WHERE account_id = ? AND ts > ? at 40 percent of CPU, doing a sequential scan since an index was dropped in a recent migration. Fix: recreate the index concurrently; CPU drops; add an alert on this query's latency; add the index to the migration review checklist.

Show you will also prevent recurrence: dashboards on query latency, load tests, and capacity forecasting.

A DynamoDB or Cassandra table throttles even though total capacity looks fine. What is wrong? Senior

In one line: a hot partition: one key takes a disproportionate share of traffic, and per-partition limits apply no matter how much total capacity the table has; fix it with a better or sharded key, caching and splitting large tenants.

Why total capacity does not help. In DynamoDB (and similarly Cassandra, Bigtable), data is spread across partitions by hashing the partition key, and each partition can serve only a fixed amount of throughput (DynamoDB documents per-partition limits of about 3,000 read units and 1,000 write units per second; hedge exact figures). If 40 percent of requests use the same key (a celebrity user, a "today's date" key, a single huge tenant), they all land on one partition and throttle, while the others sit idle. The table's headline capacity is the sum over partitions, not available to one key.

Diagnose. DynamoDB CloudWatch Contributor Insights shows the most accessed keys; Cassandra shows per-node and per-partition metrics (nodetool toppartitions). Look at key distribution against expected traffic, not row counts: many keys can exist while traffic concentrates on one.

Fixes.

  • Choose a higher-cardinality key (user id plus something, not just date or country).
  • Write sharding with a suffix: append a random or calculated suffix, post#123#0 to post#123#9. Writes spread over 10 partitions; reads query all 10 suffixes and merge (or sum, for counters).
  • Cache hot reads in front of the store (DynamoDB DAX, Redis, CDN) so repeated reads of the same key do not reach the partition.
  • Combine time with another dimension for time-based keys (date plus user id), so "today" is not one key.
  • Split big tenants onto dedicated partitions or tables.

Prevent. Check key distribution before launch with realistic traffic skew (real traffic follows a power law), and load-test the hottest key.

A migration that added an index locked the orders table for 20 minutes during peak. How do you prevent a repeat? Senior

In one line: use online DDL with a lock timeout, rehearse on production-sized data, schedule off-peak with a kill switch, review DDL against a checklist, and use online schema-change tools for big changes.

What probably happened. A plain CREATE INDEX (or an engine that needs a table-level lock for the build) blocked writes to orders for the 20 minutes it took to scan and sort a large table. Requests queued, pool connections filled, and the incident spread to everything touching orders.

  • Online index creation: CREATE INDEX CONCURRENTLY (Postgres) or online DDL with ALGORITHM=INPLACE, LOCK=NONE (MySQL) allow writes during the build. Takes longer, but does not block. Note a failed concurrent build leaves an invalid index to clean up.
  • Lock timeout: set lock_timeout (and for sessions, a statement timeout) so the migration gives up quickly instead of queueing behind a long query and blocking everyone behind it; retry later.
  • Rehearse on a production-sized copy to learn duration, I/O, and replication lag effects. A 10-second index on staging can be 20 minutes on production.
  • Operational safeguards: run in an off-peak window, watch replication lag and active locks live, and have a kill switch (cancel the statement) and rollback plan.
  • Review DDL like code with a checklist: which lock, how long, does it rewrite the table, is the backfill batched, is it reversible?
  • Big changes: gh-ost or pt-online-schema-change, or expand and contract, instead of one blocking statement.
A write-heavy database disk hit 100 percent and the database stopped accepting writes. How could this happen and what do you do? Senior

In one line: the usual culprit is something retaining logs or old versions (a stuck replication slot, a long transaction) or unbounded growth; free space safely, fix the cause, then add alerts and limits.

How it happens.

  • WAL or binlog growth: a replica or CDC consumer (Debezium) stopped consuming. In Postgres, a replication slot forces the primary to retain all WAL the slot has not yet confirmed, so a dead consumer makes the WAL directory grow until the disk is full. A well-known hazard.
  • Long-running transaction prevents vacuum from removing old row versions, so tables bloat.
  • Compaction (LSM) needing temporary space, especially size-tiered with a disk already above 50 to 60 percent.
  • Unbounded table growth with no retention job, or a log or audit table nobody cleans.
  • Runaway temp files from a bad query sorting or joining huge sets.

Response.

  1. Stop the growth: find and fix or remove the stuck slot or consumer (dropping a slot means the consumer must resync), kill the runaway query or the long transaction.
  2. Free space safely: drop or archive old partitions, delete rotated logs and old backups on the data volume, extend the volume online if the platform allows. Never delete WAL files by hand; that corrupts the database.
  3. Bring writes back, verify consistency, and check replicas.

Guardrails. Alerts on disk at 70 and 85 percent and on growth rate (predict time to full); cap replication slot retention (Postgres max_slot_wal_keep_size); alert on slot lag; retention jobs; alerts for transactions open too long; capacity forecasting; keep WAL and data on separate volumes.

Users update their profile and, on refresh, see the old value. The system uses read replicas. Why, and how do you fix it? Intermediate

In one line: asynchronous replication lag means the replica has not yet applied the user's write; fix it with read-your-writes routing, session stickiness, immediate client or cache updates, or synchronous replication for critical paths.

Timeline.

  1. t=0: user submits a new display name; the write goes to the primary and commits.
  2. t=10 ms: the browser reloads the profile page; the read is routed to a replica.
  3. The primary has not yet shipped or the replica has not yet applied that change (lag from tens of milliseconds to seconds, longer under load or a big transaction), so the replica returns the old name.

The user thinks the save failed. This violates read-your-writes consistency.

Fixes.

  • Read-your-writes routing: after a write, send that user's reads to the primary for a short window (for example 5 seconds), or until the replica's log position (LSN, GTID, or a version token) has passed the write's position. The app stores the position returned by the write and passes it on reads.
  • Sticky routing per session to one replica (gives monotonic reads, which prevents seeing newer data and then older data) plus primary reads for the user's own recent writes.
  • Optimistic client update: the UI or the cache holds the new value immediately; or write-through to the cache on update.
  • Synchronous (or semi-synchronous) replication for critical paths, at the cost of higher write latency and availability risk.
  • Route only safe reads to replicas: reports and public pages tolerate lag, "my profile after I edit it" does not.

Operate. Monitor replica lag; when lag exceeds a threshold, fall back to the primary or remove the replica from rotation.

You need to pick storage for a messaging inbox with 1 billion messages per day and a "load latest 50 messages of a conversation" query. What do you reason? Senior

In one line: this is a high-append, read-latest-N-per-conversation workload, which points to an LSM wide-column or key-value store partitioned by conversation and clustered by time descending.

Reasoning, step by step.

  1. Dominant operations: very high append rate (1 billion messages per day is about 11,600 writes per second on average; peaks maybe 3 to 5 times that), read the newest 50 messages of one conversation, almost never update, keep data for a long time.
  2. Access pattern shape: always "one conversation, newest first, limit 50". No joins, no cross-conversation scans. That is a single-partition range read.
  3. Store: an LSM wide-column store (Cassandra, ScyllaDB, HBase) or a key-value store with a sort key (DynamoDB). LSM gives very fast sequential writes and the cluster scales horizontally by adding nodes.
  4. Data model: partition key (conversation_id, bucket), clustering key message_id DESC (time-ordered id, such as a snowflake id or UUID v7). The newest 50 are the first 50 rows of one partition: one sequential read. 
    PRIMARY KEY ((conversation_id, month), message_id)
WITH CLUSTERING ORDER BY (message_id DESC)
  5. Watch partition size: a very busy group chat can have millions of messages, which makes an unbounded partition. Bucket by time (per month or per N messages) and, when a read needs more than 50, read the next bucket.
  6. Other needs: keep older data in cheaper tiers, keep search over history as a separate derived index (Elasticsearch), keep read state or unread counts in a separate small table, and use idempotent writes keyed by message id for retries.

Honest alternative. A relational store (Postgres, MySQL) with an index on (conversation_id, id DESC) works at smaller scale and has simpler operations. The argument for wide-column here is write volume and horizontal scaling. (This is reasoning about a storage choice, not a full design.)

Insert latency on a table keeps degrading as it grows past memory, though the query load is unchanged. What is likely and what do you do? Senior

In one line: a random UUID primary key is the likely cause; once the index is bigger than memory, each insert needs a random disk read and a page split. Use time-ordered keys, partition by time, drop unneeded indexes, and add RAM.

Why it degrades "as it grows past memory".

  1. With a random key (UUID v4), each new row belongs at a random place in the B-tree, so each insert touches a random leaf page.
  2. While the whole index fits in RAM, that is cheap: all pages are cached.
  3. Once the index exceeds RAM, most of those random leaf pages are not in cache, so each insert first reads a page from disk (about 100 microseconds on SSD, milliseconds on spinning disk), then modifies it, and often splits it because pages fill up randomly. Pages end up about half full, so the index grows even faster.
  4. Also each secondary index entry has the 16-byte key, multiplying the effect, and every secondary index has the same random-insert problem if its leading column is random.

Query load did not change, but the working set no longer fits, so latency climbs smoothly with size. That matches the symptom.

Remedies.

  • Time-ordered keys: UUID v7, ULID, or a bigint sequence, so new rows go to the right edge of the index, which stays in cache regardless of table size.
  • Remove unneeded indexes to cut the number of random writes per insert.
  • Partition by time so the active partition's index is small and fits in memory.
  • More RAM buys time but does not remove the cause.

Migration warning. Changing the primary key of a large live table cannot be one statement; use expand and contract (new table or column, dual write, backfill, switch, retire). Note: engines with clustered primary keys (InnoDB) suffer most, since the table itself is the primary-key B-tree.

Can you describe an industry incident where database operations or backups failed badly, and the lessons? Senior

In one line: GitLab 2017 shows that backups are only real if restores are tested, that destructive commands on production need guardrails, and that backup and replication jobs must be monitored.

What happened (as publicly described by GitLab; check their post-mortem for exact figures). On 31 January 2017, while fighting replication lag on the production PostgreSQL, an engineer, tired and late at night, intended to wipe the data directory on the broken secondary but ran the delete on the primary. Much of the production data directory was removed before it was stopped. Recovery was hard because several backup mechanisms turned out not to be working: regular dumps were failing silently (a version mismatch meant they produced empty output, and the failure alerts were not being delivered), disk snapshots were not taken on that host as people assumed, and the replication setup was the thing already broken. They ultimately restored from a snapshot of a staging database taken some hours earlier for an unrelated reason, which meant losing several hours of data (issues, merge requests and similar, not git repositories). The company published a detailed post-mortem and live-streamed the recovery, which is itself a good practice.

Lessons.

  • An untested backup is not a backup. Run scheduled restore drills and measure recovery time and data loss against your RTO and RPO targets.
  • Monitor the backup jobs and alert on failure and on empty or suspiciously small backups; make sure the alert emails actually arrive.
  • Guardrails for destructive commands: distinct prompts and colours per environment, hostnames shown in the shell, separated production access, require a second person for dangerous actions, and prefer automation with review over manual commands in an incident.
  • Multiple independent backup layers (logical dumps, snapshots, replicas, point-in-time recovery from the log) so one failing layer is not fatal.
  • Keep tooling simple and documented; fatigue and pressure cause mistakes, so blameless post-mortems and runbooks matter.
What are lessons from large-scale database outages caused by cascading load or failover? Senior

In one line: automated failover across a flaky link can create divergent data on two primaries; recovery is slow and manual, and failover storms add second-order damage. Design and rehearse for partitions and for reconnect floods.

Case: GitHub, October 2018 (as publicly described in their post-mortem; check it for details). A brief loss of network connectivity (on the order of tens of seconds) between their US East coast data centre and the main network hub triggered the orchestration tool to fail over MySQL primaries to the other site (US West). But the original primaries had accepted some writes that had not replicated before the partition, so after connectivity returned, the two sides had different data. The cross-coast latency also caused application timeouts. Because they chose to preserve data rather than discard the unreplicated writes, restoring a consistent state took a long time (the incident lasted roughly a day, with degraded service), involving restoring from backups and replaying binlogs.

Takeaways.

  • Automated failover across high-latency links can produce split brain style divergence. Prefer a fencing mechanism so the old primary cannot accept writes, and be cautious about cross-region automatic promotion.
  • Asynchronous cross-region replication loses the unreplicated tail on failover; decide in advance whether that loss (RPO) is acceptable or whether to use synchronous or semi-synchronous replication for critical data.
  • Recovery from divergent data is slow and manual, so rehearse it, and have tools to reconcile.
  • Applications must tolerate cross-site latency and have sane timeouts.

Second-order failures in general. After any failover, every client reconnects at once (a failover storm), and connection pools can overwhelm a freshly promoted primary with cold caches. Use jittered exponential backoff on retries, connection limits and warm-up, and load shedding at the edges. Such rare events are worth a game-day drill before they happen for real.

DocumentAggregates read as one unit; embed what is read together.
Wide-columnLSM, huge writes, query-first table design, watch hot partitions.
GraphVariable-depth relationship traversal.
Time-seriesTime-partitioned, compressed, downsampled; mind cardinality.
Search engineInverted index; derived from source of truth; near real time.
OLTP vs OLAPRow store for small transactions; column store for big scans.
ACID vs BASECorrectness first vs availability and eventual convergence.
Lost updateAtomic SQL, row lock, version check, compare-and-set.
Write skewNeeds serializable, or lock what you read, or a constraint.
B-tree vs LSMReads and ranges vs write throughput; compaction cost.
Composite indexLeftmost prefix; equality columns then range column.
Index costWrite amplification, memory, planner confusion.
Zero-downtime schema changeExpand, dual write, backfill, switch reads, contract.
Blob storageObject store plus CDN; metadata in DB; presigned multipart upload.
RetentionHot, warm, cold, archive tiers; drop partitions, never mass-delete.
Connection poolSmall and bounded; instances x pool must fit DB max.
N+1Batch or join; count queries per request.
PaginationKeyset instead of large offsets.
Read-heavyIndex, cache, replicas, precompute.
Write-heavyLSM store, shard, queue and batch, fewer indexes.
