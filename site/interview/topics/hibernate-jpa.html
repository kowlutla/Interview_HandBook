Mental model: the 8 ideas everything hangs on

One line: an entity is a Java object that is being watched. Inside a transaction, the watcher (the persistence context) remembers every entity it loaded, notices what you changed, and writes the SQL when it flushes. Most bugs come from forgetting the watcher exists.
  1. JPA is a spec, Hibernate is an implementation, Spring Data is a convenience layer. You code against JPA, Hibernate runs it, Spring Data JPA removes repository boilerplate.
  2. An entity is always in a state: new, managed, detached or removed. Only managed entities are watched.
  3. The persistence context is a per-transaction identity map. Load row 5 twice and you get the same Java object. This is the first-level cache.
  4. Dirty checking. Change a managed entity and you do not call save. At flush, Hibernate compares it with the snapshot taken at load and writes an UPDATE.
  5. Writes are delayed. SQL is queued and sent at flush: before a query that could be affected, and at commit. SQL order is Hibernate's, not your code's.
  6. Laziness is a proxy. A lazy association is a placeholder that loads on first touch, and only while the context is open. That is the source of LazyInitializationException and of N+1.
  7. The owning side decides the foreign key. In a two-way relationship only the side without mappedBy writes the column.
  8. Concurrency is your job. The persistence context does not stop two users overwriting each other. @Version (optimistic) or row locks (pessimistic) do.

1. Basics and the entity lifecycle

What is the difference between JPA, Hibernate and Spring Data JPA? Basic

JPA is only a specification: annotations and interfaces such as @Entity, EntityManager and JPQL. Hibernate is the most popular implementation that actually generates SQL. Spring Data JPA sits on top and writes the repository boilerplate for me, so findByEmail becomes a query without any code.

In practice I write against the JPA API and Hibernate does the work, so I can still use Hibernate extras (batch fetch size, filters, Envers) when I need them. Hibernate's Session extends JPA's EntityManager, and SessionFactory extends EntityManagerFactory. unwrap(Session.class) gives the Hibernate object. The factory is thread-safe and built once; an EntityManager is cheap, not thread-safe, and lives for one unit of work (in Spring, one transaction). Spring Data JPA is not part of JPA: it generates repository implementations at startup and delegates to the EntityManager.

Why three layers exist

Before JPA, every ORM (Hibernate, TopLink, JDO) had its own annotations and API, so switching meant a rewrite. JPA was created as a common standard: a set of interfaces and annotations in a package (javax.persistence, later jakarta.persistence) plus a defined behaviour. A spec alone does nothing, so you need a provider that implements it. Hibernate is by far the most common provider (others: EclipseLink, OpenJPA). Spring Data JPA is a separate Spring project that removes the repetitive DAO code on top of any JPA provider.

One line of code, three layers

Take customerRepository.findByEmail("a@x.com"). Each layer does a different job:

  1. Spring Data JPA sees the method name at startup, parses it as "where email = ?" and builds a JPQL query. You wrote no implementation.
  2. JPA is the vocabulary the query is expressed in: EntityManager.createQuery(...), JPQL, @Entity.
  3. Hibernate turns the JPQL into real SQL for your database dialect, runs it through JDBC, and maps the rows back to Customer objects.

Trade-off and what interviewers probe

Staying inside the JPA API keeps you portable in theory, but in practice almost every real project uses a few Hibernate-only features, and that is fine as long as you know which ones. A common follow-up is "can you swap Hibernate for EclipseLink?". The honest answer is: possible for simple code, but behaviour differences (flush rules, id generation, caching) make it a real migration, not a configuration change.

Remember: JPA = rules, Hibernate = engine, Spring Data = shortcuts. The factory is shared, the EntityManager is not.

Why use an ORM at all, and what does it cost you? Basic

An ORM (object-relational mapper) removes the repetitive code that turns rows into objects and back, and gives me dirty checking, relationships, caching and database portability. The cost is that SQL becomes indirect: it is easy to create N+1 queries, load too much data, or hit surprises at flush time. I use JPA for normal CRUD on aggregates and drop to SQL or jOOQ for reports and heavy bulk work.

The root problem is the "impedance mismatch": objects form graphs and use inheritance, while tables have rows, foreign keys and joins. Hibernate bridges that, but you still have to know what SQL it produces. The rule I follow is to log the SQL in development, watch the statement count per request, and never treat the ORM as magic.

The problem an ORM solves

Plain JDBC works, but a simple "load an order with its lines" needs about thirty lines: write SQL, set parameters, loop over a ResultSet, call getString for each column, build objects, and join parent and child rows by hand. Multiply that by every table and every insert/update, and you have lots of boring code where a column rename breaks things silently at runtime.

The deeper problem is the impedance mismatch: the object world and the relational world model data differently.

What you get and what you pay

You get: less boilerplate, automatic change tracking (dirty checking), relationship navigation (order.getLines()), a first-level cache, optimistic locking via @Version, and a degree of database portability through dialects.

You pay: the SQL is generated for you, so you can accidentally issue 1,001 queries for one page (the N+1 problem), fetch whole entities when you needed two columns, or be surprised by when an UPDATE actually fires. A new developer who never looks at the SQL will eventually ship a slow endpoint.

Decision rule

Use JPA for transactional create/read/update of aggregates (an order and its lines). Use DTO projections or plain SQL/jOOQ/JdbcTemplate for reports, large aggregations, bulk updates and anything where you need exact control of the SQL. Many healthy systems use both in the same service. Always enable SQL logging (or a statement counter) in tests so a regression in query count fails the build.

Remember: ORM saves typing, not thinking. Always look at the SQL it generates.

What does a class need to be a JPA entity? Why should it not be final? Basic

It needs @Entity, an @Id field, and a no-argument constructor that is at least protected. The class and its persistent methods should not be final, because Hibernate creates proxy subclasses for lazy loading and a final class cannot be subclassed.

Hibernate also reads and writes fields reflectively and needs to instantiate the object itself when loading rows, hence the empty constructor (I make it protected and keep a real constructor for my own code). Whether Hibernate uses fields or getters is decided by where I put @Id: on the field means field access, which I prefer, because setters with logic then do not run during loading. Records cannot be entities in Hibernate 6 (they are final and immutable), though they work well as DTOs and as embeddables in recent versions.

@Entity
public class Customer {
    @Id @GeneratedValue private Long id;
    private String name;
    protected Customer() {}                // for Hibernate
    public Customer(String name) { this.name = name; }
}

Why each rule exists

  • @Entity tells the provider "this class maps to a table". Without it the class is invisible to JPA.
  • @Id gives every object a stable identity. The persistence context is keyed by (entity type, id), so no id means no tracking.
  • No-arg constructor: when Hibernate reads a row it creates an empty object first and then fills the fields by reflection. It cannot guess which of your constructors to call with which column values. The JPA spec requires public or protected; protected stops application code from creating half-built objects by accident.
  • Non-final class and methods: for a lazy @ManyToOne Hibernate generates a subclass at runtime (a proxy) that overrides your methods to load data on first call. A final class cannot be subclassed, so lazy loading silently turns off or fails at startup. A final method on the entity would be called on the proxy itself and see empty fields.

Field versus property access

Hibernate picks how to read and write state from where @Id sits. On a field means field access: it touches the variables directly, so your getters and setters can contain logic (validation, trimming) without being run during loading. On a getter means property access: it calls the getters and setters, which can cause odd bugs if they have side effects. Pick one per entity hierarchy and do not mix.

Other practical rules

Prefer wrapper types for ids (Long, not long), because a null id is how Spring Data and Hibernate know the object is new. Implement equals and hashCode deliberately (a later question covers it), and avoid Lombok @Data on entities because its generated toString, equals and hashCode walk lazy associations and can trigger queries or infinite loops in two-way relationships.

Remember: entity = annotation + id + protected no-arg constructor + non-final, so proxies can work.

Explain the entity lifecycle states and what moves an entity between them. Basic

There are four states. New (transient) is a plain object with no row. Managed (persistent) is attached to a persistence context, so changes are tracked. Detached has an id but its context is closed, so changes are ignored. Removed is scheduled for deletion at flush. persist makes new into managed, find and queries return managed, remove makes removed, and merge copies a detached object onto a managed one.

The state that matters most in practice is detached. After the transaction ends, an entity you return from a service is detached: you can still read it, but a setter on it changes nothing in the database, and untouched lazy fields cannot load. Detached happens through detach, clear, closing the EntityManager, or simply the end of a Spring transaction.

Walking one object through all four states

The easiest way to learn this is to follow a single Order object:

Order o = new Order("A-100");     // NEW: plain Java, no id, not in DB
em.persist(o);                    // MANAGED: now tracked; id assigned
o.setStatus(PAID);                // still MANAGED: change will be flushed
em.getTransaction().commit();     // flush writes INSERT (+ UPDATE if needed)
em.close();                       // o is now DETACHED: has id 7, not tracked
o.setStatus(SHIPPED);             // silently ignored by the database
Order again = em.merge(o);        // 'again' is MANAGED, o stays DETACHED
em.remove(again);                 // REMOVED: DELETE sent at next flush

Why it matters in real code

Most "my update did nothing" bugs are a detached entity: an object loaded in one transaction, modified outside any transaction, and never merged. Most "detached entity passed to persist" errors are the opposite: passing an object that already has an id to persist. Learn to ask, for any entity variable: which context owns it right now?

Interviewers often follow up with "what does persist do to the cascade?" (it also persists children marked CascadeType.PERSIST) and "does persist run INSERT immediately?" (not necessarily: with IDENTITY ids it does, with sequences the INSERT waits for flush).

Remember: new, managed, detached, removed. Only managed entities get UPDATEs for free.

What is the difference between persist, merge, save and update? Intermediate

In JPA, persist takes a new object and makes that same object managed. merge takes an object that may be detached, copies its state onto a managed instance (loading it first if needed) and returns that managed copy; the object I passed stays detached. Hibernate's old save, update and saveOrUpdate are Hibernate-specific and were removed in Hibernate 6, so I use the JPA calls, or Spring Data's save which picks between them.

The classic mistake is to call merge(x) and keep using x: further changes go to a copy nobody tracks. Always use the return value. persist on a detached object throws "detached entity passed to persist". Merge costs a SELECT when the entity is not already in the context, because it must load the current state to copy onto.

Order managed = em.merge(detachedOrder);   // use 'managed' from here on
managed.setStatus(PAID);                   // tracked

How merge works, step by step

  1. You pass detachedOrder (id 7, status SHIPPED).
  2. Hibernate looks in the context for Order 7. If missing it runs SELECT ... WHERE id = 7.
  3. It copies every field from your object onto the managed instance, which makes it dirty.
  4. At flush an UPDATE is issued. Your original object is untouched and still detached.

A subtle point: merge copies all fields, including nulls. If you built a detached object from a partial form with some fields missing, merge overwrites the database values with null. For partial updates, load the entity, set only what changed, and let dirty checking do the rest.

How Spring Data decides "new"

save calls isNew. For an entity with a wrapper-type id, null id means new. If the entity has a @Version of a wrapper type, a null version means new. If you assign ids yourself (for example a UUID you generate), the id is never null, so save thinks it is existing and calls merge, which does a useless SELECT first. Fix by implementing Persistable (with an isNew flag) or by using a version field.

The old Hibernate calls

save, update, saveOrUpdate and load on Session were deprecated in Hibernate 5.x and removed in Hibernate 6. If you see them in a code base, it is older code, and the JPA equivalents are persist, merge and getReference.

Remember: persist attaches this object, merge returns a different managed copy. Use the return value.

find versus getReference: when would you use the lazy one? Intermediate

find loads the row now and returns null if it does not exist. getReference returns a lazy proxy holding only the id and does not hit the database until I touch a field. I use getReference when I only need to set a foreign key, for example order.setCustomer(em.getReference(Customer.class, id)), so I save a pointless SELECT.

The trade-off is that a missing row only shows up later as EntityNotFoundException (or at the foreign key on flush), and touching it after the context closes throws LazyInitializationException. In Spring Data the same idea is repository.getReferenceById(id) (called getOne in old versions). If I need the data or a clean "not found" answer, I use find.

Why a placeholder is useful

Suppose you create an Order for customer 9. The database only needs the number 9 in order.customer_id. If you call find, Hibernate runs SELECT * FROM customer WHERE id = 9, builds a full object, and you throw it away after setting one foreign key. With getReference there is no SELECT: Hibernate makes a proxy whose only real data is the id, and writes 9 straight into the INSERT.

Order o = new Order();
o.setCustomer(em.getReference(Customer.class, 9L)); // no SELECT
em.persist(o);                                      // INSERT order(customer_id=9)

Pitfalls

If the row does not exist, a bad id is only caught when the database rejects the foreign key at flush, so the error is far from the cause. Also, if the entity is already loaded in the context, getReference just returns that real object, not a proxy. And remember that returning a proxy from a service and serialising it to JSON is a classic way to hit lazy-loading errors. A simple rule: reference for writes by id, find for everything else.

Remember: find = load now or null. getReference = cheap placeholder, just to link by id.

How do Hibernate proxies work, and what traps do they create? Senior

For a lazy association Hibernate puts a generated subclass of my entity in the field. It holds the id, and on the first call of any method (other than getId) it loads the real row through the open session and delegates to it. The traps are that the proxy is a different class than my entity, so getClass(), instanceof with final classes and some equals implementations break, and that it only loads while the session is open.

Concrete traps: obj.getClass() == Customer.class is false for a proxy, so I compare with Hibernate.getClass(obj) or instanceof. Accessing a field directly (not through a getter) on a proxy returns null, because the proxy's own fields are empty. A lazy @ManyToOne to a class in an inheritance tree can give a proxy of the base type that cannot be cast to the subtype. To check if something is loaded use Hibernate.isInitialized(x); to force loading inside a transaction use Hibernate.initialize(x).

What a proxy is, concretely

Imagine Order has @ManyToOne(fetch = LAZY) Customer customer. When Hibernate loads order 5 it knows customer_id = 9 but does not want to load the customer yet. So it puts into the field an object of a class it generated at runtime, something like Customer$HibernateProxy$x1, which extends Customer. That object stores the id 9 and a reference to the session. When you call customer.getName() the proxy sees it has no data, runs SELECT ... WHERE id = 9, stores the real Customer inside, and forwards the call. Calling getId() is special: it answers from the stored id without any SQL (for property access this depends on the setup).

Timeline of one lazy read

  1. order.getCustomer() returns the proxy. No SQL. The proxy is not yet "initialized".
  2. order.getCustomer().getId() still no SQL.
  3. order.getCustomer().getName() triggers the SELECT. The proxy is now initialized.
  4. If the session was already closed at step 3, you get LazyInitializationException.

The traps in practice

  • Class checks. getClass() returns the generated subclass. Use Hibernate.getClass(o) or instanceof.
  • Equality. equals written with getClass() != o.getClass() says a proxy and the real object are different. Prefer instanceof and compare via getters.
  • Inheritance. A lazy proxy of a base class cannot be cast to a subclass, because the proxy is a sibling subclass, not the real one. Hibernate offers Hibernate.unproxy(x) to get the real object.
  • Direct field access on a proxy reads the proxy's own empty field, giving null. Always use getters on objects that may be proxies.
  • Serialisation. Jackson walking a proxy outside a session triggers the lazy load error. Return DTOs.

Hibernate generates proxies with a bytecode library (ByteBuddy in modern versions), which is why the class must not be final.

Remember: a lazy field is a proxy subclass. Use getters, instanceof, and stay inside the session.

2. Persistence context, flush and dirty checking

What is the persistence context, and what is the first-level cache? Basic

The persistence context is the set of managed entities that one EntityManager (one Session) keeps in memory. It works as an identity map: asking for the same entity id twice gives me the same Java object, and the second find costs no SQL. That is the first-level cache. It is always on, and it is scoped to one transaction in a normal Spring service.

The context also keeps a snapshot of each entity's values at load time, which is what dirty checking later compares against. Two consequences. First, it is not a shared cache: another transaction has its own context and may see different data. Second, it grows with every entity I load, so a loop over a million rows without clear() ends in OutOfMemoryError. A JPQL query always goes to the database, but the rows it returns are matched with entities already in the context, so I get the existing object back and my in-memory changes are not overwritten.

Why a first-level cache exists at all

Without it, two find(Order.class, 5) calls in one transaction would give two different Java objects for the same row. Change one, and the other is stale, and at flush you would not know which to write. The persistence context guarantees one object per row per context, so there is a single source of truth inside the unit of work. The caching benefit is a side effect of that guarantee.

A concrete example

@Transactional
void demo() {
  Order a = em.find(Order.class, 5L);   // SELECT
  Order b = em.find(Order.class, 5L);   // no SQL, served from context
  System.out.println(a == b);           // true: same object
  a.setStatus(PAID);
  System.out.println(b.getStatus());    // PAID: it is the same object
}

What it also does

  • Stores a snapshot per entity, used for dirty checking.
  • Holds the queue of pending inserts, updates and deletes (the action queue) until flush.
  • Resolves query results to existing objects: if a JPQL query returns row 5 and order 5 is already managed, you get the managed object with your unsaved changes, not a fresh copy.

Scope and misuse

In Spring, the context lives for the transaction (a "transaction-scoped" context). With Spring Boot's open-in-view default it can stretch across the whole web request, which hides lazy-loading problems but holds a database connection for longer. In a batch job it never ends unless you clear it, so memory grows with every loaded entity.

Interview probe: "is the first-level cache shared between users?" No. It is per EntityManager, never shared across threads. The shared cache is the second-level cache, which is optional and off by default.

Remember: one transaction, one context, one object per id. Huge loops need clear().

How does automatic dirty checking work, and what does it cost? Intermediate

When Hibernate loads an entity it keeps a copy of its field values. At flush time it compares every managed entity with its copy, and for each one that differs it queues an UPDATE. So inside a transaction I just call a setter, and I never call save. Nothing happens for detached objects.

The cost is proportional to the number of managed entities times their fields, on every flush, so a context with 50,000 entities makes each flush slow even if only one changed. For read-only code I avoid the cost with @Transactional(readOnly = true), read-only queries, or DTO projections. By default the UPDATE includes all columns, not only the changed ones (@DynamicUpdate changes that, at the price of more distinct statements that cannot be reused or batched as well). Bytecode enhancement can track dirty fields without comparing, but few teams enable it.

@Transactional
public void pay(Long id) {
    Order o = repo.findById(id).orElseThrow();
    o.setStatus(PAID);       // no save() needed: UPDATE happens at commit
}

Walk through with numbers

  1. Transaction starts. You load Order 5 with status=NEW, total=40. Hibernate stores the entity and a snapshot array [NEW, 40].
  2. You call setStatus(PAID). Only the Java object changes. No SQL yet.
  3. At commit (or an earlier flush) Hibernate loops over all managed entities, compares each current value array with its snapshot. For Order 5: [PAID, 40] differs from [NEW, 40].
  4. It queues UPDATE orders SET status='PAID', total=40 WHERE id=5 and runs it.
  5. The snapshot is refreshed, so a second flush finds nothing to do.

Why Hibernate works this way

It lets the domain code stay free of persistence calls: a method that changes an order reads like normal Java. The price is that "who writes to the database" becomes implicit. A team member who modifies an entity returned by a query "just to compute something" may cause an unintended UPDATE.

Pitfalls

  • Changing a managed entity you meant only to read (for example, trimming a string in a getter's caller) makes it dirty. Use DTOs or detach it.
  • Mutable fields like Date or a JSON object: Hibernate compares by equals or by a type-specific mutability plan. In-place mutation of a mutable value may or may not be noticed, depending on the type. Prefer immutable values.
  • Calling save on a managed entity is harmless but pointless; it does not speed anything up.
  • Cost at scale. The check is O(entities times columns) per flush. A big context plus many auto-flushes (a query inside a loop) can be quadratic. Use clear() or read-only transactions.

@DynamicUpdate builds the UPDATE with only changed columns. It helps for very wide tables or to reduce lock contention and write amplification, but it prevents reusing a cached prepared statement and can reduce JDBC batching, so measure before enabling.

Remember: managed + changed = UPDATE at flush. No save needed, and none helps a detached object.

When does Hibernate flush, and what is the difference between flush and commit? Intermediate

Flush means "send the queued SQL to the database inside the open transaction"; commit means "make it permanent". With the default AUTO flush mode Hibernate flushes at commit and also before a query that might read data I changed, so my own queries see my own changes. A flush can still be rolled back; a commit cannot.

Flush modes are AUTO (default), COMMIT (only at commit, so queries may miss my pending changes), ALWAYS and, in Hibernate, MANUAL (only when I call flush()). I call flush() myself when I need constraint errors early (to catch a duplicate key inside the try block) or before native SQL, because Hibernate cannot tell which tables a native query reads. Through the JPA EntityManager it typically flushes everything first, but the Hibernate-native Session API may not, so I flush explicitly to be safe. Because flush runs at commit, a constraint failure often surfaces in the transaction proxy after my method returned, which confuses people reading the stack trace.

Why Hibernate delays writes

If every setter wrote SQL immediately, you would send many tiny statements and could not combine them. By queueing changes and sending them together at flush, Hibernate can batch, order them to respect foreign keys, and skip statements that cancel out (an entity persisted and removed in the same transaction never touches the database).

Flush versus commit with a timeline

begin transaction
  em.persist(order);          // queued, no SQL (sequence id)
  order.setStatus(PAID);      // still queued
  em.createQuery("from Order where status = 'PAID'")  // AUTO flush: INSERT sent first
        .getResultList();      // the query now sees the new order
commit                         // flush any leftovers, then COMMIT in the database

Before the query, Hibernate noticed pending work on a table the query reads, so it flushed. Had the query been on an unrelated table, an optimised flush could be skipped. After flush, the rows exist inside this transaction only. Other transactions do not see them until commit (with the usual isolation levels), and a rollback removes them.

Practical consequences

A unique-constraint violation appears at flush, which is often at commit, so the exception pops up when the transaction method returns, not on the line that caused it. To catch it where it happens, call saveAndFlush or em.flush() inside a try block. Also remember that a native SQL query is a black box to Hibernate: if you changed entities and then run a native query on the same tables, flush first, or you will read stale rows.

Remember: flush sends SQL, commit finalises it. Flush is automatic before affected queries and at commit.

In what order does Hibernate execute SQL at flush, and why does it matter? Senior

Hibernate does not run statements in the order I wrote the code. At flush it runs, roughly, all inserts, then all updates, then collection changes, then all deletes. This matters when my logic depends on order, for example deleting a row and re-inserting the same unique key: the insert runs first and fails with a duplicate key.

The reason is that Hibernate collects an action queue and sorts it to respect foreign keys and to allow batching. When order matters I call em.flush() right after the delete so it goes out before the insert. Better, I update the existing row instead of delete and insert. The same ordering can cause deadlocks when two transactions touch the same rows in different order: hibernate.order_updates=true and order_inserts=true sort statements by entity and id to make that more consistent.

The order, exactly

Hibernate's action queue executes in this fixed order at flush, regardless of the order of your Java calls:

  1. Orphan removals
  2. Entity inserts
  3. Entity updates
  4. Collection removals, collection updates, collection inserts
  5. Entity deletes

The classic failure

repo.delete(oldRow);                 // queued as a delete
repo.save(new Row("EU-1"));          // queued as an insert (same unique code)
// at flush: INSERT runs first -> duplicate key on the unique index "code"

Fix options, from best to worst: (1) update the existing row instead of deleting and recreating; (2) call repo.flush() after the delete so the DELETE is sent before the INSERT is even queued; (3) in some databases use deferrable constraints, which move the check to commit.

Why this order

Inserts first means new parents exist before updates that point at them. Deletes last means rows that are being referenced are removed only after the referrers have been updated. This works for the common cases but cannot know about your unique constraints.

Deadlocks and ordering settings

Two transactions each updating rows A and B, but in opposite orders, can deadlock in the database. Setting hibernate.order_updates=true and hibernate.order_inserts=true makes Hibernate sort statements by entity type and primary key. That gives a consistent lock order between transactions and also improves JDBC batching, because statements for the same table end up adjacent. The deadlock detector in the database then fires less often. If you still see deadlocks, check the application code that touches different tables in different orders.

Remember: inserts, then updates, then deletes. Need another order? Call flush() between the steps.

What do detach, clear, refresh and flush each do, and when do you use them? Intermediate

flush writes pending changes to the database. clear empties the whole persistence context, detaching everything, and detach(e) does it for one entity. refresh(e) reloads one entity from the database and overwrites my in-memory changes. I use flush plus clear in batch loops, clear after a bulk update, and refresh after a database trigger or a native update changed a row.

Order matters: always flush() before clear(), otherwise pending changes are thrown away silently. After clear(), every entity I still hold is detached, so touching its lazy fields fails. refresh on an entity with unflushed changes throws those changes away, so I use it carefully.

One table to compare

Two typical patterns

Batch loop. Without clear every saved entity stays in memory:

for (int i = 0; i < rows.size(); i++) {
    em.persist(rows.get(i));
    if (i % 50 == 49) { em.flush(); em.clear(); }   // write, then forget
}

After a bulk update. A JPQL UPDATE ... SET status='X' changes the database but the context still holds old objects. Either call clear() afterwards or use @Modifying(clearAutomatically = true) so the next read goes to the database.

What goes wrong

clear() without a prior flush() loses unsent changes with no error. After clear(), entities you still hold are detached, so a later lazy access throws. refresh on an entity that has unflushed edits discards them. Also, if the entity was deleted from the database in the meantime, refresh throws EntityNotFoundException.

Remember: flush writes, clear forgets, refresh re-reads. Flush before you clear.

What does @Transactional(readOnly = true) really do? Intermediate

It is mainly a hint. With Spring and Hibernate it switches the flush mode to MANUAL, so there is no dirty checking and no automatic flush, and it tells the JDBC driver and database the connection is read-only, which some databases use to optimise or route to a replica. It does not make the database refuse writes in every case, and it still opens a transaction with a consistent snapshot.

I use it on every query-only service method: it saves the dirty-check pass and documents intent. If someone changes an entity inside it, the change is simply not flushed, which can look like "my update was ignored". Whether the read-only flag is enforced depends on the driver and database (PostgreSQL rejects writes, MySQL typically does too with InnoDB, others only treat it as a hint). A small trap is that a readOnly method called from an existing read-write transaction does not change that transaction.

What Spring does when you set it

  1. Spring's JPA dialect tells Hibernate the session is read-only: flush mode becomes MANUAL and, in typical setups, loaded entities are marked read-only so Hibernate does not even keep the dirty-check snapshot (saving memory and CPU).
  2. Spring tells the JDBC connection setReadOnly(true). Drivers and databases treat that differently: PostgreSQL's driver sets the transaction read-only and the server rejects writes; other databases only use it as a hint.
  3. With a routing data source (a common pattern) the read-only flag can route the call to a read replica.

Example and its surprise

@Transactional(readOnly = true)
public void touch(Long id) {
    Order o = repo.findById(id).orElseThrow();
    o.setStatus(PAID);     // never flushed: change is silently ignored
}

Nothing fails, nothing is saved. This is the "my update was ignored" trap when someone adds a write into a read method.

When to use it

Put it on service methods that only read, or put readOnly = true on the class and override with plain @Transactional on write methods. It reduces dirty-check work and documents intent. Avoid assuming it protects data: it is not an authorisation feature, and a native or JDBC write may still succeed on a database that treats it as a hint.

A key trap with replicas: replication lag. If a read-only call right after a write is routed to a replica, it may not see the new row. Read-your-own-writes flows should stay on the primary. And remember propagation: if a read-only method is called from within an existing read-write transaction, the outer transaction's settings win, because the inner method simply joins it.

Remember: readOnly = no flush, no dirty check, driver hint. It is a performance and intent flag, not a security feature.

3. Mappings: relationships, cascades, inheritance, ids

What is the owning side of a relationship, and what does mappedBy do? Basic

In a two-way relationship, only one side controls the foreign key column. That is the owning side, normally the "many" side with @ManyToOne and @JoinColumn. The other side uses mappedBy = "fieldName", which means "I am just a mirror of that field". Hibernate ignores changes made only to the mirror side.

So if I do order.getItems().add(item) but never call item.setOrder(order), the order_id column stays null, even though the Java objects look right in memory. The foreign key always lives in the table of the many side, which is why that side is the natural owner.

The problem this solves

A database relationship is stored once: a single foreign key column in one table. Java is different: in a two-way link Order has a list of items and each OrderItem has an order, so the same fact is written in two places. Hibernate needs a rule for which Java field is the "real" one to copy into the column, otherwise it would have to guess when the two disagree. That rule is the owning side.

How to tell the sides apart

  • The owning side is the one that physically maps the column: @ManyToOne @JoinColumn(name = "order_id").
  • The inverse side carries mappedBy = "order", where "order" is the field name on the owning class. It is read-only as far as the foreign key goes.

In a one-to-many the foreign key is always in the "many" table (order_item.order_id), so the many side is the natural owner. In a one-to-one or many-to-many you choose, and in many-to-many the owner is the side that declares the @JoinTable.

What goes wrong

Order o = new Order();
OrderItem i = new OrderItem();
o.getItems().add(i);          // inverse side only
em.persist(o);                // cascade saves i, but order_id = NULL
// fix: i.setOrder(o);        // the owning side

Nothing throws; the row is simply saved without a parent (or fails a NOT NULL constraint if you declared one). Inside the same transaction the object graph looks fine, but the next request loads order.getItems() as empty. This is the most common mapping bug in code reviews. The cure is a helper method that sets both sides (next question).

Interview probe: "what happens if I forget mappedBy on a bidirectional one-to-many?" Hibernate treats the two directions as two independent relationships and creates an extra join table with its own writes.

Remember: the side without mappedBy writes the foreign key. Always set the owning side.

How do you map a bidirectional one-to-many safely? Intermediate

I put @ManyToOne(fetch = LAZY) on the child as the owner, @OneToMany(mappedBy = ..., cascade = ALL, orphanRemoval = true) on the parent, and I add helper methods addItem and removeItem on the parent that update both sides. I never expose the raw collection to be modified from outside.

@Entity class Order {
  @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
  private List<OrderItem> items = new ArrayList<>();

  public void addItem(OrderItem i)    { items.add(i);    i.setOrder(this); }
  public void removeItem(OrderItem i) { items.remove(i); i.setOrder(null); }
}
@Entity class OrderItem {
  @ManyToOne(fetch = FetchType.LAZY) @JoinColumn(name = "order_id")
  private Order order;
}

Why this shape: the helper keeps memory and database in step, so the object graph does not lie within the same transaction. Cascade ALL plus orphanRemoval makes the parent own the children's lifecycle, which is right for true parts of an aggregate (order items) and wrong for independent entities (a customer). Initialise the collection in the field so it is never null, and avoid replacing it with setItems(new list) when orphanRemoval is on: Hibernate complains about a dereferenced collection.

Why a safe mapping needs helper methods

In a two-way link there are two Java references to keep in sync: the item inside order.items and item.order. Hibernate only writes the owning one (item.order), but your in-memory objects, equals logic, validations and JSON all read both. If you update only one side, the graph is inconsistent until the next load. A helper method makes it impossible to forget.

What each annotation does in the example

  • @ManyToOne(fetch = LAZY) on the child: the foreign key owner, lazy so loading items does not drag the order each time.
  • mappedBy = "order": declares the parent list as the mirror.
  • cascade = ALL: persisting, merging or deleting the order does the same to its items.
  • orphanRemoval = true: removing an item from the list deletes its row.

Flow of "add an item and save"

  1. order.addItem(item) adds to the list and sets item.order.
  2. The order is managed (loaded in this transaction), so the new item is picked up at flush by cascade.
  3. Flush: INSERT INTO order_item (order_id, ...) VALUES (5, ...).

No explicit itemRepository.save(item) is needed.

Pitfalls to mention

  • The List is a "bag"; adding an element to a lazy collection initialises it (a SELECT) in many cases. For huge collections, do not model the list at all: save the child with its parent id and query children through a repository.
  • Do not expose getItems() as a mutable list. Return Collections.unmodifiableList(items) and use the helpers.
  • Replacing the collection with a new list when orphanRemoval is on throws "A collection with cascade all-delete-orphan was no longer referenced". Clear and add instead.
  • If equals/hashCode are wrong, items.remove(i) can silently do nothing.

Remember: child owns the FK and is LAZY, parent has mappedBy, and helper methods update both sides.

What is wrong with a unidirectional @OneToMany? Senior

Without @JoinColumn, Hibernate invents an extra join table for it, which means extra writes and extra joins. With @JoinColumn it works on the child's table, but the child row is inserted first with a null foreign key and then updated, which needs a nullable column and doubles the statements. A bidirectional mapping with the owner on the child is cheaper.

A List (a "bag", with no index column) makes it worse: removing one element often deletes all rows of that collection from the join table and re-inserts the rest. Using a Set, or @OrderColumn for ordered lists, reduces this. My default is to map the many side with @ManyToOne, and add the @OneToMany(mappedBy) only if I really navigate that direction.

What Hibernate generates, by example

Take Order with @OneToMany List<OrderItem> items and no back-reference on the child. For three items:

MappingTablesSQL for saving 3 items
No @JoinColumnorder, order_item, order_items (join table)3 inserts into order_item + 3 inserts into join table
@OneToMany @JoinColumn(name="order_id")order, order_item with order_id3 inserts (order_id null), then 3 updates setting order_id
Bidirectional with @ManyToOne ownerorder, order_item with order_id3 inserts with order_id already set

The join table mapping is surprising because you never designed it. The @JoinColumn variant avoids the extra table, but because the child entity has no field for the key, Hibernate cannot include it in the INSERT. So it inserts, then updates. That forces the column to be nullable and doubles the writes.

Why bags make removal expensive

A List without an order column has no stable identity per element. When you remove one element, Hibernate does not know which row it was, so for a join-table bag it deletes all rows for that owner and re-inserts the remaining ones. For 1,000 elements, removing one means 1 delete and 999 inserts. A Set (identified by element) or an @OrderColumn list avoids this.

Decision rule

Use a bidirectional mapping with the many side owning the key. If you never need to navigate parent to children, drop the @OneToMany entirely and query children by parent id. A unidirectional @OneToMany is acceptable only for tiny collections you rarely modify.

Remember: unidirectional one-to-many means a join table or insert-then-update. Prefer a @ManyToOne owner.

How do you map many-to-many, and why do people avoid it? Intermediate

With @ManyToMany and @JoinTable on the owning side, using a Set. I avoid it for real domain data because a join table never stays "just two ids": soon I need a created date, a role or a status, and then I have to remodel it as an entity. So I usually create the link entity from the start, for example Enrollment between Student and Course.

Two more problems. First, with a List, removing one link deletes and re-inserts the whole set of links for that owner, so use Set with a good equals/hashCode. Second, never use CascadeType.REMOVE or ALL on many-to-many: deleting one student would delete courses that other students share. Cascade PERSIST and MERGE at most, and keep helper methods that update both sides.

What it looks like

@Entity class Student {
  @ManyToMany
  @JoinTable(name = "enrollment",
     joinColumns = @JoinColumn(name = "student_id"),
     inverseJoinColumns = @JoinColumn(name = "course_id"))
  private Set<Course> courses = new HashSet<>();
}
@Entity class Course {
  @ManyToMany(mappedBy = "courses")
  private Set<Student> students = new HashSet<>();
}

The join table enrollment(student_id, course_id) holds only the two keys. Hibernate manages it for you; there is no Java class for a row of it.

Why "just two ids" never lasts

The day someone asks "when did the student enrol?", "what grade?", "is the enrolment active?", you need a column on the link row, and a @ManyToMany has nowhere to put it. You then have to migrate to a link entity. Starting with the link entity is more code today and no rewrite later:

@Entity class Enrollment {
  @Id @GeneratedValue Long id;
  @ManyToOne(fetch = LAZY) Student student;
  @ManyToOne(fetch = LAZY) Course course;
  LocalDate enrolledOn;
}

Now Student and Course each have a @OneToMany(mappedBy) to Enrollment, and Enrollment can be queried, paged and extended.

Pitfalls

  • List versus Set. A List (bag) rewrites the whole link set on a change; a Set deletes and inserts only the changed rows.
  • Cascade remove. Cascading REMOVE from a student would delete courses other students attend. Cascading only PERSIST/MERGE is safe at most.
  • Both sides. Keep helpers that update both collections, or the in-memory view and the table drift apart.
  • Loading. Touching student.getCourses() joins the link table and the course table; in a loop this is N+1.

Use plain many-to-many only for pure tagging relationships that are truly just a pair (for example user to role) and unlikely to gain attributes.

Remember: many-to-many hides a table you will need to extend. Use a link entity, and never cascade remove.

What does cascade mean, and which cascade types exist? Intermediate

Cascade makes an entity operation on the parent automatically apply to the related child entities. The JPA types are PERSIST, MERGE, REMOVE, REFRESH, DETACH and ALL (all of them). I use ALL only where the child cannot live without the parent, like order items, and never between independent entities.

Example: with cascade = PERSIST, persisting an order also persists new items added to it; without it, I get "object references an unsaved transient instance" at flush. Cascade is about operations, not about the foreign key: the foreign key is still decided by the owning side. Dangerous case: REMOVE on a @ManyToOne would delete the shared parent when one child is deleted. Remember that cascade runs when the operation is called, so a child added to a managed parent after persist is still saved at flush, because PERSIST cascades at flush time too.

The problem cascade solves

Without cascade you must persist every object yourself, in the right order:

em.persist(order);
for (OrderItem i : order.getItems()) em.persist(i);   // easy to forget

If you forget a child, flush fails with TransientPropertyValueException: object references an unsaved transient instance, because the order points at an item Hibernate has never heard of. With cascade = PERSIST (or ALL), persisting the order walks the collection and persists every new item for you.

What each type means

TypePropagatesTypical use
PERSISTpersist to childrenSaving a new aggregate

REFRESHreload children with parentRare

Decision rule: who owns the lifecycle?

Ask "if the parent disappears, should the child?". Order lines: yes, so cascade ALL. Order to Customer: no, because a customer outlives an order, so do not cascade REMOVE or even PERSIST from the order side. Cascading from child to parent (on @ManyToOne) is almost always wrong; the one case where it is acceptable is PERSIST for convenience of creating a parent together with the child.

Pitfalls

  • Cascade ALL on a large collection can make merge load and compare thousands of rows.
  • Hibernate's own CascadeType.DELETE, SAVE_UPDATE and REPLICATE exist in org.hibernate.annotations.CascadeType, not in JPA. Stick to JPA types.
  • Cascade REMOVE deletes children one by one with one DELETE per child. For big sets use a JPQL bulk delete, or database-level ON DELETE CASCADE (with @OnDelete in Hibernate).

Remember: cascade follows the lifecycle, so use ALL for parts of an aggregate and never for shared entities.

What is orphanRemoval, and how is it different from CascadeType.REMOVE? Intermediate

CascadeType.REMOVE deletes the children when the parent is deleted. orphanRemoval = true also deletes a child when I simply take it out of the parent's collection, because a child without a parent (an orphan) is considered meaningless. It is the right tool for "this list owns its elements".

It works only for one-to-one and one-to-many, and only for true parts of an aggregate. Gotchas: the collection must be modified in place with remove or clear, not replaced with a new instance; and if the same child is moved to another parent in the same transaction, it can get deleted by mistake. Each orphan removal is a separate DELETE by id, so removing 1,000 items from a list is 1,000 deletes. For bulk deletes use a JPQL delete.

The two situations, compared

Action in codecascade REMOVE onlyorphanRemoval = true
em.remove(order)Items deletedItems deleted
order.getItems().remove(item)Item stays in DB with a null or stale parentItem row is deleted at flush
order.getItems().clear()Rows stayAll item rows deleted

The word "orphan" says it: an item that is no longer in any order's list has lost its parent. With orphanRemoval the persistence context treats that as a deletion. Without it, the foreign key would still point at the order and the item would still show up in the next load, which surprises people who thought "removing from the list" removes the row.

Example

@OneToMany(mappedBy = "order", cascade = ALL, orphanRemoval = true)
private List<OrderItem> items = new ArrayList<>();

@Transactional
void dropFirst(Long id) {
    Order o = repo.findById(id).orElseThrow();
    o.removeItem(o.getItems().get(0));   // DELETE FROM order_item WHERE id = ? at flush
}

Pitfalls

  • Collection replacement. setItems(newList) makes Hibernate throw because the old tracked collection was dereferenced. Modify the existing list.
  • Moving a child. Removing an item from order A and adding it to order B in one transaction can delete it, depending on the order of operations. Create a new child or avoid moves.
  • Not for shared entities. If a child can belong to several parents (many-to-many) or must outlive the parent, never use it.
  • Cost. One DELETE per orphan. For thousands, use a bulk delete.

Remember: REMOVE reacts to deleting the parent, orphanRemoval also reacts to removing a child from the list.

How do you map a one-to-one, and why is lazy loading a problem there? Senior

The owning side has the foreign key (or shares the primary key with @MapsId). On the owning side, @OneToOne(fetch = LAZY) works. On the inverse side (mappedBy) Hibernate usually cannot be lazy, because it cannot know whether the other row exists without querying, and a proxy cannot represent "null". So it loads that side eagerly with an extra query.

That produces a hidden N+1 when loading a list of parents. Options: (1) make the child the owner so the parent side holds the key, (2) share the primary key with @MapsId so the child can be loaded by the parent's id, (3) make the relation a unidirectional pointer from the child only, or (4) use bytecode enhancement for lazy inverse-side proxies (works but adds build complexity). My default is a shared primary key and navigating from the dependent side only.

@Entity class UserProfile {
  @Id private Long id;
  @OneToOne(fetch = LAZY) @MapsId @JoinColumn(name = "id")
  private User user;
}

Why the inverse side cannot be lazy

To make a lazy reference Hibernate must decide, without a query, whether to put a proxy or null in the field. On the owning side that is easy: the foreign key column is in the row it already loaded, and a null key means null. On the inverse side the key lives in the other table. The only way to know "is there a profile for user 5?" is to run a query, so Hibernate runs it right away and fills the field, which is eager behaviour whatever the annotation says.

The hidden N+1

Load 100 users that each have an inverse-side profile: 1 query for users, then 100 queries for profiles, even though you never use them. The fix list from the answer, in practice:

  1. Flip ownership: put the foreign key on the side you navigate from, so the owned side is lazy.
  2. Shared primary key (@MapsId): the child's id equals the parent's id, no extra key column. You can fetch the profile with find(UserProfile.class, userId) when needed. This is the shape I usually pick.
  3. Remove the inverse mapping and query the child by id when needed.
  4. Bytecode enhancement with lazy-loading (enableLazyInitialization) so even the inverse side can be lazy. It works but needs a build plugin and has caveats.

Things to remember

A one-to-one is often a design smell. If the two rows are always created and read together, they may belong in one table, using @Embedded. If the child is optional and large (a CV document, a photo), a separate table with a shared key is reasonable, and queries that need it can use a join fetch or a projection explicitly.

Remember: a lazy one-to-one works only on the side that owns the key. The inverse side loads eagerly.

What inheritance mapping strategies does JPA have, and how do you choose? Intermediate

There are three entity strategies. SINGLE_TABLE (the default) puts the whole hierarchy in one table with a discriminator column: fastest, no joins, but subclass columns must be nullable. JOINED has one table per class joined by id: clean schema, but reads need joins. TABLE_PER_CLASS has a full table per concrete class: polymorphic queries become UNIONs, so I avoid it. For just sharing fields, @MappedSuperclass is simpler.

My choice: single table when the subclasses differ by a few columns and I query the base type a lot; joined when subclasses have many columns and need not-null constraints. Whatever I choose, polymorphic queries and polymorphic associations (a field of the base type) are where cost appears. For common fields like id, createdAt, version I use @MappedSuperclass, which is not an entity and cannot be queried.

What problem inheritance mapping solves

Java lets CardPayment and BankPayment extend Payment; relational tables have no inheritance. JPA offers three ways to store such a hierarchy, and the choice shapes your schema, constraints and query cost.

How to choose

  • Few subclass-specific columns, polymorphic queries are common: SINGLE_TABLE. Use @DiscriminatorColumn and add check constraints to protect data integrity.
  • Many subclass-specific columns or strong NOT NULL needs, and you accept a join: JOINED.
  • TABLE_PER_CLASS: avoid. A polymorphic query becomes a UNION, and generated ids cannot use IDENTITY.

Related option: MappedSuperclass

A @MappedSuperclass is for code reuse, not polymorphism. Fields like id, createdAt and version are copied into each child entity's table. You cannot query the superclass or point a relationship at it.

Interviewers may also ask whether inheritance is the right tool at all. Often composition (an @Embedded value or a type enum column) is simpler than an entity hierarchy, and avoids polymorphic proxy problems.

Remember: single table is fast, joined is clean, table-per-class is rarely right. Shared fields: MappedSuperclass.

Explain the id generation strategies: IDENTITY, SEQUENCE, AUTO and UUID. Which do you pick? Intermediate

I pick SEQUENCE where the database has sequences (PostgreSQL, Oracle, SQL Server; MySQL has none, so it uses IDENTITY). With a sequence Hibernate gets a block of ids at once (allocation size 50 by default) and assigns ids in memory, so inserts can be batched. IDENTITY uses an auto-increment column, so Hibernate must run the INSERT immediately to learn the id, which disables JDBC insert batching.

AUTO lets the provider choose; in Hibernate 6 that is a sequence per entity named like order_seq, in Hibernate 5 a shared hibernate_sequence, which is a common upgrade surprise. If the database sequence increments by 1 but allocationSize is 50, ids collide, so the INCREMENT BY of the sequence must equal the allocation size. TABLE is slow and rarely used. A random UUID is easy to generate in the app and good for distributed inserts, but a random primary key scatters inserts across a B-tree index and is bigger; time-ordered UUIDs (v7) or a sequence for the clustered key reduce that.

How each strategy works, step by step

IDENTITY: the table column is auto-increment. persist(a) must send the INSERT immediately, because only the database knows the id, and Hibernate needs an id to put the entity in the persistence context. So no batching of inserts.

SEQUENCE: the database holds a counter. Hibernate with the pooled optimiser asks "next value" once, gets for example 1000, and knows ids 951 to 1000 are free (with allocationSize = 50). It hands them to entities in memory with no SQL, and the INSERTs can be batched at flush. The cost: ids are not strictly in insertion order across multiple application nodes, and restarts leave gaps. Neither matters for correctness.

UUID: generated in Java (@UuidGenerator in Hibernate 6.2+, or GenerationType.UUID in JPA 3.1). No database round trip, safe across shards and services, and ids can be created before saving. The cost is a 16-byte (or 36-char text) key, and with a random v4 UUID as clustered primary key (MySQL InnoDB, SQL Server) inserts land all over the index, causing page splits and a poor cache hit rate. Time-ordered UUIDs (v7, ULID-like) fix most of that.

Pitfalls and what interviewers ask

  • Increment mismatch. The database sequence says INCREMENT BY 1 but the entity says allocationSize = 50 (the default). Two application instances then hand out overlapping ids and you get duplicate key errors. The two numbers must match.
  • Hibernate 5 to 6 upgrade. The AUTO default changed, so ids can jump or collide if the old shared sequence is not mapped explicitly. Declare @SequenceGenerator per entity during migration.
  • Exposing a sequential id in URLs lets people guess neighbours (a security smell); a UUID or a separate public id avoids that.

Remember: SEQUENCE batches, IDENTITY does not. The sequence increment must equal allocationSize.

How should you implement equals and hashCode on JPA entities? Senior

Never include all fields or lazy associations, and do not rely on a database-generated id alone. I use either a natural business key (an email, an order number), or a constant hashCode with an equals that compares ids only when both are non-null. And I never put Lombok @Data on an entity.

Why it is tricky: the generated id is null until persist, so a hash based on it changes after saving, and an entity stored in a HashSet before that is lost in the wrong bucket. Using all fields breaks as soon as one field changes, and a lazy association in equals or toString triggers loading, or a LazyInitializationException, or an infinite loop through a bidirectional link. Also compare with instanceof (or Hibernate.getClass), not getClass(), because proxies are subclasses.

@Override public boolean equals(Object o) {
  if (this == o) return true;
  if (!(o instanceof Order other)) return false;
  return id != null && id.equals(other.getId());
}
@Override public int hashCode() { return Order.class.hashCode(); } // constant

Why this is hard for entities in particular

equals and hashCode are used by HashSet, HashMap keys, and List.remove. Rules for good ones: equal objects have equal hashes, and the hash must not change while the object is in a hash collection. Entities fight those rules:

  • The id is null before persist and set after. A hash computed from id changes.
  • The same row can be a proxy or a real object, and a detached copy can exist from an earlier transaction. They should be "equal".
  • Fields change during the object's life, so a field-based hash changes.

The failure, by example

Set<Item> set = new HashSet<>();
Item i = new Item();          // equals/hashCode use id
set.add(i);                   // hash computed with id = null
em.persist(i);                // id becomes 42, hash changes
set.contains(i);              // false! the item is in the wrong bucket

The constant-hash version is the pragmatic default recommended by many Hibernate authors: correct, simple, and slow only when you put many thousands of entities of one type in one hash set, which you rarely should. Never include lazy associations or collections, and never use Lombok's @Data or @EqualsAndHashCode defaults on an entity: they include every field.

Remember: equals on a stable key, hashCode must not change when the id is assigned, and no @Data on entities.

How do you map enums, embedded value objects, converters and simple collections? Intermediate

I map enums with @Enumerated(EnumType.STRING) (never ordinal), group related columns into an @Embeddable value object used with @Embedded, use an AttributeConverter for custom types, and use @ElementCollection only for small collections of values that have no identity of their own.

Enums: why STRING and not ORDINAL

The default ORDINAL stores the position (0, 1, 2). If someone inserts a new constant in the middle of the enum or reorders it, every existing row now means something else, with no error. STRING stores the name, so adding or reordering constants is safe (renaming one still needs a data migration). If you want a compact, stable code, write a converter that maps each constant to an explicit short code.

Embeddables: value objects without their own table

@Embeddable class Address { String street; String city; String zip; }
@Entity class Customer {
   @Id Long id;
   @Embedded Address billing;
   @Embedded @AttributeOverrides({
      @AttributeOverride(name = "street", column = @Column(name = "ship_street")),
      @AttributeOverride(name = "city",   column = @Column(name = "ship_city")),
      @AttributeOverride(name = "zip",    column = @Column(name = "ship_zip"))}) Address shipping;
}

The columns live in the owner's table, there is no id, no join and no lazy loading. They are a clean way to model money (amount and currency) or an address, and they keep the entity class small. Make them immutable if you can, and give them equals/hashCode on all fields (they are values, so that is correct here).

Converters

@Converter with AttributeConverter<X, DbType> maps a Java type to a column type: for example a Money object to a number, a list of tags to a comma-separated string, or an enum to a short code. autoApply = true uses it for every attribute of that type. A converted attribute cannot be used in some query positions (like relationship joins) and dirty checking relies on equals of the converted value, so use immutable types.

@ElementCollection

It maps a collection of basic or embeddable values into a separate table keyed by the owner (@CollectionTable). It has no identity per element, so changing it often means delete all rows and reinsert them (for a List without an order column). That is fine for a handful of values, such as a user's phone numbers or tags. For anything large, queried, or growing, make a real entity with a @ManyToOne instead.

What interviewers probe

  • "Why is ordinal dangerous?" Silent data corruption when the enum changes.
  • "Embedded versus one-to-one?" Embedded means same table and no identity; one-to-one is a separate entity with its own lifecycle.
  • JSON columns: Hibernate 6 supports mapping a field to JSON with @JdbcTypeCode(SqlTypes.JSON) (version and database dependent); fine for flexible attributes, but you lose relational constraints and easy querying.

Remember: enums as STRING, value objects as embeddables, converters for custom types, element collections only when small.

4. Fetching, N+1 and projections

What is the difference between lazy and eager loading, and what are the JPA defaults? Basic

Eager loads the related data together with the owner. Lazy loads it only when I first touch it. The JPA defaults are EAGER for @ManyToOne and @OneToOne, and LAZY for @OneToMany, @ManyToMany and @ElementCollection. I set every association to LAZY explicitly and fetch what I need per use case.

Eager is a trap because it is fixed in the mapping: every query on that entity pays for it, whether the screen needs it or not. A JPQL query does not honour EAGER as a join, so it loads the parents first and then runs a second select per parent, which is N+1 again. Lazy is not free either: touching it outside the transaction throws LazyInitializationException, and touching it in a loop causes N+1. In JPA, FetchType on the mapping is only the default plan; a query or entity graph can override it per use case, and that is the right place to decide.

What it means, with a timeline

Take Order with a customer and a list of items.

  • Eager customer: find(Order.class, 5) runs one SELECT joining the customer (or a second SELECT immediately after). By the time the call returns, order.getCustomer() is a real object.
  • Lazy items: find returns the order with items as an uninitialised collection wrapper. Nothing runs until you iterate or call size(); then a SELECT loads the items, but only if the session is still open.

Why JPA chose different defaults

A ToOne association adds one row to the result, so eager is cheap in the spec's view. A ToMany can add thousands of rows, so lazy is the default. In real systems both defaults hurt: eager ToOne chains (order, customer, address, country) cascade into joins you did not ask for.

The correct strategy

  1. Mark every association fetch = LAZY (for @ManyToOne and @OneToOne you must write it explicitly).
  2. For each use case, fetch what you need with join fetch, an entity graph, batch fetching, or a projection.
  3. Return DTOs from the service layer, so no one touches lazy state outside the transaction.

Pitfalls

FetchType.LAZY is only a hint in the spec; Hibernate honours it for ToMany and for ToOne where a proxy can be made (see the one-to-one answer for the inverse side). em.find follows the mapping and joins eager associations; JPQL ignores that and runs follow-up selects, which is how an "all eager" model still produces N+1. Finally, open-in-view only hides LazyInitializationException by keeping the session open during rendering; it does not remove the extra queries.

Remember: ToOne is EAGER by default, ToMany is LAZY. Make all LAZY and fetch per query.

What is the N+1 select problem, and how does it happen? Basic

N+1 means one query loads N parent rows, and then N more queries run, one per parent, to load a lazy or eager association. For 10,000 orders that is 10,001 round trips. It happens because the loop touches order.getCustomer().getName() and each touch triggers its own SELECT.

It hides well: the code looks innocent, tests with 3 rows are fast, and production with 5,000 rows takes seconds. The fix is to tell Hibernate up front what the use case needs, instead of letting it discover it one row at a time. The usual tools are join fetch, an entity graph, batch fetching, or a projection (next question). The unit of measure is statements per request, so I count queries in tests rather than trust timing.

How to read this diagram. Left side: the code loads the list of orders with one query (step 1), then loops. Each pass through the loop touches a lazy customer, and each touch sends its own query (the red moving arrows, steps 2 to N+1), so the cost grows with the number of rows. Right side: a join fetch asks for orders and customers together, so the same loop needs only one round trip.

A concrete walk-through

Controller code that looks harmless:

List<Order> orders = orderRepo.findAll();            // 1 query
for (Order o : orders) {
    names.add(o.getCustomer().getName());            // lazy proxy: 1 query EACH
}

With 1,000 orders and 400 distinct customers, the log shows 1 query for orders, then up to 1,000 customer selects (the persistence context avoids repeating a customer it already loaded, so you get about 400 here, but the first-level cache does not rescue you in general). If each query costs 2 ms over the network, that is about 1 s instead of one 5 ms join.

Why it happens

Hibernate loads in terms of single entities. Asking for orders returns orders. Anything linked is a separate load triggered by access. It cannot know that the loop will touch every customer. Eager mappings do not fix this: a JPQL select o from Order o loads orders first and then issues the extra selects for the eager part.

Variants to recognise

  • ToOne N+1: one customer select per order (above).
  • Collection N+1: one items select per order when you call o.getItems().
  • Nested N+1: orders, then items per order, then product per item: N + N*M queries.
  • Serialisation N+1: Jackson walks getters and triggers every lazy association. Return DTOs instead.

How seniors reason about it

Cost is round trips times latency, not rows. A 1 ms query run 5,000 times is 5 seconds, and it multiplies under load because each one holds a pooled connection, which can exhaust the pool and stall unrelated requests. That is how an N+1 becomes an outage, not just a slow page.

Remember: 1 query for the list plus 1 per row for the association. Count SQL statements, not milliseconds.

How do you fix N+1? List your options and pick one. Intermediate

For a screen that reads data, my first choice is a DTO projection with exactly the columns needed. If I need entities, I use join fetch or an entity graph for ToOne associations, and batch fetching (@BatchSize or default_batch_fetch_size) for collections, especially when paging. Whatever I pick, I make the mapping LAZY first.

Projection (DTO)read-only lists, reportsno managed entity, so no updates

Do not "fix" it by switching to EAGER: that makes the cost permanent everywhere. After fixing, I add a test that asserts the statement count, so the problem cannot come back unseen.

When to pick which, in plain terms

  • I only display or return data: projection. One query, only needed columns, no entities.
  • I need entities and the association is ToOne (many-to-one, one-to-one): join fetch or entity graph. A ToOne join does not multiply rows.
  • I need entities and the association is a collection: if one small collection and no paging, join fetch is fine; otherwise batch fetching or a second query with in (:ids).
  • I cannot touch queries (framework generated, many call sites): set default_batch_fetch_size as a broad safety net.

Before and after

// before: 1 + N
select o from Order o where o.status = :s

// after, entity graph: 1 query with a left join on customer
@EntityGraph(attributePaths = "customer")
List<Order> findByStatus(Status s);

// after, projection: 1 query, 3 columns
select new OrderRow(o.id, o.total, c.name) from Order o join o.customer c

Why not the other "fixes"

  • EAGER everywhere: moves the cost into every query, including ones that never needed it.
  • Second-level cache: can mask N+1 for hot lookups, but a cold cache or an invalidation brings it back, and caches add staleness. Treat it as an optimisation after the query shape is right.
  • Bigger pool or faster hardware: the number of statements is still O(N).

Making it stick

A fix without a guard regresses. Add a test that loads a realistic list and asserts a statement count, for example "at most 3 SELECTs for this endpoint". Also review new association mappings in code review for explicit LAZY.

Remember: LAZY first, then projection, join fetch or graph for ToOne, batch size for collections.

What is the difference between join fetch and an entity graph? Intermediate

Both load an association in the same query as the owner. join fetch is written inside the JPQL text. An entity graph (@EntityGraph or @NamedEntityGraph) is declared separately and attached to a query or repository method, so the same query can be reused with different fetch plans, and it works with derived queries like findByStatus where I cannot write JPQL.

In Spring Data I write @EntityGraph(attributePaths = {"customer", "items"}) on a repository method. Graph hints come in two flavours: fetch graph (attributes not listed are treated as lazy) and load graph (listed attributes are eager, others keep their mapping default). Under the hood both run a left join. The rules do not change: a collection join still multiplies rows, and a collection graph with paging is still done in memory.

@EntityGraph(attributePaths = {"customer"})
List<Order> findByStatus(Status status);

@Query("select o from Order o join fetch o.customer where o.status = :s")
List<Order> findWithCustomer(@Param("s") Status s);

What each one is

A join fetch is a JPQL keyword: select o from Order o join fetch o.customer. It says "load the customer in the same SQL statement and put it into the order's field". An entity graph is a separate description of "which attributes to load for this entity", attached to a query as a hint. The SQL ends up similar (a join), but the fetch plan is not tied to one query string.

Why the graph exists

  • Spring Data derived queries (findByStatus) have no JPQL text to edit. Annotate with @EntityGraph and you are done.
  • One query, many plans. findById from the base repository can be reused with different graphs without copy-pasting JPQL.
  • Graphs can be nested: attributePaths = {"items", "items.product"}.

Fetch graph versus load graph

JPA defines two hints. With jakarta.persistence.fetchgraph (javax.persistence.fetchgraph before JPA 3) (fetch graph), every attribute not in the graph is treated as lazy even if mapped EAGER. With loadgraph, the listed attributes are eager and the rest follow the mapping. Spring Data's @EntityGraph defaults to FETCH type. Most teams make everything LAZY anyway, where the difference rarely shows.

Pitfalls

Never use an alias on a fetched collection to filter it (join fetch o.items i where i.qty > 5): the parent then holds only the filtered children in memory, which can be saved back wrongly. Use a separate query or a projection. And remember both still obey the pagination and multiple-bag rules.

Remember: join fetch lives in the query text, a graph lives beside it. Same SQL idea, graph works on derived queries.

How does @BatchSize work, and when is it better than join fetch? Intermediate

With batch fetching, when I touch the first lazy association, Hibernate loads it for up to a batch (say 50) of parents from the context at once, with where parent_id in (?, ?, ...). So 1 + N queries become 1 + N/50. It is better than join fetch for collections, especially with paging, because it does not multiply the parent rows.

I set it globally with hibernate.default_batch_fetch_size=50 (or per mapping with @BatchSize). It is a safety net more than a perfect fix: the queries are still lazy, so an access outside a transaction still throws, and I still pay more round trips than a single join. Its big strength is that it needs no change in the queries, and that it fixes ToOne and collections at once. It is not enough when I know exactly what I need: then a projection or fetch join is faster.

How it works, with numbers

You load 100 orders (1 query). Each has a lazy customer. With @BatchSize(size = 25) on Customer (or the global default):

  1. You touch orders.get(0).getCustomer().getName().
  2. Hibernate sees that order 0's customer proxy is uninitialised, and so are 99 other proxies of the same type in the context.
  3. It runs select ... from customer where id in (?, ?, ... 25 ids), initialising 25 proxies at once.
  4. When you reach the 26th unloaded customer, it runs the next batch.

Total: 1 + 4 queries instead of 1 + 100. For collections the same applies: select ... from order_item where order_id in (?, ... ).

Why choose it over join fetch

Caveats

The batch only applies to entities already in the current persistence context, so it still needs an open session at the time of touching. A typical value is 16 to 100 (the exact best number depends on the database's limit for IN parameters and on the typical page size); Hibernate rounds batch sizes to a few fixed shapes to reuse prepared statements. It reduces N+1 but does not remove it, so a known hot path should still get an explicit join or projection.

Remember: batch size turns N lazy selects into N/50 IN selects. Great default, safe with paging.

What is MultipleBagFetchException and how do you handle it? Senior

It is thrown when one query tries to join fetch two or more List collections (bags, unordered lists with duplicates allowed). The fix is not to change them to Set, which hides the error but creates a huge cartesian product. The fix is to load one collection per query: fetch the parents with the first collection, then a second query for the second collection, and let the persistence context merge them.

Why the product is the real problem: an order with 10 items and 5 payments becomes 50 rows in a double join, and with real data this explodes memory and bandwidth. Hibernate cannot tell which duplicate rows are real duplicates in a bag, which is why it refuses. Running two simple queries (select o from Order o join fetch o.items where o.id in :ids then the same for payments) uses the first-level cache to fill the same entities. Batch fetching is the other clean solution.

What "bag" means and why two are a problem

In Hibernate a List mapping without an index column is a bag: it has duplicates allowed and no stable position. When you fetch a bag with a join, each parent row is repeated once per child. If you fetch two bags together, the result is the product of the two sizes. Example: an order with 3 items and 4 payments yields 12 SQL rows. Hibernate then has to rebuild "3 items and 4 payments" from those 12 rows, but with bags that allow duplicates it cannot tell a real duplicate item from an artifact of the product. So it throws MultipleBagFetchException: cannot simultaneously fetch multiple bags instead of risking wrong data.

Why Set is only a false fix

Changing to Set makes the exception go away, since sets do not have the ambiguity. But the SQL is the same product: 1,000 orders with 20 items and 10 payments become 200,000 rows transferred and de-duplicated in Java. It works in tests and falls over in production.

The right pattern

List<Order> orders = em.createQuery(
  "select distinct o from Order o join fetch o.items where o.id in :ids", Order.class)
  .setParameter("ids", ids).getResultList();           // loads items

em.createQuery(
  "select distinct o from Order o join fetch o.payments where o.id in :ids", Order.class)
  .setParameter("ids", ids).getResultList();           // fills payments on the SAME objects

Because both queries return the same managed Order instances from the persistence context, the second just initialises the other collection. Cost: 2 queries with small results. Alternatives: @BatchSize on both collections (then no join fetch at all), a DTO projection or two separate DTO queries, or @OrderColumn to make a list an indexed list rather than a bag. Interviewers like the explanation of the cartesian product more than the code.

Remember: never fetch two collections in one query. One collection per query, or use batch size.

Why is pagination with a collection join fetch dangerous? Senior

Because joining a collection returns one row per child, so a SQL LIMIT would cut children, not parents. Hibernate cannot apply the limit in SQL, so it loads the whole joined result into memory and cuts the page in Java. The log shows HHH000104: firstResult/maxResults specified with collection fetch; applying in memory (the warning code differs in Hibernate 6, but the behaviour is typically the same). With a big table, that is an out-of-memory incident waiting to happen.

The correct approach is two steps: first query only the ids of the page (no collection join, with LIMIT), then load those parents with their children using where id in :ids. Alternatives are batch fetching (page the parents, children load in batches) or a DTO projection. Fetching a ToOne association together with a page is safe, because it does not multiply rows.

Why SQL cannot do it

Say page size is 20. The SQL for orders joined with items returns one row per item. If order 1 has 7 items, rows 1 to 7 are the same order. A LIMIT 20 on this join would return perhaps 3 orders, one of them cut in the middle (only some items). That is wrong, so Hibernate refuses to push the limit down and instead loads all matching rows, assembles the orders, and takes the first 20 in memory. With 2 million rows in the table, the JVM gets 2 million rows for each page request.

The two-step fix, with SQL shape

// Step 1: ids of one page, no collection join
List<Long> ids = em.createQuery("select o.id from Order o order by o.createdAt desc, o.id desc", Long.class)
    .setFirstResult(page * 20).setMaxResults(20).getResultList();

// Step 2: children for exactly those parents
List<Order> orders = em.createQuery(
    "select distinct o from Order o left join fetch o.items where o.id in :ids " +
    "order by o.createdAt desc, o.id desc", Order.class)
    .setParameter("ids", ids).getResultList();

Step 1 uses a real SQL limit. Step 2 returns only the rows of 20 parents. The sort must be repeated in step 2 because IN does not preserve order, and the sort key should include a unique tie-breaker like the id so pages are stable.

Alternatives

  • Batch fetching: page the parents with a normal query, set default_batch_fetch_size, and children load in a few extra IN queries as you touch them. Simple and often enough.
  • DTO projection with window functions or a native query when you need maximum control.
  • Keyset pagination (seek method) for deep pages, since big OFFSET values are slow in the database no matter what the ORM does.

Practical detection: search logs for the in-memory pagination warning, and set an alarm on it, because it silently works in development with 50 rows.

Remember: never page a collection fetch join. Page the ids first, then fetch children for those ids.

Why do I get duplicate parents with a join fetch, and what does distinct do? Intermediate

A join on a collection returns one SQL row per child, so a parent with 3 children appears 3 times in the result list. In Hibernate 5, I add select distinct in JPQL to de-duplicate the entities in memory. In Hibernate 6 the duplicates are removed automatically for entity results, so distinct is no longer needed for that purpose.

In Hibernate 5, distinct was sent to SQL as well, which can slow down the query; the hint hibernate.query.passDistinctThrough=false keeps it in Java only. When counting parents with a collection join, use count(distinct o), since a plain count counts rows.

Seeing the duplicates

Data: Order 1 with items A, B, C. The query select o from Order o join fetch o.items returns three SQL rows, each containing the order columns plus one item:

order 1 | item A
order 1 | item B
order 1 | item C

Hibernate builds the entity once and attaches the three items to it, but the returned List<Order> has one entry per SQL row, so you get the same Order object three times (list.size() == 3). With two orders of 3 items each, the list has 6 entries.

What distinct does here

In JPQL select distinct o ... asks Hibernate to remove repeated entity references from the result after building it. In Hibernate 5 it also put distinct into the SQL, which is useless (the rows differ in the item columns) and can make the database sort or hash for no reason. The query hint hibernate.query.passDistinctThrough=false (QueryHints.HINT_PASS_DISTINCT_THROUGH) keeps it Java-side. In Hibernate 6, entity results are always de-duplicated, and a leading distinct is not needed to collapse duplicates (writing it does no harm).

Related traps

  • Counting: select count(o) ... join fetch counts rows. Use count(distinct o), or better, count without the join.
  • Pagination: a collection join with setMaxResults cannot be paged in SQL (previous question).
  • Spring Data: the same behaviour applies to @EntityGraph on a collection. Check the returned list size on a Hibernate 5 project.

Remember: collection join gives one row per child. Hibernate 5 needs distinct to collapse parents, Hibernate 6 does it for you.

When should you use a projection or DTO instead of loading entities? Intermediate

Whenever the use case is read-only, such as a list screen, an API response or a report. A projection selects just the columns I need into a DTO, so there are no proxies, no snapshots for dirty checking, no lazy loading surprises and less data on the wire. I load entities only when I am going to modify them.

In JPQL I use a constructor expression, in Spring Data an interface or a record/class projection:

select new com.acme.OrderRow(o.id, o.total, c.name)
from Order o join o.customer c where o.status = :s

interface OrderRow { Long getId(); BigDecimal getTotal(); String getCustomerName(); }
List<OrderRow> findByStatus(Status s);

A trap in Spring Data: a closed interface projection (only simple getters) selects only those columns, but an open projection (with @Value("#{...}")) loads the whole entity first. Also, one big projection with a collection inside is awkward; usually I run a second query for the collection.

What you save by not loading entities

Loading an entity means: select all its columns, build the object, create a dirty-check snapshot, register it in the persistence context, possibly create proxies for lazy associations. For a table with 40 columns and a list screen that shows 4, you read and allocate 10 times more than needed. Projections skip all of that.

Three common styles

StyleExampleNotes
JPQL constructor expressionselect new OrderRow(o.id, o.total) from Order oNeeds the full class name and a matching constructor

Another option is selecting a Tuple or Object[], which is untyped and easy to get wrong, so I use it only for quick ad-hoc code.

Trade-offs and rule

Projections are read-only: you cannot modify and have it saved. They also do not share the first-level cache. The rule: for any path that ends in JSON or a table, use projections; for any path where the user changes data and you save it, load the entity (it is a unit-of-work object).

Pitfalls

  • A DTO that contains nested collections cannot come from one flat projection without duplicated rows; run a second query for the children and assemble in Java.
  • Dynamic projections (findBy(..., Class<T>)) are handy but can hide the choice of which columns get read.
  • Do not return entities from REST controllers just to avoid writing a DTO: it leaks the schema, triggers lazy loads while serialising, and breaks when mappings change.

Remember: read = DTO projection, write = entity. Open projections load the full entity.

How do you detect N+1 and other query problems before production? Intermediate

I count the SQL statements per request. In development I turn on SQL logging and Hibernate statistics, and in tests I assert the number of queries with a datasource proxy (datasource-proxy, or Hibernate's statistics bean), so a regression fails the build. In production, an APM or tracing tool shows the number of DB calls per request and flags the repeated same-shape statement.

Signs to look for: the same SELECT repeated with different ids, a request with hundreds of statements, HHH000104 pagination warnings, and long transactions. Test with realistic data volumes, since N+1 is invisible with 3 rows. Practical setup: spring.jpa.properties.hibernate.generate_statistics=true in a profile, plus a test helper that resets and reads the prepared-statement count.

Three levels of defence

  1. While developing: turn on spring.jpa.show-sql or, better, log org.hibernate.SQL at debug level so you see parameter-bound statements in order. Scroll once through the log for the endpoint you just wrote. If you see the same SELECT shape repeating, you have N+1.
  2. In automated tests: count statements and fail the build when the count grows. A small library such as datasource-proxy wraps the DataSource and counts SELECT/INSERT/UPDATE per test. Hibernate's Statistics (getPrepareStatementCount()) also works. The assertion reads like "listOrders issues at most 2 SELECTs".
  3. In production: tracing/APM (for example OpenTelemetry with JDBC instrumentation) shows spans per database call under each HTTP request, so a trace with 300 child spans of the same query is obvious. Dashboards for "DB calls per request" catch regressions after a release.

Example test shape

statementCounter.reset();
service.listOrders();                       // call the endpoint logic
assertThat(statementCounter.selects()).isLessThanOrEqualTo(2);

Why data volume matters

Test fixtures usually have two or three rows, so N+1 costs 4 queries and nobody notices. Seed enough rows (50 to 100) in the test that the count scales visibly: a result of 102 versus 3 is unmistakable.

Other signals to watch

  • Slow-query log shows tiny queries with very high call counts (a different pattern than one slow query).
  • Connection pool metrics (active connections, wait time) spike under modest traffic.
  • Tools: Hibernate's slow query threshold (hibernate.session.events.log.LOG_QUERIES_SLOWER_THAN_MS, version dependent), and an index advisor or EXPLAIN on the repeated statement.

Remember: you cannot see N+1 in one query's timing. Count statements per request, in tests and in APM.

5. Transactions with Spring, and lazy loading errors

How does @Transactional work inside Spring? Intermediate

Spring wraps my bean in a proxy. When someone calls a @Transactional method through that proxy, the proxy starts a transaction (gets a connection and binds an EntityManager to the thread), calls my method, then commits if it returns normally or rolls back on a runtime exception. My code never calls begin or commit.

The proxy is the whole trick, so anything that bypasses it gets no transaction: a call from another method in the same class, a private method, a bean created with new. The transaction is stored in a thread-local, so work on another thread (an @Async method, a parallel stream, a CompletableFuture) is outside it. At commit, Spring flushes the persistence context first, and that is when most SQL and most constraint errors actually appear.

How to read this diagram. The controller never talks to your real service directly: it holds the Spring proxy (the tinted box). Follow the moving arrows left to right. (1) The proxy starts the transaction, borrows one connection and binds an EntityManager to the thread. (2) It calls your real method. (3) Inside it, repositories reuse that same EntityManager, which talks to the database over the one connection. (4) When your method returns, the proxy flushes and commits (or rolls back on a runtime exception). (5) It closes the EntityManager and returns the connection. If a call skips the proxy, steps 1, 4 and 5 never happen.

Why a proxy and not something else

Spring wants transactions to be declarative: you describe "this method needs a transaction" and the framework does the plumbing. To do that without changing your class, it creates a stand-in object (a proxy) that has the same methods as your service. Every other bean that receives your service actually receives the proxy. A call goes through three stages:

  1. Before: the proxy asks the PlatformTransactionManager to start a transaction. For JPA it borrows a connection from the pool, begins the database transaction and binds an EntityManager to the current thread.
  2. Invoke: it calls your real method. Repositories used inside find the same thread-bound EntityManager, which is how many repository calls share one persistence context.
  3. After: on normal return it flushes and commits. On a runtime exception it rolls back. Then it unbinds and closes the EntityManager and returns the connection.

Small example

@Service
class TransferService {
  @Transactional
  void transfer(Long from, Long to, BigDecimal amt) {
     Account a = repo.findById(from).orElseThrow();   // same EntityManager
     Account b = repo.findById(to).orElseThrow();     // same EntityManager
     a.debit(amt); b.credit(amt);                     // two UPDATEs at commit, atomic
  }
}

If credit throws, neither UPDATE is committed. Without @Transactional, each repository call would run in its own short transaction, and the debit could be saved while the credit is lost.

What to remember about the mechanics

  • Proxies are made with JDK interfaces or CGLIB subclasses (Spring Boot defaults to class-based CGLIB). This is why the class and the intercepted methods cannot be final, and why annotations on private methods are ignored.
  • The binding is to a ThreadLocal, so a different thread has no transaction.
  • The default propagation is REQUIRED: if a transaction is already open on this thread, the method joins it.
  • The commit-time flush explains why constraint violations appear as DataIntegrityViolationException thrown by the proxy after your method has already returned.

Remember: @Transactional = a proxy around the call. No proxy, no transaction.

Why might @Transactional not work? Give the usual causes. Intermediate

The usual causes are: self-invocation (a method calling another method of the same class skips the proxy), a non-public or final method or class where the proxy cannot intercept, an object created with new instead of injected, a checked exception that by default does not roll back, a caught exception that never reaches the proxy, and work on another thread.

  • Self-invocation: this.save() from the same class. Fix: move it to another bean, or inject a self-reference, or use TransactionTemplate.
  • Checked exception: the default rule rolls back on unchecked exceptions and Error only. Use rollbackFor = Exception.class when needed.
  • Swallowed exception: a try/catch that logs and continues means the proxy sees success and commits.
  • Wrong annotation or config: a different Transactional import still works (both are supported), but a missing @EnableTransactionManagement outside Spring Boot, or a bean not managed by Spring, does not.
  • Another thread: @Async methods and executors get their own, separate (or no) transaction.

Why each trap happens

Every trap has one root: the transaction lives in the proxy, not in your code. If the call does not go through the proxy, or the proxy does not see the failure, the annotation has no effect.

Self-invocation, with the smallest example:

@Service class OrderService {
  public void process() {          // no @Transactional
     this.saveAll();               // direct call on 'this', not on the proxy
  }
  @Transactional
  public void saveAll() { ... }    // NO transaction here
}

Fix: move saveAll to another bean, put @Transactional on the outer method, or wrap the block with TransactionTemplate (explicit, works everywhere). Injecting the bean into itself also works but is considered a smell.

Rollback rule. A checked exception such as IOException does not roll back by default (the EJB-era convention treated checked exceptions as business outcomes). Use @Transactional(rollbackFor = Exception.class) when you throw checked exceptions you consider failures.

Swallowed exception.

@Transactional
void run() {
  try { repo.save(x); }          // may fail at flush
  catch (Exception e) { log.error("ignored", e); }   // proxy sees a normal return
}

The proxy sees a normal return and commits (or hits the rollback-only problem if an inner proxy already marked it). Either rethrow, or set TransactionAspectSupport.currentTransactionStatus().setRollbackOnly().

Checklist when "my transaction does nothing"

  1. Is the bean Spring-managed (injected, not new)?
  2. Is the call coming from another bean, through the proxy?
  3. Is the method visible to the proxy? Public is the safe choice; recent Spring versions can advise protected or package-private methods with class-based proxies, but do not rely on it.
  4. Does the failing exception match the rollback rule?
  5. Is the code running on the same thread (no @Async, no parallel stream, no reactive switch)?
  6. Is the right transaction manager used when there are several data sources?

Quick diagnosis: set logging.level.org.springframework.transaction.interceptor=TRACE or org.springframework.orm.jpa=DEBUG to see "Getting transaction for ..." lines, or check TransactionSynchronizationManager.isActualTransactionActive().

Remember: self-call, private, checked exception, swallowed exception, another thread.

Explain transaction propagation: REQUIRED, REQUIRES_NEW, NESTED and the rest. Intermediate

Propagation says what a method does when a transaction already exists. REQUIRED (default) joins it, or starts one if none. REQUIRES_NEW suspends the current one and runs in a completely separate transaction with its own commit. NESTED runs inside the same transaction but with a savepoint, so only the inner part can roll back. The rest: SUPPORTS, NOT_SUPPORTED, MANDATORY (fail if none) and NEVER.

I use REQUIRES_NEW for things that must commit even if the caller fails, such as an audit record, and I accept the cost: it takes a second connection from the pool while the first is held, so in a busy system a pool of 10 can deadlock itself. NESTED needs JDBC savepoint support and is rarely used with JPA. The most common surprise is with REQUIRED: if the inner method throws, it marks the shared transaction as rollback-only, so the outer caller cannot rescue it just by catching (see the scenario on UnexpectedRollbackException).

Why propagation exists

Real code calls services from services. When checkout() calls paymentService.charge() and both are transactional, you must decide: is this one atomic unit or two? Propagation is that decision, made at the callee.

Behaviour of each setting

A worked example: audit log that must survive

@Transactional
void placeOrder(Order o) {
   orderRepo.save(o);
   audit.record("ORDER_ATTEMPT", o.getId());   // REQUIRES_NEW: committed right away
   if (o.getTotal().signum() <= 0) throw new IllegalArgumentException();  // outer rolls back
}

The order insert is rolled back, but the audit row stays, because it committed in its own transaction. With REQUIRED, the audit row would have vanished too.

Costs and traps

  • Two connections. REQUIRES_NEW holds the outer connection while using a second. With a pool of 10 and 10 concurrent requests all waiting for their second connection, you get a pool-exhaustion deadlock. Keep the inner work small or size the pool accordingly.
  • Visibility. The new transaction cannot see the outer transaction's uncommitted rows. If the inner method reads an entity the outer just inserted, it will not find it.
  • NESTED needs JDBC savepoint support; JpaTransactionManager with Hibernate can use savepoints, but the persistence context is not rolled back to the savepoint (entities changed in the nested part stay dirty), so most teams use REQUIRES_NEW or restructure.
  • Propagation also only works across proxies: calling a REQUIRES_NEW method on this does nothing special.

Remember: REQUIRED joins, REQUIRES_NEW is separate (and needs a second connection), NESTED is a savepoint.

What are the isolation levels, and which problems does each prevent? Intermediate

Isolation controls what a transaction can see of other transactions' work. READ_UNCOMMITTED allows dirty reads. READ_COMMITTED prevents dirty reads but allows non-repeatable reads and phantoms. REPEATABLE_READ also prevents non-repeatable reads. SERIALIZABLE prevents all anomalies, at a high cost. The default of @Transactional is the database default: typically READ_COMMITTED on PostgreSQL, Oracle and SQL Server, and REPEATABLE_READ on MySQL InnoDB.

LevelDirty readNon-repeatable readPhantom
READ_UNCOMMITTEDpossiblepossiblepossible
READ_COMMITTEDnopossiblepossible
REPEATABLE_READnonopossible (standard), often no in practice
SERIALIZABLEnonono

The exact behaviour differs by database (PostgreSQL's repeatable read is snapshot isolation and also prevents phantoms; it does not have a real read-uncommitted). I rarely raise the level in application code: for "check then update" I use a version column or a row lock, which is cheaper and more explicit than serializable. Note also that isolation protects database reads, not the persistence context: a repeated find returns the cached object anyway.

The three anomalies, in plain terms

  • Dirty read: you read a value another transaction has written but not yet committed. If they roll back, you used data that never existed.
  • Non-repeatable read: you read row 5 twice in your transaction and see different values because someone committed in between.
  • Phantom read: you run select ... where status = 'NEW' twice and the second time extra rows appear because someone inserted matching rows.

A concrete timeline (READ_COMMITTED)

  1. T1 reads balance of account 1: 100.
  2. T2 sets it to 50 and commits.
  3. T1 reads again: 50. That is a non-repeatable read, allowed at READ_COMMITTED, not at REPEATABLE_READ.

Why not use SERIALIZABLE everywhere

Higher isolation means more locking or more aborted transactions (serialization failures that you must retry). Throughput drops and application code must handle retries. Most apps keep the default and guard specific "read then write" spots with locks or versions.

Important details that interviewers probe

  • The table above is the SQL standard. Real databases deviate: PostgreSQL implements multi-version snapshots, so its REPEATABLE_READ has no phantoms but can fail with a serialization error; MySQL InnoDB's REPEATABLE_READ uses gap locks for locking reads. Oracle offers READ COMMITTED and SERIALIZABLE only.
  • Lost update is a separate problem. At READ_COMMITTED, two transactions can read-then-write the same row and one overwrites the other. Isolation levels in the standard do not name it; it is handled by @Version, SELECT FOR UPDATE, or an atomic UPDATE.
  • In Spring you can set it with @Transactional(isolation = Isolation.SERIALIZABLE), and the transaction manager applies it only when it starts a new transaction (not when joining).
  • The persistence context can hide differences: the second find in one transaction returns the cached object without touching the database, so you get "repeatable" reads from Hibernate whatever the database level.

Remember: default is READ_COMMITTED (MySQL: REPEATABLE_READ). Use @Version or locks for conflicts, not higher isolation.

What are the rollback rules, and what is UnexpectedRollbackException? Intermediate

By default Spring rolls back for RuntimeException and Error, and commits for checked exceptions. I change this with rollbackFor and noRollbackFor. UnexpectedRollbackException appears when an inner method that joined my transaction threw an exception, which marked the shared transaction rollback-only, and I caught it and carried on; at the end Spring refuses to commit and throws it.

The reason is that there is only one physical transaction under REQUIRED, and the inner proxy has already decided "this transaction must roll back". Catching the exception in the outer method does not undo that mark. Fixes: let the exception propagate, call the risky part with REQUIRES_NEW (accepting its separate transaction), or do not use an exception for an expected case (check first, return a result). A related trap: after any exception from the persistence context, the entities may be in an unknown state, so the Hibernate session should be treated as unusable.

The two rules, side by side

Exception thrown out of the @Transactional methodDefault result
RuntimeException (e.g. IllegalStateException, DataAccessException)Rollback
Error (e.g. OutOfMemoryError)Rollback
Checked (IOException, custom extends Exception)Commit

Override per method with rollbackFor = {MyBusinessException.class} or noRollbackFor = .... A common team rule is to make business exceptions unchecked, so the default does the right thing.

How UnexpectedRollbackException happens, step by step

@Transactional                       // outer, REQUIRED
void outer() {
   try { inner.risky(); }            // inner is also REQUIRED: joins the same tx
   catch (Exception e) { log.warn("continuing"); }
   repo.save(something);             // looks fine
}                                    // commit -> UnexpectedRollbackException
  1. risky() throws a runtime exception as it exits its proxy.
  2. The inner proxy sees it must roll back, but it does not own the transaction (it only joined), so it cannot actually roll back. Instead it marks the transaction rollback-only.
  3. The outer method catches the exception and carries on, believing it recovered.
  4. At the outer proxy's commit, Spring sees the rollback-only flag, rolls back, and throws UnexpectedRollbackException: Transaction silently rolled back because it has been marked as rollback-only so that you do not think the data was saved.

Fixes, by intent

  • If failure of the inner call should fail everything: do not catch, or rethrow.
  • If the inner call is optional and may fail independently: make it REQUIRES_NEW so its failure only rolls back its own transaction.
  • If it is an expected situation (not found, duplicate): do not use an exception at all; check first or return a result object.

Related: after a Hibernate exception (such as a constraint violation at flush) the session state is inconsistent, so continuing to use the same persistence context is unsafe even if you caught the exception.

Remember: unchecked rolls back, checked commits. Catching an inner exception does not clear the rollback-only mark.

What is LazyInitializationException and how do you fix it properly? Basic

It means I touched a lazy association (a proxy or lazy collection) after the session was closed, so Hibernate had no connection to load it. The proper fix is to load what I need while the transaction is still open: use a join fetch, an entity graph or a DTO projection, and map to the DTO inside the service method. I do not fix it with EAGER or with enable_lazy_load_no_trans.

The usual place it happens is in the controller or JSON serialiser, after the service method returned a detached entity. EAGER fixes the symptom by making every query pay for the data, forever. hibernate.enable_lazy_load_no_trans=true opens a new session for each lazy touch, so each lazy access gets its own connection and transaction: it hides the problem and turns N+1 into N+1 connections. The clean design is that services return DTOs, and controllers never see entities.

What actually happens, step by step

  1. The service loads an Order in a transaction. Its items field holds a lazy wrapper (PersistentBag) that knows only the owner id and the session.
  2. The service method returns. The transaction commits, the session closes.
  3. The controller or Jackson calls order.getItems().size().
  4. The wrapper tries to run select ... where order_id = ?, finds no open session, and throws LazyInitializationException: failed to lazily initialize a collection of role ..., could not initialize proxy - no Session.

Fix options and their quality

FixQualityWhy
Fetch inside the transaction (join fetch, entity graph, Hibernate.initialize)GoodExplicit, one controlled query
Map to a DTO inside the serviceBestNo entity leaves the transaction; no accidental lazy load
Make the association EAGERBadEvery query on the entity pays, forever
Open Session In ViewHides itKeeps connection open during rendering
enable_lazy_load_no_trans=trueAnti-patternOpens a temporary session per lazy access: more connections, N+1 queries

Example of the proper fix

@Transactional(readOnly = true)
public OrderView get(Long id) {
    Order o = repo.findWithItemsById(id).orElseThrow();   // join fetch / graph
    return new OrderView(o.getId(), o.getItems().stream().map(ItemView::from).toList());
}

Remember that the exception is a helpful signal: it tells you the code is reading data it never planned to load. A related surprise: a lazy collection can be fine in a unit test with an open session but fail in production, so test through the real layering.

Remember: fetch inside the transaction and return DTOs. EAGER and no-trans lazy loading only hide the bug.

What is Open Session In View (OSIV), and should you leave it on? Intermediate

OSIV keeps the EntityManager open for the whole web request, until the response is rendered, so lazy loading works in controllers and in JSON serialisation. Spring Boot enables it by default (spring.jpa.open-in-view=true, with a startup warning). For a serious service I turn it off, because it hides lazy-loading and N+1 bugs and holds a database connection while the controller does slow work.

The details: the session is open, but each lazy load outside a transaction runs in autocommit mode on a connection that is held until the request ends. So a slow remote call in the controller, or serialising a big response to a slow client, keeps a pool connection busy; under load this exhausts the pool. With OSIV off, all loading must happen inside the service transaction, which forces explicit fetching and DTOs. That is the design I want, though the migration finds many hidden lazy accesses.

What it does, concretely

With OSIV, Spring registers an interceptor (OpenEntityManagerInViewInterceptor) at the start of each web request. It creates an EntityManager and binds it to the request thread. The service's @Transactional method then reuses that EntityManager, but when the transaction commits, the EntityManager is not closed. It remains open until the response is fully written, so lazy loads in the controller or view still find a session.

Why it is convenient and why it is risky

  • Convenient: returning an entity from a controller and letting Jackson walk lazy getters "just works" in a demo.
  • Hides problems: each lazy touch outside the service runs its own SELECT in autocommit, so the N+1 is moved to the serialisation phase where it is hard to see in code review.
  • Holds connections: after the service method, the JDBC connection can stay checked out (depending on release mode) while the controller calls other services, builds big JSON, or waits on a slow client. Under load, the pool of say 10 connections is used by 10 slow responses, and everyone else waits.
  • Semantics: lazy loads after commit read data in different transactions, so a response may combine inconsistent snapshots.

Turning it off

Set spring.jpa.open-in-view=false. You will immediately find places that rely on lazy loading outside the service. Fix each one by fetching in the service (join fetch, graph, projection) and returning DTOs. This forces the layered design you want anyway: the service decides what data a use case needs, the controller only formats it.

Interviewers often ask "why does Spring Boot print a warning about open-in-view at startup?" Because the Boot team considers the default risky and wants you to choose consciously.

Remember: OSIV on = convenient but leaks connections and hides N+1. Set open-in-view=false and return DTOs.

Why should you not call remote services inside a transaction? Senior

Because the transaction holds a database connection and often row locks for as long as the remote call takes, and the remote call is slow or can hang. Under load the connection pool empties, and other requests wait or fail. I keep transactions short and database-only, and call remote services outside them.

There is also a correctness problem: if I call an external API or send a message inside the transaction and then the commit fails, the outside world has already seen the effect, and I cannot roll it back. Patterns: do the remote call first and the database write after; use TransactionTemplate for a small, explicit transactional block; or use a transactional outbox (write an event row in the same transaction, and a separate publisher sends it after commit). @TransactionalEventListener(phase = AFTER_COMMIT) is a lightweight option inside one service.

What a transaction costs while it is open

  • A pooled database connection (pools typically have 10 to a few dozen).
  • Row locks acquired by writes (and by FOR UPDATE reads) that block other transactions until commit.
  • Old row versions the database must keep for snapshots (in MVCC databases), which can bloat storage if transactions are very long.

A remote HTTP call inside the transaction adds its latency, and its worst case (timeout, hang), to all of the above.

A before-and-after example

// risky: connection and row locks held while waiting for the payment API
@Transactional
void checkout(Order o) {
   o.markPending();
   paymentApi.charge(o);          // maybe 200 ms, maybe 30 s when the provider is down
   o.markPaid();
}

// better: split into short database steps around the remote call
void checkout(Long id) {
   tx.executeWithoutResult(s -> repo.markPending(id));    // short tx
   PaymentResult r = paymentApi.charge(id);               // no tx, no connection
   tx.executeWithoutResult(s -> repo.markResult(id, r));  // short tx
}

This makes the in-between state ("PENDING") explicit, which also helps when the app crashes after charging: a recovery job can look for pending orders and ask the provider what happened. Idempotency keys on the remote call make retries safe.

The messaging variant

"Update the database and publish a message" cannot be atomic across two systems. If you publish inside the transaction and the commit fails, consumers see an event for something that did not happen. If you publish after commit and crash, the event is lost. The transactional outbox solves it: write an outbox row in the same transaction as the business change, and a separate process reads outbox rows and publishes them, retrying until done (consumers must tolerate duplicates). For a lighter in-process option use @TransactionalEventListener(phase = AFTER_COMMIT), accepting that a crash between commit and handler loses the event.

Remember: short DB-only transactions. Remote calls go outside, or through an outbox.

6. Concurrency and locking

What is a lost update, and how does optimistic locking prevent it? Intermediate

A lost update happens when two users read the same row, both change it, and the second save silently overwrites the first. Optimistic locking prevents it by adding a @Version column. Every UPDATE includes where id = ? and version = ? and increments the version; if another transaction already changed the row, zero rows match and Hibernate throws an OptimisticLockException instead of overwriting.

"Optimistic" means I do not lock anything while the user thinks; I assume conflicts are rare and detect them at write time. The caller then retries (for automatic work) or tells the user "this record was changed by someone else" (HTTP 409 in a REST API). In Spring the exception arrives as ObjectOptimisticLockingFailureException. For this to protect a web form, the version must travel with the data: send it to the client and send it back in the update request, otherwise I re-read the latest version in the update call and the check protects nothing.

@Entity class Customer {
  @Id @GeneratedValue Long id;
  @Version Long version;     // Integer, Long or Timestamp
  String name;
}
-- generated: update customer set name=?, version=2 where id=? and version=1

How to read this diagram. Time runs downward. Both transactions first read the same customer at version 1. Transaction 1 saves first: its UPDATE has WHERE version=1, matches the row, and the row moves to version 2 (green arrow). Transaction 2 then sends the same kind of UPDATE with version 1, but the row is already at version 2, so zero rows match (red arrow) and Hibernate throws instead of overwriting.

The problem, with a timeline

  1. Asha opens customer 7 in an edit form (name "Ann", phone "111"). Version is 1.
  2. Ben opens the same customer. Version 1.
  3. Asha changes the phone to "222" and saves. Row: phone "222", version 2.
  4. Ben changes the name to "Anna" and saves. Without a version check his save writes name "Anna" and the old phone "111", because his form held the old value. Asha's change is lost, and nobody gets an error.

How @Version stops it

Ben's UPDATE carries the version he read: update customer set name='Anna', phone='111', version=2 where id=7 and version=1. The row is already at version 2, so zero rows match. Hibernate checks the update count, sees 0 where it expected 1, and throws. The transaction rolls back, Ben gets a clear conflict instead of silent data loss.

Making it work across HTTP requests

Within one transaction the persistence context holds the version, so protection is automatic. But in a web app the read and the write are different requests. If your update endpoint loads the latest entity and only then applies Ben's field changes, the version it holds is the latest (2), the check passes, and the lost update still happens. You must send the version (or an ETag) to the client and require it back:

PUT /customers/7   If-Match: "1"      // version from the earlier GET
// server: load, compare version with If-Match; if different, return 409/412
// or copy the client's version into the detached entity before merge

Details worth knowing

  • Types: int, long, short or timestamp. Numbers are preferred; timestamps can collide when two updates happen in the same tick.
  • Bulk JPQL updates and native SQL bypass versioning unless you add version = version + 1 yourself (JPQL has update versioned in HQL).
  • A change to a @OneToMany collection (inverse side) does not bump the parent's version unless you use @OptimisticLock settings or OPTIMISTIC_FORCE_INCREMENT.
  • Retry is correct for background jobs (reload and reapply); for users, show a "changed by someone else" message.

Remember: @Version turns a silent overwrite into an exception. Retry or return 409, and send the version with the form.

How does pessimistic locking work in JPA? Intermediate

Pessimistic locking locks the database row when I read it, so nobody else can change it until my transaction ends. I ask for it with LockModeType.PESSIMISTIC_WRITE (or @Lock on a Spring Data query), and Hibernate issues SELECT ... FOR UPDATE. I use it for short, high-contention work like decrementing stock, and always with a lock timeout.

The costs: other writers wait, so throughput drops and deadlocks become possible if two transactions lock rows in a different order. So keep the transaction short, lock rows in a consistent order, and set jakarta.persistence.lock.timeout so waiting ends. PESSIMISTIC_READ (shared lock) is less used. A useful variant is skip-locked (SELECT ... FOR UPDATE SKIP LOCKED, via Hibernate's lock timeout hint -2) for job queues, where each worker takes rows nobody else holds. Plain atomic SQL like update stock set qty = qty - 1 where id = ? and qty > 0 often beats both.

@Lock(LockModeType.PESSIMISTIC_WRITE)
@QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout", value = "3000"))
Optional<Account> findById(Long id);

How it plays out

Two payment workers both try to deduct from account 1 (balance 100).

  1. Worker A: SELECT ... FROM account WHERE id=1 FOR UPDATE. The database locks the row and returns it.
  2. Worker B runs the same statement. The database makes it wait.
  3. A updates the balance and commits, releasing the lock.
  4. B's select now returns the up-to-date balance and B proceeds.

No lost update, no retries, but B was blocked for A's whole transaction.

Lock modes in JPA

ModeEffect
PESSIMISTIC_WRITEExclusive lock (FOR UPDATE): nobody else reads-for-update or writes
PESSIMISTIC_READShared lock (FOR SHARE or equivalent where supported): others may read, nobody writes
PESSIMISTIC_FORCE_INCREMENTWrite lock plus version bump
OPTIMISTIC, OPTIMISTIC_FORCE_INCREMENTVersion checks without a database lock

Dangers and how to handle them

  • Deadlock. A locks row 1 then row 2; B locks row 2 then row 1. The database detects it and kills one transaction. Always lock in a fixed order (for example ascending id).
  • Waiting forever. Set a timeout, so the user sees an error and the pool is not exhausted by blocked threads. Treat PessimisticLockException and LockTimeoutException as retryable.
  • Long transactions. Never hold a pessimistic lock across user think time or a remote call.
  • Range locks. Locking a query that returns many rows locks them all; query by id where you can.

SKIP LOCKED for queues. If many workers poll a job table, select ... for update skip locked limit 10 lets each worker take free rows without waiting on rows another worker has locked. Support depends on the database (PostgreSQL, Oracle, MySQL 8 and later have it).

Often the best option is no lock at all: update stock set qty = qty - 1 where id = ? and qty > 0 is atomic in the database, and the returned row count tells you whether it succeeded.

Remember: pessimistic = FOR UPDATE, short transaction, fixed lock order, always a timeout.

Optimistic or pessimistic: how do you choose? Senior

I default to optimistic: it needs no database locks, scales well and fits web apps where users take time between read and save. I choose pessimistic when conflicts on the same row are frequent and a failed retry is expensive or not possible, such as a hot account balance or a job queue. And when the update can be a single atomic SQL statement, I use that instead of both.

SituationPick
Rare conflicts, user think time (forms)Optimistic (@Version)
Frequent conflicts, short critical sectionPessimistic write with timeout
Counter or stock decrementAtomic update ... where qty > 0
Many workers taking jobsFOR UPDATE SKIP LOCKED
Whole aggregate must stay consistentOPTIMISTIC_FORCE_INCREMENT on the root

Under high conflict, optimistic locking wastes work in retries, a "retry storm". Under low conflict, pessimistic locking wastes throughput for no reason. A version column is cheap insurance on almost every table, even when I also use a lock.

The deciding question: how likely is a conflict, and what does failure cost?

Optimistic bets conflicts are rare. Cost when right: almost nothing (one extra column and a WHERE clause). Cost when wrong: a failed transaction that the app must retry or report. Pessimistic bets conflicts are likely, and pays up front with waiting. Cost when right: nothing is wasted, because only one transaction at a time does the work. Cost when wrong (no conflict): every request waits for no benefit, and you risk deadlocks.

Worked comparison with numbers

  • Profile editing, 1 in 10,000 saves conflicts. Optimistic: 9,999 cheap successes and one 409. Pessimistic would lock rows while users read the form, which is unthinkable (a user may leave for lunch).
  • Flash-sale stock counter, 500 buyers per second on one row. Optimistic: most attempts fail and retry, so the system burns CPU and gets slower as load rises (a retry storm). Better: an atomic update ... where qty > 0, or a short pessimistic lock, or a queue that serialises decrements.
  • Job table with 20 workers. Pessimistic with SKIP LOCKED (or a broker such as Kafka/SQS instead of a table).

How to explain the safeguards

  • With optimistic: bounded retries with a small random delay (jitter), idempotent operations, and a clear message for user-facing conflicts.
  • With pessimistic: timeouts, ordered locking, short transactions, and metrics on lock wait time.
  • With either: keep @Version on important tables as a last line of defence, because developers forget locks but a version column guards every write that goes through JPA.

Another senior-level point: both approaches protect one database. If the same data is also changed through another service or an event, you need the same discipline there (for example, conditional updates or an owning service), because locks do not cross systems.

Remember: rare conflicts = optimistic, hot rows = lock or atomic SQL. Add @Version by default.

An OptimisticLockException happened. How do you retry correctly? Senior

I retry the whole unit of work in a new transaction: reload the entity, reapply the business change, save. I never retry inside the same transaction or with the same stale object. For background jobs and idempotent commands I retry a few times with jitter; for a user editing a form I return HTTP 409 and let the user decide.

Why the retry must be outside the transaction

Once the optimistic check fails, Spring marks the transaction rollback-only, and the persistence context holds a stale copy of the entity. A second save in the same transaction cannot succeed. The retry has to wrap the transactional method from outside so it gets a new transaction, a new persistence context and a fresh read.

// Spring Retry (or a manual loop)
@Retryable(retryFor = ObjectOptimisticLockingFailureException.class,
           maxAttempts = 3, backoff = @Backoff(delay = 50, multiplier = 2, random = true))
public void rename(Long id, String name) { inner.renameTx(id, name); }   // renameTx is @Transactional

// the retry advice must sit OUTSIDE the transaction advice, and
// the call goes through another bean so both proxies apply

What must be true to retry safely

  • The operation is idempotent or recomputed from fresh data ("set balance = balance - 10" on the freshly loaded row is fine; "apply the old computed result" is not).
  • No external side effects happened inside the failed attempt (emails, messages). Use an outbox so side effects only follow a committed transaction.
  • The number of attempts is bounded, with jitter, so competing writers do not collide in lockstep.

When retrying is the wrong answer

If conflicts are common (a hot row), retries waste work and make things worse; move to a pessimistic lock or an atomic update. If a human saw stale data on a form, retrying silently would overwrite what they did not see; report the conflict instead.

Remember: retry the whole transaction with fresh data, bounded and with jitter. Humans get a 409, not a silent retry.

7. Caching

What is the difference between the first-level and second-level cache? Intermediate

The first-level cache is the persistence context: per session, always on, and it cannot be turned off. The second-level cache is optional, shared by all sessions of the same SessionFactory, and needs a provider like Ehcache, Infinispan or Hazelcast. A lookup by id checks L1, then L2, then the database.

L2 stores entity data in a "dehydrated" form (column values, not objects) and is used by find and lazy loading by id, not by ordinary queries. I enable it per entity (@Cacheable with @Cache(usage = ...)) for data that is read often and changes rarely, such as countries or product categories. Strategies are READ_ONLY, NONSTRICT_READ_WRITE, READ_WRITE and TRANSACTIONAL, in increasing consistency and cost. The main risk is staleness: if another application, a SQL script or another node writes the row, a local cache does not know.

How to read this diagram. A find(id) inside a transaction first asks the L1 cache (the persistence context). On a miss it asks the L2 cache, if one is enabled for that entity. On a second miss it goes to the database, and the row it returns is stored in L2 and L1 on the way back. A hit at any box ends the walk there, so no SQL runs.

Two caches with different jobs

Walk through

  1. Request 1 does find(Country.class, "IN"). L1 miss, L2 miss, database read. Result stored in L2 and L1.
  2. Request 2, different transaction, same call. L1 is empty (new context), L2 hit: Hibernate rebuilds an entity from the cached values. No SQL.
  3. Someone updates the country through Hibernate. Hibernate updates or invalidates the L2 entry (depending on the strategy) at commit.

What L2 does not do

It is used for lookups by id (find, lazy loading of a ToOne, collection element loading if cached). Ordinary JPQL queries always go to the database unless the query cache is enabled, and even then it returns ids. So L2 helps "load by id" workloads and does nothing for "search" workloads.

Concurrency strategies

  • READ_ONLY: never changes; fastest. Updates throw an error.
  • NONSTRICT_READ_WRITE: updates invalidate after commit; a small stale window exists.
  • READ_WRITE: uses soft locks to avoid stale reads; good default for mutable data.
  • TRANSACTIONAL: full JTA transactional caches; rare.

The big caveat: a cache only sees changes made through the same Hibernate. Changes by a DBA script, a native update, or another application leave stale values unless you evict manually or use short expiry.

Remember: L1 is per transaction and automatic. L2 is shared, opt-in, and only good for read-mostly data.

How do you enable the second-level cache, and when is it a bad idea? Senior

I add a cache provider (usually through JCache, with Ehcache or Infinispan), set hibernate.cache.use_second_level_cache=true and the region factory, and annotate only the chosen entities with @Cacheable and @Cache(usage = READ_WRITE). I also size and expire the regions. It is a bad idea for data that changes often, is written by other systems, or runs on many nodes without a cluster-aware provider.

Collections need their own annotation (@Cache on the collection) and are cached as id lists. Reality check before I enable it: most "slow read" problems are N+1 or missing indexes, which a cache hides rather than fixes, and a stale cache creates bugs that are hard to reproduce. In a multi-node deployment I would rather use an application-level cache (Spring Cache with Redis) where I control keys and expiry, and keep Hibernate L2 for small static reference data. Bulk JPQL updates evict the affected entity regions, but native SQL may not, so be careful there.

Setup in practice

Property names vary by version (for example the JCache provider key, and javax versus jakarta in names), so I check the Hibernate documentation for the version in use. Then configure each region's size and time-to-live in the provider (for example Ehcache XML), and turn on statistics to confirm hits.

How to decide if L2 is justified

  1. Is the data read very often and changed rarely (reference tables: countries, currencies, product categories)?
  2. Is it read by id (or via lazy ToOne) rather than searched?
  3. Can you tolerate seconds of staleness, or is every write from this application?
  4. Can you measure a real database bottleneck that it would remove?

If any answer is no, use something else. Per-node local caches in a cluster means each node has its own copy and invalidation messages must be distributed (Infinispan, Hazelcast, or Ehcache with replication/terracotta). Without that, node A updates a country and node B serves the old one until expiry.

Alternatives

  • Spring Cache (@Cacheable) on service methods, with Caffeine locally or Redis shared. You choose the keys, TTL and eviction, and caching DTOs avoids entity-state issues.
  • HTTP caching (ETag, Cache-Control) for read APIs.
  • Fix the real cause (indexes, N+1, a projection) first.

Remember: L2 is opt-in per entity, for read-mostly data. Measure first, and expect staleness across nodes.

What is the query cache, and why is it rarely worth it? Senior

The query cache stores the result of a query (the list of ids) keyed by the query text and parameters. It must be switched on globally and per query. It is rarely worth it because any write to a table involved invalidates every cached query that touched that table, so on busy tables the hit rate is poor and the cache only adds overhead.

It stores ids only, and the entities themselves must come from L1, L2 or the database, so without L2 for those entities, a cached query can even lead to N queries by id. It fits queries over read-mostly data with a small result set and repeating parameters, like "all active currencies". For everything else, a good index, a projection, or an application cache is better.

How it works, step by step

  1. You run select c from Country c where c.active = true with setHint("org.hibernate.cacheable", true) and the query cache enabled.
  2. First time: SQL runs, returns ids [1, 5, 9]. Hibernate stores (query text + parameters) to [1, 5, 9] plus a timestamp.
  3. Next time with the same parameters: Hibernate finds the entry, checks that no table the query reads has been modified since the timestamp (via an "update timestamps" region), then loads entities 1, 5, 9 from L2 or L1.
  4. If any write touched the country table, all cached queries on that table are considered stale and are discarded.

Why it rarely pays

  • Coarse invalidation: one write to the table invalidates every cached query for that table, so on a busy table entries are evicted before being reused.
  • Ids only: if the entities are not in L2, each id turns into a separate select (an N+1 you introduced with a cache).
  • Memory: parameter combinations multiply entries.
  • Staleness and cluster consistency concerns same as L2.

When it does fit

A small, rarely changed table, a query with a handful of repeating parameter values, entities cached in L2, and no external writers. Examples: "all active currencies", "feature flags", "tax rates by country". Even then, a plain application cache of a DTO list is simpler to reason about and to invalidate. Measure hit ratio with Hibernate statistics before keeping it.

Remember: query cache = ids per query, wiped by any write to its tables. Use only on static data.

8. Queries: JPQL, Criteria and native SQL

What is JPQL, and how is it different from SQL and HQL? Basic

JPQL (Java Persistence Query Language) is an object-oriented query language: I query entities and their fields (select o from Order o where o.status = :s), not tables and columns, and Hibernate translates it to SQL for the database in use. HQL is Hibernate's own, richer language, and JPQL is effectively a subset of it.

The benefit is portability and refactoring safety: I use entity names, joins follow mapped associations (join o.customer c), and results come back as managed entities or projections. The limit is that it cannot use database-specific features, so I use native SQL for window functions, recursive queries or vendor hints. Hibernate 6 added many functions and made HQL stricter and closer to SQL (for example, better support for subqueries in from and set operations), so some sloppy queries from Hibernate 5 may need small fixes after an upgrade.

What it looks like next to SQL

GoalSQLJPQL
Orders of one customerselect * from orders o join customer c on o.customer_id = c.id where c.email = ?select o from Order o where o.customer.email = :e
Count by statusselect status, count(*) from orders group by statusselect o.status, count(o) from Order o group by o.status

Notice that JPQL uses class and field names (Order, o.customer.email), not table and column names, and navigates relationships with dots instead of writing the join condition. Hibernate reads the mapping, knows the foreign key, and writes the join for you.

Why it exists

It gives one query language that runs on every database (Hibernate generates the right dialect: limits, functions, joins). It also survives schema renames: if the column changes, you update the mapping, not every query. And query results can be managed entities, so dirty checking works on them.

Things interviewers like to hear

  • JPQL supports join, left join, join fetch, group by, having, subqueries, case, new constructor expressions, and bulk update/delete.
  • It validates at runtime when the query is created. @Query strings in Spring Data are checked at startup, and @NamedQuery too, which catches typos early.
  • HQL is Hibernate's superset: it adds extras (more functions, select-less shortcuts such as from Order, and in 6, set operations and common table expressions). Code using only JPQL stays portable between providers.
  • Entity names are case-sensitive (Order is the entity name, which defaults to the simple class name). Careful: order is also an SQL keyword, so many projects map the table as orders.

Use native SQL only when you need a feature JPQL lacks; use JPQL for the bulk of domain queries.

Remember: JPQL queries entities, not tables. Native SQL is the escape hatch.

How do you pass parameters safely, and what is the injection risk? Basic

I always use bind parameters, either named (:email) or positional (?1), and never concatenate user input into the query string. Bound values are sent separately from the SQL text, so they cannot change the query structure, which prevents SQL injection and also lets the database reuse the execution plan.

The same rule applies to JPQL, native queries and Spring Data @Query with @Param. Injection is still possible if I build a query string from a column name or sort field that comes from the request. For dynamic sorting I allow-list the field names, or use Spring Data's Sort with validated properties. A like filter needs the wildcard added to the parameter value ("%" + text + "%"), not to the query string, and I escape % and _ in the user's text if needed.

// unsafe: "select u from User u where u.email = '" + email + "'"
em.createQuery("select u from User u where u.email = :email", User.class)
  .setParameter("email", email)
  .getResultList();

Why bind parameters are safe

With a bind parameter, the SQL text and the value travel separately. The database parses ... where email = ? into a plan first, then plugs in the value as data. Whatever characters the value has, it can only ever be a value, never part of the command.

With concatenation the user controls the command. If the input is ' or '1'='1, the query becomes where email = '' or '1'='1' and returns every user. A worse payload can end the statement and run another one, or read other tables via union.

Named versus positional

// named (preferred: readable, order-independent)
q = em.createQuery("select u from User u where u.age > :min and u.city = :c", User.class);
q.setParameter("min", 18).setParameter("c", "Pune");

// positional (JPA style ?1, ?2)
"... where u.age > ?1 and u.city = ?2"

Avoid the plain JDBC-style ? without numbers in JPQL: in Hibernate 6 it is not supported in the same way.

Where injection still sneaks in

  • Dynamic order by: "order by " + request.getParam("sort"). Parameters cannot bind identifiers, so check the value against an allowed list of field names, or use Spring Data Sort built from validated properties.
  • Dynamic table/column names in native queries, same rule.
  • like: put the wildcard in the bound value. If you want a literal % from the user, escape it (escape '\').
  • in (:ids): bind a collection; do not join ids into a string.
  • Spring Data SpEL in @Query is for entity names and escaping helpers, not for user strings.

Plan cache benefit: a given statement text is parsed and planned once, which also helps performance. Concatenated queries create a new text per value, which floods the plan cache and the Hibernate query plan cache.

Remember: bind parameters always. Allow-list anything dynamic like column names.

What is the Criteria API, and when would you use it instead of JPQL? Intermediate

The Criteria API builds a query from Java objects instead of a string, so it is type-checked by the compiler and can be assembled dynamically. I use it when the query shape changes at runtime, such as a search form with many optional filters. For fixed queries I prefer JPQL because it is much easier to read.

In Spring Data this usually appears as Specification objects (see the Spring Data section), which wrap Criteria predicates into small reusable pieces that I combine with and / or. Plain Criteria is verbose, and many teams use Querydsl or jOOQ for a nicer type-safe API. The real danger of dynamic queries is not the API but performance: a flexible filter produces many different SQL shapes, so I make sure each common combination has an index.

The same query two ways

// JPQL
select o from Order o where o.status = :s and o.total > :min

// Criteria
CriteriaBuilder cb = em.getCriteriaBuilder();
CriteriaQuery<Order> cq = cb.createQuery(Order.class);
Root<Order> o = cq.from(Order.class);
List<Predicate> ps = new ArrayList<>();
if (status != null) ps.add(cb.equal(o.get("status"), status));
if (min != null)    ps.add(cb.greaterThan(o.get("total"), min));
cq.select(o).where(ps.toArray(new Predicate[0]));
List<Order> result = em.createQuery(cq).getResultList();

For a fixed query, JPQL is shorter and easier to read. The Criteria version shines when the list of conditions depends on runtime input: you add predicates only for filters the user filled in. With JPQL you would concatenate strings and track parameters by hand, which is error-prone.

Safety: stringly-typed attribute names

o.get("status") is still a string, so a typo fails at runtime. The JPA static metamodel (Order_.status, generated by an annotation processor) makes the field names compile-time checked and refactoring safe.

Options for dynamic queries

The performance risk is often missed: a very flexible search produces many query shapes, and each shape needs a suitable index. Review the most used combinations and keep the rest behind a required filter (for example always a date range), so no one can run an unindexed full table scan.

When do you use native queries, and what do they cost you? Intermediate

I use a native query when JPQL cannot express it or when I need database features: window functions, recursive CTEs, JSON operators, upserts (on conflict), or tuned hints. The cost is losing portability and some safety: the result mapping is manual, and Hibernate cannot always tell which tables the query touches.

That last point has practical effects. Pending changes may not be flushed before a native query (through the JPA EntityManager Hibernate typically flushes everything, but I call flush() myself to be safe), and a native update does not update the persistence context or the second-level cache. For results I can map to an entity (createNativeQuery(sql, Order.class)), to an interface projection in Spring Data, or to a DTO via a result mapping. With paging, a native @Query in Spring Data needs an explicit countQuery.

Typical reasons to go native

  • Window functions (row_number() over (partition by ...), running totals).
  • Recursive CTEs for trees (org charts, category paths).
  • Upsert: insert ... on conflict (code) do update ... (PostgreSQL) or merge (Oracle, SQL Server). Hibernate has no JPQL for it.
  • JSON, full-text, array operators and vendor hints.
  • A heavy report that you tuned with EXPLAIN and do not want the ORM to rewrite.

How to map the result

// entity (columns must match the mapping)
em.createNativeQuery("select * from orders where status = ?1", Order.class)

// Spring Data interface projection
@Query(value = "select o.id as id, sum(i.qty) as qty from orders o join item i on ... group by o.id",
       nativeQuery = true)
List<OrderQty> totals();   // interface OrderQty { Long getId(); Long getQty(); }

Use column aliases that match the getter names. In Hibernate 6 you can also use a Tuple or constructor-style @SqlResultSetMapping.

The hidden costs

  1. Flush. Hibernate cannot parse your SQL to know which tables it reads, so it may not flush pending changes first. With the JPA EntityManager it typically flushes before a native query, but behaviour varies by version and API (the native Hibernate Session can flush only if you declare query spaces). Calling flush() yourself removes doubt.
  2. Stale context. A native update or delete changes rows behind Hibernate's back. Managed entities keep their old values, and L2 cache entries are not evicted unless you tell Hibernate which tables changed. Clear or refresh afterwards.
  3. Portability is lost: a PostgreSQL-specific query fails on H2 in tests unless you test against the real database (for example with Testcontainers).
  4. Paging in Spring Data needs a separate countQuery; sort via Pageable is not applied to native queries automatically in all cases.

Rule: JPQL by default, native for features, and always bind parameters.

Remember: native for power features. Flush before it, and clear or refresh after a native write.

Offset or keyset pagination? What goes wrong with deep pages? Senior

Offset pagination (limit 20 offset 100000) is simple, but the database must read and discard all earlier rows, so deep pages get slower and slower, and concurrent inserts can shift rows so items appear twice or are skipped. Keyset pagination remembers the last seen key and asks for rows after it (where id < :last order by id desc limit 20), which uses the index and costs the same on page 1 and page 10,000.

The price of keyset is that I cannot jump to "page 57" directly, so it fits "load more" and infinite scroll, and exports. The sort must be on a unique, indexed key (add the id as a tie-breaker when sorting by a non-unique field like date). Spring Data offers Window / ScrollPosition support for keyset scrolling in recent versions (3.1 and later, typically). Also remember that Page runs an extra count(*), which can be slow on big tables; Slice avoids it.

select o from Order o
where (o.createdAt < :ts or (o.createdAt = :ts and o.id < :id))
order by o.createdAt desc, o.id desc

Why offset gets slower

For select * from orders order by id limit 20 offset 100000, the database cannot jump to row 100,001. Even with an index it must walk 100,020 entries and throw the first 100,000 away. Page 1 costs 20 rows of work, page 5,000 costs 100,020. A user or export job that crawls pages sees time per page grow linearly.

The correctness problem

Pages are defined by position, not identity. If a new row is inserted at the top while someone reads page 2, every row shifts down by one: the last row of page 1 appears again as the first row of page 2 (a duplicate). A delete causes the opposite: one row is skipped. For feeds and exports this produces visible bugs.

How keyset works, with numbers

  1. First page: order by created_at desc, id desc limit 20. The last row has created_at = T9, id = 812.
  2. The client sends back a cursor containing (T9, 812).
  3. Next page: where (created_at, id) < (T9, 812) order by created_at desc, id desc limit 20. With an index on (created_at, id) the database seeks straight to that position.

Every page costs about the same, and inserts or deletes elsewhere do not change what comes after the cursor.

Pitfalls: the sort columns must be unique together (add the id), nullable sort columns complicate the comparison, and the database must have a matching composite index in the same order and direction. Offset is fine for small admin screens (a few hundred pages at most); use keyset for feeds, APIs consumed by machines, and big exports.

9. Spring Data JPA

How do derived query methods work, and what are their limits? Basic

Spring Data parses the method name at startup and builds the query from it: findByStatusAndCreatedAtAfter(status, date) becomes a JPQL query with two conditions. It saves a lot of code for simple lookups, and an invalid property name fails at startup instead of at runtime.

The limits: long names become unreadable, joins and fetch joins are awkward, and complex conditions or aggregates are better as @Query. Keywords include And, Or, Between, In, Like, OrderBy, IsNull, Top5, exists and count. Derived methods work on entities, so a read-only list should still use a projection (List<OrderRow> findByStatus(...)) or an @EntityGraph to avoid N+1. As a rule, when a method name has more than about three conditions, I switch to @Query.

How parsing works

At application startup, Spring Data splits the method name into a subject and a predicate. findByStatusAndCreatedAtAfter means: subject "find", then conditions status = ?1 and createdAt > ?2. It checks that status and createdAt exist on the entity (so typos fail startup), builds a Criteria query once, and reuses it.

Useful keywords

KeywordMeaningExample

In, IsNull, TrueSets and flagsfindByStatusIn(List)

Nested properties use underscores or camel case: findByCustomerAddressCity navigates customer.address.city (use findByCustomer_AddressCity if names are ambiguous). That creates a join.

Where it stops being a good idea

  • Names beyond three conditions read like a sentence nobody can check at a glance.
  • It cannot express fetch joins by itself: pair with @EntityGraph.
  • No custom aggregates, no subqueries, no database functions.
  • Return type matters: returning an entity loads everything; use interface or record projections for read-only views.
  • deleteBy... loads the entities before deleting them (see the delete question).

Interview point: derived queries are checked at startup, so a failing method name stops the application from booting, which is good: you find the mistake in the first test run, not in production.

Remember: the method name is the query. Keep it short, otherwise use @Query.

How do @Query and @Modifying work, and what is clearAutomatically for? Intermediate

@Query lets me write the JPQL or native SQL myself. For an update or delete query I must add @Modifying, and the method needs a transaction. The statement runs directly in the database and does not touch the persistence context, so @Modifying(clearAutomatically = true) clears the context afterwards, and flushAutomatically = true flushes pending changes first.

@Modifying(flushAutomatically = true, clearAutomatically = true)
@Transactional
@Query("update Order o set o.status = 'EXPIRED' where o.createdAt < :limit")
int expireOld(@Param("limit") Instant limit);

Why clear: otherwise entities already loaded in the same transaction keep their old values, and a later find returns stale data (see the bulk update question). The downside of clearAutomatically is that it detaches all other entities I hold, which may break later lazy access, so I run bulk updates early or in their own transaction. The method returns the number of rows changed; check it when it matters.

The stale-entity problem it solves

A bulk update runs as SQL, so the persistence context does not know about it:

@Transactional
void demo() {
   Order o = repo.findById(5L).get();       // status = NEW, now in the context
   repo.expireOld(limit);                   // SQL: sets status = EXPIRED in the DB
   o.getStatus();                           // still NEW! the context was not told
   repo.findById(5L).get().getStatus();     // still NEW: served from the context
}

Worse, if you then change o and the transaction flushes, the dirty check writes your stale copy back over the bulk update.

What the two flags do

  • flushAutomatically = true: before running the update, flush pending changes so that the bulk statement sees them and so they are not lost when you clear.
  • clearAutomatically = true: after the update, clear the persistence context so later reads reload from the database.

Rules and costs

  • It needs a transaction, otherwise TransactionRequiredException.
  • Clearing detaches everything, including entities you plan to use afterwards, which can cause LazyInitializationException. Run bulk updates first in the method, or in a separate transactional service method.
  • Bulk statements skip @Version, entity listeners and auditing fields. Add o.version = o.version + 1 and o.lastModified = :now in the statement if they matter.
  • Returning int gives rows affected; return void if you do not care.
  • Bulk JPQL updates and deletes evict the matching L2 cache regions, but native modifying queries need an explicit eviction or a declared query space.

Use these for set-based changes ("expire all old orders") because one SQL statement beats loading and saving thousands of entities.

Remember: @Modifying for update and delete queries. Flush first, clear after, or you read stale entities.

What does repository.save() actually do? Intermediate

save checks whether the entity is "new". If it is new, it calls persist; otherwise it calls merge. "New" means the id is null, or, when there is a @Version field of a wrapper type, the version is null. So with a generated id it behaves as I expect, but with an id I assign myself (for example a UUID created in code), save thinks it is not new and calls merge, which first runs a SELECT and then the INSERT.

That is the extra SELECT before each INSERT that slows imports. Fixes: add a @Version field (null means new), or implement Persistable<ID> with an isNew() method (for example a transient flag set in a @PostLoad / @PostPersist callback). Also, inside a transaction I do not need save for changes to a managed entity: dirty checking writes them at flush. And save returns the managed instance, so I use the return value, as with merge.

Inside SimpleJpaRepository.save, step by step

  1. Call entityInformation.isNew(entity).
  2. If new: em.persist(entity) and return the same instance.
  3. Otherwise: em.merge(entity) and return the managed copy.

The isNew rule: if the entity has a version attribute of a wrapper type, it is new when the version is null. Otherwise, if the id is a wrapper type, it is new when the id is null. Primitive ids (long id) are considered new when 0. Or the entity can implement Persistable to define its own answer.

Why assigned ids hurt

@Entity class Product {
  @Id private String sku;       // assigned by you, never null
}
repo.save(new Product("A-1"));
// isNew() = false -> merge -> SELECT ... WHERE sku='A-1' (nothing found) -> INSERT

Every insert costs two statements. For an import of 100,000 rows that is 100,000 wasted selects. And if the row already exists, the same call silently updates it, which can hide duplicates.

Fixes

@Entity class Product implements Persistable<String> {
  @Id private String sku;
  @Transient private boolean isNew = true;
  @Override public String getId() { return sku; }
  @Override public boolean isNew() { return isNew; }
  @PostPersist @PostLoad void markNotNew() { this.isNew = false; }
}

Or add @Version Long version; (null on new objects). Both make save choose persist.

Other points

  • save is transactional by itself, so a single call commits at its own end if you have no outer transaction.
  • For bulk inserts use saveAll with batching enabled, plus flush/clear in chunks.
  • Calling save on an entity you just loaded in the same transaction is harmless (merge returns the same instance) but unnecessary.

Remember: save = persist if new, else merge. Assigned ids need @Version or Persistable to avoid the extra SELECT.

What are Specifications, and how do you build a dynamic search with them? Intermediate

A Specification<T> is a small reusable piece of a Criteria query (one predicate). I make the repository extend JpaSpecificationExecutor, write one specification per filter, and combine only the filters the user actually sent with Specification.where(...).and(...). This gives a dynamic search without string building.

static Specification<Order> hasStatus(Status s) {
  return (root, q, cb) -> s == null ? null : cb.equal(root.get("status"), s);
}
static Specification<Order> placedAfter(Instant t) {
  return (root, q, cb) -> t == null ? null : cb.greaterThan(root.get("createdAt"), t);
}
repo.findAll(where(hasStatus(s)).and(placedAfter(t)), pageable);

A null predicate is ignored, which makes optional filters simple. Watch the performance side: each combination needs a supporting index, a collection join inside a specification brings back the paging problem, and for list screens I still want a projection instead of full entities (specifications return entities). Paging with a specification also runs a count query.

How the pieces fit

A Specification is a function that receives the Root (the entity being queried), the CriteriaQuery, and the CriteriaBuilder, and returns a Predicate. Spring Data runs JpaSpecificationExecutor.findAll(spec, pageable) by building one Criteria query from the combined predicate. Because each spec is a plain static method, you can unit test them and reuse them across screens.

A request example

Search request: status=PAID, nothing else. hasStatus(PAID) returns a predicate, placedAfter(null) returns null and is skipped, so the SQL is where status = ?. If both are sent, the SQL has both conditions joined by AND. You never write if/else chains of query strings.

Joins inside specifications

static Specification<Order> customerCity(String city) {
  return (root, q, cb) -> city == null ? null
        : cb.equal(root.join("customer").get("city"), city);   // ToOne join: fine
}

If the join is to a collection, the result can contain duplicate parents; call q.distinct(true) and be careful with paging and count queries.

Specification versus other tools

NeedPick
A handful of filters on one entity, with pagingSpecification
Fixed, hand-tuned query@Query
Complex joins, projections, readable fluent APIQuerydsl or jOOQ
Cross-entity reportingNative SQL or a read model

Pitfalls

  • Specifications return entities by default; for list screens, it is cheaper to use a projection with a dedicated query.
  • Free-text like '%x%' cannot use a normal b-tree index; full-text search or a search engine is the right tool for big tables.
  • Sorting and filtering are open-ended, so a query planner may pick poor plans; protect with required filters or limits.

Remember: one Specification per filter, combine with and/or, null means "skip". Index the common combinations.

How do you set up auditing (created and modified timestamps and users)? Intermediate

I enable it with @EnableJpaAuditing, add @EntityListeners(AuditingEntityListener.class) to a @MappedSuperclass, and annotate fields with @CreatedDate, @LastModifiedDate, @CreatedBy and @LastModifiedBy. For the user fields I provide an AuditorAware bean that returns the current user, usually from the security context.

The listener runs on persist and update callbacks, so the fields are filled at flush time. Limits: it only sees changes made through the persistence context, so a bulk JPQL update or native SQL does not update lastModified, and it records who and when, not what changed. For a full change history (old and new values) use Hibernate Envers or database-level audit tables.

What you set up, in order

@Configuration @EnableJpaAuditing
class AuditConfig {
  @Bean AuditorAware<String> auditor() {
    return () -> Optional.ofNullable(SecurityContextHolder.getContext().getAuthentication())
                         .map(Authentication::getName);
  }
}

@MappedSuperclass
@EntityListeners(AuditingEntityListener.class)
abstract class Auditable {
  @CreatedDate     private Instant createdAt;
  @LastModifiedDate private Instant updatedAt;
  @CreatedBy       private String createdBy;
  @LastModifiedBy  private String updatedBy;
}

Entities extend Auditable and get the four columns. On persist, the listener sets created and modified fields; on update (when the entity is dirty), it refreshes the modified ones.

Gaps you should know

  • Bulk updates, native SQL and database-side changes bypass the listener. Add the timestamp in the query yourself, or use a database trigger if you must guarantee it.
  • No history. You only get "last changed by whom and when". To see old and new values, use Hibernate Envers (@Audited, creates _AUD tables with a revision per change) or database change data capture.
  • Background jobs have no security context; the AuditorAware should return a fixed system user in that case, not empty or an exception.
  • Time zones: use Instant (UTC) rather than local date-times.
  • A @PrePersist/@PreUpdate callback is a lightweight alternative without Spring Data.

Mention that compliance auditing (who read or changed what, tamper-proof) is a different, larger requirement than these four columns.

Remember: enable auditing, add the listener, give an AuditorAware. Bulk updates bypass it.

Why is deleteBy or deleteAll slow, and what is a better way? Intermediate

Derived deletes such as deleteByStatus and deleteAll(entities) first load every matching entity, then delete them one by one so that cascades and callbacks run. For 100,000 rows that is 100,000 loaded objects and 100,000 DELETE statements. For a bulk removal I use @Modifying @Query("delete from X where ..."), or deleteAllInBatch, which issue a single statement.

The trade-off is that a bulk delete skips cascades, orphanRemoval, entity listeners and the persistence context, so child rows must be handled by database cascade or by deleting them first, and the context should be cleared. For very large deletes I delete in chunks (limit by ids) to avoid long locks and a giant transaction.

What happens, for 100,000 matching rows

  1. select * from orders where status = 'OLD' returns 100,000 rows. All become managed entities in the persistence context (memory).
  2. For each entity Hibernate runs cascade logic, loads any lazy collections it must cascade to, and fires listeners.
  3. At flush it sends 100,000 delete from orders where id = ? statements (batched if configured, but still 100,000 row deletes plus the dirty-check cost of a big context).

Memory, time and lock duration all grow with the row count. The reason Spring Data does this is that deleteBy must honour the entity lifecycle: cascade REMOVE, orphanRemoval, @PreRemove listeners and @Version checks.

The alternatives

MethodStatementsHonours cascade and listeners?
deleteByStatus, deleteAll(entities)1 select + N deletesYes
deleteAllInBatch(entities) / deleteAllInBatch()1 delete (with or / in, or all rows)No
@Modifying @Query("delete from Order o where o.status = :s")1 deleteNo
Chunked delete by id ranges1 per chunkNo

Doing a bulk delete correctly

  • Children first. If order items have a foreign key to orders and no ON DELETE CASCADE, a bulk delete of orders fails with a constraint error. Delete the children with a query first, or define database cascades (@OnDelete in Hibernate).
  • Clear the context afterwards, or stale entities remain.
  • Chunk it. Deleting millions of rows in one transaction creates a long lock, a huge undo/redo log and replication lag. Delete 5,000 to 50,000 rows at a time, committing between batches, and index the filter column.
  • Consider soft delete (a deleted flag, Hibernate @SQLDelete and @SQLRestriction / @Where) or partition drops for archival data.

Remember: deleteBy loads and deletes row by row. Use a bulk delete query for volume, and handle children yourself.

How do you implement soft delete with Hibernate, and what are the pitfalls? Intermediate

Soft delete means marking a row as deleted (a deleted_at timestamp or a flag) instead of removing it. In Hibernate I override the delete SQL with @SQLDelete so remove runs an UPDATE, and filter deleted rows from every read with @SQLRestriction (Hibernate 6.3 and later; @Where in older versions). It keeps history and allows undo, at the cost of subtle query and constraint problems.

How it looks

@Entity
@SQLDelete(sql = "update customer set deleted_at = now() where id = ? and version = ?")
@SQLRestriction("deleted_at is null")
class Customer {
   @Id Long id;
   @Version Long version;
   Instant deletedAt;
}

Now repo.delete(c) issues the UPDATE, and findAll, find and lazy associations add where deleted_at is null automatically. (The parameters of a custom @SQLDelete follow the entity's column order, so check the generated SQL; with a version column the statement usually needs both id and version.)

Why people choose it

  • Recoverability: "restore" is clearing the timestamp.
  • Foreign keys from history tables (orders referencing a deleted product) stay valid.
  • Auditing and legal retention requirements.

Pitfalls

  • Unique constraints. A deleted customer with email a@x.com still occupies the unique index, so a new customer cannot use it. Use a partial unique index (where deleted_at is null, PostgreSQL) or include the delete marker in the key.
  • Native queries and bulk statements bypass the restriction. Every hand-written query must remember the condition.
  • Data growth and performance. Indexes grow with dead rows; add deleted_at to indexes where needed, and archive old rows.
  • Privacy rules (right to erasure) may require real deletion or anonymisation; soft delete alone is not compliant.
  • Cascades. Parent soft deleted, children not: decide the rule and implement it explicitly.
  • find by id of a deleted row returns null, but a lazily referenced deleted row can raise EntityNotFoundException on first access.

Alternative: move deleted rows to an archive table with a trigger or an event, keeping the live table clean and small.

Remember: soft delete = @SQLDelete plus a read filter. Watch unique indexes, native queries and privacy rules.

Page, Slice and List: what is the difference in the SQL they run? Intermediate

Page runs the data query plus a count(*) query to know the total pages. Slice runs only the data query, but asks for one extra row to learn whether a next page exists, so it has no total. List with a Pageable just applies the limit and returns nothing about totals. I use Slice for infinite scroll and when the count is expensive.

The count query can be the slowest part on a large filtered table, so options are: Slice, a cached or approximate total, or a custom countQuery that skips the joins. Always include a stable ORDER BY with a unique tie-breaker, or pages can overlap. Also remember that Pageable sort properties come from the client and should be validated.

The SQL each one produces

For PageRequest.of(2, 20) (third page, size 20) on Order filtered by status:

Return typeSQL runYou get
Page<Order>select ... limit 20 offset 40 and select count(*) ...Content, total elements, total pages
Slice<Order>select ... limit 21 offset 40 (one extra row)Content and hasNext()
List<Order> with Pageableselect ... limit 20 offset 40Just the rows

The extra row in a Slice is the trick: if 21 rows come back, a next page exists, and the 21st is dropped before returning. No count query is needed.

Why count can hurt

On a table with 50 million rows and a filter that matches 5 million, count(*) may scan a big index range and take longer than the page query itself. Users rarely need the exact total on a feed or search results. Options: Slice; skip the count after page one; use an approximate total (database statistics) or a capped count (count over a limited subquery, showing "10,000+"); or provide a hand-written countQuery that drops joins and sorts the original query needs.

Correct and stable paging

  • Always add a deterministic ORDER BY with a unique tie-breaker (createdAt desc, id desc). Without it, rows with equal sort values can swap places between pages.
  • Do not trust sort fields from the client; map them to an allowed list.
  • Collection join fetch plus a Pageable triggers in-memory paging (see the fetch pagination question).
  • For deep pages, move to keyset scrolling (Window / ScrollPosition in Spring Data 3.1 and later).

When asked in an interview, state the trade: Page costs an extra query for convenience, Slice is cheaper but less informative.

Remember: Page = data + count, Slice = data + 1 peek row, List = just the limit.

10. Performance, bulk work and large data

What is the problem with bulk updates in JPA? Intermediate

A bulk JPQL or native update (update Order set status = 'EXPIRED' where ...) goes straight to the database and bypasses the persistence context. Entities already loaded keep their old values, so a later find in the same transaction returns stale data. Bulk updates also skip @Version increments, entity listeners and auditing, unless I set those columns myself.

The rules I follow: flush before the bulk update, clear (or refresh) after it, and keep it in its own short transaction when possible. I also bump the version in the statement (set version = version + 1) if other code relies on optimistic locking. The benefit is huge: one statement instead of loading and updating thousands of entities, so for mass changes it is the right tool, as long as I respect its side effects.

Why bulk updates exist

The entity way to expire 50,000 old orders is: load all 50,000 into the context, call setStatus on each, and let dirty checking issue 50,000 UPDATE statements. That is slow, memory hungry and holds locks for a long time. One statement does the same job: update orders set status='EXPIRED' where created_at < :limit. The price is that the persistence context is bypassed completely.

What can go wrong, with a timeline

  1. Inside a transaction you load Order 7 (status NEW). It sits in the context with a snapshot.
  2. You run the bulk update. The database row becomes EXPIRED. The context does not know.
  3. You call find(Order.class, 7): Hibernate answers from the context, returning NEW.
  4. Worse: you also changed some other field on Order 7 earlier. At flush the dirty check issues update orders set status='NEW', other=... where id=7, overwriting the bulk change.

The safe recipe

em.flush();                                   // 1. push pending entity changes first
int n = em.createQuery(
   "update Order o set o.status = 'EXPIRED', o.version = o.version + 1 " +
   "where o.createdAt < :limit").setParameter("limit", t).executeUpdate();   // 2. bulk
em.clear();                                   // 3. forget stale entities

What the bulk statement skips

  • Dirty checking and the context (hence the clear).
  • @Version unless you increment it; otherwise an optimistic-lock user may overwrite your change without error.
  • Entity listeners and auditing (@PreUpdate, @LastModifiedDate): set those columns in the statement.
  • Cascades and orphan removal.
  • L2 cache: JPQL bulk statements evict the affected entity regions in Hibernate, but native ones need explicit handling.

When to choose which

Choose bulk for set-based changes that apply the same rule to many rows. Choose entity updates when each row needs business logic, validation or events. For millions of rows, bulk updates also need chunking (by id range) so they do not lock the table for minutes.

Remember: bulk SQL skips the context. Flush before, clear after, and set the version yourself.

How do you make Hibernate insert 100,000 rows quickly? Senior

I turn on JDBC batching with hibernate.jdbc.batch_size=50 and order_inserts=true, use a sequence id (not IDENTITY), and in the loop I flush() and clear() every 50 rows so the persistence context stays small. Without this, each insert is its own round trip, and 100,000 entities pile up in memory.

spring.jpa.properties.hibernate.jdbc.batch_size=50
spring.jpa.properties.hibernate.order_inserts=true
# PostgreSQL JDBC url: ...?reWriteBatchedInserts=true  (MySQL: rewriteBatchedStatements=true)

for (int i = 0; i < rows.size(); i++) {
    em.persist(rows.get(i));
    if (i % 50 == 49) { em.flush(); em.clear(); }
}

Checks I make: IDENTITY ids disable batching, so switch to SEQUENCE with a matching allocation size; assigned ids make save run a SELECT first (use persist or Persistable); the driver option rewrites batches into multi-row inserts and gives a further large speed-up; and I split a huge import into several transactions of a few thousand rows, so a failure does not roll back everything. For truly big loads, a database bulk loader or JdbcTemplate.batchUpdate is faster than any ORM.

Why inserts are slow by default

By default, each persist turns into one INSERT JDBC call, which is one network round trip. 100,000 rows at 1 ms each is 100 seconds of pure waiting, and all those entities stay in memory in the context. JDBC supports batching: add many statements to a batch and send them in one round trip. Hibernate only uses it if you enable it.

The four ingredients

  1. hibernate.jdbc.batch_size=50 tells Hibernate how many statements to group. 30 to 100 is a typical range; test on your database.
  2. Sequence ids. With IDENTITY, Hibernate must run each INSERT immediately to get the id, so it cannot defer and group them. With a sequence, ids are assigned in memory and INSERTs can wait for flush.
  3. order_inserts=true (and order_updates=true). Batches only group consecutive statements for the same table. If you insert parent, child, parent, child, batches break up every time. Sorting makes all parents then all children.
  4. Flush and clear every batch. This sends the batch and drops the entities so memory stays flat and dirty checking stays cheap.

Driver-level boost

Some JDBC drivers send the batch as separate statements unless asked to rewrite them: PostgreSQL reWriteBatchedInserts=true, MySQL rewriteBatchedStatements=true. This merges them into multi-row inserts and can speed up loads many times. Verify with the driver and database logs, since behaviour depends on version.

Verification and failure handling

  • Check that batching works: enable Hibernate statistics and look at the "JDBC batches executed" count, or use a datasource proxy that logs batch sizes. Many people think they have batching and do not.
  • Split the import into transactions of a few thousand rows so one bad row does not roll back an hour of work, and record progress to resume.
  • With saveAll on assigned ids you still pay a SELECT per row (see the save question).
  • For the very largest loads, skip the ORM: JdbcTemplate.batchUpdate, PostgreSQL COPY, MySQL LOAD DATA, or the database's bulk loader.

Remember: batch size + sequence ids + flush and clear every batch. IDENTITY silently kills batching.

You must process 1 million rows. How do you avoid running out of memory? Senior

I never load them all with findAll(). I read in chunks, using keyset paging (where id > :last order by id limit 1000), or stream with a database cursor, and I clear the persistence context after each chunk so the managed entities can be garbage collected. If I only read, I use projections or a read-only query so no snapshots are kept.

Streaming with a Spring Data Stream<T> return type needs an open transaction, must be closed (try-with-resources), and the driver must really use a cursor: PostgreSQL needs autocommit off and a fetch size, MySQL needs Integer.MIN_VALUE or useCursorFetch. Without the fetch size, the driver loads the whole result set first and I get the same memory error. Chunked keyset reads are simpler and more predictable; they also allow commit per chunk and resuming after a crash. Hibernate's StatelessSession (no context, no dirty checking, no cache) is another option for pure processing.

Why it runs out of memory

findAll() creates an object for every row, plus a snapshot for dirty checking and an entry in the persistence context. One million entities with 20 fields can be many gigabytes, and the JDBC driver may also buffer the full result set. Processing is limited by memory, not by the database.

Option 1: chunked keyset reads (my default)

Long last = 0L;
while (true) {
    List<Row> page = repo.findNext(last, PageRequest.of(0, 1000)); // where id > :last order by id
    if (page.isEmpty()) break;
    process(page);
    last = page.get(page.size() - 1).getId();
    em.clear();                      // let the chunk be garbage collected
}

Each chunk is a short query using the index, and memory stays about 1,000 entities. You can commit per chunk and resume after a crash by remembering last. Use a projection when you only read, so no entities are created at all.

Option 2: streaming with a cursor

Return Stream<T> from a repository method (inside a transaction, closing it with try-with-resources) or use ScrollableResults in Hibernate. This works only if the driver streams. PostgreSQL requires autocommit off and a fetch size (for example 1000); MySQL needs useCursorFetch=true with a fetch size, or the special row-by-row mode. Without that, the driver silently loads everything and you get the same OOM.

Option 3: StatelessSession

Hibernate's StatelessSession has no persistence context, no dirty checking, no cascades and no L1/L2 cache. It suits pure read/transform or insert pipelines. You lose lazy loading and cascade convenience.

Trade-offs

ApproachStrengthWeakness
Keyset chunksSimple, resumable, driver-independentNeeds an indexed unique key
Cursor streamOne query, no key logicHolds a connection and transaction for the whole run; driver-specific
StatelessSessionLowest overheadNo ORM features

Also run such jobs against a replica or in off-peak hours, because long scans compete with user traffic.

Remember: chunk by key or stream with a real fetch size, and clear the context. Never findAll() a big table.

How do you see the SQL Hibernate runs, including parameter values? Basic

Set the logger org.hibernate.SQL=DEBUG for the statements, and for the bound values use org.hibernate.orm.jdbc.bind=TRACE on Hibernate 6 (org.hibernate.type.descriptor.sql.BasicBinder=TRACE on Hibernate 5). Do not use spring.jpa.show-sql in real code, since it prints to standard output and without values.

These loggers are for development only, because they are noisy and slow. For a view that shows the final SQL with values, and counts per request, a datasource proxy (datasource-proxy, p6spy) is more practical, and it is also what I use to assert statement counts in tests. In production I rely on slow-query logs from the database and tracing from an APM tool.

Which settings to use, and why

# Hibernate 6
logging.level.org.hibernate.SQL=DEBUG
logging.level.org.hibernate.orm.jdbc.bind=TRACE
# Hibernate 5
logging.level.org.hibernate.type.descriptor.sql.BasicBinder=TRACE

The first logs each prepared statement text with ? placeholders. The bind logger adds lines like "binding parameter (1:BIGINT) <- [42]", so you can reconstruct the query. spring.jpa.show-sql=true prints through System.out (no log levels, no formatting control, no values), so I avoid it. hibernate.format_sql makes multi-line statements readable.

Why a datasource proxy is better

A proxy such as datasource-proxy or p6spy wraps the DataSource and sees the real JDBC calls, including batches and final parameter values. It can also count statements per test or request, which lets you assert "this endpoint runs at most 3 SELECTs", the best protection against N+1 regressions. Hibernate's own statistics (hibernate.generate_statistics=true) give counts of queries, entity loads, cache hits and slow queries, at a small cost.

What not to do

  • Do not leave bind logging on in production: it is slow and writes personal data (emails, tokens, card fragments) into logs. That can be a compliance incident.
  • Do not judge performance by log timestamps; use query timings from the database or tracing.
  • In production, rely on the database's slow-query log, pg_stat_statements or equivalent, plus APM traces.

A useful habit: after writing a new endpoint, look at its SQL once. It takes a minute and catches most mapping surprises.

Remember: org.hibernate.SQL for text, bind logger for values. Dev only. Count statements with a datasource proxy.

How does the connection pool relate to JPA performance? Intermediate

Every transaction takes one connection from the pool (HikariCP in Spring Boot, default size 10) and holds it until the transaction ends, or with OSIV until the request ends. So throughput depends on how short the transactions are, not on how many threads I have. When the pool is empty, requests wait and then fail with "Connection is not available, request timed out after 30000ms".

Making the pool bigger is usually the wrong fix: the database can only do so much parallel work, and a larger pool adds contention. The right fixes are shorter transactions (no remote calls or slow work inside), OSIV off, fewer queries per request, and watching for REQUIRES_NEW, which needs a second connection while holding the first. A rough starting size is small (about 10 to 20 per instance); multiply by the number of instances and check it against the database's connection limit. Hikari can warn about leaks with leakDetectionThreshold.

The model in one paragraph

Opening a database connection is expensive (network handshake, authentication), so applications keep a pool of ready connections. A transaction borrows one and returns it at the end. The number of requests the app can run in parallel against the database is therefore at most the pool size. If each request holds a connection for 100 ms, a pool of 10 supports about 100 requests per second (10 connections times 10 per second each). If the hold time becomes 1 s (a slow remote call inside the transaction), the same pool supports only 10 requests per second.

When the pool runs dry

  1. All connections are in use.
  2. New requests wait for up to connectionTimeout (30 s by default).
  3. They then fail with an error like "HikariPool-1 - Connection is not available, request timed out after 30000ms".
  4. Meanwhile the waiting threads pile up, and the whole service looks hung, though the database may be nearly idle.

Why bigger is not better

A database has a limited number of cores and disks. Beyond a certain point, more concurrent queries only add context switching and lock contention. Rule of thumb from the HikariCP project: a small pool (a few times the number of database cores) often beats a large one. Also remember the total: 20 application pods times a pool of 20 is 400 connections, which may exceed the database limit (for example max_connections in PostgreSQL), so one deployment scale-up can take the database down.

Common causes of long holds

  • Remote calls or heavy computation inside a transaction.
  • OSIV keeping the connection through the controller and JSON rendering.
  • REQUIRES_NEW nested in a request: 2 connections per request. With 10 concurrent requests all holding one and waiting for a second, the pool is deadlocked until timeouts.
  • Connection leaks (a manually obtained connection never closed). leakDetectionThreshold logs a stack trace for connections held too long.
  • Long-running reports on the same pool as the online traffic; use a separate pool or replica.

Monitor active, idle and pending counts (Hikari exposes them as Micrometer metrics) and alert on pending threads above zero for a sustained period.

Remember: a transaction equals a held connection. Fix pool exhaustion with shorter transactions, not a bigger pool.

11. Schema management and testing

What does ddl-auto do, and what should you use in production? Basic

spring.jpa.hibernate.ddl-auto lets Hibernate create or change the schema from the entities. Values: none, validate, update, create, create-drop. In production I use none or validate, and manage the schema with versioned migrations in Flyway or Liquibase. update is not safe for production.

Why not update: it only adds missing tables and columns. It never drops or renames, cannot do data migrations, behaves differently per database, and runs at startup on every node, so with several nodes starting together it races. Migrations are versioned SQL files, reviewed in pull requests and run once, in order, with a history table that records what ran (Flyway: file names like V12__add_status.sql; Liquibase: changelogs). With validate, the application refuses to start if the entities and the schema do not match, which catches a forgotten migration. For schema changes with no downtime, I use expand and contract: add the new column first (old code ignores it), deploy code that uses both, backfill, then remove the old column in a later release.

The options, one by one

ValueWhat happens at startupWhere it is acceptable
noneNothingProduction
validateCompare entities with the schema; fail if something is missingProduction, staging, CI
updateAdd missing tables, columns; never drops or altersQuick local experiments only
createDrop and recreate the schemaLocal development, tests
create-dropCreate at start, drop at shutdownIn-memory test databases

Spring Boot's default depends on the database: for an embedded database (H2, HSQL, Derby) with no schema manager it defaults to create-drop; otherwise none. That is why a project that "works on H2" can create tables magically in tests.

Why migrations are better

  • Repeatable and reviewable: each change is a file (V12__add_status.sql) in version control, reviewed like code.
  • Recorded: a history table shows what ran on each environment, so staging and production cannot silently differ.
  • Can do everything: rename columns, backfill data, add indexes, change types, which update cannot.
  • Safe with many nodes: Flyway and Liquibase take a lock, so only one instance applies a migration.

Zero-downtime changes (expand and contract)

  1. Expand: add the new nullable column or table. Old code ignores it.
  2. Deploy code that writes both old and new, and backfill old rows in batches.
  3. Deploy code that reads only the new one.
  4. Contract: drop the old column in a later release.

This is needed because during a rolling deployment old and new versions of the app run at the same time against one schema.

Tip: use Hibernate's schema export (jakarta.persistence.schema-generation.scripts.action) only to draft a migration, then review and edit the SQL by hand. And always test migrations on a copy of production-size data: adding an index or a column with a default can lock a large table.

Remember: production = migrations (Flyway or Liquibase) plus validate. Never update or create.

How do you test the persistence layer? Intermediate

I use @DataJpaTest with a real database in Testcontainers (the same engine as production), not H2, whenever behaviour matters: native queries, locking, JSON columns, constraints and collations all differ between databases. I test repositories and queries with real data and assert the statement count to catch N+1.

Traps: @DataJpaTest wraps each test in a transaction that rolls back, and the persistence context hides what the database really does. So in a test I call flush() and clear() before asserting, to prove that the SQL runs and that data is read back from the database, not from the context. To use a real database, I add @AutoConfigureTestDatabase(replace = NONE). Rolled-back tests cannot check commit-time behaviour (a constraint checked at commit, an AFTER_COMMIT listener, optimistic lock conflicts between two transactions); for those I use a test without the wrapping transaction.

Why H2 is risky for persistence tests

An in-memory database makes tests fast to set up, but it is a different engine. Differences that bite: SQL dialect, JSON and array types, locking behaviour (SKIP LOCKED, FOR UPDATE), constraint timing, text collation and case sensitivity, sequence semantics, and native query functions. Tests pass on H2 and fail in production, or worse, the other way round. Testcontainers starts a real PostgreSQL or MySQL in Docker for the test run, so the SQL, the migrations (run Flyway in the test too) and the locks are the real ones.

The persistence-context trap in tests

@DataJpaTest
@AutoConfigureTestDatabase(replace = NONE)
class OrderRepoTest {
  @Autowired OrderRepository repo; @Autowired EntityManager em;

  @Test void findsByStatus() {
     repo.save(new Order(PAID));
     em.flush();     // really run the INSERT now (catches constraint errors)
     em.clear();     // forget the object so the next read hits the database
     assertThat(repo.findByStatus(PAID)).hasSize(1);
  }
}

Without flush and clear, the test only proves that Hibernate can return the object it already holds. Mapping errors (wrong column name, missing converter) and query errors would go unnoticed.

What the default test transaction hides

  • Each test is wrapped in a transaction that rolls back, so nothing ever commits. Commit-time behaviour (deferred constraints, @TransactionalEventListener(AFTER_COMMIT)) is never triggered.
  • Two-transaction scenarios such as optimistic lock conflicts and deadlocks need @Transactional(propagation = NOT_SUPPORTED) or TransactionTemplate, with explicit cleanup afterwards.
  • Lazy loading works inside the test's transaction even where it would fail in the app, so also test the service layer end to end (a @SpringBootTest slice) with the real boundaries.

What I assert

Query results, constraint behaviour (insert a duplicate and expect the exception), cascade and orphan removal, version conflicts, and statement counts for main use cases. Keep container startup fast by sharing one container across test classes.

Remember: test against the real engine, flush and clear before asserting, and assert query counts.

The orders page was fast in test and now takes 12 seconds in production. APM shows 800 SQL calls. What happened? Senior

It is almost certainly N+1: one query for the page of orders, then hundreds of tiny SELECTs because lazy (or eager ToOne) associations are touched in a loop or by the JSON mapper. I confirm it from the statements, then give the list its own query with a projection or fetch join, and add a test that counts statements.

Situation: test data had five rows, production has 200 per page, so one extra query per row became hundreds.

Check first: open one slow trace. Many identical statements that differ only by the id value is the signature, and the table name tells me which association is touched. Count statements per request in staging.

Fix:

  1. Give the screen a read use case: a DTO projection, or join fetch or an entity graph for the ToOne parts.
  2. For collections, never join them into a paged query. Use @BatchSize or default_batch_fetch_size=50, or a second query by parent ids.
  3. Make all associations LAZY (ToOne defaults to EAGER).

Prevent: a statement-count assertion in tests of the main endpoints, a global batch fetch size as a safety net, open-in-view=false, and test data of realistic size. Adding a cache is not a fix: it hides the first request and adds invalidation problems.

How I would run the investigation, minute by minute

  1. Minute 1: confirm the shape. Open one slow trace in APM. If 800 calls are the same SELECT with different ids, it is N+1. If they are different statements, look for a loop calling a service per item.
  2. Minute 5: find the owner. The table in the repeated SELECT tells you which association (for example customer) is touched. Search the endpoint code and DTO mappers for getCustomer() inside a loop or a stream.
  3. Minute 15: reproduce with data. Seed 200 rows locally with statement logging. Write a failing test that asserts a maximum statement count.
  4. Fix and compare. After the change the test shows 2 or 3 statements, and staging shows the endpoint back to tens of milliseconds.

A concrete before and after

// before: 1 + 200 + 200 statements (customer, then shipping address)

return page.map(o -> new Row(o.getId(), o.getCustomer().getName(), o.getShipTo().getCity()));

// after: 1 statement (+1 count)

Why it was invisible before

With 5 rows the page needed 11 queries, about 15 ms. With 200 rows it needs 401 queries; at 30 ms each under production latency (network, shared database) that is 12 seconds. The query count grew with data, not the cost per query. A senior answer names this scaling behaviour and the guard (a statement-count test with realistic data).

Remember: many identical SELECTs = N+1. Fix the query shape, then lock it in with a statement-count test.

Two support agents edit the same customer, and one agent's change disappears. How do you find and fix it? Senior

This is a lost update: both agents loaded the same row, both saved, and the second save silently overwrote the first. I add a @Version column so the second save fails, return HTTP 409, and make the screen show the conflict. I also send the version to the client and back.

Situation: last write wins, with no error anywhere.

Check first: look for a @Version field. Check whether the update API re-reads the entity by id and copies all fields from the request (this overwrites even fields the agent never touched), and whether the request carries the version the agent saw.

Fix: add @Version (a numeric column with a migration, default 0). Include version in the response and require it in the update request, then copy it onto the loaded entity (or compare) so Hibernate's check uses the agent's version, not the fresh one. Map ObjectOptimisticLockingFailureException to 409 with a message. Where partial updates are the real need, use a PATCH that changes only the sent fields.

Prevent: a version column on every mutable table, and a concurrency test with two threads or two transactions.

Reproducing it and reading the evidence

  1. Open the same customer in two browser tabs (two agents). Edit the phone in tab A and the email in tab B.
  2. Save A, then save B. Check the row: B's save has restored the old phone because the request body contained every field.
  3. The log shows an UPDATE listing all columns, with no version in the WHERE clause. That confirms no optimistic check exists.

Two layers of fix

Database layer: add version bigint not null default 0 via a migration and @Version Long version in the entity. From now on every JPA update carries where version = ?.

API layer (this is where many teams stop too early): the check only works if the version the agent saw is the one compared. Return version (or an ETag) in the GET response, require it on the PUT (If-Match header or a body field), and set it on the entity before saving:

Customer c = repo.findById(id).orElseThrow();
if (!c.getVersion().equals(req.version())) throw new ConflictException();   // clear and cheap
c.setPhone(req.phone());           // dirty checking: UPDATE ... where version = ?

Map both this exception and ObjectOptimisticLockingFailureException to 409 (or 412 with If-Match) with a body that explains "this customer was changed by someone else; reload and retry".

Alternative: reduce the overwrite surface

Even with versions, a form that posts all fields makes conflicts likely. A PATCH that sends only changed fields, or per-section updates, reduces them. Also consider field-level merge only when the business agrees (phone and email are independent). Test with two threads using a barrier to force the interleaving.

Remember: silent overwrite means no version check. Add @Version, pass it through the API, answer 409.

Production logs show "Deadlock found when trying to get lock" a few times per hour during order processing. What do you do? Senior

A deadlock means two transactions each hold a row the other needs, in opposite order. The database kills one of them. I find the two statements in the database's deadlock report, make all code lock rows in the same order, shorten the transactions, and add a retry for the victim.

Situation: for example transaction A updates order 1 then order 2, while B updates order 2 then order 1.

Check first: read the deadlock detail from the database (SHOW ENGINE INNODB STATUS in MySQL, the server log in PostgreSQL). It lists the statements and the locked rows. Then map them to code paths. Remember that Hibernate orders statements itself at flush (inserts, updates, deletes), so the actual order differs from the order in my code.

Fix:

  • Process rows in a stable order (sort ids before updating or locking), and set hibernate.order_updates=true.
  • Keep transactions short, and move remote calls out.
  • Replace read-then-write with one atomic update ... where, or lock with FOR UPDATE in id order.
  • Retry the failed transaction a couple of times (deadlock victims are safe to retry).

Prevent: a documented lock order, missing foreign-key indexes added (they widen locks), and load tests with concurrent writers.

Reading a deadlock report

The report shows two transactions, each waiting for a lock held by the other. For MySQL SHOW ENGINE INNODB STATUS prints "LATEST DETECTED DEADLOCK" with the statements and the index locks. A typical case:

  1. Tx A: update stock where sku='X' (holds X) then update stock where sku='Y' (waits for Y).
  2. Tx B: update stock where sku='Y' (holds Y) then update stock where sku='X' (waits for X).
  3. Neither can continue; the database aborts one (the victim) with the error you see.

In order processing, this comes from two orders containing the same products in different line order. The fix is to sort lines by sku before touching rows, so every transaction takes locks in the same order.

Hibernate-specific reasons

  • Flush order differs from code order. Setting order_updates and order_inserts makes updates sorted by entity and id.
  • A missing index on a foreign key or filter column makes the database lock more rows (or scan a range), widening the conflict window.
  • Gap locks in MySQL under REPEATABLE_READ can cause deadlocks between inserts, which sometimes go away at READ_COMMITTED.

Fix hierarchy

  1. Remove the need to lock multiple rows: single atomic update ... set qty = qty - ? where sku = ? and qty >= ? per row.
  2. If multiple rows are needed, lock in a canonical order.
  3. Shorten the transaction.
  4. Retry on deadlock (Spring: CannotAcquireLockException / DeadlockLoserDataAccessException), with a limited count and jitter. Safe only if the whole unit is idempotent or has no external side effects.

Deadlocks cannot be fully eliminated in a busy system, so a low rate with a clean retry is acceptable; a rising rate means a new code path broke the ordering.

Remember: deadlock = opposite lock order. Same order, short transactions, retry the victim.

The product list endpoint with filters and paging is slow and the database CPU is high. Walk me through it. Senior

I measure first, in this order: how many statements run, what the slowest statement is and its execution plan, and then whether I load more than I show. The usual culprits are N+1, a collection join with paging, a slow count(*), a missing index, and loading full entities for a list.

Check first: SQL log or APM for statement count per request; EXPLAIN on the slowest query; look for the in-memory pagination warning (HHH000104) and for offset with big numbers.

Fix, in order of payoff:

  1. Return a DTO projection with only the displayed columns, with ToOne data joined in the same query.
  2. Index the filter and sort columns for the common combinations; avoid leading-wildcard like.
  3. Page ids first when a collection is involved; use Slice or a cheaper count if the total is expensive; use keyset paging for deep pages.
  4. Only then consider caching.

Prevent: an endpoint-level performance test with production-sized data, and statement-count assertions.

A structured way to narrow it down

  1. Is it the app or the database? If database CPU is high, a query is expensive (scan, sort, count). If app CPU or memory is high with low database load, the ORM is materialising too much (entities, in-memory paging).
  2. Statement count. Many small queries means N+1. A few heavy ones means plan problems.
  3. The heavy query. Run EXPLAIN (ANALYZE) on it with production-like parameters. Look for sequential scans on big tables, sorts on unindexed columns, and large OFFSET.
  4. Loaded versus displayed. Compare columns selected with columns shown. Loading 40-column entities for a 5-column list is wasteful.

Measure, fix the query shape and indexes (cheap and durable), then reduce the data volume (projection, paging), and only then add caching. Quote the principle: an index or a projection removes work; a cache only avoids repeating it, and brings invalidation issues.

After disabling Open Session In View, the API returns LazyInitializationException on several endpoints. How do you handle it? Intermediate

That is the bug OSIV was hiding: controllers or serialisers were touching lazy data after the transaction ended. I go endpoint by endpoint: load what the response needs inside the service transaction (fetch join, entity graph or projection) and return DTOs, so nothing lazy leaves the service.

Check first: the stack trace names the lazy field and the serialiser or controller line that touched it. List the endpoints that return entities directly.

Fix: for each endpoint, decide what the response needs, fetch exactly that in a read-only transaction, map to a DTO inside the service. Use default_batch_fetch_size to soften the remaining cases. Do not go back to OSIV, EAGER, or enable_lazy_load_no_trans: they bring the same hidden costs back.

Prevent: a rule that controllers never return entities, and integration tests that call the real endpoints with OSIV off.

Why this is a healthy pain

With OSIV on, the application worked by accident: the session stayed open so Jackson could trigger lazy loads while writing JSON. Each such load was an invisible query. Turning OSIV off exposes every place where the service did not decide what data to return. A big batch of exceptions on day one is the migration cost of fixing a design weakness.

A repeatable procedure per endpoint

  1. Read the stack trace: it names the entity and field (for example Order.items) and where it was touched.
  2. Decide what the response needs. If a DTO exists, list its fields; if the endpoint returns an entity, define a DTO now.
  3. Write one read query that fetches exactly that (projection, or join fetch for ToOne plus batch fetching for collections), inside a @Transactional(readOnly = true) service method.
  4. Map to the DTO inside the transaction. Controllers receive only DTOs.
  5. Add a test that calls the endpoint and asserts both the JSON and the statement count.

Temporary measures

  • Set default_batch_fetch_size to reduce the cost of leftover lazy loads inside services.
  • For a big list of endpoints, rank by traffic and fix the busiest first, while keeping OSIV off in new code only if you can split configuration (usually it is global, so fix before releasing).

Things not to do

Do not switch associations to EAGER, set enable_lazy_load_no_trans, or put @Transactional on controllers to cover serialisation. The last one extends the transaction over JSON rendering and brings back the connection-holding problem. Also avoid @JsonIgnore on lazy fields as a blanket fix: it removes data the client may need and hides design issues.

Remember: LazyInit after turning OSIV off is a good sign: the hidden lazy loads are now visible. Fetch in the service, return DTOs.

After a bulk update the API still returns the old status for some records. Why? Senior

The bulk update ran in the database but the persistence context still holds the old entities, so later reads in the same transaction answer from memory. I flush before the bulk update and clear (or refresh) after it, or use @Modifying(flushAutomatically = true, clearAutomatically = true). If the stale value is on another server, I also check a second-level cache.

Check first: is the stale read in the same transaction as the update? If yes, it is the context. If it is in a later request, look at L2 or query caches, or an application cache that the bulk update did not evict. Native SQL updates are the usual cache bypass.

Prevent: a convention that bulk updates run in their own method and transaction, and the version column updated in the statement (set version = version + 1) so optimistic locking still sees the change.

The overwriting variant

Sometimes the data is not stale, it is overwritten: the same transaction loaded the entity before the bulk update, modified it later, and its flush wrote the old status back. The symptom is "the update worked and then reverted". Clearing right after the bulk statement avoids that, because the stale entity is detached and its later changes are ignored (so keep the order of operations clear in the code).

Prevention in code

Wrap bulk updates in a dedicated repository method with @Modifying(flushAutomatically = true, clearAutomatically = true), include version = version + 1 and the audit timestamp in the statement, and call it at the start of a transaction or in its own transaction so no other entities are loaded before it. Tests should load, bulk update, then read again and assert the new value.

Remember: bulk SQL skips the context and the version. Flush before, clear after.

Under load the service logs "Connection is not available, request timed out after 30000ms", though the database CPU is low. What is going on? Senior

The pool is empty because connections are held too long, not because the database is busy. Threads wait for a free connection and time out. I look for what runs while a connection is held: remote calls inside transactions, OSIV keeping the session open during slow work, REQUIRES_NEW needing a second connection, or leaks. Then I shorten those, instead of just raising the pool size.

Check first: HikariCP metrics (active, idle, pending threads) and a thread dump: are many threads waiting for a connection while others sit in a remote call or a long loop with a connection held? Check whether OSIV is on. Enable leakDetectionThreshold to find code that holds a connection too long.

Fix: move remote calls out of transactions, turn OSIV off, avoid nested REQUIRES_NEW in a pool-limited path (or make sure the pool is bigger than the maximum nesting times concurrent requests), split long transactions into chunks, and size the pool deliberately.

Prevent: pool metrics and alerts, and a load test that includes the slowest downstream.

The key observation

"Database CPU is low and the pool is empty" means the connections are mostly idle while checked out: the application holds them without using them. Using the throughput relation (concurrent requests supported equals pool size divided by hold time), the hold time has grown, usually because something slow happens between "transaction started" and "transaction ended".

How to find who holds the connection

  1. Hikari metrics: active near max, pending above zero, usage time histogram rising.
  2. Thread dump: look at threads that have a connection (they show frames under the transaction interceptor) but are in SocketInputStream.read (remote call), Thread.sleep, or serialisation.
  3. Leak detection: set spring.datasource.hikari.leak-detection-threshold=20000 to log a stack trace of code holding a connection for over 20 s.
  4. Database side: sessions "idle in transaction" (PostgreSQL pg_stat_activity) are exactly this problem.

Typical culprits and the matching fix

Remember: empty pool with idle database = connections held too long. Shorten transactions, do not just grow the pool.

A transaction deletes a row and inserts a replacement with the same unique key, and fails with a duplicate key error even though the delete comes first in the code. Why? Senior

Hibernate runs inserts before deletes at flush, so the new row hits the unique constraint while the old row still exists. I either call em.flush() right after the delete so it is sent first, or, better, change the existing row instead of deleting and inserting.

Situation: in the code, repo.delete(old); repo.save(new) with the same unique value, and the log shows INSERT before DELETE.

Check first: the SQL log order. It confirms the action-queue order (inserts, updates, collection changes, deletes).

Fix: update the row in place when the intent is "replace". If a delete plus insert is really needed, flush between them (deleteAndFlush in Spring Data, or em.flush()). For collections of children with a unique key, the same ordering applies to orphanRemoval.

Prevent: remember that code order is not SQL order, and add an integration test for the replace case.

What the log shows

insert into product (code, name) values (?, ?)     -- runs first
delete from product where id = ?                   -- runs second
ERROR: duplicate key value violates unique constraint "uk_product_code"

Even though the Java code deleted first, the flush executed the action queue in its own order (inserts before deletes), so at the time of the insert the old row with the same code still exists.

Fix options, from best to worst

  1. Update in place. If "replace" really means "same business entity, new values", load the existing row and change it. One UPDATE, no uniqueness conflict, history preserved, fewer locks.
  2. Flush between. repo.delete(old); repo.flush(); repo.save(newRow);. The DELETE goes first. Spring Data has deleteAndFlush in the JPA repository.
  3. Deferrable constraints (PostgreSQL DEFERRABLE INITIALLY DEFERRED) move the check to commit, but not every database supports it and Hibernate cannot create it from the annotation.
  4. Bulk delete first via a JPQL delete in the same transaction, which runs immediately.

Collection variant

The same thing happens when a parent's child collection has a unique constraint (for example (order_id, line_no)) and you remove one child and add a new one with the same key within a flush: the insert runs before the orphan delete. Update the existing child, or flush between the removal and the addition.

Remember: flush order is insert, update, delete. Need delete first? Flush after it, or just update.

Users report old prices after an admin updated them, but only on some servers. What do you check? Senior

"Only on some servers" points to a node-local cache. Each node has its own second-level or application cache, and the update on one node did not invalidate the others. I check which cache holds prices, whether the provider is cluster-aware, and whether the price was changed outside Hibernate (SQL script, another service, a bulk or native update).

Check first: is the Hibernate L2 cache or query cache enabled for the price entity? Is the provider local (default Ehcache) or distributed? Does an application cache (Spring Cache) hold price DTOs without expiry?

Fix: give the data a time-to-live as a safety net, use a distributed cache with invalidation (Redis, Hazelcast, Infinispan) or evict by event, and make every writer go through the same path. If prices change often, do not cache them in L2 at all.

Prevent: decide per data type how stale it may be, and write a test that updates on node A and reads on node B.

Narrowing "only some servers"

  1. Reproduce: call the same endpoint against each instance directly (not via the load balancer) and compare the price. This confirms which nodes are stale.
  2. Check the age of the stale value: does it fix itself after a fixed time? That is a TTL cache. If it never fixes itself until restart, there is no expiry.
  3. Find the write path: was the price updated by this application via Hibernate, or by a script, another service, or a native query? Hibernate invalidates its L2 entry only for changes it performs (and bulk JPQL), not for other writers.
  4. List caches in the read path: Hibernate L2/query cache, Spring @Cacheable with Caffeine (local), a CDN or HTTP cache, a browser cache.

A developer says "I put @Transactional, but half the changes were saved and half were not". How do you debug it? Intermediate

Either there was no transaction around the whole method, or it committed even though an error happened. I check the usual four: self-invocation (the call never went through the proxy), a swallowed exception, a checked exception that does not roll back by default, and a REQUIRES_NEW or async call that ran in a different transaction.

Check first: turn on logging.level.org.springframework.transaction.interceptor=TRACE (or org.springframework.orm.jpa) to see "Getting transaction for ..." and "Completing transaction". Does the log show one transaction or several? Was the annotated method called from another bean?

Fix: move the method to another bean or use TransactionTemplate; let the exception propagate or call TransactionAspectSupport.currentTransactionStatus().setRollbackOnly(); add rollbackFor = Exception.class if checked exceptions are expected; keep async work in its own transaction by design.

Prevent: an integration test that forces a failure in the middle and asserts that nothing was saved.

A debugging recipe with the log

Turn on logging.level.org.springframework.transaction.interceptor=TRACE. For each call you expect to be transactional you should see lines like "Getting transaction for [OrderService.place]" and "Completing transaction for ...". Interpret what you see:

  • No such lines for the method: it was called without the proxy (self-invocation, new, private or final method). Fix the call path.
  • Several short transactions instead of one: the annotation is on an inner method only, so each repository call used its own transaction. Move @Transactional to the entry method.
  • "Completing" (commit) although an error occurred: the exception was caught, or it was checked. Look at the catch blocks and the exception type.
  • "Suspending current transaction" / "Creating new transaction": a REQUIRES_NEW or async hop.

Example of the "half saved" bug

@Transactional
public void importRows(List<Row> rows) throws IOException {   // checked exception
    for (Row r : rows) repo.save(r);
    if (bad) throw new IOException("bad file");         // default: COMMIT, rows stay saved
}

Fix with rollbackFor = Exception.class or throw an unchecked exception. Another common one: the controller calls service.a(), and a() calls this.b() where b is the @Transactional one, so everything runs without a transaction and each save commits alone.

Where to put the annotation

On the service method that represents one business operation (the use case boundary), not on repositories or every private helper. That gives one transaction per use case and a clear picture of what commits together.

Remember: partial saves mean the transaction did not span the work. Check proxy bypass, swallowed and checked exceptions.

We catch an exception from an inner service call and continue, but the request ends with UnexpectedRollbackException. Explain and fix. Senior

The inner method is @Transactional(REQUIRED), so it joined the outer transaction. When it threw, the proxy marked the whole shared transaction rollback-only. My catch block swallowed the exception, but the mark stays, and at the end Spring cannot commit and throws UnexpectedRollbackException. To keep going after an inner failure, the inner work must run in its own transaction or not throw.

Check first: find which inner call threw (the log shows "Participating transaction failed - marking existing transaction as rollback-only").

Fix:

  • If the inner step is optional, run it with REQUIRES_NEW, so its rollback is separate. Watch the second connection.
  • Or do not use an exception for expected cases: check first and return a result.
  • Or use noRollbackFor for an exception that is really harmless.
  • Do not catch and continue after a persistence exception in the same context: the session may be in an inconsistent state.

Prevent: test the failure path of each inner call, and keep transaction boundaries visible in the design.

The mechanism, replayed with the log

  1. Outer @Transactional method starts transaction T.
  2. It calls inner.sync(), also @Transactional. Log: "Participating in existing transaction".
  3. sync() throws. Log: "Participating transaction failed - marking existing transaction as rollback-only".
  4. Outer catches and logs a warning, then does more work and returns normally.
  5. At commit the proxy sees rollbackOnly = true, rolls back, and throws UnexpectedRollbackException: Transaction silently rolled back because it has been marked as rollback-only.

A transaction has one fate. Once any participant has said "roll back", the final decision cannot be reversed by a different participant catching an exception.

Choosing the right fix

IntentFix
Inner failure should fail the whole requestDo not catch; let it propagate
Inner work is optional ("best effort")REQUIRES_NEW on the inner method, so its failure only affects itself
Exception is a normal outcome (not found, duplicate)Return a result, or check first; or noRollbackFor on that exception
Inner is a repository call that failed on a constraintTreat the persistence context as broken; end the transaction

Costs to mention

REQUIRES_NEW takes another connection (pool risk) and cannot see the outer transaction's uncommitted data. If the "best effort" work depends on rows the outer just wrote, it will not find them. In that case restructure: perform the best-effort step after the outer commit, for example from an AFTER_COMMIT event listener.

Remember: inner REQUIRED failure poisons the shared transaction. Use REQUIRES_NEW or avoid the exception.

You are asked to upgrade a service from Spring Boot 2.7 (Hibernate 5) to Spring Boot 3 (Hibernate 6). How do you plan the persistence part? Senior

I treat it as a behaviour change, not only a rename. Step one is javax.persistence to jakarta.persistence (mechanical, with a migration tool). Step two is to check what Hibernate 6 does differently: id generation naming, stricter HQL, some type mappings, and SQL it generates. Then I run the full integration test suite on a real database and compare statements and schema.

Check first (known areas of change, typically):

  • Ids: AUTO and sequences now use one sequence per entity (entity_seq) instead of the shared hibernate_sequence, so existing databases break unless I set the legacy naming strategy or add the sequences.
  • HQL: stricter parsing and some different semantics; a few queries need fixing. distinct for fetch joins is no longer needed.
  • Types: date, time, enum and JSON mappings changed in places; check with ddl-auto=validate against the real schema.
  • Config: remove a hand-set dialect (it is detected), and check logging names (the bind logger moved to org.hibernate.orm.jdbc.bind).
  • Java 17 minimum, and Spring Data JPA 3.

Prevent surprises: upgrade on a branch with Testcontainers against the production database engine, run validate, diff the SQL of key flows before and after, and roll out gradually.

Plan in phases

  1. Prepare on the old stack. Upgrade to the latest Boot 2.7.x, remove deprecated APIs, make sure tests are good and run against the production engine with Testcontainers. Fewer variables at once.
  2. Mechanical migration. Rename imports javax.persistence to jakarta.persistence (tools: OpenRewrite recipes, IDE refactoring), bump Java to 17, update third-party libraries that touch persistence (QueryDSL, MapStruct, Hibernate extensions, Flyway, JDBC drivers) to Jakarta-compatible versions.
  3. Behaviour review (below).
  4. Validate against real data. Run ddl-auto=validate against a copy of the production schema; compare generated SQL for the top 10 flows before and after; run load tests.
  5. Roll out gradually with a quick rollback path, since persistence changes can affect data written by the new version.

Hibernate 6 behaviour changes to know

  • Id generation: sequence per entity by default with allocation size 50 (named like order_seq) and legacy settings exist to restore the old naming and optimiser. If you used the shared hibernate_sequence with allocationSize 1, either define @SequenceGenerator explicitly or enable the legacy option, or you will see duplicate keys.
  • HQL: a new parser and SQL AST. Stricter on invalid queries, implicit join and some function behaviours changed, and select distinct for fetch joins is no longer needed.
  • Types: java.time and enum handling, Instant/OffsetDateTime mapping, UUID, JSON and array mappings were reworked; check column types with validate.
  • Removed APIs: Hibernate's save, update, saveOrUpdate, legacy Criteria API, @Type syntax changes.
  • Dialects: auto-detected; version-specific dialect classes were reorganised.
  • Logging names: bind logging moved to org.hibernate.orm.jdbc.bind.

Say that exact details differ by 6.x minor version, so read the official migration guide for the target version and run your tests as the final authority.

Remember: javax to jakarta is the easy part. Watch id sequences, HQL strictness and type mappings, and validate against a real schema.
