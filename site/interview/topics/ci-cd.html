CI/CD interview questions

The CI/CD questions a working developer is really asked: what a pipeline is and how to design one, keeping it fast and trustworthy, shipping safely with rolling, blue-green, canary and feature flags, rolling back (even with a database change), and keeping secrets safe. Each answer starts with a short spoken reply, then goes deeper, then ends with one line to remember.

Mental model: the 7 ideas everything hangs on

One line: a pipeline is an automated, repeatable path from a commit to production. Each stage is a question ("does it compile?", "do tests pass?", "is it safe to release?"), asked cheapest first, and the output is one artifact that is promoted unchanged through the environments.
  1. Integrate often. Small changes merged many times a day mean small, easy-to-find breakages. Big, rare merges mean big, painful ones.
  2. The pipeline is the only path. If a build or deploy works only from someone's laptop, nobody can trust or repeat it.
  3. Build once, promote the same artifact. What you tested in staging must be byte for byte what runs in production. Only configuration changes between environments.
  4. Fail fast, cheap checks first. Lint and unit tests (seconds) before integration tests (minutes) before end-to-end (many minutes).
  5. Deploy is not release. Putting code on servers and turning a feature on for users are different steps. Feature flags separate them.
  6. Every change must be reversible. Rollback, roll forward, flag off, or traffic switch back. Database changes are the hard part, so they go in small compatible steps.
  7. Measure the flow. Lead time, deployment frequency, change failure rate and recovery time tell you if the process is healthy.

1. Pipeline basics

What is continuous integration, and why does it matter? Basic

Continuous integration means every developer merges small changes into the shared main branch often, at least daily, and each merge is built and tested automatically. The point is fast feedback: if two people break each other's code, I find out in minutes while the change is fresh, not three weeks later at release time.

What it is, from scratch. Imagine five developers each working alone on a copy of the code for three weeks, then trying to combine everything on the Friday before release. The pieces will not fit: someone renamed a method that someone else calls, two people edited the same file, a library was upgraded in one copy but not the others. Continuous integration (CI) is the habit that prevents this "integration hell": everyone integrates their work into the shared main branch very often, and a machine checks every integration automatically.

Why it exists. The cost of fixing a defect grows with the time between writing it and finding it. If the build goes red ten minutes after my commit, the cause is in the only change I just made and my memory is fresh. If it goes red three weeks later, the cause is hidden among hundreds of commits from many people. CI keeps that gap small.

What one CI run does, step by step:

  1. A developer pushes a small change on a short branch and opens a pull request.
  2. The CI server notices the push (a webhook) and starts a clean machine or container.
  3. It checks out the code, compiles, runs static checks (lint, formatting) and the unit tests, and builds the package.
  4. The result (green or red) is posted back on the pull request. Merging is blocked while red.
  5. After merge, the same checks run again on main, because main now contains everyone's work combined.

Example. Ana renames getUser() to findUser() and merges at 10:00. Ben, who still calls getUser() in his own branch, rebases at 10:30. His build fails at once with "cannot find symbol", he fixes one line, and nobody else noticed. Without CI that same clash would surface at release time.

The tool (Jenkins, GitHub Actions, GitLab CI) only runs the checks. The practice is the habit: small changes, short-lived branches, and a rule that a broken main is fixed first. A team with a CI server that merges huge branches once a month is not really doing CI. At minimum CI compiles, runs unit tests and static checks, and builds the package to prove it can be built. A healthy sign is that main is almost always green and a red build is everyone's problem until fixed.

Remember: CI is a habit (merge small, merge often, keep main green), not a tool.

What is the difference between continuous integration, continuous delivery and continuous deployment? Basic

Continuous integration is merging and testing often. Continuous delivery means every change that passes the pipeline is always in a releasable state, but a human decides when to release it. Continuous deployment goes one step further: if the checks pass, the change goes to production automatically, with no human gate.

Why the three terms exist. They describe how far automation reaches along the path from commit to users. People mix them up because "CD" is used for both of the last two.

Automatic partWho decides to reach users
Continuous integrationBuild and test every mergeNot covered, release is a separate matter
Continuous deliveryCI plus packaging and deploy to staging, always releasableA human presses the button
Continuous deploymentEverything, including productionThe pipeline itself, if checks pass

Example. A bank's payment service: every merge produces a tested artifact that is deployed to staging (continuous delivery), and the release manager approves the production rollout on Tuesday morning because of a change-control rule. A consumer web app at a startup: a merge at 14:03 is in production at 14:12 with no human involved (continuous deployment).

How to choose. The question is not "which is more modern" but "do I have enough safety nets to remove the human?". Those nets are fast reliable tests, feature flags, a canary with automatic abort, and good monitoring. If those exist, the human click adds delay but little safety. If they do not exist, automatic deployment is just automatic outages. Regulation (audit, separation of duties) can also legitimately require a named approver; then you keep delivery and make the approval fast and evidence-based.

So the only difference between delivery and deployment is the human click in front of production. Teams pick delivery when there is business timing, approvals or regulation, and deployment when they trust their tests, feature flags and monitoring enough to ship every merge. Deployment needs more trust in automated tests and rollback than delivery does. The usual middle ground: auto-deploy to staging, one approval for production. The "approval gate" is a rule that blocks the next stage until satisfied. It can be automatic (all tests green, no critical vulnerability, error rate normal) or manual (a named reviewer). Prefer automatic gates, because manual approvals slow the flow and often become a rubber stamp.

Remember: delivery = "could ship any time" (human clicks), deployment = "ships by itself".

What are the typical stages of a pipeline, and in what order? Basic

Checkout, build, fast checks (lint, unit tests), package one versioned artifact, slower checks (integration tests, security scans), publish the artifact, deploy to staging, run smoke tests there, then promote to production. The order follows two rules: cheap and likely-to-fail checks first, and do each expensive thing, like building the artifact, only once.

What a stage is. A pipeline is a series of stages, and each stage answers one yes/no question about the change: "does it build?", "do the unit tests pass?", "does it work against a real database?", "is it safe to ship?". If any answer is no, the line stops and the author is told.

Why the order matters. Two stages that are equally useful can differ a hundredfold in cost. Imagine lint takes 20 seconds, unit tests 3 minutes, integration tests 12 minutes and end-to-end tests 25 minutes. If a typo breaks formatting and I run the slow suites first, the developer waits 40 minutes to learn about a 20-second problem. Cheap-and-likely-to-fail first gives the earliest possible feedback and wastes the least machine time.

A concrete walk-through for a Java service:

  1. Checkout and build: clone at the exact commit, restore the dependency cache, compile.
  2. Fast checks in parallel (about 3 minutes): lint, unit tests, dependency vulnerability scan.
  3. Package once: build the container image, tag it with the commit SHA, push it to the registry.
  4. Integration tests: start PostgreSQL and Kafka in containers, run the service tests against them.
  5. Deploy to staging using that exact image, then run a few smoke tests (the app starts, login works, one key request returns 200).
  6. Promote to production (manually or automatically), gradually, with monitoring.

Pitfall: putting slow end-to-end tests on every pull request makes people batch their changes to avoid waiting, which is the opposite of CI. A common split is: fast core on every PR, heavy suites on main or nightly.

That is "fail fast": a formatting error should turn the build red in seconds, not after ten minutes of slow tests. Stop on the first failure, cancel older runs when a new commit lands on the same branch, and run independent checks (lint, unit tests, dependency scan) in parallel to cut wall-clock time. Put slow end-to-end tests after the artifact exists, against a deployed environment, often only on main. The one time you do not stop at the first failure is when you want a full report, for example a test matrix across platforms.

Remember: cheap first, expensive once, parallel where independent, stop on first red.

What does "build once, deploy many" mean, and why is rebuilding per environment a bad idea? Intermediate

I build the artifact (a container image, jar, zip) one time, give it an immutable version such as the commit SHA, store it in a registry, and deploy that same artifact to dev, staging and production. If I rebuild for production, I am no longer running what I tested: a new base image or transitive dependency can sneak in, and "it passed in staging" means nothing.

Why this rule exists. A test result is only evidence about the thing that was tested. If staging runs build #101 and production runs a fresh build #102 made from "the same code", the two are not identical: the base image may have moved, a dependency declared as a version range may have resolved differently, a build tool may have been upgraded. Then "it passed in staging" says nothing certain about production, and you have lost the main value of staging.

How it works.

  1. On merge, the pipeline builds once and tags the output with an immutable identifier, usually the commit SHA (for example orders:9f3c2ab). A container image can also be pinned by its digest, a hash of its content, which cannot be re-pointed.
  2. It pushes the artifact to a registry or repository (Nexus, Artifactory, a container registry).
  3. Each environment is deployed by telling it "run orders:9f3c2ab" plus that environment's configuration.
  4. Promotion from staging to production does not build anything. It only changes which version production runs.

What differs between environments is configuration: database URL, feature flags, credentials, replica count. The application reads these at start-up from environment variables, mounted files or a secret manager. A useful test: if I must rebuild to change a database URL, that URL was baked in, which breaks the rule.

Trade-off and exceptions. The artifact must be built with no environment-specific assumptions, which sometimes takes work for front-end apps that embed API URLs at build time. The usual fix is to load a runtime config file at start-up. Also, base images get security patches, so you still rebuild regularly, but each rebuild produces a new version that goes through the whole pipeline again.

Only configuration changes between environments: database URLs, feature flags, secrets, resource limits. These are injected at deploy or start time (environment variables, mounted files, a secret manager), never baked into the artifact. Tag images with the commit SHA, not just latest, because latest moves and you cannot tell what is running or roll back to a known version. A good check: can you take the exact image running in production and trace it to one commit and one pipeline run?

Watch out: a build step that runs per environment (for example build:prod only in the deploy job), or secrets and URLs baked into the image.

Remember: same bytes everywhere, only config differs.

Tests pass on my laptop but fail in CI. Why does that happen, and how do you make builds reproducible? Intermediate

CI starts from a clean machine, so it exposes hidden assumptions on my laptop. The usual suspects are a different tool version, an unpinned dependency that resolved to something new, a git-ignored local file or environment variable, case-sensitive file names on Linux, time zone or locale, and test order or timing. I find out by running the same container image and the same commands that CI runs, locally.

What is really going on. Your laptop is a long-lived, messy machine: it has tools installed years ago, caches, environment variables, a locally edited config file, a database that happens to be running. CI starts from nothing every time. So a CI failure usually means the build had a hidden input that was never written down. The goal of a reproducible build is: same inputs in, same output out, anywhere.

Typical culprits and the tell-tale sign of each:

CauseHow it shows upFix
Different tool or JDK/Node versionSyntax or API errors only in CIPin versions (toolchain file, .nvmrc, image tag)
Floating dependency rangeWorked last week, fails today with no code changeCommit a lock file, pin versions
Git-ignored local file or env var"File not found" or null configDocument and inject it explicitly in CI
Case-insensitive file system (Windows, macOS)Import vs import path works locally, fails on LinuxFix the casing
Time zone, locale, clockDate tests fail near midnight or in UTCInject a clock, set the zone in tests
Test order or timingPasses alone, fails in the full runIsolate test data, randomise order locally

Debug method. Do not guess. Run the exact CI image locally (docker run --rm -v $PWD:/w -w /w ci-image ./build.sh) and watch it fail the same way, then change one thing at a time. Once reproduced, the fix is usually obvious.

Also avoid network access at test time (use local mirrors and mocks), because a flaky external site becomes a flaky build.

To make builds reproducible: pin the language and tool versions, commit lock files (package-lock.json, poetry.lock; Maven and Gradle can pin versions too), build inside a container with a fixed image, and do not read from the live network at test time. A fully "hermetic" build depends only on declared inputs, which tools like Bazel enforce. Most teams do not need that, but the lock file plus pinned image gets you most of the way.

Remember: if CI differs from my machine, reproduce CI locally in its container, then pin the difference.

2. Artifacts, speed and tests

What is the difference between an artifact and a cache? Basic

An artifact is an output I need: the built jar, image or test report, which later stages or people consume. A cache is only a speed-up, such as downloaded dependencies, which I can lose at any time and the build must still work, just slower.

The practical difference is "what happens if it disappears?". Delete a cache and the next build is slower but correct. Delete an artifact and you may be unable to deploy, roll back, or investigate a production incident.

ArtifactCache
PurposeOutput others consume (jar, image, test report, coverage)Speed-up of repeated work (downloaded libraries, compiled objects)
LifetimeKept, versioned, immutableDisposable, evicted when old or full
WhereRegistry or artifact repository, or passed between jobsCI cache storage, runner disk
If lostReal problemSlower build only

Example of a good cache key. For a Gradle project the key is linux-gradle-<hash of the lock/build files>. While dependencies are unchanged the key matches and a 90-second download becomes a few seconds. When someone upgrades a library the hash changes, the key misses, the build downloads fresh and saves a new cache. A fallback key (linux-gradle-) restores the most recent older cache so only the difference is downloaded.

Pitfalls. A poisoned cache (a half-written or corrupt directory) causes failures that vanish on a clean build. Build outputs cached by timestamp can serve stale classes. Never cache anything secret, and be careful sharing caches between untrusted branches or forks because a malicious pull request could plant content that a later trusted build reads. Rule of thumb: the build must pass with an empty cache, and you should run one periodically to prove it.

That difference shows in design. Artifacts are versioned, immutable and kept in a proper repository or registry. A cache is keyed and disposable. A good dependency cache key is the OS plus a hash of the lock file, so it refreshes exactly when dependencies change, with a fallback to the most recent cache. What can go wrong: a stale or poisoned cache gives strange failures that vanish on a clean build, and caches shared across branches can leak bad state. If a build only passes with the cache, the cache has become a hidden input and is a bug.

Remember: artifact = something I must keep; cache = something I may lose.

Your pipeline takes 40 minutes. How do you make it faster? Senior

I measure first: time per stage plus queue time. Then I attack the biggest costs in order: cache dependencies and build layers, run independent stages in parallel, split the slow test suite across machines, run only what a change affects, and move slow end-to-end tests off the pull-request path to main or nightly.

Step 0: measure. "40 minutes" is a total, not a diagnosis. Open the pipeline timeline and write down time per stage including queue time (waiting for a free runner). Often one thing dominates: say 6 min queue, 8 min dependency download, 4 min compile, 18 min tests, 4 min scans. Fixing the 18 gives the most. Optimising the wrong stage is the most common mistake.

Worked example of getting from 40 to about 12 minutes:

  1. Cache dependencies keyed on the lock file: 8 min becomes 1 min.
  2. Order Docker layers so rarely-changing steps come first: copy the dependency file, install, then copy source. Source edits then reuse the cached install layer.
  3. Shard the tests: split the 18-minute suite over 4 machines, balanced by past run time (not file count) so all finish together: about 5 minutes.
  4. Run independent stages in parallel: lint, scans and unit tests together instead of one after another.
  5. Skip what cannot be affected: a docs-only change should not run the integration suite (path filters); in a monorepo build only the modules touched and their dependants.
  6. Move heavy checks off the PR path: full end-to-end and long security scans on main or nightly, with a small smoke set on the PR.

Fix the tests too. Fixed sleep calls, tests that boot a whole application context when a plain object would do, and retries that quietly double the time are common hidden costs.

Trade-offs. Sharding costs more runners and adds a little set-up overhead per shard. Running less on PRs risks finding bugs later, so make sure main failures are reported loudly and fixed first. Keep a time budget (for example PR check under 10 minutes) and alert when it is exceeded, because pipelines slow down gradually and nobody notices.

Concrete moves, cheapest first:

  • Cache dependencies keyed on the lock file; order Docker layers so dependencies are installed before source is copied.
  • Parallelise lint, unit tests and scans; shard tests by historical duration so each machine finishes at the same time.
  • Skip work that cannot be affected (path filters, or affected-module builds in a monorepo).
  • Fix the tests themselves: slow sleeps, tests hitting real networks, flaky retries that double the time.
  • Capacity: if queue time is the cost, add runners; faster machines can be cheaper than waiting developers.

Pitfall: do not make it faster by deleting checks that guard quality. Move them, do not drop them.

Remember: measure, then cache, parallelise, split, skip, and move slow tests off the PR path.

What is the test pyramid, and how does it shape a pipeline? Basic

The pyramid says: many fast unit tests at the bottom, fewer integration tests in the middle, very few slow end-to-end tests at the top. Cost, run time and flakiness all grow as you go up, so I put most of my confidence at the bottom and keep the top to a handful of critical user journeys.

Why a pyramid. Every test trades realism against speed and precision. A unit test is not very realistic but runs in a millisecond and, when it fails, names the exact class. An end-to-end test is very realistic but takes seconds or minutes, needs a whole environment, fails for many unrelated reasons, and tells you only "something broke somewhere". So you want lots of the cheap precise kind and a few of the realistic kind.

LayerChecksTypical speedFailure tells you
UnitOne class or function, dependencies fakedMillisecondsThe exact method
IntegrationCode with a real DB, broker or HTTP clientSecondsWhich boundary is wrong (SQL, mapping, config)
End-to-endWhole system through the UI or public APIMany seconds to minutesOnly that some journey broke

Example. For an order service: hundreds of unit tests on price and discount rules; dozens of integration tests that save and load orders against a real PostgreSQL and publish to a real Kafka; and maybe five end-to-end tests ("log in, add to cart, pay, see confirmation") that run after deploy to staging.

Where contract tests fit. When service A calls service B, a contract test records what A expects (fields, status codes) and verifies B still honours it, without starting both. It catches "B renamed a field" without a slow end-to-end run.

Anti-patterns. The "ice cream cone" (mostly manual or end-to-end tests) and the "hourglass" (unit and e2e but no integration layer, so wiring bugs escape). The shape is a guideline, not a law: for a thin CRUD service, integration tests may deliver more value than many tiny unit tests. Judge by confidence per second of run time.

Unit tests check one class with no network or database, run in milliseconds and point to the failing line. Integration tests check real neighbours such as a database or broker. End-to-end tests drive the whole system like a user: realistic but slow, fragile and hard to debug. In the pipeline, unit tests run on every commit, integration tests on every pull request, and a small end-to-end or smoke set runs after deploy to staging. Contract tests sit between services: they check that a consumer and a provider agree on an API without deploying both. An "ice cream cone" (mostly end-to-end tests) gives slow, flaky pipelines.

Remember: many unit, some integration, few end-to-end.

How do integration tests get a real database or message broker inside a pipeline? Intermediate

I start the real dependency as a throwaway container for the test run. Either the CI tool starts "service containers" next to the job, or the tests start their own with Testcontainers, a library that launches Docker containers from test code and removes them afterwards. That gives a real PostgreSQL or Kafka, not a fake that behaves differently.

The problem. A repository class that builds SQL, a Kafka consumer, a cache layer: unit tests with mocks cannot prove these work, because the bugs are in how the code and the real system interact (a wrong column type, a missing index, a serialisation mismatch). But CI machines do not have a database installed, and a shared test database makes tests interfere with each other.

The solution: a disposable real dependency per run. Two common ways:

  • CI service containers: the pipeline definition says "start a postgres:16 container next to my job, reachable at host postgres". Simple, but the same setup must be reproduced by hand on a laptop.
  • Testcontainers: a library. Test code declares new PostgreSQLContainer<>("postgres:16"), the library starts it through Docker, gives a random free port and JDBC URL, and removes it at the end. The same test runs on any machine with Docker.
@Testcontainers
class OrderRepoIT {
  @Container static PostgreSQLContainer<?> db = new PostgreSQLContainer<>("postgres:16");
  // point the datasource at db.getJdbcUrl(), run migrations, then test
}

How to keep it fast and stable. Start the container once per test class or per suite, not per test. Isolate tests by rolling back a transaction or cleaning only their own rows. Run the same migrations (Flyway or Liquibase) that production uses, so the schema is also tested. Wait for readiness through the container's health or log check instead of a sleep. Pin the image version to match production.

Why not H2 or an in-memory fake? It speaks a different SQL dialect, handles locking, JSON, and types differently, so tests can pass while production fails. Use a fake only when behaviour genuinely does not matter. The CI runner needs Docker access, and pulling images costs time, so cache them or use a registry mirror.

Testcontainers is usually better for developers, because the exact same test runs on a laptop and in CI. Keep tests independent: each test creates its own data or rolls back, and the container is reused across tests to stay fast. Avoid in-memory substitutes (such as H2 for PostgreSQL) when behaviour matters, since SQL dialects, locking and types differ and bugs hide there. Wait for the container to be ready (a health check), not a fixed sleep, which is a classic cause of flaky tests.

Remember: test against the real thing in a disposable container, not a lookalike.

What is a flaky test, what causes it, and how do you handle it? Intermediate

A flaky test passes and fails on the same code. It matters because once "just re-run" becomes normal, people stop trusting red builds and real bugs slip through. I quarantine it fast so it stops blocking others, give it an owner and a deadline, then fix the root cause instead of adding retries.

Why flaky tests are expensive. A test is a smoke alarm. An alarm that sometimes rings for no reason teaches everyone to ignore it, and then the day it rings for a real fire nobody reacts. Flakiness also wastes time: a 20-minute pipeline that fails randomly 10 percent of the time costs every developer many re-runs per week.

Common causes, with a fix for each:

CauseExampleFix
Timingsleep(2) then assert, fails on a slow runnerWait for a condition with a timeout (poll or await)
Shared stateTwo tests use the same DB row or static fieldIsolate data per test, reset state
Order dependenceTest B passes only if test A ran firstMake each test self-contained, randomise order
Real clock / randomnessFails at midnight or on random valueInject a fixed clock and seeded random
External networkCalls a real API that is sometimes downStub it, or use a local container
Resource pressureFine alone, times out when CI is busyFix timeouts, reduce parallel load

The process I would run. (1) Detect: track pass/fail history per test, so "failed 4 of the last 50 runs on the same commit" is visible. (2) Quarantine: move it to a non-blocking job so others are not stopped, but keep running it and keep it visible. (3) Own: create a ticket with a named owner and a deadline. (4) Reproduce: loop it 200 times, in random order, under CPU stress, in the CI container. (5) Fix the root cause. (6) Return it to the blocking suite.

Do not simply delete it or add retries: a flaky test can be the only thing exposing a genuine race condition in the product code. Automatic retries are acceptable as a short-term stopgap if they are counted and reported.

Typical causes: fixed sleeps and unawaited async work, shared state between tests (database rows, static variables, files), test-order dependence, real clocks and time zones, unseeded random data, real network calls, and a busy CI machine. Quarantine means moving the test to a separate non-blocking job, not deleting it: it may be a real race condition in the product code. Fixes: wait on a condition instead of sleeping, isolate data per test, inject a fake clock, mock the network. To reproduce, run it in a loop, in random order, under CPU load, inside the CI container. Automatic retry is only a stopgap, and retried tests must be reported so the flakiness stays visible.

Remember: quarantine, own, fix the root cause. Never normalise "just re-run".

3. Deployment strategies

What is the difference between deploying and releasing? Intermediate

Deploying means putting a new version of the code on production machines. Releasing means making a feature available to users. They do not have to happen together: with feature flags I deploy code switched off, check it is healthy, then turn it on for staff, then 1 percent, then everyone, without another deployment.

Why separate them. Traditionally "deploy" and "release" were the same event: copy the new code to the servers and users instantly get the new behaviour. That makes every deployment a high-stakes moment, so teams deploy rarely and in big batches, which makes problems bigger. If you can ship code that is invisible to users, deployment becomes routine.

Example timeline of one feature (new checkout page):

  1. Monday: code merged and deployed, behind a flag new-checkout that is off. No user sees any change. This is a deployment, not a release.
  2. Tuesday: flag on for employees only. Real production data, real infrastructure, zero customer risk.
  3. Wednesday: flag on for 1 percent of customers. Watch errors and conversion.
  4. Thursday: 25 percent, then 100 percent. That is the release. If a metric drops, flip the flag off in seconds with no redeploy.

Who benefits. Engineers can deploy many times a day without waiting for a launch date. Product or marketing decide the release moment (for example a sale at 09:00) without needing engineers to run a deployment at that minute. Incidents become easier: "turn the flag off" is faster and safer than "redeploy the old version".

Limits. Not every change can sit behind a flag, for example a library upgrade, a schema change or a framework migration. Those still need safe deployment strategies (rolling, canary) and compatible database steps. Flags also add code paths that must be tested and later removed.

This lowers risk twice. A deployment becomes a boring technical event because nothing visible changes, and a release becomes a configuration change I can undo in seconds. It also decouples teams: engineering can deploy daily while product decides when users see the feature.

Remember: deploy = code is on servers; release = users can see it.

How does a rolling deployment work, and what are its trade-offs? Basic

A rolling deployment replaces old instances with new ones a few at a time: start a new instance, wait until it is healthy, send it traffic, stop an old one, repeat. The service is never fully down and I need little extra capacity. The cost is that old and new versions serve traffic together, and rollback is another rolling update, so it is not instant.

What problem it solves. The simplest way to deploy is to stop all old instances and start new ones (called "recreate"), which means downtime. A rolling update keeps the service up by changing the fleet in small waves, so some instances are always serving.

Walk-through with 4 instances, maxSurge: 1, maxUnavailable: 0:

  1. Start a 5th pod running v2 (surge allowed one extra).
  2. Wait until its readiness probe passes, then the load balancer sends it traffic.
  3. Only now terminate one v1 pod (gracefully: stop new requests, finish in-flight ones). Back to 4 pods, 1 of them v2.
  4. Repeat: 2 of 4, 3 of 4, 4 of 4 on v2.

With maxUnavailable: 0 capacity never drops below 4. With maxUnavailable: 1 and maxSurge: 0 it needs no extra pods but runs at 75 percent capacity briefly. That is the tuning: spend extra resources, or accept reduced capacity.

The hidden requirement. While the rollout runs, a user can hit v1 on one request and v2 on the next. So v1 and v2 must both work against the same database schema, the same message formats and the same cache entries. For example, if v2 writes a new JSON field into Redis that v1 cannot parse, v1 pods crash during the rollout. Design for this: add before you remove (see expand and contract).

When to choose it. Default for stateless services where a short mix of versions is fine and you want low cost. Avoid it when versions truly cannot coexist (use recreate) or when you want the exact same traffic on both for comparison (use canary).

Pitfall. A rollout that is "successful" only means pods became ready, not that the business works. Without real readiness probes and monitoring, a broken version can finish the rollout before anyone notices. If it stalls, kubectl rollout undo returns to the previous revision, but that is itself another rolling update.

Kubernetes does this by default for a Deployment. maxSurge is how many extra pods may exist, and maxUnavailable is how many may be missing (setting it to 0 keeps full capacity). Because two versions coexist, they must work with the same database schema and the same message formats. If the new version is broken in a way health checks do not catch, it slowly takes over before anyone notices.

strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 25%
    maxUnavailable: 0   # never drop below desired capacity

Remember: rolling = no downtime, cheap, but mixed versions and slow rollback.

What health checks should a service expose so deployments are safe? Intermediate

Mainly a readiness check, which tells the platform "I can take traffic right now", and a liveness check, which says "I am stuck, restart me". Rolling updates and canaries wait on readiness before sending users to a new instance, so an honest readiness check is what keeps a deploy from serving errors.

Why health checks matter in delivery. The deployment tool needs a signal to know when a new instance is safe to use. Without it the platform assumes "process started" equals "ready", and sends real users to an app that is still loading caches or cannot reach its database. A good health check is what lets a rolling or canary release pause itself when something is wrong.

ProbeQuestion it answersIf it fails
StartupHas the app finished starting yet?Keeps waiting up to a limit, then restarts; other probes are held back
ReadinessCan it take traffic right now?Removed from the load balancer, not restarted
LivenessIs it hopelessly stuck?Container is killed and restarted

Design rules. Readiness should reflect "can I serve a request now?": config loaded, connection pool created, essential dependency reachable. Liveness should be cheap and local ("my event loop still responds"). If liveness calls the database and the database has a 30-second blip, every pod fails liveness, all restart together and the outage grows into a restart storm.

Graceful shutdown completes the picture. On the stop signal (SIGTERM) the app should fail readiness first, so the load balancer drains it, finish in-flight requests, close connections, then exit within the grace period. Otherwise each rolling update drops a few requests.

Kubernetes has three probes. Readiness failing means stop sending requests, but do not restart. Liveness failing means restart. Startup gives slow-starting apps time before the others begin. A good readiness check confirms the app really can work (config loaded, main dependencies reachable in a light way). Do not make liveness depend on downstream services, or one database blip restarts every pod and makes the outage worse. Also support graceful shutdown: on a termination signal, stop being ready, finish in-flight requests, then exit.

Remember: readiness gates traffic, liveness triggers restarts, and liveness must not depend on other services.

What is a blue-green deployment, and what are its pros and cons? Intermediate

I keep two full production environments. Blue is live; I deploy the new version to idle green, test it fully there, then flip the router so all traffic goes to green at once. Blue stays up untouched, so if something is wrong I flip back and rollback is nearly instant. The price is double capacity during the switch, and the shared database.

Core idea. Instead of changing the running system, build a second identical one next to it. "Blue" is what users use now. "Green" is the new version, deployed and tested while receiving no user traffic. The release is one small action: repoint the load balancer or DNS from blue to green. Because the switch is tiny, so is the rollback: point back at blue, which was never touched.

Step by step:

  1. Deploy v2 to green with production configuration, but no users.
  2. Run smoke tests and even a copy of real traffic against green. This rehearses the real environment.
  3. Flip the router. All users now hit v2, with no mixed versions visible.
  4. Watch metrics for a soak period (say 30 minutes to a day). Blue stays running, ready as the escape hatch.
  5. When confident, scale blue down (or reuse it as the next green).
AdvantageCost or catch
Instant switch and rollbackRoughly double the infrastructure while both exist
No two versions serving users at onceAll-or-nothing: if v2 has a subtle bug, 100 percent of users meet it before you notice
Full rehearsal on real infrastructureShared database means schema must be compatible with both

The database catch in detail. If v2 needs a column to be renamed and you do it in the shared database, blue (v1) breaks immediately and rollback no longer works. So blue-green still needs backward-compatible schema steps. Also think about in-flight work: sessions, long requests and queue messages being processed by blue at the moment of the switch (connection draining), and caches warmed in blue but cold in green.

Choose it when you need a fast, clean cut-over and rollback and can afford temporary double capacity (cheap in the cloud). Choose a canary instead when you want to expose only a few users first.

Pros: no mixed versions serving users, instant rollback, and a realistic rehearsal. Cons: both environments usually share one database, so schema changes must work with both versions (see expand and contract below). Long-lived sessions and in-flight work need care at the switch. It is also all-or-nothing, so it gives less gradual risk control than a canary. To reduce the double cost, keep green only during the release and scale the old environment down after the soak period.

Remember: blue-green = instant switch and instant rollback, paid for with double capacity.

What is a canary release, and how do you decide to promote or abort it? Intermediate

I send a small slice of real traffic, say 1 to 5 percent, to the new version while everyone else stays on the old one, and compare the two on error rate, latency and business metrics. If the canary is as healthy as the baseline I raise the share in steps (5, 25, 50, 100). If a metric breaches a threshold I route everything back, and only a few users were affected.

Name and idea. Coal miners carried a canary: if the bird got sick, the miners knew to leave before they were harmed. A canary release exposes a tiny share of real users to the new version so that if it is bad, only they are affected, and you find out from numbers rather than complaints.

A typical progression with decision rules:

  1. Deploy v2 to one or two instances; route 1 percent of traffic there. Hold for 10 minutes.
  2. Compare canary and stable at the same time on: HTTP 5xx rate, p95 and p99 latency, CPU and memory, and one business metric (checkout success, messages processed).
  3. Rule example: abort if canary 5xx rate exceeds stable by more than 0.5 percentage points, or p99 latency is more than 20 percent higher, for 5 minutes. Otherwise step to 5, 25, 50, 100 percent.
  4. On abort, set the canary weight to 0 and keep it for debugging.

Why compare against stable instead of a fixed number. Traffic naturally changes by hour, so "error rate under 1 percent" may be normal at noon and abnormal at 3 a.m. Comparing two groups under the same conditions removes that noise.

What makes it hard. You need enough traffic for statistics (at 1 percent of 100 requests per hour you learn nothing, so use longer holds or synthetic traffic); you need per-version metrics (label metrics with the version); and slow-burn problems such as memory leaks only appear later. Stateful effects matter too: a user bouncing between versions can see inconsistent behaviour, so use sticky routing by user id when that matters. Because two versions run together, the same compatibility rules as rolling updates apply.

Tools: Argo Rollouts, Flagger, service-mesh traffic splitting, or a load balancer with weighted targets. Canary on the infrastructure level (a share of instances) is different from a flag-based gradual rollout (a share of users), and many teams use both.

The skill is choosing the right metrics and waiting long enough to see rare problems. Compare canary against stable at the same time, not against yesterday. Tools such as Argo Rollouts, Flagger or a service mesh can automate the analysis and promotion. Trade-offs: more moving parts, you need good monitoring, and two versions run at once so compatibility rules apply. A low-traffic service may not produce enough data to compare, so use a longer soak or synthetic requests. Assigning users randomly is simple; sticky by user avoids one person bouncing between versions.

How to read this diagram. Users send requests to the router. The router splits them by weight: most go to the stable version 1 (top arrow) and a small share goes to the canary version 2 (bottom, moving green arrow). Both versions report errors and latency to the metrics box (dashed arrows), which compares them side by side. If the canary looks healthy, you raise its share step by step; if not, you send it back to 0 percent.

Remember: canary = small real traffic, decided by metrics, tiny blast radius.

Compare rolling, blue-green, canary and recreate. When would you use each? Senior

Recreate for simple things that tolerate downtime, rolling as the default for normal stateless services, blue-green when I need an instant switch and rollback, canary when the service is high-traffic and a bad release is expensive. I choose by asking: how bad is a failed release, how fast can I detect it, can two versions coexist, and how much spare capacity do I have?

How to explain the choice. I do not pick a favourite. I ask four questions about the change and the service:

  1. Can two versions run at the same time? If not (a breaking protocol change, a job that must not run twice), only recreate or a carefully coordinated blue-green fits.
  2. How costly is a bad release? Payment or login: use canary or blue-green. An internal report tool: rolling or recreate is enough.
  3. How quickly can I tell it is bad? Good metrics and traffic make canary automatic. Poor monitoring means any strategy only delays discovery.
  4. What capacity can I spare? Blue-green needs about double. Rolling needs little. Recreate needs none but accepts downtime.

Small examples. A nightly batch job: recreate (nobody is waiting). A stateless REST service with ten pods: rolling by default. A checkout service on Black Friday week: blue-green or canary plus a flag for the risky part. A high-traffic API with strong dashboards: automated canary.

They stack. A common mature setup: rolling mechanics inside a canary (the canary is a few pods, the rest follows by rolling) plus feature flags for user-visible parts plus expand and contract for the database. The strategy handles how code reaches servers; flags handle who sees it; migration discipline handles whether rollback is still possible.

Common interview trap. Saying "canary is always best". It costs tooling, monitoring and time. For a low-risk service it is over-engineering, and a rolling update with good probes is the right answer.

How do feature flags work in a delivery pipeline, and what are the risks? Intermediate

A feature flag is a runtime switch in the code: if (flags.isOn("new-checkout", user)) newFlow(); else oldFlow();. The value comes from a flag service or config, so I can change behaviour without deploying. They let unfinished work merge to main safely, enable gradual rollouts and targeting, and give an instant kill switch.

What a flag is. A line of code that asks "is this on for this user?" at run time, with the answer coming from configuration that can change without redeploying. It turns a risky release into something like a light switch.

if (flags.isEnabled("new-checkout", user)) {
    return newCheckout.handle(cart);   // new path
}
return oldCheckout.handle(cart);        // old path stays until the flag is removed

Four kinds, with different lifetimes (a useful senior distinction):

TypePurposeLifetime
Release flagHide unfinished work, gradual rolloutDays to weeks, then delete
Experiment flagA/B test variantsUntil the experiment ends
Ops flag (kill switch)Turn off an expensive or risky feature under loadLong-lived, intentionally
Permission flagPlans, entitlements, beta customersLong-lived

How a rollout works. The flag service stores a rule such as "on for staff, plus 10 percent of users by hash of user id". Hashing the user id gives a stable choice, so the same user always gets the same experience. The app keeps the rules in memory and refreshes them, so a flag service outage does not take down requests: it falls back to the last known value or a safe default.

Risks and discipline. Each flag doubles the paths to test (old and new), and with ten flags the combinations explode, so keep them independent. Flags that are never removed become "flag debt": nobody dares delete the old path. Give every flag an owner and an expiry date and add a cleanup ticket when it is created. Never put secrets in client-side flag payloads, and audit who changes production flags, since a flag change is a production change.

Uses: dark launches, percentage rollouts, staff-first or per-region targeting, A/B experiments. Risks: every flag doubles the code paths to test; stale flags pile up as hidden behaviour ("flag debt"); a flag service outage must fall back to a safe default; and flag logic evaluated on the client can leak. Good practice: give each flag an owner and an expiry date, remove it after rollout, and keep defaults safe. Flags also help database migrations by controlling which code path reads or writes.

Remember: flags separate deploy from release, but every flag must be removed when its job is done.

How do you roll back a bad release? Rollback versus roll forward? Senior

I restore users first with the fastest, lowest-risk move: flag off, canary to 0 percent, router back to blue, or redeploy the previous artifact. Rollback works when the old version still works with the current data. When the release changed shared state, such as a destructive migration, I roll forward with a quick fix instead.

The goal in an incident is to stop user pain, not to find the bug. Rollback and roll forward are two ways to get there. The skill is knowing which is safe.

Rollback means returning to the last good version. It is fast and needs no new thinking, but only works if the old code still understands the current state. Roll forward means shipping a new fix on top. It is the right move when the bug is trivial and well understood, or when going back is impossible.

Decision walk-through:

  1. Is the change behind a flag? Turn the flag off (seconds).
  2. Is it a canary? Set its weight to zero.
  3. Did the release change data irreversibly (dropped a column, rewrote values, sent messages in a new format that old code cannot read)? If yes, rolling back would fail or corrupt, so roll forward.
  4. Otherwise redeploy the previous artifact.

Why "rollback is safe" is often untrue. Example: release 42 renamed a column and migrated the data. Old code (release 41) reads the old column, which no longer exists. Rolling back makes things worse. This is exactly why migrations are split into backward-compatible steps: they keep rollback available.

Prepare before you need it: keep previous artifacts in the registry; make deploy a one-command or one-click pipeline run; rehearse rollback in staging; define triggers up front ("error rate over 2 percent for 5 minutes, roll back"); write the git revert approach down. On git, use git revert to add a new commit that undoes the change instead of rewriting shared history.

Follow-up the interviewer may ask: "what about messages already in Kafka?" Consumers on the old version must tolerate messages written by the new one, so event formats evolve additively too.

What makes rollback easy: old artifacts stay available, deploys are repeatable and one-click, schema changes are backward compatible, and the procedure is rehearsed. Decide the trigger in advance (for example error rate above X for Y minutes) so nobody debates it mid-incident. In git terms, revert the merge commit (a new commit that undoes the change) and let the pipeline redeploy, rather than rewriting main. Roll forward is better when the bug is small and well understood, or when rollback is unsafe because of data changes.

kubectl rollout undo deployment/orders      # previous revision
kubectl rollout status deployment/orders    # watch it complete
Watch out: a rollback plan never tested, assuming "undo" is safe after a destructive migration, and debugging live before service is restored.

Remember: restore service first; roll back if the data allows, roll forward if it does not.

What is GitOps, and how is it different from a pipeline pushing to the cluster? Senior

GitOps keeps the desired state of the environment (Kubernetes manifests, Helm values, image versions) in a git repository, and an agent inside the cluster (Argo CD or Flux) continuously pulls that repo and makes the cluster match it. A deploy is therefore a merged commit, and a rollback is a git revert. CI builds and publishes the image; it does not need credentials to the cluster.

The two models. In a classic push pipeline, the CI job holds cluster credentials and runs kubectl apply or helm upgrade. In a pull (GitOps) model, an in-cluster controller watches the repository and reconciles. Reconciliation means: compare desired state (git) with actual state (cluster) and fix any difference, over and over.

  1. CI builds orders:9f3c2ab, pushes it to the registry, and opens a commit or pull request that changes the image tag in the environment repo.
  2. The change is reviewed and merged. Git now says "production runs 9f3c2ab".
  3. The controller sees the new commit, applies it, and reports sync and health status.
  4. If someone edits the cluster by hand (drift), the controller reverts it or alerts, so the repo stays the truth.
BenefitCost or catch
Audit trail and review: every change is a commitTwo repositories to manage (app code and environment config)
Rollback is revert; recreate a cluster from gitSecrets cannot sit in plain git: need sealed or external secret tooling
CI no longer holds production cluster credentialsProgressive delivery and database migrations still need extra design

Pitfall. Git rollback restores configuration, not data, so the expand and contract rules still apply.

Remember: in GitOps, git is the source of truth and a controller in the cluster pulls and reconciles. Deploy = merge a commit.

How do you know a deployment actually worked, beyond "the pods are running"? Intermediate

A finished rollout only proves the new instances started and passed their probes. To know the release is good, I run automated smoke tests against it right after deploy, then watch the key health signals (error rate, latency, saturation, one business metric) for a soak period, comparing against the previous version. Failing any of those triggers an automatic abort or rollback.

Three layers of verification:

  1. Technical readiness: the platform confirms instances are ready (readiness probes, rollout status).
  2. Smoke tests: a handful of fast synthetic checks run against the real deployed service: the health endpoint reports the right version, login works, one read and one write through the real database succeed. They take under a minute and answer "is it basically alive and wired up?". Keep them non-destructive or use test accounts.
  3. Observation window: compare golden signals (errors, latency, traffic, saturation) for the new version with the old for some minutes or hours, plus a business metric such as orders per minute. A slow memory leak or a bug that affects only one customer type will show here and not in smoke tests.

Make it automatic. Encode thresholds in the pipeline or in a progressive-delivery tool ("abort if 5xx more than 1 percent for 5 minutes"). Expose the running version in a /version endpoint and in metrics labels, so you can tell which version a graph line belongs to. Annotate dashboards with deploy markers so a change in a graph lines up with the deploy time.

Pitfall. Smoke tests that call only the health endpoint prove nothing about business functions. Another one: "success" declared the moment the rollout finishes, while errors only appear when the next traffic peak arrives.

Remember: ready is not the same as good. Smoke test, then watch real metrics, with automatic abort.

4. Database changes, secrets and scanning

How do you change a database schema without downtime and without breaking rollback? Senior

I use expand and contract (also called parallel change): split the change over several releases so that every step works with both the old and the new application code. Add the new thing first, move code over, and drop the old thing last, in a later release. Rollback stays safe until that final destructive step.

The underlying problem. Code and database cannot change at the same instant. A rolling update runs old and new app versions together against one database, and a rollback runs old code against a database that already moved on. So every schema state must be readable by both the current and the previous version of the code. A single step "rename column and deploy code" breaks one of the two groups for a while.

Full example: rename users.name to users.full_name over four releases.

ReleaseSchemaCodeSafe to roll back?
1 ExpandAdd nullable full_nameUnchangedYes
2 Dual writeSameWrites both columns, reads nameYes
3 Backfill and switchCopy old rows in batchesReads full_name, still writes bothYes
4 ContractDrop nameWrites only full_nameNo (this is the point of no return)

Backfill details. Update in batches of, say, 5,000 rows with a short pause, so you do not hold long locks or create replication lag, and so it can resume after a failure. New writes during the backfill are covered by dual write.

-- release 1 (expand)
ALTER TABLE users ADD COLUMN full_name VARCHAR(200);
-- release 3 (batched backfill, repeat until 0 rows)
UPDATE users SET full_name = name WHERE full_name IS NULL AND id BETWEEN ? AND ?;
-- release 4 (contract), weeks later
ALTER TABLE users DROP COLUMN name;

Other cases follow the same idea. Adding a NOT NULL column: add nullable, backfill, then add the constraint. Splitting a table: create the new one, write to both, copy, switch reads, remove the old one. Index creation on big tables: use a non-blocking form where the database supports it (for example PostgreSQL's concurrent index build).

Tooling and ordering. Migrations run as a versioned pipeline step with Flyway or Liquibase before the new code receives traffic. The "contract" step belongs to a later release, after the rollback window is closed. The cost is more releases and temporary duplicate data, which is the price of zero downtime.

Why it is needed: during a rolling or canary release old and new code run together against one database, and after a rollback the old code meets the new schema. Example, renaming name to full_name: (1) add the new nullable column, no code change; (2) deploy code that writes both columns and still reads the old one; (3) backfill old rows in small batches (one huge update holds locks and causes replication lag), then deploy code that reads the new column; (4) once nothing uses the old column and the rollback window has passed, drop it. Adding a NOT NULL column to a big table: add it nullable, backfill, then add the constraint, since a table rewrite can lock the table. Run migrations as a pipeline step (Flyway or Liquibase) before the new code starts, so the schema is always ahead of the code.

Remember: never rename or drop in the release that stops using the old name. Expand first, contract last.

How should secrets be handled in CI/CD? Intermediate

Secrets never go in the repository, the image, or plain pipeline config. They live in a secret store (the CI tool's encrypted secrets or a vault or cloud secret manager) and are injected at run time, scoped to the job that needs them, and rotated. Wherever possible I avoid long-lived keys entirely and use short-lived credentials.

The threat. A CI system holds the keys to production: it can deploy, read registries and often touch cloud accounts. So attackers target it, and mistakes (a printed variable, a build run on a malicious pull request) leak secrets easily. Everything below is about keeping a secret out of places where it persists or can be copied.

Layers of defence:

  1. Never store in git or images. Git history is forever, and image layers keep every file ever added, even if a later layer deletes it.
  2. Central secret store (CI encrypted secrets, Vault, a cloud secret manager) and inject at run time as environment variables or mounted files, only for the jobs that need them.
  3. Prefer no long-lived secret at all. With OIDC federation the job presents a signed identity token ("I am workflow X of repo Y on branch main"), the cloud trusts that issuer, and returns credentials that expire in about an hour. Nothing durable exists to steal.
  4. Least privilege and separation: the build job cannot deploy, the deploy job cannot read other teams' secrets, production credentials only for protected branches or approved environments.
  5. Untrusted code gets nothing: pull requests from forks should run without secrets, because their author controls the code that would read them.
  6. Detect and rotate: secret scanning on commits and logs, regular rotation, and immediate revocation on any exposure.

How to read this diagram. Follow the arrows left to right. (1) The CI job asks the CI identity provider for a signed token that says which repository and branch it is. (2) The job sends that token to the cloud provider. (3) The cloud provider checks its trust rule and, if the repository and branch are allowed, returns short-lived credentials (moving green arrow) that the job uses to deploy. No long-lived key is stored anywhere.

Why masking is not enough. CI tools replace the exact secret string with asterisks in logs. If the value is base64-encoded, split across two lines, or printed by a tool in another form, it escapes. Treat masking as a seat belt, not a lock.

The strongest pattern is OIDC (OpenID Connect) federation: the CI job proves its identity to the cloud provider and receives a token that expires in minutes, so there is no stored cloud key to steal. Other rules: least privilege (a deploy job gets only deploy rights), separate secrets per environment, protect production secrets behind approvals or protected branches, and never expose secrets to untrusted code, such as pipelines triggered by pull requests from forks. Add secret scanning (for example in pre-commit and in CI) to catch keys committed by mistake. Log masking helps but is not a defence: encoded or split values slip past it.

Watch out: printing the environment for debugging, passing secrets as command arguments (visible in process lists), and baking them into Docker layers, which stay in image history.

Remember: inject at run time, least privilege, prefer short-lived tokens, and rotate anything that leaks.

What are SAST, SCA, DAST and secret scanning, and where do they fit in a pipeline? Intermediate

SAST reads my source code for insecure patterns, SCA checks my dependencies for known vulnerabilities (CVEs), secret scanning looks for committed keys, and DAST attacks a running copy of the app from outside. The first three run early on every pull request because they are fast, and DAST runs against a deployed test environment.

Four different questions. It helps to remember what each tool looks at:

This is why you need a pipeline you can run for all services quickly.

Supply-chain note. The pipeline itself is a target: pin third-party actions or plugins to a commit SHA rather than a moving tag, and verify what you download.

Make them useful, not noisy: fail the build only on high-severity findings that are fixable, track the rest as tickets, and give a way to suppress a false positive with a reason and an expiry. Also scan container images for OS-package CVEs. For a new critical CVE in a dependency, the steps are: find which services use it (an SBOM, a list of components, helps), upgrade or patch, redeploy through the normal pipeline, and use a temporary mitigation if no fix exists yet. Pin dependency versions and reference third-party pipeline actions by commit SHA, since the pipeline itself is part of your supply chain.

Remember: SAST = my code, SCA = my libraries, DAST = the running app. Fail on severity, not on noise.

5. Branching, tools and metrics

What is trunk-based development, and why do high-performing teams use it? Intermediate

In trunk-based development everyone merges to one main branch (the trunk) in small changes, at least daily, using very short-lived branches. Unfinished work hides behind feature flags. It keeps integration continuous, so merges stay small, conflicts are rare, and main is always releasable.

What it means in practice. There is one long-lived branch, main (the trunk). Developers either commit straight to it or use branches that live hours, at most a day or two. They do not keep a private branch for a two-week feature. Anything not ready for users merges anyway but hidden behind a flag, or built in small steps that are harmless until the last one.

Why it helps. The cost of merging grows with the size and age of the divergence, roughly in a non-linear way. Merging 50 lines written yesterday is trivial. Merging 5,000 lines written over a month involves conflicts, semantic breakage and a risky "big bang". Trunk-based development keeps each integration small, so problems appear while the author still remembers the context. It also means main is the single source of truth about what will ship.

Techniques that make it possible:

  • Feature flags for unfinished or risky features.
  • Branch by abstraction: to replace a component, introduce an interface, switch callers gradually, then delete the old one, all on main.
  • Small pull requests with fast review (a team agreement to review within hours).
  • Required checks and a merge queue: the queue re-tests each PR on top of the latest main, so two PRs that are individually green cannot combine into a broken main.

What it demands. Reliable fast tests (otherwise people avoid merging), a culture where a red main is fixed first, and good flag hygiene. For a team without tests, trunk-based development is risky until that safety net exists.

Releases. Deploy from main continuously, or tag a commit as a release. When you must support old versions, cut a short-lived release branch and cherry-pick fixes (fix on main first).

It needs discipline and support: a fast, trusted test suite, required pull-request checks, small changes, and flags for incomplete features. Branch protection (required reviews and green checks) keeps main safe. For a busy repo, a merge queue tests each change on top of the latest main before merging, so two individually green changes cannot combine into a red main. Research (the DORA reports) links this style with better delivery performance, mostly because long-lived branches delay feedback.

Remember: small, frequent merges to main, with flags hiding unfinished work.

Trunk-based development versus Git Flow: which would you choose? Intermediate

For a service that is deployed continuously I choose trunk-based development. Git Flow, with long-lived develop and main plus release and hotfix branches, fits software shipped in numbered versions that need parallel support, such as installed products, mobile apps or libraries. For those I use trunk plus short release branches cut only when needed.

What Git Flow is. A branching model with two permanent branches: main holds released code, develop holds the next release being assembled. Features branch from develop. When develop is ready, a release branch stabilises it, merges into main and gets a version tag. Urgent production fixes use hotfix branches from main, merged back into both.

Where it made sense. When software was shipped as numbered versions every few months (installers, desktop apps, on-premise products, libraries) and several versions were supported in parallel, the explicit release and hotfix branches matched reality.

Why it is a poor fit for continuous deployment. Code merged to develop is not deployed until a release is cut, so feedback is delayed. Develop and main diverge, hotfixes must be merged in two places (easy to forget), and large merges bring conflicts. You also test one thing (develop) and ship another (the merged release).

The practical middle path. Use trunk-based development; when you need to maintain a released version (say 3.2 for a customer), branch release/3.2 from the tag, apply fixes to main first, then cherry-pick to the release branch. That gives support for old versions without a permanent develop branch.

How to answer. State the dependency: "what do I deploy, and how many versions must I support at once?" One live version means trunk. Many supported versions means release branches.

Git Flow's cost is long-lived branches that diverge, painful merges, and a gap between "merged" and "released" that delays feedback. A release branch in the lighter model works like this: fix on main first, then cherry-pick the fix back to the release branch, so fixes never get lost. GitHub Flow (feature branch, pull request, merge to main, deploy) sits in between and suits most teams. In an interview, name the trade-off, not a winner: the more code that lives outside main, the less continuous the integration is.

Remember: trunk for continuous deployment, release branches only when you must support several versions.

Jenkins versus GitHub Actions versus GitLab CI: how do you choose, and what is "pipeline as code"? Intermediate

They all do the same job: run a pipeline defined in a file in the repository. I choose mostly by where the code lives and who runs the platform: GitHub Actions or GitLab CI when the code is already there and I want managed runners, Jenkins when there is existing investment or a need for heavy customisation. The concepts transfer, so I learn the model, not the syntax.

What they have in common. All three follow the same model: an event (push, pull request, schedule) triggers a pipeline made of jobs (sometimes grouped in stages) that run on runners or agents, produce logs, artifacts and a pass or fail result. Learn that model once and any tool is just different syntax.

Pipeline as code, from scratch. Early CI servers were configured by clicking in a web UI. The configuration lived on the server: not versioned, not reviewed, lost with the server, and one shared setup for all branches. Putting the definition in a file in the repository fixes all of that. It is reviewed in pull requests, has history ("who changed the deploy step and why"), is branch-specific (an old release branch rebuilds with its old pipeline), and can be recreated from scratch.

Scaling it. With dozens of repositories, copy-pasted pipelines drift apart. Use shared libraries (Jenkins), reusable workflows and composite actions (GitHub), or includes and templates (GitLab) so a fix is made once. Keep logic in versioned scripts (a make target or shell script) that run the same locally and in CI, so the CI file stays thin and debugging does not need a pipeline run.

Pitfall. A pipeline change can break everyone, so test it on a branch, and treat third-party actions and plugins as supply-chain dependencies.

"Pipeline as code" means the pipeline is a text file in the same repo (Jenkinsfile, .github/workflows/*.yml, .gitlab-ci.yml). It is versioned, reviewed in pull requests, and branches with the code, so an old release branch builds with its old pipeline. A pipeline clicked together in a UI is hidden, unreviewable and lost when the server dies. Jenkins is flexible but you maintain the controller, agents and plugins; hosted tools trade flexibility for less upkeep. To avoid copying pipelines across 50 repos, use shared libraries (Jenkins), reusable workflows (GitHub) or templates and includes (GitLab). Because a mistake in the file breaks everyone's builds, test pipeline changes on a branch.

Remember: same ideas in every tool: pipeline lives in the repo, runs on runners, is reviewed like code.

What are the DORA metrics, and what do they tell you? Intermediate

Four metrics measure delivery health: deployment frequency, lead time for changes (commit to production), change failure rate, and time to restore service. The first two measure speed, the last two measure stability, and the research shows strong teams are good at both together, not trading one for the other.

Why measure delivery at all. Without numbers, discussions about "being faster" or "being more careful" are opinions. DORA (DevOps Research and Assessment) studied thousands of teams and found four measures that predict both delivery performance and organisational outcomes.

MetricPlain meaningHow to measureDimension
Deployment frequencyHow often we ship to productionCount of production deploys per day or weekSpeed
Lead time for changesTime from commit to running in productionMedian of (deploy time minus first commit time)Speed
Change failure rateShare of deploys that cause a failure needing a fix or rollbackFailed deploys divided by total deploysStability
Time to restore serviceHow fast we recover from a production failureMedian of incident start to recoveryStability

Example reading. A team deploys monthly, has a lead time of 3 weeks and a 30 percent change failure rate. Why? Big batches make each deploy risky, so they deploy less, which makes batches bigger. The cure is smaller changes, better automated tests and flags, which should raise frequency and lower failure rate together. The key finding of the research is that speed and stability are not opposed: good teams are better at both.

Using them well. Measure at team or service level, track trends rather than ranks, and pair them with context. Define terms before you count (what is a "failure", when does lead time start?). Do not use them as individual targets or compare teams with different products, because people will game the numbers: deploy empty changes to raise frequency, or avoid reporting incidents to lower failure rate.

Connection to the pipeline: slow tests and manual approvals lengthen lead time; flaky tests and thin coverage raise failure rate; poor rollback and monitoring lengthen restore time. Recent DORA reports also discuss a fifth measure, rework rate, so state that definitions evolve.

They tell you where the pipeline hurts: long lead time points to slow tests, queues or manual approvals; high failure rate points to weak tests or large batches; slow recovery points to poor rollback or monitoring. Use them as team-level diagnostics. They are misused when turned into individual targets, because people then game them (splitting deploys into trivial ones, hiding failures). Newer reports also track rework rate, so check the current definition if asked.

Remember: frequency and lead time = speed; failure rate and restore time = stability. Measure teams, not people.

6. Real-life scenarios

Every answer follows the same shape: situation, what you check first, steps, and how you prevent it next time. Saying this shape aloud shows you stay calm under pressure.

The main branch build is red and ten people are blocked. What do you do? Senior

Restore green first, investigate second. I tell the team to hold merges, find the commit that broke it, and revert it within minutes. The author re-lands a corrected version later. Nobody should be debugging forward for an hour while ten people wait.

Why this is treated as an emergency. A red main breaks the shared promise of CI: "main is always safe to build on and release". While it is red, nobody can merge with confidence, every new pull request shows failures that may not be theirs, and a hotfix could not ship. Ten blocked people at one hour each is a day and a quarter of lost work, so a five-minute revert is almost always the cheapest option.

Worked example. At 11:02 main turns red with NoSuchMethodError in the order module. Looking at the history: the last green commit is a1, the first red is a4; a2 and a3 are in between. A bisect or a read of the diffs shows a3 removed a method that a4 (from a different author, merged moments later) still calls. Each PR was green on its own base, but the two together are broken. The owner reverts a3 through a PR, merges it on a fast path, main goes green at 11:12, and the authors re-land a combined fix with a test.

What that example teaches. The real cause was two individually green changes combining, which a merge queue (re-test each PR on top of the latest main before merging) prevents. Also decide the "who owns this" rule in advance: the author of the breaking commit leads the fix, with a named backup.

Do not disable the failing test just to get green without a ticket and owner, and do not leave a red build "for later": people learn to ignore it, which is how real failures get missed.

Situation: the latest builds on main fail and new pull requests cannot merge.

Check first: is it a real code break, a flaky test, or infrastructure (registry outage, expired credential, full disk)? Compare the last green commit with the first red one, read the first error in the log, and see who merged in between.

  1. Announce "main is red, investigating, hold merges" and name one owner, so five people do not fix it at once.
  2. If a commit caused it, revert it through a pull request (git revert SHA). Fix forward only when the fix is obvious and takes minutes.
  3. If it is infrastructure, fix or work around it. If it is a flaky test, rerun to unblock and quarantine it with a ticket.
  4. Confirm green and announce it.

Prevent: required checks before merge, a merge queue so combined changes are tested together, and a team rule that a red main beats feature work. Hold a short blameless review: why did the checks not catch it before merge?

Remember: revert first, root-cause after. Green main is a team emergency.

A release went out and error rates are climbing. What do you do in the first 15 minutes? Senior

I stop the damage before I understand it. I confirm the release is the cause, then use the fastest safe lever: flag off, canary to 0, router back, or redeploy the previous version. Once users are fine, I investigate with logs and the diff, and write it up.

Mindset for the first 15 minutes. You are an incident responder, not a debugger. The target is "users stop being hurt", and a rollback that takes 3 minutes beats a brilliant fix that takes 40. Understanding comes after mitigation, using the logs and metrics you saved.

A sample timeline:

MinuteAction
0Alert: 5xx rate jumps from 0.2 percent to 8 percent. Open an incident channel, name an incident lead and a communicator.
2Correlate: did the rise start at the deploy marker on the dashboard? Is it all pods or only the new version? Any migration or config in this release?
4Pause the rollout so no more users reach the bad version.
5Apply the lever: it was a canary at 30 percent, so route to 0. (If it had been a full rolling update with a compatible schema, redeploy the previous image.)
9Verify: error rate and latency back to baseline for several minutes.
15Status update to stakeholders, keep the bad version isolated for debugging, create the post-incident review.

When correlation is unclear (errors began before the deploy): do not blame the release by reflex. Check dependencies, traffic spikes and infrastructure, because rolling back an innocent release wastes time and may add risk.

After it is calm. Reproduce in staging, write a regression test, and ask process questions: why did the canary or tests not catch it, was an alert late, was rollback easy? Improve the system, not blame a person.

Situation: metrics turn bad soon after a deploy.

Check first: does the error start exactly at the deploy time? Is it all traffic or one endpoint, one version, one region? Was there a migration or config change in the same release?

  1. Declare the incident and name an owner and a communicator.
  2. Pause any ongoing rollout so more users do not get the bad version.
  3. Pick the lever from the diagram below: rollback if the old version still works with current data, roll forward only if rollback is unsafe (for example a destructive migration).
  4. Verify error rate and latency recover, then communicate status.

Prevent: canary with automatic abort on metrics, flags for risky features, backward-compatible migrations, a tested rollback procedure, and a blameless review.

Remember: mitigate first, diagnose second; the quickest safe lever wins.

A secret shows up in plain text in the CI logs. What do you do? Senior

I treat it as leaked: rotate the secret right away, then clean up. Deleting the log line is not enough, because anyone with read access, or any tool that copied the logs, may already have it.

Why deleting the log is not enough. Build logs are read by many people, indexed by tools, forwarded to log platforms, sometimes cached by notifications and scrapers. Once the value was printed you cannot prove who saw it. The only safe assumption is "compromised", so the main action is to make the secret worthless: rotate it.

Worked example. A deploy job fails and a developer re-runs it with set -x (shell tracing) to debug. The script runs curl -H "Authorization: Bearer $TOKEN" ..., and tracing prints the expanded command, including the token, in plain text. Masking did not trigger because the shell expanded and re-quoted the value. Steps:

  1. Within minutes: revoke the token and issue a new one; update the secret store.
  2. Check the provider's audit log for use of the old token between exposure and revocation (unknown IPs, unusual actions). If misuse is found, escalate to the security team as an incident.
  3. Delete or restrict the build log and any artifacts that contain it; check whether logs were exported elsewhere.
  4. Remove the cause (the set -x) and add a guard: a secret-scan step on logs or a lint rule that forbids tracing near secrets.

Scope of impact decides urgency. A read-only token for a test system is low risk. A cloud admin key in a public repository's log is an emergency. Public or widely visible logs raise the urgency.

Structural fixes. Replace stored keys with OIDC short-lived credentials so a leaked value expires in about an hour anyway; pass secrets through files or environment, not command-line arguments; and keep secret scope narrow so a leak has a small blast radius.

Situation: a token or password is visible in a build log, often because masking did not match (the value was transformed, split, or printed by a debug flag).

Check first: what is the secret, how powerful is it, who can read these logs (public repo or wide access?), and how long has it been there?

  1. Rotate or revoke the secret and update the secret store.
  2. Check the provider's audit logs for use since the exposure.
  3. Delete or restrict the affected logs and artifacts, and find the cause (set -x, printing the environment, a secret in a command argument, a failing tool echoing its config).
  4. Fix the pipeline so it cannot happen again.

Prevent: short-lived OIDC tokens instead of stored keys, secrets scoped to single jobs, secret scanning on logs and commits, no environment dumps, and treating masking as a safety net only.

Remember: a secret that was ever visible is a secret you rotate.

The pipeline has grown from 8 to 45 minutes and developers are complaining. What is your plan? Senior

Measure before changing anything: time per stage, queue time, and the slowest tests. Then fix the biggest bar first with caching, parallel stages, test sharding, and moving slow tests off the pull-request path. I set a target (for example under 10 minutes for the PR check) and track it like a product metric.

Why pipelines creep. Nobody makes a 45-minute pipeline on purpose. It grows by dozens of small additions: one more test suite, a new scanner, a cache that quietly stopped hitting, a runner pool that is too small for the team. Each looks harmless alone. So the fix is as much about visibility and ownership as about technique.

Worked example of the investigation. Pull the last 50 runs and chart stage durations. You may find:

Stage8 min eraNowCause
Queue wait09 minTeam doubled, runner pool did not
Dependency install17 minCache key accidentally includes a timestamp
Integration tests320 minNew tests each boot a full app context and a database
Security scan06 minNew full scan on every PR

Then the plan writes itself: add runners or autoscale, fix the cache key, reuse the app context and database between tests plus shard them, and scan only changed code on PRs with the full scan nightly.

Agree the target and defend it. For example PR feedback under 10 minutes and main under 20. Show the number on a dashboard, alert on regressions, and make "new test over 30 seconds" a review conversation. Developers also need to feel the improvement soon, so deliver the biggest win first (often queue time or cache) and report progress.

Trade-off. Faster runners and more parallelism cost money; compare with the engineering time wasted waiting (a 30-minute wait times 40 developers times several runs per day is far more expensive than a bigger machine).

Check first: is the time in waiting for a runner (queue), in dependency download, in compile, or in tests? Which five tests take the longest? Did a recent change disable the cache?

  1. Fix cache hits and Docker layer order.
  2. Run independent stages in parallel and shard the test suite by duration.
  3. Build only what changed (path filters or affected-module builds).
  4. Run end-to-end and heavy scans on main or nightly, with a fast core on PRs.
  5. Add runners if queueing is the cost, and set stage time budgets with an alert.

Prevent: a pipeline-duration dashboard, a review rule that new slow tests need a justification, and regular pruning of useless tests. Every deleted check needs a replacement elsewhere, not silence.

Remember: measure, then cache, parallelise, shard, skip. Speed without losing coverage.

A critical bug is in production on Friday afternoon and the full pipeline takes 40 minutes. May you skip it? Senior

No, I do not skip the pipeline. A hotfix is exactly when mistakes are most likely. I first mitigate with the fastest safe lever (flag off or rollback), and for the fix I use the normal pipeline, ideally a documented fast path that keeps the critical checks and drops only the slow, low-value ones.

Why the instinct to skip is dangerous. A hotfix is made under pressure, by a tired person, with little review, in a part of the code that is already misbehaving. Those are precisely the conditions where a second mistake is likely. A hotfix that makes things worse turns one incident into two. The pipeline exists for these moments.

First, separate "stop the bleeding" from "ship the fix". Most of the time pain can be removed without any new code: turn off the flag, roll back to the previous version, scale out, or disable the broken path. That takes seconds and relieves the pressure, so the real fix can be made properly. Only if none of these is possible do you need an emergency code change.

The fast but real path. Mature teams define a hotfix pipeline beforehand (so nobody invents it at 16:45 on a Friday):

  1. Branch from the production version tag, not from main if main has unreleased work.
  2. Smallest possible change plus a test that fails before and passes after.
  3. Pipeline runs: build, unit and integration tests, security scan, smoke tests. Long e2e suites may run in parallel after deployment or be limited to relevant journeys.
  4. A second person reviews (a quick pair review is enough).
  5. Canary or staged deploy with someone watching the metrics.
  6. Merge the fix into main so the next release does not reintroduce the bug.

If an exception is truly needed (for example, a full outage and a broken pipeline), do it with explicit approval from a named person, record it, and follow up immediately with a review. Skipping must be a rare, visible decision, not a habit.

Underlying lesson. If the pipeline is so slow that skipping it is tempting, the pipeline is the problem.

Check first: can I stop the pain without new code? A rollback or flag usually takes seconds and buys time to fix properly.

  1. Mitigate users first (rollback, flag off, scale, disable the bad path).
  2. Write the smallest possible fix and a test that reproduces the bug. Keep the change tiny.
  3. Run the pipeline. Many teams have a pre-agreed hotfix pipeline: build, unit and integration tests, security scan, smoke tests, with long end-to-end suites running in parallel after deploy.
  4. Deploy gradually (canary) with someone watching, merge the fix back to main so it is not lost.

Prevent: a pipeline fast enough that skipping is never tempting, rehearsed rollback, and no-deploy-Friday as a team judgement, not a rule that hides slow delivery.

Remember: mitigate with rollback or flag, then ship a small fix through a fast but real pipeline.

A rolling deployment is stuck halfway: new pods keep crashing and the old ones are still up. What do you do? Senior

Users are still served by the old pods, so there is no outage and I have a moment to think. I look at why the new pods fail, then either fix the cause or abort the rollout with a rollback to the previous revision. The rollout is stuck because new pods never become ready, so the platform will not replace more old ones.

Why "stuck" is actually good news. A Kubernetes rolling update only removes an old pod after a new pod is ready (with maxUnavailable: 0). If new pods never become ready, the update simply stops, leaving the old version serving users. The system protected you. Your job is to find out why the new pods are unhealthy.

Triage order (usually 5 minutes):

  1. Is the rollout the cause? kubectl rollout status shows "waiting for 1 old replica to terminate" or "0 of 3 updated replicas available".
  2. Pod state: kubectl get pods shows the status word, which narrows the cause.
  3. Events and logs: describe and logs --previous explain the last crash.

  2. If it is not a quick fix, roll back (rollout undo), then fix on a branch and redeploy.
