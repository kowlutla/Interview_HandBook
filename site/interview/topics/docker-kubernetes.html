Mental model: the 8 ideas everything hangs on

One line: a container is an ordinary Linux process with a private view of the machine. An image is its read-only starting filesystem. Kubernetes is a control loop that keeps comparing "what you declared" with "what is running", and fixes the difference. Helm is a templating and release tool on top.
  1. A container is not a small VM. It is a normal process on the host kernel, isolated by namespaces (what it can see) and cgroups (how much it can use).
  2. An image is layers. Each Dockerfile step adds a read-only layer. A running container adds one thin writable layer, thrown away when the container is removed.
  3. Containers are disposable. Anything that must survive goes to a volume or an external store. Config comes from the environment, not from the image.
  4. Declarative, not imperative. You write YAML that says "3 replicas of this image". Controllers keep working until reality matches.
  5. The Pod is the unit of scheduling. One or more containers sharing a network address and volumes. A Deployment owns the Pods; you rarely create them directly.
  6. Pods are mortal and their IPs change. A Service gives a stable name in front of a changing set of Pods, chosen by labels.
  7. Requests and limits drive everything. Requests decide where a Pod is placed. Limits decide when it is throttled (CPU) or killed (memory).
  8. Probes tell Kubernetes the truth about your app. Liveness restarts it, readiness gates traffic, startup protects slow boots. Wrong probes cause most self-inflicted outages.

1. Containers and images

What is a container, and how is it different from a virtual machine? Basic

A container is a normal process on the host's Linux kernel that the kernel has isolated, so it thinks it has the machine to itself. A virtual machine carries its own full guest operating system and kernel on virtual hardware. So a container starts in under a second and costs megabytes, while a VM boots a whole OS and costs gigabytes. The trade-off is weaker isolation, because all containers share one kernel.

Two kernel features do the isolating. Namespaces limit what the process can see: its own process list (the app is PID 1), network interfaces, mounts, hostname and users. Cgroups (control groups) limit what it can use: CPU and memory. This explains real symptoms. Go over the memory cgroup limit and the kernel's out-of-memory killer ends the process, which you see as OOMKilled. Go over the CPU limit and nothing dies; the process is just paused for part of each scheduling period, called throttling. There is no "container" object in the kernel. The runtime simply sets up namespaces and cgroups and starts your process.

A Linux container cannot run a different kernel, so on a Mac or Windows laptop Docker quietly runs a small Linux VM underneath. I would still pick a VM for strong isolation between untrusted tenants or a legacy app that expects a full OS.

Why it exists

Before containers, you had two bad options for running many apps on one machine. Run them side by side and they fight over library versions, ports and memory ("works on my machine"). Or give each its own VM and pay for a full operating system, a minute of boot time and several GB per app. Containers fix this by giving each app its own private view of the machine without a second kernel.

What happens when you start one

  1. The runtime unpacks the image's filesystem into a directory on the host.
  2. It asks the kernel for new namespaces (PID, network, mount, UTS for hostname, IPC, user) so the process gets its own process tree, network interfaces and root directory.
  3. It creates a cgroup and writes the limits into it, for example 512 MiB of memory and 0.5 CPU.
  4. It starts your program inside all of that. On the host you can still see it with ps, as a normal process with a high PID. Inside, it sees itself as PID 1.

Analogy: a VM is a separate flat in its own building; a container is a locked room in a shared flat with its own meter for electricity and water.

What an interviewer probes next

"Is a container secure?" Say: it is isolated, not sandboxed. Root in a container with a mounted Docker socket or the privileged flag is effectively root on the host. For hostile multi-tenant code, people add a stronger boundary (gVisor, Kata Containers, or a VM per tenant). Also expect "what is PID 1 doing in a container?": it is your app, so it must handle signals and reap child processes.

Remember: container = isolated process on a shared kernel (namespaces limit what it sees, cgroups limit what it uses). VM = its own kernel.

What is the difference between an image, a container and a registry? Basic

An image is a read-only package of filesystem layers plus metadata like the default command and ports. A container is a running instance of an image, like an object created from a class. A registry is a server that stores and serves images, such as Docker Hub or my company's private registry.

One image can start many containers. An image name looks like registry.example.com/team/orders:1.4.2: host, repository path, then a tag. A tag is a label that can be moved to other content, while a digest (@sha256:...) is the content hash and never changes.

docker build -t registry.example.com/team/orders:1.4.2 .
docker push registry.example.com/team/orders:1.4.2
docker run -d --name orders -p 8080:8080 registry.example.com/team/orders:1.4.2

docker run creates a new container from the image and starts it. docker start restarts an existing stopped one, with its old writable layer.

The three nouns, step by step

  1. Build. docker build turns a Dockerfile plus your files into an image on your machine. The image has an ID (a content hash) and is immutable.
  2. Push. docker push uploads the layers to a registry under a name and tag, so other machines (CI, the Kubernetes nodes) can fetch them.
  3. Pull and run. A node pulls the image (only the layers it does not already have) and starts a container from it.

A concrete mental picture: an image is a frozen snapshot of a filesystem plus a note saying "start with this command, listen on this port, run as this user". The container is that snapshot brought to life as a process, with a scratch layer on top for its own writes. Start five containers from one image and you get five independent processes that share the same read-only files.

Reading an image name

registry.example.com/team/orders:1.4.2 has three parts: the registry host, the repository path, and the tag. If you leave out the host, Docker assumes Docker Hub; if you leave out the tag, it assumes latest. A digest looks like orders@sha256:9f2c... and points to one exact image forever, so it is what you pin when you need certainty.

Useful details

  • docker ps lists running containers; docker ps -a includes stopped ones, which still occupy disk until docker rm.
  • docker images lists images. Many "dangling" images accumulate in CI; docker system prune cleans them.
  • Public registries rate limit anonymous pulls, so production clusters usually pull from a private registry or a pull-through cache, with credentials supplied through imagePullSecrets.

Pitfall: people say "the container is gone, so my image is gone". They are separate; removing a container never removes the image, and removing the image fails while a container still uses it.

Remember: image = class, container = object, registry = where images live. Tags move, digests do not.

How do image layers work, and what is copy-on-write? Intermediate

Most Dockerfile steps (FROM, COPY, RUN) each produce a read-only layer: the file changes on top of the previous layer. Layers are named by content hash, so images that share a base share those layers on disk and during pulls. A running container gets one thin writable layer on top, and when it changes a lower file the file is copied up first. That is copy-on-write.

Two practical consequences. First, layers only add. If one step downloads a 500 MB archive and a later step deletes it, the image still carries 500 MB, because the delete is just a marker in a newer layer. Download and delete in the same RUN, or use a multi-stage build. Second, the writable layer is slow for heavy writes and disappears with the container, so real data belongs in a volume. docker history IMAGE shows each layer and its size.

How a layer is built, with an example

Take this Dockerfile:

FROM eclipse-temurin:21-jre      # layers come from the base image
RUN apt-get update && apt-get install -y curl   # layer: the files apt changed
COPY app.jar /app/app.jar        # layer: one file, say 60 MB
ENTRYPOINT ["java","-jar","/app/app.jar"]   # metadata only, no layer size

Each filesystem-changing instruction records only the difference from the layer below it: files added, changed or deleted. Metadata instructions such as ENTRYPOINT, ENV and EXPOSE add configuration but essentially no file data. The image is the ordered list of layer hashes plus that configuration.

Why layers exist

Sharing and caching. If ten services start from the same JRE base, the node stores that base once. When you push a new version of your app where only app.jar changed, only that one layer is uploaded and pulled, not the whole image. That is why a Kubernetes rollout of a small change is fast.

Copy-on-write, step by step

  1. The container sees all layers merged into one view (the OverlayFS union filesystem on Linux).
  2. Reading a file reads straight from whichever lower layer holds it. No copy.
  3. The first time the container modifies a file that lives in a lower layer, the filesystem copies the whole file up into the writable layer and changes the copy. The lower layer stays untouched, which is what lets other containers share it.
  4. Deleting a lower-layer file just drops a "whiteout" marker in the upper layer so it looks gone.

The cost: writing to a big file the first time copies all of it, and the writable layer is slower than a real volume. Databases and heavy logging should write to volumes, not the container layer.

Pitfall that interviewers love

"I deleted the secret in the next line, so it is gone." No. The earlier layer still contains it and docker save or a registry pull exposes it. The same logic explains bloat: RUN curl -O big.tgz then RUN rm big.tgz keeps the archive in the image. Merge them into one RUN or use a multi-stage build.

Remember: layers only add, never shrink. Clean up in the same step that created the mess.

Why is the latest tag a bad idea in production, and what should you use? Intermediate

Because latest is only a movable label, not a version. If production runs orders:latest I cannot tell which code is running, two nodes can pull different content, and I cannot roll back since the old content has no name. I tag every build with something immutable, like a semantic version or the Git commit SHA, and for the strongest guarantee I deploy by digest.

In Kubernetes there is an extra trap: with latest or no tag, imagePullPolicy defaults to Always; with any other tag it defaults to IfNotPresent. So re-pushing the same tag (v1, dev) does not refresh nodes that already cached it. Pipelines usually keep both a readable version tag and the digest recorded in the deployment. Many registries can enforce tag immutability so a tag can never be overwritten.

What a tag really is

A tag is just a pointer stored in the registry, like a Git branch name. Pushing orders:1.4 again simply moves the pointer to the new image. Nothing stops you, and nothing tells the nodes. A digest is the SHA-256 hash of the image manifest, so by construction it identifies one and only one image.

What goes wrong with mutable tags, a timeline

  1. Monday: you deploy orders:latest to 3 Pods. All three pull build A.
  2. Tuesday: CI pushes build B to latest. The running Pods are untouched and still run A.
  3. Wednesday: node 2 fails and its Pod reschedules to a new node, which pulls latest and gets B. You now run A and B side by side, and the Deployment YAML never changed, so Kubernetes started no rollout and kubectl rollout undo has nothing to go back to.

During an incident you ask "which commit is in production?" and the answer is "it depends on the node". That is the real cost.

The same image bytes move from test to staging to prod: promote the artifact, do not rebuild it per environment.

Pitfall: pinning by digest but never updating means you stop receiving base-image security patches, so pair it with an automated bump (Renovate, Dependabot) and a rebuild schedule.

Remember: never reuse a tag. One build, one immutable tag (version or commit SHA); digest if you want it bulletproof.

What is the difference between CMD and ENTRYPOINT, and between shell form and exec form? Basic

ENTRYPOINT is the program the container always runs. CMD is the default arguments to it, and anything I type after the image name in docker run replaces CMD but not ENTRYPOINT. For the main process I always use exec form, the JSON array, so my app is PID 1 and receives stop signals directly.

ENTRYPOINT ["java", "-jar", "/app/app.jar"]
CMD ["--server.port=8080"]
# docker run orders --server.port=9090   replaces CMD only

Shell form (CMD java -jar app.jar) is wrapped by Docker as /bin/sh -c "...". The shell becomes PID 1 and your app is its child. A shell does not forward SIGTERM, so on docker stop or a Kubernetes pod shutdown the app never hears the request to stop, Kubernetes waits out the grace period (30 s by default) and then kills it hard with exit code 137. That is the classic "pod takes 30 seconds to terminate" symptom. PID 1 also has to reap orphaned child processes; if your app spawns children, docker run --init adds a tiny init (tini) for that.

If I need environment variable expansion, I use a small start script that ends with exec java ..., which replaces the shell with the app. In Kubernetes, command overrides ENTRYPOINT and args overrides CMD. To debug, docker run --entrypoint sh image gives a shell.

The mental model

Think of the final command as ENTRYPOINT + CMD glued together. ENTRYPOINT is the fixed part ("this container is the java program"). CMD is the default, easy-to-replace part ("with these flags"). Whatever you add after the image name in docker run (or args in Kubernetes) replaces CMD.

The exec-versus-shell problem, walked through

  1. Shell form CMD java -jar app.jar becomes /bin/sh -c "java -jar app.jar". PID 1 is sh, and java is its child.
  2. On shutdown the runtime sends SIGTERM to PID 1 only. Many shells do not forward signals to the child (some shells exec the last command as an optimisation, but you cannot rely on it).
  3. Java never learns it should stop, so its shutdown hooks and graceful drain do not run.
  4. After the grace period (30 s in Kubernetes) the runtime sends SIGKILL. Exit code 137, in-flight requests lost.

With exec form, java itself is PID 1 and gets SIGTERM directly. One more subtlety: Linux gives PID 1 no default signal handlers, so a program that does not install a SIGTERM handler will ignore the signal as PID 1. The JVM does install one, which is why Java apps work, but a plain script or some other runtimes may not. docker run --init (or tini in the image) fixes both signal forwarding and zombie-process reaping.

Practical rules

  • Need $JAVA_OPTS expansion? Exec form does not expand variables. Use a script with exec java $JAVA_OPTS -jar app.jar "$@", or JAVA_TOOL_OPTIONS which the JVM reads itself.
  • Kubernetes mapping: command replaces ENTRYPOINT, args replaces CMD. Setting only command also discards the image's CMD.

Remember: ENTRYPOINT = the program, CMD = its default args. Exec form (JSON array) so signals reach the app.

2. Writing good Dockerfiles

How does the Docker build cache work, and how do you order a Dockerfile for fast builds? Intermediate

For each instruction Docker checks whether it already built that exact step on top of that exact previous layer, and if so reuses it. The moment one step misses, every step after it is rebuilt. So I put slow, rarely changing steps first: copy the dependency file, install dependencies, and only then copy the source that changes on every commit.

For RUN the cache key is the command text. For COPY and ADD it is a checksum of the files. For a Maven project the difference is minutes:

# slow: any source change re-downloads all dependencies
COPY . .
RUN mvn package

# fast: dependency layer is cached until pom.xml changes
COPY pom.xml .
RUN mvn -B dependency:go-offline
COPY src ./src
RUN mvn -B package -DskipTests

Three more tips. A .dockerignore (listing .git, target/, .env) keeps junk and secrets out of the build context and stops irrelevant file changes from breaking the cache. With BuildKit, RUN --mount=type=cache,target=/root/.m2 ... keeps the Maven repository between builds. And in CI, where every build starts on a clean machine, the local cache is empty, so you need a shared one (--cache-from and --cache-to with a registry). Also put apt-get update and install in the same RUN, otherwise a cached update line goes stale.

How the cache decides

Each layer's cache key is: the parent layer plus the instruction. If both match a layer already built, Docker reuses it and prints CACHED. For COPY/ADD Docker also hashes the copied files' contents (and metadata such as permissions). The moment one instruction produces a different result, the chain is broken: every later layer is new because its parent is new.

A worked example with timings

Suppose dependencies take 3 minutes to download and the compile takes 40 seconds. You change one line in a Java file.

  • Bad order (COPY . . then mvn package): the copy layer changed, so Maven re-downloads everything. Build time about 3m40s.
  • Good order (copy pom.xml, resolve, then copy src): the pom layer and the dependency layer are CACHED. Only the source copy and compile rerun. Build time about 45 s.

Rule of thumb: sort instructions by how often their inputs change. Base image, OS packages, dependency manifest, dependencies, source, build, labels with a commit hash or timestamp last.

Things that silently break the cache

  • A COPY . . that includes a changing file you do not need (logs, .git, the target folder). Fix with .dockerignore.
  • ARG BUILD_DATE or a commit SHA declared early: its value changes every build and invalidates everything after it. Declare it late.
  • RUN apt-get update on a line by itself. The command text never changes, so the stale package index is cached for months. Always apt-get update && apt-get install ... in one line.
  • CI runners that start empty. Use --cache-to type=registry / --cache-from, or the CI vendor's cache backend.

The cache is also a correctness risk: a cached RUN git clone or curl will not fetch new content. Use --no-cache for a clean release build when you need it.

Remember: order from least to most frequently changing. One cache miss rebuilds everything below it.

What is a multi-stage build, and why use it? Basic

A multi-stage build uses several FROM lines in one Dockerfile. An early stage has the JDK, Maven and source code and builds the jar. The final stage starts from a small runtime image and copies only the finished artifact with COPY --from=build. The shipped image has no compilers or source, so it is much smaller, pulls faster and has fewer packages that can have security holes.

# ---- build stage ----
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /src
COPY pom.xml .
RUN mvn -B dependency:go-offline
COPY src ./src
RUN mvn -B package -DskipTests

# ---- runtime stage ----
FROM eclipse-temurin:21-jre
RUN useradd -r -u 10001 app
WORKDIR /app
COPY --from=build /src/target/orders.jar app.jar
USER 10001
ENTRYPOINT ["java", "-jar", "app.jar"]

It also makes the build repeatable on any machine, because the toolchain lives in the Dockerfile and not on a CI box. docker build --target build . stops at a stage, handy for running tests.

The problem it solves

To compile a Java app you need a JDK, Maven, and hundreds of MB of downloaded dependencies. To run it you need only a JRE and one jar. Before multi-stage builds, teams either shipped the whole toolchain (large, more to patch) or maintained two Dockerfiles and a shell script to copy artifacts between them. Multi-stage builds put both in one file.

How it works

  1. Each FROM starts a fresh stage with its own filesystem. You can name it with AS build.
  2. Earlier stages do the heavy work. Their layers are used for caching but are not part of the final image.
  3. COPY --from=build /src/target/orders.jar app.jar reaches back into a previous stage and takes just the files you name.
  4. The last stage is the image that gets tagged and pushed.

Typical result: a single-stage Maven image of roughly 700-900 MB becomes about 200-300 MB with a JRE base (exact sizes depend on the base image).

Beyond size

  • Security: no compiler, no git, no package manager in production means fewer CVEs to scan and less for an attacker to use. Secrets used only in the build stage (via secret mounts) never reach the final image.
  • Reproducibility: the build environment is pinned in the Dockerfile, so every developer and CI agent builds the same way.
  • Test stage: add a stage that runs tests and build with --target test in CI, while the default build skips it.
  • Parallelism: BuildKit builds independent stages concurrently and skips stages the final image does not need.

Pitfall: tests need to run somewhere. Do not put -DskipTests on every build and forget them; run them in a separate stage or in the CI job before the image build. Also remember a JRE-only image has no jstack/jcmd for debugging.

Remember: build fat, ship thin. Copy only the artifact into the final stage.

How do you make an image small and safe? Alpine, slim, distroless or scratch? Intermediate

First a multi-stage build, then a small base. For Java I would use a -slim or JRE-only base as the safe default, and distroless when I want the smallest attack surface. I would not pick Alpine blindly: it uses musl instead of glibc, which can break native libraries or change behaviour. Smaller means faster pulls, quicker starts on a new node and fewer packages to patch.

  • Full OS (ubuntu): familiar tools, large.
  • Slim (Debian with fewer packages): a good default.
  • Alpine: tiny, musl libc. Fine for many apps, but test it, especially with native code.
  • Distroless: only the runtime and your app, no shell or package manager. Little to attack, harder to debug (use kubectl debug to attach a temporary debug container).
  • scratch: empty; right for a single static Go binary.

Other habits: install with --no-install-recommends and clean package lists in the same RUN, keep a .dockerignore, and pin the base image by version (ideally digest) but rebuild regularly so you pick up security patches. For Java, Jib or Spring Boot layered jars split dependencies from your own classes, so a code change only moves a tiny layer.

Why size and content matter

Three practical reasons. Speed: a new node must pull the image before the Pod starts, so a 900 MB image can add tens of seconds to every scale-up or failover. Cost and storage: registries and node disks fill up. Security: every package in the image is something that can have a CVE. A scanner on a full Ubuntu image typically reports dozens of findings that are irrelevant to your app, and each one costs triage time.

Why Alpine surprises people

Alpine uses musl instead of glibc. Most pure-Java apps run fine, but anything with native code (some JNI libraries, certain DNS or locale behaviour, older glibc-only binaries like some monitoring agents) may crash or behave differently, and thread-stack defaults differ. If you pick Alpine, run your full test suite on it, not just on your laptop's glibc.

Distroless debugging

With no shell you cannot exec in. Use an ephemeral debug container: kubectl debug -it pod/orders-abc --image=busybox --target=orders, which shares the process namespace so you can inspect the running app. Another habit: scan with Trivy or Grype in CI, fail on high severity, and rebuild weekly so base-image fixes arrive even when your code did not change.

Java-specific shrink: Spring Boot layered jars and Jib split dependencies (rarely change) from your classes (change every commit), so a code-only change pushes a few MB instead of 80.

Remember: multi-stage first, then slim or distroless. Small is good, but rebuild often for patches.

Why should containers not run as root, and how do you do it? Intermediate

By default the process inside a container is root. That is not the same as root on the host, but it is a thinner wall than people think: if the app is exploited, or a misconfiguration mounts a host path or leaves extra capabilities, a root process can do far more damage. So I create a non-root user in the Dockerfile, switch to it with USER, and enforce it again in the Kubernetes Pod spec.

Prefer a numeric user ID (USER 10001) so Kubernetes can verify it is not root. In the Pod spec I add:

securityContext:
  runAsNonRoot: true
  runAsUser: 10001
  allowPrivilegeEscalation: false
  readOnlyRootFilesystem: true
  capabilities:
    drop: ["ALL"]

With a read-only root filesystem, writes go only to explicit volumes, such as an emptyDir mounted at /tmp. Many clusters enforce this with Pod Security Standards (the "restricted" level). If the app fails with "permission denied" after the switch, the files were copied in as root (use COPY --chown) or it writes to a directory the user cannot write. A non-root user also cannot bind ports below 1024, so listen on 8080 and let the Service map it.

The threat, concretely

Suppose an attacker finds a remote code execution bug in your app. If the process is root inside the container, they can: install tools, write anywhere in the container filesystem, bind low ports, and, if the Pod has a hostPath mount, extra capabilities or a leaked service-account token, try to escape or move sideways. A non-root user with no capabilities turns many of those steps into "permission denied". It is defence in depth: you assume one layer will fail and limit the damage.

Debugging the "permission denied" after switching

  1. Files copied as root: use COPY --chown=10001:10001 ... or chown in the same layer.
  2. The app writes to /tmp, a log folder or a cache directory while the root filesystem is read-only: mount an emptyDir there.
  3. Volumes owned by root: set fsGroup in the Pod securityContext so Kubernetes makes the volume group-writable.
  4. Port below 1024: listen on 8080 and map it in the Service.

Also avoid privileged: true and mounting the Docker socket; both hand the container root-equivalent power over the host. Platform teams enforce all this with Pod Security Admission (the baseline and restricted profiles) or policy engines such as Kyverno or OPA Gatekeeper, so a Pod that violates the rules is rejected at admission.

Remember: USER with a numeric ID, no privilege escalation, read-only root filesystem, drop all capabilities.

How do you handle secrets during a build and at run time? Intermediate

Never put a secret in a layer, because anything written into an image stays there, even if a later step deletes it, and anyone who can pull the image can unpack it. For build-time secrets I use BuildKit secret mounts. For run time I inject secrets from outside the image: a Kubernetes Secret or, better, a vault or cloud secret manager.

That rules out COPY .env, ENV API_KEY=... and ARG (build args show up in docker history). A secret mount exists only during that one RUN step and is not stored in any layer:

RUN --mount=type=secret,id=npm_token \
    NPM_TOKEN=$(cat /run/secrets/npm_token) npm ci

docker build --secret id=npm_token,src=./npm_token.txt .

If a secret ever reached an image, treat it as leaked and rotate it. Deleting the image tag does not delete copies others have already pulled. Run an image scanner in CI (Trivy, Grype, Docker Scout) to catch leaked secrets and known CVEs.

Why an image is the wrong place for secrets

An image is a set of tarballs that anyone with pull access can read with docker save and tar. It gets copied to registries, build caches, developer laptops and node disks, and it lives for as long as those copies do. Even if the final filesystem looks clean, an intermediate layer may hold the file. Build arguments (ARG) and ENV values are recorded in the image history in plain text. So the rule is simple: nothing secret is ever baked in.

Two moments, two techniques

WhenNeedHow
Build timePrivate Maven/npm token, SSH key to fetch a dependencyBuildKit --mount=type=secret (or --mount=type=ssh). Exists only during that RUN, not saved in a layer.
Run timeDB password, API key, TLS keyInject from outside: Kubernetes Secret as a mounted file, or fetched at start from Vault or a cloud secret manager using the Pod's identity.

Run-time options, ranked

  1. Workload identity plus a secret manager (for example cloud IAM role bound to the service account): no long-lived password is stored in the cluster at all.
  2. External Secrets operator or the CSI Secrets Store driver: syncs from a vault into a Secret or file, with rotation.
  3. Plain Kubernetes Secret from a sealed or encrypted source in Git: simple, but remember base64 is not encryption.

Prefer files over environment variables: env vars show up in kubectl describe output of other tooling, in crash dumps, in child processes and in debug endpoints (Spring Boot actuator /env, which should be locked down anyway).

If it already happened

Rotate first (see the scenario on leaked passwords). Cleaning the image is secondary. Prevention: a .dockerignore excluding .env, *.pem, .git; a secret scanner in CI (gitleaks, Trivy secret scan); and image scanning at the registry.

Remember: a secret in a layer is a leaked secret. Mount at build time, inject at run time, rotate if it leaked.

What is the difference between ARG and ENV, COPY and ADD, and what does EXPOSE really do? Basic

ARG is a variable that exists only while the image is being built; ENV is stored in the image and is visible in every container started from it. COPY copies files from the build context, while ADD also unpacks local tar archives and can fetch URLs, so I use COPY unless I need that extra. EXPOSE is documentation about which port the app listens on; it publishes nothing.

ARG versus ENV

ARGENV
Available during buildYes (from its declaration)Yes (from its declaration)
Available in the running containerNoYes
Set at build time with--build-arg NAME=valueFixed default; overridable at run time with -e or Kubernetes env
Visible in docker historyYesYes

Use ARG for things like a base-image version or a build number, and ENV for a default the app reads (for example JAVA_TOOL_OPTIONS). Neither is safe for secrets. A subtle trap: an ARG declared before FROM is only usable in the FROM line, and an ARG that changes each build invalidates the cache for every step after it.

COPY versus ADD

ADD app.tar.gz /app/ auto-extracts the archive, and ADD https://... downloads a file. Both surprises make builds harder to reason about (a remote URL is not covered by the cache the way local files are, and a download adds no checksum check unless you give one). The recommended habit is COPY for files and an explicit RUN curl ... && tar ... when you need to download, ideally with checksum verification.

EXPOSE and publishing

EXPOSE 8080 records the intended port in the image metadata, which tools and humans can read. To reach a container from the host you still need docker run -p 8080:8080 (or -P to publish all exposed ports to random host ports). In Kubernetes, the container port in the Pod spec is informational too; what makes the port reachable is a Service pointing at it.

Remember: ARG = build only, ENV = baked in and runtime, COPY over ADD, EXPOSE documents and does not publish.

How do you run a JVM application well in a container? Senior

I make sure the JVM sees the container's limits and I leave room outside the heap. Modern JVMs are container aware (JDK 10 and later, and 8u191), but the default max heap is only 25% of container memory, so I set -XX:MaxRAMPercentage=70 or so. The rest of the limit is needed for non-heap memory. If heap plus non-heap exceeds the limit, the kernel kills the container with OOMKilled, even though Java never threw OutOfMemoryError.

That is the key distinction. A Java OutOfMemoryError is the JVM complaining about its heap. OOMKilled (exit code 137, which is 128 plus signal 9) is the kernel complaining about the whole process. Non-heap memory is bigger than people expect: metaspace (class data), thread stacks (about 1 MB each), code cache, direct buffers and GC structures. Setting -Xmx equal to the limit is the classic mistake.

Other points. CPU: the JVM sizes its thread pools and GC from the CPU count it sees. Below about 2 CPUs and 2 GB it behaves like a "small machine" and picks the serial garbage collector, so check the GC with -Xlog:gc or set it deliberately. Startup: JIT warm-up burns CPU, so a tight CPU limit makes cold starts slow; use a startup probe. Shutdown: handle SIGTERM (Spring Boot has graceful shutdown) and use exec form. Also add -XX:+ExitOnOutOfMemoryError so a broken JVM restarts instead of limping.

ENV JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=70 -XX:+ExitOnOutOfMemoryError"
# k8s memory limit 1Gi  -> heap max about 700Mi, rest is non-heap

Why this question is hard

The JVM was designed when a machine was a machine. Inside a container the JVM must discover the cgroup limit instead of the host's total RAM. Old JVMs (before 8u191) read the host's memory, so a 1 GB container on a 64 GB node would size its heap to 16 GB and get killed almost immediately. Modern JVMs read the cgroup limit, but there are still two defaults to override.

Where a 1 GiB limit actually goes

AreaRough sizeNotes
Java heapup to MaxRAMPercentageDefault 25% means only 256 MiB heap; 70% gives about 700 MiB.
Metaspace50-200 MB for a Spring appLoaded classes; grows with proxies and frameworks.
Thread stacks~1 MB x thread count200 threads = about 200 MB reserved (touched pages count).
Code cache + JITtens of MBCompiler threads use memory during warm-up.
Direct buffers, Netty, mmapvariesOften the hidden culprit in the "OOMKilled but heap looks fine" story.
GC structures, libc arenas5-15% of heapglibc malloc arenas can fragment; MALLOC_ARENA_MAX=2 is a common mitigation.

This is why 70% is a starting point, not a law. A thread-heavy or Netty-heavy service may need 50-60%; a small simple one can use 75%.

Checklist for a production JVM Pod

  1. Set memory request equal to limit (Guaranteed or at least stable behaviour), and MaxRAMPercentage to 60-75.
  2. CPU: give a request of at least 1 core for real services. Fractions of a core make start-up and GC slow. Know that availableProcessors() rounds the limit or request, which sizes the common ForkJoin pool and GC threads; override with -XX:ActiveProcessorCount if needed.
  3. Choose the GC deliberately: with fewer than 2 CPUs or little memory the JVM picks SerialGC; G1 is the usual choice for larger services; ZGC or Shenandoah for strict latency.
  4. Enable graceful shutdown and exec-form start (see the signals question).
  5. Expose heap and non-heap metrics (Micrometer) and alert on container_memory_working_set_bytes versus the limit, not only on heap.
  6. Set -XX:+ExitOnOutOfMemoryError (or a heap dump path plus exit) so Kubernetes restarts a broken JVM cleanly.

Diagnose with -XX:NativeMemoryTracking=summary and jcmd <pid> VM.native_memory summary. Remember the working set counts page cache too, so file-heavy apps show higher numbers.

Remember: heap is not the whole process. Set MaxRAMPercentage about 70, never -Xmx equal to the limit. OOMKilled is the kernel, OutOfMemoryError is the JVM.

Review this Dockerfile: what is wrong with it? Intermediate 
FROM ubuntu:latest
RUN apt-get update
RUN apt-get install -y openjdk-17-jdk maven
COPY . /app

It has eight problems. Unpinned latest base, a stale-prone apt-get update on its own line, a full JDK and Maven in the final image, a bad copy order that kills the cache, a password baked into ENV, running as root, shell-form CMD that hides SIGTERM, and no JVM memory settings. The fix is a multi-stage build, which brings roughly 900 MB down to about 200 MB.

  1. ubuntu:latest: builds change over time. Pin a version.
  2. apt-get update alone is cached and goes stale. Combine with install and clean the lists.
  3. JDK and Maven in the shipped image: use multi-stage with a JRE-only runtime.
  4. COPY . /app before the build: any file change rebuilds all, and without a .dockerignore it copies .git and secrets. Copy pom.xml first.
  5. Password in ENV is in the image forever. Inject at run time.
  6. No USER: runs as root.
  7. Shell-form CMD: PID 1 is a shell that will not pass SIGTERM. Use exec form.
  8. No JVM flags: set MaxRAMPercentage. Note EXPOSE only documents a port; it publishes nothing.

The fixed version

FROM maven:3.9-eclipse-temurin-21 AS build

COPY src ./src
RUN mvn -B package -DskipTests

FROM eclipse-temurin:21-jre

# DB_PASSWORD is injected at run time from a Secret, never baked in

Why each fix matters, in priority order

  1. Secret in ENV is the most severe: it is readable by anyone who can pull the image or run docker inspect. Fix: remove and rotate.
  2. Root user and shell-form CMD are security and operations bugs: a compromise has more power, and shutdown is a hard kill after 30 s.
  3. Single stage with JDK and Maven: large and carries build tools plus the whole source into production.
  4. Cache order: every code change re-downloads all dependencies. This costs developer time on every commit.
  5. Unpinned base and separate apt-get update: builds are not reproducible, and the cached update line goes stale. (In the fixed file, base images are pinned by version; pin by digest for stricter supply-chain control.)
  6. No JVM memory setting: leads to OOMKilled or an under-used heap.

An interviewer may also ask what else you would add: a HEALTHCHECK is optional in Kubernetes (probes do it instead); a .dockerignore; OCI labels (org.opencontainers.image.revision) with the Git SHA for traceability; and an image scan in CI. When answering aloud, group the issues: "reproducibility, size and cache, security, and runtime behaviour" so you do not sound like you are reciting a list.

Remember: pin, multi-stage, cache order, no secrets, non-root, exec form.

3. Networking, volumes and Compose

How does container networking work in Docker? What are bridge, host and none? Intermediate

By default a container joins a bridge network, which is a virtual switch on the host. It gets a private IP, outgoing traffic is translated (NAT) to the host's address, and to reach it from outside I publish a port with -p 8080:80. On a user-defined bridge network, which Compose creates, containers reach each other by name through Docker's built-in DNS. host shares the host's network stack with no isolation, and none gives only loopback.

On the default bridge, containers can only find each other by IP. On a user-defined one, a JDBC URL like jdbc:postgresql://db:5432/app just works. Host mode is fast but can clash with host ports. The most common beginner mistake: using localhost to reach another container. Inside a container, localhost is that same container. To reach a service on my laptop from Docker Desktop, I use host.docker.internal.

Kubernetes changes the model: every Pod gets its own IP, all Pods can reach all Pods without NAT, and Service names replace Docker DNS names.

What happens on the default bridge, step by step

  1. Docker creates a virtual switch (docker0) on the host with a private subnet, for example 172.17.0.0/16.
  2. Each container gets a virtual network card connected to that switch and an IP like 172.17.0.3.
  3. When the container calls the internet, the host rewrites the source address to its own (NAT masquerade), and rewrites replies back.
  4. With -p 8080:80, Docker adds a rule that forwards host port 8080 to container port 80. The syntax is host:container, which people reverse constantly.

The three modes compared

ModeWhat the container seesUse it when
bridge (user-defined)Its own IP, DNS by container or service nameNormal case, Compose default
hostThe host's network directly, no port mapping neededVery high network throughput or needs many ports; loses isolation. Not available the same way on Docker Desktop.
noneOnly loopbackBatch job that must have no network

Why name resolution matters

Container IPs change on every restart, so you never hard-code them. On a user-defined network an embedded DNS server resolves db to the right container. The default bridge network does not have this feature, which is why Compose and docker network create are recommended.

Debugging a "connection refused"

  • Is the app listening on 0.0.0.0? An app bound to 127.0.0.1 inside its container cannot be reached from anywhere else, even with -p.
  • Are both containers on the same network? docker network inspect shows members.
  • Did you publish the port, or only expose it?
  • Inside Compose, use the service port (5432), not the host-published port (for example 15432), when calling another container.

In Kubernetes the same ideas map as: each Pod has its own IP (no NAT between Pods), a Service gives the DNS name, and port publishing is replaced by Services, NodePorts and Ingress.

Remember: containers talk by name on a user-defined network, never by localhost. Outside access needs a published port.

What are volumes, bind mounts and tmpfs, and when do you use each? Basic

The container's own writable layer disappears with the container, so data that matters must live outside it. A named volume is Docker-managed storage that survives container removal, right for database data. A bind mount maps an exact host path into the container, perfect in development for live source code or a config file. A tmpfs mount lives in memory only, for temporary or sensitive data.

docker run -v pgdata:/var/lib/postgresql/data postgres:16     # named volume
docker run -v "$PWD/conf:/etc/app:ro" myapp                    # bind mount, read-only
docker run --tmpfs /tmp myapp                                  # in-memory

Bind mounts tie the container to a host layout and can have file permission problems. "I removed the container and lost my data" almost always means the app wrote into the writable layer, not a volume. In Kubernetes the same ideas become emptyDir (scratch space that lives as long as the Pod), ConfigMap and Secret volumes, and PersistentVolumeClaims for durable storage. hostPath exists but I avoid it.

The problem

A container's filesystem is the image layers plus one thin writable layer. When the container is removed, that layer is deleted. A Postgres container that writes to its default data directory without a volume loses every row on docker rm. A volume is a directory managed outside the container's layer stack, mounted into a path inside it.

The three types compared

TypeWhere the data livesTypical useWatch out for
Named volumeDocker-managed area on the hostDatabase data, anything that must persistGone with docker volume rm or down -v
Bind mountAn exact host path you chooseLive-reloading source, config files in devDepends on host layout; permission and UID mismatches; slower on Mac/Windows file sharing
tmpfsHost RAM onlyScratch files, secrets you do not want on diskLost at stop; counts against memory

A walk-through of data surviving

docker run -d --name pg -v pgdata:/var/lib/postgresql/data postgres:16
# write rows, then:
docker rm -f pg
docker run -d --name pg2 -v pgdata:/var/lib/postgresql/data postgres:16
# the rows are still there: the volume outlived the first container

Kubernetes equivalents

  • emptyDir: created empty when the Pod starts, deleted when the Pod is removed; shared between the Pod's containers. Good for caches, scratch space and a read-only-root-filesystem app's /tmp. Can be memory-backed (medium: Memory).
  • configMap/secret/projected: files built from cluster objects.
  • persistentVolumeClaim: durable storage that survives Pod replacement (next sections).
  • hostPath: a node directory; ties the Pod to a node and is a security risk, so it is for node agents only.

Interview pitfall: "Is it OK to run a database in a container?" Yes with a volume, but know that in Kubernetes a durable database also needs correct backups, replication and upgrade handling, which is why many teams use a managed service.

Remember: volume for data, bind mount for dev, tmpfs for temp. The writable layer is not storage.

What is Docker Compose, and how would you use it for local development? Basic

Compose describes a group of containers, their networks and volumes in one YAML file, so docker compose up starts my app plus its database, cache and broker together. All services share a default network and reach each other by service name. It is a development and test tool on one machine, not a production orchestrator: no scheduling across nodes, no rolling updates, no cross-host healing.

services:
  app:
    build: .
    ports: ["8080:8080"]
    environment:
      DB_URL: jdbc:postgresql://db:5432/orders
    depends_on:
      db: { condition: service_healthy }
  db:
    image: postgres:16
    environment: { POSTGRES_PASSWORD: dev }
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      retries: 10

The detail interviewers like: "my app starts before the database is ready and crashes". depends_on alone only waits for the container to start, not to be ready. The proper fix is a health check on the database plus condition: service_healthy, and also making the app retry its connection, since in production nothing orders start-up for you.

What it replaces

Without Compose you start a network, a database, a cache and your app with four long docker run commands that you must remember in the right order. Compose turns that into a file you commit to the repo, so a new developer runs one command and has a working local environment.

Everyday commands

docker compose up -d --build   # build images, create network and volumes, start everything
docker compose logs -f app     # follow one service's logs
docker compose ps              # state and health
docker compose exec db psql -U postgres
docker compose down            # stop and remove containers and network
docker compose down -v         # ... and also delete named volumes (data!)

What Compose gives you, and what it does not

  • Gives: a default network with DNS by service name, named volumes, environment injection from .env or env_file, profiles to switch optional services on, and a dev override file (compose.override.yaml) for bind mounts and debug ports.
  • Does not give: scheduling across machines, self-healing beyond a simple restart: policy, rolling updates, autoscaling, or Kubernetes semantics like probes and Services. Behaviour that works in Compose can still fail in Kubernetes, for example start order, so test the real thing in a cluster too.

Why depends_on alone is not enough

Compose's default depends_on only orders start-up: it launches db first, but PostgreSQL needs several more seconds before it accepts connections. So the app tries immediately and crashes. With condition: service_healthy Compose waits for the database's health check. In production nothing orders your start-up, so the application must retry (with backoff) and tolerate the database coming up later. A good answer always names both.

Testcontainers is a related tool for integration tests: it starts throwaway containers from test code, so each test run gets a clean database without a shared Compose stack.

Remember: started is not ready. Health check plus service_healthy locally, retries in the app always.

4. Kubernetes core: architecture, Pods and workloads

Describe Kubernetes architecture at a high level. Basic

A cluster has a control plane and worker nodes. The API server is the front door: every tool talks to it and it stores the desired state in etcd, the cluster database. The scheduler picks a node for each new Pod, controllers keep real state equal to desired state, and on each node the kubelet runs the Pods assigned to it. Nothing calls anything directly; each part watches the API server and reacts.

Follow one Deployment. I run kubectl apply; the API server stores it. The Deployment controller creates a ReplicaSet, and the ReplicaSet controller creates Pods. The scheduler assigns each Pod a node. The kubelet on that node sees it and asks the container runtime (containerd) to start the containers. The key idea behind it all is the control loop: you declare the desired state ("3 replicas") and controllers endlessly observe, compare and correct. That is why Kubernetes self-heals, and why you edit YAML instead of poking running things.

If the control plane goes down, running Pods keep running, but nothing can be changed or healed. Running the control plane is cluster-operations depth; most teams use a managed service (EKS, GKE, AKS).

The components and their jobs

ComponentWhereJob
kube-apiserverControl planeThe only door. Authenticates, validates and stores objects. Everything else is a client of it.
etcdControl planeConsistent key-value store holding all cluster state. Only the API server talks to it.
kube-schedulerControl planeWatches for Pods with no node, filters nodes that fit (resources, taints, affinity), scores the rest, writes the chosen node.
controller managerControl planeRuns many control loops: Deployment, ReplicaSet, Node, Job, endpoints and more.
kubeletEvery nodeMakes the containers for its assigned Pods exist and report status; runs probes.
container runtime (containerd, CRI-O)Every nodePulls images and actually starts containers.
kube-proxy / CNI pluginEvery nodeService routing rules and Pod networking.

What happens on kubectl apply -f deploy.yaml, as a timeline

  1. kubectl sends the YAML to the API server, which authenticates, authorizes (RBAC), runs admission checks and writes the Deployment to etcd.
  2. The Deployment controller sees a new Deployment (it is watching) and creates a ReplicaSet.
  3. The ReplicaSet controller sees "wants 3, has 0" and creates three Pod objects. They have no node yet (Pending).
  4. The scheduler sees unscheduled Pods, picks a node for each and records it.
  5. The kubelet on each chosen node sees a Pod assigned to it, tells containerd to pull the image and start containers, runs probes and reports status back.
  6. When a Pod is Ready, the endpoints controller adds it to the Service's endpoints.

Every step is "watch, compare, act" rather than a direct call. This loosely coupled design is the answer to "why is Kubernetes self-healing": if a node dies, the node controller marks its Pods for removal, the ReplicaSet notices the missing replicas and creates new ones, and the scheduler places them elsewhere.

Failure behaviour interviewers ask about

  • API server down: running Pods and Services keep working (kubelets and kube-proxy keep their last state), but no deploys, scaling or healing until it returns.
  • etcd lost without backup: the cluster forgets what it should be running. etcd backup is the operator's most important job.
  • A node unreachable: Pods are evicted only after a toleration timeout (typically 5 minutes by default), so recovery is not instant.

Remember: API server is the hub, etcd is the memory, controllers and the kubelet make reality match the declaration.

What is a Pod, and why is the Pod the smallest unit rather than a container? Basic

A Pod is one or more containers that always run together on the same node. They share one network address, so they talk over localhost, and they can share volumes. Most Pods have one container. The Pod is the unit because some helpers are tied to the main app, like a log shipper or a proxy, and must be scheduled together and share files or network.

Pods are disposable. If a Pod dies or its node fails, nobody repairs it; a controller creates a new one with a new name and a new IP. That is why I never create bare Pods and always use a Deployment (or Job). Under the hood, a hidden "pause" container holds the Pod's network namespace and the others join it.

Init containers run one at a time, in order, to completion, before the app starts: wait for a dependency, download a file into a shared volume, set permissions. A sidecar runs next to the app for the Pod's whole life: a service-mesh proxy or log forwarder. I avoid running database migrations in an init container, since every replica would try at once; a Job or Helm hook is safer.

initContainers:
- name: wait-db
  image: busybox:1.36
  command: ["sh","-c","until nc -z db 5432; do sleep 2; done"]
containers:
- name: app
  image: orders:1.4.2

Why not just schedule containers?

Some processes are only useful together: an app and a proxy that terminates its TLS; an app writing log files and an agent shipping them; a main app and a helper that refreshes a config file. They must land on the same machine, talk over loopback and share a directory. If Kubernetes scheduled single containers, you would need extra rules to keep them together. The Pod is that "co-located group" made a first-class unit.

What the containers in a Pod share

  • Network namespace: one IP, one port space. Two containers cannot both listen on 8080. They reach each other at localhost.
  • Volumes: declared at Pod level and mounted into any container that wants them.
  • Lifecycle placement: they are scheduled onto one node and live and die with the Pod (a crashed container is restarted in place by the kubelet; the Pod itself is not rescheduled for that).

They do not share a filesystem by default, and each container has its own image, CPU/memory limits and probes. Scheduling uses the sum of container requests (plus the larger of the init containers).

Init containers, sidecars, and a Pod's life

  1. Pod accepted and scheduled; volumes are set up.
  2. Init containers run one by one; each must exit 0 or the Pod does not proceed (it restarts the failed init container).
  3. App containers start; probes begin.
  4. On deletion, preStop hooks and SIGTERM run (see the shutdown question).

Native sidecar support (init containers with restartPolicy: Always) was added in recent Kubernetes versions (beta in 1.29, stable in 1.33, check your cluster version). It solves the old problem of a proxy sidecar starting after, or outliving, the app, and of Jobs never finishing because a sidecar keeps running.

When to use multiple containers

Only when they truly must share a Pod's fate and resources. A database and the app that uses it do not belong in one Pod, because you could not scale or restart them independently. Rule: "scale together and fail together means same Pod; otherwise separate Deployments".

Restart behaviour also differs: restartPolicy applies to all containers in the Pod (default Always for Deployments); the kubelet restarts a crashed container on the same node with exponential backoff, which is what CrashLoopBackOff is.

Remember: Pod = containers sharing network and volumes, disposable, owned by a controller. Init containers run first, sidecars run alongside.

What is a Deployment, and how does it relate to ReplicaSets and Pods? Basic

A Deployment manages a stateless app. I declare the Pod template and a replica count. The Deployment creates a ReplicaSet for that exact template, and the ReplicaSet keeps the right number of Pods alive. When I change the template, for example a new image, the Deployment creates a new ReplicaSet and gradually scales it up while scaling the old one down. That is a rolling update.

The old ReplicaSets stay around with zero Pods, which is what makes rollback quick: scale the old one back up. Kept revisions are limited by revisionHistoryLimit (10 by default). Changing only the replica count does not create a new ReplicaSet. If I delete a Pod, the ReplicaSet replaces it.

apiVersion: apps/v1
kind: Deployment
metadata: { name: orders }
spec:
  replicas: 3
  selector: { matchLabels: { app: orders } }
  strategy:
    type: RollingUpdate
    rollingUpdate: { maxSurge: 25%, maxUnavailable: 0 }
  template:
    metadata: { labels: { app: orders } }
    spec:
      containers:
      - name: orders
        image: registry.example.com/team/orders:1.4.2

Why a Deployment instead of a bare ReplicaSet or Pod

A bare Pod is not replaced when its node dies. A bare ReplicaSet keeps N Pods alive but has no idea how to change them safely: edit its image and nothing happens to existing Pods. The Deployment adds the missing piece: controlled change over time (rolling update, rollback, pause).

A rollout, step by step, with numbers

Say replicas: 3, maxSurge: 1, maxUnavailable: 0, and you change the image from 1.4.1 to 1.4.2.

  1. Kubernetes hashes the new Pod template and creates ReplicaSet v2 with 0 replicas.
  2. It scales v2 to 1 (4 Pods total, allowed by surge). It waits for that Pod to be Ready.
  3. Now it scales v1 down to 2 (3 Pods Ready: 2 old, 1 new). Repeat until v1 is 0 and v2 is 3.

At no point were fewer than 3 Pods Ready. If the new Pod never becomes Ready, step 2 never completes, the old Pods keep serving, and the rollout shows as stalled after progressDeadlineSeconds. That safe failure is the main value of the Deployment.

Things that trigger or do not trigger a rollout

  • Triggers: any change under spec.template (image, env, resources, probes, labels, annotations).
  • Does not trigger: changing replicas (scale only), or editing a ConfigMap the template merely references.
  • The selector is immutable after creation, so choose labels carefully; the Pod template labels must match it.
  • kubectl rollout restart adds a timestamp annotation to the template to force a new ReplicaSet.

Common bug: two Deployments with overlapping selectors fight over the same Pods. Keep the selector specific (app.kubernetes.io/name plus instance).

Remember: Deployment owns ReplicaSets, ReplicaSets own Pods. One ReplicaSet per template version.

What happens when a Pod is shut down, and how do you shut down gracefully? Intermediate

When a Pod is deleted (rolling update, scale-down, node drain) Kubernetes marks it Terminating, removes it from Service endpoints, runs the preStop hook if there is one, sends SIGTERM, waits up to terminationGracePeriodSeconds (30 s by default), then sends SIGKILL. A good app handles SIGTERM by finishing in-flight requests, closing connections and exiting before the grace period ends.

The catch is a race: endpoint removal and SIGTERM happen at about the same time, but it takes a moment for every node and load balancer to stop sending traffic. So some requests can arrive after SIGTERM. The fix is a short preStop sleep (a few seconds) so the Pod keeps serving while the removal spreads, then drain and exit. Spring Boot supports this with server.shutdown=graceful. This all depends on the app actually receiving SIGTERM, which needs exec-form ENTRYPOINT.

The sequence in detail

  1. Something decides the Pod must go (rolling update, scale-down, kubectl delete, node drain, eviction). The API server sets a deletion timestamp: the Pod is now Terminating.
  2. In parallel, two things start: the endpoints controller removes the Pod from every Service's endpoints (so kube-proxy and ingress controllers stop picking it), and the kubelet runs the preStop hook, if any.
  3. When preStop ends, the kubelet sends SIGTERM to the main process of each container.
  4. The kubelet waits until the process exits or until terminationGracePeriodSeconds (counted from the start of step 2, so preStop time is part of it) runs out.
  5. If still alive, SIGKILL. The Pod object is then deleted.

Why requests still arrive after SIGTERM

Step 2 runs in parallel. Removing a Pod from endpoints is an update that must be noticed by every kube-proxy and by the ingress controller or cloud load balancer, which can take seconds. During that window they may still send new requests. If your app closes its listener right at SIGTERM, those requests fail with connection refused or reset, which users see as 502 or 503.

A good config

lifecycle:
  preStop:
    exec: { command: ["sleep", "10"] }   # keep serving while endpoints propagate
terminationGracePeriodSeconds: 45        # > 10 s sleep + slowest request + shutdown time
# Spring Boot
server.shutdown=graceful
spring.lifecycle.timeout-per-shutdown-phase=25s

Sleep needs a sleep binary in the image; a distroless image has none, so use the built-in sleep action of preStop in recent Kubernetes versions (beta in 1.30, check support) or a tiny binary. During the drain the app should also make its readiness fail so no new connections are accepted, finish in-flight requests, close pools, then exit 0.

Pitfall: long-lived connections (WebSockets, gRPC streams) will not drain by themselves; the app must tell clients to reconnect. Also, a stuck shutdown hook means every deploy waits the full grace period, so measure it.

Remember: short preStop sleep, handle SIGTERM, drain, exit within the grace period. Exit 137 means it got SIGKILL.

What is a StatefulSet, and how is it different from a Deployment? Intermediate

A Deployment treats Pods as identical and interchangeable. A StatefulSet is for apps where each member has an identity, like a database or Kafka broker. It gives each Pod a stable name (db-0, db-1), a stable network name through a headless Service, its own PersistentVolumeClaim that is re-attached if the Pod is re-created, and ordered start and stop.

A headless Service has clusterIP: None, so DNS returns the individual Pod addresses, such as db-0.db.prod.svc.cluster.local. The volumes are kept by default when you scale down or delete, to protect data. The honest point: a StatefulSet does not make a database highly available. It supplies identity and storage; replication and failover still come from the database itself or an operator. Many teams use a managed database outside the cluster instead.

Why a Deployment is wrong for a database

Imagine a 3-node database run as a Deployment. Pod names are random and change, there is no per-Pod disk, and the cluster peers cannot tell which Pod is "node 2" after a restart. Replication configuration breaks. A StatefulSet exists to keep identity stable across restarts.

The four guarantees, with an example

A StatefulSet named kafka with 3 replicas and a headless Service named kafka-hs in namespace prod:

  1. Stable names: kafka-0, kafka-1, kafka-2. A re-created Pod keeps its name.
  2. Stable DNS: kafka-1.kafka-hs.prod.svc.cluster.local always points at that Pod, even after it moves node and gets a new IP.
  3. Stable storage: volumeClaimTemplates create data-kafka-0 etc. When kafka-0 is re-created it re-attaches the same PVC.
  4. Ordered operations: created 0, 1, 2 (each Ready before the next), deleted in reverse. Updates also go in reverse order, by default. podManagementPolicy: Parallel relaxes this for apps that do not need it.

Behaviour to know

  • Scaling down or deleting the StatefulSet does not delete PVCs by default, to protect data; newer versions have persistentVolumeClaimRetentionPolicy to opt into deletion (check the version in your cluster).
  • If a node dies, a StatefulSet Pod is not rescheduled instantly. Kubernetes avoids running two Pods with the same identity ("at most one" semantics), so recovery can need the node to be confirmed down or removed.
  • A ReadWriteOnce disk in zone A means the Pod must run in zone A; plan capacity per zone.

The honest limit

A StatefulSet manages identity and disks, not data correctness. Leader election, replication, backup and version upgrades are the database's job or an operator's (for example a Postgres or Kafka operator). For most application teams the better answer is a managed database or an operator; say that clearly in an interview.

Remember: StatefulSet = stable name + stable disk + ordered start. It is not automatic high availability.

When do you use a Job, a CronJob or a DaemonSet? Basic

A Job runs Pods until a task completes successfully, such as a migration or report. A CronJob creates Jobs on a cron schedule. A DaemonSet runs one Pod on every node, for agents like log collectors. A Deployment is for things that run forever.

Jobs retry failed Pods up to backoffLimit (6 by default), and the Pod's restartPolicy must be OnFailure or Never. For CronJobs, concurrencyPolicy (Allow, Forbid, Replace) decides what happens if the previous run is still going, and times are in UTC unless you set timeZone. Always make job code idempotent, because a retry or an overlapping run can happen. ttlSecondsAfterFinished cleans up finished Jobs.

How each one behaves

KindRunsEnds?Typical example
DeploymentN identical PodsNever; restarted when they exitREST API
JobPods until a number complete successfullyYesDB migration, one-off import
CronJobA new Job per schedule tickEach Job endsNightly report, cleanup
DaemonSetOne Pod on each (matching) nodeNeverLog shipper, node monitoring agent

Job settings that matter

  • completions and parallelism: run 10 successful Pods, 3 at a time.
  • backoffLimit: retries before the Job is marked failed (default 6, with growing delay).
  • activeDeadlineSeconds: hard time limit for the whole Job, a safety net against hangs.
  • restartPolicy: Never keeps failed Pods for log inspection; OnFailure restarts the container in the same Pod.
  • ttlSecondsAfterFinished: automatic cleanup so finished Pods do not pile up.

CronJob traps

  1. Overlap: a run that takes longer than the interval overlaps the next. concurrencyPolicy: Forbid skips the new run; Replace cancels the old one.
  2. Missed runs: if the controller was down, startingDeadlineSeconds decides whether a late run still starts.
  3. Time zone: UTC by default; set timeZone in recent versions or you will be an hour off after daylight saving shifts.
  4. At-least-once, not exactly-once: a Job can start more than one Pod for the same work in rare cases, so make the work idempotent (use a unique key or "already processed" check).

For DaemonSets, remember they need tolerations to run on tainted nodes (such as control-plane nodes), and a rolling update replaces them one node at a time. The usual CI/CD use of a Job: run a database migration as a pre-upgrade Helm hook Job and fail the release if it fails.

Remember: forever = Deployment, once = Job, scheduled = CronJob, per node = DaemonSet. Make jobs idempotent.

How does the scheduler decide where a Pod goes, and what are taints, tolerations and affinity? Intermediate

The scheduler filters out nodes that cannot run the Pod (not enough unreserved CPU or memory for its requests, a taint the Pod does not tolerate, a failed nodeSelector or affinity) and then scores the rest, usually favouring spread and balance. A taint on a node repels Pods; a toleration on a Pod allows it onto the tainted node. Affinity and nodeSelector attract Pods to nodes (or to other Pods).

Three replicas that all land on one node are not highly available: one node failure takes the service down. Remember: requests decide fit, taints repel, tolerations permit, affinity attracts, topology spread distributes. Spread replicas or one node failure is an outage.

What is a PodDisruptionBudget, and how do node drains and upgrades affect your service? Senior

A PodDisruptionBudget (PDB) tells Kubernetes how many replicas of an app may be down at once during voluntary disruptions such as kubectl drain, node upgrades or cluster autoscaler scale-down. Without one, a drain can evict all your Pods at the same moment and cause an outage even though everything was "managed". I set one for every multi-replica production service.

Voluntary versus involuntary

  • Voluntary: drain for node upgrade, autoscaler removing an underused node, eviction by an admin. PDBs apply to these through the eviction API.
  • Involuntary: node crash, kernel panic, out-of-memory kill, a zone failure. A PDB cannot stop these; only replicas spread across nodes and zones can help.

Example and what it does

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: orders }
spec:
  minAvailable: 2          # or maxUnavailable: 1
  selector: { matchLabels: { app: orders } }

With 3 replicas, a drain may evict one Pod; the next eviction waits until a replacement is Ready elsewhere, so you always keep 2 serving. During a node-pool upgrade the platform drains nodes one after another and respects this.

Pitfalls

  1. Too strict: minAvailable equal to replica count (or maxUnavailable: 0) makes eviction impossible, so node upgrades hang forever. Platform teams hate this.
  2. Single replica with a PDB: same blocking effect; a one-replica app is not highly available anyway.
  3. Unready Pods count as unavailable, so a PDB combined with a broken readiness probe can also block drains.
  4. All replicas on one node: the PDB does not help if that node dies; combine with spread constraints.

Combine PDB with a graceful shutdown (preStop and SIGTERM handling) so each eviction is invisible to users. This is the core of "zero-downtime during cluster upgrades".

Remember: PDB protects against voluntary disruption only. Set minAvailable below the replica count, and spread replicas across nodes.

5. Services, Ingress and configuration

What is a Service, how does it find Pods, and what are the types? Basic

A Service gives a stable name and virtual IP in front of a changing set of Pods, because Pod IPs change every time a Pod is replaced. It finds its Pods with a label selector, and it only sends traffic to Pods that are Ready. The types are ClusterIP (internal only, the default), NodePort (opens a port on every node), LoadBalancer (asks the cloud for an external load balancer) and ExternalName (a DNS alias).

Behind a Service, Kubernetes keeps a list of the matching Ready Pod IPs (the endpoints), and kube-proxy on each node turns the Service IP into one of them. Other Pods reach it by DNS: orders in the same namespace, or orders.prod.svc.cluster.local from anywhere. A NodePort uses ports 30000 to 32767 by default. When a Service gets no traffic, the cause is nearly always a label mismatch between the Service selector and the Pod labels, or Pods that are not Ready. kubectl get endpoints orders shows it at once: empty means no match.

Labels are the glue of Kubernetes: Services, ReplicaSets and kubectl get pods -l app=orders all select by them. Annotations are key-values not used for selection (tool settings). Namespaces split a cluster into areas for names, quotas and access, but are not hard security isolation.

The problem

Pods are replaced all the time and each new Pod gets a new IP. If service A hard-coded the IP of service B's Pod, it would break at the next deploy. A Service is a stable virtual IP and DNS name that load-balances over whichever Pods currently match.

How a request is routed, step by step

  1. Client Pod resolves orders (cluster DNS, CoreDNS) and gets the Service's ClusterIP, for example 10.96.12.5.
  2. It connects to 10.96.12.5:80. That IP does not belong to any interface; it is a virtual IP.
  3. kube-proxy on the client's node has installed rules (iptables or IPVS) that rewrite the destination to one of the endpoint Pod IPs, for example 10.1.4.7:8080, picked roughly at random.
  4. The Pod answers directly. No proxy process sits in the data path in the common modes.

The Service's port is what clients call; targetPort is the container's port. Mismatch there is the number one "Service exists but nothing works" bug.

apiVersion: v1
kind: Service
metadata: { name: orders }
spec:
  selector: { app: orders }        # must match Pod labels
  ports:
  - { port: 80, targetPort: 8080 } # client calls 80, container listens on 8080

The types, from narrow to wide

TypeReachable fromUse
ClusterIPInside the clusterService-to-service calls (default)
NodePortAny node IP and the port (30000-32767)Simple tests, or as a building block for a load balancer
LoadBalancerInternet or VPC via a cloud load balancerExposing one service directly
ExternalNameReturns a DNS CNAMEGive an external database an in-cluster name
Headless (clusterIP: None)DNS returns Pod IPs directlyStatefulSets, client-side load balancing

Pitfall: load balancing is per connection, not per request. A long-lived HTTP/2 or gRPC connection sticks to one Pod, so one Pod can get all the traffic. For gRPC use a headless Service with client-side balancing, or a mesh or L7 proxy. sessionAffinity: ClientIP gives sticky sessions if you need them.

Remember: Service = stable name + selector on labels + only Ready Pods. Empty endpoints means label mismatch or not Ready.

What is an Ingress, and how is it different from a LoadBalancer Service? Intermediate

An Ingress is a set of HTTP routing rules (by host and path) that lets one entry point route to many Services. A LoadBalancer Service gives one external load balancer for one Service, usually at cloud cost per service. An Ingress needs an Ingress controller installed in the cluster, such as NGINX or a cloud controller, because the Ingress object alone does nothing.

Ingress also handles TLS termination and, depending on the controller, rewrites and rate limits through annotations. It is HTTP and HTTPS only; for other protocols you use a LoadBalancer Service. Gateway API is the newer, more expressive standard that is replacing Ingress for many teams. The community ingress-nginx controller has been announced for retirement in 2026, so check which controller your cluster uses.

Why Ingress exists

With ten HTTP services, ten LoadBalancer Services means ten cloud load balancers, ten public IPs and ten bills, and no shared place to do TLS, redirects or auth. Ingress moves routing into one object that describes "this host and path goes to that Service", served by one shared entry point.

The two halves

  1. Ingress resource (YAML, you write it): the desired routing rules.
  2. Ingress controller (a Deployment, a platform team installs it): watches Ingress objects and configures a real proxy (NGINX, HAProxy, Envoy, or a cloud load balancer) to match. Without a controller the resource does nothing.
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata: { name: shop }
spec:
  ingressClassName: nginx
  tls: [{ hosts: [shop.example.com], secretName: shop-tls }]
  rules:
  - host: shop.example.com
    http:
      paths:
      - { path: /orders, pathType: Prefix, backend: { service: { name: orders, port: { number: 80 } } } }
      - { path: /users,  pathType: Prefix, backend: { service: { name: users,  port: { number: 80 } } } }

A request flows: client, DNS name pointing at the load balancer, controller Pod (terminates TLS, matches host and path), then directly to a backend Pod IP (most controllers skip the Service's own balancing and use the endpoints).

Ingress versus Gateway API

Ingress is deliberately small, so features such as rewrites, timeouts and header matching were added as controller-specific annotations that are not portable. Gateway API splits responsibilities (infrastructure owners define Gateways; app teams attach HTTPRoutes), supports more protocols and portable traffic splitting. It is the direction the ecosystem is moving, but plenty of clusters still run Ingress.

Common problems: wrong or missing ingressClassName (no controller picks it up), TLS secret in the wrong namespace, path type mismatch, and a 503 because the backend Service has no ready endpoints. cert-manager is the usual tool to get and renew TLS certificates automatically.

Remember: LoadBalancer = one Service per balancer. Ingress = one entry point, many routes, needs a controller.

How do ConfigMaps and Secrets work, and how do you consume them? Basic

A ConfigMap holds non-secret configuration and a Secret holds sensitive values like passwords and keys. A Pod consumes either as environment variables or as files in a mounted volume. The key facts: a Secret is only base64 encoded, not encrypted by default, and changes reach a running Pod only through mounted files, not environment variables.

env:
- name: DB_PASSWORD
  valueFrom: { secretKeyRef: { name: db-secret, key: password } }
envFrom:
- configMapRef: { name: orders-config }
volumeMounts:
- { name: cfg, mountPath: /etc/orders }

Environment variables are read once at container start, so a changed ConfigMap needs a Pod restart (kubectl rollout restart deploy/orders). Mounted files are updated in place after a delay of up to a minute or so, but not when mounted with subPath, and the app must re-read the file. Helm charts often add a checksum of the ConfigMap as a Pod annotation, so a config change triggers a rolling update on its own.

On Secret safety: base64 is not protection. I rely on RBAC to limit who can read Secrets, encryption at rest for etcd (configured by the cluster operator), and for serious setups an external secret manager (Vault, a cloud service, or the External Secrets operator). Never commit Secret YAML to Git unencrypted. Prefer mounting as files over env vars, since env vars leak into logs and crash dumps more easily.

Why configuration lives outside the image

The same image should run in dev, test and prod. Only the configuration differs: database URL, feature flags, credentials. If you rebuilt the image per environment, what you tested would not be what you ship. So the image stays generic and Kubernetes injects configuration at start (the "twelve-factor" idea).

Secret details that get asked

  • Values are base64 only so binary data fits in YAML. echo c2VjcmV0 | base64 -d decodes it. Anyone with read access to Secrets, or to the repo if you committed the YAML, has the value.
  • Real protection comes from: RBAC (who can get secrets), encryption at rest in etcd (a cluster setting, ideally with a KMS), a secret manager integration, and not committing Secrets to Git (use Sealed Secrets, SOPS or External Secrets).
  • Size limit is about 1 MiB per object. Mark them immutable: true to prevent accidental changes and reduce API load.
  • Secret types include kubernetes.io/tls and kubernetes.io/dockerconfigjson (registry credentials for imagePullSecrets).

A neat practice: put a hash of the config in a Pod annotation so a config change rolls the Pods automatically (see the config-change scenario).

Remember: Secret is base64, not encryption. Env vars need a restart to change, mounted files update eventually.

6. Probes, resources, scaling and rollouts

Explain liveness, readiness and startup probes. How do they differ and what goes wrong with them? Intermediate

Liveness asks "is this container stuck beyond repair?" and a failure restarts it. Readiness asks "can it take traffic right now?" and a failure removes the Pod from Service endpoints without restarting it. Startup asks "has it finished booting?" and holds off the other two until it passes, which protects slow-starting apps like Spring Boot.

startupProbe:   { httpGet: { path: /actuator/health/liveness,  port: 8080 }, periodSeconds: 5, failureThreshold: 30 }  # up to 150 s to boot
readinessProbe: { httpGet: { path: /actuator/health/readiness, port: 8080 }, periodSeconds: 5 }
livenessProbe:  { httpGet: { path: /actuator/health/liveness,  port: 8080 }, periodSeconds: 10, failureThreshold: 3 }

The mistakes cause real outages. The worst: a liveness probe that checks the database or another service. When the database is down, every Pod fails liveness and restarts forever, turning a small outage into a big one. Liveness should check only that the process itself is alive. Dependency checks belong, carefully, in readiness. Other traps: a liveness probe with a short timeout and no startup probe kills slow-booting apps in a loop, and a readiness probe that fails under load removes all Pods at once. Spring Boot Actuator (2.3 and later) exposes separate liveness and readiness endpoints.

What each probe is really for

Kubernetes cannot see inside your app. It knows the process is running, not whether it is useful. Probes are how you tell it.

ProbeQuestionOn failureTypical check
StartupHas the app finished booting?Container restarted after the limit is exceeded; liveness and readiness are held off until it passesSame endpoint as liveness, generous threshold
ReadinessCan it serve traffic right now?Removed from Service endpoints; keeps running; re-added when it passesApp up and (carefully) essential dependencies usable
LivenessIs it stuck, deadlocked, beyond self-recovery?Container killed and restartedCheap local check, no dependencies

Probe mechanics

  • Types: httpGet (2xx or 3xx is success), tcpSocket (port opens), exec (command exits 0), and grpc.
  • Timing knobs: initialDelaySeconds, periodSeconds, timeoutSeconds (default 1 s, often too tight for a busy JVM), failureThreshold, successThreshold.
  • Time to detect a failure is about periodSeconds x failureThreshold. The startup budget in the example is 5 s x 30 = 150 s.

A failure timeline that shows why probes matter

  1. A new Pod starts; the JVM takes 60 s to boot. Startup probe is failing, but it has 150 s, so nothing is killed.
  2. The app comes up; startup passes; readiness starts and passes after a few seconds; the Pod joins the Service endpoints.
  3. Later the app deadlocks. Readiness might still pass (if it only pings a trivial endpoint) but liveness fails 3 times in a row, 30 s later the container is restarted.
  4. During a heavy GC pause readiness fails once or twice and the Pod is briefly removed from traffic, then comes back. That is the intended behaviour of readiness.

Design rules

  • Liveness: only things a restart can fix. A database being down is not fixed by restarting your Pod.
  • Readiness: include dependencies only if your app truly cannot serve without them, and prefer degraded modes; if every replica shares one broken dependency, all go unready at once and you get a full outage with no capacity left.
  • Readiness is also what rolling updates and PDBs rely on, so make it honest.
  • In Spring Boot use the dedicated health groups (management.endpoint.health.probes.enabled=true), which wire the app's state to the liveness and readiness endpoints, and reports "refusing traffic" during graceful shutdown.

Remember: liveness = restart, readiness = traffic, startup = give it time. Never put dependency checks in liveness.

What are resource requests and limits, and how do they differ for CPU and memory? Intermediate

A request is what the Pod is guaranteed and what the scheduler uses to pick a node. A limit is the ceiling. Going over the CPU limit only throttles the container, but going over the memory limit gets it killed with OOMKilled. So CPU is compressible and memory is not.

resources:
  requests: { cpu: "250m", memory: "512Mi" }   # 250 millicores = a quarter of a core
  limits:   { memory: "512Mi" }                 # often no CPU limit

The scheduler only looks at requests, never at actual usage. Set them too high and you waste nodes; too low and Pods get crowded onto a node and starve each other. The Pod's QoS class follows from the settings: Guaranteed (requests equal limits for every container), Burstable (some requests set), BestEffort (none). Under node pressure BestEffort Pods are evicted first. For memory I set request equal to limit, since memory cannot be taken back without killing. For CPU many teams set a request but no limit, because CPU limits throttle bursts and add latency even when the node is idle; this is debated, so say "it depends" with the reason. CPU throttling shows up as mysterious latency spikes. The HPA's utilization percent is measured against requests.

Two different jobs

A request is a reservation: "my Pod needs at least this". The scheduler adds up requests on each node and refuses to place a Pod where they would not fit. It also sets the CPU weight the Pod gets when the node is busy. A limit is enforcement at run time by the kernel: cgroup memory limit and CPU quota.

Why CPU and memory differ

  • CPU is compressible. If a Pod wants more than its limit, the kernel simply pauses it for part of each 100 ms period. With a limit of 500m the container can use 50 ms of CPU time per 100 ms across all threads; a multi-threaded JVM can burn that budget quickly and then stall. Result: no crash, but latency spikes.
  • Memory is not compressible. You cannot take back memory a process already holds without killing it. Over the limit means OOM kill.

An example of the effect

A node has 4 CPUs. Four Pods each request 1 CPU: the node is "full" for scheduling even if they idle at 100m. A fifth Pod stays Pending: "Insufficient cpu". That is why oversized requests waste money, and why undersized requests (say 100m for an app that uses 1 core) allow too many Pods per node and cause noisy-neighbour slowdowns.

QoS and eviction

QoS classConditionEvicted
GuaranteedEvery container has CPU and memory requests equal to limitsLast
BurstableAt least one request or limit, not all equalMiddle (those using more than their request go first)
BestEffortNo requests or limitsFirst

How to choose numbers

  1. Load test or observe in production: take typical (p50 to p90) usage for the CPU request and peak plus margin for memory.
  2. Memory request = memory limit (so the Pod is not overcommitted and not OOMKilled because the node ran short).
  3. CPU: set a request; a limit is a trade-off. Without it, a noisy Pod can use idle CPU (good for latency) but may also starve others when everyone bursts (requests still guarantee a fair share). Some platforms mandate limits for cost control. Say "I would measure for throttling (container_cpu_cfs_throttled_periods_total) and decide".
  4. Use the Vertical Pod Autoscaler in recommendation mode, or tools like Goldilocks, to find real values.

Namespaces often have a LimitRange (defaults) and ResourceQuota (totals). A Pod without requests in a quota-controlled namespace may be rejected.

Remember: requests place, limits cap. CPU over limit = throttled, memory over limit = killed.

How does the Horizontal Pod Autoscaler work, and what are its pitfalls? Intermediate

The HPA checks a metric about every 15 seconds, usually average CPU, and changes the Deployment's replica count with this formula: desired = ceil(current replicas x current metric / target metric). If CPU averages 90% against a 60% target with 4 Pods, it asks for ceil(4 x 90/60) = 6. It needs the metrics-server installed and CPU requests set on the Pods.

The CPU percentage is relative to the request, not the limit. No request means no HPA, and a request that is far too high or low makes the percentage meaningless. Pitfalls: scaling takes time (metric lag, image pull, JVM warm-up, readiness), so it cannot absorb a sudden spike; it scales down slowly on purpose (a 5-minute stabilization window by default) to avoid flapping; and CPU is a poor signal for I/O-bound services, where requests per second or queue length (custom metrics, or KEDA) fits better. Also set minReplicas at 2 or more for availability, and make sure the cluster has room, or new Pods just sit Pending. Do not combine HPA on CPU with a fixed replicas in your Deployment YAML, or each apply resets the count.

The control loop, with a worked example

Setup: Deployment with 4 Pods, each requesting 500m CPU; HPA target 60% average CPU utilization; min 2, max 10.

  1. metrics-server reports each Pod's usage; say they use 450m each. Utilization = 450/500 = 90%.
  2. Desired = ceil(4 x 90 / 60) = 6. The HPA writes replicas: 6 to the Deployment.
  3. Pods are created, scheduled (maybe a node must be added first), pull the image, boot, pass readiness. Only then do they reduce load.
  4. Usage drops to 40%: ceil(6 x 40/60) = 4. But scale-down waits for the stabilization window (5 minutes by default) and uses the highest recommendation in that window, to avoid thrashing.

A tolerance (about 10%) also prevents tiny changes from causing action. Scale-up is allowed quickly; the behavior field lets you tune both directions (for example add at most 4 Pods per minute).

How long is the real lag?

Metric scrape (about 15-60 s) + HPA sync (15 s) + node provisioning if needed (1-3 min) + image pull + JVM start (30-90 s) + readiness. Realistically 1 to 5 minutes. A flash crowd that arrives in 10 seconds will hit your existing replicas, so autoscaling is for trends, not spikes; for spikes you need headroom (a higher min, or over-provisioned capacity) and good load shedding.

Choosing the metric

WorkloadBetter signal

Related autoscalers

HPA changes the Pod count. VPA changes Pod requests (usually requires a restart; do not let VPA and HPA both act on CPU). The Cluster Autoscaler (or Karpenter) adds nodes when Pods are Pending. They work as a chain: HPA creates Pods, the node autoscaler makes room. Missing requests, a max that exceeds cluster quota, and a database that cannot take more connections are the usual failures; more replicas also means more DB connections, so size the pool per Pod.

Remember: HPA = ceil(current x metric / target), measured against requests. Reactive and slow, so keep a sensible minimum.

How does a rolling update work, and how do maxSurge and maxUnavailable change it? Intermediate

On a template change the Deployment creates a new ReplicaSet and shifts Pods over in small steps: start new Pods, wait until they are Ready, then stop old ones. maxSurge is how many extra Pods above the desired count may exist at once, and maxUnavailable is how many below it may be missing. Both default to 25%. For zero capacity loss I set maxUnavailable: 0 and maxSurge: 1 (or 25%).

This only works safely if the readiness probe is honest: Kubernetes trusts "Ready". If the new version never becomes Ready, the rollout stalls with old Pods still serving, which is a safe failure. kubectl rollout status shows progress and gives up after progressDeadlineSeconds (600 s default). Your app must also support both versions running at once, so database changes should be backward compatible (expand, then migrate, then contract). The alternative strategy Recreate kills all old Pods first, with downtime. Blue-green and canary releases need extra tooling (an ingress, a service mesh, or Argo Rollouts).

The two knobs in numbers

replicasmaxSurgemaxUnavailableMeaning during rollout
425% (1)25% (1)Between 3 and 5 Pods exist; at least 3 Ready. Fast, small capacity dip.
410Always 4+ Ready, up to 5 Pods. Slower, needs one spare slot of capacity.

4100%0Blue-green-like: start 4 new, then remove old. Needs double capacity.

Percentages round up for surge and down for unavailable. Both cannot be zero.

Why your readiness probe and shutdown handling decide success

The controller removes an old Pod as soon as enough new Pods are Ready. If your readiness probe says "ready" while the app is still warming caches, traffic hits a cold Pod. If the old Pod drops connections when it terminates, users see errors even though the rollout looks perfect. minReadySeconds adds a pause after a Pod becomes Ready before it counts as available, a cheap safety net.

When a rollout goes wrong

  • New Pods CrashLoop or never become Ready: rollout stalls with old Pods still serving. Check kubectl rollout status, then describe and logs of the new Pods. Undo if needed.
  • Two versions run at once, so APIs, messages and database schema must be compatible with both: use expand-then-contract migrations and tolerant readers.
  • Resource shortage: surge Pods stay Pending because there is no room for the extra Pod; set maxSurge 0 and maxUnavailable 1, or add capacity.

Other strategies

Recreate: stop all, then start all (downtime; needed when two versions cannot coexist, such as a single-writer schema change). Blue-green: run a full second environment and switch the Service selector or route instantly; easy rollback, double cost. Canary: send 5% then 25% then 100% of traffic to the new version while watching metrics; implemented with ingress weights, a service mesh, or Argo Rollouts and Flagger, which can abort automatically on SLO breach.

Remember: maxSurge adds, maxUnavailable removes. For no capacity drop use maxUnavailable 0 and trust honest readiness probes.

How do you roll back a bad release in Kubernetes? Basic

I run kubectl rollout undo deployment/orders, which returns the Deployment to the previous ReplicaSet, or --to-revision=N for an older one. With Helm it is helm rollback orders N. In a Git-driven setup I revert the commit and let the pipeline redeploy, so Git stays the source of truth.

kubectl rollout history deploy/orders
kubectl rollout undo deploy/orders
kubectl rollout status deploy/orders

Rollback only reverts the Pod template (and in Helm, the manifests). It does not undo a database migration, and it does not undo changes to a ConfigMap or Secret that live outside the template. That is why migrations must be backward compatible. A good rollback also needs a real image tag for the old version: with latest there is nothing to go back to. If a rollout is stuck halfway, kubectl rollout pause and resume let you stop and continue it.

What a rollback actually does

Each Deployment revision is a ReplicaSet kept with its Pod template. rollout undo copies the old template back into the Deployment's spec. That counts as a template change, so the normal rolling update runs again, this time towards the old version. It is just a new rollout in reverse, and respects the same surge, unavailable and readiness rules.

Choosing the right rollback tool

How you deployRoll back withNote
kubectl applykubectl rollout undoNext apply of the old YAML would redo the bad version; fix the source too
Helmhelm rollback REL REVRestores all chart objects (ConfigMaps, Services) to that revision, not only the Deployment
GitOps (Argo CD, Flux)git revert and let it syncManual kubectl changes get overwritten; Git is the truth

What rollback cannot fix

  • Database migrations already applied. If v2 dropped a column, v1 breaks. Therefore: expand (add nullable column), deploy code that handles both, migrate, and only later contract (drop) in a separate release.
  • Messages and events already published in a new format that old consumers cannot read.
  • Mutable image tags: you need the old image to still exist. Registry retention rules must not delete recent releases.
  • History limit: revisionHistoryLimit bounds how far back you can go.

Decision rule

If a release is clearly bad and the change is only code, roll back first, investigate afterwards (restore service quickly). If a data change is involved, think before undoing: sometimes a forward fix is safer. Feature flags make this easier by turning the new behaviour off without a deploy. In the incident, state the sequence aloud: confirm the signal (error rate, latency), roll back, verify metrics recover, then write the post-mortem.

Remember: rollout undo, helm rollback, or git revert. Rollback does not undo data changes.

7. Storage and day-to-day kubectl

Explain PersistentVolume, PersistentVolumeClaim and StorageClass. Intermediate

A PersistentVolume (PV) is a piece of real storage in the cluster. A PersistentVolumeClaim (PVC) is a Pod's request for storage of some size and access mode. A StorageClass says how to create storage on demand, for example a cloud SSD. In practice I write a PVC, name a StorageClass, and Kubernetes provisions a PV and binds it.

The Pod mounts the PVC, so the app never knows about the underlying disk. The access mode matters: ReadWriteOnce means one node at a time can mount it read-write, which is what a block disk gives you, while ReadWriteMany needs shared file storage (NFS, EFS). Cloud disks are tied to one availability zone, so a Pod that must move zones cannot take its disk with it. The reclaim policy decides whether data is kept or deleted when the PVC is deleted. For stateful apps, a StatefulSet creates one PVC per Pod.

Why three objects?

It separates who owns what. The platform team knows the real storage (cloud disks, NFS) and defines StorageClasses. The application developer only says "I need 20 Gi of fast read-write storage" in a PVC. The result: app YAML stays the same on any cloud.

The lifecycle with dynamic provisioning

  1. You create a PVC naming storageClassName: fast-ssd, 20Gi, ReadWriteOnce.
  2. The provisioner for that class (a CSI driver) creates a real disk in the cloud and a PV object for it.
  3. The PVC binds to that PV. Many classes use WaitForFirstConsumer, which delays creation until a Pod is scheduled so the disk is created in the same zone as the Pod.
  4. A Pod lists the PVC under volumes and mounts it. Kubernetes attaches the disk to the node and mounts it into the container.
  5. If the Pod is replaced, the PVC and data stay. When you delete the PVC, the reclaim policy (Delete or Retain) decides what happens to the disk.
apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: orders-data }
spec:
  accessModes: [ReadWriteOnce]
  storageClassName: fast-ssd
  resources: { requests: { storage: 20Gi } }

Access modes

ModeMeaningBacked by
ReadWriteOnce (RWO)Read-write by a single node (several Pods on that node can share)Block disks (EBS, Persistent Disk)
ReadWriteOncePodOnly one Pod in the clusterNewer CSI drivers
ReadOnlyManyMany nodes, read onlyShared file storage
ReadWriteMany (RWX)Many nodes read-writeNFS, EFS, CephFS

Pitfalls: a Pod stuck Pending because the PVC is Pending (no matching class, quota, or zone mismatch); a Deployment with an RWO volume and a rolling update, where the new Pod on another node cannot attach the disk while the old Pod still has it (use Recreate or a StatefulSet); volumes only expand if the class allows allowVolumeExpansion; and snapshots and backups are separate from "persistent", because a deleted PVC with Delete policy takes the data with it.

Remember: PVC asks, PV provides, StorageClass creates on demand. RWO = one node at a time.

Which kubectl commands do you use every day, and what does each tell you? Basic

Mostly get to see state, describe to see why (its Events section is the most useful part), logs for the app output, exec to look inside, and rollout to manage releases. For debugging, describe and logs --previous solve most problems.

kubectl get pods -o wide -n prod            # state, node, IP
kubectl describe pod orders-abc             # Events: why it is Pending, killed, not Ready
kubectl logs orders-abc --previous          # logs of the crashed container
kubectl exec -it orders-abc -- sh           # shell inside
kubectl port-forward svc/orders 8080:80     # reach it from the laptop
kubectl top pod --containers                # real CPU and memory use
kubectl get events --sort-by=.lastTimestamp
kubectl diff -f f.yaml                      # preview before apply

kubectl apply is declarative: it creates or updates objects to match the file, so it is safe to re-run, while create fails if the object exists. Always check kubectl config current-context before destructive commands.

A working loop for any problem

  1. What exists? kubectl get pods,svc,deploy,ing -n prod. Add -o wide for node and IP, --show-labels for labels, -w to watch changes.
  2. Why is it this way? kubectl describe pod X. Scroll to Events at the bottom: scheduling failures, image pulls, probe failures, OOM kills show up there.
  3. What did the app say? kubectl logs X -c container; -f to follow; --previous for the last crashed run; -l app=orders --tail=50 for many Pods.
  4. Look inside: kubectl exec -it X -- sh or an ephemeral kubectl debug container.
  5. Reach it: kubectl port-forward to test without going through Ingress.

Useful formatting and filtering

kubectl get pod X -o yaml                      # full object including status
kubectl get pods -o jsonpath='{.items[*].spec.containers[*].image}'
kubectl get events --sort-by=.lastTimestamp -n prod
kubectl api-resources                          # list kinds
kubectl explain deployment.spec.strategy       # built-in docs for any field
kubectl auth can-i delete pods -n prod         # check your own permissions

Declarative versus imperative

kubectl apply -f compares your file with the live object (and the last applied configuration) and patches the difference; running it twice is harmless. create fails if the object exists. kubectl edit and scale change live state quickly but leave Git out of date, so use them for emergencies and reconcile later. Use --dry-run=client -o yaml to generate a starting YAML and kubectl diff to preview.

Safety habits

  • Check kubectl config current-context and namespace before anything destructive; many outages were a command run in the wrong cluster. Tools such as kubectx and a prompt that shows the context help.
  • kubectl top needs metrics-server and shows current usage, not history; use your monitoring stack for trends.
  • Deleting a Pod managed by a Deployment just causes a replacement, which is a legitimate way to restart one Pod; deleting the Deployment removes the app.

Remember: get shows what, describe shows why, logs --previous shows the crash.

8. Helm

What is Helm, and what problem does it solve? Basic

Helm is the package manager for Kubernetes. A chart is a bundle of templated YAML plus default settings. I install it into a cluster with my own values, and that installed instance is a release. It solves two problems: plain YAML has no way to reuse one set of files across dev, test and prod without copy-paste, and it has no notion of "version 3 of this app" that I can upgrade or roll back as a unit.

Helm 3 has no server-side part (Tiller was removed); it keeps release history as Secrets in the release's namespace. That history is what makes helm rollback possible. Alternatives are Kustomize (patches plain YAML, no templating or history) and GitOps tools like Argo CD that often use Helm underneath. I use Helm when I need parameterised packaging and release history, and Kustomize for simple per-environment overlays.

The problem in a picture

One app in Kubernetes is often 6 to 10 YAML files: Deployment, Service, ConfigMap, Ingress, HPA, ServiceAccount, PDB. For three environments you would copy them three times and change a few lines (image tag, replicas, hostname, resources). Copies drift, and "upgrade everything and roll it all back as one" has no meaning in plain kubectl. Helm fixes this by templating the differences and recording each install as a versioned release.

Vocabulary

TermMeaning
ChartThe package: templates, default values, metadata, dependencies
ValuesThe settings you supply to fill in the templates
ReleaseOne named installation of a chart in a namespace (orders in prod)
RevisionA numbered version of a release: each install, upgrade or rollback adds one
Repository / OCI registryWhere charts are published and downloaded from

What helm install does

  1. Loads the chart and merges your values over the defaults.
  2. Renders the templates into plain Kubernetes YAML locally (no server-side templating).
  3. Sends that YAML to the API server and stores a record of it (revision 1) as a Secret named like sh.helm.release.v1.orders.v1.
  4. On upgrade, it renders again, diffs against the last revision and applies the changes as revision 2.

Subtleties interviewers like: Helm manages the objects it created; if someone edits them with kubectl, Helm's three-way merge (old manifest, new manifest, live state) tries to preserve or reconcile those changes. CRDs placed in a chart's crds/ folder are installed once and not upgraded or deleted by Helm, so CRD upgrades need a separate process. Helm is also commonly a rendering engine for GitOps tools, which then do the applying themselves.

Remember: chart = package, values = settings, release = installed instance with history.

What is inside a Helm chart, and how do values and templates work? Intermediate

A chart is a folder with Chart.yaml (name and version), values.yaml (defaults), a templates/ folder of Kubernetes YAML written with Go templating, and optional dependencies. Templates read settings through .Values, so the same chart serves every environment, and I override defaults per environment with -f prod.yaml or --set.

# templates/deployment.yaml (excerpt)
replicas: {{ .Values.replicaCount }}
image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
resources: {{- toYaml .Values.resources | nindent 12 }}

# values-prod.yaml
replicaCount: 5
image: { tag: "1.4.2" }

Precedence, lowest to highest: chart defaults, then each -f file in order, then --set. Built-in objects like .Release.Name and .Chart.Name are also available. Before deploying I preview with helm template (render locally) and helm lint; helm upgrade --dry-run and the helm-diff plugin compare against the cluster. Two cautions on secrets and values: do not commit real secrets in values files (use an external secret mechanism or a tool like helm-secrets or sealed secrets), and keep a values file per environment in Git.

The layout

orders/
  Chart.yaml          # name, version (chart), appVersion (the app)
  values.yaml         # defaults
  templates/
    deployment.yaml
    service.yaml
    _helpers.tpl      # reusable named templates (labels, names)
    NOTES.txt         # text printed after install
  charts/             # dependency charts (subcharts)

Remember two versions: version is the chart's own version (bump when templates change); appVersion is informational, the application release the chart ships.

Templating essentials

  • {{ .Values.x }} reads a value; {{ .Release.Name }}, {{ .Chart.Name }}, {{ .Release.Namespace }} are built in.
  • {{ if .Values.ingress.enabled }} ... {{ end }} makes whole objects optional; {{ range }} loops; {{ default "x" .Values.y }} sets fallbacks; {{ required "msg" .Values.z }} fails with a clear message when a value is missing.
  • toYaml with nindent inserts a block with correct indentation. Indentation mistakes are the most common template bug; helm template shows the output so you can see them.
  • include "orders.labels" . pulls shared snippets from _helpers.tpl so labels and selectors are written once.

Value overrides in practice

helm upgrade --install orders ./orders -n prod \
  -f values.yaml -f values-prod.yaml \
  --set image.tag=$GIT_SHA

Later sources win. Typical split: values.yaml holds sane defaults, values-prod.yaml holds environment differences, and CI sets only the image tag with --set. Lists are replaced wholesale rather than merged, which surprises people.

Good chart habits

  1. Put the checksum of ConfigMaps into Pod annotations so config changes roll Pods.
  2. Expose resources, probes, security context, and replicas as values, with safe defaults.
  3. Add a values.schema.json to validate input early.
  4. Run helm lint, helm template | kubeconform and a policy scan in CI before installing.

Remember: defaults in values.yaml, overrides with -f then --set. Always helm template before you deploy.

How do helm upgrade and helm rollback work, and which flags do you use? Intermediate

Each helm upgrade renders the chart again and applies the difference as a new numbered revision of the release. helm rollback orders 3 re-applies the manifests of revision 3, as a new revision. In CI I use one command that works for first install and later upgrades.

helm upgrade --install orders ./chart -n prod -f values-prod.yaml \
     --atomic --timeout 5m
helm history orders -n prod
helm rollback orders 3 -n prod

--install installs if the release does not exist. --atomic (which implies waiting) rolls back automatically if the upgrade fails or times out, so the pipeline fails cleanly instead of leaving a half-deployed release. Without waiting, Helm reports success when the YAML is accepted, not when Pods are Ready. Rollback restores the Kubernetes objects, not data. Helm hooks (annotation helm.sh/hook: pre-upgrade) run a Job at a point in the release, which is the usual place for a database migration. If a cancelled pipeline leaves a release in pending-upgrade, check helm history and use helm rollback to a good revision.

What the flags buy you

FlagEffect
--installInstall if the release is missing, so one command covers first deploy and upgrades
--waitWait until Deployments are Ready (and Jobs complete) before returning success
--atomicImplies wait; if it fails or times out, automatically roll back to the previous revision
--timeout 5mHow long to wait before giving up (default 5 minutes)
--history-maxLimit how many revisions (Secrets) are kept; default 10
--reuse-values / --reset-valuesReuse the last release's values or reset to chart defaults; --reuse-values can hide new chart defaults, so many teams avoid it and pass all values every time

A release timeline

  1. CI runs helm upgrade --install --atomic with the new image tag.
  2. Helm renders, applies, creates revision 12 (status pending-upgrade).
  3. Kubernetes does a rolling update; Helm waits for readiness.
  4. Success: revision 12 is deployed and 11 is superseded. Failure: Helm applies revision 11 again as revision 13 and the CI step fails, so everyone knows.

Hooks for migrations

metadata:
  annotations:
    "helm.sh/hook": pre-upgrade
    "helm.sh/hook-weight": "0"
    "helm.sh/hook-delete-policy": before-hook-creation,hook-succeeded

A hook Job runs before the new Pods roll out and Helm waits for it; if it fails the upgrade fails. Be careful: the migration runs against the live database while old Pods still serve, so it must be backward compatible.

Gotchas

  • Rollback goes forward in history: it creates a new revision with old content.
  • A stuck pending-install or pending-upgrade state (from a killed pipeline) blocks further upgrades with "another operation in progress"; fix by rolling back, or as a last resort remove the stuck release Secret.
  • Resources changed manually in the cluster can conflict with the chart; helm diff upgrade (plugin) shows what will change before you do it.
  • Helm 3 uses a three-way merge; immutable fields (a Deployment selector, a Job template) cannot be changed in place and the upgrade fails, needing recreate.

Remember: upgrade --install --atomic in CI, rollback by revision number. Success means accepted, only --wait or --atomic means Ready.

Helm or Kustomize? How would you choose? Intermediate

Helm templates the YAML and tracks releases, so I choose it to package and distribute an app with many settings and when I want install, upgrade and rollback. Kustomize patches plain YAML with overlays, so I choose it when I own the YAML and only need small per-environment differences without a template language. Many teams combine them.

Helm's strength is a rich ecosystem of third-party charts (databases, ingress controllers) and release history. Its weakness is templates that become hard to read, and Go-template whitespace bugs. Kustomize's strength is that the base is valid YAML you can read and apply; its weakness is that it has no release history or packaging, and deep customisation gets awkward. Kustomize is built into kubectl apply -k.

How each one thinks

Helm: write YAML with holes in it ({{ }}), fill the holes with values. Output depends on logic you write in the template. Kustomize: write complete, valid YAML (the base), then describe patches in overlays. Nothing is a template; the result is the base with changes applied.

# Kustomize overlay for prod
resources: [../../base]
replicas: [{ name: orders, count: 5 }]
images: [{ name: orders, newTag: 1.4.2 }]
patches:
- target: { kind: Deployment, name: orders }
  patch: |-
    - op: add
      path: /spec/template/spec/containers/0/resources
      value: { requests: { cpu: 500m } }

Comparison

Decision rule

  • Installing someone else's software (ingress controller, Prometheus, Kafka): Helm, because the chart exists and exposes the right knobs.
  • A service you build, deployed to a few environments with small differences: Kustomize is often simpler; Helm if you want to publish a reusable chart for many teams.
  • With GitOps (Argo CD, Flux): either works, and combining is common, for example Helm to render a vendor chart and Kustomize to patch the output.

Whatever you choose, keep one source of truth in Git, review the rendered output, and keep environment differences small, because every difference between staging and production is a place for a surprise.

Remember: Helm = templates + releases. Kustomize = patch plain YAML. Pick by whether you ship a package or tweak your own YAML.

9. Troubleshooting a failing app

A deployed app is not working. What is your step-by-step approach? Intermediate

I follow the request path from the Pod outwards. First, are the Pods Running and Ready? Then, what do the logs and events say? Then, does the Service have endpoints? Then, does the Ingress route to it? The status of the Pod tells me where to look, and kubectl describe Events usually contain the answer.

For a Ready Pod with no response, kubectl get endpoints svc (empty means selector mismatch), then kubectl port-forward to test the Pod directly, then check ports (Service targetPort must match the container port), and only then Ingress and network policies. Also check kubectl config current-context so I am debugging the right cluster.

The layered approach

Think of the request path: DNS and Ingress, Service, Pod, container, app, dependencies. Debug from where you can prove things are fine, and move to the first layer where they are not. Do not guess; each step has a command that gives a yes or no.

Worked example

  1. Users report 503. get pods shows orders-7d9 0/1 Running (not Ready).
  2. describe shows "Readiness probe failed: HTTP probe failed with statuscode: 503".
  3. logs shows "cannot connect to redis: timeout". The app reports unready because Redis is unreachable.
  4. Check the Redis Service from a debug Pod: DNS resolves but connection times out. A recent NetworkPolicy change blocked the namespace; fix the policy.

Other tools in the box: kubectl get events for the namespace; kubectl top for resource pressure; node conditions via kubectl describe node (MemoryPressure, DiskPressure); and the monitoring dashboards. Say aloud that you first check what changed recently (deploy, config, certificates expiring, quotas), since most incidents follow a change.

Remember: status picks the command: describe for Pending and pulls, logs --previous for crashes, endpoints for no traffic.

A Pod is in CrashLoopBackOff, or keeps restarting with OOMKilled. What does it mean and how do you fix it? Basic

CrashLoopBackOff means the container starts, exits, and Kubernetes keeps restarting it with a growing delay (10 s, 20 s, up to 5 minutes). It is a symptom, not a cause. I run kubectl logs --previous to see why the last run died, and kubectl describe pod to see the exit code and reason.

  • Exit 1 with a stack trace: an app error, often a bad config, a missing env var, or a database it cannot reach.
  • Exit 137 and reason OOMKilled: over the memory limit. Raise the limit or fix the leak, and for Java check heap versus the limit (see the JVM question).
  • Exit 137 without OOMKilled: killed by SIGKILL, often a failing liveness probe or the grace period expiring.
  • Exit 126 or 127: command not executable or not found, a Dockerfile or command mistake.
  • Exit 143: terminated by SIGTERM, a normal stop.

If it crashes too fast to exec into, override the command to sleep to get a shell, or use kubectl debug to attach a debug container (useful too for distroless images with no shell). Also check CreateContainerConfigError, which is different: a referenced ConfigMap or Secret is missing.

What the status words mean

CrashLoopBackOff is not an error by itself; it is Kubernetes saying "this container keeps exiting, I am waiting longer between restarts". The wait doubles from 10 s up to a cap of 5 minutes and resets after the container runs cleanly for a while. The reason is in the previous run's exit code and logs.

A short diagnosis routine

  1. kubectl describe pod X: look at "Last State: Terminated", the Reason and Exit Code, and Events.
  2. kubectl logs X --previous: the final lines before the crash.
  3. Match the cause:
SymptomLikely causeFix
Stack trace, exit 1Bad config, missing env var, cannot reach DB at startFix config, add retry, check Secret keys
OOMKilled, exit 137Memory over limitRaise limit or fix heap or leak
Exit 137, no OOMKilled, probe eventsLiveness probe killed it (or grace period expired)Startup probe; fix probe timing
Exit 127/126Binary not found or not executable (wrong ENTRYPOINT, wrong architecture, CRLF line endings in a script)Fix image or command
Exit 0 but restartsThe process finished; Deployment expects a long-running processUse a Job, or fix the app (daemon forks into background)
Permission deniedNon-root user cannot write to a pathFix ownership, fsGroup, or an emptyDir

OOMKilled in two flavours

Container OOMKilled: the container's own cgroup limit was exceeded. Node-level eviction: the node ran out of memory and evicted Pods (reason Evicted), mostly BestEffort or those above their request. Look at kubectl describe node for MemoryPressure.

When the container dies too fast to inspect, temporarily set command: ["sleep","3600"], then exec in and run the real start command by hand; or use kubectl debug --copy-to to clone the Pod with a debug container. A different status, CreateContainerConfigError, means a ConfigMap, Secret or key referenced by the Pod does not exist, so the container never even starts.

Remember: logs --previous plus the exit code. 137 is killed (OOM or probe), 1 is the app, 127 is wrong command.

A Pod stays Pending, or shows ImagePullBackOff. What are the possible causes? Intermediate

Pending means the scheduler has not placed the Pod, so I run kubectl describe pod and read the Events line. ImagePullBackOff means the node could not download the image. Both have a short list of usual causes, and Events names the right one.

Pending: not enough CPU or memory for the Pod's requests on any node (the message says "Insufficient cpu"); a node taint the Pod does not tolerate; a nodeSelector or affinity nothing matches; a PVC that is not bound; or a namespace ResourceQuota that is full (then the Pod is not even created). If the cluster autoscaler exists, it may just need a minute to add a node.

ImagePullBackOff or ErrImagePull: a typo in the image name or tag; the tag does not exist; a private registry with no or wrong imagePullSecrets; the node cannot reach the registry (network or proxy); or a rate limit on a public registry. If only new nodes fail, the credentials or network access differ on those nodes. A common one is an image built on an Apple Silicon laptop (arm64) that is pulled to amd64 nodes, which shows up as "exec format error" or "no matching manifest"; build with docker buildx build --platform linux/amd64 or a multi-arch image.

Pending: reading the scheduler's message

A typical Event is 0/6 nodes are available: 3 Insufficient memory, 2 node(s) had untolerated taint {dedicated: gpu}, 1 node(s) didn't match Pod's node affinity. The numbers add up to the total node count and each part names a filter that rejected some nodes. Work through them:

Test from a node or a debug Pod with the same credentials if you can. A subtle one: the image exists but for the wrong CPU architecture (built on an ARM laptop), which shows as "no matching manifest for linux/amd64" or "exec format error"; build multi-arch with docker buildx build --platform linux/amd64,linux/arm64. Also check whether the tag was overwritten and the node has an old cached copy with IfNotPresent.

What are NetworkPolicies, ServiceAccounts and RBAC, and why does an application developer need to know them? Intermediate

By default every Pod can talk to every other Pod, so a NetworkPolicy is how you restrict that: it selects Pods and lists which traffic is allowed in or out. A ServiceAccount is the identity a Pod uses when it calls the Kubernetes API, and RBAC (Role and RoleBinding) says what that identity may do. As a developer I need them because "it works locally but times out in the cluster" and "forbidden" errors are very often one of these.

NetworkPolicy, with an example

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: orders-allow-web }
spec:
  podSelector: { matchLabels: { app: orders } }   # applies to these Pods
  policyTypes: [Ingress]
  ingress:
  - from:
    - podSelector: { matchLabels: { app: web } }  # only the web Pods may connect
    ports: [{ port: 8080 }]

The rule that surprises people: Pods are open until a policy selects them; once selected, anything not allowed is dropped. A namespace-wide "default deny" policy is a good security baseline, and then you add allow rules. Policies are enforced by the network plugin (CNI); some simple plugins ignore them silently. Remember to allow DNS egress (port 53 to CoreDNS) if you restrict egress, or name lookups break.

ServiceAccount and RBAC

  1. Every Pod runs as a ServiceAccount (the namespace's default if you do not say). The Pod gets a token mounted so it can call the API.
  2. A Role lists permissions in a namespace (for example "get and list ConfigMaps"); a RoleBinding grants it to a ServiceAccount, user or group. ClusterRole and ClusterRoleBinding work cluster-wide.
  3. Principle of least privilege: most apps need no API access at all, so set automountServiceAccountToken: false.

Useful check: kubectl auth can-i list configmaps --as=system:serviceaccount:prod:orders -n prod. A Spring app using Kubernetes config or leader election getting "403 Forbidden" needs a Role for exactly what it reads. Cloud workload identity (IRSA on EKS, Workload Identity on GKE) ties a ServiceAccount to a cloud IAM role so Pods reach cloud services without static keys. Designing cluster-wide RBAC is platform work, but writing a correct namespace Role for your app is a developer skill.

Remember: NetworkPolicy limits who can connect (open until selected, then deny by default). ServiceAccount is the Pod's identity, RBAC is its permission list. Timeouts hint at policy, 403s hint at RBAC.

Your Java service is OOMKilled every few hours in Kubernetes, but the heap looks fine in monitoring. What do you do? Senior

The kernel is killing the whole process because heap plus non-heap memory exceeds the container limit, while the JVM never sees a heap problem. I find what is using memory outside the heap, give the heap less of the limit, and only then raise the limit if the data justifies it.

Situation: restarts with exit code 137 and reason OOMKilled, no Java OutOfMemoryError in the logs.

Check first: kubectl describe pod for OOMKilled and the time pattern (every few hours suggests slow growth, not a spike). Compare the container's working-set memory with the limit, and check the flags: is -Xmx or MaxRAMPercentage close to the limit (like 90)?

Fix: list what lives outside the heap: thread count (about 1 MB of stack each), direct buffers (Netty, NIO), metaspace growth, native libraries. In a test, turn on Native Memory Tracking (-XX:NativeMemoryTracking=summary, then jcmd <pid> VM.native_memory). Set the heap to about 60 to 70% of the limit, add -XX:+ExitOnOutOfMemoryError, and if memory climbs steadily take two heap dumps hours apart to look for a leak.

Prevent: a team sizing rule (heap percentage, memory request equal to limit), load tests inside a container with the real limits, and an alert at 85% of the limit.

Investigation in order

  1. Confirm the kill type. describe pod shows "Last State: Terminated, Reason: OOMKilled, Exit Code: 137". No OutOfMemoryError in logs means the heap did not fill: the kernel struck first.
  2. Plot the right metric. Heap graphs hide the problem. Chart container_memory_working_set_bytes against the limit, next to JVM heap, non-heap and thread count. A sawtooth heap with a rising working-set line points outside the heap.
  3. Name the consumer. Run NMT in a test or a canary: -XX:NativeMemoryTracking=summary, then jcmd PID VM.native_memory summary twice, and use summary.diff after baseline to see what grows (Thread, Class, Internal for direct buffers, Code, GC).
  4. Match the common causes. Unbounded thread pools or one thread per request (each thread reserves stack); Netty or NIO direct buffers not released (limit with -XX:MaxDirectMemorySize); metaspace growth from class-loader leaks or runtime proxy generation; glibc malloc arena fragmentation (MALLOC_ARENA_MAX=2, or a different allocator); memory-mapped files; large off-heap caches.
  5. Fix and verify. Cap the culprit, set MaxRAMPercentage to leave 30-40% for non-heap, and rerun a load test inside a container with the same limit. Watch for a flat working-set line over several hours, not minutes.

Also rule out a real heap leak: if the heap's post-GC floor rises hour after hour, take heap dumps and diff them (Eclipse MAT, a profiler). A quick stopgap is to raise the limit, but state clearly that it only buys time and cost until you know the cause.

Remember: OOMKilled is the whole process, not the heap. Leave headroom for non-heap memory.

Users see a burst of 502 errors on every deployment, even though the rollout is "zero downtime". Why, and how do you fix it? Senior

Because a terminating Pod is removed from the endpoints and sent SIGTERM at the same time, but the load balancer or ingress needs a few seconds to stop sending it new requests. I fix it by letting the Pod keep serving briefly with a preStop sleep, then draining gracefully on SIGTERM.

Situation: errors only for a few seconds around each release, lining up with Pods stopping or starting.

Check first: correlate error times with Pod start and stop. Is there a real readiness probe? Does the app actually get SIGTERM (PID 1 a shell?) and how long does its shutdown take? Do the ingress logs show connection reset or upstream refused?

Fix:

  1. Add a preStop sleep of about 5 to 15 seconds so the Pod keeps serving while the removal spreads.
  2. On SIGTERM stop accepting new connections and finish in-flight ones (Spring Boot: server.shutdown=graceful).
  3. Use exec form so the signal reaches the app, and set the grace period longer than the sleep plus the slowest request.
  4. Give new Pods a readiness probe so they get no traffic before the server listens, and set maxUnavailable: 0.
  5. Make the app's keep-alive timeout longer than the proxy's, so the proxy does not reuse a connection the Pod just closed.

Prevent: put these defaults in a shared chart, and run a load test during a rollout in staging.

Why "zero downtime" still drops requests

Kubernetes guarantees capacity (the rollout keeps enough Ready Pods), but not that every in-flight and newly routed request is handled cleanly by the Pod being removed. Walk through one Pod's last seconds:

  1. t=0: Pod marked Terminating. Endpoint removal begins; preStop begins.
  2. t=0+: the app (no preStop) receives SIGTERM and closes its listening socket at once.
  3. t=1 to t=5: some ingress workers and kube-proxy nodes still have this Pod in their backend list; new requests go there and get "connection refused" or reset. The proxy answers 502.
  4. With the preStop sleep (say 10 s): the app keeps serving through t=10, by which time every proxy has dropped it. SIGTERM then starts a graceful drain and the app exits cleanly.

Starting Pods can also fail users

A new Pod can be marked Ready slightly before its server accepts traffic if the readiness endpoint is shallow, or before connection pools and caches are warm. Use a real readiness check, and consider minReadySeconds. Some load balancers also need time to register a new target; with cloud LBs in IP mode there is a known gap, which is solved by pod readiness gates provided by the LB controller.

Another classic: keep-alive mismatch

If the Pod's server closes idle connections after 5 seconds but the proxy keeps them for 60, the proxy sometimes reuses a connection the Pod just closed, producing a sporadic 502. Make upstream keep-alive timeouts at the server longer than the proxy's idle timeout.

How to prove the fix

Run a steady load (for example 200 requests per second) in staging while triggering a rollout, and count non-2xx responses before and after the change. The goal is zero errors, and the evidence beats guessing. Also confirm PDBs and node drains behave the same way, because they follow the same termination path.

Remember: endpoint removal is slower than SIGTERM. Sleep, drain, then exit.

You changed a ConfigMap but the application still uses the old values. What happened? Intermediate

The Pod read the old value at start-up and is not re-reading it. Environment variables are fixed when the container starts, so I restart the Deployment. Files mounted from a ConfigMap do update in place, but only after a delay and only if the app re-reads them.

Check first: how is the ConfigMap consumed: env/envFrom, a mounted volume, or a volume using subPath? Then compare what the Pod sees (kubectl exec pod -- env or cat the file) with the live ConfigMap.

Fix: for env vars or subPath mounts (which never update) run kubectl rollout restart deploy/orders. For mounted files, wait for the sync (up to about a minute) and make sure the app reloads, for example with Spring Cloud refresh or a file watcher.

Prevent: in Helm add a checksum of the ConfigMap as a Pod template annotation, so any config change triggers a rolling update automatically. That also makes rollbacks consistent with config.

Why it behaves this way

Kubernetes does not know your app uses a ConfigMap value; it only wires it in when the container starts. An environment variable is copied into the process once, like a function argument. A mounted file, on the other hand, is a live view that the kubelet refreshes periodically by swapping a symlink; but your app has to re-open or watch the file to see the new content, and Spring Boot does not do this by itself without a refresh mechanism.

Decision table

Automating the restart in Helm

spec:
  template:
    metadata:
      annotations:
        checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}

When the ConfigMap content changes, the hash changes, the Pod template changes, and Kubernetes performs a rolling update. The same trick works with Secrets, and tools such as Reloader do it at runtime without Helm. The benefit of rolling update over in-place reload: Pods change one at a time, readiness protects you from a bad config, and rollback restores the old config together with the old image.

Be wary of in-place reload for risky config: a typo then affects all Pods at the same moment with no staged rollout.

Remember: env vars need a restart, mounted files update slowly, subPath never. Checksum annotation automates the restart.

The Service exists, the Pods are Running and Ready, but calls to the Service time out. What do you check? Intermediate

I check the endpoints first. If they are empty, the selector does not match the Pod labels. If they are filled, I test the Pod directly to separate an app problem from a Service or network problem, then check the port numbers and any NetworkPolicy.

kubectl get endpoints orders -n prod        # empty = selector mismatch
kubectl get pods -n prod --show-labels
kubectl port-forward pod/orders-abc 8080:8080   # does the Pod itself answer?
kubectl run t --rm -it --image=nicolaka/netshoot -- curl -sv orders.prod:80

Common causes: a typo in the Service selector or a label changed in the Deployment; Service targetPort not equal to the port the container listens on; the app bound to 127.0.0.1 instead of 0.0.0.0; a NetworkPolicy that allows no ingress from the caller; or calling across namespaces without the full name orders.prod.

Prevent: use named ports, template the labels and selectors from one place in Helm, and keep a smoke test in the pipeline that calls the Service.

A methodical walk, from the inside out

  1. Is the Pod itself healthy? port-forward straight to the Pod and curl it. If this fails, the problem is the app or its port, not Kubernetes networking.
  2. Does the Service point at it? kubectl get endpoints orders. Empty or wrong IPs: compare kubectl describe svc orders "Selector" with kubectl get pod --show-labels. Remember endpoints only list Ready Pods.
  3. Do the ports line up? The Service targetPort must be the port the app listens on. Named ports help avoid drift.
  4. Which address does the app bind to? 0.0.0.0 (or the Pod IP) works; 127.0.0.1 works for exec + curl inside the Pod but not through the Service. Spring Boot's default is all interfaces; some frameworks default to loopback.
  5. Name resolution. From a debug Pod, nslookup orders.prod. Failure points at CoreDNS or a wrong namespace or name.
  6. NetworkPolicy. If any policy selects the target Pods, only explicitly allowed traffic gets in. A "default deny" in the namespace silently drops everything not allowed. Look at kubectl get networkpolicy and check ingress rules for the caller's labels and namespace.
  7. Service mesh or proxy settings (mTLS mode, sidecar not ready) if you run one.

Timeout versus connection refused

This distinction narrows the cause fast. Timeout usually means packets are dropped: a NetworkPolicy, a security group, or a wrong IP. Connection refused means the packet reached a host but nothing listens on that port: wrong targetPort or the app bound elsewhere. 503 from an ingress means no healthy upstream, so look at endpoints.

Remember: empty endpoints = label mismatch. Filled endpoints = check targetPort, 0.0.0.0 and NetworkPolicy.

A short database outage turned into a 30-minute full outage of your service. The Pods kept restarting. What went wrong? Senior

The liveness probe almost certainly checked the database. When the database blipped, every Pod failed liveness and was restarted, so even after the database came back the whole fleet was restarting, re-warming and hammering the database with reconnections. I make liveness check only the process itself, and handle dependencies in readiness and retries.

Check first: describe shows "Liveness probe failed" events and a rising restart count. Look at what the probe endpoint actually calls (Spring Boot health groups including the database in liveness).

Fix: make liveness a cheap "am I alive" check with no dependencies. Put dependency checks in readiness, or better, in the app's own retry and circuit-breaker logic. Add a startup probe so a slow boot is not mistaken for a hang, and use a reasonable failureThreshold and timeout. Add exponential backoff with jitter on database reconnect so a recovery is not a stampede.

Prevent: review probes like code, test by killing the database in staging, and alert on restart counts.

The failure cascade, step by step

  1. The database has a 20-second blip (a failover).
  2. Liveness is configured to the health endpoint that includes the database check, so every Pod's probe fails 3 times in a row.
  3. The kubelet restarts all containers at nearly the same time. The service is down for the restart plus JVM boot plus warm-up, even though the Pods themselves were fine.
  4. The database recovers, but now all Pods start together and open their connection pools simultaneously (a thundering herd). Pool initialisation, schema checks and cache warming hammer a database that was just recovering, so it slows or fails again.
  5. Pods fail liveness again during start-up (no startup probe) and the loop continues. Restart counts climb and backoff delays grow to 5 minutes between attempts, stretching the outage to 30 minutes.

The core lesson: a liveness failure causes an action (restart) that cannot fix an external problem, and acting on all replicas at once amplifies the damage.

The corrected design

ReadinessReports unready if the app cannot do useful work; but consider degraded modes (serve cached reads) rather than flipping every Pod unready.

Mention the follow-up: also watch connection counts. Many replicas times a big pool can exceed the database's connection limit; pool size per Pod times max replicas must stay below it (or use a pooler such as PgBouncer).

Remember: liveness restarts, so it must never depend on something outside the container.

Your Spring Boot app takes 90 seconds to start, and Kubernetes keeps killing it. How do you fix it? Intermediate

The liveness probe starts firing before the app has finished booting and kills it, in a loop. The fix is a startup probe that gives it enough time, so liveness and readiness only begin once the app is up. Then I look at why it is slow.

Check first: describe shows "Liveness probe failed" and restarts, and the logs show the app restarting at about the same point. Check CPU limits too: a tight CPU limit slows JVM start-up, because class loading and JIT need CPU.

startupProbe:
  httpGet: { path: /actuator/health/liveness, port: 8080 }
  periodSeconds: 5
  failureThreshold: 30        # 5 x 30 = up to 150 s to boot
livenessProbe:
  httpGet: { path: /actuator/health/liveness, port: 8080 }
  periodSeconds: 10

Better long term: give the Pod more CPU during start-up, trim unneeded auto-configuration and component scanning, use lazy initialization carefully, use AppCDS or Spring Boot's CDS support (a smaller start-up on newer versions), or a native image if start-up time is critical. Do not "fix" it with a huge initialDelaySeconds, which delays detection of real failures forever.

Why the kills happen, with numbers

Suppose liveness is configured with initialDelaySeconds: 30, periodSeconds: 10, failureThreshold: 3. The kubelet starts probing at 30 s, and three failures at 30, 40, 50 s lead to a restart at about 60 s, while the app needs 90 s. It never gets there, and every restart starts the clock again: a permanent CrashLoopBackOff although the app itself is fine.

Why a startup probe is the right tool

A startup probe runs alone first with its own budget (here 150 s) and holds liveness and readiness until it succeeds once. After that the aggressive liveness settings apply, so a real hang later is detected in 30 s, not 150. A big initialDelaySeconds on liveness cannot do this, because it delays detection for every restart forever and is a guess that breaks as the app grows. Startup probes have been stable since Kubernetes 1.20.

A database password turns up inside a container image in the registry. What do you do? Senior

I treat the password as compromised. I rotate it first, because deleting the image does not delete the copies already pulled, then find and remove the leak from the build, and rebuild clean images.

Check first: which image tags and which layer contain it (docker history, or a scanner like Trivy), who could pull those images, and whether the password was used from unexpected places (database audit logs).

Fix:

  1. Rotate the credential now and update the real secret store.
  2. Delete the affected tags from the registry and any mirrors, noting that others may have copies.
  3. Find the cause: ENV or ARG in the Dockerfile, a COPY . that swept in a .env file, or a config file in the build context.
  4. Fix it: add a .dockerignore, use BuildKit secret mounts for build-time secrets, and inject run-time secrets from a Kubernetes Secret or vault.
  5. Rebuild and redeploy.

Prevent: a secret scanner and an image scanner in CI that fail the build, and a code review rule that no credential appears in a Dockerfile or values file.

Why rotation comes before cleaning

Every minute spent deleting images is a minute the credential still works for anyone who already pulled one, including build caches, developer laptops and CI mirrors. Rotation makes the leaked value useless. Cleaning only reduces future exposure.

A response plan with owners

  1. Contain (minutes): rotate the password or key in the secret manager and the database; restart workloads to pick up the new value. Revoke any tokens that were in the image too.
  2. Assess (hours): which tags, who had pull access (a private registry limits the blast radius; a public one makes it a full incident), and when the secret first appeared. Check database and cloud audit logs for logins from unknown sources since that date.
  3. Remove: delete affected tags and untagged manifests, purge CI caches and mirrors, and expire old layers (garbage-collect the registry).
  4. Root cause: inspect with docker history --no-trunc or a scanner to find whether it was ENV, ARG, a COPY of a config or .env, or a build step printing it into a file.
  5. Prevent: .dockerignore; BuildKit secret mounts; runtime injection via Secrets or a vault; secret scanning (gitleaks, Trivy) as a required CI gate; least-privilege database users so a leak has limited reach; and short-lived credentials (workload identity, dynamic database credentials) so the next leak expires on its own.

Close with the blameless post-mortem: describe the fix to the process, not the person.

Remember: rotate first, clean up second. A secret in an image is already out.

CI builds the Docker image in 12 minutes for a one-line code change. How do you speed it up? Intermediate

The dependency layer is being rebuilt on every commit, either because the Dockerfile copies all source before installing dependencies, or because CI starts with an empty cache. I reorder the Dockerfile so dependencies install first, and give CI a shared layer cache.

Check first: read the build output for which steps say CACHED. If the dependency download reruns every time, the cause is the copy order (COPY . . before mvn package), a changing file earlier in the Dockerfile (for example a timestamp or build number written too early), or a clean CI runner with no local cache.

Fix:

  • Copy pom.xml first, resolve dependencies, then copy src.
  • Add a .dockerignore so unrelated changes do not break the cache.
  • Use a BuildKit cache mount for ~/.m2, and a registry cache (--cache-from, --cache-to) so clean CI runners reuse layers.
  • Use a multi-stage build and a smaller final image so the push and pull are small.
  • Put volatile steps (build number, version labels) last.

Prevent: track build time per stage, and review Dockerfile order in code review.

Find where the time goes first

Do not optimise blindly. Run docker build --progress=plain . (BuildKit) and read the per-step timings. Typical culprits, in order of frequency: dependency download (minutes), the Maven or Gradle compile, pulling a huge base image, running the tests, and pushing a large image.
