Mental model: the ideas everything hangs on

One line: an exception is an object that travels up the call stack until someone handles it; generics are a compile-time check that is erased before runtime; I/O is bytes plus (sometimes) a charset plus a resource that must be closed.
  1. An exception is a normal object with a captured stack. Creating it walks the stack and records it, which is the expensive part. Throwing it unwinds frames until a matching catch is found.
  2. Checked vs unchecked is a compiler rule only. At runtime they behave the same.
  3. Never lose the cause. Wrap with the original as the cause, log once where it is finally handled, never swallow silently.
  4. Handle an exception at the layer that can do something about it. Lower layers translate technical errors; the top layer turns them into a response.
  5. Generics exist only at compile time. The compiler checks types, inserts casts, then erases the type arguments.
  6. Bytes are not text. Text needs a charset. Always name it in code.
  7. Every opened resource needs a guaranteed close. In modern Java that means try-with-resources.
  8. Java serialization rebuilds objects without calling your constructor. That is the root of both its bugs and its security problems.

1. Exception basics

Draw the exception hierarchy. What are Throwable, Error, Exception and RuntimeException? Basic

Throwable is the root, and only a Throwable can be thrown or caught. It has two children. Error is for serious JVM problems such as OutOfMemoryError that the program normally cannot fix. Exception is for problems the code might handle, and under it RuntimeException and its children are unchecked, while everything else (IOException, SQLException) is checked.

What an exception is, from scratch. When something goes wrong, a Java method does not return a status code. It creates an object (the exception) that describes the failure, and throws it. The JVM then abandons the current method, jumps to the caller, and keeps going up the call stack until it finds a catch that matches the exception's type. If no frame catches it, the thread dies and the stack trace is printed. The hierarchy matters because catch (X e) matches X and every subclass of X.

Why the split into Error and Exception exists. The designers wanted to separate "the environment is broken" from "your code hit a problem it can reason about". Error covers things like OutOfMemoryError, StackOverflowError and NoClassDefFoundError: the JVM itself is in trouble, so ordinary code cannot meaningfully repair it. Exception covers conditions an application may want to react to, such as a file that does not exist or a bad argument.

Why it matters in practice. The tree decides what a catch can see. A few consequences you should be able to state:

  • catch (Exception e) does not catch OutOfMemoryError, because that is an Error, not an Exception. catch (Throwable t) catches both.
  • catch (IOException e) also catches FileNotFoundException and NoSuchFileException, because they are subclasses; the subclass relationship, not the name, is what counts.
  • With several catch blocks, put the narrow type first. Writing catch (Exception e) above catch (IOException e) is a compile error, because the second block could never run.
try {
    Files.readString(Path.of("config.txt"));
} catch (NoSuchFileException e) {      // narrow first
    useDefaults();
} catch (IOException e) {              // broader parent next
    throw new UncheckedIOException(e);
}                                      // RuntimeExceptions fly past both

What an interviewer probes next: "Is StackOverflowError checked?" (No, it is an Error, so unchecked.) "Can you throw a String?" (No, only Throwable subclasses.) "Where do Throwable's useful methods come from?" (getMessage, getCause, getStackTrace, addSuppressed are all defined on Throwable, so every exception has them.)

So "unchecked" means Error plus RuntimeException and their children: the compiler does not force you to catch or declare them. Typical runtime exceptions are NullPointerException, IllegalArgumentException, IllegalStateException and IndexOutOfBoundsException. All of them are programming mistakes. A custom exception is checked if it extends Exception and unchecked if it extends RuntimeException.

Remember: Throwable splits into Error (do not catch) and Exception; RuntimeException is the unchecked part of Exception.

What is the difference between checked and unchecked exceptions? Basic

A checked exception must be either caught or declared with throws, and the compiler enforces that. An unchecked exception needs neither. The intent was: checked for failures the caller can reasonably recover from and that are outside the program's control (a missing file, a dropped network), unchecked for programming mistakes like a null argument, where the fix is to change the code.

The problem checked exceptions try to solve. In C, a function that fails returns -1 and callers often forget to test it. Java's designers wanted to make "this call can fail in a way you should plan for" impossible to ignore. So they made some exceptions part of the method's type signature, and the compiler refuses to build code that neither handles nor passes them on.

What the compiler actually does. For each call to a method that declares throws IOException, the compiler asks: is this call inside a try with a matching catch, or is the enclosing method itself declared to throw it? If neither, compile error ("unreported exception"). For unchecked exceptions it asks nothing.

A rule of thumb for choosing. Ask: "can a reasonable caller do something useful and different when this happens?" If yes (retry, use a fallback, ask the user for another file name), a checked exception makes sense. If the only sensible reaction is "fix the code" or "give up and report a 500", make it unchecked. Throwing IllegalArgumentException for a negative age is unchecked because no caller should write a recovery branch for it; they should pass a valid age.

Common confusion to clear up. "Unchecked" does not mean "cannot be caught". You can catch RuntimeException any time. It only means the compiler will not force you. Also, throws on a method is documentation for unchecked exceptions and a hard contract for checked ones.

At runtime there is no difference at all. The rule is purely a compile-time contract on method signatures. That is why a method can throw an unchecked exception from deep inside without any signature change, while adding a new checked exception forces changes in every caller.

void read() throws IOException { ... }   // caller must handle or declare
void check(int n) {
    if (n < 0) throw new IllegalArgumentException("n < 0");   // no declaration needed
}

Remember: checked = the compiler makes you deal with it; unchecked = your bug or an Error. Same behaviour at runtime.

Are checked exceptions a good idea or a mistake? What do you use in your own code? Senior

Good idea in theory, awkward in practice, so I default to unchecked exceptions with clear domain names. I keep a checked one only where the caller really has a different recovery path. At the boundary with legacy APIs I translate checked to unchecked and keep the cause.

The two sides, with real examples. Imagine a UserRepository interface. If findById declares throws SQLException, then the service layer must handle SQL, and the day you switch to a REST backend or Mongo, you change the interface and every caller. That is what "leaking implementation details" means. With an unchecked DataAccessException, the interface stays stable.

The lambda problem is concrete too. This does not compile, because Function.apply declares nothing:

names.stream().map(n -> Files.readString(Path.of(n)))   // error: unreported IOException

Where checked exceptions still earn their place. A public library method where "the remote call may time out and every caller must decide what to do" is a real part of the contract. Java's own InterruptedException is a good checked example: forgetting it exists leads to bugs, and the compiler prevents that. Another good case is a small, closed API where the failure is part of the normal story, such as parse(String) throws ParseException.

The decision rule I would state aloud.

  1. Can the immediate caller recover in a meaningful, different way? Consider checked.
  2. Does the failure cross a layer boundary or an interface that many implementations share? Make it unchecked and domain-named.
  3. Is it a programming bug (null, bad argument, broken invariant)? Always unchecked.

What goes wrong in real code. The worst outcomes of checked exceptions are catch (Exception e) {} written just to make the compiler quiet, and throws Exception on every method, which removes all information. Both are worse than unchecked. The worst outcome of unchecked-everywhere is that failure modes are invisible in signatures, so you must document them (Javadoc @throws) and test them.

The case for checked: the signature honestly lists what can fail and the compiler stops you ignoring it. The case against, which most of the industry accepted (Spring and Hibernate are unchecked): they leak implementation details up the layers (a SQLException in a service interface), they push people into empty or wrapping catch blocks, and they do not work with lambdas, because Function and friends declare no checked exceptions. Adding a checked exception to an interface also breaks every implementation and caller.

Watch out: do not say "checked is always bad". Say it depends on whether the caller can recover and whether the exception crosses an abstraction boundary.

Remember: checked leaks details and breaks lambdas, so unchecked by default, checked only for real recoverable cases.

Should you ever catch an Error such as OutOfMemoryError or StackOverflowError? Intermediate

Normally no. After an OutOfMemoryError the JVM may be in a bad state, so the sensible reaction is to log if possible and let the process die so the orchestrator restarts it. The legitimate catch is at the top of a worker loop, where I catch Throwable so one bad task does not silently kill the thread, and I log it.

Why not recover from OutOfMemoryError. Suppose a thread tries to allocate a 200 MB array, the heap is full and OutOfMemoryError is thrown. You catch it and carry on. The problem: the failed allocation might have happened anywhere, in a library half-way through updating a map, or in another thread at the same moment. Objects can be left half-built, locks may not be released, and your own catch block needs memory to log. So the program continues in an unknown state, which is worse than a clean restart. In containers the standard answer is: crash fast (-XX:+ExitOnOutOfMemoryError), write a heap dump for later (-XX:+HeapDumpOnOutOfMemoryError), and let Kubernetes or systemd restart the process.

There are different OOM flavours and the message tells you which: "Java heap space" (too many live objects), "Metaspace" (too many classes, usually a classloader leak), "unable to create native thread" (OS thread limit), "GC overhead limit exceeded" (the JVM is spending nearly all its time collecting). The fix differs for each, so always log the message.

The one place catching Throwable is correct. A worker loop, for example a Kafka consumer or a scheduler, where one failed job must not kill the thread:

while (running) {
    Job job = queue.take();
    try { job.run(); }
    catch (Throwable t) {                 // boundary: log, do not die silently
        log.error("job {} failed", job.id(), t);
        if (t instanceof VirtualMachineError) throw (Error) t;   // OOM etc: stop for real
    }
}

StackOverflowError is different in practice: unwinding the stack frees the memory, so catching it is survivable, but it nearly always means infinite or too-deep recursion, which you fix in the algorithm (convert to a loop or use an explicit stack).

Other threads can also fail anywhere after an OOM, even inside your own handler, and data structures may be half updated. Useful flags are -XX:+HeapDumpOnOutOfMemoryError and -XX:+ExitOnOutOfMemoryError. A StackOverflowError is more recoverable, since the stack unwinds when you catch it, but fixing the runaway recursion is the real answer. Note that catch (Exception e) does not catch Errors.

A classic follow-up: ClassNotFoundException is a checked exception from Class.forName when a class cannot be found by name, while NoClassDefFoundError is an Error meaning the class existed at compile time but is missing or failed to initialize at runtime.

Remember: do not try to recover from an Error; catch Throwable only at a boundary to log, then fail or restart.

2. try, catch, finally and resources

Explain the execution order of try, catch and finally. When does finally not run? Basic

The try block runs. If it throws, the first matching catch runs. Then finally runs in every case, whether the try finished, threw, or returned. After that the method continues, returns, or rethrows. Finally does not run only if the JVM stops first: System.exit(), a crash, kill -9, or power loss.

Why finally exists. Imagine you lock a resource, do work, and want to unlock it whatever happens: a normal finish, an exception, or an early return. Without a construct that runs on every exit path, you would have to repeat the unlock code in every branch and every catch, and a future edit would forget one. finally is the "always do this on the way out" block.

A walk-through. Take this code and trace three situations:

try {
    System.out.println("A");
    riskyCall();            // may throw IOException
    System.out.println("B");
} catch (IOException e) {
    System.out.println("C");
} finally {
    System.out.println("D");
}
System.out.println("E");
  1. No exception: prints A, B, D, E (catch skipped).
  2. riskyCall throws IOException: prints A, C, D, E (B skipped, catch handled it, execution continues).
  3. riskyCall throws IllegalStateException (no matching catch): prints A, D, then the exception continues up the stack, so E is not printed. Finally ran, but it did not stop the exception.

What interviewers probe. "What if the catch block itself throws?" Finally still runs, then the new exception propagates. "What if try returns and finally prints?" The print happens before the method actually hands back the value. "What does System.exit(0) in try do?" The JVM begins shutdown; finally does not run (shutdown hooks do). Practical use: releasing locks (lock.unlock() belongs in finally right after lock()) and restoring state. For closing files and sockets, prefer try-with-resources, covered next.

If try or catch does a return, the return value is computed and saved first, then finally runs, then the method returns the saved value. So changing a local primitive in finally does not change what is returned, but changing a mutable object that was returned does show. A finally also will not complete if the thread loops or blocks forever, and a daemon thread can be stopped mid-way when the JVM exits. So finally is not a place for critical durability: use transactions and idempotent recovery.

Remember: finally runs on every path unless the JVM dies first. The return value is saved before finally runs.

What is multi-catch, and what is "precise rethrow"? Intermediate

Multi-catch (Java 7) lets one handler cover several unrelated exception types: catch (IOException | SQLException e). The variable is implicitly final, and its static type is the closest common supertype. The types in the list may not be related by subclassing (the compiler rejects IOException | FileNotFoundException). Precise rethrow means that rethrowing an effectively final catch parameter is checked against what the try block can really throw, not against the broad type you caught.

Why it exists. Before Java 7, handling two exception types the same way meant copy-pasting the block, or catching Exception and losing precision. Multi-catch removes the duplication without widening the catch.

try {
    parse(); save();               // throws ParseException, IOException
} catch (ParseException | IOException e) {
    log.warn("import failed", e);  // e is final here
    throw new ImportException("import failed", e);
}

Precise rethrow, by example.

void run() throws IOException {        // not "throws Exception"
    try { readFile(); }                // declares IOException only
    catch (Exception e) {              // broad catch
        log.warn("failed", e);
        throw e;                       // compiler knows e can only be IOException (or unchecked)
    }
}

Since Java 7 this compiles. Earlier it required throws Exception. The rule works only if you do not assign to e inside the block.

Order rules for several catch blocks. The first matching block wins, so list narrow before broad; putting a parent first is a compile error (unreachable catch). Catching a checked exception that the try block cannot throw is also a compile error, except for Exception and Throwable.

Remember: use A | B for the same handling of unrelated types; the compiler tracks what a rethrown final variable can really be.

What is the difference between final, finally and finalize? Basic

They are three unrelated things with similar names. final is a modifier: a final variable cannot be reassigned, a final method cannot be overridden, a final class cannot be subclassed. finally is the block after try/catch that runs on every exit path. finalize() was a method the garbage collector called before reclaiming an object; it is deprecated, and marked for removal since Java 18, and should not be used.

NameWhatUse today
finalKeyword on variable, method or classYes: immutability, safe publication, clear intent
finallyBlock that runs after try/catchYes, for cleanup that is not a resource (unlock, restore state)
finalize()Object method called by GCNo. Use try-with-resources; Cleaner only as a safety net

Why finalize failed. It runs at an unpredictable time (maybe never), delays collection of the object by at least one extra GC cycle, can resurrect the object, runs on a special thread so errors there are swallowed, and was a classic source of attack and performance problems. An object with a finalizer also costs more to allocate and collect.

A clarification on final. A final reference means the variable always points to the same object; the object itself can still change (a final List can still be added to). Final fields also get special visibility guarantees under the Java memory model once the constructor finishes.

Remember: final = cannot change, finally = always runs, finalize = obsolete GC hook.

What does this print, and why is return inside finally dangerous? Intermediate

The first method returns 1, because the return value was already saved before finally changed the variable. The second returns 42 and the exception disappears, because a return (or break or continue) inside finally overrides everything, including a thrown exception, with no trace.

Step-by-step for method f(). Java evaluates the expression after return (the value 1), stores it in a hidden slot, and starts the pending-exit process. It runs the finally block, where x = 2 changes the local variable but not the already-stored copy. When finally ends normally, the method completes the return it had pending, delivering 1. For primitives and immutable values the stored copy is independent of later changes.

A subtle variant. If the returned thing is a mutable object, the stored value is the reference, so mutations in finally are visible to the caller:

static StringBuilder h() {
    StringBuilder sb = new StringBuilder("a");
    try { return sb; }
    finally { sb.append("b"); }     // caller receives "ab"
}

Why the second case is dangerous. The pending exit in g() is "throw RuntimeException". When finally executes its own return 42, it replaces the pending exit. The exception is thrown away without any warning. In a real service this turns a database failure into a "successful" return with a default value, and nobody notices until data is wrong. The same is true for break and continue that leave the finally block, and for a throw from finally: the original exception is lost (try-with-resources avoids this by attaching the second as suppressed).

Rule for your code. A finally block should only release or restore things, never produce a result. Tools like SpotBugs and IDE inspections flag "finally block does not complete normally". If you must guard cleanup that can itself throw, wrap that cleanup in its own try/catch inside finally and log the failure.

static int f() {
    int x = 1;
    try { return x; }          // value 1 is saved
    finally { x = 2; }         // does not change the saved value
}                              // returns 1

static int g() {
    try { throw new RuntimeException("boom"); }
    finally { return 42; }     // exception is discarded, returns 42
}

The same thing happens if finally itself throws: the new exception replaces the original, and the original cause is lost. Keep finally blocks tiny and non-throwing, or use try-with-resources, which handles this properly. The compiler flag -Xlint:finally warns when a finally cannot complete normally.

Remember: never return or throw from finally; it silently replaces the real outcome.

What is try-with-resources and why is it better than try/finally? Basic

Any object that implements AutoCloseable (files, streams, sockets, JDBC connections) can be declared in the parentheses after try, and Java calls close() automatically at the end, even if the block throws. Several resources are closed in reverse order. It is better than try/finally because it is shorter, it cannot forget to close, and a failing close() no longer hides the real exception.

The old way and why it was broken. Before Java 7 the safe code looked like this, and it is surprisingly hard to write correctly:

InputStream in = null;
try {
    in = new FileInputStream(path);
    use(in);
} finally {
    if (in != null) {
        try { in.close(); } catch (IOException ignore) { }   // hides real problems
    }
}

Problems: noisy, easy to forget the null check, and if both use and close throw, the close exception replaces the useful one. With two resources the nesting doubles.

What the compiler generates. try-with-resources is syntactic sugar. For try (R r = open()) { body } the compiler produces roughly: run the body; record any exception as the primary; in a finally-like step call r.close() if r is not null; if close throws and a primary exists, add it as suppressed; otherwise throw it. For several resources it nests them, so each is closed only if it was successfully opened.

What you can put in the parentheses. Anything that implements AutoCloseable: streams, readers, JDBC Connection, Statement, ResultSet, Scanner, ExecutorService (from Java 19) and your own classes. The variables are implicitly final, so you cannot reassign them.

Pitfalls.

  • Wrapped streams. try (var r = new BufferedReader(new FileReader(f))) is fine because closing the outer closes the inner. But if the inner constructor (new FileReader) succeeds and the outer constructor throws, the inner leaks. Declaring each as its own resource avoids that.
  • Only closes what is declared. A resource created in the body, outside the parentheses, is not closed.
  • A returned resource must not be closed. If a method returns a stream to its caller, do not wrap it in try-with-resources inside that method.

When to choose it. Always, for any closable resource, unless the lifetime is longer than one block (then manage it in a class with its own close()).

The old pattern needed a finally with null checks and a nested try/catch for close, and if close threw, it replaced the real error. Try-with-resources keeps the body's exception as the main one and attaches the close failure to it as a suppressed exception. If a resource expression is null, nothing is closed for it and there is no NPE. If opening resource B fails, resource A (already open) is still closed. Since Java 9 you can write try (res) for an existing effectively final variable.

try (var in  = Files.newBufferedReader(src);
     var out = Files.newBufferedWriter(dst)) {
    in.transferTo(out);
}   // out closed first, then in

Remember: open in order, close in reverse, body exception wins, close failures become suppressed.

What are suppressed exceptions? When would you see one? Intermediate

When the body of a try-with-resources throws exception E and then close() also throws C, only one can propagate. Java keeps E, the real cause, and attaches C to it with E.addSuppressed(C). You read them with getSuppressed(), and the stack trace prints them under "Suppressed:".

Why this feature had to exist. A Java method can only throw one exception at a time. In the old try/finally pattern, if the body threw E and then close() in finally threw C, C won and E vanished. That is terrible for debugging, because C ("socket already closed") is usually a consequence of E ("connection reset"), not the cause. Suppression keeps the cause in front and the follow-up as a side note.

Concrete example.

class Res implements AutoCloseable {
    public void close() throws IOException { throw new IOException("close failed"); }
}
try (Res r = new Res()) {
    throw new IOException("write failed");        // primary
} catch (IOException e) {
    System.out.println(e.getMessage());           // write failed
    for (Throwable s : e.getSuppressed())
        System.out.println(" suppressed: " + s.getMessage());   // close failed
}

Some details worth knowing.

  • With several resources each closing and failing, you can get several suppressed exceptions on one primary, in close order (reverse of opening).
  • Suppression can be disabled for one exception class using the protected constructor Throwable(msg, cause, enableSuppression=false, writableStackTrace).
  • Logging frameworks print suppressed exceptions as part of the full stack trace, but if you log only e.getMessage() you never see them. That is another reason to pass the exception object to the logger.
  • You can use it yourself: if a cleanup loop closes five resources and two fail, keep the first and call addSuppressed for the rest, then throw once at the end.

If the body succeeded but close throws, then C simply propagates as the main exception. You can call addSuppressed yourself in hand-written cleanup, for example when closing several resources in a loop and wanting to keep every failure.

java.io.IOException: write failed
    at App.run(App.java:12)
    Suppressed: java.io.IOException: close failed
        at MyRes.close(MyRes.java:8)

Remember: primary exception = body failure; suppressed = failures during close that would otherwise hide it.

AutoCloseable versus Closeable, and how do you write a good close()? Intermediate

AutoCloseable (Java 7) is what try-with-resources needs: one method, close() throws Exception. Closeable (in java.io) extends it, narrows the exception to IOException and requires that closing twice is harmless. A good close() is idempotent, releases in reverse order of acquisition and does not let one failed release stop the others.

The relationship in one picture. AutoCloseable is the general contract in java.lang: "I hold something that must be released; call close() when you are done." Closeable is the older I/O-specific one in java.io (Java 5) that was retrofitted to extend AutoCloseable in Java 7. All streams, readers and writers are Closeable; JDBC Connection and many non-I/O classes are plain AutoCloseable.

Why idempotence matters. With nested wrappers it is easy to close the same thing twice (you close the outer stream, and also the inner one in a finally). If the second close threw, you would get a spurious failure that masks the real one. A guard flag, as in the example, or delegating to a type that is already idempotent solves it.

Designing close() well, with an example of several parts. If your class owns two things, close both even if the first fails:

public void close() throws IOException {
    IOException first = null;
    try { a.close(); } catch (IOException e) { first = e; }
    try { b.close(); } catch (IOException e) {
        if (first == null) first = e; else first.addSuppressed(e);
    }
    if (first != null) throw first;
}

Pitfall: do not do heavy or blocking work, or throw from close in a way you cannot explain; close runs during error handling when things are already bad. Also, an AutoCloseable that is not used in try-with-resources triggers IDE warnings "resource leak", a useful cheap check.

Do not declare throws Exception in your own implementation if you throw nothing, otherwise every caller must catch it. Document whether close also closes anything it wraps. And never rely on the garbage collector to release scarce things such as file handles: finalize() is deprecated for removal since Java 18 because it runs at an unpredictable time, maybe never. Cleaner (Java 9) is only a last-resort safety net, not a plan.

public final class Conn implements AutoCloseable {
    private boolean closed;
    @Override public void close() {   // no checked exception, idempotent
        if (closed) return;
        closed = true;
        release();
    }
}

Remember: make close idempotent and non-throwing if you can; the GC is not a close mechanism.

What is exception chaining, and how do you preserve the cause? Basic

When I catch a low-level exception and throw a different one, I pass the original as the cause: new OrderStoreException("cannot save order 17", e). Then the stack trace shows "Caused by:" lines down to the root. Without the cause, only the place where I rethrew is visible and the real failure is lost.

Why wrap at all? A repository that throws raw SQLException forces the service to know about JDBC. So we wrap it in our own exception, but doing so naively discards why it failed. A cause is simply a field on the new exception pointing at the old one, so the whole chain is kept.

A worked example of what a log shows.

OrderServiceException: cannot place order 17
    at OrderService.place(OrderService.java:40)
Caused by: OrderStoreException: cannot save order 17
    at OrderRepo.save(OrderRepo.java:22)
Caused by: java.sql.SQLIntegrityConstraintViolationException: Duplicate entry '17' for key 'PRIMARY'
    at ...

Reading bottom to top tells the whole story: a duplicate key at the database caused the store failure, which caused the service failure. Each layer added its own context (the order id), and the root cause is intact. If any layer had written new OrderStoreException("failed") without e, the trace would stop there and the duplicate key would be invisible.

Ways to attach a cause.

  • Constructor: super(message, cause), the normal way.
  • initCause(e): for legacy classes with no such constructor; it can be called only once.
  • getCause() to read; loop until null (or use a library helper) to reach the root.

Good practice: do not wrap an exception more than once for no reason (a chain of five layers each saying "failed" is noise); do not wrap exceptions that your caller already expects (for example IllegalArgumentException from validation should usually pass through unchanged); keep the message about what you were trying to do, since the cause already says what went wrong.

For old exception classes with no cause constructor use initCause. Write a message that adds context the low level did not know, such as the order id, instead of repeating the same words. To find the root, walk getCause() in a loop. When reading a trace, the last "Caused by" is the root cause and usually the first place to look.

try { repo.save(order); }
catch (SQLException e) {
    throw new OrderStoreException("cannot save order " + order.id(), e);   // cause kept
}
Watch out: throw new RuntimeException(e.getMessage()) loses the type and stack. e.printStackTrace() writes to stderr, outside your logging.

Remember: always pass the cause as the second constructor argument.

How do you read a long stack trace with several "Caused by" sections? Basic

The first line is the outermost exception, the last one thrown. Below it are the calls, most recent first. Each "Caused by:" starts the cause of the previous one, and the last "Caused by:" is the root cause, which is where I start. Inside that section I look for the first frame in my own package.

A trace annotated. Here is a short example and how to read it:

1  com.shop.OrderServiceException: cannot place order 17
2      at com.shop.OrderService.place(OrderService.java:40)
3      at com.shop.OrderController.post(OrderController.java:18)
4      at org.springframework.web.method.support.InvocableHandlerMethod.invoke(...)
5      ... 40 more
6  Caused by: java.sql.SQLTransientConnectionException: connection timed out
7      at com.zaxxer.hikari.pool.HikariPool.getConnection(HikariPool.java:200)
8      at com.shop.OrderRepo.save(OrderRepo.java:22)
9      ... 3 more
  1. Line 1 is the top-level exception: type, then message. It is what the caller finally saw.
  2. Lines 2 to 4 are frames, innermost first: place threw it, called by post, called by framework code.
  3. Line 6 is the cause. This one is the root (no further "Caused by"). It says the connection pool timed out, so the real problem is likely pool exhaustion or a slow database, not the order code.
  4. Line 8 is the first frame in our code under the root cause: OrderRepo.save line 22 is where we asked for a connection.
  5. "... 3 more" means the last 3 frames of this section are the same as the frames at the bottom of the section above, so they are not repeated.

Habits that save time. Ignore framework frames at first; scan for your own package name. Check the exception type before the message, since the type is more stable and searchable. Note the line numbers match the deployed version, not necessarily your checkout. If a trace is cut off with no frames at all, it may be the JIT's fast-throw optimization (see the performance question). In very deep recursion the trace is capped at 1024 frames by default (-XX:MaxJavaStackTraceDepth).

A line like "... 23 more" means those frames are identical to the enclosing trace and were left out to save space. Also look for "Suppressed:" entries from try-with-resources. If the root cause message is generic, search the surrounding log lines with the same correlation id.

Remember: read from the bottom "Caused by", then find the first frame in your own code.

What does "swallowing an exception" mean and why is it so harmful? Basic

Swallowing means catching an exception and doing nothing: an empty catch block, or logging only e.getMessage() and carrying on. The code continues with wrong or missing data, and the failure shows up much later with no trace to follow. Each catch should do one of three things: recover for real, translate and rethrow with the cause, or log with the full stack and an explicit decision to continue.

A story of how it hurts. A nightly import loads 10,000 customers. For one row, Integer.parseInt throws NumberFormatException. The loop has catch (Exception e) { }. The job reports success with 9,999 rows. Weeks later finance asks why one customer has no invoices. There is no log, no stack, no exception to search for. All the information needed to fix it existed for a millisecond and was thrown away.

The three legitimate things a catch can do.

  1. Recover: the program really can continue correctly, for example fall back to a default config when an optional file is missing. Log what you did.
  2. Translate and rethrow: wrap in a more suitable exception with the cause (previous questions).
  3. Handle at the boundary: this is the top of the request or job; log the full stack once, produce an error response or mark the job failed.

Less obvious forms of swallowing.

  • Logging only e.getMessage(): the message may be null (NPE, for example) and there is no stack.
  • e.printStackTrace() in server code: goes to stderr and bypasses log levels, format and correlation ids.
  • Catching Exception broadly in a loop and continuing, so a systemic failure (database down) produces 10,000 identical warnings and no stop.
  • Returning null or an empty list from a catch so that the caller cannot tell "no data" from "failed".

When ignoring is acceptable. Closing a resource in a cleanup path after another failure already occurred, or a best-effort metric update. Even then, a debug log with the exception and a clearly named method such as closeQuietly shows the intent to the next reader.

If you truly want to ignore something, for example closing quietly after a failure, say so in a named helper and still log at debug level.

catch (IOException e) { }                            // bad: silent
catch (IOException e) { log.warn(e.getMessage()); }  // bad: no stack, no cause
catch (IOException e) {
    log.warn("cache write failed, continuing without cache", e);  // ok if intended
}

Remember: a catch block must recover, rethrow with the cause, or log the full stack on purpose. Never nothing.

Are exceptions slow? Where does the cost come from? Intermediate

The expensive part is creating the exception, not throwing it. The Throwable constructor calls fillInStackTrace(), which walks the whole call stack and records every frame. With the deep stacks typical in Spring or servlet code that is microseconds and some memory per exception. A try block that never throws costs nothing, because the handler table is just data.

What actually happens when you create one. new RuntimeException("x") runs the Throwable constructor, which calls the native fillInStackTrace(). The JVM walks every frame on the current thread's stack and records class, method, file and line. In a typical Spring application the stack is 50 to 200 frames, so this takes on the order of microseconds and allocates memory proportional to depth. The throw and the lookup of the handler are cheap compared to that. (Treat exact timings as machine and JVM dependent; measure with JMH if it matters.)

A concrete bad design and a better one.

// bad: exception for an expected outcome, runs for every miss
try { return Integer.parseInt(s); }
catch (NumberFormatException e) { return -1; }

// better when misses are common: check without exceptions
if (!s.isEmpty() && s.chars().allMatch(Character::isDigit)) return Integer.parseInt(s);
return -1;

If one request in a million fails, nobody cares about the cost. If 30% of calls fail in a hot loop, the cost shows up in a profiler as time inside fillInStackTrace.

Practical guidance.

  • Do not avoid exceptions for genuine errors; clarity and correctness matter more.
  • For expected, frequent outcomes use Optional, a boolean test (hasNext, containsKey) or a result type.
  • If you need a cheap "signal" exception, such as an internal control-flow jump in a parser, pre-allocate it or disable the stack trace as shown.
  • Stack depth multiplies the cost, so exceptions thrown from deep inside frameworks or reactive chains are costlier than from a shallow method.

Memory side: a trace stored in a long-lived structure (an error cache, a queue of failures) can retain a lot of memory, since it references class and method metadata and, through the exception, other objects.

So using exceptions for normal control flow, for instance one per failed lookup in a hot loop, can hurt. Fix it by returning Optional or a result for expected outcomes. For a truly hot path you can use the protected constructor with writableStackTrace=false to skip the stack.

class LightException extends RuntimeException {
    LightException(String m) { super(m, null, false, false); }  // no suppression, no stack trace
}

One log-reading trap: after many throws, the JIT may throw a pre-allocated NullPointerException or similar with an empty stack trace. If you see that, look for earlier occurrences of the same error, or run with -XX:-OmitStackTraceInFastThrow.

Remember: the cost is the stack capture at creation; do not use exceptions for expected outcomes.

What are the rules for exceptions when overriding a method? Intermediate

An overriding method can throw the same checked exceptions, narrower ones, or none. It cannot add a new or broader checked exception, because a caller using the parent type would not know to handle it. It may freely throw any unchecked exception.

Why the rule exists (the substitution principle). A caller writes code against the parent type: Base b = ...; b.run(); and handles only IOException, as declared. At runtime b might actually be a subclass. If the subclass could throw a new checked SQLException, the caller's code would suddenly produce an exception nobody planned for. So the compiler restricts overrides: they may not promise more failures than the original.

Precisely. For each checked exception type declared by the override, it must be the same as, or a subclass of, some exception declared by the overridden method. Fewer is always fine. Unchecked exceptions are not restricted, because callers were never promised anything about them.

Constructors, interfaces and a common trap.

  • Interfaces: implementing Runnable.run() cannot declare throws IOException, which is why work that does I/O inside a Runnable must wrap exceptions. Callable.call() throws Exception is the variant that allows it.
  • Constructors are not overridden, so a subclass constructor may declare any exceptions, but it must at least declare whatever the called super constructor throws.
  • Try-with-resources and the close method: if your AutoCloseable implementation narrows close() to throw nothing, callers using that type directly need no catch for close.

Design takeaway. When designing an interface that many classes implement, declaring a broad checked exception is a decision you cannot easily reverse. That is another reason library designers prefer unchecked exceptions for extensible APIs.

class Base { void run() throws IOException { } }
class Ok1 extends Base { void run() throws FileNotFoundException { } }  // narrower: ok
class Ok2 extends Base { void run() { } }                                // fewer: ok
class Bad extends Base { void run() throws Exception { } }               // broader: compile error

The same rule applies to interface implementations: the interface method sets the maximum. This is one more source of friction with checked exceptions: an implementation that talks to a database cannot throw SQLException through an interface that did not allow it.

Remember: an override may narrow or drop checked exceptions, never widen them.

How should you handle InterruptedException? Senior

It means another thread asked this one to stop. I either let it propagate by declaring throws InterruptedException, or, if I cannot, I restore the flag with Thread.currentThread().interrupt() and then return or exit the loop. I never swallow it, because that erases the cancellation request and the thread keeps running.

What interruption is. Java has no safe way to forcibly stop a thread. Instead, thread.interrupt() sets a boolean interrupt flag on the target and politely says "please stop when convenient". Code that waits (sleep, wait, BlockingQueue.take, Lock.lockInterruptibly) notices the flag, wakes up early, clears the flag and throws InterruptedException. Code that does not block can check Thread.currentThread().isInterrupted() itself.

Why swallowing is a real bug. Imagine a worker thread in a loop and an executor's shutdownNow(), which interrupts workers. If the worker does this:

while (true) {
    try { Thread.sleep(1000); }
    catch (InterruptedException e) { /* ignore */ }   // flag cleared, loop continues forever
    doWork();
}

the thread wakes, the flag is gone, and the loop keeps going. The service never shuts down, deployments hang, and someone ends up with kill -9.

The three correct options.

  1. Propagate: declare throws InterruptedException and let the caller decide. This is the best choice for library and business methods.
  2. Restore and stop: catch it, call Thread.currentThread().interrupt() so that code higher up can still see the flag, then exit the current work (return, break out of the loop).
  3. Restore and finish a critical section first, for example complete cleanup, then restore the flag at the end.

Edge cases that come up. In a Runnable you cannot declare the exception, so use option 2. Never convert it into a generic RuntimeException without also restoring the flag. Virtual threads (Java 21) are cancelled by the same mechanism. Interrupt is cooperation, not force: code running a tight CPU loop that never checks the flag will not stop.

When the exception is thrown, Java clears the interrupt flag, so catching it and carrying on loses the signal and the executor never shuts down cleanly. Blocking calls such as sleep, wait, join, BlockingQueue.take and Future.get all throw it. More on threads in Java concurrency.

try { queue.put(item); }
catch (InterruptedException e) {
    Thread.currentThread().interrupt();   // restore the signal
    return;                               // stop cleanly
}

Remember: propagate it, or re-set the interrupt flag and stop. Never swallow it.

3. Exception design and error handling strategy

How do you design a good custom exception? Intermediate

I name it after what went wrong in the domain (PaymentDeclinedException, not MyException), usually make it unchecked, and always provide a constructor that takes a message and a cause. I add useful final fields such as an error code or entity id, so callers do not have to parse the message.

Why a custom type at all? Compare throw new RuntimeException("payment declined") with throw new PaymentDeclinedException(...). The first can only be matched by parsing the message text, which breaks the moment someone rewords it. The second lets a caller write catch (PaymentDeclinedException e) and lets a global handler map it to HTTP 402. A good exception type is therefore a machine-readable failure, with the message for humans.

A checklist for a design review.

  • Name describes the failure, ends with "Exception" (InsufficientFundsException).
  • Parent expresses the family: PaymentException then PaymentDeclinedException, PaymentTimeoutException. Catch the parent for "any payment problem", the child for one case.
  • Data as typed fields (ids, amounts, retry flag), not embedded in the message string.
  • Message short, has no secrets (card numbers, tokens, passwords), and says what was being attempted.
  • Cause constructor present. Without it people cannot chain.
  • Immutability: fields are final, so a stored exception cannot change.

Pitfalls. Holding a non-serializable field (a connection, a stream) in an exception breaks serialization, for example when it crosses RMI or is stored in a distributed cache. Holding a big object keeps it alive for as long as the exception is referenced. Do not extend Exception out of habit if the caller cannot recover. Avoid a flat explosion of dozens of classes, one per message; use a handful of types plus an error code enum for fine detail that clients can show or translate.

Keep a small hierarchy: one base per module (OrderException) with a few meaningful children, so callers can catch broadly or narrowly. Keep messages safe: no passwords, tokens or personal data. Add serialVersionUID, because Throwable is Serializable. Do not create one class per error message; an enum error code inside one class is often enough.

public class PaymentDeclinedException extends RuntimeException {
    private static final long serialVersionUID = 1L;
    private final String paymentId;
    private final boolean retryable;
    public PaymentDeclinedException(String paymentId, boolean retryable, String msg, Throwable cause) {
        super(msg, cause);
        this.paymentId = paymentId; this.retryable = retryable;
    }
    public String paymentId() { return paymentId; }
    public boolean retryable() { return retryable; }
}

Remember: domain name, message plus cause constructor, final fields with data, small hierarchy.

What is exception translation, and where should it happen in a layered application? Senior

Translation means catching a low-level exception at a layer boundary and throwing one that makes sense to the layer above, with the original as the cause. The repository turns SQLException into a store error, the service turns that into a domain outcome, and the web layer maps domain exceptions to HTTP status codes in one central place. That way upper layers never depend on JDBC or an HTTP client.

Walking one failure through the layers. A user requests GET /orders/17 and the database is down.

  1. Driver: throws SQLTransientConnectionException.
  2. Repository (or Spring's template) translates it to DataAccessResourceFailureException (a Spring type), keeping the cause. The service layer now does not depend on JDBC.
  3. Service decides: this is a system failure, no sensible fallback, so it lets it pass, or wraps it in OrderUnavailableException("cannot load order 17", e). If instead the repository returned empty, the service would throw OrderNotFoundException (a business outcome, not a fault).
  4. Controller advice maps OrderNotFoundException to 404 and OrderUnavailableException to 503, builds a JSON error with a correlation id, and logs once (ERROR for 503, probably nothing or INFO for 404).

Why not let it pass through untouched? Two reasons. First, coupling: if the controller has catch (SQLException e), you cannot swap the database technology without touching the web layer. Second, meaning: SQLException says "something with SQL", while the web layer needs to know "client's fault or server's fault, retryable or not".

@RestControllerAdvice
class ApiErrors {
    @ExceptionHandler(OrderNotFoundException.class)
    ResponseEntity<Problem> notFound(OrderNotFoundException e) {
        return ResponseEntity.status(404).body(new Problem("ORDER_NOT_FOUND", e.getMessage()));
    }
}

Common mistake: translating too early and losing a distinction a higher layer needs (a unique-key violation and a connection failure both becoming "StoreException"). Keep subtypes for the cases the caller must tell apart.

The cost is a little extra code and the discipline to keep the cause every time. Frameworks help: Spring translates JDBC and JPA errors into its DataAccessException hierarchy, and @ControllerAdvice with @ExceptionHandler maps exceptions to responses in one place.

Remember: translate at each layer boundary, keep the cause, map to HTTP in one handler.

Design an error handling strategy for a layered REST service. Senior

I separate three kinds of failure: client mistakes (bad input, not found, conflict: 4xx, no alert), expected business outcomes (insufficient funds), and system failures (database down, timeout: 5xx, alert). I use a small set of unchecked domain exceptions, one global handler that returns a consistent error body with a correlation id and never a stack trace, and I log each failure once where it is finally handled.

Why classify first. The same word "error" covers very different things, and each needs a different response:

KindExampleHTTPLog level and alertingRetry?
Client mistakeMissing field, bad id400, 404, 422INFO or WARN, no alertNo, fix the request
Business outcomeInsufficient funds, duplicate order409, 422INFO, no alertNo
System failureDB down, downstream timeout, bug500, 502, 503, 504ERROR, alert on rateMaybe, safely

A request walked through. POST /payments arrives. Validation rejects a negative amount at the controller: 400 with field errors, nothing deeper runs. The service checks the balance and throws InsufficientFundsException: mapped to 409 with a stable code INSUFFICIENT_FUNDS that the client can show. The service calls a bank API that times out: the HTTP client has a 2 s timeout, one retry with backoff for idempotent calls, then a circuit breaker opens after repeated failures, and the user gets 503 with a correlation id. The log has one ERROR entry for the whole request with the full cause chain.

Details that make this senior-level.

  • Error body is a contract. Clients depend on codes, not messages. Use a stable machine code plus a human message, and never leak SQL, class names or stack traces.
  • Correlation id generated at the edge, put in MDC, returned to the client in a header and in the body, so support can find the log line.
  • Retries need idempotency. Retrying a POST that charged a card without an idempotency key double-charges.
  • Async and batch paths need their own handlers: message consumers need a dead-letter route, scheduled jobs need a catch-all that logs, and background threads need uncaught-exception handlers (earlier questions).
  • Observe it: metrics for error rate by type, alerts on 5xx not 4xx.
  • Validate at the edge (Bean Validation) and fail fast, so deep layers can trust their inputs.
  • One error format: Spring 6 supports RFC 9457 ProblemDetail. For a 500 return a generic message plus the correlation id; details stay in the logs.
  • Calls to other services: timeouts, bounded retries for transient errors only, a circuit breaker.
  • Make writes idempotent so a retry is safe (see the duplicate-payment scenario).
  • Test the failure paths, not just the happy ones.

Remember: classify failures (client, business, system), one global handler, log once, safe retries.

Why is "log and throw" an anti-pattern? How should you log an exception? Intermediate

If every layer logs the exception and rethrows it, one failure produces five log entries with the same stack. That doubles the noise, makes error counts wrong and confuses whoever reads the log at 3 a.m. The rule is: either handle it (and log it there) or let it propagate (adding context in a wrapper). Not both.

What the damage looks like. One failed request, with a repository, a service and a controller each doing log.error(..., e); throw e;, writes the same 80-line stack three times, with three slightly different messages. A dashboard that counts ERROR lines now shows three errors for one failure. Searching by exception text finds three hits and you start wondering whether three things broke.

The principle: one event, one log entry. The place to log is where the exception is consumed, meaning no one above will see it. Layers below the consumer just add context by wrapping. If a lower layer must log something useful that the top cannot know (for example a retry attempt number), log it at DEBUG or WARN without the stack, as a different kind of event.

How to log well.

  • Pass the exception as the last argument to SLF4J, without a {} for it: log.error("cannot send invoice {}", id, ex). The framework recognises a trailing Throwable and prints the stack and causes. Writing log.error("failed: " + ex) loses the stack.
  • Put the business keys (order id, tenant, user) in the message or in MDC so the line is searchable.
  • Level by who should react: user error INFO/WARN, system failure ERROR, a successfully recovered retry WARN.
  • Never log secrets or full request bodies with personal data.
  • For tight failure loops, sample or rate-limit, or log the stack for the first N occurrences and a counter after.

When logging and rethrowing is acceptable: at a process boundary where the exception will cross to code you do not control and may not be logged (a thread pool task, a message listener that rethrows to trigger redelivery). Then log once there and make sure the next layer knows it is already logged, for example with a flag or a specific exception type.

Log at the boundary where the exception stops travelling: the controller advice, the message consumer loop, the scheduler wrapper. Pass the exception object as the last argument so the logger prints the stack and all causes, and put identifying context in the message (order id, operation), plus the correlation id from MDC. Choose the level by impact: user errors at WARN or INFO, system failures at ERROR. For a repeating error in a retry loop, rate-limit the log, because millions of identical stacks can fill the disk.

// bad: logged here and again at the top
catch (SQLException e) { log.error("db failed", e); throw new StoreException("db failed", e); }
// good: add context, log once at the top
catch (SQLException e) { throw new StoreException("cannot load order " + id, e); }

log.error("cannot send invoice for order {}", orderId, ex);   // exception last, no placeholder for it

Remember: handle or propagate, never both. Log once, with the exception object, at the end of the road.

What are the alternatives to exceptions? When would you use a Result type? Senior

Exceptions suit unexpected failures that most callers cannot handle locally. For expected outcomes, a normal return value is clearer and cheaper: Optional for "may be absent", or a result type that carries success or failure and forces the caller to look at both. I use results for validation and business rules where failure is common and local, and exceptions for real faults.

The idea from scratch. A method has an honest return type when its signature describes every outcome. int parse(String) lies, because it can also fail. A result type puts "this can fail" into the return value, so the caller must look at it. The three common forms, from lightest to heaviest:

  1. Special return value: -1, null. Cheap but easy to forget to check; avoid for new code.
  2. Optional<T>: "a value or nothing". Good for lookups (findById). Does not say why it is empty.
  3. Result/Either: "a value or an error description". Good when callers need the reason and several steps are chained.

Chaining example. Validation with a result avoids a pyramid of try/catch:

Result<Order> r = validateCustomer(req)
        .flatMap(c -> reserveStock(req, c))
        .flatMap(s -> charge(req, s));
return switch (r) {
    case Ok<Order> ok  -> ResponseEntity.ok(ok.value());
    case Err<Order> er -> ResponseEntity.unprocessableEntity().body(er.code());
};

(flatMap is a small helper you write on the sealed interface; it is not built into the JDK.)

Use exceptions whenUse result values when
Failure is rare and unexpectedFailure is a normal, frequent outcome (validation)
Most callers cannot handle it locally, so it should bubble upThe immediate caller is expected to branch on it
You want a stack trace for diagnosisYou want zero stack cost and explicit flow

Trade-offs and pitfalls. Results are verbose in Java without helper methods, they do not compose with the many JDK APIs that throw, and teams that mix both styles end up with exceptions wrapped into results wrapped into exceptions. Pick a convention per layer: exceptions for infrastructure and bugs, results for domain validation if you adopt them at all. Spring's controllers, transactions and most libraries are built around exceptions, so a result type must be translated at the edge.

In Java 21 a sealed interface with record cases plus a pattern-matching switch gives a compiler-checked result type with no library (libraries like Vavr offer Try and Either). Optional is poor for errors because it says "nothing" but not why. The trap is mixing styles: a method that returns a Result and also throws makes callers handle both.

sealed interface Result<T> permits Ok, Err {}
record Ok<T>(T value) implements Result<T> {}
record Err<T>(String code) implements Result<T> {}

String msg = switch (parse(input)) {
    case Ok<Integer> ok -> "value " + ok.value();
    case Err<Integer> err -> "error " + err.code();
};

Remember: expected failure = return value; unexpected failure = exception. Pick one style per method.

In Spring, which exceptions roll back a transaction? Intermediate

By default @Transactional rolls back on unchecked exceptions (RuntimeException and Error) and commits on checked ones. So a method that writes to the database and then throws IOException still commits. To change that use @Transactional(rollbackFor = Exception.class).

Why that default? It copies the EJB convention: an unchecked exception means "something unexpected broke, the unit of work is invalid, roll back", while a checked exception is treated like a business outcome the caller may deal with, so the work done so far may still be valid. It surprises people because most developers assume any exception rolls back.

How it works. @Transactional is implemented by a proxy around your bean. The proxy opens a transaction, calls your method, and then decides: if your method returned normally, commit; if it threw, ask the rollback rules whether to roll back or commit. The decision is made by the proxy, from the outside.

Example of the surprise.

@Transactional
public void pay(long id) throws IOException {
    repo.markPaid(id);          // UPDATE executed
    notifier.send(id);          // throws IOException (checked)
}                               // transaction COMMITS: row stays "paid"

@Transactional(rollbackFor = IOException.class)   // now it rolls back
@Transactional(noRollbackFor = IllegalStateException.class)   // opposite: commit anyway

The three "committed anyway / not transactional at all" traps, in order of frequency.

  1. Self-invocation: this.save() inside the same class calls the real object, not the proxy, so no transaction starts.
  2. Swallowed exception: inner try/catch hides the failure from the proxy.
  3. Inner method marks rollback-only: if an inner @Transactional (REQUIRED, joining the outer transaction) throws a runtime exception and the outer catches it, the shared transaction is already marked rollback-only; the outer's commit then fails with UnexpectedRollbackException. Use REQUIRES_NEW if the inner work should be independent.

Also, @Transactional on a private method or on a method of a class created with new does nothing. And the exception must reach the proxy: errors thrown inside an @Async method run on another thread and do not roll back the caller's transaction.

Two more traps give the same "it committed anyway" symptom. If you catch the exception inside the transactional method and swallow it, the proxy sees a normal return and commits. And if you call a transactional method from another method in the same class (self-invocation), the call bypasses the proxy, so no transaction logic runs at all. Private or final methods are also not intercepted by proxies. See Hibernate and JPA.

Remember: rollback on RuntimeException and Error only; swallowed exceptions and self-invocation also defeat it.

How do you deal with NullPointerException in a principled way? Basic

I stop nulls at the entry and avoid returning them. I validate arguments early with Objects.requireNonNull(x, "x"), return empty collections instead of null, and use Optional for return values that may be absent (not for fields or parameters). I never catch an NPE to hide a bug.

What an NPE is. It is thrown when code uses a null reference as if it were an object: calling a method on it, reading a field, unboxing a null Integer to int, or using synchronized (null). Tony Hoare called the null reference his "billion-dollar mistake": it is that any reference can silently be null. The cure is not to catch NPEs but to reduce where null is allowed.

Practical tactics, with examples.

  • Check at the door. this.name = Objects.requireNonNull(name, "name"); in a constructor fails at the point of the mistake instead of ten calls later.
  • Never return null for collections or arrays. Return List.of() or Collections.emptyList(). Callers can then iterate without a check.
  • Optional for return values that can be absent: Optional<User> findByEmail(String e) forces the caller to decide. Do not use it for fields, parameters or collections elements (it adds an object and noise), and never call optional.get() without checking; prefer orElse, orElseThrow, map.
  • Constant first for equals: "ADMIN".equals(role) does not throw if role is null; Objects.equals(a, b) handles both.
  • Beware unboxing: Integer count = map.get(k); int n = count; throws if the key is absent. Use getOrDefault or Integer checks.
  • Tools: @NonNull/@Nullable annotations with IDE or build-time checkers (SpotBugs, Checker Framework, NullAway) turn many NPEs into compile-time warnings.

Debugging: read the helpful message (Java 14+); it names the exact variable or method call that was null, for instance because the return value of "Order.customer()" is null, which shows a chain like order.customer().address().city() failed at customer(). Without it you had to guess which link in the chain was null. Note the message is built lazily and only mentions local variable names if the code was compiled with -g; otherwise it says "<local1>".

Since Java 14 (on by default from 15) the NPE message says exactly what was null, for example Cannot invoke "String.length()" because "name" is null, which saves a lot of debugging time. Annotations like @Nullable with a checker make the contract visible.

Remember: fail fast with requireNonNull, return empty not null, Optional only for return values.

4. Exceptions in lambdas, threads and static initializers

How do you deal with checked exceptions inside lambdas and streams? Intermediate

The standard functional interfaces (Function, Consumer, Supplier) declare no checked exceptions, so a lambda calling something that throws IOException does not compile. The simplest fix is to catch inside the lambda and rethrow as an unchecked exception with the cause. For repeated use, write a small helper, or just use a plain loop, which is often clearest.

Why it does not compile. Function<T,R> has the single method R apply(T t) with no throws clause. A lambda is just an implementation of that method, and an override cannot add checked exceptions (see the override rules). So the compiler rejects the lambda body that can throw IOException.

Four ways out, in order of preference.

  1. A plain for-loop. The loop body can use try/catch or just let the method declare throws. Often the clearest code.
  2. Catch inside the lambda and convert (shown): catch (IOException e) { throw new UncheckedIOException(e); }. UncheckedIOException is a JDK class made for exactly this.
  3. A reusable wrapper like the unchecked(...) helper, so call sites stay short. Libraries like Vavr provide similar helpers.
  4. A custom functional interface that declares throws Exception, used where you control the API (for example your own retry helper taking a Callable).

What happens to the stream. Streams are lazy: the lambda runs during the terminal operation, so the exception is thrown from toList() or collect(), not from map(). When it is thrown, the pipeline stops, items already processed are not undone, and with parallel streams you may get any one of several exceptions. To process everything and report failures afterwards, return a result per item:

List<Result<String>> rs = paths.stream().map(p -> tryRead(p)).toList();   // no throw, inspect each

Pitfall: the "sneaky throw" trick (using generics to throw a checked exception without declaring it) compiles but confuses callers and should be avoided in application code.

An exception in the middle of a stream pipeline stops the whole pipeline. If you want to skip bad items, catch inside the lambda and return an empty Optional or a result, then filter.

@FunctionalInterface interface ThrowingFn<T,R> { R apply(T t) throws Exception; }
static <T,R> Function<T,R> unchecked(ThrowingFn<T,R> f) {
    return t -> { try { return f.apply(t); }
                  catch (Exception e) { throw new RuntimeException(e); } };  // cause kept
}
paths.stream().map(unchecked(Files::readString)).toList();   // toList: Java 16

Remember: wrap in an unchecked exception with the cause, or use a loop. Never drop the cause.

An exception is thrown inside a task submitted to an ExecutorService. Where does it go? Senior

It depends on how I submitted it. With submit() the exception is stored inside the Future and nothing is logged unless someone calls get(), which throws ExecutionException. With execute() it kills the worker thread and goes to the thread's uncaught exception handler, which by default only prints to stderr. A periodic task in a ScheduledExecutorService that throws is silently cancelled and never runs again.

Why this happens. A worker thread in a pool runs a loop: take a task, run it. Different submission methods wrap the task differently. submit wraps it in a FutureTask whose run() catches any Throwable and stores it for get(). So the worker never sees the exception, and nobody logs it. execute runs your task directly, so an escaping exception reaches the worker, which terminates (the pool replaces it) after calling the uncaught exception handler.

A concrete demonstration of the silent failure.

ExecutorService ex = Executors.newFixedThreadPool(2);
ex.submit(() -> { throw new IllegalStateException("boom"); });   // nothing printed at all
Future<?> f = ex.submit(() -> { throw new IllegalStateException("boom"); });
try { f.get(); }
catch (ExecutionException e) { System.out.println(e.getCause()); }  // java.lang.IllegalStateException: boom

Scheduled tasks are the nastiest. With scheduleAtFixedRate the task is also held in a FutureTask. If one run throws, the future completes exceptionally and the executor does not schedule another run. A heartbeat or cache-refresh job dies after one bad run, and the only symptom is that it stops happening.

CompletableFuture. Exceptions inside supplyAsync are captured in the future, wrapped as CompletionException when passed along stages; join() throws CompletionException, get() throws ExecutionException. If nobody calls join, exceptionally or handle, the failure disappears the same way.

Rules to adopt. (1) Wrap every task body in a catch-all that logs, especially scheduled ones. (2) Always do something with the Future. (3) Install a default Thread.setDefaultUncaughtExceptionHandler as a safety net that logs through your logger. (4) Track failed-task counts as a metric. See also Java concurrency.

The fix is to wrap the task body in a try/catch that logs, and always handle the Future result. For pools, set a handler through a custom ThreadFactory with setUncaughtExceptionHandler. The handler only fires for threads that die from the exception, never for ones stored in a Future. For CompletableFuture, exceptions are wrapped in CompletionException, so end every chain with exceptionally or handle.

executor.submit(() -> {
    try { doWork(); }
    catch (Throwable t) { log.error("job failed", t); }   // never let it vanish
});

Remember: submit hides it in the Future, execute prints to stderr, scheduled tasks stop. Catch and log inside the task.

What happens when a static initializer throws? What is ExceptionInInitializerError? Senior

The first caller gets ExceptionInInitializerError with the real exception as its cause. The class is then marked as failed, and every later use in that classloader throws NoClassDefFoundError: Could not initialize class X, which does not show the original cause. So in the logs you see the useless second error thousands of times, and the informative first one is long gone.

Class initialization in brief. The first time a class is used (create an instance, call a static method, read a non-constant static field), the JVM runs its static initializers and static field assignments exactly once, under a lock so it is thread safe. If that code throws an unchecked exception (a static initializer cannot throw checked ones), the JVM wraps it as ExceptionInInitializerError, throws it to that first caller, and marks the class "erroneous". It will never be re-initialized in that classloader.

The timeline that confuses people.

  1. 10:00:01 request A touches Config. Static block reads a missing file and throws. Log: ExceptionInInitializerError ... Caused by: FileNotFoundException.
  2. 10:00:02 request B touches Config. Log: NoClassDefFoundError: Could not initialize class Config. No cause, no hint.
  3. From then on, every request fails with the second error until someone restarts the JVM.
class Config {
    static final Properties P = load();          // static init
    static Properties load() {
        try (var in = new FileInputStream("app.properties")) { ... }
        catch (IOException e) { throw new UncheckedIOException(e); }   // becomes ExceptionInInitializerError
    }
}

Why it hurts in production. The first error may be in a log file that rotated, or from a start-up where nobody was looking. Also, an exception in a static initializer of a framework-managed class can make a whole app fail in a way that looks like a classpath problem.

Safer design. Do not do I/O, network calls or heavy parsing in static initializers. Use lazy holders with clear error handling, or initialise through an explicit init() invoked at start-up that logs and stops the application. If a static init can fail, wrap it with a try/catch that logs the cause itself, so the real reason appears in the logs even if the class is poisoned. Instance initializer failures are different: they just throw from the constructor, and the next new can try again.

When you see "Could not initialize class", search the logs backwards for the first ExceptionInInitializerError, whose "Caused by" is the real problem (often a missing config value or a failed resource load). You cannot recover in the same classloader; you need to fix the cause and restart. Prevention: keep static initialization simple, never connect to remote systems there, and load config in an explicit start-up phase that fails fast with a clear message.

Remember: first failure = ExceptionInInitializerError (real cause); every later one = NoClassDefFoundError (no cause).

5. Generics

What are generics for, and what is type erasure? Intermediate

Generics let the compiler check types, so List<String> rejects an Integer at compile time and you do not cast on every read. Type erasure means that after checking, the compiler removes the type arguments: at runtime a List<String> is just a List, and new ArrayList<String>().getClass() == new ArrayList<Integer>().getClass().

The problem generics solve. Before Java 5 a collection held plain Object. You wrote String s = (String) list.get(0); and nothing stopped a colleague from adding an Integer to that list. The mistake surfaced as a ClassCastException in production, far from the line that caused it. Generics move that check to compile time: List<String> says "only Strings go in", and the compiler enforces it and writes the cast for you.

Why erasure rather than real runtime types. Java 5 had to keep billions of lines of old non-generic code and old libraries working. If List<String> were a different runtime class from List, old and new code could not share objects. So the compiler does its checking and then erases: it replaces every type parameter with its bound (Object if there is none) and adds casts. The runtime stays unaware of generics. (C# chose the opposite, "reified" generics, at the cost of breaking old code.)

What the compiler does, step by step, for a tiny class.

class Box<T extends Number> {
    private T value;
    T get() { return value; }
}
Box<Integer> b = new Box<>();
Integer i = b.get();
// After erasure the class is effectively:
//   class Box { private Number value; Number get() {...} }
// and the call site becomes:  Integer i = (Integer) b.get();
  1. Check: assigning a String to Box<Integer>'s T is a compile error.
  2. Erase: T becomes Number, its first bound.
  3. Cast: the compiler inserts (Integer) where the value is read.
  4. Bridge: if a subclass overrides get() with a more specific return type, the compiler adds a synthetic bridge method so virtual dispatch still works.

What survives erasure. Declarations keep their generic signatures as metadata (field types, method signatures, the generic superclass). Reflection can read those; it cannot ask an object "which T are you?". That asymmetry explains the "type token" trick covered below.

What an interviewer probes next: "Why does List<String> have the same class as List<Integer>?" (Same erased class.) "What is a bridge method?" (Compiler-generated method that keeps overriding correct after erasure.) "Is the cast free?" (Nearly; the JIT removes redundant ones.)

Before Java 5 a List held Object, so you cast on every read and a wrong type failed at runtime with ClassCastException. Erasure was a deliberate choice so old non-generic code and new generic code could work together. The compiler replaces an unbounded T with Object (or with its bound, for T extends Number), inserts casts where values are read, and generates hidden bridge methods where needed so overriding still works. The class file keeps generic signatures of declarations as metadata, which reflection can read, but objects carry no type arguments.

Remember: generics are checked at compile time, erased at runtime, and the compiler adds the casts.

What can you NOT do with generics because of erasure? Intermediate

Anything that needs the type argument at runtime. You cannot write new T(), new T[10] or new List<String>[10], and you cannot use instanceof List<String> (only List<?>). You also cannot use primitives as type arguments, so List<int> is illegal and you pay for boxing.

The one idea behind all the restrictions: at runtime the JVM does not know what T is. Every rule below is the compiler refusing to let you write code that would need that knowledge.

What are bounded type parameters and generic methods? Explain <T extends Comparable<T>>. Intermediate

A bound limits which types are allowed and lets me call the bound's methods. In <T extends Comparable<T>>, T must be comparable with itself, so I can call a.compareTo(b). A generic method declares its own type parameter before the return type, as in static <T> T firstOr(List<T> xs, T fallback), and the compiler usually infers T from the arguments.

Why bounds exist. An unbounded <T> is only known to be an Object, so inside the method you can call just toString, equals and hashCode. To write max you need compareTo. A bound is a promise to the compiler: "whatever T is, it is at least a Comparable", which unlocks those methods.

Reading <T extends Comparable<T>> slowly.

  1. T extends Comparable<T>: T can compare itself to another T. String is a Comparable<String>, so it fits.
  2. Here extends means "is a subtype of or implements", also for interfaces.
  3. The type parameter appears in its own bound (an F-bounded or "recursive" bound). That is normal and is how "compare to my own kind" is expressed. Enums use it: Enum<E extends Enum<E>>.

The problem the ? super T version fixes. Suppose class Apple implements Comparable<Fruit> (apples compare as fruit) and you have List<Apple>. With T extends Comparable<T>, T would be Apple but Apple is not Comparable<Apple>, so the call is rejected. With Comparable<? super T> it is accepted, since Comparable<Fruit> can consume any Apple. This is the PECS rule applied to a bound: the Comparable consumes T values.

Generic methods versus generic classes. A class parameter is fixed for each object (Box<String>); a method parameter is chosen per call, so a method in a non-generic class can still be generic. Static methods cannot use the class's T, so they must declare their own, which is why Collections and List.of are generic methods.

static <T> void swap(T[] a, int i, int j) { T t = a[i]; a[i] = a[j]; a[j] = t; }
swap(new String[]{"a","b"}, 0, 1);        // T inferred as String
<T extends Number & Comparable<T>> T bigger(T x, T y) { ... }   // class bound first, then interfaces

Pitfall: when the compiler cannot infer, for example with a chain starting from an empty collection, write the type witness or assign to a typed variable first.

The more flexible real-world form is <T extends Comparable<? super T>>, because a subclass such as java.sql.Timestamp compares as its parent Date, not as itself. Multiple bounds use & (T extends Number & Comparable<T>), with the class first. After erasure, T becomes its first bound. When inference fails you can give an explicit witness: Collections.<String>emptyList().

static <T extends Comparable<? super T>> T max(Collection<? extends T> c) {
    Iterator<? extends T> it = c.iterator();
    T best = it.next();
    while (it.hasNext()) { T x = it.next(); if (x.compareTo(best) > 0) best = x; }
    return best;
}
String s = firstOr(names, "none");   // T inferred as String

Remember: a bound gives T abilities; use Comparable<? super T> for the flexible form.

Explain wildcards and the PECS rule: Producer Extends, Consumer Super. Senior

? extends T means "some unknown subtype of T": I can safely read items out as T, but I cannot add anything (except null). ? super T means "some unknown supertype of T": I can safely write a T in, but reads only give me Object. So if a parameter produces values for me I use extends, if it consumes values from me I use super, and if both I use the exact type.

The root problem: invariance. List<Integer> is not a List<Number>. Without wildcards you could not write one method that sums a list of Integers and a list of Doubles. Wildcards say "a list of some unknown subtype or supertype" and let the compiler allow only the safe operations.

Reason it out, do not memorise. Take List<? extends Number> xs. It might really be a List<Integer> or a List<Double>; you do not know which.

  • Reading is safe: whatever it is, every element is at least a Number.
  • Writing is unsafe: if you put a Double and the list is a List<Integer>, you corrupted it. So the compiler forbids all adds except null.

Now take List<? super Integer> out. It might be List<Integer>, List<Number> or List<Object>.

  • Writing an Integer is safe: all of these can hold an Integer.
  • Reading is unsafe to rely on: the element could be anything up to Object, so you only get Object.

Why "producer" and "consumer". From the method's point of view a parameter that gives you items to use (a source) is a producer: ? extends. A parameter you put items into (a destination) is a consumer: ? super. Compare Collections.copy(dest, src): src produces, dest consumes.

Real examples in the JDK: Comparator<? super T> in List.sort (a comparator of a parent type can order the children), and Stream.map(Function<? super T, ? extends R>) (the function consumes T and produces R). Design advice: use wildcards on parameters, not on return types, otherwise callers must handle wildcard types.

Why can't I add to a List<? extends Number>? The real list might be a List<Integer>, and adding a Double would corrupt it. The classic example is Collections.copy(List<? super T> dest, List<? extends T> src). A bare ? means unknown: read as Object, write nothing.

double sum(List<? extends Number> xs) { double s = 0; for (Number n : xs) s += n.doubleValue(); return s; }
void fill(List<? super Integer> out) { out.add(1); out.add(2); }
sum(List.of(1, 2.5));               // ok
fill(new ArrayList<Number>());     // ok

Remember: PECS: producer extends (read), consumer super (write), both means no wildcard.

What is the difference between List<?>, List<Object> and a raw List? Intermediate

List<Object> is a list that holds anything, and I can add any object to it, but it only accepts exactly that type: a List<String> cannot be passed to it. List<?> accepts a list of any element type, but I can only read items as Object and cannot add (except null). A raw List turns the generic checks off completely and should be avoided.

Invariance is the key. People assume that because String is an Object, List<String> is a List<Object>. It is not. If it were, you could pass a List<String> to a method that adds an Integer to a List<Object>, and the string list would then contain an integer. Java rejects the assignment to prevent that.

So the three types answer different questions:

  • List<Object>: "a list whose element type is exactly Object." Anything can go in, but only a real List<Object> fits.
  • List<?>: "a list of some type I do not know or care about." Any list fits; since the type is unknown, the compiler will not let you add anything except null, but you can read, call size(), clear() and so on.
  • raw List: "pretend generics do not exist." Anything fits and anything goes in, and the compiler only warns.

If it needs to relate types (copy from one list to another, return the same element type), make it generic: <T> void swap(List<T> l, int i, int j). There is a neat trick with wildcard capture: a public method takes List<?> and calls a private generic helper, which lets you swap elements of an unknown-typed list safely.

A common interview trap is "Is List<?> the same as List<Object>?" Say no, and give the List<String> argument example.

So when a method only needs to look at the list without caring about element type (for example print it or get its size), List<?> is the right choice. List<Object> is rarely what you want, because of invariance: List<String> is not a List<Object>.

void printAll(List<?> xs)        { for (Object o : xs) System.out.println(o); }  // takes any list
void addAny(List<Object> xs)     { xs.add("x"); xs.add(1); }                      // only List<Object>
printAll(List.of("a"));   // ok
addAny(new ArrayList<String>());   // compile error

Remember: List<?> = any list, read-only in practice. List<Object> = exactly that type. Raw = no safety.

Arrays are covariant but generics are invariant. What does that mean and why does it matter? Senior

Covariant means that because Integer is a Number, Integer[] is also a Number[]. That is true for arrays, and it is unsafe: I can store a Double through a Number[] alias and get an ArrayStoreException at runtime. Generics are invariant: List<Integer> is not a List<Number>, so the same mistake is rejected at compile time.

Definitions first. Covariant means the subtype relationship carries over: if Integer is a subtype of Number, then Integer[] is a subtype of Number[]. Invariant means no relationship at all: List<Integer> and List<Number> are unrelated types.

Why arrays are covariant. In Java 1.0 there were no generics, and designers wanted a method like Arrays.sort(Object[]) or fill(Object[], Object) to accept any array of objects. Covariance made that possible, and a runtime store check was added to keep it safe (ArrayStoreException). It is a historical compromise.

The trouble.

  1. Integer[] ints = new Integer[1]; (real runtime type: Integer array).
  2. Number[] nums = ints; compiles, same object.
  3. nums[0] = 1.5; compiles because Double is a Number. At runtime the array knows it is an Integer array and throws ArrayStoreException.

The error is a runtime failure on a line that looks fine. Generics were designed to prevent exactly this, so the compiler rejects List<Number> l = new ArrayList<Integer>() up front.

The practical consequences.

  • Arrays are reified (they know their element type at runtime); generics are erased. These two worldviews do not mix, which is why new T[n] and new List<String>[n] are illegal and why generic varargs warn.
  • For read-only flexibility use List<? extends Number> parameters, the safe version of covariance.
  • Prefer List<T> over T[] in APIs. Use arrays for performance-critical primitive data.

What is a raw type, and why should you avoid it? Basic

A raw type is a generic class used without type arguments, like List instead of List<String>. It exists only so pre-Java-5 code still compiles. With a raw type the compiler switches off the generic checks and gives only an "unchecked" warning, so a wrong value goes in silently and blows up later, somewhere else, as a ClassCastException.

Why a raw type exists. When generics arrived in Java 5, every existing program used List with no arguments. For those programs to keep compiling, List by itself remained legal, and the compiler treats it as "a list of Object with all checks off". The language kept it for migration only, and it is a legacy feature.

What the damage looks like.

List<String> names = new ArrayList<>();
List raw = names;          // warning: unchecked
raw.add(123);              // compiles, no check at all
for (String n : names) {}  // ClassCastException here, far from the add

Also, a raw type affects everything inside the expression: calling a generic method on a raw receiver erases the generics of its return type too, so raw.iterator() returns a raw Iterator, and you lose type safety further down the chain.

What to do instead.

  • Know the type: use List<String>.
  • Do not care about the type: use List<?>.
  • Calling old APIs that return raw types: assign to a properly typed variable in one tiny method and annotate it with @SuppressWarnings("unchecked") plus a comment on why it is safe. Keep the suppression on the smallest scope (one local variable or method), never the whole class.
  • Compile with -Xlint:unchecked,rawtypes in CI so new warnings are noticed.

One legitimate use: instanceof and class literals. You must write x instanceof List or List.class, since type arguments are not allowed there. Those are not harmful raw usages.

If you do not care about the element type, write List<?>, which is safe. Do not suppress unchecked warnings widely: suppress on the smallest scope, with a comment saying why it is safe.

Remember: never use raw types; use List<?> if the element type does not matter.

What is heap pollution, and how can it cause a ClassCastException that looks impossible? Senior

Heap pollution means a variable of a parameterized type refers to an object that is not of that type. It happens through raw types, unchecked casts or generic varargs. The JVM cannot see it at the point of the mistake because the type arguments are erased, so the failure appears later, at the compiler-inserted cast on a line that looks perfectly safe.

The definition made concrete. The compiler promises "a List<String> variable only holds Strings". Heap pollution is a situation where that promise has been broken at runtime. The JVM cannot detect it when it happens, because the list does not know it was supposed to hold Strings. It only notices later, at a place where the compiler inserted a cast to String.

How it can happen, three routes.

  1. Raw types (the example above): the raw alias bypasses the check.
  2. Unchecked casts: (List<String>) someObject compiles with a warning but checks only List.
  3. Generic varargs: static <T> void f(T... xs) makes an Object[] array; if the method leaks it as T[] or stores into it, it can pollute callers. @SafeVarargs is a promise that you do not.

Why the exception "looks impossible". The stack trace points at a line like String s = strings.get(0); which has no visible cast and no obvious bug. The cast is compiler-inserted. The place that stored the wrong object might be in a different class, a library or another thread.

How to debug it.

  1. Compile with -Xlint:unchecked and look at the warnings near where the list was created or populated.
  2. Check who else holds a reference to the list and whether any raw or deserialization code touches it.
  3. In tests, wrap the list with Collections.checkedList(list, String.class), which throws at the moment of the bad insert, giving you the guilty stack trace.

Serialization and JSON are the common production cause. mapper.readValue(json, List.class) gives List<LinkedHashMap> and the code that assigns it to List<User> compiles with an unchecked warning; the failure appears at first read, LinkedHashMap cannot be cast to User.

List<String> strings = new ArrayList<>();
List raw = strings;                 // unchecked warning
raw.add(42);                        // pollution: no error here
String s = strings.get(0);          // ClassCastException: Integer cannot be cast to String

Generic varargs are another source: static <T> void f(T... xs) creates an array that is really an Object[], so the method could store wrong things in it. If your method only reads the array and does not leak it, mark it @SafeVarargs. Another common real-world case: a JSON mapper given List.class returns a list of maps, and the cast fails when you read an element as your class (use a TypeReference). To find the culprit, compile with -Xlint:unchecked and in tests wrap suspicious lists with Collections.checkedList, which checks at insertion.

Remember: treat every unchecked warning as a bug until proven safe; the exception shows up far from the cause.

Why can't you create a generic array, and how does ArrayList get around it? Senior

new T[n] is illegal because arrays need their real element type at runtime to check stores, and T is erased. Library code gets around it by creating an Object[] and casting: (T[]) new Object[n]. That unchecked cast is safe only if the array never escapes to code expecting a real T[].

Why the rule is there, with a worked example. Suppose Java allowed List<String>[] a = new List<String>[1];. Arrays are covariant, so you could then do:

Object[] o = a;                         // legal: array covariance
o[0] = new ArrayList<Integer>();       // runtime store check sees "ArrayList": passes!
String s = a[0].get(0);                 // ClassCastException on a line with no cast

The array's runtime check only sees the erased class ArrayList, so it cannot reject the Integer list. Allowing generic arrays would break the whole promise of generics, so the language forbids creating them. (You can declare such a variable, and you can create List<?>[], whose elements are unknown anyway.)

What ArrayList really does. Internally Object[] elementData. get(i) returns (E) elementData[i]; the cast to E is an unchecked cast that compiles to nothing, and the caller's inserted cast does the real check. Because the array is private and never handed out as E[], nothing can observe the wrong runtime type. This is the standard pattern: keep an Object[] private, cast on read.

The problem case. If you expose the array, it breaks:

class Stack<T> {
    private T[] items = (T[]) new Object[10];
    T[] raw() { return items; }          // caller does: String[] s = stack.raw();
}                                         // ClassCastException: Object[] cannot be cast to String[]

Ways to get a properly typed array when you need one. (1) list.toArray(new String[0]) or list.toArray(String[]::new) (Java 11); (2) Array.newInstance(type, n) with a Class<T> token; (3) avoid the array altogether and use a List<T>.

If it were allowed, you could build a List<String>[], put a List<Integer> in through an Object[] alias, and the array's runtime check could not catch it. ArrayList keeps an Object[] internally and casts on each read. When you must return a real typed array, pass a Class<T> and use Array.newInstance, or accept an IntFunction<T[]>, which is what stream.toArray(String[]::new) does.

@SuppressWarnings("unchecked")
T[] make(int n) { return (T[]) new Object[n]; }       // fine inside, ClassCastException if returned as String[]
String[] arr = list.stream().toArray(String[]::new);  // the clean way

Remember: store an Object[] and cast on read; to return a real typed array, take a Class or an array constructor.

If generics are erased, how does Jackson still know the type when I pass a TypeReference? Senior

Erasure removes type arguments from objects, but the class file still stores the generic signature of declarations: fields, method parameters and the generic superclass. new TypeReference<List<User>>() {} creates an anonymous subclass whose generic superclass records List<User> permanently, and the library reads it with reflection.

The puzzle. Erasure means a List<User> object does not know it holds Users. So when Jackson parses a JSON array, and you pass List.class, it has no way to know the elements should be User; it falls back to maps. We need a way to hand Jackson the full type List<User> at runtime.

The loophole. Erasure removes type arguments from objects and local expressions, but not from class declarations. If you write class Foo extends Bar<User>, the class file records "superclass is Bar<User>" and Foo.class.getGenericSuperclass() returns it as a ParameterizedType. An anonymous class new TypeReference<List<User>>() {} is exactly such a declaration, written inline. The empty {} is the whole trick, and forgetting it (writing new TypeReference<List<User>>(), which is abstract and will not compile) is why the braces are needed.

How the library uses it.

  1. TypeReference's constructor calls getClass().getGenericSuperclass() on the anonymous subclass.
  2. It reads the first type argument: List<User>, a ParameterizedType with raw type List and argument User.
  3. The mapper builds a deserializer for a list whose element deserializer is for User.
List<User> users = mapper.readValue(json, new TypeReference<List<User>>() {});   // elements are Users
List<User> bad   = mapper.readValue(json, List.class);                             // elements are LinkedHashMap
// alternative without anonymous class:
JavaType t = mapper.getTypeFactory().constructCollectionType(List.class, User.class);

Other places you meet it. Spring's ParameterizedTypeReference for RestTemplate.exchange; Guava's TypeToken; Gson's TypeToken. All are the "super type token" pattern (named by Neal Gafter).

Limits: it works only when the type is fixed where you write the anonymous class. Inside a generic method <T>, new TypeReference<List<T>>() {} captures the unresolved T, so the library cannot find the real type. Pass the concrete type in from the caller instead.

That is why mapper.readValue(json, new TypeReference<List<User>>() {}) works, while passing List.class would give a list of maps, not Users. Guava's TypeToken and Spring's ParameterizedTypeReference use the same "super type token" trick. For non-generic cases a plain Class<T> token is enough.

Remember: an anonymous subclass keeps its generic superclass in the class file; frameworks read it back.

6. Java I/O: streams, readers, buffering, charsets

What is the difference between byte streams and character streams (readers and writers)? Basic

InputStream and OutputStream move raw bytes: images, zip files, network packets. Reader and Writer move characters. A reader sits on top of a stream and uses a charset to decode bytes into characters, and a writer encodes characters back. I use streams for binary data, readers for text, and I always name the charset.

The core distinction: bytes versus characters. A file on disk is just bytes. The letter "é" is not a byte; it is a character that must be encoded into one or more bytes by a rule (a charset). In UTF-8 "é" is 2 bytes, in ISO-8859-1 it is 1 byte. A byte stream does no interpretation at all. A character stream adds the decode step so your code deals in char and String.

Why wrappers. Java I/O follows the decorator pattern: a small piece of functionality per class, stacked as needed. Source (FileInputStream) gives bytes; InputStreamReader decodes with a charset; BufferedReader adds an in-memory buffer and readLine(). Other decorators you will meet are GZIPInputStream (decompress), DataInputStream (read ints, doubles) and ObjectInputStream.

A mistake that shows the point. Reading a PNG with a FileReader tries to decode image bytes as text; invalid sequences are replaced with a replacement character, the data is permanently altered, and the image is corrupt. Conversely, reading a UTF-8 text file with a raw InputStream and casting each byte to char works for ASCII and shows garbage for every accented letter.

try (var r = new BufferedReader(new InputStreamReader(new FileInputStream(f), StandardCharsets.UTF_8))) {
    String line;
    while ((line = r.readLine()) != null) { handle(line); }
}
// shorter, same thing, UTF-8 by default:
try (var r = Files.newBufferedReader(path)) { ... }

Edge cases. read() on a stream returns an int 0 to 255, or -1 at the end, which is why it is an int, not a byte. System.in is an InputStream; wrap it with a Scanner or reader to read text. Closing the outermost wrapper closes everything beneath it.

The bridge classes are InputStreamReader and OutputStreamWriter: new InputStreamReader(in, StandardCharsets.UTF_8). A reader on binary data corrupts it, and a stream on text forces you to decode by hand. Each wrapper adds one job (the decorator pattern), and closing the outermost one closes the rest.

Remember: streams = bytes, readers = characters via a charset. Say the charset out loud.

Why does buffering matter, and when do you need to flush? Intermediate

Each unbuffered read() or write() can become a system call into the OS, which is slow compared to memory. A buffered wrapper (BufferedReader, BufferedOutputStream, default 8 KB) moves data in big blocks and hands out small pieces from memory, which can be orders of magnitude faster. The catch is that data sitting in the buffer is not written yet, so I must flush() or, better, close(), which flushes first.

Why unbuffered is slow. Reading a file one byte at a time with FileInputStream.read() makes a native call (and typically a system call) for every byte. A system call crosses from user mode into the kernel and back, which costs far more than touching memory. For a 100 MB file that is 100 million crossings. A buffered stream reads 8 KB at a time with one system call and then returns bytes from a Java array, so that same file needs about 12,000 calls. The speed-up is easily one or two orders of magnitude for byte-at-a-time code. (Exact numbers depend on OS and hardware; measure, do not assume.)

How a buffered writer behaves, step by step.

  1. w.write("hello") copies the characters into an internal array. Nothing reaches the file yet.
  2. More writes fill the array. When it is full, it is written to the underlying stream in one go.
  3. flush() pushes the current buffer contents to the underlying stream right now, then flushes that stream.
  4. close() calls flush() and then closes the resource.

If the program exits (or crashes) between steps 1 and 3, those buffered characters are lost. This is why a log or output file can end mid-sentence.

Layers of "flush" people mix up.

  • flush(): Java buffer to the OS (the OS page cache).
  • FileChannel.force(true) or FileDescriptor.sync(): OS cache to physical disk. This is what durability requires (databases do it on commit).
  • PrintWriter and PrintStream swallow IOExceptions; use checkError() if you care.

When flushing explicitly matters. Interactive protocols over sockets: if you write a request into a buffered stream and wait for the reply without calling flush(), the request is still in the buffer and both sides wait forever, a classic hang. Also for progress or log output you want to appear immediately. When not to buffer: when you already read or write in large chunks (a 64 KB byte array), a buffered wrapper adds only an extra copy. Tune the buffer size only with measurements.

If you forget to close a buffered writer, the tail of the file can be silently missing. flush() only hands data to the OS; to force it to disk you need FileChannel.force(true). A GZIPOutputStream must be closed (or finish()ed) to write its trailer, or the file is corrupt.

try (var w = Files.newBufferedWriter(Path.of("out.txt"))) {   // UTF-8 by default
    w.write("hello"); w.newLine();
}   // close() flushes

Remember: buffer for speed, close (which flushes) so the last bytes are not lost.

Explain charsets. What is the default charset, and why is it a trap? Intermediate

A charset is the rule that maps characters to bytes. UTF-8 (1 to 4 bytes per character, ASCII as a subset) is the sensible choice for almost everything. If you write with one charset and read with another you get garbage like "Ã©" instead of "é". The trap: new String(bytes), getBytes(), FileReader and new InputStreamReader(in) use the platform default, which before Java 18 depended on the OS, so code worked on a laptop and broke on the server.

What a charset really is. A character set is the list of characters (Unicode assigns each a number, a code point, for example "é" is U+00E9). An encoding is how those numbers become bytes. Java uses "charset" for the encoding. UTF-8 stores code points in 1 to 4 bytes: ASCII (A to Z, digits) in one byte, accented Latin in two, most Asian scripts in three, emoji in four. ISO-8859-1 (Latin-1) uses exactly one byte per character, so it cannot represent most of the world's text.

Why mismatches produce garbage. Take "café". UTF-8 bytes: 63 61 66 C3 A9. If a reader assumes Latin-1, it reads C3 as "Ã" and A9 as "©" and shows "cafÃ©". This garbled look is called mojibake and is a strong hint that a UTF-8 file was decoded as Latin-1. The opposite (Latin-1 bytes decoded as UTF-8) often gives replacement characters or errors, because lone bytes like E9 are not valid UTF-8.

The default charset trap in detail. new FileReader(f) and new String(bytes) use the JVM's default charset. On Windows that was often windows-1252, on Linux containers frequently "ANSI_X3.4-1968" (plain ASCII) when no locale was set, and on macOS UTF-8. The same jar behaved differently per machine. Since Java 18 the default is UTF-8 (JEP 400), but code can run on older JVMs, and System.out and stdout.encoding are separate settings that still follow the console. The fix is simply to pass the charset everywhere.

Behaviours worth knowing for interviews.

  • Malformed input policy. Decoders can REPORT an error or REPLACE bad bytes with U+FFFD. new String(bytes, cs) and InputStreamReader replace silently; Files.readAllLines, Files.lines and CharsetDecoder (by default) report. For strict validation use a CharsetDecoder with onMalformedInput(REPORT).
  • BOM. Windows tools (Excel, Notepad historically) may put a UTF-8 BOM (EF BB BF) at the start; Java does not strip it, so the first header in a CSV looks like "﻿id" and lookups fail. Strip it explicitly.
  • Unicode length. "😀".length() is 2 because Java strings are UTF-16 and emoji need a surrogate pair; use codePointCount for characters. Cutting a string with substring in the middle of a pair makes invalid text.
  • HTTP and databases have their own charset settings (Content-Type: ...; charset=, MySQL utf8mb4, not the 3-byte utf8). The chain is only as good as its weakest link.

From Java 18 (JEP 400) the default is UTF-8 everywhere, but older runtimes still exist, so I always pass the charset. The NIO helpers Files.readString, Files.newBufferedReader and Files.lines default to UTF-8 regardless of version.

byte[] b = "café".getBytes(StandardCharsets.UTF_8);          // 5 bytes
String wrong = new String(b, StandardCharsets.ISO_8859_1);   // "cafÃ©"  (mojibake)
String ok = new String(b, StandardCharsets.UTF_8);           // "café"

Smaller traps: invalid bytes are silently replaced by InputStreamReader but throw MalformedInputException in Files.readAllLines. A UTF-8 byte-order mark (EF BB BF) is not stripped, so the first CSV field may contain an invisible character. And String.length() counts UTF-16 units, so an emoji counts as 2.

Remember: always pass StandardCharsets.UTF_8; never trust the platform default.

How do you read a very large file efficiently without running out of memory? Intermediate

I stream it instead of loading it. For text I use BufferedReader.readLine() or Files.lines(path) in try-with-resources, and for binary data I read in fixed chunks (8 KB to 1 MB). I process each record, write results out as I go and keep per-record state small, so memory use stays constant however large the file is.

The mental shift. Do not think "load, then process". Think "pipe": data flows through a small window. Memory use should depend on the size of one record or chunk, not on the size of the file. A 50 GB log can be scanned by a program with a 64 MB heap if it only ever holds one line at a time.

Why read-all methods fail. Files.readAllBytes allocates one array the size of the file; for a 1.5 GB file that is a 1.5 GB contiguous allocation, which needs a heap bigger than that, and a file over about 2 GB cannot be read this way at all because arrays cannot exceed about 2 GB (int index). readAllLines is worse: each line becomes a String object with header and array overhead (Java 9+ compact strings help for Latin-1 text), so memory can be a couple of times the file size. Result: OutOfMemoryError on production data that worked in the test environment with a small file.

A pattern for processing with bounded memory.

  1. Open with try-with-resources.
  2. Read a line or chunk.
  3. Transform and either aggregate in a small structure (a counter, a map of bounded size) or write straight out.
  4. Periodically flush or batch (for example, insert into the database every 1,000 rows and commit).
  5. Track progress and make the job restartable (store the last processed line offset or id).
try (BufferedReader r = Files.newBufferedReader(in);
     BufferedWriter w = Files.newBufferedWriter(out)) {
    String line;
    while ((line = r.readLine()) != null) {
        if (line.contains("ERROR")) { w.write(line); w.newLine(); }   // constant memory
    }
}

Other tools for the job.

  • Memory-mapped files (FileChannel.map) let the OS page a file in on demand and give random access; a single mapping is limited to 2 GB, so map in regions. Good for index files and random reads, not required for simple sequential scans.
  • Sorting data larger than memory needs an external merge sort: sort chunks, write them out, merge.
  • Parallelism: split by byte ranges (aligned to line boundaries) when the disk can feed multiple readers; sequential reads on a single spinning disk usually do not benefit.

Pitfalls: forgetting to close Files.lines or Files.walk leaks a file handle (they hold an open directory or file); a single huge line (a file with no newlines) still blows the heap with readLine, so cap the line length for untrusted input; and collect(toList()) at the end of a stream defeats the point.

Files.readAllBytes, readString and readAllLines load everything (and are limited to about 2 GB because arrays are int-indexed), so they are for small config files only. Files.lines returns a lazy stream that holds an open file, so it must be closed. Java strings and objects also have overhead, so a 4 GB file can need far more than 4 GB of heap once parsed into objects. For database loads use JDBC batches (hundreds to a few thousand rows) and commit per batch.

try (Stream<String> lines = Files.lines(path)) {       // lazy, close it
    long errors = lines.filter(l -> l.contains("ERROR")).count();
}
try (InputStream in = Files.newInputStream(path)) {
    byte[] buf = new byte[1 << 16]; int n;
    while ((n = in.read(buf)) != -1) { process(buf, n); }
}

Remember: stream and process as you go; read-all methods are only for small files.

7. NIO, files and paths

What is the difference between java.io.File and java.nio.file.Path and Files? Why prefer NIO.2? Basic

File is the old API: methods like delete() and mkdir() just return false on failure without saying why, and it handles links and attributes poorly. Path and the Files helper class (NIO.2, Java 7) throw descriptive exceptions such as NoSuchFileException and AccessDeniedException, and support copy and move options, atomic moves, attributes, symbolic links, directory walking and even zip file systems. I use Path/Files in all new code.

The practical problems with java.io.File.

  • file.delete() returns false for "does not exist", "no permission", "directory not empty" and "file is locked". You cannot tell which.
  • file.mkdir() returns false likewise; file.renameTo() behaves differently on different platforms.
  • No real symbolic-link support, limited metadata, no way to walk a tree lazily, no atomic operations.
  • File is a pathname holder that also does I/O, mixing two jobs.

How NIO.2 splits the jobs. Path is an immutable value: a sequence of names, with pure string-like operations (resolve, relativize, normalize, getParent, getFileName), and nothing touches the disk. Files is a set of static methods that do the actual work and throw specific exceptions. FileSystem is the abstraction behind it, which is why the same API works for a zip file (FileSystems.newFileSystem) or an in-memory test file system.

What is the difference between classic I/O and NIO? When do selectors matter? Intermediate

Classic I/O is stream based and blocking: a thread calls read() and waits until data arrives, so one busy connection needs one thread. NIO is buffer and channel based and can be non-blocking: many channels are registered with one Selector, and a single thread asks "which channels are ready?" and handles only those. Classic I/O is simple and fine for files and modest concurrency; NIO selectors matter when you hold thousands of mostly idle connections.

The scaling problem first. A server must talk to many clients. With blocking I/O the simple design is one thread per client: socket.getInputStream().read() blocks that thread until bytes arrive. Each platform thread reserves stack memory (often around 1 MB of address space, committed gradually) and the OS must schedule it. Ten thousand mostly idle connections means ten thousand sleeping threads, which wastes memory and adds context-switch overhead. The question NIO answers is: "can one thread watch many sockets and only act on the ones with data?"

How a selector loop works.

  1. Open a Selector. Open each SocketChannel in non-blocking mode (configureBlocking(false)).
  2. Register each channel with the selector and the events of interest: OP_ACCEPT, OP_READ, OP_WRITE, OP_CONNECT.
  3. Loop: call selector.select(). It sleeps until the OS (epoll on Linux, kqueue on macOS, IOCP-based or select on Windows) reports ready channels.
  4. For each ready key, do the small, non-blocking action (accept a new connection, read whatever bytes are available into a buffer, write what can be written).
  5. Go back to step 3.

Because a read may return only half a message, you must keep per-connection state and assemble messages yourself. That is the hard part and the reason people use Netty instead of raw selectors.

Important clarification. NIO for files is not non-blocking: FileChannel is always blocking, and regular files cannot be registered with a selector. The non-blocking benefit is for sockets and pipes. For async file work use AsynchronousFileChannel or a thread pool. Rule of thumb: ordinary business services use a framework (Tomcat with virtual threads, or WebFlux/Netty) rather than raw NIO; the interview answer is understanding why and what the trade-off is.

With 10,000 blocking connections you need about 10,000 threads, which costs memory and context switching. With a selector, one event-loop thread (backed by epoll on Linux) serves them all. Netty, Vert.x and Spring WebFlux are built on this. The trade-off is a harder programming model: you must never block the event loop, and heavy or blocking work must move to another pool. Tomcat uses NIO to hold connections cheaply but still gives each active request its own thread. Since Java 21, virtual threads let you write simple blocking-style code and still scale to many connections, which reduces the need for hand-written non-blocking code (see concurrency).

Remember: blocking = a thread per connection; NIO selector = one thread for many ready channels.

Explain NIO channels and buffers. How is a ByteBuffer different from a byte array? Senior

A channel (FileChannel, SocketChannel) is a connection that reads and writes through buffers rather than streams. A ByteBuffer is a block of memory with three numbers: capacity (its size), position (next index to read or write) and limit (first index you must not touch). After filling it from a channel I call flip() to switch to reading, then clear() or compact() to prepare for the next fill.

Channels versus streams. A stream is one-directional and moves bytes one after another. A channel is closer to the OS handle: it can be read and written (some are bidirectional), can be non-blocking, can be positioned (FileChannel.position), and can transfer data directly to another channel. Channels never touch Java arrays directly; they work with ByteBuffer.

The three numbers, with a worked example. Allocate ByteBuffer.allocate(10): capacity 10, position 0, limit 10.

  1. Put 4 bytes: position 4, limit 10. The buffer is in fill mode: you may write up to limit.
  2. Call flip(): limit becomes 4, position becomes 0. Now it is in drain mode: you may read 4 bytes, no more.
  3. Read 4 bytes with get(): position 4 equals limit, hasRemaining() is false.
  4. clear(): position 0, limit 10 again (data is not erased, just considered overwritable). If you had read only 3 of the 4 bytes, compact() copies the 1 unread byte to the front and sets position to 1 so the next fill appends after it.

Why this design. The buffer is a reusable fixed block that tracks how much of it is meaningful, so a channel can read "up to n bytes" into it and you can find out how many arrived. A plain byte[] needs you to carry a separate length variable around.

A plain byte array has no notion of "how much is valid", while a buffer tracks it. flip() sets limit to the old position and position to 0. A buffer can be on the heap (allocate) or direct (allocateDirect, outside the Java heap), which avoids one copy during I/O but is costlier to allocate and not freed promptly. FileChannel.transferTo lets the OS move data to a socket without passing through user space (zero-copy, typically via sendfile). Buffers are not thread-safe.

try (FileChannel ch = FileChannel.open(path, StandardOpenOption.READ)) {
    ByteBuffer buf = ByteBuffer.allocate(8192);
    while (ch.read(buf) != -1) {
        buf.flip();
        while (buf.hasRemaining()) consume(buf.get());
        buf.clear();
    }
}

Remember: fill, flip, drain, clear. A buffer tracks position and limit; an array does not.

How do you write a file so readers never see a half-written file? Senior

I write the full content to a temporary file in the same directory, close it, and then rename it over the final name with Files.move(tmp, target, ATOMIC_MOVE). A rename within one file system is atomic on common systems, so a reader sees either the old complete file or the new complete file, never a mix. A crash during the write leaves only a stray temp file.

The problem. You write a 200 MB export to export.csv directly. For several seconds the file exists but is partial. A reader (another process, a file watcher, a downstream job triggered by "file appeared") opens it and processes truncated data. If your process crashes mid-write, the half-written file stays and looks valid. Overwriting an existing good file is even worse: the old good copy is destroyed before the new one is complete.

The fix: separate "being written" from "published". On POSIX file systems (and NTFS in practice) a rename of a file into place is a single directory operation: the name export.csv switches from pointing at the old data to pointing at the new data in one step. There is no moment when it points at half of each.

  1. Create a temp file in the same directory (export.tmp123), so it is on the same file system.
  2. Write all content, flush, close. Optionally FileChannel.force(true) so the bytes are on disk before the rename, otherwise a power cut after the rename could leave an empty file in the new name on some file systems.
  3. Files.move(tmp, target, ATOMIC_MOVE) (optionally with REPLACE_EXISTING; on some platforms replace behaviour with ATOMIC_MOVE is implementation-specific).
  4. Consumers read only final names, ignoring the temp suffix. If a consumer needs a signal, publish a small "ready" marker or use the rename event itself.

What can still go wrong.

  • Different file systems (temp in /tmp, target on a mounted volume) turn the move into copy plus delete, which is not atomic. Java signals this with AtomicMoveNotSupportedException, which is helpful rather than silent.
  • Network file systems (NFS, SMB, object-store mounts) may not guarantee atomic rename or visibility ordering. For S3-like stores there is no rename; use a manifest or "write then flip a pointer" design.
  • A reader that already opened the old file keeps seeing the old data on Unix (the old inode lives until closed); on Windows replacing an open file may fail.
  • Appending to a shared log file is a different problem (use a single writer or FileChannel locks).

The same idea is the general pattern for safe updates elsewhere: build the new version off to the side, then swap one pointer (blue-green deployments, copy-on-write data structures, database transactions).

The temp file must be on the same file system, otherwise atomic move fails with AtomicMoveNotSupportedException. Use Files.createTempFile(dir, "x", ".tmp") for the name, and tell consumers to ignore .tmp files. If you also need to survive power loss, force the temp file to disk before the rename. This matters when another process watches the folder (a file-watch event can fire before the write finishes).

Path tmp = Files.createTempFile(dir, "export", ".tmp");
Files.writeString(tmp, content, StandardCharsets.UTF_8);
Files.move(tmp, dir.resolve("export.csv"), StandardCopyOption.ATOMIC_MOVE);

Remember: write to a temp file in the same folder, then atomic rename.

8. Serialization

How does Java serialization work? What do Serializable and transient do? Basic

Serialization turns an object graph into a byte stream (ObjectOutputStream.writeObject) and rebuilds it later (ObjectInputStream.readObject). A class opts in by implementing the marker interface Serializable, which has no methods. All non-static, non-transient fields are written, and every object they reference must also be serializable, or I get NotSerializableException.

What problem serialization solves. Objects live in memory. To save them to disk, send them to another JVM, or cache them in a session store, you need a sequence of bytes that can recreate an equivalent object. Java builds this for you through reflection: you do not write the format. ObjectOutputStream walks the object graph, writes class descriptors and field values, handles shared references and cycles (an object referenced twice is written once), and ObjectInputStream reverses it.

A small example.

class User implements Serializable {
    private static final long serialVersionUID = 1L;
    String name;
    transient String password;          // not written
    Address home;                       // Address must be Serializable too
    static int count;                   // not written, belongs to the class
}
try (var out = new ObjectOutputStream(Files.newOutputStream(p))) { out.writeObject(user); }
try (var in  = new ObjectInputStream(Files.newInputStream(p)))  { User u = (User) in.readObject(); }
// u.name restored, u.password == null

Reading it step by step. On writeObject: check the class is Serializable, write its descriptor (name, serialVersionUID, field list), write each non-transient instance field recursively. On readObject: allocate the object without running the constructors of Serializable classes, set the fields from the stream, and run the no-arg constructor only for the first non-serializable superclass (usually Object). That explains the surprise that field initializers and constructor checks in your class are bypassed.

Consequences to remember.

  • A class that holds a non-serializable object (a Thread, a Connection, a Logger in some frameworks) fails with NotSerializableException unless that field is transient.
  • A transient field comes back as default, so you often need to rebuild it in readObject or lazily.
  • Collections serialize their contents; ArrayList writes its elements, not the empty spare capacity.
  • Singletons and enums need special care (enums are safe; singletons need readResolve).
  • Where you still meet it: HttpSession replication, some caches (Hazelcast, Ehcache disk store), RMI, legacy messaging.

A transient field is skipped and comes back as null, 0 or false; use it for caches, threads, connections and secrets. static fields belong to the class and are not written. Two details interviewers like: on reading, the constructor of the class itself is not called (that is why invariants can break), and if the parent class is not Serializable, its public or protected no-arg constructor runs to initialize the parent's fields. Serialization writes the whole graph, so one careless reference can drag in a huge structure.

Remember: Serializable opts in; transient and static are skipped; the constructor is not run on read.

What is serialVersionUID? What happens if you do not declare it? Intermediate

It is a version number for the class. When reading, Java compares the number in the stream with the one in the loaded class and throws InvalidClassException if they differ. If I do not declare it, Java computes one from the class structure, so even a harmless change like adding a method changes it and old data becomes unreadable. So I declare it explicitly: private static final long serialVersionUID = 1L;.

What it is for. A serialized stream carries the class name and a long version tag. When you read it, the JVM loads your current class and checks the tag. Matching tags say "same version of the class, the fields line up". Mismatching tags raise InvalidClassException: local class incompatible: stream classdesc serialVersionUID = ..., local class serialVersionUID = ... rather than risk filling fields wrongly.

What happens when you leave it out. The JVM calculates a hash from the class name, interfaces, fields, methods and more. Adding a public method, changing a modifier, or even compiling with a different compiler can change the hash. A rolling deploy then breaks: node A (new code) writes sessions to a shared cache, node B (old code) fails to read them. Or you restart an app that restored data from disk and every old object is rejected.

Compatibility table with an explicit UID.

When to bump the number. When you make an incompatible change and want old data rejected deliberately (change 1L to 2L), or when you handle versions yourself in readObject. The typical value is 1L; the number itself is arbitrary. IDEs and the serialver tool can generate one, but a fixed constant is a design decision, not a computed one.

Danger of "fixing" the error by setting the UID to match the old one. That silences the check but does not make the data compatible; if the layout truly changed, you may deserialize garbage. Also note that -Xlint:serial warns when a Serializable class lacks the field.

With a fixed id, adding a field is compatible (old data gives it the default value) and removing a field is compatible (the data is ignored). Changing a field's type, renaming or moving the class (the class name is in the stream), or changing between class and enum is incompatible. This causes real outages when old and new nodes share a cache or session store during a rolling deploy. For data that outlives a deploy, prefer a schema-based or JSON format.

Remember: declare it yourself; a computed one changes on almost any edit.

How do you customize serialization: writeObject, readObject, readResolve, the serialization proxy? Senior

I add private writeObject and readObject methods, call defaultWriteObject() or defaultReadObject() first, then handle extra data. In readObject I treat the stream as untrusted input: re-validate invariants and make defensive copies, because deserialization builds the object without running my constructor. readResolve() swaps in another object, which keeps a singleton single.

The core problem these hooks solve. Default serialization copies fields blindly and skips your constructor. Imagine a class DateRange whose constructor enforces start <= end and makes defensive copies of its Date fields. An attacker or a bug can supply bytes with start > end, or hold a reference to the internal Date objects inside the stream. After default deserialization you have a DateRange that violates its own invariants.

The hooks, with when to use each.

HookPurposeTypical use
writeObject(ObjectOutputStream)Add or change what is writtenWrite a computed or transient-derived value after defaultWriteObject()
readObject(ObjectInputStream)Restore and validateRe-check invariants, defensively copy mutable fields, rebuild transient fields
readResolve()Replace the freshly read object with anotherSingletons, canonical instances, enums-like classes
writeReplace()Substitute another object before writingSerialization proxy

The serialization proxy pattern in code.

public final class DateRange implements Serializable {
    private final Date start, end;
    public DateRange(Date s, Date e) {                // validating constructor
        start = new Date(s.getTime()); end = new Date(e.getTime());
        if (start.after(end)) throw new IllegalArgumentException();
    }
    private Object writeReplace() { return new Proxy(this); }
    private void readObject(ObjectInputStream in) throws InvalidObjectException {
        throw new InvalidObjectException("proxy required");   // block direct forged streams
    }
    private static class Proxy implements Serializable {
        private final Date start, end;
        Proxy(DateRange r) { start = r.start; end = r.end; }
        private Object readResolve() { return new DateRange(start, end); }  // constructor runs: validation applies
    }
}

The only thing in the stream is the Proxy; reading it calls the real constructor. It adds a bit of code but closes the "object without constructor" hole completely, which is why Effective Java recommends it.

Other facts. The methods must be private with exact signatures (they are found by reflection, not an interface). readResolve can be any access modifier but is inherited-sensitive (a private one is not used by subclasses). Records are serialized by their components and deserialized through the canonical constructor, so validation in the compact constructor applies automatically. Enums serialize only their name, which makes them the safest singleton.

The safest design is the serialization proxy pattern: writeReplace returns a small private nested class holding the logical state, and its readResolve rebuilds the real object through the normal constructor, so all validation runs. Records work like this by design: they are rebuilt through the canonical constructor (their custom hooks are ignored). Enums are serialized by name only and always come back as the same constant.

private void readObject(ObjectInputStream in) throws IOException, ClassNotFoundException {
    in.defaultReadObject();
    if (amount < 0) throw new InvalidObjectException("amount must be >= 0");   // re-validate
    items = List.copyOf(items);                                                  // defensive copy
}

Remember: deserialization skips the constructor, so re-validate in readObject or use a serialization proxy.

Why is deserializing untrusted data dangerous? How do you protect against it? Senior

readObject instantiates whatever classes the stream names and runs their readObject methods before my code can check the type. An attacker builds a stream from "gadget" classes already on the classpath whose normal methods chain together into running a command, so the result can be remote code execution. The best protection is to never deserialize untrusted Java objects: use a data-only format such as JSON or Protobuf with a fixed schema.

The mechanism in plain steps.

  1. Your service accepts bytes and calls new ObjectInputStream(in).readObject(). You may expect a Settings object.
  2. The stream says "I contain an object of class X". ObjectInputStream loads X, allocates it, and calls X's readObject or sets fields. This happens before readObject returns, so your (Settings) cast or instanceof check comes too late.
  3. Many library classes have readObject methods that do real work: call hashCode on keys of a HashMap, invoke a comparator, resolve a URL, run a transformer. An attacker chains these (a "gadget chain") so that, starting from innocent-looking HashMap.readObject, the chain ends in Runtime.exec. Famous chains used Apache Commons Collections, Spring and others, which is why tools like ysoserial exist.

Even without code execution there are denial-of-service stream tricks: deeply nested or huge arrays or a hash collision structure that eats CPU and memory before anything is validated.

Defence in layers.

  1. Avoid it. Use JSON or Protobuf into fixed data types. This removes the attack class.
  2. Allow-list filter. ObjectInputFilter inspects each class (and depth, array length, number of references, stream bytes) before it is created: 
    var f = ObjectInputFilter.Config.createFilter("com.myco.model.*;java.base/*;maxdepth=10;maxbytes=1000000;!*");
ois.setObjectInputFilter(f);     // reject everything not listed
    A JVM-wide default can be set with -Djdk.serialFilter=.... Block-lists are weak because new gadgets appear; use allow-lists.
  3. Reduce the classpath of risky libraries and keep dependencies patched (a Commons Collections or similar update closes known chains).
  4. Authenticate the data with a signature or MAC before parsing: if only your own system could have produced the bytes, forging becomes hard. Encrypting alone does not authenticate.
  5. Least privilege and isolation: the process should not be able to spawn commands or reach internal networks anyway.

Where this bites in real systems: session cookies and "remember me" tokens holding serialized objects, JMX/RMI endpoints, message queues (JMS ObjectMessage), cache servers, and "view state" in old web frameworks. The same class of bug appears with unsafe JSON/YAML polymorphic deserialization (Jackson default typing, SnakeYAML constructing arbitrary classes). In an interview, name the principle: "never let untrusted data choose which classes to instantiate".

If I must use Java serialization, I set an allow-list ObjectInputFilter (Java 9, backported to 8u121; JVM-wide with -Djdk.serialFilter=com.myco.*;!*, per-stream filters, and context-specific filters since Java 17), limit depth, array size and stream bytes, keep libraries patched, and run with least privilege. The same class of problem appears in JSON mappers with default typing enabled on untrusted input.

Remember: the object is built before you can check it. Never deserialize untrusted bytes; otherwise allow-list with ObjectInputFilter.

What are the alternatives to Java serialization, and when would you choose each? Intermediate

Java's built-in format is Java-only, fragile across versions, slow, large and a security risk, so I avoid it for anything new. For APIs and config I use JSON (Jackson). For service-to-service messages and storage I use a schema-based binary format such as Protobuf or Avro, which are compact and have clear rules for adding fields. The deciding questions are: who reads it, how long must old data stay readable, how big and fast must it be, and is the source trusted.

Why the built-in format is a poor choice for new work.

  • Java only. Other languages cannot read it, so it ties systems together.
  • Tightly coupled to class structure. Renaming a package or field breaks old data; the format is the class.
  • Bulky and slow. It writes class descriptors and uses reflection, so it is larger and usually slower than Protobuf or other binary formats.
  • Security (previous question) and the "no constructor" semantic surprise.

How to choose, as a decision flow.

  1. Who reads it? A browser or third party: JSON over HTTP. Humans debug it easily, every language supports it.
  2. High-volume internal service calls or events with long-lived consumers? A schema-based format. Protobuf (with gRPC) uses numbered fields: you can add optional fields, never reuse a field number, and old and new readers interoperate. Avro stores the schema alongside (or in a registry) and resolves reader and writer schemas, which suits Kafka and data lakes where data lives for years.
  3. Same-JVM short-lived cache? Sometimes a fast Java-specific library or Kryo is acceptable, but then you accept version fragility; clear the cache on deploy.
  4. Untrusted source? Never Java serialization; use a strict schema and validate.

Compatibility rules in practice. With Protobuf: add new fields with new numbers, treat missing fields as defaults, do not change types, reserve removed numbers. With JSON and Jackson: ignore unknown properties on read (FAIL_ON_UNKNOWN_PROPERTIES false) so older clients tolerate newer servers, and use explicit field names via @JsonProperty, not class internals. With Avro: give new fields defaults so older data resolves.

Trade-off summary. JSON: easiest, bigger, no enforced schema (use JSON Schema or OpenAPI for contracts). Protobuf: compact and fast, needs code generation and tooling. Avro: best for data pipelines, needs a schema registry operationally. Choose by evolution needs and tooling, not just by byte size.

What is Externalizable, and how is it different from Serializable? Intermediate

Externalizable extends Serializable but gives me full control: I implement writeExternal and readExternal and write exactly the bytes I want, and nothing is saved automatically, not even superclass fields. On reading, Java first calls the class's public no-argument constructor and then readExternal.

The difference in one table.

SerializableExternalizable
Who decides what is writtenJava, by reflection over fieldsYou, in writeExternal
Superclass fieldsWritten if the superclass is SerializableOnly if you write them yourself
On read, constructor calledNone of the serializable classesPublic no-arg constructor of this class, then readExternal
transientRespectedMeaningless: you control everything
Missing no-arg constructorFineInvalidClassException
public class Point implements Externalizable {
    private int x, y;
    public Point() { }                                   // required, public
    public Point(int x, int y) { this.x = x; this.y = y; }
    public void writeExternal(ObjectOutput o) throws IOException { o.writeInt(x); o.writeInt(y); }
    public void readExternal(ObjectInput i) throws IOException { x = i.readInt(); y = i.readInt(); }
}

Why someone would use it. Default serialization writes field names and type descriptors for each class, which is wasteful for tiny objects sent in huge numbers. With Externalizable you write only the two ints: smaller, and the format is decided by you, so you can version it with an explicit version byte. Some frameworks (Hazelcast, older Coherence) offer their own variants of this idea (DataSerializable, PortableObject).

Why it is rarely the right choice now. The order of reads must exactly mirror the order of writes, any mismatch silently produces wrong data, and the public no-arg constructor means an object can exist in an uninitialized state. You also still carry the security profile of Java serialization. If you want control over the bytes, a purpose-built schema format is safer and works across languages.

It can give smaller and faster output and lets me manage versions by hand. The costs are more code, the risk of forgetting a field, and the mandatory public constructor. The security issues are the same as for Serializable. Today most teams pick a schema-based format instead.

Remember: Externalizable = you write every byte, and the class needs a public no-arg constructor.

9. Real-life scenarios

Each scenario is answered the same way: a one-line diagnosis, then situation, what you check first, the fix, and how you prevent it next time.

Orders silently stop being saved. The logs show nothing wrong. A teammate finds an empty catch block. What do you do? Intermediate

An empty catch swallowed the failure, so callers think the save worked. I remove it, let the exception travel (translated, with the cause) to the global handler that logs once and returns a 5xx, and reprocess the missed orders from the source data.

Why this is such a damaging bug. Everything looked healthy: no errors in the log, no alerts, HTTP 200 on every request. The only symptom was a business number (orders per day) drifting down. A swallowed exception turns an observable failure into silent data loss, which is the worst category because discovery depends on a customer complaining.

Investigation, in order.

  1. Prove the loss. Compare orders received (access log, message broker, payment provider) with rows in the database for the same window. This gives you the missing set and the start time.
  2. Find the first failure. Use version control history on the catch block to see which deploy introduced it. The start time of the loss should match that deploy.
  3. Find the real exception. Temporarily log inside the catch (or reproduce locally). It may be something simple like a new non-null column or an oversized string; the empty block hid it for days.
  4. Fix the cause and the handling. The catch should translate and rethrow; the real failure then surfaces as a 5xx and is retried or alerted.
  5. Recover the data. Replay from the source of truth (the broker topic, the upstream log, the payment events), idempotently so already-saved orders are not duplicated.

Prevention beyond the code fix: static analysis rules (empty catch, catch (Exception) in service code), an alert comparing business counters across systems, and a test asserting that a failing repository produces an error response, not a success.

Situation: a save method catches Exception, does nothing and returns; support tickets arrive days later. Check first: reproduce with a failing input, find when the first order went missing and compare with the deploy that added the catch (version control blame). Fix: catch only what you can handle; translate and rethrow the rest. Prevent: a review rule and static analysis against empty catch blocks, a metric and alert on save failures, and a test that proves a failing repository gives a failure response.

// before
try { repo.save(order); } catch (Exception e) { }
// after
try { repo.save(order); }
catch (DataAccessException e) { throw new OrderStoreException("cannot save order " + order.id(), e); }

Remember: a swallowed exception turns a loud failure into silent data loss.

After a few hours the service fails with "Too many open files" and "Timeout waiting for connection from pool". How do you investigate? Senior

That is a resource leak: something opens files, sockets or connections and does not close them on every path. I confirm the descriptor count grows, find what is leaking, and fix it with try-with-resources.

What the two symptoms mean together. "Too many open files" means the process hit the OS limit on file descriptors (sockets and files both count; the usual default is 1024 unless raised with ulimit -n). "Timeout waiting for connection from pool" means every pooled database connection is checked out and none comes back. Both grow with uptime and clear on restart: the signature of a leak.

Step-by-step investigation.

  1. Trend, not snapshot. Sample the descriptor count every minute for an hour (ls /proc/PID/fd | wc -l, or a metric such as process_open_fds). A steady climb confirms a leak; a sawtooth that stays below the limit does not.
  2. Classify. lsof -p PID grouped by type. Many TCP ... CLOSE_WAIT entries point to sockets the remote side closed but your code never closed (often HTTP clients). Many regular files point to unclosed readers or Files.list/Files.walk streams. Connections to the database port point to JDBC.
  3. Find the borrower. HikariCP's leakDetectionThreshold logs the stack trace of the code that borrowed a connection too long. For files, a heap dump shows many FileInputStream or FileDescriptor objects, and their referrers.
  4. Read the suspect code looking for any path (early return, exception, a continue) that skips close.
// leaks if parse() throws
Connection c = ds.getConnection();
Statement st = c.createStatement();
parse(st.executeQuery(sql));
c.close();

// fixed
try (Connection c = ds.getConnection();
     Statement st = c.createStatement();
     ResultSet rs = st.executeQuery(sql)) {
    parse(rs);
}

Other classic leaks. An HTTP client response body not consumed or closed, so the connection never returns to its pool; a ZipFile or Scanner not closed; threads that block holding a connection while waiting for another pool (nested pool deadlock). Raising the limit or the pool size only delays the failure; fix the leak itself.

Check first: count open descriptors over time (ls /proc/PID/fd | wc -l on Linux) and group with lsof -p PID to see whether they are files, sockets to one host, or database connections. Take a thread dump to see threads waiting for the pool. Turn on pool leak detection (HikariCP leakDetectionThreshold), which prints the stack of the code that borrowed a connection and never returned it. Fix: usual culprits are an early return or exception before close(), an unclosed Files.lines or Files.list stream, or an HTTP response body not consumed. Prevent: try-with-resources by rule, static analysis for resource leaks, dashboards for open descriptors and pool usage, and a long-running load test that exposes slow leaks.

Remember: a problem that grows with time and a restart that "fixes" it means a leak. Count descriptors, then try-with-resources.

Customer names with accents show as "Ã©" after a release to Linux, though they looked fine on laptops. Why, and how do you fix it? Intermediate

The bytes are right but they are being decoded with the wrong charset, because some code uses the platform default, which differs between a Windows laptop and a Linux server. I pass StandardCharsets.UTF_8 everywhere and agree the encoding as part of the file or API contract.

Why it worked on laptops. The developers' machines had a UTF-8 (or matching Windows) default charset and the test data round-tripped through the same default in both directions, so it appeared fine. On the Linux server in a container with no locale set, the JVM default became plain ASCII or Latin-1 (before Java 18), so the same code read and wrote with a different mapping.

Two different failure shapes, and what each means.

  • "Ã©" for "é" (mojibake): UTF-8 bytes were decoded as Latin-1 or Cp1252. The data is intact in the bytes; only the reader is wrong.
  • "?" or U+FFFD: the text was encoded to a charset that cannot represent the character, so it was replaced by "?" at write time. That data is permanently lost and no re-decoding brings it back.

Telling these apart decides whether you can repair the data.

Diagnosis chain. Follow the data through every hop and ask "which charset here?":

  1. Browser or client to server: the request Content-Type charset and the servlet container's default (for example request.setCharacterEncoding).
  2. Your code: new String(bytes), getBytes(), FileReader, PrintWriter, Scanner without a charset.
  3. JDBC and database: connection parameter (MySQL characterEncoding=UTF-8 and column type utf8mb4), table collation.
  4. Output: response headers, file writer, log appender encoding.

Print the actual bytes (xxd or HexFormat.of().formatHex(bytes), Java 17) at each hop; the hop where "C3 A9" turns into "C3 83 C2 A9" is where a second wrong decode and re-encode happened (the "double encoding" case).

Repair of already-corrupted rows works only for the mojibake shape and only if it happened exactly once. Test on a copy first. Set -Dfile.encoding=UTF-8 as a stop-gap on old JVMs, but still fix the code, as the property does not cover everything (console and native.encoding are separate on newer JDKs).

Check first: look at the raw bytes with xxd: "é" as C3 A9 is UTF-8, E9 is ISO-8859-1 or Cp1252. Search the code for new String(bytes), getBytes(), FileReader and InputStreamReader without a charset, and check the database connection charset and the HTTP Content-Type charset. Fix: explicit charsets; repair already-corrupted data by re-decoding (new String(s.getBytes(ISO_8859_1), UTF_8)) if it was misdecoded exactly once. Prevent: a lint rule against charset-less overloads, tests run with a non-UTF-8 default on older JDKs, and Java 18 or newer where UTF-8 is the default.

Remember: garbled text means a charset mismatch. Look at the bytes, then name the charset in code.

A nightly import job fails with OutOfMemoryError on a 4 GB file, although it worked on small test files. What is wrong? Intermediate

The job loads the whole file (Files.readAllLines or one big String) and builds a big list of objects, so memory grows with file size. I switch to streaming: read line by line, process each record, and write results in batches.

Reproduce it with arithmetic. A 4 GB text file with 50 million lines, loaded via readAllLines, creates 50 million String objects. Each has an object header, a hash field, a reference to a byte array with its own header and length; allocate roughly 40 to 60 bytes of overhead per line plus the characters, plus the 8-byte (compressed 4-byte) slot in the list. So memory is roughly the file size plus a few GB of overhead, and the JVM also needs room for copying garbage. A 4 GB heap (or the default quarter of RAM) is not enough. On a 20 MB test file you never saw it.

Steps to resolve.

  1. Confirm with the heap dump that the dominating object is the list or string (the dump's dominator tree names the field).
  2. Rewrite the reading loop to process one record at a time, as in the large-file question.
  3. Check the other memory consumers in the pipeline: collecting all parsed objects into a list for a later bulk insert has the same problem, just one step later. Insert in batches.
  4. If the job truly needs a global operation (dedupe, sort, group), use a bounded approach: a database table or temp file with an index, external sort, or a hash of keys in a compact structure (a Set<Long> of 50 million ids is itself over 1 GB, so consider a Bloom filter or the database).
  5. Make it restartable: record progress (last line or id) per batch so a failure at 90 percent does not restart from zero.
try (Stream<String> lines = Files.lines(path);
     Connection c = ds.getConnection();
     PreparedStatement ps = c.prepareStatement(INSERT)) {
    c.setAutoCommit(false);
    int n = 0;
    for (Iterator<String> it = lines.iterator(); it.hasNext(); ) {
        bind(ps, it.next()); ps.addBatch();
        if (++n % 1000 == 0) { ps.executeBatch(); c.commit(); }
    }
    ps.executeBatch(); c.commit();
}

Do not just raise -Xmx. It buys time until the next larger file, and a large heap raises GC pause and cost. Streaming fixes the growth rate rather than the symptom.

Check first: a heap dump (-XX:+HeapDumpOnOutOfMemoryError) shows one huge array or list as the largest object. Remember that Java strings and objects carry overhead, so a 4 GB file needs well over 4 GB of heap once parsed. Fix: BufferedReader.readLine() in a loop or Files.lines inside try-with-resources, JDBC batches of a few hundred to a few thousand rows with a commit per batch, so memory stays constant. For sorting or grouping, use external sort or let the database do it. Prevent: a test with a generated large file, a heap limit in CI, and a rule that bulk-read methods are for known-small files only.

Remember: memory should not grow with input size. Stream and batch.

A security scan flags an endpoint that reads a Java-serialized object from a cookie. How serious is it and what do you do? Senior

It is critical: the server calls readObject() on bytes the client controls, so a gadget class on the classpath can give an attacker code execution. I block or filter the endpoint at once, then replace the design so no client-supplied Java objects are deserialized.

Why "critical", with the exact reasoning. A cookie is client-controlled input. If the server deserializes it with ObjectInputStream, the attacker chooses which classes get instantiated and their field values. If the classpath contains any known gadget chain (very common with older Commons Collections, Spring, Groovy, Hibernate), the attacker gets arbitrary command execution as the application's OS user, with access to its database credentials, keys and internal network. This is pre-authentication in many designs, since cookies are read before login checks.

Response, in time order.

  1. Contain (hours). Block the cookie at the gateway or WAF, or disable the endpoint. Add a strict allow-list ObjectInputFilter as a temporary guard (-Djdk.serialFilter allows a quick JVM-wide patch without code changes).
  2. Assess exposure. Look at logs for odd class names, InvalidClassException, ClassNotFoundException, long cookies, unusual child processes or outbound connections from the app host. If exploitation is plausible, treat secrets on that host as compromised and rotate them.
  3. Fix the design (days). Do not hand the client a serialized object. Options: keep session state on the server and give the client an opaque random session id; or put a small, flat data in a signed token (JWT with a strong algorithm, or JSON plus an HMAC verified before parsing).
  4. Prevent. Dependency scanning for gadget-bearing libraries, a code-review rule against readObject on external input, and a unit test or static check that fails the build when ObjectInputStream appears in request-handling code.

A subtle point to mention. Signing the cookie helps only if the key stays secret and the signature is verified before deserialization. Encryption without authentication is not enough, since attackers can tamper with ciphertext in some modes. And a cookie that is "only readable by our code" is not safe if the key or the generation logic is guessable.

Check first: is the data signed or encrypted with a key the client does not know? Which libraries on the classpath have known gadget chains? Do logs show odd class names in InvalidClassException (probing)? Immediate step: a strict allow-list ObjectInputFilter or disable the endpoint, and patch vulnerable libraries. Real fix: keep session state on the server, or send JSON with an explicit schema and an HMAC checked before parsing. Prevent: dependency scanning, a code-review ban on readObject for external input, and rotating any secrets the host held if exploitation is possible.

Remember: client-controlled Java deserialization equals remote code execution. Replace it, do not just patch it.

A scheduled cleanup job ran for weeks and then simply stopped, with no error in the logs. What happened? Senior

One run threw an exception that escaped the task, and ScheduledExecutorService.scheduleAtFixedRate (and scheduleWithFixedDelay) suppresses all later runs when that happens. The exception sits in the returned ScheduledFuture, which nobody reads. I wrap the whole body in try/catch (Throwable), log it, and restart the job.

Why the JDK works this way. scheduleAtFixedRate returns a ScheduledFuture. The javadoc says: "If any execution of the task encounters an exception, subsequent executions are suppressed." The exception is stored in the future and the executor simply never reschedules. It is a documented but surprising behaviour, designed around the idea that a failing periodic task should not hammer a broken resource forever; the price is silence.

Timeline of the incident.

  1. Day 1 to day 27: the job runs every 10 minutes, deleting expired rows.
  2. Day 28, 02:10: the database fails over; the job's query throws a runtime exception.
  3. Executor stores the exception in the ScheduledFuture. No log line, because nobody calls get(). The executor thread is fine and idle.
  4. From 02:20 on, nothing runs. The table grows, disk fills, and an unrelated alert fires weeks later.

Fix and hardening.

scheduler.scheduleWithFixedDelay(() -> {
    try { cleanup(); }
    catch (Throwable t) { log.error("cleanup failed, will retry next run", t); }
    finally { lastRun.set(Instant.now()); }       // heartbeat
}, 0, 10, TimeUnit.MINUTES);
  • Choose scheduleWithFixedDelay when runs must not overlap or pile up (delay is measured after the end of the previous run); scheduleAtFixedRate tries to keep a start-to-start cadence and runs back-to-back to catch up after a slow run.
  • Expose a "last successful run" gauge and alert when it is older than a few intervals. This catches stops from any cause, including deadlock inside the task.
  • Do not swallow Errors blindly in the catch: for OutOfMemoryError consider failing the process.
  • If using Spring @Scheduled, errors are logged by a default handler and the schedule continues, but a custom TaskScheduler or an ErrorHandler bean can change that, so verify.

The same silent-stop effect appears in a thread-pool worker that died from an uncaught exception, and in a Kafka consumer loop that exits on an unexpected exception without restarting.

Check first: confirm there is no try/catch around the task body and look for a failure (a database blip, a null pointer) around the time it stopped; a thread dump will show no activity for that job. Fix: catch Throwable inside the task so one bad run does not cancel the schedule. Spring @Scheduled logs the error and keeps going, but check your error handler anyway. Prevent: a heartbeat metric (last successful run time) with an alert if it is older than two intervals.

Remember: an uncaught exception cancels a periodic task silently. Catch inside, and alert on a missing heartbeat.

After a network timeout, your client retried "create payment" and the customer was charged twice. How do you prevent it? Senior

A timeout means "unknown outcome", not "failed": the first request probably succeeded and only the response was lost. I make the operation idempotent with an idempotency key, so the retry returns the stored result instead of creating a second payment.

The logic of the failure. The client sent POST /payments, the server processed it and committed, and the response was lost or slow. The client saw a timeout. From the client's side, "no reply" is ambiguous: the request may not have arrived, may have been processed, or may still be running. Retrying a non-idempotent operation in this situation duplicates the effect. HTTP says GET, PUT and DELETE are idempotent by definition; POST is not, so it needs help.

Idempotency key flow, step by step.

  1. Client creates a UUID for this logical payment and sends it in an Idempotency-Key header. It reuses the same key on every retry of that payment.
  2. Server begins a transaction and tries to insert (key, request hash, status "in progress") into an idempotency table with a unique constraint on key.
  3. If the insert succeeds: process the payment, store the response with the key, commit both together, and return the response.
  4. If the insert hits the unique constraint: another request with this key exists. If it finished, return the stored response; if still in progress, return 409 or make the caller wait; if the request hash differs, reject (the key was reused for a different request).
  5. Expire keys after a window (for example 24 hours).
CREATE TABLE idempotency (
  key        VARCHAR(64) PRIMARY KEY,
  req_hash   CHAR(64) NOT NULL,
  response   JSON,
  created_at TIMESTAMP NOT NULL
);

Calling external payment providers. Pass your idempotency key through to the provider (most payment APIs support one), so a retry inside your server also cannot double-charge. A natural business key (order id with a unique constraint on "one successful payment per order") works as a second line of defence.

Retry policy details. Retry only errors that are safe and transient (connect timeouts, 429, 502, 503, 504), cap attempts (three is typical), use exponential backoff with full jitter so many clients do not retry in lockstep, honour Retry-After, and put a circuit breaker in front of a failing dependency. Retry at one layer only; nested retries multiply load. Make clear which operations are safe to retry in documentation.

Check first: compare the two requests in the server logs: same payload, different request ids, seconds apart. Fix: the client generates one unique key per logical operation and sends it on every retry. The server stores the key with the result in the same transaction as the payment, under a unique constraint, and returns the stored result for a repeat. Refund the duplicates. Retry only transient errors (timeouts, 503, 429), with a small attempt limit, exponential backoff with random jitter, and retries at one layer only (otherwise three layers of retries turn one failure into 27 calls). Prevent: every non-idempotent POST accepts an idempotency key, and tests replay the same request twice. See Distributed systems.

Remember: never retry a non-idempotent call without an idempotency key.

A @Transactional method failed halfway, but part of the data was committed anyway. Why? Senior

Almost always one of three causes: the method threw a checked exception (Spring commits for those by default), it caught the exception itself so the proxy saw a normal return, or it was called from another method in the same class, which bypasses the proxy so there is no transaction at all.

Systematic diagnosis. Treat it as a checklist, from the cheapest to check upward:

  1. Was there a transaction at all? Enable logging.level.org.springframework.transaction.interceptor=TRACE (and JpaTransactionManager at DEBUG). Look for "Getting transaction for [...]" and "Completing transaction" or "Rolling back". No "Getting transaction" means the proxy was bypassed: self-invocation, private/final method, or the bean was created with new.
  2. What exception left the method? Checked exceptions commit by default.
  3. Did the exception reach the proxy? A catch inside the method (or an @Async boundary) hides it.
  4. Which operations are in the transaction? Work done through a different datasource, a REST call, or a message sent to a broker is not rolled back by the database transaction. Sending a Kafka message and then failing leaves the message published.
  5. Propagation and nesting. A REQUIRES_NEW inner method commits independently of the outer one. And a rollback-only mark on a shared transaction leads to UnexpectedRollbackException at the outer commit.
@Service class OrderService {
    @Transactional public void place(Order o) {
        repo.save(o);
        this.audit(o);               // self-invocation: REQUIRES_NEW is ignored, no new transaction
    }
    @Transactional(propagation = REQUIRES_NEW) public void audit(Order o) { ... }
}
// fix: move audit() into another bean (AuditService) and inject it

Verify the fix with an integration test using a real database (for example a Testcontainers instance), forcing a failure after the first write and asserting the first write is absent. Note that Spring's @Transactional test annotation rolls back everything at test end, which can hide the problem; for this check, run the service outside a test transaction.

Check first: set logging.level.org.springframework.transaction=DEBUG to see whether a transaction started and whether it rolled back, then read the code for the three patterns (also private or final methods, and objects not managed by Spring). Fix: rollbackFor = Exception.class for checked exceptions, rethrow after logging, and move the inner method into another bean. Prevent: an integration test against a real database that forces a failure and asserts nothing was persisted. Details in the Spring rollback question above.

Remember: checked exception, swallowed exception, or self-invocation: those are the three reasons a rollback does not happen.
