1. Salesforce: APIs, search and per-tenant caching

You wrote "OpenAPI-first" REST services. What does that mean in practice, and why do it? Basic

OpenAPI-first means the API contract (a YAML or JSON specification) is written and reviewed before the code, and the server stubs, models and client code come from it. The contract is the source of truth, so consumers, tests and documentation cannot drift from what the service really does.

The typical workflow (generic, adjust to what you really did):

  1. Draft or edit the spec: paths, request and response schemas, status codes, error model, auth scheme.
  2. Review it as a contract in a pull request. Reviewers who own consuming services comment here, which is far cheaper than after the code exists.
  3. Generate interfaces and DTOs (for example with the OpenAPI Generator Maven or Gradle plugin) and implement the generated interface in a controller.
  4. Run contract checks in CI: lint the spec, compare it with the previous version to detect breaking changes, and validate that responses match the schema.

Why it helps: parallel work (a client team can build against the spec), consistent error shapes across services, and generated clients (your "SAL" libraries) that stay in step with the server. What it costs: generated code can be awkward, the spec must be maintained, and teams sometimes edit generated code by hand, which breaks regeneration.

Probing follow-up: "What is the opposite, and when would you pick it?" Code-first (annotations generate the spec) is faster for a small internal service with one consumer. Contract-first wins when many teams consume the API.

Make it yours: say which generator and build tool you really used, whether the spec lived in the same repo as the service, and what CI check enforced it. If you only edited existing specs, say that honestly and describe what you reviewed.

Remember: the spec is written first and reviewed as a contract; code and clients are derived from it.

How did you support V1, V2 and V3 of an API at the same time, and how do you decide when a change needs a new version? Intermediate

A change needs a new version only if it breaks an existing consumer. Additive changes (a new optional field, a new endpoint) stay in the current version. Breaking changes go into a new version, and old versions stay alive until consumers migrate.

ChangeBreaking?
Add an optional response fieldNo (clients must ignore unknown fields)
Add an optional request field with a safe defaultNo
Remove or rename a field, change its type or meaningYes
Make an optional request field requiredYes
Tighten validation, change an error code or statusUsually yes
Change pagination or default orderingOften yes, because clients depend on it silently

Common implementation patterns: version in the URL path (/v2/...) or in a header. Separate controllers and DTOs per version, with a shared service layer so business rules are not copied three times. A mapping layer converts version DTOs to the internal model. This keeps V1 frozen while V3 evolves.

The hard parts: (1) tests per version, because a shared service change can break V1 silently; (2) a deprecation policy: announce, add a deprecation header, watch traffic per version in logs, and remove only when traffic is near zero; (3) bug fixes: a fix that changes behaviour might itself be breaking, so decide whether to patch all versions.

Trade-off: three versions means three contracts to test and document. The alternative, one version that never breaks, forces ugly compatibility hacks. A middle path is additive evolution plus a new version only for real breaks.

Make it yours: what actually triggered V2 and V3 (a field redesign? a pagination change?), how consumers were told, and how you knew V1 was safe to retire. Do not claim a retirement that did not happen.

Remember: only breaking changes earn a new version; share the service layer, freeze the old contract, and track traffic per version.

What is a "SAL" client library, and what goes wrong with shared client libraries? Intermediate

A SAL is a client library that wraps calls to a service: it builds requests, adds authentication and tenant headers, handles retries and timeouts, and maps responses to typed objects, so each consuming team does not re-implement that. Because it is generated or maintained next to the contract, it stays in step with the API.

  • Sensible defaults: connect and read timeouts, bounded retries with backoff only for idempotent calls, propagation of tenant, user and trace headers.
  • A clear exception model so callers can tell "not found" from "service down".

You built Elasticsearch queries dynamically from configuration-backed registries. Explain the design and its risks. Senior

Instead of hard-coding one Java query builder per search, field behaviour (which fields are searchable, their type, boost, how they map to match, term or range clauses) lives in a registry loaded from configuration. A generic builder reads the registry and the request filters and assembles the Elasticsearch query DSL. Adding a searchable field becomes a configuration change.

Likely structure (generic; confirm against your code):

  • A registry maps a logical field name (the API name) to its physical Elasticsearch field, type, and allowed operators.
  • A request filter such as "name contains X and status in [A, B]" is validated against the registry, then translated into bool clauses: text goes to match, exact values to term/terms on keyword fields, ranges to range. Clauses that do not affect scoring go in filter context, which is cacheable and faster than must.
  • A tenant filter is always added by the framework, not by the caller.

Risks and how to handle them:

RiskControl
Query injection or user-supplied raw DSLOnly registry-approved fields and operators; never concatenate user text into JSON; use the builder API
Expensive queries (leading wildcards, deep nested, huge terms lists)Limits on clause count, terms size, page depth; disallow wildcard on large fields
Mapping drift: registry points to a field that was reindexed or renamedStartup validation of the registry against the mapping, tests
Bad config reaches productionSchema validation, review, staged rollout, safe defaults
Harder to read than a plain queryLog the generated DSL at debug level, unit tests with expected JSON

Why config rather than code: new fields need no code release and consistent behaviour across APIs. Why not: a generic engine is harder to debug and can hide a slow query behind configuration.

Make it yours: what the registry looked like (YAML? database?), how changes were reviewed, and one query that was wrong or slow because of the registry. Say "I believe" for parts you did not build.

Remember: a registry plus a generic builder gives flexibility; guard it with allow-lists, limits and mapping validation.

How do you guarantee one tenant never sees another tenant's search results in Elasticsearch? Senior

The tenant constraint is added centrally in the query builder, as a filter the caller cannot omit, and the tenant identity comes from the authenticated context, never from a request parameter. Defence in depth: index design, per-tenant routing or aliases where appropriate, and tests that try to cross the boundary.

Options for isolating data in Elasticsearch (generic):

ApproachStrengthCost
Shared index, tenant id field, mandatory filterCheap, scales to many small tenantsOne missing filter leaks data; noisy neighbour
Filtered alias per tenant over a shared indexFilter built into the alias, hard to forgetMany aliases bloat cluster state at high tenant counts

Routing by tenant idQueries touch fewer shardsHot shard for a huge tenant

Controls that hold regardless:

  1. Tenant id is taken from the verified token or context in one place and passed to the builder.
  2. The builder wraps the user query: bool { filter: [tenant term], must: [user query] }, so a user clause with should or must_not cannot widen the result.
  3. Aggregations, suggestions and "get by id" calls get the same filter; leaks often happen in the less-used paths.
  4. Automated test: two tenants with overlapping data, assert each query returns only its own.
  5. Code review checklist item for any new search path.
Make it yours: which isolation model you really had, and where the tenant filter was added. Do not claim index-per-tenant if it was a shared index.

Remember: enforce the tenant filter in one central place, outside the caller's control, and test every path including aggregations.

How did you design per-tenant Redis caching, and how do you avoid cross-tenant cache hits? Intermediate

Every cache key starts with the tenant id (and a version or type prefix), such as tenantId:entity:id, built by one helper so developers cannot forget it. TTLs and size limits are set per cache type, and invalidation is by exact key or by a tenant-scoped prefix pattern.

Design points:

  • Key builder: one utility creates keys from a context object. Raw string keys in business code are rejected in review.
  • TTL plus explicit invalidation: TTL bounds staleness if an invalidation is missed.
  • Tenant-wide invalidation: deleting all keys for one tenant should not use KEYS (it blocks the server). Use SCAN with a pattern in the background, or put a tenant version number in the key and bump it (old keys then expire by TTL).
  • Noisy neighbour: one tenant filling memory evicts others. Mitigate with per-tenant TTL, value-size limits, and monitoring of keys per tenant.
  • Failure mode: if Redis is down, fall back to the source with a circuit breaker so the database is not crushed.

Typical bug to mention: a cache key built from entity id only (no tenant), where ids are unique per tenant but not globally. Two tenants with id 42 then share a cache entry. Prevent it by construction, not by discipline.

Make it yours: whether you used Spring Cache or a custom wrapper, how you invalidated a whole tenant, and any real stale-data bug you fixed.

Remember: tenant id is part of every key, built in one place; bound staleness with TTL and avoid KEYS.

How does per-tenant rate limiting with Redis work, and which algorithm would you choose? Intermediate

A counter per tenant per time window lives in Redis. Each request increments it atomically; if it exceeds the tenant's limit the service returns 429 with a retry hint. The algorithm choice is a trade-off between simplicity (fixed window) and smoothness (sliding window or token bucket).

AlgorithmHowWeakness
Fixed windowINCR a key like rl:tenant:minute, set EXPIRE on first incrementA burst at a window boundary can allow about twice the limit
Sliding window logSorted set of timestamps, trim old, countMore memory per tenant
Sliding window counterWeighted sum of current and previous window countersApproximate
Token bucketTokens refill at a rate; each request takes oneNeeds atomic read-modify-write, usually a Lua script

Atomicity: INCR alone is atomic, but "check, then set expiry" is two steps; if the process dies between them the key never expires. Use a short Lua script or SET key 0 EX n NX followed by INCR, and be aware of the gap.

Operational choices: what happens if Redis is unreachable? "Fail open" keeps the service up but removes protection; "fail closed" protects backends but causes an outage. Many teams fail open with a local in-memory fallback limit. Also decide the response: HTTP 429 plus a Retry-After header. Limits may differ per tenant tier and per endpoint (bulk endpoints cost more).

Make it yours: which algorithm you actually used, where it ran (gateway, filter, or service) and how limits were configured per tenant. If it was a library, name it.

Remember: per-tenant atomic counters in Redis; pick fixed window for simplicity, token bucket for smoothness; decide fail-open versus fail-closed on purpose.

You list Kubernetes and Kafka. What were your hands-on responsibilities, and what do you know beyond the YAML? Intermediate

Answer with what you really touched: deployment manifests or Helm values, resource requests and limits, probes, config and secrets, and on the Kafka side producers, consumers, consumer groups and offsets. Then show you understand the failure modes behind them.

Kubernetes knowledge an interviewer will test:

  • Requests versus limits: requests drive scheduling, limits cap usage. Exceeding the memory limit means the container is killed (OOMKilled, exit code 137); exceeding the CPU limit means throttling, which shows as latency, not a crash.
  • Liveness restarts a stuck container; readiness removes it from service endpoints; startup probe protects slow starters. A liveness probe that checks a dependency can restart every pod when the dependency is down.
  • Rolling update settings (maxSurge, maxUnavailable) and graceful shutdown (preStop, termination grace period).

Kafka knowledge:

  • A partition is consumed by one consumer per group, so parallelism is capped by partition count.
  • Offsets are committed after processing for at-least-once; committing before processing risks loss.
  • A rebalance pauses consumption; long processing between polls can trigger one (max.poll.interval.ms).
  • Key choice gives per-key ordering and decides skew.
Make it yours: list the exact things you owned (for example "I tuned consumer settings for X", "I wrote the readiness probe for Y"). Do not claim cluster administration if the platform team ran it.

Remember: know the failure semantics: OOMKilled versus throttling, probes, rebalances, offset commit order.

2. Salesforce: Spark, CDC, Iceberg and write paths

Walk me through how you used Spark Structured Streaming on Kafka. What are checkpoints and why do they matter? Intermediate

Structured Streaming reads a Kafka topic as an unbounded table, runs transformations in micro-batches, and writes to a sink. The checkpoint directory stores the offsets read and the state, so after a crash or restart the query resumes where it stopped instead of starting over or losing data.

Pieces to be able to explain:

  • Source: the Kafka source tracks offsets per partition; maxOffsetsPerTrigger bounds batch size so a backlog does not create one giant batch.
  • Trigger: processing-time interval, or available-now for incremental batch-like runs.
  • Checkpoint: offsets and state per batch. Do not delete or share a checkpoint path between queries; changing the query logic may make an old checkpoint incompatible.
  • Sink and guarantees: replay after failure re-runs the last batch, so end-to-end correctness depends on the sink being idempotent or transactional (see the next question).
  • State and watermark: for aggregations and joins, state grows unless a watermark lets Spark drop old keys.

Operational signals: the streaming tab in the Spark UI shows input rate versus processing rate; if processing lags input, batches queue and Kafka lag grows. Typical fixes: more partitions or executors, cheaper transformations, smaller or larger batch size, fixing skew.

Make it yours: the topic volume, trigger interval and sink you used, in your own words, and one operational problem (lag, state growth, checkpoint issue) you really dealt with.

Remember: checkpoint = offsets plus state; recovery replays the last batch, so the sink must tolerate duplicates.

You say at-least-once delivery. What does that imply for correctness, and how do you handle duplicates? Senior

At-least-once means a record is never lost but may be processed more than once, typically after a retry or restart. So every write must be idempotent: applying the same record twice gives the same final state as applying it once.

Ways to make a write idempotent:

TechniqueExample
Upsert by natural or business keyMerge on primary key; second apply overwrites with the same values
Deduplicate with an event idStore processed ids, or dropDuplicates with a watermark in streaming
Version or sequence checkApply an update only if its version is newer than the stored one (also protects against out-of-order delivery)
Transactional sinkIceberg commits are atomic per snapshot; a table format can make a batch commit all-or-nothing

Why not exactly-once? Kafka transactions plus an idempotent producer give exactly-once inside Kafka. End to end across Spark and an external store, you still need an idempotent or transactional sink. "Effectively once" (at-least-once plus idempotence) is the realistic target. Be careful with the claim "exactly-once": interviewers will ask what the sink does.

Ordering trap: duplicates and retries can reorder events for one key. If "delete then re-create" arrives reversed, the final state is wrong. Use a per-entity version or timestamp and ignore stale events.

Make it yours: what your sink was and what key made the write idempotent. If you relied on the sink's upsert, say that plainly.

Remember: at-least-once plus idempotent writes (upsert, version check, dedup key) is how duplicates become harmless.

What is CDC, and how did CDC-driven batch jobs differ from the streaming path? Intermediate

Change data capture records inserts, updates and deletes from a source system as a stream of change events. A CDC-driven batch job processes the accumulated changes since the last run, rather than rescanning the whole table, so it is cheaper and fresher than a full reload.

Two common CDC styles: log-based (read the database transaction log, low load on the source) and query-based (poll a modified-time column; simple but misses hard deletes and can miss rows if timestamps are not monotonic).

Concerns that appear in a CDC batch job:

  • High-water mark: store the last processed offset or timestamp. Advance it only after a successful write.
  • Ordering and compaction: several changes to one key in a batch should collapse to the latest; pick the last by sequence, not by arrival time.
  • Deletes: need tombstones or a delete flag; a table merge must handle them.
  • Backfill and replay: be able to reprocess a window safely (again, idempotence).
  • Schema changes: a new column upstream should not break the job.

Streaming versus CDC batch: streaming gives low latency but is always running and costs more; a batch every N minutes or hours is simpler to operate when freshness requirements are loose. Choose by the real freshness requirement, not by what is fashionable.

Make it yours: what the CDC source was, what the batch schedule was, and what "reverse-sync" meant in your system (see the Spark bottleneck question).

Remember: CDC feeds changes, not full snapshots; keep a safe high-water mark and handle deletes and ordering.

Explain the dual-mode write path: synchronous versus asynchronous bulk ingestion. When is each used? Senior

Small, interactive writes go through a synchronous path: the caller waits and gets the final result or error. Large or batch writes go through an asynchronous bulk path: the API accepts the request, returns an identifier immediately (typically HTTP 202), and a background pipeline processes it; the caller polls or is notified.

QuestionSyncAsync bulk
Latency to callerFull processing timeJust validation and enqueue
Error reportingImmediatePer-record status later (partial success is normal)
Load controlSpikes hit the store directlyQueue absorbs spikes; worker rate is tunable
ComplexityLowJob state, retries, idempotency, status API

Design details an interviewer expects: a job id and a status endpoint; per-record results rather than all-or-nothing; idempotency key so a client retry does not create a second job; limits on payload size; and the same validation and tenant checks in both paths (a classic bug is that the bulk path skips one). The P1 deserialization story below is exactly the kind of bug that appears when two paths serialize the same data differently.

Make it yours: the threshold or rule that decided which path a request took, and what store each path wrote to. If you did not design the split, describe it as "the system had" and explain what you changed.

Remember: sync for small and interactive, async with a job id for large; both paths must enforce the same rules.

What is Apache Iceberg, and why use it for a lakehouse over multi-cloud storage? Intermediate

Iceberg is an open table format: it keeps table metadata (schema, partitioning, snapshots, file lists) in metadata files next to the data files in object storage, giving a plain folder of Parquet files the behaviour of a table, with atomic commits, schema evolution, snapshots and time travel.

Why this matters: object stores such as S3 have no multi-file transactions. Iceberg commits by atomically swapping a pointer to a new metadata file, so readers always see a consistent snapshot, and concurrent writers use optimistic concurrency (a commit fails and retries if the table changed).

Features to name:

  • Schema evolution by column id, so renames do not break old files.
  • Hidden partitioning: queries filter on the real column, the table prunes partitions.
  • Row-level deletes and merge (position or equality deletes, copy-on-write or merge-on-read; check what your version used).
  • Snapshot expiry and compaction: many small files hurt read speed, so periodic rewrite_data_files and metadata cleanup are needed.

Multi-cloud: the catalog and the storage layer are pluggable, so the same table logic can sit on S3, Azure storage or GCS. The practical costs are credentials per cloud, different consistency and latency characteristics, egress charges when data crosses clouds, and a catalog that must be reachable from each place. Be honest if you used a thin abstraction that picked the storage per tenant or region rather than one table spanning clouds.

Make it yours: which catalog and engine you used, and whether one table really spanned clouds or each cloud had its own tables.

Remember: Iceberg adds table semantics (atomic commits, snapshots, evolution) to files in object storage; it needs compaction and a catalog.

What operational problems does a streaming-into-Iceberg pipeline create, and how do you handle them? Senior

The main ones are many small files from frequent micro-batch commits, commit conflicts between writers, and unbounded metadata growth. They are handled with larger trigger intervals, scheduled compaction, snapshot expiry and a clear single-writer rule per table or partition.

SymptomCauseRemedy
Slow reads, many tiny filesEach micro-batch writes at least one file per partition per taskLonger trigger, fewer shuffle partitions at write time, scheduled compaction
Commit failures on retryTwo writers (for example streaming plus compaction) update the same tableRetry logic, schedule compaction away from writes, partition-scoped compaction
Metadata and storage keep growingOld snapshots retainedExpire snapshots and remove orphan files on a schedule
Skewed partitionsHot tenant or dateBetter partition spec, or sort within files

The trade-off is freshness versus file size: a 10-second trigger gives fresh data and many small files; a 5-minute trigger gives bigger files and slower freshness. Pick from the real latency requirement.

Make it yours: which of these you actually hit. Only claim the ones you can describe from experience.

Remember: frequent commits mean small files; compact, expire snapshots, and avoid competing writers.

Consumer lag keeps growing on a Kafka topic feeding your Spark job. How do you investigate? Intermediate

Compare the input rate with the processing rate. Lag grows when processing is slower than arrival. Find out whether it is a throughput problem (needs more capacity), a stuck consumer, a skewed partition, or a downstream sink slowdown.

  1. Measure lag per partition (consumer group describe or monitoring). All partitions lagging means overall capacity; one partition lagging means skew or a poison record.
  2. Spark UI, streaming tab: input rate, process rate, batch duration. If batch duration exceeds the trigger interval, batches queue.
  3. Stage view: which stage is slow? A few tasks far slower than the rest signals data skew; long GC time signals memory pressure; long shuffle read signals network or spill.
  4. Sink check: a slow write (small files, throttled storage, commit retries) can be the real bottleneck.
  5. Rebalances or restarts: pods restarting (OOMKilled) repeatedly restart the query and replay.

Fixes by cause: add executors or partitions if the work parallelizes; salt or repartition a skewed key; bound maxOffsetsPerTrigger to keep batches stable; cheaper transformations; fix the sink. Keep an alert on lag growth rate, not only the absolute number.

Make it yours: a real lag episode, if any, with the cause you found.

Remember: lag = arrival faster than processing; localize it to all partitions, one partition, or the sink.

Tell me about the Java OOM you fixed with heap profiling. How did you find the cause? Senior

A good answer follows the real order: confirm what kind of out-of-memory it is, capture evidence (heap dump or live histogram), find the objects that dominate the heap and what keeps them reachable, fix the retention or the sizing, then verify under load.

Step 1, classify. The message tells you the memory area: Java heap space (heap full), GC overhead limit exceeded (collector thrashing), Metaspace (class metadata), unable to create native thread (thread or OS limit), or a container kill with exit code 137 and no Java error at all (the container limit was hit, which can be native memory, not heap).

Step 2, capture. Start the JVM with -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=... so the dump exists at the moment of failure. On a live process use jcmd <pid> GC.class_histogram (cheap, shows counts by class) or jcmd <pid> GC.heap_dump file (pauses the app). Turn on GC logging to see whether the heap after full GC keeps rising (a leak) or just spikes (sizing).

Step 3, analyze in Eclipse MAT or a similar tool: dominator tree and "leak suspects", then follow the path to GC roots to see what holds the objects. Common culprits: unbounded caches or maps, per-request objects stored in static or thread-local fields, large result sets loaded fully into memory, listeners never removed, big byte arrays from payload buffering.

Step 4, fix: bound the cache (size and TTL), stream or paginate instead of loading all, clear thread-locals, or fix sizing (heap versus container limit). Step 5, verify: repeat the load, compare heap after GC over time.

Make it yours: the symptom you saw (pod restarts? latency?), the exact error, which tool you used, what object type dominated, the fix, and the result. If your root cause was one of the common ones above, say which, and how you proved it.

Remember: classify the OOM, capture a dump, read the dominator tree, find what holds the objects, then fix and prove it under load.

The pod keeps restarting with exit code 137 but the heap looks fine. What now? Senior

Exit code 137 means the container was killed (SIGKILL), usually because total process memory exceeded the container limit. The JVM uses more than the heap: metaspace, thread stacks, direct buffers, code cache and native libraries all count.

Memory budget in a container: limit > heap + metaspace + thread stacks + direct/off-heap buffers + code cache + native allocators. If the heap is set to nearly the whole limit, the process is killed as soon as the other areas grow.

CheckHow
Confirm OOMKilledkubectl describe pod: last state reason OOMKilled
What the JVM sized itself toUse percentage-based flags such as -XX:MaxRAMPercentage, leave headroom (a common starting point is well below 100%, tune from measurements)
Where non-heap memory goesNative Memory Tracking: -XX:NativeMemoryTracking=summary then jcmd pid VM.native_memory
Direct buffers and threadsNetty or NIO buffers, thread count growth, large thread pools

Fixes: raise the limit, lower the heap percentage, cap thread pools and direct memory, and fix the native leak if NMT shows steady growth. Also note that lowering the heap alone without understanding the pattern can turn this into a heap OOM.

Make it yours: whether your OOM was heap or container-level. Interviewers often ask this to check you did not just "increase memory".

How do you recognize and fix data skew, and why is it so common in multi-tenant data? Senior

How does AOP-based declarative privilege enforcement work, and what are its pitfalls? Senior

Aspect-oriented programming lets you attach cross-cutting behaviour to methods without editing each method. A custom annotation such as a required-privilege marker on a service method is intercepted by an aspect that checks the caller's role and tenant before the method runs, and rejects the call if it is not allowed.

@RequiresPrivilege("PREF_WRITE")        // illustrative annotation name
public void updatePreference(...) { ... }

@Around("@annotation(requiresPrivilege)")
Object check(ProceedingJoinPoint pjp, RequiresPrivilege requiresPrivilege) throws Throwable {
    authz.assertAllowed(currentUser(), requiresPrivilege.value());   // throws 403 if not
    return pjp.proceed();
}

Why declarative: the rule is visible on the method, reviewers can grep for unprotected methods, and developers cannot forget to call a check inside the body.

Pitfalls (these are the interview questions):

  • Self-invocation: in Spring proxy-based AOP, a call from one method to another in the same class bypasses the proxy, so the aspect does not run. Put protected methods on a different bean or use AspectJ weaving.
  • Visibility and final: proxies cannot intercept private or final methods.
  • Annotation on the interface versus class: depends on proxy type and configuration.
  • Default allow: a method without the annotation is unprotected. Prefer a default-deny at the controller layer plus method annotations, or a test that fails on unannotated public service methods.
  • Data-level rules: a role check is not enough; "may edit this tenant's record" also needs the tenant check on the data.
  • Order of aspects with transaction and caching advice matters.

How do you implement idempotent processing concretely? Intermediate

Give each logical operation a stable unique key (an order id or an idempotency key), record it with its outcome atomically with the effect, and on a repeat return the stored outcome instead of redoing the work.

  1. Choose the key: a client-supplied idempotency key or an id derived from the business data.
  2. Store it in a table with a unique constraint. Insert the key first (or in the same transaction as the effect). A duplicate insert violates the constraint, which tells you this is a repeat.
  3. For a repeat, return the earlier result (or "already processed").
  4. Consider concurrent duplicates: two threads can pass an existence check at the same time; the unique constraint is what really protects you, not the check.
  5. For calls to external systems that you cannot make transactional, send their idempotency key if they support one, or check state before acting.
  6. Expire old keys after a period that exceeds the maximum retry window.
try { processedRepo.insert(messageId); } catch (DuplicateKeyException e) { return; }  // already handled
applyEffect(msg);   // ideally in the same transaction as the insert

Scenario: the billing system becomes slow and your service threads pile up, then the whole service stops answering. What happened and what do you change? Senior

A slow dependency without timeouts or isolation holds threads; when all request threads are waiting, the service cannot answer anything, even unrelated calls. The fix is timeouts, a circuit breaker, bulkheads, and moving non-urgent work to a queue.

Mechanism: by Little's law, concurrent requests = arrival rate times latency. If latency goes from 100 ms to 10 s, the same traffic needs 100 times more threads. The pool exhausts, the queue fills, health checks may fail, and pods restart, which makes it worse.

Fixes in order:

  1. Timeouts on the outbound client, short enough to fail fast.
  2. Circuit breaker so after repeated failures calls fail immediately and the dependency can recover.
  3. Bulkhead: a separate bounded pool for billing calls so the rest of the service stays responsive.
  4. Degrade gracefully: accept the order, queue the billing step, and process it when billing recovers.
  5. Backpressure: reject early with 503 or 429 instead of queuing unbounded.
  6. Alerting on dependency latency, not only errors.

Verify with a test that makes the dependency slow and checks the rest of the service stays healthy.
