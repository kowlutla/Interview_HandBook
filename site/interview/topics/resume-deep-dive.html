1. Salesforce: the platform, search APIs and REST microservices

This section covers the first three bullets of the Salesforce block: the metadata platform itself, the Elasticsearch-backed search REST APIs (tenant filters and policy-based authorization), and the OpenAPI-first microservices with generated client libraries. The designs below are generic and describe how such a platform works. Where an answer depends on what you personally did, a Make it yours box marks the slot. Fill those in with your own facts and never claim more than you did.

Your resume says you worked on a multi-tenant metadata platform. What is it, what did you build on it, and what makes multi-tenancy hard? Basic

It is a platform that stores and serves metadata about customers' data assets (tables, columns, glossary terms, lineage) so that governance and catalog products can search and govern them. I worked on Java 17 / Spring Boot microservices and Apache Spark batch jobs on it. The hard part of multi-tenancy is that many customers share the same services and stores, so every read, write, cache key and job must be scoped to one tenant.

Shape of the platform:

  • Online services (Spring Boot, REST, some gRPC) that answer user and service requests with low latency.
  • Batch jobs (Spark) that ingest and reconcile large volumes of metadata.
  • Several stores, each good at one job: a graph store for relationships, Elasticsearch for search, a lakehouse (Iceberg tables) for bulk and history, Redis for caches and locks, a relational database for configuration.
  • Events on Kafka so that a change in one place can trigger indexing and notifications elsewhere.

Why multi-tenancy is hard: a bug is not just a wrong result, it can be one customer seeing another customer's data. So the tenant id has to be present in every layer: the request context, query filters, cache and lock keys, storage paths, job parameters. One missed layer is a data-leak risk. The second hard part is the noisy neighbour: one large tenant must not starve the others, which is why batch work is chunked, throttled and idempotent.

Trade-off: a shared, multi-tenant deployment is far cheaper to run and upgrade than one stack per customer, but it moves the isolation burden from infrastructure into code and tests.

Make it yours: state in one sentence which services or jobs you owned, which you only contributed to, and how many teammates worked in the same area. Interviewers often ask "what part was yours?" right after this question.

Remember: online services plus batch jobs over several specialised stores, and the tenant id must travel through every layer.

Walk me through what happens, end to end, when a user types a word in the catalog search box. Intermediate

The browser calls a gateway, which forwards the request with the user's session to the search service. The service works out which tenant and which user type this is, turns the request into an engine query, asks the policy engine what this user may read, folds that answer into the query, runs it on Elasticsearch or the graph engine, and maps the outcome to a stable HTTP response. The service itself stores nothing and decides nothing about permissions; it makes the query safe and runs it.

Steps in order:

  1. The tenant and user come from the authenticated session, never from the request body.
  2. The service picks the search road (raw Elasticsearch query, or the higher-level catalog search request).
  3. The catalog request is parsed and planned. The planner decides whether Elasticsearch alone can answer it or the graph must be walked.
  4. The caller's read conditions are added as a filter on the plan.
  5. The engine runs the query and the response is post-processed (for example to hide attribute values the user may not see).
  6. Success returns 200 with hits and totals; every failure maps to a defined status.

Why a separate service: reads are bursty and latency sensitive while writes are batched. A slow graph query can be timed out and retried without touching any ingestion job, and the permission logic exists once, at the door, for every read.

Watch out: do not say the search service "checks permission per result". It asks once and pushes the answer into the query.
Make it yours: say which of these steps you coded or changed (query generation, the filter, the error mapping, the client).

Remember: session gives tenant and user, policy answer becomes a filter, one secured query runs, failures map to stable statuses.

How did you generate Elasticsearch queries from request criteria, and what happens when the criteria are wrong? Intermediate

A shared library turns a catalog request (query text, filters, sort, ranking, aggregations, page window) into a logical plan and then into Elasticsearch JSON, or into graph query text when relationships are needed. I treat it like a small compiler: parse, build a plan, resolve names against the data model, secure it, translate it. The key behaviours are sensible defaults, and a forgiving fallback to plain keyword search when the structured part cannot be understood.

Building blocks:

  • Default search fields with boosts: when the caller names no fields, the name field gets the highest boost, aliases and business name a medium boost, descriptions the lowest. Matching the title should rank above matching a long description.
  • Filters go in the filter context (cacheable, no scoring) while the text goes in must/should clauses (scored).
  • Name resolution: attributes and classes in the request are checked against the model registry. An unknown name is an error to report, not something to send to the engine.
  • Explain mode: return the generated query instead of running it. It is the safest way to debug "why did this match".

The forgiving fallback and its price: if a structured query string fails to parse or resolve, the engine can degrade to an unstructured keyword search and report the problem in an errors list on a 200 response. Users get results instead of a hard failure. The cost is that a typo can silently return broader results, and clients that ignore the errors list never notice.

Rejected combinations (for example mixing two incompatible aggregation styles) should fail fast with a clear message, because guessing what the caller meant is worse than refusing.

Small example: text "customer ssn" with a filter on asset type = Column becomes a bool query: a multi-match across the boosted fields in must, a term filter on type in filter, plus the permission filter added later.

Watch out: never build query JSON by string concatenation from user input. Build it from typed objects so a user cannot inject clauses.
Make it yours: which query features you added (a filter type, boosts, an aggregation) and one real mis-ranking or wrong-result case you debugged with explain.

Remember: typed plan, defaults, name resolution, then translate; fall back gently but report the problem.

How do you guarantee one tenant can never see another tenant's data in search? Senior

The tenant never comes from the request. It comes from the authenticated session, and the data layer selects the tenant's own index or applies a mandatory tenant filter on every query. So even a hand-written query body cannot name another tenant. I also test isolation explicitly, because the failure mode is a silent data leak.

Layers of defence:

  1. Identity from the session: an authentication layer binds the request to one tenant before the controller runs. Request parameters and headers that claim a tenant are ignored or cross-checked.
  2. Scoped data access: the Elasticsearch client is obtained for that tenant, so queries run against that tenant's data only (a tenant-specific index or alias, or a tenant filter that is added server side).
  3. Tenant in every key: cache keys, lock names, storage paths and job parameters all include the tenant id, so a shared Redis or bucket cannot mix tenants.
  4. Tests: create two tenants with overlapping content and assert tenant A never gets a hit owned by tenant B, including through facets, counts and exports, which are easy to forget.

Index-per-tenant versus shared index with a filter: per-tenant indices give strong isolation and easy deletion, but thousands of small tenants mean many shards and cluster-state cost. A shared index with a mandatory filter is cheaper but one missing filter leaks data. Choose by tenant count and size; mixed approaches (large tenants get their own index) are common.

Watch out: tenant isolation and permission are different layers. Tenant isolation says which organisation's data; the policy filter says which assets inside that organisation this user may read. Both apply to every query.
Make it yours: say honestly whether you wrote the tenant binding or relied on shared platform code, and describe one isolation test or review you did. Do not claim to have designed the index strategy unless you did.

Remember: tenant comes from the session, never the body; scope the data access and every key; test with two overlapping tenants.

How is policy-based authorization enforced in search? Why not check each result? Senior

Search asks the policy engine once per query for a condition, a tree of and/or rules over asset properties describing what the user may read. That condition is added to the query as a filter, so the data store returns only permitted rows. I prefer this to checking each result because paging and totals stay correct and the cost stays proportional to what the user may see.

Why not post-filter: if you fetch 20 rows and discard 8 the user cannot read, the page is short, the total count leaks the existence of hidden assets, and deep pages become unpredictable. Per-row policy calls also add one network hop per asset.

How the pushdown works: the engine evaluates the user's roles and compiled rules as far as it can without seeing a specific asset and returns what is left as a condition tree. The search layer converts that tree into filter clauses (a non-bool query is wrapped in a bool query, and the policy filter is added as a must clause).

Attribute masking: row filters cannot hide one column of a visible row, so a post-processing step removes attribute values the user may not see from the response.

Why deny looks like empty: a 403 would reveal that something exists. An empty 200 reveals nothing, at the price that a broken permission setup is invisible to the caller and must be diagnosed from the policy side.

Trade-offs:

  • The request object is rewritten on its way to the engine, so a retry must start from a fresh parse of the original body.
  • Every new endpoint must opt in. A facet or export endpoint that forgets the filter leaks.
  • Complex rules can produce large filters. Large filters cost query time, so rule shape matters.
Watch out: avoid saying "I wrote the authorization engine". The policy engine is its own service; search is a consumer that pushes its answer into the query.
Make it yours: say which part you touched (calling the engine, converting the condition, masking, tests) and name one bug or edge case you found there.

Remember: ask once for a condition, push it into the query, keep pages and totals honest, make deny look like empty.

Follow-up: what if the policy engine returns nothing, or fails? Should search fail open or closed? Senior

There are three different situations and they must not be mixed up. A normal condition becomes a filter. An explicit deny-all becomes an empty 200. An error from the policy call becomes a 5xx and the search is not run. The dangerous one is a successful but empty answer: if search reads "no conditions" as "nothing to restrict", it runs unfiltered, which is fail-open. My preference for a security boundary is to fail closed, and where the platform made a different choice, to monitor it loudly.

The decision rule: on a security boundary, "no verdict" should mean deny, and a failed call should be an error, not a guess. Availability pressure is the usual argument for failing open (an outage in the policy engine would otherwise break search), but the better answer to that is caching, timeouts and graceful degradation to an error, not to unfiltered data.

If you inherit a fail-open path:

  1. Log a distinct, searchable event every time it triggers, and alert on it.
  2. Test it explicitly, including the case where a deployment problem makes the engine answer empty for everyone.
  3. Raise it with the owners as a risk, with the evidence, rather than silently changing shared behaviour.
  4. After an incident, review what was served in that window.

Different callers of the same policy engine may reasonably treat a missing answer differently. That inconsistency is itself a finding worth reporting.

Watch out: do not claim the fail-open path "never happens". Say it is a defensive gap, how it is detected, and what you would change.
Make it yours: if you did not personally find this, say you learned it while studying the code and explain what you would do about it. That is honest and still shows judgement.

Remember: filter, deny-all, error are safe; empty means unfiltered, so alert on it and prefer fail-closed.

Follow-up: internal jobs and services call search too. How should they be treated for permissions? Intermediate

Trusted machine callers (agents and service accounts) usually skip the per-user permission filter, because a background job such as a sync or an export must see every matching asset to do its work. The decision is made on an attribute of the authenticated session, not on anything in the request body, so a caller cannot grant itself the bypass. The tenant filter still applies to them.

Why it exists: a user's permission filter describes what a person may see. A reconciliation job that compares the index with the graph needs the whole picture, otherwise it would "repair" assets it simply could not see.

The risks to name:

  • Any new machine caller is fully trusted, so granting the service user type must be a deliberate review step.
  • If a human-facing feature is built on a machine identity, it silently bypasses permissions. Always pass the end user's identity when acting on a user's behalf.
  • Machine access is a bigger blast radius when credentials leak, so they need rotation, narrow network exposure and audit logs.

Better pattern for user-triggered work: an export requested by a user should run with that user's rights, even if a job executes it. Carry the user identity in the job request and apply the same filter, rather than letting the job read as a trusted service.

Trade-off: a bypass is simple and fast. Per-job scoped permissions are safer but more work to model. Start with the bypass only for jobs that truly need global visibility.

Make it yours: mention a real machine caller you dealt with (for example an ingestion job or client library) and how you made sure it was not used for user-driven reads.

Remember: trust is decided by session attribute, tenant filter still applies, and user-triggered work should keep the user's rights.

How do you handle paging in search, and what changes when someone needs more than ten thousand results? Intermediate

Normal pages use from and size. Elasticsearch limits from + size to a result window (ten thousand by default), because deep offsets are expensive: every shard must collect and sort all rows up to that offset. For deeper walks I use a cursor, meaning the sort values of the last hit passed back as a search-after value, so the window never grows.

Behaviour to know:

  • The service can add its own guard on page size, and treats a special value as "all" for trusted internal callers. That value skips the guard, so it needs care.
  • The store enforces its own window, and the service translates the store's error into a stable 400 instead of leaking engine text.
  • A cursor is only meaningful for the same query and the same sort. If the service does not validate it, a mismatched cursor either fails with a generic search error or returns rows from a surprising position.

Example: a client exports 25,000 assets. A single request of size 25,000 is refused. Paging with size 500 works until the offset reaches the window and the store refuses it. The fix is to keep the last hit's sort values and send them as the cursor with from = 0.

Cursor requirements: a stable, unique sort (add a tiebreaker such as the asset id), otherwise ties can duplicate or skip rows. For consistent views over changing data, a point-in-time snapshot can be used so that updates during the walk do not shuffle pages.

Trade-off: offsets support jumping to page 7; cursors only move forward. UIs usually need offsets for a few pages, exports need cursors.

Watch out: raising the engine's window setting is a trap. It moves the cost to every shard and can destabilise the cluster.
Make it yours: describe a client you saw hit the window and what you recommended. Do not quote latency numbers you did not measure.

Remember: offsets for shallow pages, cursor with a stable unique sort for deep walks, never raise the window as a fix.

How do retries and timeouts work in the search service, and which failures should never be retried? Senior

I retry only failures that are likely to be transient (a closed connection, a node restart, a 429 or 502/503/504 from the cluster) with exponential backoff and a small attempt limit. I never retry a timeout or a wrong query, because the same query will be slow or wrong again and retrying only adds load. A timeout is a final answer: the caller gets a 504.

The classification order matters:

  1. Is a timeout anywhere in the cause chain? Then do not retry, even if another cause looks transient. (A memory-limit failure converted into a timeout is a good example: the original looks transient, the conversion makes it final.)
  2. Is any cause a known transient failure? Then retry with backoff.
  3. Otherwise rethrow immediately, so a bad attribute becomes a 400 without three wasted attempts.

Default shape: three attempts with waits of about half a second and then one second. Settings live in configuration so they can be tuned without a release. Each attempt re-parses the request body, because the permission step mutates the request object.

Timeouts: a caller-supplied timeout is honoured, otherwise a configured default applies. A value of zero commonly means "no timeout", which is dangerous for interactive callers because a runaway graph traversal can hold a transaction for as long as it likes.

Pitfalls:

  • Retries are uneven across roads: if only one path is wrapped, the other fails on a one-off blip. Know which paths have a retry.
  • Matching driver exceptions by class name avoids a compile-time dependency but silently disables retry if a driver renames a class.
  • Retry storms: when the cluster is struggling, three attempts from every client triple the load. Backoff, a small cap, and not retrying timeouts are the protection.
Make it yours: if you did not write the retry code, say how you verified its behaviour (tests, logs) or what you would add (a circuit breaker, jitter).

Remember: classify first (timeout, transient, other), back off, cap attempts, re-parse each time, never retry a timeout.

What does a caller get back when search fails, and why do you want stable error responses? Intermediate

Every outcome maps to a defined HTTP status and a short code, so callers can write logic against it. Bad input is a 400, a query timeout is a 504, a service that is not ready is a 503, an unexpected error is a 500, and a user who is allowed nothing gets an empty 200. Error bodies carry no stack traces or internal messages.

SituationStatusCaller's next step
Missing or unsupported language or invalid body400Fix the request
Unknown attribute, window too large, store rejected the query400 with a codeSimplify or page differently
Query exceeded the time limit504Narrow the query or raise the limit
Dependency down or model not ready503Safe to repeat later
Feature switched off (for example natural-language search)403Not available for this tenant
Unexpected failure500Use the trace id to find it in logs

Why stability matters: clients and other services branch on these. If a slow query sometimes returns 500 and sometimes 504, callers cannot decide between "retry" and "give up". Mapping happens in one central exception handler, not scattered try/catch blocks.

Imperfect corners worth knowing:

  • Some server-side failures from the store can surface as a 400, so a 400 does not always mean the caller was wrong.
  • An unsupported-operation exception that is not an argument error can fall through to a 500 when a 400 would be more correct.
  • A forgiving fallback returns 200 with an errors list, so clients must read that list.

Security angle: no message, stack trace or exception name in error pages. Details go to logs, correlated by a trace id that also flows across REST, gRPC, Kafka and Spark.

Make it yours: name one error path you fixed or one status you changed, and how you checked existing clients would not break.

Remember: one central handler, stable statuses, no internals in bodies, and a trace id to find the details.

What does "OpenAPI-first" mean in practice, and why do it? Basic

The API contract, an OpenAPI specification, is written and reviewed before the code, and server interfaces, models and client libraries are generated from it. The contract is the source of truth, so documentation, consumers and tests cannot drift from what the service really does.

Typical workflow:

  1. Edit the spec: paths, request and response schemas, status codes, error model, auth.
  2. Review it in a pull request. Teams who consume the API comment here, which is cheaper than after the code exists.
  3. Generate interfaces and models (OpenAPI Generator plugin in the build) and implement the generated interface in a Spring controller.
  4. Run checks in CI: lint the spec, compare with the previous version to detect breaking changes, validate that responses match the schema.

Why it helps: parallel work (a client team builds against the spec), consistent error shapes across services, and generated clients that stay in step with servers.

What it costs: generated code can be awkward, the spec needs maintenance, and people sometimes edit generated code by hand, which breaks regeneration.

Code-first as the alternative: annotations generate the spec. It is quicker for a small internal service with one consumer. Contract-first wins when several teams consume the API or when generated clients are shipped.

Make it yours: say which generator and build tool you used, where the spec lived (same repo or separate), and which CI check enforced it. If you mostly edited existing specs, say that and describe what you reviewed.

Remember: spec first, reviewed as a contract; code and clients derived from it.

How do you keep API changes backward compatible, and when does a change need a new version? Intermediate

A change needs a new version only if it can break an existing consumer. Additive changes (a new optional field, a new endpoint) stay in the current version. Breaking changes go into a new versioned contract, and the old version stays alive until consumers migrate.

ChangeBreaking?
Add an optional response fieldNo, if clients ignore unknown fields
Add an optional request field with a safe defaultNo
Remove or rename a field, change type or meaningYes
Make an optional request field requiredYes
Tighten validation or change an error statusUsually yes
Change default ordering or pagingOften yes, clients depend on it silently

Implementation pattern: a version in the path, separate DTOs per version with a shared service layer, and a mapping layer to the internal model. That keeps the old version frozen while the new one evolves, and business rules live in one place.

Hard parts:

  • Tests per version, because a shared service change can break the old version silently.
  • Deprecation policy: announce, add a deprecation header, watch traffic per version in logs, remove only when traffic is near zero.
  • Bug fixes that change behaviour may themselves be breaking.

Trade-off: every version is another contract to test and document, but a "never break" single version forces ugly hacks. Additive evolution plus a new version only for real breaks is the middle path.

Watch out: "we just added a field" can still break strict clients. Say that your clients must tolerate unknown fields and that this is stated in the contract.
Make it yours: give one real change you classified as additive or breaking, how consumers were told, and how you knew an old contract was safe to leave alone or retire.

Remember: only breaking changes earn a new version; freeze the old contract, share the service layer, track traffic per version.

You generated client libraries for service-to-service calls. What do they give you and what goes wrong with shared client libraries? Intermediate

A generated client wraps a service's API: it builds requests, adds authentication and tracing headers, serialises models and maps errors, so every consuming team does not hand-write HTTP calls. Because it is generated from the same spec as the server, a contract change shows up as a compile error in consumers instead of a runtime surprise. The cost is a shared artifact that every consumer must upgrade.

What a good client does:

  • Carries the tenant, trace id and caller identity on every call.
  • Applies sensible timeouts and limited retries for safe (idempotent) calls only.
  • Maps error responses to typed exceptions.

What goes wrong:

  1. Version skew: consumer A uses client 1.2, consumer B uses 1.5, the server moved on. Keep clients backward compatible and deprecate slowly.
  2. Transitive dependency clashes: the client drags in a JSON or HTTP library version that conflicts with the consumer's. Keep the dependency footprint small.
  3. Hidden behaviour: a retry or cache inside the client surprises a consumer. Document it and make it configurable.
  4. Release coupling: a client bump forces many services to redeploy. Publish clients with the server release, and avoid breaking changes inside a major version.
  5. Security fixes: a vulnerable library inside the client must be fixed once and rolled to all consumers, which is a reason for RDCV work to include client artifacts.

Alternative: thin hand-written calls are flexible but drift. Generated clients win when many services call the same API.

Make it yours: say how clients were built and published in your setup, one version-skew or dependency problem you hit, and what you changed to avoid it.

Remember: generated clients turn contract drift into compile errors; manage version skew, dependency footprint and hidden behaviour.

Scenario: a customer says the catalog search suddenly shows no assets, but the data is there. What do you do? Senior

I would first suspect permissions, not the index. An empty 200 is exactly how deny-all looks, so I check what the policy engine returned for that user before I touch Elasticsearch. Then I compare with another user in the same tenant, and only then look at the index and recent deployments.

Situation: one tenant reports an empty catalog for some or all users since this morning. There are no errors in the UI and search returns 200.

Check first:

  1. Is it every user or one? One user points to roles; everyone points to the policy side or a deployment.
  2. Use the trace id from one failing request to find the logs: does the log show a deny-all or empty-result event from the permission step?
  3. Compare a machine caller (which skips the user filter) and a human user on the same query. If the machine caller sees data, the data and index are fine.
  4. Check recent changes: a policy publish, a role change, a deploy of the policy engine or search service.
  5. Only if the machine caller also sees nothing: check index health, document counts for the tenant and the ingestion pipeline.

Fix: restore the role or policy, republish compiled policies, or roll back the bad change. Confirm with the same query for the affected user.

Prevent: a metric or alert on the rate of deny-all results per tenant, a canary query after policy publishes, and a runbook line "empty results: check policy first". Also review the opposite failure (an empty policy answer that runs unfiltered) on the same dashboard.

Make it yours: if you have handled a real "search returns nothing" report, tell it in this order: symptom, first hypothesis, evidence, fix. Leave out ticket numbers and customer names.

Remember: empty 200 usually means deny, so check the policy answer for that user before the index.

Scenario: an integration pages through all assets and starts failing near the ten-thousandth result, and some graph searches return 504. How do you diagnose and fix it? Senior

These are two separate limits, so I treat them separately. The paging failure is the store's result window, fixed by switching to a cursor. The 504s are graph queries hitting a time limit, fixed by narrowing or restructuring the query, not by retrying.

Situation: a nightly job reads the whole catalog with from and size. It fails once the offset approaches the window limit. Separately, interactive lineage-style queries sometimes return 504 after a long wait.

Check first:

  1. Read the exact error: a 400 with the window-too-large code confirms the paging limit. A 504 with the graph timeout code confirms a query time limit.
  2. For the job, find the offset where it fails and the page size it uses.
  3. For the 504s, find the query shape (depth of traversal, filters) and the timeout in force (caller header or configured default). Check whether any caller sends zero, meaning no timeout.
  4. Check whether the 504 retried: timeouts should not be retried, so load should not triple.

Fix:

  • Job: send the last hit's sort values as the cursor with from = 0, with a unique tiebreaker in the sort. Do not raise the engine window.
  • Graph: add selective filters, limit depth, or split the query; raise the caller timeout only if the work is legitimately long. Avoid "no timeout".

Prevent: document the window and the cursor in the API contract, add a client-side helper that pages by cursor, alert on rising timeout rates, and test the long-walk path with a large synthetic tenant.

Make it yours: say whether you hit this yourself or are reasoning from the design. Both are fine if you say which.

Remember: window limit means use a cursor; timeout means fix the query shape, never retry it.

Your resume says event-driven change processing on Kafka. Walk me through what that system does end to end. Basic

When catalog data changes, the write path publishes a small change event to Kafka. A consumer service matches each event against registered subscriptions, collapses a burst of events into one pending trigger, and a periodic drain later delivers that trigger, for example as a webhook to a downstream service. The goal is that downstream systems stay current without polling and without being flooded.

Why events at all? A downstream consumer such as a re-index job or a lineage refresher needs to know "something changed for this tenant". Polling the catalog every few seconds is wasteful and slow. Pushing one call per change is worse, because one bulk edit can create thousands of changes in a minute. So the design is: publish cheap events, then reduce them.

The stages in order:

  1. The write path publishes a change event after a successful write. The tenant id travels in a message header so every later step is tenant-scoped.
  2. A consumer group reads the topic. Each message is handled by one pod of the group.
  3. An in-memory matcher, built from the subscription table, decides which subscriptions the event matches for that tenant.
  4. For each match, a scheduler records a pending trigger with a deadline (the debounce window). Repeated events find the trigger already there and do nothing.
  5. A drain pass finds due triggers, calls the receiver, and either deletes the row or reschedules it with backoff.

What the receiver gets: a nudge, not a list of changes. It reads current state when called, so nothing is lost by merging events.

Make it yours: say which part you worked on (consumer, scheduler, drain, or a producer side) and one concrete change you made. Do not claim the whole pipeline if you owned one stage.

What delivery guarantee does your Kafka consumer give, and how do offsets, duplicates and ordering behave? Intermediate

The consumer is at-least-once: it commits the offset only after the handler returns, so a crash or an exception before that causes redelivery. That means duplicates are normal and the handler must be idempotent. There is no ordering logic, so the design makes outcomes independent of arrival order.

How offsets work. Kafka keeps messages in an ordered log per partition. A consumer group tracks a bookmark (the offset) per partition. Reading a message does not remove it. The consumer acknowledges by committing the bookmark. If it dies before committing, the next owner of that partition starts from the old bookmark and sees the same message again.

Where duplicates come from: a pod killed after handling but before committing; a rebalance that moves a partition mid-batch; the handler throwing and the message being retried; a producer retrying a send. You cannot remove all of these, so you absorb them.

How the handler absorbs them. Each layer of the scheduler makes a repeat a no-op: a cache claim says "already pending", a database read finds the existing row, and an insert-or-ignore guarantees exactly one row even under a race. Applying the same event twice leaves the same state as applying it once, which is the definition of idempotence.

Ordering. Two events for the same subscription and tenant can arrive in either order. The first handled one sets the deadline and the second finds the row, so the result is identical. If ordering did matter you would key messages by entity so they land on one partition, and add a version check to ignore stale events.

Failure behaviour: a null body is dropped and acknowledged. An unexpected exception is wrapped and rethrown so there is no commit and a redelivery. Whether the client library retries immediately, delays, or ever dead-letters is a library behaviour you should state as something to confirm, not as fact.

Watch out: do not say "exactly-once". Say at-least-once plus idempotent handling, and be ready to explain what makes it idempotent.

Remember: commit after handling means redelivery on failure, so safety comes from idempotent layers, not from the broker.

Explain coalescing and debouncing. How does your consumer turn a burst of events into one trigger? Intermediate

Coalescing merges many events into one, and debouncing waits for a quiet moment before acting. For each subscription and tenant, the first event of a window creates one pending trigger with a deadline, and every later event in that window is absorbed. Three layers do the work: a Redis claim, a MySQL read, and an insert-or-ignore.

Why it is needed. One bulk edit can emit thousands of events for a tenant within a minute. A webhook receiver wants one call after things settle, then it reads current state.

Worked example. A subscription has a 300-second window. Event A arrives: the claim succeeds with a time-to-live a little longer than the window, nothing exists in the database, so A inserts a row with a deadline 300 seconds ahead. Event B finds the claim and stops, touching only Redis. At t=300 the drain delivers once and removes the row and the claim. Event D ten seconds later starts a new window.

Why three layers. Redis answers a duplicate in well under a millisecond and keeps load off the database, but it is a cache and can lose keys. The row is durable and is what the drain reads. The insert-or-ignore is the final arbiter if two pods pass the probe at the same instant.

Remember: claim to absorb volume, row as truth, insert-or-ignore to settle races.

What if Redis is down, or the claim is taken but the database write fails? How do you avoid losing a trigger? Senior

The database is the source of truth and Redis is only an accelerator. If Redis fails, the scheduler fails open: it skips the shortcut and goes to the database, which still yields one row. If the database write fails after a claim, the scheduler releases the claim and rethrows, so the redelivered message can try again instead of finding a stale claim.

Case 1, Redis unavailable. The claim call returns "no answer" rather than yes or no. The code treats that as "carry on": it increments a counter and runs the probe and the upsert. The cost is extra database reads. Correctness is unchanged because the primary key allows one row per subscription and tenant.

Case 2, claim succeeded but the write failed. This is the dangerous one. The order is claim first, row second. Suppose MySQL has a brief failover. The claim exists, no row exists, and the message is not acknowledged, so Kafka redelivers it. On redelivery the claim is still there, the scheduler thinks "already pending", skips the write, and the trigger is silently lost. The defence: on any exception in the probe or upsert, delete the claim, then rethrow. Now the redelivered event claims again and gets another chance.

Remaining gaps, stated honestly. If the process is killed hard between claim and write, no cleanup runs. A claim can then hide a missing row for at most its time-to-live. If the release call itself fails after a database failure, the same gap appears. The claim's time-to-live bounds the damage, and a new event after expiry creates the row.

Principle. A claim should only live while a row exists or is being written. A hint that can outlive the truth is the classic way a debounce loses work.

Watch out: do not claim "no loss ever". Say the design bounds loss to a narrow crash window and explain the bound.

Remember: fail open on the cache, release the claim on write failure, and let the TTL bound what is left.

Why a fixed window where the first event sets the deadline, rather than a sliding window that restarts on each event? Intermediate

A sliding (trailing-edge) window can starve: if events never pause, nothing is ever delivered. A fixed window bounds latency. The first event sets the deadline and later events do not move it, so the receiver is called at most one window plus one drain interval after the first change.

The two designs side by side.

DesignBehaviourRisk
Fixed, first event winsDeadline = first event + window. Later events absorbed.A late event in the window gets no fresh full window.
Sliding, last event winsEvery event pushes the deadline out.A steady stream delays delivery forever.

Why the fixed design is safe here. The receiver is told to look, not given the changes. When it is called it reads the catalog and sees the effect of every event, including those that arrived late in the window. A late event costs nothing because the state it changed is visible at read time.

Implementation detail that preserves the rule. The upsert is insert-or-ignore: on conflict it assigns each key column to itself, a true no-op. A losing writer neither errors nor overwrites the winner's deadline, so "first event wins" holds even under a race. A plain update on conflict would move the deadline and quietly turn the design into a sliding window.

Retries use the same idea. When a delivery fails, the row stays with a later deadline and the claim is refreshed, so new events coalesce into the pending retry instead of creating a second row.

When you would choose sliding. If the receiver needs to act only after the source goes quiet (for example "run once the import finishes") and bounded delay is not required, trailing-edge debounce fits. You could also cap the total wait.

How do you batch and split a very large publish so it runs fast but does not deadlock the graph database? Senior

A planner cuts one large request into batches of roughly a hundred items and draws a dependency arrow only between batches that could conflict. An executor runs the batches on a pool of ten threads and releases a batch's successors as soon as its predecessors finish. Independent batches run in parallel, conflicting ones run in order, so the graph store never sees two writers on the same vertex.

The problem. One request may create thousands of assets, delete others, and connect them. As one unit it holds a transaction open for ages and one bad item sinks everything. As a hundred parallel slices, two slices may touch the same vertex and the graph database answers with a deadlock, where each transaction waits for the other and one is killed.

How the plan is built. Small requests (under about a thousand items) take a short route: object work, then relationship batches, then one stakeholder batch. Larger ones get phases: delete relationships grouped by shared vertex, delete objects, provisional-id groups, ordinary objects, hierarchy edges, other relationships, and stakeholder relationships. Rules that matter: groups that must be written together are never split, even if oversized; stakeholder edges are grouped by source and never split because they are recomputed per source asset.

Dependency edges. Arrows point only from earlier batches to later ones, so no cycle can form. A batch depends on another only when footprints (the vertices it touches) overlap, or when a child created earlier is the parent later. There is no global barrier, so a slow batch holds up only what depends on it.

Execution. The plan is first written to a durable manifest so a retry can rebuild unfinished work. Each batch ends as successful, retryable-failed (data landed but a confirmation is owed) or non-retryable-failed. Successors are released in every case.

Remember: conflict-driven arrows, no barrier, whole groups never split, manifest first.

How do you stop a burst of changes from overwhelming a slow consumer such as webhooks or indexing? Is that backpressure? Senior

Backpressure here is implicit, not a dedicated mechanism. It comes from bounded concurrency: a fixed thread pool, serial draining in the bulk-ingestion job, page and chunk sizes in the drain, and Kafka's pull model. I would describe it as "bounded work per unit of time that protects downstream", and not claim a reactive-streams style signal.

What backpressure means. When a consumer is slower than a producer, something must slow the producer or buffer. Without it, queues grow, memory fills and downstream services fall over.

Where limits really exist:

  • Pull-based Kafka. The consumer fetches at its own pace. If it is slow, lag grows in the broker, not in the app's memory. That is natural backpressure, paid for in latency.
  • Fixed thread pools. The batch executor runs a bounded number of batches at once, so the search index and graph store see limited parallel writes.
  • Serial drain. The bulk-ingestion job reads messages into a queue and works through them strictly one at a time. This protects the lake and its merge lock but means throughput is capped.
  • Drain paging. Due triggers are read in pages, split into chunks, handled by a bounded pool, and each delivery has a timeout.
  • Coalescing itself. Collapsing thousands of events into one call is the strongest protection for webhook receivers.

What is not there. No explicit rate limiter on webhook delivery, no adaptive slowdown based on receiver health, and no dedicated pause of Kafka consumption when downstream is overloaded. Failures are handled by retry with exponential backoff, not by throttling.

Watch out: if asked "show me the backpressure code", you should point to the pools, the serial loop and the paging, and say plainly that it is bounded concurrency. Overclaiming here is easy to catch.

Consumer lag is growing on the change topic. How do you investigate? Intermediate

Lag means the consumer group is behind the end of the log. I first check whether it is a throughput problem (handlers too slow), a stall (stuck or rebalancing), or a surge (producer burst), then look at the dependency each handler calls, usually Redis and MySQL. I fix the cause rather than just adding pods.

Step 1, shape of the lag. Per partition: is lag growing on all partitions or only one? One partition suggests a hot key, a stuck consumer or a poisoned message. All of them suggest slow handlers or a surge.

Step 2, consumer health. Are pods running and in the group? Frequent rebalances (visible in logs) pause consumption and cause redeliveries. Check poll interval settings: a handler slower than the max poll interval gets the member kicked out, which makes things worse.

Step 3, handler time. The handler warns when message age exceeds a threshold (here around a minute, rate-limited in the log). In Kibana, search for slow-handler entries and outcome counters: matched, no-match, coalesced, scheduled, failed. A sudden rise in failures means redelivery loops that eat throughput.

Step 4, dependencies. Redis latency or timeouts push every event to the database path (fail open), which is slower. A slow database makes each handler slow. Check dashboards for both.

Step 5, fix. Options in order: fix the slow dependency; remove an expensive step from the handler; scale consumers up to the partition count (more consumers than partitions sit idle); increase partitions (a planning change, because it affects ordering and rebalances).

Step 6, after. Because the handler is idempotent and coalescing absorbs bursts, catching up does not create extra webhook calls. That is the benefit of the design.

How do you handle poison messages, retries and dead-lettering, and what happens when a webhook receiver keeps failing? Senior

A poison message is one that fails every time. Rethrowing it from a commit-after-handling consumer would block that partition forever, so each path needs a policy. Here, bad input is dropped, transient failure is retried by redelivery, and webhook delivery failures follow a bounded exponential backoff. A dead-letter record for permanently failed triggers is the known gap.

Message handling. Null or malformed input is logged and acknowledged, so it cannot wedge the partition. An exception from a dependency (database down) is rethrown for redelivery. How often Kafka retries, and whether it ever parks the message, depends on the shared client library, so state that you would confirm it.

Spark path contrast. A micro-batch processor catches everything, logs, and lets Spark commit. A poison record cannot stall the stream, but a failure loses that tenant's triggers for the batch with no replay. That trade-off is deliberate and worth naming.

Scenario: a downstream team says a webhook for one tenant was never called after a large bulk edit. How do you find out why? Senior

Situation. Tenant X edited many tables. Receiver Y expected a call within the window and got none.

Your resume says Spark ingestion and bulk jobs. Walk me through the stages from an uploaded file to data in the lake. Basic

What is delta computation, and why not simply write every incoming row to the lake? Intermediate

Delta computation compares the incoming batch with what the Iceberg table already holds and keeps only rows that must change, each tagged INSERT, UPDATE or DELETE. Without it every scan would rewrite the world, downstream consumers would be told everything changed, and two runs of the same batch could disagree about the final state.

Why most rows are noise. A scanner crawls a database daily. A table unchanged since yesterday still appears in today's scan. If 10 percent of rows changed, writing 100 percent wastes storage and compute and pollutes the change history.

How the comparison works. Rows are matched on an identity and then compared by a hash, a fingerprint over the data columns:

  • Objects match on the source system's external id within an origin (for example a table's qualified name).
  • Relationships match on the pair of their two ends, after provisional and external ids are resolved to internal identities.
  • Associations match on the pair plus a partition key.
  • Extension rows hang off a master row and are kept only if the master exists.

The outcomes: no match in the lake means INSERT; match with a different hash means UPDATE; present in the lake but absent from the incoming set (in a full-replace scan) means DELETE; same hash means drop, nothing to do.

Small worked example. Lake holds t1 (hash h1) and t2 (h2). The scan brings t1 (h1), t2 (h9) and t3. Delta: t2 UPDATE, t3 INSERT, and t1 disappears because nothing changed. Only two rows go to the merge.

Cost control. Existing rows are read only for the partitions present in the batch, so a scan of one source reads a slice of the table, not all of it.

Safety. The stage only reads the lake and writes a checkpoint. If it fails, nothing was written and the batch can simply be rerun.

Pitfall. Deletes depend on knowing the scan is complete. A partial scan treated as full would delete good rows, so the producer's operation tag matters.

Remember: match on identity, compare by hash, keep only changes, tag one operation per row.

Why a lakehouse on Iceberg? What does it give you over plain Parquet files or a relational database? Basic

Iceberg is a table format over files in cloud storage. Data files are immutable and a chain of snapshots says which files make up the table at each moment. That gives atomic commits, safe concurrent readers, schema evolution, time travel and efficient partition pruning, with cheap object storage underneath.

What plain Parquet lacks. A folder of Parquet files has no transaction. A job that dies halfway leaves readers seeing a mix of old and new files. There is no easy update or delete. Iceberg adds a metadata layer so that a commit is a single pointer move to a new snapshot, and readers see either the before state or the after state, never half of each.

What it gives this platform:

  • Atomic MERGE. Inserts, updates and deletes in one commit.
  • Snapshot labels. Each snapshot has a summary where the job writes which batch produced it. This powers idempotent reruns.
  • Partitioning by source. Scans of one system touch one partition.
  • Schema evolution. A new column does not need a rewrite.
  • Open format. Spark, and other engines, read the same tables, and storage is cheap on every cloud.

What it costs. Every commit adds files, manifests and a snapshot, so small files and long histories build up. That is why a maintenance job compacts files and expires old snapshots. Concurrent writers can conflict at commit, which is why the merge takes a lock and also retries.

Versus a relational database. A database is better for low-latency point reads and transactions on small data. The lake holds the large, historical, analytical copy, where scans over millions of rows dominate. Serving low-latency search stays in Elasticsearch.

Remember: immutable files plus snapshots equal atomic commits, time travel and cheap storage, at the price of maintenance.

How does the atomic merge into Iceberg work? Cover the lock, the generated MERGE, the idempotence key and commit conflicts. Senior

The merge takes a lock keyed by table type and partition, builds a SQL MERGE with only the clauses the delta needs, and commits inside a block that stamps the new snapshot with an idempotence key naming the batch. A retry policy handles commit conflicts that still occur. The lock keeps conflicts rare, the retry makes them safe, and the key makes a repeated merge detectable.

Lock. Keys are built from the request type and the batch's partitions, so batches for different sources do not block each other. The lock is released in a finally block, and a lock that was never released expires on its own.

Generated MERGE. Before merging, the delta is sorted within each Spark partition by the first partition key so each output file holds one partition's rows. Then rows are counted by operation. No UPDATE rows means no UPDATE clause, no INSERT rows means no INSERT clause, and an all-no-op delta skips the commit. The delta is registered as a temporary view and the statement runs through Spark SQL. Each extra clause costs planning and file rewrites, so a pure-insert batch should not pay for an update. A brand-new partition is a plain append.

Idempotence key. The commit runs inside a block that writes a property into the snapshot summary, for example object-and-batch-id. It is a label: "this snapshot was produced by batch X".

Conflicts. Iceberg commits optimistically: if another writer committed since the table was read, the commit fails and is retried. Locks can expire and some writers do not take them, so retry is needed even with a lock.

Watch out: the merge function reports success as a boolean, so callers must check it. Say how failures reach the task.
Make it yours: name the clause, key or retry rule you changed or debugged.

Remember: lock to reduce conflicts, retry to survive them, snapshot label to make reruns detectable.

What happens if the job dies right after the Iceberg commit but before it records success? How does a rerun avoid merging twice? Senior

On restart the job reads the table's snapshot history and looks for a snapshot whose summary carries its own idempotence key. If found, the work already landed and the merge is skipped. If not, the commit never happened and the delta is safely applied. The label in the snapshot is the source of truth, not a separate status file.

The hard window. Writing the data, then writing "done", are two actions, and a crash can fall between them. Any design that trusts only the "done" marker will either redo work (a duplicate merge) or, worse, skip work. Putting the label inside the Iceberg commit itself closes the window, because the commit and the label are one atomic action.

Recovery logic.

  1. Rerun starts, reads the progress marker and sees the merge step was started.
  2. It asks Iceberg for recent snapshots and checks summaries for the batch's key.
  3. Key found: mark the step complete, move on. Key not found: run the merge normally.

Is a double merge dangerous anyway? Often not. An UPDATE applied twice gives the same row, and an INSERT guarded by a matching key becomes an update. But deletes combined with later changes, or appends into a new partition, can duplicate. The key removes the need to argue about each case.

Lock expiry. If the killed job still holds the lock, the lock expires by itself, so the rerun is not blocked forever. The wait can be long, which is an operational cost to mention.

What the key cannot do. It does not repair a different bug, such as a batch that was wrong to begin with. It also depends on snapshots not having been expired between the crash and the rerun, so snapshot retention must be longer than the rerun delay.

Remember: label the commit itself, check history on restart, and keep snapshot retention longer than rerun delay.

Give a concrete example of an idempotent rerun, and explain what a stale marker is and how you handle it. Senior

Idempotence means doing a step again has the same final effect as doing it once. In ingestion, a rerun reuses the saved delta and merges it, or detects that the merge already landed, so the lake ends in the same state either way. A stale marker is a marker that claims work is done when its data is missing or out of date, and it is the main way this design can mislead you.

Example. Batch B1 brings t2 UPDATE and t3 INSERT.

  1. Run 1: preprocessing and delta succeed and are checkpointed. The merge commits, stamped B1. The pod is evicted before the final marker is written.
  2. Run 2: preprocessing is skipped (marker present), delta is loaded from its checkpoint, the merge step finds a snapshot labelled B1 and skips, then propagation runs.
  3. Final state: t2 updated once, t3 inserted once, no duplicate rows. A rerun of Run 2 changes nothing again.

Why it matters that the delta is saved. If the delta were recomputed after the merge landed, the lake would already contain the changes, so the recomputed delta would be empty or different. Reusing the saved delta keeps the run self-consistent.

Stale marker cases:

  • A marker file exists but the data directory was cleaned, so a stage loads nothing.
  • A marker from an earlier attempt at the same batch, whose input changed. The rerun skips work that should be redone.
  • A count file never written, so a reindex retry cannot tell what to redo.

How to handle them. Keep the marker and its data under the same path and delete them together; key everything by batch id; on doubt, wipe the batch's checkpoint directory and rerun from the start, which is safe because the lake merge is idempotent. Operators need to know which markers mean what before deleting by hand.

Watch out: "just rerun it" is only safe because every write step is idempotent. Say that explicitly.

Iceberg tables get slower over time. What causes it and how is it kept healthy? Intermediate

Every commit adds data files, manifest files and a snapshot, and files are never edited in place. Over months this leaves tiny files, long snapshot histories and half-written files from aborted commits. A scheduled maintenance job compacts data and manifests, expires old snapshots and removes orphan files, once per tenant.

Why small files hurt. A query plans over manifests and opens each data file. Ten thousand tiny files means ten thousand opens, each with a fixed cost. The metadata tree also grows and planning gets slow. Storage bills rise because old snapshots keep old files alive.

The steps, in order:

  1. Compact data. Rewrite many small files into files near a target size (hundreds of megabytes), optionally sorted. Old files remain referenced by older snapshots.
  2. Compact metadata. Rewrite manifests so the planner reads few large lists.
  3. Expire snapshots. Remove snapshots older than a threshold (about a day by default), keeping a minimum number. Files only the expired snapshots referenced are deleted.
  4. Remove orphan files. Delete files that no snapshot references, for example from failed commits.

Only the last two steps delete files. A table with few snapshots is skipped entirely, because compaction has its own cost.

Failure behaviour. The job tries to make progress even if one step fails, and reports a partial-completed status rather than failed. It also skips non-active tenants and reports success, so a green run does not prove anything was maintained.

Interaction with reruns. Snapshot expiry removes the labelled snapshots that idempotence checks rely on. Retention must be longer than the longest rerun window.

Write-side help. Sorting delta rows by partition key before the merge keeps files tight, so fewer small files appear in the first place.

Why are the ingestion and change-processing jobs batch or micro-batch, not continuous streaming? Intermediate

The work is bulk by nature: a scan arrives as a complete set, the delta needs a comparison against existing state, and the merge is one atomic commit. Batches give simpler failure handling, cheaper cost and natural rerun units. Where freshness needs are loose, a trigger every few minutes beats an always-hot streaming pipeline.

Reasons for batch in ingestion.

  • Delta needs a full picture. Detecting deletes means comparing a complete incoming set with the table. A record-at-a-time stream cannot know what is missing.
  • Atomic commits. One merge per batch is far cheaper than a commit per record, and it avoids a flood of small files.
  • Rerun unit. A batch id is a natural unit for checkpoints and idempotence keys.
  • Cost. Pods run when there is work instead of idling.

The micro-batch used for change processing. A Spark streaming driver reads the topic in five-minute micro-batches, groups by tenant so each tenant is handled in one partition, and launches at most one job per subscriber per batch. It is a coarse cousin of the per-record debounce: it collapses thousands of events to one launch. The checkpoint on object storage lets a restarted driver continue instead of re-reading history.

Trade-offs. Latency is a few minutes, not seconds. The micro-batch processor catches all errors, so a poison record cannot stall the stream, but a failure loses that tenant's triggers for that batch with no replay. The per-record consumer is chosen where lower latency and retry by redelivery are needed.

How to decide. Ask for the real freshness requirement. If minutes are fine, batch. If a user is waiting, use the per-record path.

Why not use distributed transactions (two-phase commit) across the stores? What does CAP say here? Intermediate

Because the stores do not support a shared transaction protocol. A search engine and an Iceberg catalog have no prepare/commit interface to join a coordinator. For a metadata platform, a user editing one asset should not be blocked because the lakehouse is slow, so we pick availability and make the gap short, visible and repairable.

What eventual consistency means in practice here: the search index is the system the user touches first, the lakehouse catches up through a change-event stream, and a window exists where the two differ. The design goal is to make that window bounded and to guarantee that nothing is silently lost.

Explain the write-ahead log you used. What exactly is written, and in what order? Senior

Before content changes, the writer synchronously records an intent event with state NOT_COMMITTED in an append-only change-event stream. Then it updates the search index content. Only after that succeeds does a COMMITTED message go out, and a consumer uses it to update the next store and assign an ordered sequence number. If anything fails in between, the intent record shows what was attempted.

Why two phases: NOT_COMMITTED proves a write was attempted; COMMITTED proves the content write succeeded. A reader of the log can tell three situations apart: never started, started but not finished, and finished.

Why synchronous intent: if the intent were queued asynchronously, a crash could lose it and leave a content change with no trace. Writing it first, and failing the whole publish if it cannot be written, means no content change ever happens without a record.

Why ids are deterministic: the intent and committed documents use ids derived from the change itself, so retries create the same document and conflict harmlessly instead of duplicating.

How did you use distributed locking, and what does the lock actually protect? Intermediate

The lock serialises writers that would otherwise change the same tenant's data at once. We use Redis-based locks with a time-to-live, keyed by tenant and resource. A holder that dies stops refreshing, so the lock expires on its own and nobody is stuck forever.

Three details that matter:

  • Refreshable lease: long operations extend the lock periodically, so a short TTL still protects a long job, while a crashed holder is released within seconds.
  • Sorted keys: when one request needs several locks, it acquires them in a fixed sorted order. If every writer uses the same order, a circular wait (deadlock) cannot form.
  • Scope: the lock is per tenant, so one large tenant never blocks others.

What a lock does not give you: it is not a transaction. It stops overlap but does not make the three-store write atomic; that is the log's job. Also, a lease can expire while a slow holder is still working (pause, GC), so correctness must not rely on the lock alone. That is why optimistic checks and idempotent writes sit underneath it.

How do you handle two writers updating the same search document at the same time? Intermediate

Optimistic concurrency. The writer reads the document along with its sequence number and primary term, then writes with those values as a condition. If someone else changed it first, the engine rejects the write with a 409 conflict, and we re-read and retry only the conflicted items.

Why optimistic: conflicts are rare, so taking a lock for every read-modify-write would cost more than the occasional retry. Locks are used where a larger section must be exclusive; version checks protect each individual document.

Bulk is not atomic. A bulk request returns a status per item. Some items can succeed while others conflict. The retry logic therefore re-sends only the conflicted items, with a bounded number of attempts, and reports the rest as failed for that item. Resending the entire bulk would re-apply items that already succeeded.

What does "idempotent consumption" mean in your pipeline, and how did you achieve it? Intermediate

It means processing the same message twice has the same effect as once. Brokers deliver at least once, so duplicates will happen; the consumer must make them harmless. We get this from deterministic document ids: a replay builds the same id, the create is rejected with a 409 conflict, and we count that as success.

  • Before writing: ids already marked COMMITTED are filtered out, so most duplicates never reach the store.
  • During writing: a residual duplicate hits the id conflict and is mapped to success or no-op.
  • Lake side: checkpointed reruns skip work already recorded, so a restarted job does not append twice.

Trade-off: treating 409 as success is only safe if the id is unique per logical event. If two different events can hash to the same id, the second is silently dropped. The id design therefore has to include everything that distinguishes events, and this is the first thing to review when someone proposes changing the id.

How do you order changes across stores? Tell me about the per-tenant sequence number. Senior

Each tenant has a monotonically increasing sequence number made of two parts, (hi, lo). The consumer takes the next value when it processes a committed event, and downstream readers use the pair as the order. The counter lives in Redis for speed, with a durable copy in a relational row for recovery.

Recovery if Redis loses the counter (flush, failover, replacement): the increment script reports the key missing, the generator reads the relational row under a row lock, sets hi to hi+1 with lo at zero, and continues. Because hi grew, new numbers are still larger than anything issued before, so monotonicity holds without knowing the exact last lo.

Ordering limits to state clearly:

  • Numbers are assigned at consume time, so the order is consumption order, not original commit order. With several partitions and consumers, two events can swap.
  • Within one change set, object events come before relationship events, and dependencies are processed in topological order.
  • Two consumers finding the key missing at once could both initialise it. If the initialise step is a plain SET rather than set-if-absent, one could reset lo and issue a duplicate pair. I would harden this with SET NX or a lock.

If sequence generation fails (cache down), the committed event is skipped and the offset advances, so it is lost unless replayed by hand. Alerting on that log code is the mitigation.

Explain stale-asset cleanup and de-duplication. What can go wrong if you run them blindly? Intermediate

How did you make time-series writes replay-safe without updating rows? Senior

The lake checks whether the table already holds a snapshot tagged with this batch id and skips the append if so. The stream builds each document id from the row itself, so inserting a replayed row hits a 409 conflict, which is treated as success.

  1. Merge into the lake: keep only INSERT operations (time series are never updated), validate, add system fields. Ask whether the current table already has a snapshot for the batch id. Only append if not.
  2. Write a checkpoint of the merged rows.
  3. Index into the stream: read the checkpoint, build a deterministic id per row, bulk create. Streams accept only create, so a replay conflicts instead of duplicating.

Worked example: a batch of three rows is appended and tagged with its batch id. The pod dies before indexing finishes. On restart, merge finds the tagged snapshot and skips the append; indexing rebuilds the same ids, two creates conflict (already there, counted as success) and one is created. The end state equals a clean single run.

Follow-up: can treating a 409 conflict as success ever hide a real problem? Senior

Yes. A 409 means "a document with this id exists". It is a replay if the row is the same, but a collision if two different rows produce the same id. The mapper cannot tell them apart, so a collision drops the second row silently and reports success.

When it can happen: if the id is built from external id, class and origin, two events for the same asset in the same class and origin share an id unless the external id differs per event. Whether every producer guarantees that is a data contract question, not something the consumer can check.

What are rolling tables, and why not alter the table when the model changes? Intermediate

When a time-series class changes shape, the platform starts a new numbered table (001, 002, and so on) and leaves the older ones as history, instead of rewriting a very large table. The highest number is the current table, where writes go. Readers and purge jobs visit all of them.

  • Why: rewriting the column layout of a huge table is expensive and risky. A new table makes a model change cheap and old data stays untouched.
  • Partitioning: tables are partitioned by month of the event timestamp, so time-range reads and age-based deletes touch few partitions. Tenant (origin) is also a filter column for purge.
  • Views: views over the rolling tables let readers see one logical table.
  • Cost: every expiry or purge must walk all numbers, not just the current one. Forgetting an older table leaves residue.

How does expiry work, and why do usage data and profiling history use different rules? Intermediate

How do the change events (the change trail) themselves expire, and what happens to the orphan intents? Intermediate

  • Why expire: unbounded growth costs storage and slows queries. Thirty days is long enough for sync and investigation.
  • Caveat: expiry is not reconciliation. It deletes the orphan record; it does not fix content that was written and never confirmed. Detect and repair covers that.

How is time-series data cleaned up when an asset source or tenant is deleted? Senior

A delete stage removes everything for that origin from both stores. It deletes from the data stream first, then runs a delete against every rolling table. The stream delete is strict: failure stops the stage. The lake delete is lenient: a failure on one table is logged and the loop moves on.

  1. Stream first: an asynchronous delete-by-query filtered by origin; the task waits for it and fails the stage on failure. A missing stream is skipped.
  2. Find all rolling tables (every number, not just current).
  3. Delete from each table where origin equals the source, with retry decorators for catalog connection errors and concurrent-modification errors (for example a compaction commit in flight).
  4. One table failing logs a warning and continues, so one broken historic table does not block the purge.

Why strict and lenient: the stream is what users see and is cheap to repeat, so failing fast is right. The lake purge is wide, and blocking the whole job on one table would be worse. The price is a silent partial result: the job ends green while rows remain.

Rerun safety: every delete is a predicate on the origin, so rerunning deletes what is left and ignores what is gone. Rerun is the normal recovery.

Improvement: count failed tables and fail or alert at the end, so a partial purge is visible, and verify with a count query afterward.

How do you use ELK/Kibana to investigate a problem in a multi-tenant platform? Basic

I start from a tenant id and a time window, then narrow by service and log level. In a multi-tenant system the first question is always "which tenants, which service, since when", because a problem that hits one tenant is usually data or configuration, and a problem that hits all tenants is usually code or infrastructure.

My routine is: filter by tenant and time, group errors by message and service to see the shape, pick one failing request and follow its trace id across services, then open the single component that actually failed. I look at the count over time before reading single lines, because a spike that starts exactly at a deploy time points at the release, and a slow climb points at data growth.

Logs are a witness, not the truth. When a log line says something succeeded I still confirm the state in the store if the decision depends on it.

Watch out: Searching on free text across all tenants is slow and noisy. Always put the tenant and time range first.

Remember: Tenant, time window, service, level, then one trace id. Shape first, single lines second.

How do you follow one failed request across services using a trace id? Intermediate

The platform generates a trace id at the edge and carries it, together with the tenant id, over REST headers, gRPC metadata, Kafka message headers and job environment variables. Every log line prints it, so one search shows the whole path of a request, including the part that ran later in a batch job.

One detail matters for Spark: executor threads do not inherit the driver's thread-local context. The job therefore re-applies the trace and tenant context inside every task. Without that, executor logs would carry no trace id and the trail would go cold exactly where the heavy work happens.

Remember: The id must cross every boundary, including async ones. A boundary that drops it is where the investigation stops.

You search a trace id and the trail stops halfway. What do you do? Intermediate

A trail that stops is information. I find the last log line that has the id and ask what the next hop was: an outgoing REST call, a Kafka publish, or a job launch. Then I check whether that hop carries the id, and whether the next component is even running.

Three usual causes: the next hop does not propagate the context (a code gap), the work is queued and not started yet (lag, covered below), or the work died before logging its first line (container killed, covered in the exit code 137 question). I search the tenant and time window without the trace id to tell a missing id from missing work.

Remember: No trace id does not mean no work. Check the tenant and time window before concluding nothing ran.

"Java out-of-memory" is not one thing. What kinds are there and how do you tell them apart? Intermediate

The error message names the area. Heap space means too many live objects for the configured maximum heap. Metaspace means too many loaded classes. Direct buffer memory means off-heap buffers, common with network and file libraries. A silent kill by the container, with no Java error, means the whole process went above the container memory limit.

The fix differs: heap needs less data held at once or a bigger heap, metaspace usually points at class-loader leaks or heavy reflection, direct memory needs bounded buffers, and a container kill needs the heap plus off-heap plus thread stacks to fit under the limit with headroom.

Watch out: Raising the heap first is a guess. Read the message, then collect evidence.

Remember: Message first: heap, metaspace, direct memory, or container kill. Four different fixes.

Walk through how you find the cause of a heap out-of-memory with a heap dump. Senior

I make sure a dump exists: run the JVM with the option that writes a heap dump on out-of-memory to a path that survives the pod, or capture one from a live pod when memory is high but the process is still alive. Then I open it in a profiler and look at the dominator tree, which shows which objects keep the most memory reachable.

Questions I ask the dump: which class or collection holds the largest share, who references it (the path to the garbage collection root), and does its size scale with input size or with time. A collection growing with input points at "loads everything"; growth with time points at a leak such as an unbounded cache or listener.

A real example from this domain: a cleanup job that compares the index with the lake collects all hits into the driver as rows. That is fine for small classes and an out-of-memory risk for very large ones. The fix is to bound the work, for example per class or per source, and to process in pages instead of collecting.

A job pod disappears with exit code 137 and no Java error. What happened? Senior

137 is 128 plus signal 9: the process was killed from outside, most often by the container runtime for exceeding its memory limit. The JVM never got the chance to print an out-of-memory error, which is why the logs just stop.

I confirm with the pod's last state (the reason reads out of memory killed), then compare the limit with what the JVM can use: heap maximum plus metaspace, direct buffers, thread stacks and native libraries. Spark adds off-heap and shuffle buffers on executors. If the heap is set close to the container limit there is no room for the rest.

Fixes: leave real headroom between heap and limit, reduce per-task data (more partitions, smaller batches), or raise the limit if the work really needs it. Because the job contract treats a failed pod as a failed task, I also check that a retry does not repeat the same oversized work blindly.

Remember: 137 means killed from outside, usually the memory limit. Heap must fit under the limit with headroom.

How do you read a Spark execution plan to find why a job is slow? Intermediate

I use the Spark UI together with the physical plan. The plan tells me which join strategy was chosen, where the shuffles (exchange steps) are, and whether filters were pushed down to the source. The UI tells me which stage and which tasks took the time.

What I look for: a sort-merge join where a broadcast would be enough (or the reverse, a broadcast of a side that is too large), many shuffles that could be avoided, a filter applied after a wide read instead of before, and stages where a few tasks run far longer than the rest, which is skew.

In our delta and cleanup jobs the small side of a join is given a broadcast hint. A broadcast of a side that turned out too large can fail with an out-of-memory or oversized-frame error. The job wraps the step in a retry policy with at most two attempts, and the retry runs with the hint removed, which is slower but usually succeeds.

Remember: Plan shows strategy and shuffles, the UI shows time. Check join type, shuffles, pushdown and uneven tasks.

What is data skew and how do you fix it? Senior

Skew means a few keys hold a large share of the rows, so after a shuffle a few tasks get far more data than the others. In the UI one task runs for a long time while the rest finish quickly, and the same task is often the one that runs out of memory.

In a multi-tenant platform the natural skew key is the tenant: one very large tenant next to many small ones. Fixes in rising effort: filter earlier so less data shuffles, broadcast the small side so the large side is not shuffled at all, split the job per tenant or per partition so a heavy tenant cannot hold up everyone, and salt the key to spread a hot key over several tasks.

Watch out: More executors do not help skew. The hot task still runs on one core.

Remember: One slow task means skew. Broadcast, filter early, split per tenant, or salt the key.

What is CDC reverse sync in this platform and why can it become a bottleneck? Intermediate

Real-time writes land in the search index first, and the lake must catch up. Reverse sync is the job that reads changes from the index and applies them to the lake tables. It is cursor driven: it remembers the last change it applied and processes the next range, so a rerun continues instead of starting over.

Several design choices make it correct and also make it a throughput limit. It holds a lock so two runs cannot apply the same range. It works in bounded batch ranges, each with its own batch id, and it commits the lake changes together with the checkpoint so a crash never leaves the cursor ahead of the data. It also pauses briefly between batches to avoid hammering the index. Safe, but when the incoming change rate is higher than "range size per batch, divided by batch time plus pause", the backlog grows.

Remember: Cursor plus lock plus atomic commit with checkpoint. Correct by design, so throughput is bounded by batch size and batch time.

How would you find the bottleneck in a job like reverse sync? Senior

I split one batch into phases and time each: reading the change range from the index, computing what changed, writing to the lake, committing the checkpoint, and waiting. The slowest phase is where I dig. Without that split, "the job is slow" gives me nothing to act on.

Typical findings and what they suggest: slow read means a deep or expensive query (check cursor use and filters); slow compute means a bad plan or skew (read the plan); slow write means small files or contention on the table commit (check commits and compaction); long gaps between batches mean fixed pauses or lock waits; and a growing backlog with healthy batches means the batch range is too small for the incoming rate.

After a change I compare the same metrics for the same tenant, so I know the improvement is real and not a quiet period.

Remember: Time each phase of one batch, then fix only the slowest. Verify with the same metric afterwards.

Consumers or jobs are lagging behind. How do you decide whether to scale, tune or fix code? Senior

I compare the arrival rate with the processing rate. If processing is steady but arrival jumped, capacity is the issue. If processing slowed while arrival is steady, something got slower: a dependency, a plan change or data growth. If only one tenant or partition lags, it is skew or a poison item, and adding capacity will not help.

Scaling is right only when work is parallel and one unit is cheap. For serial pieces such as a locked, cursor-driven sync, more pods just wait on the lock, so the fix is a bigger range, less waiting or a cheaper batch.

Remember: Arrival rate versus processing rate decides it. One tenant or partition behind means skew, not capacity.

You say you remediated RDCVs. What is an RDCV, and how does a remediation go from start to finish? Basic

An RDCV is a tracked security finding against one of our services or jobs, with an owner and a deadline. It is usually either a vulnerable third-party library (a CVE) or a problem in our own code, such as data that could leak. I take the finding, work out whether we are really exposed, fix it by upgrading or changing code, prove the fix, ship it, and close the ticket with evidence before the deadline.

A CVE is a public identifier for a known vulnerability in a specific version range of a library, for example the well-known Log4Shell issue in a logging library. A scanner compares the libraries in our build with a database of CVEs and files a finding. The SLA is the time we are allowed to take, and it is usually shorter for higher severity.

Why the order matters: "exposed" is not the same as "the library is in the build". A library may be present but the vulnerable function may never be called, or the vulnerable feature may be switched off. That changes the urgency and the risk of the fix, though most teams still upgrade, because a scanner keeps reporting it until you do.

A scanner flags a third-party library with a high-severity CVE. How do you decide whether we are actually exposed? Intermediate

Why is remediation harder for batch jobs than for a normal service? Senior

Because a Spark job does not control its whole classpath. Spark and Hadoop bring many libraries with them, and our job has to run with the versions the cluster provides or ships. So a plain version bump can clash with what Spark expects, and I have to test with the real runtime, not only with unit tests.

What makes jobs different:

  • Spark brings its own libraries. Many common ones (JSON, logging, compression, networking) arrive with Spark. If I force a newer version, Spark internals may call a method that no longer exists.
  • Classpath order matters. The job's jar and the runtime's jars share one classpath. Which copy wins can differ between local tests and the cluster, so a fix that passes locally can fail on the cluster.
  • Shaded or bundled jars. A job packaged as one fat jar may carry an old copy of a vulnerable library that the dependency tree never shows.
  • Bigger blast radius per run. A bad release breaks a scheduled job for every tenant that run covers, and the failure may show up hours later.
  • Several libraries together. The data table format (Iceberg), Spark and the storage connectors are version-matched. Upgrade one and you may have to move another.

How I handle it: check the vulnerable library is truly in the job's final artifact (look inside the packaged jar), check which version Spark itself provides, bump only if the versions are compatible, and run a real job on a small dataset in a test environment before release. When the clash cannot be solved, I report it and go to the no-fix options (next question).

Watch out: "the unit tests pass" is weak evidence for a job. The test that matters is a real run on the real runtime.

Tenant isolation

Your summary says "strict tenant isolation". How does a multi-tenant platform like this keep one customer's data away from another's? Senior

Isolation is not one switch. It is a habit repeated at every layer. The tenant is taken from the verified identity of the request, then it is put into every query filter, every cache key, every lock name, every storage path and every encryption request. So if one layer has a bug, the layers behind it still hold.

A tenant is one customer organisation. In a multi-tenant platform many tenants share the same running services and the same data stores, which is cheap, but it means isolation has to be built in on purpose.

Layer by layer:

  1. Identity. The tenant comes from the authenticated token, never from a query parameter or a body field that the caller controls.
  2. Queries. Search and database access add the tenant condition in one shared place, so a developer cannot forget it on a new endpoint.
  3. Keys and locks. A cache key like tenant:item, not just item. A lock name that includes the tenant, so tenant A's work never blocks or reuses tenant B's. Messages on the event bus carry the tenant in a header, and the consumer restores the tenant context before it does any work.
  4. Storage. Table catalogs and warehouse locations are resolved per tenant, and blob paths are scoped per tenant.
  5. Files. Data files are encrypted with a key that belongs to the tenant (next question).

Trade-off: sharing infrastructure with per-tenant naming is far cheaper than one cluster per tenant. The price is that isolation now depends on every caller applying the naming scheme. That is why the scheme must live in shared helpers and be covered by tests.

Remember: tenant from the token, then in every filter, key, lock, path and encryption request. Defence in depth, not one gate.

What is "cryptographic isolation", and how does envelope encryption give it per tenant? Senior

It means that even if someone could read tenant A's files, they could not decode them without tenant A's key. With envelope encryption, each data file gets its own random data key. That data key is itself locked ("wrapped") by a key management service using a key that belongs to the tenant. Only the wrapped version is stored next to the file, so no plain key ever sits on disk.

Why two keys? Encrypting big files with a key held in a key management service (KMS) would mean sending all the data to the KMS, which is slow. So we use a fast local key for the data and use the KMS only to protect that small key.

What you get: a stolen or mis-routed file is unreadable noise to anyone else, and you can retire one tenant's data by destroying that tenant's key.

Limits to say out loud:

  • Whether the KMS truly refuses a cross-tenant unwrap depends on how the key service is configured. I would verify that with a test, not assume it.
  • Older files written before encryption was added may have no key information. The reader treats them as plain text for backward compatibility, which also means a configuration mistake can silently produce unencrypted files. A startup check and a test that opens a freshly written file and fails if it is readable as plain text would catch that.
  • Not every file type is necessarily covered (for example small delete-marker files). Know the list.
  • Encryption protects confidentiality. A separate integrity check is needed if you also want to detect tampering.
Make it yours: if you worked on this path, say what you did (reviewed, tested, debugged). If you only understand it from the design, say so plainly and show you know the limits above.

Remember: a fresh data key per file, wrapped by a per-tenant key in a KMS, only the wrapped key stored. Verify the failure cases too.

What happens if one layer forgets to apply the tenant? How do you find that kind of bug before a customer does? Senior

If a single layer forgets, the layers behind it limit the damage. For example a missing query filter still meets a per-tenant path or a per-tenant key. But I do not rely on that. I make the safe path the easy one with shared helpers, and I test with two tenants that deliberately have overlapping data.

Where forgetting usually happens:

  • A new endpoint that builds its own query and skips the shared filter.
  • A cache key built by hand with a string, missing the tenant part.
  • A background job or consumer that processes a message and forgets to restore the tenant context.
  • A lookup by id that never checks the owner.

How to catch it early:

  1. Two-tenant tests. Create tenants A and B with the same ids and similar data. Run the operation as A. Assert no row, key, file or log line belongs to B.
  2. One helper per concern. One function builds cache keys, one builds lock names, one builds storage paths. Review any code that builds them by hand.
  3. Code review checklist. "Where does the tenant come from? Where is it applied?"
  4. Static search. Search the code for direct data-store calls that bypass the shared wrapper.
  5. Runtime signals. Log the tenant on each request (as an id, not as data) so a suspicious cross-tenant pattern can be traced.
Watch out: some mappings in a shared stack come from external libraries, such as how a tenant maps to an index in the search engine. If you cannot show where the rule is enforced, call it an assumption and write a test for it.

Spark executors reuse threads across tenants. How do you stop one tenant's context from leaking into another's task? Senior

I never keep tenant state in a long-lived, shared place. The tenant is passed in with each task, set just before the call that needs it, and cleared right after in a finally block. A design that caches one key or one session for the whole process is only safe if the process handles exactly one tenant.

The problem in simple words. A worker thread runs many tasks one after another. If task 1 (tenant A) stores "current tenant = A" in a thread-local variable and does not clear it, task 2 (tenant B) can start with A's value. Anything it writes or decrypts may then use A's context.

What is the "noisy neighbour" problem, and is it the same thing as a leak? Intermediate

No, it is a different failure. A leak is about data going to the wrong tenant. A noisy neighbour is about one tenant using so much shared capacity that others get slow. Both come from sharing infrastructure, so I design for both: tenant-scoped data for isolation, and limits and fair scheduling for capacity.

  • Examples: one tenant sends a huge bulk update and the shared queue backs up; a very wide search query hogs the search cluster; one tenant's job fills memory on a shared executor.
  • Controls: rate limits per tenant, a cap on query size and result size, batching with a maximum per tenant per cycle, separate queues or partitions for heavy work, and per-tenant metrics so you can see who is heavy.
  • Link to security: a capacity problem can become a denial-of-service route, so limits also count as a security control.

When the authorization check itself fails or returns nothing, should the system fail open or fail closed? Senior

For data that tenants care about, fail closed. If I cannot prove a user may see something, I do not show it. Failing open is only acceptable for low-risk features, and only on purpose, with the choice written down. What I watch for is a system where different callers behave differently without anyone having decided that.

Fail open means "if the check is missing or broken, allow". Fail closed means "deny". Closed protects data but can hide content when the policy service has a bad moment. Open keeps users working but can leak.

How this plays out in a policy-based design:

  • Policies written by people are compiled into rules and stored in files and a cache. A decision service evaluates them per request, often in batches.
  • For search, a good design asks the policy engine for a condition to add to the query, so documents the user may not see are never returned at all.
  • If the cache is empty, the reader falls back to the files with a few retries. If that also fails, "no rules found" must mean deny, not allow.
  • Be careful with an empty list. "No restrictions apply" and "I failed to load the restrictions" look the same. Treat an empty result as suspicious unless it was explicitly proven to mean "unrestricted".
  • Check how each caller treats a missing verdict, a null, and an error. In a real review I list these per caller and decide each one, rather than assuming they agree.
Watch out: a cache refresh that deletes then sets has a short window where the key is empty. If the empty case means "allow", that window is a leak.

Remember: unknown means deny for protected data, and each caller's behaviour should be chosen and tested, not accidental.

How do you implement idempotent processing concretely? Intermediate

Give each logical operation a stable unique key (an order id or an idempotency key), record it with its outcome atomically with the effect, and on a repeat return the stored outcome instead of redoing the work.

  1. Choose the key: a client-supplied idempotency key or an id derived from the business data.
  2. Store it in a table with a unique constraint. Insert the key first (or in the same transaction as the effect). A duplicate insert violates the constraint, which tells you this is a repeat.
  3. For a repeat, return the earlier result (or "already processed").
  4. Consider concurrent duplicates: two threads can pass an existence check at the same time; the unique constraint is what really protects you, not the check.
  5. For calls to external systems that you cannot make transactional, send their idempotency key if they support one, or check state before acting.
  6. Expire old keys after a period that exceeds the maximum retry window.
try { processedRepo.insert(messageId); } catch (DuplicateKeyException e) { return; }  // already handled
applyEffect(msg);   // ideally in the same transaction as the insert

Scenario: the billing system becomes slow and your service threads pile up, then the whole service stops answering. What happened and what do you change? Senior

A slow dependency without timeouts or isolation holds threads; when all request threads are waiting, the service cannot answer anything, even unrelated calls. The fix is timeouts, a circuit breaker, bulkheads, and moving non-urgent work to a queue.

Mechanism: by Little's law, concurrent requests = arrival rate times latency. If latency goes from 100 ms to 10 s, the same traffic needs 100 times more threads. The pool exhausts, the queue fills, health checks may fail, and pods restart, which makes it worse.

Fixes in order:

  1. Timeouts on the outbound client, short enough to fail fast.
  2. Circuit breaker so after repeated failures calls fail immediately and the dependency can recover.
  3. Bulkhead: a separate bounded pool for billing calls so the rest of the service stays responsive.
  4. Degrade gracefully: accept the order, queue the billing step, and process it when billing recovers.
  5. Backpressure: reject early with 503 or 429 instead of queuing unbounded.
  6. Alerting on dependency latency, not only errors.

Verify with a test that makes the dependency slow and checks the rest of the service stays healthy.

Make it yours: if this happened to you, use the real story; otherwise present it as the standard failure mode you designed against.

Remember: a slow dependency eats threads: timeouts, breaker, bulkhead and a queue contain it.
