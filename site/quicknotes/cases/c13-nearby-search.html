Case sheet 13: Design Uber / Nearby Search

A cheat sheet for a ride-hailing service: a live map of about a million moving cars, nearby search, one driver for one trip, and the static "places near me" variant.

1 Problem · 2 Requirements · 3 Estimation · 4 API · 5 Data · 6 Architecture · 7 Deep dives · 8 Scaling · 9 Failures · 10 Impress · 11 Q&A · 12 Links

1. Problem in 3 lines and clarifying questions

One line: riders ask "who is near me", a million drivers move all the time, and the system must find the best few cars in milliseconds and give each trip to exactly one driver.
  • The hard core is geospatial (maps points on the earth to something we can look up fast) plus correct assignment. Payments, ratings, map drawing are secondary.
  • Location data is huge in volume but tiny in size and disposable. Trip data is small in volume but must be exactly right.
  • A static variant ("find restaurants near me") uses the same geometry with a very different workload.
Question to askAssumed answer
Which flows matter?Rider requests a ride, system finds and assigns a driver, both see live positions, trip completes. Also the "cars near me" map before booking.
Scale?100 million monthly riders, 20 million trips per day, 5 million registered drivers, about 1 million online at peak, many cities worldwide.
How fresh are positions?GPS fix about every 4 seconds. Matching may use data 5 to 10 seconds old. The rider map should look smooth.
Matching speed?First offer within about 1 second at p99. Full assignment depends on humans (seconds to tens of seconds).
Can a driver get two trips?Never. One driver, one active trip. This is the main correctness rule.
Ride types, pricing?One car type plus a few categories. Upfront fare with surge by area. Pooled and scheduled rides are out.
Multi-region?Yes, but a trip is local: both people are in one city, and cities map to regions.

2. Requirements

Functional

  • Drivers go online or offline and stream location
  • Rider sees nearby drivers, pickup time and price
  • Rider requests a trip; system offers, handles decline or timeout, reassigns
  • Both see each other's live location and trip status
  • Trip moves through defined states, each change durable
  • Location history kept for support, fraud, analytics

Non-functional

  • Nearby query p99 under 100 ms; first offer under 1 s
  • Hundreds of thousands of location writes per second, mostly overwrites
  • Never double-assign a driver, even with retries and crashes
  • Location index: availability over perfect freshness. Trip state: durable and strongly consistent per trip
  • One city's failure must not stop other cities

Out of scope

  • Payments and receipts
  • Driver background checks
  • Map tile drawing, turn-by-turn navigation
  • Pooled rides, incentives, chat, fraud models

Say: "Three data shapes, three stores. Positions are small, hot and overwritten, so memory. Trips are rare and must be correct, so a durable database. History is huge and cold, so a log into cheap columnar storage."

4. API

     -> { drivers: [ {id_masked, lat, lon, heading} up to 20 ], eta_min }
POST /v1/fare-estimates   { pickup, dropoff, type } -> { fare range, surge, quote_id, expires_at }
POST /v1/trips            { quote_id, pickup, dropoff, type }
     Header: Idempotency-Key   -> 202 { trip_id, state: "REQUESTED" }
POST /v1/trips/{id}/cancel     GET /v1/trips/{id}  (reconnect and recovery)
POST /v1/drivers/me/status     POST /v1/offers/{id}/accept | /decline

WebSocket:
driver -> server  { t:"loc", lat, lon, hdg, spd, ts, seq }     every ~4 s
server -> driver  { t:"offer", offer_id, trip_id, pickup, expires_in_s: 15 }
server -> rider   { t:"trip", trip_id, state, driver, version }
server -> rider   { t:"pos", lat, lon, hdg, eta_s }            every 2-4 s on trip
  • Idempotency-Key (a unique tag per action): a retried or double-tapped request returns the same trip, never a second one.
  • Request returns 202 Accepted at once because matching takes unknown time; progress comes over the socket.
  • version on trip messages and seq on location messages let the receiver ignore an old message that arrives late.

6. Architecture and main flows

Flow A: one location update

  1. Driver app sends a fix over its open WebSocket (slower when parked, every 2 s on a trip).
  2. Gateway adds the authenticated driver id (never trust the id in the payload) and forwards by hash of driver id so one driver's updates stay in order.
  3. Location service computes the cell id and runs one small pipeline on the shard: drop if seq is older, write the hash, refresh the 15 s TTL, and if the cell changed move the id from the old cell set to the new one.
  4. It publishes the fix to Kafka asynchronously. If the log is slow it buffers a little then drops; history may have gaps, the live index is never blocked.

Flow B: nearby query and dispatch

  1. Compute the home cell and its ring of neighbours (9 squares or 7 hexagons).
  2. Read those cells in parallel from one or two shards.
  3. Drop stale records (older than about 10 s), drivers not AVAILABLE, wrong vehicle type.
  4. Drop drivers outside the radius with exact distance (haversine). If fewer than about 10 remain, widen one ring (cap at 2 or 3 rings).
  5. Pre-rank by straight-line distance, take the top 8 to 10, ask the ETA service for road time in one batch, rank by ETA.

Offer details: timeout 10 to 20 s, stored as expires_at and fired by a scheduler so it survives a crash; a late accept is rejected. After a bounded time (about 2 minutes) or about 8 offers the trip becomes NO_DRIVERS.

7. Deep dives

7.1 Geospatial index: how to turn a point into something searchable

A normal database index sorts by one number, so "within 2 km" scans a whole band of latitudes. We need to map two dimensions to one key, or cut the map into buckets and look buckets up.

OptionHow it worksGoodBad
GeohashInterleave lat and lon bits into a base-32 string; shared prefix = shared cell. Length 6 is about 1.2 km x 0.6 kmPlain string key, works in any DB and Redis, everyone knows itClose points across a boundary have different prefixes, so always read 8 neighbours. Cell shape distorts away from the equator
QuadtreeSplit a square into 4 when it holds more than K pointsAdapts to density (deep downtown, one leaf in a desert)Pointer-heavy; every move may delete and insert, split and merge. Awkward at 250k moves per second
S2Sphere on a cube, cells ordered on a Hilbert curve, 64-bit ids, 30 levelsUniform cells, good locality, covers polygonsNeeds a library
H3Hexagons, 16 resolutions (res 8 about 0.7 km2, res 9 about 0.1 km2)Six equal-distance neighbours; clean rings and surge mapsChild cells do not nest exactly in the parent

Choice: a fixed-resolution cell id as the key (H3 or S2; geohash would also work). The id is a cheap pure function of lat and lon, so an update touches no tree. Use cells about 1 km wide for dispatch and a coarser parent (about 10 to 20 km) as the sharding unit. Quadtree is for the static POI variant.

Trap: searching only the rider's own cell. A driver 20 m away across the boundary would be missed. Always read neighbours, then filter by exact distance.

7.2 One driver, one trip

The location index can show a driver as free for a few seconds after they accepted another trip. So the index is a hint; a separate strongly consistent row is the authority.

OptionMechanismGoodBad
A. Conditional update in the trips DBUPDATE driver_assignment SET status='BUSY' ... WHERE driver_id=? AND status allows; check rows affectedDurable, atomic on one row, no new system, safe to retryOne DB round trip per claim (fine at 2,000 per second)
B. Redis lock with TTLSET lock NX PX 20000Very fastLock can expire while a slow worker continues; failover can lose it. Fine as a speed-up only
C. Lock service with fencing tokenetcd/ZooKeeper token that only increases; storage rejects stale tokensSafe under pausesExtra component, still needs the DB to check the token
D. Single writer per driverAll operations for a driver go to one ownerNo locksOwnership handover on failure

Choice: A as the source of truth, B as an optional quick pre-check. A compare-and-set means "the world is still as I thought, and now it is changed", which stays right when processes pause, crash or run twice. A version or offer id in the WHERE clause makes a stale worker update zero rows.

Two-sided claim (trip and driver may sit on different shards): shard trips and assignments by region so both sit together and use one local transaction. A trip is local to a city, so this is natural. Alternative: claim the driver first (the commit point), attach the driver to the trip with retries, and release the driver if that fails (a saga).

Say: "I do the assignment as a state transition on a durable row, not as a lock. The index finds candidates; the assignment row decides."

Choice: coarse parent cell with a directory (a lookup table from cell to shard) so specific cells can be rebalanced. Run 16 or more shards for headroom (250k writes per second is about 5 to 8 shards of work).

Surge pricing (derived data)

  • Stream job counts requests per cell (about H3 res 8) over 1 to 5 minutes against available drivers now; smooths neighbouring cells.
  • Multiplier from the demand to supply ratio, clamped (for example 1.0 to 5.0), rate-limited, recomputed every 30 to 60 s, stored in an in-memory map.
  • Fare estimate returns a quote_id that locks the price briefly, so surge changes do not change what the rider agreed to.

Trip state machine

States: REQUESTED, MATCHING, ACCEPTED, DRIVER_ARRIVED, IN_PROGRESS, COMPLETED. Dead ends: NO_DRIVERS, CANCELLED. ACCEPTED may go back to MATCHING (driver cancels or goes silent); IN_PROGRESS may not be cancelled by the simple path. Every transition is UPDATE ... SET state=new, version=version+1 WHERE id=? AND state=old. Events go out by the outbox pattern (write the event in the same transaction, a relay publishes it) so payments and analytics never miss a transition.

Realtime delivery

  • WebSocket for two-way low latency; APNs and FCM push as backup when the app is in the background.
  • A Redis presence table maps user id to gateway id (TTL refreshed by pings); no entry means send a push.
  • On reconnect the client sends its last version; the server returns the current trip document instead of replaying messages. Positions are latest-wins and may be dropped; state changes are acknowledged and re-sent.

Trap: using the index as the lock ("remove the driver from the cell set when offering"). Another dispatch can read the driver before the removal, and a crash after removal leaves the driver invisible forever.

10. Things to say to impress

Say: "The index is a hint, the assignment row is the authority. Positions are eventually consistent and disposable; assignments are a conditional write with a version, so retries, crashes and paused workers cannot double-assign."
Say: "Dispatch is only about 2,100 offers per second. Correctness is the hard part, not scale. The scale problem is 250,000 location writes per second on 200 MB of data, so I shard for throughput, not capacity."
Say: "I rank by ETA, not distance, in two stages: cheap distance pre-rank, then one batch ETA call for the top 10, with a circuit breaker fallback."
  • Do not replicate the live index across regions; replicate trip state only.
  • Make the invariant observable: counters for double assignments must be exactly zero, with a reconciliation job and an immediate alert.
  • Name greedy matching as the weakness and batched global matching as the evolution.
  • Privacy: public map shows jittered positions and masked ids; exact identity only to the rider on an active trip; limit location retention.
  • Show the adapt-to-workload skill: the Yelp variant flips to read-heavy, search engine or quadtree, cache by cell.
  • SLIs: update-to-visible lag p99 under 2 s, nearby p99 under 100 ms, match rate within 2 minutes per city, reassignments per trip.
  • Phasing: one city with one Redis and sequential offers, then ETA ranking and surge, then sharding and regions, then batched matching.

11. Interview Q&A

Why not store driver locations in a relational database with a lat/lon index?

A normal index sorts on one dimension, so "within 2 km" scans a large band of latitudes. Spatial indexes such as an R-tree do exist, but the real problem is the write rate: 250,000 updates per second, each rewriting an index entry and obsolete four seconds later. We would pay for disk transactions and durability with no benefit. An in-memory store keyed by cell id makes each update a few constant-time steps and each query a handful of key reads. A relational spatial index is fine for the static place variant, where writes are rare.

How do you choose the cell size?

Smaller cells hold fewer irrelevant drivers and give a tighter search, but a query must read more cells, and more driver updates cross a boundary, which costs two writes instead of one. A good rule is a cell about the search radius divided by 2 or 3, so the home cell plus its ring covers the radius. For 2 km that is cells about 1 km wide (H3 resolution 8, geohash length 6 or 7). Dense areas can go finer and sparse areas coarser through the directory. Check it with numbers: tens of drivers per cell on average is comfortable to read in one call.

Two riders request at the same instant and the same driver is nearest to both. What happens?

Both dispatch flows rank that driver first and both try to hold them. The first conditional update that moves the driver from AVAILABLE to OFFERED for its trip succeeds, and the other updates zero rows. The loser sees the failure and moves to its second candidate with no human involved. If both offers were sent anyway (broadcast mode), the accept step is a second guard: only one accept makes the driver BUSY and the trip ACCEPTED, and the other gets "no longer available". The database row decides, so the answer is the same under retries, crashes and clock skew.

How do you detect that a driver went offline without telling you?

Each driver record has a time to live of about 15 seconds that every update refreshes. If the phone dies or the car enters a tunnel, updates stop and the record expires by itself. Queries also ignore entries older than about 10 seconds, so the driver vanishes from searches before the physical expiry. For a driver on a trip, a silence beyond about 60 seconds raises an alert to the rider and a support flow, but not an automatic cancel, because tunnels are normal. This needs no cleanup job and fails safe: stale means invisible.

Why rank by ETA instead of distance, and how do you keep it cheap?

Straight-line distance ignores rivers, one-way streets, closed roads and traffic, so the nearest driver is often not the quickest. ETA is what the rider feels and what drives cancellations. Routing every driver in range would be expensive, so I pre-filter by straight-line distance to about 10 candidates and make one batch call to the routing service. A road graph with precomputed shortcuts answers in about a millisecond each, so the step costs a few milliseconds. If the service fails, a circuit breaker falls back to distance times a city factor, which is slightly worse but available.

Why not use a Redis lock to guarantee one driver, one trip?

A lock with a TTL can expire while a slow or paused worker still believes it holds it, and a Redis failover can lose the lock entirely. Without a fencing token (a number that only goes up, which storage uses to reject old holders) two workers can both act. A conditional write on a durable row is stronger, because it says "only if the state is still what I saw". I would still use the Redis lock as a cheap pre-check to avoid pointless database work, but never as the only guard.

How would you avoid a thundering herd when a stadium empties?

Several layers help. The map reads from replicas and a short per-cell cache, so thousands of app opens do not hit the primary. Dispatch coalesces requests per cell into batches and reads each hot cell once per batch. The hot parent cell is split into finer children over several shards, and each query caps how many candidates it reads. At the product level, surge pricing and designated pickup zones spread demand over time and space. Finally, admission control sheds or delays excess requests with a clear "high demand" message, which keeps latency healthy for the ones accepted.

What consistency do you need for location data versus trip data?

They sit at opposite ends. Location data is eventually consistent, last-write-wins by sequence number, and may be a few seconds stale or occasionally lost, since the next point arrives soon. Trip and assignment data need strong consistency per record: a conditional write on one row, durable replication before acknowledging, and monotonic versions so clients can order messages. This is the CAP trade-off chosen per data type: speed and availability for positions, correctness for assignments. Making location writes durable would waste capacity; making assignments loose would cause double assignment.

The Redis shard for downtown crashes at peak. What do you do?

First, confirm the impact: queries in that area return fewer cars and dispatch may widen its search. The replica is promoted within seconds, and even if the data is gone, the 4-second update cycle repopulates a fresh shard almost completely within one or two cycles. Trip and assignment data are untouched because they live in the trips database. During the gap, dispatch widens rings and the map shows fewer cars, so riders see a thinner map rather than an error. Afterwards I would check shard skew and consider splitting the hot parent cell so one shard does not carry all of downtown.

Ride requests are succeeding but riders complain nobody accepts. How do you investigate?

I would look at the match rate within 2 minutes per city, then the offer acceptance rate, timeout rate and reassignments per trip. Rising timeouts with many offers per trip point to a stale index (offers going to drivers who are gone or busy) or bad ranking. I would check update-to-visible lag, and whether the record TTL is too long. Then I would compare the supply count in the index with the count of drivers online from gateway connections. If the index is healthy, the cause may be low supply or a surge setting that is too low. I would also check whether the ETA service is down and the fallback is making poor matches.

What happens if the whole region goes down?

That region's cities fail over to the paired region through DNS or the global edge. The paired region holds a trips database replica, so open trips and assignment rows are available, with a small chance of losing the latest asynchronous writes, which we reconcile using trip versions and the driver app's own knowledge (it re-asserts its trip state on reconnect). The live index needs no copy: within one or two update intervals, every online driver re-publishes its position into the new region. Gateways absorb the reconnect storm with jittered backoff and admission control. In-progress trips continue because the apps hold state. Recovery is minutes for dispatch and near zero for in-flight trips.

Why one home region per city instead of multi-master across regions?

A trip involves one rider and one driver in one city, so all its data is naturally local. If trips for a city are written in only one region at a time, there are no conflicting writes and no need for conflict resolution, which is where multi-master gets hard. Latency is also best, because users are routed to the region of their city. Global pieces stay thin: accounts, payment methods and the analytics pipeline. The cost is a failover step when a region dies, which is acceptable because a regional outage is rare and the paired region has the replicated trip state.

How would the design change for a Yelp-style place search?

The workload flips. Writes almost vanish (about 1 per second) and the dataset is bigger (200 GB) but static, so the index can be a search engine or a quadtree rebuilt offline, sharded by geography, replicated for reads, and fronted by a cache keyed by cell and filters. We drop the TTLs, sequence checks and in-memory hot path, and add text relevance, category filters, open-now logic and ranking by rating and popularity. Freshness relaxes from seconds to minutes, so change-data-capture indexing is enough. The ideas that stay are: point to cell, read cell and neighbours, exact distance filter, widen rings when sparse.

How do you test and verify the "never two trips" rule?

In tests, run many parallel claims against one driver row and assert exactly one success. Use fault injection: kill workers between offer and claim, and pause them past expiry to confirm the fenced update rejects the stale worker. In production, a reconciliation job continuously scans for drivers with more than one active trip or trips with more than one driver, and any non-zero count alerts immediately. A shadow replay of the state machine against the event log can find illegal transitions. Together these turn the rule into a metric you can watch.
