Case sheet: Design Dropbox / Google Drive

One-page cheat sheet for the file sync case study. Full worked solution: Handbook case study 9.

1 Problem2 Requirements3 Estimation4 API5 Data and stores6 Architecture and flows7 Deep dives8 Scaling9 Failures10 Impress11 Q&A12 Links

1. Problem in 3 lines, and what to ask

One line: keep a folder identical on laptop, phone and cloud, even with offline edits, same-file conflicts and 50 GB uploads over bad networks, without ever losing a file.
  • A client watches a folder, cuts files into pieces called chunks, uploads only the pieces the server lacks, and tells the user's other devices what changed.
  • Users can also share folders, see old versions and restore deleted files.
  • Two sides: huge but simple bytes (immutable chunks) and small but strict metadata (the file tree).
AskAssume
Users500 M registered, 100 M daily active
Data per user, file sizesAbout 2 GB average (skewed); files up to 50 GB; average file about 10 MB
Devices per userAbout 3 (laptop, phone, web)
ConsistencyFile tree strongly consistent per account; other devices may lag by seconds
Speed to other deviceSmall files p95 under 5 s when online
Real-time co-editing?No. Two edits to one file make a conflict, not a merge
Durability, offlineEleven nines; offline edits must sync later

2. Requirements

Functional

  • Upload, download, rename, move, delete
  • Auto sync across devices
  • Resume interrupted uploads and downloads
  • Share files and folders (view or edit)
  • Version history (about 30 days or 100 versions) and restore
  • Offline edits reconcile; conflicts kept, never overwritten

Non-functional

  • Durability first: never lose acknowledged data
  • Efficiency: no re-upload of known bytes (dedup) or unchanged bytes (delta)
  • Tree never points to missing chunks; devices converge
  • Survive one data center loss
  • Hundreds of billions of files, exabytes

Out of scope

  • Real-time collaborative editing
  • Full-text search of contents
  • Photo and video transcoding
  • Billing
  • End-to-end (zero-knowledge) encryption

4. API (a few lines)

Two kinds of endpoints: small JSON metadata calls and large block calls that go straight to storage.

POST /v1/blocks/check   { hashes[] }  -> { missing[] }
PUT  /v1/blocks/{hash}  (chunk bytes, up to ~4 MB; idempotent)
POST /v1/files/commit   { namespace_id, path, parent_rev, chunks[], idempotency_key }
                        -> { rev, cursor } | 409 conflict
upload_session start / PUT ?offset=N / finish   (very large files)
GET  /v1/files/list_changes { namespace_id, cursor } -> { changes[], cursor }
GET  /v1/notify/subscribe   (long-poll) -> { changed: [ns] }
POST /v1/shares   GET /v1/files/versions   POST /v1/files/restore
  • Chunks are named by their hash, so uploading twice is safe (idempotent).
  • parent_rev in commit is how the server spots conflicts.
  • Every change feed uses an opaque cursor: "what changed since here", never "send everything".

5. Data model and store choices

DataStoreWhy
Chunk bytes (1 EB, immutable)Object storage with erasure codingCheap per GB, eleven-nines durability, chunks are never edited
Chunk index: hash to location, refcount (220 B rows, 11 TB)Sharded key-value store keyed by hashPoint lookups at 10k+ per s; hash keys spread evenly, no hot shard
File tree, versions, sharing, journal (150 TB)Sharded SQL, sharded by namespace_idCommits and renames need multi-row transactions plus indexes
Notification map (namespace to connections)Redis pub/subSoft state, rebuilt on reconnect
Key idea, namespace: a file tree root. Every user has a private root namespace; every shared folder is its own namespace, mounted into each member's tree. All metadata is keyed by namespace_id, so sharing and sharding fit together and an ordinary commit stays on one shard.
namespace(ns_id, owner, kind)       mount(user_id, ns_id, mount_path, role)
file(ns_id, file_id, parent_id, name, latest_rev, deleted, UNIQUE(ns_id,parent_id,name))
file_version(ns_id, file_id, rev, size, chunk_list[], client_id)
journal(ns_id, seq, file_id, op, rev, ts)     block_index(hash, size, loc, refcount)
  • Journal: append-only change log per namespace with a gap-free seq (1, 2, 3), written in the same transaction as the change. A cursor is just "namespace, seq".
  • Identity is file_id, not the path, so a rename or a folder move is one row update and touches no chunks.

6. Architecture and main flows

Upload flow (bytes first, metadata last)

  1. Client cuts the file into chunks and hashes each one (SHA-256).
  2. check(hashes): server answers with the ones it lacks.
  3. Client uploads only those, 4 to 8 in parallel; each is written erasure-coded and acked as durable.
  4. commit(path, parent_rev, chunk list, idempotency key).
  5. Server, in one transaction: verify all chunks exist, check parent_rev equals latest, insert version, bump latest_rev, append journal row.
  6. Reply {rev, cursor}; server publishes "ns changed" to notifications.

If the client dies before step 4, nothing user-visible changed; orphan chunks are cleaned up later. A version is visible only if all its chunks are durable.

7. The deep dives

7.1 Chunking and dedup

OptionInsert in the middleCPUBest for
Fixed-size chunksAll later chunks changeAlmost noneVM images, databases, media (in-place edits)
Content-defined (chosen)Only 1 to 2 chunks changeRolling hash (FastCDC about GB/s per core)Documents, source code, archives
Whole file, no chunksRe-upload everythingNoneTiny internal tools only

Choice: content-defined, 4 MB average (1 MB min, 16 MB max); files under 4 MB are a single chunk. The client does the chunking, so unchanged bytes never cross the network. Size trade: 64 KB chunks mean about 10 trillion index entries (500 TB); 64 MB chunks make a tiny edit upload 64 MB; 4 MB balances.

Dedup: the hash is the identity. Each chunk has a reference count. Zero-reference chunks are garbage collected only after a grace period (about 7 days) plus a confirming mark phase.

Trap: cross-user dedup leaks information ("I already have this chunk" confirms someone stored that file). Fix: proof of possession (hash a random byte range with a nonce), scope dedup per account or team for sensitive tiers, and authorize every block read through a file that references it.

7.2 Resumable, parallel upload and sync protocol

OptionForAgainst
One big POST per fileSimpleNo resume, one TCP stream is slow, retries restart everything
Chunks, parallel, hash-addressed (chosen)4 to 8 streams fill the link; a drop costs one chunk; retries idempotentMore requests per file
Poll "list everything"Trivial100 M devices every 30 s is 3.3 M requests per second of waste
Journal + cursor + long-poll (chosen)Near zero load when idle; self-healing; offline for a month is one callNeeds a notification tier

Choice and why: bytes first, commit last, so no one sees a file with missing chunks. For files of tens of GB, an upload session records progress so a reboot can resume, and hashing and uploading run as a pipeline. Delta sync (rsync-style rolling checksum inside a changed chunk) is an extra for big, often-edited files. Mobile uses push (APNs, FCM) instead of a held connection to save battery.

7.3 Metadata sharding and conflicts

Shard byResult
File idA folder spreads over shards; listing and moves become multi-shard
UserBreaks shared folders (they belong to several users)
Namespace (chosen)Tree, versions and journal together; commit is one local ACID transaction. Cost: a giant namespace is a hot shard (use a dedicated shard and limits)

Scale: 150 TB over 256 clusters (about 600 GB each), 4096 logical shards moved between clusters; 175,000 peak QPS is about 700 per cluster. One primary and two replicas each; commit checks read the primary.

Conflict policyBehaviorVerdict
Last write wins (timestamp)Later clock overwritesSilent data loss, clocks are wrong. Reject.
File lockingOne editor at a timeImpossible offline
Automatic merge3-way mergeOnly for known text formats
Conflicted copy (chosen)First commit wins the name; the stale one gets 409 and becomes "name (user's conflicted copy date)"No data lost; user merges

Other tree rules: edit vs delete, the edit wins (resurrect). Rename vs edit never conflicts (identity is file_id). Same name created twice, the unique constraint rejects the second, which is renamed. Move a folder into its own descendant, the ancestry check rejects it. Cross-namespace move is a copy-then-delete saga (no bytes copied, chunks are shared by hash).

Consistency summary: strong inside a namespace for metadata (the commit is the linearization point); immutable and content-addressed for bytes (no consistency problem); eventual, with a bound of seconds, for reaching other devices.

10. Things to say to impress (senior and lead)

Say this:
  • "I split the problem: immutable bytes in an erasure-coded object store, small strict metadata in namespace-sharded SQL. Bytes never pass through the metadata servers."
  • "Upload order is bytes first, commit last, so a visible file version can never point to missing chunks."
  • "Notifications are hints, the journal and cursors are the truth, so the system heals itself when a notification is lost."
  • "I reject last-write-wins because device clocks are wrong; I use a base revision and keep both versions."
  • "Garbage collection is slow on purpose: a leaked chunk costs a few MB, a wrongly deleted chunk costs a customer's file."
  • "Namespaces make sharing and sharding the same decision, and I know the cost: one giant namespace is a hot shard."
  • "Cross-user dedup is a security trade-off; I would add proof of possession."
Common mistakes: uploading whole files, using fixed chunks for documents, polling the whole tree, using timestamps for conflicts, sharding metadata by file id, deleting zero-refcount chunks immediately, putting file data in notifications.

Build order: MVP is a single region with fixed 4 MB chunks, per-user dedup, one SQL cluster using the namespace schema, long-poll and conflicted copies. Then shard by namespace, add the chunk-index KV, content-defined chunking and batch commits. Later: sharing and link sharing, retention, cold tiers, multi-region, delta sync, pack files. At 10x (5 B users, 10 EB) storage cost dominates: better compression, cold tiers, own hardware, and cell-based architecture for 1 billion connections.

11. Follow-up Q&A

Why chunk files instead of storing them whole, and how big should chunks be?

Chunking gives four things at once. You upload only the pieces that changed. An interrupted upload resumes from the last finished chunk. Identical content across files and users is stored once, because the chunk is named by its hash. And big files move in parallel. Chunk size is a trade-off between metadata cost and edit precision. At 64 KB you would have about 10 trillion index entries and a lot of per-request overhead. At 64 MB a one-byte edit re-uploads 64 MB. About 4 MB average with a 1 MB minimum and 16 MB maximum balances both, and files smaller than one chunk are not split.

A user inserts a paragraph at the top of a large document. How much is re-uploaded?

With fixed-size chunks every byte after the insert shifts, so every later chunk gets a new hash and the whole file is re-uploaded. With content-defined chunking the cut points depend on the nearby bytes, so only the chunk holding the insert changes and later boundaries land in the same places. The client hashes its chunks, asks the server which are missing, and sends just that one plus a new commit with an updated chunk list. For a very large chunk you can also send a binary delta against the old chunk.

How do devices stay in sync without scanning the whole tree?

Each namespace has an ordered journal. The sequence number is assigned inside the same transaction as the change, so there are no gaps. Each device stores a cursor, the last sequence it applied, and asks for entries after it. To learn quickly, the device holds a long-poll to the notification service, which the metadata service pings on every commit. The ping says only which namespace changed. If it is lost, the device still finds the change on its next poll or reconnect. A device offline for weeks catches up with one call.

How do you detect and resolve a conflict?

Every commit carries parent_rev, the revision the edit was based on. Inside the commit transaction the server compares it with the file's latest revision. If they differ, someone committed first, so the server returns 409 instead of overwriting. The client keeps the winning version in place and uploads its own as a conflicted copy with a clear name. Nothing is lost and the user merges by hand. I avoid timestamps because clocks differ by seconds to minutes. For edit versus delete, I bring the file back with the edit, because keeping data is safer than destroying it.

Why shard metadata by namespace and not by user or file id?

A commit must check the base revision, insert the version, move the latest pointer and append to the journal, all atomically. If everything for a namespace lives on one shard, that is a local transaction, with no distributed commit. Sharding by file id scatters a folder across shards and makes listing and moves multi-shard. Sharding by user breaks shared folders, which have several owners. The namespace is the natural unit for sync, sharing and permissions. The price is that a huge company drive can become a hot shard, so I give it a dedicated shard and per-namespace limits.

How does dedup work and what are its risks?

The SHA-256 of a chunk is its key. The client sends hashes, the server replies with the ones it lacks, and only those are uploaded. A reference count tracks how many versions use each chunk. The risk is that "I already have it" tells an attacker that someone stored that content, and an attacker who knows only the hash could claim the data. I would require proof of possession, scope dedup to an account or team for sensitive tiers, and check authorization on every block read through the files that reference it. Zero-reference chunks are deleted only after a grace period.

How do you make a 50 GB upload reliable?

Cut it into chunks and upload many in parallel, each with its own retry. Because chunks are addressed by hash, a retry is harmless, and after any disconnect the client asks what is missing and continues. A server-side upload session records progress so a laptop reboot can resume. The client hashes and uploads as a pipeline instead of hashing 50 GB first. Only when every chunk is durable does it send one commit with the chunk list, so a half-uploaded file is never visible. It mirrors multipart upload in object stores.

What if the notification service goes down completely?

Sync gets slower but stays correct. The journal and cursors are the source of truth, so clients fall back to calling list_changes at a modest interval with random jitter, and devices still converge, in tens of seconds instead of a couple. Notification servers hold only soft state (who is connected), so they can be restarted freely and clients reconnect with backoff. I would alert on the sync-lag metric, the time between a commit and the last online device applying it. This is why notifications must never carry the data itself.

How would you support a shared folder with 10,000 members?

The folder is its own namespace with one journal, so one edit writes one journal row no matter how many members exist. The cost is the fan-out: one commit wakes up to 10,000 devices and each calls list_changes. I batch and coalesce notifications, add random jitter before the follow-up fetch, and cache the journal read keyed by sequence number so 10,000 identical requests are cheap. Popular file downloads go through a CDN. This namespace also gets its own shard and rate limits because it is the likeliest hot spot.

How do you delete data safely and keep versioning cheap?

A version is just a chunk list, and unchanged chunks are shared by hash, so 100 versions of a 1 GB file that changes 1% per edit cost about 2x, not 100x. Deleting a file sets a tombstone and keeps its versions for the retention window (say 30 days free, 180 paid). When a version expires, a job lowers the reference counts. A chunk at zero waits out a grace period, then a mark phase confirms no version uses it, and only then is it removed. Restore is a new commit that copies an old chunk list, so no bytes move.

Production incident: users report files "stuck syncing" for 20 minutes. What do you check?

First the sync-lag metric and notification connection counts: if lag is high everywhere, the notify tier or pub-sub is the suspect, and I know clients still poll as a fallback. Then metadata shard health: a failed primary or a slow failover blocks commits for the namespaces on it. Then the block tier: error rates and p95 on chunk PUT and GET, and object store quorum errors. I would also check whether one huge namespace or a reconnect storm is saturating a shard, and turn on admission control and jittered backoff. Correctness is safe throughout because commits are idempotent and the journal is the truth.

What would change if the product required end-to-end encryption?

The client would encrypt chunks with keys the server never sees. So the server could not dedup across users, scan for malware or build previews. Chunking and hashing stay on the client, and dedup is limited to one user's data, or convergent encryption is used, accepting that a known file becomes detectable. Sharing means wrapping each namespace key with each member's public key and rekeying when someone is removed. I treat it as a separate product tier, not the default.

Why not one big key-value store for all metadata?

It scales easily, but commits and renames need multi-row transactions, and the tree rules (unique names per folder, no folder cycles) are hard to enforce without them. A NewSQL database or a KV store with a transaction layer can work, but sharded SQL by namespace is simpler to reason about for this shape of data, and the namespace choice already avoids cross-shard transactions for normal edits.
