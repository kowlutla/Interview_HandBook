Case Sheet: Design Search Autocomplete

Typeahead for a search box: top 10 completions in under 100 ms, from a trie with precomputed top-K lists, built from query logs.

1 Problem2 Requirements3 Estimation4 API5 Data6 Architecture7 Deep dives8 Scaling9 Failures10 Impress11 Q&A12 Links

1. Problem in 3 lines Handbook case

One line: as the user types a prefix like "wea", show the 10 best query completions (weather, weather tomorrow, ...) fast enough that the dropdown keeps up with typing.
  • It fires several times per search, the time budget is tens of milliseconds, and the data underneath changes every minute.
  • Key idea: a trie (a tree where each path from the root spells a prefix) that stores the top-K best completions at every node, built offline, served from memory.
  • Autocomplete is an extra. If it breaks, search still works, so the failure mode is "no suggestions", never an error page.

Clarifying questions to ask (and the assumed answer)

AskAssume
What do we suggest?Past popular search queries, not products or people.
Prefix only or fuzzy?Prefix first; typo tolerance is a fallback path.
How many suggestions?Top 10 (K = 10), ranked by popularity plus a freshness boost.
Scale?200M daily users, 10 searches each per day.
Latency?p99 under 100 ms for the user; server side p99 under 20 ms.
Freshness?Breaking trends in 5 to 15 minutes; the long tail can be a day old.
Personalized?Lightly: merge in the user's own recent searches.
Languages and bad content?Multi-language; never show slurs, personal data, or adult terms to general users.

2. Requirements

Functional

  • Prefix (plus language, locale, optional user) in, up to 10 ranked completions out
  • Rank by popularity, boosted for recent surges
  • Merge in the signed-in user's recent searches
  • Remove blocked terms, and never learn them
  • Tolerate a small typo ("wheather")

Non-functional

  • p50 under 30 ms, p99 under 100 ms at the client
  • 99.99% available; degrade to no suggestions
  • Hundreds of thousands of requests per second at peak
  • Eventual consistency is fine; no transactions
  • Trends visible within minutes

Out of scope

  • The results page itself
  • "Did you mean" on the results page
  • Voice input, image suggestions, ads in the dropdown

Key takeaway: the whole trie (about 16 GB) fits in one 64 GB server. We shard for QPS and blast radius (how much breaks when one part fails), not for size. We replicate for availability.

4. API

GET /v1/suggest?q=wea&lang=en&locale=US&limit=10
200 OK   Cache-Control: public, max-age=60
{ "prefix":"wea",
  "suggestions":[ {"text":"weather","score":9120000,"type":"global"},
                  {"text":"wear os","score":1200000,"type":"trending"} ],
  "trie_version":"2026-11-17T09:00Z" }

POST /v1/suggest/events     (fire and forget: impressions and clicks for ranking)
  • GET with the prefix in the URL so browsers and the CDN can cache it. Normalize the prefix (lowercase, Unicode NFKC, collapsed spaces) on client and server so cache keys match.
  • No "write suggestion" endpoint: the normal search request is already logged; the beacon adds click data.
  • Personal data must not make the whole response uncacheable, so it is fetched or merged separately.
  • Use a persistent HTTP/2 connection so each keystroke does not pay the connection setup cost.

5. Data model and store choices

DataStoreWhy
Raw logs (searches, clicks)Kafka, then object storage in columnar filesHuge append-only writes, replayable, cheap per GB
Aggregated countsBatch output files plus a key-value or wide-column store for streaming countersKeyed increments and time-window reads
Serving index (prefix to top-K)In-memory trie in each process, loaded from an immutable snapshot fileMicrosecond lookups, no network hop, replicate by copying a file
User historyRedis list, or on the deviceSmall per-user data, fast reads
Blocklist and rulesSmall versioned config pushed to every serviceRare writes, must apply within a minute
The crux: a naive trie scans the whole subtree under "a" (millions of queries) and sorts them. Instead, precompute the top-K ids at every node at build time. Lookup is: walk L characters, read one list, turn ids into strings. Time is O(L), no matter how much data exists. We pay with memory (the 12 GB) to buy constant-time reads.
  • Radix compression: merge chains of single-child nodes into one edge labeled with a string (why 100M queries need only about 150M nodes).
  • Ids, not strings, in the lists; scores stored once in a shared query table.
  • Depth cap: no lists below the point where a subtree has K or fewer queries; cap indexed prefix length (about 40 characters).
  • Flat array layout with integer offsets, not millions of heap objects. This avoids garbage-collection pauses (a real p99 killer) and lets a snapshot load by memory map in seconds.

6. Architecture and main flows

Most important structural choice: two halves that meet only at a published file. The serving path (online) answers keystrokes and never touches logs. The build path (offline plus near-real-time) turns logs into immutable trie snapshots. If the pipeline fails, suggestions get stale but autocomplete stays up.

Request flow: one keystroke

  1. User types; the browser waits for a short pause (debounce), normalizes the prefix, and checks its local prefix map. A hit means no network at all.
  2. On a miss, send GET /v1/suggest?q=wea over an open HTTP/2 connection to the nearest edge.
  3. The CDN edge answers short, popular prefixes from a 60 s cache (about 10 to 20 ms).
  4. On an edge miss, the gateway authenticates (if a token exists), rate-limits, and forwards to the suggest service.
  5. The service picks the shard from the first two characters and calls one replica. In parallel it reads the trending overlay and (if signed in) the user's recent queries.
  6. It merges the three sources, drops anything on the live blocklist, ranks, truncates to 10, and returns JSON with Cache-Control.

Build flow: logs to a live trie

  1. Collect: one Kafka event per submitted query, partitioned by hash of the normalized query; clicks go to a second topic.
  2. Normalize and filter: lowercase, NFKC, drop too-long text, URLs, emails, card-like digits, blocklist hits, and bots.
  3. Count: batch job over the last N days with exponential decay (half-life about 7 days) and unique-user counts, so one noisy user cannot promote a query.
  4. Score: blend of decayed frequency, click-through rate when suggested, and a quality prior that demotes junk.
  5. Build: sort, insert, compute each node's top-K bottom-up (merge of its children's lists), radix-compress, write one flat file per shard plus a manifest with checksum and version.
  6. Publish and swap: each shard downloads in the background, checks checksum, size (within 20% of last version) and canary prefixes, then flips one pointer atomically. Old version is freed after readers drain. Rollback is flipping back.

7. Deep dives

7.1 Sharding and caching

OptionHowGoodBad
Full replicas, no shardsEvery server holds the whole trieSimplest; any server answers anything16 GB loaded everywhere on each deploy; cannot outgrow one machine
Shard by first letter(s)Shard i owns a range, e.g. a to fEasy to reason aboutSkewed: "s" and "c" are far busier than "x"; differs per language

Choice: the third option. One-character prefixes come from a tiny replicated "root table", so every lookup touches exactly one shard. A hot bucket (a viral term) gets extra replicas, not a re-shard.

Latency budget, full miss, p99: 20 ms client to edge + 12 edge to origin + 3 gateway + 4 service + 6 shard call + 2 merge + 30 return = 77 ms of 100 ms. Server work is only about 15 ms; most of the budget is network. Edge hit: about 20 ms. Browser hit: 0 ms.

Tail latency tactics: hedged requests (if a replica has not answered by its p95, ask another and take the first answer), a hard 40 ms timeout on the shard call, and pre-warming a new snapshot's hot pages before it takes traffic.

Trap: a cache key that includes a session id or timestamp drops the hit rate to zero. Personalized responses must be private or fetched separately so they never poison the shared cache.

7.2 Pipeline: freshness, filtering, typos

OptionFreshnessCostVerdict
Daily batch onlyup to 24 hLowestMisses breaking news
Hourly batch only1 to 2 h24 full rebuilds a dayBetter, still too slow for trends
Stream updates written into the live triesecondsHigh; mutating a shared structure; spam can poison itRejected: breaks immutability, swap and rollback
Batch snapshot plus small streaming trending overlay5 to 15 min for trendsModerate; overlay is tinyChosen

Trending overlay: a stream job counts queries in 5 minute windows and compares the recent rate with the baseline from the batch data. Only queries passing every gate enter: minimum count, burst ratio (say above 5 times baseline), enough distinct users and IP prefixes (so one bot cannot fake a trend), and the blocklist. It holds a few thousand entries, is refreshed every minute or two on every suggest instance, and is merged with the trie list using a boost that decays over hours. Count-Min Sketch and Space-Saving track heavy hitters in bounded memory.

Ranking: score = w1*decayed_count + w2*CTR_when_suggested + w3*trend_boost + w4*quality_prior, computed offline so weights are tuned by experiments and changing them needs a rebuild, not a serving deploy.

Safety, layered: (1) learning time: blocklist, toxicity classifier, PII detectors (emails, phones, Luhn card check) keep bad queries out of the candidate set; (2) privacy threshold, e.g. at least 50 distinct users; (3) build-time second pass over final lists; (4) live blocklist applied in the merge step, propagating in under 2 minutes with targeted CDN purge: the emergency brake.

Personalization without breaking the cache: keep the global top-10 (plus trending) cacheable and the same for everyone in a locale. Fetch the user's recent queries separately (device or Redis, last 50 to 100) and merge them in the browser or aggregation layer with a boost and a history icon. Segment overlays (language, region, interest cluster) are cacheable per segment. A trie per user is never viable. This keeps about 95% of the work cacheable.

8. Scaling and bottlenecks

  • Reads: add replicas per shard; the trie is read-only so no coordination. Edge caching grows with traffic for free.
  • Hot prefix: caches absorb most repeats; least-outstanding-requests routing; add replicas to just that bucket.
  • Data growth: raise frequency or privacy thresholds, or cap prefix depth. At 400M candidates, memory is about 64 GB, which is when size-driven sharding becomes necessary.
  • Build: batch partitions by query hash, builder partitions by bucket, so 8 shard files build in parallel; an hourly build of 20 to 30 minutes is realistic.
  • Geography: each region has local replicas pulling the same snapshot via object-store replication; one pipeline builds.
  • 10x scale: 3.5M edge QPS, about 240 serving instances, 64 shards, about 160 GB index, incremental builds (only changed buckets), and a learned ranker on the top 50 candidates.
  • Biggest cost lever: cache hit rate. Each extra 10 points removes about 35,000 QPS from the origin.

10. Things to say to impress

Say: "The whole trie is only about 16 GB, so I shard for QPS and blast radius, not size, and I use hashed two-character buckets mapped by measured traffic, not first letter, because letter frequency is skewed."
Say: "Serving and building only meet at an immutable snapshot file. A pipeline outage makes suggestions stale, never down, and rollback is a pointer flip."
Say: "Most of the 100 ms is network, not the lookup, so browser cache, debounce, CDN and warm HTTP/2 matter more than micro-optimizing the trie."
Say: "Autocomplete appears to endorse what it shows, so I filter at learning time, build time, and serve time, with a live blocklist as the emergency brake and a distinct-user privacy threshold."
Say: "I would alert on product metrics (click-through, null-result rate), because a snapshot with broken ranking looks healthy on CPU and latency."
Common mistakes: computing top-K by scanning the subtree at query time; mutating the live trie from the stream; making personalized responses uncacheable; sharding by first letter; no live blocklist; forgetting stale-response handling on the client.

11. Q&A: follow-up questions

Why precompute the top-K list at every node instead of computing it at query time?

Without it, a short prefix like "a" forces a walk over millions of queries and a sort, so latency depends on data size and is worst for the most common requests. With precomputed lists, lookup is O(L) for prefix length L and reads one stored list, a few microseconds regardless of data volume. The cost is memory (K ids per node, about 12 GB here) and build time, both paid offline where they are cheap. Building is also efficient: each node's list is the merge of its children's lists, computed bottom-up in one pass.

How do you update the trie without downtime or serving a half-built structure?

Snapshots are immutable and versioned. The builder writes a complete file; each shard downloads it in the background, checks the checksum, the size change, and canary prefixes, loads it into a second memory region, and flips one atomic pointer. Requests already running finish on the old version, which is then freed. Rollback is flipping back while the old version is still in memory. We never change the live structure, so there are no locks on the read path.

How do you surface a breaking-news query within minutes if the trie is rebuilt hourly?

A stream job counts queries in 5 minute windows and compares them with baseline rates. Only queries with a strong burst ratio, a minimum count, and enough distinct users and networks enter a small trending overlay of a few thousand entries. Every suggest instance reloads it every minute or two and merges it with the trie result using a decaying boost. The base trie stays stable. If the stream job dies, overlay entries expire by TTL and we simply lose trends.

How do you prevent offensive or private suggestions, and what do you do when one slips through?

Defense is layered: blocklists, a toxicity classifier and PII detectors when learning; a privacy threshold (for example 50 distinct users) before a query is eligible; a second pass on final top-K lists at build time; and a live blocklist in the merge step. When one slips through, on-call adds it to the live blocklist, which reaches all instances in under 2 minutes, and purges the matching CDN keys. It is also removed from the learning set so the next build does not bring it back. Afterwards we find out why the classifier missed it. The key point is that the emergency brake does not wait for a rebuild.

Why shard by prefix bucket instead of replicating the whole trie everywhere?

At 16 GB replication is a valid start. Sharding wins on operations: smaller files load and swap faster, a hot bucket gets extra replicas without copying the whole index, a bad shard has a smaller blast radius, and growth in candidates needs no new hardware class. I avoid splitting by first character because letter frequency is skewed and differs by language. I hash the first two characters into thousands of buckets and assign buckets to shards using measured traffic. One-character prefixes come from a tiny replicated root table, so no request fans out to several shards.

How does the client decide when to call the server, and how do you handle out-of-order responses?

It debounces: a 100 to 150 ms timer restarts on every keystroke and the request is sent only when typing pauses, so a 20-character query makes about 6 requests instead of 20. Each request has an increasing sequence number, and the client drops any response older than the one already shown and aborts older in-flight requests. It also keeps a prefix-to-results map for backspace and retyping, and remembers dead prefixes so it does not call the server for anything that extends a prefix with no results.

How would you add personalization without making responses uncacheable?

Split the response. The global top-10 plus trending is cacheable at browser and CDN and is the same for everyone in a locale. The personal part, the user's recent queries matching the prefix, comes from the device or a small per-user store and is merged on the client or at the aggregation layer with a boost and a history marker. For deeper personalization, use a limited number of segment overlays (language, region, interest cluster), which are cacheable per segment. A trie per user would mean millions of copies of mostly identical data.

Redis sorted sets look simpler. Why not use them?

They are a good first version and I would ship them for a smaller product. At our scale, each query is written under every one of its prefixes, so writes multiply by query length, and memory is about 5 times a compact trie (roughly 75 GB against 16 GB). Trimming each key to the top 10 throws information away, so an item that drops out cannot come back without recomputation, and there is no clean atomic swap or rollback of the whole index. Their strengths are real-time increments and easy sharding, which is why I would keep Redis for user history and maybe the trending overlay.

How do you support typos without slowing every lookup?

The hot path stays an exact trie lookup. When it returns fewer than about 3 results, we fall back, under a strict time budget, to a corrected prefix. The cheapest fallback is a table of learned aliases mined from sessions where users searched a misspelling and then the right phrase, which costs nothing at serve time. Next is a bounded edit-distance walk (one edit, prefix of at least 3 to 4 characters). Only if both fail do we ask Elasticsearch with fuzziness. Since most keystrokes find exact matches, the extra cost hits a small share of requests.

What happens in the first seconds after a snapshot swap, when caches are cold?

We pre-warm: after loading and before the flip, the process touches the memory pages of the most frequent prefixes (known from the logs), so the first real requests do not take page faults. Swaps are staggered with jitter so not every replica changes at once, and the CDN and local caches keep serving older answers until their TTL ends, which smooths the change. The first replica is a canary; if its errors or latency rise, the rollout stops and rolls back automatically.

Production incident: p99 latency suddenly doubles. What do you check?

First split client-observed latency from server-side latency. If only the client number rose, look at the edge: did the cache hit rate fall (a key change, a purge, or an edge problem) and push load to the origin? If server-side rose, check whether a snapshot swap just happened (cold pages, garbage-collection pauses), whether one replica is slow and hedging is not firing, and whether history lookups became serial. I would roll back the latest snapshot or deploy first since it is cheap and fast, then dig into per-shard and per-bucket graphs to find a hot prefix. Extra replicas for a hot bucket are a quick relief.

Click-through on suggestions drops 10% but all system dashboards are green. Why, and what do you do?

This is the case for product metrics: a snapshot can load fine and serve fast yet carry broken ranking, for example a bad weight, a wrong decay, or a filter that removed popular queries. Compare null-result rate and top suggestions for a set of canary prefixes between the current and previous versions, and check the size delta. If the new snapshot looks wrong, flip the pointer back to the previous one, which takes seconds, then debug the pipeline offline. Going forward, add the click-through drop as an alert and as a gate in staged rollout.
