Case sheet 17: Design a Message Queue (Kafka-class log)

One-page cheat sheet: a distributed log at 1 million messages per second. Full walk-through: Handbook case study 17.

1 Problem2 Requirements3 Estimation4 API5 Data6 Architecture7 Deep dives8 Scaling9 Failures10 Impress11 Q&A12 Links

1. Problem in 3 lines and clarifying questions

Problem: build a shared platform where producers publish messages and consumers read them, at very high speed, and a message we have said "got it" to is never lost. We build a Kafka-class log from an empty page: how a broker stores data, how partitions and copies give speed and safety, how consumers share work and remember their place, and what happens when machines die.

2. Requirements

Functional

  • Topics (named streams) split into partitions
  • Producers append key, value, headers; partition chosen by key hash or round robin
  • Consumers read in order from any offset (the position number)
  • Consumer groups: each partition read by one member of a group
  • Commit offsets so a restart resumes
  • Retention by time or size; log compaction
  • Opt-in idempotent producer and transactions

Non-functional

  • 1M msg/s (1 GB/s) peak, scale by adding machines
  • No loss of acknowledged data on one broker failure
  • Partition writable after a seconds-long failover
  • Milliseconds latency when batching is tuned; throughput is the main goal
  • Add brokers and partitions with no downtime

Out of scope

  • Per-message priority, delayed delivery
  • Broker-side filtering, SQL layer
  • Cross-region active/active
  • Stream-processing engine

4. API

Produce(topic, [records], acks = 0|1|all, producerId, epoch, baseSequence, txnId?)
  record = {key, value, headers, timestamp};  reply per partition = {baseOffset, error}
Fetch(topic, partition, fetchOffset, maxBytes, maxWaitMs, minBytes) -> {highWatermark, records[]}
JoinGroup / Heartbeat / CommitOffset(group, topic, partition, offset, generation)
CreateTopic(name, partitions, replicationFactor, configs);  Metadata(topics) -> leader, epoch, replicas, isr
  • Records go in batches per partition. The batch is the unit we compress, check, replicate and write.
  • Consumers pull with long polling (the broker waits until enough data arrives). A slow reader just falls behind safely and controls its own speed.
  • Clients cache metadata and talk straight to the partition leader. No central router in the data path.

5. Data model and store choices

DataStoreReason
Message payloadsPer-partition segment files on broker disksSequential IO, page cache, zero copy
Cluster metadata (topics, leaders, ISR, configs)Replicated log run by a Raft quorum of 3 or 5 controller nodesSmall, strongly consistent, rarely changes
Consumer offsetsInternal compacted topic __consumer_offsetsReuses the log: durable, replicated, latest value wins
Transaction stateInternal compacted topic __transaction_stateSame trick
Old segmentsObject store (tiered storage)Cheap cold storage
  • Why an append-only log: we only append at the end, read a range, and delete from the front. A B-tree pays for in-place updates we never do; an LSM sorts by key, which we do not need. An append-only file is the simplest and fastest. Deleting is dropping whole files.
  • Segments: a partition is a folder of files named by their first offset. Only the newest (active) one is written; at 1 GB it rolls. Old segments never change. Files: .log (records), .index (offset to file position), .timeindex.
  • Sparse index: one entry per about 4 KB. Find the segment by file name, binary search the index, scan forward a few KB.
  • Page cache, no fsync per write: the broker writes through the OS cache. Safety comes from copies on other machines, not from flushing each write. No private heap cache, so no double caching and no big GC pauses.
  • Zero copy: disk format equals wire format, so sendfile moves pages from cache to the network card. TLS breaks this (plan about 2x CPU).
  • Batch format: baseOffset, length, leaderEpoch, CRC, compression flag, producerId/epoch/sequence, records. Brokers store and forward batches still compressed (often 2x to 5x saving).

6. Architecture and main flows

Start simple, then fix three failures. One server, one log file works (replay, many readers). It fails because (1) one writer and disk cap speed: split into partitions over many brokers; (2) the machine dies: replicate each partition with one elected leader; (3) workers need to share work: consumer groups assign each partition to one member and store offsets.

Produce flow with acks=all

  1. Producer sends a compressed batch to the partition leader (found from cached metadata).
  2. Leader checks permission, quota and idempotence sequence, assigns offsets, appends to the active segment (page cache).
  3. Followers already have long-poll fetches waiting; the new data completes them and they append it.
  4. A follower's next fetch carries the new offset, which tells the leader it is caught up (that fetch is the ack).
  5. When every member of the in-sync replica set (ISR) has it, the leader moves the high watermark forward. Consumers see only data below it.
  6. With acks=all the leader now answers the producer.
acksSuccess whenLoss windowUse
0Bytes handed to networkAny failure loses silentlyMetrics
1Leader appendedLeader dies before followers fetchLogs, lowest latency
allAll ISR have it and ISR size at least min.insync.replicasNone while one ISR member survivesBusiness events
  • Producer batching: send when the batch hits about 64 KB or has waited linger.ms (about 5 ms). Big throughput gain for a few ms of delay, and compression works better. Keep up to 5 requests in flight.
  • Partitioning: hash(key) mod N keeps one key in one partition. No key: sticky (fill one batch, then move on).
  • RF 3 with min ISR 2: one broker may fail with no loss and no write outage. Two down: writes are rejected (consistency over availability).

7. Deep dives

7.1 Replication: ISR versus majority quorum

PropertyMajority quorum (Raft style)ISR (wait for all in-sync)
Copies to survive f failures2f + 1f + 1
Write latencyMedian replica, slow minority ignoredSlowest ISR member, but a slow one is dropped from the ISR after about 30 s
Storage costHigherLower, matters at petabytes
ElectionBuilt into the algorithmAny ISR member is safe; the controller picks, so a metadata quorum is needed

Choice: ISR. At 0.9 PB the copy count is the cost driver, and f + 1 copies is cheaper than 2f + 1. Consensus runs only on rare metadata changes, so the data path stays cheap.

  • High watermark (HW) is the highest offset on all ISR members; log end offset (LEO) is what one replica has. A crashed leader's extra tail (above HW) is cut off when it returns.
  • Leader epoch is a counter bumped on every leader change and stamped on batches. A returning replica asks "where did epoch N end?" and truncates there. This avoids silent divergence after quick double failovers.
  • Controller failover: broker session (about 10 s) expires; controller picks the first live ISR replica, bumps the epoch, writes one metadata record per partition. Clients get NotLeader, refresh and retry. Thousands of leaders move in seconds.
  • Unclean election: if all ISR members are gone, either wait (clean only: safe, partition offline) or promote an out-of-date replica (available, silently loses messages). Default: clean only, min ISR 2, acks=all for tier-1 topics. Unclean is fine for metrics and clicks.

7.2 Consumer groups, offsets and delivery guarantees

  • A group shares a group id. Each partition has exactly one owner in the group, so parallelism is capped by partition count (600). Another group gets its own full copy: this is how fan-out works.
  • The group coordinator is the broker leading the __consumer_offsets partition that the group id hashes to. No new component, automatic failover.
  • Rebalance (join, leave, missed heartbeat, slow poll loop, partition change): bump generation, JoinGroup, leader member assigns, SyncGroup. The generation number fences old members, so a stale consumer cannot commit.
  • Reduce pain: cooperative rebalancing (only moved partitions pause), static membership (quick restart keeps partitions), sticky assignor, short poll loop.
Commit styleCrash in betweenResult
Commit, then processMarked done, not doneAt-most-once (loss)
Process, then commitDone, not marked; redoneAt-least-once (duplicates). Default.
Process and commit atomically (same DB transaction or Kafka transaction)Both or neitherExactly-once effect
  • Idempotent producer: broker gives a producerId; the producer numbers batches per partition. The leader remembers the last 5 sequences, so a retried batch gets the old offset back and is not appended again. A gap raises an error, which also keeps order under retries. Scope: one producer session, one partition.
  • Transactions: InitProducerId (bumps epoch, fences old instance), AddPartitions, produce, SendOffsetsToTransaction, EndTxn; coordinator logs PREPARE_COMMIT (the decision point), then writes commit markers to every partition. read_committed readers stop at the last stable offset and skip aborted records. Batch commits (about every 100 ms).
  • "Exactly-once" holds only inside the system (topics and offsets). Emails, HTTP calls and outside databases need idempotent handlers or an outbox.
Trap: saying "Kafka gives exactly-once" with no qualifier. Say: at-least-once delivery plus idempotent processing gives an exactly-once effect; transactions cover topic to topic only.

7.3 Retention, compaction, ordering

OptionKeepsCostUse for
Delete by time or sizeEverything in the windowNear zero (drop whole segments)Event streams, logs, clicks
CompactionLatest value per key, foreverRewrite IO, cleaner CPU and memory (about 24 B per key)Changelogs, config, offsets
BothLatest per key inside a windowBothExpiring state

Choice: delete by 7 days for events; compaction for state topics. A delete is a null-value record (tombstone), kept for delete.retention.ms so slow readers see it.

  • Retention drops only closed segments whose newest record expired. A quiet partition can hold older data, so roll segments at least daily.
  • Order exists only inside a partition. Changing partitions from 600 to 900 changes hash mod N and breaks per-key order across the change, so over-provision up front.
  • Hot key (say 30% of traffic) pins one partition: salt the key when strict order is not needed, or give the tenant its own topic.
  • Process each partition on one thread, or dispatch by key, otherwise handlers reorder.

10. Things to say to impress

  • "Speed comes from sequential IO, the page cache, batching, compression and zero copy. Disks are slow at seeking, not at streaming."
  • "Durability is replication, not fsync: acks=all, min ISR 2, election only from the ISR, epoch truncation, and a Raft controller against split brain."
  • "The log is also the database for its own state: offsets and transaction state are just compacted topics, so they get replication and failover for free."
  • "ISR needs f + 1 copies, majority quorum needs 2f + 1. At petabytes that matters, and consensus is only on the rare metadata path."
  • "Exactly-once only holds inside the system boundary. Outside it, idempotent consumers."
  • "Partition count is a one-way door for keyed topics, so I over-provision."
  • "Durability limit: if a whole region loses power, unflushed cache on all three copies can be lost. Use periodic flush or cross-region mirroring when that matters."
  • "At 10x (10M/s) I would use about 300 brokers, cells per domain to limit blast radius, and mandatory tiered storage."
  • Phasing: single node log, then partitions plus ISR plus controller, then groups, retention, compaction, then idempotence, transactions, quotas, then tiering and mirroring.
  • Not chosen: Raft per partition (3 copies and thousands of groups), heap cache (duplicates page cache), push delivery (no natural batching), all-in-object-store (hundreds of ms write latency), global order (one partition, about 10 MB/s).

11. Interview Q&A

Why is this storage fast when "disk is slow"?

Disks are slow at seeking, not at streaming. We only append to the end of a file and read forward, so drives do large sequential transfers at hundreds of MB/s. The OS page cache holds the recent tail, so readers who keep up never touch the disk. Producer batching and compression turn many small messages into big writes. Because the on-disk format equals the wire format, sendfile moves bytes from cache to the network card without copying through the application. Our 1 GB/s needs about 30 machines mostly for capacity, not because any piece is slow.

A producer times out on an acks=all send. Was the message written? What do you do?

You cannot know. The leader may have appended and replicated it with the reply lost, or the request may never have arrived. Retry, and make the retry safe with the idempotent producer: the producer id and sequence number let the leader spot a duplicate and return the original offset instead of appending again. Without it, retries create duplicates and the consumer needs a dedup key. Use bounded exponential backoff with jitter and an overall delivery timeout so a long outage fails loudly.

What guarantees an acknowledged message survives a leader crash?

Three rules together. First, with acks=all the leader answers only after every in-sync replica has the batch and the ISR holds at least min.insync.replicas (2), so the data is on two machines in different zones. Second, a new leader is chosen only from the ISR, so it has all committed data. Third, the old leader's uncommitted tail is truncated on return, using leader epochs. Break any rule (acks=1, unclean election, min ISR 1) and you reopen a loss window.

How do you choose the number of partitions, and what breaks if you pick badly?

Take the larger of target throughput over per-partition throughput (1 GB/s over 10 MB/s is 100) and the consumer parallelism you will need (200 consumers at 5 MB/s is 200), then add headroom: 600 for the big topic. Too few caps throughput and consumer scale. Too many costs open files, index memory, replication overhead, slower failover (each partition needs an election), and more latency from smaller batches. For keyed topics the count is hard to change later because hash mod N reshuffles keys, so I over-provision up front.

Explain a consumer rebalance and how to reduce its impact.

When a member joins, leaves or stops heartbeating, the coordinator bumps the generation and members run JoinGroup and SyncGroup to get a new assignment. With the eager protocol everyone stops during this, so a rolling deploy of 200 consumers causes 200 stalls. I would use cooperative rebalancing so only moved partitions pause, static membership so a quick restart keeps its partitions, a sticky assignor, and a session timeout longer than a typical restart. I would also keep the poll loop short so slow work is not mistaken for a dead consumer.

How would you provide exactly-once?

I would not claim it end to end. Inside the system you combine the idempotent producer (no retry duplicates), transactions (output and consumer offsets commit atomically, with transactional id fencing to kill zombie instances) and read_committed consumers. That gives exactly-once for consume, transform, produce between topics. For an outside effect like a database row or email, the sink must join the same transaction (store the offset in the same DB transaction) or be idempotent with a dedup key. The honest answer is at-least-once plus idempotent processing.

Compaction or time-based retention?

Compaction when the topic holds latest state per key and new readers must rebuild it, like profiles, config or the offsets topic. Time retention would delete a key that just did not change in 7 days, which is wrong. Time retention fits events, where each record is a fact and the replay window matters. Compaction costs rewrite IO and memory for the key map, loses intermediate history, and needs tombstones kept long enough for slow readers to see deletes.

Why a log instead of an SQS-style queue, and when is the opposite right?

The log keeps one integer per group and partition rather than state per message. That is why it reaches millions per second, supports replay by resetting an offset, and lets many groups read at no extra write cost. The price is head-of-line blocking per partition, parallelism capped by partitions, and no native delay or per-message retry. A per-message queue is right for a task pool: independent jobs of uneven length, elastic workers, retry counts and dead-lettering per message, no need for order or replay. Many platforms run both.

A partition is offline and the business wants it back now. Options and risks?

First check whether an ISR member is only slow or restarting; waiting is the safe path and keeps all committed data. If the ISR replicas are truly gone, enable unclean leader election for that topic and promote an out-of-date replica. That restores availability at once but permanently loses messages it lacked, may leave committed consumer offsets beyond the new end of log, and can change history that downstream systems saw. It is a per-topic business call: wait for payments, promote for clickstream. Afterwards I would find out why the ISR shrank to one.

Production incident: consumer lag keeps growing. What do you do?

First, find out whether it is all partitions or a few. All partitions means consumers are too slow or down: check handler time, downstream dependency, and rebalance rate (a loop of rebalances makes zero progress). A few partitions means a hot key or a poison message stuck on one partition. Add consumers only up to the partition count. Send poison records to a dead-letter topic and commit past them. Watch lag against retention: if it nears 7 days, extend retention temporarily so data is not deleted unread.

Under-replicated partitions alert fires. What do you check?

It means some follower fell out of the ISR, so the safety margin is smaller. Check whether one broker is common to all the alerts: a dead or slow broker, a bad disk (disk await), a long GC pause, or a saturated network. If it is one broker, fix or replace it; it will truncate, catch up and rejoin. If it is cluster-wide, suspect a reassignment eating bandwidth (lower the throttle) or overload. Meanwhile, with min ISR 2 and RF 3, writes still work; a second loss would stop writes.

How do you keep one noisy tenant from hurting others?

Per-client quotas on produce bytes, fetch bytes and request-handler time, enforced by delaying replies rather than rejecting, so well-behaved clients just see slower calls and no retry storm. Also caps on partitions and connections, ACLs scoped to topic prefixes, and a dedicated cluster for huge or critical tenants. Quotas are per broker, so the cluster-wide limit is that value times the brokers the tenant touches. Per-tenant bytes and throttle time show who is hitting limits before others notice.

How does tiered storage change recovery and consumers?

With only about 6 hours local, a replacement broker copies about 1 TB instead of 30 TB, so recovery and expansion go from days to under an hour, and the time with a reduced ISR is much shorter. Tail consumers see no change. Replaying consumers are served from the object store with a higher first-byte latency, and they do not push hot data out of the page cache. Risks: extra dependency on the object store, request fees, and trouble with compacted topics, which are often kept local.

Why pull and not push delivery?

With push the broker must know each consumer's speed and can flood a slow one. Pull moves flow control to the reader: a slow consumer just falls behind and the disk holds the backlog. Pull also makes batching natural, since the reader asks for up to a number of bytes, and long polling avoids empty spinning. Replay is simply asking for an older offset.
