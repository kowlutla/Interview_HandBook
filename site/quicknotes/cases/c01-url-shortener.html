Case sheet: Design a URL Shortener

One-page revision of Handbook Case Study 1 (bit.ly / TinyURL style). Same numbers as the handbook.

1. Problem in 3 lines

One line: turn a long web address into a short one, then send anyone who opens the short one to the long one, fast, forever, and count the clicks.
  • Two actions: create (long URL in, short code out, e.g. sho.rt/aZ3k9Qb) and redirect (short code in, send the browser to the long URL).
  • It looks easy. The hard parts are: unique codes at scale, the redirect status code, a cache-heavy read path, counting clicks off the hot path, and abuse.
  • Reads dominate: about 100 redirects for every creation.

2. Requirements Ch 01

Functional

  • Create a short link (optional alias, expiry, owner)
  • Redirect fast
  • Custom alias if free and valid
  • Expire or delete (then 404 or 410)
  • Analytics: totals and breakdowns
  • Abuse: blocklist, rate limit, takedown

Non-functional

  • Redirect p99 under 50 ms in the data center
  • 99.99% available (about 52 minutes of downtime a year)
  • Durable: an issued link is never lost or re-pointed
  • Scale 10x by adding machines
  • Codes unique, always
  • Analytics may lag a minute (eventual)

Out of scope

  • Web front end, accounts, billing
  • Link-in-bio, A/B destinations, QR codes
  • Custom-domain onboarding (mention only)
  • Building the phishing classifier (we call one)

4. API Ch 05

POST /v1/links          (Idempotency-Key header recommended)

GET    /v1/links/{code}              metadata
DELETE /v1/links/{code}              204, link now returns 410
GET    /v1/links/{code}/stats?from=&to=&granularity=day

The Idempotency-Key lets a client retry after a timeout without getting two codes. The server keeps key to code for 24 hours (Ch 32).

6. Architecture and request flows

Why split read and create? Load is 100 to 1, and the redirect path must not depend on the allocator, safety checker, or analytics being healthy. If Kafka is down, redirects work. If the allocator is down, old links still resolve.

Create a link (steps)

  1. Authenticate and rate limit (Ch 16).
  2. Validate URL: http or https only, at most 2,048 characters, not pointing at ourselves.
  3. Ask the safety checker (blocklist, threat lists).
  4. Alias given? Use it. Otherwise take the next number from the local range and encode as base62.
  5. Conditional insert "if code does not exist". Alias taken gives 409; a rare collision retries.
  6. Return 201. Optionally prime the cache so the first click is a hit.

Follow a link (steps)

  1. Check the code matches [A-Za-z0-9_-]{1,16}. Garbage never touches a store.
  2. Look in a tiny in-process cache (hottest few thousand codes, a few seconds).
  3. Look in Redis. On a miss read the store; if not found, write a 30 to 60 second negative cache entry.
  4. Expired or deleted gives 410; abuse-disabled gives a warning page or 451/404.
  5. Publish the click event (best effort), return the redirect.

7a. Deep dive 1: generating unique codes Ch 32

One line: encode a number in base62 (0-9, a-z, A-Z) so 7 characters cover 3.52 trillion codes. The question is where the number comes from.
ApproachUnique?CoordinationLengthGuessable?Main risk
A. Counter ranges + permutationYes, by construction1 allocator call per 1,000 links7No, after permutationAllocator losing state
B. Hash of long URLProbably; check on insertNone, conditional writes7NoCollisions start after about 1 to 2 million links (birthday bound)
C. Random 42 bits + retryProbably; check on insertNone, conditional writes7NoRetry rate grows as space fills (0.17% at 6 billion)
D. Snowflake 64-bit IDYesUnique machine ids only11Partly (time-ordered)Clock skew; code too long

Choice: A. Uniqueness is structural, so collisions (hard to debug, rare) cannot happen. Crash with 600 unused numbers? They are lost, which is fine: 1,000 per crash out of 3.5 trillion. Allocator down? Servers keep using their block (make blocks 10,000 to ride out longer). Persist the advanced next_free before handing out a block, and replicate it (Ch 29).

Guessability fix: sequential numbers give sequential codes that anyone can walk through. Apply a keyed reversible permutation (a small Feistel cipher over the 42-bit space) before encoding. Because it is one-to-one, uniqueness is kept and codes look random.

Custom aliases: generated codes are exactly 7 base62 characters. Aliases are 3 to 30 characters from [a-z0-9-] and may not be exactly 7 pure base62 characters. Reserved words (api, admin, login) are rejected. Store aliases lowercase. The conditional insert gives one winner and one 409 when two people race.

Trap: read-then-insert ("is it free? yes, insert") has a race where two creators both see free. Always use one atomic conditional insert.

7b. Deep dive 2: 301 versus 302, and caching Ch 13

Concern301 Moved Permanently302 Found (temporary)
Server loadLower: browsers remember it and skip usHigher: every click arrives
AnalyticsUndercounts repeat clicksAccurate
Change or disableHard: cached for months, cannot be revokedEasy: next click sees the change
Expiry and abuse takedownCached copies outlive themWorks within seconds
Search rankingPasses it to the destinationNot treated as permanent

Choice: default 302 with Cache-Control: private, max-age=0, because analytics, expiry, and takedown are requirements. Allow 301 as an owner opt-in with a finite max-age (such as one day). If the product were pure permanent vanity links with no analytics, 301 would win.

Caching the hot path, three layers

LayerDetailWhy
In-process LRUabout 10,000 entries, 5 to 30 s TTLA viral link at 50,000/s over 20 instances is 2,500/s each, which becomes one Redis read per TTL per instance. Protects a hot Redis shard.
Redis, cache-asidekey l:{code}, TTL 24 h plus or minus 10% jitter, allkeys-lru, about 20 GB (Ch 15)Jitter stops entries made together from expiring together. TTL is the lesser of 24 h and time left to expiry.
CDN (optional)301 links and 302 links marked cacheable for 60 s (Ch 12)Lowest global latency, but slower revocation and click counts must come from edge logs.

Stampede

  • Hot entry expires, 5,000 requests miss at once
  • Fix: coalesce (one DB read per code per instance), jitter, refresh-ahead for the hottest

Penetration

  • Scanners ask for random fake codes
  • Fix: pattern check, negative cache 30 to 60 s, Bloom filter of existing codes (Ch 57)

Stale after change

  • Update DB first, then delete Redis key and publish an invalidation
  • A missed message is bounded by the 30 s local TTL
  • Abuse denylist is pushed at once

Expiry: checked at read time; cleanup is lazy plus a sweeper job (rows expired over 30 days). Never reuse old codes: an old printed link would silently open someone else's page.

7c. Deep dive 3: click analytics off the hot path Ch 37

ApproachProsCons
Increment a column on the link rowTrivialWrite per click on the hot path, hot row, no breakdowns
Redis counters onlyFast totalsNo breakdowns, loss on failure, no history
Kafka events + stream aggregationOff hot path, replayable, any breakdownMore parts, eventual, bots and duplicates
Batch parse of CDN or LB logsNo service code; sees edge hitsHours of delay, fewer fields

Choice: Kafka pipeline plus Redis INCR for the instant "total clicks" number, plus a nightly batch as the safety net. Kafka is at-least-once, so dedupe by event id. If Kafka is unreachable, buffer a bounded number of events then drop: lose a few clicks, never fail a redirect. Hot partition from a viral link: key by code + bucket (0 to 7) and sum later, or pre-aggregate per instance and flush a delta each second (20,000 events/s becomes about 1,000 deltas/s). Hash the IP; do not keep raw IPs.

8. Scaling and bottlenecks Ch 25

AreaHow we scale it
Stateless servicesAdd instances behind the load balancer. About 2,000 req/s per instance means 10 for peak; run 20 to 30 for failures and deploys (about 30 redirect, 6 create).
Link storeShard by a hash of the code into 4,096 logical slots over 16 nodes. Lookups are always by code, so every redirect is a one-shard read. Permuted codes look random, so data spreads evenly. Adding a node moves whole slots, with no mass rehash.
ReplicasOne leader and two followers per shard. Misses may read followers because rows never change except status; the abuse path reads the leader.
"My links"Separate table by owner id, updated async, with a repair job.
Hot keyViral link: in-process cache, Redis replicas, optional CDN. Writes are never hot, since every link is written once.
Create burstsPer-owner token bucket; allocation is local so bursts are cheap.
Multi-regionReplicate rows everywhere asynchronously. Each region gets disjoint ID blocks, so no two regions mint the same code. Aliases need one owning region (hash of alias) or a strongly consistent store. A local miss on a fresh link falls back once to the code's home region (Ch 26).
10x scale1 billion links a month, 200,000 peak reads/s: cache about 200 GB, store about 30 TB over 64+ nodes, 7 characters still enough (1.7% fill), hundreds of Kafka partitions, local pre-aggregation mandatory.
Build order: phase 1 one region, SQL, random codes, 302, Redis. Phase 2 split services, allocator, Kafka, blocklist. Phase 3 shard, in-process cache, Bloom filter. Phase 4 multi-region, custom domains, SLO dashboards.

9. Failure modes Ch 40

What failsWhat happensFix
Redis cacheReads fall to the store (5% up to 100%); latency risesReplicas and failover, load shedding, 20 ms client timeout then fall through, local caches soften it. Size the store for the miss rate, and protect it with connection limits.
Link store shardThat shard's misses and writes fail; cached links still workLeader plus two followers, auto failover, serve stale cache beyond TTL (stale-if-error).
ID allocatorCreates continue from local blocks, then return 5033-node consensus, large blocks, persist before hand-out, alert if latency over 1 s. If state is lost, numbers could be reissued.
KafkaRedirects unaffected; events buffered then dropped; duplicatesAsync, bounded buffer, dedupe by event id, count drops as a metric.
Safety checkerCreates blocked or unchecked; false positivesFail open for trusted users with a re-scan, fail closed for anonymous, appeal path.
Redirect instanceSlow instance hurts p99; bad deploy returns wrong URLHealth checks, outlier ejection, canary deploys with auto rollback.
Whole regionTraffic shifts by DNS or anycast; newest links may be missingRequire a second-region acknowledgment on create (adds 50 to 150 ms; acceptable).

Consistency rules: the destination is write-once (edits create a new version and invalidate caches), which makes caching and replication safe. Only status is mutable, with 30 to 60 s staleness allowed, except the pushed abuse denylist. Idempotency key and link are written on the same shard (or key first with a pending state).

SLOs: redirect success 99.99% (alert at 14x burn in 1 hour); p99 under 50 ms (alert above 100 ms for 5 min); create 99.9%; cache hit above 95% (alert below 90%); analytics visible within 2 minutes for 95% of clicks.

10. Things to say to impress (senior and lead level)

Say: "Uniqueness by construction beats uniqueness by collision handling. Leased counter ranges plus a keyed permutation give collision-free, non-enumerable codes, and the conditional insert is only a safety net."
Say: "The redirect path has no dependency on the allocator, the safety checker, or analytics. Each can be down and redirects still work."
Say: "302 is a product decision, not a technical one: analytics, expiry and takedown need every click to reach us. 301 is an opt-in."
Say: "The link row is write-once, which is why aggressive caching and multi-region replication are safe. The only hard multi-region case is custom aliases, where I pick consistency over latency."
  • Size the store for the cache miss rate (5%) and then explain what happens if the cache dies (100%): load shedding and local caches.
  • Name the three cache attacks (stampede, penetration, hot key) and one fix each.
  • Never reuse codes; analytics may drop clicks, redirects may not fail; takedown pushes a denylist in seconds.
  • Cost: the biggest bill is analytics (70 GB a day), so sample, aggregate early, and keep raw files only 30 to 90 days.
Trap: spending 20 minutes on base62 maths and none on caching, analytics, or abuse. Show the numbers, then spend time on the three deep dives.

Abuse and security in brief Ch 55

  • At creation: check threat lists, reject private IPs, localhost and our own domain, CAPTCHA or account after a threshold, rate limits per account and IP.
  • After creation: re-scan destinations (pages can turn bad later); disable plus denylist push gives a warning page or 451/404 in seconds.
  • Interstitial and preview: warn for new or low-reputation links; a + suffix shows the destination without following it.
  • Header safety: only http and https schemes, never javascript: or data:; reject newlines in the URL to stop response splitting.
  • Privacy: 404 rate limiting stops harvesting; sensitive links get longer random codes (12 characters) and optional passwords.

11. Q&A: follow-ups an interviewer asks

Why not just use an auto-increment column and encode it? What goes wrong at scale?

One auto-increment works until you have many writers or shards. Then it is a single point of failure and a bottleneck, and it gives sequential codes anyone can walk through to find private links. I keep the counter idea but lease ranges of 1,000 numbers to each create server, so the central allocator is touched about once per thousand links. Before encoding I run a keyed one-to-one permutation so codes look random. Ranges never overlap, so uniqueness is guaranteed without any collision checks.

How many characters do you need, and how did you decide?

We expect 6 billion links in five years. Base62 with 6 characters gives about 56.8 billion codes and with 7 gives about 3.52 trillion. Six would technically fit but would be about 10% full, which makes random schemes retry often and leaves no room for growth or aliases. Seven keeps the fill near 0.17% and survives a 10x growth (1.7% fill) for the price of one extra character.

Why 302 and not 301? When would you pick 301?

A 301 can be cached for a very long time by browsers and middle boxes, so repeat clicks never reach us. That hides clicks from analytics and means we cannot expire, change, or disable the link for anyone who already cached it. Since analytics, expiry and takedown are requirements, 302 is the default with max-age 0. For a permanent vanity link with no analytics need, 301 cuts load and passes search ranking, so I allow it as an owner opt-in with a finite max-age such as a day.

One link goes viral at 100,000 requests per second. What breaks and how do you protect it?

The risk is one hot key: all requests hit one Redis shard, and when the entry expires a stampede hits the database. I defend in layers. Each redirect instance has a small in-process cache with a short TTL, which turns the flood into a handful of Redis reads. Redis keys get jittered TTLs and request coalescing, so one fetch per instance refills an expired key. For known hot links I can copy the key to several cache nodes, and opted-in links can be served from the CDN edge.

How do you count clicks without slowing redirects or losing accuracy?

The redirect appends an event to Kafka asynchronously and returns at once. A stream job drops duplicates by event id, adds country and device, and writes windowed counts to an analytics store, while raw events go to object storage so a nightly batch can recompute. If Kafka is unreachable the service buffers a bounded number of events and then drops them, because losing a few clicks is better than failing redirects. Dashboards are eventually consistent, usually within a minute or two, and we say so.

How do you handle custom aliases that could collide with generated codes or each other?

We separate the namespaces by format. Generated codes are exactly seven base62 characters. Aliases are 3 to 30 characters of lowercase letters, digits and hyphens, and may not be exactly seven pure base62 characters. Reserved words are rejected. The insert is conditional, so when two people race for one alias exactly one wins and the other gets 409. Across regions, alias claims go to one owning region (chosen by hashing the alias) or a strongly consistent store, since async replication could accept both.

How do you shard the link store, and what about the "list my links" query?

I partition by a hash of the code into 4,096 logical slots mapped to about 16 nodes. Redirects look up by code, so each is a single-shard read with an even spread. Adding capacity moves whole slots, not every key. Listing by owner would otherwise hit every shard, so I keep a second table partitioned by owner id with the owner's codes, filled asynchronously on create, with a repair job for any missed update.

Hash the URL or use a counter: defend each.

Hashing gives free deduplication and needs no coordinator, but collisions are probabilistic and appear after only a couple of million links in a 42-bit space (birthday bound). So every insert needs a conditional write and retry logic. A counter with leased ranges makes uniqueness structural, needs one tiny coordinator touched rarely, and keeps codes short, but needs a permutation to stop enumeration and an extra index if we want dedupe. I choose the counter, because rare collisions are expensive bugs and construction removes the whole class.

Cache hit ratio suddenly drops from 97% to 70%. What do you do?

First I check what changed: a deploy, a Redis failover or restart (cold cache), or an eviction spike because memory is full. Then I look at the 404 rate per source IP, since a scanner hitting random codes causes penetration; the fix is the pattern check, negative caching and a Bloom filter. I also look for TTL changes that made many entries expire together. Meanwhile I protect the database with load shedding and connection limits, and warm the cache from the hottest keys if it was a restart.

How do you stop the service being used for phishing and malware?

At creation we check the destination against threat lists and blocklists, reject private addresses and loops, and rate limit by account and IP, with a CAPTCHA for anonymous users. After creation we rescan destinations, because a page can turn bad later. Disabling a link pushes to a denylist that every redirect instance checks, so takedown takes seconds. Using 302 matters here: browsers do not cache the redirect, so the block applies on the next click. New or low-reputation links can show a preview page first.

A region goes down. What happens, and how do you avoid false 404s for new links?

DNS or anycast steers traffic to another region. That region already has every link replicated up to the replication lag, so redirects continue. A link created seconds before the failure may be missing, so creation can wait for a second-region acknowledgment, which adds 50 to 150 ms to a path that is not latency critical. For a link created in one region and clicked in another before replication arrives, a local miss falls back once to the code's home region (the code identifies it) and the answer is cached.

The allocator is down. Can users still create links?

Yes, for a while. Each create server holds a block in memory, so with 1,000 numbers and 200 creations per second across the fleet each server has well over 25 seconds of headroom; a block of 10,000 rides out longer outages. Redirects are not affected at all, since they never call the allocator. We alert if allocator latency passes 1 second or the remaining range falls below about 10 minutes. The real danger is the allocator losing state and reissuing numbers, so it runs on a replicated consensus store and persists the new next_free before handing out a block.

Redis dies completely. What does the database see?

Up to 100% of reads instead of 5%, which is about 20,000 per second at peak. Local in-process caches absorb a large share, especially for hot links. We shed load and cap connections to the store so it does not collapse, use short client timeouts (20 ms) before falling through, and may serve stale entries (stale-if-error). Redis runs with replicas and automatic failover, so a full loss is rare. Afterwards we warm the cache gradually so we do not stampede the store.
