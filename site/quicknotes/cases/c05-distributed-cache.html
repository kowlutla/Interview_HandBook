Case Sheet 05: Design a Distributed Cache

A shared in-memory cache (Memcached or Redis Cluster style) that holds about a billion hot objects so the databases see only a small part of the traffic.

1 Problem · 2 Requirements · 3 Estimation · 4 API · 5 Data model · 6 Architecture · 7 Deep dives · 8 Scaling · 9 Failures · 10 Impress · 11 Q&A · 12 Links

1. Problem in 3 lines

One line: a cache keeps copies of data in fast memory so we do not ask the slow database every time. "Distributed" means one machine is not enough for the memory or the request rate.
  • Many servers together hold a billion keys and answer 1.5 million operations per second.
  • The hard parts are not "put and get". They are spreading keys without reshuffling everything, surviving node failures, stopping stampedes and hot keys, and keeping cached data close to the truth.
  • A cache outage must slow the system down, not take it down.

Clarifying questions to ask (and the assumed answers)

QuestionAssumed answer
Who are the clients?Internal backend services: a few hundred services, thousands of app instances. Not browsers.
Cache or database?A cache. Losing any entry is safe because the database is the source of truth. No durability promise.
Data model?Key to value with an optional time to live (TTL). Values are opaque bytes up to 1 MB. Counters are nice to have.
Who fills it?The application (cache-aside). The cache does not talk to databases, except an optional invalidation feed.
Scale and latency?1.5M ops/s peak, 1 billion live keys, about 1 KB each. Server p99 under 2 ms, client p99 under 5 ms in one data center.
Availability and consistency?99.99%. Eventual consistency with bounded staleness (a few seconds normally, never longer than the TTL).
Multi-tenant? Multi-region?Yes, many teams share it, so we need quotas. Each region runs its own cluster.

2. Requirements

Functional

  • get and multi-get (one web request often needs 20 to 100 objects)
  • set, add (only if absent), delete, touch (extend TTL)
  • compare-and-set with a version token
  • atomic increment and decrement
  • TTL expiry and automatic eviction when memory is full
  • Namespaces per tenant, with quotas

Non-functional

  • Sub-millisecond server time, one network hop on the read path
  • Hit rate 97 to 99%: the real quality metric, since every miss costs a database read
  • Add nodes with only a small fraction of keys moving
  • A node can die without an error burst or crushing the database
  • Clear metrics, safe resizing, rolling upgrades

Out of scope

  • Durable storage (that is a database)
  • Strong consistency between cache and database
  • Cross-key transactions, secondary indexes, query languages
  • "List all keys" or scan by pattern
Say: "A cache that tries to be a database is worse at both jobs, so I will say no to durability and transactions up front."

4. API

get(ns, key)          -> value + flags + cas + ttl_left | MISS | LEASE(token) | STALE(value, token)
get_multi(ns, keys)   -> map of key to the same result
set(ns, key, value, ttl, flags)  -> STORED
add(ns, key, value, ttl)         -> STORED | EXISTS
cas(ns, key, value, ttl, token)  -> STORED | EXISTS | NOT_FOUND
lease_set(ns, key, value, ttl, token) -> STORED | REJECTED
delete(ns, key) | touch(ns, key, ttl) | incr(ns, key, delta)
  • ns is the tenant namespace and is part of the stored key.
  • get can return a lease or a stale value. These two outcomes are the stampede protection.
  • touch exists so we do not rewrite a 500 KB value just to extend its life. Every reply carries the remaining TTL so clients can refresh early.
  • No "scan all keys": it would stall a node and push people to use the cache as a database.

5. Data model and store choice

Each shard is a hash table in memory. An entry points to an item holding the key, value bytes, expiry, flags, a version (the CAS id) and the pointers eviction needs. No disk on the hot path: the latency target and request rate are far beyond what disk gives at this cost.

OptionStrengthsWeaknessesVerdict
MemcachedSimple, multi-threaded, predictable memory (slab allocator), tiny per-item overheadNo built-in replication or persistence; clustering is client or proxy sideGood for pure caching at scale
Redis ClusterReplication, failover and slot sharding built in; rich structures; optional persistenceOne command thread per process; bigger per-item overhead; snapshots need memory headroomGood when you want fewer moving parts
Build our ownTailoredYears of work on allocator, networking, bugsNo. Build on one of the above and explain its internals
Say: "Memory only, because the source of truth is the database. That is exactly why losing a node is tolerable."

6. Architecture and request flows

Read flow

  1. App calls get. The client checks its tiny near-cache, then hashes the key to a slot and a shard.
  2. The request goes over a pooled connection (through the proxy by default).
  3. Hit: value returns after one hop, about 1 ms. Done.
  4. Miss: the shard gives the first caller a lease token. Other callers wait a few milliseconds or get a stale value.
  5. The lease holder reads the database, then calls lease_set with the token, and returns the value.

Write flow

  1. Write the database first. It is the source of truth.
  2. After commit, delete the cache key (do not set the new value).
  3. The change feed also emits a delete, which repairs a crash between steps 1 and 2 and covers writes by other systems.
  4. The next reader misses, takes a lease and refills with fresh data.
Trap: deleting before committing. A reader can miss in between, read the old row, and refill the old value. Always commit first, delete after.

7. Deep dives

7.1 Stampedes and hot keys

A stampede is many clients missing the same popular key at once and all hitting the database. At 50,000 reads/s and a 40 ms query, about 2,000 requests miss together. A hot key is one key so popular (say 200,000 reads/s) that its single shard saturates while 31 others idle. Adding shards does not help.

DefenseHowCost
LeasesShard gives one caller a token to fill; others wait or take staleSmall server logic; best place, it sees every caller
Single-flightInside one process, concurrent loads share one in-flight loadNone on the server
Stale-while-revalidateSoft TTL 9 min, hard TTL 10 min; serve old value while one caller refreshesSlightly old data
TTL jitterRandom plus or minus 10% so a million keys do not expire togetherNone
Near-cache for hot keysIn-process map, 1 s TTL: 4,000 instances send at most 4,000 reads/s, not 200,000Up to 1 s staleness
Key replicasStore key#0 to key#3 on different shards; read a random oneWrites must update all copies
DetectionSampled counters or a count-min sketch; flag keys over about 20,000 reads/s and push to clientsSmall

Choice: leases plus single-flight plus soft TTL plus jitter for stampedes; automatic hot-key detection that turns on near-cache, then key replicas for keys that cannot tolerate staleness. Rate-limit one abusive key at the proxy as a last resort.

7.2 Consistency with the database

Write policyProsCons
Cache-aside, delete on write (our default)Simple, safe, only read data is cached, cache outage does not block writesA miss after each write; the races below
Cache-aside, update on writeNo miss after writeTwo writers can leave the older value
Write-throughCache matches what went through itCache must know the database; bypass writes unseen
Write-behindVery fast writesData loss if the node dies before flush; that is a database
Read-throughLoader logic in one placeNeeds a loader inside the cache tier (we offer it only in the client library)

Other races and fixes: lost delete (retry from a durable queue, change feed, TTL as backstop); stale read replica during fill (fill from the primary or a caught-up replica). Add a change data capture feed that tails the database log and issues deletes, so writes from scripts and other services are covered too. The honest guarantee: after a commit the cache may be stale for milliseconds to seconds, never longer than the TTL. Readers who need read-your-writes bypass the cache for a few seconds.

7.4 Memory: slabs, eviction, TTL

  • Slab allocator (Memcached): memory is cut into 1 MB pages, each given to a slab class with a fixed chunk size (growth factor 1.25). Items go in the smallest chunk that fits. No external fragmentation, about 10 to 12% internal waste (our 15% includes the hash table). Risk: slab calcification when the size mix shifts; fix with the slab rebalancer. Redis uses jemalloc and reports a fragmentation ratio; above about 1.5 means investigate.
  • Eviction: exact LRU needs a lock and 16 bytes per item on every hit. Memcached uses segmented LRU (hits almost lock free). Redis samples about 5 random keys and evicts the oldest. LFU protects popular keys from scans. Default to an approximate LRU; use LFU for stable-popularity tenants with batch scans. Use allkeys-* policies so memory pressure never causes write errors.
  • Expiry: lazy (check on read) plus active (background sampling; Redis samples 20 keys ten times a second). Never use "no TTL" for derived data: a missed invalidation would last forever.
Trap: filling memory to 100%. Replication buffers, client buffers and fork copy-on-write need headroom. Run at 80 to 85%, alert at 90%.

8. Scaling and bottlenecks

Adding a shard

  • Slots move: the 33rd shard gets about 496 of 16,384 slots (about 3% of keys).
  • Live migration: mark MIGRATING and IMPORTING, copy in small batches with remaining TTL, serve from the source until moved, then ASK redirect, then publish the new owner.
  • Without copying, misses rise from 2% to about 4.9% and DB reads from 28,600 to about 70,000/s.
  • Pace it: 20 to 30 minutes is typical. Resize only below 80% memory.

Multi-tenant isolation

  • Memory quota per tenant; evict from the tenant furthest over quota; unused quota can be borrowed.
  • Token bucket per tenant at the proxy (for example 200,000 ops/s, burst 400,000); excess is a fast "throttled" reply, treated as a miss.
  • Max value 1 MB, key 250 bytes, connections per host.
  • Big tenants get dedicated shards.

At 10x scale

  • 15M ops/s and 13 TB: about 320 shards. SSD tiers for the long tail.
  • Split into cells (own proxies, shards, control plane) to limit blast radius.
  • Gossip failure detection gets costly; use hierarchical or external membership.
  • Network and compression matter more.
Cold start math: an empty cluster sends 1.43M reads/s to databases sized for 28,600: 50 times too much, and the cache can never refill, a metastable failure. Refilling one 41 GB shard (about 37M entries) at 15,000 spare reads/s takes about 41 minutes. So: replicas, rolling restarts, gradual traffic ramp (1%, 5%, 25%, 100%), replay of recent hot keys, lease-limited fills.
Cost: 64 nodes × $0.50/hour (placeholder) × 730 hours is about $23,000 per month. Replicas are half of it. Without the cache the databases would serve 50 times more reads, which costs far more.

Degraded mode: clients time out fast and treat it as a miss; a global cap on database loaders keeps the DB inside capacity; non-critical tenants are shed first; serve stale on error. The gutter pool (about 1% of capacity) takes the hot keys of a dead shard with a short TTL of a few seconds. Failover caveats: a split-brain old primary is bounded (it stops serving without a majority and resyncs as a replica); add hysteresis against flapping.

10. Things to say to impress

Say: "The cache is an optimization, so its failure must never be a correctness failure. But the database was sized for a 98% hit rate, so it can easily be a capacity failure. I will design for both."
Say: "Consistent hashing spreads keys, not load. Hot keys need near-caches or key replicas, and adding shards will not help."
Say: "The leases do two jobs: they collapse a stampede into one database query, and a delete cancels the lease so a slow reader cannot write an old value."
  • Make the hit rate a first-class SLO (97% floor), and alert on the database load caused by misses: the single most protective alert.
  • Name the metastable failure: a cold cache plus an overloaded database cannot heal itself. Gradual traffic ramps are the answer.
  • State the staleness bound honestly: seconds in the normal case, never longer than the TTL.
  • Eviction age (how old evicted items were) is the best capacity signal: evicting items younger than their TTL means the cache is too small.
  • Security: private subnets only, TLS or per-tenant credentials scoped to namespaces, negative caching or a Bloom filter against penetration (floods of keys that do not exist).
  • Multi-region: do not replicate contents; carry invalidations in the database replication stream so deletes arrive in order.
  • Phases to build: replicated pair with cache-aside, then sharding plus proxy plus leases plus quotas, then CDC and hot-key detection, then multi-region and SSD tiers.

11. Interview Q&A

Why not just use hash(key) mod N to pick the shard?

Modulo is even and trivial, but every key's location depends on N. Going from 32 to 33 shards, a key stays put only about 1 time in 33, so roughly 97% of the cache moves. Moved keys are simply unreachable because the new owner is empty, so the hit rate drops to a few percent and the database sees almost the full read load. That is an outage disguised as a routine resize. Consistent hashing or fixed slots move only about 1/33 of the keys, and with slots we can copy even those live so they rarely miss.

Memcached or Redis for this service?

For plain strings with simple get and set, a very high request rate and huge memory, Memcached gives predictable memory, multi-threading and low per-item overhead, and gets replication and failover from a proxy such as mcrouter. Redis Cluster gives replication, automatic failover, slots, counters and sorted sets, and optional persistence for fast restarts, at the cost of more memory per item and a mostly single-threaded engine per shard. At 47,000 ops/s per shard either works. I would pick Redis Cluster for a small team that wants fewer moving parts, and Memcached with a proxy tier for a huge uniform fleet.

A single key gets 200,000 reads per second. What do you do?

Adding shards cannot help because one key lives on one shard. First put a near-cache of about one second in each client: with 4,000 instances the shard sees at most about 4,000 reads per second. If the key tolerates no staleness, store it under several suffixed names on different shards and read a random one, updating every copy on write, or allow reads from the replica. Detect hot keys automatically with sampled counters so developers do not need to know in advance, and rate-limit at the proxy so one key cannot hurt its neighbours.

How do you stop a cache stampede?

I layer defenses. The shard issues a lease to the first missing caller and makes others wait briefly or take a stale value, so one database query runs per key. Inside each process, single-flight shares one load between threads. Stale-while-revalidate with a soft TTL lets users keep getting the old value while one caller refreshes it. TTL jitter stops mass expiry at the same second. Finally, a global limit on database loaders caps the pressure even when many different keys miss at once.

The database row changes. How do you avoid stale data forever?

Commit to the database first, then delete the key, not set it. The classic race is a slow reader that loaded the old row before the write and fills the cache after the delete. Leases close it because the delete cancels the outstanding token; a row version with compare-and-set also works. Back this up with a change data capture feed that emits deletes for every write, including ones the application did not make, and a TTL as the final bound. The honest guarantee is bounded staleness, typically a few seconds and never beyond the TTL.

A cache node dies. What happens, and how do you protect the database?

Peers miss heartbeats and mark the node suspect, a majority of primaries agree it failed, and the most up-to-date replica is elected and promoted. Clients learn the new map from a redirect or a refresh. For those 5 to 15 seconds, 1/32 of keys miss, adding about 45,000 reads per second to the database. Clients use short timeouts, a circuit breaker and leases to collapse duplicate loads, and the database has about 2x headroom. A gutter pool can hold the hottest keys of the dead shard for a few seconds, and the replacement is warmed gradually.

How do you add a node without a spike of misses?

Use slots or consistent hashing so only about 3% of the keys change owner when going from 32 to 33 shards. Then migrate those slots live: copy keys in small batches with their remaining TTL, serve from the source until a key has moved, redirect afterwards with ASK, and publish the new owner when the slot is empty. If copying is not possible, run both rings for a window, read the new owner first and fall back to the old one on a miss. Pace the move to protect the source, and only resize when memory use is below about 80%.

Explain LRU and why a real cache does not implement it exactly.

LRU evicts the item whose last use is oldest, on the idea that recent use predicts future use. Exact LRU keeps all items in a linked list and moves the item to the head on every read. That needs a lock around shared pointers and 16 bytes extra per item, which becomes a bottleneck at high read rates. Memcached uses segmented LRU with lazy bumping so hits are almost lock free. Redis stores a coarse timestamp and samples about 5 random keys at eviction time, evicting the oldest, which closely approximates LRU with no per-hit cost. If the workload has scans, LFU protects popular keys better.

How do you share the cache fairly among many teams?

Namespace keys per tenant and enforce three limits. Memory: evict first from the tenant furthest over its quota, so a growing neighbour cannot push out a tenant under quota. Request rate: a token bucket at the proxy, with excess answered as fast misses so the app degrades instead of queueing. Connections and value size: caps so nobody blows up buffers or slab classes. Unused quota may be borrowed, which is why sharing is cheaper than separate clusters. Very large or sensitive tenants get dedicated shards, and per-tenant dashboards of hit rate, memory and throttling keep quotas understandable.

Hit rate suddenly drops from 98% to 85%. What do you check?

First look at the database load from misses, since 85% means about 7 times more database reads, and protect it (shed low-priority tenants, cap loaders). Then find the cause by checking the timeline. Did a node fail or restart empty? Was there a resize or deploy? Did evictions jump, with eviction age falling below the TTL, meaning memory pressure or one tenant flooding the cache with a scan? Did a key format or version change in a deploy so old keys no longer match? Did many TTLs expire together? Fix the cause, ramp traffic back gradually, and add an alert on the miss rate.

Why is a cold cache so dangerous?

Databases are sized for the miss traffic, about 2% of reads, so a zero hit rate sends 50 times more load than they were built for. They slow down, requests time out, loaders never finish filling the cache, and the system stays broken even after the original cause is gone. So we avoid emptiness with rolling restarts, replicas and snapshots, and bring new capacity in gradually by shifting a growing percentage of keys. We prefill the hottest keys from recent access logs at a controlled rate, and use leases and a loader cap so the database sees each key once. During recovery we shed low-priority traffic.

Should the cache write to the database (write-through or write-behind)?

Not for a general shared cache. Write-through forces the cache tier to know each database's schema and failure behaviour, slows every write, and still misses writes that bypass it. Write-behind makes the cache hold the only copy of recent writes, so a node loss means data loss, which turns a cache into an under-engineered database. Cache-aside with delete on write keeps the cache free of correctness duties: it can be wiped at any time and the system stays right, only slower. A tolerant exception is counters, where losing a few seconds of increments is acceptable.

Where should routing live: client, proxy or server redirect?

A smart client is fastest, with one hop, but the routing logic must be kept consistent in every language, and 4,000 instances open connections to all 32 shards, about 512,000 in total. A proxy tier adds roughly 0.2 ms and a fleet to run, but gives thin clients, pooling, failover, quotas and safe resizing in one place. Redis Cluster redirects cost one wasted trip on a stale map. I would default to a proxy tier for tenants and offer a smart client with the same slot map to the few latency-critical services.
