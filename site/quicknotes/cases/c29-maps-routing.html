Case sheet 29: Design Maps and Routing

One-page cheat sheet: a Google Maps style product with map tiles, address search, driving directions, live traffic and arrival times. Full write-up: Handbook case study 29.

ProblemRequirementsEstimationAPIDataArchitectureDeep divesScalingFailuresImpressQ&ALinks

1. Problem in 3 lines

One line: "Design Google Maps" is really four small systems on one shared map: draw the map (tiles), find the place (geocoding), find the fastest path (routing), and know how busy the roads are (traffic and arrival time).
  • Each system has different data, different load and a different bottleneck. Say that out loud first, then go one by one.
  • Scale: 1 billion monthly users, 500 million daily users, worldwide, mostly phones.
  • Targets: tiles feel instant (p95 under 100 ms from the nearest edge), a cross-country route in well under 1 second (p99 about 500 ms with network), traffic about one minute old, arrival time (ETA) within about 10 percent for trips under an hour.

Clarifying questions to ask (and the answers we assume)

AskAssume
Which features?Pan and zoom map, place and address search with autocomplete, driving directions with alternatives, live traffic, ETA. Reverse geocoding (point to address) is included because it is cheap once search exists.
Which travel modes?Driving in full. Walking and cycling use the same machinery on other graphs. Transit is out.
Where does map data come from?Licensed and open data plus user edits. We design ingest and publish, not the cartography pipeline.
How live is "live"?Road speeds refreshed about every minute, mostly from anonymous phone probes plus incident feeds.
Offline maps?A short extension: download a region's tiles and a compact routing graph.

2. Requirements

Functional

  • Render the map at any zoom and viewport, light and dark style, many languages
  • Search text to ranked places, autocomplete while typing, reverse geocode
  • Route from A to B with waypoints, a few alternatives, turn-by-turn steps
  • Colour roads by current speed; use traffic in route choice
  • ETA now or for a later departure; keep it updated and offer a reroute

Non-functional

  • Tiles are read-heavy and identical for everyone, so serve from CDN caches
  • Routing cannot touch tens of millions of nodes per query, so precompute
  • Freshness differs: tiles minutes to days, traffic about 1 minute, closures minutes
  • Available over consistent: stale beats an error
  • Degrade gracefully: no traffic means typical speeds; slow routing means straight-line estimate
  • Location probes are anonymous and aggregated

Out of scope

  • Transit timetables
  • Street-level imagery and indoor maps
  • Ads, business listings, reviews
  • Fleet optimisation with many stops
  • Voice guidance
  • Cartographic compilation from raw imagery

3. Estimation (same numbers as the handbook)

One line: tiles need about 1.4 M requests per second at peak (the CDN must absorb 98 percent), search about 9 K per second, routing and ETA about 20 K per second, probes about 2 M per second. The whole world road graph fits in one server's RAM.

Four subsystems, four bottlenecks: tiles are bound by egress and hit rate; geocoding by index latency; routing by CPU per query (so spend hours offline to save milliseconds online); traffic by ingest and aggregation. Partition the graph for preprocessing, blast radius and locality, not because it does not fit.

4. API

GET  /tiles/v{style_ver}/{z}/{x}/{y}.pbf      Cache-Control: public, max-age=86400, stale-while-revalidate=604800
GET  /v1/geocode?q=...&bias=lat,lon&lang=en&limit=5   -> results[{place_id, name, lat, lon, bbox, type, score}]
GET  /v1/autocomplete?q=amph&session=ab12&bias=...      GET /v1/reverse?lat=..&lon=..
POST /v1/route   { origin, destination, waypoints[], mode, depart_at, avoid[], alternatives }
                 -> routes[{ distance_m, duration_s, duration_in_traffic_s, polyline, steps[], graph_version }]
POST /v1/eta-matrix   { origins[], destinations[], mode, depart_at }   -> n x m table
POST /v1/navigation/{route_id}/reroute   { current_position, heading }
POST /v1/probes  [ { ts, lat, lon, speed, heading, acc } ... ]   (batched uploads every 10 to 30 s)
  • The style version is in the tile URL: changing a style means a new URL, never a cache purge.
  • The route response carries graph_version so an engineer can replay what the router saw.
  • Phones batch probes to save battery, so the server never sees strictly one point per request.

5. Data model and store choices

DataStoreWhy
Map features (roads, buildings, places), editable truthSpatial database plus versioned snapshot filesEditors need spatial queries and transactions; batch jobs need immutable snapshots
TilesObject storage behind a CDN, key style_ver/z/x/yWrite once, read by key, huge parallel reads, only 1.6 TB
Place indexSearch engine cluster, sharded by regionInverted index, prefix and fuzzy matching, location boost. Derived, so it can be rebuilt freely
Road graphCompiled read-only snapshot in memory (flat arrays)Path search chases pointers millions of times; a database round trip per node would take minutes
Live speedsIn-memory table on every routing node, fed by a streamSmall, rewritten each minute, read on every query
Typical speeds by time of weekWide-column store sharded by regionLarge, read by segment and time slot
Raw probe archiveObject storage, columnar files, by day and regionCheap and huge, used for training and replay

The graph is stored as compressed sparse row arrays: a node array points to its first outgoing edge, and an edge array holds target, length, speed class and flags (one-way, toll, ferry). It is versioned (for example graph_v2026_11_17_03), built offline, and memory-mapped. A query pins one version, which makes consistency trivial.

6. Architecture and main flows

Main flow: a route request

  1. Phone sends POST /route. The gateway checks the key and rate limit.
  2. Search resolves text to coordinates and snaps them to the road.
  3. The gateway sends the query to the region that owns the origin.
  4. The routing service pins one graph version and one speed snapshot for the whole request.
  5. It runs the contraction hierarchy query (about a millisecond), finds 2 alternatives, and unpacks shortcuts into real roads.
  6. It re-times the path with a clock: live speeds for the first 15 to 30 minutes, typical speeds for later parts, plus turn and signal delays.
  7. The ETA model applies a learned correction, and the response goes back with polyline, steps and ETA.

Main flow: a tile request

  1. Phone checks its disk cache, then asks the CDN edge (hit about 98 percent, done).
  2. Edge miss goes to a regional shield cache; many edges collapse into few requests here.
  3. Shield miss: request coalescing means one fetch for many waiters. The tile service reads the blob, or renders it if zoom 15 or deeper.
  4. The tile fills shield, edge and phone on the way back. Meanwhile the phone draws the parent tile larger (over-zoom).

7. Deep dives

7.1 Tiles: raster or vector, pre-generate or on demand

The map is cut into a pyramid: zoom z has 2^z by 2^z tiles, addressed (z, x, y). Every viewer of a place requests the same URL, which is what makes the CDN work.

OptionGoodBadUse
Raster tiles (images)Dumb clients, simple20 to 100 KB each, blurry between zooms, rebuild per style and languageSatellite photos
Vector tiles (geometry)5 to 40 KB, smooth zoom, rotate and tilt, one tile for many styles and languagesClient needs a GPU rendererBase map in apps
Pre-generate allPure reads, no render at serve timeZoom 17 alone is 17 B tiles, mostly never viewedZoom 0 to 14
Render on demandStores only what is used, cheap updatesFirst viewer waits; cold stampede can overload renderersZoom 15 and deeper

Choice: vector tiles, hybrid generation (precompute to zoom 14, about 1.6 TB), with shield caching and request coalescing. Freshness by versioned URLs: a new data version is a new set of keys. Urgent fixes purge only the touched tiles by coordinate. Before flipping a new version, warm the popular tiles to avoid a wall of misses.

7.2 Shortest path: Dijkstra, A*, ALT or contraction hierarchies

AlgorithmPreprocessingQuery work (continental)Live trafficVerdict
DijkstraNoneTens of millions of nodes, secondsTrivialBaseline and fallback
Bidirectional DijkstraNoneAbout half of DijkstraTrivialBuilding block
A* (straight-line bound)NoneStill a large share of the areaTrivialWeak on roads
ALT (landmarks)Minutes to hoursAbout 10x fewer than DijkstraBounds stay valid only if speeds never go below preprocessed onesMiddle ground
Contraction hierarchies (CH)Minutes to hours per region; shortcuts about equal original edge countHundreds to a few thousand nodes, about 1 msNeeds re-weightingChosen

Live traffic problem: shortcut weights are sums of edge weights, so one speed change makes shortcuts stale. Options: customizable CH (fixed ordering and shortcut shape, recompute weights bottom-up in seconds), time-bucketed hierarchies (cheap but ignores today's accident), or hybrid (CH on typical weights, then re-time candidates with live speeds and run local Dijkstra near big deviations). Choice: customizable hierarchy refreshed each minute, hybrid as fallback for local incidents and future departures, plain Dijkstra if the hierarchy is down.

7.3 Partitioning the graph

OptionGoodBad
Grid or country bordersSimpleCuts roads at random, many border edges, unbalanced (city versus desert)
Balanced partitioner that minimises border nodes, plus overlay graphFew border nodes, small overlay; a traffic change recomputes only one cellMore complex code; cross-cell queries do extra work

Choice: balanced cells with an overlay (the idea behind customizable route planning). The query searches in detail inside origin and destination cells and uses precomputed border-to-border shortcuts in between. We partition for parallel preprocessing, regional blast radius and the 134 GB of profiles, even though the 8 to 10 GB graph fits on one machine.

7.4 Geocoding in one paragraph

Normalise (case, accents, "st" means street or saint, keep both), parse tokens (number, street, city, postcode), retrieve candidates from the search index (prefix for the last token, fuzzy for typos, location boost), rank by text match, place importance, distance and learned popularity, and interpolate house numbers along street ranges. Shard by country or large region so the local shard answers most queries; only weak results trigger a wider query. Reverse geocoding is a spatial cell lookup (grid, R-tree, S2 or geohash style), cached at about 10 m rounding.

7.5 Live traffic and ETA

  • Aggregate robustly: median or trimmed mean per segment per minute, with a sample count as confidence. Few samples means blend toward typical speed. Empty segments are filled from neighbours and history. Event-time windows handle late batched uploads.
  • ETA is not a sum of current speeds: the far end of a 90-minute trip is reached 90 minutes from now. Walk the route with a clock, use live speeds for the first 15 to 30 minutes then typical speeds, add signal and turn delays, then apply a learned model (for example gradient-boosted trees) trained on trips actually driven. Judge by median and 90th percentile error per region and trip length.
  • Reroute: trigger on deviation (missed turn) or on improvement (alternative now saves a few minutes or 10 percent). Index segment to active routes so only affected routes are recomputed. Use hysteresis to avoid flapping.

Reads are safe to retry, so no idempotency key. The key consistency rule: one route request reads one graph version and one speed snapshot. During a snapshot swap, old and new live side by side until in-flight queries finish. Duplicate probes are tolerated or deduplicated by (trip id, sequence).

10. Things to say to impress

  • "Maps is four systems; here is the bottleneck of each": egress and hit rate, index latency, CPU per query, ingest and aggregation.
  • Do the hit-rate arithmetic: 1.4 M per second, 98 percent hit leaves 28 K per second, 90 percent leaves 140 K.
  • "The whole world graph is 8 to 10 GB, it fits in one machine's RAM. We partition for preprocessing, blast radius and locality."
  • Name the catch: contraction hierarchies are fast but bake edge weights into shortcuts, so traffic needs customizable hierarchies or an overlay with fast weight refresh.
  • "ETA is a clock walk over the route, not a sum of current speeds, plus a learned residual, tracked by error percentiles."
  • Degrade, never fail: stale tiles, typical speeds when traffic is old, Dijkstra when the hierarchy is down.
  • Versioned immutable artifacts (tiles, graph) turn rollback into a pointer flip, and a golden set of routes catches bad data builds.
  • Privacy: no account id on probes, rotating ids, trimmed trip ends, aggregates only with enough distinct devices.

11. Interview Q&A

Why not just run Dijkstra on the whole graph? What is the real number?

Dijkstra settles nodes in order of distance from the origin, so a long trip processes nearly every node within the trip radius. On a continental network that is tens of millions of nodes, which takes seconds. With about 20,000 route and ETA queries per second, plain Dijkstra would need tens of thousands of cores. Contraction hierarchies cut each query to hundreds or a few thousand settled nodes, about a millisecond, so about 100 busy cores are enough. The trade is hours of offline preprocessing against milliseconds saved on billions of online queries.

Explain contraction hierarchies in a minute. What is the catch with traffic?

Rank nodes by importance, then remove them from least to most important. When removing a node would break the only shortest path between two neighbours, add a shortcut edge with the combined cost. A query runs one search from the origin and one from the destination, each allowed to follow only edges that go up in rank, and they meet near the top, among highway-like nodes. The catch is that shortcut weights are sums of base edge weights, so a live speed change makes every shortcut built on it stale. Rebuilding every minute is too slow. So we use a customizable variant: the ordering and shortcut shape are fixed and only the weights are recomputed bottom-up in seconds. A hybrid re-timing of candidate routes covers local incidents.

Does the road graph fit on one machine? Then why partition?

Yes. About 200 million edges at 16 bytes is 3.2 GB, and with shortcuts about 8 to 10 GB, so one ordinary server can hold the planet. We partition anyway for four reasons. Preprocessing and weight updates run in parallel across regions. Servers sit near their users and keep only the regions they serve, which improves CPU cache behaviour and restarts. A bad data build or outage in one region stays contained. And the time-of-week profiles are about 134 GB, which does not fit. We cut with a balanced partitioner that minimises border nodes and build an overlay of border-to-border shortcuts, so a cross-cell query searches in detail only in the origin and destination cells.

How do tiles stay fast for a billion users without melting the origin?

A tile is a static object whose URL holds zoom, x, y and a version, so everyone looking at the same place asks for the same bytes and the CDN can keep it for a long time. At 1.4 million requests per second peak, a 98 percent hit rate leaves 28,000 per second for origin. A shield tier in front of origin merges misses from many edges, and request coalescing makes ten thousand simultaneous misses on one tile cause exactly one render. We precompute tiles up to zoom 14 (about 1.6 TB) and render deeper ones on demand while the phone draws the parent tile larger. New data ships as a new version warmed in popular regions first, so there is never a mass invalidation.

Raster or vector tiles, and why?

Vector for the base map. A raster tile is a finished picture: simple for any client, but 20 to 100 KB, blurry between zooms, and it must be rebuilt for every style, language and screen scale, which multiplies the cache. A vector tile carries compact geometry and labels, typically 5 to 40 KB, and the phone draws it with a style sheet. So dark mode, languages, rotation, tilt and smooth zoom cost nothing extra on the server, and one cached tile serves all styles. The cost is a GPU renderer on the client. Satellite imagery stays raster because photos are raster. Vector also cuts egress by roughly 3 to 5 times, and egress is the biggest cost line.

How do you compute an ETA that is right for a one-hour trip?

Summing current speeds is wrong, because the far end of the trip is reached an hour from now when traffic is different. I walk the route with a clock and look up each segment's speed for the time I will arrive there: live speeds for the first 15 to 30 minutes, then blend toward the typical speed for that time of week. Then I add delays that speeds miss, such as signals, stop signs and turns, learned per intersection from probe data. On top I run a model trained on trips that were actually driven, predicting the correction from features like road mix, time of day and weather. I track median and 90th percentile error per region and trip length, and log predicted versus actual at the end of every navigation.

Probe data is sparse on a road, or wrong. What do you do?

For sparse data I estimate with a confidence value. With few samples in a minute, the result shrinks toward a prior built from neighbouring segments and the typical speed for that time slot, and routing can treat low confidence as "use typical". For wrong data I use robust statistics such as the median, require a minimum number of distinct devices, compare with history, and distrust sudden drops unless several independent devices agree. Spoofing a jam to divert others is a real abuse case, so I add signed batches, device attestation and per-device rate limits. If the pipeline is unhealthy, the fallback is always typical speeds, never an error.

A bridge closes. How fast does routing find out, and what about other map changes?

There are two speeds. Urgent changes such as closures are overrides: the affected edges get infinite weight in the speed table, which reaches routing servers in a minute or two, and related tiles are purged by coordinate. Ordinary changes such as a new road go through the build pipeline: edit the feature store, regenerate affected tiles, update the place index incrementally, and build a new graph snapshot daily or weekly. The new graph is checked against a golden set of routes and canaried on shadow traffic before the pointer flips, and the old snapshot stays in memory until in-flight queries finish. A small patch list can fix a known error in the live graph without waiting for a full build.

How do you serve a route that crosses continents or many cells?

Every region keeps a coarse world overlay: border nodes of cells plus precomputed distances between them, including ferry links where relevant. A coordinator runs the detailed search in the origin region out to its borders, uses the overlay for the middle, and the destination region's detailed search for the end, then stitches the parts. It is the same multi-level overlay idea used inside a continent. Cross-region requests are rare, so accepting a slightly slower path for them is better than copying full graphs everywhere.

Pre-generate tiles or render on demand?

Look at tile count, popularity and the cost of a miss. Low zooms have few tiles that everyone asks for, so precomputing is free benefit. Deep zooms have billions of tiles and most are never requested, so on-demand rendering with caching stores only what is used. The danger of on-demand is a cold stampede after a release, so I coalesce at the shield, size the renderer pool for the peak miss rate, and warm known-popular tiles before switching versions. I would put the boundary at the zoom where fewer than a few percent of tiles are ever requested, which is roughly zoom 14 to 15 here.

How would you do autocomplete in under 100 ms?

Use a search engine with edge n-gram matching for the last token, exact matching for the earlier tokens, and a boost for the user's location. Shard the index by country so the local shard answers most queries, and query a wider shard only when the local result is weak. Cache hot prefixes keyed by prefix and a coarse location cell, since early keystrokes of popular queries repeat. On the client, debounce 100 to 150 ms and cancel the previous request when a new key arrives. At 9,000 requests per second peak, a few dozen index nodes with replicas are enough.

How would you support offline maps?

Let the user download a region: vector tiles up to a chosen zoom, a trimmed place index with names and addresses, and a compact routing graph with typical-speed profiles in a hierarchy format that runs on a phone. Updates arrive as diffs against the downloaded version. Live traffic is not available, so ETAs use historical profiles by time of week and the app labels them as such. A large country takes a few hundred MB to a couple of GB, so let users pick regions and compress hard.

Everyone reroutes after a crash. What goes wrong, and how do you avoid it?

If thousands of drivers get the same "better route" suggestion, they all move to the alternative and it becomes the new jam. To limit this, suggest only when the gain beats a threshold (a few minutes or 10 percent), use hysteresis so a user is not flipped back and forth, and spread suggestions among near-equal options. Cost matters too: instead of rerunning routing for millions of navigating users every minute, keep an index from segment to active routes and recompute only routes whose segments changed a lot.
