Case sheet 28: Design a Distributed Unique ID Generator

One-page revision of the Snowflake-style 64-bit ID design: the bit layout, worker-id leases, and clock rollback. Full write-up: handbook case study 28.

1 Problem · 2 Requirements · 3 Estimation · 4 API · 5 Data · 6 Architecture · 7 Deep dives · 8 Scaling · 9 Failures · 10 Impress · 11 Q&A · 12 Links

1. Problem in 3 lines

One line: hundreds of machines must hand out names (IDs) that never repeat, with no machine asking a central counter for each ID, and with IDs that sort roughly by time.
  • On one database, auto-increment is easy. With many shards, services and regions there is no single counter.
  • We want three things: unique, small (64 bits) and ordered by time. Random UUIDs give only the first. Counters in a database give order but need a call per ID.
  • A duplicate silently corrupts data (two orders overwrite each other), so uniqueness must hold by construction, not by luck.

Clarifying questions to ask

QuestionAssumed answer
What is the ID for?Primary key for orders, messages, events across about 200 services. Seen in URLs, so not absurdly long.
How big?64 bits: fits a BIGINT and a Java long, half of a 128-bit UUID.
Sorted by time?Roughly ("k-sortable": correct to within a few milliseconds). Strict global order is not needed.
Gap free?No. Invoice numbers are a separate problem.
Scale?300,000 IDs/s average, 1,000,000/s peak, 3 regions.
Latency?Microseconds in-process, under 2 ms p99 as a service.
Guessable OK?Internal keys yes. Secret tokens (password reset links) must not use this generator.
Clocks?NTP, roughly right (tens of ms), but they can jump and step backwards.
Say this: "The triangle is uniqueness, compactness and order. Snowflake gets all three by moving coordination from once per ID to once per process start. The interesting failure is the clock."

2. Requirements

Functional

  • Unique for about 69 years.
  • 64-bit positive number.
  • Roughly time ordered.
  • Decodable: time and worker can be read from the ID.
  • Generating an ID never waits on a remote quorum in the normal path.

Non-functional

  • 1,000,000 IDs/s at peak across the fleet, at least 100,000/s per generator.
  • Under 1 microsecond in-process; under 2 ms p99 as a service.
  • Losing a generator, a zone or the lease registry must not stop generators already running.
  • A backwards clock must never create a duplicate.

Out of scope

  • Gap-free business numbers (invoices).
  • Unguessable security tokens.
  • Strict global order (needs a consensus sequencer).
  • Content hashes as IDs.

4. API

// Embedded library (no network)
long id = gen.nextId();                 // thread safe, microseconds
IdParts p = IdGenerator.decode(id);     // { timestampMs, workerId, sequence }

// Service, for browsers and short-lived scripts
POST /v1/ids        { "count": 100 }    -> { "ids": ["123...", ...] }   // max 1,000
GET  /v1/ids/{id}/decode                -> { "created_at", "worker", "sequence" }

// Lease protocol (internal, library at startup)
acquire(service, hint) -> { worker_id, lease_id, ttl_ms, last_ts_ms }
renew(lease_id)        -> { ttl_ms }
release(lease_id)
  • Return IDs to JSON clients as strings. A JavaScript number keeps only 53 bits exactly, so a 63-bit ID would be rounded.
  • Retry is safe: a retry may waste an ID but never duplicates one.
  • The lease returns last_ts_ms, the highest timestamp this worker id ever used. A new owner must wait it out.

5. Data model and store choices

The generator keeps only last_ts, sequence and worker_id in memory. We never store issued IDs. The only durable state is the lease registry.

RecordFieldsStore and reason
WorkerLeaseworker_id (key), owner (host, pid, nonce), lease_deadline, last_ts_ms, generationetcd or ZooKeeper (5 nodes), or a relational table keyed by worker_id. We need mutual exclusion ("no two live processes share a worker id"), which a strongly consistent store gives. About 1,024 rows and a few writes per second.
Configcustom epoch, bit widths, region ranges, layout versionImmutable after launch. Changing a bit width changes the meaning of every old ID, so layouts are versioned.
Generator memorylast_ts, sequence, worker_idA few bytes in process; nothing persisted per ID.

6. Architecture and main flows

Flow A: process startup (once)

  1. Ask the registry for a worker id, sending host, pid and a random nonce.
  2. Registry picks the free id that has been free longest, writes a lease (deadline now + 60 s), returns worker_id, generation and last_ts_ms.
  3. If the local clock is behind last_ts_ms, wait until it passes. This makes reusing a worker id safe.
  4. Start renewing every TTL/3 (20 s), then serve nextId.

Flow B: nextId (hot path, no network)

  1. Read the clock in ms, subtract the custom epoch.
  2. Same ms as last: add 1 to the sequence. If it passes 4,095, wait for the next ms.
  3. Later ms: reset the sequence to 0.
  4. Earlier ms than last: the clock went backwards, apply the rollback policy (section 7).
  5. Save last timestamp, return (now << 22) | (worker << 12) | seq.

7. Deep dives

7.1 Which ID scheme?

Choice: Snowflake, because we need 64 bits, order and no per-ID coordination. UUIDv7 is the stated alternative when 128 bits are fine.

7.2 Worker-id assignment

OptionProsCons
Static configNo dependencyBreaks with autoscaling; human error
Hash of IP or hostnameNo registry10-bit collisions: about 38 hosts give 50 percent chance of a clash
StatefulSet ordinalStable, simpleOnly for the ID service pods; ranges per cluster
Lease from etcd or ZooKeeperHandles churn and crashesNeeds registry at startup; paused-holder risk
DB row with unique keyFamiliar, auditableSame caveats as the lease

Choice: leases from the registry. Danger: a process pauses longer than its lease, the id is given to a new process, and the old one wakes up still thinking it owns it. Four cheap defenses:

  1. Self-expiry check on every call, using the local monotonic clock, minus a safety margin.
  2. TTL 60 s, renew every 20 s, and a quarantine (2 x TTL = 120 s) before an id can be reassigned.
  3. Wait out old timestamps: a new owner waits until its clock is above the persisted high-water mark.
  4. Least-recently-used allocation: hand out the id that has been free the longest.

Multi-region: each region owns a disjoint range (region 1: 0 to 340, region 2: 341 to 681, region 3: 682 to 1,023). A partitioned region can never hand out another region's id.

7.3 Clock rollback

Clocks go back from NTP step corrections, leap seconds, VM migration or restore, and operator error. If the clock goes back 3 ms, the worker revisits milliseconds it already used and, with the sequence restarting at 0, emits exact duplicates.

LayerWhat we do
PreventSlew-only NTP or chrony (no steps), smeared leap seconds, timestamp = wall time at start + monotonic elapsed.
DetectCheck now < lastTs on every call. It is free and a duplicate is a data incident.
RespondTiers above. The "borrow from the future" logical-clock trick is reserved for tiny offsets only.
Survive restartAt each renewal persist now + TTL + safety as a high-water mark. A new owner waits until its clock exceeds it. Cost: one write per renewal, not per ID.
Skew between workersNever makes a duplicate (worker field differs). It only widens k in k-sortable. Alert above 50 ms.

7.4 Bit layout and sequence

LayoutTimeWorkerSequenceLifetime
Original Snowflake and ours41 bits, 1 ms1012 (4,096 per ms)about 69.7 years
Instagram41 bits, 1 ms13 (logical shard)10 (1,024 per ms)about 69.7 years
Sonyflake style39 bits, 10 ms168about 174 years
  • Use a custom epoch (for example 2024-01-01). A 1970 epoch would run out around 2039.
  • If the sequence overflows in one ms, wait for the next ms. That is a throttle under 1 ms, not a failure.
  • Sequence always starting at 0 makes low bits nearly constant. Shard on a hash of the ID, not raw low bits.

7.5 Why time order helps databases

Random keys land on random B-tree leaf pages: the working set is the whole index, pages split and sit about half full. Time-ordered keys append to the right edge: a few pages stay in memory and pages fill densely. "50 newest orders" becomes ORDER BY id DESC LIMIT 50. Cautions: the right edge can become a write hot spot, so hash the ID or tenant for shard placement; and time-ordered IDs leak creation time and volume.

8. Scaling and bottlenecks

  • Per worker: 4.096 million/s ceiling against about 977/s needed. Bulk imports should use several workers or the batch API.
  • ID service tier: 1,000,000/s with batches of 100 is 10,000 requests/s, about 10 pods. Each pod uses one worker id for life.
  • Registry: 400 processes renewing every 20 s is about 20 writes/s. It is not on the data path, so an outage only blocks new processes.
  • Clock reads: about 20 to 50 ns on Linux (vDSO). Cache the ms in a background thread only if profiling says so.
  • Nothing to shard or cache: the worker field partitions the ID space by construction.
  • At 10x (10 million/s): still only 2.4 workers' ceiling. If the fleet outgrows 1,024, move bits from sequence to worker (13 worker bits, 9 sequence bits gives 512 per ms), or use a 10 ms tick, via a new layout version.

The registry is CP (refuses to hand out ids without a quorum). Running generators are AP-like: they keep issuing from a lease they already hold.

10. Things to say to impress

  • "Snowflake does not remove coordination. It moves it from once per ID to once per process start, and trades the rest for a clock. Every hard problem is where the clock or the worker id is wrong."
  • "Leases need a quarantine and a self-expiry check, because a paused holder wakes up believing it still owns the id. The guarantee rests on bounded pauses and drift, and I will state that."
  • "I persist a high-water timestamp at each renewal so a new owner of a worker id can never reissue an old number."
  • "IDs are k-sortable, not causal. Never use them to decide which write happened first, and never as secrets."
  • "Key width is the real cost: 8 bytes instead of 16 saves about 207 GB per day before indexes."
  • "In regions, disjoint worker ranges mean a partitioned region cannot collide with others, with nothing to reconcile later."
  • "UUIDv7 is the right answer if 128 bits are fine. Start there and move to Snowflake when width or decoding matters."
  • Monitor: clock offset (warn 20 ms, page 100 ms), rollback events, lease age, free worker ids (alert below 20 percent), duplicate-key errors on generated columns.

11. Interview Q&A

Why not just use UUIDs everywhere?

UUIDv4 is a fine default for small systems because it needs no infrastructure. At our scale it doubles the key width, and that repeats in every index and foreign key, which is hundreds of gigabytes a day. Its randomness also scatters B-tree inserts and hurts cache use. UUIDv7 fixes the ordering but not the size. So I would say: UUIDv7 if 128 bits are fine, Snowflake if we need 64 bits and decodable fields. The constraints decide.

Two workers get the same worker id. What happens and how do you stop it?

If both are alive and issue in the same millisecond with the same sequence, they produce identical IDs. The database either rejects one with a duplicate key error or, worse, an upsert overwrites a row. Prevention is layered: the registry is the only source of ids, a quarantine delays reuse, a self-expiry check stops a paused process, and a high-water mark makes the new owner wait out old timestamps. Detection is a duplicate-key alert and a canary that samples IDs. The guarantee depends on bounded pauses and clock drift, and I would say so.

What do you do when the clock moves backwards?

First prevent it: slew-only NTP, smeared leap seconds and a monotonic clock anchored at startup. Second, detect it by comparing now with the last timestamp on every call. For a few milliseconds, wait until the clock catches up. For up to a second, fail the health check so the load balancer drains this worker. For more, release the lease and restart with a fresh worker id after waiting out the stored high-water mark. The rule is never to issue a timestamp below one already used with this worker id.

Why is the timestamp in the highest bits?

Integer comparison looks at the high bits first. With time first, a later ID compares larger, so sorting by ID approximates sorting by time and database indexes see mostly rising keys. If the worker id came first, all IDs from worker 1 would sort before worker 2 whatever the time. Inside one millisecond, order across workers is arbitrary, which is why we say k-sortable and not strictly ordered.

How does a new instance get its worker id, and what if the registry is down?

At startup it takes a lease on one of 1,024 ids from the consensus-backed registry. It gets back the last timestamp prior owners used, waits if its clock is behind, and renews every third of the TTL. If the registry is down at startup, the process cannot get a safe id, so it should fail closed, or in a documented emergency take an id from a manual reserved range. Running processes keep working until their lease deadline, which is set far longer than typical outages.

How many IDs can one worker make, and how do you go beyond that?

With 12 sequence bits it makes 4,096 IDs per millisecond, which is 4,096,000 per second. Past that it waits for the next millisecond, a built-in throttle. To scale, add workers: each has its own id, so IDs never collide. With 1,024 workers the ceiling is about 4.2 billion per second. If we ever need more, shorten the layout's bits for sequence, use a coarser tick, or go to a wider ID.

Can these IDs tell me which event happened first?

Only approximately. Within one worker, yes, because timestamps never go down. Across workers the order is right only to within clock skew, typically a few milliseconds, so two nearby IDs from different machines can sort the wrong way. For causality you need logical clocks, version vectors or a consensus sequence. I use the ID for pagination and storage locality and a separate mechanism where order must be exact.

Why not a central ID server or database sequence?

It gives exact order and no clock risk, but every ID needs a network call to one machine or one consensus group. At a million IDs per second one database cannot keep up, a consensus group adds milliseconds per ID, and the service becomes a global point of failure. Handing out blocks of numbers reduces load but loses fine time order. Snowflake removes hot-path coordination at the cost of care around clocks and worker ids, which is the better trade here.

How do you migrate from auto-increment IDs to Snowflake IDs?

Make sure the column is a 64-bit BIGINT and have clients treat IDs as opaque strings so JavaScript does not lose precision. Start giving new rows Snowflake IDs while old rows keep small integers. Because the timestamp sits in the high bits, new IDs are far larger than old ones, so rough order is kept. Dual-read for a while and move foreign keys step by step. Rewriting old rows is optional and needs a coordinated migration of every reference.

Is it a problem that IDs reveal time and worker?

It can be. Two IDs let anyone estimate how many records were created between them, which hints at business volume, and the worker bits hint at topology. For internal keys that is usually fine. For public identifiers, accept it, encrypt the ID at the API edge, or expose a separate random public id. In all cases check authorization on every access, because a guessable ID with no access check is a vulnerability whatever the generator.

Production incident: duplicate-key errors start appearing on a generated-ID column. What do you do?

Treat it as a likely worker-id collision. Decode the clashing IDs and read the worker field and timestamp. Check the registry for two live leases or a recent reassignment of that id, and check for a long garbage-collection pause or a partition on the old owner. Stop the suspect process, which releases its lease, and make sure the survivor waited out the high-water mark. Then look at clock rollback events on that host, repair the affected rows, and tighten the quarantine or self-expiry margin if they were too small.

When would you pick UUIDv7 or a ticket server instead?

UUIDv7 when 128 bits are acceptable: it removes the registry and the worker-id problem, and a rollback only misorders IDs rather than duplicating them. A ticket-server pair or block allocator when the team is small, the rate is modest and 64-bit ordered IDs are enough with little infrastructure. I would start there and move to Snowflake when the extra hop or key width starts to cost money.
