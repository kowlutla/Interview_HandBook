Case 21: Design a Distributed Lock Service

A Chubby, ZooKeeper or etcd style service that lets many processes agree on who holds a lock right now, and stays correct when clocks drift, processes pause and the leader dies.

1 Problem 2 Requirements 3 Estimation 4 API 5 Data 6 Architecture 7 Deep dives 8 Scaling 9 Failures 10 Impress 11 Q&A 12 Links

1. Problem in 3 lines

One line: a small, strongly consistent, highly available cluster that hands out locks, leader elections and tiny config values, where the answer to "who holds the lock?" must never be wrong.
  • Many independent processes need to take turns on a shared thing (a job, a leader role, a file).
  • A lock is not a database and not a work queue. It is small, read-heavy and long-held (seconds to days).
  • The hard part is not the lock table. It is staying correct when a holder freezes, the network splits or the service leader dies.

Clarifying questions to ask

AskAssume
Lock for efficiency (avoid duplicate work) or correctness (protect data)?Both. Correctness forces fencing tokens.
How many clients and locks?About 50,000 client processes, about 1 million lock or config nodes, few contended at once.
How long are locks held?Seconds to hours; leader locks for days. Millisecond critical sections do not belong here.
Consistency or availability?Never two live holders. Stay up while a majority of replicas is reachable. Choose consistency (CP).
Can we trust clocks?No wall clocks, no bound on pauses. Only that clocks run at nearly the same rate.
Regions? Fairness?One cluster per region by default; first come first served among waiters.
Say this early: "A lock with a timeout can never be perfectly safe alone, because the holder can be paused right after it checks the lock. So the design is a lease plus a fencing token that the protected resource enforces."

2. Requirements

Functional

  • Sessions kept alive by heartbeats; locks, ephemeral nodes and watches belong to the session
  • Acquire (wait with timeout), TryAcquire, Release, implicit renew
  • FIFO queue of waiters
  • Fencing token that strictly increases per lock
  • Ephemeral nodes (vanish when the session ends)
  • Watches (be told about changes, no polling)
  • Linearizable reads and cheaper stale reads

Non-functional

  • Safety first: one valid holder per lock
  • 99.99% write availability: survive 1 replica or 1 zone down (5 replicas)
  • Uncontended acquire under 10 ms p99 in a region
  • Dead holder freed within session TTL (10 to 30 s)
  • An acknowledged grant survives any minority failure
  • Read heavy: many reads, heartbeats, watchers

Out of scope

  • General database or multi-key transactional store
  • Task queue
  • Rate limiter (see case 3)
  • Client business logic
  • Auth only briefly (mutual TLS plus path ACLs)

Key conclusion: the 10,000 heartbeats per second must NOT go through the Raft log, or they would eat most of the write budget. One Raft group is enough, so we do not shard the core (keeps cross-lock atomicity simple). The real engineering is the read, heartbeat and watch path, not the write path. Latency check: zone round trip about 1 ms, batched fsync 1 to 2 ms, so a commit takes about 3 to 6 ms.

4. API (a few lines)

CreateSession(ttl_ms)  KeepAlive(session)  CloseSession(session)
Acquire(lock, session, wait_ms, mode)  -> { granted, fencing_token }   // EXCLUSIVE | SHARED
TryAcquire(lock, session, mode)        -> { granted, fencing_token, holder? }
Release(lock, session, fencing_token)
Create(path, value, ephemeral, sequential, session)   Get(path, consistency)
Set(path, value, expected_version)   Delete(path, expected_version)   // compare and set
Watch(path|prefix, from_revision)    -> stream of events
Txn(compares[], ops[])               // small atomic multi-op
consistency: LINEARIZABLE | SERIALIZABLE (follower, maybe stale)
  • One long-lived multiplexed stream per client carries heartbeats and watch events.
  • Release carries the token so a delayed release from an old holder cannot free a newer holder's lock.
  • expected_version makes writes compare-and-set, so retries are safe (idempotent).
  • Every response has a revision (the log index). A watch resumes exactly from last_seen + 1.
  • Acquire with wait_ms is parked on the server and answered at grant time. No polling.

5. Data model and store choices

RecordFieldsWhy
Sessionid, ttl, deadline (leader memory only), owned keysCreate and close are log entries; deadline extensions are not.
Nodepath, value, version, create and mod revision, owner sessionOne tree gives locks, config and membership a single namespace.
Lockname, holder, fencing counter, ordered waiter listCounter only goes up and survives restarts because it lives in the log.
Watchstream, path, next revisionMemory on the serving replica; not replicated.
Revision historylast N changesLets a watch resume; compacted regularly.
  • Store: an embedded engine (B+tree or append log with in-memory index) on each replica, plus a replicated write-ahead log and snapshots. No external database: the lock service is the foundation, and a database that needs a lock service would be a circular dependency.
  • Fencing token: the Raft log index of the grant entry, or a per-lock counter incremented in the same entry. Never from a clock or a per-leader memory counter.

6. Architecture and main flows

Flow A: acquire

  1. Client calls Acquire(lock, session, wait) through its proxy to the leader.
  2. Leader checks the session is live and appends ACQUIRE(lock, session) to its log.
  3. Leader sends it to the 4 followers in parallel; each fsyncs then acks. Leader plus 2 acks is a majority of 5.
  4. Entry commits. On apply: if free, the session becomes holder and the counter goes up (say token 9120). Otherwise it joins the waiter queue.
  5. Granted: reply {granted, token}. Queued: the reply is parked and sent at grant time.

Flow B: session and heartbeat

  1. Create session (a Raft write), TTL 15 s.
  2. Every 5 s a keepalive resets the deadline to now + TTL in leader memory only (no Raft write).
  3. No keepalive before the deadline: leader appends EXPIRE_SESSION. On commit all replicas release the session's locks, delete its ephemeral nodes and grant the next waiters with token + 1.

Flow C: leader failover

  1. Leader dies; followers elect a new one in about 1 to 3 s (majority of votes, new term).
  2. New leader does not know the deadlines, so it sets every session to now + full TTL (Chubby grace idea).
  3. Clients freeze new critical work (jeopardy), find the new leader and reconnect inside a grace window (about 45 s in Chubby). Locks and tokens stay unchanged.
Common mistakes: making every heartbeat a Raft write; deriving the token from a clock; letting a new leader expire sessions at once (mass lock loss); trusting a stale follower read to decide to take a lock.

7. Deep dives

7.1 Fencing tokens: the zombie client

Client A gets token 33, then pauses 40 s (garbage collection). Its session expires after 15 s. B gets token 34 and writes. A wakes up, still thinks it holds the lock, and writes. The fix lives at the resource.

OptionStops zombie?Verdict
Lease timeout onlyNo, a paused client acts after expiryFine only for efficiency locks
Client checks "am I holder?" before each writeNo, the pause happens after the checkNarrows the window, does not close it
Fencing token checked by resourceYes, whatever the pauses and clocksOur choice for correctness locks
Compare-and-set on the data, no lockYesBest when the store supports it

Choice and why: tokens come from the replicated log, so two holders never get equal or reversed tokens, even across leader changes. "Highest token wins" is a total order the resource enforces without trusting any clock. In SQL: UPDATE t SET v=?, fence=? WHERE id=? AND fence <= ?. The lock gives the right to try; the token proves the right to succeed.

7.2 Sessions, leases and leader failover

OptionProsCons
Each heartbeat is a Raft writeNew leader knows exact deadlines10,000 extra writes per s, about 5x normal load
Leader memory plus grace reset on failoverNo log load; matches Chubby and etcdDead sessions found up to one TTL later after a failover
Batched deadline checkpoints through the logBounds the post-failover errorExtra complexity; add only if needed
  • TTL 15 s (range 5 to 60), heartbeat every TTL / 3: two heartbeats may be lost before expiry. Short TTL (3 s) detects fast but causes false expiry on GC pauses; long TTL (60 s) is calm but leaves dead locks stuck.
  • Clocks: the server and client each use their own monotonic clock. The client counts from when it sent the keepalive and subtracts a drift allowance, so it stops using the lock before the server frees it. Only equal clock rate is assumed, never matching wall time.
  • Rule: a new leader must never expire a session earlier than the old leader could have. Resetting to a full TTL guarantees that.

8. Scaling and bottlenecks

One line: writes are not the bottleneck (6,000 per s peak is a fraction of one group). Connections, heartbeats, reads and watch fan out are.
  • Heartbeats off the log (10,000 per s served from leader memory).
  • Edge proxy tier terminates 50,000 streams and multiplexes them into few connections. Coalesced watches: 30 proxies, so 30 events not 2,000 or 40,000.
  • Followers and observers (non-voting replicas) serve reads, raising read capacity without slowing writes or changing fault tolerance.
  • Client caching with invalidation for config nodes.
  • Herd on a hot config watch: put the new value in the event, fan out through proxies, add client jitter, rate limit watch registration.
  • At 10x (500,000 clients): about 100 proxies, 5M watches (coalescing mandatory), 20,000 writes per s so shard locks by prefix into several Raft groups (with a session owner design), 10 GB state needs incremental snapshots, per-tenant isolation.
  • Multi-region: regional 5-node clusters by default (3 to 10 ms writes). A global group across 3 regions costs 70 to 150 ms per write but survives a region loss, so use a small global cluster only for true singletons. Never async active-active locks: both sides could grant the same lock.
  • Phasing: adopt etcd or ZooKeeper plus a thick client library first; then proxies, quotas, ACLs; then observers, shared locks, multi-region; sharding last.

Split brain: the table cannot have two committing leaders, since two disjoint majorities do not exist. The remaining risk is at the application level (a stale client acting as holder), and the token settles it.

10. Things to say to impress

Senior and lead level points:
  • "The lock gives the right to try; the fencing token proves the right to succeed."
  • "Heartbeats are 10,000 per s, so they live in leader memory, not in the log. A new leader resets every deadline to a full TTL."
  • "Writes are only about 20 to 60 percent of one group at peak; the real scaling work is reads, watches and connections, so I add a proxy tier and observers, not shards."
  • "Redis SET NX is fine for efficiency locks such as cron dedupe. Redlock has no fencing token and leans on timing assumptions. For correctness I use consensus plus fencing, or a compare-and-set on the data."
  • "Often the best answer is no lock: idempotent operations, optimistic versions or a single-writer queue."
  • "I would run etcd or ZooKeeper behind a thick client library, since most lock bugs are in clients (jeopardy callbacks, cancelled handles, safe retries)."
  • "I would test with Jepsen-style faults: partitions, pauses, clock skew, leader kills; check tokens strictly increase and history is linearizable."
  • Five replicas over three zones (2, 2, 1): any zone loss keeps a majority of 3. Alert on leader changes (more than 1 per 10 min), fsync p99 above 50 ms, session expiry spikes.

11. Interview Q&A

Can a lock with a TTL ever be perfectly safe on its own?

No. The holder can check the lock and then stall for a long garbage collection, a VM pause or a delayed network write, longer than the TTL. Meanwhile the lock moves to another client, and when the first client wakes it acts on a stale belief. The service cannot see or stop this. The fix is to make the resource take part: every grant carries a fencing token from the log, and the resource rejects any request with a token lower than the highest it has seen. The lock gives mutual exclusion in normal cases, and the token gives it in the worst case.

Why are heartbeats not written through Raft?

With 50,000 sessions and a 5 second interval that is 10,000 extra writes per second, each needing a disk write and a majority round trip. That would use most of the group's capacity and fill the log with data that has no long-term value. So the leader keeps deadlines in memory. The price is that a new leader does not know them, so it resets every session to a full TTL and clients get a grace window to reconnect. Dead holders are noticed a little later after a failover, which is a fair trade.

What happens to held locks when the leader dies?

Nothing, if the election and the reconnect fit inside the lease and grace windows. The committed lock table is on a majority, so the new leader has it. It gives each session a fresh full TTL. Clients see the broken connection, go into jeopardy (no new critical work), find the new leader and reconnect with the same session id. Locks and tokens are unchanged. Only a client that fails to return within TTL plus grace loses its session, and its locks pass to waiters with higher tokens.

How is the fencing token chosen, and why is it monotonic across leader changes?

It is assigned inside the state machine when the acquire entry is applied: either the Raft log index of that entry or a per-lock counter incremented in the apply function. The log is one total order agreed by consensus, and a committed entry is in every future leader's log. So two grants can never get equal or reversed tokens. A wall clock or a per-leader memory counter fails this, since clocks disagree and a new leader would restart its count.

When is a follower read fine, and when is it dangerous?

It is fine for data that tolerates a little staleness: config, service discovery, dashboards, cache refresh. It is dangerous for any read that feeds a decision such as "the lock is free, so I take it", because a lagging follower may show an old holder. Decisions go through the leader with ReadIndex or a write. A middle path is the follower ReadIndex read: the follower asks the leader only for the current commit index, catches up to it and serves locally. That is linearizable and spreads read work.

Why five replicas, not three or seven?

Three tolerate one failure, but during maintenance on one node a second failure loses quorum. Five tolerate two, which is the usual choice for critical infrastructure. Seven tolerate three, but each write needs four acks, adding latency and load, and rarely adds real availability because correlated failures (a zone, a bad deploy) dominate. We spread five replicas over three zones as 2, 2, 1 so losing any zone keeps a majority of three.

How do you stop a thundering herd when a popular lock is released?

Do not let all waiters watch the lock node. Use a server-side queue so a release wakes only the head waiter, or the ZooKeeper recipe where each contender creates a sequential ephemeral node and watches only its predecessor. For config nodes watched by many clients, coalesce watches in the proxy tier, put the new value in the event so there is no follow-up read, and add client jitter. Limiting watch registrations per session protects against a buggy client that opens thousands of watches.

Why not just use Redis Redlock?

Redlock asks five independent Redis masters and needs a majority, but it has no consensus protocol and no fencing token. Its safety depends on bounded network delay, bounded pauses and bounded clock drift, which real systems break. A paused client can still act after its key expired and another client locked. For efficiency locks, like stopping two cron instances running one report, plain Redis is simple and fine. For correctness I use a consensus-backed service with fencing tokens, or skip the lock and use compare-and-set on the data. Also, single-node Redis can lose a just-granted lock if the master crashes before the replica sees it.

How do you handle multiple regions?

Consensus latency equals the round trip to a majority, so a group across regions costs 70 to 150 ms per write. I run a separate cluster per region for regional work, keeping writes at a few milliseconds, and a small global cluster for the few truly global singletons. I would never replicate lock tables asynchronously between regions, because both sides could then grant the same lock. Remote readers can use follower or observer reads for config, where some staleness is acceptable.

How would you test that the service is actually safe?

Use deterministic simulation and Jepsen-style fault injection: random partitions, process pauses, clock rate skew, leader kills and disk stalls, while many clients acquire, write with tokens and release. A checker verifies that tokens strictly increase per lock, that no two accepted writes carry out-of-order tokens, and that the operation history is linearizable. I also test the client library by injecting pauses between the "I hold it" check and the write, to prove the resource rejects the stale token.

Production incident: the leader keeps changing every few minutes. What do you check?

Flapping leaders are usually a slow disk or a pause, not a network issue. I would look at fsync latency first, since a slow fsync delays heartbeats to followers and they time out. Then check garbage collection or CPU starvation on the leader, network drops between zones, and whether the election timeout is too tight for current latency. Each election freezes writes for 1 to 3 seconds and can cause a client retry storm, so I confirm backoff with jitter is working. Short term I move the leader off the slow node and raise the election timeout a little. Long term I put the log on faster dedicated disks and alert on more than 1 leader change per 10 minutes.

Production incident: session expiries spike across many clients at once. Is the service broken?

Not necessarily. A spike usually points to a client or network event: a bad deploy that blocks the heartbeat thread, a zone network blip, or a long failover where clients stayed away longer than TTL plus grace. I check whether the spike matches a leader change, whether keepalive lag on the leader grew, and whether the affected clients share a zone or release. Locks freed this way move to waiters with higher tokens, so safety is intact, but work churns. The fix depends on the cause: isolate the heartbeat thread in the client, tune the TTL above the real pauses, or fix the network.

Why not shard locks across many Raft groups from the start?

Our numbers show one group handles the load, and sharding has a real cost. A session expiry that must release locks across several groups becomes a multi-group operation, and a multi-lock transaction becomes a distributed transaction. So we start with one group and design the session owner record so that sessions could later be homed on one group, with locks routed by hash and expiry fanned out from the owner. We shard only when write volume nears the ceiling, around 20,000 per second at 10x scale.

Why a server-side queue instead of the ZooKeeper sequential-node recipe?

The server queue is faster and exact: one Raft entry grants the next waiter and only that client is woken, with strict first come first served order. The ZooKeeper recipe needs no queue logic in the server and also avoids a herd, since each node watches only its predecessor, but it costs the client more round trips. Because the data model supports both, I make the built-in lock use the server queue and leave the recipe available for barriers and group membership.

What must the protected resource do, and what if it cannot check tokens?

It stores the highest token per object and rejects any mutation with a lower token, then records the new maximum. In SQL that is a conditional update in the same transaction; object stores can use a version or ETag precondition. If the resource cannot be changed, I put a thin gateway in front that does the check. If even that is impossible, I say plainly that the lock is only advisory efficiency protection and should not be used to guard data that must never be corrupted.
