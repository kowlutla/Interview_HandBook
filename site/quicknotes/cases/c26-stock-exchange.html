Case sheet 26: Design a Stock Exchange

The matching core: order book, sequencer, single-threaded engine, market data fan-out, and recovery by replay. Full chapter: handbook case 26.

Problem · Requirements · Estimation · API · Data · Architecture · Deep dives · Scaling · Failures · Impress · Q&A · Links

1. Problem in 3 lines

One line: an exchange takes buy and sell orders from member firms, matches them by strict rules (best price first, then earliest first), and tells everyone what happened, in tens of microseconds, without ever losing an accepted order.
  • We design the exchange itself: gateways, sequencer, matching engine, market data. Not the retail broker app, and not settlement (we only hand a trade record to clearing).
  • Two things make it unlike a web service: fairness (one agreed order of events) and latency (microseconds are the product). So: one thread per order book, no database on the hot path.
  • The core idea in one breath: a sequencer gives every input one number, a single-threaded engine applies inputs in that order, and the output is a pure function of the input log. Replication, recovery, audit and testing all become "replay the log".
Clarifying questionAssumed answer
Asset and style?Cash equities on a central limit order book (CLOB). Price-time priority (FIFO within a price).
Who connects, how many symbols?About 2,000 member firms over persistent binary sessions; about 5,000 symbols, very uneven.
Volume?About 300 M order messages a day (new, cancel, replace) and about 15 M trades.
Latency?Median in the tens of microseconds; working goal p99 under 100 microseconds.
Durability, availability?No accepted order lost (RPO zero). Hot standby takes over in seconds. Trading hours only.
Regions?One primary data centre (participants rent racks next to it), one passive DR site in another metro.

2. Requirements

Functional

  • Place limit and market orders. Time in force: day, IOC (take what you can, cancel the rest), FOK (fill everything or nothing).
  • Cancel and replace. Lowering quantity keeps queue place; changing price or raising quantity goes to the back.
  • Match: best price first, oldest first; trade prints at the resting order's price.
  • Acknowledge: accepted, rejected, partial fill, filled, cancelled.
  • Publish market data with sequence numbers, plus snapshots for late joiners.
  • Controls: tick and lot size, price bands, pre-trade risk, circuit breakers, self-trade prevention.
  • Send trades to clearing and drop copy.

Non-functional

  • Deterministic and fair: same inputs, same outputs; strict arrival order.
  • Low, predictable latency: the tail matters more than the average.
  • Durable and consistent: nothing lost or duplicated; every subscriber sees the same order.
  • Fast failover from an identical hot standby.
  • Auditable: rebuild any book at any past instant.
  • Bursts: open and close auctions at about 20 times average.

Out of scope

  • Broker order management.
  • Clearing and settlement.
  • Listings, corporate actions.
  • Surveillance analytics.
  • Derivatives mechanics such as implied spread matching (mention only).

Key insight: matching one order costs about 1 microsecond, so one core does about 1 M orders a second. Our whole peak (250,000/s) is a quarter of one core. We partition for isolation and safety, not for throughput. The difficulty is latency and durability, not volume.

4. API

No REST. Each member holds a long-lived binary session (FIX, or a compact exchange protocol). TCP keeps each session ordered, and a session sequence number detects gaps after a reconnect.

// member -> exchange
Logon(participant_id, credentials, next_expected_seq)
NewOrder(cl_ord_id, symbol, side, type, price_int, qty, tif, account)
CancelOrder(cl_ord_id, orig_cl_ord_id)
ReplaceOrder(cl_ord_id, orig_cl_ord_id, new_price_int, new_qty)
MassCancel(participant_id, [symbol])        // firm kill switch
// exchange -> member
Accepted / Rejected / Executed(fill_price_int, fill_qty, leaves_qty, liquidity_flag) / Cancelled / Replaced
// exchange -> everyone (UDP multicast)
AddOrder / DeleteOrder / ModifyOrder / Execute / Trade / Halt   (each with seq)
Snapshot(symbol, last_seq, levels)        // separate recovery channel
  • Prices are integers (ticks), never floating point, so comparisons at a price are exact.
  • cl_ord_id (chosen by the member, unique per session per day) is the idempotency key: a resend after a disconnect returns the old result, not a second order.
  • Every outbound message has a sequence number. The liquidity flag says maker or taker, which drives fees.

5. Data model and store choices

The "database" is a data structure in memory plus an append-only file. A database commit costs hundreds of microseconds to milliseconds and adds locks, so none sits on the order path.

DataWhereWhy
Order book per symbolRAM in the engineDerived state: rebuild it from the journal any time.
Input journalAppend-only files on local NVMe, replicated to standby, archived to object storage after closeThe single source of truth. Sequential appends are the fastest disk access.
SnapshotsBinary dump of all books plus journal positionBounds recovery time.
Market data archiveAppend-only files, later a warehouseData sales, analytics, regulator queries.
Reference data (symbols, tick sizes, bands)Small relational DB, loaded into engine memory at start of dayRarely changes, needs audit, never read on the hot path.
Trade and clearing recordsRelational DB fed from the trade streamDownstream needs queries and reconciliation, not microseconds.

Order record (fixed size, in a pre-allocated array, linked by indices not pointers): order_id, participant_id, side, integer price, remaining and original qty, arrival_seq (which is also time priority), prev and next links. No allocation and no garbage collection on the hot path.

Book: each side is a set of price levels; each level is a FIFO queue plus a total quantity. Bids go high to low, asks low to high. Best bid and best ask are cached.

6. Architecture and main flows

The life of one order (buy 300 ACME at 100.01)

  1. Arrive: gateway checks the session sequence and looks up cl_ord_id to catch a duplicate.
  2. Validate and risk-check: tick, lot, price band, order size, firm credit. Rejects stop here and never use a sequence number. Limits are in-memory counters (a few hundred nanoseconds).
  3. Sequence: the sequencer assigns the next number (say 9,000,001) and a timestamp, writes the journal and the replication stream.
  4. Replicate: sent to engine, standby and journal writer. Processed only once durable under our policy.
  5. Match: best ask is 100.01 with D 100, E 400, F 100 queued. D fills 100 and leaves; E fills 200. The buy is done. Trades print at 100.01.
  6. Output: Accepted, two executions, market data (delete D, modify E, trade), all tagged with the input's sequence number.
  7. Deliver: fills go back through the gateway; the publisher multicasts; clearing gets the trade. About 30 microseconds in the target.

Cancel goes through the sequencer like any input. The hash index finds the order, and the doubly linked queue unlinks it in O(1). If a fill was sequenced first, the cancel gets "too late". The sequence number settles every race.

7. Deep dives

7.1 Order book and matching rule

RuleHow it worksGoodBad
Price-time (FIFO)Best price, then earliestSimple, easy to audit, one queue per levelSpeed race for queue place
Pro-rataSplit the incoming size by resting sizesLess of a latency raceEncourages inflated size; rounding rules
HybridPart FIFO, part pro-rataTunableHard to explain and test

Choice: price-time. It is the classic CLOB, maps to the simplest correct structure, and the fairness story is "first in, first out". The allocation function can be swapped per product. Trades print at the resting order's price, so the taker may get price improvement. FOK needs a pre-check (sum available quantity first) so a partial trade never has to be undone. Auctions, halts and stop or iceberg orders are extra states in the same deterministic machine, switched by sequenced messages.

7.2 Sequencer, single thread, low-latency core

OptionResult
Many threads on one book with locksEach lock costs tens of ns to microseconds when contended; results depend on timing. Slower and not repeatable.
One thread owns each book (single writer)No locks, data stays in one core's cache, deterministic. About 1 M orders a second per thread against 250,000 total at peak.

Choice: single writer per book, parallel across symbols. The sequencer is tiny (number, timestamp, append, publish), needs only about 16 MB/s at peak, and has its own hot standby, so it is not a capacity or availability risk.

TechniqueRemoves
Kernel bypass networkingSystem calls and copies, several microseconds a message
Pinned cores, busy-spinContext switches and jitter (burns a core on purpose)
Pre-allocated memory, no GCAllocation time and pauses
Cache-friendly arrays and indicesCache misses (about 100 ns each)
Binary fixed-width protocolText parsing cost
Batch on output onlyPer-packet cost; input is never delayed

Latency budget (median, illustrative): NIC and decode 5, gateway risk 8, sequence plus replicate 10, match 2, encode and send 5, about 30 microseconds. The tail comes from GC, page faults, interrupts, a slow replica in the sync path, or a hash table resizing. Warm everything before the open and watch p99.9 and the max.

7.3 Durability, replay and failover

PolicyAdded latencyIf the primary dies
Local fsync, then processTens of microseconds on NVMeLost machine loses the tail
Replicate to standby memory and journal writer, then processAbout 5 to 10 microsecondsStandby has every acknowledged message
Quorum (Raft style)Tens to hundreds of microsecondsSurvives any single failure; more moving parts
Async onlyLowestAcknowledged orders can vanish: not acceptable

Choice: replicate to the standby's memory and the journal writer, then process. Journal flushes to disk in the background in big sequential batches; the two machines sit in separate power domains. Honest summary: durable means "in the memory of two independent machines", not "on disk".

Determinism rules: no wall clock inside the engine (the sequencer stamps time), no randomness, no unordered iteration that changes output, ids from an internal counter. Primary and standby exchange a rolling hash of outputs every second; a mismatch pages someone.

Recovery: load the newest snapshot (taken on the standby), replay the journal after its sequence number through the same live code path. A 5-minute tail is about 3.8 M events, under 4 seconds.

Split brain: promotion needs epoch N+1 from a small consensus-backed coordinator. Gateways, publisher and clearing reject anything with an older epoch, and the promoter powers off the old machine out of band. If the coordinator cannot be reached, trading halts (consistency over availability).

7.4 Market data fan-out

OptionFairnessCostVerdict
Unicast TCP per subscriberPoor, each has its own queueAbout 160 Gbps at peakOnly for the slow retail tier
Kafka-style log, consumers pullMediumBroker fan-out multipleGood for post-trade, analytics, clearing
UDP multicast with A/B and sequence numbersExcellent, switches copy at equal delayOne copy per pathChosen for trading feeds
  • Sequence numbers show gaps (1,204 then 1,206 means 1,205 is missing).
  • A/B paths: the same stream on two switch paths; the receiver keeps the first copy of each number.
  • Gap recovery: if both copies are lost, ask a retransmission service over TCP.
  • Snapshots: late joiners fetch a book snapshot tagged with a sequence number, then apply later live messages.
  • Heartbeats tell silence from loss. Slow consumers cannot slow the engine: multicast has no per-receiver queue.
  • Tiers: full depth feed, top-of-book feed, and a delayed or conflated retail feed over WebSockets (conflation allowed there only).

8. Scaling and bottlenecks

  • Partition by symbol: 10 partitions of about 500 symbols, each with its own sequencer pair, engine, standby and journal. The map is static during the day; heavy symbols move overnight.
  • Why 10 when one thread could do it? Blast radius (a bug hits 500 symbols, not 5,000), tail isolation, headroom (25,000 per second per partition at peak, about 2.5% of a core), rolling upgrades, independent feeds.
  • Hot symbol: about 12,500 per second is easy. For millions a second, give it dedicated hardware, pipeline the stages, and speed up the single thread. Never split one book across threads (it kills determinism).
  • Gateways scale out by participant. A firm's risk limit is shared by handing each gateway a budget chunk, or by pinning a firm to one gateway.
  • Journal disk: about 0.8 MB/s average, 16 MB/s peak; fsync batching is the limit, not bandwidth.
  • Network: market data switches are the shared resource, sized for opening bursts.
  • Cross-symbol order types (spreads, baskets) must live in one partition or use a coordinator.

9. Failure modes

Gateway crashesSessions drop; orders stay live on the bookReconnect elsewhere, resync by session sequence. Optional cancel-on-disconnect for market makers.

Engine primary diesOutputs stop mid-streamHot standby becomes primary; outputs carry the input sequence number, so duplicates are dropped.

Consistency: per-symbol total order by sequence number; no cross-symbol promise. Wire is at-least-once, effect is exactly-once through cl_ord_id and session sequence. Trade ids come from the input sequence number plus an index, so replay gives the same ids and downstream dedupes. A trade is final; busting is a separate manual event.

10. Things to say to impress

  • "The core is a deterministic state machine: a sequencer fixes order, a single thread applies it, so replication, recovery, audit and testing are all replay."
  • "We do not need threads for throughput. One core does about a million orders a second and our peak is 250,000. We partition by symbol for isolation, not speed."
  • "Durability here means in the memory of two independent machines before we process, with disk flushed in the background. DR is async and is the one case where RPO is not zero."
  • "Averages hide the real enemy. I would watch p99.9 and max, warm all memory before the open, and remove GC and page faults."
  • "Standby divergence is the scary bug, so we hash outputs every second and replay the whole day nightly."
  • "Multicast makes the cost one copy and gives every subscriber equal delay. UDP reliability is rebuilt with sequence numbers, A/B paths, retransmit and snapshots."
  • "Split brain is handled by epoch fencing plus powering off the old primary, and we halt rather than risk two sets of trades."
Traps: using a database or Kafka on the hot path; reading the wall clock inside the engine; floating-point prices; sharding one book across threads; saying "exactly once" without naming cl_ord_id; forgetting that cancel must be as fast as new orders.

11. Interview Q&A

Why is the matching engine single-threaded? Is that not a bottleneck?

Matching for one symbol is sequential, since each order's result depends on the book left by the previous one. Many threads would need locks on the same price levels, and the waiting costs more than the work. It would also make the result depend on thread timing. One thread that owns the data keeps it in its CPU cache, takes no locks, and is repeatable. It can do about a million orders a second, while our whole peak is 250,000. We get parallelism across symbols, where it is safe.

What does the sequencer do, and is it a single point of failure?

It gives each validated message the next number and a timestamp, then appends it to the journal and the replication stream. That number is the official arrival order, so we get fairness, determinism and an audit log. It is one logical point but not one machine: a hot standby holds the same stream, and promotion uses an epoch so the old one is fenced. It only needs about 16 MB per second at peak, so capacity is no worry.

How do you recover after a crash without losing orders?

The journal of sequenced inputs is the truth and the engine is a pure function of it. A message is not processed until the standby and journal writer have it, so every acknowledged order survives. Usually the standby simply becomes primary, since it is already caught up. A brand-new node loads the latest snapshot, which records its sequence number, then replays the journal after that point through the same code as live traffic. With 5-minute snapshots the tail is about 3.8 M messages, a few seconds.

How do you stop the standby from silently diverging?

We enforce determinism by rules: no wall clock, no randomness, no unordered iteration that affects output, ids from internal counters. Then we check it. Primary and standby swap a rolling hash of their outputs every second, so a difference pages us within a second instead of at failover. Each night the day's journal is replayed through the production binary and diffed byte for byte with the live outputs. New releases must pass the same replay on recent production days.

How do you deliver market data fairly to thousands of subscribers?

Use UDP multicast: we send each packet once and the network switches copy it to every subscriber port with the same delay. That keeps the cost at 10 MB per second per feed, not 20 GB per second of unicast. Reliability is added on top with sequence numbers to spot gaps, two independent paths A and B where the receiver keeps the first copy, a TCP retransmit service for rare double loss, and a snapshot service for late joiners. A slow subscriber cannot slow the engine because there is no per-receiver queue.

What if the primary and standby are partitioned but both alive?

That is split brain. We use an ever-increasing epoch from a small consensus-backed coordinator. Promotion needs epoch N+1, and gateways, publisher and clearing reject any message with an older epoch. The promoter also powers off or isolates the old machine out of band. If neither side can reach the coordinator, trading halts. We prefer to stop than to print two different sets of trades.

How do you handle a cancel racing with a fill?

The sequencer decides, with no doubt. If the cancel is sequenced before the order that would match, the resting order is gone and the incoming order does not trade with it. If the fill came first, the order is already gone when the cancel is processed, and the member gets "too late to cancel" plus the execution report. Both messages arrive in the member's session in order, so its own view converges with the exchange.

How would you test an engine like this?

In layers. Property tests generate random order streams and compare trades and the final book with a slow, simple reference (a sorted list), checking no crossed book, quantity conserved, and price-time priority. Replay tests run recorded production days through the new binary and diff outputs. Fault injection kills the primary mid-stream, drops replication packets and delays the standby to check failover and idempotent resends. Performance tests replay at peak and 10x while recording latency percentiles with hardware timestamps, and fail the build if the tail regresses.

Why not a database or Kafka for the order flow?

Both are great for downstream stages like clearing, surveillance and analytics. On the hot path they cost milliseconds from network round trips, broker replication and commit protocols, while our budget is tens of microseconds. We want the book in memory and a local append-only log. So the matching path uses a purpose-built journal, and the same events are streamed into Kafka and a database for consumers that need queries, long retention and many independent readers.

How do you make it fair for members at different distances?

Collocation with equal-length cables from every rack to the gateways and market data switches, so distance does not help anyone. All orders go through one sequencer, so "earlier" is defined in one place. Market data is copied by switch hardware with equal delay, and gateway checks cost the same for everyone. Some venues add a small uniform delay (a speed bump) to blunt the very fastest traders; that is a policy choice we can add at the gateway.

Why pick price-time over pro-rata?

The brief is a classic CLOB. Price-time maps to the simplest correct structure, a FIFO queue per level, and the fairness story is one sentence. Pro-rata splits the incoming size by resting size, which cuts the speed race but encourages inflated orders and needs rounding rules. Because allocation is one function over a level, we could swap it per product, for example for some interest-rate futures.

What changes for a crypto or cloud-hosted exchange?

The logic stays: sequencer, deterministic engine, journal, snapshot and replay. The physical parts change. Without multicast or kernel bypass we publish over WebSockets from a fan-out tier with conflation and accept millisecond latency. A replicated log such as Raft can act as the sequencer so failover is automatic across zones. We get easy scaling for the gateway and data tiers, but must handle noisy neighbours and clock quality, so we use dedicated instances and cloud time sync.

Real-time: the p99.9 latency suddenly jumps from 60 to 900 microseconds. What do you check?

First I check per-stage hardware timestamps to see which stage grew, because the budget is split by stage. Then the usual tail causes: a garbage collection or page fault on the engine (was memory warmed, is swap off), interrupts landing on an isolated core, a slow standby making the sync replication wait, a TCP retransmit on one session, or a hash table resizing. Standby replication lag and journal flush lag are the first two graphs I open. If one partition only, I look at a hot symbol. If it is not fixed fast, I fail over to the standby and investigate on the old primary.
