Case Sheet 22: Decompose an E-commerce Monolith

Take a twelve-module shop that runs as one program on one database, split it into services step by step, never lose an order, and survive Black Friday on the way.

1 Problem · 2 Requirements · 3 Estimation · 4 API · 5 Data model · 6 Architecture · 7 Deep dives · 8 Scaling · 9 Failures · 10 Impress · 11 Q&A · 12 Links

1. Problem in 3 lines

One line: this is not "design a new system". It is "change a running system without stopping the money". The path matters more than the end picture.
  • A nine-year-old Java app (a "monolith": one program, one release) with 12 modules and one PostgreSQL database (about 1.4 TB, 380 tables). Deploys hurt, Black Friday is scary, and the CTO wants microservices.
  • The hard parts: finding the right boundaries, choosing what to extract first and what to leave alone, moving data without losing writes, and keeping checkout correct when one database transaction becomes many services.
  • A big-bang rewrite is rejected. Every step must be reversible within minutes.

Clarifying questions to ask (and the assumed answers)

QuestionAssumed answer
What is inside the monolith?Catalog, search, cart, checkout, orders, payments, inventory, shipping, users, promotions, notifications, reviews.
How is it released?One artifact, 12 instances, release every 2 weeks after a 45-minute build and 3-hour regression. About 60 engineers in one repository.
Data situation?One primary (64 vCPU) plus 4 read replicas. Any module reads any table. Foreign keys cross module lines.
Business pain?A reviews bug took checkout down twice. Promotions cannot ship before Black Friday. Primary at 85% CPU on a normal Friday.
Traffic?Normal 5M sessions a day. Black Friday 20M (4 times), with flash-sale bursts of 2 to 4 times the peak hour.
Rewrite allowed? Team size?No rewrite. Team stays at about 60 to 70, plus a small platform team.
Compliance?Cards are tokenized by an outside payment provider (PSP), so keep PCI scope small. Personal data falls under GDPR.
Deadline?Black Friday in about 11 months. Risky moves freeze from early October.
Say this first: "My first question is whether to do this at all, and how much. Microservices are an organization tool as much as a technical one. I will extract only where independent scaling or deploying pays for the extra complexity, and leave the rest."

2. Requirements

Functional

  • Customer behavior stays identical: browse, search, cart, promo, pay, track, review
  • Each capability has one owning team and one owning data store at the end
  • At every step, traffic can go back to the monolith in minutes

Non-functional

  • Correctness: never oversell beyond tolerance, never charge without an order, never order without payment (or an explicit pay-later state)
  • Availability: browsing 99.95%, checkout 99.9% (about 43 minutes of error budget a month)
  • Latency: product page p99 under 400 ms, checkout submit p99 under 3 s including the PSP
  • Teams ship several times a week with no company-wide freeze
  • Shadow traffic, reconciliation and a rollback plan per phase

Out of scope: a new recommendation engine, replacing the PSP, a new front end, multi-region active-active (only mentioned under evolution), warehouse system internals.

3. Estimation

Use: estimation here finds which parts of the monolith are under real pressure, so we extract those that pay back.

Peak orders15% of 600k = 90,000 an hour25/s, burst 100/s

Key numbers: reads outnumber orders about 8,000 / 25 = 320 to 1 at peak. Order is about 3 KB: 150k a day = 450 MB a day (about 165 GB a year); Black Friday 1.8 GB. Catalog 2M SKUs x 10 KB = 20 GB; hot 200,000 products x 30 KB = 6 GB in cache. Reviews 40M x 1 KB = 40 GB. CDC events (change feed): 600k x 6 x 1 KB = 3.6 GB on Black Friday, trivial for Kafka.
The insight: about 70% of primary query time is reads (catalog, facets, reviews, order history), which can be cached or replicated. Only about 8% is checkout and inventory writes. So extract the read-heavy, low-risk parts first, not the money path.

4. API (a few lines)

The outside API does not change. The gateway keeps the same paths and routes each one to the monolith or a new service.

5. Data model and store choices

ServiceStoreWhy
CatalogPostgreSQL (small) plus a cached document projectionStrong consistency for editors; 20 GB fits easily
SearchSearch engine indexFull text, facets, ranking; rebuilt from catalog events
CartRedis with persistence or key-value storeOne key per user, 333 writes/s is easy
InventoryPostgreSQL (shard by SKU if needed) plus Redis counters for hot SKUsNeeds atomic conditional updates and expiring reservations
OrdersPostgreSQL, partitioned by monthRelational integrity; 165 GB a year is fine
PaymentsPostgreSQL append-only ledgerAuditable; exactly-once effect through idempotency keys
ReviewsDocument store or PostgreSQLRead heavy, simple, eventual consistency is fine
PromotionsPostgreSQL rules plus in-memory rule cacheFew rows, evaluated millions of times
Trap: do not pick a different database for every service. Each new engine is a new on-call skill. Default to PostgreSQL; add a special store only when the load proves the need.

Reporting: the old finance SQL join across orders, payments and shipping is gone. Stream events to a warehouse and tell the business early.

6. Architecture and main flows

Shape: an API gateway in front, services owned by teams, Kafka for events, one store per service, and a shrinking monolith behind the gateway.

Boundaries and team ownership

  • Split by bounded context (a zone where a word has one exact meaning), not by table or layer. "Product" means rich content in catalog, a stock count in inventory, a frozen-price line in orders, a weight in shipping.
  • Teams: Discovery (catalog, search), Engagement (reviews, notifications), Buy (cart, checkout saga), Pricing (promotions), Fulfilment (inventory, shipping), Orders, Payments, Platform (gateway, CI/CD, Kafka, mesh, observability), plus a residual core team. Rule: one team owns each database and carries its pager.
  • Do not split: order and payment record keeping at first (one transaction); pricing, tax and rounding (one function, or you get a one-cent mismatch at payment); order header and lines (one aggregate); tiny CRUD such as wish lists and store locator; the admin back office.
  • A boundary is justified when at least two are true: different scaling, different change speed, different failure tolerance, different team.

Flow A: extract one context (strangler fig)

  1. Put the gateway in front of the monolith with 100% of traffic still going to it. Nearly risk free.
  2. Make the boundary visible in the monolith: move code behind an interface and find every SQL statement from other modules that touches its tables.
  3. Break cross-boundary foreign keys (plain id plus an application check) and replace joins with two queries or a copy. An order line stores title and price at purchase time, which is also correct behavior.
  4. Start CDC (reads the database log, emits every committed change in order), then backfill history in throttled chunks, then apply the buffered changes, then verify.
  5. Shadow reads: send to both, answer from the monolith, compare. Exit when mismatch is under 0.01% for a week.
  6. Canary reads (1%, 10%, 50%, 100%), then move writes behind a flag with reverse replication kept for 2 weeks, then delete the old code and table.

Flow B: checkout saga

  1. Price the cart, apply promos, freeze totals (no side effects).
  2. Reserve stock for 10 minutes.
  3. Create the order as PENDING (event written to the outbox in the same transaction).
  4. Authorize (hold, not capture) payment with the order id as idempotency key.
  5. Commit stock, mark order CONFIRMED. After this, move forward only.
  6. Emit OrderConfirmed; notify, ship, capture payment at shipment. Failures go to a dead-letter queue and a human work queue.

7. Deep dives

7.1 Data migration: dual write versus CDC and outbox

OptionHowProblem or benefit
Dual writeApp writes old DB, then new storeNot atomic. A crash or a timeout that actually succeeded makes the stores differ silently; two writers can apply in different orders. Only a short, monitored phase with reconciliation.
CDC (change data capture)Read the database log, publish every committed change in commit orderNo app change, works on the untouched monolith. Best for early phases.
Transactional outboxInsert an event row in the same transaction as the business row; a relay publishes itNo event for a rolled-back order, no lost event for a committed one. Delivery is at least once, so consumers must be idempotent.

Choice: CDC for table-level sync and the outbox for deliberate business events like OrderPlaced. One source of truth per entity, the other side derived. Backfill order: start CDC first (Kafka keeps the changes), copy history in chunks (for example 5,000 rows, pause when replica lag passes 5 s) from a replica, upsert only if the version is newer, apply buffered events, verify until the diff is zero.

7.2 Checkout: saga versus two-phase commit, and orchestration versus choreography

OptionProsCons
Two-phase commitLooks like one transactionThe PSP cannot join; locks held over a slow call; coordinator failure blocks everyone
Choreography (events chain)No central part, loose couplingFlow spread over five codebases; hard to see where an order is stuck
Orchestration (one state machine)One place shows the flow; explicit timeouts and retries; easy to observeCentral dependency, must be highly available; keep business logic out of it

Choice: a saga (local steps plus undo steps). Orchestrate checkout (five participants, money, support must explain it). Choreograph the fan-out after confirmation. Persist saga state after every step.

Inventory reservation: one atomic statement, UPDATE stock SET reserved = reserved + :q WHERE sku = :s AND on_hand - reserved >= :q. Zero rows changed means not enough stock. Reservations expire after 10 minutes; a sweeper frees them. All three calls are idempotent by reservation id.

Hot SKU optionTrade-off
Row conditional update (default)Exact and simple; about 1,000 to 3,000 updates/s on one hot row
Redis counter in frontVery fast; second source to reconcile
Split stock into buckets10 buckets of 100 scale 10x; small false "sold out" near zero, so fall back to other buckets
Waiting roomBest experience at extreme demand; needs product work

Choice: row update for 99.9% of SKUs; buckets plus a waiting room for flagged flash-sale SKUs. Oversell tolerance only for low-value backorderable items.

7.3 Reads: API composition versus CQRS read models

OptionGood forCost
API composition (BFF calls owners in parallel, timeout each, hide what fails)Fresh, cheap data: live price, buy-button stock, cartPage needs five calls: 8,000 views/s become 40,000 internal calls/s; tail latency grows
CQRS read model (one denormalized product-view document built from events)Slow-changing shared content: title, images, rating, price band, coarse availability; one cached key per pageEventual consistency (usually under a second, unbounded in incidents); needs a projector

Choice: both. Say what may be stale: stars and descriptions, 60 seconds is fine; price and stock at add-to-cart and checkout are re-checked with the owners. Read-your-writes (order placed, "My orders" empty) is fixed by rendering confirmation from the saga response or merging the latest orders from Orders for the first minute. A read model can always be rebuilt by replaying the log (keep 7 days in Kafka plus a snapshot).

7.4 Order of extraction

WaveWhatWhy now
0Gateway, tracing, CI/CD, Kafka, CDC, read-replica offloadTools first; replicas alone drop primary load
1Notifications, Reviews, Search, read-only CatalogLow coupling, low risk; primary CPU 85% to about 50%
2Cart, Promotions, Inventory, Shipping, mesh and mTLSMedium risk; build the reservation protocol
3Saga, Orders, PaymentsHighest risk, last; canary 1% of staff orders, then 1% of customers; stop at the freeze

Extract the read path before the write path: a wrong read-only service just falls back, and nothing was changed.

8. Scaling and bottlenecks

  • Primary database: move reads to read models, cache and replicas first; shrink the 64-vCPU primary later.
  • Product pages: read model plus cache plus CDN with TTL 30 to 60 s; pre-warm the hot 200,000 SKUs; coalesce requests and add TTL jitter to avoid a thundering herd.
  • Hot SKU: buckets, Redis counter or waiting room (7.2).
  • Autoscaling: takes minutes, a flash sale ramps in seconds, so pre-scale catalog, search and gateway before Black Friday.
  • Timeout budget: client 3,000 ms, gateway cut at 3,000, orchestrator 2,500. Steps: price 200, reserve 300, order 200, PSP 1,500, confirm 200 = 2,400 ms. Typical request is about 700 ms. Past the budget the client gets "processing" and a status URL.
  • Mesh: adopt at wave 2, with more than five services; adds about 1 ms a hop and 10 to 20% CPU.
  • At 10x: shard Orders and Inventory, use cells (each cell serves a slice of customers), go multi-region with money paths pinned to a home region per customer.
Cost and reality: about 30 to 60% more infrastructure; a platform team of about 6 (10% of engineers); under about 30 engineers a modular monolith is usually better; 11 months for nine contexts is aggressive (real programs take 2 to 3 years). Honest end state: 9 to 11 services plus a residual core, and that is a good result.

9. Failure modes

What failsWhat happensFix
Gateway down or misroutedEverything unreachable, or traffic goes to an unready serviceMulti-AZ, health-gated routes, config as code with staged rollout, one switch for "all to monolith"
Inventory slow (p99 100 ms to 2 s)Checkout threads pile up300 ms timeout, separate pool (bulkhead), circuit breaker, "try again" message, cached availability on browse

Orchestrator crash mid-sagaStock reserved, payment held, order PENDING foreverState saved per step; recovery worker resumes; reservations expire; stuck-saga alert after 5 minutes
Duplicate eventDouble email or double decrementIdempotent consumers keyed on event id

Poison messageOne partition blockedBounded retries, then dead-letter topic with an owner

Trap: "we can always roll back" is false after writes move, unless reverse replication (new store back to legacy) or cohort-based cutover is tested. Plan it before moving writes.

10. Things to say to impress

  • "Two of the six pains need no microservices: read offloading and a modular monolith. I separate problems that need a network boundary from those that need discipline."
  • "Teams first, boundaries follow (Conway's law). One team owns each database and its pager."
  • "Routing rules at the gateway give me canary, shadow traffic and instant rollback. Step zero changes no behavior."
  • "No long-lived dual writes. One source of truth, the other side derived from its log. Outbox for deliberate events."
  • "Saga with a pivot point, atomic conditional reservations with a TTL, and idempotency keys from browser to PSP."
  • "I will say which data may be stale and which must not: stars 60 seconds, price and stock at checkout authoritative."
  • "Observability and contract tests ship before the first extraction; the 3-hour regression is retired. Alert on SLO burn rate."
  • "At most two extractions at once, freeze in October, and if wave 3 slips Black Friday still runs on a proven state with money in the monolith."
  • "Security: the card goes straight to the PSP, so only Payments is in scope; mTLS between services; per-service database credentials; user erasure is a saga too."

11. Interview Q&A

How do you decide service boundaries, and how do you know you got them wrong?

I begin with domain analysis, such as event storming with the business, to find where the meaning of words changes. Then I label subdomains as core, supporting or generic and match them to teams. A good boundary means most changes touch one service, it has one owner and a small stable API. Warning signs: two services that always change and deploy together, a chatty pair making dozens of calls per request, or a service that needs another one's tables. The usual fix is to merge them back. That is cheap early and expensive late, which is why I extract low-coupling contexts first and learn from them.

Why start with Reviews and Notifications instead of Checkout, where the pain is?

The first extraction teaches you how to extract, so a mistake should be cheap. Reviews and Notifications are loosely coupled, can degrade, and are off the money path, so a bug costs some stars, not orders. They still bring value: reviews caused two checkout outages through shared pools, and about 70% of primary query time is read traffic we can move. By the time we reach checkout we already have a gateway, CDC, tracing, contract tests and a practiced rollback, all proven on harmless traffic.

How do you move data with no downtime and no lost writes?

For each context I make the boundary explicit in code, cut foreign keys and joins, and start CDC so changes are captured in commit order. Then I backfill history in throttled chunks with version-checked upserts, apply the buffered changes, and run a verifier that compares both sides. Reads switch first in shadow mode; writes switch later behind a flag, with reverse replication for a rollback window. I avoid long dual writes because the two writes are not atomic and will drift. For business events I use the outbox so the event commits with the state change.

Payment is authorized but the Orders service is down. What happens?

In my ordering the order is created as PENDING before payment, so Orders failing at step 3 releases the reservation and returns an error without ever calling the PSP. If Orders fails after authorization, at the confirm step, the orchestrator retries the idempotent confirm while the budget allows and then answers "processing". If it still cannot finish, the compensation voids the authorization and releases stock. A reconciliation job that compares PSP authorizations with confirmed orders catches anything that slips through and voids orphan holds.

How do you prevent overselling in a flash sale?

Reserving is one atomic conditional update that only succeeds if available stock covers the quantity, so two buyers cannot both win the last unit. Reservations expire after about 10 minutes so abandoned carts give stock back. For one very hot SKU, a single row tops out near a few thousand updates a second, so I split the stock into buckets or put a waiting room in front that admits buyers at a rate the system can handle. A nightly audit compares on-hand, reserved and committed counts with orders, and the business sets oversell tolerance only for backorderable items.

Why orchestrate checkout but choreograph what comes after?

Checkout is a short ordered process with money, undo steps and strict timeouts, and someone must be able to ask "where is this order stuck?". One state machine answers that and makes timeouts visible. After confirmation, many consumers react on their own (email, shipping, analytics, loyalty) and none affects the others, so adding one should not touch checkout code. My rule: orchestrate a business transaction with compensations; choreograph a fan-out of independent reactions.

How does a product page stay fast when its data lives in five services?

Most of it need not be fetched live. I project catalog content, rating summary, promo badge and coarse availability into one product-view document, updated by events and cached behind the CDN with a short TTL, so a page reads one key. Only volatile, decision-critical fields such as current price and buy-button stock are composed in parallel at request time with tight timeouts and fallbacks. This keeps 8,000 page views a second from turning into 40,000 internal calls a second, and a reviews outage just hides the stars.

What is the biggest risk and how do you control it?

Technically it is moving the write path of orders, stock and payments without losing or duplicating anything. I control it by ordering work from low to high risk, shadow testing before switching, daily PSP reconciliation, canary by cohort, at most two extractions at once, and a freeze in October so Black Friday runs on a state we proved. Organizationally the risk is a distributed monolith. I counter it with team-aligned boundaries, contract tests, and a review for every new synchronous dependency.

A query used to be a SQL join, for example "orders with product titles and shipping status". Now what?

In order of preference: first, copy the data at write time (the order line stores title and price at purchase, which is also correct behavior). Second, build a CQRS read model from order and shipping events so history is one lookup. Third, for rare internal questions, compose in the BFF or use the analytics warehouse. I would not give services a shared read replica to join across, because that rebuilds the schema coupling we are removing.

When would you tell a company not to do this migration?

If the team is under about 30 engineers, the pain is mostly code organization, there is no CI/CD, tracing or container platform, or the scale is modest. A modular monolith with enforced boundaries, a read replica for reporting and a clear ownership map gives most of the benefit for far less cost. Microservices pay off when independent scaling, release speed and failure isolation are real, measured needs. I would say this plainly to the CTO with the numbers from the estimate.

How do you stop new services from re-creating coupling with the monolith?

All access goes through an anti-corruption layer with a narrow, versioned interface, and calls to it are counted on a dashboard with a target of zero. The monolith's tables are read-only (or closed) to the new service's credentials, so a direct query fails in test. Each extraction ends by deleting the old code in the monolith, not just switching it off, because dead but reachable code is how the old path quietly comes back.

Production incident: after cutting reads over to the new Catalog service, prices on some pages look wrong. What do you do?

First flip the gateway route back to the monolith, since reads were extracted before writes and nothing in the old tables changed. Then check the parity dashboard and CDC lag to see whether the read model is behind or the projector has a bug. Customers are protected because the checkout price always comes from Pricing, not from the read model. I fix the projector, replay events from the log to rebuild the view, rerun shadow comparison until the mismatch is under 0.01% for a week, and only then canary again.
