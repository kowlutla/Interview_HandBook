Scaling the stateless tier: load balancing, proxies, gateway, CDN, rate limiting

0. Key definitions (know these cold)

TermDefinition in simple words
Stateless serviceA server that keeps nothing about a user between requests. Any copy of the server can answer any request, because everything it needs comes with the request or sits in a shared store.
Vertical scaling (scale up)Buy a bigger machine: more CPU, more memory. Simple, but there is a ceiling and one machine is one point of failure.
Horizontal scaling (scale out)Add more machines of the same kind and share the work. No hard ceiling, but you now need a way to spread the work (a load balancer) and your code must not depend on one machine.
Throughput / latencyThroughput is how many requests per second we finish. Latency is how long one request takes. Tail latency (p99) is the time that 99 out of 100 requests beat; the slowest 1% are worse.
BottleneckThe one resource that fills up first (CPU, memory, disk, network, a database, a lock). Making anything else faster does not help until you fix this one.
Load balancer (LB)A front door that takes incoming requests and hands each to one of many identical servers, and stops sending to dead ones.
Layer 4 / Layer 7L4 balances by looking only at network details (IP and port), so it is fast and blind to content. L7 reads the HTTP request (URL, headers, cookies), so it can route by path and do more, at higher cost.
Health checkA small regular test (for example GET /health) that tells the LB whether a server is fit to receive traffic.
Sticky session (affinity)Sending the same user to the same server every time. Convenient for servers that keep state, but it makes spreading load uneven and hurts failover.
Forward proxyA middleman that sits in front of clients and talks to the internet for them (company web filter, VPN-like use). The server does not see the real client.
Reverse proxyA middleman that sits in front of servers and receives requests on their behalf (nginx, Envoy, HAProxy). The client does not see the real server.
API gatewayA reverse proxy with extra jobs for APIs: login checks, rate limits, routing, request shaping, metrics. One front door for many services.
BFF (backend for frontend)A small gateway-like service built for one kind of client (mobile, web) that gathers and shapes data just for that client.
CDN (content delivery network)A worldwide set of servers that keep copies of your content close to users, so most requests never travel to your own servers.
Edge / POP / originThe edge (or point of presence, POP) is a CDN site near users. The origin is your own server the CDN fetches from when it has no copy.
Cache hit / miss at the CDNHit: the edge has a fresh copy and answers itself. Miss: it must go back to the origin.
Rate limitingCapping how many requests a client may make in a time window, so one user cannot hog or break the system. Over the cap gets HTTP 429.
Token bucketA bucket that refills with tokens at a steady rate up to a maximum; each request takes a token. Allows short bursts while holding the long-run average.
Fail open / fail closedWhen the limiter itself is broken: fail open lets traffic through (risk: no protection), fail closed blocks it (risk: outage caused by the limiter).
Backpressure / load sheddingTelling callers to slow down, or deliberately dropping some requests, so the system stays healthy for the rest.
Connection drainingWhen removing a server, stop giving it new requests but let the current ones finish.

1. Scalability and stateless design Ch 08

One line: make the web tier stateless so you can add or remove identical servers freely; push state into shared stores; find the real bottleneck before you add hardware.

How it works

Scalability means the system keeps working well when the load grows. First we say what "load" is (requests per second, number of users, data size, read to write ratio), then what "well" is (for example p99 under 300 ms). Scaling out is only easy when servers are interchangeable. That is why we keep servers stateless: the user's login session, shopping cart and uploads must not live in the memory or disk of one server.

Where session state can go

OptionHowGood forWatch out
Sticky sessionsLB pins a user to one server that keeps the session in memoryQuick fix for old appsUneven load; session lost when the server dies; hard to drain
Shared session storeSession in Redis or a database; servers fetch it by idDefault for most web apps; easy to revokeExtra network hop; the store must be highly available
Client-side tokenSigned token (for example a JWT) carries the session in the requestTruly stateless servers; scales easilyHard to revoke before expiry; size grows; must be signed and short-lived

Scaling reads versus writes

ToolsNotes
ReadsCaches, CDN, read replicas, precomputed viewsEasy: copies of data are cheap. The price is staleness.
WritesSharding (split data across machines), queues to smooth bursts, batching, fewer indexesHard: every write must reach the owner of the data. Plan this early.

Why ten machines are not ten times faster

Amdahl's law: if a part of the work cannot be split (a lock, a single database, a serial step), that part caps the speed-up. If 5% of the work is serial, even infinite machines give at most 20 times. The Universal Scalability Law adds that machines also need to talk to each other, so after a point more machines make it slower. Say this when asked "why not just add servers".

Finding the bottleneck

SignalLikely saturated resourceTypical fix
CPU near 100%, latency risingCPUOptimise hot code, add servers, cache computed results
Many threads waiting, CPU lowA slow dependency (database, remote call)Timeouts, caching, connection pool tuning, async calls
Memory climbing, long garbage-collection pausesMemoryFix leaks, shrink objects, bigger heap or more servers
Disk wait highDisk I/OFaster disks, caching, batch writes
Network at line rateBandwidthCompression, CDN, bigger links

Concurrency models in one table

ModelHow it worksGood forWatch out
Thread per requestOne OS thread handles one request, and blocks while waitingSimple code, moderate loadThousands of threads cost memory and context switches
Event loopOne thread watches many connections and runs code only when data is ready (Node, nginx)Many idle connections, I/O-heavy workOne slow CPU task freezes everything on that loop
Lightweight threadsCoroutines, goroutines, virtual threads: cheap threads managed by the runtimeSimple blocking-style code at high concurrencyStill limited by the downstream resource
Numbers: thread pool size for CPU-bound work is about the number of cores; for I/O-bound work it is about cores × (1 + wait time / compute time). Little's law: requests in flight = arrival rate × time per request (200 req/s × 0.1 s = 20 in flight). A queue that is allowed to grow without limit only hides overload and raises latency; bound it.
Trap: saying "we will just add servers". Name the bottleneck first. If the database is the limit, ten more web servers only send it more traffic. Also: a "stateless" service that keeps a local cache or a local file upload is quietly stateful.
Say: "I keep the web tier stateless: sessions in Redis or a signed token, files in object storage. That lets me scale horizontally behind a load balancer, and I find the bottleneck with metrics before adding capacity."

2. Load balancing Ch 09

One line: a load balancer spreads requests over healthy identical servers, hides failures from users, and gives you one stable address.

Layer 4 versus layer 7

Layer 4 (transport)Layer 7 (application)
SeesIP addresses, ports, TCP/UDPURL, headers, cookies, method, body
SpeedVery fast, millions of connections, little CPUSlower, needs to parse HTTP and often ends TLS
Can doSpread connections, health checks, pass-through TLSRoute by path or host, rewrite, retry, sticky by cookie, canary, auth
Use whenNon-HTTP protocols, raw speed, a first tier in front of L7HTTP APIs and microservice routing (the common case)
Do not use whenYou must route on content; HTTP/2 or gRPC where one connection carries many requestsExtreme connection counts where CPU is the limit

A typical big setup is two layers: an L4 balancer spreads load over a fleet of L7 proxies, which route to services.

Algorithms

AlgorithmIdeaUse whenDo not use when
Round robinTake servers in turnEqual servers, similar short requestsRequests vary a lot in cost
Weighted round robinBigger servers get more turnsMixed machine sizesWeights go stale
Least connectionsSend to the server with the fewest open requestsLong or uneven requests, websocketsMany LB nodes each see only part of the picture
Least response timePrefer the fastest serverSlow servers should get lessNoisy measurements can cause herding to one server
Power of two choicesPick two at random, send to the less loadedLarge fleets, many LB nodes; nearly as good as global least-load with no shared stateTiny fleets
IP hashHash client IP to a serverCheap stickinessMany users behind one NAT; changes when the server list changes
Consistent hashingHash a key onto a ring; each server owns an arc; adding a server moves only a small share of keysCaches and sharded data where the same key must hit the same nodePlain stateless services (needless)
RandomPick anySimple, surprisingly good with many requestsSmall numbers: can be unlucky

Health checks, draining, slow start

  • Active checks: the LB calls a health URL every few seconds. Passive checks: the LB watches real traffic and ejects a server after several errors or timeouts. Use both.
  • Thresholds: mark down after, say, 3 failures in a row and up after 2 passes, so one blip does not flap a server in and out.
  • Shallow versus deep check: a shallow check says "the process is up". A deep check also tests the database. If every server checks the shared database and it blips, all servers go "unhealthy" together and you have made an outage. Keep the check light, or have the LB stop ejecting when too many servers are down (panic mode).
  • Slow start: a new server gets a rising share of traffic, because a cold one (empty caches, cold JIT) falls over under a full share.
  • Connection draining: on deploy or scale-in, stop new requests, let in-flight ones finish (with a time limit), then stop the server.

TLS: terminate or pass through

ChoiceMeaningProsCons
Terminate at LBLB decrypts, talks plain or re-encrypted to serversL7 features, central certificates, less CPU on serversTraffic inside is plain unless re-encrypted
Pass throughLB forwards encrypted bytes untouchedEnd-to-end encryption, simpleLB cannot read HTTP, so no path routing

Connections and HTTP/2

Opening a connection (TCP plus TLS) is costly, so LBs keep a pool of warm connections to servers and reuse them (keep-alive). With HTTP/2 and gRPC, one connection carries many requests. An L4 balancer picks a server once per connection, so all of that client's calls pile onto one server. Use an L7 balancer that spreads individual requests.

Numbers: health check interval 2 to 10 s; mark down after about 2 to 3 failures; drain timeout about 30 to 60 s (longer for websockets). Cloud load balancers are themselves a scaled, highly available fleet; the LB must not be a single point of failure (use several nodes behind one DNS name or anycast address).
Trap: sticky sessions to "solve" state, and a load balancer with no spare capacity. If one of three servers dies and the other two were at 70%, they now need 105% and the whole tier falls over. Keep headroom for losing a node (N+1) or a zone.
Say: "An L7 load balancer in front of a stateless service, power-of-two or least-connections, with active and passive health checks, slow start and draining on deploys. Consistent hashing only where the same key must land on the same node, like a cache."

3. Proxies Ch 10

One line: a proxy is a middleman. A forward proxy speaks for clients; a reverse proxy speaks for servers.

What a reverse proxy gives you

  • TLS termination, compression, HTTP/2 to clients while using simple connections inside.
  • Buffering: it reads the whole slow client request or response, so a slow phone does not tie up an app thread. This also blunts slowloris attacks (clients that open connections and dribble bytes to exhaust the server).
  • Connection pooling to backends, caching of static or cacheable responses, routing by host or path, retries, simple access control.
  • Real client IP: the proxy adds X-Forwarded-For (or the standard Forwarded header). Only trust it when it was added by your own proxies. A client can send a fake one. Take the address your trusted proxy appended, not the first value.

Reverse proxy vs load balancer vs API gateway vs CDN

Main jobWhereOverlap
Load balancerSpread traffic over copiesIn front of a server groupAn L7 LB is a reverse proxy
Reverse proxyStand in for the servers: TLS, buffering, caching, routingIn front of one app or fleetOften also load balances
API gatewayAPI policy: auth, limits, versioning, shapingThe front door of an API platformA reverse proxy plus policy
CDNServe cached content from near the userWorldwide edge, before your originA geographically spread caching reverse proxy

Other points interviewers like

  • WebSocket and gRPC through proxies: the proxy must allow protocol upgrade and long idle timeouts, and spread gRPC per request (L7 with HTTP/2 support).
  • Caching proxy: the cache key is the URL plus the headers named in Vary. Respect Cache-Control. Collapse simultaneous misses into one origin request.
  • Sidecar proxy: a small proxy next to each service instance (service mesh) that handles retries, mTLS and metrics, so the app code stays simple.
  • Hop-by-hop headers (such as Connection) apply to one link and must not be forwarded blindly.
Trap: trusting X-Forwarded-For from the internet for rate limits or allow-lists: attackers set it themselves. Also forgetting that a proxy is another hop with its own timeouts; mismatched timeouts cause strange 502 and 504 errors.
Say: "I put a reverse proxy at the edge for TLS, buffering and routing, and I only trust the forwarded client address that my own proxy appended."

4. API gateway Ch 11

One line: one front door for many backend services that handles the same chores (login, limits, routing, logging) once instead of in every service.

Responsibilities

JobWhat it means
RoutingMap host and path (/orders/*) to a service; versioning (/v1, /v2) and canary splits.
Auth offloadCheck the token (JWT signature, API key, OAuth) once and pass the verified identity inward. Services still enforce what a user may do.
Rate limits and quotasPer key, per user, per plan.
Transform and protocol translationRename fields, REST outside and gRPC inside.
AggregationCombine several backend calls into one response (cuts mobile round trips).
Caching, TLS, WAF, observabilityCache common GETs, terminate TLS, block known attacks, emit logs, metrics and trace ids.
ResilienceTimeouts, retries with limits, circuit breakers so one sick service does not drag everything down.

Gateway vs others, and topologies

PatternWhat it isUse whenCost
Edge gatewayOne gateway for outside trafficPublic API, many servicesA shared dependency: must be highly available, and no business logic
Internal gatewayFor service-to-service or partner trafficCentral policy for internal APIsExtra hop
Service mesh (sidecars)Proxy per instance for east-west trafficMany services needing mTLS, retriesOperational weight
BFFOne gateway-like service per client typeMobile and web need very different data shapesMore services to own; duplicated code
GraphQL gatewayClients ask for exactly the fields they need; the gateway fans outMany client types, nested dataQuery cost control, caching is harder, N+1 calls
Numbers: a gateway adds about 1 to 10 ms per hop. Run at least 3 instances across zones; scale them like any stateless tier. Keep response caching and aggregation light: heavy logic here becomes a bottleneck every team shares.
Trap: turning the gateway into a "god" service with business rules, or making it the only place that checks permission. Also: a gateway that is a single instance is a single point of failure for everything. Do not forget that internal services should not trust the network blindly (zero trust).
Say: "The gateway does cross-cutting chores only: TLS, auth, limits, routing, observability. Business logic stays in services. For mobile versus web I would add a thin BFF if their needs really differ."

5. CDN Ch 12

One line: keep copies of content in many places near users so most requests are answered a few milliseconds away and your origin sees only the misses.

How it works

  • Reaching the nearest edge: DNS-based routing (the CDN's DNS answers with a nearby edge) or anycast (many sites share one IP and the network delivers to the closest).
  • Pull CDN (common): edge fetches from origin on the first miss and caches. Push CDN: you upload content ahead of time; good for big, rarely changing files.
  • Request collapsing: if 1,000 users ask for the same missing item at once, the edge sends one request to the origin and gives the answer to all.
  • What belongs there: images, scripts, CSS, video segments, downloads, static pages, and increasingly cacheable API responses. Not per-user private data, unless you use signed URLs or a per-user key.

Controlling the cache

ToolWhat it does
Cache-Control: max-age=NBrowser and CDN may reuse for N seconds. s-maxage targets shared caches (the CDN) only.
private / no-storeprivate: only the browser may keep it. no-store: nobody keeps it.
ETag, Last-ModifiedValidation: after expiry the cache asks "has it changed?" and gets a tiny 304 reply if not.
VaryNames headers that change the response (for example Accept-Encoding). A careless Vary (like Cookie or User-Agent) shatters the cache into many copies and kills the hit ratio.
Cache keyWhat makes two requests "the same": usually host + path + chosen query parameters. Strip tracking parameters.
stale-while-revalidateServe the old copy while fetching a fresh one in the background.

Changing content that is already cached

MethodHowVerdict
Versioned URLsapp.3f9a1c.js or /v42/logo.png: a new file gets a new nameBest. Cache it for a year; no invalidation needed.
Short TTLLet copies expire in seconds or minutesFine for content that changes often; more origin load.
PurgeTell the CDN to delete a path or tagUse for emergencies and unversioned pages; takes seconds to minutes to spread.

Video and large files

Video is cut into small segments in several quality levels (adaptive streaming such as HLS or DASH). The player picks the quality that fits the current bandwidth and fetches segments like ordinary files, which a CDN caches very well. Large downloads use range requests so a client can resume.

Private content and security

Use signed URLs or signed cookies with an expiry for paid or private files. A CDN also absorbs traffic floods (DDoS), provides a WAF and hides your origin address. Lock the origin so it only accepts requests from the CDN, or attackers bypass it.

Numbers: user to nearby edge about 5 to 30 ms versus 100 to 300 ms across oceans. Target a hit ratio of 90% or more for static content. If the hit ratio is 95%, the origin sees 5% of the traffic. Typical TTLs: versioned assets 1 year; HTML a few minutes or revalidated; API data seconds.
Trap: caching a response that depends on the user (a page with a name, or a Set-Cookie) so one user sees another's data. Also forgetting that a purge does not clear the user's browser cache. Cache the personalised bits separately.
Say: "Static assets go on a CDN with versioned file names and a long TTL. User-specific data is not cached at the edge. I watch the hit ratio and use an origin shield to protect the origin on misses."

6. Rate limiting Ch 16 Case sheet

One line: count what each client does and reject (HTTP 429) or delay requests beyond a fair limit, so abuse, bugs and spikes cannot take down everyone.

Why, where, and what to key on

  • Why: stop abuse and brute force, share capacity fairly, control cost (pay-per-call backends), protect fragile dependencies.
  • Where: client (polite, not trusted), edge or gateway (the default place), service (knows business cost), and per dependency (protect the database or a partner API).
  • Key: user id, API key, IP address (weak behind NAT), tenant, endpoint, or a combination. Different plans get different limits (free, pro).

The algorithms

AlgorithmHowProsCons
Fixed window counterCount per minute; reset on the minuteTiny and simple (one counter)Edge burst up to 2x the limit
Sliding window logKeep a timestamp per request; count those in the last N secondsExactMemory per request; costly at high rates
Sliding window counterWeigh the previous window by how much of it still overlapsCheap and close to exactAn approximation
Token bucketRefill at rate r up to capacity b; each request takes a tokenAllows controlled bursts, only two numbers per key; most popularBursts reach the backend
Leaky bucketRequests enter a queue that drains at a fixed rateSmooth output rateQueue adds delay; old requests may wait
GCRAToken-bucket behaviour using one stored timestampVery compact, preciseHarder to explain

Distributed limiting

  • Central store (usually Redis): every gateway node updates the same counter. Simple and accurate; adds about 1 ms per request and needs the store to be highly available.
  • Race condition: "read counter, check, then write" lets two nodes both pass. Fixed window can use atomic INCR plus EXPIRE. Anything more complex (token bucket, sliding window) needs a Lua script so the read-check-update is one atomic step.
  • Local counters with periodic sync: each node allows a share and syncs now and then. Fast, no central hop, but the limit can be over by a bit. Fine for coarse protection.
  • Hot keys: one huge customer can overload one Redis shard; split their counter into sub-counters or use local limits for them.
  • Fail open or fail closed: if Redis is down, usually fail open for ordinary APIs (do not cause an outage) and fail closed for expensive or security-critical ones (login, SMS).

What to return

HTTP 429 Too Many Requests with Retry-After (seconds to wait) and ideally headers showing the limit, the remaining count and the reset time. Good clients back off with exponential delay plus random jitter so retries do not arrive in a wave. Distinguish a hard limit (reject) from a soft one (queue or slow down).

Numbers: token bucket state is about two numbers per key (tokens, last refill time). One Redis node handles roughly 100,000 or more simple operations per second. 10 million active keys at about 100 bytes each is about 1 GB. A limiter should add only a millisecond or so.
Trap: limiting only by IP (many users share one office address, and attackers have many addresses), a non-atomic check in Redis, and a limiter that crashes the API when it fails. Also: rejecting requests costs less than serving them, but still costs; at huge floods use the CDN or network layer first.
Say: "Token bucket per API key, kept in Redis with a Lua script so the update is atomic, enforced at the gateway, returning 429 with Retry-After. Fail open, with a coarse local limit as a backstop."

7. Say-aloud script (about 45 seconds)

Say: "I keep the application tier stateless: sessions in Redis or a signed token, files in object storage. That lets me scale out behind a layer 7 load balancer that uses least connections or power of two choices, checks health actively and passively, slow-starts new servers and drains old ones on deploy. In front of that, a CDN serves static content from the edge with versioned file names, so the origin only sees misses. The API gateway is the single front door: it ends TLS, checks the token, enforces a per-key token-bucket rate limit held in Redis with an atomic script, and routes to services. I keep headroom so losing one node or one zone does not overload the rest, and I would find the real bottleneck with metrics before adding more servers. The riskiest part is the shared pieces, the gateway and Redis, so I run them highly available and decide in advance whether the limiter fails open or closed."

8. Interview Q&A (32)

A. Concepts

1. What does "stateless" mean, and why does it matter for scaling?

A stateless server keeps no information about the user between requests; everything it needs comes in the request or from a shared store. This matters because any server can then answer any request. We can add servers during a peak, remove them after, replace a dead one without logging anyone out, and deploy by rolling through the fleet. If state is trapped in one server's memory, that server becomes special, and the load balancer must pin users to it. I would still keep state, but in places built for it: Redis for sessions, a database for records, object storage for files.

2. Vertical versus horizontal scaling: when would you pick each?

Vertical means a bigger machine. It is the simplest first step because the code does not change, and it is good for databases that are hard to split. Its limits are a hardware ceiling, rising cost per unit of power, and one machine as a single point of failure. Horizontal means more machines. It gives no hard ceiling and better fault tolerance, but you need a load balancer, stateless code, and a plan for data. For a web tier I go horizontal almost always; for a first database I often go vertical plus read replicas, then shard only when needed.

3. Why do ten servers not give ten times the throughput?

Because some work cannot be split. Amdahl's law says the serial part caps the gain: if 5% of work must run one at a time (a lock, a single database, a coordinator), the best possible speed-up is 20 times, however many servers you add. On top of that, servers spend effort coordinating, which the Universal Scalability Law models: past some point more machines slow the system. In practice I look for the shared resource (the database, a hot key, a global lock) and remove or shard it.

4. What is the difference between Layer 4 and Layer 7 load balancing?

A layer 4 balancer works on connections: it sees IP addresses and ports and forwards the bytes without reading them. It is very fast and works for any protocol. A layer 7 balancer reads the HTTP request, so it can route by path, host or header, retry, rewrite, use cookies and terminate TLS, but it costs more CPU. I choose L7 for APIs and microservices, and put an L4 tier in front when I need huge connection counts or non-HTTP traffic. For gRPC and HTTP/2 I need L7, since L4 would pin all of one client's calls to one server.

5. What is the difference between a forward proxy and a reverse proxy?

A forward proxy stands in for clients: the clients are configured to send traffic through it and the outside server sees only the proxy. Companies use it for filtering, auditing and caching. A reverse proxy stands in for servers: clients think they talk to it, and it forwards to hidden backends. It gives TLS termination, buffering, caching, routing and protection. A simple memory trick: the forward proxy hides who is asking, the reverse proxy hides who is answering.

6. What does an API gateway do that a plain reverse proxy does not?

A reverse proxy forwards and does generic chores. A gateway adds API-aware policy: checking tokens and API keys, per-client rate limits and quotas, versioning, request and response transformation, protocol translation, aggregation of several calls, and per-API metrics. In practice a gateway is built on a reverse proxy; the difference is the layer of policy. The risk is stuffing business logic into it, so I keep it to cross-cutting chores.

7. How does a CDN actually make things faster?

Two ways. First, distance: the copy sits at an edge site a few milliseconds from the user instead of an ocean away. Second, load: a hit never reaches the origin, so the origin needs far less capacity, and a traffic spike is absorbed by the edge. The edge also keeps warm connections to the origin and can compress content. A good hit ratio is the key number. If it is low, the CDN adds a hop instead of removing one.

8. Explain the token bucket algorithm and why it is popular.

There is a bucket with a maximum number of tokens. It refills at a steady rate, say 5 per second, and each request removes one token. If the bucket is empty, the request is rejected or delayed. This allows a short burst (up to the bucket size) while holding the long-run average to the refill rate, which matches how real clients behave. It needs only two numbers per key (token count and last refill time), and it is easy to explain and tune: rate controls the average, capacity controls the burst.

9. What is the problem with a fixed-window rate limiter?

Windows reset at fixed times, so a client can send the full limit at the very end of one window and the full limit again at the start of the next. With a limit of 100 per minute that is 200 requests in about two seconds. A sliding window counter fixes most of this cheaply by weighing the previous window by its overlap. A sliding window log is exact but stores one timestamp per request. A token bucket avoids the issue and allows a controlled burst.

10. What are the main HTTP caching headers a CDN obeys?

Cache-Control is the main one: max-age sets freshness for everyone, s-maxage sets it only for shared caches such as the CDN, private means only the browser may store it, and no-store means nobody should. ETag and Last-Modified let a cache revalidate cheaply with a 304 reply. Vary says which request headers change the response. I add stale-while-revalidate so users are never made to wait for a refresh.

B. Design scenarios

11. Design the front door for a public API used by web, mobile and partners.

Traffic first meets a CDN or edge network for DDoS absorption and caching of public GETs. Then a layer 4 balancer spreads connections across a fleet of API gateway instances in several zones. The gateway ends TLS, validates tokens, applies a per-key token-bucket limit (state in Redis), adds trace ids and routes to services through their own L7 balancers or service discovery. Partners get separate keys and quotas, and mobile may get a BFF if its data needs differ. Every layer is stateless and horizontally scalable, and I say what each layer does on failure.

12. How would you design a rate limiter for 1 million requests per second across many gateway nodes?

Key by API key and endpoint class. A central Redis cluster, sharded by key, holds token-bucket state, updated by a Lua script so check and decrement are atomic. 1 million per second is too much for a single node, so shard across many, and reduce round trips by having each gateway take tokens in batches (for example 10 at a time) and spend them locally. That trades a little accuracy for far less traffic. Heavy hitters get local limits or sub-counters. If Redis fails, fail open with a coarse local limiter as a backstop. Return 429 with Retry-After. The case sheet has the full design.

13. A web app keeps shopping carts in server memory. How do you make it scale out?

I move the cart out of the server. Options: store it in Redis keyed by session id (fast, expiry built in), store it in the database for durable carts, or put it in a signed client token if small. I would use the database or Redis, depending on how precious a cart is. Then I remove stickiness at the load balancer, so any server can handle any request, and test by killing a server mid-session. During migration I can keep sticky sessions as a bridge while the new path is rolled out.

14. How would you serve a global video or image site fast?

Put media on object storage as the origin and a CDN in front. Images get versioned names and long TTLs, with several sizes prepared in advance or generated once and cached. Video is cut into segments at several bitrates (adaptive streaming) so each segment is a cacheable file. Use an origin shield so a popular new release does not stampede the origin. Private or paid content uses signed URLs with a short expiry. Popular titles can be pushed to edges ahead of a launch. Measure hit ratio per region and fix the low ones.

15. Design routing for 20 microservices behind one domain.

One domain, one gateway tier. Host and path rules map /orders to the orders service, /users to the users service, and so on. The gateway handles login, limits and observability once; each service handles its own authorisation rules. For canary releases the gateway splits a percentage of traffic to the new version. Service discovery keeps the routing table current, or the gateway uses an internal load balancer name per service. To avoid a shared bottleneck I run the gateway as many identical instances and keep its config declarative and reviewed.

16. How do you do a zero-downtime deploy behind a load balancer?

Roll new servers in gradually. The new instance must pass health checks before it gets traffic, and slow start gives it a growing share. For the old instance I use connection draining: stop new requests, wait for in-flight ones to finish (up to a time limit), then shut down. Keep spare capacity during the roll, so removing one server does not overload the rest. For risky changes, use a canary: send 1% to the new version, watch error rate and latency, then widen or roll back. Database changes must be backward compatible for the period when both versions run.

17. How would you rate limit a login endpoint differently from a normal API?

Login is a target for password guessing and credential stuffing, so I key on account name and on IP and device, with a low limit (for example 5 failures per 15 minutes per account) and increasing delays or a CAPTCHA after repeated failures. It must fail closed: if the limiter is down, I do not want attackers to get unlimited guesses. Also avoid a lockout that lets an attacker lock out real users forever; prefer slowing and challenge over hard lock. Log and alert on spikes across many accounts.

18. Where would you put caching in this stack, and where not?

At the CDN for public static and cacheable responses; at the gateway or reverse proxy for common GETs with short TTLs; in Redis for computed or database results; in the browser through headers. I avoid caching in layers where I cannot invalidate (fan-out to many edges) for fast-changing data, and I never cache personalised responses in a shared cache without a per-user key. Every layer I add is another place for stale data, so I state the freshness bound for each data type.

C. Failures and real-time production scenarios

19. One of three servers dies and the other two collapse. What happened and how do you prevent it?

They were running too hot. With three servers at 70% each, losing one pushes the two others to about 105% of capacity, so latency grows, health checks time out, the balancer ejects them too, and it becomes a full outage (a cascading failure). Prevention: capacity planning with N+1 headroom (so the survivors stay under about 70 to 80%), autoscaling, timeouts and load shedding so overload does not spread, and a panic mode on the balancer that keeps sending traffic when too many servers look unhealthy. In the incident itself: add capacity fast, shed low-priority traffic, and stop retries from multiplying the load.

20. Your CDN hit ratio suddenly drops from 95% to 60%. What do you check?

First, what changed. A deploy that changed cache headers (a Cache-Control: no-cache or a Set-Cookie on static files), a new Vary header that splits the cache, or a new query parameter such as a tracking id that makes every URL unique. Second, a purge of everything, or a TTL cut. Third, a new traffic pattern, for example crawlers requesting the long tail. I inspect the cache status header on sample responses, compare top missed URLs before and after, and fix the key (strip useless parameters, normalise Vary). Meanwhile I protect the origin with the shield and rate limits.

21. Redis for your rate limiter goes down. What should happen?

It depends on the endpoint. For ordinary APIs, fail open: allow the requests and rely on a coarse in-memory limit on each gateway node, because blocking everyone would be an outage caused by our safety tool. For expensive or security-sensitive endpoints (login, SMS, payments) fail closed or apply a strict local limit. The decision must be made in advance, with metrics and alerts when the limiter is in fallback mode. Use Redis replicas and fast failover so this is rare, and a short timeout (a few milliseconds) on limiter calls, so a slow Redis does not slow every request.

22. All servers are marked unhealthy at once, and the site is down. Why?

Most likely the health check is too deep: it calls the shared database or another dependency, which had a blip, so every server failed together even though each one could have served cached or partial data. Another cause is a bad deploy that broke the health endpoint, or checks timing out under load (so the check itself is overloaded). Immediate steps: use the balancer's panic or fail-open mode (route to all servers when too many are down), fix or roll back the check. Long term: make health checks shallow (the process can serve), keep dependency health in separate alerts, and use thresholds so one failure does not eject a server.

23. Users are getting 502 and 504 errors from the proxy. How do you debug?

502 means the proxy got a bad or no response from the backend (crashed process, closed connection, protocol mismatch). 504 means the backend was too slow and the proxy gave up. I check backend health and latency first, then compare timeouts through the chain: if the proxy's idle timeout is shorter than the backend's keep-alive, the proxy reuses a connection the backend just closed, causing sporadic 502s. Set the backend keep-alive longer than the proxy's. I also check connection pool limits, recent deploys, and whether a slow dependency is holding workers. Retries must be limited, or they pile on.

24. A viral link causes a spike; one cached item expires and the origin is flooded. What is this and how do you fix it?

This is a cache stampede (thundering herd). Many edges or many users miss at the same moment and all go to the origin. Fixes: request collapsing at the edge so one origin fetch serves everyone; an origin shield; stale-while-revalidate and stale-if-error so old content is served while one refresh runs; TTL jitter so many items do not expire together; and pre-warming popular objects. At the origin itself, add rate limits and a circuit breaker so it degrades gracefully instead of falling over.

25. A single customer is sending far more traffic than allowed and the limiter's Redis shard is overloaded. What now?

That customer's key is a hot key, so one shard handles all its checks. Short term: block or throttle them harder at the edge or CDN, which is cheaper than a Redis call per request. Medium term: split the counter into several sub-keys (one per gateway node or per slice) so load spreads, or enforce their limit locally with periodic sync. Also use batching of tokens, so a gateway node asks for 100 tokens at a time. Add a per-key metric and alert so we see such customers before they hurt others.

26. After a purge, users still see old content. Why?

Several possibilities. The purge may not have finished spreading to all edges yet (usually seconds to minutes). The old copy may live in the browser cache, which the CDN cannot purge, or in another cache layer such as a corporate proxy or the origin shield. The purge path may not match the real cache key (for example it differs by query string or Vary). Best practice is to avoid depending on purges: use versioned URLs for assets and short TTLs plus revalidation for pages. For urgent fixes, purge at every layer and then change the URL.

27. Users behind one big company all get 429 errors. What is going on?

The limiter keys on IP address, and the whole company shares one outside address through NAT, so they share a single bucket. Fix by keying on a better identity: authenticated user id or API key, and use IP only for anonymous traffic with a higher limit. For anonymous traffic add other signals such as a device id or cookie. Also check the forwarded-for handling: if the limiter sees the proxy's own address instead of the real client, everybody looks like one client.

D. Trade-offs and why-questions

28. Why not use sticky sessions instead of a shared session store?

Sticky sessions are easy but they tie a user's data to one server. Load becomes uneven (a few heavy users on one machine), a dead server loses every session on it, and draining or scaling in becomes harder. A shared store costs an extra network hop and needs to be highly available, but it makes all servers equal. Stickiness is fine as a cache hint (the same user often hits the same server to reuse a warm local cache) as long as correctness does not depend on it.

29. JWT in the client versus a server-side session in Redis: which would you choose?

A signed token needs no lookup on each request, so it scales well and suits many services that all need to verify identity. The downsides are that it cannot be revoked before it expires without extra state, and it grows with data. A server-side session is easy to revoke and holds any amount of data, but costs a lookup and needs the store to be available. A common mix is a short-lived access token (about 5 to 15 minutes) with a refresh token tracked on the server, so revocation works within minutes.

30. Token bucket versus sliding window: how do you pick?

If I want to allow short bursts and enforce an average (most public APIs), token bucket: cheap, two numbers per key. If I must guarantee "no more than N in any rolling window" (billing rules, strict fairness), sliding window: the log is exact but costs memory, the counter version is cheap and close. Leaky bucket when the downstream needs a smooth, constant rate. Fixed window only when simplicity matters more than boundary accuracy. In an interview I pick token bucket by default and name the reason.

31. Why have both a CDN and an API gateway? Is that not duplicated?

They sit at different points and solve different problems. The CDN is global and optimised for caching and absorbing floods; it sits before your origin and sees little of your business rules. The gateway is in your region, knows your APIs and identities, and enforces policy: auth, per-customer limits, routing. They overlap a little (both can rate limit coarsely, both can cache), and I use the overlap deliberately: the CDN blocks obvious floods cheaply, the gateway applies precise per-customer limits.

32. Where should rate limiting live: gateway, service, or both?

Both, with different jobs. The gateway enforces coarse, per-client limits early, so junk never reaches services; it is the cheapest place to reject. Services enforce limits that need business knowledge (for example max exports per hour for a tenant) and protect themselves from internal callers, since the gateway can be bypassed or misconfigured. Each dependency also gets its own protection (connection limits, bulkheads, circuit breakers). The defence is layered: a failure of one layer should not be fatal.
