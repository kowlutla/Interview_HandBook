Networking, APIs and real-time

Revision sheet for the day before the interview: how bytes travel (TCP, HTTP, TLS), how names are found (DNS), how to design APIs, how to push live data, and how to pack data on the wire. Full explanations: Handbook Chapters 3 to 7.

0. Key definitions (know these cold)

TermDefinition
RTT (round trip time)How long a message takes to go to the other side and back. Same city about 1 to 5 ms; across a continent about 50 to 80 ms; across an ocean about 100 to 150 ms. Most network cost is "how many round trips", not "how many bytes".
Latency vs bandwidthLatency is the delay of one message. Bandwidth is how much data fits through per second. A big pipe does not make a long trip shorter.
TCPThe reliable, ordered way to send a stream of bytes. It sets up a connection first, numbers the bytes, resends lost ones, and slows down when the network is crowded.
UDPSend single packets with no connection and no promise they arrive or arrive in order. Cheap and fast. Used for DNS, video calls, games.
Socket / four-tupleOne connection is identified by four values: source IP, source port, destination IP, destination port. Two connections must differ in at least one.
Ephemeral portA temporary port the client's operating system picks for its end of a connection. Linux default range gives about 28,000 ports.
TLSThe layer that encrypts the connection and proves the server is who it says it is (with a certificate). HTTPS is HTTP inside TLS.
Head-of-line blockingOne slow or lost item at the front of a queue holds up everything behind it. Happens in HTTP/1.1 (one request at a time per connection) and in TCP (one lost packet stalls all streams on it).
Connection poolA set of already-open connections that requests borrow and return, so we do not pay the set-up cost every time.
DNSThe internet's phone book: turns a name like shop.example.com into an IP address.
Resolver / authoritative serverThe resolver (recursive) does the looking up for you and caches answers. The authoritative server is the one that owns the real answer for a zone.
TTL (time to live)How many seconds a cached DNS answer may be reused. Short TTL: changes spread fast, more lookups. Long TTL: fewer lookups, slow changes.
AnycastMany servers in different places announce the same IP address; the network sends each user to the nearest one.
REST / resourceA style where URLs name things (nouns: /orders/42) and HTTP methods say what to do (GET, POST, PUT, DELETE).
IdempotentDoing it twice has the same effect as doing it once. PUT and DELETE are; a plain POST is not. This is what makes retries safe.
Idempotency keyA unique id the client sends with a POST so the server can spot a retry and return the first result instead of doing the work again.
Pagination (offset / keyset / cursor)Returning a long list in pages. Offset: skip N rows. Keyset: "rows after this key". Cursor: an opaque token that hides the key.
Polling / long polling / SSE / WebSocketFour ways to get live updates: ask again and again; ask and let the server hold the answer until there is news; a one-way stream from server to browser; a two-way open connection.
Connection gatewayA tier of servers that only hold long-lived client connections (WebSockets) and pass messages in and out, separate from business logic.
BackplaneThe pub/sub system (Redis, Kafka) that lets any server tell the gateway holding a user's connection to deliver a message.
SerializationTurning an in-memory object into bytes to send or store, and back again (JSON, Protobuf, Avro).
Schema evolutionChanging the shape of data over time while old and new code still read each other's data. Backward compatible: new readers read old data. Forward compatible: old readers read new data.
BatchingGrouping many small messages or writes into one bigger one to save per-item overhead, at the price of a little waiting.

1. Networking essentials: TCP, UDP, HTTP, TLS Ch 03

One line: every new connection costs round trips (TCP, then TLS, then the request), so good design reuses connections, keeps users close to a server, and sets timeouts everywhere.

Layers in one minute

Think of mail. The IP layer is the street address that gets a packet to the right machine. The TCP or UDP layer adds the apartment number (the port) and decides how reliable delivery is. TLS is the sealed envelope. HTTP is the letter's format. Each layer wraps the one above (encapsulation). A server listening on port 443 can hold hundreds of thousands of connections, because each client's (IP, port) pair makes the four-tuple unique.

TCP in simple words

  • Handshake: client sends SYN, server answers SYN-ACK, client sends ACK. That is one round trip before any data.
  • Reliability: every byte has a sequence number; the receiver acknowledges; the sender resends what is not acknowledged.
  • Flow control: the receiver says how much room it has (window) so a fast sender does not drown a slow reader.
  • Congestion control: the sender starts slow and speeds up, and backs off on loss, so the network is not overloaded. This is why a new connection is slow at first (slow start) and why long-lived warmed-up connections are faster.
  • Head-of-line blocking: bytes are delivered in order, so one lost packet holds back everything behind it, even data for other requests on the same connection.
  • Teardown and TIME_WAIT: the side that closes first keeps the socket in TIME_WAIT for about 60 seconds on Linux, so late packets from the old connection cannot confuse a new one.
  • Keep-alive: a quiet connection can look alive when the other side has died (or a NAT dropped it). Heartbeats or TCP keepalive detect that.

UDP: when to pick it

Choose UDP whenWhat you take on yourself
Late data is useless data (live voice, video call, game state)Detecting loss, resending if needed, ordering, congestion control
One small question, one small answer (DNS)Retry on timeout; no guarantee of delivery
You build your own protocol on top (QUIC, HTTP/3)Everything TCP gave you for free

HTTP versions

VersionIdeaProblem it solves / leaves
HTTP/1.1Text protocol, persistent connections (keep-alive), one request at a time per connection.Browsers open about 6 connections per host to cope; pipelining failed; headers repeated every time.
HTTP/2Binary frames, many requests share one connection (multiplexing), header compression (HPACK).Fixes HTTP-level blocking. TCP-level head-of-line blocking remains: one lost packet stalls every stream. Server push did not work out.
HTTP/3Runs on QUIC (over UDP). Streams are independent, so a loss only stalls its own stream. Faster set-up (about 1 round trip, 0 when resumed). Survives a phone switching from Wi-Fi to mobile.Some networks block or throttle UDP, so clients fall back to HTTP/2. More CPU in user space.

TLS in simple words

  • The server shows a certificate signed by an authority the client trusts. That proves identity. Then both sides agree on a short-lived key (ephemeral key exchange, which gives forward secrecy: stealing the server key later does not reveal old traffic).
  • After the handshake, data is encrypted with a fast symmetric cipher (AES-GCM or ChaCha20), so the main cost is the handshake delay, not the per-byte cost.
  • TLS 1.3 needs 1 round trip (TLS 1.2 needs 2). Session resumption lets a returning client skip most of it; 0-RTT resumption data can be replayed by an attacker, so allow it only for safe (GET) requests.
  • mTLS (mutual TLS): the client also shows a certificate. Common between services, so each side knows who the other is.
  • Where to end TLS: at the edge or load balancer near users saves round trips for far-away clients; inside the data centre you may re-encrypt or use a service mesh.

NAT, firewalls, MTU, proxies

  • NAT lets many private machines share one public IP by rewriting addresses. It keeps a table of connections; idle entries are dropped after a while, so a quiet connection can silently die. Send keepalives. Conntrack tables can fill up and drop new connections.
  • Firewalls and security groups allow or block traffic by IP and port.
  • MTU (largest packet, usually 1500 bytes) means big messages are cut into pieces. Tunnels and VPNs shrink it; wrong MTU gives the odd bug where small requests work and big ones hang.

Connection pools and port exhaustion

What a pool saves

  • The TCP and TLS round trips on every request
  • Slow-start warm-up of the congestion window
  • CPU for the handshake on both sides

A pool also protects

  • The server: a cap on connections stops a flood from your own clients
  • The port space: far fewer sockets stuck in TIME_WAIT
  • Size it from concurrency needed (about throughput x latency), not guesses

Port exhaustion

  • Client to one server IP and port can vary only the source port
  • Linux default 32768 to 60999 = 28,232 ports
  • With 60 s TIME_WAIT: about 470 new short connections per second, then "cannot assign address"
  • Fix: reuse connections, more source IPs or backend ports, let the server close first
Numbers: TCP handshake 1 RTT; TLS 1.3 1 RTT, TLS 1.2 2 RTT; TIME_WAIT about 60 s; ephemeral ports about 28k default (about 64k at most); a client opening and closing 1,000 short connections/s piles up about 60,000 TIME_WAIT sockets; browsers about 6 connections per host on HTTP/1.1; MTU 1500 bytes; default file descriptor limit often 1,024 (raise it for servers).
Traps: no timeouts (a hung call holds a thread forever); timeouts that do not nest (inner call allowed longer than the outer caller's timeout, so work continues for nobody); retrying with no limit (retry storms); advice to "turn off TIME_WAIT" (unsafe); forgetting that a load balancer to backend hop has the same port limit; assuming a pool size larger than what the database can accept.
Say: "I count round trips on the critical path. I keep connections open through a pool, put TLS termination near the user, use HTTP/2 or 3 between clients and edge, and put a timeout and a retry budget on every call, with each inner timeout shorter than the outer one."

2. DNS Ch 04

One line: DNS turns names into addresses through a hierarchy of servers with caches at every step, so every answer is allowed to be stale for its TTL; that is both its speed and its weakness during failover.

How a lookup works

Your app asks a small local helper (the stub resolver). It asks a recursive resolver (your ISP, company, or a public one). If that resolver has no cached answer, it walks down the tree: the root servers say who runs .com; the TLD servers say who is the authoritative server for example.com; the authoritative server gives the real answer. The resolver caches each step for its TTL and answers you. Browsers and operating systems also keep their own caches, so many lookups never leave the machine.

Record types

RecordMeaningNote
A / AAAAName to IPv4 / IPv6 addressCan list several addresses (round robin)
CNAMEName is an alias for another nameCannot sit at the zone apex (example.com itself) and cannot coexist with other records on that name; adds a lookup
ALIAS / ANAMEProvider feature: CNAME-like behaviour at the apexResolved by the DNS provider, returns plain A records
NSWhich servers are authoritative for a zoneDelegation to a child zone
MXMail servers for the domainWith priority numbers
TXTFree text: domain verification, SPF, DKIM
SRVHost plus port for a service, with priority and weightUsed in service discovery
SOAZone metadata, including the negative-caching time

TTL: the trade-off and the myths

Short TTL (30 to 60 s)Long TTL (hours)
Changes and failoverSpread fastSlow, some users stuck on old address
Lookup load and latencyMore queries, more first-visit delayFewer, mostly cached
Resilience to DNS outageWeak: caches expire during the outageStrong: caches keep serving
  • Planned change routine: days before, lower the TTL; make the change; wait at least the old TTL; raise the TTL again.
  • "Propagation" myth: DNS does not push anything. Changes appear as caches expire. Some resolvers and apps ignore TTLs (Java used to cache forever, some ISPs enforce minimums), so plan for a tail of old clients.
  • Negative caching: "this name does not exist" is cached too, using the SOA value. A name created seconds after a failed lookup can stay invisible for minutes.

DNS for load balancing, geography and failover

Round robin

  • Return several IPs, rotate the order
  • Coarse: caches pin users, no idea of server load, dead servers stay listed until removed

GeoDNS / latency-based

  • Authoritative server gives different answers by where the resolver is
  • Sees the resolver's location, not always the user's (EDNS client subnet helps)

Anycast

  • Same IP announced from many sites; routing picks the nearest
  • Used by root servers, public resolvers, CDNs; also spreads DDoS traffic
  • Fits UDP and short connections best
  • Health-checked failover: the DNS provider probes your endpoints and stops returning a dead one. Worst case switch time = detection time + TTL + resolvers that ignore TTL.
  • Worked example: health check every 10 s, 3 failures to declare dead = 30 s; TTL 60 s; so most users move within about 90 s, a few take longer. If that is too slow, use anycast or a global load balancer with a fixed IP, and keep DNS for coarse region choice.
  • Service discovery: internal DNS names (A or SRV records) for services, as in Kubernetes. Caveat: client-side caching and long-lived connections mean clients may keep talking to a retired address.

Security and failure modes

TopicWhat to know
UDP and TCPQueries use UDP (port 53) first; fall back to TCP when the answer is too big or for zone transfers.
DNSSECAnswers are digitally signed so a resolver can detect forged data. It does not encrypt.
DoT / DoHDNS over TLS / over HTTPS: encrypts the query between you and the resolver (privacy).
Cache poisoningAttacker tricks a resolver into caching a fake answer. Defences: random source ports and ids, DNSSEC.
DDoS on DNSUse several providers, anycast, rate limiting, long enough TTLs so caches ride out an attack.
Resolver or authoritative outageUsers with warm caches keep working; new lookups fail. Use two or more independent providers.
Numbers: cold lookup 20 to 120 ms; cached lookup well under 1 ms; typical TTLs: 30 to 60 s for failover records, 300 s common default, hours to a day for stable records; root servers: 13 named addresses served by many anycast sites.
Traps: promising "instant failover with DNS" (TTL plus ignoring clients make it minutes); putting a CNAME at the apex; lowering TTL only right before a change; one DNS provider as a single point of failure; assuming a client re-resolves while holding a long-lived connection (it does not).
Say: "DNS picks the region coarsely with geo or latency records and a short TTL on failover records. Inside a region a load balancer with a fixed address does the fast failover, because DNS cannot be faster than its TTLs."

3. API design Ch 05

One line: an API is a contract that is very hard to change once clients use it, so design names, errors, pagination and versioning up front, and make every write safe to retry.

REST resources and URLs

  • Use nouns, plural, and nest only when ownership is clear: /users/42/orders/7. Avoid verbs in paths.
  • Actions that are not plain create/read/update/delete: model them as a sub-resource or an action noun, e.g. POST /orders/7/cancel or POST /payments/9/refunds.
  • Return a stable representation (JSON), consistent field names and ids, ISO-8601 UTC timestamps, money as integer minor units plus currency (not floats).

Methods, safety, idempotency

MethodUseSafe (no change)?Idempotent?
GETReadYesYes
PUTReplace a whole resource at a known URLNoYes
PATCHPartial updateNoNot guaranteed (depends: "set x=5" yes, "add 5" no)
DELETERemoveNoYes (second call may return 404, state is the same)
POSTCreate under a collection, or run an actionNoNo, unless you add an idempotency key

Status codes to know

CodeMeaning and when
200 / 201 / 202 / 204OK / Created (with Location) / Accepted for later processing / Success with no body
301 / 304Moved permanently / Not modified (conditional request, use your cache)
400 / 422Malformed request / understood but invalid values
401 / 403Not authenticated (who are you?) / not allowed (I know you, no)
404 / 409 / 412Not found / conflict with current state (duplicate, version clash) / precondition failed (ETag mismatch)
429Too many requests; send Retry-After
500 / 502 / 503 / 504Server bug / bad answer from upstream / overloaded or down (retry later) / upstream timed out

Rule of thumb for clients: 4xx means "fix your request, do not blindly retry" (except 408, 429); 5xx and timeouts may be retried with backoff, but only if the call is idempotent or carries an idempotency key.

Idempotency keys for POST

Problem: the client sends "charge 50 dollars", the network drops the reply, the client retries, the customer is charged twice. Fix: the client generates a unique key (a UUID) per logical operation and sends it in a header (Idempotency-Key). The server stores the key with a hash of the request and the response it produced, behind a unique constraint. A repeat with the same key returns the stored response; the same key with a different body is rejected (422 or 409). Two concurrent first requests must not both run: use the unique insert as the lock and have the second wait or get 409. Keep keys for about 24 hours.

Conditional requests and ETags

  • ETag is a version tag for a response. Client sends If-None-Match; unchanged data returns 304 with no body (saves bandwidth).
  • Optimistic concurrency: client sends If-Match: etag on update; if someone else changed it, the server returns 412. This stops lost updates without locks.
  • Content negotiation: Accept and Accept-Language pick the format and language.

Pagination

StyleHowGoodBad
Offset?offset=1000&limit=20Simple; can jump to page NDatabase must scan and throw away 1000 rows, so deep pages are slow; rows shift when data changes (duplicates or skips)
Keyset (seek)?after_id=9876&limit=20 using WHERE id > 9876 ORDER BY idFast at any depth with an index; stable under insertsNo jump to page N; needs a unique sortable key (add id as tie-breaker)
Cursor?cursor=opaque_tokenHides internals; can change the implementation; may carry sort and filter stateSame limits as keyset; tokens need care (sign or encrypt, expire)

Filtering, sorting, versioning, errors, rate limits

  • Filtering and sorting: ?status=open&sort=-created_at; only allow indexed fields; cap page size (for example 100); allow fields= to trim the response and expand= to include related objects.
  • Backward-compatible changes: adding optional fields, new endpoints, new enum values (if clients are told to ignore unknown). Breaking: removing or renaming fields, changing types or meaning, making a field required.
  • Versioning styles: in the URL (/v2/orders, most visible), in a header, or in the media type. Prefer evolving additively and deprecating slowly: announce, add a Deprecation/Sunset header, watch usage per client, then remove.
  • Error contract: one shape everywhere, for example {type, title, status, detail, request_id, errors[]} (problem-details style), plus a stable machine-readable code. Never leak stack traces.
  • Auth at a glance: API keys for server-to-server identity, OAuth 2.0 tokens for users and scopes, JWT for signed claims, mTLS for service identity. Always HTTPS.
  • Rate-limit headers: 429 plus Retry-After, and limit/remaining/reset headers so well-behaved clients slow down.

Long-running work, webhooks, bulk, gRPC

  • 202 Accepted pattern: POST /exports returns 202 with a Location of a status resource; the client polls it (or gets a webhook) until it says done, then fetches the result.
  • Webhooks: the server calls the client's URL when something happens. Needs: signed requests (HMAC) so the receiver can verify, an event id for deduplication, retries with backoff (at-least-once, so receivers must be idempotent), a fast 2xx response, and a way to replay missed events.
  • Bulk endpoints: accept up to N items, return a per-item result (207-style) so one bad item does not fail all; still idempotent.
  • gRPC: contract in a .proto file, Protobuf on the wire, HTTP/2 underneath. Four call types: unary, server streaming, client streaming, bidirectional. Always set deadlines (they propagate down the call chain) and handle cancellation. Great for internal service-to-service calls; browsers need a proxy (gRPC-Web). Long-lived HTTP/2 connections need client-side load balancing, because one connection pins to one backend.
PickWhenWhen not
REST + JSONPublic APIs, browsers, easy debugging, caching by CDNVery chatty internal calls, streaming
gRPCInternal calls, low latency, streaming, strict contracts, many languagesPublic browser clients, human debugging
GraphQLMany different clients needing different shapes; fewer round tripsSimple CRUD; hard to cache and rate-limit by cost
Numbers: typical default page size 20 to 100, max about 100 to 1,000; idempotency keys kept about 24 h; webhook retries often spread over hours to days with exponential backoff; JSON payloads of 1 KB parse in microseconds, so the network, not parsing, dominates for small calls.
Traps: using POST for reads; returning 200 with an error inside; offset pagination on a large changing table; floats for money; auto-incrementing public ids that leak volume (use opaque ids); unbounded page size; retries on non-idempotent calls without a key; breaking clients by renaming a field "just once".
Say: "Resources are plural nouns. Every POST that matters takes an idempotency key. Lists use keyset or cursor pagination with a capped page size. Errors share one shape with a request id. We evolve additively and version only for breaking changes, and long jobs return 202 with a status URL."

4. Real-time: polling, SSE, WebSockets and scaling them Ch 06

One line: plain HTTP only answers when asked, so for live updates we either ask often (polling), hold the question open (long polling, SSE), or keep a two-way connection (WebSocket); the hard part is then scaling millions of open connections and routing a message to the right one.

The four options

OptionHow it worksUse whenWatch out
Short pollingClient asks every N seconds.Loose freshness (30 s or more), few users, fallback1M users polling every 5 s = 200,000 requests/s, mostly empty; average delay is half the interval
Long pollingServer holds the request until there is data or a timeout, client re-asks at once.Works everywhere; simple upgrade from pollingEach wait holds a server connection; a burst of events means a burst of re-requests; ordering and missed events between requests
SSE (server-sent events)One long HTTP response; server writes text events; browser auto-reconnects and sends Last-Event-ID.One-way feeds: notifications, dashboards, live scores, AI token streamsServer to client only; text only; browser EventSource cannot set custom headers; about 6 connections per host on HTTP/1.1; proxies that buffer
WebSocketHTTP request with Upgrade: websocket; server answers 101; then small framed messages both ways over the same TCP connection.Chat, games, collaborative editing, anything two-way and frequentStateful: you must build reconnect, resume, auth refresh, ordering, backpressure; no built-in delivery guarantee
WebRTCBrowser-to-browser audio, video, data, mostly over UDP; needs a signalling server and STUN/TURN for NAT.Calls, screen share, peer dataComplex; TURN relays cost bandwidth
MQTTLight pub/sub protocol with QoS levels for devices on weak networks.IoT, sensors, mobileNeeds a broker
Mobile push (APNs, FCM)Phone vendor keeps one connection; you send via their service.Reach users whose app is closedBest effort, not guaranteed, small payloads; do not make it your only delivery path
Say: "For one-way updates I would start with SSE, because it is plain HTTP, auto-reconnects and works through most proxies. For two-way, frequent messages like chat I would use WebSockets behind a separate connection gateway, with push notifications and a durable store for offline users."

WebSocket details worth knowing

  • Handshake: normal HTTP GET with Upgrade, Connection: Upgrade, and a random Sec-WebSocket-Key; server replies 101 Switching Protocols. Authenticate during this step (cookie or short-lived token) and check the Origin header.
  • Frames: small text or binary messages with a few bytes of header (not hundreds like HTTP).
  • Ping and pong: built-in control frames, but browsers do not expose them, so add your own application heartbeat to detect dead connections through NATs and proxies.
  • Not included: reconnect, message ids, acknowledgements, ordering across reconnects, fan-out to many users, backpressure. You design those.

Scaling stateful connections

Per server

  • Plan about 100,000 connections per gateway (idle connections are cheap, CPU is what limits)
  • Memory about 30 KB per connection, so 100k = about 3 GB
  • Raise file descriptor limit (ulimit -n) well above target
  • Watch accept backlog and NAT conntrack tables

Load balancing

  • Connections last hours, so balance by connection count, not request count (least connections)
  • On deploys, drain gradually; do not drop everyone at once
  • Cap connections per user and per IP; limit message size and rate

Separate gateway tier

  • Gateways only hold connections and forward messages
  • Business logic stays in stateless services that scale and deploy independently
  • Gateways restart rarely (each restart reconnects everyone)
Worked example: 10 million users connected at peak, 100,000 connections per gateway at about 60 percent CPU target = 100 gateways, plus headroom for a zone failure and deploys (say 150). Memory about 30 KB x 100k = 3 GB per gateway. Heartbeat every 30 s from 10M clients = about 333,000 tiny messages/s just to say "still here". If one message per 2 minutes per user: about 83,000 messages/s outbound.

Routing a message to the right gateway

BackplaneGoodBad
Redis pub/subVery fast, simple, low latencyFire and forget: nobody listening means the message is gone; no replay
KafkaDurable, replayable, ordered per partitionHigher latency, heavier; many tiny per-gateway topics are awkward (use partitions by gateway or user)

Common answer: Redis pub/sub for the live push, plus a durable store (database or log) as the source of truth, so a missed push is recovered by the client asking "what did I miss since sequence N?".

Delivery, ordering, heartbeats, reconnect, offline, presence

  • Delivery: practical guarantee is at-least-once: the sender retries until acknowledged, the receiver removes duplicates using a message id. "Exactly once" is at-least-once plus dedupe.
  • Ordering: give each conversation (or user stream) an increasing sequence number assigned by one owner (a partition). The client shows by sequence and asks for gaps.
  • Heartbeats: client sends a small ping every 20 to 30 s; server closes connections that miss two or three. This frees dead sockets and updates presence.
  • Reconnect: exponential backoff with jitter (random delay), otherwise a server crash makes millions reconnect at once (a reconnect storm). Server also sheds load: limit new connections per second.
  • Resume: the client sends the last sequence or event id it saw; the server replays from there (SSE does this with Last-Event-ID).
  • Offline users: write every message to a durable store first, then try live delivery, then push notification; on reconnect, sync from the store.
  • Presence: online status is a key with a short TTL refreshed by heartbeats. Fan-out is the cost: telling every friend of a user with 5,000 friends each time they go online is expensive, so send presence only to people looking at that user, batch it, or fetch it on demand. Typing indicators are ephemeral: send, never store, and rate limit.
Traps: using sticky sessions as the routing answer (breaks on failure); no jitter on reconnect; trusting TCP to tell you a client is gone; storing presence forever; letting one gateway crash lose messages because they were only in memory; assuming push notifications always arrive; no limit on message size or rate per connection; putting business logic in the gateway.

5. Serialization, compression and batching Ch 07

One line: the format you pick decides CPU cost, bytes on the wire, and whether old and new code can keep talking after the data changes; compression and batching then trade CPU and a little waiting for fewer bytes and fewer calls.

Text vs binary

FormatKindGoodBad
JSONText, self-describingHuman readable, universal, easy debuggingBig (field names repeated), slower to parse, no real number or binary types, no schema by default
XMLTextNamespaces, schemas, legacy systemsVerbose, heavy
CSVText, flatSpreadsheets, bulk exportsNo types, no nesting, quoting bugs
Protocol BuffersBinary, schema requiredSmall, fast, strong evolution rules, gRPCNot readable without the schema
AvroBinary, schema required (schema travels or is looked up)Compact; reader and writer schemas resolve differences; big in Kafka and data pipelinesNeed a schema registry
Thrift, MessagePackBinaryThrift: like Protobuf with RPC. MessagePack: "binary JSON" without a schemaLess common now
FlatBuffers, Cap'n ProtoZero-copy binaryRead fields straight from the buffer with no parsing step (games, very low latency)Larger, awkward to use
Parquet, ORCColumnar filesAnalytics: read only the columns you need; compress wellPoor for single-row lookups and frequent small writes
Say: "JSON at the public edge for ease; Protobuf or Avro between services and on Kafka for size, speed and a schema; Parquet for analytics storage."

Inside Protocol Buffers

Each field is sent as a tag (field number plus a wire type) followed by the value. Field names never travel, only numbers, which is why it is small. Numbers use varints: 7 bits of value per byte, and the top bit says "more bytes follow", so small numbers take 1 byte. Strings are length-prefixed. Fields that equal their default are simply left out.

Schema evolution rules

ChangeSafe?Reason
Add a new optional field with a new numberYesOld readers ignore it; new readers see the default for old data
Remove a fieldYes, if you reserve its number and nameNever reuse the number later
Rename a fieldYes in Protobuf (names are not on the wire); breaks JSON and Avro readers by name
Change a field's type or reuse a numberNo (a few types are compatible, avoid it)Old data would be misread silently
Add a required fieldNoOld writers cannot supply it. This is why "required" is considered harmful and removed in proto3
  • Backward compatible: new code reads old data (upgrade readers first for consumers). Forward compatible: old code reads new data. Full: both. Kafka topics usually want at least backward, often full.
  • Avro keeps the writer schema and the reader schema; it resolves differences by field name and defaults. New fields need defaults.
  • Schema registry: stores every version, hands out an id; each message carries just that id, and the registry refuses an incompatible new version before it breaks consumers (a CI check, in effect).
  • JSON evolution: there is no enforcement, so rely on "ignore unknown fields", additive changes, and contract tests.

Compression

AlgorithmRatioSpeedUse
gzipGoodMediumHTTP text responses, universal support
BrotliBetter for textSlow to compress, fast to decompressStatic web assets compressed once ahead of time
zstdGood to very good, tunable levelsFast; supports dictionariesModern default for storage and logs
Snappy, LZ4ModestVery fastKafka, databases, hot paths where CPU matters most
  • Three-way trade-off: compression ratio, CPU time, and speed. Pick by where the bottleneck is: slow network (compress harder), busy CPU (compress lighter).
  • Where: at the edge for user responses; per batch for Kafka (batches compress far better than single messages); at rest for storage and backups.
  • Tiny payloads (a few hundred bytes) barely compress and cost CPU; dictionaries help small repetitive messages.
  • Order: compress then encrypt (encrypted data does not compress). Secrets and attacker-controlled text mixed in one compressed response can leak through size (CRIME and BREACH attacks).
  • Compression bombs: a small upload that expands to gigabytes. Cap decompressed size and ratio.

Batching

  • Sending 1,000 items as one call pays the fixed per-call cost (headers, round trip, disk sync) once. It raises throughput and shrinks bytes (better compression).
  • The cost is latency: the first item waits for the batch to fill. Use two triggers: a size limit and a time limit, whichever comes first (Kafka producer: batch.size and linger.ms).
  • Also seen in database bulk inserts, log shippers, metrics agents, and API bulk endpoints. Make sure one bad item does not fail the batch and that retries are idempotent.
Numbers: JSON is typically 2 to 5 times larger than Protobuf for the same record and several times slower to parse; gzip on JSON text often shrinks it 70 to 90 percent; LZ4/Snappy compress at hundreds of MB/s per core; Kafka linger.ms often 5 to 20 ms to build useful batches; a 1 KB message sent alone carries about as much header overhead as payload.
Traps: reusing or renumbering a Protobuf field; adding a required field; assuming JSON clients ignore unknown fields; compressing already compressed data (images, video); compressing tiny messages one by one; unbounded batch size (memory) or no time limit (a quiet stream never flushes); parsing untrusted input without size limits.

6. Say-aloud script (45 seconds in an interview)

  1. "First I count round trips: DNS, TCP, TLS, then the request. So I reuse connections, terminate TLS near the user, and use HTTP/2 or HTTP/3 at the edge."
  2. "DNS chooses the region with short-TTL, health-checked records, but it is slow to fail over, so inside a region a load balancer with a stable address handles failures."
  3. "The API uses plural resource names, keyset or cursor pagination, one error format, additive evolution, and idempotency keys on every POST so retries are safe."
  4. "For live updates I start with SSE for one-way and WebSockets for two-way, behind a dedicated gateway tier of about 100,000 connections per node, with a registry and pub/sub backplane to route messages."
  5. "Delivery is at-least-once with sequence numbers and client dedupe; reconnect uses backoff with jitter and resume from the last sequence; offline users get a durable store and a push notification."
  6. "Between services I use Protobuf over gRPC with deadlines, with strict field-number rules and a schema registry on Kafka; batches are compressed with zstd or LZ4."

7. Interview Q&A (detailed answers)

Click a question to open the answer. Grouped as: concepts, design scenarios, failure and real-time (production) situations, and trade-off or "why" questions.

A. Concept questions

1. What happens, step by step, when you type a URL and press Enter?

The browser checks its caches, then asks the operating system to resolve the name: the local cache, then a recursive resolver, which walks root, TLD and authoritative servers if it has no cached answer. With the IP address, the browser opens a TCP connection (one round trip), then does the TLS handshake (one round trip on TLS 1.3, two on 1.2), then sends the HTTP request. The request may be answered at a CDN edge near the user, or goes to a load balancer, a web server and the database. The response comes back, the browser parses it and loads more resources, ideally over the same HTTP/2 connection. In an interview I attach a time to each step, for example about 3 round trips before the first byte on a cold connection, to show where caching, connection reuse and a nearby edge help.

2. TCP vs UDP: how do you choose?

TCP gives a reliable ordered byte stream: it resends lost data, orders it, and slows down when the network is crowded. That is right for almost all request and response traffic: web, databases, file transfer. UDP gives raw packets with no promise of delivery or order, but no connection set-up and no waiting for lost packets. It suits cases where late data is worthless (live voice, video, game state) or the exchange is one tiny question and answer (DNS). If you need some reliability on top of UDP you build it yourself, which is exactly what QUIC and HTTP/3 do. My rule: default to TCP; choose UDP only when waiting for a resend is worse than losing the packet, or when I need control TCP does not offer.

3. What is head-of-line blocking and how do HTTP/2 and HTTP/3 deal with it?

It is when one stuck item at the front of a line holds up everything behind it. In HTTP/1.1 a connection handles one request at a time, so a slow response blocks the next ones; browsers open about six connections to cope. HTTP/2 fixes that by multiplexing many streams on one connection, but all those streams still share one TCP connection, and TCP delivers bytes in order, so one lost packet pauses every stream until it is resent. HTTP/3 runs on QUIC over UDP, where each stream is delivered independently, so a loss only delays its own stream. This matters most on lossy networks such as mobile.

4. What does a TLS handshake do, and how can you make it cheaper?

It does three jobs: the server proves who it is with a certificate signed by a trusted authority, both sides agree on encryption settings, and they derive a fresh session key using an ephemeral key exchange, which gives forward secrecy. After that, data is encrypted with a fast symmetric cipher. The cost is mostly delay: one round trip in TLS 1.3, two in TLS 1.2. To cut it: use TLS 1.3, reuse connections through pools and keep-alive, enable session resumption, terminate TLS at an edge close to the user so the long-distance round trips are short, and use HTTP/3 which merges transport and TLS set-up. 0-RTT resumption is faster still but its data can be replayed, so only allow it for safe reads.

5. Explain how DNS resolution works and where caching happens.

Your app asks the OS stub resolver, which asks a recursive resolver. If the resolver has no cached answer it asks a root server, which points to the TLD servers (for example .com), which point to the authoritative servers for the domain, which return the record. Caches exist in the browser, the OS, the recursive resolver (shared by many users, so the most effective), and sometimes in the application runtime. Each cached entry lives for the record's TTL. That is why a cold lookup can take tens of milliseconds, while a warm one is nearly free, and why changing a record takes as long as the old TTL to reach everyone.

6. What is the difference between a CNAME, an A record and an ALIAS?

An A record maps a name to an IPv4 address (AAAA for IPv6). A CNAME says "this name is another name for that name" and the resolver then looks up the target; it cannot be placed at the zone apex (example.com) because the apex must also hold NS and SOA records, and a CNAME cannot share a name with other records. ALIAS or ANAME is a DNS provider feature that behaves like a CNAME at the apex: the provider resolves the target itself and returns ordinary A records. Use CNAME for subdomains pointing to a CDN or load balancer name, and ALIAS when you need the bare domain to point at one.

7. What is idempotency and why does it matter for APIs?

An operation is idempotent when doing it several times leaves the system in the same state as doing it once. It matters because networks fail in the middle: a client that does not get a reply cannot know whether the server did the work, so it must retry. GET, PUT and DELETE are idempotent by definition; POST is not, so a retried "create order" or "charge card" can run twice. The fix is an idempotency key: the client sends a unique id per intended operation, and the server stores the key and the result, returning the saved result for any repeat. This is also what makes at-least-once delivery in queues and webhooks safe.

8. Compare offset, keyset and cursor pagination.

Offset says "skip N rows, give me 20". It is simple and allows jumping to a page, but the database has to read and discard the N rows, so deep pages get slow, and if rows are added or removed between requests you see duplicates or gaps. Keyset says "give me 20 rows after this key" and uses an index, so the cost is the same at any depth and results are stable, but you cannot jump to an arbitrary page and you need a unique sort key (add the id as a tie-breaker). A cursor is the same idea wrapped in an opaque token, so the server can change the underlying key, sort, or even storage without breaking clients. For feeds and large tables I use cursor pagination; offset is fine for small admin lists.

9. Polling, long polling, SSE, WebSocket: explain each in a sentence and when to use it.

Short polling means the client asks every few seconds; it is simple but wasteful, since most answers are empty, so use it only for loose freshness or as a fallback. Long polling means the server holds the request open until it has news; it works everywhere but costs one request per event. SSE is one long HTTP response where the server streams events to the browser, with automatic reconnect and resume; ideal for one-way feeds like notifications and dashboards. A WebSocket upgrades an HTTP connection into a two-way channel with tiny frames; best for chat, games and collaboration, but you must build reconnect, ordering and fan-out yourself. I choose the simplest one that meets the direction and frequency needs.

10. What does a schema registry do and why use one?

It is a service that stores every version of each data schema (Avro, Protobuf, JSON Schema) and gives each a numeric id. Producers put the schema id in front of each message instead of the full schema, so messages stay small, and consumers fetch the schema by id to decode. The registry also enforces a compatibility rule (backward, forward or full) when someone registers a new version, rejecting changes that would break existing consumers. That moves a nasty production incident (consumers crashing on a bad message) into a build-time failure. It is standard with Kafka.

B. Design scenarios

11. Design the API for creating payments safely, including retries.

Endpoint: POST /payments with an Idempotency-Key header, a body with amount in minor units, currency and a payment method token. Server steps: insert the key with a request hash into a table with a unique constraint; if it already exists and the hash matches, return the stored response; if the hash differs, return 422. Process the payment, store the result under the key in the same transaction as the payment record, and return 201 with a Location. If processing is slow, return 202 and let the client poll GET /payments/{id} or receive a webhook. Concurrent duplicates: the second request waits or gets 409. Keep keys for about 24 hours. Errors use one shape with a request id, and 429 carries Retry-After.

12. Design a "notifications" feed that updates live for 5 million concurrent users.

It is one-way, so use SSE (or a WebSocket if the client also sends frequent messages) behind a gateway tier of about 100,000 connections per node, so about 50 nodes plus headroom for failures and deploys. A registry (Redis, with TTL refreshed by heartbeats) maps user to gateway. When something happens, the notification service writes to a durable store first, then publishes to the pub/sub topic of the user's gateway, which pushes it down the connection. Each event has an increasing id; on reconnect the client sends the last id and the server replays what was missed. Offline users get mobile push notifications. Add per-user and per-IP connection limits, heartbeat every 30 s, and backoff with jitter on the client.

13. Design the API and behaviour for a long-running export job.

POST /exports with the filters and an idempotency key returns 202 Accepted with Location: /exports/123 and a body showing state "queued". A worker does the job from a queue. GET /exports/123 returns the state (queued, running, done, failed), progress, and when done a link (a signed, expiring URL to the file in object storage). Offer a webhook for completion with a signed payload and retries, and let clients cancel with DELETE. The job is idempotent and resumable so a worker crash does not restart from zero. Limit concurrent jobs per tenant so one customer cannot starve others.

14. Design the failover so a regional outage moves traffic in under 2 minutes.

Use health-checked DNS records with a short TTL (30 to 60 s) pointing to each region's load balancer address, with the health check probing a real dependency-aware endpoint every 10 s and declaring failure after 3 misses. The worst case is about 30 s detection plus 60 s TTL = 90 s, and a tail of clients or resolvers that ignore TTLs will take longer. To do better, put a global anycast or global load balancer in front so the address never changes and the network re-routes in seconds, and keep DNS only for coarse routing. The data side must also be ready: replicated databases and a tested promotion procedure, otherwise moving traffic only moves the failure. Rehearse it with a game day.

15. How would you version a public API that already has thousands of clients?

First avoid needing versions: only make additive changes (new optional fields, new endpoints), tell clients to ignore unknown fields, and keep field meanings stable. When a breaking change is truly needed, introduce /v2 (or a header version) alongside v1, run both, and map both onto the same internal logic. Announce a deprecation date, add Deprecation and Sunset headers to v1, measure per-client usage, contact the biggest clients directly, and only switch v1 off when traffic is near zero or the date passes. Contract tests and a published changelog catch accidental breaks before release.

16. Design a chat message delivery path between two users on different servers.

Both users hold WebSockets to gateways (G1 and G2). The sender's message goes to a chat service, which assigns a per-conversation sequence number and writes it to a durable store first. It then looks up the recipient in the registry, finds G2, and publishes to G2's channel on the pub/sub backplane. G2 pushes it down the socket; the client acknowledges and the sender sees "delivered". If the recipient is offline, the registry has no entry, so we send a mobile push notification and the client syncs from the store on next connect. Duplicates are removed by message id; gaps are found by sequence numbers.

17. You must send 50,000 events/s from services into Kafka. How do you pick the format and settings?

Use Avro or Protobuf with a schema registry, enforcing at least backward compatibility, because many independent consumers will read these events for years. Batch on the producer with a size limit and a short linger time (for example 5 to 20 ms) and compress each batch with LZ4 or zstd: batches compress far better than single messages and the broker stores them compressed. Keep messages small by sending ids and a few key fields rather than whole objects when consumers can look up the rest. Make the producer idempotent and the consumers tolerant of duplicates. Measure end-to-end latency to confirm the batching delay is acceptable.

C. Failures and real-time production scenarios

18. After a deploy, your service starts failing with "cannot assign requested address" at 600 requests/s. What is wrong?

This is ephemeral port exhaustion. A client talking to one destination IP and port can only vary its own source port, and Linux gives about 28,000 by default. Each short connection that closes leaves a socket in TIME_WAIT for about 60 s, so the sustainable rate of new connections is about 28,000 / 60 = 470 per second. At 600 requests/s with a new connection per request you run out. Fix it in this order: reuse connections with a pool and keep-alive (the real fix), let the server close first so TIME_WAIT lands on the side with the listening port, widen the port range or add source IPs or backend ports, and only as a secondary measure enable tcp_tw_reuse. Do not shorten TIME_WAIT blindly. Then check that a recent change did not disable the pool.

19. One data centre restarts and 2 million WebSocket clients reconnect at the same second. What happens and how do you prevent it?

This is a reconnect storm: all clients retry together, every gateway and the auth service get a huge spike of TLS handshakes and logins, some fail, and those clients retry again, making it worse. Prevention: clients use exponential backoff with random jitter (for example wait random between 0 and min(cap, base times 2 to the n)), the server caps new connections per second and returns a "try later, wait X seconds" hint, authentication tokens can be validated locally without a database call, and gateways have spare capacity and drain gracefully during deploys instead of dropping everyone at once. Resume with the last sequence so reconnecting does not trigger full resyncs.

20. Users report that chat messages arrive out of order or twice. How do you debug and fix?

Possible causes: retries after a lost acknowledgement (duplicates), messages sent through different paths or gateways with different delays (reordering), or two servers assigning ordering numbers. Check logs for the same message id delivered twice and for sequence gaps. The fixes: assign a per-conversation increasing sequence number from a single owner (one partition or shard), have clients dedupe on message id and display by sequence, make sends idempotent, and let the client ask for missing ranges after a gap or reconnect. State plainly that the guarantee is at-least-once plus dedupe, not magic exactly-once.

21. Users see the old IP after you changed a DNS record an hour ago. Why, and what do you do?

DNS is not pushed; caches keep the old answer until their TTL expires, and the TTL may have been long (hours) when you made the change. Some resolvers or apps hold records longer than the TTL, and some runtimes cache forever. Mitigations now: keep the old endpoint working (proxy or redirect to the new one) until traffic drains. For next time: lower the TTL a few days before the change, make the change, wait at least the old TTL, then raise it again; or avoid the change by using a stable address with a load balancer or anycast and changing what is behind it.

22. Your DNS provider has an outage. What still works and how do you design for it?

Clients and resolvers with cached answers keep working until the TTL expires, so a longer TTL on stable records gives more cover; new lookups and cache misses fail. A very short TTL, ironically, makes an outage hurt faster. Design for it with two independent DNS providers serving the same zone (with the same records kept in sync by automation), anycast name servers, and reasonable TTLs for non-failover records. Monitor from outside your network. Remember you also depend on resolvers: keep client libraries from caching failures for too long, and make sure internal service-to-service calls have fallbacks or cached addresses.

23. An API endpoint gets slower the further users scroll, and the database CPU is high. What is happening?

It is almost certainly offset pagination: OFFSET 100000 LIMIT 20 makes the database read and discard 100,000 rows each time. Confirm by checking the slow query log and the plan. Fix by switching to keyset or cursor pagination using an indexed unique sort key (for example created_at plus id), and cap the maximum page depth or page size meanwhile. If clients must keep offset for compatibility, limit deep pages, cache early pages, and offer the cursor version as the recommended path. Also check that the sort columns are covered by an index.

24. A webhook receiver is down for 3 hours. What should the sender do and what should the receiver do on recovery?

The sender retries with exponential backoff and jitter for a defined window (hours to days), keeps a delivery log, and after repeated failures marks the endpoint unhealthy, pauses sending, alerts the customer, and queues events for replay. It also offers a replay API or a "list events since id" endpoint. The receiver, when back, may see old events and duplicates, so it deduplicates on the event id, processes idempotently, verifies the signature, tolerates out-of-order events (using timestamps or versions), responds quickly with 2xx and does heavy work asynchronously.

25. A new service version fails to parse messages in a Kafka topic and the consumer lag grows. What do you do?

Stop the bleeding first: roll back the consumer or route the unparseable messages to a dead-letter topic so the rest keep flowing, because one poison message must not block a partition forever. Diagnose: did a producer register or send a schema change that is not compatible, like a changed type, a reused Protobuf field number, or a removed required field? Check the registry history and the message bytes. Fix by correcting the schema in a compatible way, reprocess from the dead-letter topic once consumers are fixed, and prevent it by enforcing compatibility checks in the registry and in CI, and by upgrading consumers before producers for backward-compatible changes.

26. A gateway node runs out of memory with 150,000 connections. How do you investigate?

Compare with the budget: at about 30 KB per connection, 100,000 connections is about 3 GB, so 150,000 could be 4.5 GB plus the runtime. Look for the real per-connection cost: large per-connection buffers, queued outbound messages for slow clients (no backpressure), subscriptions per connection, or leaked dead connections that were never detected because heartbeats were missing. Fixes: cap per-connection buffers and drop or disconnect slow consumers, enforce heartbeat timeouts, limit subscriptions and message size, set a hard connection cap per node so the load balancer spreads load, and add nodes. Also confirm the file descriptor limit and kernel settings match.

D. Trade-offs and why-questions

27. REST vs gRPC vs GraphQL: which and why?

REST with JSON is the best default for public APIs: every client can use it, it is easy to debug, and HTTP caching and CDNs work. gRPC is better for internal service-to-service calls: a strict contract, small fast Protobuf messages, streaming and deadlines, with code generated for many languages; the costs are limited browser support and harder debugging. GraphQL lets clients ask for exactly the fields they need, which helps when many different clients (mobile, web) need different shapes and chatty multi-call screens, but it complicates caching, rate limiting (by query cost) and protection against expensive queries. Many companies use REST or GraphQL at the edge and gRPC inside.

28. WebSocket vs SSE: why not always use WebSocket?

Because WebSocket's two-way power comes with extra things to build and operate. SSE is plain HTTP, so it passes through proxies, works with HTTP/2 multiplexing, reconnects automatically and resumes with Last-Event-ID, and it is enough when only the server sends. WebSockets need their own upgrade handling, heartbeat, reconnect and resume logic, and sometimes trouble with corporate proxies. Choose WebSocket when clients send frequent messages as well (chat, games, shared editing). If the client's sends are rare, SSE for downstream plus ordinary POST requests for upstream is simpler and often better.

29. Why use Protobuf instead of JSON, and when is JSON still better?

Protobuf is smaller (no field names, varint numbers), faster to encode and decode, and comes with a schema and clear evolution rules, so a typed client in any language is generated for you. That wins for internal high-volume traffic and for data stored or streamed long term. JSON wins where humans and unknown clients are involved: you can read and craft it with a browser or curl, every language supports it, and debugging needs no tools. For small payloads at modest rates the CPU difference does not matter and network latency dominates, so I do not force Protobuf everywhere; I use it where volume, contract strictness, or message size justifies the tooling.

30. Redis pub/sub vs Kafka as the message backplane for real-time delivery?

Redis pub/sub is very fast and simple, ideal for pushing live messages to the gateways, but it is fire and forget: if a gateway is not subscribed at that instant, the message is lost and nothing can be replayed. Kafka is durable and replayable with ordering per partition, so gateways can resume from an offset after a restart, but it adds latency and operational weight, and per-gateway topics are awkward. A common design uses both ideas: a durable store (or Kafka log) as the source of truth for messages, and a light live push for speed, with clients recovering gaps from the durable store using sequence numbers.

31. Where should compression happen, and is it always worth it?

Compress where bytes are expensive and the data is compressible: HTTP text responses at the edge (gzip or Brotli), Kafka batches (LZ4, zstd), and data at rest (zstd, Parquet with its column codecs). It is not worth it for already compressed data (images, video), for tiny payloads where the overhead exceeds the gain, or on a CPU-bound hot path with a fast network, where a very light codec like LZ4 or none is better. Compress before encrypting, set limits on decompressed size to resist compression bombs, and avoid mixing secrets with attacker-controlled text in a compressed response. Measure CPU and bytes saved rather than assuming.

32. Should DNS or a load balancer handle failover?

Use both for different jobs. DNS is good for coarse decisions: pick a region by geography or latency, and move whole regions during a disaster. It is slow and imprecise because of caching: the switch time is health-check detection plus TTL plus clients that ignore TTLs. A load balancer with a stable address detects a bad instance within seconds and stops sending traffic immediately, with no client involvement. So: DNS (or anycast) to choose the region, a load balancer inside it to choose the instance, and health checks at both levels. Promising sub-minute failover through DNS alone is a common mistake.
