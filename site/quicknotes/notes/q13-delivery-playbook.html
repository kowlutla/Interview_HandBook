Pattern playbook, delivery, and last-hour cheat sheet

The last sheet to read before the interview: the recurring design patterns, how to deliver an answer in 45 minutes, and four condensed cheat sheets (numbers, decision tables, failure checklist, microservices checklist). Full explanations: Handbook Chapters 60 and 61 and the four cheat sheets.

0. Key definitions (know these cold)

TermDefinition
PatternA reusable answer to a problem that keeps coming back ("two buyers want the last seat"). Name the pattern out loud before you name a product.
Hot keyOne key (a viral product, a celebrity) that gets far more traffic than the others, so the one machine holding it is overloaded while the rest sit idle.
Fan-outSpreading one event to many receivers, for example one post to all followers. Fan-out on write does the work when the post is made; fan-out on read does it when someone opens the feed.
IdempotentDoing the same operation twice has the same result as doing it once. This is what makes retries safe.
Idempotency keyA unique id the client sends with a request. The server remembers it and returns the saved result if the same key comes again, so a retry never charges twice.
CAS (compare-and-set)"Change this value only if it is still what I read." Used for optimistic locking with a version number.
Reservation (hold)Holding an item for a buyer for a short time (about 5 to 15 minutes) before the sale is final. If the buyer does not pay, the hold expires on its own.
OutboxA table in the same database transaction as your data change. A relay reads it and publishes events, so the database and the message broker never disagree.
CDC (change data capture)Reading the database's own change log and publishing each committed change as an event, to feed search, caches and warehouses.
SagaA long business action split into small local steps, each with an "undo" step (compensation) in case a later step fails.
CellA complete, independent copy of the stack that serves some of the customers. A failure in one cell cannot reach the others.
Load sheddingRejecting some requests early and cheaply when the system is overloaded, lowest priority first, so the rest still succeed.
BackpressureSlowing the sender when the receiver cannot keep up (bounded queues, "429 try later"), instead of buffering without limit.
SLO / error budgetSLO: the target ("99.9 percent of reads under 300 ms"). Error budget: how much failure the target allows (about 43 minutes a month at 99.9 percent).
RPO / RTORPO: how much recent data we may lose, in time. RTO: how long we may be down.
Little's LawThings in the system = arrival rate x time each one spends there. It sizes thread pools, connection pools and queues.
Die, slow, lieThe three questions for every box on your diagram: what if it stops, what if it answers late, what if it answers wrong (stale, duplicate)?
Gives, costs, becauseThe sentence template for a trade-off: "X gives us A, costs us B, and I pick it because C."
Distributed monolithServices that must be deployed together or share a database: all the cost of microservices, none of the benefit.

1. The pattern playbook Ch 60

One line: system design questions look different but the same twenty or so problems keep returning. Hear the symptom, name the pattern, then pick the product.

Each pattern has the same five beats: the problem, the technique, the trade-off, the numbers that tell you when you need it, and the chapter that owns the details. Here they are in groups.

1a. Load shape: reads, writes, hot spots, contention

PatternProblem it solvesTechnique (short)Cost
Read-heavy shapingReads outnumber writes by 10:1 or moreCache the hot subset (cache-aside), read replicas, pre-computed or denormalised read models (CQRS), CDN for static contentStale data, replica lag, invalidation bugs
Write-heavy shapingWrites dominate (logs, clicks, chat)LSM-tree storage, batch small writes, buffer through a log or queue, shard by an even key, aggregate before storingExtra latency (5 to 50 ms linger), read cost
Fan-out hybridFeed or timeline; celebrities with millions of followersPush post ids into followers' lists for normal users; for huge accounts store once and merge at read timeTwo code paths; deletes need a read-time filter
Hot key / hot partitionOne key melts one node; adding nodes does not helpDetect with a heavy-hitter sketch; local in-process cache with a 1 to 5 second TTL; split the key (key#0 to key#9); request coalescing; give big tenants their own cellStaleness up to the local TTL; writes must update all copies
Contention controlOversold stock, double-booked seatReservation with TTL; CAS with a version number; pessimistic lock kept tiny; one ordered queue per item; shard the stock into buckets; shed excess demand earlyRetries under conflict; stranded units in buckets
Numbers: one Redis node about 100k simple ops/s, so a key with 500k reads/s cannot be served by any single node. A row under lock held 5 ms tops out at 200 updates/s. A cache atomic decrement does tens of thousands per second. 100M daily users x 2 posts x 200 followers = 40 billion list inserts a day, about 460k/s average, about 1.5M/s at peak: that is why pure push needs the celebrity exception.
Say: "This is a hot-key problem. I would put a one-second local cache in each app server, coalesce misses, and split the key into ten copies for reads. For a hot write key I would use sharded counters."
Trap: an expired reservation must be rejected at confirm time, not only by a background sweeper. Confirm with a conditional write that names the hold id and owner, or a late sweeper allows a double sale.

3. Worked example: combining patterns for a flash sale Ch 60

One line: shed and absorb the load that does not need the scarce item, protect the scarce item with one atomic step, do the slow work asynchronously, then reconcile.

Setup: 2,000 consoles, go-live at noon, 1.5 million users in 30 seconds. About 3 presses each in the first minute is 4.5M requests in 60 s, about 75,000/s on average and about 150,000/s at the spike. Only 2,000 can succeed (0.13 percent), so this is mostly a read-and-reject workload.

ProblemPatternConcrete choice
150k page views/sRead shaping, CDNStatic page from CDN; stock indicator is a tiny cached flag with 1 s TTL
Everyone polls one keyHot keyLocal cache in app servers, coalesced misses
Too many usersAdmission controlWaiting room admits a few thousand per second
Last unitContention controlAtomic decrement on sharded stock; success makes a 10-minute reservation
Slow order creationAsync pipelineWinning holds go to a queue; workers write at the DB's pace
Double clickIdempotencyClient key plus unique constraint
Payment and stock in two servicesSaga, ledgerCompensate by releasing stock on payment failure
Dependency slowsDegradationSwitch off recommendations and live counts; keep checkout alive
Trap: hold time must be longer than the payment timeout, and the charge must be idempotent. Otherwise a late payment success lands after the hold was re-sold, or the buyer is charged twice.
Say: "The skill here is layering: edge and admission first, one atomic step on the scarce resource, async and idempotent for the slow work, reconciliation to prove it."

4. The delivery playbook Ch 61

One line: an interviewer can only score what they hear and see. Make your reasoning visible: the question you are answering, the options, the choice, and why.

4a. What is being scored

DimensionWhat it looks like when it is good
Problem navigationClarify first, build a rough end-to-end design before polishing any part, notice the hardest part and spend time there
Technical depthGo one level below the box: "cache-aside Redis, TTL 24 h with jitter, one node lost remaps about one sixth of keys, so the DB must absorb a spike"
Trade-off reasoningCompare options against the stated requirements, say what would change your mind
CommunicationShort signposted chunks, defined terms, a diagram that matches your words, thinking aloud
CollaborationCheck in, take hints, push back with reasons not defensiveness
Handling ambiguityTurn vague prompts into decisions: ask the questions that matter, state assumptions for the rest, stay flexible when requirements change

4b. The same answer at three levels

SignalMid (about L4)Senior (about L5)Staff / lead (L6+)
ScopeMain flow and one or two parts wellWhole system: data, scale, failureSystem plus neighbours, dependencies and adoption
OwnershipQuality of the piecesHow it is run: monitoring, on-call, rollout, SLOsWho owns each part, team interfaces, long-term cost
AmbiguityAsks clarifying questionsResolves it with explicit assumptionsChallenges the problem and how success is measured
Trade-offsMain alternative and one costTwo or three options with numbersAdds team skills, migration risk, lock-in, time to market

What lead adds: phases (what ships in month one, what waits, what you will not build yet), people (which team owns which service), migration (shadow mode, small traffic percentage, dual write or CDC with reconciliation, a rollback), and a closing "what I would worry about" list of two or three real risks with mitigations.

4c. Clarifying questions that change the design

FamilySample questionWhat it changes
Functional scope"Only create and read, or also edit, delete, analytics?"API, data model, number of services
Scale"Daily active users? Read-heavy or write-heavy?"Sharding, caching, queues
Consistency"After posting, must the user see their own post straight away?"Replication mode, cache invalidation, store choice
Latency and availability"p99 under 200 ms? Can we tolerate brief downtime?"Hops, caching, multi-region

Trap: asking ten questions in a row (an interrogation), asking questions whose answer you will ignore, or asking none. Five or six grouped questions, then a stated list of assumptions. If the interviewer says "you decide", that is the test: pick a value, give a one-line reason, and say what changes if it is wrong.
Say: "I am going to assume 100 million daily users, because that is large but not the largest. If it were ten times that, I would revisit the storage layer." Keep five to eight numbered assumptions in a corner of the board.

4d. Driving the conversation

  • Agenda (10 seconds): "Estimate, then API and data model, then high-level design, then a deep dive on the riskiest part, then failures. Does that work, or is there somewhere you want more time?"
  • Signposts: "Now the write path." "So far we have X; that covers the happy path." "I will park notifications and come back if there is time."
  • Check-ins: four to six times, at the end of each phase ("Should I go deeper here or move on?"). Each one is a cheap way for the interviewer to hint.
  • Interruptions are evidence, not failure. Answer briefly, then return: "Back to the read path, where I was about to..."

4e. Whiteboard technique

HabitWhy
Flow left to right: clients, edge, services, data storesReaders expect it and follow without help

4f. Trade-off language

Template: "X gives us A, costs us B, and I would pick it because C. I considered Y, but it loses here because D. I would switch if E."
WeakStrong
"We will use Kafka.""A durable log such as Kafka, because we need replay and several independent consumers. A simple queue is lighter but cannot rebuild the search index."
"NoSQL scales better.""A wide-column store gives write scaling by partition key and costs ad hoc queries. Our access is lookup by key, so it fits."
"We could use either.""Both work. I pick the first because of X and would switch if Y."

Choosing the deep dive: pick the riskiest part, not the easy one. Ask: where is the scale pressure highest, where is correctness hardest (ordering, duplicates, consistency), and what is least obvious? URL shortener: ID generation and the redirect path. News feed: fan-out and celebrities. Chat: ordering, delivery guarantees, presence. Use a stack discipline: announce the dive, go deep, then say "coming back up, in the whole system it sits between X and Y".

4g. Hints, pushback, not knowing, mistakes, curveballs

MomentGood response
Hint"Good catch." Solve out loud, then update the diagram or assumptions. Never fight a hint.
Pushback ("why not just a relational DB?")Restate the concern. Defend with a number ("at 50,000 writes/s one primary is the bottleneck") or concede cleanly and change the design. Do not become defensive; do not cave without reasons.
Not knowingAdmit the boundary, reason from first principles ("it must give ordered delivery per key and durability"), ask one focused question. Never bluff, never freeze.
Own mistakeSay it plainly, fix it, follow the consequence: "100M posts at 1 KB is 100 GB a day, not 10. A single node is out, I shard sooner."
Curveball ("now three regions")Restate, map to the assumption it breaks, say what changes and what does not, propose the smallest sufficient change with its cost, say what you defer. Do not redesign from scratch.

4h. Microservices talking points and production stories

  • Why split: independent deploy and scale, failure isolation, team autonomy. Cost: network calls, distributed data, harder debugging. Small team or fuzzy domain: modular monolith first.
  • Boundaries: business capability and data ownership; each service owns its data.
  • Sync vs async: sync where the user waits; events where it can wait. Say what happens when the callee is slow.
  • No cheap distributed transactions: saga with compensations plus outbox.
  • Be willing not to split: "I would keep payments and ledger together because they need one strong transaction."
  • Real experience: context, your exact role, decision, result, lesson. Numbers ("8,000 req/s peak, 400 GB table"), one scar ("hot partition caused two hours of lag; we salted the key and added a lag alert"), and one hindsight ("idempotency keys from day one"). Do not claim your team's work as yours or invent numbers.

4i. Anti-patterns

MistakeFix
Jumping to tech names in minute twoDescribe the need ("a durable log with replay"), then name a product
Buzzword stacking (mesh, CQRS, event sourcing for CRUD)Each component names the requirement that forces it
Over-engineering (multi-region for 1,000 users)Start simple, scale where the estimate says

5. The 45-minute interview time plan Ch 61

One line: without a plan, candidates overspend on estimates and the first diagram, rush the deep dive, and skip failures. Failure handling is short but must exist: senior signal concentrates there.
Numbers: real design time is about 35 to 50 minutes of a 45 or 60 minute slot. High-level design plus deep dive take about half to two thirds. Reserve about 6 to 8 minutes for failures and scaling. Ask 5 or 6 clarifying questions, state 5 to 8 assumptions, check in 4 to 6 times.
Say (practice habit): practise aloud at a real board, with a visible timer, recorded audio, and mock interviews with a person who interrupts. After each run, pick the two lowest items on the self-review list and fix only those.

Day-of checklist

  • Before: test video, audio, canvas; re-read Numbers and Decision Tables; prepare two or three production stories with numbers and one question for the interviewer; warm up by talking one familiar design aloud for five minutes. Do not learn new topics today.
  • During: clarify 5 minutes, state assumptions, give the agenda; estimate, draw the simplest design, number the flows; name the bottleneck before each addition; pick the riskiest deep dive and say why; keep 8 minutes for failures; check in; take hints with thanks; if lost, say so and reason from first principles.
  • After: summarise in three sentences, list open risks, ask a real question, write down what to improve while memory is fresh.

6. Cheat sheet: numbers to remember Cheat sheet

One line: all values are order of magnitude ("about"). Be within a factor of two or three, round aggressively (86,400 becomes 100,000; 365 becomes 400), say that you are rounding, and always end with the design consequence.

Sizes and constants

  • 2^10 about 1 thousand (KB), 2^20 million (MB), 2^30 billion (GB), 2^40 trillion (TB), 2^50 (PB)
  • 1 day = 86,400 s, about 10^5. 1 month about 2.6M s. 1 year about 3 x 10^7 s
  • 32-bit int about 4.3 billion; UUID = 128 bits (16 bytes binary, 36 chars text)
  • Network speeds are bits/s, storage is bytes: divide by 8 (an 8x error is common)

QPS shortcut

  • Per day / 10^5 = per second. 1M/day about 12/s; 100M/day about 1,150/s; 1B/day about 11,600/s
  • Peak = 2 to 3x average for global consumer traffic; 10x or more for flash sales and launches
  • Read:write ratio then splits the total (feed about 100:1)

Availability

  • 99.9 percent: about 8.8 h/year, 43 min/month
  • 99.99 percent: about 53 min/year, 4.3 min/month
  • 99.999 percent: about 5.3 min/year
  • Series multiplies: three 99.9 percent in a chain is about 99.7 percent
  • Two independent 99 percent copies in parallel: 99.99 percent

Storage recipe: daily = writes per day x bytes per record. Yearly = daily x 400. Then x3 for replication (erasure coding about 1.4 to 1.5x) and add 20 to 30 percent for indexes. 100M users posting a 3 MB photo a day is about 100 PB a year before replication: object storage, not a database.

The 60-second estimation recipe

  1. Users: 100M monthly, 20M daily active.
  2. Actions: 10 reads and 1 write per user per day = 200M reads, 20M writes.
  3. Per second: divide by 10^5 = 2,000 reads/s, 200 writes/s; peak 3x = 6,000 and 600.
  4. Size: 1 KB per write = 20 GB/day, about 7 TB/year, about 21 TB with 3x copies, about 100 TB over 5 years.
  5. Bandwidth: 6,000 x 5 KB = 30 MB/s, about 240 Mbit/s peak.
  6. Cache: hot 20 percent, 10M keys x 5 KB = 50 GB: a small Redis cluster.
  7. Conclude: 6,000 reads/s is easy; 600 writes/s fits one primary; the 100 TB over 5 years is the real constraint and drives the storage choice.
Trap: average QPS hides bursts, so always state a peak factor. Bits versus bytes gives an 8x error. Throughput figures are single-node ceilings, not targets.
Say: "I will round 86,400 to 100,000. 20 million writes a day is about 200 a second, 600 at peak. That fits one primary, so the real driver is 100 TB over five years."

Numbers: retry amplification = tries per layer ^ layers (3^3 = 27). Quorum = floor(n/2)+1: 3 nodes tolerate 1 failure, 5 tolerate 2. 8f. The 10-point failure walkthrough (say it in order after the main design)

  1. Single points of failure: walk the request path; every box has redundancy across AZs.
  2. Failure model: crash, slow, partial, wrong data, overload; slow is the dangerous one.
  3. Timeouts and deadlines: every call has one, under the caller's deadline.
  4. Retries: backoff with full jitter, one layer, a budget, idempotent calls only.
  5. Idempotency: keys on mutating endpoints; consumers dedupe.
  6. Isolation: bulkheads per dependency and tenant, breakers, cells.
  7. Overload: edge rate limits, priority shedding, bounded queues, autoscale with headroom.
  8. Async failures: backoff then DLQ with alerts and replay; outbox.
  9. Data durability and consistency: sync or async per data class, RPO, what users see in failover, reconcile cross-service flows.
  10. Recovery and detection: SLO alerts, runbooks, tested backups, DR strategy with RPO and RTO, canary and rollback, game days.
Say: "The cache fails, the hit rate drops from 95 to 0 percent, the database sees about 20x the reads, so we coalesce, shed low-priority reads and keep checkout alive. We detect it from the hit-rate alert."
Traps: retries without idempotency, "just add a replica" without naming replication lag, claiming exactly-once delivery, a failover target with no spare capacity, never saying how you would detect the failure.

11. Interview Q&A (detailed answers)

Click a question to open the answer. Grouped as: concepts, design scenarios, failure and real-time (production) situations, and trade-off or "why" questions.

A. Concepts

1. What do interviewers actually score in a system design interview?

Most companies give interviewers a rubric with about six parts: problem navigation, technical depth, trade-off reasoning, communication, collaboration and handling ambiguity. The first three are about the design; the last three are about how you behave while designing, and candidates often neglect them. The interviewer writes down evidence for each part, so anything you think but do not say earns nothing. That is why I say the question I am answering, the options, the choice and the reason. A strong idea that was never spoken cannot be scored.

2. What is the difference between a senior and a lead answer to the same question?

A senior engineer designs a system that works: whole system, data, scaling, failure, plus how it is run (monitoring, rollout, SLOs). A lead designs the path from where the organisation is today. I add phases ("month one ships X, sharding comes when the primary passes about 60 percent CPU"), team boundaries (who owns each service and the contract between them), a migration plan with shadow mode and a rollback, build-versus-buy economics, and a closing "what I would worry about" list of two or three real risks with mitigations. I also challenge the problem itself: what is success measured by?

3. What is a pattern playbook and why name the pattern before the product?

It is a catalogue of the twenty or so problems that keep coming back: hot keys, fan-out, contention, large uploads, counting, presence, ledgers, search, geo, scheduling, notifications, pipelines, idempotency, CDC, rate limiting, multi-tenancy, ML serving, media, leaderboards, sagas and degradation. Saying "this is a hot-key problem" shows I have seen the class of problem and lets the interviewer steer me. Naming a product first ("use Redis") only shows pattern matching. The pattern comes with its trade-offs and the numbers that tell me when it is needed.

4. How do you decide whether a workload is read-heavy or write-heavy, and why does it matter?

I ask for the read-to-write ratio first because the two directions scale with opposite tools. Above about 10 to 1, I use caches, read replicas, denormalised read models and a CDN. Near 1 to 1 or write-dominated, I use batching, a log or queue to smooth bursts, LSM storage, and sharding by an even key. Most systems are read-heavy on the user path and write-heavy on the ingestion path, so I design the two paths separately. Applying read tricks to a write-heavy system just adds stale-cache bugs and does not help.

5. What is idempotency and how do you implement an idempotent payment API?

An idempotent operation has the same effect whether it runs once or many times, which makes retries safe. The client sends a unique idempotency key per logical payment. The server first inserts the key as "in progress" under a unique constraint, then does the work, then stores the response with the key. A concurrent duplicate hits the constraint and waits or gets a conflict; a later duplicate gets the stored response. Keys are scoped per user, kept at least 24 hours, and reusing a key with a different payload is an error. Where possible I also prefer naturally idempotent operations like PUT or "set status to shipped".

6. What is the outbox pattern and what problem does it solve?

The problem is a dual write: I update my database and publish an event, and one of the two succeeds while the other fails, so the systems disagree. With the outbox I write the event to an outbox table in the same database transaction as the data change, so both happen or neither does. A relay process (or CDC reading the log) publishes the rows to the broker, at least once. Consumers dedupe by event id. That gives reliable publication without a distributed transaction.

7. Explain "die, slow, lie" and why slow is the dangerous one.

For each box on the diagram I ask what happens when it dies (stops responding), slows (answers late) and lies (answers with stale, wrong or duplicate data). A dead dependency fails fast and the caller can fall back. A slow one holds threads and connections, queues build, retries add load, and the failure climbs upstream until the whole system is down. So every call needs a timeout, retries need a budget, and a circuit breaker should turn slow into fast failure. I state the blast radius and recovery, such as "one shard of users sees errors for about 30 seconds and no acknowledged writes are lost".

8. What do RPO and RTO mean and how do they pick a disaster recovery strategy?

RPO is how much recent data I can lose, measured in time. RTO is how long I can be down. Backup and restore has an RPO of hours and an RTO up to a day and is the cheapest. Pilot light has minutes and tens of minutes to hours. Warm standby has seconds to minutes of RPO and minutes of RTO at medium cost. Active-active has near-zero RPO and seconds to minutes of RTO at the highest cost, plus conflict handling. I ask the interviewer for the targets or state them, and I add that failover is tested regularly, because an untested plan is a hope.

B. Design scenarios

9. Design the feed for a social app. How do you handle celebrities?

I start from the read-to-post ratio and the follower distribution. Fan-out on write pushes a post id into each follower's precomputed list, so a read is one lookup, but a post by an account with 50 million followers would cost 50 million inserts. Fan-out on read stores the post once and merges at read time, which makes reads expensive for people who follow many accounts. The standard answer is a hybrid: push for normal accounts, pull for celebrities, and at read time merge the pushed list with the recent posts of the few celebrities the reader follows. Lists hold only ids and I filter deleted or hidden posts at read time, so the post store stays the source of truth. I also skip push for inactive users to save writes.

10. Design checkout for a flash sale of 2,000 units with 1.5 million users.

The load is about 150,000 requests per second at the spike but only 2,000 can succeed, so it is mostly read-and-reject. I layer it. The CDN serves the page, and a tiny cached stock flag with a 1 second TTL answers "sold out" without touching the backend. A waiting room admits a few thousand users per second with signed tokens. The scarce item is protected by an atomic decrement on sharded stock buckets in a cache, and a win creates a 10-minute reservation. Winners go to a queue, so workers write orders at the pace the database sustains. Checkout has an idempotency key, payment and stock are a saga with compensation, and a reconciliation after the sale compares units, holds, ledger entries and provider settlement.

11. How would you build a reliable job scheduler for delayed work?

I persist each job with its due time in durable storage, for example a table indexed on run_at or a sorted set keyed by due time, so the schedule survives restarts. Workers poll for due jobs and claim them atomically with a lease (a conditional update or SELECT with SKIP LOCKED). If a worker dies the lease expires and another worker takes the job, which gives at-least-once execution, so jobs must be idempotent. To scale, I shard jobs by id or bucket by time slice. Failures retry with exponential backoff and jitter and finally move to a dead-letter queue with an alert. In-memory timers or timing wheels are only a cache over this durable record.

12. Design large file upload for 4 GB videos.

I split the file into 5 to 16 MB parts and upload them in parallel; a failed part is retried alone. The server or object store tracks received parts, so after a disconnect the client asks which parts exist and sends only the missing ones. My app server authenticates the user and hands out presigned URLs, so the bytes go straight from client to storage and my servers only handle metadata. Each part has a checksum, and a final "complete" call assembles the file so readers never see a half-uploaded object. I use content-hash dedup (per user is safer than global), CDN range requests for downloads, and a lifecycle rule to clean up abandoned uploads. 4 GB in 8 MB parts is 512 parts, about 20 seconds with 8 streams at 25 MB/s.

13. How do you count likes on a viral post and unique viewers?

A single counter row becomes a hot key and a lock convoy. For likes I use sharded counters: 16 or 64 sub-counters, each increment goes to a random one, and a read sums them or reads a cached total. I can add write-behind aggregation in memory, flushing a combined delta every second, accepting that a crash loses the unflushed delta for non-critical counts. For unique viewers I use HyperLogLog: about 12 KB and 1 to 2 percent error, versus about 800 MB to store 100 million 8-byte ids exactly, and HLLs can be merged. Anything that is money or stock stays exact, transactional and reconciled with the event log.

14. How do you show who is online in a chat app?

Nobody reliably announces going offline, because phones lose signal and processes crash, so I infer absence. The client sends a heartbeat every 15 to 30 seconds, which refreshes a key like presence:user42 with a TTL of about 45 seconds. If heartbeats stop, the key expires and the user is offline with no cleanup job. Events flow through pub/sub topics per room to the gateway servers that hold the connections, using a user-to-gateway registry. I limit presence fan-out (only users who currently see that contact, debounce flapping), and persist messages for offline users to deliver by cursor on reconnect. 10 million users heartbeating every 20 seconds is 500,000 writes a second, so presence needs sharding too.

15. Design a payments ledger.

For money, approximately right is a bug. I use double-entry bookkeeping: every transfer is at least two entries that sum to zero. Entries are immutable and append-only, and mistakes are fixed by a reversing entry. All entries of a transaction post in one database transaction. Balances are derived from entries, with a cached running balance that can be recomputed. Amounts are integers in the smallest currency unit with a currency code. Requests carry idempotency keys so a retry never charges twice, and a reconciliation job compares the ledger with the processor's settlement file and lists exceptions for repair or human review.

16. How would you build search with autocomplete?

Full text uses an inverted index (term to document list) scored with BM25. The index is split into shards, a query goes to all shards and each returns its top K, and a coordinator merges them, so latency is set by the slowest shard. The search cluster is a derived copy fed from the source of truth by CDC, never the source itself. Autocomplete uses a trie, an edge n-gram index or a sorted set per prefix with the top few completions precomputed from query logs. I rebuild hourly or daily, layer in trending queries, and cache the first one or two characters because they are the hottest keys.

C. Failures and real-time production scenarios

17. The cache cluster dies. What happens and what do you do?

Hit rate falls from about 95 percent to 0, so the database suddenly sees about 20 times the reads. If it was sized only for the misses, it may fall over. In the first minutes I turn on request coalescing so one query per key reaches the database, shed low-priority reads, and keep the checkout or critical path alive. The circuit breaker on the cache client makes calls fail fast instead of waiting for timeouts. Afterwards I warm the top keys gradually, and in the design review I size the database for a plausible cache outage and add cache replicas. I detect it from the hit-rate and origin-QPS alerts.

18. p99 latency spiked but p50 is fine. How do you investigate?

A fine median with a bad tail points to something that hits only some requests. The usual suspects are a hot key or hot shard, a stampede on an expiring key, garbage collection pauses, one slow replica, or the tail of a scatter-gather where the slowest shard sets the latency. I check per-shard and per-key latency and QPS, cache hit ratio by key, GC logs and dependency latency. Fixes depend on the cause: local cache and key splitting for hot keys, coalescing for stampedes, hedged reads after the p95 for slow replicas, and load shedding if it is overload. Tail latency compounds across sequential calls, so I also check the call depth.

19. Customers report duplicate charges after a timeout incident. What happened and how do you fix it?

The client timed out, retried, and the server had in fact succeeded the first time, so it charged again. The fix is an idempotency key per payment stored under a unique constraint with the result; a retry returns the saved result. I also check the retry design: retries at several layers multiply, and the key must be stored before or atomically with the side effect, otherwise a crash leaves a gap. On the message side, consumers dedupe by message id, because delivery is at-least-once. Finally I run a reconciliation against the processor to find and refund the existing duplicates.

20. A queue backlog keeps growing. What do you check?

I look at queue depth and the age of the oldest message, then consumer lag and error rate. A poison message that always fails can block a partition, so I check for repeated redelivery and move it to a dead-letter queue after a few attempts. If consumers are healthy but slow, I scale them out, up to the partition count for a log. If producers outpace consumers permanently, I add backpressure or shed low-priority work, and check whether a downstream dependency is slow, since that is a common cause. Unbounded queues only hide the problem and turn it into memory exhaustion, so I keep them bounded and alert on age, not just depth.

21. One tenant makes the whole service slow. How do you contain it?

That is a noisy neighbour. Immediately I apply per-tenant rate limits and quotas so that tenant is throttled with 429 and Retry-After rather than starving the others. I use separate pools (bulkheads) and priority classes so one tenant cannot use all threads or connections. Long term I shard by tenant, move the whale to its own shard or cell, and keep a router from tenant to cell so a failure or bad release stays inside one cell. Tenant id must travel in every call, log line, message and cache key and be enforced at the data layer, because cross-tenant leaks are the worst bug class.

22. Search results are stale compared with the database. Why and how do you fix it?

Usually the application dual-writes to the database and the index, and one write fails or the indexer lags. The fix is to make the database the single source of truth and feed the index from its change log with CDC, partitioned by primary key so one row's changes stay ordered, with idempotent upserts keyed by id and version. New consumers bootstrap from a snapshot and then switch to the log. I add a periodic reconciliation that compares counts or checksums between source and index, and monitor index lag as a metric. A short lag is acceptable if I state it.

23. A retry storm takes down a service after a dependency slowed. What is the fix?

Slow dependency calls held threads, callers timed out and retried, and the retries multiplied the load; with three layers each retrying three times it is 27 times. I add timeouts on every call under the caller's deadline, retry at only one layer with exponential backoff, full jitter and a budget such as 10 percent of traffic, and only for idempotent calls. A circuit breaker stops calls to the sick dependency for a cool-down period. Bulkheads keep that dependency from using the shared pool, and load shedding rejects excess requests early with 503. I also make sure there is a tested fallback, such as stale data.

24. An order is stuck half-complete across services. How do you recover and prevent it?

Without cross-service atomicity, a failure between steps leaves partial state: money held but no order, or stock reserved but no payment. A saga has compensating actions (refund, release stock) and a persisted state per step, so a replacement worker can continue or roll back. I add per-step timeouts and a stuck-saga detector, and a reconciliation job that finds orders in a pending state past their limit and fixes or alerts. Steps that cannot be undone, like sending an email, go last. The UI shows honest pending states. Compensations must be idempotent so retrying them is safe.

D. Trade-offs and why-questions

25. Why default to a relational database, and when would you leave it?

It gives transactions, joins, constraints and ad hoc queries, and one well-tuned primary handles a few thousand writes per second and a few TB of data. That covers most designs, and derived stores (cache, search, warehouse) can be added without replacing the source of truth. I leave it when a number forces me: writes beyond one node that cannot shard cleanly, a pure key-value lookup at huge scale, very high append rates (wide-column or LSM), data that is mostly blobs (object storage), or text search and similarity search. I always name the number that would make me leave, such as 50,000 writes per second.

26. Queue or log: how do you choose?

If consumers must be able to rewind, replay history or read the same data independently, I use a log such as Kafka: high throughput, per-key ordering, many consumer groups. If each message is a job that should be completed once with per-message ack, retries, delay and a DLQ, I use a task queue like SQS or RabbitMQ. Pub/sub is for broadcast where missing an offline subscriber is fine. In every case delivery is at-least-once, so consumers are idempotent. I avoid a log at tiny scale where its operations cost dominates.

27. Strong or eventual consistency?

I decide per feature, not per system. Money, inventory, unique usernames, locks and leader election need linearizable reads. A user's own edits need read-your-writes, which I give through primary reads for a short window or session tokens. Feeds, likes, counters and caches can be eventual. Strong consistency costs latency across regions and availability during partitions (CAP), and even without a partition it is a latency-versus-consistency choice (PACELC). I say the staleness bound out loud, for example "up to about a second of replica lag".

28. When should you shard, and how do you pick the key?

Last. First tune and index, then add cache and replicas, and only shard when data or writes clearly exceed one node with replicas (a few TB, a few thousand writes per second). The key should have high cardinality, spread access evenly and match the query I run most. Hash sharding (consistent hashing) spreads evenly but loses range scans; range sharding keeps scans but monotonic keys make the newest range a hot spot; a directory handles uneven tenants. The cost I accept is cross-shard queries and transactions, which need scatter-gather or sagas.

29. Microservices or a modular monolith?

I default to a modular monolith with enforced module boundaries, and extract a service when a real pain appears: several teams blocked on one release, parts with very different scaling or availability needs, or a compliance boundary. Microservices cost network failure modes, split data, distributed transactions and observability work. They need a platform and clear bounded contexts, otherwise I get a distributed monolith with lockstep deploys and shared tables. Willingness not to split is a sign of experience: I would keep payments and the ledger together because they need one strong transaction.

30. How do you use the last ten minutes of a 45-minute interview?

I spend about six minutes on failures and scaling and three on the wrap. For failures I take the two or three boxes whose failure hurts most and run die, slow, lie, then do a capacity check against my earlier estimates, then name monitoring: SLO burn-rate alerts, queue age and replication lag. The wrap is a three-sentence summary, what I deliberately left out, my top two or three risks with mitigations, and a real question for the interviewer. If I am behind, I stop adding detail and finish the end-to-end path first, because a complete shallow design can be deepened and an unfinished detailed one cannot be rescued.
