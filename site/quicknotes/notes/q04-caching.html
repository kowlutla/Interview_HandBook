0. Key definitions (know these cold)

TermDefinition
CacheA small, fast store that keeps copies of data, so we do not ask the slow database every time.
Cache hit / missHit: the data was found in the cache. Miss: not found, so we go back to the real store (the database or the origin server).
Hit ratiohits / (hits + misses). The single most important cache metric. At 99% hit ratio the backend sees 1% of the traffic.
TTL (time to live)How long an entry may be served before it is considered expired. Bounds staleness.
InvalidationRemoving or updating a cached entry because the source data changed.
Source of truthThe store whose data is the "real" one (usually the database). The cache is only a copy that we can throw away at any time.
Working setThe data actually accessed in a time window. A cache only needs to hold the hot working set, not all data (often 10 to 20% of data serves 80% or more of requests).
Cache keyThe identifier a cache uses to find an entry (e.g. user:42:profile:v3). Good keys are deterministic and include a version.
Stale dataA cached value older than the source. Acceptable only within an agreed staleness bound.
Warm / cold cacheWarm: already populated with hot data. Cold: empty (after restart or deploy), so most requests miss.
Negative cachingCaching the fact that something does not exist (a "not found" result), with a short TTL.
EvictionRemoving entries to free memory when the cache is full (policy decides which). Different from expiry, which is time-based.
OriginThe backend server a CDN fetches from on a miss. POP / edge: a CDN data centre near users.
IdempotentDoing the operation twice gives the same result as doing it once (deleting a key twice is fine). This makes retries safe.
StampedeMany requests miss the same key at the same moment and all rush to the database together.
ReplicaA second copy of a server's data kept on another machine, used as a backup or to share reads.

1. Why cache, and where Ch 13

One line: a cache keeps a copy of data that is slow to get in a place that is faster and closer. We give up some freshness and some memory, and we get quicker answers and less load on the database.

Layers (closest first)

  • Browser / app memory
  • CDN edge
  • API gateway / reverse proxy
  • Local in-process cache
  • Distributed cache (Redis, Memcached)
  • DB buffer pool

Cache when

  • Read-heavy (10:1 or more)
  • Same data read repeatedly (skewed, Zipf-like)
  • Expensive to compute or fetch
  • Slight staleness is acceptable

Do not cache when

  • Write-heavy or unique reads
  • Needs strict read-after-write everywhere
  • Data is cheap to fetch already
  • Per-user secrets without a per-user key
Numbers: RAM read ~100 ns; Redis round trip in a DC ~0.2–1 ms; SSD read ~100 µs; cross-region ~50–150 ms. Hit rate 90% to 99% changes DB load 10x (miss rate 10% to 1%). Average latency = hit% × cache + miss% × (cache + DB).

Hit versus miss, with times

Worked example (sizing in 60 seconds)

Example: 50,000 reads/s, 1 KB per item, 20 million items total. The hot 10% (2M items) serve most traffic, so the cache needs about 2M × 1 KB = 2 GB plus overhead (about 1.5x in Redis) = about 3 GB: one node, or two for HA. At a 95% hit ratio the DB sees 5% of 50,000 = 2,500 reads/s instead of 50,000. Average latency with 1 ms cache and 20 ms DB: 0.95×1 + 0.05×21 ≈ 2 ms vs 20 ms.

Choosing a TTL

  • Pick it from how stale the business can tolerate, not from technical convenience: product description minutes to hours; price seconds to minutes; account balance do not cache (or sub-second).
  • Shorter TTL means fresher data but more misses and more DB load; longer TTL is the reverse.
  • Add jitter (e.g. TTL ± 10%) so a batch of keys written together does not expire together.

Multi-level caching

Typical stack: browser, CDN, local in-process (tiny, a few seconds TTL), Redis, DB. Each level absorbs part of the traffic. The cost is that each added level adds another place where data can be stale, so keep TTLs shorter closer to the user for mutable data.

2. Cache patterns Ch 13

One line: a pattern is just a rule for who talks to the cache and the database, and in what order, on reads and on writes.

3. Eviction and expiry

One line: a cache has limited room. Eviction means throwing out some entries when it is full. LRU (least recently used) throws out the one nobody has touched for the longest time.

Policies

  • LRU: drop least recently used. Default, good for recency.
  • LFU: drop least frequently used. Good for stable hot sets; slow to adapt.
  • FIFO / random: cheap, weaker.
  • TTL: time-based expiry, independent of memory pressure.

Facts

  • LRU = hash map + doubly linked list, O(1) get and put.
  • Redis uses approximated LRU/LFU (sampling), not exact.
  • Add random jitter to TTLs so keys do not expire together.

Redis eviction policies (maxmemory-policy)

PolicyMeaning
noevictionReject writes when full (use when Redis is a store, not a cache)
allkeys-lru / allkeys-lfuEvict from all keys by recency / frequency (typical cache setting)
volatile-lru / volatile-ttlEvict only keys that have a TTL (soonest expiry for volatile-ttl)
allkeys-randomRandom eviction

Why LFU can beat LRU: a one-time scan of many keys pushes hot keys out of an LRU (cache pollution); LFU keeps the keys that are used often. Why LRU can beat LFU: old once-popular keys never leave an LFU without ageing.

4. Failure modes Ch 14

One line: caches fail in a few well-known ways. Most of them end with the database getting far more requests than it can handle.

Stampede: what goes wrong and how a lock fixes it

ProblemWhat happensFixes
Stampede (thundering herd, dogpile)A hot key expires; thousands of requests all miss and hit the DB at once.Let only one request reload the value (single-flight: one request does the work, the others share its result); use a lock or lease (a short-lived permission to reload); serve the old value while refreshing; refresh a little before expiry; add jitter (a small random amount) to TTLs.
PenetrationRequests for keys that do not exist always miss and reach the DB (often an attack).Cache the "not found" answer for a short time; use a Bloom filter (a tiny structure that says "definitely not valid" cheaply); check inputs; rate limit.
AvalancheMany keys expire at once, or the whole cache dies; the DB is overwhelmed.TTL jitter; replicas and automatic failover (switch to the backup); warm-up; circuit breaker (stop calling a failing service) and load shedding (drop low-priority requests); several cache layers.
Hot keyOne key gets far more traffic than one node can serve.Local in-process cache in front; replicate hot key across nodes (key suffix 1..N); detect hot keys and promote.
Stale / inconsistentCache and DB disagree after a write or a lost invalidation.Delete on write; TTL; version stamps; CDC-driven invalidation from the DB log; accept bounded staleness explicitly.
Cold startEmpty cache after deploy or restart means a miss storm.Pre-warm top keys; gradual traffic shift; persistence (Redis RDB/AOF).
Trap: "the cache is just an optimisation" is false once the DB cannot survive without it. Size the DB for a plausible cache outage or have load shedding.

The read-fill race (classic follow-up)

Scenario: Reader A misses and reads old value v1 from the DB. Writer B updates the DB to v2 and deletes the cache key. Reader A then writes v1 into the cache. The cache now holds v1 (stale) until the TTL.
Mitigations: short TTL as backstop; versioned writes (only set if version is newer); lease tokens (the cache gives a token on miss; a delete invalidates it so the stale fill is rejected); delayed second delete a moment after the write.

Consistency stance by data type

DataStance
Static assets, product descriptionsLong TTL or versioned URLs; stale is fine
Feeds, counters, view countsEventual consistency; seconds of staleness fine
User's own profile just editedRead-your-writes: bypass cache or update it on write for that user
Inventory, balances, paymentsRead the DB (or cache with very short TTL for display only, never for the decision)

5. Redis Ch 15

One line: Redis is a server that keeps data and useful structures (lists, sets, sorted lists) in memory. It runs one command at a time, so each command is atomic (it finishes completely before the next starts). It can also save data to disk, keep copies on other machines, and split data across machines (sharding).

Structures to name

  • String: cache values, counters (INCR), locks (SET NX EX)
  • Hash: object fields
  • List: queues, recent items
  • Set: uniqueness, tags
  • Sorted set: leaderboards, delayed jobs, rate limit windows
  • Others: streams, bitmap, HyperLogLog, geo

Persistence

  • RDB: periodic snapshot. Compact, fast restart, can lose minutes.
  • AOF: log of writes. fsync every second (typical) loses about 1 s.
  • Both can be combined. Pure cache: often neither.

Scaling and HA

  • Replication: the leader copies data to followers in the background (async). Writes not yet copied can be lost if the leader dies.
  • Sentinel: monitors and promotes a replica (non-sharded).
  • Cluster: 16384 hash slots spread over nodes; client routes by slot; multi-key ops need the same slot (hash tags).
Numbers: one Redis node roughly 100k simple ops/s (order of magnitude, pipelining raises it); value limit 512 MB but keep values small (KB); big keys and slow commands (KEYS, big SMEMBERS) block everyone because execution is single-threaded.
Traps: using Redis as the only copy of important data without persistence and replication; lock via SET NX without expiry or without a fencing token (see Chapter 30); big-key deletes blocking the server (use UNLINK).

6. CDN Ch 12

One line: a CDN (content delivery network) is a cache spread over many cities. Static files (and some dynamic ones) are served from a data centre near the user (the edge), not from your own server far away (the origin).

How it works

  • DNS or anycast sends the user to a nearby edge (POP).
  • Hit: served from edge. Miss: edge fetches from a mid-tier or origin, caches by cache key (URL plus chosen headers).
  • Tiered caching reduces origin load (edge to regional to origin).

Push vs pull

  • Pull: fills on first request. Simple, default.
  • Push: you upload ahead of time. Good for large, predictable files (video releases).

Invalidation

  • Versioned URLs (app.v123.js or content hash): best, no purge needed.
  • TTL via Cache-Control (max-age, s-maxage, stale-while-revalidate).
  • Explicit purge API: works but slow to propagate and costly at scale.
  • Signed URLs / cookies: time-limited access to private content at the edge.
  • Also does: TLS termination close to users, DDoS absorption, compression, image resizing, edge compute.
  • Cost note: egress from the CDN is usually cheaper than from the origin cloud; high hit ratio is the lever.

Cache-Control headers to know

Trap: forgetting that varying the cache key on cookies or many query params destroys the hit ratio; and caching personalised responses publicly leaks data (use Cache-Control: private or Vary correctly).

7. Say-aloud script (30 seconds in an interview)

  1. "Reads are about 100:1 and skewed, so I add a cache in front of the database."
  2. "Static assets go to a CDN with versioned URLs; API reads use Redis with cache-aside."
  3. "On write I update the DB and delete the key; every key has a TTL with jitter as a safety net."
  4. "For hot keys I add a small local cache and request coalescing so a miss does not stampede the DB."
  5. "If the cache is down the DB must still survive: replicas for the cache, load shedding, and a circuit breaker."
  6. "I accept bounded staleness of a few seconds on this data; for balances I would read the DB directly."

8. Interview Q&A (detailed answers)

Click a question to open the answer. Grouped as: concepts, design scenarios, failure and real-time (production) situations, and trade-off or "why" questions.

A. Concept questions

1. What is caching and why does it help?

Caching stores a copy of data that is expensive to get (a DB query, a computed result, a remote file) in a faster and closer place such as memory, so repeated requests skip the slow path. It helps in two ways: lower latency for the user (microseconds to a millisecond instead of tens of milliseconds) and lower load on the backend, which lets the same database serve many more users. It works because access patterns are skewed: a small hot set of data gets most of the requests. The price is staleness and the extra complexity of keeping copies in sync, so you only cache data that is read much more often than it changes.

2. Explain cache-aside, read-through, write-through, write-back and write-around, and when to use each.

Cache-aside: the application checks the cache, on a miss reads the DB and fills the cache; on a write it updates the DB and deletes the key. It is the default because the cache is optional and simple. Read-through: the cache library loads from the DB on a miss, so application code only talks to the cache. Write-through: every write goes to cache and DB synchronously, so reads after writes hit a fresh cache, at the cost of slower writes. Write-back: writes go to the cache and are flushed to the DB later in batches; very fast writes but you can lose data if the cache fails before the flush. Write-around: writes go straight to the DB and skip the cache, good for data written once and rarely read. In an interview I name cache-aside first and mention the others only when the workload (write-heavy counters, read-after-write needs) calls for them.

3. What is the difference between eviction and expiry?

Expiry is time-based: an entry is removed or ignored after its TTL passes, regardless of memory. Eviction is memory-based: when the cache is full, a policy such as LRU or LFU picks entries to remove to make room. A cache normally uses both: TTL to bound staleness and eviction to bound memory.

4. LRU vs LFU: which and why?

LRU removes the entry unused for the longest time and suits workloads where recent data is likely to be needed again. LFU removes the entry used least often and suits a stable set of popular items. LRU is vulnerable to scans (one large read pushes out all the hot keys); LFU is vulnerable to old popular items that stay forever unless counts decay. Redis implements approximate versions by sampling a few keys, which is cheaper than keeping an exact ordering. My default is LRU (or allkeys-lfu in Redis for stable hot sets) and I check the hit ratio to confirm.

5. Why is Redis fast, and what does single-threaded mean for you?

Data lives in memory, structures are simple and efficient, network handling uses I/O multiplexing, and commands run one at a time on one thread so there is no locking overhead. The consequence is that each command is atomic (good for counters and locks), but one slow command (KEYS, a huge SMEMBERS, deleting a giant key) blocks every other client. So you avoid O(N) commands on big data, use SCAN, and use UNLINK for large deletes.

6. Redis Sentinel vs Redis Cluster?

Sentinel monitors a leader and its replicas and promotes a replica on failure; the whole dataset still lives on one leader, so it solves availability but not capacity. Cluster shards data over many leaders using 16384 hash slots, each with replicas, so it scales memory and throughput and also fails over. In Cluster, multi-key commands only work when keys are in the same slot (use hash tags like {user42}). I choose Sentinel for a small dataset that fits one node and Cluster when data or throughput exceed one node.

7. What does a CDN cache, and how do you invalidate it?

It caches static files (images, JS, CSS, video segments) and sometimes API responses at edge locations near users, keyed by URL plus selected headers. Invalidation options: versioned or content-hashed URLs (best; the new file has a new URL, nothing to purge), TTLs through Cache-Control, and purge APIs for emergencies (slow to propagate and costly in volume). I design static assets so they never need purging.

B. Design scenarios

8. Design the caching for a product page with 100,000 reads/s and rare updates.

Put static assets on a CDN with content-hashed URLs and long max-age. For the product JSON use cache-aside in Redis keyed by product id and version, TTL a few minutes with jitter. On an update the service writes the DB and deletes the key (or publishes an event that invalidates). Add a small local in-process cache (a few seconds) for the very hottest products, and request coalescing so a miss on a popular product triggers one DB load. Size: hot set times item size times overhead, replicated across two nodes. Metrics: hit ratio, p99 latency, DB QPS. State the staleness bound (for example seconds to minutes for descriptions; the price shown at checkout is re-read from the DB).

9. How would you cache user-specific data such as a feed or profile?

Include the user id in the key (feed:user42:page1) so users never see each other's data. Store compact precomputed structures (a sorted set of post ids) and hydrate details from a second cache of items by id. TTL or size-limit per user to bound memory; evict inactive users. For the user who just posted or edited, apply read-your-writes by updating that user's cached entry on write (or bypassing the cache for a short period). Never mark personalised responses publicly cacheable at the CDN.

10. How do you cache a leaderboard or "top N" that updates constantly?

Use a Redis sorted set: ZADD updates scores in O(log N), ZREVRANGE 0 N-1 returns the top N, ZRANK gives a user's rank. For huge scale shard by leaderboard id or by score range and merge the top results. If exact freshness is not needed, snapshot the top N every second or few seconds and serve the snapshot from a cache or CDN to absorb huge read traffic.

11. How would you implement a rate limiter with Redis?

Fixed window: INCR a key per user and window, set EXPIRE on first increment, reject above the limit (simple, but allows bursts at window edges). Sliding window: keep timestamps in a sorted set, remove older than the window, count. Token bucket: store tokens and last-refill time and update them atomically in a Lua script so concurrent requests cannot race. Handle Redis failure by deciding fail-open or fail-closed based on the risk (login endpoints: fail closed; general API: fail open with a local fallback limiter). Details in Chapter 16 and the rate-limiter case study.

12. How would you design a distributed cache from scratch?

Partition keys across nodes with consistent hashing (or hash slots) so node changes move only about 1/N of the keys. Each node holds an in-memory hash table with an eviction policy and a replica for failover. Clients (or a proxy) route requests by key. Add TTL support, hot-key handling (local copy or key replication), metrics, and a warm-up procedure. Covered in the distributed-cache case study.

C. Failure and real-time (production) scenarios

13. Your cache hit ratio suddenly drops from 95% to 60% and the DB is on fire. What do you do?

Stabilise first: enable load shedding or rate limiting on the expensive endpoints, extend TTLs temporarily, or serve stale. Diagnose: was there a deploy that changed the cache key format or version? A cache node failure or restart (cold cache)? A mass expiry at the same moment (no jitter)? A new traffic pattern, such as a crawler or scan, polluting the cache? A memory shortage causing heavy eviction? Fix: roll back the key change, warm the cache gradually, add TTL jitter, add request coalescing, and add alerts on hit ratio and eviction rate. Prevent: canary deploys that watch hit ratio, and size the DB for a plausible cache outage.

14. A viral item makes one cache key receive 1M requests/s. What now?

A single Redis node handles roughly 100k simple ops/s, so this key overloads its node. Solutions: put a short-TTL local in-process cache in every application instance (absorbs most requests, no network); replicate the key under several names (key#1 to key#N) and have clients pick one at random; push the content to a CDN if it is cacheable; detect hot keys automatically by sampling counters and promote them. Accept a small staleness window on hot keys.

15. The cache and DB disagree for some users. How do you debug and fix it?

First check how the entry got there: was invalidation skipped on some write path (a batch job, an admin tool, another service writing the DB directly)? Was there the read-fill race (stale value written after the delete)? Was the delete lost due to a network error or retry without idempotence? Fix with: all writes through one path or CDC-based invalidation from the DB log, versioned writes (only accept newer versions), leases, a TTL as a backstop, and a reconciliation job comparing samples. For the immediate incident, delete the affected keys.

16. After a deployment all instances restart and the site crawls for 5 minutes. Why?

If the cache is local (in-process), every restart empties it, producing a miss storm on the shared DB. Or a new cache key version made every old entry unusable. Solutions: rolling restarts (a few instances at a time), pre-warm the cache from the hot-key list before taking traffic, use a shared distributed cache so restarts do not lose data, ramp traffic gradually, and keep request coalescing to avoid duplicate loads.

17. The Redis primary fails over and users report missing data. Why?

Redis replication is asynchronous, so writes acknowledged by the old primary but not yet copied to the replica are lost on promotion. For a pure cache that is fine (reload from the DB). For data stored only in Redis (sessions, counters), use AOF with fsync every second, WAIT for replica acknowledgement on important writes, or keep a durable copy in a database. Be explicit in the interview about what is a cache and what is a store.

18. Attackers request random IDs that do not exist and your DB is overloaded. What do you do?

This is cache penetration: every request misses and reaches the DB. Cache the "not found" answer with a short TTL, put a Bloom filter in front containing all valid ids so impossible ids are rejected cheaply, validate the id format, and rate limit by IP and user. Monitor the miss ratio per endpoint to spot it.

19. Thousands of requests hit the DB when one popular key expires. How do you stop it?

That is a cache stampede. Use single-flight: the first request takes a short lock or lease and loads the value while others wait or receive the stale value; add probabilistic early refresh so the key is refreshed shortly before it expires; add jitter to TTLs; or refresh hot keys in the background on a schedule so they never expire under load.

20. The whole cache cluster goes down. Does your system survive?

It should degrade rather than collapse. Requests fall through to the DB, which was sized for the cache hit ratio and may not cope. Protect it with a circuit breaker on the cache client (fail fast, do not wait on timeouts), load shedding of low-priority traffic, rate limits, stale-serving from a local cache, and replicas or multiple zones for the cache itself. Practise it with a game day. The honest answer is to design the DB for a partial cache outage and to treat total outage as a degraded-mode scenario.

D. Trade-off and "why" questions

21. Why delete the cache key on write instead of updating it?

Updating can leave the older value in the cache if two writers race (writer A computes v1, writer B computes v2 and writes it, then A writes v1 to the cache). Deleting is idempotent and the next read fetches the latest from the DB. Deleting costs one extra miss, but it is simpler and safer. Updating is acceptable when writes are serialised per key (for example one partition owner).

22. Local (in-process) cache vs distributed cache: which one?

A local cache has no network hop (nanoseconds), but each instance has its own copy so copies diverge and total memory is multiplied by the number of instances. A distributed cache is shared (one copy, consistent view, big capacity) but costs a network round trip and is another system to run. Common answer: both. A tiny local cache with a few seconds TTL for hot items in front of a shared Redis, which absorbs hot keys while keeping staleness small.

23. Redis or Memcached?

Memcached is a simple, multi-threaded, in-memory key-value cache for blobs; it is excellent for plain caching at very large scale with little operational complexity. Redis adds data structures, persistence, replication, Lua scripting, pub/sub and streams, which let it serve as more than a cache (rate limiter, leaderboard, queue, lock). If you only need a cache, either works; if you want structures or durability options, choose Redis.

24. What are the risks of write-back caching?

Data loss if the cache fails before flushing, ordering problems between multiple cache nodes, and complex recovery. Mitigate with a durable write-ahead log, replication of the cache, small flush intervals, and using it only for data that tolerates loss (metrics, counters, view counts). Do not use it for payments or orders.

25. How do you keep the cache consistent in a multi-region system?

Perfect consistency across regions is expensive, so state a bound. Options: each region has its own cache fed by the regional DB replica (staleness equals replication lag plus TTL); propagate invalidations through a cross-region event stream; keep a short TTL for mutable data; route a user's reads to their home region to give read-your-writes. For data that must be exact, read from the region that owns it.

26. When is caching the wrong answer?

When the data is written as often as it is read, when every request is unique, when the backend is already fast enough, when the consequences of stale data are severe (balances, stock at checkout), or when the real problem is a missing index or bad query. Fix the query first, because a cache hides a slow query but does not make it cheap on a miss.

27. How do you decide what TTL to set?

Ask the product owner how stale the data can be and what the cost of staleness is; set the TTL at or below that, then use hit ratio and DB load to see whether it is affordable. Add jitter, use a longer TTL for immutable or versioned data, and a very short or zero TTL for sensitive data. Combine with explicit invalidation when freshness matters more than the TTL allows.

28. Walk me through what happens end to end when a user opens a page.

Browser checks its own cache; if missing it resolves DNS and connects to the nearest CDN edge; the edge serves cached static files and forwards dynamic requests to the load balancer and application. The application checks the local cache, then Redis; on a miss it reads the DB, fills Redis, and returns the response, which may be marked cacheable by the CDN if public. Each step is a place to say what is cached, for how long and how it is invalidated.
