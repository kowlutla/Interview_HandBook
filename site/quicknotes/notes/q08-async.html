0. Key definitions (know these cold)

TermDefinition
AsynchronousThe caller hands off the work and moves on. It does not wait for the answer. The opposite is a synchronous call, where the caller waits.
BrokerThe middleman server that holds messages between the sender and the reader (Kafka, RabbitMQ, SQS).
Producer / consumerProducer: the code that sends a message. Consumer: the code that reads and handles it.
QueueA line of messages. Each message goes to one worker and is removed once handled. Good for sharing work.
LogAn append-only list of records that is kept for a while. Readers keep their own bookmark, so many readers can read the same data and can read it again.
Topic / partitionTopic: a named stream of messages. Partition: one ordered slice of a topic. The partition is the unit of order, storage and parallel work.
OffsetThe position number of a record inside one partition (0, 1, 2 ...). A consumer remembers its offset as a bookmark.
Consumer groupA team of consumers that share a topic. Each partition goes to one member of the team. Different teams each get every message.
Consumer lagHow far behind a consumer is: newest offset minus its committed offset. The main health number for async systems.
ISR (in-sync replicas)The copies of a partition that are fully caught up with the leader. A write counts as safe once every ISR member has it.
At-least-onceA message is never lost but may arrive twice. The normal default. Needs idempotent consumers.
IdempotentDoing the same operation twice gives the same result as doing it once. The key tool for living with duplicates.
Dead-letter queue (DLQ)A side queue where messages that keep failing are parked, so they do not block the rest.
BackpressureA signal or limit that slows the sender when the receiver cannot keep up.
OutboxWrite the message into the same database transaction as your data, then a relay publishes it. Fixes "saved to DB but never sent".
Command / eventCommand: "please do this" (one receiver). Event: "this happened" (anyone may listen, the sender does not care who).
Event sourcingStore the list of events as the truth, and compute the current state by replaying them.
CQRSUse one model for writes and a separate, read-friendly model for reads. Updated from events, so reads are slightly behind.
CDC (change data capture)Read a database's own change log and turn each change into an event.
Batch / streamBatch: process a big finished pile of data now and then. Stream: process each record as it arrives, all the time.
Event time / watermarkEvent time: when it happened. Watermark: the engine's guess "I have seen everything older than this time", used to close time windows.
CheckpointA saved snapshot of a stream job's state and read positions, so it can restart without losing work.
Lease / heartbeatLease: a temporary claim on a job that expires. Heartbeat: a "still alive" ping that renews the lease.
Misfire / overlapMisfire: a job was due while the scheduler was down. Overlap: the previous run is still going when the next one is due.
Durable executionA workflow engine that saves each step's result so a long process can survive crashes and carry on where it stopped.

1. Queues, logs and Kafka Ch 34

One line: a broker is durable storage between two services. The sender writes and moves on. The reader catches up at its own speed. We pay with extra delay, duplicates and harder debugging.

Why go async (name all five)

  • Decoupling in time: the reader can be down or being deployed. Messages wait.
  • Decoupling in knowledge: the sender does not know who reads. Add a new reader later with no change to the sender.
  • Load leveling: a spike is soaked into the backlog and drained slowly. Example: 50,000 orders/s for two minutes while fulfilment does 5,000/s. The queue absorbs it and drains in about 20 minutes. No need to build for the peak.
  • Fan-out: one event, many independent reactions (email, search index, analytics).
  • Failure isolation and retry: a slow or broken downstream does not break the user request. Failed work is retried later.

Three models: queue, log, publish/subscribe

Classic queue (RabbitMQ, SQS)Log (Kafka, Kinesis)Pub/sub topic (SNS, Google Pub/Sub)
Message after it is readRemoved after ackStays until retention endsDelivered to each subscriber
Who tracks progressBroker, per messageConsumer group, one number per partitionBroker, per subscription

RabbitMQ

  • Producers send to an exchange, which routes by binding rules (direct, topic, fanout) into queues.
  • Rich routing, per-message ack, priorities, TTL.
  • Throughput in tens of thousands per second per node, not millions.

Amazon SQS

  • Fully managed queue. Standard: huge throughput, at-least-once, best-effort order. FIFO: order per message group id plus dedup.
  • Message up to 256 KB. Retention 1 minute to 14 days (default 4). Delay up to 15 minutes.
  • No replay. Use SNS plus SQS for durable fan-out.

Kafka

  • Distributed, replicated, partitioned commit log.
  • Millions of messages per second across a cluster. Replay by moving offsets.
  • Cost: more to operate, ordering only per partition, consumer count capped by partitions.

Kafka in one minute

  • A topic has N partitions. Each partition is an ordered append-only file split into segments (default 1 GB). Old data is removed by deleting whole segment files, which is cheap.
  • Fast because: sequential disk writes, the OS page cache does the caching, and zero-copy sends from the file to the network.
  • Keys: same key means same partition (hash of key mod partition count), so same key stays in order. Pick the entity whose events must stay ordered (orderId, accountId). Keys must be spread evenly or you get a hot partition.
  • Producer batching: records collect into batches (batch.size, linger.ms) and can be compressed. A little linger gives much more throughput.
  • Replication: each partition has a leader and followers (typically replication factor 3). Followers pull from the leader. The leader moves the high watermark forward when all ISR members have the record. Consumers only see records below it.

Consumers, offsets, rebalances

  • Consumers pull. A group divides partitions among members. Max useful consumers in a group equals the partition count.
  • Progress is stored in the internal topic __consumer_offsets. After a crash the new owner resumes from the last committed offset.
  • Rebalance: when members join, leave or crash, partitions are reassigned. Work pauses for a moment, and some messages may be handled twice. Frequent rebalances (slow handlers that miss the poll deadline, rolling deploys) cause lag spikes. Fixes: static membership, cooperative rebalancing, shorter processing per poll, tune max.poll.interval.ms.
  • Exactly-once in Kafka means: idempotent producer plus transactions that write output records and offsets together, for Kafka-to-Kafka flows. To any outside system you still need an idempotent write.
  • Retention: delete by time or size (default about 7 days), or compaction: keep only the latest record per key (good for "current state" topics, such as a changelog).
  • Controller: one broker manages leader elections and metadata. Newer Kafka uses KRaft (its own Raft quorum) instead of ZooKeeper.
Numbers and sizing: a good rule is about 10 MB/s of writes per partition to plan from (measure for your hardware). Partitions = max(target throughput / per-partition throughput, number of consumers you need). Storage = bytes/s x retention seconds x replication factor. Example: 100 MB/s ingress, 7 days, factor 3 gives 100 x 604,800 x 3 = about 181 TB. Check you can survive losing one broker: spare disk and network for its share. Drain time for a backlog = backlog / (consumer rate minus arrival rate); if the difference is small it takes forever, so add consumers.
PickWhenDo not pick when
KafkaHigh volume event streams, many independent readers, replay, stream processingTiny team with simple task queue needs; need per-message delay or priority
RabbitMQComplex routing, per-message ack, priority, delay, moderate volumeMillions per second, long retention and replay

Pulsar / KinesisPulsar: log plus queue semantics, separate storage from brokers. Kinesis: managed log on AWS.Need the biggest ecosystem (Kafka wins)
Traps: (1) "Kafka guarantees exactly-once" with no context. It is true only inside Kafka with transactions. (2) Choosing a key with a few hot values, so one partition melts. (3) Raising partitions later: the hash changes and old keys may move, which breaks per-key order across the change. Plan the count up front. (4) Using a queue where a plain function call is simpler. Not everything needs a broker: if the caller needs the answer now, call directly.
Say: "I put a log between the services so the producer is never blocked by the consumer. I key by orderId for per-order order, use replication factor 3 with min in-sync 2 and acks=all, and treat delivery as at-least-once with idempotent consumers. I watch consumer lag as the main health signal."

2. Messaging patterns Ch 35

One line: the broker is only the pipe. Correctness comes from the patterns around it: retries, dead-letter queues, idempotent handlers, ordering by key, the outbox, and watching lag.

Point-to-point, fan-out, competing consumers

  • Point-to-point: each message handled by exactly one worker. Use for jobs.
  • Publish/subscribe: each subscriber gets its own copy. Use for events.
  • Competing consumers: many workers on one queue share the load. Scale by adding workers (up to partitions in Kafka).
  • Durable fan-out on AWS: SNS topic to one SQS queue per subscriber. Each subscriber has its own buffer and retries, so a slow one does not hurt the rest.
  • Fan-out on write vs read: copy to every follower's feed when posting (fast reads, heavy writes for celebrities) or gather at read time (cheap writes, slow reads). Large systems mix both.

Ordering

NeedHowCost
No order neededAny number of parallel workersNone. Prefer this when you can.
Order per entity (usual)Partition or message group by key (orderId)One worker per key at a time, hot keys limit speed
Global orderOne partition or one writerNo parallelism. Rarely truly needed.
Order lost anyway (retries, many workers)Sequence numbers in the message, consumer buffers or drops stale onesExtra state at the consumer

Retries, DLQ and poison messages

  • Retry with exponential backoff and jitter (wait 1s, 2s, 4s ... plus random). Without jitter, all failing messages retry together and hammer the broken service again.
  • Retry topics or tiers: failed message goes to a "retry-1m" topic, then "retry-10m", then the DLQ. This keeps the main stream moving (no head-of-line blocking).
  • Bound retries: a retry budget and a max attempts count. Infinite retry of a bad message is a poison message that loops forever.
  • DLQ: keep the original message plus error, attempt count and timestamps. Alert on DLQ depth. Build a redrive tool to push messages back after the bug is fixed.

Idempotent consumers (the answer to "but duplicates?")

  • Give each message a unique id. Before doing the work, record the id in a table with a unique key (an inbox), in the same transaction as the work. A repeat hits the unique key and is skipped.
  • Or make the action naturally safe: "set status = shipped" is safe to repeat; "add 10 to balance" is not.
  • For outside side effects (send email, charge card) pass an idempotency key to the outside system, or record "sent" first.

Numbers: watch these: consumer lag (messages and also seconds-behind), DLQ depth, oldest message age, processing time per message, redelivery rate, rebalance count. Alert on "oldest message age" more than raw lag: it ties to user delay.
Traps: (1) Retry that never stops, which blocks the partition behind one poison message. (2) Committing the offset before the work is done: a crash loses the message. (3) Dual write: "save to DB, then publish" with no outbox loses the event if the process dies in between. (4) Assuming a queue gives order when you have 10 workers. (5) Adding more consumers than partitions.
Say: "My default is at-least-once delivery, with idempotent handlers keyed by message id, bounded retries with backoff and jitter, a dead-letter queue with redrive, and an outbox so database change and publish never drift apart."

3. Event-driven design Ch 36

One line: services announce facts ("OrderPlaced") instead of calling each other, so they stay loosely tied. The price is eventual consistency and harder tracing.

Command, event, query

KindMeaningExampleReceivers
CommandPlease do this. Can be refused.ChargeCardOne
EventThis happened. Past tense. Cannot be refused.PaymentCapturedZero to many
QueryTell me the answer.GetOrderOne, caller waits

Three things people call "event-driven"

StyleWhat the event holdsGoodBad
Event notificationJust "something changed, id 42"Tiny, simpleReceivers call back to get data, so coupling returns
Event-carried state transferThe data needed, so receivers keep a local copyNo callbacks, reads stay local and fastBigger events, copies can lag, schema changes are felt everywhere
Event sourcingThe events are the only source of truthFull history, audit, rebuild any view, time travelHard to learn, replay time, schema evolution, delete requests (GDPR)

Choreography vs orchestration

  • Choreography: each service reacts to events and emits more. No boss. Loose, but the whole flow is hard to see and debug.
  • Orchestration: one coordinator tells each step what to do. Easy to follow and to add timeouts and undo. The coordinator is a central piece to keep healthy.
  • Rule of thumb: choreography for simple 2 to 3 step fan-out; orchestration for long business flows with undo.

A good event

  • Named in past tense as a business fact (OrderShipped, not OrderUpdated).
  • Has a unique event id (for dedup), an ordering key (entity id), a type and schema version, two times (when it happened and when it was published), and a trace id.
  • Evolve safely: add optional fields, never rename or remove; use a schema registry with compatibility checks.

CQRS and event sourcing

CQRS

  • Writes go to a model built for rules and correctness. Reads come from a view built for the screen (search index, denormalised table).
  • The read side is updated from events, so it lags slightly: eventual consistency.
  • Worth it when reads and writes have very different shape or load. Overkill for simple CRUD.

Event sourcing

  • Event store is append-only, per aggregate (for example one bank account) with a version number.
  • Optimistic concurrency: a write says "I expect version 7". If it is already 8, reject and retry.
  • Snapshots every N events avoid replaying all history. Projections build read views.

CDC and the outbox via CDC

  • Log-based CDC (Debezium style) reads the database's write-ahead log and emits one event per change. It catches every write path, has low load, and keeps order per row. First it takes a snapshot, then follows the log.
  • Better than polling "updated_at" columns (misses deletes, adds load) and better than triggers (add cost to every write).
  • Outbox plus CDC: the service writes data and an outbox row in one transaction. CDC publishes the outbox rows. Safe and no dual write.
  • Materialized views: keep search, cache and warehouse in step by consuming the stream. Make updates idempotent and keyed so late or repeated events do not break things.
If you needUse
Tell others something happened, they fetch detailsEvent notification
Others keep local data without calling youEvent-carried state transfer

Publish after a DB change safelyOutbox (plus CDC or a poller)

Traps: (1) Event soup: hundreds of events, nobody knows who depends on whom. Fix with ownership, a catalog and tracing. (2) Events as remote calls: publish "DoThis" and wait for "Done": that is a slow, fragile RPC. (3) Huge events with all the data. (4) Event sourcing for everything. Use it only where history really matters. (5) Forgetting the user: after a write the screen may not show it yet. Show "pending", return the new value in the response, or read your own writes.
Say: "Services publish facts, not commands. I use an outbox so the fact and the data commit together, carry enough state that consumers do not call back, and design the UI for eventual consistency. I use orchestration for long flows with undo, and choreography for simple fan-out."

4. Batch and stream processing Ch 37

One line: batch handles a big finished pile of data on a schedule (cheap, high throughput, slow to answer). Stream handles each event as it arrives (fast answers, harder state and time rules). Micro-batch sits in between.
BatchMicro-batchStream
LatencyMinutes to hoursSecondsMilliseconds to seconds
EngineMapReduce, SparkSpark Structured StreamingFlink, Kafka Streams
Good forDaily reports, big re-computes, ML training dataNear-real-time dashboardsFraud, alerts, live counters
ComplexityLowestMediumHighest (state, time, failure)

MapReduce and Spark in short

  • MapReduce: map (each record to key and value), shuffle (group by key across machines), reduce (combine each group). Fault tolerant by re-running failed tasks. Slow because every stage writes to disk. Speculative execution re-runs slow "straggler" tasks.
  • Spark: keeps data in memory, builds a plan (DAG) lazily, and runs it when you ask for a result. Narrow steps (map, filter) stay on one machine. Wide steps (group, join) need a shuffle: data moves across the network and is the most costly part.
  • Data skew: one key with far more data makes one task run forever. Fix: salt the key (add a random suffix, aggregate twice), broadcast the small side of a join, or split the hot key.
  • Recovery: Spark recomputes lost partitions from the plan (lineage). Cache data you reuse.

Stream processing: state, time, windows

  • Stateless steps (filter, map) are easy. Stateful steps (count per user, joins) keep state per key, in a state backend (memory or RocksDB on disk), and need checkpoints.
  • Checkpoint: Flink inserts barrier markers into the stream. When every operator has seen the barrier it saves its state plus the input offsets. After a crash, restore the last checkpoint and replay from those offsets. That gives exactly-once state.
  • Event time vs processing time: event time is when it happened on the device. Processing time is when we see it. Mobile events arrive late and out of order, so use event time.
  • Windows: tumbling (fixed, no overlap, for example each minute), sliding (overlap), session (gap of silence closes it).
  • Watermark: "no more events older than T are expected". When it passes the window end, the window fires. Allowed lateness keeps the window open a bit longer and updates the result; later events go to a side output.

Joins, top-K, backpressure, sinks

  • Stream-stream join: match two streams within a time window; both sides are buffered as state. Stream-table join: enrich each event from a (cached or changelog) table. Broadcast a small table to every worker.
  • Top-K: keep partial counts per partition, then merge. Count-min sketch and heaps for very large key spaces (approximate).
  • Backpressure: when a stage is slow the upstream stages slow down automatically (Flink) or the broker buffers (Kafka). Watch it: it means a slow sink or a skewed key.
  • Exactly-once at a sink: either an idempotent write (upsert by key) or a transactional two-phase commit sink. Idempotent upsert is simpler and the usual choice.
  • Key skew in streams: one hot key overloads one task. Pre-aggregate locally, or add a salt, then merge.

Lambda vs Kappa, ETL vs ELT

StyleMeaningProCon

KappaOne stream path. To recompute, replay the log through a new version of the job.One code baseNeeds a long-retention log and a good engine

Worked example (clicks per minute): 100,000 events/s, 200 bytes each is about 20 MB/s, about 1.7 TB per day. Kafka with partitions by user id, Flink job with 1-minute tumbling event-time windows, 1-minute watermark delay, checkpoint every 30 to 60 seconds, results upserted into a store by (window, page) key. After a crash it restores the last checkpoint and replays a minute or so of input; the upsert makes the replay harmless. Size the partitions and Flink parallelism so each task handles well under its limit, with headroom for a backlog catch-up.
Traps: (1) Using processing time for business counts, which gives wrong numbers whenever there is lag. (2) A watermark that is too tight (drops late data) or too loose (slow results). (3) Unbounded state: keep a TTL on state, or it grows until the job dies. (4) Ignoring skew. (5) Saying "exactly-once" without saying where the sink is idempotent. (6) Choosing stream when a nightly batch would do.
Say: "If the business can wait an hour, I use batch, because it is simpler and cheaper. If we need seconds, I use event-time streaming with watermarks, checkpointed state, and idempotent upserts into the sink so a replay is harmless. I handle backfills by replaying the log."

5. Scheduling and workflows Ch 38

One line: a scheduler runs work at the right time, once in effect, even when machines crash. Hard parts: finding due work fast, never having two owners, and handling retries, overlaps and missed runs.

Why one cron is not enough

  • One machine is a single point of failure: if it dies, no jobs run.
  • Two machines both running cron fire every job twice.
  • No history, no retries, no visibility, and it cannot scale to millions of jobs.

Parts of a distributed scheduler

  • Job store: the definition (what, when, owner) and each run (state, attempt, lease). A database, sharded by job id or tenant.
  • Due-time index: a way to find "what is due now" without scanning everything. An indexed next_run_time column, or a time-bucketed structure.
  • Dispatcher: moves due jobs into a work queue.
  • Workers: pull from the queue, run, report status, and renew a lease.
  • Recurring jobs: turn a cron rule into "occurrences": compute the next time and store one row; after it runs, compute the next.

Execution rules

  • At-least-once run, exactly-once effect: a worker can crash after doing the work but before reporting. The job will run again, so jobs must be idempotent (use the run id as an idempotency key).
  • Lease and heartbeat: a worker claims a job for, say, 30 seconds and renews it. No renew means the worker is presumed dead, and the job is handed out again. A zombie worker that comes back must be fenced (fencing token or version check on the result write).
  • Misfire policy (scheduler was down when job was due): run now once, skip, or run all missed ones. Choose per job (a daily report: run once; a billing tick: maybe catch up).
  • Overlap policy (previous run still going): skip, queue, or allow in parallel.
  • Retries: exponential backoff with jitter, a max attempts and a retry budget, then DLQ.
  • Fairness: per-tenant quotas and rate limits, plus priority queues, so one big tenant cannot starve others.

Workflow engines and durable execution

  • Orchestrator (Airflow, Step Functions, Temporal) runs multi-step flows: order of steps, branches, timers, human approvals.
  • Durable execution (Temporal style): the engine saves an event history of every step. If the worker dies, another worker replays the workflow code against the history and continues. So workflow code must be deterministic (no random, no wall clock, no direct network calls). Side effects live in activities with their own retries and timeouts. Timers and signals (outside events) are first class. Changing workflow code needs versioning for flows in flight.
  • Airflow: scheduled DAG batches, best for data pipelines. Step Functions: managed state machine on AWS. Temporal: code-first long-running business flows.
  • Sagas as workflows: a series of steps each with an undo (compensation). Orchestration makes the status obvious.
Scale example (reminder service): 100 million reminders per day is about 1,150 per second on average, with peaks perhaps 10 times that. Each job row is about 200 bytes, so a month of pending reminders is a few hundred GB: shard the store by job id. Dispatchers poll the next minute's bucket and push to a queue; workers send. A timing wheel or sorted set gives fast near-term lookups, the database stays the truth.
Traps: (1) Two schedulers both firing: need a lease or a claim. (2) Jobs that are not idempotent plus at-least-once equals double charges. (3) A long job with no heartbeat gets stolen mid-run. (4) Everything scheduled at 00:00: a thundering herd; spread with jitter. (5) Ignoring time zones and daylight saving for cron rules; store the zone and compute occurrences with it. (6) Non-deterministic workflow code that breaks on replay.
Say: "I keep jobs in a sharded store with an index on next run time. Dispatchers own shards and push due jobs to a queue. Workers take leases and heartbeat. Jobs are idempotent because execution is at-least-once. I define misfire and overlap policy per job, and put retries, backoff and a DLQ around it. For multi-step business flows I use a workflow engine with durable execution."

6. Say-aloud script (about 60 seconds)

Say: "For anything slow, spiky or fan-out, I take it off the request path and put a durable log or queue in between. That gives the producer isolation from consumer speed, lets me absorb spikes, and lets new consumers join without changing the producer. In Kafka I key by the entity whose order matters, use replication factor 3, min in-sync replicas 2 and acks=all, and I know that parallelism is capped by partition count. Delivery is at-least-once, so every consumer is idempotent, usually with an inbox table keyed by message id. Failures go through bounded retries with backoff and jitter, then a dead-letter queue with a redrive tool. To publish an event and change the database safely I use an outbox, often read by CDC. I design for eventual consistency in the UI, and I watch consumer lag and oldest message age. For heavy analytics I choose batch unless seconds matter; if they do, event-time stream processing with watermarks, checkpoints and idempotent sinks. For timed work I use a sharded job store with a due-time index, leases and heartbeats, explicit misfire and overlap rules, and a workflow engine for long multi-step flows."

7. Interview Q&A (30)

A. Concepts

1. Why would you put a queue or log between two services?

I use a broker when the sender should not wait for the receiver. It gives me five things. The two services do not have to be up at the same moment. The sender does not need to know who reads. A spike is soaked into a backlog and drained at a safe pace, so I do not size for the peak. One event can feed many readers. And a slow or broken reader does not break the user's request. The cost is extra delay, duplicates, weaker ordering, and a harder time debugging a flow that crosses services. So if the caller needs the answer right now, I keep a direct call.

2. What is the difference between a queue, a log and pub/sub?

In a classic queue each message goes to one worker and is deleted after it is acknowledged, so it is great for sharing tasks. The broker tracks each message. In a log such as Kafka, records stay for a retention period and each reader keeps a bookmark (an offset), so many independent readers can read the same data and can go back and replay. Order is strict inside a partition. In pub/sub, every subscriber gets its own copy of each message. Kafka really combines the log with pub/sub through consumer groups: inside a group the partitions are shared like a queue, and across groups every group gets everything.

3. How does Kafka store data and why is it fast?

A topic is split into partitions, and each partition is an append-only log made of segment files (default 1 GB each). Only the newest segment is written. Kafka is fast because it only appends to the end of files, which disks do very well, because it leans on the operating system page cache instead of its own big cache, and because it can send data from the file to the network with zero-copy. Producers batch and compress records, so one network call carries many. Deleting old data is just deleting old segment files, which costs almost nothing.

4. How do consumer groups and offsets work?

Consumers that share a group id split the topic's partitions: each partition is owned by exactly one member of the group at a time. The group's progress is one number per partition, the offset of the next record to read, stored in an internal topic. If a consumer dies, a rebalance gives its partitions to others, who resume from the last committed offset. Because the commit may be behind the real progress, some records are handled again, so handlers should be idempotent. Different groups are independent. That is how analytics and email can both read the same topic at their own pace.

5. What do at-most-once, at-least-once and exactly-once mean, and which do you pick?

At-most-once means a message may be lost but is never repeated (commit the offset first, then process). At-least-once means never lost but may repeat (process first, then commit). Exactly-once means one effect per message. A network cannot truly give it end to end, so I build it from at-least-once delivery plus an idempotent handler. Kafka offers exactly-once inside Kafka with an idempotent producer and transactions that write output and offsets together. For databases and other outside systems I use upserts or an inbox table. My default is at-least-once with idempotent consumers.

6. What is the difference between a command, an event and a query?

A command asks one receiver to do something and it may refuse, like ChargeCard. An event states a fact that already happened, like PaymentCaptured, and the sender does not care who listens. A query asks for an answer and the caller waits. Mixing them up causes trouble. If I publish an event named DoThis and wait for Done, I have built a slow remote call with extra steps. Events are named in the past tense and describe business facts, so many readers can use them without the sender changing.

7. What is the difference between batch, micro-batch and stream processing?

Batch works on a big finished set of data on a schedule. It is simple, cheap and has very high throughput, but the answer comes minutes or hours later. Stream processing handles each event as it arrives and gives answers in milliseconds to seconds, but it needs state, checkpoints and rules about time and late data. Micro-batch chops the stream into tiny batches, such as one second, which is easier to run but has delay of about a batch. I choose by how fresh the answer must be to the business. If an hour is fine, I choose batch.

8. Explain event time, windows and watermarks.

Event time is when the thing really happened, for example when a user tapped on a phone. Processing time is when our job sees it. They differ because of network delay and offline phones, so counts by processing time are wrong when there is lag. We group events into windows by event time: tumbling (fixed, no overlap), sliding (overlapping) or session (closed after a gap). A watermark is the engine's estimate that no more events older than time T will come. When it passes the end of a window, the window fires. Allowed lateness keeps a window open a little longer, and very late events go to a side output. A tight watermark is fast but drops data. A loose one is accurate but slow.

B. Design scenarios

9. Design the order flow for a flash sale of 50,000 orders per second when fulfilment handles 5,000 per second.

I accept the order quickly: validate, write it with an outbox row in one transaction (or straight into a durable log), and reply "received". A queue or Kafka topic keyed by orderId sits in front of fulfilment. The backlog from a two-minute spike is about 45,000 x 120 = 5.4 million messages. Draining at the spare capacity takes long, so I add consumers (and enough partitions) to raise the rate and tell users the order is pending. Consumers are idempotent by order id. Failures go to retry tiers then a DLQ. I watch lag and oldest message age, and I set a limit on admission or a stock reservation so I do not accept more than I can ever fulfil.

10. How do you make sure a message is published if and only if the database change commits?

This is the dual write problem. If I save to the database and then publish, a crash between the two loses the event. If I publish first, I might announce something that never committed. The fix is the transactional outbox. In one database transaction I write the business row and an outbox row. A separate relay, either a poller or a CDC tool reading the database log, publishes outbox rows and marks them done. Delivery is at-least-once, so consumers dedupe by event id. The cost is a little extra delay and one more table, but the data and the event can never disagree.

11. How would you keep a search index in sync with the primary database?

I use CDC. A connector reads the database's write-ahead log and writes one event per row change into Kafka keyed by primary key. An indexer consumes it and upserts into the search index, with the row version so older events cannot overwrite newer ones. It also handles deletes. Because the key is the row id, changes to one row stay in order. For first load, I take a snapshot then switch to the log. I monitor lag between database and index, and I keep a way to rebuild the whole index by replaying or re-snapshotting. Polling an updated_at column is worse because it misses deletes and loads the database.

12. Design a delayed or scheduled job system (for example reminders).

I store each job with its next run time in a store sharded by job id, with an index on the run time. Dispatchers each own some shards, query the next minute of due jobs, and push them into a queue. Workers take a lease, run the job, and write the result. Recurring jobs turn a cron rule into the next occurrence after each run. Because a worker can crash after doing the work, execution is at-least-once and the job uses its run id as an idempotency key. I add retries with backoff and jitter, a DLQ, and per-tenant quotas. For near-term lookups I may use a Redis sorted set or timing wheel, but the database is the source of truth.

13. How would you design a pipeline that counts clicks per minute for a dashboard?

Clients send click events to an ingestion service that writes to Kafka, keyed by user or page. A Flink (or Spark streaming) job reads the topic and uses one-minute tumbling windows on event time with a watermark of about a minute for late arrivals. State is checkpointed every 30 to 60 seconds to durable storage with the Kafka offsets. Results are upserted into a serving store keyed by page and window start, so a replay after a crash writes the same values again. A nightly batch job over the raw events in the lake can correct the numbers if exactness matters, which is the lambda idea. Hot pages are salted to avoid skew.

14. How do you pick the partition count and the key for a Kafka topic?

The key is the entity whose events must stay in order, such as orderId or accountId, and it must have many values spread evenly, or one partition gets all the traffic. For the count I take the larger of two numbers: target throughput divided by what one partition handles (plan from about 10 MB/s and measure), and the maximum number of consumers I want in parallel. Then I add headroom, because raising the count later changes where keys go and breaks per-key order across the change. Too many partitions cost memory, file handles, longer failovers and slower rebalances, so I do not go wild.

15. How would you orchestrate a multi-step process such as order, payment, shipping, with undo?

I use a saga: each step is a local transaction with a compensating action (refund, release stock). For three or more steps and any timeouts or undo, I prefer orchestration with a workflow engine, since the flow is written in one place and I can see the status of each order. In a durable engine like Temporal each step is an activity with retries and timeouts, the history is saved, and a crashed worker is replaced and resumes by replaying. Choreography (each service reacts to events) is fine for a simple fan-out, but it is hard to see and debug for long flows. All activities must be idempotent.

C. Failures and production scenarios

16. Consumer lag keeps growing. What do you do?

First find out whether it is a rate problem or a stuck problem. If arrival is higher than processing, check if all partitions are growing or just one. One partition means a hot key or a poison message looping on retry. All partitions mean the consumers are too slow: look at processing time per message, a slow downstream or database, GC pauses, or constant rebalances. Short-term fixes: add consumers (only up to the partition count), scale the downstream, or shed low-value work. Long-term: add partitions, batch the downstream writes, make handlers faster, and alert on oldest message age rather than only on lag. If it was a bad deploy, roll back first.

17. One poison message keeps failing and blocks the partition. What now?

A message that can never succeed (bad data, a code bug) will block a partition if the consumer retries it forever, since order must be kept. I limit attempts. After a few tries with backoff I move the message to a DLQ together with the error, attempt count and original metadata, commit the offset, and continue. An alert fires on DLQ depth. After the bug is fixed or the data cleaned, a redrive tool sends the messages back to the main topic. If order matters strictly for that key, I may pause only that key instead of the whole stream.

18. A broker dies. What happens to your Kafka topic, and how do you avoid data loss?

For every partition led by that broker, the controller elects a new leader from the in-sync replicas. Producers and consumers refresh metadata and continue; there is a short pause. With replication factor 3, min.insync.replicas of 2 and acks=all, every acknowledged write is on at least two brokers, so none is lost, and writes still succeed with one broker down. With unclean leader election off, we never promote an out-of-date copy. If two brokers die, the ISR falls below the minimum and writes are refused: we choose consistency over availability. I also watch under-replicated partition counts.

19. After a deploy you see many duplicate emails. How do you find and fix it?

Likely causes: a rebalance during the rolling deploy made another consumer re-handle messages that were not committed yet; a producer retry without idempotence; an offset committed after a long handler that exceeded the poll deadline; or a retry after a timeout where the first attempt actually succeeded. I check logs by message id, rebalance counts and the commit times. The real fix is making the handler idempotent: an inbox table with a unique message id written in the same transaction as the send record, or an idempotency key to the email provider. Then use static membership or cooperative rebalancing to calm deploys.

20. Your CDC pipeline falls behind or the connector breaks. How do you recover?

First, how far behind is it, and is the database log still available? Databases keep the log only for a limited time, so a long outage can lose the starting point. If the position is still there, the connector resumes from its stored offset and catches up. If the log is gone, I must take a new snapshot of the tables, then continue from the log, and downstream consumers must handle repeated rows because they are idempotent upserts keyed by primary key. To prevent this I alert on connector lag and on replication slot size, keep enough log retention, and test a rebuild.

21. A stream job crashed and restarted. Are results wrong?

If checkpoints work, no. The job restores its state and the input offsets from the last completed checkpoint and replays input from there. State is then exactly as if there was no crash. The risk is the sink: records written between the checkpoint and the crash will be written again. If the sink uses idempotent upserts keyed by window and key, the replay writes the same values. If the sink is append-only, I get duplicates, so I would use a transactional sink that commits with the checkpoint. I also check that recovery time and checkpoint size are acceptable.

22. The scheduler was down for an hour. What runs when it comes back?

That is the misfire policy, and it must be chosen per job. A daily report should run once now, not 24 times. A "cleanup" job can skip. A billing job might need to run each missed occurrence in order. I store the run time that was due, not just "now", so a job knows which occurrence it is processing. After recovery I also spread the catch-up, with limits on how many run at once, so the backlog does not crush the workers or downstream systems. Alerts on "oldest overdue job" help me notice the problem quickly.

23. A job runs twice, or two workers run the same job at the same time. Why, and what do you do?

Common causes: a worker did the work but crashed before reporting; the lease expired during a long job with no heartbeat, so another worker took it, and the first one is now a zombie; or two schedulers both fired. I fix it in layers. Use a claim with a conditional update or SKIP LOCKED so only one worker gets a job. Use a lease with heartbeats and a fencing token so a zombie's late write is rejected. And make the job idempotent with the run id as a key, since at-least-once is unavoidable. Then the effect happens once even if the run happens twice.

24. Hot partition: one Kafka partition is far busier than the others. What do you do?

The usual cause is a skewed key, such as one huge tenant or a "null" key mapped to a single place. First confirm with per-partition metrics. Options: pick a better key with more spread; add a salt for the hot key (key plus random 0 to N) and merge downstream if order for that key is not needed; give the hot tenant its own topic; or split work after the consumer reads (hand off to a worker pool, keeping order per sub-key). Adding partitions alone does not fix one hot key because that key still hashes to one partition.

25. Messages arrive out of order and the data is wrong. How do you fix it?

First, ask if order really matters for that data. If it does, I check that all events for one entity share a key so they go to one partition, and that the consumer does not process one key with several threads without care. Retries and DLQ redrive also reorder events. For protection I put a version or sequence number in each event. The consumer applies an event only if its version is newer than what is stored (upsert where version less than new), or buffers and resequences. For state updates, "last write by version wins" removes most order problems.

D. Trade-offs and why-questions

26. Why Kafka instead of RabbitMQ or SQS?

I pick Kafka for very high volume, many independent consumers, replay, and stream processing. The log keeps data, so a new service can read history and a bug fix can reprocess from an old offset. I pick RabbitMQ when I need rich routing, per-message ack, priorities or delays at moderate volume. I pick SQS when I want a simple managed task queue and no servers to run, with SNS in front for fan-out. Kafka costs more to run, orders only within a partition, and caps consumers by partition count, so for a small task queue it is overkill.

27. Choreography or orchestration, and why?

Choreography has no central controller: services react to events. It is very loosely coupled and good for simple fan-out, but the full flow lives nowhere, so it is hard to see, test and add timeouts to, and cyclic event chains can appear. Orchestration has a coordinator that calls each step and tracks state. The flow is readable, undo and timeouts are easy, and status is one query. The cost is a central component and some coupling to the steps. For short, simple reactions I choose choreography. For business flows with several steps, money, undo or human approval, I choose orchestration.

28. Why not just use Kafka as the database, or event sourcing everywhere?

Event sourcing is powerful where history is the product: audit, finance, undo, rebuilding views. But it brings costs: you must replay or snapshot to read state, queries need projections, old events must be upgraded when the schema changes (upcasting), and deleting personal data conflicts with an immutable log (a common fix is encrypting per-user data and throwing away the key). Most CRUD systems get little from it. Kafka can keep data for a long time, and compacted topics hold the latest value per key, but it is not good at ad-hoc queries or transactions across keys. I use it as the pipe and the history, and keep a normal database for serving reads.

29. Batch or stream: when is real time not worth it, and what are Lambda and Kappa?

Real time costs more in engineering and running effort: state, checkpoints, late data, on-call. If decisions are made daily, a batch job is cheaper and easier to fix and rerun. Stream is worth it for fraud checks, alerts, live counters and anything where the value fades in seconds. Lambda runs both a batch path and a speed path and merges them, which gives exact results eventually but needs two code bases that must agree. Kappa uses only the stream path and recomputes by replaying the log through a new version of the job, which is simpler if the log is retained long enough and the engine is strong. Most teams today lean to Kappa or to one engine (like Spark or Flink) that does both.

30. Polling the database, a leader, or sharded dispatchers: how do you choose a scheduler design?

For modest scale (a few thousand jobs per second), every instance polling with SKIP LOCKED on an indexed due-time column is the simplest: no leader, no election, durable. When one database becomes the limit, I shard the jobs by id and give each dispatcher a set of shards, with failover by lease. A single leader is simple to reason about but is a throughput ceiling and has a failover gap. For huge counts of short timers, an in-memory timing wheel or sorted set speeds near-term lookups, backed by a durable store. For multi-step flows with long waits I use a workflow engine instead of building it by hand. The trade is always simplicity against scale and failover speed.
