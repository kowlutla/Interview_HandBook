0. Key definitions (know these cold)

TermDefinition in simple words
Partial failureSome machines or links break while others keep working. On one computer it either works or crashes. In a cluster, "half broken" is normal.
Network partitionThe network splits the machines into groups that cannot talk to each other, though every machine is still running.
Timeout"I waited this long with no answer, so I will assume something is wrong." It cannot tell a dead machine from a slow one.
Failure detectorA small part of the system that guesses who is dead, usually from missing heartbeats (regular "I am alive" messages). It is a guess, never a fact.
Clock skew / driftSkew: two clocks show different times right now. Drift: a clock slowly runs fast or slow. Both are normal, even with NTP (the protocol that syncs clocks over the network).
Wall clock vs monotonic clockWall clock is the date and time of day and can jump backwards when corrected. Monotonic clock only moves forward and is good for measuring how long something took.
Happens-beforeEvent A happened before B if they are on the same machine in that order, or A sent a message that B received (or a chain of those). Otherwise they are concurrent.
Lamport clockA single counter per machine that goes up on every event and jumps ahead when a message with a bigger number arrives. Gives an order that respects cause and effect.
Vector clockOne counter per machine, kept as a list. Comparing two lists tells you "A before B", "B before A", or "concurrent" (a real conflict).
Consistency modelThe promise about what a read can return after writes: strong (always the latest), or weaker (maybe old for a while).
LinearizableThe strongest promise: the system behaves as if there is one copy and every operation takes effect at one instant between its start and end.
Eventual consistencyIf writes stop, all copies will agree after some time. In between, reads may be old.
CAP / PACELCCAP: during a partition you pick consistency or availability. PACELC adds: even with no partition you trade latency against consistency.
Quorum (W + R > N)N copies; a write must reach W of them and a read asks R of them. If W + R > N, the read set always overlaps the write set, so it sees the latest write.
ConsensusGetting several machines to agree on one value (for example "who is the leader") even if some crash. Paxos and Raft do this.
Leader, term, logRaft: one leader handles writes; a term is a numbered period with at most one leader; the log is the ordered list of commands every machine applies.
Split brainTwo machines both believe they are the leader and both accept writes. Causes data corruption.
LeaseA lock or role that expires on its own after a set time unless renewed. Protects against a holder that dies.
Fencing tokenA number that grows with every lock grant. The protected resource rejects any request carrying a smaller number than one it has already seen.
SagaA long business action split into local steps, each with an "undo" (compensating) step to run if a later step fails.
Two-phase commit (2PC)A coordinator asks everyone "can you commit?" (prepare), then tells everyone "commit" or "abort". Atomic but can block.
Outbox patternWrite the business change and the "event to send" in the same local DB transaction; a separate process publishes the event later. Avoids losing messages.
IdempotentDoing the operation twice has the same effect as doing it once. This makes retries safe.
Snowflake IDA 64-bit ID made of timestamp bits, machine bits and a sequence counter. Unique without asking a central server, and roughly sorted by time.
GossipEvery machine regularly tells a few random others what it knows, so news spreads like a rumour to everyone.
Merkle treeA tree of hashes. Two copies compare the top hash; if equal, the data is the same; if not, walk down to find exactly which part differs.

1. Failure, time and ordering Ch 27

One line: in a cluster you cannot tell "dead" from "slow", and you cannot trust clocks, so you design for retries, timeouts and orderings that do not depend on exact time.

Why distributed systems are harder

  • Partial failure: a request may succeed on machine A and be lost on machine B. The caller often does not know which.
  • Unreliable network: messages can be lost, delayed, duplicated or reordered. There is no such thing as "I know it arrived" without an acknowledgement, and the acknowledgement can be lost too.
  • No shared clock, no shared memory: each machine has its own clock and its own memory. They only learn about each other through messages.

Slow versus dead

You send a request and nothing comes back. Maybe the machine crashed. Maybe the request was lost. Maybe the machine is busy with a long garbage-collection pause. Maybe the reply was lost on the way back. From the outside all four look the same. This is the idea behind the two generals problem: two sides can never be completely sure the other got the final message over a lossy link. So we never aim for certainty. We aim for "safe if we guess wrong".

Failure detectors

MethodHowTrade-off
Fixed heartbeat timeoutSend "I am alive" every second; suspect after, say, 3 missed.Simple. Short timeout = false alarms; long timeout = slow to notice real death.
Phi accrual (Cassandra, Akka)Learn the normal gap between heartbeats; output a suspicion level that grows as the gap gets unusual.Adapts to slow networks; the app chooses its own threshold.
Gossip-basedMany peers share what they see; a node is declared down when several agree.Scales, avoids one observer's bad view; slower to agree.
Trap: a suspicion is not a fact. A machine declared dead may still be alive and still writing. This is why locks need leases and fencing tokens (section 4).

Physical clocks and why timestamps lie

  • Drift and skew: ordinary server clocks drift by a few milliseconds a day and can differ by tens of milliseconds even with NTP. Over a bad network or after a VM pause the error can be much larger.
  • NTP corrects clocks over the network, which can make the clock jump backward or forward. Leap seconds add a second and have crashed software that assumed time never repeats.
  • Use the right clock: use the monotonic clock to measure durations and timeouts; use the wall clock only for display or approximate ordering.
  • Four ways a timestamp misleads: (1) two machines disagree, so a later event gets an earlier time; (2) a clock jumps back, so time repeats; (3) two events share the same millisecond; (4) a paused process wakes up believing its old time is current.
  • Last-write-wins (LWW) uses timestamps to pick a winner. With skew it can silently throw away a newer write. Use it only when losing a write is acceptable.
  • Bounded-uncertainty clocks (Google TrueTime, using GPS and atomic clocks) report "the time is between t1 and t2", and the database waits out the uncertainty (a few milliseconds) before committing. That gives strong ordering without a central server, but needs special hardware.

Logical time

If wall clocks cannot be trusted, count events instead of seconds. Lamport clock: every machine keeps a counter. Add 1 for each local event. When sending, attach the counter. When receiving, set your counter to max(yours, received) + 1. Now if A happened before B, then A's number is smaller than B's. The reverse is not true: a smaller number does not prove "before", so a Lamport clock cannot detect concurrency. Vector clock: keep one counter per machine. A is before B if every entry of A is at most the matching entry of B and at least one is smaller. If neither is before the other, the events are concurrent, a real conflict that the app or user must merge (Dynamo-style shopping cart). The cost is a list that grows with the number of machines.

Numbers: same-datacentre round trip about 0.5 ms; cross-region about 50 to 150 ms; typical NTP error about 1 to 50 ms (can be worse); heartbeat every about 1 s, suspect after about 3 to 10 misses; TrueTime uncertainty about 1 to 7 ms.
Say: "I do not trust wall clocks for ordering. I use a log or sequence number for order, vector clocks or version numbers to detect conflicts, and timeouts only as hints that I back with idempotent retries."
Trap: saying "use timestamps to order events across servers". Interviewers want you to say that skew breaks it and name the alternative.

2. CAP, consistency and quorums Ch 28

One line: if the network splits, a replicated system must either refuse some requests (stay consistent) or answer with possibly old data (stay available). When the network is fine, you still trade latency for consistency (PACELC).

CAP in plain words

Three wishes: Consistency (everyone sees the latest write), Availability (every request to a working node gets an answer), Partition tolerance (keeps working when the network splits). Partitions will happen, so "P" is not optional. The real choice is only during a partition: CP (refuse or wait on the minority side, keep correctness) or AP (both sides keep answering, then repair the differences later). When there is no partition you can have both; the cost is then latency (PACELC: if Partition then A or C, Else Latency or Consistency).

ChoiceDuring a partitionExamplesGood for
CPMinority side rejects writes (and maybe reads) until it rejoins.ZooKeeper, etcd, Spanner, HBase, most SQL with sync replicasMoney, inventory, locks, leader election, metadata
APBoth sides accept writes; copies diverge; merge later.Cassandra, DynamoDB (default), Riak, DNSCarts, feeds, likes, sessions, metrics
Trap: "pick two of three". Wrong framing: you cannot give up P. Also CAP "consistency" means linearizable, which is not the same as the C in ACID.

The consistency ladder (strongest to weakest)

ModelWhat you can rely onCost
LinearizableActs like one copy; once a write is seen by anyone, all later reads see it.Coordination on every op; slowest, least available in partitions.
SequentialEveryone sees the same order of operations, but it may lag real time.Slightly cheaper.
CausalIf B was caused by A, everyone sees A before B. Unrelated writes can appear in any order.Needs metadata (vector clocks); stays available.
Read-your-writes / monotonic readsYou see your own writes; you never see time go backwards.Sticky sessions or version tokens; cheap and very useful.
EventualCopies agree if writes stop.Cheapest; app must handle stale reads and conflicts.

Quorums

With N copies, write to W, read from R. If W + R > N, any read touches at least one copy that has the latest write. Example N=3: W=2, R=2 gives strong-ish reads and survives one node down. W=1, R=1 is fastest but may read old data. W=N makes writes fail if any node is down. Sloppy quorums (writing to any available node, then handing back later: "hinted handoff") boost availability but weaken the guarantee. A quorum alone is not full linearizability (clock issues, concurrent writes, failed writes that partly landed), so databases add read repair and versioning.

Numbers: N=3 tolerates 1 failure; N=5 tolerates 2; majority = floor(N/2)+1; typical settings W=2,R=2 (balanced), W=1,R=N (write fast), W=N,R=1 (read fast).
Say: "For this data I pick AP with eventual consistency and read-your-writes for the user who wrote. For payments and inventory I pick CP and accept that the minority side rejects writes during a partition."

3. Consensus: Paxos, Raft, leader election Ch 29

One line: a majority (quorum) of machines votes, so the group agrees on one leader and one ordered log even when a minority crashes or is cut off.
  • Problem: several machines must agree on one value and never disagree later (who is leader, the next log entry, the config). The FLP result says no algorithm can guarantee both safety and finishing in a fully asynchronous network with even one crash; real protocols stay safe always and make progress when the network behaves (timeouts).
  • Majority quorum: any two majorities overlap in at least one machine, so two conflicting decisions can never both get a majority. 2f+1 machines tolerate f failures.
  • Paxos: the classic, hard to teach; proposers, acceptors, two phases (prepare/promise, accept/accepted). Multi-Paxos keeps a stable leader to avoid phase one every time.
  • Raft: designed to be understandable; used by etcd, Consul, CockroachDB, TiKV. Three roles: follower, candidate, leader.

How Raft works

  1. Election: a follower that hears no heartbeat from a leader for a random timeout (about 150 to 300 ms) becomes a candidate, adds 1 to the term and asks for votes. A node votes once per term. A candidate with a majority becomes leader. Random timeouts avoid split votes.
  2. Replication: clients send writes to the leader. The leader appends to its log and sends the entry to followers. When a majority has stored it, the entry is committed, applied to the state machine and the client gets a reply.
  3. Safety rule: a candidate can only win if its log is at least as up to date as the majority's, so a committed entry is never lost by a new leader.
  4. Old leader returns: it sees a higher term and steps down. A leader cut off from the majority cannot commit anything.

Leader election and what consensus is used for

UseNotes
Leader election for a service or database shardExactly one leader per term; others follow.
Replicated metadata and configurationetcd, ZooKeeper, Consul. Small, important data.
Replicated log for databasesCockroachDB, TiDB, Spanner (Paxos groups per range).
Distributed locks and coordinationBuilt on the above (section 4).
Do not use consensus forWhy
Every bulk data write across the worldEach commit needs a majority round trip. Slow across regions, and throughput is limited by one leader per group.
Huge clusters (dozens of voters)More voters make every commit slower. Keep the voting group to 3, 5 or 7 and shard data across many groups.
Numbers: 3 nodes tolerate 1 failure, 5 tolerate 2, 7 tolerate 3. Commit latency is about one round trip to the nearest majority (about 1 to 2 ms in one region; tens to 100+ ms across continents). Typical Raft election timeout 150 to 300 ms. Use an odd number of nodes: 4 tolerates no more than 3 does.
Traps: an even-sized cluster (no gain); placing all nodes in one zone (a zone outage kills the quorum); thinking Raft handles malicious nodes (it does not; that needs Byzantine fault tolerance, e.g. PBFT, blockchains).
Say: "I would not build consensus myself. I would use etcd or ZooKeeper for leader election and config, keep the voter group at 3 or 5 across zones, and shard the data so no single Raft group is the bottleneck."

4. Coordination and distributed locks Ch 30

One line: a lock across machines must expire (lease) because holders die, and because a paused holder can wake up after expiry, the protected resource must also check a fencing token.
  • Why locks: make sure only one worker runs a job, or one process updates a resource at a time. First ask if you can avoid the lock: use a single-writer partition, an atomic conditional update (compare-and-set), or an idempotent operation.
  • Lease: the lock auto-expires after a TTL (say 10 seconds), and the holder must renew. If the holder dies, the lock frees itself.
  • The danger: the holder pauses (garbage collection, slow disk, VM freeze) longer than the lease. The lock expires, another process takes it, then the first one wakes up still thinking it holds the lock. Now two processes write.
  • Fix: fencing tokens. The lock service gives an increasing number with each grant (33, then 34). Every write to the storage carries the token. The storage remembers the highest token seen and rejects anything lower. The late process (token 33) is rejected after 34 has written.

Ways to build a lock

OptionHowUse whenWatch out
Database row or conditional updateUPDATE ... WHERE owner IS NULL, or a version column (optimistic lock).You already have a DB; low rate.No automatic expiry unless you add it; DB load.
Redis SET NX PXSet a key with random value and TTL; release with a compare-and-delete script.Efficiency lock: duplicate work is only wasteful.Async replica failover can grant the lock twice; no fencing token by itself.
ZooKeeper / etcdConsensus-backed. ZooKeeper uses ephemeral sequential znodes; etcd uses leases and revision numbers.Correctness lock, leader election, config.More to run; session timeouts; still needs fencing in the resource.
Redlock (multi-Redis)Take the lock on a majority of independent Redis nodes.Debated: relies on timing assumptions.Not safe for correctness without fencing. Prefer a consensus system.

Related coordination tools

  • Leader election: one lock holder is the leader (a cron-like job runs only on the leader).
  • Service discovery and config: store addresses and flags in etcd or ZooKeeper; watches push changes.
  • Barriers and queues: "wait until all workers are ready"; ordered work queues using sequential nodes.
  • Optimistic concurrency: read a version, write only if the version is unchanged. No lock held; retry on conflict. Best when conflicts are rare.
Numbers: lease TTL typically 5 to 30 s with renewal at about one third of the TTL; ZooKeeper session timeout about 10 to 30 s; a long GC pause can last seconds; consensus-backed lock acquire about a few ms to tens of ms.
Traps: lock with no expiry (a crash blocks everyone forever); releasing a lock you no longer own (always compare the owner value before deleting); assuming a lock alone guarantees safety without fencing; holding a lock across a slow network call.
Say: "For just avoiding duplicate work I use a Redis lease. For correctness I use etcd or ZooKeeper, a lease with renewal, and a fencing token checked by the storage. And first I try to remove the lock with a conditional write." See the lock service case sheet.

5. Distributed transactions: 2PC, Saga, outbox Ch 31

One line: a business action that touches several services cannot use one database transaction, so choose 2PC (all-or-nothing, can block) or sagas (steps with undo, eventually consistent), and make every step idempotent.

Two-phase commit

  1. Prepare: the coordinator asks every participant "can you commit?" Each does the work, writes it durably and locks the rows, then votes yes or no.
  2. Commit or abort: if all said yes, the coordinator logs "commit" and tells everyone; otherwise it tells everyone to abort.
  3. The problem: if the coordinator dies after the participants voted yes, they must wait, holding locks, until it returns. 2PC is a blocking protocol. It is also slow (two round trips plus disk writes) and couples services to each other's availability.
  4. Three-phase commit reduces blocking on paper but is rarely used. Systems like Spanner run 2PC across Paxos groups, so the coordinator itself is replicated and does not die alone.

Saga

Split the action into local transactions, one per service. Each has a compensating action (undo). If step 3 fails, run the compensations for steps 2 and 1 in reverse. Example: book flight, book hotel, charge card. If charging fails, cancel the hotel, cancel the flight. Between steps other users can see the half-done state, so sagas give no isolation; design with "pending" states and semantic locks (for example a "reserved" status).

Saga styleHowProCon
OrchestrationA central coordinator tells each service what to do next and tracks state.Easy to see and debug; clear flow.The orchestrator is another service to run; risk of too much logic in it.

Outbox and inbox (reliable events)

  • The dual-write problem: "save to DB, then publish to Kafka" can fail between the two, leaving them out of sync. There is no atomic way across a DB and a broker.
  • Outbox: in one DB transaction, write the business row and an "outbox" row. A relay (a poller or CDC reading the log) publishes outbox rows to the broker and marks them sent. Delivery is at least once, so consumers must be idempotent.
  • Inbox / dedupe table: the consumer records the message ID it has processed in the same transaction as its own effect, so a duplicate is skipped.
  • "Exactly once" in practice = at-least-once delivery + idempotent processing.
Numbers: 2PC = 2 round trips plus 2 log forces; lock hold time is at least the coordinator round trip (ms in one DC). Saga with k steps needs up to k compensations. Outbox relay lag typically tens to hundreds of ms.
Traps: compensations that can fail with no retry plan; a compensation that is not idempotent; forgetting that "undo" is business logic (an email cannot be unsent; you send an apology); using 2PC across services you do not own.
Say: "Across services I use an orchestrated saga with an outbox for reliable events and idempotent steps. 2PC only inside one trust zone with few participants, such as sharded SQL."

6. Idempotency and unique IDs Ch 32

One line: networks make duplicates certain, so give every operation an ID that lets the server recognise a repeat, and give every record an ID that needs no central bottleneck.

Idempotency

  • Naturally idempotent: set x = 5, PUT, DELETE. Not: add 5 to x, POST create, send email, charge card.
  • Idempotency key pattern: the client generates a unique key (a UUID) for one logical action and sends it in a header on every retry. The server stores key to result (with a TTL, often 24 hours). First arrival: do the work, save the result. A repeat: return the saved result and do nothing.
  • Races: two copies of the same request arrive at once. Use an atomic insert of the key (unique constraint) or a lock; the second request waits or gets "in progress".
  • Same key, different body: reject it as an error (the client has a bug).
  • Where to keep it: in the same DB transaction as the effect where possible, so key and effect commit or fail together. A Redis-only key can be lost or set without the effect.
  • Retries: use exponential backoff with jitter, a retry limit and a retry budget to avoid a retry storm.
Delivery guaranteeMeaningEffect
At most onceSend and never retryCan lose messages
At least onceRetry until acknowledgedDuplicates; need idempotent consumers
Exactly once (effect)At least once + dedupeWhat real systems offer

Traps: using random UUIDs as a clustered primary key at high write rate (index fragmentation); Snowflake clock going backwards; two machines given the same machine ID; exposing sequential IDs in public URLs (guessable); storing the idempotency key without the request hash.
Say: "Clients send an idempotency key; I store key to result in the same transaction as the effect with a TTL. For IDs I use Snowflake style: timestamp, machine ID, sequence. They are compact and sortable with no central call."

7. Gossip and Merkle trees Ch 33

One line: gossip spreads membership and state to a big cluster with no central node; Merkle trees let two replicas find exactly which data differs by comparing hashes, not all the data.

Gossip

  • How: every second (or so) each node picks a few random peers and exchanges what it knows (who is alive, versions, load). Information spreads like a rumour: the number of nodes that know roughly doubles each round, so it reaches all N nodes in about log N rounds.
  • Used for: cluster membership and failure detection (Cassandra, Consul/Serf, Dynamo), sharing config and metadata, spreading aggregates.
  • Good: no single point of failure, scales to thousands, tolerates node loss and lost messages.
  • Bad: only eventually consistent; extra background traffic; slow to agree during big changes; a bad actor can spread false info.
  • Styles: push (tell others), pull (ask others), push-pull (both; fastest to converge). SWIM: gossip failure detector with indirect probes (ask a few others to ping a suspect before declaring it dead).

Merkle trees (anti-entropy)

Hash each small chunk of data (a leaf). Hash pairs of hashes to make the parent, and so on up to one root hash. Two replicas compare roots. If equal, their data is the same, one comparison for millions of rows. If different, compare the two children, and keep going down only the branches that differ. At the bottom you find the few chunks to copy. This is anti-entropy repair in Cassandra and Dynamo, and the same idea appears in Git and blockchains.

ToolSolvesCost
Read repairFix stale copies when a read finds a mismatch.Only repairs data that is read.
Hinted handoffStore writes for a down node and deliver later.Hints can pile up or be lost; limited time.
Merkle anti-entropyBackground fix of all rarely read data.CPU and disk to build trees; run on a schedule.
Numbers: gossip fan-out about 2 to 3 peers per round, once per second; a 1,000-node cluster converges in about 10 to 15 rounds (a few seconds to tens of seconds); a tree over 1 million chunks has about 20 levels.
Trap: thinking gossip gives strong consistency or quick failure removal. It gives eventual agreement and suspicion, so use consensus when you need exact agreement (leader, config).
Say: "Membership and failure detection use gossip with SWIM-style indirect probes. Replicas heal with read repair and hinted handoff, and a background Merkle-tree compare catches the rest."

8. Say-aloud script (45 seconds in an interview)

  1. "In a cluster, I cannot tell a slow node from a dead one, and clocks disagree, so I do not order by wall-clock time. I use sequence numbers, version vectors or a log."
  2. "If the network splits I must pick: payments, inventory and locks are CP; carts, feeds and counters are AP with eventual consistency and read-your-writes."
  3. "For leader election and config I use a consensus system like etcd or ZooKeeper with 3 or 5 voters across zones, and I do not put bulk data through it."
  4. "Locks are leases with a fencing token checked by the storage, because a paused process can wake up after the lock expired."
  5. "Across services I use a saga with compensations and an outbox, not 2PC. Delivery is at least once and every handler is idempotent with an idempotency key."
  6. "IDs come from a Snowflake-style generator: timestamp, machine ID and sequence. Replicas stay in step through gossip, read repair and Merkle-tree comparison."

9. Interview Q&A (detailed answers)

Click a question to open the answer. Grouped as: concepts, design scenarios, failure and real-time (production) situations, and trade-off or "why" questions.

A. Concept questions

1. Why is a distributed system harder than a single machine?

On one machine, a program either works or crashes, memory is shared, and there is one clock. In a cluster, parts fail independently (partial failure), the network can lose, delay, duplicate or reorder messages, and every machine has its own memory and its own clock. You can never be sure whether a silent peer is dead, slow, or just unreachable. That means every remote call needs a timeout, every retry must be safe, and every ordering assumption needs a logical rather than physical clock. Most interview answers on this topic come back to this: design so that a wrong guess about failure does not corrupt data.

2. What is a network partition and how is it different from a node crash?

In a crash, one machine stops. In a partition, the machines are all running but the network splits them into groups that cannot talk. Each group may think the others died. If both groups keep accepting writes, you get split brain, which means conflicting data. The standard defence is a majority quorum: only the group with more than half of the nodes may continue, so at most one side makes progress. The minority side waits or rejects requests until the network heals.

3. Explain the CAP theorem correctly.

CAP says that when a partition happens, a replicated system must choose between consistency (every read sees the latest write, meaning linearizable) and availability (every non-failed node answers). Partitions cannot be avoided, so the real choice is CP or AP, and it only applies during the partition. CP systems such as ZooKeeper and etcd refuse requests on the minority side. AP systems such as Cassandra and DynamoDB keep answering and repair later. A better framing is PACELC: when there is no partition, you still trade latency against consistency, for example by waiting for more replicas before replying. I also note that the C in CAP is not the C in ACID.

4. What is the difference between linearizable, causal and eventual consistency?

Linearizable means the system behaves as if there is one copy, and once a write is visible to anyone it is visible to all later reads; this needs coordination and is slowest. Causal means that if one event could have caused another, everyone sees them in that order, but unrelated events may appear in different orders on different nodes; it can stay available during partitions. Eventual means copies will agree after writes stop, with no promise about what you read in between. A useful middle ground for users is read-your-writes plus monotonic reads, which stops the user from seeing their own change vanish or time go backwards. I pick the weakest model the product can accept because it is faster and more available.

5. What does W + R > N mean?

With N replicas, a write waits for W acknowledgements and a read asks R replicas. When W + R is greater than N, the set of replicas read must overlap with the set that took the latest write, so at least one answer is fresh, and the newest version (by version number) wins. For N=3, W=2 and R=2 works and tolerates one failed node. W=1,R=1 is fast but can return stale data. W=3 makes writes fail when any node is down. It is not a full guarantee of linearizability, because of concurrent writes, partial failed writes and sloppy quorums, so systems add read repair and version metadata.

6. What is the problem with using timestamps to order events?

Machine clocks drift and differ, NTP corrections can make a clock jump backward, and two events can share the same millisecond. So an event that happened later in real life can get an earlier timestamp. With last-write-wins this silently deletes a newer write. Safer approaches are Lamport clocks (a counter that respects cause and effect), vector clocks (also detect concurrent conflicts), a single leader assigning sequence numbers, or a consensus log. If you truly need real-time order, bounded-uncertainty clocks like Google TrueTime plus waiting out the uncertainty do it, but they need special hardware.

7. Lamport clocks vs vector clocks?

A Lamport clock is one number per machine: increment on each event, and on receiving a message set it to max(local, received) + 1. It guarantees that if A happened before B, A has the smaller number, but it cannot tell you that two events were concurrent. A vector clock keeps one counter per machine, and comparing two vectors tells you whether one event came before the other or whether they are concurrent. Vector clocks are what you use to detect conflicts (Dynamo style), but they grow with the number of writers, so systems prune them or use version vectors per key.

8. What problem does consensus solve, and what is Raft in short?

Consensus lets machines agree on one value or one ordered log even if some of them crash, for example "who is the leader" or "what is the next entry". Raft does it with a single leader per term. A follower that stops hearing the leader becomes a candidate and asks for votes. The one with a majority leads. The leader appends client commands to its log and sends them to followers. When a majority has stored an entry it is committed and applied. Because any two majorities overlap and a candidate needs an up-to-date log to win, committed entries are never lost. With 2f+1 nodes you tolerate f failures.

9. What is a fencing token and why do leases need it?

A lease expires after a set time so a dead holder cannot block everyone. But a holder that is only paused (garbage collection, VM freeze) can wake up after the lease expired and still believe it owns the lock, while a new holder is already working. A fencing token is an increasing number issued with every grant. The protected storage keeps the highest token it has seen and rejects lower ones. The old holder's late write carries a smaller token and is refused. The lock service alone cannot make this safe; the check must be at the resource.

10. Explain two-phase commit and its weakness.

In phase one the coordinator asks all participants to prepare: each does the work, writes it durably, keeps locks and votes. In phase two, if all voted yes the coordinator records the commit decision and tells everyone to commit; any no or timeout means abort. The weakness is blocking: if the coordinator crashes after participants voted yes, they cannot decide alone and must hold their locks until it recovers. It is also slow because of two round trips and disk writes, and it makes every service depend on all the others being up. It is acceptable inside one database cluster (sharded SQL), and poor across independent microservices.

11. What is a saga and what are compensating actions?

A saga breaks a business flow into local transactions in each service. Every step has a compensating action that semantically undoes it. If a later step fails, the saga runs the compensations of the earlier steps in reverse order. For example reserve stock, create order, charge card: a card failure cancels the order and releases the stock. Sagas give eventual consistency but not isolation, so other readers can see the in-between state, and you design for it with statuses like "pending". Steps and compensations must be idempotent and retryable, because they will be repeated.

12. What is the idempotency key pattern?

The client creates a unique key (a UUID) for one logical operation and sends it with every attempt. The server records key to response. On the first request it performs the work and stores the result; on a repeat it returns the stored result without doing the work again. The key is stored with a TTL, typically a day. If the same key arrives with a different payload, the server rejects it. If two copies arrive at once, a unique constraint or lock makes one wait. This turns at-least-once delivery into an exactly-once effect, which is how payment APIs avoid double charges.

13. What is a Merkle tree used for in distributed databases?

Each replica hashes its data into leaves and builds a tree of hashes up to a single root. Two replicas compare roots, and if they match, all data is identical, found with one small message. If they differ, they compare children and descend only into the branches that differ, until they find the few differing chunks to copy. This is anti-entropy repair in Cassandra and Dynamo. It avoids transferring or scanning the whole dataset, at the cost of CPU and disk to build the trees. Git and blockchains use the same idea for integrity.

B. Design scenarios

14. Design a distributed lock service. What must it guarantee?

Core promise: at most one holder at a time per lock name, and a crashed holder does not block forever. I would run a small consensus cluster (3 or 5 nodes, etcd or ZooKeeper style) so lock state survives a node failure. Locks are leases with a TTL that the holder renews with heartbeats. Each grant returns a monotonically increasing fencing token that the resource checks. Clients get a watch or a queue for waiting, to avoid hammering. I would also expose "try-lock with timeout" and release only by the owner. The honest note is that the lock cannot stop a paused client, so the fencing check at the storage is part of the design. See the lock service case sheet.

15. Design unique ID generation for a system with 100,000 writes per second across regions.

I would use a Snowflake style 64-bit ID: 41 bits of millisecond time from a custom epoch, 10 bits of machine ID, 12 bits of sequence. That gives 4,096 IDs per millisecond per machine, so even a few machines cover 100k per second, and IDs sort roughly by time so database inserts stay append-friendly. Machine IDs come from a small coordination service (etcd or ZooKeeper) at startup, or are assigned by configuration. I protect against clock moving backward by refusing to issue (or waiting) until the clock passes the last timestamp. If ordering is not needed, UUID v7 is a simpler option at 128 bits. For global strict ordering I would not promise it, because it needs a central sequencer.

16. Design a payment endpoint so a customer is never charged twice.

The client sends an idempotency key generated once per checkout attempt. The server, in one database transaction, inserts the key with a unique constraint and the payment record with state "pending". A duplicate request hits the constraint and returns the saved result or "in progress". The call to the card processor also carries the same key, so the provider dedupes too. The result is saved with the key, and an outbox row is written in the same transaction to publish "payment completed". A reconciliation job compares our records with the processor's, to catch unknown outcomes after a timeout. Retries from the client use backoff with jitter.

17. How would you coordinate an order flow across inventory, payment and shipping services?

I would use an orchestrated saga. An order service holds the saga state: reserve stock, authorize payment, create shipment. Each service makes a local transaction and publishes the outcome through an outbox so no event is lost. If payment fails, the orchestrator sends cancel commands to release stock. Every command carries the order ID as an idempotency key, and each handler dedupes using an inbox table. Orders show states like PENDING, CONFIRMED, FAILED so users and other services never read half-done work as final. I choose orchestration over choreography because the flow is easy to see, monitor and test.

18. You need a leader for a nightly job running across 10 instances. How?

Use leader election through a lease in etcd, ZooKeeper or even a database row with a conditional update and an expiry. All instances try to take the lease; one wins and runs the job; the others retry. The leader renews the lease while working. If it dies, the lease expires and another takes over, so the job must be restartable or idempotent (checkpointed). If the job writes to a shared store, pass the fencing token so a stale leader cannot write. If duplicate runs are merely wasteful, a simple Redis lease is enough.

19. How do you choose consistency per feature in one product, such as a social network?

Split by the cost of being wrong. Likes, view counts and feed ordering can be eventual and AP, since a few seconds of lag is fine. A user's own posts and profile edits need read-your-writes, which is cheap with sticky routing or a version token. Follow and block actions need stronger guarantees, because a stale block list is a privacy problem, so read those from the primary or a quorum. Money, such as ad budgets or purchases, is CP with transactions. Stating the staleness bound for each feature is what interviewers want to hear.

20. How would you keep three data centres in agreement about cluster membership?

Use gossip with SWIM-style failure detection: every node regularly pings a few random peers, asks others to probe a suspect indirectly before suspecting it, and spreads membership changes on those messages. Everyone converges in about log N rounds with no central node. For decisions that must be exact (who owns which shard, cluster config changes), keep a small consensus group (etcd) as the source of truth and let gossip carry only soft state like liveness and load. Mixing the two avoids both the single point of failure and the inconsistency risk.

C. Failures and real-time production scenarios

21. Two nodes both think they are the leader and the data is corrupted. What happened and what do you do?

This is split brain. Likely causes: a network partition with a leader election that did not need a majority, a leader that paused and kept acting after a new one was elected, or failover scripts that promoted a replica while the old primary was still alive. Immediate action: stop writes to one side (fence the old leader by cutting its network or storage access), decide which side's data is the truth, and reconcile the diverged writes from logs. The long-term fix is majority-quorum election, terms or epochs on every write so stale leaders are rejected, fencing tokens at the storage, and automatic step-down when a leader cannot reach a majority.

22. A client timed out on a payment request. Do you retry? How do you know if it was charged?

A timeout does not tell you the outcome: the request may never have arrived, or the charge may have happened and only the reply was lost. The safe action is to retry with the same idempotency key, so the server returns the first result if it already processed it. If the API has no key, query the status by a client-generated reference before retrying. Never create a new charge with a new reference. For an unknown final outcome, mark the payment "pending reconciliation" and let a job compare with the processor's records.

23. After a deploy, you see duplicate orders in the database. How do you investigate?

First find out whether duplicates have the same business key. Check if the client retries without a stable idempotency key (for example a key regenerated on each retry), if the consumer processes at-least-once messages without dedupe (a rebalance in Kafka replays messages), or if the service writes the DB and then publishes, and a retry re-runs both. Look at logs by request ID and message offset. Fix with a unique constraint on the idempotency key or business key, an inbox table for consumers, and idempotent handlers. Clean up the duplicates with a script that keeps the earliest and compensates the rest.

24. A lock-holding worker was paused by a long GC and two workers wrote the same record. How do you prevent it?

The lease expired during the pause and the lock moved on. Fix at the resource: have the lock service issue a fencing token and make the database or storage accept a write only if the token is greater than or equal to the last seen. Also shorten pauses (tune GC), renew the lease at about a third of its TTL, make the worker check that its lease is still valid right before the write (helpful but not sufficient, because a pause can occur after the check), and make the operation idempotent or use compare-and-set on a version column, which removes the need for the lock altogether.

25. The Raft leader is alive but slow and keeps being replaced. What do you check?

This is flapping elections. Look for election timeouts that are too short compared with real network latency or disk fsync times, because heartbeats arrive late and followers start elections. Check disk latency on the leader (Raft must fsync the log before acknowledging; slow disks are the usual cause in etcd), CPU starvation, long GC pauses, noisy neighbours and cross-zone network jitter. Fixes: faster disks (SSD, dedicated), raise the election timeout and heartbeat interval together, avoid overloading the cluster with large values or too many watches, and use a pre-vote feature so a node that is merely partitioned does not disrupt a healthy leader.

26. Your saga's compensation step itself fails. What now?

Compensations must be retried until they succeed, so they are idempotent and driven by a durable state (the orchestrator stores "compensating step 2, attempt 5"). Use retries with backoff and a dead-letter queue and alert for humans when attempts exceed a limit. Design compensations that cannot logically fail, for example "mark order cancelled" rather than "delete", and use "pending" states so nothing is exposed as final. For things that cannot be undone, such as an email sent, the compensation is a follow-up action like an apology message. Track stuck sagas with a dashboard on age and state.

27. A node's clock jumped back 30 seconds after an NTP correction. What breaks?

Anything that assumes time never goes backward: last-write-wins would treat new writes as older and drop them; Snowflake IDs could repeat or fail; lease expiry and TTL checks using wall time could extend or fire early; log ordering and "created at" sorting go wrong. Defences: use monotonic clocks for durations and leases, make ID generators wait or refuse when the clock moves back, use NTP slewing (gradually adjust) rather than stepping, monitor clock offset, and prefer logical versions over timestamps for conflict resolution.

28. The consensus cluster loses two of its three nodes. What happens and how do you recover?

With 3 nodes a majority is 2, so with only 1 left there is no quorum: the cluster stops accepting writes (and usually reads that need linearizability) to protect correctness. The service that depends on it becomes unavailable for leader election and config changes, though data planes that already have leaders and cached config may continue for a while. Recovery: bring the failed nodes back (preferred, since their logs hold committed data). If they are lost permanently, perform a controlled disaster recovery from the last snapshot or force a new cluster from the surviving node, accepting that recent commits may be lost. Prevention: spread nodes across zones, use 5 nodes for critical systems, and take regular snapshots.

D. Trade-offs and why-questions

29. Why not just use 2PC everywhere for strong consistency?

Because it blocks and couples availability. If any participant or the coordinator is down at the wrong moment, the others hold locks and wait; the chance that all services are up is the product of their availabilities, which is lower than any single one. It also adds two round trips plus durable logging to every transaction, and it only works with participants that support it (XA), which excludes most message brokers and third-party APIs. I would use it within one database system, such as a sharded SQL database, where the coordinator is replicated, and use sagas between independent services.

30. Orchestration or choreography for sagas?

Orchestration puts the flow in one place: the orchestrator knows the steps, state and compensations, so the flow is easy to read, monitor and change, but it is a new component and can grow into a "god service". Choreography has services react to events with no central owner, which keeps coupling low for short flows of two or three steps, but the full flow is invisible, ordering and cycles are hard to reason about, and debugging is painful. For flows longer than three steps or with complex failure paths I choose orchestration; for simple fan-out notifications, choreography.

31. UUID, Snowflake, or database auto-increment for IDs?

Auto-increment is simple and compact but a single point of failure and a bottleneck when sharded, and it leaks business volume. UUID v4 needs no coordination, but is 16 bytes and random, which scatters inserts in B-tree indexes and hurts write performance; UUID v7 fixes the ordering. Snowflake gives 8-byte, roughly time-ordered IDs with no per-ID network call, but needs unique machine IDs and a reliable clock. For a sharded, high-write system I choose Snowflake or UUID v7. For a small single-database app I use auto-increment and keep it simple. If IDs are public, I avoid exposing guessable sequences.

32. Redis lock, ZooKeeper/etcd lock, or database lock?

It depends on what a double hold costs. If it only wastes work (a duplicate cache refresh), a Redis SET NX PX lease is fast and easy, but a failover on asynchronous replication can hand out the lock twice. If correctness matters, use a consensus-backed lock (etcd, ZooKeeper) with leases and fencing tokens, accepting more operations work and higher latency. A database row lock or conditional update fits when you already have the database and the rate is low, and it has the advantage that the lock and the data are in the same system, so you can make the update atomic and skip a separate lock. I also mention that Redlock is controversial and that a fencing token is what makes any of them safe.

33. Gossip or a central coordinator for cluster state?

A central coordinator (consensus group) gives an exact, agreed view and fits small, critical data like shard ownership, but every client depends on it, and it does not scale to thousands of nodes sending heartbeats. Gossip scales to very large clusters, has no single point of failure and tolerates message loss, but state is only eventually consistent and failure detection can be slow or produce temporary disagreement. Large systems combine them: gossip for membership and liveness, a small consensus store for the few facts that must be exact.

34. Why does Raft use random election timeouts, and why an odd number of nodes?

If all followers timed out at the same moment, they would all become candidates, split the votes and nobody would get a majority, repeating forever. Random timeouts (for example 150 to 300 ms) mean one candidate usually starts first and wins before the others begin. On odd numbers: the majority of 4 is 3, so 4 nodes tolerate only 1 failure, the same as 3 nodes, while costing more and committing slower. 5 nodes tolerate 2 failures. So you choose 3, 5 or 7.
