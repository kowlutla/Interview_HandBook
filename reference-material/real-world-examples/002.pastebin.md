# 002. Design Pastebin.com

## 1. Problem Statement & Requirements
### Functional Requirements:
- Users can upload plain text (paste) and get a unique URL.
- Users can view the paste via the URL.
- Optional expiration time for pastes.

### Non-Functional Requirements:
- Low latency for reading pastes.
- High reliability (data should not be lost).
- 10MB limit per paste.

## 2. Capacity Estimation
- 10 million daily active users (DAU), 1 write per user/day = 10M writes/day (~116 writes/sec).
- Read QPS = 10 * write QPS = 1,160 reads/sec.
- Storage: 10M pastes * 10KB avg size = 100 GB/day (~36 TB/year).

## 3. High-Level Architecture
- **Web Tier**: Nginx load balancers.
- **Application Tier**: Stateless REST API service.
- **Storage Tier**: Object Storage (S3) for paste contents (> 1KB) + Metadata Database (MySQL/DynamoDB).
- **Caching**: Redis for hot pastes.

## 4. Detailed Design
- **Metadata DB Schema**: `paste_id` (PK), `title`, `user_id`, `created_at`, `expiration_date`, `file_path_s3`.
- **URL Shortening**: Similar to URL shortener using Base62 encoding.
