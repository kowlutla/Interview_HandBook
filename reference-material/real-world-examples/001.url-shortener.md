# 001. Design a URL Shortener (TinyURL / Bit.ly)

## 1. Problem Statement & Requirements
### Functional Requirements:
- Given a URL, generate a shorter and unique alias (e.g., `https://tinyurl.com/y3t5nz`).
- When users click a short link, they are redirected to the original URL.
- Links should expire after a default or custom timespan.
- Users should be able to create custom short links (optional).

### Non-Functional Requirements:
- High availability (system must not go down; redirection must be instant).
- Low latency for redirection (< 10ms).
- Highly scalable to handle billions of URLs.
- Read-heavy system (read-to-write ratio ~ 100:1).

## 2. Capacity Estimation & Constraints
- **Traffic**: 100 million URL generations per month.
- **Write QPS**: 100M / (30 days * 86400 seconds) ≈ 40 URLs/sec.
- **Read QPS**: 40 * 100 = 4,000 requests/sec.
- **Storage**: 100M URLs * 5 years * 500 bytes per URL = 250 GB over 5 years.
- **Bandwidth**: 4,000 reads/sec * 500 bytes = 2 MB/sec read bandwidth.

## 3. High-Level Architecture
- **Client** -> **Load Balancer** -> **API Servers** -> **Distributed Key-Value Store / SQL DB**.
- **Caching Layer**: Redis in front of the database to cache hot URLs.

## 4. Detailed Design & Deep Dives
### Data Model (SQL / NoSQL)
- `id` (Primary Key), `long_url`, `short_key`, `created_at`, `expires_at`.
### Hash Generation
- Hash function (MD5/SHA256) on `long_url + timestamp` -> truncate to 6-7 characters using Base62 encoding (`[a-zA-Z0-9]`).
- Collision handling: Append counter or salt and rehash.
- Unique ID Generator (Twitter Snowflake) + Base62 conversion.

## 5. Trade-offs & Fault Tolerance
- **Cache Redirection**: Redis caching prevents database overload for trending links.
- **Database Scaling**: Sharding based on hash key range or consistent hashing.
